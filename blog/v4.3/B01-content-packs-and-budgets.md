# 内容包、资产预算与只读元数据：一次收口的三个边界

一个本地优先的桌面 AI 应用，功能长到一定阶段后，最难的不再是“再加一个能力”，而是决定哪些东西可以装进来、装进来之后占多大、以及界面应该展示什么。我们这一轮做的三件事——场景包、道具包与资产预算、平台元数据——表面看互不相干，实际都在回答同一个问题：系统的边界应该画在哪里。

## 一、内容生态不能靠“先放开再说”

早期做能力包时，重点是把安装、校验、启用、停用、升级和回滚跑通。管道有了，内容类型却只有少数几类。用户想加一段桌宠表演，只能等内置版本；想加一个桌面道具，只能改代码。

最直接的做法是允许包内执行脚本。但桌面应用和浏览器沙箱不同：包一旦能执行任意代码，安装校验、权限确认、崩溃隔离和回滚语义都会变成另一套复杂度。我们选择了更窄的路：内容包只能声明，不能执行。

场景包只允许现有的场景、节拍与动作原语；道具包只允许元数据加静态模型文件。它们复用同一套能力包清单、校验和与签名，不新建安装器。这个决定让内容生态慢一点，但把“装进来会做什么”限制在可枚举的动作里。

## 二、资产预算要能重复执行

第二个边界是体积。模型、贴图、表情数据和安装包本身都会随版本增长。只靠发版前目测，问题一定会在某个版本集中爆发。

我们把预算写成脚本：解析模型文件的 JSON 与二进制块，读取贴图尺寸，比较表情目标的有序签名，再统计安装包体积。输出不是一句“超标”，而是具体到哪个模型、哪张图、哪个表情序列。

预算分三层：

- 硬上限：超过就失败，例如单模型超过 25MB、安装包超过 300MB；
- 目标值：超过只警告，例如颜色贴图目标 2048、非 WebP 格式；
- 语义快照：表情数量与顺序变化必须显式更新快照，否则失败。

分层的意义在于，现有资产不会被历史问题卡死，但继续增长会被挡住。门禁只有在“能长期跑、结果稳定”的前提下才有价值。

## 三、元数据只读，执行不动

第三个边界是平台元数据。工具描述符过去有两套命名：执行侧叫 `parameters` 和 `permission`，调试台又叫另一套。字段不统一，展示和适配就会各自打补丁。这一轮把它们收敛成一组只读字段，内置工具、MCP 工具与流程工具共用同一层映射。

供应商能力也是类似的处理：只声明流式、工具调用、视觉与向量，不落库、不参与模型选择。它解决的是“设置页能不能把事实说清楚”，而不是“路由应该怎么选模型”。

只读元数据最重要的约束是：改完之后，工具调用、权限门与模型路由必须一行不变。做不到这一点，就不叫元数据统一，而叫行为变更。

## 四、三条边界共同的收益

把三件事放在一起看，收益不是代码量减少，而是系统更容易解释：

- 装进来的内容能做什么，由声明式契约决定；
- 内容能占多大，由可重复执行的预算决定；
- 界面展示什么，由只读元数据决定，不影响执行。

这三条都能单独写测试，也都能在发布说明里用一句话讲清。对一个单人维护的桌面应用来说，可解释性比“支持更多类型”更重要。

## 五、这一轮刻意没做什么

没有做在线内容目录，没有做内容包自动更新，没有做运行时代码插件，也没有做内容热替换。场景和道具在安装/停用后，要等下一次挂载或下一次触发才生效。

这些限制不是技术做不到，而是它们会把一次低风险的内容扩展，变成一次高风险的运行时重写。边界先守住，下一轮再谈扩展。

## 六、为什么把三件事放在同一版

场景包、道具包、资产预算与元数据，看起来可以拆成三个版本。放在一起做，是因为它们共享同一批验证路径：

- 场景包与道具包都依赖能力包的启用状态，内容快照的版本计算方式一致；
- 道具包把二进制资源带进能力包，体积预算与路径校验必须同时存在；
- 元数据统一不改变执行，但需要全量回归证明“没有行为变化”。

如果拆开，每一版都要重复一次安装、启用、停用与回归验证。合并之后，验证链路只跑一遍，发布说明也能用一组数字收口。

代价是单版范围偏大。控制方式是明确 P0/P1/P2：内容与资产是 P0，设备与元数据是 P1，音频全图是 P2 且不承诺。

## 七、可验证的收尾

发布前真正执行的命令只有几条：

```text
pnpm check        # typecheck / lint / 行数 / 结构 / 循环 / ASCII / 资产
pnpm test         # 9 个包的全量测试
pnpm release:win  # 构建并归档 Windows 安装包
pnpm release:verify
```

`check` 里的资产检查会输出三席体积、贴图警告与 morph 签名；测试输出包级文件数与用例数；归档脚本生成 SHA256SUMS 与 build-info。

发布说明里的每个数字都能在这三条命令的输出里找到对应行。这比“发版前人工确认”可靠，也让下一次收尾有固定模板。

## 八、边界之外

这一轮之后，内容系统仍然是一个本地 ZIP 安装器，没有在线目录，也没有自动更新。它支持两种新内容类型，但没有变成插件平台。

这不是终点，而是把“可安装内容”从少数内置类型扩展到一组可验证的声明式契约。下一步如果要支持更多资源类型，应该先问：它是否仍能用“声明 + 预算 + 快照”三件事描述。如果答案是否定的，就需要新的边界，而不是往现有契约里塞例外。

## 九、为什么没有做在线目录

内容包目前仍然只能从本地 ZIP 安装。不是技术上不能做在线目录，而是它会引入一整套新问题：来源信任、版本解析、网络失败、断点续传、更新提示、回滚策略。

这些问题每一个都合理，但加起来会吞掉一个版本。先把本地安装、内容快照与资产预算跑稳，再谈在线分发，是更稳的顺序。

本地 ZIP 还有一个好处：它迫使内容格式先稳定。在线目录会把格式问题放大成兼容问题，而本地安装允许我们在小范围内迭代契约。

## 十、一句话总结

这一轮做的不是“更多功能”，而是“让内容扩展有边界”：能装什么、能占多大、什么时候生效、界面展示什么，各自有明确答案。边界清晰之后，下一轮才有资格谈更快、更多、更自动。
