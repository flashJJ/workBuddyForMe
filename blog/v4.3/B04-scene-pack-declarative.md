# 场景包为什么只允许声明式 Scene

给桌宠加一段新表演，最自由的方式是让内容包执行代码：想做什么动作、放什么语音、什么时候触发，全写在脚本里。我们最终没有走这条路，而是把场景包限制成一组声明式数据。

原因不是技术上做不到，而是执行代码会把内容安装变成另一类问题。

## 一、可执行内容会改变信任模型

能力包已经有清单校验、校验和、签名、升级与回滚。这些机制假设包内是数据：安装时校验一次，运行时按已知类型读取。如果包内可以执行任意脚本，同一个签名就不再代表“这份数据可信”，而代表“这段代码可以在你的应用里运行”。

随之而来的是权限、沙箱、崩溃隔离、超时、资源上限与回滚语义。对一个本地优先的桌面应用来说，这是一整套新系统，不是一次内容扩展。

所以我们把场景包限定为：只能组合现有的场景、节拍与动作原语，不能携带代码。

## 二、契约先于实现

场景包的核心字段很窄：

- 包名与描述；
- 1 到 50 个场景；
- 每个场景有 id、触发键、优先级、冷却与节拍序列；
- 每个节拍只能使用现有的动作、表情、语音、等待等原语。

节拍必须按时间升序，场景不能为空。所有约束都在 schema 层完成，读取 payload 时就失败，而不是等到播放时才报错。

这条“先定契约”的顺序很重要：如果先写安装器再想字段，最后一定会为了兼容旧包留下可选分支，契约会越来越松。

## 三、命名空间用前缀，而不是运行时查重

场景 id 必须形如 `pack.<名字>`。内置场景使用 `touch.`、`moment.`、`ambient.`、`state.`、`pool.`、`gen.` 等前缀，插件场景因此与内置场景天然隔离。

前缀不是装饰。它让内核不需要知道内置场景列表，也能保证不会冲突；让调试面板可以按前缀分组；也让用户一眼能看出“这是装进来的场景”。

包内重复 id 在 schema 层拒绝。跨包重复 id 在聚合层拒绝：如果两个已启用包声明了同一个场景 id，内容快照直接报错，而不是后者覆盖前者。

## 四、跨包冲突为什么 fail-closed

覆盖看起来更友好，但会产生不确定行为：用户不知道最终生效的是哪个包，停用一个包后另一个包的行为又变了。

我们选择让冲突显式失败：接口返回校验错误，用户停用其中一个包即可恢复。代价是极端情况下内容快照不可用，但内置场景不受影响，桌宠仍能启动。

对内容系统来说，“明确失败”比“静默覆盖”更容易排查。

## 五、安装 effect 只做校验

场景包的启用 effect 很短：读取 payload、schema 校验、返回句柄。没有把场景写进数据库，也没有修改内置场景表。

原因在于内容快照是“按已启用能力行实时聚合”的。启用只是把能力行状态改为 enabled；下一次读取快照时，自然会包含这个包。停用同理。

这让安装、启用、停用、升级都复用同一条管道，不需要为场景包单独维护一份索引。

## 六、声明式的代价与收益

代价是表现力有限：不能根据运行时状态写分支，不能调用外部接口，不能动态生成台词。复杂玩法仍然要进内核。

收益是可预测：每个场景能做什么，从 payload 就能读完；校验失败会指出具体字段；回滚只需停用能力行；安全边界不依赖运行时沙箱。

对内容生态来说，先有可预测的扩展，再谈表现力，是更稳的顺序。

## 七、payload 示例

一个最小的场景包 payload 大致长这样：

```json
{
  "name": "示例场景包",
  "description": "抬手触发的一段问候",
  "scenes": [
    {
      "id": "pack.sample.greeting",
      "triggers": ["touch::raised::tap"],
      "priority": 1,
      "cooldownMs": 60000,
      "interrupt": "all",
      "beats": [
        { "at": 0, "cue": { "kind": "expression", "tag": "joy", "holdMs": 1200 } },
        { "at": 120, "cue": { "kind": "gesture", "gesture": "nod", "intensity": 0.8 } },
        { "at": 600, "cue": { "kind": "speak", "text": "场景包安装成功。" } },
        { "at": 2400, "cue": { "kind": "expression", "tag": "neutral", "holdMs": 800 } }
      ]
    }
  ]
}
```

字段都来自现有引擎：触发键、优先级、冷却、打断策略与节拍原语。包作者不需要学一套新 DSL。

## 八、与既有能力包管道的复用

场景包没有新建安装器，也没有新的签名格式。它复用：

- 清单文件与 kind / entry 约定；
- ZIP 校验和与签名策略；
- 安装落盘、启用、停用、升级与回滚；
- 健康检查与残留清理。

新增的只有 payload schema 与启用 effect。这样能力包的通用能力（依赖拓扑、升级保护、信任库）自动对场景包生效。

复用也意味着约束一致：entry 必须在 `payload/` 下，体积有上限，状态变更走同一条能力行。

## 九、什么时候不该用场景包

场景包适合“把现有动作组合成一段表演”。如果需求是：

- 根据运行时状态做复杂分支；
- 调用外部接口或读写文件；
- 动态生成台词并即时合成；
- 改变模型、骨骼或渲染管线；

那就不应该塞进场景包。这些属于内核能力，应该走代码与版本发布，而不是内容安装。

把不该声明式的东西强行声明式，最终会得到一个又长又难懂的 schema，以及一堆无法表达的需求。边界清晰，比覆盖一切更重要。
