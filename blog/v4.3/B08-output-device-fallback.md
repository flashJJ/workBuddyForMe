# 切换音频输出设备：偏好、回退与四个 sink

桌面应用里同时有音乐、剧场配乐、音效和语音。用户插上耳机后，希望所有声音一起切过去；拔掉耳机后，希望至少还有声音。

这一轮给音频导演加了输出设备偏好。看起来只是保存一个 deviceId，实际要处理三种能力、四个播放器和两类跨窗口同步。

## 一、偏好放在导演，执行放在 sink

音频导演在上一轮已经统一了静音、duck 与背景互斥。输出设备也放在同一层：导演保存 `outputDevice`，`null` 表示系统默认。

播放器仍然只做自己擅长的事。Sink 契约增加一个可选方法：

```ts
interface AudioSink {
  setGain(gain: number): void;
  setSuspended?(suspended: boolean): void;
  setOutputDevice?(deviceId: string | null): void;
}
```

可选意味着不支持 `setSinkId` 的播放器不需要改。导演在注册 sink 时立即下发当前偏好，切换时广播给所有 sink。

## 二、三种能力，两条路径

浏览器里有两类音频对象支持 `setSinkId`：

- `HTMLMediaElement`：音乐与剧场 BGM 使用；
- `AudioContext`：剧场音效与语音使用。

它们的调用方式相同，但生命周期不同。媒体元素通常已经存在，直接设置即可；AudioContext 往往是惰性创建的，设置设备时可能还没有上下文。

处理方式是让 sink 自己保存偏好，在上下文创建后补应用。语音播放器甚至在上下文创建前就收到设备切换，也不会丢失。

## 三、设备消失时回退默认

`setSinkId` 可能失败：设备被拔出、权限变化、系统拒绝。失败后如果直接放弃，用户会突然没有声音。

统一工具函数做两段尝试：

1. 先设置目标设备；
2. 失败后设置空字符串，回到系统默认。

返回值区分 `applied`、`fallback`、`unsupported`，但 UI 不需要显示错误。用户只感知到“还有声音”，而不是一个红色弹窗。

不支持 `setSinkId` 的环境返回 `unsupported`，同样静默。

## 四、枚举只在设置面板发生

设备列表需要权限与用户手势。如果在桌宠启动路径枚举，可能拿到空标签，还会拖慢启动。

因此枚举放在设置面板的 hook 里：面板挂载时读一次，监听 `devicechange` 刷新，用户点击“刷新设备”时再读一次。

没有 `mediaDevices` 或没有 `audiooutput` 时，面板显示“当前环境不支持”，播放仍使用系统默认。

## 五、跨窗口同步

桌面应用可能有主窗、桌宠窗和舞台窗。偏好存在本地存储里，设置页修改后，其他窗口需要跟随。

导演监听 `storage` 事件：键匹配时读取新值、广播给 sink、更新快照。这样用户在主窗切到耳机，桌宠窗的下一次播放也会走耳机。

本地存储写入失败（隐私模式、配额）时静默忽略，偏好只在当前会话生效。

## 六、四个 sink 的接入差异

- 音乐：媒体元素已经存在，直接调用 `setSinkId`；
- 剧场 BGM：元素可能尚未创建，保存偏好，创建后补应用；
- 剧场音效：AudioContext 惰性创建，创建时读取导演当前偏好；
- 语音：WebAudio 播放器保存偏好，上下文创建后补应用。

四个 sink 的 `setGain` 语义保持不变。语音的 `setGain` 仍然是空实现，因为已有行为是“背景静音不影响语音”，这一轮只增加设备路由，不改变静音策略。

## 七、结论

输出设备选择看起来是一个设置项，实际是“偏好 + 能力探测 + 失败回退 + 跨窗口同步”的组合。

把它放在导演层，而不是每个播放器各自实现，才能保证四个播放器的行为一致。回退策略则保证：无论设备发生什么，用户至少不会突然失去声音。

## 八、回退函数的形状

核心逻辑只有一个函数：

```ts
async function applySinkId(target, deviceId) {
  if (!target?.setSinkId) return 'unsupported';
  const id = deviceId?.trim() || '';
  try {
    await target.setSinkId(id);
    return 'applied';
  } catch {
    try {
      await target.setSinkId('');
      return 'fallback';
    } catch {
      return 'unsupported';
    }
  }
}
```

调用方通常不等待结果，只需要知道它不会抛错。测试则可以直接断言三种返回值。

## 九、跨窗口同步的细节

偏好写入本地存储后，其他窗口通过 `storage` 事件收到通知。事件只带键与新值，不带“为什么变”。

导演收到后：

- 归一化设备 id；
- 与当前值比较，相同则忽略；
- 更新内部状态；
- 广播给所有已注册 sink；
- 更新订阅快照。

如果本地存储不可用，写入失败被吞掉，当前窗口仍然生效，只是刷新后丢失。

## 十、为什么不给每条音轨独立设备

技术上可以做到每条音轨一个设备，但产品上没有这个需求。独立设备会带来更多状态组合：音乐在耳机、语音在扬声器时，静音与 duck 的语义会变得难以解释。

统一设备是更简单的默认值。未来如果确实需要，可以在导演层扩展成“音轨到设备的映射”，但那是另一个产品决策，不是这一轮的实现细节。

## 十一、真机验证要点

自动化测试覆盖了返回值与广播，但设备切换最终要在真机上验证：

- 插入耳机后，设置页能否看到新设备；
- 切换后音乐、剧场、语音是否一起走新设备；
- 拔出耳机后，是否回退默认且不报错；
- 刷新页面后，偏好是否保留。

这四条都通过，才算真正完成。
