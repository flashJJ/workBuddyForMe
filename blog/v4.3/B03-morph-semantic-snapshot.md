# morph 不能只看数量：用有序签名锁住表情

3D 角色的表情通常由 morph target 驱动。一个模型有 100 多个表情目标并不罕见，数量相同也不代表两个模型兼容：顺序变了、名字变了、少了一个，都会让按索引或按名字驱动的代码出现错位。

这一轮我们把表情兼容性做成快照，而不是靠“看起来一样”。

## 一、为什么数量不够

假设两个模型都有 118 个 morph target。第一个模型的第 30 个叫 `mouthSmile`，第二个模型的第 30 个可能叫 `eyeBlink`。如果代码按索引驱动，笑容会变成眨眼；如果代码按名字驱动，名字对不上时表情会静默失效。

更隐蔽的是顺序。名字集合完全相同，但顺序不同，某些按位置缓存的实现也会出错。只看数量，永远发现不了这些问题。

## 二、快照记录什么

快照为每个模型记录三件事：

1. morph 数量；
2. 按声明顺序拼接后的 target 名称 SHA256；
3. 骨骼数量。

数量负责快速发现增删，签名负责发现重排与重命名，骨骼数量负责发现骨架变化。三个字段都不大，但足以把“兼容”变成一个可比较的事实。

扫描时，如果模型不在快照里，直接失败；如果在，但数量、签名或骨骼数任一不同，也失败。要更新快照，必须显式执行写快照命令，再跑三席回归。

## 三、三席结果一致

当前三个内置模型的结果完全一致：118 个 morph、49 根骨骼、相同的签名。这不是巧合，而是它们来自同一套制作规范。

一致带来一个实际好处：表情驱动代码可以假设三席共享同一组目标名，不需要为每个模型维护映射表。快照把这个假设固定下来，任何新模型破坏它，门禁会先发现。

## 四、快照更新的正确姿势

快照不是“自动跟随”，而是“显式确认”。流程是：

- 模型改动后先跑扫描，看到差异；
- 确认差异是预期的，执行写快照；
- 重新扫描，确认通过；
- 跑三席回归，确认表情、动作与口型没有异常。

如果快照自动更新，它就失去了门禁意义；如果完全不更新，正常迭代又会被卡死。显式更新是两者之间的折中：它要求人做一次判断，但不会阻止合理变更。

## 五、语义指纹的通用做法

这套方法不限于 morph。任何“集合相同但顺序有意义”的数据，都可以用有序签名做指纹：

- 工具列表的顺序影响提示词缓存；
- 迁移脚本的顺序影响数据库结果；
- 场景节拍的顺序影响表演；
- 配置项的优先级顺序影响覆盖关系。

做法都一样：排序前先确认顺序是否有语义，有语义就直接按原顺序拼接，再取哈希；没有语义就先排序再哈希。前者发现重排，后者忽略重排。

## 六、结论

资产检查里最容易被忽略的不是体积，而是语义。体积变大只是慢一点，表情错位会让角色“看起来不对”，而且很难定位。

用一个几十字节的签名把这种问题锁住，是这一轮性价比最高的检查之一。

## 七、快照文件长什么样

快照本身是一个普通 JSON，按模型名索引：

```json
{
  "xuetuan": {
    "morphCount": 118,
    "boneCount": 49,
    "signature": "405347bd…40966dce"
  }
}
```

扫描时做三件事：

1. 读取模型的 morph target 名称，按声明顺序拼接；
2. 取 SHA256，与快照中的签名比较；
3. 比较 morph 数量与骨骼数量。

任何一个不同，都输出具体模型与差异项。写快照命令只更新这个文件，不改模型、不改代码。

## 八、回归范围不只是表情

签名通过，只能说明 morph 集合兼容；还需要跑三席回归，确认：

- 表情切换仍然正常；
- 口型与语音电平没有错位；
- 待机动作与剧本动作没有因为骨骼变化而异常；
- 换装与热替换后表情仍然可用。

快照是静态检查，回归是动态检查。两者缺一不可：只有快照，可能漏掉权重或绑定问题；只有回归，可能漏掉低频分支。

## 九、什么时候应该更新快照

只有三种情况值得更新：

- 新增模型，且确认符合当前制作规范；
- 有意调整表情集合或顺序，并同步更新驱动代码；
- 骨骼结构变化，且回归通过。

如果只是“扫描失败但看起来没问题”，不要更新快照。先查清楚差异来源，再决定是修模型还是更新契约。

门禁的价值在于强迫这个判断发生，而不是让判断消失。
