# 工具描述符统一之后，执行链路一行没改

工具系统最容易出现两套真相：执行侧关心参数与权限，展示侧关心描述与来源。两边字段名一旦不同，适配代码就会越来越厚。

这一轮我们统一了工具描述符，同时明确了一条约束：执行链路一行不改。

## 一、旧结构的问题不是字段名

旧调试列表里，每个工具长这样：

```ts
{
  name,
  source,
  permission,
  description,
  parameters,
}
```

执行侧用 `permission` 判断是否需要确认，用 `parameters` 生成函数调用参数。展示侧也读这两个字段，但某些外部工具返回的是 `inputSchema`，需要临时映射。

问题不在于名字本身，而在于没有一份共同契约。内置工具、MCP 工具与流程工具各自拼对象，字段缺失时靠默认值兜底，久而久之就没人说得清哪些字段是必填的。

## 二、统一成一组只读字段

新描述符固定为：

- `name`：工具名；
- `description`：给模型和用户看的说明；
- `inputSchema`：函数调用参数 JSON Schema；
- `source`：builtin、mcp:<server> 或 flow；
- `permissions`：权限等级数组；
- `readOnly`：是否只读；
- `alwaysConfirm`：是否总是需要确认。

`permissions` 用数组而不是单值，是为了给未来多权限组合留空间；当前每个工具仍只有一个等级，适配层会把单值包成数组。

`readOnly` 不是从权限字符串猜的，而是在适配时明确计算：只有 read 权限的工具才是只读。

## 三、适配层只做映射

适配层有三个入口：

- 内置工具：读工具定义里的参数与权限；
- 流程工具：同样走内置映射，只是 source 固定为 flow；
- MCP 工具：读服务器返回的名称、描述与 inputSchema，权限固定为 read。

映射结果会用 schema 再校验一次。字段缺失、类型不对或权限值非法时，直接抛错，而不是把半成品下发给调试台。

这条“适配完再校验”的规则很重要：它保证所有消费方拿到的是同一种形状，不会出现某个来源悄悄少一个字段。

## 四、调试列表补上流程工具

执行侧早就支持流程工具，但调试列表之前只列内置与 MCP。统一描述符后，流程工具也进入列表，source 标为 flow。

这不是行为变更，只是展示更完整。用户可以像调试内置工具一样，看到流程工具的参数 schema 与权限。

## 五、provider 能力是另一层只读元数据

供应商侧也有类似问题：设置页需要告诉用户“这个协议支持什么”，但能力不应该参与路由。

我们按协议声明四个布尔值：流式、工具调用、视觉、向量。它们存在共享常量里，不落库，也不进入模型选择。

供应商卡片只增加一行只读徽章，并附一句说明：按协议声明，不代表每个模型都支持。

## 六、零行为变化怎么证明

约束是“执行链路一行不改”，验证方式是回归测试：

- 工具的构建、解析、权限门与熔断测试全部通过；
- 调试接口仍返回全部内置工具，字段断言更新为新契约；
- 供应商服务与路由测试不受影响；
- 全量测试数量与通过率保持稳定。

如果统一描述符导致某个工具无法执行，回归会立刻暴露。没有暴露，才说明改动停留在元数据层。

## 七、结论

元数据统一的价值，不是让代码更短，而是让“展示”和“执行”共享同一份事实。

共享的前提是只读：描述符可以告诉界面工具长什么样，但不能决定工具怎么执行。把这条边界守住，统一才是安全的。

## 八、描述符 schema

统一后的形状可以直接用一个 schema 表达：

```ts
interface ToolDescriptor {
  name: string;
  description: string;
  inputSchema: Record<string, unknown>;
  source: string;
  permissions: PermissionLevel[];
  readOnly: boolean;
  alwaysConfirm: boolean;
}
```

适配层产出对象后，再用同一份 schema 校验一次。这样“类型正确”和“运行时数据正确”是同一件事。

## 九、source 的设计

`source` 不是枚举，而是字符串。内置工具用 `builtin`，MCP 工具用 `mcp:<server>`，流程工具用 `flow`。

用字符串而不是枚举，是为了让 MCP 服务器名直接进入来源，不需要维护一张服务器白名单。代价是展示层需要按前缀分组，但这比新增一个来源就要改枚举更灵活。

## 十、 provider 元数据的展示边界

能力徽章只是事实展示：

- 流式：协议是否支持增量返回；
- 工具调用：协议是否支持函数调用；
- 视觉：协议是否支持图片输入；
- 向量：协议是否提供嵌入接口。

它不回答“这个模型能不能用”。模型是否支持，仍由模型自身的元数据决定。

## 十一、零行为变化的验收

验收不是“看起来没变”，而是：

- 工具构建与解析测试通过；
- 权限门与熔断测试通过；
- 调试接口字段断言更新；
- 供应商服务与路由测试通过；
- 全量测试数量与通过率稳定。

只有这五条同时成立，才能说统一描述符停留在元数据层。
