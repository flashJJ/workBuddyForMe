# 把场景包接进剧本引擎：快照、校验与触发索引

场景包安装之后，真正的问题是：它怎么进入正在运行的桌宠剧本引擎，又怎么保证停用后干净地消失。

这一轮我们没有把场景写进数据库，也没有在安装时直接修改引擎，而是走了一条“快照 + 注入”的链路。

## 一、内容快照只包含已启用包

服务端每次读取场景内容时，先查能力仓库里已启用的 `scene-pack` 行，再逐个读取包内 payload，最后合并成一个数组。

合并结果带一个版本号：没有包时是 `none`，有包时由排序后的 `id@version` 取哈希。版本号不参与播放，但可以用来判断“这次读取的内容有没有变化”。

安装和停用都不触碰快照本体，只改能力行状态。下一次请求自然读到新集合。这比“安装时写缓存、停用时清缓存”少一套失效逻辑。

## 二、接口只返回数据

内容接口返回 `{ version, scenes }`，不返回包元数据，也不返回文件路径。前端拿到场景数组即可。

前端用一个小 hook 在挂载时读取一次，失败时降级为空数组。场景包服务异常不会阻塞桌宠启动，内置场景仍然可用。

这里没有做轮询，也没有做实时推送。安装/停用后，用户下一次打开桌宠或刷新页面时生效。对内容包来说，这个延迟可以接受，换来的是更简单的生命周期。

## 三、注入点选在“校验之前”

剧本引擎原本已经支持额外场景：内置场景 + 生成场景，统一走一遍校验，再建立触发索引。

场景包最自然的接入点就在校验之前：

- 内置场景；
- 生成场景；
- 场景包场景；
- 三者合并后一起校验；
- 通过后建立 id 索引与触发键索引。

这样场景包不需要自己的调度器，也不需要绕过校验。非法节拍会在合并阶段被丢弃，并在开发环境打印原因。

## 四、触发与手动播放

进入触发索引后，包内场景和内置场景一样，能被真实交互触发。优先级、冷却与打断规则沿用原有引擎。

调试面板会列出全部场景，包括包内场景，因此即使没有真实触发条件，也可以手动播放验证。场景包里的示例场景同时提供了触发键，方便验证事件链路。

这里有一个有意的取舍：场景包场景进入触发索引和调试面板，但不进入“主动播放”的生成场景轮换。主动播放依赖生成场景的元数据，包内场景没有这些字段，混进去会让选择逻辑变得不确定。

## 五、停用后的清理

停用能力包后，能力行变为 disabled，下一次内容快照不再包含它的场景。

已经挂载的引擎不会热替换：当前会话继续使用旧场景集合，直到下一次挂载。如果场景正在播放，也不会被强制中断。

这是“内容快照不热替换”原则的一部分：安装/停用是内容边界，不是运行时命令。

## 六、跨包冲突的处理

如果两个已启用包声明同一个场景 id，聚合层直接报错。前端降级为空数组，内置场景仍然可用。

用户停用其中一个包后，下一次请求恢复。这个行为比静默覆盖更容易解释，也避免“到底哪个包生效”的长期困惑。

## 七、这条链路的通用性

同样的结构可以复用到其他内容类型：

- 服务端按已启用能力行聚合；
- 生成带版本的只读快照；
- 前端在挂载时读取；
- 通过既有校验后注入；
- 停用后下一次读取消失。

它不追求实时，但把“安装”“启用”“读取”“播放”四个阶段分得很清楚。对本地优先的桌面应用来说，这种清晰比实时更重要。

## 八、合并顺序与版本号

前端合并场景时顺序固定：

```text
内置场景
  → 生成场景
  → 场景包场景
  → validateScenes
  → 触发键索引
```

后合并的场景不会覆盖先合并的场景 id；如果出现重复，校验层会记录并丢弃非法项。场景包使用独立前缀，正常不会与内置或生成场景冲突。

服务端快照的版本号只由已启用包的 `id@version` 决定，不包含内置场景。内置场景随应用版本变化，不需要参与内容包版本计算。

## 九、失败与降级

这条链路上有三类失败：

- 内容接口失败：前端保留内置场景，包内场景为空；
- 单个场景非法：校验层丢弃该场景，其余场景继续注册；
- 跨包 id 冲突：聚合层报错，前端降级为空。

三类失败都不会阻止桌宠启动。包内容是可选的，内置体验必须始终可用。

调试面板会显示被丢弃的原因，但只在开发环境输出。生产环境不弹错误，避免内容包问题打断用户。

## 十、为什么不做实时刷新

安装/停用后不推送、不轮询，下一次挂载才生效。原因是场景引擎持有触发索引与正在播放的状态，实时替换会让“当前场景是否还在”“新场景是否抢占”变得难以解释。

内容快照的版本号已经具备判断变化的能力，未来如果需要实时刷新，可以在这层加通知。但现在没有必要。

对用户来说，安装完刷新一下页面或重新打开桌宠，是可以接受的成本；对系统来说，这避免了运行时热替换的一整类问题。
