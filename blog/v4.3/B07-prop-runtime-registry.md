# 运行时道具注册表：为什么用 getter 而不是重建 session

道具包的内容快照是异步加载的，而 3D 渲染控制器通常在内容到达之前就已经创建。两者之间的时序差，决定注册表应该怎么接。

我们最后用了一个很小的设计：控制器不持有注册表快照，只持有一个 getter。

## 一、先看时序

页面加载时大致发生这些事：

1. 渲染控制器创建，场景与模型开始初始化；
2. 前端请求道具内容；
3. 内容返回，合并内置道具与包内道具；
4. 用户触发某个场景，场景里的道具 cue 执行 attach。

如果控制器在创建时拷贝一份注册表，那么第 3 步到达的新道具它永远看不到。除非销毁控制器重建 session，但重建会打断模型加载、动作状态与正在播放的音频。

## 二、getter 让“读取时刻”后移

把注册表换成一个函数：

```ts
type PropRegistry = Readonly<Record<string, PropSpec>>;

new PropLayer(vrm, scene, prepare, loader, () => registryRef.current);
```

控制器在构造时只保存这个函数，不保存注册表内容。每次 attach 或 show 时再调用它，拿到最新注册表。

这样内容到达后不需要任何通知，也不需要重建 session。下一次 cue 执行时自然使用新表。

## 三、已经挂载的道具不热替换

getter 只影响“下一次 attach/show”。已经挂在角色手上或舞台上的模型不会被替换，也不会因为注册表变化而消失。

这是有意的：热替换一个正在显示的 3D 对象，会涉及资源释放、骨骼绑定与动画状态，风险远高于收益。用户停用道具包后，下一次场景触发时不再加载即可。

## 四、渲染层与校验层共用一张表

道具有两个消费方：

- 渲染层：根据 id 找到模型 URL 与几何参数；
- 剧本校验层：判断某个 `prop` cue 引用的 id 是否合法。

如果两边各自维护一张表，就会出现“校验通过但渲染找不到”或“渲染能加载但校验丢弃”的情况。

这一轮把同一份注册表同时传给渲染控制器、剧本适配器与校验函数。注册表由内置道具与已启用包合并而成，三处读取同一份数据。

## 五、资源 URL 由服务端生成

注册表里的每个包内道具都带一个 URL，指向只读资源接口：

```text
/api/prop-assets?pack=<能力包 id>&file=<payload 相对路径>
```

URL 在内容快照生成时拼好，前端不关心包目录结构。接口负责路径与声明校验，渲染层只把 URL 交给模型加载器。

这样渲染层不需要知道能力包安装在哪里，也不需要判断文件是否存在。它只消费“可加载的 URL”。

## 六、失败时的降级

内容接口失败时，前端保留内置道具，包内道具为空。角色仍能正常渲染，剧本里引用内置道具的场景不受影响。

单个道具加载失败时，渲染层返回 false，场景继续执行后续节拍，不会因为一个道具卡住整段表演。

## 七、这个模式的适用条件

任何“控制器早于异步内容创建”的场景，都可以考虑 getter 注入：

- 早于配置加载的渲染器；
- 早于权限加载的工具注册表；
- 早于主题加载的样式解析器。

前提是读取成本低、内容变化不要求立即重建。如果内容变化必须触发一次完整重排，那还是应该显式通知。

getter 不是万能解，但它把“内容到达”与“控制器生命周期”解耦了，这对本地优先、异步加载的桌面应用特别实用。

## 八、代码形状

渲染层的构造大致是这样：

```ts
const registryRef = useRef<PropRegistry>({ ...builtinProps });

useEffect(() => {
  registryRef.current = mergedProps;
}, [mergedProps]);

const controller = new VrmController(
  vrm,
  scene,
  prepare,
  motionContent,
  () => registryRef.current,
);
```

`mergedProps` 是内置道具与包内道具合并后的对象。控制器只保存 getter，不保存对象本身。

## 九、为什么不在 getter 里合并

也可以让 getter 每次现场合并内置与包内两张表，但那样每次 attach 都会创建新对象，引用不稳定，调试也困难。

最终选择在 hook 层合并一次，用 ref 持有结果。getter 只做一次属性读取，成本可以忽略。

## 十、测试怎么覆盖

这类设计不容易用纯函数测试，但可以分两层：

- 渲染层：注入一个只含包内道具的注册表，断言 attach/show 能找到并加载；
- 适配层：注入同一个注册表，断言 `prop` cue 能执行 attach，并在场景结束时清理。

两层都通过，说明“同一张表被三个消费方共享”这个假设成立。

## 十一、边界

getter 模式只解决“读取最新值”，不解决“内容变化需要立即生效”。如果产品要求停用道具包后立刻从角色手上消失，就需要额外的通知与卸载逻辑。

我们选择不做，因为即时卸载涉及资源释放与动画中断，风险高于收益。把生效点放在下一次 cue，是更稳的边界。
