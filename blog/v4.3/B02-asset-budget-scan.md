# 给 3D 资产做预算：从人工目测到 25MB 门禁

桌面宠物类应用最容易失控的资产不是代码，而是模型、贴图和表情。一个 VRM 模型动辄十几 MB，贴图从 1K 到 4K 不等，表情目标可能有上百个。每次加模型都“看起来还好”，几个版本之后安装包就会悄悄涨上去。

这一轮我们把资产体积从“发版前看一眼”变成了可重复执行的检查。

## 一、先明确检查什么

检查项不能只看文件大小。一个模型体积正常，不代表它的贴图分辨率合理；贴图合理，也不代表表情顺序没被改过。我们最终检查四类：

1. 模型文件体积：单文件与三席合计；
2. 贴图：数量、最大边长、MIME 格式；
3. 表情：morph 数量、有序目标名签名、骨骼数；
4. 安装包：归档目录里的最新安装器体积。

前两类是体积与性能问题，第三类是语义问题，第四类是交付问题。它们必须一起看，否则会出现“模型没超，但安装包超了”的情况。

## 二、不引入渲染引擎也能读模型

检查脚本没有加载 three.js，也不需要真的渲染。GLB 是容器格式：头部之后是 JSON 块与二进制块。我们只做三件事：

- 解析头部，拿到 JSON 块；
- 从 JSON 里读取 meshes、materials、images、extensions 与 skins；
- 需要图片尺寸时，从二进制块按 image 的 bufferView 取出字节，读 PNG/JPEG/WebP 的文件头。

这样脚本可以在 Node 里直接跑，不需要 DOM、WebGL 或 GPU。代价是要自己处理少量格式细节，收益是检查足够快，也不会因为渲染环境不同产生偏差。

## 三、贴图尺寸要区分“颜色”和“数据”

同样是 4K，颜色贴图和法线/ORM 贴图的成本不一样。颜色贴图直接影响观感，可以放宽；法线与数据贴图通常不需要那么高。

预算因此写成：

- 硬上限统一 4096，超过直接失败；
- 颜色贴图目标 2048，超过只警告；
- 数据贴图目标 1024，超过只警告；
- 允许 WebP/PNG/JPEG，但优先 WebP，非 WebP 只警告。

这就是“硬上限 + 目标值 + 警告”的三层结构。现有资产里确实有 4096 颜色贴图和 PNG，如果一刀切失败，门禁第一天就会被绕过；如果完全不报，又挡不住继续增长。警告层是给维护者的信号，不是给发布流程的阻断。

## 四、结果要具体到资产

第一版脚本只输出“有 N 项超标”。这种输出没法行动。后来改成每条都带上下文：

- 哪个模型；
- 哪张贴图、多大、什么格式；
- 哪个表情数量或签名不一致；
- 哪个安装包、多少 MB、和上一版差多少。

最终扫描结果：三席合计 22.29MB，预算 25MB；三个模型分别是 9.28MB、7.01MB、6.00MB。警告 13 条，其中 3 张 4096 颜色贴图超过目标，10 张 PNG/JPEG 未使用 WebP。没有硬失败项。

这些数字本身不重要，重要的是下一次改资产时，脚本会立刻告诉我们是哪一项变了。

## 五、安装包检查要允许“干净检出”

安装包不在仓库里，通常归档在构建机的目录。脚本默认读取归档目录，目录不存在时跳过，而不是失败。这样在干净检出、没有构建产物的机器上，`pnpm check` 仍然可以跑。

一旦目录存在，就读取最新版本与上一版本的安装器体积，输出对比。发布说明里的“较上一版增加/减少多少”由此而来，不再手工记录。

## 六、门禁的价值在可重复

资产预算不是一次性的审计，而是每次提交都能跑的门禁。它不需要 CI，也不需要 GPU；一条命令、几秒钟，就能回答“这次改动有没有让资产变胖”。

对单人维护的项目来说，这一点尤其重要：记忆会失效，脚本不会。

## 七、脚本结构

检查脚本本身不复杂，分成四层：

```text
GLB 解析       读取头部、JSON 块与二进制块
贴图尺寸       从 bufferView 取图片字节，读 PNG/JPEG/WebP 头
预算判定       硬上限 / 目标值 / 语义快照
报告输出       文本摘要 + JSON 明细
```

解析层不依赖渲染引擎；判定层只接收“模型、贴图、体积、签名”这些普通对象；报告层负责把结果翻译成人能读的句子。

这种分层让脚本可以在测试里直接构造小模型与小图片，不需要真实资产。也意味着未来换一种模型格式，只需要替换解析层，预算规则不动。

## 八、尝试过的错误做法

第一版把所有超限都当失败，结果现有资产立刻失败 16 项。第二版把所有超限都当警告，门禁又失去意义。

最终的三层结构来自一个简单问题：这项超限会不会影响运行或交付？

- 影响运行：硬失败；
- 影响体积但不影响正确性：警告；
- 影响兼容性：语义快照，必须显式确认。

预算不是越严越好，而是要让“正常迭代能通过、异常增长被看见”。这需要给每一类检查找到正确的失败等级。

## 九、一项容易被忽略的检查

安装包体积默认读归档目录，目录不存在时跳过。这个行为看起来不起眼，但决定了脚本能否在干净检出上运行。

如果缺少安装包就失败，每个新环境第一次跑门禁都会被卡住；如果永远跳过，又没人知道安装包是否超限。正确做法是：目录存在就检查并输出对比，不存在就明确跳过。

门禁要适应环境，而不是要求环境适应门禁。
