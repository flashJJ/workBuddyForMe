# 把桌宠入口放回主窗：桌面端检测、底栏布局与三档窄窗

桌宠一直存在，但主窗没有入口。用户要么记住命令面板，要么去设置页。v4.19 在侧栏底部补了一个图标入口，并顺手把 1024/1280/1440 三档窄窗复核了一遍。

## 一、入口只在桌面端存在

Web 版本没有 Electron preload，也就没有 `window.wbfm.pet`。入口不能无条件渲染，否则浏览器用户点开只会得到一个错误。

实现用现有桥接做能力检测：

```ts
const [petReady, setPetReady] = React.useState(false);
React.useEffect(() => {
  setPetReady(Boolean(getPetBridge()));
}, []);
```

首帧按 Web 处理，挂载后再显示。这样服务端渲染与客户端首帧一致，不产生 hydration 警告。

点击只做一件事：`void getPetBridge()?.open()`。打开、幂等、模型回落等逻辑全部沿用现有桥接，侧栏不新增任何窗口管理代码。

## 二、放在底栏，而不是主导航

侧栏主导航是页面路由，适合用 `<Link>`。桌宠不是页面，是窗口，放进导航会破坏「导航即路由」的心智模型。

底栏原本已有版本号、演示模式徽标与主题切换。入口作为同一组工具按钮加入：

```text
v4.19.0    [桌宠] [演示] [主题]
```

窄栏（<768px）只显示图标，靠 `title` 与 `aria-label` 提供名称；宽栏也不加文字。原因是底栏横向空间有限，加文字后演示徽标与主题按钮容易被挤压。

## 三、窄窗复核只看三件事

复核范围限定为 1024 / 1280 / 1440 三档，检查项只有三类：

1. 文档是否出现横向滚动条；
2. 入口是否完整落在视口内；
3. 入口中心点命中的元素是否是它自己（是否被其他控件遮挡）。

第三项用 `document.elementFromPoint` 判断。只断言「可见」不够：元素可以被另一个透明层覆盖，视觉上存在但点不到。

## 四、E2E 需要模拟桌面桥

Web 构建没有 preload，所以 E2E 用 `addInitScript` 注入一个最小 pet 桥：只实现主窗会调用到的 `open / close / isOpen / relayPerformance / onOpenChange / onChatRequest`。

第一次跑的时候只实现了三个方法，结果对话页因为 `onChatRequest is not a function` 直接进了错误边界。这个失败很有价值：它说明「检测到桥」与「桥实现完整」是两回事。之后补全最小方法集，并加了一条「对话页正常渲染」断言，避免桩自身的问题被误判成布局问题。

## 五、截图不入库

三档截图输出到 `test-results/responsive-v419/`，与既有响应式用例一致。`test-results/` 已在忽略列表中，复核结论写进版本总结，不把二进制截图提交进仓库。

最终三档均无横向溢出、无遮挡，点击入口调用 `open` 一次。没有发现需要修的布局问题，这也符合本版的约束：只修遮挡与溢出，不改视觉风格。
