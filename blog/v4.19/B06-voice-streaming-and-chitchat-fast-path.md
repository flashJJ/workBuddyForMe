# 首音更快、寒暄更省：一条语音链路和一条快路径

v4.19 实现期追加了一组语音与对话成本优化。它们不在原计划内，但直接决定「开机后第一句话」的体感，因此单独记录。

## 一、流式 TTS：不要等整句合成完

原链路是「文本事件 → 整句合成 → 下发音频」。首句稍长，用户就会感觉「回答已经出来了，但一直不出声」。

改造分三层：

- `TtsEngine` 增加可选 `synthesizeStream(text, opts, sink)`，按生成顺序回传增量 PCM，返回值仍是完整结果；
- 本地 sherpa worker 改用 `generateAsync` 与进度回调，在块边界检查取消；
- 语音桥收到音频块立即下发，不再等下一个文本事件。

没实现流式的引擎由上层退回一次性合成，行为不变。流式是能力，不是强制契约。

## 二、Matcha：用速度换声线多样性

本地新增 Matcha 模型：声学模型 + 独立 vocoder + lexicon + tokens + 词典，与 Melo/Kokoro 共用同一套下载、预热、缓存链路。

定位很明确：单一中文女声，合成速度约为 Kokoro 的 10 倍。默认仍是 Melo，需要首音速度的用户可以手动切换。

## 三、两种在线朗读：有密钥与免密钥

不是所有人都愿意下载本地模型，也不是所有人都有云厂商密钥。因此提供两条在线路径：

- 腾讯云：API 3.0 `TextToVoice`，TC3-HMAC-SHA256 签名，PCM 直出；凭据加密落库，设置页只显示脱敏状态；单次文本上限 150 字，超长按标点切分；
- 微软 Edge：复用「大声朗读」WSS 端点，内置公开客户端令牌，无需用户密钥；请求 MP3，再用 WASM 解码为 24kHz 单声道。

两者都在失败时回退本地引擎；本地也未就绪时返回带引导的错误。设置页按来源展示配置：只有本地离线才显示本地模型卡片，在线模式只保留在线配置与通用语速。

> 依赖偏离：`ws` 与 `mpg123-decoder` 是本版新增的两个运行时依赖，均无原生编译。打包时 `ws` 的可选依赖 `bufferutil` 会被解析为空模块，长帧发送报 `mask is not a function`；处理方式是运行时动态 import，并在加载前设置 `WS_NO_BUFFER_UTIL=1`。

## 四、寒暄快路径：先证明「它真的不需要工具」

「你好」这类输入实测会带上 122 个工具 schema，prompt token 接近 2.8 万。降本方案不是无条件裁剪，而是先满足一组严格条件：

- 意图为 `chitchat`，来源不是 fallback，置信度 ≥ 0.7；
- 文本非空、不超过 40 字；
- 无图片、无 URL；
- 不含任务/工具关键词。

全部满足时，本轮 `supportsTools=false`，不注入工具 schema，跳过长期记忆召回，`isLeanTurn` 同时生效。

前置修正同样重要：原规则对「你好」只给 `chitchat + fallback + 0.3`，快路径条件永远不成立。新增纯寒暄规则后判为 `rule + 0.85`；含任务或知识内容的句子不命中，继续走完整链路。

## 五、保守回退是设计的一部分

任务关键词、URL、图片、长文本、低置信度、fallback，任一出现即走完整链路。宁可多花 token，也不因为误判丢掉工具能力。

`context_snapshot` 增加 `fastChitchat` 字段，便于核对某轮是否命中。没有这个字段，成本变化只能靠猜。

语音与快路径都不是本版原定范围，但它们共同回答了一个问题：同样的回答，能不能更快出声、更少花钱。这个问题值得单独一轮实现。
