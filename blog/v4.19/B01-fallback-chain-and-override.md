# 从单备用到备用链：一次把模型切换的配置层级补齐

v4.18 只做了助手级、单值的备用模型。真实使用里很快遇到两个缺口：一个会话临时想换模型，只能改助手；一个备用模型也挂了，只能等用户手动重试。

v4.19 把这两件事一起补完：助手可以配一条最多 3 个模型的备用链，会话可以单独覆盖这一条链。

## 一、为什么不改数据库

三个配置都落在既有的 `settings_kv`：

| 键 | 值 | 说明 |
|---|---|---|
| `assistant-fallback-models` | `Record<assistantId, modelId>` | v4.18 旧键，继续读写 |
| `assistant-fallback-chains` | `Record<assistantId, string[]>` | 新键，最多 3 个 |
| `conversation-fallback-models` | `Record<conversationId, modelId>` | 新增，会话覆盖 |

升级即覆盖安装，不需要迁移。代价是读取时要处理「新旧键并存」：链非空时以链为准，链为空或缺省时回落到旧单值。第一个备用模型仍写回旧键，旧客户端和旧数据都能读。

## 二、优先级要能一句话解释

解析顺序固定为：

```text
会话覆盖（有效时）
  → 助手链（按顺序，跳过主模型与重复项）
  → 助手单值备用
  → 无备用
```

会话覆盖只作用于当前会话，不改主模型，也不改助手配置。会话设置里直接显示来源：会话覆盖 / 助手配置 / 未配置。用户不需要猜「这次到底用了谁的备用模型」。

## 三、校验放在写入和读取两侧

写入时拒绝：模型不存在、没有 `chat` 能力、包含助手主模型、超过 3 个。重复项保留首次出现的顺序去重，不报错。

读取时再过滤一次已删除或失效的模型。配置是用户可能长期不动的数据，模型却可能随时被删；只在写入时校验，时间一长必然出现指向空模型的链。

## 四、切换仍然是「最多两次」

候选链变长，但单轮切换次数不变：最多 2 次，已尝试过的模型不再尝试。

次数上限不是模型数量上限。链有 3 个，不代表一次失败要把 3 个都试一遍；两次之后仍失败，就应该明确告诉用户自动恢复失败，而不是继续消耗时间和额度。

另一个不变的原则是首字后不切换。链再长，也不能把已经输出一半的回答推倒重来。

## 五、事件与可见性

切换事件沿用四字段：`fromModelId / toModelId / reason / attempt`。`attempt` 现在能表达「第几次切换」，消息流提示与供应商健康面板都消费同一份事件。

配置层级可以复杂，但用户看到的行为必须简单：要么正常回答，要么一行「已从 A 切换到 B」，要么明确的失败提示。
