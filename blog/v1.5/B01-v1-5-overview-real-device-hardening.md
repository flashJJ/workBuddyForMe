# 总览：强模型演示全过，换成 7B 本地模型每天翻车——一个版本的真机补课

我们做的是一个本地优先的桌面 AI 应用：Electron 壳 + Next.js 前端 + 本地 SQLite，模型走 OpenAI 兼容协议，可以接云端，也可以接本机 Ollama。上一个大版本上线了最小多智能体协作——规划、执行、审查三个固定角色，结构化交接，预算硬约束，泳道时间线。验收时用的是云端强模型，十几个 golden 用例和四十多个端到端场景全绿。

然后真日常开始了：模型切成了本机跑的 7B 量化模型。

同一个任务，演示时一轮通过的协作链路，在小模型手上每天换一种死法。这个版本我们没有增加任何协作拓扑，只做了一件事：**把「能演示」修到「能用」**，顺带把真机暴露出的三个性能与布局问题一并处理。

先花两句交代协作本身。所谓三角色，是指一次复杂任务不再由一次对话直接回答，而是固定走三个环节：规划者把目标拆成带验收标准的子任务单，执行者在步数和 token 预算内调用工具完成，审查者对照验收条逐条裁决，不通过就沿固定路径返工。三个角色之间交接的不是自由文本，而是带校验的结构化载荷，每一轮都落库、可回放。这套机制在上一个大版本已经跑通，强模型加持下评测全绿——本版的故事从「模型换成 7B」开始。

## 小模型把状态机的「善意假设」全部打穿

三角色协作的内核是一个确定性状态机，但它对模型行为有一系列善意假设：假设模型会读完子任务、假设调用工具后会阅读返回、假设检索几次没找到会换关键词、假设交不出结果会如实写失败原因。

强模型确实会。7B 模型不会，而且每种「不会」都恰好卡在状态机没有兜底的地方：

| 真机现象 | 被打穿的假设 |
|---|---|
| 执行角色零工具调用，一轮直接失败 | 假设子任务的完整 brief、验收标准、工具目录都会被下传，实际只拼了标题 |
| 汇报「已完成」，结论区一片空白 | 假设模型记得工具返回正文，实际观察里只有工具名，模型在盲调 |
| 换着词检索同一个东西，二十步耗尽 | 假设模型自己知道何时放弃检索 |
| 明明绑定了知识库，零检索直接收尾 | 假设「请先查资料」写在提示词里就会被遵守 |
| 决策连败后整条交接被拒收，真实报错（403）被吞 | 假设终态总结永远非空、异常会被日志记录 |

每一条的修法都不是「把提示词写得再诚恳一点」。这个版本最大的体会是：**提示词是软约束，弱模型对软约束的遵循率约等于零；凡是真正重要的不变量，必须在确定性代码里兜底。** 比如授权了检索工具却没成功检索过就要收尾，决策循环直接驳回这次决策、注入强制纠正观察，给两次宽限，第三次尊重模型终态——既拦住裸奔，又不造死循环。

## 这个版本的四类交付

| 主题 | 做了什么 |
|---|---|
| 知识扩容 | 助手与协作节点从单知识库扩到最多 10 库：一次向量编码、各库向量与全文双通道召回、跨库 RRF 融合、全局去重与统一重排；引用来源超过 3 条默认折叠 |
| 协作收敛 | 子任务完整上下文下传、工具正文回注观察、每任务检索上限 3 次并实时显示预算、零检索收尾门控、终态注记非空兜底、失败原因全链打印、规划角色禁止给读写类任务乱挂桌面域 |
| 双语系统轨迹 | 系统产出的状态文案不再存中文裸串，改存语言中立的稳定标记；历史记录切换语言后即时变化，喂给模型时固定解码中文 |
| 真机热修 | 开语音的长回复从 429 秒降到正常；急停早于事件流建连导致任务永久卡在运行态；浏览器下展开任务详情凭空多出几千像素空白滚动区 |

多库检索值得单独说一句设计选择。每个知识库都有向量与全文两条召回通道，多库之后结果怎么合并？最直觉的做法是把各库相似度分数加权求和，但这条路在多库场景走不通：不同库的文档长度分布、嵌入质量、分词情况都不同，向量余弦分跨库不可比，权重只能靠人工标定，库一加减权重就作废。

方案是所有库的候选放进同一个 RRF（倒数排名融合）锅里——每个通道只贡献自己通道内的排名，公式只认名次不认分数，因此不需要跨库标定阈值；一个库召回质量差，影响的只是它名下候选的名次，不会污染全局量纲。一次提问只编码一次向量（编码是整条链路里最贵的一步），各库用同一个向量并行召回；融合之后再做全局多样性去重（同一原文片段被多个库命中只保留一条）和统一规则重排，角标编号在最终结果集上连续生成。空的库集合直接返回空结果，零成本短路。

## 系统文案的双语：存 key，不存译文

协作跑起来后，界面上有两类文字：一类是模型自由产出的（任务总结、审查意见），一类是系统模板产出的（「预算触顶」「已降级为直派」「第 3 步失败：…」）。后者之前直接以中文落库，英文界面里读历史记录就是一片中文，而且切语言不变。

做法是给系统模板定义一套稳定 key，落库时写成一行语言中立标记：控制字符包裹的一小段 JSON，里面是 key 加变量。它有两个解码边界：

- **喂给模型时**，固定解成中文——模型协议语言必须稳定，不能跟着界面语言飘；
- **渲染给人看时**，按当前界面语言解——React 组件走 hook，事件流回调这种非 React 场景走一个直接读页面语言标记的轻量翻译器。

模型的自由产出不进这个体系，原样存取。可枚举的系统文案才配拥有 key，不可枚举的模型文本强行翻译只会制造半中半英的怪物。

协议上有几个小坑值得一提。定界符选了两个不会出现在正常文本里的 ASCII 控制字符包住 JSON，这样 JSON 体内出现花括号、中文、冒号都没有歧义，同一条消息里「标记 + 普通文本」夹带也能逐段解析；变量值本身如果又是一条标记，渲染器递归展开（终态注记里嵌套末次失败原因就是这么实现的）；坏标记（控制字符不配对、JSON 解析失败）按普通文本透传，绝不吞字。长度也有限制：子任务标题有定长校验，带变量的标记超长时退化为不带变量的短标记——纯标记字符串绝不允许截断，切断定界符会让整条历史记录在渲染端解析失败。老数据没有标记，渲染时原样显示，无需迁移。

## 数字与边界

- 五个提交，139 个文件，约 +3000/-700 行，增量主要在协作内核与测试；
- 静态检查全绿，shared/core/web/voice 各包单测全绿，协作端到端场景全绿；
- 新增运行时依赖 0 个，数据库迁移 1 个（助手多知识库数组列，旧单值幂等回填）。

刻意不做的事：

- 不增加角色数量、不做并行执行，三角色串行拓扑保持不变；
- 检索上限是提示词加预算引导，而非工具层硬封——保留模型在意外场景下的决策空间；
- 门控两次后放行，不替模型做内容判断；
- 协作记录不进备份、无人值守触发桌面工具仍然直接拒绝，这两条前代的安全边界原样保留。

## 怎么证明修复有效

这类「模型行为变好了」的改动最容易自欺欺人，验证分三层：

1. **确定性层全用单测钉死**：门控的触发条件、宽限计数、降级单字段完整性，全部是纯函数输入输出断言，不依赖任何模型；
2. **真机层只做一件事——用最弱的模型跑**：本地 7B 量化模型，知识问答类任务从「必失败」跑到一轮收敛，并且三轮复测行为稳定；
3. **取证不看界面看数据库**：协作运行、桌面任务、步骤、角色交接四张表按时间线拉出来，每轮的决策消息、观察正文、交接载荷字段逐个核对。

测试侧也有结构性的新增，而不只是补断言：协作决策循环的「强制纠正」独立成纯函数配专门用例（门控触发条件、宽限计数、纠正不计连败）；角色交接的降级路径补了独立测试套件，专门证明失败时字段不丢；线格式协议自己有一百多个用例，覆盖夹带、嵌套、坏标记、旧数据四类输入。

还有一个流程上的教训。系统轨迹改成双语后，真机验证时一度看到界面直接把 JSON 原样显示出来，以为是渲染 bug，实际是开发服务器的热更新对新模块链失效——旧标签页跑的还是旧渲染器。**验证 i18n 改动必须关掉旧标签开新标签**，这类「假 bug」浪费了将近半小时。

## 一个必须说清楚的结论

修完之后，7B 模型跑知识类任务能一轮收敛，但产出内容仍然模板化、有正确的废话。这不是缺陷，是模型能力上限。

框架能保证的是：**失败的方式是收敛的、可预期的、有轨迹可审计的**——预算耗尽会交付最佳结果加未竟清单，零检索会被拦住纠正，真实错误原因会出现在终态注记里，任何一轮都能在泳道时间线回放。至于结论写得够不够好，那是模型的事，框架不背，也背不动。

这其实也是给所有想做 Agent 产品的人一个很实际的预期管理：框架的能力曲线和模型的能力曲线是两条线，工程能做的是把模型能力的下限兜住，让「用最弱的模型也不会出灾难性事故」，而不是把上限拉高。选模型时省下的钱，迟早会以提示词调试和兜底代码的形式花掉；但这笔钱花得值不值有明确判据——每一道兜底都应该是确定性的、可单测的、有真实失败案例背书的，而不是「感觉弱模型可能会犯错」的预防性堆料。

回看这条桌面 AI 应用的产品线，前面几个版本解决的是「能不能」：能读文档、能记事情、能接工具、能看见屏幕、能编排工作流、能说话；上一个版本解决的是「会不会分工」；这个版本第一次只解决「好不好用」。没有新功能演示，没有新节点可讲，但它可能是日常使用频率提升最明显的一版——因为真正每天跑任务的模型，从来不是验收演示时那个最强的模型。
