# 三个 dev 下隐身的坑：429 秒的回复、停不掉的任务、八千像素的空白

这个版本除了协作链路的补课，还修了三个性质完全不同、但气质一致的问题：本地开发时一切正常，到了生产模式或浏览器里才现形。它们分别关于**背压**、**时序**、**包含块**——三个写业务代码时很少主动想、出问题却极难定位的概念。

## 坑一：一条 2035 字的回复，流式连接挂了 429 秒

应用支持本地语音合成（TTS）：模型流式吐字的同时，把句子送进本地神经合成器，音频块通过同一条 SSE 连接（服务器单向推送事件的流式 HTTP 协议）继续下发给桌宠播放。

真机收到一条长回复（2035 字）后，现象是界面一直在「生成中」，输入框灰了七分多钟，实际连接耗时 429 秒。模型生成早就结束了。

根因是一句最经典的异步错误：**在数据流的主管线上 await 了 CPU 密集任务**。原来的语音桥逐句合成，每一句都串行 `await` 合成结果再放行：

```text
原管线（错误形态）：
模型 delta → 切句 → await 本地合成（占住管线）→ 文本事件下发 → 下一句……
```

本地合成器的实时率约 0.71（合成 1 秒音频要 0.71 秒），全文合成要 185 秒。文本的 delta 帧、最后的完成帧，全部排在合成任务后面等。前端又把「生成中」状态绑定在整条连接的生命周期上——连接为了把音频发完还不能关，于是 UI 老老实实陪绑七分多钟。

修法是把两个承诺彻底拆开：

- 合成从主管线摘下来，句子片段进入一个**保序的后台合成链**并行推进，文本事件零背压即时下发；
- 文本完成帧不等任何合成结果，连接仅在尾部为尚未发完的音频帧保活；
- 前端「生成中」状态只认文本完成帧：完成即解除，输入框和重试按钮立即可用，后台音频继续播完不被打断。

配套还处理了两个合成质量问题。其一是送给合成器的文本没有清洗 Markdown，表格竖线、分隔线、网址全被朗读，刷出一百多个无意义发音；清洗时表格管道符转成逗号以保留单元格间的停顿，分隔线与网址直接剔除，正文原有标点不能误剥。其二是一个 104 字没有任何标点的长句被单句合成，一次耗时 10.5 秒；切块策略是 40 字上限内按软标点贪心打包，没有标点就按字硬切，多块保序合成，只让第一块携带字幕，避免桌宠气泡把同一句显示多遍。

实测（同一条 2035 字回复）：

| 指标（同一条 2035 字回复） | 修复前 | 修复后 |
|---|---|---|
| 文本连接总耗时 | 429 秒（陪绑全文合成） | 纯模型生成时长 |
| 最大单块合成 | 104 字 / 10.5 秒 | 40 字 / 约 4 秒 |
| 输入框恢复可用 | 全部音频发完后 | 文本完成帧到达即恢复 |
| 噪声片段 | 表格/URL 刷 130+ 行 OOV | 3 个纯噪声片段整段丢弃 |
| 音频完整性 | —— | 后台继续播完，不被打断 |

> 通用结论：流式管线的每一段都要问自己「我在为什么东西等待」。CPU 任务、慢 IO、第三方回执，凡是和「本帧必须现在到客户端」无关的等待，都不该出现在主管线上。文本完成和媒体播完是两个独立承诺，不要让一个状态同时代表两者。

## 坑二：点了急停，任务永远停在「运行中」

协作任务支持中途急停。开发环境下测了几十次都正常，生产模式（编译后启动）的自动化测试稳定复现：点停止，界面泳道卡一直转圈，任务永远停在运行态。

差别出在事件流的建连时机。停止动作发生时，客户端做两件事：断开 SSE 订阅、让服务端把任务终结。原来的实现里，「断开订阅」就是全部取消信号——服务端靠「最后一个订阅者离开了」来感知用户走了。但生产模式没有编译延迟，用户点击停止时，**事件流的连接可能根本还没建立**：

```text
生产模式时序（出问题）：
点击停止 → abort 一个还没发出的 SSE 请求 → 请求消失，服务端从未见过订阅者
                                            → 「最后一个订阅者离开」的逻辑永远不会触发
                                            → 任务成为运行态孤儿

开发模式时序（侥幸正确）：
编译耗时 → SSE 先建好 → 用户才点得到停止 → abort 一个真实存在的连接 → 服务端感知到断线
```

开发服务器的编译延迟，意外地把竞态窗口填上了。这是「dev 绿 CI 红」最阴险的一种：不是环境差异导致逻辑错误，而是环境的慢让错误时序永远不被走到。

修复是双保险，并且补的是「订阅从未建立」这个之前不存在的状态：

- 服务端取消接口对「运行中但没有任何活跃订阅」的任务直接终结（原来返回 404，等于什么都没做）；迟到的事件流订阅请求由状态机以 409 拒绝，杜绝孤儿复活；
- 客户端 abort 订阅的同时，显式发一次取消请求，best-effort 处理（404/409/网络错误都不阻塞收尾）；
- 终态对账改成短轮询到真正终态（300ms 一次，上限 10 秒），容忍 abort 后服务端在一个动作内的收敛延迟。

> 通用结论：任何依赖「连接断开」传递的信号，都要回答「连接从未建立时信号怎么走」。取消语义必须至少有一条不依赖连接存在的通道（显式取消接口），对账不能只信一帧事件，要回读权威状态。

## 坑三：一个读屏标签，把页面撑出 8344 像素空白

第三个问题最反直觉。浏览器里展开一条协作任务详情，页面底部凭空多出一大段深色空白，横向看没异常，纵向可以把整个应用滚出视口；折叠后空白立刻消失。桌面壳里完全正常。

DOM 扫描发现，撑高整个文档的元素是验收清单每条末尾的一个序号标签——供屏幕阅读器使用的视觉隐藏元素（Tailwind 的 `sr-only` 类）。它的实际样式是 `position:absolute; width:1px; height:1px; clip` 裁剪。一个 1 像素的元素怎么撑出八千像素？

关键在**包含块**。绝对定位元素的位置相对最近的「定位祖先」计算；如果所有祖先都是默认的 `position: static`，它的包含块会一路退化到**初始包含块**（视口对应的画布根）。更要命的是 CSS 溢出规则的一个细节：中间容器的 `overflow: hidden/auto` 只能裁剪「包含块在自己内部」的绝对定位后代；对包含块已经逃逸到根画布的元素，沿途六层 overflow 全部无效。

这些标签的静态位置跟着清单项走，清单内容深入页面六千多像素，它们的真实位置就在六千像素处；它们不可见（被 clip），却**实实在在地计入了根滚动区域的高度**——这正是「一大段什么都没有、却可以滚动」的来源。桌面壳的外壳文档不响应滚动，所以同样的底层溢出在壳里无感。

修复一行：给清单项（标签的直接父级）加 `position: relative`，包含块回到条目内，标签的绝对定位坐标从此只在这一行里算。另外给应用最外层的固定外壳也补了 `relative`，让它本来就有的 `overflow: hidden` 对未来任何逃逸元素生效——一行成本的根治。

排查这类问题有个固定手法：在控制台找 `position: absolute` 的元素，检查它的 `offsetParent` 是不是 `body`（Chrome 对无定位祖先元素的返回值），再看它的文档坐标是否超出视口。整个排查脚本不超过十行：

```javascript
// 找出包含块逃逸、且静态位置撑到视口外的绝对定位元素
const vh = window.innerHeight;
const escapees = [...document.querySelectorAll('*')]
  .filter((el) => getComputedStyle(el).position === 'absolute')
  .filter((el) => el.offsetParent === document.body)
  .map((el) => ({ el, bottom: el.getBoundingClientRect().bottom }))
  .filter((x) => x.bottom > vh + 1);
console.log(escapees);
```

当时输出的十七个元素全部指向同一个组件——验收清单里的读屏序号，最深一个的文档坐标 9245px，和文档滚动高度精确相等。页面底部那段空白的「作者」当场归案。

> 通用结论：使用任何视觉隐藏或浮层类绝对定位元素前，先问一句「它的包含块是谁」。深层滚动容器内的绝对定位元素尤其危险——裁剪不生效、空白可滚动、还只在特定外壳下现形。滚动容器的固定外壳加一个 `relative`，是廉价的全站保险。

## 三个坑的共同形状

回头看，它们都是**边界处的隐性契约被违反**：

- 坑一违反的是**生命周期边界**：流式管线默认「帧到达 = 这一段工作完成」，但文本帧和音频帧的完成时刻根本不同；
- 坑二违反的是**状态空间边界**：取消逻辑只覆盖了「连接存在后断开」，漏了「连接从未建立」这个初始态；
- 坑三违反的是**布局假设边界**：`overflow: hidden` 能裁住一切的前提，是后代的包含块在自己内部——绝对定位元素并不默认满足这个前提。

开发环境的慢、桌面壳的滚动策略、强模型的高遵循度，都在悄悄替这些契约兜底；一旦环境换成生产模式、浏览器、小模型，兜底消失，问题才以夸张的方式显形。

所以这个版本之后我们新增了一条真机验证纪律：凡是涉及时序、流式生命周期、深层定位布局的改动，验证必须在三个最不友好的环境里各过一遍——

1. **最慢的模型**：提示词软约束在弱模型上的真实遵循率；
2. **编译后的服务**：没有编译延迟填充竞态窗口时的时序；
3. **普通浏览器标签页**：外壳不帮忙裁滚动、不拦截文档滚动时的布局。

开发服务器只负责让代码跑起来，不负责证明它是对的。
