# 小剧场的声场：逐句配音、会闪避的背景乐与可分发曲库

三个角色轮流说话，画面做得再细，音频也最容易露馅：谁在说话、声音从哪来、台词会不会被音乐盖住、这些曲目能不能随安装包一起发出去。

我们的桌面 AI 应用在本地跑着一个三席小剧场。这一篇只讲它的声音：逐句语音怎么跟时间线对齐、背景乐为什么要给台词让路，以及为什么素材许可最终变成了代码里的一条约束。

## 一、语音跟着台词走，不跟着计时器走

小剧场的时间线按「句」推进：每句台词有自己的停留时长，另有一个上限兜底，避免某一句把整场挂住。

音频编排只认当前句和播放状态：

```text
if (!enabled || !playing || !ready) { stopVoice(); return; }
const member = cast.find(m => m.slot === line.slot);
speak(line.text, member.avatarModelId);
```

三个细节决定了它好不好用：

- **按席位找声线**：台词只声明「谁说」，由 cast 把席位映射到模型，再映射到该模型的声线；换角色不需要改剧本。
- **切句先停上一句**：`speak` 内部会取消上一段合成，避免两句叠在一起；失败时只留字幕，不弹错误。
- **没就绪就不开口**：模型加载完成前不放音，否则幕布还没拉开，声音先出来了。

暂停、退出、切到后台都走同一条停止路径。回到前台时补播当前句，时间线重新计时——用户看到的和听到的是同一句。

## 二、说话时把背景乐压到 35%

背景乐的音量不是由 UI 滑块直接改的，而是由一个目标值函数算出来：

```text
target = !running || muted ? 0 : base(0.3) * (ducked ? 0.35 : 1)
```

于是进入剧场是 0.3，角色一开口就落到约 0.105，说完再抬回去。所有改音量都走同一个淡入淡出入口：默认 800ms 线性渐变，闪避用更短的 120ms，因为「压低」要听得出即时反应，「抬起」太急则显得突兀。

把音量收敛到一个函数里，好处是状态组合不会打架。静音、暂停、切后台、离开路由都只是改标志位，最后由这个函数算出唯一正确的目标值。

## 三、从振荡器垫音换成真实曲目

最早期的背景乐是 WebAudio 现场合成的和弦垫音：零外部素材、零许可、永不加载失败。问题也很明显——它只能提供一层氛围，撑不起喜剧、日常、悲剧、悬疑这四类情绪。

后来改成用 `HTMLAudioElement` 播四首真实曲目，按情绪映射到文件：

```text
warm → theme-warm      playful → theme-playful
tense → theme-tense    melancholy → theme-melancholy
```

换幕时不是直接换源，而是「淡出旧曲 → 换源 → 播放 → 淡入」。直接换源会有一个硬切，尤其在两句之间最刺耳。如果此时并未在播放，只记录新情绪，等下次启动再生效，避免为一个还没开始的幕预加载并空跑一次播放。

`start()` 还处理了一个竞态：`play()` 返回成功时，用户可能已经点了暂停或静音。所以播放前后都要复查运行标志，必要时立刻 `pause()`。自动播放被拦截则返回 `false`，交给上层显示「需要一次点击」。

## 四、自动播放策略：把第一次点击当作解锁

浏览器不允许页面在没有用户手势时发声。对剧场的处理是「监听一次，然后用掉」：

```text
pointerdown / keydown（once）
  → 解锁语音上下文
  → 启动背景乐
```

这里有个容易做错的产品细节：右上角的背景音按钮在被拦截时，第一次点击只负责解锁，不切换静音状态。否则用户点一下，按钮变成「已静音」，但他其实什么都没听到，会以为功能坏了。

## 五、音效继续用合成，不引入第五个素材

短音效没有外置文件，仍然是 WebAudio 合成：

- 幕布声是一段 0.9 秒的噪声，低通滤波从 260Hz 扫到 1600Hz，包络快速起、缓慢落；
- 换句提示音是正弦波，起频与落频按类型标签选：喜剧偏高、日常居中、悲剧下沉、悬疑上扬。

音效与背景乐共用静音开关，被策略拦截时静默跳过。演出不因为一个提示音没响而中断——这是刻意的降级。

## 六、把许可当作工程约束

曲库真正难的不是播放，而是「能不能发出去」。我们把它拆成四件必须同时成立的工程动作：

1. **来源**：只收协议允许再分发的素材；逐曲确认页面许可，不采信站点总声明。
2. **转码**：原始文件格式各异，统一转 MP3 192kbps、44.1kHz 立体声，并做响度归一到 -16 LUFS。
3. **元数据**：转码后检查 ID3 里的标题与作者，别把来源信息在编码这一步丢掉。
4. **清单**：逐曲登记作者、来源、时长、许可，和代码许可分开说明。

这四条一旦缺一条，就会在发布前变成返工。早期用生成式音乐工具产出的曲目只有个人学习用途的授权，不能随包分发，最后只能整体移出发布目录、在本机留档；连「忽略音频文件」的版本控制规则也得跟着改回来。

现在内置 11 首 CC0 曲目（3 首主题曲 + 8 首氛围曲），合计约 30.4MB，构建产物与安装包里各带一份。曲库许可与代码、角色模型许可彼此独立，这一点必须写清楚，否则后面每加一首歌都要重新讨论一次。

## 七、数字与验收

- 剧场音频相关的单测覆盖：拦截与淡入、闪避与静音归零、换幕切曲、未运行时切情绪、淡出途中停止后补齐曲目、销毁后重建。
- 真机采样 8 秒：最低 0.105、最高 0.3，确认闪避和恢复都在预期区间；跨幕切到轻快曲目后回到 0.3。
- 静音后音量为 0 且暂停，恢复后回到 0.3；两个曲目请求都返回部分内容响应，控制台无错误。
- 舞台路由会卸载全局迷你播放器，剧场里只有一路背景乐，不会出现两条音轨叠在一起。

## 八、一个验收环境上的坑

用 Playwright 内置的 Chromium 跑音乐用例，会出现「代码看起来没错、就是没声音」的假阴性——那个构建不含 MP3 解码能力。音频验收改用系统上的 Edge 或 Chrome，才能区分「解码不支持」和「实现有问题」。

## 九、边界

音效尚未外置；四首背景乐按情绪粗分，没有为单幕精修；单元素播放器只能先出后进，没有真正的交叉淡化；响度是一刀切归一，遇到本身动态很大的曲子仍会偏平。

## 十、一句话

**小剧场的声音不是「加一条音轨」，而是三件事同时对：让语音跟着句子走，让音乐给台词让路，让素材从第一天起就能合法地随包分发。**
