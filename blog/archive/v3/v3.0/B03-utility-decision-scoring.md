# 主动说话的「为什么」：Utility 打分与可解释决策记录

桌面角色突然开口，用户的第一反应往往不是「好可爱」，而是「它怎么这时候说话」。

如果系统里只有冷却和每日次数，这个问题没有答案：冷却只说明「可以说了」，不说明「为什么是这场」。继续加 `if` 也不行——深夜、忙碌、关系、最近演过什么，条件一多就互相覆盖，最后没人能复现某次选择。

我们的做法是把「能不能演」和「演哪一场」彻底分开：硬门控持有唯一否决权，Utility 打分只在合法候选之间排序，并把排序原因写进一条用户可读的记录。

## 一、否决权只属于硬门控

一次主动播放要过这些关：功能是否开启、是否处于勿扰时段、今日额度是否用完、这场今天是否已经演过、角色当前是否被占用。

任何一关没过，候选直接消失，不打分、不记录、不解释。这样做的好处是打分函数变得极简：它拿到的候选**一定合法**，不需要在公式里再写一遍「如果正在忙碌则……」。

反过来说，如果把门控塞进打分，会出现一种糟糕情况：某个候选分数很低但其实完全合法，用户看到「低分」却以为是「不允许」，两件事被混成一件。

## 二、六项权重

打分是一个加权和，权重写成常量表：

| 维度 | 含义 | 权重 |
|---|---|---|
| `hour` | 当前时段与场景时长的匹配 | 0.20 |
| `mood` | 情绪档位与节奏的匹配 | 0.15 |
| `level` | 关系等级与亲密度的匹配 | 0.15 |
| `work` | 工作信号（忙碌/空闲）与场景的匹配 | 0.20 |
| `idleCost` | 空闲够久 + 场景本身不贵 | 0.15 |
| `fresh` | 今天还没演过 | 0.15 |

六项相加恰好为 1，再叠加去重惩罚与弱偏好奖励，最后裁剪到 0–1。权重是先按经验给的一套保守值，刻意不做「某一项一票定生死」；真实数据积累后再调，结构不用动。

## 三、每个维度都要看时长

同一个场景，深夜演和上午演，合适程度完全不同。所以六个维度里有一半直接吃 `durationMs`：

- 深夜（22 点后或 6 点前）：一分钟内的短场景 0.95，超过一分钟跌到 0.3。
- 工作时段：一分半以内 0.85，更长的 0.4。
- 情绪偏低：偏好长一点的陪伴（0.85 / 0.55）；情绪不错：偏好轻快短场（0.9 / 0.4）。
- 关系较熟：偏好长场景（0.85 / 0.6）；刚认识：偏好短场景（0.8 / 0.4）。
- 正在忙：短场景 0.95，长场景直接掉到 0.15；空闲够久：长场景 0.85。

`idleCost` 是唯一同时看环境和成本的维度：空闲分钟数归一化后占一半，场景时长与道具数量折算的「打扰成本」占另一半。空闲越久越想演，但越贵的长场景越难拿高分。

## 四、去重与弱偏好必须真的影响排序

最容易犯的错，是把「去重」写成一句解释文案，却没让它进入总分。

我们的做法是把它做成加减项：

```ts
score = 0.20*hour + 0.15*mood + 0.15*level
      + 0.20*work + 0.15*idleCost + 0.15*fresh
score += 道具重复 ? -0.12 : 0
score += 主题重复 ? -0.15 : 0
score += 标签重复 ? -0.08 : 0
score += 长场次   ? -0.06 : 0
score += 弱偏好命中时段 ? +0.04 : 0
score += 弱偏好命中情绪 ? +0.03 : 0
score = clamp01(round3(score))
```

主题重复给最重的惩罚（-0.15），因为它最容易被用户感知成「又是这个套路」；道具重复次之（-0.12），标签重复更轻（-0.08）。弱偏好只给小幅奖励，它是「倾向」，不是「命令」。

还有一个细节：计算最近主题与标签时，要按场景 id 把候选自身排除。否则一个场景会「匹配到自己」，永远吃到去重惩罚。

## 五、平局必须是确定性的

浮点分数难免撞车，撞车时不能靠数组顺序碰运气。排序键写成三级：

```ts
sortBy:
  1. score 降序
  2. lastPlayedAt 升序（更久没演的优先）
  3. sceneId 字典序
```

同一触发键下有多个候选时，最高分组内还保留一个轮换游标：这次从第几条开始，下次顺延一条。否则上下文的微小抖动会让角色永远只演同一段。

## 六、理由码：把差值翻译成人话

用户不需要看公式，但需要看懂结论。所以每次打分同时输出理由码，每条只带两个字段：码与加权后的增量。

- 时段：`hour:late-night`、`hour:work-hours`
- 情绪：`mood:calm`、`mood:lively`
- 关系：`level:partner`
- 工作信号：`work:busy-short`、`work:idle-companion`
- 空闲：`idle:long`；新鲜度：`fresh:unplayed`
- 去重：`dedupe:prop`、`dedupe:theme`、`dedupe:tag`
- 成本与偏好：`cost:long-scene`、`pref:hour`、`pref:mood`

生成规则有三条：增量绝对值小于 0.02 的不记（噪音）；最多留 6 条；按绝对值降序，同值再按码字典序，保证同样输入得到同样理由列表。

界面上它长这样（数值与场景无关，只示意格式）：

```text
主题重复 -0.15   今日未演 +0.08   空闲陪伴 +0.07
长场次   -0.06   关系较熟 +0.05   深夜     -0.04
```

## 七、只记录真正开演的那一次

记录时机比记录内容更容易出错。

我们的规则是：**只有真正开演之后才落库**。候选再高分，被门控拒绝、被预算挡下、被更高优先级抢占，都不写。这样一条记录就等价于「用户确实看到的一场戏」。

容量上分两层：持久化只留最近 20 条，设置页展示 5 条。写入时同场景同时间戳视为重试，覆盖而不是追加；读取时坏记录逐条丢弃，不让一条脏数据拖垮整个列表。标题由服务端按剧情日记补齐，缺失就回退场景 id。

## 八、为什么拒绝只进开发日志

被拒绝的候选是高频事件——冷却、勿扰、额度、占用，每隔几十秒就可能发生一次。把它们也写进持久化记录，真实决策会被瞬间淹没，用户翻五条看到的全是「没演」。

所以拒绝只进开发日志：本地调试时能看到「这个候选为什么出局」，发布版不占存储、不打扰用户。

这条分工背后是一个判断：**设置页里的记录是给用户的解释，不是给开发者的审计日志**。两种需求混在一个列表里，两边都会变难用。

## 九、边界

权重仍是手工常量，没有在线学习；弱偏好的命中率还需要真实数据观察；关系等级门槛与低语池之间的打分缺少元数据接口。

但结构是稳定的：门控负责合法性，打分负责排序，理由码负责解释，记录负责回看。四件事各自可测，也各自可以单独演进。
