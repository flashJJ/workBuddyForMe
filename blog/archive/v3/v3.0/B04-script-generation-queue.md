# 让模型写剧本，但不让它决定演出：受限 schema 与画像注入

我们的桌面 AI 应用是本地优先、单人开发、Electron + Next.js 交付的私人助手，桌宠会在空闲时演一小段日常。

手写台词写到第三十句就开始重复。交给模型生成，又马上撞上两个问题：输出不可控，以及它根本不知道坐在屏幕前的是谁。

这一篇讲后台生成的两条边界：模型只产出受限的剧本数据，演出全部交给引擎；用户画像只进提示词，不进台词。

## 一、生成的是数据，不是表演

模型输出被限定成一个 JSON 对象，形状大致是：

```text
{
  story: { title, theme, tags[], cliffhanger? | resolves? },
  scene: { id, triggers[], priority, cooldownMs, interrupt, beats[] }
}
```

`beats` 里每个节点只有一个时间点和一个 cue，例如 `{ at: 12000, cue: { kind: "line", pool: "池名" } }`。

模型拿到的是原语目录：可用 pose 预设、手势、动作、行为、表情、视线目标、台词池、道具。它只能从目录里挑，不能自己发明。

演出侧拿到的还是原来那条 `StageDirection` 执行链，没有为「生成内容」新增任何渲染分支。

## 二、一条不满足，整条不要

解析分三层：先剥掉 Markdown 代码围栏取出 JSON，再用 zod 校验形状，最后跑一遍生成场景专属规则。

专属规则比 zod 更严：

- id 必须以 `gen.` 开头，和手写场景隔离；
- triggers 恰好一个，且只能取自七个触摸/上下文触发键；
- priority 只能是 1 或 2，cooldown 落在 120 秒到 30 分钟；
- beats 8 到 80 条，最后一条落在 60 到 180 秒；
- 至少一条 line 台词池；
- 道具必须成对：attach 后有更晚的 detach，show 后有更晚的 hide；
- 禁用 speak、branch、sound、effect、move、emit 六类 cue；
- 禁用会改常驻状态的 pose（sleep、wake、face-away、face-front、sit-*、stand）与接管状态机的 behavior。

最后还要过一遍原语白名单。只要有一处被丢弃，整条场景判为非法，而不是「尽量修一修」。

## 三、为什么不做自动修复

自动修复听起来友好，实际会掩盖问题：模型对 schema 的理解偏差被悄悄改掉了，下次还会犯，而且没人知道。

更麻烦的是语义。删掉一个 attach 或许能过校验，但道具出场顺序就变了；把一个越界的 `at` 夹到区间内，节奏也不再是模型原本想写的。

所以这里选 fail-closed：拒收、记录原因、下一次再试。代价是产出率低一些，收益是队列里只会有能安全演出的场景。

## 四、失败之后演什么

生成失败不是空白。返回值里带一个 `fallback` 标记，客户端看到它就继续用手写剧本池。

失败路径包括：当日额度用尽、没有可用模型、模型调用报错、输出不是 JSON、校验不通过、与最近剧情重复。

这些情况下界面只提示一句「回落本地池：原因」，角色照常演本地内容，用户不会看到一个卡住的舞台。

## 五、画像只取四类记忆

长期记忆分很多种，但能进剧本背景的只有四类：约束（忌口、禁谈话题）、事实、偏好、共同经历。

筛选口径是三个条件同时成立：状态为 active、类型在上述四类内、内容非空。排序是置顶优先，其次重要度。

数量上先卡 8 条，再用 480 字硬截断。超出的条目直接不进入提示词，而不是截半句。

```text
select(memories):
  keep status == active and kind in [constraint, fact, preference, relationship]
  sort by pinned desc, importance desc
  take 8
build lines: "- [约束] 内容" while total <= 480
```

没有可用记忆时返回 null，提示词里写「暂无可用画像，按普通用户处理」，而不是留一个空标题让模型自由发挥。

记忆库读取本身也可能失败，比如数据库被占用。这一层用 try/catch 兜住，降级为无画像，不阻断生成。

## 六、提示词里写清「怎么用」

画像块给的是背景，不是台词素材。规则里单独一条说明：可以自然称呼用户、避开忌口、尊重作息与共同经历；不要编造画像之外的隐私，也不要在台词里直接复述条目。

最后一句很关键。模型很容易把「用户对花生过敏」写成一句台词念出来，听感立刻从陪伴变成念档案。

同一条提示词还约束了剧情连续性：最近用过的主题不重复、已用梗标签不复用、上一条未收的悬念优先续接，到上限必须收线。

## 七、队列、预算与心跳

生成状态按本地日期存：当天调用次数、估算 token、已入队场景。跨天自动清零，坏数据回落空状态。

闸门是每日 8 次调用、6 万估算 token；token 按「两个字符约一个 token」粗估，只用于拦截，不追求精确。

新场景入队时同 id 覆盖并置顶，队列最多保留 10 条，超出裁掉最旧的。失败的调用也计数，防止用户连点把额度刷穿。

调度刻意不建常驻定时器：客户端每小时发一次心跳，服务端用「今日次数 + 上次运行时间」判断是否到期。

启用后的第一次检查立即到期，之后两次之间至少间隔 30 分钟，因此真实节奏约为每小时最多一场。每日次数默认 5，可在设置页配 0 到 24，0 表示不生成。

勿扰时段默认 23 点到次日 6 点。落在勿扰内直接返回，不生成、也不消耗当日次数。

到期时先记一次运行再调用生成器，这样即使生成失败或并发请求撞上，也不会在 30 分钟内反复触发。

## 八、弱偏好：可选、可丢

模型可以额外给出 `story.moods`（最多 2 个心情档位）与 `story.hours`（最多 1 段时段窗口）。

这两项在 schema 里挂的是「非法就丢弃」：值不合法时字段变成 undefined，不影响整条场景的校验结果。

它们只做加分项。客户端选场时，命中心情给 `pref:mood`，命中时段给 `pref:hour`，同分时再看上次播放时间。

这样设计的原因是命中率还不确定。弱偏好写错不应该让一场本来合规的戏被拒，写对也不应该压过去重与冷却这些硬规则。

## 九、一句话

**生成的价值不在「让模型自由发挥」，而在「给它一个能安全落地的形状」。**

schema 决定它能写什么，画像决定它写给谁，队列与预算决定它什么时候写，失败回落决定它写不出来时用户看到什么。
