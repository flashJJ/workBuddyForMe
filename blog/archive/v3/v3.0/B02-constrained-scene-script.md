# 让角色演一段而不是说一句：受限剧本引擎的数据结构与调度

让桌面角色动起来，第一反应通常是「让模型直接输出动作」。

模型回一段「挥手 → 歪头 → 说句话」，前端照着播。写 demo 很快，接进真实产品就会撞上三件事：模型给的节奏和渲染时钟对不上，长台词会被下一个动作截断；两个来源同时想动上半身，谁赢取决于回调顺序；一旦模型输出跑偏，没有任何降级路径，角色只能僵在那里。

我们的做法是反过来：模型（或人）只写数据，播放交给一个受限的剧本引擎。这篇讲这套引擎的数据结构、调度规则，以及把旧互动搬进来时踩的坑。

## 一、单位先定清楚：一场戏

剧本的最小单位不是「一个动作」，而是「一次互动」——它有明确的开始、结束和优先级。

```ts
scene = {
  id: 'touch.body-tap',
  triggers: ['touch::body::tap'],   // 触发键；空数组表示只能手动播放
  priority: 1,                       // 0 拖拽 / 1 触摸 / 2 环境 / 3 待机
  cooldownMs: 800,
  interrupt: 'all',                  // all = 可被更高优先级打断
  gating: { level: { min: 'acquaintance' } }, // 可选入场条件
  beats: [
    { at: 0, cue: { kind: 'pose', preset: 'squash' } },
    { at: 0, cue: { kind: 'expression', tag: 'smirk', holdMs: 1800 } },
    { at: 0, cue: { kind: 'line', pool: 'body-tap' } },
  ],
}
```

字段不多，但每个都在回答一个调度问题：谁能触发、什么时候允许、能被打断吗、演多久。

## 二、Beat 与 Cue：表现拆到最小

`beats` 是相对场景起点的毫秒数组，每个 beat 挂一个 cue。cue 只描述意图，不写骨骼、不碰音频：

- 身体类：`pose`（姿势预设）、`gesture`（点头/歪头/瞥视）、`motion`（动作文件）、`behavior`（分层行为）。
- 表现类：`expression`（表情标签 + 停留时长）、`look`（视线目标 + 权重）、`prop`（手持道具）。
- 语言类：`line`（台词池）、`speak`（指定文本）。
- 结构类：`wait`（只影响同层后续 cue 的偏移）、`branch`（按条件二选一）。

轨道不是另写的字段，而是从 `kind` 推导出来的：姿势/手势/动作/行为归 `body`，表情归 `face`，视线归 `look`，台词归 `voice`，特效归 `ui`，位移与道具归 `world`。少一处声明，就少一处漂移。

`body` 与 `world` 是独占轨道——同一时刻只能有一场戏占用。这决定了「两场戏能不能同时演」这个问题的答案。

## 三、时间必须单调

时间轴只有一条硬规则：`at` 必须非降序。

同一个 `at` 可以有多个 cue（比如第 0 毫秒同时换姿势、给表情、说话），但后一个 beat 不能早于前一个。单场还设了 10 分钟上限——这明显超过任何合理互动，纯粹是拦住「少写一个零」把场景挂死。

`wait` 不占轨道，只把同层之后的 cue 整体后移；`branch` 在开演那一刻求值一次，选中的分支被展开进时间轴，之后不再回看条件。

**条件只求值一次**，是重放能力的来源：同一个场景、同一个种子，得到的 cue 序列完全一致。

## 四、Director 的四道闸门

场景注册之后，一次播放请求要依次通过四道判断：

```ts
play(sceneId, ctx):
  if not scene: reject
  if not gate(scene, ctx): reject          // 入场条件 + 忙碌/睡眠/背对
  if inCooldown(scene): reject             // 本场冷却
  if repeatBlocked(scene): reject          // 同一场已经连着开演两次
  if 独占轨道冲突:
     if 对方 interrupt == 'never': reject
     if 对方优先级更高: reject
     if 同优先级: 入队等待
     else: 抢占对方
  start(scene)
```

其一，**门控分层**：对话中、睡眠中、背对屏幕只挡环境级场景（优先级 2 及以上），触摸与最高优先级的落地动作仍要响应。用户戳一下，角色装睡不理人，体验很差。

其二，**同优先级不是直接失败**，而是进等待队列。独占轨道空出来之后按入队顺序补演，避免「身体单击连着点两下，第二下静默丢失」。

预算不在这层。每日主动播放额度属于播放策略，在开演前向服务端认领；Director 只管「这场戏现在是否合法」。职责分开了，两边都能单独测。

## 五、单时钟推进，说话时不推进

Director 不新开定时器，只暴露一个 `update(dt)`，由渲染层的帧回调驱动：

```ts
update(dt):
  if dt <= 0: return                 // 切后台不补帧
  time += dt
  for play in active:
    elapsed = time - play.startedAt
    while next.at <= elapsed:
      emit(next.cue)                 // 台词、表情、动作在这里分发
  drainPending()
```

为什么坚持单时钟：动作与台词共享一条时间线，才不会出现「话还没说完，人已经在做下一个动作」。礼物是确定性和可测性——给定总时长，推进序列是唯一解。

「说话时不推进」在结构层还有一个更隐蔽的变体：舞台小剧场里，语音还在播时轮播计时暂停，并留了一个 15 秒硬上限，防止自动播放被拦截时整场卡死在同一句。

## 六、把旧互动搬进新结构

迁移不是重做行为，而是把已有的六个触摸反应逐条写成等价场景。等价关系可以逐项核对：

- 挤压姿势 ↔ 原来的 squash 调用；轻拍 ↔ 原来的 tap。
- 临时表情 ↔ 带停留时长的一次性表情；常驻表情 ↔ 停留时长为 0。
- 台词 ↔ 从台词池取一句，字幕停留时长缺省由适配器补。

环境与状态类另算：低语是一条只有台词的场景，环顾与换重心是一条两条视线的场景；睡眠、唤醒、背对、转回被写成四个 `interrupt: 'never'` 的状态场景，优先级压到 1，这样它们不会被「睡着就不许演」的门控挡住。

还有一条容易忘：勿扰与「关闭台词」只影响 `voice` 轨道，不阻断整场。角色可以照样动、照样看，只是不说话。

## 七、生成失败回落本地池

生成场景进入同一条链路，但入口多一层 fail-closed 校验：id 唯一、触发键在允许集合内、beats 单调、道具 attach/detach 成对、cue 都能被适配器识别。非法 cue 被剔除并记原因，清洗后为空的场次才整场丢弃。

生成服务任何一步失败都返回降级标记，客户端继续用手写剧本池。也就是说，模型不稳定只会让内容变少，不会让角色不演。

发布前还有两道闸：跨场景 lint 检查 id 唯一与触发键白名单；内置场景的 cue 时间轴做成 golden 快照，改剧本必须显式更新快照才能过。

## 八、一个真实的坑

接入 React 时出过一次「所有场次都播不出来」。

现象是触发事件进来了，Director 却始终返回拒绝。根因不在调度逻辑，而在 StrictMode 的 effect 会执行两遍：实例在 memo 里创建，第一次清理把它 dispose 了，第二次 setup 拿到的还是那个废实例。

修法是把 Director 的创建放进 effect 内部，清理时置空引用。教训是：**带生命周期的调度器不能交给 memo 管理**，它的存活范围必须和订阅它的 effect 完全一致。

## 九、边界

这套引擎目前只做「单机、单角色、确定性回放」。它不理解情绪，不判断内容好不好，也不负责选哪一场——那是打分器的事。它也不解决「模型写的剧本是否有趣」，只用校验保证它不会把角色演坏。
