# 剧本也要门禁：跨场景 lint 与 cue 时间线快照

写内容最容易出的事故，不是崩溃，而是「什么都没发生」。

角色站在原地，道具没消失，某句台词永远等不到——控制台干净，页面正常，只有用户觉得她卡住了。我们的桌面 AI 应用里有一批手写剧本场景，数量到二十多个之后，这类问题开始变成常态。

## 一、内容错误长什么样

- 复制一场戏改内容，忘了改 id，两个场景同名，运行时按 id 查表命中谁看运气；
- 触发键少写一个字符，这场戏永远不会被触发，也没有任何日志；
- `at` 写反或写重，时间线跳帧、卡住，或者两拍挤在同一毫秒；
- 道具 `attach` 了却没有 `detach`，谢幕后杯子还留在台上；
- 整场只有 `wait`，演了，但观众什么也看不见。

它们的共同点是：不抛异常。运行时不校验，测试只覆盖自己那组场景，于是错误一路滑到用户面前。

## 二、为什么需要一层跨场景总账

每场戏都有自己的单元测试，但它们只管自己。

新增场景通常是从旧场景复制出来的，作者会补自己的断言，却不会回头检查「我的 id 和别人撞了没有」「我用的触发键在不在白名单里」。而生成式剧本与手写剧本共用同一个 `Scene` schema、同一个导演器和同一个校验入口：生成侧有 schema 与动作白名单兜底，手写侧反而更松。

所以补的不是更多逐场测试，而是一层「只关心全库自洽」的 lint。

## 三、六类约束

| 约束 | 检查什么 | 失败说明 |
|---|---|---|
| 身份 | id 非空且全局唯一 | 同 id 会让查表结果不确定 |
| 契约 | 触发键、打断策略在白名单内；priority 为 0–100 整数；cooldown 为非负整数 | 拼错的触发键等于死场景 |
| 时间 | beats 非空、`at` 单调不减、不超过单场上限 | 时间倒挂会卡住时间线 |
| 可感知 | 全库不能只有 `wait`；至少有一句 `line` | 演了等于没演 |
| 道具 | `attach/detach`、`show/hide` 计数成对 | 谢幕后台面不干净 |
| 不丢弃 | `validateScene` 返回的 `dropped` 为空，beat 数量不变 | 校验在悄悄删内容 |

打断策略只有两种值，语义很直接：一种是「更高优先级可以抢占」，另一种是「不可被打断」，落地、久别这类场景用它。触发键则来自一份封闭清单，剧本不能自己发明。

时间上限存在的理由不是美学，而是防呆：`at` 多写一个零，场景就会被挂到几十分钟之后，从用户视角看就是「今天不演了」。

## 四、把 cue 摊平再检查

剧本里允许出现分支，分支里又能嵌分支。检查道具是否成对、有没有可感知反馈时，必须先递归摊平：

```text
function flatten(cues, out = []) {
  for (const cue of cues) {
    out.push(cue);
    if (cue.kind === 'branch') {
      flatten(cue.then, out);
      if (cue.else) flatten(cue.else, out);
    }
  }
  return out;
}
```

漏掉递归，等于给 `branch` 开了一个后门：分支内的道具不配对、分支内只有 `wait`，都检查不到。这类漏洞不会立刻出事，只会在某次加了新分支之后悄悄出现。

## 五、可感知 cue 是最贵的一条

`wait` 本身合法，它是节奏。问题是一个场景**只有** `wait`。

这种场景不崩溃、不报错、测试也能过，只是没人看得见。把它定义为失败，等于把「内容空转」从体验问题提前成构建问题——这是整组约束里性价比最高的一条。

台词兜底则是另一层：全库至少存在一句 `line`，保证字幕与语音通道有内容可跑，不会出现整批场景都没有说话能力的情况。

## 六、golden 只记时间与类别

节奏快照刻意做得很小：

```text
timeline(scene) = { id, beats: [{ at, kind }] }
```

两份快照各司其职：一份存整张时间线，一份单独存场景 id 的顺序。前者能抓到「某一拍从 1200ms 挪到了 1800ms」，后者让新增或删除场景在 diff 里一眼可读。

台词文本、表情参数、动作名称都不进快照。原因是文案改动频繁，全塞进去会让快照变成噪音，最后所有人的处理方式都会退化成「无脑更新」。快照守的应该是最不该漂的东西：节奏。

二十多个场景被压成一张几十行的节奏表。改动剧本后跑一次测试，diff 会明确列出哪一场的第几拍变了；不确认更新就一直红着——内容改动因此必须有一次显式确认。

## 七、为什么不用运行时兜底

道具清理当然可以在场景结束时统一做。但那会把内容 bug 变成静默行为：看起来一切正常，实际是引擎在替作者擦屁股。

成对约束把责任放回作者，并且让错误停在测试阶段。同理，`validateScene` 丢弃非法 cue 是一种容错，但容错不能当作正确——所以还要断言它一个都没丢。

## 八、门禁入口要够快

单独的 `check:scenes` 只跑场景目录，几秒钟结束。全量测试要几分钟，改一句台词的人不会每次都跑；只有把检查拆成随手可跑的一条命令，它才会真的被跑。

这一组口径是 6 个测试文件、37 项通过：场景自身的单测、台词池与时刻表、状态切换，再加上 lint 与 golden。数量不大，但它兜住的是「新增场景时的整体一致性」，而不是每一场演得对不对。

## 九、几个具体的坑

- **只断言「能跑」不够**：校验会删掉非法 cue 并返回一个合法场景，所以必须同时断言 `dropped` 为空和 beat 数不变。
- **分支要递归**：不递归就等于放过分支内容。
- **两份快照都要**：只有时间线快照时，场景重排的 diff 难读；只有 id 快照时，节奏漂移抓不到。
- **文案别进快照**：否则每次改台词都要更新快照，很快就没有人认真看 diff 了。

## 十、一句话

**内容也需要门禁：让写错的剧本在启动前失败，而不是在用户面前表现成「她今天不太想动」。**
