# 重构怎么证明“没变”：golden、身份断言与注入测试

重构最难的不是改代码，是证明改完和改之前一样。

尤其是动效这种靠眼睛判断的东西。单元测试可以证明函数返回值，但证明不了“角色抬手角度没变”。如果只靠人工截图对比，每次改注册表都要重看一遍所有行为，成本高且不可靠。

这次把静态动效表改成可注入快照，我们用了三层验证，各管一件事。

## 一、第一层：golden 快照锁观感

golden 的思路很简单：把“观感”变成数字摘要。

对每个行为，在固定时间点采样：

- 全部身体骨骼的四元数。
- 根节点的垂直位移、朝向与侧摆。
- 量化到 0.02 网格后做哈希。

```ts
for (const at of [0, 120, 300, 600]) {
  runtime.captureFrame();
  runtime.update(at - elapsed);
  frames[`t${at}`] = digest(values(runtime, bones));
}
```

量化是为了容差。浮点计算结果不可能逐位相同，0.02 的网格足以吸收无意义的抖动，又能抓住真正的角度变化。

结果存成快照文件。重构前后对比，16 项全部一致。

这一层负责回答：**默认内容下，角色看起来和以前一样吗？**

## 二、第二层：身份断言锁实现约束

golden 只能证明结果一致，证明不了“没有偷偷拷贝”。

如果默认快照是静态表的深拷贝，golden 一开始也会通过；但后续修改静态表时，默认快照不会跟着变，观感会慢慢漂移。

所以我们加了一条引用断言：

```ts
expect(DEFAULT_MOTION_CONTENT.poses).toBe(POSES);
expect(DEFAULT_MOTION_CONTENT.motions).toBe(MOTIONS);
expect(DEFAULT_MOTION_CONTENT.behaviors).toBe(BEHAVIORS);
```

`toBe` 检查的是同一个对象引用。它把“默认快照必须与内置表同源”从口头约定变成可执行测试。

这一层负责回答：**默认路径是不是零拷贝？**

## 三、第三层：注入测试锁新能力

前两层都在证明“没变”，第三层证明“能变”。

我们构造一个只含一个姿势的内容快照，然后断言：

- 自定义姿势存在。
- 内置姿势不存在。
- 内置动作不存在。
- 内置行为播放失败。
- 应用自定义姿势后骨骼四元数真的被改写。

这组断言的价值在于反证：如果运行时仍然偷偷读全局表，第二条和第三条会失败；如果构造参数被忽略，第一条会失败；如果只改库不改骨架，最后一条会失败。

这一层负责回答：**注入的内容是不是真的替换了默认内容？**

## 四、测试放在哪也受门禁约束

新增测试文件时遇到一个很实际的问题：目录预算。

动画测试目录已经有 12 个直接文件，达到结构门禁上限。再放一个测试文件，检查直接失败。

解决办法不是改门禁，而是按能力建子目录：

```text
animation/__tests__/content/content.test.ts
```

同理，新增的内容快照模块也放在 `animation/content/` 子目录。两个子目录各自只有一个文件，不增加父目录的直接文件数。结构门禁通过，代码组织也更清晰。

这件事说明：**测试文件也是代码，也要遵守目录预算。**

## 五、测试数量怎么分配

这次相关测试的分布：

| 范围 | 文件数 | 用例数 | 关注点 |
|---|---|---|---|
| core 能力包 | 9 | 57 | 六类 effect、启停、卸载、升级、签名、健康 |
| ai registry | 1 | 5 | 内置协议、未知协议、新协议、重复注册 |
| web 动效与剧本校验 | 34 | 215 | golden、注入、姿势、动作、行为、白名单 |
| web 舞台 | 12 | 65 | 布局、剧场、BGM、分享卡 |
| desktop 舞台与托盘 | 4 | 20 | 窗口、IPC、托盘菜单 |

不是所有测试都要重写。能力与 provider 的现有测试原样跑通，就是“零回归”的证据；只在新增能力处补新用例。

## 六、门禁矩阵

除了单测，还有六项工程门禁：

- typecheck：注册表类型是否闭合。
- lint：是否有未使用变量与越界引用。
- 行数：单文件不超过 300 行。
- 结构：目录预算、公开入口、跨域引用。
- 循环依赖：新增注册表不能引入环。
- ASCII：文档框图是否可渲染。

这次有两个门禁真实拦截了问题：

1. 动画运行时文件加到 303 行，行数门禁失败，最后压回 297 行。
2. 动画测试目录到 13 个直接文件，结构门禁失败，最后移入子目录。

如果没有门禁，这两个问题会以“以后再说”的形式留进仓库。

## 七、为什么不追求覆盖率数字

覆盖率高不代表行为等价。golden 与注入测试的价值，是在改动出错时给出明确失败信号。

## 八、可迁移的结论

做“等价重构”时，可以按这个顺序设计验证：

1. 先写结果快照，证明默认行为不变。
2. 再写身份断言，锁住关键实现约束。
3. 最后写新能力测试，证明扩展路径真的可用。
4. 让现有测试原样通过，作为零回归的底线。
5. 把测试文件也纳入目录与行数门禁。
