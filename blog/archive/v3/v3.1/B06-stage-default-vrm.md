# 舞台为什么默认是 2D 角色：默认形象的三个数据源

一个功能“支持 3D”和“默认是 3D”是两件事。

我们的桌面 AI 应用有三种舞台：自由演示、协作 run、会议。小剧场早就用上了三个内置 3D 角色，但用户从托盘打开舞台时，看到的仍然是 2D 立绘。

原因不是渲染不支持，而是三种模式各自写死了默认形象，而且都写的是 2D 模型。

## 一、先找到默认值在哪

舞台的路由判定很简单：

```text
/stage                   → 自由舞台
/stage?run=<id>          → 协作 run
/stage?meeting=<id>      → 会议
/stage?stage=play        → 小剧场
```

小剧场的 cast 是三个内置 3D 角色。自由舞台、协作 run、会议则分别从三个地方拿默认形象：

| 模式 | 默认来源 | 原值 |
|---|---|---|
| 自由舞台 | 前端 mock cast | 三个 2D 模型 |
| 协作 run | 适配器角色表 | 三个 2D 模型 |
| 会议 | 会议 cast 的 fallback | 一个 2D 模型 |

三个地方都是硬编码。只改一处，另外两处仍然会回到 2D。

## 二、为什么会出现三份默认值

这是很典型的演进结果：

- 自由舞台最早是演示骨架，用最小成本跑通三个槽位。
- 协作 run 后来接入真实数据，但沿用“角色 → 默认形象”的冻结映射。
- 会议模式再后来加入，成员来自真实会议，没有形象字段，只能给一个全局 fallback。

每一处单独看都合理，合起来就成了三份不一致的默认值。

这也解释了一个常见误判：文档里写了“舞台三席使用内置 3D 角色”，指的是小剧场；普通舞台从未切换。

## 三、统一成什么

我们把三个内置角色按槽位固定：

| 槽位 | 角色 |
|---|---|
| 左 | 冉卡露丽 |
| 中 | 雪团 |
| 右 | 菲比 |

自由舞台和协作 run 直接使用这组映射。会议模式稍微复杂：成员数量是 2–4，不能所有人都用同一个模型。

做法是给槽位一份默认表：

```ts
const DEFAULT_BY_SLOT = {
  left: 'vrm:builtin:rankaluli',
  center: 'vrm:builtin:xuetuan',
  right: 'vrm:builtin:feibi',
  farRight: 'vrm:builtin:xuetuan',
};
```

会议 cast 的优先级变成：

```text
场景覆盖 > 调用方 fallback > 槽位默认
```

这样既保留了“调用方可以指定统一 fallback”的能力，又避免未指定时整场四个席位长得一模一样。

## 四、声音要不要跟着换

3D 角色不只是渲染，还牵着语音。

舞台念台词时会按 `avatarModelId` 找声线。内置 3D 角色已经有固定映射：雪团、冉卡露丽、菲比各一条声线。

所以把形象换成 3D 后，语音不需要改链路；它本来就读同一个 id。真正需要检查的是“没有映射时怎么办”，旧逻辑会回落到默认声线，这条兜底保留。

## 五、性能预期要提前说

三个 3D 模型同台比三个 2D 立绘重。

这也是为什么舞台保留性能档位：

- 全渲染：三席都保持正常更新。
- 省电档：只保留发言者的高频更新，其余角色降速，但不卸载模型。

省电档的文案原来写死了“仅发言者 Live2D”，默认改成 3D 后就不准确了。我们把文案改成“仅发言者”，让档位语义对所有角色成立。

## 六、测试怎么调整

协作 run 的开场 cast 有单测，原来断言三个 2D id。改默认值后同步改成三个 3D id。

会议 cast 原来没有单测，这次补了一条：

- 三个成员时，按槽位得到三个不同 3D 模型。
- 显式传 fallback 时，fallback 仍然优先。

前者防止“统一成 3D 但全一样”，后者防止“默认表覆盖了调用方意图”。

舞台前端 65 项测试与动画 golden 不受影响，因为渲染路由只认 `vrm:` 前缀，不关心具体是哪个角色。

## 七、默认值也是产品行为

这次改动没有新增渲染能力，也没有改舞台布局，但用户感知非常直接：打开舞台，角色从 2D 变成 3D。

它提醒我们：**默认值是产品行为的一部分，不是实现细节。**

凡是写死默认值的地方，都要问三个问题：

1. 这个默认值有几个副本？
2. 修改时会不会只改到其中一个？
3. 有没有测试锁住默认值？

## 八、已知代价

首屏要加载三个 3D 模型，低配机器更依赖省电档；会议四人席时第四席会复用模型，视觉上仍有重复。

## 九、可迁移的结论

如果你有多个入口共享同一类实体，先列一张“默认值来源表”：

| 入口 | 数据来源 | 默认值 | 谁维护 |
|---|---|---|---|

只要同一列出现多个值，就说明默认策略没有收口。统一默认值不一定要抽配置中心，先把副本找齐、把优先级写清楚，往往就够了。
