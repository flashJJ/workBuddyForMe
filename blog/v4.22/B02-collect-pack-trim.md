# 采集、装包、再裁剪：任务上下文的三段式重构

任务上下文是一块拼出来的提示词：会话摘要、结构化事实、当前计划、近期对话、长期记忆，按优先级拼在一起，再按预算裁剪。

过去它是一个从上写到下的函数。现在它被拆成采集与装包两段。这篇讲清楚拆完之后，每一段到底负责什么。

## 一、旧实现长什么样

简化后的旧逻辑大概是这样：

```ts
const blocks: string[] = [];
if (summary) blocks.push(`【会话摘要】\n${summary}`);
if (facts) blocks.push(`【已知事实】\n${facts}`);
if (plan) blocks.push(`【当前计划】\n${plan}`);
if (recent) blocks.push(`【近期对话】\n${recent}`);
if (memory) blocks.push(`【相关长期记忆】\n${memory}`);
return truncateToTokens(blocks.join('\n\n'), budget);
```

它没有错，但把四件事揉在了一起：

1. 数据从哪来（查询、检索）；
2. 片段怎么排（代码行序）；
3. 重复怎么处理（没有处理）；
4. 超预算怎么办（整串尾部截断）。

结果就是：想加第六个来源，得同时考虑这四件事；想知道「为什么这一段没进来」，只能读完整函数。

## 二、第一段：来源只负责采集

来源被抽成一个对象：

```ts
interface ContextSource {
  id: string;
  priority: number;
  enabled?: (request) => boolean;
  collect(request): Fragment[] | Promise<Fragment[]>;
}
```

每个片段带三样东西：唯一键、正文、优先级。正文里已经包含标题，比如 `【近期对话】\n用户：…`。

这样拆开之后，来源内部的逻辑可以很复杂——同步查询、异步检索、开关判断都行——但它只需要对「我产出了哪些片段」负责。排序、去重、预算，一概不碰。

五个内置来源的优先级是固定的：摘要 10、事实 20、计划 30、近期对话 40、长期记忆 50。数值越小越靠前。

## 三、第二段：收集器并发与容错

收集器做的事只有两件：

```ts
const results = await Promise.all(
  sources.map((source) => runSource(source, request)),
);
```

- 所有来源并发执行；
- 每个来源包一层 `try/catch`：抛错就记 `failed`，返回空片段，不向外抛；
- `enabled` 返回 false 记 `skipped`，连 `collect` 都不调用；
- 空白片段视为无效，来源没有有效片段时记 `empty`。

这一步同时解决了旧实现里最别扭的问题：单来源失败不再让整个上下文降级。记忆检索超时，摘要和近期对话照常注入。

收集器还会按来源优先级做一次稳定排序，保证同一份输入永远得到同一顺序。

## 四、第三段：装包只管约束

装包器接收片段数组和预算，做三件事：

```text
1. 按 priority 升序稳定排序
2. 同 key 只保留排在最前（优先级最高）的一条
3. 拼接后超预算：从尾部整段丢弃，仅剩一段仍超限才按 token 截断
```

为什么是「整段丢弃」而不是「截断字符串」？

因为截断字符串会把一句话砍成半句，而整段丢弃至少保证剩下的每一段都是完整的。摘要、事实这类高密度信息在最前面，天然最后才被丢；记忆和近期对话在尾部，超预算时先让位。

代价是：如果最高优先级的那一段本身就超过预算，仍然要截断。这时装包器只会对这一段做 token 截断，并标记 `truncated`，调用方可以据此判断是不是真的发生了压缩。

## 五、等价性怎么保证

拆结构最容易出的问题是「行为悄悄变了」。所以这一版把「输出逐字一致」写成验收项：

- 固定夹具下，新管线输出的完整字符串必须与旧实现快照完全相等；
- 分隔符统一为双换行，标题原样保留；
- 空结果仍然返回 `null`，调用方按「无上下文」处理。

测试里不比对片段数量，也不比对来源状态，只比对最终字符串。这比断言「包含某段」更严格，也更接近真实影响。

## 六、收益

- 新增来源只写一个 `collect`，注册进去即可；
- 单个来源失败有明确状态，排查时知道是哪一段没进来；
- 预算裁剪规则集中在一处，改一次全部生效；
- 采集与装包都是纯函数，可以单独测试，不需要启动整个任务流程。
