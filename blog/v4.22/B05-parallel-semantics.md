# 并行的代价：预算、幂等与失败隔离

让两个分支同时跑起来，代码量并不大。难的是跑起来之后，那些原本「因为串行所以不存在」的问题。

这一版在放开并发之前，先把三件事写成了契约：预算怎么共享、节点会不会重复执行、一个分支挂了另一个怎么办。

## 一、预算共享：超限要返回结果，不能抛错

工具调用有一个轮次预算，防止一个流程无限调用工具。串行时它很简单：每次调用减一，减到零就拒绝。

并发时有两个选择：

1. 每个分支一份预算；
2. 整个运行一份预算。

第一种会让「并行度越高、总调用越多」，预算失去意义；所以选第二种。

共享预算的实现关键不在计数，而在**拒绝的形态**：预算耗尽的分支必须拿到一个正常的工具结果（`ok: false` + 说明），而不是异常。因为异常会触发节点失败，进而影响运行终态；而预算耗尽只是「这次不执行」，不该让整个运行失败。

```text
预算充足 → 执行工具，返回 ok:true
预算耗尽 → 返回 ok:false + 「本轮工具预算已用尽」，节点仍算成功
```

这也意味着：并行下某个分支被预算拒绝，其它分支继续跑，运行最终仍然可能成功。这是有意为之。

## 二、幂等：同一节点只执行一次

调度器有一个「待执行集合」，启动节点时立即把它移出，同时登记到「运行中集合」。这样即使扫描循环重复看到同一个节点，也不会二次启动。

契约把幂等键写成 `${runId}:${nodeId}`，含义是：

- 同一次运行内，一个节点最多执行一次；
- 如果因为任何原因被重复调度，直接复用已完成的作用域输出，不重复写作用域。

为什么需要这条？因为并行调度里「扫描—启动—等待」是循环进行的，节点状态在多个集合之间流转。没有显式的已启动标记，很容易在某个 await 间隙里把同一个节点启动两次。

实现上不需要额外的缓存 Map：把节点从待执行集合移除，本身就是幂等键。契约里的 memo 描述的是语义，不是数据结构。

## 三、失败隔离：让无关分支跑完

串行时，首个失败立刻 `run_failed` 并停止，这是合理的：反正后面也跑不了。

并发时如果照搬，会出现一个奇怪的现象：A 分支失败，B 分支明明与它无关，却被一起中断。用户看到的是「整个流程挂了」，而实际只有一个节点有问题。

所以并发 > 1 时的规则是：

1. 失败节点标记 `failed`，立即发出 `node_failed`；
2. 它的后代因为「前驱未成功」而判定不活，标记 `skipped`，理由写「上游失败」；
3. 无关分支继续执行；
4. 运行收敛后，如果存在失败，终态仍是 `run_failed`，消息取首个失败。

注意终态没有变成「部分成功」。失败隔离改变的是「什么时候停」，不是「算不算失败」。

「上游失败」这个理由需要沿链传播：直接后代看到前驱 `failed`，再往下的节点看到的是前驱 `skipped`。所以调度器要记录跳过的原因，而不是只记状态，否则第二层后代会被误标成「分支未命中」。

## 四、结果收敛：多个 end 取哪个

扇出图天然可能有多个 `end`。并发下它们可能都成功，谁作为运行输出？

契约选择：按拓扑序靠前者。

原因不是为了「更对」，而是为了「可预测」。完成顺序受调度与耗时影响，不稳定；拓扑序是编译产物的一部分，重跑也一致。其余 `end` 的产出只出现在各自的 `node_succeeded` 事件里，不丢失，但也不作为运行结果。

## 五、取消

取消信号的处理在并发下也变了：

- 停止启动新节点；
- 等待运行中的节点结束；
- 发出 `run_cancelled`。

不强行中断执行中的工具调用，是为了避免半完成状态。工具本身如果支持取消，会在自己的执行里返回失败；调度器只保证不再扩大并发面。

## 六、怎么观测

语义写清楚之后，还需要让人看得见。三处观测就够了：

- 起始事件带 `parallelism`，一眼知道这次运行是串行还是并发、并发几路；
- 节点完成事件带 `durationMs`，并发下也能看出每个节点自身耗时，而不是被兄弟分支拉长；
- 执行面板展示「并发 ×N」徽标，只读，不提供设置入口。

最后一条是刻意的：并行度属于图本身的结构属性，改图 JSON 就行了。面板只负责告诉用户「这次跑的是几路」，避免又多一个需要维护的配置面。

## 七、哪些没做

- 不做跨分支数据汇聚：编译器仍限制非 end 节点单入边，两个分支的结果不能合并到一个节点；
- 不做完成顺序排序：事件按实际完成顺序发出，消费方自己按节点分组；
- 不做分布式调度：并发只是进程内的 Promise 任务池。
