# 从按序遍历到就绪集合：流程引擎的真并行

一个工作流图，画布上是两路扇出：开始节点同时连到两个节点，最后各自连到一个结束节点。

但在引擎眼里，它一直是一条线。

## 一、旧引擎的假设

旧引擎的循环非常直白：

```ts
for (const nodeId of compiled.order) {
  // 判断活性，执行节点，写作用域
  if (node.type === 'end') return runSucceeded(output);
}
```

它依赖三个假设：

1. 拓扑序等于执行序；
2. 一个 `end` 成功就意味着运行结束；
3. 同一时刻只有一个节点在执行。

在纯链式流程里，这三个假设都成立。但扇出图一出现，第二个假设就把另一条分支吞掉了：第一个 `end` 完成，函数返回，另一个分支连 `skipped` 都不一定有。

## 二、新的循环：只看就绪

新调度器不再问「下一个是谁」，而是问「现在谁可以跑」：

```text
待执行集合 = 所有节点
循环：
  ready = 待执行中「所有前驱都已落定」的节点
  对 ready 中每个节点：
    如果分支未命中 → 标记 skipped
    如果可并行 → 有空位就启动
    如果必须独占 → 等运行中节点清零再启动
  取一个完成事件
  直到没有运行中节点、也没有可启动节点
```

「落定」包括三种状态：成功、跳过、失败。只要前驱落定，后继就可以被判定：要么执行，要么因为分支不通而跳过。

这个改动看起来只是换了个遍历方式，实际上换掉了三个假设：

- 拓扑序只用于确定扫描顺序与结果收敛顺序，不再等于执行顺序；
- `end` 成功只记录候选输出，不立即返回；
- 同一时刻可以有多个节点在执行，数量受并发上限约束。

## 三、为什么需要「独占」

并不是所有节点都适合并发。

- `human` 节点会挂起等待用户输入，两个同时挂起会让授权弹窗打架；
- 写操作或危险工具需要用户确认，确认框不能并发弹；
- `agent` 节点内部有自己的多轮循环与事件流，并发会让输出交错。

所以调度器维护一个白名单：

```text
可并行：llm、knowledgeSearch、condition、只读 tool、end
独占：  human、写/危险 tool、agent、start
```

独占节点的规则很简单：只有当运行中节点数为 0 时才启动它；它运行期间也不再启动其它节点。这样交互时序与旧版一致。

只读工具需要先解析权限才能判断。解析不到或解析失败，一律按独占处理——宁可慢一点，也不要并发弹窗。

## 四、事件怎么发

并行之后，事件不再天然有序。做法是：

- 每个节点执行时把事件推进一个队列；
- 主循环从队列取事件向外产出；
- 完成事件按实际完成顺序发出，不做排序缓冲。

保留顺序的是「节点内部」：`node_started` 一定先于该节点的 `node_succeeded`；`node_waiting_human` 一定发生在等待之前。跨节点之间只保证因果关系（前驱完成后继才可能开始），不保证兄弟分支谁先。

这带来一个使用上的注意点：读取事件流做时间线时，要按事件里的节点 id 分组，而不是假设相邻事件属于同一节点。

## 五、结束条件

运行收敛后统一结算：

1. 被取消 → `run_cancelled`；
2. 有失败 → `run_failed`，取首个失败；
3. 有成功的 `end` → 取拓扑序靠前者的输出，`run_succeeded`；
4. 都没有 → 按「未连通到结束节点」失败。

「首个失败」指完成顺序上的第一个，不是拓扑序上的第一个。并发下两者可能不同，这一点在契约里写死，避免实现漂移。

## 六、默认串行

这套调度器只在 `parallelism > 1` 时启用。缺省为 1 时引擎走原来的顺序循环，一个字都没改。

这不是为了省事，而是为了把风险关在笼子里：新调度器的正确性只需要在显式开启的图上证明，旧图的行为完全不受影响。
