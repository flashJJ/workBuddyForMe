# 默认关闭的艺术：parallelism=1 如何做到逐字等价

给流程引擎加并发，最危险的不是并发本身，而是「顺手把默认行为也改了」。

这一版的做法是：并发能力藏在一个可选字段后面，缺省为 1；为 1 时引擎走的是**旧代码路径**，不是新调度器退化后的串行模式。

这篇讲为什么这样做，以及「逐字等价」到底怎么验证。

## 一、两条路径，而不是一个开关

一种常见的实现是：写一个统一调度器，`parallelism = 1` 时它的行为自然退化成串行。

听起来优雅，但有两个问题：

1. 退化行为需要额外证明——调度器的扫描顺序、事件发出时机、结束条件都必须恰好等于旧循环；
2. 任何一个为了并发做的改动（比如事件队列、完成顺序、失败处理），都会顺带影响串行路径。

所以这一版直接分成两条路径：

```text
if (parallelism === 1) {
  走旧顺序循环
} else {
  走就绪集合调度器
}
```

旧循环几乎原封不动，只做了两件不改变事件序列的事：把单节点执行体抽成共享函数、给完成事件补上 `durationMs`。

代价是两套代码要一起维护；收益是串行路径的正确性不需要重新证明。

## 二、等价要测什么

「逐字等价」如果只测「最终输出一样」，是不够的。真正影响使用方的是事件序列：

- 起始事件、结束事件的类型与字段；
- 每个节点的 `node_started` / `node_succeeded` 顺序；
- 分支未命中时 `node_skipped` 的位置与理由；
- 失败时 `node_failed` 与 `run_failed` 的先后。

这些都被现有引擎测试覆盖着。改造的原则是：**现有测试一条断言都不改，必须全绿**。

这不是形式主义。测试里写死了事件类型的排列，如果改造后有一个事件挪了位置或少了字段，测试会立刻失败。反过来，如果为了让测试通过去改断言，就等于把「等价」的定义改掉了。

新增的测试只覆盖并发路径：扇出双分支、并发上限、失败隔离、写工具独占。

## 三、旧图为什么安全

图 JSON 新增了一个可选字段：

```text
parallelism?: 1..4
```

校验规则是：缺省不填；填了必须是 1 到 4 的整数。

读旧图时字段不存在，引擎按 1 处理。这意味着：

- 用户已有的所有工作流，行为完全不变；
- 不需要数据迁移，也不需要重写已保存的图；
- 想试并行的用户，在图上加一个字段即可。

边界值被拦在 schema 层：0、5、1.5 都会在保存时被拒绝，不会流到引擎里。引擎还会再钳一次（把越界值收敛到 1–4），作为第二道保险。

## 四、重放为什么不并行

节点重放是早期的调试能力：只执行目标节点的祖先闭包，跑到目标节点就收尾。

它依赖两个串行假设：祖先闭包按序执行、目标节点完成即结束。并发调度器不满足这两个假设，所以重放在任何并行度下都走串行路径。

这是一个明确的取舍：重放是低频调试功能，没有必要为它维护一套并行语义。将来如果真要并行重放，再单独设计。

## 五、回滚成本

默认关闭还有一个隐性收益：回滚只需要退代码。

- 没有数据库迁移，不需要降级脚本；
- 图里的 `parallelism` 字段对旧代码是未知字段，会被忽略；
- 备份格式不变，旧版本可以读新备份。

对一个本地优先、单人维护的应用来说，「能干净地退回去」比「一次做对所有事」更重要。

## 六、这条经验可以复用

任何「会改变默认行为」的能力，都可以问三个问题：

1. 默认值能不能保持旧行为？
2. 旧路径能不能原样保留，而不是靠新实现退化？
3. 等价性有没有可以被现有测试直接验证的出口？

三个都答「能」，改动的风险就基本被关进笼子里了。
