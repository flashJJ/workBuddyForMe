# 把「能用」打磨成「顺手」：四个真机痛点与六条收口线

我们做的是一个本地优先的桌面 AI 应用：Electron 桌面壳 + Next.js 前端 + 本地 SQLite 存储。模型、知识库、工作流、MCP 与技能都跑在本机，不依赖云端账号。功能清单早就很长了，但用户把窗口拖窄一点、点开一个下拉、第一次进入知识库，体验立刻露出毛边。

这一轮没有增加任何后端能力，只做一件事：把「能用」打磨成「顺手」。起点不是功能清单，而是两张真机截图和一次代码走查——四个看起来毫不相干的毛病，最后指向同一种工程习惯。

## 一、四个痛点，两种根因

| 现象 | 直接原因 | 真正的根因 |
|---|---|---|
| 下拉选项挤在一起、系统蓝高亮 | 原生 `<select>` 的弹出面板由操作系统渲染，CSS 只能改闭合态 | Radix Select 早已在依赖里，却从未被组合成组件；同时有 13 个文件裸用 `<select>`，另有一个「原生封装」，两套并存 |
| 数字框上下小箭头生硬、点起来没反馈 | 浏览器原生 `type="number"` 的 spinner 不可定制 | 11 个文件裸用 `type="number"`，没有统一的可空与钳制语义 |
| 窗口一窄，文字挤压、控件贴边 | 侧栏固定 224px 且不能折叠；任务页有 260px 固定列；场景矩阵有 160px 固定标签列 | 布局从设计之初就假设「窗口宽度固定」，全仓几乎没有响应式断点 |
| 知识库空空如也，工作流模板看不见 | 知识库零播种；列表空态只让「创建」 | 内容策略缺位：starter 一直在，但没在用户会经过的地方露出来 |

前三个痛点其实是同一种习惯的两面：**装了库不等于用了库**，**写了弹性布局不等于真的能伸缩**。第四个不是技术问题，是「有内容但没人知道」。

还有一个细节能说明问题有多分散：下拉的 13 处裸用分布在设置、事件、舞台、流程编辑器、提醒等六个目录，数字输入的 11 处分布在七个目录。它们不是某个人漏改了一处，而是从来没有一个统一控件。

取证的方式也很朴素：把截图里的每个控件定位到文件，再用几条搜索确认规模——

```text
搜 '<select'          → 13 个业务文件
搜 'type="number"'    → 11 个业务文件
搜 'grid-cols-['      → 若干固定网格列
搜 'ensureStarter'    → 工作流与技能有播种，知识库没有
```

这样「不好看」就变成了「13 处、11 处、224px、零播种」——可以分配工作量，也可以验收。

## 二、为什么这四件事必须一起做

四个痛点单独看都能修，但放在一起才会互相暴露：

- 只换下拉不换数字框，同一张表单里会出现「系统下拉 + 自绘步进器」的混搭，观感比原来更割裂；
- 只做响应式不统一控件，窄窗下两套控件的换行行为不一致，截图永远对不齐；
- 只播种模板不补入口，用户仍然不知道模板在哪，首启还是空的；
- 只补入口不做测试连接，MCP 填完表单后失败原因不可见，等于把门槛从「不会填」换成「不知道错在哪」。

所以顺序是：先统一控件语言（下拉、数值、表单排版），再统一空间分配（侧栏、网格、切换器），最后补内容与入口（模板、starter、预置目录），并用三尺寸 E2E 把前两类改动钉住。内容与入口放在最后，是因为它们依赖控件与布局已经稳定——否则模板弹窗自己就是窄窗挤压的下一个现场。

## 三、六条主线

这一轮的工作被拆成六条线，每条都有可检查的出口，而不是「改完看起来好一点」。

| 主线 | 动作 | 出口 |
|---|---|---|
| 下拉统一 | 用 Radix 组合出 Select / SimpleSelect，空值走哨兵适配 | 业务代码裸 `<select>` 归零 |
| 数值统一 | NumberInput 步进器，保留 `allowEmpty` | 裸 `type="number"` 归零 |
| 窄窗响应式 | 侧栏自动折叠、固定列改 `minmax`、按钮与数值框 `shrink-0` | 三档尺寸无横向滚动 |
| 开箱即用内容 | 知识库模板 3 个幂等播种；工作流 starter 3 → 6 | 首启即有可点的库与流程 |
| MCP / 技能入口 | MCP 预置目录 4 个一键填入；技能「重新扫描」 | 不用查命令也能加能力 |
| 一致性收尾 | FormField 表单排版、MCP 测试连接、token 文档、三尺寸 E2E | 后续不再裸用原生控件 |

六条线里，前两条是「控件语言」，第三条是「空间分配」，第四条是「内容策略」，第五条是「入口」，第六条是把前五条钉住的约束。顺序不是随意的：控件不统一，响应式改完还是会露出两套观感；内容不露出，播种等于没播。

## 四、明确不做：边界比清单更重要

体验补课最容易滑向「顺手把 UI 重做一遍」。这一轮把不做的部分先钉死：

- **不换 UI 库**：Radix Select 本来就在依赖里，增量只有组件组合与样式；不引入 Storybook、新组件库，也不换 Tailwind。
- **不做移动端**：这是桌面应用，只把窄窗优化到合理下限（720×520），不追平板与手机。
- **不改检索与安全口径**：编译式 RAG、混合检索、语句级引用保持原样；MCP 与技能的权限确认、黑名单策略一条不改。
- **不重做视觉与品牌**：沿用既有设计 token，只做收敛和一致性，不引入新配色体系。
- **不做在线模板市场与云同步**：模板和内置内容全部本地，本地优先的定位不动摇。
- **不做助手级技能绑定的数据模型改造**：这一轮只补入口与文案口径，绑定留给后续。

红线里最容易被误解的是「不换 UI 库」。有人会问：既然下拉不好看，为什么不换一套更完整的组件库？因为问题不在库的能力，而在「已经装了的库没被用」。换库会把一次控件迁移扩大成一次全站重构，收益却和组合现有库一样。

## 五、门禁数字

| 项目 | 结果 |
|---|---|
| `pnpm check` | 8/8：类型检查通过、ESLint 0 error、300 行硬门禁通过 |
| `pnpm test` | 8/8 全绿：web 端 507 例、shared 包 314 例、桌面壳 164 例，其余包全绿 |
| 裸控件 | 裸 `<select>` 13 处 → 0；裸 `type="number"` 11 处 → 0 |
| 迁移面 | 26 个文件、42 处使用点（13 处裸 select、18 处旧封装 import、11 处裸 number） |
| 响应式 E2E | 1280×800 / 900×700 / 720×520 三档，横向溢出 ≤1px、主内容可见 |
| 新增单测 | Select 空值适配、NumberInput 钳制与可空、模板播种幂等、MCP 测试连接 |
| 回归 | 步进器数字被裁切（表现为「加减没反应」）修复并纳入 E2E |

数字里最值得看的是最后一行。它不是新增功能，而是一个被窄窗改造放大的旧问题：值一直在变，只是数字被挤到看不见，用户就判定按钮坏了。体验类 bug 常常以「功能坏了」的形式被报告。

## 六、这一版真正的收获

三条经验，和具体控件无关：

1. **统一控件不是换库，是补语义层。** 旧代码用空字符串表示「未选择」，新组件要求非空值——真正的成本在适配与回归，不在样式。
2. **响应式不是加断点，是拆固定宽。** 断点只决定「在哪一刻换布局」，固定宽才决定「换之前挤不挤」。先改 `minmax(0,1fr)`、`min-w-0`、`shrink-0` 的分工，再谈断点。
3. **开箱即用不是多做功能，是把已有内容放到用户会经过的地方。** 模板要出现在「新建」旁边，预置目录要出现在「添加」里面。

门禁没有降级，反而多了可自动化的断言：横向溢出量、窄档文字是否隐藏、步进器数字是否被裁。体验类改动一旦能被断言，就不会在下一个版本悄悄退化。

「顺手」不是一个可以一次性交付的状态，而是一组愿意被反复断言的约束。

下一篇讲替换原生控件时那两个不会报错的坑：Radix Select 的空值语义，以及 `position="popper"` 在 jsdom 里把测试拖成几十秒的定位循环。
