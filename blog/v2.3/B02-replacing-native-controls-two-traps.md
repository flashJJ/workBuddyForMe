# 换掉原生控件，真正难的不是样式：两个静默陷阱

把系统原生的下拉和数字框换成自定义控件，看起来是最机械的一类改造：找到标签、替换组件、跑一遍测试。样式确实是最先解决的部分——原生 `<select>` 的弹出面板由操作系统绘制，CSS 只能改它闭合时的那个盒子；`type="number"` 的上下箭头同理，浏览器不给任何定制入口。真正花时间的，是两个既不报错、也不影响编译的坑。

## 一、先承认一件事：两套控件语言并存

代码走查的结果很直白：一个「原生 select 封装」负责一部分页面，13 个文件直接裸写 `<select>`，同一个应用里两套下拉的外观、行高、选中高亮必然不一致。数字输入也是 11 个文件裸用 `type="number"`，各自带一个 `w-20` 之类的固定宽。

依赖列表里其实早就装了 Radix Select，只是没人把它组合成组件。于是第一步不是「选型」，而是「把已有的库用起来」：Trigger / Content / Item / Group / Label / Separator 组合成一套，样式全部走既有设计 token。可访问性由 Radix 兜底——键盘导航、焦点回收、`role="listbox"` 这些不用自己实现，也不容易实现错。

## 二、坑一：Radix Select 的 value 不能是空字符串

这是整个迁移里唯一需要动脑的地方。

旧代码里大量存在这样的写法：`value=""` 表示「未选择 / 跟随默认」。比如场景模型矩阵里有一个「默认模型」选项，选中它时业务层拿到的是空字符串，表示不覆盖。这个语义在原生 select 里完全合法。

但 Radix Select 的 `value` 必须是非空字符串：空字符串会被当成「没有值」，触发器显示 placeholder，受控状态直接失效。

最直接的修法是把业务层的 `''` 全改成 `'none'`——这会污染数据库、API 和所有判断分支，风险远大于收益。我们选择在组件边界加一层适配：

```text
const NONE = '__none__'

toRadix(v)   = (v === '' || v == null) ? NONE : v
fromRadix(v) = (v === NONE) ? '' : v
```

- 进入组件前，`''` 与 `null` 都映射到哨兵值；
- 离开组件时，哨兵值还原成 `''`；
- 触发器看到哨兵值时渲染 placeholder，而不是把 `__none__` 显示给用户；
- 业务层、存储层、API 完全不知道哨兵值的存在。

这类映射必须用单测锁死：`'' → NONE → ''`、`null → NONE → ''`、普通值往返不变，以及一条「哨兵值不得出现在提交数据里」的断言。没有最后这条，某次重构很容易把它漏进数据库——它看起来只是一个普通字符串，没有任何类型能拦住。

还有一个迁移纪律：**逐文件回归，不做一次性批量替换。** 下拉分布在设置、事件、舞台、流程编辑器、提醒里，每一处的空值语义都要人看一眼。批量替换能把「归零」做得很快，也能把一处「空表示跟随默认」悄悄改成「空表示不合法」。

## 三、坑二：popper 定位在 jsdom 里不会停

第二个坑更隐蔽。

Radix Select 支持两种定位：`item-aligned`（默认，选中项对齐触发器）和 `popper`（浮层挂在触发器下方）。popper 看起来更接近我们对「下拉菜单」的直觉，于是第一版用了它。

结果是测试时间爆炸：涉及下拉的用例从约 0.2 秒涨到几十秒，实测能到三十多秒，个别直接超时。生产代码没问题，浏览器里也正常，只有 jsdom 里慢。

原因是 popper 定位依赖持续的 rAF 测量循环：浮层要每一帧读取触发器和内容的位置，才能算出该往哪放。真实浏览器有布局，测量会收敛；jsdom 没有布局系统，所有几何值都是 0，测量永远不收敛，rAF 就一直排下一帧。测试进程被这个循环拖住，用例本身早就跑完了。

修法是把定位改回默认的 `item-aligned`：交互和视觉对我们的场景等效，测试立刻恢复到亚秒级。组件仍然保留 `position` 入参，需要时可以在真实浏览器里覆写。

| 定位方式 | 测量机制 | jsdom 行为 | 结论 |
|---|---|---|---|
| `popper` | 持续 rAF 读取几何位置 | 无布局，永不收敛 | 测试慢几十倍，不用 |
| `item-aligned`（默认） | 选中项与触发器对齐 | 无需持续测量 | 采用 |

这条经验可以推广成一句：**无头 DOM 里，凡是依赖真实布局的组件，成本不在功能正确性，而在测试时间。** 绿灯不代表没问题，要看每个用例跑了多久。测试从 0.2 秒变成 30 秒，是组件在告诉你「我在等一个永远不会到来的布局」。

## 四、NumberInput：受控不等于逐字符提交

数字输入看起来只是「减号 + 输入框 + 加号」，真正的约束在提交时机。

如果做成纯受控、每次 `onChange` 就把值写回上层，输入「120」会触发三次写入；如果这个字段背后是设置保存或网络请求，就是三次无意义的写。做法是**受控 + 本地草稿 + 失焦提交**：

```text
输入时：只更新本地草稿字符串，不动上层值
失焦时：解析 → 钳制到 [min, max] → 提交一次
非法输入：回退到上一次有效值，不产生 NaN
```

另一个必须保住的是**「空」的语义**。模型上下文窗口这类字段，空表示「未设置 / 使用默认」，和 0 是完全不同的两件事。如果迁移时统一写成 `Number(value) || 0`，用户眼里的「不限制」就会变成「上限为零」。所以组件有 `allowEmpty`：

```text
apply(raw):
  if raw.trim() === '':
    allowEmpty ? emit(null) : emit(min)
  else:
    emit(clamp(Number(raw), min, max))
```

`min/max/step` 的钳制要同时覆盖三条路径：点加减、键盘输入、失焦提交。只在按钮上做判断是不够的——用户可以直接把 999 打进输入框。到上下限时按钮停在原地，不循环、不回绕。

可访问性不能丢：输入框保留 `role="spinbutton"` 与 `aria-valuenow` / `aria-valuemin` / `aria-valuemax`，加减按钮有可读的名称，键盘上下键仍然可用。原生 spinner 被换掉了，但屏幕阅读器看到的东西不能变少。

## 五、迁移规模与验收

最终的迁移面：26 个文件、42 处使用点——13 处裸 `<select>`、18 处旧封装的 import、11 处裸 `type="number"`。验收不是「看起来统一了」，而是可以 grep 出来的：

- 业务代码里 `<select` 与 `type="number"` 命中数为 0；
- 空值适配、钳制、可空、a11y 属性各有单测；
- 全量测试与类型检查不降级，新增文件仍受 300 行门禁约束；
- 交互语义不变：只换外观与手感，不改默认值、提交时机与业务判断。

最后一条最容易在迁移中失守。统一控件时「顺手修一下提交时机」看起来是改进，实际上是在没有验收项的情况下改业务行为；等用户发现设置保存变慢或变多，已经很难把原因追回到一次「样式迁移」。

## 六、小结

- 控件迁移的难点在**语义适配**，不在样式；哨兵值只能活在组件边界内，并且要被单测钉住。
- 依赖真实布局的定位方案，在 jsdom 里会用测试时间收税；默认的 `item-aligned` 是更稳的工程选择。
- 受控输入要区分「显示的值」和「已提交的值」；「空」是一种合法状态，不能顺手压成 0。
