# 开箱即用：为什么「有内容」不等于「用户看得见」

一个本地优先的桌面 AI 应用，第一次启动时最容易被忽略的体验是「空」：知识库是空的，工作流列表只有几个内置项且没说明来源，MCP 要用户自己去查命令，技能面板只能看不能加。功能都在，但用户不知道从哪开始。

「开箱即用」经常被理解成「多塞几个示例」。真正做过一轮才发现，它由三件事组成：**有内容、看得见、加得上。** 缺任何一件，前面做的都等于零。

## 一、先分清四种「没有」

| 状态 | 表现 | 该修的是 |
|---|---|---|
| 真空 | 知识库零播种，首启只有「创建」按钮 | 内容 |
| 有但不可见 | 工作流 starter 已播种并发布，列表空态却不提来源 | 露出 |
| 有入口但门槛高 | MCP 只能手填命令、参数、传输方式 | 入口 |
| 有数据但无操作 | 技能只列、只能全局启停，没有加载新技能的路径 | 操作 |

四种状态的修法完全不同。把它们混成一句「体验不好」，最后只会做出一个更漂亮的空页面。

## 二、知识库模板：固定 id、幂等、删除后不复活

知识库这一轮补了 3 个模板：产品需求、会议纪要、研究资料。定义放在 shared 包的常量里，core 包提供一个启动时调用的播种函数。

关键不在「建三个库」，在**播种判据**。

最自然的写法是「id 不存在就创建」。它会让两个用户行为变得很糟：用户把模板改名，下一次启动发现 id 还在，不会覆盖——这一步没问题；用户把模板删了，下一次启动发现 id 不在，又建一个——**删除变成了「下次再说」**。用户越想清理，应用越坚持。

所以判据不能是「id 在不在」，而是「这批模板播过没有」：

```text
if (seeded('kb-starters')) return
for (t of KB_TEMPLATES):
  if (!exists(t.id)) create(t)
markSeeded('kb-starters')
```

- 全新安装：没有播种记录，创建三个模板，记一笔；
- 用户改名：id 存在，播种逻辑不碰它；
- 用户删除：播种记录还在，不重建；
- 后续新增模板：换一个批次标记，只补新批次，不回填旧批次。

这和内置角色卡、内置工作流的策略是同一套：**固定 id + 幂等 + 不覆盖用户改动**。固定 id 让「是不是同一个东西」可判断，幂等让重复启动安全，批次标记让「删除」成为用户的最终决定。

「幂等」在这里不是一句口号，它有一个很具体的边界：重复执行不能改变结果，但**用户主动造成的缺失**也不该被「修复」。这两件事看起来相反，区分它们的唯一办法是把「播种过」和「当前存在」分开记录。

## 三、模板不带样本文档：一个反直觉的取舍

模板最容易顺手带一份「示例文档」，让用户点进去就能看到内容。这一轮明确不带。

原因是本地优先应用的备份模型：备份就是数据目录的一份拷贝。模板带文档，意味着每个用户的每一次备份都多背几份他可能永远不看的示例；模板越多、文档越大，膨胀越明显。用一次性的「好看」换长期的存储成本，不划算。

所以模板只预填三样东西：名称、说明、推荐的分块参数。新建对话框提供「从模板开始」，用户选一个，得到的是一个**结构正确但内容为空**的库。

这也划清了开箱即用的边界：**给结构，不替用户产生内容。** 知识库的价值在用户自己的资料，模板的作用是让他不用纠结「分块大小填多少」。

## 四、工作流：从 3 个到 6 个，并把来源写进空态

工作流原本有 3 个内置 starter（资料研究助手、周报流水线、网页摘要器），启动时幂等播种并发布，播种后直接成为对话里可调用的 `flow:<id>` 工具。问题不是数量，是**用户不知道它们是内置的**。

这一轮做了两件事：

- starter 扩到 6 个，新增会议纪要整理、竞品对比、知识库问答；
- 列表空态不再只说「创建」，而是说明这些流程来自内置模板，并给出「从模板创建」的入口。

新增的三个不是随便凑数，它们分别对应三种高频场景：把一场会议变成结构化记录、把多个对象放在同一张表里比较、把知识库检索包装成一次问答。模板名本身就是说明书。

沿用同一套播种策略：固定 id、幂等、不覆盖用户改动。工作流播种后会发布并成为对话里可调用的 `flow:<id>` 工具，因此幂等不只关乎列表，还关乎对话里可见的工具集合。

## 五、MCP：把「查命令」变成「选一个」

MCP 原来的添加流程是一张空表单：命令、参数、传输方式全靠用户自己填。对熟悉这套协议的人是自由，对第一次用的人是门槛。

补的是 4 个预置项：filesystem、fetch、git、memory。每一项包含推荐命令、参数占位、用途说明和风险标注，点一下填入表单，用户仍然可以改。

填入之后还有一步「测试连接」：服务端重连并等待终态，成功给成功，失败给排查提示（命令不存在、路径不可读、启动超时之类）。没有这一步，用户填完只能靠「对话里试一下」来验证，失败时也不知道错在哪。

需要强调的是：**预置目录只降低填写成本，不绕过任何确认。** MCP 的权限确认、黑名单、启停策略一条没改；一键填入的是表单，不是授权。

## 六、技能：为什么是「重新扫描」，不是「上传」

技能在这套应用里本来就是数据目录下的一个文件夹。用户把技能放进去，应用应该能看见——这是「加载」，不是「导入」。

所以技能面板给的动作是「重新扫描」：服务端做一次 reconcile，扫描目录、校验、加载，不需要重启。它解决的问题是「我已经有了，但应用还不知道」。

没有做上传导入，原因是安全面：上传意味着新增一条「把外部字节写进本地目录」的通道，路径、覆盖、权限都要重新设计。而用户真正的需求往往只是「让我放好的文件夹生效」。用扫描代替上传，功能等价，攻击面不增加。

面板文案也统一成全局口径：技能是全局启停的，不绑定到某个助手。之前内置技能描述里「再让助手启用本技能」的说法与实现不一致，这一轮先把话说对，助手级绑定留到后续。

## 七、露出策略：模板要出现在动作发生的地方

内容做完了，最后一公里是「在哪儿出现」。这一轮的规则很简单：**用户正准备做这件事的地方，就是他愿意看模板的地方。**

| 场景 | 入口位置 | 默认行为 |
|---|---|---|
| 第一次进知识库 | 列表空态 + 新建对话框 | 已备 3 个模板，可改名、可删除 |
| 找工作流 | 列表空态说明 + 模板入口 | 6 个 starter 已播种并发布 |
| 添加 MCP | 添加表单内的预置目录 | 一键填入，仍需确认 |
| 加载技能 | 技能面板「重新扫描」 | 扫描数据目录下已有文件夹 |

三条原则：默认可用但不强制（不选模板也能建空库）、可撤销（改名删除都是最终决定）、就地露出（不把模板藏进「关于」或独立市场页）。

## 八、小结

- **幂等不等于 `if not exists`。** 要区分「没播过」和「被删了」，否则用户的删除会被下一次启动推翻。
- **开箱即用的成本要可控。** 模板给结构不给内容，是对本地备份体积的尊重。
- **入口比功能更能决定感知。** 三个 starter 一直在，用户看不见就等于没有；四个预置项本身不新，但把「查命令」变成「选一个」，门槛就消失了。

这一轮留下的最有用的一句话是：先问「用户第一次打开时，眼前有什么、下一步点哪里」，再决定要写多少功能。
