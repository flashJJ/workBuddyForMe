# 治理要被看见：授权、策略与证据如何落到界面

治理能力如果只存在于后端，用户感受到的只会是「怎么又要确认」和「怎么突然被拒绝」。我们的桌面 AI 应用是单人使用的私人助手，没有管理员，也没有审计部门；唯一会看治理界面的人，就是设置它的那个人。

所以这一版做 UI 的标准不是「功能齐全」，而是：**每一个决定，都能在界面上找到它来自哪里；每一次执行，都能查到它为什么被允许或拒绝。**

## 任务启动：先选约束，再点开始

任务启动对话框多了三样东西：执行模式、工作目录、策略摘要。

五档模式各有说明，不是五个缩写：

| 模式 | 用户看到的含义 |
|---|---|
| `confirm_each` | 每次写操作都问（默认） |
| `auto_edits` | 目录内的编辑自动放行，目录外仍问 |
| `smart_approve` | 目录内编辑自动放行，高危操作仍需确认 |
| `plan_only` | 只读、只出计划，不做任何变更 |
| `full_access` | 本次运行完全放行，需二次确认 |

默认是 `confirm_each`，和上一版的实际行为一致。升级后用户不会突然被要求更多确认，也不会突然被放开权限——这是默认档最重要的兼容性。

`full_access` 的二次确认不是前端弹窗了事。API 必须收到显式的确认字段，缺失直接 422。原因很直白：前端可以绕过，服务端不能假设调用方是界面。

工作目录是可选的。选了，文件与命令类操作就被限制在目录内；不选，涉及路径的写操作在自动模式下会降级为询问。界面上会显示路径是否通过校验，而不是等运行时再报错。

## 任务详情：一次运行要能自解释

任务详情显示四样东西：模式、工作目录、策略哈希、来源定时任务，并提供到对应审计事件的入口。

为什么是这四个？因为用户回看一次运行时的疑问通常是连续的：它按什么规则跑的、在哪个目录、当时策略是哪一版、是不是定时触发的。只显示「成功 / 失败」，等于把四个问题都推给日志。

策略哈希尤其重要。设置页的策略会变，运行详情里的哈希不会变；两者对不上，说明这次运行用的是旧快照。这个差异不该靠人记住时间线，应该在界面上直接可见。

来源标记把「手动点开始」和「到点自己跑」区分开。两者失败的处置方式不同：前者可能当场就能问，后者只能等下一次看结果。混在一个列表里，会让人误判。

## 设置页：策略是可编辑的，也是可导出的

设置里新增一组 Agent 治理：默认模式、无人值守允许模式、工具 allow/deny、路径根、域名 allow/deny、命令规则、运行限额。

这一组刻意不做图形化规则编排。规则就是列表：精确名、后缀通配、域名前缀、可执行文件名。复杂表达式能表达更多，也会让「这条为什么被拒」变得难以解释。单机个人场景，可解释性比表达力更值钱。

保存时做三件事：Zod 校验、计算策略哈希、写一条 `policy_updated` 审计。界面显示当前哈希，方便和运行详情、审计事件对上。

支持 JSON 导入导出。导入失败不落盘，不会出现「导了一半」的中间状态。多标签页并发保存沿用设置页既有行为，这一版没有为策略单独做乐观锁——知道边界，比假装没有更实际。

## 审批中心：批准的是具体操作，不是一句话

审批项现在展示结构化摘要：工具、级别、参数摘要、工作目录、目标窗口或进程、策略来源。

关键在「策略来源」四个字。用户需要知道这次为什么问：是默认询问，是模式要求，还是策略里某条规则命中。只写「需要确认」，等于把判断依据藏起来。

审批通过后并不是直接执行。执行前会重算绑定：参数哈希、cwd、环境哈希、文件操作数、目标窗口、策略哈希。任一字段变了，返回 409 并审计。界面上会显示漂移提示，而不是让用户以为「点过允许就一定能跑」。

「允许一次」只对当前绑定生效；「记住」沿用既有的长期授权语义。这两者的区别必须在文案上说清，否则一次放宽会被误解成永久放宽。

## 审计页：只读账本，没有删除按钮

审计页进入时先校验一次链状态，显示一个徽章：完整，或断在第几条。支持按时间、事件类型、运行 ID 过滤，游标分页，倒序展示。

详情里能看到：事件类型、决策、原因码、策略哈希、绑定摘要、当前事件哈希与前序哈希。JSONL 导出走流式下载，升序、每行一条 canonical JSON，便于外部归档和比对。

**没有删除，没有编辑。** 这不是没来得及做，而是账本的定义：可删除的账本不是证据。保留完整链，归档方案后置，是这一版明确接受的成本。

链状态徽章不是装饰。用户点开审计页的第一眼，应该知道这份账本还能不能信；如果断了，断在第几条，从那里往后的事件都不再具备链上证明。完整时刻意不喧哗，断链时足够显眼，是唯一合理的优先级。

筛选按事件类型分组，而不是把所有 kind 平铺。策略变更、策略拒绝、审批、漂移、运行生命周期、定时触发、无人值守拒绝，各是一类。分类展示降低的是阅读成本，不改变账本内容。

## 定时任务表单：Agent 字段与类型锁定

新建定时任务时，可以选「提醒」或「Agent 任务」。选后者会展开目标、会话、模式、工作目录、通知方式。

模式下拉只列出策略允许无人值守的档位，`full_access` 不出现。即使有人绕过前端直接调 API，服务端仍会返回 422。前端做的是减少误操作，服务端做的是保证边界。

编辑已有任务时，类型锁定并显示说明：提醒不能就地改成 Agent 任务。要换只能新建。这条限制在 UI 上会让人觉得麻烦，但它保护的是历史语义——过去的时间线不能被一次编辑重新解释。

列表里 Agent 任务带标记，和提醒区分开。用户一眼能看出「这条到点会执行」，而不是「这条到点会响」。

这几个入口遵守同一个原则：能在创建时拒绝的，不留到运行时报错；能显示来源的，不要求用户记住。界面的价值不是把治理画得好看，而是把「谁批准了什么、依据是什么」变成可见的事实。

## 治理 UI 的取舍

这一版在界面上做了三个明确取舍：

1. **账本只读**。不做删除、不做编辑，甚至不做「标记为已处理」。代价是界面会越来越长，收益是证据链不被产品交互污染。
2. **分类而非聚合**。不做「治理评分」「风险仪表盘」。评分需要一套解释模型，单人应用没有维护它的余量；分类列表至少每条都能点开看清。
3. **展示摘要而非全量**。审批中心不传完整参数和环境变量，只传哈希与摘要。用户需要判断「这是不是我要的」，不需要看到密钥原文。

还有一条隐性的取舍：治理界面不追求「让用户少做决定」。该问的时候问，该拒绝的时候拒绝，把原因写清楚。顺畅不是目标，可解释才是。
