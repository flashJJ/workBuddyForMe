# 双端调度与运行时限额：让该跑的一端跑，让该停的停在边界上

定时任务能跑 Agent 之后，第一个架构问题不是「怎么跑」，而是「谁去标记」。我们的应用有两个天然的 tick 位置：Web 服务端常驻循环，和渲染进程里的每 10 秒扫描。两边都能看见同一张 `scheduled_tasks` 表，两边都能调用同一个 `markFired`。

上一版只有渲染进程一个 tick，所以没人想过这个问题。现在服务端接管了 Agent 任务，如果两边都不加区分地扫全表，就会出现同一时刻两边都认为「这条该我跑」：一个先标记成功，另一个标记失败但可能已经把运行创建出来了，或者反过来，标记成功的一方还没开始投递，另一方已经跳过。结果不是重复执行，就是丢掉一次运行。

## 分流规则：按 payload 种类分家

规则很短，但要落到两端：

- **服务端只接管 `agent_task`**：每 10 秒扫描到期项，`markFired` 后直接启动任务；
- **渲染进程只处理提醒和 `follow_up`**：`/api/schedules/due` 在服务端就把 `agent_task` 过滤掉，渲染端根本看不见它们。

这样一来，同一条记录在任意时刻只有一端会尝试标记，抢标记的窗口从「两端并发」缩成了「单端串行」。剩下唯一的并发来源，是同一端内部的重复触发，这由「先标记后投递」兜住。

过滤放在服务端而不是渲染端，是有意的：如果渲染端拿到 `agent_task` 再自己判断「这个不该我管」，判断代码就多了一份，未来加第三种 payload 时还要记得改两处。让不该出现的记录从一开始就不出现在响应里，比让消费方自律更可靠。

## 为什么还留着渲染进程的 tick

有人会问：既然服务端已经常驻，为什么不把渲染 tick 删掉，只留一个调度器？

因为两端的可用性前提不同。服务端循环依赖 Web 服务被初始化；渲染 tick 依赖页面存在。删掉渲染 tick，等于把所有提醒的触发也押在服务端初始化成功上。提醒是旧能力，不能为了新能力改变它的失败模式。

保留它，同时用分流保证它们不碰同一批记录，是一种低成本的冗余：提醒继续走原来的路径，Agent 任务走新的路径，两边的故障不会互相放大。

这也解释了为什么服务端 tick 还要保留旧 `/due` 里的关系检查点和里程碑扫描副作用。调度主体换了，但那些与提醒共用的副作用不能悄悄消失，否则「只是把 Agent 任务接进来」会变成一次不易察觉的行为回退。

两端的分工可以列成一张表，边界就很清楚：

| 事项 | 服务端循环 | 渲染进程 tick |
|---|---|---|
| 扫描范围 | 只扫 `agent_task` | 只扫提醒 / `follow_up` |
| 标记 | `markFired` | `markFired` |
| 投递 | 创建运行并后台启动 | 发出提醒 / 通知 |
| 审批 | 挂起，等审批中心 | 不涉及 |
| 终态 | WorkSignal + 审计 | 沿用旧通知口径 |
| 跳过 | 写 `unattended_blocked` | 沿用旧跳过逻辑 |

这张表也解释了一个容易混淆的问题：并发上限只统计无人值守的 Agent 运行，不是所有任务运行。手动启动的任务、聊天触发的工具调用，都不占这个名额。检查发生在启动前，不是创建运行后；不通过就不创建，避免出现「先建了再取消」的中间状态。

## 先标记后投递：幂等的唯一抓手

顺序是 `listDue -> markFired -> deliver`，不是 `listDue -> deliver -> markFired`。差别在失败时的语义：

| 顺序 | 投递前崩溃 | 投递后崩溃 |
|---|---|---|
| 先投递后标记 | 可能重复投递 | 标记丢失，下次还会再跑 |
| 先标记后投递 | 这次不跑（错过即跳过） | 不会重跑 |

我们选后者。单机场景里，「这一次没跑」比「同一次跑两遍」可控得多：前者是可见的缺失，后者可能产生两份写入、两条通知、两次外部调用。先标记等于把「是否已经触发」变成一次原子声明，投递只是声明的后果。

代价也要认：如果标记成功、投递前进程被杀，这次触发就永久丢失，不会补跑。这与「错过即跳过」的产品口径一致，不是意外。

## 运行时限额：四个计数器长在任务循环里

策略里有一组限额，真正强制的地方不在 API，而在任务循环的每一轮：

| 限额 | 默认 | 累计方式 | 超限结果 |
|---|---|---|---|
| 步数 | 20（1–50） | 创建时取 `min(payload.maxSteps, 全局上限, 策略上限)` | 既有 `max_steps` 终止 |
| 运行时长 | 10 分钟 | 每轮检查 `createdAt + maxRuntimeMs` | `stopped / policy_limit` |
| 写入次数 | 100 | 工具执行前按 `permission='write'` 累加 | `policy_limit` |
| 外部调用 | 20 | `source='mcp'` 或网页抓取工具累加 | `policy_limit` |

四个计数器都只活在本次运行的内存里。为什么不落库？因为它们是「本次运行的预算」，不是长期事实。步数上限仍然只以 `task_runs.max_steps` 为唯一持久值，其他三个每次启动重新从零开始。这样即使进程重启，也不会出现「上次用掉 60 次写入，这次只剩 40 次」这种无法解释的余额。

写入计数放在工具执行前而不是执行后，是为了在越界的那一次就拦住，而不是先写进去再发现超额。外部调用按工具来源粗分，MCP 和网页抓取算一类，浏览器工具接入后也进同一个计数。粗分的代价是精度，收益是规则简单、可解释。

## 超限为什么收敛到 `policy_limit`

停止原因是枚举，不是自由文本。超限一律收敛到 `policy_limit`，不细分「步数超了」还是「时长超了」。细分信息放在审计和运行详情里，枚举本身保持稳定。

这样做的好处是：上游只需要判断「是不是策略性停止」，不需要为每一种限额写一个分支。用户看到的也是同一句话——「本次运行达到了策略限额」——而不是四套文案。

## 时间从运行创建起算的取舍

时长限额的起点是 `task_run.createdAt`，不是「开始执行」的时刻。这带来一个真实副作用：一个排队很久的手动任务，可能刚开始跑就接近时限。

我们接受这个取舍，原因是实现简单且语义一致：`createdAt` 是运行的出生时间，运行的生命周期就该从那里算。如果改成「首次进入循环」再计时，就要额外记录一个启动时间，还要处理暂停、恢复、重排后的重置规则，复杂度不值得。

但边界要写清楚：定时任务基本都是即时启动，受影响的主要是长时间排队的手动任务。文档里点明这一点，比让用户自己撞上再猜更体面。

## 超限之后发生什么

超限不是崩溃，而是一次正常终态：运行以 `stopped` 结束，停止原因是 `policy_limit`；这次运行仍然写 `run_finished`，如果是定时任务，还会写 `scheduled_run_finished` 并发出 WorkSignal。用户看到的是「跑到了限额」，不是「系统坏了」。

这条路径必须走通。否则限额会变成一种新的静默失败：计数器生效了，运行停了，但没有留下任何可读的结果。治理里的「停」和「拒绝」一样，都要有明确的落点。

## 限额不是沙箱

最后提醒一句：这些限额控制的是「Agent 主动做了多少次」，不是「它能碰什么」。真正的边界仍然在工作目录、策略 deny、审批绑定和进程隔离上。限额负责让失控的运行停下来，不负责证明它没做坏事。
