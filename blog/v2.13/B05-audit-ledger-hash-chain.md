# 审计账本：给 Agent 的执行留一条可校验的哈希链

产品里原本有两张「时间线」：任务步骤表记录每一步做了什么，会话事件表记录会话里发生了什么。它们都很有用，但回答不了治理问题——**谁在什么策略下允许或拒绝了什么**。

举个具体例子：用户发现 Agent 删了一个文件。翻任务步骤，只能看到「执行了删除工具」；翻会话事件，只能看到「工具调用成功」。至于这次调用是被哪条策略放行的、有没有经过审批、审批时绑定的参数后来有没有变，这些信息根本不存在。所以要有一本独立的账本。它不是业务日志的补充，而是治理证据的唯一载体。

## 两种时间线，别混在一起

| | 业务时间线 | 治理账本 |
|---|---|---|
| 表 | 任务步骤 / 会话事件 | `audit_events` |
| 回答 | Agent 做了什么 | 谁允许的、依据什么、是否漂移 |
| 写入 | 业务流程各点 | 策略、审批、绑定、运行生命周期 |
| 完整性 | 无哈希链 | 逐条哈希，可校验 |
| 删除 | 按保留期清理 | 不提供删除与修改 |
| 用途 | 界面回放、调试 | 事后追责、合规导出 |

会话事件本身是追加式、可按范围查询、保留 180 天，听起来和账本很像。差别在于它没有链：删掉中间一条，剩下的记录仍然「看起来正常」。治理账本要解决的正是这一点。

## 表结构

一次纯加法迁移，新增一张表与三个索引：

```sql
CREATE TABLE audit_events (
  id              TEXT PRIMARY KEY,
  seq             INTEGER NOT NULL UNIQUE,
  created_at      TEXT NOT NULL,
  kind            TEXT NOT NULL,
  actor           TEXT NOT NULL,   -- user / agent / system
  run_id          TEXT,
  conversation_id TEXT,
  tool            TEXT,
  decision        TEXT,            -- allow / deny / ask
  reason_code     TEXT,
  policy_hash     TEXT,
  binding_json    TEXT,
  outcome         TEXT,
  prev_hash       TEXT NOT NULL,
  hash            TEXT NOT NULL
);
CREATE INDEX idx_audit_created ON audit_events(created_at);
CREATE INDEX idx_audit_run     ON audit_events(run_id);
CREATE INDEX idx_audit_kind    ON audit_events(kind);
```

`binding_json` 存的是绑定摘要，不是原始参数；`policy_hash` 指向当时那版策略；`outcome` 对运行事件记模式或终态原因。字段设计围绕一个原则：**能证明判断依据，但不复制业务数据**。

## 事件种类

账本记录的不是所有日志，而是治理动作。按场景分四组：

| 组 | 事件 |
|---|---|
| 策略 | `policy_updated`、`policy_denied` |
| 审批 | `approval_requested`、`approval_granted`、`approval_denied`、`approval_timeout`、`binding_drift` |
| 运行 | `run_started`、`run_finished`、`scheduled_run_started`、`scheduled_run_finished`、`unattended_blocked` |
| 完整性 | `audit_verified` |

运行开始事件在 `outcome` 里写 `mode:<模式>`，`policy_hash` 取自运行创建时的策略快照；运行结束写 `status[:stopReason]`。这样单看两条事件，就能知道这次运行为什么被允许、为什么停下。

## 哈希链：一条公式与一个起点

```text
hash = sha256(prev_hash + "\n" + canonicalJson(事件去掉 hash 与 prev_hash))
```

首条的 `prev_hash` 固定为 `GENESIS`。每条事件的内容哈希覆盖除 `hash` 与 `prev_hash` 之外的全部字段，再把上一条的哈希拼进输入。于是任何一条被改动，它的 `hash` 会变；下一条的 `prev_hash` 就对不上，断链从这里开始。规范化 JSON 仍然是前提：键递归排序、数组保序、拒绝非有限数字与函数。否则同一份事件换个构造顺序就会算出不同哈希，校验会误报。公式里特意加了 `\n` 分隔符，让 `prev_hash` 的尾部与事件 JSON 的开头有明确边界。

## seq 与追加事务

`seq` 是单调递增的整数，不是自增主键。追加时在同一次同步调用里完成三件事：

```text
读链尾（max(seq) 与最后一条 hash）
→ 计算 seq = max(seq) + 1
→ 计算 hash，插入
```

`seq` 上有唯一索引，作为并发写入的兜底。数据库驱动是同步执行的，单进程内天然串行，所以这个「读—算—写」不会被打断。两条硬规则：不允许先插入再补哈希，不允许跳过 `seq`。前者会留下一个窗口期，后者会让「连续性校验」失去意义。任何为了性能而放松这两条的做法，都会让账本退化成普通日志。

## 校验：按序重算，返回首个断链

校验接口按 `seq` 升序扫描，对每一条做三件事：

1. 检查 `prev_hash` 是否等于上一条的 `hash`；
2. 用同样的公式重算内容哈希，与存储的 `hash` 比对；
3. 检查 `seq` 是否连续（没有空洞）。

任何一项失败，立即返回首个断链的 `seq`，响应形如 `{ ok, checked, firstBrokenSeq? }`。返回「首个」而不是「全部」，是因为链式结构一旦断开，后面的哈希全部失去可信基准，继续报告没有意义。校验本身也追加一条 `audit_verified`。这带来一个副作用：审计页进入即校验时，账本会多一条记录。它是契约行为，不是重复写入的 bug。

## 查询与导出

查询按时间闭区间、事件类型、运行 id 过滤，`seq` 游标倒序翻页，单页上限 200；校验是一个只读语义的 POST，返回链状态；导出是 JSONL 流式输出，升序，每行一条规范化 JSON。导出用流式而不是一次性拼字符串，是为了账本变大时不把内存打满。每行都是规范化 JSON，外部工具可以逐行重算哈希，独立验证这份导出没有被改过——这让「导出归档」真正具备证据价值，而不只是备份。

## 只追加，且这一版不清理

账本不提供删除、修改的 API 与界面。界面上没有删除按钮，不是漏做，而是刻意不提供。清理同样不做。按天删除旧事件会直接把链剪断，剩下的部分再也无法证明完整性。产品上的取舍是：先保留完整账本，归档方案后置；需要长期保存时，导出 JSONL 到外部存储。

## 写入失败：不同事件，不同代价

| 事件类别 | 写入失败处置 |
|---|---|
| 策略拒绝、审批请求与结果、绑定漂移 | fail-closed，拒绝操作，返回 `AUDIT_UNAVAILABLE` |
| 运行生命周期 | 告警后继续运行 |
| 策略变更 | 告警后继续保存 |

为什么不全 fail-closed？因为「记不下来就不许跑」对生命周期事件过于苛刻——一个审计磁盘问题会让所有任务无法启动。反过来，治理判断本身必须 fail-closed：如果「这次拒绝」没能留痕，事后就无法证明系统执行过治理，账本的核心承诺就破了。账本内容也有硬约束：不存密钥、不存完整环境变量、不存完整参数值。只存哈希、摘要、原因码与策略哈希。

## 尾部截断：必须说清的诚实边界

哈希链能发现中间篡改、内容改动、序号空洞，但**发现不了尾部截断**。如果攻击者把最后 N 条事件整段删掉，剩余部分仍然是一条自洽的链：最后一条的 `prev_hash` 对得上，`seq` 连续，哈希全部正确。校验会返回 `ok`。

这不是实现缺陷，而是无锚点哈希链的数学边界。要覆盖它，需要外部锚点：定期把链尾哈希导出到别处、写入只追加的外部存储、或用签名把「截至某时刻的链尾」固定下来。这一版没有做，所以必须在文档和产品文案里如实写出来。还有一层更朴素的边界：数据库文件就在本机，同用户的进程或拿到磁盘的人可以直接改库。账本防的是「静默篡改后仍然冒充完整」，不是「有权限的人无法篡改」。前者靠密码学，后者要靠 OS 级隔离——那是另一个量级的事。

## 收口

这本账本只做了三件事：每条事件可重算、断链可定位、整本可导出。它们分别对应三个问题——这条记录还是原来的吗、从哪条开始不对、能不能拿到外部独立验证。

治理的闭环到这里才真正合上：模式决定态度，目录限定范围，策略给出依据，绑定保证同一性，账本留下证据。五者缺一，前面所有的「拒绝」都只是一次没有记录的行为。
