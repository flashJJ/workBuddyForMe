# Agent 的网页能力，为什么不能借用你的浏览器登录态

让 Agent 操作网页，最省事的做法是接上用户常用的浏览器：已经有登录态、有 Cookie、有书签，打开就能用。很多自动化方案就是这么做的。我们一开始也认真考虑过，最后明确拒绝。

原因不是技术难度，而是授权范围。用户的浏览器登录态是一份覆盖了邮箱、代码托管、支付、社交的长期凭证。Agent 的一次网页任务，可能只是「打开某个文档读一段内容」，没有理由附带用户全部在线身份。一旦共享，任务里的一次误点击、一个被注入的页面指令、一次失控的重定向，都会以「你本人」的身份发生。

这一版的选择是：每次任务运行开一个独立的、临时的浏览器会话，可见、可观察、用完即弃。

## 隔离会话长什么样

桌面壳基于 Electron，创建独立的 `BrowserWindow`，并给它一个非持久化的 `session` 分区：

- 每个 `runId` 一个窗口、一个分区；
- 不导入主浏览器 Cookie，不读取主浏览器配置；
- 分区不持久化，运行结束就清理 storage 和 cache；
- 窗口可见，用户能看到 Agent 在点什么、在输什么。

「可见」是刻意设计，不是没做离屏。让自动化在用户眼前发生，本身就是一层监督：不需要理解日志，看到窗口跳来跳去就知道它没闲着。

用户在隔离窗口里手动登录，可以，但只在该次运行内有效。关掉即失效，不能跨运行续用。这是能力的边界，也是隐私的边界。

## 六个工具，不做万能入口

浏览器能力只开放六个工具：

| 工具 | 级别 | 能做什么 |
|---|---|---|
| `browser_open` | danger | 打开 http/https 页面 |
| `browser_read` | read | 读取页面纯文本，默认 8000 字符、上限 20000 |
| `browser_snapshot` | read | 截图，长边不超过 1568，供视觉模型观察 |
| `browser_click` | danger | 按选择器或可见文本点击 |
| `browser_type` | danger | 按选择器或占位文本输入，可先清空 |
| `browser_close` | read | 关闭会话并清理 |

没有 `browser_eval`，没有任意脚本执行，没有文件上传下载，没有读取本地文件。这不是「暂时没做」，而是不开放：网页任务一旦能执行任意脚本，前面的协议、域名、审批约束都可以被绕过，治理模型会退化成一句口号。

所有工具都必须携带 `runId`。聊天场景没有运行上下文，调用会返回「仅在任务运行中使用」的说明，并且标记为 `ok: true`，不计入熔断失败。降级不是错误，不该被统计成故障。

## 网络边界：协议、地址、域名，逐层过

一次导航要过三道检查，顺序固定：

1. **协议白名单**：只允许 `http:` / `https:`；`file:`、`data:`、`javascript:`、`blob:` 一律拒绝；
2. **地址检查**：回环、私网、链路本地地址走既有 SSRF 防护，不允许借浏览器访问本机服务；
3. **域名规则**：策略里的 `domains.deny` 优先，`domains.allow` 非空时才收敛到命中项。

检查放在两层：core 在发起前先做 URL、DNS 与 SSRF 校验；桌面壳在导航事件里再按域名规则复核。为什么重复？因为 core 管的是「请求是否合理」，桌面壳管的是「窗口实际去了哪里」。后者是最后一道，不能假设调用方永远正确。

域名匹配支持完整域名和 `*.` 前缀，端口必须显式。deny 优先意味着：即使某个域名同时在 allow 和 deny 里，结果也是拒绝。不做「后写覆盖前写」这种依赖顺序的语义。

## 重定向是第二个入口

只检查初始 URL 是不够的。一个允许的域名可以 302 到任意地址，包括私网和内网服务。所以 `will-redirect` 处必须再判一次：协议、私网字面量、域名 allow/deny。命中拒绝就中止导航，并写一条 `policy_denied` 审计。

这里有一个必须诚实说明的边界：重定向阶段只复核域名与 IP 字面量，没有对重定向目标再做一次 DNS 私网解析。也就是说，针对 DNS rebinding 的解析时校验只发生在首次打开。要做得更严，需要在 `will-redirect` 里异步解析目标地址；这一版没做，并在已知边界里写明。

写清楚比假装没有更安全。用户知道边界在哪，才能决定要不要把某个域名放进 allow。

## 下载、弹窗、新窗口：一律关掉

网页任务不需要这些能力，开放它们只会扩大攻击面：

- `will-download` 直接取消，不产生文件；
- 权限请求（摄像头、麦克风、通知、地理位置等）全部拒绝；
- `setWindowOpenHandler` 拒绝新窗口；
- 外部协议唤起一律拦截。

新窗口的处理特别值得说。很多站点用 `window.open` 打开登录页或支付页，如果放行，Agent 就会跑到一个没有域名规则约束的新窗口里。拒绝或回收进同一会话，才能保证「所有导航都经过同一套检查」。

## 终态关闭：治理要管到生命周期末尾

会话不是开完就忘。任务运行进入终态、用户急停、或应用退出，都必须关闭窗口并清理分区：

- 正常运行结束，由任务运行服务的 `finish` 调 `browser_close`；
- 急停同样走关闭路径；
- 应用退出时再由 `closeAll` 兜底。

清理的不只是窗口，还包括 storage 和 cache。否则「临时会话」会变成事实上的持久会话，下一次运行可能继承上一次的登录态，隔离就名存实亡。

## 纯 Web 模式：不伪造能力

桌面壳才有浏览器控制通道。纯 Web 模式没有这条通道，调用会返回明确的不可用说明，而不是报一个看起来像网络错误的东西。更不会计入熔断失败——能力不存在，不该被当成能力故障。

这和桌面键鼠工具的降级口径一致：通道不可用，就给一句人话，告诉用户「这个能力需要桌面端」。

## 这一版做到哪，没做到哪

做到了：独立临时会话、可见窗口、六个受限工具、协议/私网/域名/重定向检查、禁下载禁弹窗、终态清理、纯 Web 降级。

没做到：DNS rebinding 的重定向二次解析、跨运行续用登录态、离屏渲染、任意脚本执行。每一条都写进了已知边界，而不是留给用户自己发现。

治理的诚实，往往不体现在「我们拦住了什么」，而体现在「我们明确说没拦住什么」。
