# 可治理的 Agent：单机助手也需要一套执行治理

一个本地优先、单人开发、桌面交付的私人 AI 应用，默认拿着整台机器的权限：读写用户选中的目录、启动外部代理进程、模拟键盘鼠标、打开浏览器窗口。早期我们给工具打了三级标签——`read` / `write` / `danger`，授权按「工具 × 助手」记住，写操作与高危操作在执行前挂起，等用户在审批中心点一下。这套机制跑了很久，也没出过事故。

但「没出过事故」不等于「有治理」。真正复盘时会发现五个空洞：

- 权限只有工具级，没有「本次任务要多严」的执行档位；
- 没有工作目录，文件与命令类操作能落到哪里，全靠工具自觉；
- 审批只记工具名和一段参数摘要文本，通过之后执行路径不再比对；
- 没有独立账本，业务时间线回答不了「谁在什么策略下拒绝过什么」；
- 定时任务只会提醒，不能无人值守地跑一次 Agent。

这一版的主题，就是把治理对象从「工具能不能用」推进到「这一次执行怎么被允许、被约束、被证明」。

## 一次执行要回答的四个问题

| 问题 | 早期答案 | 治理后的答案 |
|---|---|---|
| 谁允许的 | 一条模糊的长期授权记录 | 策略层、模式、授权各自出决策，带原因码与策略哈希 |
| 允许到什么范围 | 工具级，没有路径概念 | 工作目录 + 路径 / 域名 / 命令规则 |
| 批准的是不是正在跑的那次 | 一段参数摘要文本 | 七字段操作指纹，执行前重算 |
| 事后能不能证明 | 产品时间线 | 追加式哈希链账本，可校验、可导出 |

再补一条：出事时能不能止损。答案是超时即拒绝、限额即终止、无人值守有白名单。

## 治理的五个面，加上两个新入口

| 面 | 解决什么 | 落在哪 |
|---|---|---|
| 执行模式 | 本次运行要多严 | 任务运行的 `permission_mode` 字段 |
| 工作目录 | 文件与命令能碰哪里 | `workspace_path` + realpath 双重校验 |
| 策略即代码 | 组织级的 allow / deny | 设置里的 `agentPolicy` + 运行快照 |
| 审批绑定 | 批准与执行是同一个操作 | `OperationBinding` + 409 漂移 |
| 审计账本 | 治理证据 | `audit_events` 哈希链 |
| 定时 Agent | 无人值守的执行 | `agent_task` 载荷 + 服务端调度 |
| 隔离网页 | 新边界下的能力 | 独立浏览器会话 + 六个工具 |

五个面是主线，后两个是新入口：定时任务把治理推到没有人在场的场景，隔离网页把治理推到应用之外的网络世界。两者都不是新能力，而是同一套约束在新场景下的延伸。

## 五档模式：从每步都问到本次全放

模式不改变工具分级，只决定本次运行如何对待某一级：

| 模式 | read | write | danger | 无人值守 |
|---|---|---|---|---|
| `confirm_each`（默认） | 允许 | 询问 | 询问 | 可，遇询问挂起 |
| `auto_edits` | 允许 | 目录内允许，目录外询问 | 询问 | 可 |
| `smart_approve` | 允许 | 目录内允许 | 命中 `dangerAllow` 才允许，否则询问 | 可 |
| `plan_only` | 允许 | 拒绝 | 拒绝 | 可（只读） |
| `full_access` | 允许 | 允许 | 允许 | 禁止 |

默认档等价于旧行为：只读放行，写与高危询问。`full_access` 必须由服务端收到确认字段才生效，只对本次运行有效，永不进入无人值守白名单；它也仍然受策略 deny 与系统硬拒绝约束，不是「无视一切」。

模式只作用于任务运行。聊天与协作 Agent 不单独选档，统一按策略里的默认模式求值，但策略、审批、审计在这些路径上同样全量生效。

## 工作目录：把「能碰哪里」变成可校验的路径

工作目录是可选参数，但一旦指定，文件写入、命令执行、外部代理的 cwd 都必须落在目录内。校验不是一次字符串比较：

1. 去空白、必须绝对路径、归一化盘符与分隔符；
2. 必须存在且是目录；
3. `realpath` 解析后再校验一次，符号链接指向目录外一律拒绝；
4. 拒绝盘符根、系统目录、用户主目录根、应用数据根与安装目录；
5. 运行前再查一次目录是否还在，消失就拒绝。

越界返回 `WORKSPACE_ESCAPE`，目录本身非法或消失返回 `WORKSPACE_INVALID` / `WORKSPACE_MISSING`。此外，`.ssh`、`.gnupg`、浏览器配置、密钥目录这类敏感目录，即使位于工作目录内也默认拒绝。

必须同时说清一句话：**工作目录不是安全边界**。它限制的是助手主动访问的范围，不防恶意代码；包内任意代码执行仍然禁止。

## 策略即代码：deny 永远优先

策略存在设置 JSON 里，覆盖工具、路径、域名、命令与运行限额。求值顺序固定为七层：

```text
系统硬拒绝 → 策略 deny → 权限记录 deny → 模式处置
→ 策略 allow → 持久授权 → 默认询问
```

任何一层 deny 都直接拒绝，后续不再求值。策略 allow 只能放宽 `write`，不能把 `confirm_each` 下对 danger 的询问变成允许；danger 的放宽只有两条路：`smart_approve` 命中 `dangerAllow`，或者本次 `full_access`。

策略保存时计算哈希，运行创建时把快照写进任务记录。这样复现一次历史决策时，不需要猜「当时是哪条规则」，只需要拿快照重放。

## 审批绑定：批准的必须是正在跑的那一次

审批项不再只有一段文本摘要，而是绑定一个结构化指纹：工具、参数哈希、cwd、环境哈希、文件操作数、目标窗口或进程、策略哈希。审批时算一次，用户允许后、执行前再算一次；任一字段变化就返回 409 `APPROVAL_BINDING_DRIFT`，拒绝执行并记账。

这解决的是一个很具体的漏洞：模型重试时重新拼了参数、审批等待期间用户改了策略、前台窗口换了——批准的和执行的可能已经不是同一个操作。

所有拒绝路径都是 fail-closed：超时、断线、没有审批 UI、审计写不进去，一律拒绝，并把结构化原因回灌给模型，避免 Agent 误以为执行成功。

## 审计账本：业务时间线不是治理证据

任务步骤与会话事件记录的是「Agent 做了什么」，属于产品时间线；治理要回答的是「谁在什么策略下允许或拒绝了什么」。后者需要独立账本：

```text
hash = sha256(prev_hash + "\n" + canonicalJson(事件去掉 hash 与 prev_hash))
```

账本只追加，`seq` 连续，首条 `prev_hash` 为 `GENESIS`；校验按序重算，返回首个断链位置；不提供删除或修改入口，支持流式导出 JSONL。写入失败时，策略决策、审批结果、绑定漂移这些关键事件 fail-closed，运行生命周期事件只告警后继续。

它也有诚实边界：哈希链能发现中间篡改与断链，但整表尾部被截断时剩余链仍自洽，需要外部锚点才能覆盖。这一点后面单独讲。

## 定时任务与隔离网页：治理延伸到无人值守和新边界

定时任务新增了 `agent_task` 载荷：目标、会话、模式、目录、通知方式。调度由服务端常驻循环每 10 秒扫描一次，先标记后投递，错过即跳过，不补跑；渲染进程的 tick 只作为兜底，避免双端抢同一条标记。

无人值守遇到需要审批的操作，会挂起进审批中心，5 分钟超时按拒绝；`full_access` 不进白名单；同一任务不并发，并发数受策略限额约束。所有边界都写进用户可见文案：应用进程退出后，不会「到点自己跑」。

隔离网页会话则是另一个方向：每次运行一个独立、非持久的浏览器会话，不共享用户主浏览器的登录态；只开放打开、读取、截图、点击、输入、关闭六个工具，不提供任意脚本执行；仅 http/https，域名规则 deny 优先，回环与私网地址走既有防护，重定向逐次复核，禁止下载、弹窗与新窗口。仅桌面端可用，纯 Web 模式明确降级。

## 为什么单机 Agent 反而更需要治理

云端产品的安全边界通常是「租户 + 网关 + 审计」，单机应用没有这层外力，Agent 的权限就是用户自己的权限。三个现实约束让治理成为必需品：

- **后果不可逆**：删错目录、点错按钮、发错请求，没有服务端回滚；
- **没有第二双眼睛**：单人开发，没有安全团队在每次执行前 review；
- **默认路径就是放宽**：如果治理只写在文档里，模型一次重试就能绕过。

所以治理不能是「设置页里的一个开关」，必须是执行路径上的一道道闸门：模式决定态度，目录限定范围，策略决定允许，绑定保证同一性，账本留下证据。

这一版收尾时，八包单测 2805 例通过。数字本身不说明治理有效，但它至少证明这些闸门接进了执行链路，而不是停在设计稿里。

治理不是把能力关掉。它让「放宽」变成一次可解释、可追溯、可拒绝的决定——这正是一个私人 Agent 能长期放心跑下去的前提。
