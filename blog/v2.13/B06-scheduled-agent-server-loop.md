# 定时任务从「只能提醒」到「能跑 Agent」：无人值守链路怎么收口

我们的桌面 AI 应用是本地优先的个人助手。早期的定时任务只做一件事：到点弹一条提醒。数据结构很薄，`payload` 里只有一个 `follow_up`，调度靠渲染进程每 10 秒扫一次。用户关掉窗口，提醒可以等下次打开再说——这没有问题，因为提醒的价值本来就在于「人看到」。

但当我们想让 Agent 在固定时间自己跑一次任务，这套假设立刻不成立：没人看着、没有页面、也没有交互。一个「只能提醒」的调度器，要变成「能执行」的调度器，缺的不是一个按钮，而是一整套对无人值守的约束。

## 谁在跑：先把调度从页面里搬出来

旧 tick 长在渲染进程里。页面在，tick 就在；页面关，tick 就停。对提醒来说这可以接受，对 Agent 任务则直接失效：无人值守恰恰意味着没有页面。

所以这一版把调度主体换成服务端：Web 服务初始化后挂一个 10 秒的常驻循环，单进程单例。循环本身很朴素：

```
listDue() -> markFired() -> deliver()
```

`listDue` 找到期任务，`markFired` 先把它标成已触发，`deliver` 再做实际投递。顺序不能反，后面会讲。

这里有个 Next.js 特有的坑：开发态热重载会重新执行模块，`setInterval` 如果没有兜住，就会注册出第二个、第三个循环。做法是把计时器挂到 `globalThis` 上，模块重复加载时先看有没有现成的实例，有就复用。不是靠「只执行一次」的注释，而是靠一个进程级变量。

还有一个容易被忽略的时序：这个循环不是进程启动瞬间就运行，而是在服务首次初始化时启动。也就是说，应用起来后要等第一个请求把服务拉起来，10 秒节拍才开始。这一点必须写进文档，否则「为什么刚开机没触发」会被当成 bug。

## 判别联合：两种任务共用一张表，但不能共用一套语义

`scheduled_tasks` 继续用同一张表，`payload` 从单一形状改成判别联合：

```ts
type ScheduledTaskPayload =
  | { kind: 'follow_up'; conversationId?: string; planId?: string; runId?: string }
  | {
      kind: 'agent_task';
      goal: string;                 // ≤2000
      conversationId: string;
      assistantId?: string;
      permissionMode: AgentPermissionMode;
      workspacePath?: string;
      maxSteps?: number;
      notify: 'work_signal' | 'desktop' | 'none';
    };
```

`kind` 是判别字段。读库时用 Zod 解析，遇到未知形状回落为 `null`，而不是「猜一个最像的」。UI 上仍然用 `text` 作为标题，`goal` 只放在 payload 里，展示与执行分开。

为什么不给 `agent_task` 单开一张表？因为它和提醒共享同一套周期、同一次触发、同一份运行历史入口。分表会把「到点该做什么」拆到两个调度器里，幂等和迁移都会变复杂。

## 创建时就拦住：无人值守没有「先跑起来再说」

能执行意味着可能闯祸，所以校验必须前移到创建表单和 API，而不是等运行时再补救：

| 校验项 | 规则 | 失败表现 |
|---|---|---|
| 执行模式 | 必须在策略的无人值守白名单内 | 422，不允许保存 |
| `full_access` | 永不进入白名单 | 422 |
| 会话 / 助手 | 创建时解析，必须存在 | 422 |
| 模型能力 | 不具备视觉能力则拒绝（桌面任务要观察屏幕） | 422 |
| 工作目录 | 绝对路径、存在、非系统目录，realpath 复核 | 422 |
| 通知目标 | `work_signal` / `desktop` / `none` | 不合法即拒绝 |

白名单的意义在于：用户可以在设置里收紧「无人值守允许哪些模式」，但 `full_access` 是硬编码排除的。一次放宽只对当前运行有效，不能通过定时任务变成永久放宽。

另一个看似小、实际很关键的限制：提醒和 Agent 任务不能就地切换类型。`PATCH` 一个已有任务时，`payload.kind` 不可变，想换类型只能新建。原因是历史语义会漂移——一条跑过很多次的提醒，突然变成会改文件的 Agent 任务，过去的时间线就解释不清了。

## 运行期的两道闸：同任务冲突与并发上限

即使创建校验全过，运行时仍可能撞车。典型场景：上一次运行还没结束，下一次触发时刻到了。我们不做「排队等下一次」，而是直接跳过并记账：

- 同一任务已有 `queued` / `running` / `paused` 的运行 → `SKIPPED_ACTIVE_RUN`；
- 当前无人值守运行数达到策略上限（默认 1，范围 1–3）→ `MAX_CONCURRENT_RUNS`；
- 两种情况都写 `unattended_blocked` 审计事件，而不是静默吞掉。

跳过比排队更符合单机预期：用户设的是「每天九点跑一次」，不是「每天九点开始排队」。错过就跳过，不补跑，也不自动重试，这条口径与旧提醒完全一致。

启动前还会再复核一次模式。用户可能在任务创建后把白名单收紧了，运行前必须以最新策略为准。复核不通过同样走 `unattended_blocked`。

## 终态必须有声音：WorkSignal 与审计

无人值守任务最怕的不是失败，是失败得无声无息。所以运行终态有两条出口：

1. **WorkSignal 始终写入**。它是应用内可靠的事件通道，任务面板和时间线都能看到；
2. **桌面通知尽力而为**。只有渲染进程在的时候才可能弹系统通知，不在就不弹，但不影响 WorkSignal。

审计则记录 `scheduled_run_started` 和 `scheduled_run_finished`，后者带状态与停止原因。这样「九点那次到底跑没跑、为什么停」不依赖任何人的记忆。

需要审批的操作不会因为无人值守就自动放行。它会照常登记到审批中心并挂起，5 分钟无人处理就按拒绝收敛。窗口全关时，这几乎等于必然拒绝——这是刻意选择的失败方向，而不是漏洞。

## 这一版不承诺什么

边界必须写进用户可见文案，否则「定时」两个字会被误解成系统级服务：

- 只在应用进程存活时触发，退出即停；
- 不做开机自启、系统服务、云调度；
- 不补跑、不自动重试；
- 桌面通知尽力而为，WorkSignal 才是可靠通知；
- 窗口全关时审批可能无人处理，最终按拒绝。

把这五条写清楚，比在设置页加一句「支持定时任务」更诚实。单机应用的调度能力，首先取决于它敢不敢承认自己的生命周期。
