# 可治理 Agent 的复盘：七条方法论，和它们在这一版的证据

这一版把治理从「工具三级权限」推进到「每次执行都可授权、可约束、可审计」：五档模式、工作目录、策略即代码、审批绑定、审计账本、定时 Agent、隔离网页。功能清单很长，但真正值得留下来的不是清单，而是七条在实现过程中被反复验证的判断。

这套治理有一个前提：单机、单人、桌面交付。没有管理员分级，没有远程运维，也没有第二个能审核的人。所有约束最终都要落在「用户自己看得懂、能解释」上，而不是对一套外部合规系统负责。

也正因为如此，这一版没有做策略表达式语言、没有做多用户角色、没有把调度做成系统服务。有些是范围选择，有些是能力边界；把它们混在一起谈，复盘就会变成愿望清单。

下面每条都配一个这一版的真实例子，包括我们做得不完美的地方。

## 一、deny wins：优先级不是排序，是提前退出

策略求值顺序写死为：系统硬拒绝 → 策略 deny → 权限记录 deny → 模式 → 策略 allow → 持久授权 → 默认询问。关键不在顺序表本身，而在「任何一层 deny 都直接返回，不再往下求值」。

例子：`smart_approve` 的 `dangerAllow` 可以放行一部分高危工具，但桌面键鼠、启动应用、窗口焦点这类操作永远不自动放行。原因是目标窗口的上下文无法在策略层可靠证明——批准时前台是编辑器，执行时可能已经换成了别的东西。所以这类 danger 只有两条路：逐次审批，或本次 `full_access`。

另一条配套规则是：策略 `allow` 只放宽 `write`，不能把 `confirm_each` 下的 danger 询问变成允许。否则「策略允许」会变成绕过模式的暗门，五档模式就只剩文案。

## 二、fail-closed 要分层，不能一刀切

「失败就拒绝」听起来很安全，但所有路径都 fail-closed 会让系统无法使用；所有路径都 fail-open 又等于没有治理。这一版按事件性质分了三层：

| 层 | 失败策略 | 例子 |
|---|---|---|
| 治理关键操作 | fail-closed | 策略决策、审批结果、绑定漂移写不进审计 → 拒绝执行 |
| 运行生命周期 | 告警后继续 | `run_started` / `run_finished` 写失败不阻断任务 |
| 旁路记录 | 告警后继续 | 策略保存成功后的 `policy_updated` 追加失败 |

审批本身还有一条更硬的规则：超时、断线、没有审批界面，一律按拒绝。无人值守时没有 UI，不能「默认允许」；任务停在等待审批，比悄悄放行正确。

分层的判断标准不是「这条重不重要」，而是「写不进去时，继续执行会不会产生无法解释的授权」。会，就拒绝；不会，就记账并继续。

## 三、先标记后投递：接受「少跑一次」，拒绝「多跑一次」

定时任务触发走 `listDue -> markFired -> deliver`。先标记，再投递。如果标记成功、投递前进程被杀，这次触发就丢了，不补跑。

反过来，先投递后标记，进程在投递后崩溃，下一次扫描会认为没触发过，再跑一遍。对单机 Agent 来说，重复执行的后果可能是两份文件写入、两条通知、两次外部调用，甚至两次审批请求；漏跑的后果只是「这次没发生」，用户能看到、能接受。

这条选择与旧提醒的「错过即跳过」口径一致，也让幂等有了唯一抓手：标记是一次原子声明，投递只是声明的后果。代价写进文档，不假装没有。

## 四、绑定即授权范围：批准 A 就不能执行 B

审批绑定包含工具名、参数哈希、工作目录、环境哈希、文件操作数、目标窗口、策略哈希。用户点「允许」后，执行前会重新计算一次；任一字段变化就返回 409，并写 `binding_drift`。

例子：外部代理的运行审批绑定命令、参数、cwd 和环境哈希；子进程的权限帧绑定帧 id 与参数哈希。审批等待期间用户改了设置，也算漂移。桌面控制的绑定还包含前台窗口与进程名——批准后窗口切走，同样拒绝。

这条方法论的底层判断是：**审批的对象不是「一个工具」，而是「一次具体操作」**。只绑定工具名，等于批准了该类工具在任意参数下的任意一次调用，授权范围被悄悄放大。

同样属于「授权范围」的还有两个设计：`full_access` 必须服务端收到确认字段，只对当前运行生效；工作目录限制的是助手主动访问的范围，不是安全沙箱。后者必须说清楚，否则用户会以为目录约束能防恶意代码。

## 五、账本要诚实：哈希链能证明什么，不能证明什么

审计事件按 `sha256(prev_hash + "\n" + canonicalJson(事件))` 串成链，追加在同步事务内完成，校验按 seq 升序重算，返回首个断链。中间篡改、跳号、改内容，都能被发现。

但它不能发现尾部截断：把最后几条事件整段删掉，剩下的链仍然自洽。要覆盖这一点，需要外部锚点——导出归档的哈希、后续版本的签名，或者第三方存证。这一版没有做，因此在文档里明确写成已知边界。

账本还有两个诚实边界：策略变更事件是旁路写入，失败只告警，不阻断保存；子进程权限帧的「请求」事件是尽力而为，结果写失败不会否决已经发生的帧决策。运行审批的请求与结果仍然 fail-closed。

「可校验」不等于「万能取证」。把不能证明的部分写出来，账本才可信。

## 六、单机 Agent 有进程边界，能力必须跟着进程走

定时 Agent 只在应用进程存活时触发。应用退出，调度停止；不做开机自启、系统服务、云调度；错过不补跑，失败不自动重试。

服务端循环本身也不是进程启动即运行，而是在服务首次初始化时挂上 10 秒节拍。这个时序差异会直接影响用户对「刚开机为什么没触发」的理解，所以必须写进文档，而不是等用户来问。

通知同样受进程边界约束：WorkSignal 始终写入，是应用内可靠通道；桌面系统通知依赖渲染进程存在，属于尽力而为。窗口全关时，审批可能无人处理，5 分钟后按拒绝——这不是漏洞，是 fail-closed 的必然结果。

单机应用最容易犯的错，是把「本地常驻」说成「系统级常驻」。承认进程会退出，能力设计才不会悬空。

## 七、审计不可写时，按操作的危险程度做取舍

审计写入失败不是同一种失败：

- 策略拒绝、审批结果、绑定漂移写不进去 → 操作拒绝，返回审计不可用；
- 运行生命周期写不进去 → 告警，任务继续；
- 策略保存成功后的变更事件写不进去 → 告警，保存仍然生效。

这不是双标，而是按「失去这条记录后，系统还能不能解释自己的行为」来判断。审批与拒绝的缺失会让一次执行变成无据可查，所以必须停；运行开始与结束的缺失只影响时间线的完整度，停掉任务反而制造更大的不可用。

代价是账本可能不完整，但每次不完整都有明确的告警位置。比「所有写入都假装成功」诚实，也比「任何写入失败都让应用不可用」可用。

## 收口

七条方法论可以压缩成一句话：**治理不是加一层判断，而是让每个判断都有明确的失败方向、可复现的范围和留下的证据。**

它们不是七条独立的口号。deny wins 决定求值结构，fail-closed 分层决定写入失败时谁停谁继续，绑定决定授权范围，账本决定证据能证明到哪，进程边界决定能力不能承诺什么。少任何一条，另外几条都会出现解释不了的缝。

这一版仍有清楚的缺口：重定向未做二次 DNS 私网解析、账本尾部截断不可检出、审计不自动清理、定时任务不跨进程生命周期、纯 Web 模式没有浏览器能力。它们没有被藏起来，而是逐条写进已知边界。

能力可以下一版再加，边界必须这一版就说清。对单人维护的桌面应用，这可能是比任何功能都更重要的交付物。
