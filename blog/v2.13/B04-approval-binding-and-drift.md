# 审批绑定：批准的是「这一次」，还是「一个工具名」？

旧的审批项只记两样东西：工具名，和一段给人看的参数摘要。用户点「允许」之后，执行路径拿着原始参数继续跑，没有任何一步去确认「现在要执行的，还是刚才批准的那个操作」。

这在大多数时候没问题，因为从登记到执行只有几十毫秒。但只要中间存在等待——用户在审批中心犹豫了半分钟、模型在重试前重新拼了参数、审批期间设置被改了——批准与执行就可能分叉。安全上的经典表述是：**TOCTOU，检查时与使用时不是同一个对象**。

这一版给审批加了一个结构化的操作指纹：`OperationBinding`。审批绑定它，执行前重算它，不一致就拒绝。

## 只绑定 callId 的三个漏洞

| 漏洞 | 具体场景 | 后果 |
|---|---|---|
| 参数可变 | 模型重试时改了目标路径或命令 | 批准的是 A，执行的是 B |
| 环境可变 | 审批期间切换了工作目录或环境变量 | 同一命令落到不同上下文 |
| 策略可变 | 审批等待期间策略被收紧或放宽 | 按旧策略做的判断，用在新策略下执行 |

第三个最隐蔽：用户批准时策略允许，但等待期间策略被改成 deny，执行路径如果不重新求值、不比对策略哈希，就会绕过刚生效的收紧。

## OperationBinding 的七个字段

```ts
interface OperationBinding {
  tool: string;
  argsHash: string;        // sha256(canonicalJson(args))
  cwd?: string;            // realpath 之后
  envHash?: string;        // 只存哈希，不存环境变量本身
  fileOperands?: string[]; // 归一化绝对路径，升序
  target?: { windowId?: string; processName?: string };
  policyHash: string;
}
```

几个字段的取舍值得说明：

- `argsHash` 而不是完整参数：账本与审批项都不应该保存可能含敏感内容的原始参数，哈希足以证明同一性；
- `envHash` 同理，环境变量里常有密钥，只保留哈希；
- `fileOperands` 归一化后升序，避免「同一组文件、不同顺序」被误判成漂移；
- `target` 是可选维度：桌面键鼠看前台窗口与进程，浏览器工具看会话、域名与 URL 哈希；
- `policyHash` 把「当时按哪版策略做的判断」也纳入同一性。

## 三段时序：算、批、再算

```text
执行请求
  → 求值（策略 / 模式 / 授权）
  → 需要审批：计算 binding，登记审批项，展示摘要
  → 用户允许
  → 执行前重新计算 binding
      ├─ 完全一致 → 执行
      └─ 任一字段变化 → 409 APPROVAL_BINDING_DRIFT，拒绝并审计
```

注意重算发生在「执行前」而不是「审批通过时」。审批通过只是一个信号，真正的闸门在工具真正动手之前。两者之间可能还隔着队列、锁、模型回合，这些间隙正是漂移发生的地方。

## 为什么是 409，而不是 403

错误码的语义在这里很重要：

- 403 表示「你没有权限」，用户应该去改策略或授权；
- 409 表示「你批准的对象已经变了」，用户应该重新审批。

如果把漂移也返回 403，客户端会以为需要提权，用户会去改设置，而真正该做的是再看一眼新参数。语义错了，恢复路径就错了。

409 的响应里会带漂移字段与新的摘要，审批中心据此提示「参数已变化，请重新确认」。审计同时记一条 `binding_drift`，保留旧绑定与新绑定的哈希，不保留原始参数。

## 接入点：门控原来只拿得到摘要

改造时遇到一个很实际的问题：工具门控函数的入参只有 `argsSummary`，一段给人看的文本，根本拿不到原始参数。没有原始参数，就算不出 `argsHash`，绑定无从谈起。

处理方式是给门控新增 `binding` 入参，由两个调用方在发起调用时计算并传入：聊天工具调用循环与桌面任务循环。门控本身不负责构造绑定，它只负责比对——职责边界清楚，测试也好写。

对于没有改造到的旧路径，口径是「无绑定」，但仍然受策略与模式约束。这是一个显式的降级：承认覆盖不全，而不是假装所有路径都有绑定。

契约里，桌面键鼠的 `target` 记录前台窗口 id 与进程名；浏览器工具记录会话、域名与 URL 哈希。用户在审批后切了窗口，就算参数一模一样，也按漂移拒绝——因为「点这个坐标」在不同窗口下是完全不同的操作。

## 外部代理：运行审批 + 权限帧双层绑定

外部代理不是一次工具调用，而是一个长驻子进程，所以绑定分两层：

| 层 | 绑定内容 | 漂移处置 |
|---|---|---|
| 运行审批 | 命令、参数数组、cwd、环境哈希 | 拒绝启动或终止运行 |
| 权限帧 | 帧 id + 参数哈希 | 拒绝该帧并审计 |

运行审批在启动前完成；子进程运行中每发来一个权限请求帧，都要和帧 id 与参数哈希比对。命令、参数、cwd、环境任一变化，都按漂移处理。

审批超时沿用 5 分钟；没有审批入口（比如纯 Web 模式或桌面通道未就绪）时 fail-closed，不允许「默认放行」。

## fail-closed 清单

审批链路上所有「拿不到确定答案」的情况，都归到拒绝：

| 情况 | 处置 |
|---|---|
| 审批超时 | 拒绝，写 `approval_timeout` |
| 连接断开 | 拒绝 |
| 没有审批 UI | 拒绝，返回不可用说明 |
| 审计不可写 | 拒绝执行，返回 `AUDIT_UNAVAILABLE` |
| 用户明确拒绝 | 拒绝，写 `approval_denied` |

拒绝不是终点：结构化原因会回灌给模型，说明「该操作未被执行、原因是未获批准」。这一步很重要——如果只返回一个空结果，模型很容易把「没执行」理解成「执行了但没输出」，然后在下一轮基于错误事实继续推理。

## 审批中心：允许一次，还是记住

审批项展示的不再只有工具名，而是工具、级别、参数摘要、工作目录、目标窗口或进程、策略来源，以及绑定摘要。两个按钮的语义被刻意分开：

**允许一次**只对当前 binding 生效，执行完即失效；**记住**沿用旧的长期授权语义，写授权记录，审计里记为一次 `grant`。

「允许一次」不再产生任何持久授权。这样用户在看到可疑操作时，点一次允许不会留下一个永久开口。

## 无人值守时，审批只能挂起

定时 Agent 遇到需要审批的操作，没有第二条路：挂起进审批中心，等 5 分钟，超时按拒绝。窗口全关时没人处理，结果就是超时拒绝，运行可能因此失败——这是设计接受的结果，而不是 bug。`full_access` 永远不进入无人值守白名单，所以后台任务不可能靠模式绕过审批。策略可以在运行前收紧无人值守允许的模式，这个收紧会在启动复核时生效。

## 诚实边界

绑定不是万能的，有几处要如实说：

- 旧调用路径可能没有 binding，只受策略与模式约束；
- 子进程权限帧的「请求」事件是尽力而为，帧审批结果写入失败不会否决已经发生的帧决策；运行审批的请求与结果仍然 fail-closed；
- 桌面键鼠的目标窗口维度依赖平台能提供前台窗口信息，拿不到时退化为工具 + 参数哈希；
- 绑定保证的是「同一个操作」，不保证「操作本身安全」——安全性仍由策略、模式与用户判断负责。

## 收口

审批绑定把一次人工确认，从「我相信这个工具」变成「我批准这组参数、在这个目录、这个环境、这版策略下执行一次」。它不增加用户的操作次数，只是让那一次点击有了明确的指向。下一篇讲账本：当所有这些允许、拒绝、漂移都发生后，如何留下一条能自证未被篡改的证据链。
