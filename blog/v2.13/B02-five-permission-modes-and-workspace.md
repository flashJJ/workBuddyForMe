# 五档权限模式与工作目录：默认档兼容旧行为，放宽只对这一次

早期的权限模型很窄：工具被打上 `read` / `write` / `danger` 三级，授权按「工具 × 助手」记住，用户还能选择「本任务内有效」。它能回答「这个工具能不能用」，但回答不了另一个问题——**这一次任务，我想让它多严**。

于是同一个 Agent，在无人值守的整理任务和一次需要改三个文件的开发任务里，面对的是同一套询问规则。想放宽只能去改长期授权，而长期授权一旦记住，下一次任务也一起放宽了。这是模式的出发点：把「本次运行的态度」从「长期信任」里拆出来。

## 模式不改分级，只改对待方式

工具仍然只有三级，模式不新增权限种类，只决定本次运行如何对待某一级：

| 模式 | read | write | danger | 无人值守 |
|---|---|---|---|---|
| `confirm_each`（默认） | 允许 | 询问 | 询问 | 可，遇询问挂起 |
| `auto_edits` | 允许 | 目录内允许，目录外询问 | 询问 | 可 |
| `smart_approve` | 允许 | 目录内允许 | 命中 `dangerAllow` 才允许，否则询问 | 可 |
| `plan_only` | 允许 | 拒绝 | 拒绝 | 可（只读任务） |
| `full_access` | 允许 | 允许 | 允许 | 禁止 |

`plan_only` 的定位是「先看看要做什么」：允许读信息、产出计划，不允许任何变更。它和「询问后拒绝」的区别在于——根本不会去打扰用户，因为这次任务从一开始就不打算动手。

模式在任务启动时选择，写进运行记录，整个运行固定不变。它不产生任何新的持久授权，运行结束即失效。

## 默认档必须等于旧行为

升级不能制造惊吓。默认档 `confirm_each` 的语义就是旧版本的 write/danger 审批：只读直接放行，写与高危挂起询问。既有的长期授权、任务内授权、助手级授权全部保留，作为求值链路里的输入，而不是被模式取代。

这条约束看着保守，其实是治理系统的底线：**任何治理升级，默认档都不能比升级前更严或更松**。否则用户第一次升级就会遇到两种事故——要么突然被一堆新确认淹没，要么某些操作悄悄被放开。

## full_access：放宽只对这一次，且不能无人值守

五档里最危险的是 `full_access`。它需要三道具象的约束：

1. **服务端确认字段**：创建任务时必须显式携带确认标记，缺失返回 422。只靠前端弹窗不够，因为 API 可以被直接调用；
2. **只对当前运行生效**：确认一次不等于记住，运行结束即回到默认；
3. **不进无人值守白名单**：定时任务、后台运行永远不会拿到这一档。

还有一条容易被误解：`full_access` 不是「无视一切」。它仍然受策略 deny 与系统硬拒绝约束。放宽的是模式层，不是治理层。

## smart_approve 与桌面 danger 的错位

策略里有一个 `dangerAllow` 列表，看起来可以让 `smart_approve` 自动放行高危工具。但它对桌面控制类工具（鼠标、键盘、启动应用、窗口聚焦）**永远不生效**。

原因是目标窗口的上下文无法在策略层可靠证明。一个 `click` 的参数里只有坐标，没有「点的是哪个窗口的哪个按钮」；策略放行等于让模型在用户看不见的地方操作屏幕。这类工具只允许两条路径：逐次审批，或本次 `full_access`。

`fetch_webpage` 与 MCP 工具不在此列，可以按策略放行——它们的参数与目标至少是可枚举、可绑定的。

## 写操作没有工作目录时，一律降级

`auto_edits` 和 `smart_approve` 的核心承诺是「工作目录内自动允许写」。如果任务根本没有指定目录，这个承诺就不成立：`auto_edits` / `smart_approve` / `full_access` 一律降级为询问，`plan_only` 直接拒绝。

这是一个刻意的保守设计。没有目录就等于没有范围，没有范围的「自动允许写」等于全盘放行。

## 工作目录：七步校验，两次执行

工作目录是本次运行允许读写的根，可选。指定之后，文件写入、命令执行、外部代理的 cwd 都必须落在目录内。

校验在创建时与执行前各做一次：

| 步骤 | 规则 |
|---|---|
| 1 | 去首尾空白，必须是绝对路径 |
| 2 | 归一化：盘符大写、分隔符统一、去掉末尾分隔符，含 `..` 归一化后仍须是绝对路径 |
| 3 | 必须存在且是目录 |
| 4 | `realpath` 解析后再校验一次，防符号链接逃逸 |
| 5 | 拒绝盘符根、系统目录、用户主目录根、应用数据根、安装目录 |
| 6 | 拒绝 realpath 落在上述任一目录内；Windows 路径比较不区分大小写，POSIX 区分 |
| 7 | 不存在或不可读返回 422 `WORKSPACE_INVALID` |

运行期的规则更简单：目录消失返回 `WORKSPACE_MISSING`；任何路径参数越界返回 403 `WORKSPACE_ESCAPE`。敏感目录（`.ssh`、`.gnupg`、浏览器配置、密钥目录）即使位于工作目录内也默认拒绝。

需要重复一遍边界声明：工作目录限制的是助手主动访问的范围，**不是沙箱**。它不防恶意代码，也不改变「包内任意代码执行仍被禁止」这一条。

## 模式的作用范围：任务运行，不含聊天

这是最容易被误解的一点。五档模式只写入任务运行记录，聊天与协作 Agent 不提供逐轮选择，统一按策略里的默认模式求值。

但「不选模式」不等于「不受治理」：聊天路径上的策略求值、审批绑定、审计写入全部照常生效。模式只是治理的一层，不是全部。

协作 Agent 的子任务同样落任务运行，但也不单独选档，按默认模式执行，预算与步数沿用协作预算。这样避免为另一套运行模型再加一套模式字段与迁移。

## 一个完整例子

用户在启动对话框里选了 `auto_edits` 和一个项目目录。接下来：

```text
读文件        → read，直接允许
改目录内文件  → write，目录内，自动允许
改目录外文件  → write，目录外，降级询问
执行外部代理  → cwd 必须在目录内，否则 422
点击桌面按钮  → danger，询问（smart_approve 也不会自动放行）
```

任务详情页会显示模式、工作目录与策略哈希，点进去能跳到本次运行的审计事件。用户在事后不需要回忆「当时选的是哪档」，记录里有。

## 收口

五档模式的价值不在于「多了一个设置项」，而在于把两种信任分开：长期信任归长期授权，本次放宽归本次模式。默认档保证升级无感，`full_access` 用服务端确认与无人值守排除守住底线，工作目录把「范围」从口头约定变成可校验的路径。

下一篇讲策略：当模式、授权、目录都在求值时，谁说了算——答案是 deny 永远优先。
