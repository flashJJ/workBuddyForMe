# 任务经验要不要进长期记忆：一次克制的写入

任务模式跑完就把经验丢掉了。同一个助手，上周刚做过一次渠道对账，这周再做，依然从零猜口径、从零试工具。

长期记忆已经在普通对话里跑了很久：用户说“记住我用中文写周报”，下一轮就能召回。那任务里学到的东西，能不能也进这套记忆？

我们的答案是：能，但要克制。

## 一、先想清楚“写什么”

任务和闲聊不同，它的信息密度高，噪声也高。把整段执行流水写进记忆，等于往长期记忆里倒垃圾。

所以只写四类内容：

- 目标：这次到底要做什么，截断到 120 字；
- 结论：成功时的最终结论，或失败时的原因；
- 证据：引用过的文档名称，去重后最多 5 个；
- 未竟事项：明确没做完的部分。

整体再截断到 1200 字。一条记忆要能在一次召回里被读完，否则它就不是记忆，而是档案。

## 二、写成什么类型

我们把它写成“事件”类记忆，作用域是助手，而不是会话。

- 类型是事件，因为它描述“某次任务发生了什么”，不是一条稳定事实；
- 作用域是助手，因为经验应该跟着这个助手走，而不是锁在某次会话里；
- 来源会话单独记录，方便追溯这条经验是从哪次对话来的。

这样同助手的下一次对话或任务，都有可能召回它；换一个助手则不会串味。

## 三、去重靠一个键

记忆写入管线本身有去重和合并，但它需要一个稳定的主体键。

我们用运行 id 拼出主体键：

```ts
subjectKey: `agent-task:${run.id}`
```

一次运行固定对应一个键。重复回调、重试、竞态都不会产生第二条记忆；内容有更新时，管线按同一主体合并。

这比“按内容哈希去重”更可靠：两次任务结论文字可能恰好相同，但它们是两段独立经验，不该被合并。

## 四、重要度：成功 0.55，失败 0.4

长期记忆按重要度参与排序和衰减。任务经验的分数刻意低于普通对话里的事实。

- 成功任务：0.55；
- 失败或预算触顶：0.4。

为什么失败反而更低？因为失败经验的价值在于“别再这么干”，它更适合作为负例参考，而不是高频召回的结论。而成功经验也只算“一次可参考的做法”，不该压过用户明确说过的偏好和约束。

如果不设这个上限，任务流水会迅速淹没真正重要的长期记忆——用户说过“我不吃香菜”，结果每次召回排在前面的都是某次整理表格的过程。

## 五、只在该助手开启长期记忆时写

写记忆之前先查助手配置。没有开启长期记忆的助手，任务结束后什么都不写。

这条限制很重要：

- 用户关掉记忆，是对整个助手的承诺，任务模式不能绕过去；
- 不开记忆的助手通常也不需要跨会话经验；
- 少写一条，就少一条将来需要解释和删除的数据。

记忆不是越多越好，能被用户理解和控制才有价值。

## 六、只覆盖协作任务的终态

写入时机是协作运行进入终态之后，且只认三种状态：完成、失败、预算触顶。

- 运行中不写，避免中途结论被当成最终经验；
- 被用户取消、被计划拒绝的运行不写，因为它们没有产出可复用的结论；
- 单 Agent 任务暂不写，避免和协作任务的经验混在一起。

范围先收窄，等两种任务的经验格式统一了再合并。

## 七、回投失败不阻断记忆，记忆失败也不阻断回投

回投和记忆是两条独立链路，顺序是：先写会话消息，再异步写记忆。

记忆写入是“发了就不管”的调用，异常被吞掉，不影响任何用户可见的结果。同理，回投失败也不会撤销已经确定的运行状态。

这样设计的原因是失败代价不对称：回投失败用户立刻能感知，必须保证幂等和重试；记忆失败只是少一条经验，下次任务还能重新积累。

## 八、这也是可观测性的一部分

任务记忆写进去之后，用户可以问“你之前做过类似的事吗”，助手能召回并说明来源。

但我们没有做记忆管理界面，也没有做“这条经验要不要保留”的开关。第一版只保证：写进去的内容可解释、可追溯、量可控。

## 九、边界

- 不写入执行流水、工具参数、中间结果；
- 不把任务经验升级为约束，除非用户明确表达；
- 不做跨助手共享；
- 不做后台批量复盘，只在终态触发一次；
- 重要度固定，不随召回次数动态上调。

任务记忆的目标不是让助手“记住所有事”，而是让它在同类任务上少犯一次同样的错。为此，一条 1200 字以内、带来源、可去重的经验，已经够了。
