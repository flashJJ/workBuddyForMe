# 任务结束只回一行状态，等于没回

用户发起一个任务，等了十分钟，回到会话里看到一句：

> 任务「整理本月报销」已完成，共 23 步。

然后就没有了。正文在哪、引用了哪些文件、还有什么没做完，全都留在运行记录里，需要用户自己点进去翻。

这不是展示问题，而是任务模式的最后一步没做完。

## 一、回投是任务的交付面

任务模式把过程写在运行记录里，但用户真正消费结果的地方是会话。

所以我们在任务进入终态后，会向所属会话追加一条助手消息，完成“回投”。这条消息有三个约束：

- 幂等：同一次运行只投一次，重启或竞态都不会重复；
- 有会话才投：没有绑定会话的运行只写状态；
- 会话必须存在：会话被删了就静默跳过。

幂等靠一张回投记录表实现，键是“运行 id + 类型”。写入前先认领，认领失败就说明已经投过。

## 二、原来的回投只有一行摘要

旧实现里，协作任务只写最终结论的摘要字段；单 Agent 任务更简单，只写“已完成，共 N 步”。

结果是：模型辛苦产出的正文、证据清单、未竟事项，全都没有进入会话。用户下一次追问“你刚才说的第二点是什么”，助手只能重新翻运行记录，甚至答不上来。

## 三、协作任务：正文 + 证据名 + 未竟事项

新的回投结构是三段：

```text
协作「目标」已完成：<最终结论正文>
证据：<文件名 1>、<文件名 2>
未竟事项：<条目 1>；<条目 2>
```

几个细节值得说明：

- 证据只取文档名称，不贴路径，也不贴整段引用；
- 证据去重后最多 5 条，每条最多 120 字，避免刷屏；
- 未竟事项同样最多 5 条；
- 目标本身超过 60 字会截断，保证首行可读。

顺序上，正文必须在前。用户先要知道“做成了什么”，再关心“依据是什么”和“还差什么”。

## 四、单 Agent 任务：取最后一步的正文

单 Agent 任务没有三角色协作，但它的最后一步通常是模型生成的收尾说明。

回投时我们从步骤表里倒序找最后一条 final 步骤，解析其中的 message 字段作为正文；取不到才退回“已完成，共 N 步”。

这个改动很小，但效果差别很大：用户终于能在会话里直接读到结论，而不是看到一个步数统计。

## 五、失败与预算触顶也要可操作

只给成功路径写正文是不够的。失败任务如果只回“执行失败”，用户不知道下一步该做什么。

我们的处理是：

- 失败任务优先回模型给出的失败说明，没有才回步数；
- 预算触顶保留“已产出的最佳结果”，并说明是预算原因；
- 因重启中断的任务明确写“可重新发起”，而不是让用户以为任务还在跑；
- 用户主动停止的，标明是用户终止。

一句话：失败回投要回答“为什么停”和“现在能做什么”，而不是只报告一个状态。

## 六、任务的用户消息也要落库

这是容易被忽略的一半。

以前任务模式的用户消息只存在于实时界面和运行记录的目标字段里，没有写进消息表。于是回投之后，会话历史里只有助手那条回答，没有用户的问题。

后果是一连串的：导出会话缺一半、分享出去像自问自答、摘要链路拿不到原始意图。

现在的做法是：创建运行之前，先把用户消息写入消息表；同一内容紧邻重发时去重，不产生两条一样的消息。这样回投、导出、分享、摘要四条链路看到的是同一份历史。

## 七、顺序与失败隔离

回投和任务记忆是两件事，顺序不能反：先写会话消息，再异步沉淀记忆。

原因是用户感知最强的是会话消息。如果先写记忆、再写消息，一旦记忆写入抛错，用户可能什么都看不到。所以记忆写入是 fire-and-forget，失败只吞掉，不影响回投。

回投本身的失败也不会让任务变成失败状态：任务状态在执行结束时已经确定，回投只是交付动作。

## 八、结果

- 会话里能看到任务的结论正文，而不只是一行状态；
- 证据与未竟事项随结论一起回投；
- 单 Agent 任务能读到最终说明；
- 失败与中断有可操作的说明；
- 任务的提问与回答在会话历史里成对出现；
- 重复终态不会重复发消息。

回投看起来是“最后写一段文本”，实际上决定了用户是否愿意再用一次任务模式。过程再漂亮，如果交付面只有一行字，用户记住的就只有那一行字。
