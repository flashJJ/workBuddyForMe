# 复杂任务先看一眼计划：只读预览的三个阈值

任务模式最贵的错误不是跑得慢，而是方向错了还跑得很远。

用户说“把桌面上的报表整理一下”，Planner 理解成“批量重命名文件”，Executor 一路执行下去，二十步之后才发现要的不是这个。工具授权拦不住这种偏差——每一步都是合规的，只有整体理解是错的。

所以我们在执行前加了一个很轻的门：先给用户看一眼计划。

## 一、不是每个任务都需要确认

每单都弹计划卡，用户很快就会闭眼点“批准”，确认反而变成噪音。

因此第一版只对“值得看一眼”的任务触发，判断标准只有三条，任一条命中即可：

```text
1. 可用工具域里包含桌面操作（会动真实界面，代价最高）
2. 验收标准达到 3 条及以上（多目标，容易出现理解偏差）
3. 执行说明达到 400 字及以上（约束多，模型容易漏）
```

只查一轮，也就是首次规划之后。返工轮不再重复弹窗，否则用户会被同一个任务反复打断。

简单问答、单步检索、纯只读查询默认直接执行，不增加任何交互。

## 二、位置在 Planner 之后、Executor 之前

时机的选择很关键：

- 放在 Planner 之前，用户看到的是“命令”，不是“计划”；
- 放在 Executor 之后，错误已经发生；
- 放在两者之间，用户看到的是拆好的子任务、验收标准和工具范围。

流程大致是这样：

```ts
if (planReview && round === 0 && isComplex(subtask)) {
  yield preview(subtask);                 // 下发只读计划卡
  if (await decision() === 'reject') {
    return finalize('cancelled', 'PLAN_REJECTED');
  }
}
// 批准后继续执行
```

拒绝时不会执行任何工具，运行直接进入终止态，并带上“计划被拒绝”的原因码，方便在运行记录里区分“用户不同意”和“执行失败”。

## 三、只读预览：能看，但不能改

预览卡展示三样东西：子任务标题与说明、验收标准、将要使用的工具范围。

用户只有两个动作：批准，或者拒绝。不能增删子任务，不能改验收标准，也不能调整工具范围。

这不是偷懒，是刻意收窄。可编辑计划会立刻引出一串问题：

- 改过的计划算谁的版本，返工时以哪版为准；
- 用户改完之后，预算按谁的计划估；
- Reviewer 验收时对照原始计划还是修改后计划；
- 计划被改过以后，回投正文里该写哪一版结论。

第一版先把“用户是否愿意看计划”验证清楚，再决定要不要引入编辑。

## 四、拒绝的语义要干净

拒绝不是“暂停”，也不是“再想想”。拒绝就是这次运行结束。

终止时写入明确的错误码与说明，任务中心把它显示为“计划未获批准”，而不是笼统的“失败”。这样用户知道问题出在计划，而不是模型或工具。

如果用户其实只是想改个措辞，正确路径是重新发起一次任务，而不是在旧运行上反复拉锯。

## 五、无人值守必须能跳过

桌面应用里还有一类入口没有人在旁边：定时流程、自动化节点、后台链路。

这些场景如果也弹计划卡，流程会永远停在等待状态。所以：

- 无人值守入口不开启计划确认；
- 缺少批准回调时，默认视为批准；
- 流程节点强制跳过，不读取全局开关。

默认批准这个选择听起来激进，但在无人值守场景里，“卡住”比“跑偏”更糟——卡住是确定性的失败，跑偏至少还有结果可检查。

## 六、全局开关与默认值

设置里有一项“复杂任务先确认计划”，默认开启，作用于所有交互式任务入口。

它的作用只是“允不允许触发”，不改变三个阈值。关掉之后，所有任务直接执行，等价于回到旧行为；打开之后，也只有命中的复杂任务才会真的出卡。

配置项必须真的被消费，否则界面上打开了、运行时却没读，用户会以为已经生效。这条原则在计划确认里体现得特别明显：开关、阈值、跳过规则三者缺一，功能就是假的。

## 七、验证方式

这个功能最适合用“反向断言”来测：

- 拒绝计划后，执行侧调用次数必须为 0；
- 拒绝后运行状态必须是终止态，且原因码正确；
- 简单任务即使开关打开，也不产生预览事件；
- 无人值守入口即使命中复杂条件，也不进入等待。

只测“批准后能继续”是不够的，那只证明了快乐路径。

## 八、边界与后续

- 只读，不支持编辑验收标准或增删子任务；
- 只在首轮触发，返工不重复确认；
- 不替代工具授权，写操作仍然逐次确认；
- 不做计划模板，也不做跨任务复用。

计划确认解决的是“方向错误”这一类最贵的失败。它不提高单步质量，也不减少 token，但它能让一次跑偏在第一步就停下——这比事后回滚便宜得多。
