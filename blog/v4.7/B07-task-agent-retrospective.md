# 让任务模式记得住、停得下、接得上：七条工程结论

这一版做的是任务模式的“上下文与续跑”：让任务知道会话在聊什么，让长任务的历史可压缩，让中断的运行能继续，让结果回到会话时是完整的。

功能本身不算惊艳，但过程中有七条结论，值得写下来。它们不是通用大道理，每一条都对应一次真实的踩坑。

## 一、顺序永远是先一致性，再能力，最后观测

任务模式原本的问题是分散的：Planner 和 Executor 各拿各的输入，步骤截断在一处，回投在另一处，恢复逻辑又在第三处。

如果先加能力——比如先做续跑——那么“任务拿不到会话上下文”这个前提没解决，续跑出来的运行依然是瞎子。如果先做观测，指标会很漂亮地记录一条错误的链路。

所以我们按这个顺序收口：

1. 一致性：上下文装配只有一个入口，预算只有一个公式；
2. 能力：再接压缩、续跑、计划确认、记忆；
3. 观测：最后补 per-role token 用量。

per-role 的 token 统计放在最后，不是因为它不重要，而是因为前两步没稳定时，统计出来的数字没有解释力。

## 二、预算要跟着模型窗口走，不要写死

最初任务侧用一个固定的兜底值当预算。这个值恰好等于某个常见模型的单次最大生成长度，于是被反复误读成“上下文窗口”。

真实情况是：模型窗口差异极大。本地运行时常见的默认窗口是 4096，未配置时我们兜底 8192，架构默认可能是 32768，云端长上下文可以到几十万。

固定的 2000 token 预算，在 4096 窗口上是灾难，在 1M 窗口上又太抠。

改成公式之后问题消失了：

```text
任务上下文 = clamp(窗口 × 15%, 320, 2000)
步骤历史   = clamp(窗口 × 12%, 320, 1200)
```

4096 窗口下分别是 614 与 491，恰好装得下；32768 以上取到上限，不会无限膨胀。两个预算相互独立，谁也不挤谁。

结论：凡是和“窗口”有关的数字，都不该是常量。

## 三、压缩优先确定性，模型摘要往后放

任务步骤超过一定长度后必须压缩，这是共识。分歧在于用什么压。

我们选择了确定性规则：保留首 2 步与最近 8 步，中段按剩余预算逐条接纳，放不下的合并成一行计数摘要。全程不调模型。

理由在实现时变得非常具体：

- 步骤本身已经是结构化的，再摘要一次收益有限；
- 多一次模型调用就多一个失败点和一份成本；
- 确定性输出可以写单测，回归时不会“今天压得好、明天压得差”；
- 原文仍在步骤表里，随时读得回来。

模型摘要不是不做，而是留到对话侧和任务侧共用一套压缩器时再做。两条链路各写一套摘要口径，是后面一定会还的债。

## 四、续跑不等于重放

这是最容易被产品语言带偏的一条。“继续运行”听起来像是从断点接着跑，但工程上我们做的是“带着笔记重新规划”。

原因很现实：要做到步骤级重放，每一步都必须是可重入的。工具调用有副作用、模型输出不确定、外部接口可能已经变化，逐步骤重放的成本远高于重新规划。

所以续跑的真实形态是：

- 新建一次运行，记录来源运行 id；
- 携带剩余预算，不重新发一份满额；
- 把检查点作为上下文，让模型自己判断哪些已完成。

代价是可能重复少量工作，收益是实现简单、失败面小。这个取舍必须提前和用户预期对齐，否则“继续”两个字会带来错误承诺。

## 五、检查点不是审计流水，一个概念一张表

一开始最简单的方案是复用步骤表，加一个游标字段表示“恢复到哪”。

我们否掉了，原因是语义污染：续跑还需要存预算余量、待确认门、幂等键线索，这些都不是“一步执行”的属性。塞进步骤表，以后每个读步骤表的地方都要判断“这行到底是步骤还是状态”。

所以新开一张表：每次运行至多一行，按轮次和阶段覆盖写，终态封存。交接记录继续做只追加的审计流水，两者互不替代。

结论：两个概念如果需要不同的写入模式（一个覆盖、一个追加），就不该共用一张表。

## 六、配置字段必须有消费方

这一版新增了两个开关性质的东西：计划确认的全局开关，以及检查点上的“可续跑”标记。

它们的共同风险是变成死字段：界面上能打开，数据库里也写了，但运行时没人读。用户以为生效了，实际什么都没发生。

我们的检查方式是反着问：

- 开关关闭时，预览事件是否真的不再产生？
- 检查点被封存后，任务中心是否真的不再出现“继续运行”？
- 无人值守入口是否真的跳过了计划确认？

一个字段如果没有消费方，比没有这个字段更危险，因为它制造了“已配置”的错觉。

## 七、交付面要幂等，旁路失败要隔离

任务模式的最后一公里是回投：把结论写回会话。

这里有两个容易忽略的点：

第一，回投必须幂等。重启、竞态、重复终态都可能触发多次，所以写入前先按“运行 id + 类型”认领，认领失败就跳过。

第二，旁路不能拖垮主路。任务记忆是回投之后的异步动作，它失败不影响回投；单段上下文读取失败，也不影响任务继续执行。

顺序也要固定：先写用户可见的会话消息，再写后台记忆。反过来，一旦记忆写入抛错，用户可能什么都看不到。

## 八、这一版没做什么

- 不做并行或 DAG，预算共享、幂等键、审查合并三个问题还没答案；
- 不做可编辑计划，先验证用户是否愿意看计划；
- 不做上下文快照与压缩回放，等统一控制器时一次做对；
- 不做跨设备续跑，运行状态仍在本机；
- 不做任务经验的自动晋升，写进去的经验保持低重要度。

## 九、结果

- 任务模式能引用会话背景，不再从零开始；
- 长任务的早期证据不会因为固定条数截断而消失；
- 重启后的任务可以继续，且不会重复消耗预算；
- 复杂任务执行前能看到计划；
- 结果回投包含正文、证据与未竟事项；
- 任务经验进入长期记忆，但不会淹没用户偏好。

这七条结论的共同点是：它们都不是“加功能”，而是“把边界说清楚”。功能决定这一版能做什么，边界决定下一版还敢改哪里。
