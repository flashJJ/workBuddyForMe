# 让正文角标可点击：一次不动渲染器的改造

Markdown 渲染是聊天界面里最不该随便改的部分。

它要处理表格、代码块、任务列表、脚注、图片，还要在流式输出时按块增量更新。往里面塞引用解析，最容易的结果是把某个不常见的语法改坏：示例代码里的数组下标被当成引用，链接文字被拆成两半，脚注定义莫名消失。

这一版要做正文角标，第一个决定就是不动渲染器，只在它外面套一层。

## 为什么不改渲染器

渲染器是第三方组件，行为由插件决定。改它的源码意味着每次升级都要重新合并，也意味着所有语法路径都要重新测。

更现实的问题是职责。渲染器的任务是「把 Markdown 变成 DOM」，引用编号是业务语义；把业务判断写进通用渲染器，两边都会变重。

所以改造分成两层：先用纯函数把正文预处理一遍，再在渲染组件表里覆写链接。渲染器本身一行不改。

## 第一步：把独立编号变成链接

预处理是一个纯函数：输入一段 Markdown 文本，输出另一段 Markdown 文本。

它只做一件事——把独立的 [3] 和【3】替换成 `[3](#citation-3)`。

为什么先变成链接，而不是直接变成角标？因为 Markdown 里唯一能被渲染器识别的「可点击结构」就是链接。先借用链接语法，后面的组件覆写才有落脚点。

函数保持纯：不读全局状态，不依赖 React，输入相同输出必然相同。这样才能用表驱动的方式把边界情况一条条钉死。

## 围栏代码必须按行跟踪

最容易误伤的是代码块。一段讲解数组的示例里写着 `arr[0]`，一段 JSON 示例里有 `[1]`，如果全局替换，代码就被改坏了。

处理方式是按行扫描，维护一个「当前是否在围栏内」的布尔状态：

- 遇到以三个反引号或三个波浪号开头的行，翻转状态；
- 状态为真时，整行原样输出，不做任何替换；
- 状态为假时，才进入行内解析。

按行而不是按正则全局匹配，是因为围栏的起止必须成对判断。用一条跨行正则去匹配代码块，遇到嵌套、未闭合、不同缩进，很容易漏判。

## 行内代码、链接、图片与脚注

围栏之外的普通行，也不是整行都能替换。

有四类内容必须跳过：

- **行内代码**：一对反引号之间的内容，里面的 [0] 是代码，不是引用；
- **既有链接与图片**：`[文字](地址)` 和 `![说明](地址)`，方括号属于语法结构；
- **脚注定义**：形如 `[1]: 注释内容`，冒号紧跟其后；
- **本身就是链接文本的编号**：`[1](...)` 已经是链接，不能再套一层。

实现上不是先切词再判断，而是从左到右走一遍字符：遇到反引号就整段跳过到配对位置；遇到方括号先看是不是图片或链接；确认是独立的编号标记，才替换。

判断「独立」还有一个隐含条件：编号后面不能紧接左括号或冒号。这两个字符分别对应链接和脚注，是区分「引用」与「语法」的关键。

## 第二步：覆写链接组件

预处理之后，正文里多了若干指向 `#citation-n` 的链接。

渲染时把这些链接换掉。组件表里覆写链接组件：拿到 href，用一条窄正则判断是不是 `#citation-n`；不是就按原来的方式渲染，是就返回角标按钮。

按钮不是纯装饰，它带三样东西：

- 可见文本仍然是 [n]，保持阅读连续性；
- 无障碍标签是「来源 n」，读屏用户能听懂；
- 一个数据属性记录编号，供来源列表定位。

这样改的好处是渲染器完全不知情。它只是渲染了一个链接，至于这个链接最后变成 `<a>` 还是 `<button>`，由组件表决定。

## 第三步：跨组件通信不靠 props

角标在正文里，来源列表在正文下面，两者隔了好几层组件。

如果把「点击了第几条」做成状态往上提，整棵消息树都要重渲染，长回答会明显卡顿。更麻烦的是正文是分块 memo 的，状态一变，所有块都可能失效。

这一版用的是自定义事件 citation-focus：角标点击时，找到自己所在的消息根节点，向上派发一个携带编号的事件；来源列表在挂载时监听同一个根节点。

这样做有三个直接好处：正文和来源列表不需要共享状态；消息之间天然隔离，不会串号；事件只在点击时发生，流式渲染期间没有额外开销。

事件名里不带任何产品标识，纯业务语义，避免以后改产品名还要改事件。

## 折叠状态下先展开

来源列表超过三条默认折叠。用户点正文角标时，目标条目可能根本不在 DOM 里。

所以监听方收到事件后，第一步是展开，第二步才是定位。

展开是异步的：状态更新后，条目才会渲染。因此定位不能和展开写在同一个同步流程里，要等一次渲染完成再查锚点。实现上用一个带自增序号的请求对象触发副作用，避免连续点击时旧请求覆盖新请求。

## 高亮一秒半的意义

定位用平滑滚动，把目标条目滚到视口中间；滚动到位之后加一个高亮类，一秒半后移除。

这一秒半不是为了好看，而是为了解决「滚过去了但没看见」。用户视线还停留在正文，页面突然滚动，需要一点时间重新对焦；短暂高亮给了一个明确的落点。时间也不能太长：超过两秒，高亮会变成干扰，尤其在连续点几个角标时，多个高亮叠在一起反而看不清。

## 流式期间不解析

角标只在消息完成后生效。

流式输出时，正文是半截的：`[1` 可能还没写完右括号，`[12` 可能马上要变成 `[123]`。这时候如果解析，用户会看到标记忽明忽暗地跳动。

所以判断条件只有一个：消息状态是已完成，才把引用编号集合传给渲染组件；否则按纯文本渲染。

代价是流式过程中看不到角标。这个代价可以接受——流式阶段用户在读内容，等回答结束才需要核对来源。

## 找不到来源时保留原文

模型可能写出一个不存在的编号，比如只给了三条来源，正文却标了 [7]。

这时不能把标记删掉。删掉会让句子读起来缺一块，用户也不知道这里原本有个引用。

正确处理是保留 [7] 原样，降级成灰色文本，悬停说明「引用不可用」。同样的原则适用于来源缺失：可见、可解释、不报错。界面上最糟的处理不是显示异常，而是静默地什么都不显示。

## 收尾

这次改造没有碰渲染器，也没有引入新的 Markdown 插件。

它只是在渲染前后各加了一层：前面用纯函数把业务标记翻译成通用语法，后面用组件表把通用语法翻译回业务组件。中间那层第三方代码，完全不需要知道引用是什么。

这种做法的价值不在这一版。等以后要加「悬停预览」「多编号合并」「按句定位」，改的仍然是这两层，渲染器还是不用动。
