# 小版本收口：七条方法论

有些版本是加能力，有些版本是补账。

这一版属于后者。没有新模型、没有新存储、没有新依赖，做的事情是把早就存在的数据接到用户眼前：正文里的编号变成可点的角标，来源分成文档和网页，一轮结束给出一句整体交代，抓取失败不再反复重试，多角色协作留下一条交接记录。

做完回看，真正有价值的不是这几个功能，而是过程中反复用到的七条判断。它们都不是新道理，只是在这一版里被具体问题逼着用了一遍。

## 一、先接通已有数据，再谈新能力

最典型的是引用。工具结果里早就有来源字段，文档片段带章节、表格、页码坐标，网页结果带地址，这些信息一直在。缺的只是把它们显示出来，并且能点回去。

另一个例子是回合摘要。工具追踪里已经有每次调用的开始时间、耗时、成功失败，消息上已经有 token 统计和引用列表。要做「这一轮发生了什么」，不需要新接口，只需要把这些字段读出来、摆到一起。

这条方法论的价值在于控制成本。新能力意味着新契约、新存储、新兼容问题；接通已有数据只意味着新的展示层。前者要一个版本，后者可能只要几天。

判断方式很简单：先翻一遍现有类型定义和事件载荷，问「这个信息是不是已经在了」。如果在了，问题就从「怎么采集」变成「怎么表达」。

## 二、展示编号与存储序号分离

引用编号曾经出过一个很具体的问题：底部来源卡里出现了 `[0]`，还有重复编号。

原因是同一个字段被当成两种东西用。它原本表示「文档内第几个片段」，从 0 开始；展示层直接拿它当编号，而网页结果没有片段，这个值固定是 0。于是知识库条目从 0 起，网页条目也挤在 1 附近。

修法不是改那个字段的起始值，而是承认这是两件事：

- 存储序号回答「这条引用在原文的哪个位置」，服务于定位；
- 展示编号回答「这条引用在本次回答里排第几」，服务于阅读。

两者分开之后，编号可以在装配层统一重排，从 1 连续；定位仍然用原来的坐标。一个字段不再承担两种语义，之前那些边界情况自然消失。

这条经验可以推广：只要发现某个字段在不同地方有不同解释，先别急着改值，先看是不是该拆成两个字段。

## 三、纯函数先行，让解析与合并可单测

这一版新增的逻辑里，最值得写测试的部分都被抽成了纯函数。

角标解析是一个：输入一段 Markdown 文本，输出文本片段和角标片段的序列。它要跳过围栏代码块、行内代码、已有链接、图片语法和脚注定义，避免把示例代码里的 `[0]` 改成可点角标。这些规则用表驱动测试逐条断言，比渲染出来再找 DOM 稳定得多。

合并去重是另一个：给定已有引用和新到引用，按固定键判重，保留首条、合并更完整的片段，最后整体重编号。输入输出都是数组，断言可以直接写「长度是 3」「第二条的编号是 2」。

耗时格式化也是：毫秒、秒、分秒三个档位，边界值各一条用例。

纯函数先行的好处不只是好测。它逼着把「规则」从「渲染」里剥出来，剥完之后组件只剩挂载和样式，逻辑出错时定位范围小得多。

## 四、降级要可解释、有边界

抓取失败的处理集中体现了这一点。

旧行为是失败就报错，模型可以继续重试同一个地址。新行为加了一条边界：同一地址连续失败两次，本轮不再请求，结果标记为降级。

边界体现在三个「只」：只对网络、超时、连接、页面过大这类可恢复失败计数，鉴权失败和明确被拒仍按原语义返回；只有连续失败才累计，成功一次就清零；只对每个本轮新降级的地址提示一次，而且提示不落库。

可解释体现在三处一致：计数状态由编排器持有并跨轮传递，判定是纯函数，界面上的失败卡和注入给模型的提示说的是同一件事——这个地址没取到全文，请基于已有摘要作答。

这里最重要的判断是「降级不是隐藏失败」。结果仍然是失败，只是不再重复，并且把「没拿到原文」写进回答的前提。用户可以接受一次没抓到，但不能接受系统假装抓到了。

## 五、门禁约束下的增量设计

收尾时最花时间的不是功能，是让检查变绿。

一个核心类型文件涨到 306 行，本想抽新文件，但那个目录的直接文件数已经到 12，最后压缩注释回到 300。编排器涨到 314 行，把降级跟踪逻辑抽成独立 helper，顺手精简失效注释。聊天消息目录预算已满，新组件只能放进 citation 和 turn-summary 两个子目录。

三次都不是「代码写错了」，而是「东西放错了地方」。

门禁的意义在这里显出来：它在功能还没完全铺开的时候，就把「这段逻辑属于谁」这个问题摆到桌面上。等到文件 600 行再拆，调用方已经长在旧结构上了。

代价也要承认：有时会为了过检查而压缩注释，而注释里往往藏着「为什么」。所以压缩时删的是重复叙述和历史故事，决策理由要留下。

## 六、双语与可访问性同步

新增界面文案时，中英两个文件必须成对修改。有一条对等测试比较两边的键集合，缺一个就失败。

这把翻译从「上线前补一下」变成了「提交前必须做完」。对一个单人项目尤其重要，因为没有人会在评审时提醒你漏了英文。

可访问性同样是增量的一部分：角标渲染成按钮而不是文本，带明确的标签；找不到对应来源时，角标降级为原文并带提示，而不是静默消失；来源卡的分组标题同时给出两类计数，折叠状态下也知道里面有什么。

这些细节单看都很小，但它们决定了功能对读屏用户和无鼠标用户是否可用。补的成本远低于事后重构。

## 七、旧数据只读兼容、不回填不迁移

整版没有数据库迁移，schema 版本常量保持不变。

做法是把所有新增信息都放在「可缺省」的位置：展示编号只存在于消息 JSON 和内存，旧消息没有就按列表位置兜底；流式事件只新增可选字段，旧客户端忽略即可；工具结果只新增可选的降级标记，旧记录不受影响。

这条原则的收益是即时的：旧库、旧备份、旧对话都能直接打开，不需要「升级前请先导出」的提示，也不需要迁移失败的回滚预案。

代价转移到读取时：前端要处理字段缺失，装配层要负责重排，测试要覆盖两条路径。这是主动的交换——把集中的、不可逆的升级风险，换成分散的、可测试的读取成本。

## 如果顺序反过来

把这一版的顺序倒过来推演一遍，能看清七条之间其实有依赖：如果先做正文角标，前端会直接拿现有序号渲染，`[0]` 和重号会在界面里先固化下来，之后再改就要连契约一起动；如果先做抓取降级，状态没有跨轮共享，模型仍会反复请求同一地址。

顺序的价值就在这里：先定契约，展示层才有稳定的输入；先接通数据，新界面的成本才低；先有门禁，结构才有机会在功能铺开前调整。

这不意味着每次都要照这个顺序走。它更像一份检查表：当某一步卡住时，回头看看是不是前一步还没做干净。

## 七条之间不是并列关系

前三条讲怎么找价值：先看已有数据，再看语义是否混淆，再看逻辑能否抽出。中间两条讲怎么加约束：降级要有边界，结构要有门禁。后两条讲怎么收尾：文案与可访问性同步，旧数据保持可读。

它们共同指向一个判断：小版本的产出不应该只是「多了几个功能」，而应该是「系统的某一段变得更清楚」。如果做完之后，同一段逻辑仍然要跨三个文件才能看懂，那这个版本只是把债往后推了。

## 什么算收口

最后给一组可以自查的标准。

功能层面：验收口径里的每一条都能用一句话验证，不依赖「看起来对」。数据层面：没有新增迁移，旧数据打开后行为与升级前一致。结构层面：门禁全绿，新增文件都在该在的位置，没有为了过检查而登记例外。测试层面：规则类逻辑有纯函数用例，组件只验证挂载与降级路径。表达层面：中英键对等，空状态不渲染空容器，失败有可见说明。

再加一条不那么能量化的：把这一版的功能讲给没参与开发的人听，他能不能在五分钟内说出「它解决了什么问题」。说不出来，通常意味着做的还是实现，不是收口。

小版本的价值不在于规模，而在于它让下一版可以站在更干净的地面上开始。这一版做的事情很朴素——把已有的证据变成用户看得见的来路，把重复的失败变成一次诚实的降级，把散落的交接变成一条可读的时间线。

账补完了，才谈得上加新东西。
