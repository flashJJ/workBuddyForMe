# 引用编号契约：把展示编号做成派生字段

给回答加上来源标注，看起来只是界面工作：正文写 [1]，下面列一条来源，编号对上就行。

真正做起来，编号是整条引用链路上最容易出错的一环。它同时被三方使用：提示词里的资料块、模型写出的正文标记、界面上的来源卡。任何两方对不上，用户看到的就是一个点不动的数字，或者一个指向错误条目的角标。

这一版先把编号定成契约，再谈角标和分组。

## 两套编号是怎么长出来的

早期只有一个字段：引用里的片段序号。

知识库检索返回的是文档分片，分片序号天然从 0 开始，直接拿来当展示编号，第一条来源就成了 [0]。网页搜索结果没有分片概念，序号固定写 0 或从 1 起，混在同一个列表里就出现重复编号。

同时，提示词里的资料块是另一套编号：按注入顺序从 1 开始，连续排列。模型读到的是 [1]、[2]、[3]，写出来的也是这几个数字。

于是系统里同时存在三种数字：提示词编号、片段序号、界面编号。前两个语义不同，第三个干脆是借用第一个的字段。用户看到的混乱，只是这三套数字终于撞在一起。

## 新增一个从 1 起的展示编号

做法很直接：引用结构里增加一个可选字段，专门承载展示编号。

它有三条约束：

- 从 1 开始，不用 0；
- 本轮内连续且唯一，中间不跳号；
- 与提示词资料块的编号一致，模型写 [1]，界面第一条就是 [1]。

这个字段只在装配阶段产生，随消息一起走。它不进入检索，不参与排序，也不影响任何业务判断。

## 把片段序号收回定位用途

原来的片段序号没有删除，只是收窄了语义：它表示「这段内容在文档里的第几片」，只用于定位，不再用于展示。

网页结果的这个字段固定为 0，因为网页本来就没有分片。这个 0 不再出现在界面上，也就不会再让用户以为编号从零开始。

一个字段承担两种职责，是这类问题最常见的来源。拆开之后，定位归定位，展示归展示，两边都可以独立演进。

## 装配层统一编号

编号动作只放在一个地方：装配层。

具体顺序是三步：

1. 检索得到的资料块按注入顺序编号，从 1 开始；
2. 工具在同一轮里产生的引用，接着已有序号继续编号；
3. 多路结果合并之后，按最终列表顺序整体重排一遍。

第三步是关键。前两步各自编号时，谁先谁后取决于执行顺序；合并可能插入、可能去重，编号会错位。重排把「最终顺序」当成唯一事实，前面怎么编都不影响结果。

## 合并去重：一条来源只留一条

同一份资料常常被多路召回：知识库检索一次，工具搜索又一次，网页同地址被抓取两次。

去重的键由六个字段组成：文档标识、片段序号、来源层级、表格序号、表格行号、网页地址。六个字段全相同，才认为是同一条来源。

命中重复时保留首条，只做一件事：如果新条目的片段更长，就用它替换。这样既不会出现两条一模一样的来源，也不会因为先到的那条片段被截断而丢掉信息。

合并完成后统一重排编号，保证去重不会在序列里留下空洞。

把这段逻辑写成伪代码，只有两个循环：

```text
merge(existing, incoming):
  seen = map(key -> index)
  for c in incoming:
    key = documentId|ordinal|staticKind|tableNo|tableRow|sourceUrl
    if key not in seen:
      seen[key] = len(merged); merged.push(c)
    else if c.snippet longer than merged[seen[key]].snippet:
      merged[seen[key]].snippet = c.snippet
  for i, c in merged:
    c.citeIndex = i + 1
  return merged
```

第一轮负责「谁留下」，第二轮负责「谁排第几」。两轮分开之后，去重只可能更新片段内容，不会改变任何一条引用在列表里的位置。

## 旧消息的兜底

编号是新增字段，历史消息里没有。

处理方式是不回填、不迁移：前端读不到编号时，按引用在列表中的位置加一，临时算一个展示编号。

这个兜底有一个明确的前提——旧消息的来源列表本来就是按存储顺序渲染的。按位置编号，和用户过去看到的顺序一致，不会因为升级突然改号。

宁可让旧消息「看起来和以前一样」，也不做一次批量写库。历史数据一旦被改写，出问题就没有对照物了。

## 为什么让展示编号成为派生字段

最直觉的方案是改存储：把片段序号直接改成从 1 起，或者直接把界面编号写进数据库。

这个方案有两个问题。

第一，片段序号有真实语义。它是文档内的位置，检索、定位、查看器跳转都依赖它。为了让界面好看去改它，等于把展示需求塞进数据模型，后面每加一种展示方式都要再改一次。

第二，存储一旦被改写，就没有回头路。旧备份、旧导出、旧客户端读到的都是被改过的值，想核对「原来是什么」已经不可能。

所以这一版选择相反的方向：编号是算出来的，不是存出来的。它随消息序列化，落进消息 JSON，但不成为任何判断的依据。哪天展示规则变了，改装配层即可，历史数据不动。

## 代价与边界

派生字段的代价是每次都要算。合并、重排、兜底，三步都不复杂，但必须保证顺序正确；一旦某条路径漏掉重排，编号就会跳号。

这类问题的特点是安静：界面不会报错，只是某个角标点过去落空。所以测试必须钉住硬事实——编号从 1 连续、无重复、与资料块数量一致、去重后仍然连续。

边界也很清楚：这一版不校验模型是否真的按编号引用，也不判断编号是否支撑了那句话。编号只保证「对得上」，不保证「引得好」。

还有一处兼容细节：增量输出时，引用可能分多批到达。合并与重排对每批都执行一次，而不是等到最后统一算，这样前端任何时刻拿到的编号都是连续的，不会出现暂时的空洞。

## 收尾

编号看似是最琐碎的细节，实际决定了整条链路能不能成立。

把它定成契约之后，后面三件事才有了共同基础：正文角标知道该指向哪个锚点，来源列表知道该按什么顺序排，回合摘要知道该报几条引用。三处读的是同一个数字，用户看到的世界才是一致的。
