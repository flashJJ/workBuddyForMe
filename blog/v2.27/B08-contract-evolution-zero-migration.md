# 契约演进与零迁移：新增可选字段的边界

给引用加展示编号时，最先冒出来的冲动是改数据库：加一列，写迁移，回填旧数据，前端按列渲染。

这个方案能跑通，但它把三件事绑在了一起——一个纯展示需求、一次 schema 变更、一次数据回填。任何一环出问题，都会变成「升级后旧对话打不开」。

这一版走的是另一条路：只加可选字段，零迁移。schema 版本常量保持不变，没有新增迁移目录，启动时不执行任何新步骤。旧库、旧备份、旧消息都能直接读。

## 先问：这个字段需要被持久化吗

展示编号的用途只有一个：让正文里的 `[n]` 和底部来源卡的编号对得上。

它不参与检索，不参与去重，不参与任何业务判断。给定一轮的引用列表，编号就是「从 1 开始按顺序加一」。也就是说，它是一个可以被算出来的值。

可以被算出来的值，第一反应应该是不存。存下来只会带来两份额外的责任：写入时必须正确，读取时必须兼容缺失。

所以编号只出现在两个地方：消息 JSON 里已经存在的引用数组，以及运行时的内存对象。数据库层面没有新列。

## citeIndex 与 ordinal 的分工

旧的引用结构里有一个序号字段，原本的语义是「文档内片段序号」：一个 PDF 的第几个片段，从 0 开始。网页结果没有片段概念，这个值固定为 0。

问题出在展示层直接拿它当编号用。于是同一张来源卡列表里，知识库条目从 0 起，网页条目从 1 起，还会出现重复编号。

这一版把两个概念拆开：

- 原有字段继续表示文档内片段序号，只用于定位，不用于展示；
- 新增可选字段表示展示编号，从 1 起，本轮内连续唯一。

拆分的关键不是加字段，而是把「定位」和「展示」这两件本来不同的事还原成两件事。此前它们共用一个数字，才导致了 `[0]` 和重号。

## 编号在装配层统一完成

编号不是让每个工具各自算的。如果知识库工具从 1 编、搜索工具也从 1 编，合并后必然冲突。

统一的做法是在装配层：所有资料块按注入顺序先排好，工具引用按本轮追加顺序接在后面，多路合并后整体重排一次。重排的结果写回每个引用的展示编号。重排是整体映射，而不是增量续号；好在合并只往末尾追加，已展示过的编号不会因为后来多了一条来源而整体跳动。

合并还有一个去重问题。同一条来源可能被两次搜索命中，同一次检索也可能返回重复片段。去重键由文档标识、片段序号、来源层类型、表格坐标和网页地址组成——这几项一起，才能唯一确定「一条来源」。

重复时保留首条，并合并片段：谁的内容更长就用谁的。这条规则让去重不丢信息，也让编号稳定。

## SSE 只新增可选字段，旧前端忽略即可

引用会通过 SSE 事件推给前端。事件载荷变了，兼容问题的标准解法是：只加字段，不改语义，不删字段。

新增的展示编号是可选字段，旧前端不认识它，会当作不存在，继续用自己的兜底逻辑渲染。新前端认识它，就优先使用。

这条约定听起来很保守，但它是流式协议的底线。客户端和桌面壳的版本不一定同步，用户可能开着旧窗口连上新服务。任何「必须理解新字段才能正确显示」的改动，都会在这类组合下变成故障。

## 旧消息按列表位置兜底

历史消息里没有新字段。这里的处理不是回填，而是读取时兜底：如果某条引用没有展示编号，就用它在列表中的位置加一。

这个兜底和装配层的编号规则恰好一致——列表顺序就是从 1 开始的展示顺序。于是旧数据不需要任何转换，渲染出来就是连续的。

兜底还有一层含义：编号缺失不影响来源本身。标题、片段、坐标、域名都照常显示，只是编号是算出来的。兜底只发生在读取时，不写回消息，所以同一份旧对话每次打开得到的编号都一样，不会因为某次渲染被顺手改写成另一种结果。

## 工具结果的 degraded 也是可选

同一版里另一处契约变更遵循同样的形状：工具结果新增一个可选的降级标记。

它只在抓取被短路时出现，普通成功和普通失败都没有这个字段。追踪条目和结束事件都按「有则带上」的方式透传，前端按「有则显示」的方式渲染。

没有这个字段的旧记录，行为和以前完全一样。这就是可选字段的价值：它把「新能力」变成「增量信息」，而不是「新前置条件」。

## 零迁移意味着什么

零迁移不等于没有变更，而是变更全部落在「可缺省」的位置上。

具体来说，这一版守住了三条：

1. 数据库没有新列、新表、新索引，启动流程不变；
2. 消息 JSON 里只多了一个可选键，旧记录读取路径不变；
3. 流式事件只多了一个可选键，旧客户端解析路径不变。

三条合起来，升级的风险被压到最低：不需要备份提醒，不需要迁移失败的回滚方案，不需要「升级前请先导出」的引导。

对一个本地优先的桌面应用，这一点尤其重要。用户的数据在自己机器上，迁移失败没有服务端可以兜底。

## 新增可选字段与版本化迁移，怎么选

判断标准可以收敛成三个问题。

第一，这个字段能不能从已有数据算出来？能，就不要存。派生字段一旦入库，就多了一份需要维护的一致性。

第二，缺这个字段时，旧数据是否仍然可用？如果可用，说明它是增强；如果不可用，说明它其实是新的必需信息，那才需要迁移和回填。

第三，读取方能不能容忍「没有」？流式协议和跨版本客户端尤其要考虑这一点。能容忍，就加可选字段；不能容忍，就得先做版本协商。

三个问题都指向「可选」时，版本化迁移就是过度设计。反过来，只要有一个答案指向「必需」，就该老老实实写迁移，而不是靠兜底逻辑掩盖。

## 何时不该动 schema

有几类情况，我们的结论是明确不动：

- 纯展示派生值，比如编号、分组、排序位置；
- 只影响当前会话的临时状态，比如本轮失败计数、降级标记；
- 可以通过读取时计算得到的聚合值，比如来源条数、成功失败次数。

这些数据进 schema 的收益很低，成本却是长期的：每次写入都要保证正确，每次读取都要处理历史值，每次改规则都要考虑已存数据。

真正需要动 schema 的，是那些「不存下来就会丢」的事实：用户说过的话、文档的解析结果、协作运行的终态。判断依据是能否重建，而不是「存下来更方便」。

## 兼容的成本落在哪

零迁移不是没有成本，只是成本转移了。

它把成本从「升级时刻」转移到了「读取时刻」：前端每次渲染都要处理字段可能缺失的情况，装配层每次合并都要重排编号，测试要覆盖「有字段」和「没字段」两条路径。

这是一次主动的交换。升级时刻的风险是集中的、不可逆的；读取时刻的成本是分散的、可测试的。对一个单人维护的项目，后者显然更容易控制。

## 收口

契约演进最容易被误解成「加字段」。真正需要判断的是：这个字段属于存储，还是属于展示；缺了它，旧数据还能不能用；读取方能不能容忍没有。

这一版的答案全部指向可选：编号是派生的，降级标记是本轮临时的，两者都不进库。schema 版本常量保持不变，旧数据只读兼容，不回填、不迁移。

少一次迁移，就少一次「升级后打不开」的可能。这个取舍不激进，但它让一次功能交付没有变成一次数据工程。
