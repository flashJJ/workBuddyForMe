# 回合运行摘要：只报对得上的数字

一次带工具的对话跑完，界面通常只剩一行 token 用量。

这行数字回答的是「这次花了多少钱」，但用户真正想知道的往往是另一组问题：刚才调了几次工具、成功几次、是不是有一次卡了很久、这次回答用了几条来源。

这些问题在数据里都有答案。工具轨迹记了每次调用的开始时间、耗时、结果；引用列表记了条数和来源类型；消息本身记了输入输出 token。缺的只是把它们收成一句人话。

## 只有 token 的一行不够用

把 token 当唯一的运行指标，会带来一个错觉：数字小就是快。

实际并非如此。一次回答可能 token 很少，但在等一个网页抓取上花了十几秒；另一次 token 很多，工具一次都没调，纯粹在生成。两件事被压成同一个维度，用户没法判断该不该等、值不值得再问一次。

更实际的问题是排障。用户说「最近好慢」，如果没有工具次数和耗时，就只能猜；有了这行摘要，至少能看出是工具慢还是模型慢。

## 显示条件先收紧

摘要不是每轮都出现。

显示条件有两条，必须同时满足：

- 消息状态是已完成；
- 有工具调用，或者有引用。

少任何一条都不渲染。

这条规则把纯聊天排除在外。纯对话没有工具、没有来源，硬塞一行「工具 0 次」毫无意义，反而让界面变吵。这类回合继续沿用原来的 token 行，用户看到的和以前一样。

流式过程中也不显示。数字要到回合结束才稳定，边跑边报只会跳来跳去。

## 摘要行报四件事

收起状态下只有一行，内容按有无工具分成两段：

- 有工具时：`工具 5 次（成功 4 / 失败 1）· 工具耗时 8.2s`；
- 有引用时：`引用 3 条 · 知识库 + 网页`。

两段用间隔号连起来，整行保持单行可截断。

为什么强调「成功 / 失败」而不是只报总数？因为失败次数是这条摘要里最有信息量的部分。五次全成功和四次成功一次失败，用户对这次回答的信任度完全不同。

为什么报「工具耗时」而不是「回合耗时」？这一点后面单独说。

引用段的来源类型也是同样的思路：只报有哪几类，不报每类几条。三条引用里有两条文档一条网页，写成「知识库 + 网页」就够了，具体分配在来源列表里能直接看到。

## 展开后报什么

点开摘要，多两层信息。

第一层是 token：输入多少、输出多少。只在总量大于零时显示，避免纯本地模型或统计缺失时出现「0 / 0」。

第二层是逐工具耗时：每个工具一行，工具名加耗时，失败的标红，悬停能看到错误信息。

逐工具列表的意义是对账。摘要行说总耗时 8.2 秒，展开后能看到这 8.2 秒是怎么分到五次调用上的——是均匀分布，还是一次抓取吃掉了七秒。

列表顺序就是调用顺序，和上方工具时间线完全一致。两处不重新排序，用户对照时不用心算。

## 一个例子：数字如何对齐

假设一次回合调了五个工具：

- 搜索两次，各 0.4 秒；
- 抓取两次，一次 1.2 秒成功，一次 6.0 秒失败；
- 再搜索一次，0.2 秒；
- 最后补一次读取，0.4 秒成功。

摘要行会显示：`工具 6 次（成功 5 / 失败 1）· 工具耗时 8.2s`。

8.2 正好是 0.4 + 0.4 + 1.2 + 6.0 + 0.2 加上最后一次 0.0 秒级调用的和。展开后逐条列出，加回去仍然是 8.2。

这个「加得回去」是硬要求。如果摘要的耗时来自另一个计时器，或者包含排队、渲染、网络往返，它就和逐工具列表对不上；一旦对不上，用户会认为两个数字里有一个是假的。

所以摘要的耗时只做一件事：把已有字段里的耗时相加。不引入新计时，不做估算。

## 为什么不宣称端到端耗时

「这次回答总共花了多久」听起来更有用，但这一版没有报。

原因有三个。

第一，口径不可靠。端到端时间从用户按下发送开始算，包含排队、上下文装配、模型首字延迟、工具往返、渲染。这些阶段里有的在服务端，有的在本地进程，有的在渲染层，没有一个统一的计时点。

第二，会被误读。用户看到「12 秒」，会认为模型慢；实际可能十秒都在等一个超时的网页。把责任错误地归给模型，会引导错误的优化方向。

第三，与工具时间线冲突。时间线记的是工具自身耗时，摘要如果报端到端，两个数字天然不等，用户又要问「为什么对不上」。

所以这一版只报能对得上的数字：工具耗时、token、引用条数。宁可少一个指标，也不要多一个解释不清的指标。

## 纯对话回合不重复展示

纯对话回合仍然显示原来的 token 行。

这不是偷懒，而是避免同一信息出现两次。如果摘要也对纯对话渲染，界面上就会出现两行 token：一行来自旧组件，一行来自新摘要，数字一样，位置不同，用户会以为是两回事。

两条路径的边界很清楚：有工具或有引用，走摘要；否则走旧 token 行。互斥，不叠加。

## 克制口径的收益

指标越多，看起来越专业，实际越难维护。

每加一个数字，就要回答四个问题：它从哪来、什么时候更新、和别的数字什么关系、异常时怎么显示。答不上来，这个数字迟早会变成误导读者的噪音。

这一版只用了三个已有数据源：工具轨迹、token 字段、引用列表。没有新增埋点，没有新增接口，也没有新增存储。摘要组件本身是纯展示，输入相同，输出必然相同。

这种克制还有一个隐性收益：它可以被测试。断言「五次调用两次失败时显示成功三失败二」「总耗时等于逐条之和」，都是确定性用例，不依赖真实网络和模型。

## 边界

摘要不区分工具类型，只报总次数。想知道搜索了几次、抓取了几次，展开逐工具列表即可。

不做历史累计统计。跨回合的平均耗时、成功率，属于另一个层次的分析，不在这一行里塞。

也不做耗时预警。某次调用特别慢，摘要只如实显示，不弹提示、不变色——因为「多慢算慢」依赖网络环境，硬编码一个阈值只会制造误报。

## 收尾

回合摘要的价值不在数字本身，而在数字之间的关系：总耗时能加回逐项，工具次数能对上时间线，引用条数能对上来源列表。

只要这三组关系成立，用户就能相信这行摘要是描述，而不是装饰。反过来，一旦某个数字对不上，整行都会失去可信度——这也是为什么这一版宁可只报三件事，也不肯多加一个说不清来源的指标。
