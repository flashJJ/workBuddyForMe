# 抓取降级：让「不再重试」成为一条可解释的规则

联网问答里有一个很容易被忽略的坏循环：模型请求抓取某个网页，失败；它换个措辞，又抓同一个地址；再失败；上下文里已经堆了几段错误信息，用户还在等。

单看每一步都合理——模型不知道这个地址为什么打不开，重试是它唯一会做的补救。但从系统角度看，反复请求一个必然失败的地址，只是在消耗时间和预算。

这一版给这条链路加了一条边界：同一地址连续失败两次，本轮后续调用直接跳过，结果标记为降级。规则本身很短，难的是一路上的几个判断：状态放在哪、哪些失败算数、什么时候清零、界面怎么知道、模型怎么被提醒。

## 先看失败是怎么被重试的

工具调用是分轮的。模型给出若干调用，运行时逐个执行，结果回灌成工具消息，下一轮模型再决定要不要继续。

抓取失败在这里不是一个终止信号，而是一条普通的工具结果。模型读到「超时」，很自然会想：也许换个地址、也许是暂时抖动，于是它再调一次同名工具。旧实现对此没有任何记忆，失败次数既不累计，也不跨轮。

问题的本质不是模型太固执，而是系统没有把「这个地址本轮已经不行了」这件事告诉它。

## 状态必须跨工具轮共享

工具循环函数每轮都会被重新调用，参数是新的。如果把计数器写在循环函数内部，第二轮就归零，规则等于没写。

所以状态被提到编排器：每轮对话开始时创建一个追踪器，内部持有一个「地址 → 连续失败次数」的映射，随参数传进工具循环。循环只负责读和写，不负责生命周期。

```text
编排器：tracker = { failures: Map<url, count>, seen: Set<url> }
每轮：runToolCallLoop({ ..., fetchFailures: tracker.failures })
循环内：读 count 决定是否短路；执行后写 count
```

参数里的计数字段是可选的：单独调用工具循环时不传，就在本次循环内自建一个。这让循环仍然可以独立测试，不必依赖编排器。

## 只对可恢复的失败累计

不是所有失败都值得降级。

网络中断、连接被拒、域名解析失败、请求超时、页面超过体积上限——这些是「换一条路可能还有救」的失败，或者至少可以退回到搜索摘要。它们进入计数。

鉴权失败和「被拒绝访问」不走这条路。密钥失效、权限不足、目标站点明确拒绝，重试同一个地址不会有任何不同结果，但它们也不该被悄悄改写成「已降级」。这类失败保持原有语义返回，让用户看到真实的失败原因。

这个区分落在一次文本判定上：拿工具结果的可读输出与摘要去匹配一组关键词。它不完美，但对一个本地应用够用，而且规则集中在一个函数里，改起来只有一处。

## 成功一次就清零

计数是「连续失败」，不是「累计失败」。

一旦某个地址抓取成功，计数直接删除。这样做的含义是：网络抖动、临时 502、代理切换之后恢复，都不会让这个地址在后续轮次里被误伤。

反过来，如果失败是间歇性的——成功、失败、成功、失败——永远不会触发降级。这是有意的：能成功就说明这条路还有效，系统不应该替用户放弃。

## 达到阈值后短路，但仍然留痕

阈值定在两次。第一次失败可能只是抖动；第二次失败基本可以判断这条路本轮走不通。再往上加阈值，换来的是更多等待，而不是更高的成功率。

达到阈值后，后续对同一地址的调用不再发网络请求。它会立刻得到一个合成结果：`ok: false`、`degraded: true`，输出里直接写明「本轮已连续失败两次，不再重试，请基于已获得的搜索摘要作答」。

关键是这个短路并不是「什么都不发生」。工具开始事件、结束事件、追踪条目、回合摘要里的工具次数，全都照常产生。用户看到的是「有一次调用失败了，并且被标记为降级」，而不是一次凭空消失的调用。

## 降级要透传到界面

`degraded` 是工具结果上的一个可选标记，它随追踪条目和结束事件一起流到 web 端。

失败卡的文案随之收敛：抓取失败只保留两个动作——用浏览器打开、检查网络或代理。早先的实现还会引导用户「重试」，现在这条引导被拿掉了，因为重试同一个地址正是我们要阻止的行为。

卡片上额外显示一行降级说明。它不解释技术细节，只回答用户最关心的问题：这次为什么没拿到全文，以及回答是基于什么生成的。

## 收尾提示只注入一次，且不落库

界面之外，还要让模型知道。降级发生在工具轮里，而模型可能在下一轮继续尝试，所以编排器需要往出站消息里补一条系统提示。

提示的内容很明确：这些地址本轮没有取到全文，请基于已有的搜索摘要作答，并说明未取到原文，不要再请求同一链接。

两个约束保证了它不会变成噪音。第一，按地址去重：每个本轮新降级的地址只提示一次，重复降级不重复追加。第二，只进内存中的出站消息，不写库、不进历史消息。下一轮对话重新开始，这条提示不应该成为用户对话记录的一部分。

## 短路结果仍然是一份完整的工具结果

被短路的那次调用没有发网络请求，但它返回的东西必须和一次真实失败长得一样齐：`ok: false`、`degraded: true`、一句给模型的输出、一句给界面的摘要，外加一份证据——来源地址、覆盖范围标为「未获取正文」、局限里写明「同一链接重复失败，已降级」、采集时间照常填写。

带上证据不是为了好看。回合摘要、失败卡和最终回答的前提都从同一个结果对象里读；如果这里只回一个裸错误，追踪里就会出现一次没有来源的调用，界面也分不清它是「跳过」还是「真的又失败了一次」。

## 单测锁住判定，也锁住「不再累加」

这条规则的测试基本都不需要网络，因为关键判断都被拆成了纯函数。

- 地址提取：参数缺失、不是对象、`url` 不是字符串、空白串，都返回空；合法地址做去首尾空白。
- 失败分类：输出里出现超时、连接、解析失败、页面过大的特征词算可恢复；鉴权失败、明确被拒、已经标记过降级的一律不算。
- 计数语义：第一次失败只记数不降级；第二次失败把结果标成降级；成功一次后计数被删除，再来一次失败仍从 1 开始。
- 跳过路径：进入降级分支后不再发请求，也不再把计数加一——否则计数会随着每次跳过继续膨胀，日志里看不出真实失败次数。
- 提示注入：同一地址在一轮里反复降级，收尾提示只追加一次；提示只进内存中的出站消息，不进入持久化路径。

断言写在这些地方，比渲染一张失败卡再去找文案稳定得多。界面只需要验证「降级标记到了卡片上没有」。

## 它和工具熔断不是一回事

项目里本来就有一层熔断：某个工具连续失败，会被短期跳过，冷却到期后半开重试。它和抓取降级看起来相似，管的却不是同一件事。

熔断是按工具名的，目标是「依赖整体不可用」——比如搜索服务宕机，所有调用都别试了。它有冷却时间，到期自动放行，因此是一条时间维度的规则。

降级是按地址的，目标是「这一个链接本轮没救了」。它没有冷却，作用域就是当前这一轮对话；同一个工具换个地址照常请求，不受影响。

两者的执行顺序也说明了分工：熔断检查在前，命中就直接跳过，不进入执行路径；降级只在真正发起过请求、并且失败属于可恢复类别时才计数。也就是说，熔断管的是「这个工具现在还能不能用」，降级管的是「这个地址还值不值得再试」。

保留两层而不是合并成一层，是因为它们的恢复条件不同。工具可能一分钟后就恢复，地址可能整轮都不会恢复。用同一个阈值和同一套状态去表达，只会让两边都说不清。

## 为什么是「可解释」而不是「更聪明」

一个更容易想到的方案是让模型自己判断「这个地址是不是不值得再试」。但那会把一条确定性规则变成概率行为，而且失败时无法复现。

现在的结构是三层一致的：计数在编排器，判定在纯函数，呈现同时在界面和提示词里。同一个事实——这个地址本轮失败了两次——被三处用同一种方式表达。用户、界面、模型看到的是同一件事。

## 边界与代价

这条规则的覆盖面是有限的。它只处理同一地址的重复失败，不处理「换了三个地址都失败」；它靠关键词识别失败类型，措辞变化可能漏判；两次阈值对慢速站点偏保守，用户可能在第二次失败后才拿到降级结果。

我们接受这些边界，因为它的收益很直接：把一段确定无用的等待，换成一次诚实的、基于已有材料的回答。

降级不是把失败藏起来。结果仍然是失败，只是不再重复，并且把「没取到全文」写进了答案的前提里。这大概是这类规则最该守住的分寸：可以少做一次尝试，但不能少说一句实话。
