## 问题：抓回来的网页，三分之二是噪声

`fetch_webpage` 工具（v0.2 起就有）的初版行为：抓回 HTML，`htmlToText` 全量转文本。实际用起来才发现问题：**抓回的「正文」里，导航栏、侧边栏、页脚、相关推荐、评论区占了大头**。

一个典型技术博客页面，全量转文本约 8000 token，其中真正的文章正文不到 3000——其余是「首页 | 归档 | 关于我」「猜你喜欢」「Copyright © 2024」。这些噪声的代价是双重的：

**token 成本**：噪声占用上下文预算（v0.5 之后预算是稀缺的，B02 体系下每 token 都在和历史消息抢座位）。

**模型注意力**：噪声稀释正文的信号密度。模型要在 5000 token 的导航与广告里找 3000 token 的正文，长上下文下「找不到重点」的错误率明显上升——实测问「这篇文章的结论是什么」，带噪声版本更容易引用到侧边栏的「热门文章」标题。

M4 的正文抽取（[html-extractor.ts](file:///e:/code/traeWork/workBuddyForMe/packages/core/src/tools/html-extractor.ts)）就是解决这一件事：**在转文本之前，先选出「正文块」，扔掉其余**。

## 两步走：剥噪 + 选块

抽取分两步，对应 HTML 噪声的两种形态：

**第一步，剥语义噪声标签**。`nav` / `aside` / `footer` / `header` / `script` / `style` / `noscript` 整棵子树删除。这些是 HTML5 语义标签给出的免费信号——正经网站的内容结构里，导航就是 `<nav>`，侧栏就是 `<aside>`。模板引擎生成的现代站点，这一步能剥掉六七成噪声。

**第二步，候选块选择**。剥完噪声后，按优先级选正文容器：

```text
article  →  main  →  body
```

`article`（文章语义）→ `main`（主内容区）→ `body`（兜底）。为什么这个顺序：语义标签越具体，正文密度越高。`article` 存在时它几乎必然是正文（HTML5 规范语义就是「独立完整的内容单元」）；`main` 次之（页面主内容，可能含文章外的辅助区）；都没有时退回 body——此时剥噪步骤已经保证了下限。

## 为什么不引入 Readability 算法

Mozilla Readability（Firefox 阅读模式同款算法，按文本密度/链接密度/段落长度打分选正文）是「正确」的工业方案，评审时被否了，理由三条：

1. **依赖与体积**：@mozilla/readability + jsdom 进 lockfile，jsdom 的体积和打包复杂度（v0.4 canvas 的前车之鉴）对一个「剥噪选块」需求不成比例。
2. **本地场景的输入分布**：fetch_webpage 的主要输入是技术文档、博客、新闻——语义标签覆盖率在这类现代站点上很高。Readability 的价值在老旧站点和不规范 HTML，那不是主场景。
3. **可调试性**：`article → main → body` 的选择逻辑 20 行读完，抽错了看一眼 HTML 就知道为什么；Readability 的打分模型抽错了，排查要钻算法内部。**本地优先项目的算法选型，可调试性权重高于通用性**。

语义标签方案覆盖不了的情况（整个站点就一个 `<div id="app">`），兜底是 body + 剥噪后的全量——退回 v0.2 行为，不是更差。

`htmlToText` 保留 re-export 兼容：旧调用方不炸，新路径走 extractor。加法演进，不破存量。

## 与 SSRF guard 的协同

fetch_webpage 的另一层防护是 [ssrf-guard.ts](file:///e:/code/traeWork/workBuddyForMe/packages/core/src/tools/ssrf-guard.ts)（v0.2 就有，v0.6 补强）：URL 解析后校验目标 IP，拒绝内网地址（127.0.0.0/8、10.0.0.0/8、192.168.0.0/16……）——防止模型被诱导请求 `http://192.168.1.1/router-admin` 这类内网地址。

正文抽取与 SSRF guard 是同一个工具的两层防护：**guard 管「能不能去」，extractor 管「回来之后怎么用」**。danger 级权限（B04）管「要不要问人」。三层各管一段，职责不重叠。

## 效果实测

抽取上线后的典型数据（技术博客样本 20 页）：token 占用中位数从 ~8000 降到 ~3000（**-62%**），正文信噪比（正文 token / 总 token）从 ~37% 提到 ~92%。

对回答质量的影响用 v0.5 的评估方法论验证：同一批「读网页回答问题」用例，抽取前后的 judge 均分对比——结论类问题的正确率提升最明显（正文密度低时模型容易被「相关推荐」标题带偏）。

---

## 小结

正文抽取是「小投入大回报」的典型：不到 100 行的剥噪 + 选块，换来 62% 的 token 下降和可观测的回答质量提升。决策核心是克制——不为边缘场景引入工业级算法，用语义标签覆盖主场景，用兜底路径保证下限。
