# 工具熔断器：三连败跳闸、五分钟后半开试探

工具生态开放以后，工具来自外部 MCP server——它们会挂、会慢、会返回垃圾。没有防护时，一个坏掉的工具会把这个本地 AI 应用的对话拖进死亡循环。

## 问题：一个坏工具不该拖死整个对话

典型症状：模型调用 → 超时 30 秒 → 失败回传 → 模型重试 → 又超时 → ……用户看着回答流卡死两分钟，什么输出都没有。

给每个工具挂上熔断器（`packages/core/src/tools/tool-breaker.ts`）：经典三态断路器模式在工具调用场景的最小实现。

## 状态机：closed → open → half-open

```text
        连续失败 3 次              冷却 5 分钟到期
closed ──────────────→ open ──────────────────→ half-open
  ↑                                                │
  │            试探成功（1 次）                      │ 放行一次试探
  └────────────────────────────────────────────────┘
       试探失败 → 回 open，重新冷却 5 分钟
```

三态语义：

**closed（正常）**：正常放行，记录连续失败计数。成功一次计数清零——注意是**连续**失败，间歇性失败（偶发网络抖动）不会积累到跳闸。计数阈值 `BREAKER_FAILURE_THRESHOLD = 3`：三次连续失败才认定为工具级故障，而非偶发。

**open（跳闸）**：直接拒绝，工具结果回传结构化「TOOL_CIRCUIT_OPEN」——模型收到后得体告知用户「这个工具暂时不可用」，而不是继续撞墙。冷却 `BREAKER_COOLDOWN_MS = 5min`：给外部服务恢复的时间，也避免频繁试探本身成为负载。

**half-open（半开）**：冷却到期后放行**一次**真实调用试探。成功 → 回 closed（计数清零，完全恢复）；失败 → 回 open（重新计时冷却）。半开态只允许一个试探——并发场景下用状态翻转的原子性保证（先翻状态再放行，第二个并发调用看到的是 open）。

## 接入点：门控之后，执行之前

tool-call-loop 的执行序列（完整版）：

```text
resolveTool → 权限门控（三级权限 + 挂起确认）→ 熔断检查 → 执行 → recordResult
```

熔断检查在权限门控**之后**——跳闸的工具不该弹 HITL 弹窗（用户点了允许然后发现工具是坏的，白白消耗一次确认的权威性）。

`recordResult` 在执行后记录成败。判定口径：**执行抛错或工具结果带 error 算失败，正常返回算成功**。模型层的不当使用（参数错误被工具拒绝）也算失败——从熔断器视角，「这个调用没成功」就是事实，原因分类留给日志。这个口径偏保守，但保守是熔断器的本职。

## 配置怎么管：内存态 + 面板手动重置

熔断器状态是**纯内存**（Map<qualifiedToolName, BreakerState>），不落库。理由：熔断是运行期的瞬时健康状态，重启后重新探测是最自然的语义——落库反而要处理「重启后状态该不该恢复」的伪问题。外部工具的可用性本来就要实时探测，内存态 + 半开试探就是这个探测机制。

运维出口在设置页 `tool-breaker-panel.tsx`（GET/POST /api/tools/breakers）：列出所有有熔断记录的工具、当前状态、失败计数、下次可试探时间，支持**手动重置**（回 closed）。手动重置的场景：用户知道「服务我刚重启好了」，不想等 5 分钟冷却——自动化兜底 + 人工快车道，两个都要。

## 为什么调试台可以绕过它

后面要讲的调试台（`debug-executor.ts`）刻意**绕过熔断器和 HITL**。设计依据一句话：**用户在调试台点「试跑」本身就是授权**。

熔断器防的是「模型无意识地把坏工具撞死」；调试台是人有意识的单次操作——撞一次墙正是调试的目的（「我就想知道它现在通不通」）。绕过熔断，调试台才能回答「这个工具现在到底行不行」；绕过 HITL，排障流程才不会被弹窗打断。

但绕过有边界：**超时仍在**（MCP 60s / 内置 15s），权限语义仍在（工具卡片的权限徽章照常显示）。调试台绕过的是「自动防护」，不是「安全边界」——它本来就是设置页里的显式排障工具，入口本身就有足够的用户意图。

## 后来的复用：熔断信号升级为任务终止信号

熔断器后来获得一个新职责：任务 Agent 循环里，同一工具连续失败 3 次（熔断跳闸）是**任务自动终止的条件之一**——Agent 循环比普通对话更怕死循环（它会自己决定下一步），熔断信号直接升级为任务级终止信号。单个工具的故障隔离（本篇）→ 任务级的失控兜底，同一机制在两个层级的复用。

## 小结

熔断器的实现是这个模式的最小形态：三态 + 连续失败计数 + 单试探半开，内存态不落库，面板留人工重置口。它回答的问题很具体——工具生态开放后，单个工具的故障半径必须被限制在这个工具自己身上。
