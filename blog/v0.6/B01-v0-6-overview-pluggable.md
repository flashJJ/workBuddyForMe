## 先回答：v0.6 为什么是「会接活」

v0.5 让助手记得住，v0.4 让数据随身走。但回头一看，助手能干的「活」还是出厂自带的那几件：查知识库、抓网页、看时间。问题清单：

1. **工具硬编码**：`enabledTools` 是固定枚举，加一个新工具要改 core 代码发版。用户想接一个自己的工具？没门。
2. **与 MCP 生态隔绝**：业界工具生态（filesystem、fetch、各种本地服务）蓬勃生长，本地优先产品恰恰最适合 stdio MCP——但我们没有 MCP 客户端。
3. **无权限分级**：工具执行无「读/写/联网」区分。工具只有三个时这不是问题，工具 thirty 个时这就是安全问题。
4. **技能不可沉淀**：「怎么写周报」这类流程性知识（v0.5 称作程序性记忆）没有承载物，同一套 prompt + 工具组合无法打包复用。

v0.6 的主题「**会接活**」：助手能干什么是用户定义的——MCP 服务器接进来、技能包装进去、写操作必须经人确认。22 个提交，一次数据库迁移（v008，后增量到 v010），四个里程碑全部落地。

## 四件事一览

| 模块 | 代号 | 解决的问题 |
|------|------|-----------|
| MCP 客户端 + 服务器管理 | M1 | stdio/HTTP 接入外部工具生态，命名空间隔离，状态可视 |
| 权限分级 + HITL | M2 | read/write/danger 三级，危险操作弹窗确认，授权可记忆可撤销 |
| 技能包体系 | M3 | skill.json 声明式定义，文件夹放入即用，UI 启停，随备份轨导出 |
| 可观测 + 熔断 + 调试台 | M4 | 工具卡片显示来源/权限徽章，连续失败自动熔断，不经模型试跑工具 |

P0 三件是主线，M4 是把「工具多了以后」的运维面补齐。

## 架构总图

```text
┌────────────── 工具来源 ──────────────┐
│ 内置工具（v0.2 起）                   │
│ MCP 工具（mcp:<server>:<tool>）       │──→ 统一工具注册表 tool-runtime
│ 技能包（提示词注入 + 工具白名单）      │         │
└──────────────────────────────────────┘         ▼
                              ┌─── tool-call-loop ───────────────┐
                              │ 1. 权限门控（read 放行 / write+danger → HITL）
                              │ 2. 熔断检查（trip 则拒绝）          │
                              │ 3. 执行（内置直调 / MCP 转发）      │
                              │ 4. 记录结果 → 熔断器               │
                              └──────────────────────────────────┘
                                         │ SSE 事件
                                         ▼
                     工具卡片（来源/权限/耗时徽章）+ HITL 弹窗
```

三个值得注意的架构事实：

**MCP 工具与内置工具同链**。模型看到的 tool_calls 是同一种 schema，内置查表和 MCP 限定名解析都在 `resolveTool` 一处。模型无感知，链路无分叉——这是「接入生态」而不是「另起炉灶」的关键。

**技能不改变工具链路**。技能 = 提示词模板（注入 system）+ 预绑定工具白名单（与助手白名单取并集）。它影响的是「模型看到什么 prompt、能用哪些工具」，不动工具执行本身。

**权限门控在工具循环里，不在路由里**。无论是对话中的模型调用还是调试台的人工调用，危险操作都过同一道门——安全语义不随入口变化。

## 关键决策速览

**MCP 客户端最小自实现，弃官方 SDK**。官方 `@modelcontextprotocol/sdk` 对纯客户端用途硬拉 express5/hono/jose 等 17 个服务端包，lockfile +513 行。协议面（initialize/tools/list/tools/call + notifications/initialized）自己实现只要五个文件。详见 B02。

**权限三级 + HITL 挂起-恢复**。工具声明权限级，write/danger 级执行前 SSE 事件挂起循环、前端弹窗、用户三按钮（拒绝/本次允许/一直允许），120 秒无响应自动拒绝。详见 B04/B05。

**熔断器状态机**。连续失败 3 次 trip（open），5 分钟冷却后 half-open 放行一次试探。工具越接越多，单个工具的故障不能拖死整个对话。详见 B07。

**调试台绕过熔断与 HITL**。用户主动点「试跑」本身就是授权——调试台因此不经模型、不经熔断、不经弹窗，但 MCP 60s/内置 15s 超时仍在。详见 B09。

## Non-Goals

- 代码执行沙箱（Docker/WASM）——本地单机成本高，先靠权限分级兜底，v0.7+ 评估；
- 技能市场/远程分发——本地优先，先做好本地文件夹形态；
- 多智能体编排——归 v0.8；
- 云端技能同步。

## 测试基线

合入前全部门禁绿：check（typecheck + lint + 文件 ≤300 行）/ 单测 12 包 / 集成 12 / E2E 7/7。MCP 模块 17 测含真实子进程集成（测试里真的 spawn 一个 echo MCP server 跑完整握手）；HITL 服务端 5 例 + 挂起注册表 8 例；技能 loader/service/装配 25 例。

手测验收记录：技能面板启停（PATCH 往返）、删除引用（confirm 弹窗 + 磁盘源文件夹保留）、dev server 重启后内置技能自动重新登记。

## 一句话总结

v0.6 用 22 个提交把「工具」从硬编码枚举变成了**用户可扩展的生态接入 + 声明式技能包**，并用「权限分级 + HITL + 熔断」三件套回答了「工具多了以后怎么不失控」。核心取舍是一以贯之的本地优先：宁可自实现 500 行协议客户端，不为纯客户端用途拉 17 个服务端依赖。

下一篇 B02 就讲这个 v0.6 最重要的选型决策：MCP 协议最小自实现——官方 SDK 为什么被弃，五个文件怎么撑起完整握手与工具调用。
