# 从对话里发起任务，不该再交代一遍背景

我们的桌面 AI 应用有两个入口：在对话里聊天，或者在任务模式里让 agent 自己跑多步。用户最常见的动作，是聊到一半说“那就帮我把它做掉”。

此前这两条链路是断开的：任务只拿到一句话目标，完全不知道刚才在聊什么。

## 一、任务侧原来拿到什么

任务启动时，启动器只解析出三样东西：规划器、允许的工具列表、是否具备视觉能力。

没有会话上下文。目标里写了“按刚才说的改”，任务就会去猜“刚才”是什么。用户只能把背景再复述一遍，或者干脆放弃任务模式。

这不是模型能力问题，是信息根本没送进去。

## 二、启动时装配一次

改造点在启动函数上：从同步改为异步，在真正开始跑循环之前，先装配一段会话上下文块。

```ts
const contextBlock = await buildTaskContextBlock({ ... })
```

这段块不是新写的摘要器，而是复用任务侧已有的装配能力，按固定顺序拼：

- 会话摘要；
- 事实与检查点；
- 当前计划；
- 近期对话；
- 长期记忆。

顺序从“最稳定的结论”到“最鲜活的细节”，预算不够时，后面的先被裁掉。

## 三、失败不能阻断任务

启动路径上任何一次额外的读取都可能失败：数据库没有对应会话、摘要还没生成、记忆服务不可用。

我们的处理很克制：

```ts
try {
  return await buildTaskContextBlock(...)
} catch {
  return null
}
```

装配失败就当作没有上下文，任务照常启动。用户最多感受到“这次它没记住背景”，而不是“任务根本没跑起来”。

降级路径必须比正常路径更简单，否则它自己就会成为新的故障源。

## 四、启动即留痕

上下文块装好以后，立刻写一条 `task_start` 快照，记录这次装配的场景、窗口、预算和实际占用。

这样做的好处是，事后不需要猜：“任务有没有拿到上下文、拿到了多少、是不是被截断”，在时间线里一眼能看到。

真机验收里，4096 窗口下这条快照的记录是实际 54 token、预算 614。数字很小，但证明链路通了：会话内容确实进了任务启动。

## 五、块怎么传进循环

启动产物里增加一个可选字段，透传到任务循环的启动参数：

```ts
interface TaskStartParams {
  goal: string
  contextBlock?: string
}
```

可选是关键。没有会话、装配失败、老调用方不传，都走同一条路径——提示词里没有那一段，其他逻辑不变。

桌面任务和协作里的执行角色共用同一条注入路径，避免出现“协作有背景、任务没背景”的第二套分支。

## 六、每一步的决策提示词

上下文块只是启动时的一份背景。真正调用模型是在每一步决策，那里还要再装配一次。

任务决策器传入自己的场景标识，并在第一次决策时写一条 `task_step` 快照；之后只有在“未截断”变成“已截断”时才补写一条，避免每一步都产生事件。

真机里同一次任务的 `task_step` 快照是 979 token、预算 3008，未截断。启动时的 54 token 背景，加上目标、工具目录和步骤历史，最后落在预算之内。

## 七、为什么快照要节流

如果每一步都写快照，一个二十步的任务会产生二十条几乎相同的事件，时间线会被噪声淹没。

只在“首次”和“状态发生变化”时记录，既保留了基线，也保留了异常点。观测的目的是回答问题，不是收集尽可能多的数据。

## 八、两个入口都要等

任务有两条启动路径：用户在界面上发起，以及定时任务自动发起。

装配改成异步后，两条路径都必须等待结果。定时任务那条原本是同步调用，这次把返回类型放宽为“值或 Promise”，统一 `await`。

少改一处，就会出现“手动发起有上下文、定时发起没有”的诡异差异。这种差异在测试里很难发现，在用户那里却很明显。

## 九、结果

- 从对话发起任务，提示词里能带上刚才的会话背景；
- 装配失败返回空，不阻断启动；
- 启动和决策各有一条快照，预算是否吃紧可查；
- 两条启动路径行为一致，任务与协作共用注入方式。

上下文注入的价值不在“多带了一段文字”，而在于让任务模式和对话模式看起来像同一个助手，而不是两个互不相识的工具。
