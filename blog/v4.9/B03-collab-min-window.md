# 以谁的窗口为准：协作上下文块的最小窗口

协作域里有三个角色：规划、执行、审查。它们各自绑定模型，各自发请求，但共用同一段会话上下文块。

这段上下文块之前是按执行角色的模型窗口装配的。问题在于，规划角色可能绑定的模型窗口更小。

## 一、错位是怎么发生的

OpenAI 兼容的服务通常按“本次请求使用的模型”校验窗口。规划角色发请求时，服务端只看规划模型的窗口。

如果上下文块按执行角色的大窗口来算，比如按 32768 装配出 2000 token 的背景，而规划模型只有 4096 窗口，这段背景在规划侧就超标了。

结果很典型：执行角色一切正常，规划角色偶发 400，或者被上游静默截断，最后的计划质量莫名其妙地差。

更麻烦的是报错信息。上游通常只返回“总 token 超限”，不会说明是这段共享背景装多了。排查时会先去怀疑提示词模板，而不是窗口口径。

## 二、为什么不能按角色各装一份

最直接的方案是每个角色各装一份上下文块，各自适配。听起来最精确，实际成本很高：

- 同一段会话内容要被反复读取、反复压缩；
- 三份上下文块内容不同，排查时无法对齐；
- 任务执行过程中角色可能换模型，块还要重建。

更重要的是，上下文块的语义是“这次协作共享的背景”。共享的东西，应该有一个共享的装配口径。

## 三、取最小值

我们把口径改成三个角色模型窗口的最小值：

```ts
const windows = ['planner', 'executor', 'reviewer']
  .map((role) => resolveWindow(role))
  .filter((n) => typeof n === 'number' && n > 0);

const contextWindow = windows.length > 0
  ? Math.min(...windows)
  : null;
```

然后照常交给预算解析。窗口取小，预算自然跟着变保守。

举例：执行角色 32768 窗口，规划角色 4096 窗口，取最小后是 4096；上下文块预算从 2000 降到 614。执行角色本来能吃得下更多，但它少吃的这部分，换来的是规划角色不再超窗。

预算变小之后，块内部的裁剪顺序不变：摘要、事实、计划优先保留，近期对话与记忆排在后面。也就是说，小窗口组合下先被牺牲的是细节，而不是结论。

## 四、缺失角色怎么办

三个角色不一定都配置了模型。规划或审查可能复用执行角色的模型，也可能完全没绑定。

我们的处理是逐角色尝试解析，解析失败的直接跳过，不阻断装配：

- 两个角色可用，就取这两个的最小值；
- 只有一个角色可用，就用它自己的窗口；
- 三个都拿不到，传 `null`。

传 `null` 时预算函数按“窗口未知”处理，返回上限 2000。这是一条刻意保守的兜底：宁可上下文块小一点，也不要因为窗口猜错而让请求失败。

## 五、代价与边界

取最小值确实会让某些组合偏保守。执行角色拿着超大窗口，却只能吃一小块上下文。

我们接受这个代价，原因有三点：

- 偏保守只影响提示词的信息量，不影响功能正确性；
- 真正的大窗口场景，上限 2000 仍然兜底，不会无限缩小；
- 超窗失败的代价远高于少带一点背景，尤其是小窗口弱模型，失败往往没有清晰报错。

还有一条边界要说明：这里取的是模型配置里的窗口，不是服务端真实生效的窗口。如果用户手工把模型窗口配大了，还是会超。这类配置错误不在本层兜底范围内。

保守也有下限。预算函数本身还有 320 的保底，所以即使三个角色都是很小的窗口，上下文块也不会缩到不可用。

## 六、为什么不做动态调整

也考虑过“先按小窗口装，失败再升级”或者“按角色分别装”。最后都没做。

前者需要重试机制，而重试会带来重复计费和不确定的输出；后者会把共享上下文变成三份私有上下文，和协作的语义相悖。

静态取最小值还有一个好处：它只依赖模型配置，不依赖运行结果。同样的输入永远得到同样的块，测试可以直接断言“窗口取小以后预算是多少”。

一次装配、一个口径、一条失败路径，是小版本里更稳的选择。

## 七、结果

- 规划、执行、审查三个角色共用同一段上下文块；
- 上下文块按三角色最小窗口装配，规划角色不再因小窗口超限；
- 任一角色未配置模型时跳过，不阻断协作；
- 全部解析失败时回落到 2000，行为可预测。

窗口是请求的属性，不是某个角色的私有资源。共享内容以最紧的那道门为准，是这类协作系统里最省事的正确做法。
