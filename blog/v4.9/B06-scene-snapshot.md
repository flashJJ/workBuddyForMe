# 预算吃紧的时候，用户和开发者都看不见

上下文预算生效以后，一个新的问题浮现出来：你无法判断它有没有生效。

请求成功了，不代表没有发生截断；回答变差了，也不代表预算不够。日志里只有“调用成功”，没有“这次装了多少、预算多少、裁了几条”。

## 一、只覆盖一个域的观测

对话侧早就有上下文快照，能看到意图、配额和压缩结果。

但协作、桌面任务、Flow 三个域没有。它们各自有过一些预算事件，散落在阶段日志里，字段不统一，也没有统一的时间线呈现。

结果是：小窗口下协作变慢，只能靠猜；某个 Flow 节点偶发失败，只能翻上游返回码。

## 二、加一个通用事件

我们新增了一个事件类型 `context_scene_snapshot`，专门记录“一次装配的预算结果”。

它不绑定某个域，只绑定一次装配。字段就是装配函数已经算出来的那些：

```text
scene / role
contextWindow / usableWindow / reserveTokens
budgetTokens / promptTokens
truncatedMessages / droppedMessages / truncated
```

没有额外的推导，也没有二次统计。装配函数返回什么就写什么，避免出现“事件里的数字和实际用的数字不一致”。

## 三、三个作用域

事件复用现有的会话事件表，用 scope 区分归属：

| 域 | scope | scopeId |
|---|---|---|
| 协作 | `agent` | 协作运行标识 |
| 桌面任务 | `task` | 任务运行标识 |
| Flow | `flow` | 图运行标识 |

这样按运行查预算记录，和查其他事件是同一套方式，不需要新接口，也不需要新的表。

## 四、为什么复用事件表

新开一张表看起来更专业，实际会带来一串成本：建表、索引、清理策略、查询接口、备份兼容。

现有事件表已经具备三件我们需要的东西：按 scope 与 id 查询、全文检索、180 天保留。预算快照的生命周期和普通事件一样，没有理由单独管理。

复用的代价是表会变大一点。考虑到事件本来就在持续写入，这个增量可以接受。

## 五、快照粒度是设计的一部分

不是每次装配都值得记一条。三个域采用了不同的粒度：

- 协作：每个角色每次调用一条，最多三条一轮；
- 任务：首次一条，之后只在从未截断变为已截断时补一条；
- Flow：只有发生截断的节点才写。

粒度不同，是因为三个域的事件密度不同。协作一轮只有三次调用，全记下来是有价值的；任务可能跑二十步，全记就是噪声；Flow 一张图几十个节点，只记异常最划算。

## 六、写失败不能影响主流程

快照是观测，不是业务。写入采用 best-effort：

```ts
try {
  await recordSceneSnapshot(...)
} catch {
  // 忽略，不阻断请求
}
```

数据库忙、事件表锁住、字段校验失败，都不应该让一次正常的模型调用失败。

这类“顺带记录”的功能，必须有明确的失败边界。否则观测系统会变成新的单点故障。

## 七、时间线上怎么读

时间线新增了一个标签：`上下文快照：<场景>`。

详情里直接展示三个数：预算、实际、是否截断。需要更细的字段时，展开原始 payload 就能看到可用窗口、输出预留和丢弃计数。

以 4096 窗口为例，一条协作快照会显示：窗口 4096、可用 3686、预留 614、预算 3008、实际 586、未截断。

不需要懂公式，也能判断这次装配是宽裕还是紧张。

## 八、没有做独立面板

这一轮没有新增界面。任务、协作、Flow 的快照通过时间线页和应用的事件接口查看。

原因很简单：先把数据写对、写全，再决定用什么形式呈现。过早做面板，容易把还没稳定的字段固化成 UI。

## 九、结果

- 三个非对话域都有可查询的预算快照；
- 预算、实际、截断状态在同一处可见；
- 不新增表、不做数据搬迁，回滚只需回退代码；
- 写入失败不影响主请求；
- 时间线能按运行查看完整装配序列。

可观测性不是多加日志，而是让一个已经存在的决策——装多少、裁多少——变得可回答。
