# 每一块都有上限，加起来却没有

一个模型请求里通常有三类内容：系统提示词、工具目录、以及业务拼进来的上下文与历史。前两类由框架约束，后一类也各自有预算。看起来每一块都受控。

但如果把整段消息加起来，总量没有任何上限。

## 一、缺口在哪

协作的上下文块按窗口的 15% 装配，步骤历史按 12%，工具目录另算，当前观察又是另一段。每一项单独看都合理，叠在一起就可能顶穿窗口。

4096 这种小窗口最容易暴露：某一轮工具返回特别长，或者历史里有一大段报错文本，模型调用直接 400，重试也一样，因为下一次装配的结果依然超长。

分块预算解决的是“每一块别太大”，解决不了“整体别超”。这是两个不同的问题，需要一个整段装配函数。

## 二、预算怎么算

输入只有消息列表和模型窗口，输出是装包后的消息和一份统计：

```ts
fitPromptMessages(messages, { contextWindow, scene, role })
```

计算分三步：

```text
usableWindow = floor(contextWindow × 0.9)
reserve      = 按窗口比例预留的输出空间
budget       = max(64, usableWindow − reserve − 64)
```

0.9 是安全系数：token 估算用的是字符粗估，不是真实分词器，留 10% 给估算偏差和消息结构开销。

输出预留沿用对话侧的比例化做法：窗口的 15%，下限 512，上限 2048。生成也要占窗口，输入装得太满，输出会被截断。

最后的 64 是结构余量，比如 role 字段、分隔符、工具声明这些无法逐段计入的开销。

以 4096 窗口为例：可用窗口 3686，输出预留 614，最终预算 3008。

## 三、没超预算就原样返回

这是整个函数最重要的行为。

估算总量小于等于预算时，消息内容逐字不变，统计里的 `truncated` 为 false，截断计数和丢弃计数都是 0。

这条约束让接入变得安全：大窗口模型上的请求结果与改造前完全一致，只有真正超窗的请求才会看到差异。我们也在测试里用“原消息数组等于装配后数组”来固定这一点，而不是只断言长度。

## 四、超了以后的动作顺序

顺序本身就是设计：

1. 从最旧开始，丢弃非 system、非末条的消息；
2. 仍超限时，截断当前最大的消息；
3. 仍超限时，才从尾部截断 system 提示词。

先丢旧消息，是因为它们通常最不重要；后动 system，是因为里面往往有角色协议和输出格式，删掉容易让模型行为失控。

当前单轮装配基本走不到第一步，保留这条路径是给未来多段输入留位置。

## 五、截断长什么样

截断只发生在文本片段上，规则固定：

```text
保留头 60% + 固定省略标记 + 保留尾 40%
```

固定标记是 `…（上下文已截断）…` 这样的短句。它让模型和人都能看出这里发生过裁剪，而不是把两段不相关的文字直接粘在一起。

头六尾四的比例来自一个朴素观察：开头通常是任务指令和关键约束，结尾通常是当前问题与最新结果，中间最容易被牺牲。

如果单条消息的预算连标记本身都放不下，就退化成只保留头部，保证不会出现“标记比正文还长”的荒谬结果。

## 六、几条不变量

装配函数是纯函数，不调用模型、不读写数据库，所以可以用单测把边界钉死：

- 末条消息永远存在，只可能被截断，不会被丢弃；
- 预算充足时，所有非末条消息逐字不变；
- 截断后估算总量不超过预算，允许结构开销带来极小误差；
- 头尾片段必须保留：原文足够长时，结果里应同时出现开头和结尾的字符；
- 图片按既有常量计入 token，但截断不作用于图片，只压缩文本。

最后一条容易被忽略。图片的 token 成本是估算出来的，截断图片会把内容变成占位符，模型反而更难回答。所以图片只计不截，超出的部分由文本承担。

## 七、它不负责什么

`fitPromptMessages` 不做摘要，不做语义压缩，也不判断哪段内容更重要。它只是最后一道保险：在请求发出前，确认总量可控。

真正的上下文选择仍然发生在更上层——对话侧的意图配额、协作的上下文块、任务的步骤压缩。装配函数不抢这些职责，否则会变成一个没人能说清边界的“大一统”。

## 八、结果

接入后，4096 窗口的协作请求不再出现上游 400；大窗口请求的消息与改造前逐字一致；每一次装配都会产出一份统计，供快照和排查使用。

一个有界的分块系统，必须配一个有界的整体。前者决定“每块多大”，后者决定“还能不能发出去”。
