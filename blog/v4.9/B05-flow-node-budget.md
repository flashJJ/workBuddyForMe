# 图里的一个节点，也要有自己的窗口上限

Flow 是一张有向图：每个节点做一件事，边把上游输出传给下游。大多数节点都很小，提示词就是一段模板加几个变量。

但 LLM 节点有一个天然风险：它的 user 消息里拼的是上游输出，而上游输出可能非常长。

## 一、原来的写法

LLM 节点的处理很直接：取系统提示词，把上游变量填进 user 模板，然后调用模型。

没有预算，没有截断，也没有估算。模板里写着“请总结下面的内容”，下面可能是整篇文档、整页网页正文、或者上一轮模型生成的长回答。

窗口够大时一切正常；窗口小一点，或者上游突然返回一大段，这个节点就失败了。失败发生在图的中间，前面的节点都白跑。

## 二、节点的特殊性

普通请求的输入是可控的：用户输入、检索结果、历史记录，都有各自的预算。

Flow 节点的输入不完全可控。它的内容由上游决定，而上游可能是一个抓取节点、一个文件读取节点，或者另一个模型节点。

也就是说，模板本身很小，变量可能很大。只给模板设上限没有意义，必须给装配后的整段提示词设上限。

## 三、接入点放在装配之后

我们选择在“变量已经填进模板、消息已经成型”之后做一次装配：

```ts
const fitted = fitPromptMessages(messages, {
  contextWindow: model.contextWindow,
  scene: 'flow_node',
})
```

放在这里，而不是放在模板渲染之前，有两个原因：

- 只有成型后的消息才能准确估算总量；
- 截断需要保留头尾，而模板的开头和结尾恰好都在成型消息里。

装配函数不认识 Flow，也不认识节点类型。它只接收消息和窗口，返回消息和统计。这让 Flow 的接入没有引入任何图执行层面的概念。

## 四、只在需要时才动

装配函数的第一条规则是：没超预算就原样返回。

这条规则对 Flow 尤其重要。很多工作流是调好的，节点的输出格式、提示词措辞都影响下游。如果每次调用都“顺手压缩一下”，即使内容没超，输出也可能漂移。

所以接入后的行为是：

- 未超过预算：消息逐字不变，不写事件；
- 超过预算：按头六尾四截断，并写一条快照。

截断本身也是一次行为变化，但它是必要的：不截断的结局是调用失败，失败比截断更糟。

## 五、快照只在截断时写

Flow 的节点数量可能很多，一个图跑下来几十次模型调用很正常。

如果每个节点都写一条快照，事件表会迅速膨胀，而且绝大多数都是“没超预算”的无信息记录。

我们的策略是：只有 `truncated` 为 true 时才写 `flow_node` 快照。

这样得到的效果是：正常情况下时间线干净，一旦某个节点发生裁剪，立刻能看到它用了多少、预算多少、裁了几条。定位长文本问题不需要翻整张图的日志。

真机验收里，一个长文本节点记录为 3004 token、预算 3008，`truncated=true`，运行仍然成功。这说明截断确实兜住了这次调用。

## 六、回调缺失也要能跑

Flow 引擎在测试里经常不配置事件回调。它只关心节点有没有产出正确结果，不关心观测。

所以快照写入必须是可选的：

```ts
ctx.recordContextSnapshot?.(stats)
```

没有回调就只截断、不记录。引擎测试因此不需要为了新功能去补一套事件基础设施，已有测试也不用改。

观测是增强，不是前置条件。把两者耦合在一起，最后往往是观测代码拖慢了主流程。

## 七、为什么不做输出压缩

也考虑过对 LLM 节点的输出做摘要，把长结果压短再传给下游。

这一轮没有做，原因是它会改变图的语义：下游拿到的应该是上游的完整输出，压缩等于替用户做了取舍。而输入截断不同，它只影响这一次调用的可行性，不改变节点之间的数据契约。

先保证节点能跑完，再讨论输出要不要瘦身。

## 八、结果

- LLM 节点在超窗时会截断，而不是直接失败；
- 未超预算的节点，输入逐字不变，输出不受影响；
- 只有发生截断的节点产生快照，事件量可控；
- 引擎测试不配置回调也能正常运行。

图执行系统的健壮性，往往不取决于最复杂的节点，而取决于每个节点在输入失控时是否还有一条确定的退路。
