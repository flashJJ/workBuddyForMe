# 预热不是一次性的：失败缓存、下载完成与短句 LRU

本地 TTS 的第一次合成通常最慢：要加载模型、初始化原生运行时。为了不让用户在第一句朗读时等，我们在服务启动时做一次预热。

最初的实现很短：

```ts
prewarmJob ??= doPrewarm();
return prewarmJob;
```

它解决了一个问题，也埋了三个坑。

## 一、坑一：失败被永久缓存

如果服务启动时模型还没下载完，预热会返回 false。但 `??=` 把 false 的 Promise 缓存住了，之后即使模型下载完成，同一个进程里也不会再预热。

用户下载完模型，第一次朗读仍然要等冷加载；直到重启应用才恢复。

修复方式：

```ts
prewarm(force = false) {
  if (force) this.job = null;
  if (!this.job) {
    this.job = this.doPrewarm().then(ok => {
      if (!ok) this.job = null; // 失败允许下次重试
      return ok;
    });
  }
  return this.job;
}
```

成功保留，失败清空；下一次调用可以重新尝试。

## 二、坑二：模型切换后不重新预热

设置里切换 TTS 模型、线程数或模型目录时，引擎需要重建。原逻辑只清空配置键，下一次合成时才惰性重建，预热不会自动发生。

现在 `invalidateTts()` 同时清空预热任务与合成缓存；设置更新后后台调用一次 `prewarm(force)`。模型下载完成也触发一次预热。

预热仍然是异步的，不阻塞设置保存，也不阻塞服务启动；失败静默，首次朗读会再试并给出真实错误。

## 三、坑三：重复短句每次重新合成

试听按钮、问候语、小剧场台词有一个共同点：文本短、重复率高。

每次点试听都跑一遍完整合成，既浪费 CPU，也让交互显得慢。于是加一个进程内 LRU。

## 四、缓存键与淘汰策略

key 是：

```
模型 | sid | 速度 | 文本
```

这四个维度缺一不可：换模型、换角色、改语速、改文本都应该 miss；只有完全相同才命中。

限制有三层：

- 最多 64 条；
- 单条文本 ≤80 字；
- 总 PCM 样本 ≤200 万（约 8MB）。

条数限制防条目膨胀，文本长度限制防长文占用，样本数限制防短文本但长音频的极端情况。

命中时返回 PCM 的副本：

```ts
return { samples: new Float32Array(hit.samples), sampleRate: hit.sampleRate };
```

调用方可能修改 samples（例如做淡入淡出），如果直接返回缓存对象，会污染下一次命中。

## 五、什么时候清空

- 引擎重建（模型/线程/目录变化）时清空；
- `invalidateTts()` 时清空；
- 进程退出自然清空，不持久化。

没有做磁盘缓存，因为：

- TTS 文本重复率不稳定，持久化收益不确定；
- 磁盘缓存要处理版本、模型、sid、速度、文本哈希与清理策略；
- 本地合成本来就快，内存缓存已经覆盖高频场景。

## 六、测试

缓存单测覆盖：

- 命中返回副本，修改不影响缓存；
- 按条数淘汰最久未使用项；
- 长文、空文本、空音频不缓存；
- 样本总量超限时淘汰旧项；
- clear 清空。

预热测试覆盖：

- 成功只创建一次引擎；
- 模型未就绪时跳过；
- 失败不抛出，下一次可重试；
- `invalidateTts` 后重新预热会重建引擎。

这些测试不需要真实加载模型，引擎工厂用 mock 即可。

## 七、经验

1. **失败不要永久缓存。** 尤其是“资源还没准备好”这种可恢复失败。
2. **预热要和资源生命周期绑定。** 下载完成、模型切换、配置失效都是重新预热的时机。
3. **缓存键要覆盖所有影响输出的维度。** 少一个维度就会返回错误结果。
4. **缓存返回值要防外部修改。** 尤其是可变数组。
5. **先做内存缓存，再考虑持久化。** 大部分高频重复发生在一次会话内。
6. **缓存要有明确上限。** “只缓存短句”比“缓存所有文本”更容易解释和控制。

预热和缓存都不改变合成质量，但它们把用户感知的等待从“每次”降到“第一次”。对本地优先的应用来说，这种确定性很重要。
