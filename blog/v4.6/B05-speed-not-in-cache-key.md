# 改语速为什么要重建几百 MB 模型：缓存键的边界

我们的本地 TTS 引擎加载一次要读几百 MB 模型。为了避免每次合成重新加载，运行时会把引擎实例长驻，并用一个“配置键”判断是否需要重建。

最初的配置键包含：模型、模型目录、语速、线程数。

看起来合理：任何配置变了，引擎都重建。但用户把语速从 1.0 调到 1.2 时，整个模型被卸载重载，第一句要等好几秒。语速明明只是合成参数。

## 一、引擎身份和合成参数不是一回事

需要重建引擎的配置，是那些会改变原生对象结构的：

- 模型文件（Melo 与 Kokoro 是不同架构）；
- 模型目录；
- 推理线程数；
- 计算 provider。

不需要重建的，是每次调用都可以传的参数：

- 说话人 sid；
- 语速；
- 文本。

最初的代码把 sid 逐句传入，却没有把语速逐句传入；语速在构造引擎时固定，所以只能靠重建来生效。

## 二、先让语速变成逐句参数

合成选项增加 `speed`：

```ts
interface TtsSynthOptions {
  speakerId?: number;
  speed?: number;
}
```

两个引擎都改成：

```ts
const speed = opts?.speed ?? this.defaultSpeed;
```

worker 线程的合成消息里本来就带 `speed`，只是之前一直传构造时的值；现在传每次调用的值。

## 三、再把速度移出配置键

配置键从：

```ts
[spec.id, modelDir, speed, numThreads].join('|')
```

改成：

```ts
[spec.id, modelDir, numThreads].join('|')
```

设置更新接口也不再因为 `ttsSpeed` 调用 `invalidateTts()`。语速仍然持久化，但下一次合成会从设置里读到新值并逐句传入。

这样用户改语速后：

- 引擎实例不销毁；
- 模型不重新加载；
- 下一句按新速度合成；
- 第一句不再额外等待模型加载。

## 四、设置页的交互变化

以前改语速会触发一个隐性的重初始化，用户可能感觉“保存后第一句特别慢”。现在保存是即时的，语速在下一句生效。

线程数仍然会重建引擎，因为它改变原生推理配置；这是合理的，UI 也不需要额外提示，因为线程数通常只在排障时调整。

## 五、缓存键的通用原则

这件事的本质是缓存键设计：

> 缓存键应该包含“对象身份”，不包含“每次调用的行为参数”。

- HTTP 缓存键包含 URL 和方法，不包含请求体里的分页大小；
- 图片缓存键包含图片 id 和尺寸，不包含是否懒加载；
- TTS 引擎键包含模型和线程，不包含语速和 sid。

把行为参数放进身份键，会导致“改一个参数就重建整个对象”。反过来，把身份参数漏掉，会导致“改了模型还在用旧引擎”。两者都需要明确边界。

## 六、测试怎么证明没有重建

测试里让引擎工厂返回一个可观测的 mock，然后：

1. 用默认语速合成第一句；
2. 修改设置里的语速；
3. 合成第二句；
4. 断言引擎工厂只调用一次；
5. 断言第二次合成的 speed 是新值。

这条用例比“检查配置键字符串”更有价值，因为它验证的是行为，而不是实现细节。

引擎层也补了逐句 speed 的测试：inline 和 worker 两条路径都确认 `opts.speed` 覆盖默认值。

## 七、经验

1. **先区分“身份”和“参数”。** 不是所有配置变化都需要重建对象。
2. **能让参数逐句传，就不要放在构造期。** 构造期参数会迫使调用方重建。
3. **缓存键要能被行为测试验证。** 只测字符串拼接容易漏掉真实重建。
4. **设置保存的延迟要可解释。** 如果保存后第一句变慢，用户会以为是 bug。
5. **性能优化不一定要加缓存。** 有时只是把参数放对了位置。

改语速不重建模型，听起来像一个很小的优化；但对本地 TTS 来说，它把“调一下语速”从几秒的等待变成了即时生效。
