# 双时态与版本链：为什么「更正」不该覆盖旧事实

先看一个再普通不过的对话。

三月，用户说「我住在北京」。五月，用户说「我搬到上海了」。九月，用户问：「我是不是跟你说过我住北京？中间隔了多久？」

如果系统在五月是「用新内容覆盖旧内容」，这个问题就没有答案。它只知道现在住上海，不知道曾经住北京，也不知道分界点在哪。更糟的是，如果五月那句其实是用户口误、六月又改回北京，覆盖式写入会把两次变更压成一次，历史彻底失真。

这一篇讲清楚：为什么冲突不该覆盖，以及我们用一套什么样的结构，把「事实何时成立」和「系统何时知道」都保留下来。

## 覆盖式更新的三个后果

覆盖看起来最省事，但它同时毁掉了三样东西：

- **时间线**。旧值消失后，任何「之前」「后来」「什么时候」的问题都失去依据。
- **可解释性**。用户问「你为什么觉得我住上海」，系统只能指向当前那条记录，说不出它是从哪条、在什么时候演变来的。
- **可恢复性**。误抽取、误合并写进去之后没有旧版本可退回，只能靠用户重新说一遍。

对一个长期陪伴型应用来说，这三样恰恰是「记忆」区别于「缓存」的地方。

## 双时态：两个时间轴，各管一件事

我们把每条记忆的时间拆成两条轴：

- **有效时间**：这条事实在现实世界里什么时候成立，用有效起止表示。住北京从三月成立，到五月结束。
- **记录时间**：系统什么时候知道、什么时候修改过这条事实，用创建时间和更新时间表示。

两条轴分开之后，「用户五月才告诉我他三月就搬了」这种信息也能表达：有效时间从三月开始，记录时间落在五月。这不是学术洁癖，它直接决定了系统能不能诚实地说「我是五月才知道的」。

## 一次住址变更的完整轨迹

把例子走一遍。旧行是「用户住在北京」，版本 1，状态为有效，有效起始是三月，没有结束。

五月用户说搬到上海，抽取结果带上同一个主体键——比如「居住城市」。写入链路先按主体键找到当前有效的那条，发现内容不同，于是判定为取代，而不是新增，也不是覆盖。

取代在单个事务里完成四件事：

1. 插入一条新行，内容为上海，版本号在旧行基础上加一；
2. 把旧行状态从有效改为「已被取代」——等价于从有效集合归档——并写入有效结束时间和指向新行的取代指针；
3. 给新行记一条创建审计；
4. 给旧行记一条取代审计，快照里带上变更前后的状态。

事务提交后，两条行同时存在。查询只取有效行，所以对话里助手说「你住上海」；管理页展开历史，则能看到北京那条还在，带着它的结束时间和被谁取代。

## 版本链靠四个字段撑起来

这套结构不需要图，也不需要额外的链表表，四个字段就够：

- **版本号**：同一主体的第几版，取代时加一，便于排序和展示；
- **有效起始**：这一版从什么时候开始成立；
- **有效结束**：这一版从什么时候不再成立，只有被取代或归档时才写；
- **取代指针**：旧行指向新行的标识，顺着指针就能把整条链串起来。

再加上原有的状态字段，查询侧只需要一个条件：状态为有效。历史行、被取代的行、被归档的行都不进入日常召回，但都还在库里。

## 审计表：每次变更都有前后快照

版本链回答「变成了什么」，审计表回答「谁在什么时候、因为什么改的」。

每次写入、合并、取代、归档、恢复、删除，都会在审计表里留一条记录，字段很少：关联的记忆标识、动作类型、变更前快照、变更后快照、操作者、时间。动作类型覆盖创建、合并、更新、取代、归档、恢复、删除七种。

快照存的是完整对象的 JSON，不是 diff。原因是排查问题时，你几乎总是想知道「当时那条记忆长什么样」，而不是「哪几个字段变了」。存储成本可以接受，因为记忆写入的频率远低于消息。

审计与主写入在同一个事务里提交。这一点是硬要求：如果先改记忆再写审计，中间失败就会出现「记录变了但没有证据」的黑洞。

## 合并与取代是两条路

不是所有重复都要走版本链。写入决策是纯函数，输入候选内容、向量最近邻和同主体的有效记录，输出三种动作之一：

```text
同主体键，内容相同        → 合并：刷新确认时间，不新增版本
同主体键，内容不同        → 取代：旧行关闭，新行版本加一
不同主体键，向量距离 ≤ 阈值 → 合并：视为同一件事的不同说法
其余                      → 创建
```

「合并」用于同一事实的再次确认或措辞变化，比如「我住上海」说第二遍。它不产生新版本，只把确认时间刷新，让这条记忆在新鲜度上更抗衰减。

「取代」用于事实真的变了。两者的区别在于：合并之后旧内容仍然是对的，取代之后旧内容只在历史区间里成立。

阈值只看向量距离，不看模型判断。冲突裁决交给可复现的规则，是为了让同一组输入永远得到同一个结果——否则测试无法断言，线上也无法复现。

## 查询只取有效，历史按需回看

日常召回、管理页默认列表、统计计数，全部只认有效状态。这样做有两个好处：召回不会被过期事实污染；「当前事实」这个语义只有一个来源，不需要在每个调用点再判断一次。

回看历史是显式动作。用户点开一条记忆的详情，系统按取代指针向前后遍历，把整条版本链和对应审计按时间排出来。链路断了（比如手工删除了中间版本）也不会崩，能展示多少展示多少。

## 为什么不用「删除旧的」

删除最省空间，但它把「事实过期」和「用户要求忘记」混成了同一个操作。

事实过期应当保留证据，因为它是理解用户变化的依据；用户明确要求忘记，才应该真正清除。前者走取代与归档，后者走删除并留下审计。两条路径分开，语义才清晰，也才能在隐私诉求出现时做到「说删就删」。

## 边界与代价

版本链依赖抽取阶段产出稳定的主体键。如果主体键缺失，系统只能退回向量相似度判断，极端情况下仍可能产生重复事实。这是已知局限，我们的取舍是：宁可多一条重复，也不要错误地把两件不同的事合并掉。

另一个代价是存储增长。每条被取代的事实都会留下一行，长期使用后需要归档策略配合。当前的做法是按衰减分档软归档、到期归档，只归档不物理删除，需要时仍可恢复。

## 数字

- 取代时旧行与新行各写一条审计，事务内完成；
- 新行版本号等于旧行版本号加一；
- 写入去重的向量距离阈值为 0.35，只有在这个距离内才视为同一事实的不同说法；
- 全量测试覆盖 core 包 1539 例、database 包 270 例、web 端 738 例。

回到开头的问题。现在系统可以回答：三月到五月住北京，五月之后住上海，变更发生在五月，旧值仍然留着。它没有变聪明，只是不再把「更新」当成「抹掉」。
