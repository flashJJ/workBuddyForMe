# 工作记忆：为什么任务进度不能塞进长期记忆

一个很自然的产品直觉是：既然助手已经能记住「用户住在上海」「用户不吃香菜」，那它顺便记住「当前正在做第 3 步」也顺理成章。反正都是「记住点什么」，多写一条进长期记忆库似乎没有成本。

我们在这个版本里明确否掉了这条路，单独给「当前任务」造了一层工作记忆。原因不是洁癖，而是这两类信息的寿命、语义和失败模式完全不同——混在一起，长期记忆会被任务日志污染，任务态也会被长期记忆的衰减规则误伤。

## 同一个「记住」，两种完全不同的东西

长期记忆回答的是「关于用户和世界，什么是真的」。它的事实有稳定预期：住址可能几年不变，忌口可能一辈子不变。工作记忆回答的是「这一次，我做到哪了」。它的状态以分钟和小时计，任务一结束就没有价值。

把它们放进同一张表，第一处冲突是语义。任务态是**意图**，不是**断言**。一句「下一步调用导出工具」如果被当成事实写进长期记忆，下次召回时它会被当作「用户的偏好或处境」重新注入，助手就会在一个早已结束的任务里继续自言自语。

第二处冲突是演进方式。长期记忆的冲突是「新事实取代旧事实」，所以需要版本链和失效区间；任务态的「冲突」是正常推进——第 3 步完成后第 4 步开始，这不是取代，也不该留下版本记录。用同一套 supersede 机制处理，只会制造一堆没有意义的旧版本。

第三处冲突是生命周期。长期事实按 180 天半衰期慢慢变旧，任务态如果也按这个节奏，一条已经完成的任务会在记忆库里躺半年；反过来，如果给任务态套上小时级的过期时间，长期记忆的衰减任务就要为两类数据写两套判断。

第四处是作用域。任务态属于一次会话、一个计划，天然不该被另一个助手召回；长期记忆里的事实和偏好则需要在助手之间按作用域共享。

把三层记忆摆在一起，职责边界很清楚：

| 层 | 承载内容 | 寿命 | 失效后的表现 |
|---|---|---|---|
| 短期 | 会话原文与递归摘要 | 一次会话 | 上下文断裂、答非所问 |
| 长期 | 事实、偏好、关系、事件、硬约束 | 月到年 | 助手记错用户 |
| 工作 | 目标、计划、待办、最近工具、下一步 | 分钟到小时 | 任务中途失忆、重复执行 |

三层的失效表现不同，修复手段也不同。短期靠压缩，长期靠冲突消解和衰减，工作记忆靠检查点。用一层去补另一层的洞，通常只会把问题挪个位置。

## 检查点记录五件事

所以工作记忆落成一张独立的检查点表，一条记录只保留五个字段加一个到期时间：

```text
goal            目标标题
plan            计划标题 + 状态（已批准 / 执行中）
todos           待办列表，最多 10 条，每条只有标题和状态
lastToolSummary 最近一次工具结果摘要，最长 160 字
nextStep        第一个仍处于「待办 / 进行中」的步骤
expiresAt       到期时间
```

五个字段是刻意压缩过的。目标回答「为什么做」，计划回答「按什么做」，待办回答「做到哪」，最近工具回答「刚刚发生了什么」，下一步回答「接下来做什么」。再多的信息就不属于工作记忆了，而属于对话原文——原文还在，需要细节时直接读，不必在检查点里做第二份摘要。

待办最多 10 条是个硬上限。检查点每轮都要注入上下文，条目数不设限，长任务会把 system 段挤满；而超过 10 步的计划，模型真正需要的也只是「当前活跃的那几步」，其余步骤看原文即可。

最近工具摘要有一个细节：失败优先。如果最后一条工具记录是错误，摘要取错误信息而不是结果摘要，否则检查点会告诉模型「一切正常」，而真实情况是上一步已经失败。摘要统一截到 160 字，避免一次工具输出把整块挤爆。

## 一个五步任务，检查点长什么样

假设用户让助手整理一个月的账单并导出。计划被批准后，检查点在每一轮的注入大致是这样：

```text
【任务检查点】
目标：整理上月账单并导出汇总
计划：《账单整理》执行中
待办：
- [完成] 拉取账单邮件
- [完成] 解析金额与商户
- [进行中] 按类别汇总
- [待办] 生成汇总表
- [待办] 导出 CSV
最近工具：账单解析：识别 128 条，3 条金额缺失
下一步：按类别汇总
（检查点会随任务完成或超时归档；与最新对话不一致时以最新对话为准）
```

这段文本没有包含任何一条账单金额，也没有包含工具的原始输出。它只回答四个问题：为什么做、做到哪、刚发生了什么、下一步做什么。金额和明细留在对话与工具记录里，模型真需要时再读。

如果用户中途说「先别导出，我要看看分类」，检查点本身不会立刻改变——计划状态还是执行中，下一步还是汇总。但那句「与最新对话不一致时以最新对话为准」会生效，模型按照新指令先展示分类，而不是机械执行旧下一步。等计划步骤真的被更新，下一轮的检查点才跟着变。

## 只对「正在发生」的计划建模

检查点不是有状态就写。构造快照前先过两道门：

- 计划必须处于「已批准」或「执行中」。草稿态的计划还在讨论，写进工作记忆会让助手误以为自己已经开工。
- 待办里必须还有「待办」或「进行中」的步骤；如果所有步骤都是完成 / 跳过 / 受阻这类终态，且没有新的目标，就直接返回空。

返回空不是失败，而是一个明确信号：上层据此把旧检查点归档。这样「任务结束」不需要一个额外的完成回调去通知记忆层，状态本身就能推出结论。

## 跨轮注入：给它固定位置，也给它免责声明

检查点每轮渲染成一个固定格式的 system 区块，顺序是目标、计划、待办清单、最近工具、下一步。每条待办前面带一个中文状态标签（待办 / 进行中 / 完成 / 跳过 / 受阻），模型不需要猜图标含义。

区块末尾固定带一句提示：检查点会随任务完成或超时归档，与最新对话不一致时以最新对话为准。

这句话不是客套。检查点是快照，天然可能滞后于用户的最新指令；如果不给出优先级，模型会在「用户刚说换个方案」和「检查点还写着旧下一步」之间摇摆。把「对话优先」写进注入文本，等于用一句自然语言解决了一个本来要靠代码判断的时效冲突。

整块渲染完还要按 token 预算再截一次。工作记忆是每轮必进的固定开销，不能因为某条待办标题特别长就突破预算。

## 结束与超时：归档，而不是删除

检查点的退出有两条路。任务正常完成时，快照构造返回空，旧检查点被归档；任务拖得太久时，`expiresAt` 到期，生命周期任务把它归档。

超时清理有一个容易忽略的细节：它不受「七天跑一次」的衰减间隔限制。生命周期任务每次运行都会先处理到期项，再判断要不要执行分数衰减。否则一个两小时就该过期的任务态，可能要等下一次周任务才被清掉，中间几天一直以「进行中」的身份被注入。

归档而不是删除，是为了可回溯：用户问「上次那个导出任务到底做到哪了」，检查点还在，只是不再参与注入。

## 工作记忆不解决什么

它不是长期记忆的替代品。偏好、事实、硬约束仍然走长期记忆，因为它们要在任务结束后继续存在；工作记忆也不做跨会话恢复，一次任务结束，检查点归档即止。

它也不试图表达「为什么失败」。受阻原因、用户的原话、工具的完整输出都留在对话和工具记录里，检查点只保留一个指针式的摘要。工作记忆的职责是让模型在多轮之间不丢失「我在做什么」，而不是把整段执行历史再抄一遍。

一句话总结：长期记忆记「你是谁」，工作记忆记「我在干嘛」。两件事混在一张表里，模型的自我认知就会开始漂移。
