# 从向量记忆到可审计记忆系统：旧方案的三个断点

一个本地优先的桌面 AI 应用，只要开始「记住用户」，就很快会撞上一组很具体的问题。

用户上周说住北京，这周说搬到上海。第二句话写进去之后，助手再被问「我住哪」，答上海，看起来没问题。但如果用户问「我是什么时候搬的」「我之前是不是说过住北京」，系统已经答不出来了——旧的那条在写入时就被覆盖，覆盖的那一刻，历史也一起消失了。

这只是最容易被发现的一种。把长期记忆拆开看，上一代方案其实只有三个动作：抽取、向量检索、覆盖写入。每个动作单看都合理，合起来却留下了三处结构性断点。

## 断点一：覆盖式写入，等于没有历史

上一代的写入逻辑很朴素：新记忆入库前先算一次向量最近邻，距离足够近就把旧记录的正文改写成新内容。

好处是实现简单，坏处是「更正」和「替换」被混为一谈。用户改口、信息过期、说错后纠正，在这套逻辑里全都表现为同一件事：旧值消失。系统无法回答任何带时间的问题，也无法解释「这条记忆是怎么变成现在这样的」。

一旦出错，连回滚都没有依据——因为被覆盖掉的版本根本不存在。

更麻烦的是，「合并」和「取代」在旧实现里是同一个动作。用户把「预算五千」改成「预算八千」，和用户重复说一遍「预算五千」，都会走同一条改写路径。前者应该留下变更记录，后者只需要刷新确认时间，但系统无从区分，只能用同一种方式处理。

这种设计在数据量小的时候几乎无感，因为用户很少回头问「以前是什么」。可一旦产品定位是长期陪伴，历史本身就是价值，覆盖式写入就成了必须先拆掉的地基。

## 断点二：纯向量召回，没有嵌入就整体失效

第二个断点是召回只有单通道。上一代只看向量：把用户问题编码成向量，取最近的几条。

它在嵌入模型正常工作时够用，但把两个风险绑在了一起。一是嵌入模型缺席时——本地模型没装、加载失败、维度变更——召回直接归零，长期记忆形同不存在。二是向量天然弱于精确匹配，用户问「我的订单号是多少」，语义相近的一堆记忆会挤掉真正含那串数字的那条。

更隐蔽的问题是没法解释。一条记忆为什么被召回、是语义命中还是关键词命中，系统自己都说不清。

而且要补的不只是「再加一个关键词检索」。如果两个通道各自返回一份互不相干的结果，最后按什么顺序合并、冲突时信谁，仍是新的问题。召回从单通道变成多通道，打分模型必须一起重做。

## 断点三：摘要只剩自然语言，数字最先掉

第三个断点在上下文压缩。对话变长之后必须折叠早期内容，上一代的做法是让模型写一段自然语言摘要，再塞回系统提示。

自然语言摘要对「聊了什么」很擅长，对「具体是多少」很不擅长。预算从三千改成五千、体检间隔六个月、会议定在三月一日——这些值在摘要里最容易变成「预算有所调整」「间隔约半年」「三月初」。数字和日期一旦在压缩环节丢失，后面的对话再也不可能补回来。

注意，这不是让摘要承担更多责任，而是把它从「唯一的压缩产物」降级为「压缩产物之一」。数字要有自己的存储位置和校验方式，不能依赖一段散文顺手记住。

## 这一版拆成四条链路

针对三个断点，我们把记忆系统拆成四条各自可测试、可观测的链路：

1. **写入链路**：先跑零模型成本的窄规则识别硬约束，再交给模型做常规抽取；写入决策是纯函数，分创建、合并、取代三种，冲突不再覆盖。
2. **召回链路**：向量与全文检索各取 20 条候选求并集，四维加权融合，作用域与过期时间过滤后再取前三。
3. **压缩链路**：摘要输出结构化 JSON，事实单独落表，数字与日期做保真校验；注入顺序与预算配额固定。
4. **生命周期链路**：按衰减分档软归档、到期归档，置顶与硬约束永不衰减，每一步都写审计。

四条链路共享同一份数据模型：记忆行带作用域、版本号、有效区间与状态，另有一张审计表记录每次变更的前后快照。

## 四条链路怎么咬合

四条链路不是四件独立的事，它们在两个地方强耦合。

第一处是写入与召回。写入时同步维护向量索引和全文索引，召回才能同时拿到两路候选；写入时确定的置顶与重要性，直接决定召回里的固定注入和加权排序。索引不同步，召回就会「看得见旧行、看不见新行」，这是最容易出的一类线上问题。

第二处是压缩与记忆。摘要里的结构化事实属于当前对话，不进入长期记忆；但如果某条事实反复出现，它可以被抽取为长期记忆，走同一套写入决策。反过来，长期记忆的注入位置又受压缩预算约束——记忆块只占窗口的 10%，超了就截断。

换句话说，四条链路共享同一套字段、同一套事务边界和同一份预算账本。任何一条链路单独看都不复杂，难的是它们对「同一条事实」的理解必须一致。

## 三条贯穿全局的原则

拆链路不难，难的是每条链路都守住同一条底线。这一版反复用到的原则只有三条：

- **事实只增不删**。旧版本不物理删除，退出有效集即可，任何一次「更正」都可回溯。
- **模型只做它擅长的事**。规则能判的（过敏、忌口、显式记住）不交给模型；冲突判定这种需要可复现的地方，也用纯函数而不是再问一次模型。
- **每一层都能被解释**。召回带理由，写入带审计，压缩带保真校验结果。出问题时能定位到具体某一层，而不是「模型可能记错了」。

这三条原则直接对应三个断点：只增不删解决历史丢失，规则先行解决不可复现，可解释解决「说不清为什么」。

## 升级与兼容

改数据模型最大的风险是老用户。升级时所有存量记忆被标记为全局作用域、来源为历史数据、版本号为 1，行为与升级前保持一致；全文索引在迁移中一次回填，不要求用户重新说一遍。

嵌入模型仍然是可选的。没配置的用户照常写入，召回走关键词通道，不会因为「缺一个模型」导致整个记忆功能不可用。这条从第一天就写进了非目标清单：不把可选能力做成硬依赖。

## 代价与边界

这套结构不是免费的。多了一张审计表、一张事实表和一个全文索引，写入要在一个事务里完成「插新行、关旧行、写两条审计、同步两套索引」；召回多了一次全文检索和一轮融合计算。

我们接受这些成本，因为它们换回的是可解释性和可恢复性——这两样在长期陪伴型产品里，比省下的几毫秒重要得多。

也有明确没做的：不引入图数据库，不做多设备同步，不在写入时调用模型做冲突裁决。这些留给以后，而不是现在就堆进来。

可观测性也是成本的一部分。新增的线上计数接口会给出记忆总量、有效与被取代的比例、零召回率和用户纠正次数；这些数字不直接改善体验，但能让「记忆到底有没有用」从感觉变成可比较的指标。

测试也随之分层：写入决策、融合打分、保真校验都是纯函数，单测可以逐条断言；数据库迁移与仓储用真实 SQLite 跑；端到端只保留少量用例验证链路拼装。

## 数字

- 召回候选：两个通道各 20 条，融合权重 0.55 / 0.20 / 0.15 / 0.10，最终只取前 3 条；
- 硬约束：置顶、重要性不低于 0.95，每轮最多固定注入 3 条，不随时间衰减；
- 上下文预算：原文 50%、摘要 25%、结构化事实 10%、长期记忆 10%，余量留给输出；
- 全量测试：core 包 1539 例、database 包 270 例、web 端 738 例全部通过。

回到开头那个住址问题。新系统给出的不是「上海」一个答案，而是一条可以展开的时间线：某段时间住北京，某个时刻之后住上海，谁在什么时候改的、旧值是什么，都留得住。

记忆系统的难点从来不是「存下来」，而是存下来之后还能解释、能追溯、能在缺模型的时候不崩。
