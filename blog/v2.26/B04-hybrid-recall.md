# 混合召回：向量与关键词各取 20 条，为什么还要四维加权

先看两个真实会遇到的场景。

场景一：用户问「我的订单号 A7K2 处理得怎么样了」。长期记忆里确实有一条包含 A7K2 的记录，但向量模型把这句话编码成一个模糊的「查询订单状态」语义，召回回来的是五条「用户关心订单进度」的泛泛记忆，真正带单号的那条排在后面，被截掉了。

场景二：用户换了一台机器，嵌入模型还没下载完。系统里已经有几千条记忆，但这一轮召回直接返回空——因为旧的召回实现只会算向量。

这两个场景指向同一个结论：单通道召回不可靠。这一版改成向量加关键词的双通道，再在候选层面做加权融合。

## 候选层：两个通道各取 20 条，求并集

第一步不是打分，是凑候选。

向量通道按查询向量的距离取最近的 20 条；关键词通道用全文检索按匹配度取 20 条。两边取完，按记忆标识求并集，同一条只保留一次。

求并集而不是交集，是因为两个通道的强项不重叠。向量擅长「意思相近但用词不同」，关键词擅长「字面精确匹配」，尤其是数字、编号、专有名词。交集会把两边各自的独有命中全部丢掉，正好丢掉它们最擅长的部分。

候选池上限 20 是权衡的结果。太多会让后面的融合计算变重，也让噪音变多；太少则失去了「向量没排上的那条，可能正是关键词命中的那条」这个核心收益。

## 四维加权：0.55 / 0.20 / 0.15 / 0.10

拿到并集后，每条候选算四个分数，各归一化到 0 到 1：

- **语义分**：来自向量距离，距离越近分越高；没有向量时记为 0；
- **关键词分**：来自全文检索排名，按位置归一化，第一条接近 1，末条接近 0；
- **重要性分**：写入时给出的重要程度；
- **新鲜度分**：按记忆类别的半衰期做指数衰减。

融合公式是加权和：

```text
score = 0.55 × 语义 + 0.20 × 关键词 + 0.15 × 重要性 + 0.10 × 新鲜度
```

权重不是拍脑袋，而是按「这条信号有多可信」排的。语义仍然是主信号，占一半以上；关键词作为精确匹配的补充，占两成；重要性和新鲜度是修正项，各占一成多，用来在语义接近的几条之间做区分。

这里有个容易踩的细节：关键词分的归一化必须依赖本次结果集，而不是绝对分数。全文检索返回的排序位置本身就是信息，把它映射成「首条接近 1、末条接近 0」的线性分数，才能和语义分放在同一个量纲里相加。

## 没有嵌入模型时，权重并入关键词

如果这一轮根本没有查询向量——模型没配置、加载失败、或者干脆没装——语义分恒为 0。如果还按原权重算，最高只能拿到 0.45，全部低于下限，等于系统性地召回失败。

所以权重需要自适应：

```text
有嵌入：0.55 × 语义 + 0.20 × 关键词 + 0.15 × 重要性 + 0.10 × 新鲜度
无嵌入：0.00 × 语义 + 0.75 × 关键词 + 0.15 × 重要性 + 0.10 × 新鲜度
```

语义那一份不是简单丢弃，而是并入关键词。这样关键词命中一条记忆时，它仍然能靠主信号拿到高分，整个系统退化为「关键词检索加排序」，而不是「什么都召不回来」。

这个设计还有一个附带好处：没有嵌入模型的用户和有的用户，走的是同一套打分函数，只是权重不同。测试可以分别覆盖两条路径，行为差异是显式的，而不是散落在若干处「如果没有向量就跳过」。

## 下限与置顶：两条不同的及格线

融合分算完，要过两道门槛。

普通记忆的及格线是 0.5。低于这个分数说明四个信号都没有给出足够证据，与其把噪音塞进上下文，不如什么都不注入。这个下限比「取前几名」更重要——召回为空是诚实的，硬凑三条是危险的。

置顶记忆的及格线是 0.9，而且它不是靠分数过线的，是靠身份过线的：只要被标记为置顶，融合分会取原始分和 0.9 中的较大值。

为什么置顶要单独一条线？因为它的价值不随查询变化。用户明确要求记住的事、系统识别出的硬约束，即使这一轮问题跟它语义无关，也必须出现在上下文里。用统一的 0.5 去要求它，等于让「当前问什么」决定「什么重要」，方向就错了。

置顶也不无限注入，每轮最多 3 条。超出的部分留在库里，只是不进这一轮的固定段。

最后，候选按分数排序取前 3 条。这个 3 不是随便定的：上下文预算里长期记忆只占 10%，再多的条目也装不下，反而会挤掉摘要和原文。

## 新鲜度：三种半衰期，一个例外

新鲜度用指数衰减计算，但不同类别的衰减速度不一样：

| 类别 | 半衰期 |
|---|---|
| 事实、偏好 | 180 天 |
| 事件 | 60 天 |
| 共同经历 | 365 天 |
| 硬约束 | 不衰减 |

事实和偏好相对稳定，给半年；事件是「某天发生了什么」，时效性强，两个月就衰减到一半；共同经历是关系资产，一年才衰减一半，因为「我们一起经历过什么」本身就是长期价值。

硬约束是唯一的例外，直接不参与衰减。理由在前一篇讲过：过敏信息不会因为时间过去而失效。

衰减的基准时间是最后一次确认时间，没有则用创建时间。这意味着一条经常被「再次确认」的记忆，新鲜度会被不断刷新——用户反复提到的事，本来就该更抗衰减。

## 记忆块限长：召回到的，不一定全塞进去

召回结果最终要拼成一段文本注入系统提示。这段文本有硬上限：512 token，超出直接截断。

为什么要限长？因为长期记忆只是上下文预算里的一小块，占 10%。如果召回三条各写了三百字，拼接后远超配额，截断发生在哪一句就变得不可控——可能正好截掉最关键的数字。

限长放在格式化出口，而不是让每条记忆自己控制长度。这样无论上游召回多少条、内容多长，进入提示词的记忆块体积是确定的。

## 召回理由：让每条结果都能解释

每条召回结果带一个理由标记，取值四种：置顶、混合、语义、关键词。

这个标记看起来只是展示用，实际是排查问题的入口。用户问「助手为什么突然提起我喜欢猫」，你能看到那条记忆是靠语义命中的还是关键词命中的；如果一条记忆被反复误召回，你也能判断是向量太宽还是全文索引分词有问题。

理由的判定也简单：置顶优先；语义和关键词都有分就是混合；只有一边有分就是对应的单通道。没有第五种情况。

## 代价

双通道召回比单通道多一次全文检索和一轮融合计算，候选池也从几条扩到最多 40 条。在本地数据库上，这个开销远小于一次模型调用，不是瓶颈。

真正的代价是复杂度：两条路径、两套权重、两条及格线、四种理由，测试用例数比原来多了一倍。但这是值得的——单通道失效时是整个功能不可用，双通道失效时只是退化。

## 数字

- 两个通道各取 20 条候选，去重后融合；
- 有嵌入时权重 0.55 / 0.20 / 0.15 / 0.10，无嵌入时 0.75 / 0.15 / 0.10；
- 普通记忆下限 0.5，置顶下限 0.9，每轮最多 3 条置顶，最终取前 3 条；
- 半衰期：事实与偏好 180 天、事件 60 天、共同经历 365 天、硬约束不衰减；
- 全量测试覆盖 core 包 1539 例、database 包 270 例、web 端 738 例。

回到开头的两个场景。带订单号的问题，现在会同时命中向量通道和关键词通道，关键词分数把它顶到前面；没有嵌入模型的机器，召回退化为关键词排序，仍然能给出一份可用的结果，而不是空白。
