# 下载了 325MB 却提示文件缺失：模型下载器的校验、续传与版本固定

我们的桌面 AI 应用是本地优先的私人助手，语音模型不进安装包，首次启用时按清单从模型仓库下载到本机。最近一次语音模型下载修复，用户看到的错误是：

```text
下载后校验缺失：lexicon-zh.txt, model.onnx
```

但打开模型目录，这两个文件明明就在，大小也不是 0。更奇怪的是，其中一个文件比清单里的期望值小，另一个反而更大。

这篇文章拆开这次排查：为什么“文件在”会被判成“缺失”，以及一个面向几百个文件、几百 MB 的下载器，校验和续传应该怎么设计。

## 一、先看现象：不是没下下来，是校验值过期了

语音合成模型有 377 个文件，总量约 394MB。清单里记录每个文件的相对路径和期望字节数，下载完成后逐个 `stat` 比对。缺失或大小不符，都会被归入“校验缺失”。

出问题的两个文件：

| 文件 | 本地 / 上游实际 | 清单旧值 |
|---|---:|---:|
| `model.onnx` | 325,561,476 | 325,631,784 |
| `lexicon-zh.txt` | 2,120,131 | 2,119,465 |

一个变小，一个变大。如果是网络截断，两个文件通常都会偏小；一个变小、一个变大，更像是上游内容更新。

进一步核对响应头，镜像返回的 `Content-Length` 与本地文件完全一致。也就是说：下载器把新文件正确下下来了，只是拿旧清单去比，把它误判成了缺失。

## 二、根因：内容跟着 main，校验值却停在过去

原来的下载地址是这种形式：

```text
<mirror>/<repo>/resolve/main/<path>
```

`main` 是移动的。上游什么时候改文件、改哪个文件，下载端无法预知。

而清单里的 `size` 是某次生成时的快照。于是形成了一个最糟糕的组合：

- 下载内容：动态跟随 `main`；
- 校验依据：静态的旧快照；
- 完整性校验：只有大小，没有哈希；
- 版本控制：没有固定 revision。

内容一动，两边就不同步。这不是“下载失败”，而是 **TOCTOU（检查时与使用时不一致）** 的典型表现。

## 三、为什么“比大小”不够

大小校验不是没用，它便宜、快，能挡住明显的截断和空文件。但它有三个边界：

1. **同尺寸损坏挡不住**：代理篡改、磁盘位翻转、写入半截但大小碰巧一致，都会通过。
2. **上游一更新就误报**：就像这次，文件是对的，清单是旧的。
3. **无法证明来源**：大小对不代表内容对，更不代表内容来自你信任的那个版本。

所以大小适合做“快速预检”，不适合当唯一真相。对大文件，最终应该落到哈希。

## 四、把 revision 固定下来

修复的第一步不是继续补 `size`，而是固定 revision：

```text
<mirror>/<repo>/resolve/<commit-sha>/<path>
```

固定之后，下载内容和期望元数据来自同一个快照。上游继续改 `main`，不会影响已经发布的版本；只有我们主动升级模型时，才需要更新清单。

这里有一个容易走偏的点：**动态不等于跟随 `main`**。

- 完全动态跟随 `main`：看起来省维护，实际上每次上游更新都可能破坏已发布版本。
- 固定 revision + 动态读取该 revision 的元数据：既避免手工抄大小，又保持确定性。
- 本地清单：是快照和缓存，不是唯一真相；真相是“固定 revision + 哈希”。

我们保留了本地清单，用于离线校验和下载进度总量；同时提供同步脚本，按固定 revision 从仓库树接口重新生成路径、大小和大文件哈希。升级模型时跑一次，升级动作是显式的。

## 五、校验分三类，错误才可读

原来的返回值只有“缺失列表”，大小不符和真正缺失混在一起。修复后分成三类：

```ts
type Issue = 'missing' | 'sizeMismatch' | 'hashMismatch';
```

这样用户和日志能看到：

- 文件不存在；
- 文件存在但大小不对；
- 文件大小对但哈希不对。

三种情况的处理策略也不同：缺失要下载，大小不对要重下，哈希不对要删掉重下。错误文案不再把“大小不符”说成“文件缺失”。

## 六、下载器要按失败模式设计

模型下载不是一次请求，而是几百次请求的集合。任何一个文件失败，都可能让整个模型不可用。原来的下载器是顺序遍历、一次 `fetch`、失败即中止，遇到弱网就很脆弱。

这次按失败模式补了几层：

- **单文件重试**：3–5 次，指数退避加抖动；
- **尊重 `Retry-After`**：429 不立刻重试，但设上限，避免等一小时；
- **请求与空闲超时**：等响应头有超时，读完一个 chunk 到下一个 chunk 也有超时；
- **`Range` 续传**：`.part` 已有多少字节，就从多少字节继续；
- **流式写盘**：边读边写，不再把 325MB 整个读进内存；
- **内容类型校验**：返回 HTML 错误页时直接拒绝，不写入正式文件；
- **镜像 base URL 直传**：不再用字符串包含关系猜“是不是国内镜像”。

其中“流式写盘”和“断点续传”是配套的：只有写成 `.part`，下一次才能知道从哪继续；只有流式写，才不会在续传前先把内存撑爆。

## 七、断点续传要落在字节上

续传的关键不是“有个 `.part` 文件”，而是每次失败后重新读取它的实际大小：

```ts
const start = (await stat(part))?.size ?? 0;
if (start > 0) headers.Range = `bytes=${start}-`;
```

还要处理服务端的三种反应：

- 返回 `206`：正常续传，追加写入；
- 返回 `200`：服务端忽略了 `Range`，删掉 `.part` 从头写；
- 返回 `416`：本地 `.part` 与远端不匹配，删掉后从 0 开始。

这里有一个容易漏掉的细节：一次下载中途断流后，重试不能还用最初的 `start`，而要用 `.part` 的**当前**大小。否则每次重试都从 0 开始，断点续传只在外层重试时生效，内层重试仍然白下。

## 八、状态以磁盘为准

模型文件已经正确，但数据库里还留着上一次的 `error`。如果状态接口只读数据库，用户会一直看到失败，甚至被引导去重新下载 325MB。

修复后，状态刷新先看磁盘：文件缺失/大小不符才继续报错；文件齐备就清掉旧的 `error`，标记为 ready。数据库是展示缓存，不是文件事实的来源。

这样用户重新构建或重启后，已经正确的文件会直接恢复为就绪，不需要重新下载。

## 九、结果与边界

这次修复后：

- 已下载且大小正确的模型文件直接判定就绪，不再误报“校验缺失”；
- 大文件带 SHA256，下载时边写边算，续传后整文件复算；
- 弱网下支持重试、超时和 `Range` 续传；
- 下载 325MB 文件时不再整文件进内存；
- 单元测试覆盖重试、429/500、超时、`206` 续传、流中断续传、哈希不符与 HTML 错误页。

边界也要说清楚：

- 目前只固定了多角色语音模型的 revision，识别模型和单声模型仍在 `main`，下一版可以复用同一套机制；
- SHA256 只覆盖几个 LFS 大文件，小文件仍以大小和存在性为主，避免为 377 个文件都维护哈希；
- 这不等同于“把 394MB 模型打进安装包”，模型仍然按需下载。

## 十、几条可复用的经验

1. **校验值不能跟着移动的 `main` 走**。内容和期望值必须来自同一个 revision。
2. **大小是预检，不是完整性校验**。大文件最终要落到 SHA256 或等价哈希。
3. **动态元数据要用在固定 revision 上**。动态跟随 `main` 不是灵活，是把不确定性引入已发布版本。
4. **断点续传要读 `.part` 的实际大小**，并处理 `200/206/416` 三种服务端行为。
5. **下载器的错误分类要跟恢复策略对齐**：缺失、大小不符、哈希不符、超时、限流，不是同一种错误。
6. **状态以事实源为准**。文件在磁盘上，就不要让一条过期的数据库记录决定用户看到“失败”。

模型下载看起来只是“把文件拉下来”，真正难的是：在网络会抖、上游会变、进程会重启的前提下，仍然能判断“我拿到的是不是我要的那一份”。把这个问题讲清楚，下载器才算可靠。
