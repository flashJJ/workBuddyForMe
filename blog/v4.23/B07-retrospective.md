# 复盘：持久化执行里最容易忽略的五个细节

「让流程能续跑」听起来只是「重启时接着执行」。真正做完才发现，难点几乎都不在主流程，而在几个时间窗口与边界条件上。

这一版踩过的五个细节，记下来给以后。

## 一、判断顺序会影响结论

恢复策略要同时满足几条规则：等待人工、写工具在途、版本变化、chat 触发、空检查点。

一开始按「先检查在途节点」的顺序写，结果所有 `waiting_human` 的运行都被判成了「human 在途，不安全」，重启后全部变成终态——而用户只是还没点确认。

修复方式是把 `waiting_human` 提到「在途风险」之前判断：它代表的状态是「正在等待」，不是「正在执行副作用」。

这件事的教训是：**安全矩阵不是集合，是有顺序的决策树**。顺序错了，结论就反了。

## 二、状态迁移需要两道保险

恢复扫描拿到的是「原本在途」的运行，要把可续跑的改回 `queued`。

直觉写法是直接更新：

```sql
UPDATE workflow_runs SET status = 'queued' WHERE id = ?
```

但这会误伤：如果这行已经被别处改成终态，直接改会把它拉回队列。

实现上用了两步：

```text
markInterrupted    → 校验原状态，写中断原因
requeueInterrupted → 只允许 interrupted → queued
```

多一次写入，换来「状态机合法」的保证。

## 三、事件落库与执行行不同步

节点事件与 `node_executions` 是一一对应的：`node_started` 插入行，终态事件更新行。

但消息队列与数据库的边界在进程崩溃时会暴露问题：

- 事件已经发出，但行还没插入；
- 行已经更新，但进程在发终态事件前死了。

前者在本项目里不成立，因为落库发生在发事件之前；后者会出现——end 节点成功了，运行终态还没写。

所以引擎需要处理「checkpoint 已有成功 end」的情况，否则续跑会把成功运行判失败。

## 四、映射缓存必须预热

`run-store` 用内存 Map 记住节点与执行行的对应关系，避免重复插入。

续跑时这个 Map 是空的。如果不预热，重执行的中断节点会插入第二行，运行详情里出现两条同名记录——状态一条 `running`、一条 `succeeded`，非常难解释。

修复是启动续跑前从数据库预加载映射。

这个细节很小，但没有它，「幂等」就只对了一半：副作用没重复，观测重复了。

## 五、重试的等待必须可取消

退避等待很容易写成普通的 `setTimeout` 睡眠。

问题是用户点取消之后，引擎还在睡：取消信号要等到这次退避结束才被处理。对使用者来说，这等同于「取消没反应」。

实现上把等待做成可中断的：监听信号的 `abort`，触发时立刻结束等待并返回「已取消」，由调度器发 `run_cancelled`。

同样的道理适用于超时：超时只对非交互节点生效，否则会出现「审核等了两分钟被判超时」这种没法解释的行为。

## 六、方法论

1. **先写安全矩阵，再写代码**：哪些能自动做，哪些必须停，是产品决策，不是实现细节；
2. **幂等分两层**：运行内靠状态集合，跨进程靠落库检查点；
3. **默认不改变行为**：不配置重试/超时、没有中断时，旧流程的事件序列必须不变；
4. **观测也要幂等**：不重复发事件，不重复插记录；
5. **时间窗口要单独测**：「end 成功但运行未终态」这种窗口，不写测试基本发现不了。

## 七、这一版的遗留

- 写操作在途仍然需要人工重放，没有做「检查点 + 幂等键」的自动恢复；
- 没有总超时（整个运行的截止时间），只有节点级超时；
- 定时触发、事件触发还没做，流程仍以「被调用」为主；
- 跨版本迁移没有做，版本变化直接拒绝续跑。

这些不是遗漏，而是刻意留下的边界。持久化执行的诱惑是「把所有情况都自动化」，但每多自动化一种情况，就多一类难以解释的失败。

## 八、下一步

如果继续沿着这条线走，最自然的方向是「会守时」：让流程能按计划或事件自动开始，而不是等人或接口来调用。

那会带来新的问题——调度器与进程生命周期、错过执行的补偿、并发实例的互斥——正好可以把这一版积累的恢复与幂等经验用上。
