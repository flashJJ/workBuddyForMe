# 会扛事：让长流程在崩溃之后自己接上

一个本地优先的桌面 AI 应用，用户关窗口、系统睡眠、更新重启都是常态。流程画得越长，中断就越不是异常，而是日常。

上一版把执行器改成了并行调度，解决的是「运行内」的失败隔离。这一版解决另一个问题：**进程没了以后，运行还能不能接上**。

## 一、问题：能跑，但不抗摔

在改造之前，启动恢复的逻辑很克制：

```text
找到 running / waiting_human 的残留运行
把它们统一标成 interrupted
把 queued 的重新入队
```

这不算错，它至少避免了「永远卡在 running」。但它把两类完全不同的情况混在了一起：

- 跑了一半、每个已成功节点的产出都在库里；
- 刚启动、什么都没做，甚至还没开始执行。

前者其实可以接着跑，后者可以从头来。但旧逻辑一律标成终态，等用户手动重放整个流程。

用户看到的是：一个跑了十分钟的流程，因为一次重启，要从第一步重新来。如果里面有写文件、发请求之类的副作用，还可能重复执行。

## 二、先回答「什么算安全」

自动续跑不是「把所有中断都重启」——那会带来重复副作用。

所以在写代码之前，先定了一张安全矩阵：

| 中断时的场景 | 决策 |
|---|---|
| 正在等人工审核 | 续跑，重新进入等待 |
| 在途节点是 LLM / 检索 / 条件 / 只读工具 | 续跑，重执行该节点 |
| 在途节点是 human / agent / 写危险工具 | 保持中断，等人工重放 |
| 运行使用的版本已变化 | 保持中断 |
| 对话里发起的运行 | 保持中断 |
| 一个节点都没开始 | 续跑，等价从头执行 |

判断依据不是「运行状态」，而是「哪个节点在执行、它有没有副作用」。这一步想清楚之后，后面的实现反而简单。

## 三、checkpoint 不需要新表

一开始容易想到「新增一张 checkpoint 表」。但仔细看现有数据：

- 运行入参在 `workflow_runs.input_json`；
- 每个节点的状态与产出在 `node_executions`，成功时 `outputs_json` 已经写好；
- 节点执行记录在发事件之前同步落库。

也就是说，执行现场一直都在，只是没人去读。

于是 checkpoint 被定义成一个纯读取函数：

```ts
loadCheckpoint(runs, runId) → {
  nodes: [{ nodeId, status, outputs }],
  lastSucceededNodeId,
}
```

只收成功与跳过；同一节点多行取最后一行；不新增表、不改备份格式。

## 四、引擎只多做一件事

引擎原本从空状态开始跑。续跑时，它多做一步：

```text
把 checkpoint 里的 succeeded 节点写进作用域
把 skipped 节点写进状态
condition 的 result 用来重建分支边
```

然后照常调度。已经落定的节点在循环里静默跳过——不发 `node_started`，也不补发 `node_succeeded`，因为它们早就发过了。

这一步必须「静默」。如果续跑时把历史事件再发一遍，前端时间线会重复，落库也会重复。运行详情页应该展示的是「这次运行发生过什么」，而不是「这次进程看到过什么」。

## 五、失败重试与超时

抗摔的另一半是「别因为一次抖动就死」。

节点现在可以配置：

```json
{
  "retry": { "maxAttempts": 3, "backoffMs": 1000, "maxBackoffMs": 30000 },
  "timeoutMs": 60000
}
```

- 只对执行体抛出的错误重试，引用解析、参数校验、权限拒绝不重试；
- 退避是指数的，且没有随机抖动——本地应用更看重可复现；
- 超时只对非交互节点生效：写工具和人工审核不能被「一刀切」掉。

## 六、默认行为没变

所有新能力都是「有配置才生效」：

- 不配 `retry` → 只执行一次；
- 不配 `timeoutMs` → 不超时；
- 没有中断 → 续跑逻辑根本不参与。

现有流程的跑法与上一版一致，事件序列也不变。新增的只是几个可选字段：`resumed`、`resumeReason`、`attempt`。

## 七、这一版之后

流程终于可以说「关掉再打开也能接着跑」：

- 已成功的节点不会重跑；
- 等待人工的运行重启后继续等；
- 写操作在途时宁可停下来，也不重复执行；
- 瞬时错误会按配置重试，而不是直接失败。
