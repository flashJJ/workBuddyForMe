# 重试与退避：别让一次抖动终止一条长流程

模型会超时，检索会抖动，本地服务偶尔没起来。这些错误大多下一秒就好了，但在没有重试的流程里，它们等价于「整条流程失败」。

这一版给节点加了重试，但边界比「失败就再试一次」要细。

## 一、默认不重试

第一版设计最容易犯的错，是把重试默认打开。

理由很直接：同一条流程里，有的节点适合重试（LLM、检索），有的不适合（写文件、发消息）。如果默认重试，后者的副作用会被放大。

所以默认值是：

```text
maxAttempts = 1  → 不重试
```

只有节点显式配置了 `retry`，才进入重试逻辑。这保证现有流程的行为完全不变。

## 二、配置长什么样

策略放在节点 `config` 上，不新增图字段：

```json
{
  "retry": {
    "maxAttempts": 3,
    "backoffMs": 1000,
    "maxBackoffMs": 30000
  }
}
```

- `maxAttempts` 是总次数，包含首次执行；
- `backoffMs` 是第一次重试前的等待；
- `maxBackoffMs` 是等待上限。

边界在保存图时校验，避免非法值流到运行期。

## 三、什么错误值得重试

「抛错」不等于「值得重试」。这一版把错误分成两类：

| 错误 | 例子 | 是否重试 |
|---|---|---|
| 瞬时/执行类 | 模型超时、检索失败、工具运行异常 | 是 |
| 确定性配置类 | 工具不存在、未配置工具名、处理器未注册 | 否 |

实现上用一个显式的错误类型标记「确定性错误」：

```ts
class NonRetryableNodeError extends Error {}
```

节点执行体在资源缺失时抛这个类型，重试器看到就直接返回失败，不再等待。

引用解析失败发生在节点执行之前，也不重试——模板引用了不存在的字段，试一百次也是一样的结果。

## 四、退避为什么不要抖动

很多分布式系统会给退避加随机抖动，避免大量客户端同时重试造成惊群。

但这是本地单用户的桌面应用：并发量最多是个位数，没有惊群问题；而「同一份输入得到同一份时间序列」对调试和测试更有价值。

所以退避是纯指数：

```text
wait = min(backoffMs × 2^(attempt-1), maxBackoffMs)
```

3 次尝试、`backoffMs=1000` 时的等待是 0（首次）→ 1000ms → 2000ms。

测试里可以直接断言这个序列，不需要 mock 随机数。

## 五、重试怎么表达在事件里

没有新增事件类型。每次尝试都复用 `node_started`，重试时带上 `attempt`：

```text
node_started  (attempt 省略)   ← 第一次
node_started  attempt=2
node_started  attempt=3
node_succeeded
```

最终失败的 `node_failed` 也带 `attempt`，告诉用户「试了三次」。

前端时间线据此展示「重试 ×2」；落库仍然是一条节点执行记录，状态在最后一次尝试后收敛。

## 六、退避期间也要能取消

重试等待不能把取消按钮变哑。

实现上等待是可中断的睡眠：注册 `abort` 监听，信号到达时立即结束等待并返回「已取消」，由调度器发 `run_cancelled`。

否则用户点了取消，还要等几秒的退避才看到反应——体感上等同于「取消没生效」。

## 七、重试与并发的配合

上一版引入了并行调度。重试必须和它兼容：

- 重试占用同一个并发槽位，不额外扩容；
- 一个分支在退避时，其他分支照常执行；
- 重试次数按节点独立计算，不共享。

这样「并行」与「重试」组合起来不会出现「重试把并发打满」的问题。

## 八、什么时候不该重试

这条边界值得单独说：**写操作的重试必须由用户决定**。

工具节点如果权限是 write 或 danger，即便配置了 `retry`，也建议不要依赖自动重试来保证成功。写操作的失败往往不是瞬时的，而是参数、权限或外部状态问题；盲目重试只会让问题更难排查。

真正需要「至少一次」保证的写操作，应该由工具自己实现幂等键，而不是让流程引擎反复调用。
