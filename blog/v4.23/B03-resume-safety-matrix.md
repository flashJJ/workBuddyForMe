# 哪些中断可以自动续跑：一张安全矩阵

自动续跑听起来是「把中断的运行重新启动」。但真正棘手的是另一面：**哪些运行不能重启**。

一次重复的文件写入、一条重复发出的消息，代价可能比让用户手动重放高得多。所以这一版在实现续跑之前，先把「安全」写成了矩阵。

## 一、判断依据不是运行状态

最直觉的做法是按运行状态判断：

```text
running        → 可以续跑
waiting_human  → 可以续跑
```

但同一个 `running` 背后可能是完全不同的情况：

- 正在调用 LLM，没有副作用；
- 正在写文件，副作用可能已经发生；
- 正在等桌面自动化操作，外部状态未知。

只看运行状态，会把风险最高的那类也放进来。所以判断要下沉到「节点」。

## 二、按节点类型分类

沿用上一版的并行白名单，节点被分成两类：

| 类型 | 举例 | 中断时是否安全 |
|---|---|---|
| 只读/纯计算 | llm、检索、条件、只读工具、end | 可以重执行 |
| 有交互或副作用 | human、agent、写/危险工具 | 不应自动重放 |

工具节点不能只看类型，还得看权限。恢复扫描会同步解析工具名：

```text
解析到 read            → 安全
解析到 write / danger  → 不安全
解析失败 / 找不到工具  → 不安全（保守）
```

「解析失败按不安全处理」是一个刻意的偏保守选择。自动续跑的收益是省一次点击，而错误重放的代价可能是脏数据，两者不对称。

## 三、waiting_human 为什么是安全的

等待人工的运行有一个特殊情况：它的节点记录也是 `running`，但节点类型是 human。

如果按「human 在途不安全」直接拒绝，所有等待审核的运行在重启后都会变成终态，这显然不合理——用户只是还没点「同意」。

所以矩阵里 `waiting_human` 优先判断：它没有副作用在执行，续跑后会重新发出等待事件，继续等用户。这不是重放，而是恢复到「等待」这个状态本身。

## 四、版本与触发方式

还有两类不该自动续跑的情况：

- **运行版本已变化**：checkpoint 里的节点 id 来自旧图，新图可能删了节点或改了边；硬续跑会得到不可预测的结果；
- **对话触发的运行**：请求上下文已经消失，续跑出来的结果没有接收方。

这两种情况都保持 `interrupted`，让用户从运行中心手动重放。

## 五、决策顺序

把上面的规则排成顺序，避免互相覆盖：

```text
1. 本进程仍在执行          → 拒绝（already_active）
2. trigger = chat          → 拒绝（chat_request_gone）
3. 版本缺失/不一致/编译失败 → 拒绝（version_missing）
4. 运行状态 = waiting_human → 允许（waiting_human）
5. 存在不安全在途节点      → 拒绝（unsafe_in_flight）
6. 存在安全在途节点        → 允许（safe_in_flight）
7. 无任何节点进度          → 允许（empty_checkpoint）
8. 全部节点已落定          → 允许（empty_checkpoint，交给引擎收尾）
```

两个细节：

- `waiting_human` 放在不安全节点判断之前，否则人工节点会被误判；
- `start` 视为安全节点，它只写入参，没有外部副作用。

## 六、状态迁移怎么落

判定为可续跑后，运行状态要能从 `interrupted` 回到 `queued`。

但恢复扫描拿到的是「原本在途」的行（`running` / `waiting_human`），直接改 `queued` 需要额外的状态校验。实现上分两步：

```text
先 markInterrupted（校验原状态，写中断原因）
再 requeueInterrupted（interrupted → queued，清原因与终态时间）
```

多一次写入，换来的是「只有确实在途的运行才会被改」，避免误伤已经终态的行。

## 七、拒绝也要留下原因

拒绝自动续跑不是静默失败。运行保持 `interrupted`，并带上 `process_restart` 原因；如果是版本或安全节点问题，日志里会记录具体节点。

用户看到的是一个可以手动重放的终态，而不是「不知道为什么不跑」。

## 八、这张矩阵的价值

它把「自动恢复」从一个模糊的好意，变成一组可测试的判定：

- 安全节点在途 → 续跑；
- 写工具在途 → 停；
- 等待人工 → 继续等；
- 版本变了 → 停；
- 聊天触发 → 停。

每一条都有对应的单测。自动化的边界越清楚，用户才越敢把长流程交给它。
