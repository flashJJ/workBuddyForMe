# 已成功的节点，绝不重跑

续跑与重试都建立在一个前提上：同一件事不要做两遍。

这一版把「幂等」落在两个层面：节点状态决定是否执行，执行行决定是否新增记录。前者保证副作用不重复，后者保证观测不重复。

## 一、先定义「执行过」

一个节点算「执行过」，只看一个事实：它的执行记录是不是 `succeeded`。

不是看内存里有没有缓存，也不是看事件流里有没有出现过——进程重启后这些都没了，只有数据库里的状态还在。

所以续跑的判断非常简单：

```text
checkpoint 里是 succeeded → 不执行，复用 outputs
checkpoint 里是 skipped   → 不执行，维持跳过
其他（未开始 / running）   → 进入调度
```

这条规则比任何内存 memo 都可靠，因为它跨进程。

## 二、为什么内存 memo 不够

上一版在运行内用 `${runId}:${nodeId}` 做幂等，防止并发调度把同一个节点启动两次。

但那只是运行内的保证。进程崩溃后，内存里的集合清空；如果续跑只依赖它，已成功的节点会被重新执行。

所以两套机制各司其职：

| 机制 | 作用域 | 解决的问题 |
|---|---|---|
| 待执行集合 | 单进程、单次运行 | 同一节点不被调度两次 |
| checkpoint | 跨进程、跨重启 | 已成功节点不被重跑 |

契约里写的「幂等键」描述的是语义，不是某一种数据结构。

## 三、已成功的节点，连事件也不发

续跑时，已落定节点是静默跳过的：不补发 `node_started`，也不补发 `node_succeeded`。

这既是为了观测准确，也是幂等的一部分——如果把成功事件再发一遍：

- 前端时间线会重复展示；
- 事件消费者可能重复写节点记录；
- 运行详情里的耗时统计会被污染。

历史事件已经在上一进程发过并落库。订阅方要回看，走落库回放，而不是让引擎重放。

## 四、节点执行行也不该重复

这里有个实现细节值得单独说。

事件落库时，`run-store` 会为每个 `node_started` 插入一行 `node_executions`，并在内存里记住 `nodeId → executionId`。

新进程启动时这个映射是空的。续跑如果重执行一个中断节点，就会插第二行，同一节点出现两条记录。

解决方式是续跑前预加载：

```ts
const initialIds = listNodeExecutions(runId).map((n) => [n.nodeId, n.id]);
const store = createFlowRunStore(runs, initialIds);
```

这样重执行会更新原行，运行详情里仍然是一条记录。

## 五、那 running 节点怎么办

中断时正在执行的节点，状态是 `running`，产出为空。它不在 checkpoint 里，所以会被重新调度。

这是「至少一次」语义：

- 对只读/纯计算节点（LLM、检索、条件），重执行是安全的；
- 对写/危险工具、human、agent，恢复策略直接拒绝自动续跑。

也就是说，「重跑」这件事只发生在安全节点上；风险节点交给用户决定。

## 六、重试与幂等的关系

重试本质上是「同一个节点执行多次」。这时幂等靠什么？

靠两点：

1. 重试只发生在节点执行体内部，作用域写入只在成功后发生一次；
2. 每次尝试复用同一条 `node_executions` 行，最终状态取最后一次。

所以「尝试三次」在观测上是一个节点、一条记录、`attempt=3`，而不是三个节点。

对于有副作用的工具，重试是否安全由使用者和工具自己保证——引擎只保证「不会在未配置的情况下自动重试」。

## 七、一个容易被忽略的边界

如果崩溃发生在「最后一个节点成功」与「运行终态落库」之间，checkpoint 里会包含一个成功的 end。

这时续跑不能把 end 当成「已跳过」然后继续找别的 end——那会让一个实际成功的运行变成失败。

处理方式是：引擎初始化后先检查 checkpoint 里是否已有成功 end，有就直接按拓扑序最早的 end 输出收尾。

这也是幂等的一部分：成功就是成功，不需要再证明一次。

## 八、把幂等写成可测的规则

最终，幂等被拆成几条可验证的断言：

- 续跑后，已成功工具的执行次数不变；
- 续跑后，`node_executions` 里同一节点仍只有一行；
- 重试三次后，事件里有三次 `node_started`，但只有一条执行记录；
- 写工具在途时不会自动续跑。

这些断言比「保证幂等」这样的描述更有用，因为它们能在 CI 里跑。
