# 超时为什么不能对所有节点一刀切

「给节点加一个超时」听起来是最没有争议的需求：跑太久就失败，避免用户干等。

但真正实现时，如果对所有节点一视同仁，会立刻遇到几个没法解释的现象：人工审核两分钟没点就失败、写工具在确认框上被超时、Agent 的三角色协作刚进行到一半被判死。

这一版的做法是：**超时只对非交互节点生效**。

## 一、超时想解决什么

先明确目标：超时不是为了「惩罚慢」，而是为了「避免无限等」。

需要它的场景很具体：

- LLM 请求卡住，流式没有返回；
- 检索服务无响应；
- 只读工具调用了外部接口，迟迟不返回。

这些场景的共同点是：执行体在等一个外部结果，没有任何交互，用户可以接受「超时失败后重试或重放」。

## 二、哪些节点不该有超时

### 人工节点

人工节点的语义就是「等到用户决定」。给它超时，等于替用户做了「拒绝」的决定，而且是在用户可能只是离开了一会儿的情况下。

### 写 / 危险工具

写操作的超时更危险：超时只代表「没有等到结果」，不代表「没有执行」。一个写请求可能已经在外部生效，此时标记失败会误导后续处理。

而且写工具通常需要用户确认，确认框停留的时间不该被算进执行超时。

### Agent 节点

Agent 节点内部有自己的多轮循环与预算控制（轮数、步骤、token）。外层再加一个超时，会出现两套互相不知道的截止时间：外层判失败，内部还在跑，结果无人接收。

## 三、只读工具怎么判断

工具节点的类型是统一的 `tool`，权限要到运行时解析才知道。所以超时判定多了一步：

```text
读 config.toolName
解析工具
权限 = read  → 应用 timeoutMs
权限 = write / danger → 忽略
解析失败 → 忽略（保守）
```

解析失败时选择「忽略超时」而不是「应用超时」，原因和恢复矩阵一致：宁可让它继续跑，也不要在不确定的情况下强行判死。

## 四、超时是失败，不是取消

这一点需要说清楚：超时发生后，节点被标记失败，运行按策略收敛；但底层执行体并没有被强制中断。

为什么不直接中断？

- 本地大多数执行体是 Promise，没有通用的取消手段；
- 强行中断可能留下半完成状态；
- 工具调用可能已经产生外部副作用。

所以超时的语义是「不再等待这个结果」，而不是「让这个操作停下来」。这也是为什么写操作必须排除在超时之外。

如果某个执行体自身支持取消，它应该自己监听运行信号，而不是依赖引擎的超时。

## 五、超时与重试的关系

超时被当作可重试错误。配置了 `retry` 的节点，超时后会按退避重试。

这带来一个组合效果：

```text
timeoutMs = 5000, maxAttempts = 3
```

最坏情况下，一个节点会占用约 15 秒（不含退避）。对本地流程来说可以接受，但配置时应该意识到「尝试次数会放大超时」。

我们没有做「总超时」——那是另一个语义（整个运行的截止时间），留到将来需要时再单独设计。

## 六、事件里怎么体现

超时没有新增事件类型，最终表现为一次 `node_failed`，消息里包含节点 id 与毫秒数：

```text
节点 llm-1 执行超时（5000ms）
```

如果配置了重试，`node_failed` 会带 `attempt`，前端可以展示「第 3 次尝试超时」。

## 七、配置建议

给使用者的三条建议：

1. **LLM 节点**：按模型的最长响应时间设置，通常 60–120 秒；
2. **检索节点**：本地检索很快，超过 10 秒基本是异常；
3. **只读工具**：按外部接口的 SLA 设置，并配合 `maxAttempts=2` 左右。

写工具、人工节点、Agent 不要配——配了也不会生效，但容易让人误以为有保护。

## 八、小结

超时不是「越普遍越好」的能力，而是一条需要划边界的保护：

- 对无人值守、可重放的节点，它是兜底；
- 对交互与副作用节点，它是风险。

把这条边界写进契约，比事后解释「为什么审核超时了」要省事得多。

下一篇讲幂等：续跑与重试都建立在「已成功的节点绝不重跑」之上。
