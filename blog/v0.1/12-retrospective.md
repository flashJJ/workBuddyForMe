# 一个人做完一个本地 AI 应用：10 条工程复盘

一个本地优先、桌面交付、单人开发的私人 AI 助手，功能面其实不复杂：对话、知识库 RAG、自定义助手人设，Web 与 Electron 双交付，技术栈是 Next.js 14 全栈 + Electron + SQLite + pnpm Monorepo。但把它真正做到能打包、能长期迭代，难点几乎全在「非功能」的地方：架构边界、密钥安全、测试取舍、工程规范。

这篇是系列收尾，不按时间线讲故事，只沉淀 10 条在真实代码里验证过的经验，外加一张避坑表。

## 10 条经验

### 1. 分层是一个人开发的护城河

Monorepo + 单向依赖 + 服务层，让每次改动都有明确边界：改数据库不影响前端，换供应商不影响 UI。没有分层，一个人维护全栈就是持续的连锁反应噩梦。这条规矩必须靠自动化检查守护，靠自觉一定会破。

### 2. 原生模块的 ABI 问题要提前想清楚

Electron + better-sqlite3 的启动问题一度最让人动摇。最终方案是 fork 真实 Node 子进程，让原生模块跑在与编译时一致的运行时里，打包时把 Node 一起进包、fork 指定 `execPath`。记住一个操作性结论：**遇到 dlopen 报错，先查 NODE_MODULE_VERSION 是否一致**。

### 3. 密钥安全是底线，不是可选项

API Key 明文落库，等于把钥匙挂在门把手上。加密落盘 + 出参永不返明文 + 本地服务令牌守卫，三层防护缺一不可。用户把 Key 填进来，这份信任没有「先上线后补安全」的余地。

### 4. 流式对话的中断语义要专门设计

用户点停止，已生成的内容不能丢。abort 信号全链路透传、已生成部分写回数据库、消息置 stopped——这既是体验细节，也是工程素养。流式请求建立后不重试，则是避免重复计费和内容错乱的硬边界。

### 5. 小体量数据别上重型组件

几百篇文档的知识库，SQLite + sqlite-vec 完全够用：向量归一化后 L2 等价余弦，一个文件装下结构化数据和向量索引。**不要为了「技术先进」给自己引入一个需要长期运维的服务进程**。

### 6. 统一 API 契约省掉一半联调时间

`{ success, data }` / `{ success, error: { code, message } }` 加领域错误码，前端解析零猜测；Zod schema 前后端共享、类型同源，改一处全链路生效。单人前后端一肩挑时，这份契约省的是自己的时间。

### 7. 测试里绝不调真实 API

真实模型调用又慢、又贵、又不稳定。外部调用 100% mock，测试只验证自己的编排逻辑；数据库在集成测试里反而要真实，因为 SQL 和事务边界是 bug 高发区。依赖注入是这一切能低成本成立的结构前提。

### 8. 300 行红线是给「未来的自己」的礼物

超长文件意味着认知过载、意味着改不动。设一个明确的数字红线、用脚本强制、用带理由的白名单收口，拆分就会在写代码的当下自然发生。维护成本在写的时候就付清了，后面全是收益。

### 9. 一个人也要有 CI

没有 reviewer，CI 就是 reviewer。typecheck + lint + 行数门禁 + 覆盖率阈值，全绿才提交；本地和 CI 跑同一套命令，任何失败都能本地复现。它的价值不是报表，是让你敢在周五下午动核心代码。

### 10. 文档不是交付之后的事

架构文档、接口契约、模块设计要边写边更新。代码过三个月自己也会忘，文档不会——**三个月后回来，文档是你和过去自己唯一可靠的对话记录**。

## 踩过的坑（避坑表）

| 坑 | 症状 | 解法 |
|---|---|---|
| Electron fork 子进程 ABI 不匹配 | 窗口 30s 不出现 | 打包内置真实 Node，fork 指定 execPath |
| fork 无 error 监听 | 子进程崩溃无日志 | 加 error/exit 监听，转发 stdout/stderr |
| Smart App Control 拦截未签名 exe | 打包产物无法启动 | 用官方签名 electron.exe 作为宿主加载 asar |
| SSE 半包解析失败 | 流式内容错乱 | 逐字符状态机 parser，不依赖完整行 |
| 密钥明文出参 | 安全漏洞 | 仓储层分脱敏视图和含密文行，服务层才可取密文 |
| 数据库写入非单一事务 | 崩溃后数据不一致 | 四步写库包进一个 db.transaction |
| 未监听子进程端口回收 | 重启端口被占 | will-quit 先 SIGTERM 再 SIGKILL |

这张表的共同规律：每一个坑本质上都是**两个组件之间的契约没写清楚**——运行时与编译时、父进程与子进程、网络包与解析器、仓储与出参、多次写库与原子性、退出与回收。

## 独立开发真正考的是取舍

一个人做全栈产品，最大的挑战不是技术难度，是决定不做什么：

- **什么自己做，什么用现成的**：数据库不自己写（SQLite），UI 组件用 shadcn，精力留给业务编排；
- **什么现在做，什么以后做**：本地模型适配器先在注册中心预留位置，不提前实现；
- **什么是必须的，什么是锦上添花**：密钥安全必须，主题切换可以无限期延后。

目标不是完美，是**能用、好维护、能持续迭代**。

## 下一步方向

核心闭环（配置供应商 → 创建助手 → 对话 → 知识库 RAG → 桌面打包）跑通之后，自然的延伸方向有：

- 本地模型适配器，做到完全离线；
- 多模态：图片理解、文档解析增强；
- 对话导出与数据备份；
- 插件系统（函数调用）。

这些都建立在同一个前提上：边界清楚、契约稳定，新能力可以挂上去而不必推翻旧结构。

## 写在最后

把一个产品从想法做到可交付，技术选型只是其中一小部分。真正决定项目能不能活下去、能不能长大的，是架构决策、工程规范、测试体系和文档习惯这些「非功能」的东西。

如果你也在做自己的 AI 应用，只有一句建议：**先让它跑起来，再让它跑得好**——但「跑起来」的每一步，都值得顺手把边界划清楚。
