# 为什么我给项目设了「单文件 ≤300 行」的硬规则

> 不是洁癖，是一个人维护全栈项目的生存策略。

## 那个崩溃的下午

某天下午，我打开一个 800 行的组件文件想加个按钮。找了半小时没找到按钮该插哪，改完又把别的逻辑弄崩了。关掉文件的时候我想：**这不是在写代码，是在解谜**。

那天我做了个决定：所有手写 `.ts` / `.tsx` 文件，**超过 300 行就不许提交**。

## 300 行怎么来的

不是拍脑袋。我翻了几个自己维护得比较舒服的项目，发现体感良好的文件大多在 200 行以内，超过 400 行的基本都要靠搜索才能定位。取个中间值，300 行——既能容纳一个完整的服务类，又逼着你在超过之前动手拆。

## 怎么落地：一个脚本就够

我写了个 Node 脚本扫描 `apps/` 和 `packages/` 下的手写 `.ts/.tsx`，超过 300 行就非零退出：

```bash
pnpm check:lines
```

然后接到 `pnpm check` 里，和 typecheck、lint 一起跑。CI 里也跑，超限直接挂。

```text
$ node scripts/check-file-lines.mjs
文件行数检查通过：所有手写 .ts/.tsx 文件均 ≤ 300 行。
```

白名单只放行配置文件、barrel 出口、自动生成文件，而且每个白名单条目必须写注释说明理由——防止「白名单滥用」。

## 这条规则逼出来的好事

### 1. 组件自然拆分

以前一个页面文件塞 600 行，现在被迫拆成 `Sidebar`、`MessageList`、`MessageItem`、`Composer`、`EmptyGuide`……每个文件职责单一，改「消息渲染」只动 `MessageItem`，不会误伤别的。

### 2. 服务层变薄

一个 `provider-service.ts` 以前又管 CRUD 又管连接测试又管加密，现在拆成 `provider-service`（CRUD + testConnection）和 `secrets/cipher`（加解密），各司其职。

### 3. 代码评审变快

300 行以内的 diff，眼睛扫一遍就知道改了啥。一个人开发没人评审，这条规则就是「自我评审」的底线。

### 4. 可测性提升

小文件通常意味着单一职责，而单一职责的东西好写单测。项目里 `core` 包覆盖率能到 85%，300 行规则功不可没。

## 反例：什么时候可以超过

不是所有文件都适合卡 300 行。比如：
- **自动生成的迁移文件**：白名单放行
- **类型声明的 barrel**：白名单放行
- **配置文件**：白名单放行

这些都不是「手写业务逻辑」，规则的目标是业务代码，不是所有文件一刀切。

## 一个人开发的「防崩盘」机制

一个人写全栈，最大的风险不是技术难题，是**认知过载**。300 行规则本质上是给「未来的自己」降低心智负担：

- 打开任何文件，一屏能看个大概
- 改一个功能，影响范围可控
- 半年后回来，还能看懂自己写的啥

它不保证代码质量，但保证**不会烂到没法维护**。对于独立开发者，这就够了。

## 小结

300 行不是金科玉律，你可以设 400、500，关键是：

1. **有一条明确的数字红线**，而不是「尽量短」
2. **用脚本强制**，不靠自觉
3. **白名单要严格**，每个例外都有理由
