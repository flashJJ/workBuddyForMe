# 单文件超过 300 行就不许提交：一个人的全栈生存规则

长文件是单人项目最隐蔽的崩盘方式。打开一个 800 行的组件想加个按钮，找半小时定位不到插入点，改完又把不相干的逻辑弄崩——这时你会意识到：**维护长文件不是在读代码，是在解谜**。

我们这个本地优先的桌面 AI 应用全栈都由一个人写，没有同事帮你兜底。对此立的规矩简单粗暴：所有手写 `.ts` / `.tsx` 文件，**超过 300 行就不许提交**。这篇讲这条红线怎么来的、怎么强制执行，以及它逼出了哪些意料之外的好处。

## 300 这个数字怎么来的

不是拍脑袋。翻几个维护起来体感舒适的项目，会发现规律：读起来轻松的文件大多在 200 行以内，超过 400 行的基本都要靠搜索才能定位代码。取中间值 300 行——既能容纳一个完整的服务类，又逼你在越线之前动手拆。

数字本身可以商量（400、500 都行），关键是**必须是一条明确的红线**，而不是「尽量写短一点」这种无法执行的愿望。

## 怎么落地：一个脚本就够

写一个 Node 脚本扫描 `apps/` 和 `packages/` 下的手写 `.ts/.tsx`，超过 300 行就非零退出：

```bash
pnpm check:lines
```

然后接到 `pnpm check` 里，和 typecheck、lint 一起跑；CI 上也跑，超限直接挂。

```text
$ node scripts/check-file-lines.mjs
文件行数检查通过：所有手写 .ts/.tsx 文件均 ≤ 300 行。
```

白名单只放行配置文件、barrel 出口、自动生成文件，而且每个白名单条目必须写注释说明理由——防止「先加白名单再说」的滥用。规则一旦开口子不解释，很快就会形同虚设。

## 这条规则逼出来的好事

### 1. 组件自然拆分

以前一个页面文件塞 600 行，有了红线后被迫拆成 `Sidebar`、`MessageList`、`MessageItem`、`Composer`、`EmptyGuide`……每个文件职责单一。改「消息渲染」只动 `MessageItem`，不会误伤别的逻辑。

### 2. 服务层变薄

一个 `provider-service.ts` 原本又管 CRUD、又管连接测试、又管加密，后来拆成 `provider-service`（CRUD + testConnection）和 `secrets/cipher`（加解密），各司其职。拆分的契机不是有人要求，而是文件自己撞到了红线。

### 3. 代码评审变快

300 行以内的 diff，眼睛扫一遍就知道改了什么。单人开发没有人帮你 review，这条规则就是「自我评审」的底线：任何一次提交的核心改动都不该大到看不完。

### 4. 可测性提升

小文件通常意味着单一职责，而单一职责的东西好写单测。项目里 `core` 包覆盖率能到 85%，300 行规则功不可没——它在你写代码的当下就把「太大没法测」的类提前拆散了。

## 反例：什么时候可以超过

不是所有文件都适合卡 300 行：

- **自动生成的迁移文件**：白名单放行；
- **类型声明的 barrel**：白名单放行；
- **配置文件**：白名单放行。

这些都不是「手写业务逻辑」。规则的目标是业务代码，不是对所有文件一刀切——把例外也写进规则里，规则反而更站得住。

## 本质：给未来的自己降低认知负载

一个人写全栈，最大的风险不是技术难题，是**认知过载**。300 行规则是给「半年后的自己」留的后路：

- 打开任何文件，一屏能看个大概；
- 改一个功能，影响范围可控；
- 隔很久回来，还能看懂自己写的是什么。

它不保证代码质量，但保证代码**不会烂到没法维护**。对于独立开发者，这就够了。

## 小结

行数红线的精髓不在数字本身：

1. **要有一条明确的数字红线**，而不是「尽量短」；
2. **用脚本强制**，纳入 check 和 CI，不靠自觉；
3. **白名单要严格**，每个例外都写明理由。
