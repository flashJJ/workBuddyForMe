# 外部模型调用 100% mock：四层测试体系的取舍

AI 应用的核心依赖是大模型 API，而真实 API 恰恰是最不该出现在测试里的东西：

- **慢**：一次对话几秒，一套集成测试跑几分钟；
- **贵**：每跑一遍测试都是真金白银的 token 开销；
- **不稳定**：上游限流、超时、返回内容漂移，测试时绿时红；
- **有副作用**：写真实数据、污染本地库，用例之间互相干扰。

所以这个本地 AI 应用的测试铁律是：**测试中外部模型调用 100% mock**。测试验证的是我们自己的编排逻辑，不是模型今天的心情。这篇讲配套的四层测试体系，以及每一层故意放弃了什么。

## 四层测试体系

```text
┌─────────────────────────────────────┐
│  E2E（Playwright）                  │  关键路径，mock provider
├─────────────────────────────────────┤
│  集成测试（Route Handler）           │  真实 SQLite + mock provider
├─────────────────────────────────────┤
│  单元测试（core / ai / database）    │  纯函数 + 注入依赖
├─────────────────────────────────────┤
│  门禁（lint / typecheck / 行数）     │  静态质量
└─────────────────────────────────────┘
```

### 第一层：门禁

`pnpm check` = typecheck + lint + 300 行门禁。不跑任何业务逻辑，纯静态检查，秒级反馈，是提交前的最低门槛。它的价值在于把「类型错了、文件超长」这类问题挡在测试开始之前。

### 第二层：单元测试

针对纯函数和注入式服务，按包划分：

- `packages/shared`：Zod schema、错误码、SSE 序列化；
- `packages/ai`：HTTP 重试、SSE 解析（mock fetch）；
- `packages/database`：内存 SQLite 跑仓储 CRUD；
- `packages/core`：服务层（mock 仓储 / mock provider）。

覆盖率门槛设为 statements ≥ 70%，写在 Vitest 配置里强制阻断——不达标 CI 直接挂。

mock 的结构性前提是**依赖注入**。服务层通过工厂函数接收依赖，而不是在文件顶部硬编码具体实现：

```ts
function createChatOrchestrator(deps: { db, cipher, providers }) {
  // 用 deps 里的东西，不直接 import 具体实现
}
```

测试传入 mock 依赖即可隔离运行；生产环境传入真实实现。可测试性不是事后补的，是这种构造方式白送的。

### 第三层：集成测试

驱动真实 Route Handler，但用**临时数据根 + 真实 SQLite + mock provider**：

```ts
const dataRoot = mkdtempSync(...);
setDataRootForTest(dataRoot);
// 用 mock provider 替换真实适配器
```

覆盖完整 HTTP 链路：请求 → Zod 校验 → 服务层 → 真实数据库 → 响应包络，包括 SSE 流的拼接、中断和错误分支。

这一层有个刻意的不对称：**数据库不 mock，provider 必须 mock**。数据库不 mock 是因为要验证真实 SQL 和事务边界是否正确（这正是 bug 高发区）；provider mock 是因为没有任何理由在测试里打真实模型 API。

### 第四层：E2E

Playwright 跑真实浏览器，走完整用户路径：

1. 配置供应商与模型（mock）；
2. 创建自定义助手；
3. 新建对话、流式收发、中途停止；
4. 创建知识库、上传文档至 indexed；
5. RAG 提问、验证引用角标。

E2E 的 provider mock 通过环境变量 `APP_MOCK_AI=1` 注入进程内 mock，返回固定的 SSE 分块。这样 E2E 验证的是**前端交互和全链路编排**（事件顺序、中断落库、引用渲染），模型质量不在被测范围内——那本来也不该由自动化测试背书。

## mock fetch 的统一方式

Vitest 里用 `vi.stubGlobal('fetch', mockFetch)` 替换全局 fetch，按 URL 分流不同的假响应：

```ts
vi.stubGlobal('fetch', async (url, init) => {
  if (url.includes('/chat/completions')) {
    return mockSseResponse(['你', '好']);
  }
  if (url.includes('/embeddings')) {
    return mockJsonResponse({ data: [{ embedding: [0.1, 0.2, ...] }] });
  }
});
```

全仓 25 处 `vi.stubGlobal('fetch', ...)` 覆盖所有外部调用点，测试期间不存在任何真实网络请求。统一从 fetch 边界 mock，而不是在业务代码里到处插 if-test 分支。

## 测试数据隔离

每个用例使用独立的临时数据根：

```ts
beforeEach(() => {
  const dir = mkdtempSync(path.join(tmpdir(), 'app-test-'));
  setDataRootForTest(dir);
});
```

严禁依赖用户真实数据目录。临时目录用完即弃，用例之间零共享，可以任意并发、任意重复执行。

## 覆盖率阈值的真正意义

70% 不是为了报表好看，是为了**逼自己写可测的代码**。如果一个函数覆盖率怎么都上不去，通常说明它耦合太重、副作用藏得太深——这正是该拆的信号，而覆盖率阈值只是替你把信号说出口。

实测覆盖率：

- config: 96%
- database: 95%
- ai: 93%
- core: 85%

全部在 70% 阈值之上。core 稍低，是因为部分极端异常分支难以构造，但核心路径全覆盖。与其为最后几个百分点写扭曲的测试，不如承认边际收益递减。

## 一个人的测试策略：按性价比分配

单人开发时间有限，测试必须挑地方使劲：

- **核心路径必须有集成测试**：对话、知识库、设置——这是产品价值所在；
- **纯函数必须有单测**：分片、prompt 组装、SSE 解析——逻辑复杂且最容易出 bug；
- **UI 组件只测关键交互**：不是每个组件都测，挑容易坏的（表单、流式渲染）；
- **E2E 测关键路径**：5 条足够，覆盖核心用户旅程。

不追求 100% 覆盖率，追求的是**动了核心逻辑就有测试兜底**。

## 小结

1. **外部调用 100% mock**：不慢、不贵、不可预测的东西一律挡在测试外；
2. **四层测试**：门禁 → 单元 → 集成 → E2E，各有明确分工和放弃项；
3. **依赖注入**：mock 简单与否，在写构造函数时就决定了；
4. **数据隔离**：每用例一个临时数据根，可重复、可并发；
5. **覆盖率阈值**：目的是逼出可测的结构，不是凑数字。
