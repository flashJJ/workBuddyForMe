# 一个人的全栈 AI 应用怎么搭：pnpm Monorepo 分层实战

做一个本地优先、桌面交付、单人开发的私人 AI 助手——能对话、能管知识库、能自定义助手人设，最好还能打包发给朋友用——遇到的第一个工程问题与模型无关：**Web、桌面壳、公共逻辑，代码该怎么放？**

一个人、一台机器，拆成多仓库会被同步发版拖垮，全塞一个包里又会变成一团互相缠绕的面条。答案是：**Monorepo + 清晰分层**。这篇讲清楚具体怎么落。

## 为什么是 Monorepo，而不是多仓库

多仓库方案听起来干净：Web 一个、桌面一个、公共库一个。但真正动手改两天就会发现痛点——改一个类型定义，要在三个仓库里同步发版，协调成本比写代码本身还高。单人开发没有这个余裕。

最终用 **pnpm workspaces + Turborepo**，一个仓库装下所有东西：

```text
my-ai-app/
├── apps/
│   ├── web/        Next.js 14 全栈（页面 + API）
│   └── desktop/    Electron 主进程 / preload / 打包
├── packages/
│   ├── shared/     领域类型、Zod schema、错误码
│   ├── config/     数据根路径、环境变量（唯一事实源）
│   ├── database/   better-sqlite3 + 迁移 + 仓储
│   ├── ai/         Provider 抽象 + OpenAI 兼容适配器
│   └── core/       业务服务：对话 / 知识库 / RAG / 设置
└── scripts/        工程脚本
```

共享代码原地可见、原地可改，版本一致性问题从结构上消失。

## 分层的核心原则：依赖只能往下走

这是整个工程最重要的一条规矩，写进架构文档，还加了测试来守护：

```text
web ──→ core ──→ ai ──→ shared
 │       │        │
 │       ├─→ database ──→ config ──→ shared
 │       └─→ config
desktop ──→ config（只碰路径契约）
```

**反向依赖绝对禁止**：`shared` 不能引用 `core`，页面组件不能直接 `import database`。所有数据访问必须经过 `core` 服务层，由 `apps/web` 的 Route Handler 调用。

这条规矩换来的是改动的局部性：改数据库实现不影响前端，换 AI 供应商不影响 UI，每一层都可以独立测试。一旦允许反向依赖，分层会在几周内名存实亡——所以必须用自动化检查兜底，而不是靠自觉。

## 包导出的小技巧：开发走源码，生产走产物

每个 package 的 `package.json` 里用条件导出区分两种消费方式：

```json
{
  "exports": {
    "development": "./src/index.ts",
    "default": "./dist/index.mjs"
  }
}
```

- **开发态**（Next dev / Vitest）：直接消费 TS 源码，免 watch 构建，改完即生效；
- **生产态**：消费 tsup 构建产物，可追踪、可打包。

一个声明同时拿到开发体验和生产可控性，不需要在两种模式之间维护两套入口。

## 桌面端为什么只依赖 config

Electron 主进程的职责很纯粹：开窗口、托管内置服务、管密钥。它**不需要**知道对话怎么存、知识库怎么检索——那些都是 `core` 的事。

所以 desktop 只依赖 `config`（拿路径契约和环境变量），业务逻辑全在被 fork 出去的 Next 子进程里跑。桌面壳出问题不会污染业务层，业务层的异常也不会冒泡进原生窗口管理。这条边界在排查问题时价值极大：看崩溃发生在哪一层，基本就锁定了责任范围。

## 一个人维护的底气来自哪里

分层不是为了炫技，是为了**一个人也能 hold 住全栈**：

- 想加个新 API？改 `core` 服务 + `web` 的 Route Handler，两处的事；
- 想换数据库？只动 `database` 包，上层无感；
- 想支持新模型供应商？在 `ai` 包加个适配器，`core` 不用改。

Monorepo 让共享代码零成本，分层让改动有明确边界。一个人写全栈，最怕的不是代码多，是「牵一发而动全身」。分层，就是给这种恐惧上的保险。

## 小结

如果你也在一个人做全栈 AI 应用，记住三件事：

1. **Monorepo** 比多仓库省心，pnpm + Turborepo 足够撑起这个规模；
2. **依赖单向**，写进文档再加自动化检查守护；
3. **包导出分条件**，开发体验和生产可控可以兼得。
