# 页面 245 行不拆不行：管理页组件化，以及「本地开发态不算数」的端到端口径

功能做完，界面往往先撑不住。

能力包管理页本来只有一个列表：名称、版本、状态、几个按钮。这一阶段要在每行加签名徽章、健康徽章、effect 详情，再加升级对话框、健康横幅、孤儿清理确认。页面文件在改动前已经两百四十多行，继续堆下去必然突破单文件上限。

所以这一阶段先拆组件，再挂功能。同时踩到另一个问题：本地开发态的端到端结果，不能当作发布判定。

## 一、先拆三类职责

拆分不按「长得像」切，而按职责切：

| 组件 | 职责 |
|---|---|
| 行组件 | 单个包的状态、徽章、effect 详情、启停/升级/卸载入口 |
| 升级对话框 | 选 ZIP、提交、成功刷新、失败提示 |
| 健康横幅 | 触发检查、汇总问题、列出孤儿、确认清理 |

页面只保留编排：查询、筛选、安装、健康查询与清理动作、对话框开关。拆完之后行组件一百四十多行，对话框九十多行，横幅一百多行，页面两百三十行，各自都在上限内。

这件事的意义不只是行数。行组件拿到的 props 减少之后，签名徽章与健康徽章可以完全由数据驱动，不需要页面知道「怎么判断签名状态」；升级对话框只负责上传与结果展示，不关心后端状态机；健康横幅只消费报告，不自己计算问题。

## 二、徽章是状态的可见化

签名徽章显示五种状态，健康徽章显示正常、警告、损坏。两者都不是装饰，而是把两个后台链路的结果搬到用户眼前。

原则是：**徽章只显示已经算出来的结果，不在渲染时发起检查。**

签名状态在列表查询时计算，代价是逐包验签；健康状态只在用户点「检查全部」后出现。如果列表加载就扫全盘，页面会慢到不可用。徽章因此有一个「未检查」态，而不是假装正常。

升级对话框刻意不预览新版本号：浏览器端不解压 ZIP，无法可靠读取新清单。它只显示当前版本与回滚提示，升级成功后由列表刷新展示新版本。这是一个功能删减，换来的是不在前端重复解析与校验逻辑。

## 三、查询失效与错误语义

升级与清理成功后要刷新两处：能力包列表与健康报告。只刷新列表会让健康徽章停留在旧结论；只刷新健康会让版本显示落后。

错误提示统一成一句话：升级失败会说明「已回滚或未变更」，不暴露内部堆栈。用户需要知道的是「旧版本还能不能用」，而不是后端在哪一步抛了异常。

清理确认同样克制：只列出可删除的孤儿目录数量，确认后执行，结果里包含已删除与跳过两类。不提供「全选删除」这种更快的入口，因为清理的代价不可逆。

## 四、组件的输入输出契约

拆分之后，三个组件各自只回答一个问题，输入也被压到最小：

| 组件 | 输入 | 输出 |
|---|---|---|
| 行组件 | 一个包的视图数据、是否升级中 | 启停/升级/卸载动作 |
| 升级对话框 | 当前包 id 与版本 | 上传结果、关闭 |
| 健康横幅 | 健康报告、清理中状态 | 触发检查、确认清理 |

行组件不读取全局状态，也不自己发请求；升级对话框不知道后端状态机怎么实现；横幅不计算 issue，只按严重级别分组展示。页面作为编排层，负责把查询结果与动作串起来。

这样拆的直接收益是测试成本：行组件可以用固定视图数据驱动，不必搭一整套后端；对话框只需 mock 一次上传；横幅只需喂一份报告。组件越「笨」，测试越稳。

## 五、i18n 的行数连锁反应

加载签名与健康文案时，设置页的文案文件已经贴着三百行上限。新增信任库段落后必然超限。

处理方式是按领域拆文件：签名设置文案独立成一组，设置主文件只保留引用。这不是为了行数而拆，而是文案本身按功能域分组更合理；行数门禁只是把这个合理性变成了硬约束。

拆分之后，设置页组件也不需要知道文案来自哪个文件，只按 key 取用。双语键值成对维护，缺失会直接报错，而不是静默回退到中文。

## 六、端到端：先加三例，再谈全量

新增的端到端用例只有三例，但覆盖三条主链路：

1. 健康自检：点「检查全部」，出现正常徽章与空孤儿列表；
2. 升级：用测试工具生成一个高版本 ZIP，上传后版本更新；
3. 信任库与强制策略：保存策略后，未签名包安装被拒。

升级用例的关键是「生成包」而不是「准备固定文件」：用压缩库读取示例包、改版本号、重新打包，测试数据随版本变化自动跟随，不需要维护一堆二进制样本。

## 七、本地开发态为什么不算数

第一次全量端到端跑在开发模式，结果是大量超时与状态抖动，通过率远低于预期。换到生产构建模式后，同一份代码全量通过。

原因不神秘：开发模式按需编译，页面首次访问要等编译；热更新会在测试中途替换模块；设置页这种长页面在开发态滚动与加载更慢。端到端断言用的是固定超时，编译抖动直接变成失败。

CI 一直用生产构建启动服务，所以流水线的结果一直是稳定的。这次的教训是：**判定口径必须与流水线一致。** 本地开发态可以用来快速验证单条链路，但不能用来判断「这一版能不能发」。

生产模式的全量结果是 125 例全通过，约十一分钟；桌面冒烟十项通过，剩下一项依赖真实桌面会话。这两个数字与上一阶段基本持平，新增用例没有让门禁变慢或变脆。

桌面冒烟是另一条独立链路：它验证打包后的桌面壳能否启动、进程间通信是否可用、本地服务是否被正确归集。它不覆盖页面内部细节，因此与 Web 端到端互补，而不是重复。未通过的一项属于当前桌面会话的环境限制，不是本阶段引入的回归。

## 八、这一层得到什么

管理页从「一个能用的列表」变成「三个可维护的组件 + 一套明确的编排」；签名与健康从后台能力变成用户看得见的状态；端到端建立了与流水线一致的判定口径。

徽章与报告不是装饰，它们把后台判断变成用户能看见的状态；组件拆分也不是形式，它让每个交互都有独立的测试入口。这两件事合起来，才让「收口」在界面上成立。
