# 签名、升级、健康：能力包从「能装」走向「可信」

一个本地优先的桌面 AI 应用，把能力做成可安装的包之后，紧接着会遇到一类更朴素的问题：**装进来的包，凭什么信？装错了版本，怎么退？它坏了，谁先知道？**

上一阶段把六类资源统一进同一个生命周期：技能、MCP、工作流、桌宠动作、事件剧本、报告卡片都能安装、启用、停用、卸载，每类启用时返回一个真实可逆的副作用句柄。这一阶段不再扩新能力类型，只补三条收口链路：**清单签名、原地升级、健康自检**。

## 一、先列欠账

| 缺口 | 现状 | 后果 |
|---|---|---|
| 签名只记录不验证 | 清单里有 `signature` 字段，宿主不检查 | 包在传输或二次打包中被改动，没有任何判断依据 |
| 同 id 无法升级 | 安装见到已安装 id 直接冲突 | 想更新只能卸载重装，状态全丢 |
| 坏了不会自报 | 启用只检查目录存在 | 动作文件没了、工作流被手工停用，列表仍显示「已启用」 |

这三条不是新功能，而是「可扩展」走到一定阶段必然要补的账。能力越多，用户越需要知道：它是不是原包、能不能平滑更新、坏了能否定位。

## 二、签名不是字段，是判决

签名要回答的问题很窄：**这份清单是否由某个本地信任的公钥签发，且内容一字未改。**

窄问题反而难做对。清单是 JSON，直接序列化再签名会被键顺序、空格、默认值坑到：作者手写的清单与宿主解析后的清单可能逻辑等价、字节不同。所以流程必须先规范化：

1. 用 schema 解析清单，应用默认值；
2. 递归排序对象键、保留数组顺序、去掉 `signature` 字段；
3. 加域前缀，得到一个稳定的字节串；
4. 对这个字节串做 Ed25519 签名。

这一条顺序反过来就失效：先签名再解析默认值，等于签的是一份宿主永远不会看到的内容。

验签结果被拆成五态：无签名、有效、无效、未知密钥、格式坏。策略则只有三档：关闭、提醒、强制。**策略只决定「没签名」与「不认识」是否放行；签名对不上，在提醒与强制下都拒绝。** 否则签名反而成了降级攻击面——攻击者只要把签名改坏，就能落进「提醒」再被放行。

## 三、升级是一个状态机，不是覆盖文件

「升级」听起来像把新文件覆盖旧文件，实际要处理四件事：版本语义、依赖关系、磁盘原子性、失败回滚。

版本必须严格递增，`1`、`1.0`、`1.0.0` 归一化比较；id 必须与路径一致；kind 必须与已安装一致。任何一条不满足就拒绝，不猜测用户意图。

磁盘侧用三段式换位：新包先写进暂存目录，旧目录改成备份名，暂存目录再改名成正式目录。数据库行在同一事务里换成新清单。顺序不能颠倒，否则中途崩溃会留下半套文件。

失败回滚按 kind 分别处理。工作流要重新发布旧版本，剧本要恢复旧定义，技能与 MCP 要重新启用旧句柄。如果旧 effect 也起不来，就不假装成功：落 `disabled + lastError`，明确提示重新安装旧版本。**停在「半升级」比失败更糟。**

### 为什么不做同版本修复安装

一个自然的想法是：既然能升级，为什么不支持「版本不变、内容替换」的修复安装？

因为它绕过了版本语义。版本号是用户与系统共同的契约：同版本意味着同内容。如果允许同版本换内容，用户就无法用版本号判断两台机器上的包是否一致，升级日志也失去意义。

坏包的正确路径是：健康报告定位、卸载、重装。多一条「强制覆盖」的旁路，短期方便，长期会把版本号变成装饰。

## 四、健康检查以数据库行为真相

健康报告不猜，只对照：行在、目录不在；目录在、校验和对不上；payload 里多出一个没登记的文件；依赖被卸载、被停用、版本对不上；六类 effect 的目标对象是否还存在、状态是否一致；签名是否有效。

这些检查被固定成十一个 issue 码，每个码只回答一件事，带严重级别。报告把「一个包坏了」拆成「哪一层坏了」，用户不需要从「启用失败」四个字开始猜。

清理同样克制：只删数据库没有对应行的孤儿目录，跳过升级暂存与备份目录，超过 24 小时的残留才回收；删除失败进跳过清单，不中断其余项。

## 五、三条链路怎么互相咬合

签名、升级、健康不是三个独立功能，它们在关键节点上互相调用：

| 场景 | 签名 | 升级 | 健康 |
|---|---|---|---|
| 安装 | 按策略判决 | — | 安装后可选检查 |
| 升级 | 写盘前复用同一套验签 | 状态机本体 | 升级残留目录由清理回收 |
| 启用 | 按策略判决 | 依赖版本影响启用 | 启用前复核依赖 |
| 列表 | 显示五态徽章 | 显示版本与升级入口 | 显示健康徽章 |
| 设置 | 信任库与策略 | — | 策略不影响报告，但报告始终验签 |

这种咬合决定了实现必须复用而不是复制：升级不能有第二套验签，启用不能有第二套依赖检查，健康报告不能自己发明签名状态。任何一处复制，都会在后续版本里长出口径差。

## 六、零迁移的取舍

这一阶段没有新增表与列，schema 版本保持不变。签名状态按需计算，信任库与策略存进设置 JSON，升级只改已有行内字段。

代价是「上次检查时间」这类状态无处持久化，健康结果每次实时算；收益是旧库直接打开、回退旧版本不破坏数据。对一个本地单机应用，这个交换通常是值得的：升级越轻，用户越敢升。

## 七、验证：把坏路径先走一遍

收口型版本的功能增量不大，验证重点全在失败路径：

- 策略矩阵逐格覆盖：三档策略 × 五种签名状态；
- 键序不同的等价清单验签一致，改任一字段验签失败；
- 六类 kind 逐类升级成功、禁用态保持禁用、坏包不动旧包、从属版本冲突被拒；
- 凭启用失败触发回滚，确认目录、清单与旧 effect 都能恢复；
- 六类 effect 各构造一个坏场景，健康报告给出对应 issue 码；
- 孤儿目录可列出、可清理，且不误删有行的目录。

结果是：单元测试两千七百多例，生产模式端到端一百二十五例全通过，桌面冒烟十项通过、一项依赖真实桌面会话。安装包约 192 兆。

## 八、这一阶段留下什么

能力包第一次同时具备三种确定性：**来源可验证、版本可前进、损坏可诊断。** 它仍然不是插件市场，也不执行包内任意代码；变化的是边界——签名有了判决，升级有了退路，坏包有了病历。

下一篇从签名讲起：一份 JSON 清单要怎么变成稳定的字节串，默认值与键顺序为什么会让「看起来一样」的两份清单验签结果不同。
