# 收口型版本的工程方法：七条来自「签名、升级、健康」的复盘

有一种版本没有新功能，只有欠账：签名字段一直没验、同一个 id 不能升级、包坏了不会自报。这类版本的产出不是「多了什么」，而是「原来能用的东西现在更可信」。

它比加功能更考验工程判断，因为每一步都在处理「不确定」：签名可能对不上、升级可能失败、包可能已经坏了。下面是这一阶段留下的七条方法。

## 一、先定语义，再写实现

签名这件事，先回答「策略放行什么」，再写验签代码。

最终定下的语义只有一句：**策略只放行「没有签名」与「不认识这把钥匙」，不放行「签名对不上」。**

如果把「无效签名」也交给提醒档放行，签名系统就变成降级攻击面：攻击者破坏签名，就能从强制档掉进提醒档，再被放行。语义定清楚之后，实现几乎没有分支争议——三档策略 × 五种状态，逐格有唯一答案。

升级也是同理。先定「版本严格递增、id 与 kind 不可变、不做降级」，再讨论目录怎么换。语义含糊的版本，实现会用「猜用户意图」来补，最后每个分支都不可测。

## 二、唯一实现优先于「方便复用」

签名工具与宿主必须对同一份清单算出同样的字节。为此规范化函数只允许存在一份，放在共享包；签名工具从构建产物导入，宿主从源码导入。

代价是工具启动时依赖构建产物，产物缺失要提示先构建；收益是永远不可能出现「脚本里的 canonical 与运行时的不一样」。这类漂移不会立刻报错，只会在某次签名后表现为「明明没改却验签失败」，排查成本极高。

同理，验签只放在服务端包，因为客户端包里不该出现 Node 的加密模块。把「共享纯函数」与「服务端加密」分开，是一次边界设计，而不是一次代码摆放。

## 三、失败路径要有名字

升级失败不是一种失败。它至少分三种：

- 新包校验失败，磁盘与旧包都没动；
- 新 effect 启用失败，但旧 effect 成功恢复，等同升级未发生；
- 新 effect 失败且旧 effect 也失败，只能落禁用并提示重装。

三种结局对应三种用户动作。如果只看一个「升级失败」错误码，用户无法判断旧版本还能不能继续用。给失败路径命名，比给成功路径加日志更重要。

健康检查同理：十一个 issue 码不是为了好看，而是为了让每种坏法都有下一步。目录缺失要重装，依赖停用要启用依赖，状态不一致要重新启用包。

## 四、原子性靠目录换位，不靠「小心一点」

升级的磁盘一致性没有用「写完再删」这种顺序保证，而是三段式换位：暂存、备份、正式目录改名。

这不是更复杂的实现，而是更简单的推理：任何一步崩溃，磁盘最多留下一个暂存目录或一个备份目录，不会出现正式目录里混着两个版本的文件。残留由清理入口按时间回收。

同一 id 的升级互斥也是同一思路：并发请求不会让两个升级同时换目录，第二个直接冲突。互斥不是为了性能，是为了让「原子」真的成立。

## 五、零迁移是一种产品选择

这一阶段没有新增表与列，schema 版本不变。

签名状态按需计算，信任库与策略进设置 JSON，升级只改已有行内字段。代价是健康结果没有「上次检查时间」、清理需要用户点一次按钮；收益是旧库直接打开、回退旧版本不破坏数据。

对一个本地单机应用，升级摩擦是最贵的成本。每多一张表，就多一次「升级失败后能不能退回去」的担心。能用既有结构表达的状态，就不新增结构；这不是偷懒，而是把复杂度留在代码里、不留给用户。

## 六、门禁口径必须与流水线一致

功能做完后，本地开发模式的全量端到端大面积超时，一度看起来像功能把测试拖垮了。换到生产构建模式，同一份代码全量通过。

开发模式按需编译、热更新替换模块、长页面加载更慢，固定超时会把编译抖动当成功能失败。CI 一直用生产构建，所以流水线从来没这个问题。

结论被写成规则：**本地开发态用于单链路快速验证，发布判定以生产构建模式为准。** 这条规则的价值不在于这次通过，而在于以后再遇到「本地红、CI 绿」时，知道先怀疑口径，而不是先改代码。

## 七、单文件上限逼出正确的拆分

管理页在加功能前已经两百四十多行，继续堆必然超限。拆分不是按代码长度切，而是按职责切：行组件、升级对话框、健康横幅、页面编排。

拆完之后，每个组件的输入都变小了：行组件不需要知道签名怎么判断，只消费状态；对话框不关心升级状态机；横幅只消费健康报告。行数门禁看起来是形式要求，实际逼出了一次正确的关注点分离。

设置页文案也是同一回事：签名段落加进去会超过上限，于是按功能域把文案拆成独立分组。拆完之后不是因为行数合规才好，而是因为按域组织本来就更可维护。

## 八、一张可复用的收口清单

如果下次还要给已有能力补「可信度」，可以按这张清单逐项自问：

1. **语义是否只有一句话？** 策略放行什么、拒绝什么，能否用一句话说清；
2. **输入是否唯一？** 签名、校验、比较的输入是否都经过同一个规范化函数；
3. **失败是否命名？** 每种失败结局是否对应一个明确的用户动作；
4. **磁盘是否原子？** 换目录是否只靠改名，而不是「先写后删」；
5. **状态是否可退？** 失败后旧版本能否继续使用，退不回去是否说清楚；
6. **检查是否按需？** 重活是否只在用户显式触发时执行；
7. **数据是否零迁移？** 能否用既有结构表达，而不新增表与列；
8. **口径是否一致？** 本地判定是否与流水线使用同一种运行模式。

八条里没有一条是「加功能」。收口型版本的质量，基本由这些看不见的选择决定。

## 九、这一阶段证明的与没证明的

证明了三件事：清单签名可以成为可重复的判决；同 id 升级可以在不丢状态的前提下完成并回滚；坏包可以在用户点一次按钮时被定位到具体层。

没有证明的也清楚：过期清理不会自动发生，需要用户点一次；健康扫描是同步的，包很多时会变慢；升级不支持降级与同版本修复；符号链接的路径校验、运行记录下钻仍留到后续。

一个收口型版本的价值，恰恰在于它把「还差什么」写得同样清楚。功能清单会过时，边界清单不会。

## 十、给下一阶段的建议

下一阶段如果继续做能力包，优先补三件事：降级与回滚入口、信任密钥轮换、健康检查的分批执行。它们都直接来自这一阶段主动留下的边界，而不是新的想象。

工程方法则可以复用到任何「给已有能力补可信度」的版本：先定语义，再定状态机；先命名失败，再写成功；先统一实现，再谈复用；最后用与流水线一致的口径验收。
