# 坏包不会自己说：十一个 issue 码的健康自检

能力包装好之后，最容易出现的不是安装失败，而是「装好了但坏了」。

包目录被清理工具删了，动作文件被移走，工作流被手工停用，依赖被卸载——列表还显示已启用，直到用户点一次「启用」才报错。用户看到的不是故障，而是「昨天还能用，今天不行」。

这一阶段给包加了一次按需健康检查：不猜、不缓存，按十一个固定 issue 码给出结论。

## 一、以数据库行为真相

健康检查的基线很明确：**数据库里有行，就代表系统认为这个包应该存在。**

于是第一类问题自然出现：行在、目录不在。这类包在列表里仍然可见，但任何启用都会失败。报告把它命名为目录缺失，而不是笼统的「损坏」。

第二类问题是反过来：目录在、行不在。这类目录没有主人，既不会被卸载逻辑处理，也不会出现在列表里，是纯粹的磁盘残留。它被单独放进「孤儿」列表，由清理入口处理。

两边都以数据库为参照，不做「磁盘扫描后自动补行」这种聪明事。自动补行会让用户以为装过的东西还在，实际副作用早已丢失。

## 二、清单与载荷：三层校验

清单层先做一次 schema 校验。数据库里存的是 JSON 文本，仓储读取时通常只做解析；健康检查多做一步：解析后再过 schema。格式坏、字段缺失、类型不对，都归为清单无效。

载荷层做三件事：

- 清单登记的每个文件必须存在；
- 文件实际哈希必须与清单一致；
- payload 目录里不能出现清单未登记的文件。

第三条常被忽略。多出来的文件可能是旧版本残留，也可能是有人手工塞进去的东西；两种都不该被当作包的一部分。校验和只覆盖「清单说有的文件」，多余文件天然逃过校验，所以必须单独扫一遍。

清单文件本身与包根目录的散落文件不参与这项检查。范围划得越窄，误报越少；健康报告的价值在于可信，而不是覆盖一切。

## 三、依赖三态：缺失、停用、版本不符

依赖检查不只问「装没装」，而是分三种：

| 状态 | 含义 | 严重级别 |
|---|---|---|
| 缺失 | 依赖包根本没有行 | 错误 |
| 停用 | 依赖在，但处于禁用 | 警告 |
| 版本不符 | 依赖在且启用，但版本与声明不相等 | 错误 |

分级的理由很实际：停用的依赖是可恢复的，用户启用即可；缺失与版本不符则需要重新安装或升级，属于硬故障。

这套三态同时被启用路径复用。启用一个包时，签名检查之后、副作用执行之前，先做同样的依赖复核；失败时状态保持禁用并写入错误信息，文案区分三种原因。这样「健康报告发现的病」与「启用时拒绝的理由」是同一套语义，不会出现报告说警告、启用却报错的口径差。

## 四、六类 effect：每种都有自己的「还在不在」

副作用句柄指向的对象各不相同，探测方式也必须分别写：

| kind | 探测对象 |
|---|---|
| 技能 | 技能目录与已登记状态 |
| MCP | 服务器注册表中的 id |
| 工作流 | 工作流行与发布状态 |
| 桌宠动作 | 动作行与资产文件可读 |
| 事件剧本 | 剧本行与启用标记 |
| 报告卡片 | 卡片行 |

除了「在不在」，还要看「状态对不对」：包是启用态，但工作流或剧本实际被停用，属于状态不一致。用户在工作流页手工停用一个来自能力包的工作流，包本身并不知道；健康检查把这个裂缝显式化。

探测异常统一归为 effect 缺失，详情带上异常消息。不额外发明十几个错误码——错误码越多，用户越难行动。

## 五、签名始终参与报告

安装策略关闭时，安装不做验签；但健康检查始终验签。理由很简单：报告是只读的，验签不影响安装，把「签名无效」告诉用户没有副作用。

签名问题分两级：无效与格式坏是错误，未知密钥是警告。前者说明内容可能被改过，后者只说明这个公钥还没被信任。两种性质不同，混成一级会让用户对报告脱敏。

这里有一个设计一致性：策略只影响「能不能装/升/启用」，不影响「报告里写什么」。用户把策略设成关闭，不代表系统对签名一无所知。

## 六、清理：只删确定无主的东西

清理入口与报告分开：报告只读，清理有副作用，必须用户确认。

删除规则收得很紧：

- 只删数据库没有对应行的目录；
- 跳过升级暂存目录与备份目录；
- 备份与暂存超过 24 小时才回收；
- 单个删除失败进跳过清单，不中断其余项。

不删散落在根目录的单个文件，因为无法判断它是不是用户手工放进来的。清理的目标是「确定无主」，不是「看起来没用」。

## 七、性能与取舍

哈希重算的代价与包体积线性相关，所以检查只在用户点「检查全部」时执行，不在列表加载时执行。单包上传上限二十兆，最坏情况可接受。

扫描按顺序执行，没有做并发。包数量很大时接口会变慢，这是已知边界：先保证结果与磁盘一致，再考虑分批或流式。

健康结果不缓存，也就没有「上次检查时间」。零迁移的版本不新增表，这是主动换来的简单：报告的时效性由点击触发，而不是由一个可能过期的缓存字段决定。

## 八、这一层得到什么

能力包第一次有了「病历」：坏在哪一层、严重到什么程度、能不能恢复，都有明确答案。用户不必靠「启用失败」四个字猜原因。
