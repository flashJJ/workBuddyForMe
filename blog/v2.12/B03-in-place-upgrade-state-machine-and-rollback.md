# 同 id 原地升级：三段式换位、按类型回滚，与绝不停在半升级

安装能力包不难，升级难。

安装是从零开始：失败就删除，什么都不留。升级是在「用户已经在用的东西」上动刀：磁盘目录、数据库行、六类副作用句柄，任何一处没对齐，用户就会看到一个既不是旧版本、也不是新版本的中间态。

这一阶段给能力包补上了同 id 原地升级，并把「失败」拆成两种：可以完全退回去的失败，和退不回去但必须说清楚的失败。

## 一、先定版本语义，再谈实现

三条前置被固定下来：

- 路径 id 必须等于清单 id，不允许「换个包升级另一个」；
- kind 必须与已安装的一致，技能不能升级成工作流；
- 版本必须严格大于当前版本。

版本比较不引入复杂语义：只接受一到三段数字，`1`、`1.0`、`1.0.0` 归一化后比较；出现非法段直接拒绝，不做「尽力解析」。降级与同版本修复安装都不在本阶段：前者会让用户回到有问题的版本，后者会绕过版本语义，两者都容易把「升级」做成包管理器。

## 二、预检：从属包是最容易漏的一环

一个包可能被别的包依赖。升级时如果新版本改了依赖版本，已启用的从属包就会在下次启用时失败。

所以升级前要先算两件事：

1. 哪些启用中的从属包声明了对这个包的依赖？它们声明的版本必须与新版本完全相等，否则拒绝升级并列出从属包名。
2. 哪些从属包处于禁用状态？它们不阻塞升级，但要在响应里列出来，提示「后续启用会因版本不符失败」。

前者是硬约束，后者是知情同意。把两者混在一起，要么误拦正常升级，要么让用户事后才发现。

同一 id 同时只允许一个升级进行中，第二次请求直接冲突。这条互斥不是性能优化，而是避免两个升级同时换同一个目录。

## 三、状态机：先停旧，再换位，最后启新

启用态升级的顺序被固定成：

1. 停用旧 effect。失败就中止，磁盘与状态都不动；
2. 把新包写进暂存目录，校验全部通过后才继续；
3. 旧目录改名为备份，暂存目录改名为正式目录；
4. 数据库行替换成新清单，重置 effect 句柄；
5. 启用新 effect。

禁用态升级简化成：写新包、换目录、替换清单，保持禁用，不尝试启用。用户明确停用的东西，升级不应该顺手打开。

三段式换位解决的是崩溃一致性：任何一步中断，磁盘上最多留下一个暂存目录或一个备份目录，不会出现「半个新包 + 半个旧包」。残留目录由清理入口按时间回收。

## 四、按 kind 适配：六类副作用不能共用一个回滚

不同 kind 的「启用」含义不同，升级与回滚也必须分别处理：

| kind | 升级动作 | 回滚要点 |
|---|---|---|
| 技能 | 替换目录并重新登记 | 重新启用旧技能名 |
| MCP | 替换配置并重新连接 | 重新启用旧服务器 |
| 工作流 | 新增版本并发布 | 重新发布旧版本，禁用态恢复旧 current |
| 桌宠动作 | 替换资产与文件 | 重新启用旧动作 |
| 事件剧本 | 替换定义，id 不变 | 恢复旧定义与启用标记 |
| 报告卡片 | 停用删行，换包后重建 | 重建旧卡片 |

技能、MCP、桌宠动作的副作用句柄可能随包内容变化（技能名、服务器名、动作键），预检时必须排除旧句柄自身，否则会把「旧句柄即将消失」误判成资源冲突。

事件剧本的 id 不可变：剧本行与触发额度都属于用户，升级只替换定义，不换 id。工作流则相反，升级会新增版本行并切换 current；回滚把旧版本重新置为 current，但保留升级新增的版本行——运行历史不能因为回滚被删。

报告卡片最简单也最危险：停用会删行，所以升级要先删后建，失败时按旧清单重建。删了不建，就是数据丢失。

## 五、回滚的两种结局

新版本启用失败时，回滚路径按相反顺序执行：删除新目录、备份还原、清单换回旧值、按 kind 恢复旧 effect。

结局只有两种：

- **旧 effect 恢复成功**：返回失败，但说明「本次升级未发生」，磁盘与状态等同升级前；
- **旧 effect 也失败**：落 `disabled + lastError`，明确提示重新安装旧版本。

第二种结局不好看，但必须存在。假装成功会让用户在一个不可用的「已启用」状态里继续操作；假装回滚会让系统声称恢复而实际没有。把二次失败说清楚，至少用户知道下一步该做什么。

## 六、响应里要带什么

升级成功不只返回新版本号，还要返回两件事：从哪个版本升到哪个版本，以及哪些禁用从属包会受影响。前端不需要重新推导，直接把结果展示给用户。

升级失败也不只返回错误码：要区分「已回滚」「未变更」「需要重装」三种语义。错误信息如果只说「升级失败」，用户无法判断旧版本还能不能继续用。

## 七、验证：六类都要走一遍成功与失败

升级的测试矩阵按 kind 展开：

- 六类各升级一次，确认新版本可用、历史数据保留；
- 禁用态升级后仍是禁用；
- 坏包升级返回失败且旧包不动；
- 从属包版本冲突返回 409 并列出名字；
- 同版本与降级被拒；
- 人为让新 effect 启用失败，确认回滚后旧版本仍可升级。

最后一条最能说明设计意图：回滚不是终点，系统要能回到「还可以再试一次」的状态。

## 八、这一层得到什么

能力包第一次可以「更新」而不是「重装」。用户的状态留在原地，磁盘换位是原子的，失败有明确的退路。
