# 安装包里的 next 不见了：构建工具对根级 node_modules 的硬编码过滤

这是整个升级里唯一一个「开发目录一切正常、装完就崩」的问题。它没有在类型检查、单测、构建日志里留下任何痕迹，只在安装产物里出现。

## 一、现象：装完启动即报错

出包流程走完，安装包生成成功，`latest.yml` 与更新配置也正确。装到干净环境启动，主进程直接退出：

```text
Error: Cannot find module 'next'
```

不是窗口没出现，而是托管服务根本起不来——桌面壳会拉起 web 端产物，而 web 端的运行时依赖不在包里。

顺带发现，同一份产物在解包目录里运行也有同样报错。也就是说：**出问题的不是安装器，是打进包里的内容本身。**

更值得记的是：同一轮出过两次包，第一次只验证了「进程起来、窗口出现」，于是这个问题完整地漏了过去。直到在安装态日志里读到主进程的退出原因，它才浮出水面。

## 二、为什么开发目录能跑

开发态之所以正常，是因为有两套完全不同的模块解析：

| 环境 | 依赖从哪来 |
|---|---|
| 开发目录 | pnpm 的符号链接工作区，依赖都在仓库根 |
| standalone 产物 | 打包器把追踪到的依赖复制进 `server/node_modules` |
| 安装态 | 只有 `resources/server` 下被允许进包的东西 |

所以「本地跑得起来」这件事，对安装态几乎没有证明力。它证明的是源码和依赖声明是通的，不证明打包链路把依赖带上了。

## 三、归因：构建工具对根级 node_modules 有硬编码过滤

定位方式很简单：把产物目录列一遍，对照开发目录里的 standalone 输出，发现依赖齐全；再看安装包内的解包目录，`server` 下的运行时依赖整体缺失。

问题出在构建工具的过滤器里。它有一条**硬编码规则**：当一个文件集（file set）的根级条目，其相对路径恰好等于 `node_modules` 时，直接判定为「不要」，返回 false。

这条规则对普通资源是合理的——大部分应用不需要把整袋依赖当资源塞进去。但 Next 的 standalone 产物把依赖放在 `server/node_modules`，对 `from: resources/server` 这一层来说，`node_modules` 正好就是根级条目。

于是出现一个很别扭的局面：

```text
resources/server/node_modules/next        ← 需要
resources/server/.next/...                ← 正常进包
resources/server/package.json             ← 正常进包
resources/server/node_modules → 被过滤   ← 缺的就是它
```

注意它是被**静默**过滤掉的：没有警告，没有提示，构建退出码为 0。

规则本身很短，形态大致是：

```js
// 构建工具的文件集过滤器（示意）
if (relative === 'node_modules') return false;   // 根级依赖整袋跳过
```

它是一条防御性设计：避免把整棵依赖树当普通资源重复打包。问题是它按「相对路径字符串」判断，不区分「这是应用自己的依赖」还是「这是运行时产物带出来的依赖」。standalone 恰好把依赖放在了资源根级的 `node_modules` 上，于是被这条规则命中了。

## 四、修法：额外挂一条映射

既然根级被过滤，就换一个层级绕过它：把依赖目录单独作为一条资源映射挂进去。

```yaml
extraResources:
  - from: resources/server
    to: server
    filter:
      - "**/*"
  # 根级 node_modules 会被构建工具硬编码过滤，
  # 单独挂载后才能把 standalone 运行时依赖带进安装包
  - from: resources/server/node_modules
    to: server/node_modules
```

这一条映射的语义是：让 `node_modules` 不再处于某条映射的**根级**，而是作为另一个映射的起点。过滤器的那条规则只针对根级名字，换个挂载方式就不触发。

代价是产物里同一批文件可能出现两次声明（一次被过滤、一次被复制），但最终落盘位置一致，不影响运行。

## 五、为什么不能把依赖「挪下去」

最直觉的修法是：把依赖从 `server/node_modules` 移到更深一层，比如 `server/runtime/node_modules`，这样根级就不是 `node_modules` 了。

这条路走不通，有两个原因：

1. **服务入口的相对解析是基于 `server` 的。** 入口文件在 `server` 目录下，Node 的模块解析会逐级向上找 `node_modules`，改位置意味着所有外部化依赖的解析路径都要跟着改。
2. **MCP 的 stdio 子进程也从这里解析。** 内置的 MCP 服务以子进程方式启动，二进制与它依赖的包同样从 `server/node_modules` 解析。把依赖搬走，等于同时打断托管服务和 MCP 两条链路。

所以正确动作不是「换个位置」，而是「在构建配置里补一条显式声明」。**改布局会波及运行时契约，改配置只影响打包。**

## 六、复测：41 个条目进包

修完后重新出包，验证三件事：

| 验证项 | 结果 |
|---|---|
| `resources/server/node_modules` 进包条目 | **41 个** |
| 关键运行时依赖 | next、better-sqlite3、sqlite-vec 的 win32 包均存在 |
| 原生模块后缀 | `.node` 走 asarUnpack 后可加载 |
| 安装版启动 | 主窗存活，托管服务健康检查通过 |
| 控制通道 | 就绪（原生键鼠模块加载成功） |

41 个条目这个数字本身值得记下来：它说明缺的不是「几个包」，而是**整袋依赖**——这也解释了为什么现象是启动即崩，而不是某个功能报错。

顺带确认了另一件事：条目数不等于包数。41 个顶层条目里既有作用域包，也有平台专用包（例如某个原生模块的 win32 版本），所以「看起来只有几十个」其实已经覆盖了全部运行时依赖。

## 七、为什么 smoke 没发现

早期烟雾测试的检查项是：进程存活、窗口标题、健康检查接口、日志关键字。

这些检查都绕过了依赖加载路径吗？不完全是——健康检查通过就说明服务起来了。问题在于**当时的 smoke 跑的是开发态或未打包产物**，而 `win-unpacked` 目录虽然在技术上属于打包结果，却仍然能解析到仓库里的依赖（因为它就在仓库目录内）。

三种环境的证明力差别很大：

| 环境 | 能证明什么 |
|---|---|
| 开发目录 | 代码逻辑正确 |
| 打包后的解包目录 | 打包内容大致完整（但模块解析可能仍回落到仓库） |
| 安装到独立目录 | **包内自洽**，唯一有意义的发布前证据 |

所以这次把 smoke 的覆盖口径往前推了一格：从「打包产物能跑」变成「安装后的目录能跑」。

## 八、教训

1. **开发目录能跑 ≠ 安装态能跑。** 依赖解析是环境相关的，跨环境的行为差异只能靠跨环境验证发现。
2. **构建成功不代表内容完整。** 缺一整袋依赖也能 exit 0，因为过滤器认为这是「正常省略」。
3. **硬编码过滤不可配，只能绕。** 遇到这类规则，先确认它的触发条件（这里是「根级名字等于 node_modules」），再换挂载层级，而不是改目录布局。
4. **打包链路的验证要落在安装产物上。** 解包目录是中间态，它可能借用了仓库的模块解析，给你一个虚假的通过。
5. **日志里的安静不等于没问题。** 这个问题从头到尾没有一条警告，唯一的异常信号是运行时的 `Cannot find module`——所以「构建日志干净」不能当作完整性证据。

## 九、下次怎么更快定位

把这次的过程压成一份排查顺序，同类问题可以少绕几圈：

1. **先确认失败发生在哪一层**：开发目录、解包目录、安装目录。三层的证明力不同，先定位层级再谈原因。
2. **对比产物清单，而不是读构建配置**。配置写的是意图，产物才是事实；把开发目录里的 standalone 输出当作基线，与包内目录逐项对照。
3. **看缺的是「整袋」还是「单个」**。整袋指向构建配置或过滤器，单个指向版本、平台分支或可选依赖。
4. **检查有没有静默过滤**。构建工具的过滤规则通常不打印日志，必要时临时打印最终文件集，确认某个目录是否被判定为「不要」。
5. **修完只认安装态复测**。解包目录通过不算通过，安装到独立目录、启动、健康检查三步都过才算。

这五步背后是同一个态度：**打包链路的正确性，只能由最终的包自己证明。**
