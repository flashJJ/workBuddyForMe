# 把一次性审计变成可重复门禁：安全基线、残余风险与封版口径

安全升级最容易在「修完了」这一步前功尽弃。修完是一次性的，依赖树是活的：下一次装包、下一次合并、下一次传递依赖漂移，都可能把刚清掉的公告带回来。

这次除了升版本，还做了一件事——**把「这次扫出来什么」变成「以后每次扫都按同一把尺子判定」。**

## 一、一次性扫描的三个问题

第一轮取证就是一条 `audit --json` 加一份人工整理的清单。它能回答「现在有什么」，但回答不了三个更重要的问题：

- **多少算通过？** 6 条 critical 修到 0 条，还是可以留几条？没人写得清。
- **谁可以例外？** 文档发布链的漏洞要不要修？测试进程的呢？
- **下次谁来跑？** 靠记忆的话，它大概率只跑一次。

于是把它拆成三件可交付物：一条命令、一张基线表、一份允许清单。

## 二、门禁的形状

```text
security:audit
  ├─ 跑 audit --json
  ├─ 按「运行时 / 开发 / 构建」分组计数
  ├─ 对比基线表
  └─ 判定：
       运行时 critical / high  > 0        → 失败
       出现未登记的新公告（任意级别）     → 失败
       只命中已登记的 dev/build 残余项    → 通过
```

三条设计约束值得说：

1. **门槛按风险分级，不按数量。** 运行时的 critical / high 是硬门槛，一条都不许有；开发链只要求「不新增未登记项」。
2. **残余项必须登记，不能默默存在。** 允许清单是一份显式文件，写清模块、公告、为什么接受、以及下次评估的时间点。
3. **命令就是封版命令。** 发布前跑的不是「我记得扫一下」，而是同一条 `security:audit`。

这样做的结果，是审计从「一次判断」变成「一个状态机」：**任何一次依赖变动，都只能落在三个状态之一——干净、已登记、失败。**

## 三、残余 3 条 critical 的取舍

升级完成后，全仓还剩 3 条 critical。它们的共同点是：**不进安装包。**

| 模块 | 所在链路 | 会不会进安装包 | 处理 |
|---|---|---|---|
| 文档发布 CLI | 文档站发布 | 不会 | 登记，有余量再清 |
| 测试 worker ×2 | 测试进程池 | 不会 | 评估升级测试框架，不阻塞封版 |

判断依据不是「严重度」，而是「可达性」：critical 的严重度描述的是**被利用后的后果**，可达性描述的是**有没有人能碰到它**。一条只在维护者本机跑文档发布时才会触发的漏洞，和一条随安装包发给所有用户的漏洞，不该用同一个优先级。

但「接受」必须带条件，否则就是放任。登记项同时被门禁看着：一旦它作为传递依赖被拉进生产依赖树，分组会变，门禁立刻变红。

## 四、数字：从 6 到 3，从 40 到 8

| 口径 | 升级前 | 完成后 |
|---|---|---|
| critical | 6 | **3**（全部为 dev/build） |
| high | 40 | **8** |
| moderate | 48 | **12** |
| low | 9 | **2** |
| 依赖总数 | 1373 | **1343**（生产 555 / 开发 718 / 可选 199） |
| Next 公告 | 23 | **0** |
| Electron 公告 | 38 | **0** |

注意依赖总数是**下降**的：换代把一个旧构建链的整棵传递树换掉了，新树更小。这条数字顺带解释了为什么高危计数下降得比预期多。

## 五、封版口径是怎么被一次 OOM 定下来的

首轮端到端跑的是本地默认的开发服务器。跑到约 24 分钟时，Web server 堆内存耗尽：

```text
JavaScript heap out of memory
```

结果是 88 通过 / 6 失败 / 15 未运行。失败的用例集中在几个重资源场景（会议、语音、模型渲染）。

处理顺序很重要——**先归因，再改口径**。做法是把失败用例按文件单独复跑，全部通过；再用生产模式跑全量，109 例全绿。这证明失败与环境有关，与代码改动无关。

于是封版命令固定成两步：

```text
pnpm build:web
GITHUB_ACTIONS=true pnpm test:e2e     # 走生产启动路径，与 CI 一致
```

这里有一条容易被忽略的原则：**当本地跑法和 CI 跑法不一致时，以 CI 为准，而不是以「本地能过」为准。** 否则每次封版都在赌一次环境运气。

净化之后还顺手修了三处测试债：首启向导遮罩拦截侧栏点击、版本号硬编码、窗口可见性断言没有轮询异步的 `show()`。它们不是运行时回归，但会持续制造假失败。

## 六、安装包与更新链路

发布形态的验证有三层，每层都能独立失败：

| 层 | 验证内容 | 本次结果 |
|---|---|---|
| 产物体积 | 安装包大小与上一轮构建对比 | 199,146,832 B（+889,130 B） |
| 覆盖升级 | 已装旧版 → 静默安装新版 | 通过，文件与产品版本正确 |
| 自动更新 | 旧版启动后能否检测到新版 | 检测到并开始下载 |
| 差量更新 | 是否有 blockmap | **缺失，回退整包下载** |

最后一行是本轮的已知限制：构建流程尝试生成差量索引，但发布资产里没有出现对应文件，更新器请求差量时拿不到，日志显示回退到整包下载后继续完成。功能上是通的，代价是每次更新都要下完整包。

这类「功能可用但形态降级」的问题，只能在真实更新链路上发现——本地装包测试永远测不到。

## 七、五条方法论

**1. 把一次性的判断固化成可重复的命令。**
这次的形状是「命令 + 基线表 + 允许清单」。反例就在同一轮里：端到端首轮的通过率是靠人工解读的，所以它会随环境波动；只有写成固定命令，口径才稳定。

**2. 按可达性分级，而不是按严重度分级。**
桌面壳的 Electron 写在 devDependency 里，但二进制随包分发，所以按运行时处理；文档发布 CLI 是 critical，但不进包，所以登记。同一张表里两个相反的决定，用的是同一条判据。

**3. 环境性失败要先归因，再决定改不改口径。**
e2e 的 OOM 如果直接归因为「新版本不稳定」，会误导整轮排查。先单文件复跑定位，再切生产模式复验，才敢把口径改掉。

**4. 对静默失效，只信产物。**
standalone 的追踪排除在 Windows 上是静默失效的，配置不报错、规则不生效。这类问题的唯一可靠防线是构建后扫描产物并让构建失败。

**5. 验证必须落在最终形态上。**
安装包的依赖缺失只在安装后的目录里暴露，解包目录因为靠近仓库而「看起来正常」。所以发布前证据链的终点必须是安装态，而不是构建成功。

## 八、这一轮留下什么

一次安全升级的价值，一半在「清掉了什么」，另一半在「以后怎么保持干净」。前者会随时间衰减，后者才是资产：

- 一条能在任何机器上重跑的判定命令；
- 一张写清了「多少算通过」的基线表；
- 一份带理由和复查时间的允许清单；
- 两道会变红的产物断言；
- 一个和 CI 对齐的封版口径。

下一次依赖变动时，不需要再问「这次扫出来算不算多」——门禁会直接回答。
