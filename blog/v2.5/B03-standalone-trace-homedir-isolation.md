# 构建产物里出现了用户主目录：standalone 追踪隔离的两个坑与三道断言

本地优先的桌面应用有一个隐含承诺：安装包里不该出现任何用户数据。这个承诺在代码里很容易成立，在构建产物里却很容易破——只要打包器认为「这个文件运行时可能需要」，它就会把它塞进产物。

这次框架换代，就在构建日志里撕开了这条缝。

## 一、现象：一条告警和一批非法目录

升级到 Next 15.5.28 后，`build:web` 能成功退出，但日志里多了一行：

```text
Failed to copy traced files ... .next\standalone\<盘符>\<用户目录>\<应用数据目录>\...
```

同时 `standalone` 目录下出现了一个以盘符命名的目录，里面层层嵌套着应用数据目录的绝对路径。

这两件事是同一件事的两面：**文件追踪（nft）把这些路径写进了描述清单，归集阶段照着清单去复制，复制不出来就报错。**

如果只是告警，还能忍。真正的问题是它意味着两件事都可能发生：

- 构建失败（归集阶段不总是软失败）；
- 就算构建成功，安装包里也可能夹带用户本机的模型、附件路径。

## 二、第一层归因：忽略键在新版本里消失了

早期实现里，配置文件用的是一个 `experimental.outputFileTracingIgnores` 键，值是指向应用数据目录的 glob。它在旧版本里工作得很好，把整个用户数据根挡住。

新版本的类型定义里，这个键**已经不存在了**。可选替代是顶层的 `outputFileTracingExcludes`。

看起来是一次改名。于是照做，把 glob 平移到新键上，重新构建——告警还在。

这一步是整件事的分水岭：**类型系统只能保证「你写的键存在」，不能保证「它的语义等价于旧键」。** 键被移除，往往意味着行为模型变了，而不只是改名。

## 三、第二层：路由级排除在 Windows 上不命中

继续追，问题落在匹配器上。

框架生成路由级排除规则时，会把「路由目录」和「排除模式」用 `path.join` 拼起来。在 Windows 上，这一步产生的是**反斜杠**的 glob。而底层匹配库（picomatch）默认不开启 Windows 模式，反斜杠不会被当作分隔符，也就匹配不到任何真实路径。

三个假设逐一实测：

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 键名写错，规则没生效 | 打印最终配置 | 规则存在 |
| glob 写得太窄 | 放宽到整目录 | 仍不命中 |
| 路径分隔符不匹配 | 打印拼接后的模式串 | **看到反斜杠，确认根因** |

也就是说，`outputFileTracingExcludes` 在 Windows 上是**静默失效**的：配置不报错，规则不生效，只有产物能说明问题。

这类失效最难防，因为它没有任何显式信号。你能依赖的只有两样东西：产物本身，以及一条会因此变红的门禁。

## 四、第三个坑：追踪根被仓库外的 lockfile 推走

修上面那条时，又撞到一件更隐蔽的事：`standalone` 里服务入口的层级变了。

框架靠向上探测锁文件来决定「追踪根」。当仓库的上级目录里还躺着另一个项目的锁文件时，探测会把根推到仓库之外——于是产物里多出一层或几层路径，原本约定的入口位置不复存在。

表现是另一条链路断了：桌面壳的归集脚本按固定相对路径找服务入口，找不到就认为构建失败。

修法是显式声明根：

```js
// 显式钉住追踪根，不依赖向上探测
outputFileTracingRoot: repoRoot
```

这个键不在最初的迁移清单里，是实测补上的。**凡是「框架替你猜」的东西，在单仓库多项目、上级目录有残留文件的环境里都要怀疑一次。**

## 五、修复：隔离家目录，再对产物做硬断言

两条配置都修完后，我们做了一个判断：**不要继续赌配置。**

原因是这类问题的根源在追踪器对 `os.homedir()` 的静态求值——它在构建期就能算出一个绝对路径。只要构建进程的「家」指向真实用户目录，追踪器就有机会把那里面的东西写进清单。任何基于 glob 的排除，都只是事后过滤，过滤不掉「它已经看见了」这件事。

所以主防线改成构建期隔离：

```js
// 构建包装器（精简）
const buildHome = mkdtempSync(join(tmpdir(), 'next-build-home-'));
try {
  spawnSync(nextBin, ['build'], {
    env: { ...process.env, HOME: buildHome, USERPROFILE: buildHome },
  });
  assertStandaloneTrace();   // 构建后断言，命中即 exit 1
} finally {
  rmSync(buildHome, { recursive: true, force: true });
}
```

隔离让追踪器只能看见一个空的构建家目录；它再怎么求值，也求不出用户数据路径。

断言这部分，扫描两个位置：

- `.next/server` 下所有 `.nft.json`：逐条检查 `files` 里的路径，出现应用数据目录名或盘符路径就记为命中；
- `.next/standalone` 下的目录名：出现应用数据目录名、或以单个盘符命名的目录，记为命中。

命中就打印前 20 条（避免刷屏）并以非零码退出：

```text
standalone trace 门禁失败：用户数据或盘外路径被追踪进产物
  trace: <相对路由清单> -> <绝对路径条目>
  dir:   <standalone 下的非法目录>
```

配置侧的 `outputFileTracingExcludes` 没有删，但退化成非 Windows 的兜底。**主防线从「匹配器应该能挡住」换成「构建产物必须自证干净」。**

## 六、为什么这才是正确的形状

回头看，三个坑分别对应三种不同的失效模式：

| 层级 | 失效模式 | 有信号吗 |
|---|---|---|
| 配置键移除 | 类型报错 | 有，编译期就能看见 |
| 匹配器平台差异 | 规则静默不生效 | **没有** |
| 追踪根探测 | 入口层级漂移 | 有，但发生在下游链路 |

只有第二类是无信号的。对无信号的失效，配置层面再怎么写都只是「希望它生效」；只有产物断言是「不接受它没生效」。

这也是为什么断言要写成**构建失败**而不是警告：警告会被忽略，尤其是当构建本身还能成功的时候。

## 七、验收

| 项 | 结果 |
|---|---|
| 构建告警 | `Failed to copy traced files` 消失 |
| trace 命中 | **0** |
| standalone 非法目录 | **0** |
| 服务入口 | 层级恢复到归集脚本约定的位置 |
| 健康检查 | `node .next/standalone/apps/web/server.js` 的 `/api/health` 返回 **200** |
| 应用数据目录 | 未出现在任何 `.nft.json` 或产物目录中 |

## 八、方法论

这段排查留下四条可复用的判断：

1. **被移除的配置键要当行为变更处理。** 改名可以照抄，删除必须重新论证语义。
2. **跨平台 glob 默认不可信。** 只要产物在 Windows 上生成，任何「路径拼接 + 模式匹配」的组合都要用产物验证一次。
3. **凡是框架自动探测根目录的地方，显式钉死。** 探测的输入是环境，环境不可控。
4. **对静默失效，唯一可靠的防线是产物断言。** 断言必须能让构建失败，否则等于没有。

最后一条尤其重要：这条门禁之后又挡过一次配置回退。它证明的不是「这次修好了」，而是「以后再坏会立刻被发现」。
