# 先换地基再加功能：桌面 AI 应用的一次安全底座升级

有一类版本天生不好讲：没有新按钮、没有新面板，用户装完以后界面一模一样。这次升级就是这种——零新功能、零数据迁移，交付物只有依赖版本、兼容性修复和一套可重复的安全检查。

决定做它的原因很朴素：**一个已经出了支持窗口的框架，不会因为你没发版就停止被研究。**

## 一、先判断暴露面，而不是先数公告

早期实现里，web 端锁在 Next 14.2.35，桌面壳锁在 Electron 31.7.7。扫一遍依赖树，命中 6 条 critical：Next 两条未认证 RCE、构建链传递的 tar，以及两个只在开发/测试链上的项。

面对这种清单，最容易犯的错是逐条论证「我们利用不了」。所以反过来做：先判断**这些东西到底在不在用户的机器上跑**。

| 依赖 | 声明位置 | 会不会进安装包 | 结论 |
|---|---|---|---|
| Next | web 端运行时 | 会（standalone 归集） | 运行时风险 |
| Electron | 桌面壳的 devDependency | 会（二进制随包分发） | 运行时风险 |
| electron-builder / tar | 构建链 | 不会 | 构建期风险 |
| 文档发布 CLI / 测试 worker | 开发链 | 不会 | 登记为残余 |

这张表带来两个反直觉结论。

第一，**devDependency 不等于开发期风险**。桌面壳的 Electron 写在 devDependency 里，但它的运行时会随安装包一起发给最终用户；审计报告里的 dev 标签不改变这个事实。

第二，**构建链的 critical 依然要修**。tar 的问题在解压路径上，只在出包时触发，可它决定了「安装包能不能被安全地生产出来」——这条链路一旦带病，后面所有验证都建立在一个不值得信任的产物上。

## 二、回环绑定不等于不可达

两条 Next critical 值得单独说，因为它们的暴露面判断很容易被一句话糊弄过去：「只监听 127.0.0.1，外网进不来」。

服务确实由桌面壳托管、只绑回环。但把链路拆开看，至少有三层缝隙：

- **本机进程不认回环**。同一台机器上的任意进程、任意本地页面都能访问回环端口，回环挡的是远程，不是本机。
- **业务 token 只覆盖业务路由**。鉴权守卫挂在 `/api/*` 上，框架内部端点（例如图片优化接口）根本不经过这层守卫。
- **「当前没用到」不等于「版本不在区间」**。全仓检索确认没有使用框架的图片组件，可是版本仍然完整落在公告的影响区间内。

三条叠起来：**框架级漏洞要按「可达」处理，除非能证明不可达。** 而证明不可达的成本，通常高于直接升级。

于是决策不是「评估利用条件」，而是「把版本移出区间」。

## 三、公告全景与版本选择：为什么不跨大版本

把 Next 的 23 条公告按修复阈值分组，会看到一条清晰的天际线：

| 修复阈值 | 条数 | 严重度构成 |
|---|---|---|
| ≥15.5.24 | 2 | critical ×2 |
| ≥15.5.21 | 7 | high ×3 / moderate ×4 |
| ≥15.5.15–16 | 10 | high ×4 / moderate ×4 / low ×2 |
| ≥15.5.10–14 | 3 | moderate ×3 |
| ≥15.0.8 | 1 | high ×1 |

只要跨过 15.5.24 这条线，23 条一次性全清。我们选的 15.5.28 是 15.5 线最新的安全回补版本，**不是最新版**。

为什么不是最新的 16.x？三个理由：

1. **升级性质不同**。安全回补只改漏洞面；大版本迁移会同时动缓存语义、请求 API、构建产物。两件事混在一个版本里，出问题时无法判断是安全修复引入的，还是迁移引入的。
2. **回补线仍在维护**。15.5 还有安全回补，说明它不是只能前进的死路。
3. **验收口径要单一**。这次的成功标准是「公告归零 + 功能不回归」，不是「顺手把技术栈推进一代」。

## 四、Electron 31 的问题是支持窗口

桌面壳比 Next 更硬：Electron 只维护最新 3 个稳定大版本。31 命中 38 条公告，覆盖 UAF、沙箱与上下文隔离绕过、自定义协议跨域读取、渲染器命令行开关注入，最高修复阈值 42.11.3。

停在 31 不是「有几个已知问题」，而是**整条线已经不在维护范围内**，后续不会再有任何修复落到它上面。

目标定在 44 而不是刚发布的 45，同样是取舍：45 把同步的凭据存储 API 标记弃用、并移除沙箱 preload 的几个 Node 全局对象，这两项都需要单独一轮迁移；44 在支持窗口内、补丁成熟，先把窗口问题解决掉，前瞻项登记到下一步。

## 五、明确不碰的东西

把边界写死，是为了让评审能判断「该不该在这个版本里出现」：

- 不做功能开发、不改 UI、不动数据模型，**没有 schema 变更，也就没有备份版本升级**；
- 不迁 ESLint / Tailwind / Vitest / Node 运行时，工具链大版本另立排期；
- 不追求全仓审计清零，只对**运行时的 critical / high** 设硬门槛；
- 不做 macOS / Linux / 32 位构建，产品形态不变。

一个底座版本最大的风险不是漏升级，而是「顺手多升了」。多升一个东西，就多一份需要单独归因的失败。

## 六、门禁数字

零新功能的版本，验收完全靠数字说话：

| 门禁 | 结果 |
|---|---|
| 全仓 critical | 6 → **3**（剩余均为开发/构建链，不进安装包） |
| 运行时框架公告 | Next 23 → **0**，Electron 38 → **0** |
| 构建链公告 | tar 消除，构建链公告 **0** |
| 类型检查 / 静态检查 | 14/14 包通过，lint 0 error |
| 单测 | 8 个包全绿（web 555 例、desktop 165 例等） |
| 浏览器端到端 | **109/109**（生产模式，10.7 分钟） |
| 桌面打包端到端 | **11/11** |
| 打包产物 | standalone 不夹带用户数据，`/api/health` 返回 200 |

## 七、为什么允许 3 条 critical 留在账上

剩下的 3 条分别在文档发布 CLI 和测试 worker 上，两者都不进入安装包。钉死它们的成本是「可能连带升级测试框架」，收益是审计页面上多一个零。

我们选择登记而不是清零，理由是可验证性：**一条不进用户机器的漏洞，优先级低于一条会进用户机器的兼容性风险。** 但这不等于放任——它们被写进基线表，一旦哪天进了运行时依赖，门禁会立刻变红。

## 八、这一版真正的产出

功能版本交付的是能力，底座版本交付的是**「以后还能继续交付」的前提**。这次留下的三样东西比版本号重要：

- 一条可重复的安全基线命令，替代一次性扫描；
- 两道打包断言（standalone 不带用户数据、安装包不缺运行时依赖）；
- 一套「先构建、再用生产模式跑全量」的验收口径。

接下来几篇分别讲框架换代的具体破坏点、standalone 追踪如何把用户数据带进产物、异步剪贴板带来的输入竞态、安装包里那条被硬编码过滤掉的依赖，以及如何把一次性审计变成可重复门禁。
