# 剪贴板变成异步之后：一次中文输入竞态和它的时序测试

桌面控制里输入中文，最稳的办法不是逐键模拟，而是「写剪贴板 → 按 Ctrl+V」。这个方案在同步剪贴板时代几乎零成本；桌面壳升级到 Electron 44 之后，它变成了一个时序问题。

## 一、现象：粘出来的是上一段内容

升级完成后，控制通道的结构性检查全部通过，键鼠调用也都回来了，但用连续输入验证时出现了丢字和错字：

- 输入第一段正常；
- 紧接着输入第二段，屏幕上是**第一段的内容**；
- 再输入第三段，屏幕上才是第二段。

典型的「后写覆盖前一次粘贴」顺序错误：读取剪贴板的那一刻，新的内容还没进剪贴板。

## 二、根因：签名没变，语义变了

Electron 44 起，剪贴板的读写方法全部返回 Promise，同步版本被移除，渲染进程也不再暴露剪贴板对象。

关键在于**这次变更没有改调用形状**。旧代码长这样：

```ts
setClipboard(text);              // 同步写入，立即返回
await keyboard.pressKey(LeftControl, V);
await keyboard.releaseKey(V, LeftControl);
```

如果 `setClipboard` 仍然是同步实现，这段代码是对的。但现在它内部变成了异步写入，调用只是**发起**了写入，不等结果就往下走。于是按键几乎必然先落地。

用一个时间轴看更清楚：

```text
t0  发起写入操作（返回 Promise，尚未完成）
t1  按下 Ctrl+V  → 系统读取剪贴板 → 读到旧内容
t2  写入完成
```

`t1 < t2` 是常态，不是偶发。所谓「竞态」，在这里其实是确定性错误——只是它看起来像随机丢字。

## 三、修复：把顺序写进类型

修法分三层，缺一层都不算完。

**第一层，改类型。** 把注入点的签名从「同步函数」改成「返回 Promise 的函数」：

```ts
export type ClipboardSetter = (text: string) => Promise<void>;
```

这一步的价值是让编译器把「忘记 await」变成错误，而不是留给运行时。

**第二层，在输入路径上串行化。** 非 ASCII 文本走剪贴板分支时，先等写入完成，再按键：

```ts
// 非 ASCII（中文等）：libnut 逐键输入不可靠，改走剪贴板粘贴
await setClipboard(text);
await keyboard.pressKey(Key.LeftControl, Key.V);
await keyboard.releaseKey(Key.V, Key.LeftControl);
```

**第三层，在注入侧真的异步。** 桌面控制启动时把 Electron 的剪贴板包一层：

```ts
const setClipboard: ClipboardSetter = async (text) => {
  await clipboard.writeText(text);
};
```

之所以要包这一层而不是直接把 `clipboard.writeText` 传进去，是为了保住注入式可测：输入模块不依赖 Electron，测试可以塞一个受控实现进来。

## 四、测试：用受控 Promise 把时序钉住

只改签名不改测试，等于把风险从「代码错」转移到「没人知道它对不对」。这次的测试不验证「有没有调用剪贴板」，而验证**调用顺序**：

```ts
it('等待剪贴板写入完成后再按 Ctrl+V', async () => {
  let finishWrite!: () => void;
  const written = new Promise<void>((resolve) => { finishWrite = resolve; });

  const typing = backend.typeText('中文');
  await Promise.resolve();

  // 写入未完成：一次按键都不许发生，否则会粘贴旧内容
  expect(calls).toEqual([]);

  finishWrite();
  await typing;
  expect(calls).toEqual(['press:LeftControl+V', 'release:V+LeftControl']);
});
```

两个细节值得说：

- 断言点放在 `await Promise.resolve()` 之后。此时 `typeText` 已经跑到第一个 await 处，如果实现漏了 await，按键调用此刻就已经记录下来了——测试会立刻红。
- 断言用「调用为空」而不是「顺序正确」。顺序断言在漏 await 时也可能碰巧通过（因为按键确实发生了，只是早了一点）；**空调用**这个断言只有真正等了才会成立。

同时保留一条对照组：ASCII 文本仍走逐键输入，且完全不碰剪贴板。两条用例合起来，才算把分支和时序都覆盖住。

## 五、为什么不用固定延时兜底

发现竞态之后，团队里出现过一种更省事的修法：写入之后睡一小会儿再按键。

```ts
setClipboard(text);
await sleep(120);               // 看起来能过
await keyboard.pressKey(LeftControl, V);
```

它在开发机上大概率能过，在慢机器、长文本、系统繁忙时就会失败——而且失败是概率性的，最难复现。更根本的是它修错了因果：代码知道「写入什么时候完成」，却选择用一个猜出来的时间代替这个信息。

正确的修法只有一种：**把「写入完成」这个事件本身 await 到。** 延时只是在赌这个事件会在给定时间内发生，而 await 是等它发生。

顺带说，延时还不能省掉——按键前的固定动作延迟是有产品语义的（给用户看到指示圈的反应时间）。两种等待必须分开：一个是给用户看的，一个是给正确性用的。

## 六、为什么中文输入非要走剪贴板

这不是偷懒。底层键鼠库的逐键输入对非 ASCII 字符不可靠：它按物理按键描述符输出，中文没有对应的键位，只能靠输入法或 Unicode 注入，两者在不同应用里行为不一致。

剪贴板粘贴是唯一跨应用稳定的路径，代价就是它依赖剪贴板状态——所以它天生对时序敏感。

这也解释了为什么这个问题只在「连续输入」时明显：单次输入时，写入往往能在用户看到结果前完成；连续输入时，第二段的按键会追上第一段的写入。

## 七、真机验证为什么主动中止

原计划是驱动记事本连续输入 20 段中文做真机确认。实际执行时卡在了窗口聚焦：

- 控制通道请求把目标窗口提到前台；
- Windows 的前台窗口锁拒绝了这次请求，通道返回 500；
- 焦点仍停在未知窗口上。

此时如果继续按键，文本会输入到**当前获得焦点的那个窗口**——可能是编辑器、可能是终端、也可能是一个正在等待输入的命令行。

所以我们选择在按键之前中止整段验证：**输入类自动化在焦点不确定时，正确动作是停，不是重试。**

异步顺序交给单测保证，原生模块加载由「控制通道就绪」的结构性检查保证，剩下的真实粘贴并入人工手测。这不是完美的覆盖，但是安全的覆盖。

## 八、教训

| 教训 | 这次的具体形态 |
|---|---|
| API 变异步必须重排时序 | 同步签名保持不变，语义从「已写入」变成「已发起」 |
| 时序要写进测试，不能只改签名 | 受控 Promise + 「未 resolve 时调用为空」 |
| 类型是第一道门禁 | `Promise<void>` 让漏 await 变成编译错误 |
| 焦点不确定时不执行输入 | 前台锁拒绝后主动中止，避免误输入 |
| 结构性检查不等于行为验证 | 「控制通道就绪」只证明模块加载成功 |

一句话总结：**把一个同步 API 改成异步，改的不是返回值，是所有调用点与它之间的因果关系。** 谁承担这个因果，谁就必须被测试覆盖。
