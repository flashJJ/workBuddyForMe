# 失败之后的重试，为什么应该新建分支而不是重启

分支失败时，界面上最诱人的按钮是「重试」。

用户理解的重试很简单：刚才那次没成功，再来一次。但系统里的「再来一次」有好几种实现，最容易的是把状态从失败改回运行中，让原分支重新跑。代码量最少，用户点一下就能看到它重新动起来。

我们的桌面 AI 应用是本地优先的助手，分支会话有独立的子会话、留痕的事件与可核对的回传。在这套结构里，原地重启会同时破坏三样东西：终态的不可逆、证据的可追溯、准入的准确性。

## 原地重启破坏了什么

第一，终态不再是终态。状态机约定分支进入成功、失败、取消、中断或预算超限后，不能再回到运行中。这条约定不是形式主义，它是回传、归档、预算结算的共同前提。允许失败分支复活，所有「已结束」的判断都要加例外。

第二，证据会被覆盖。失败分支有一份证据：错误摘要、真实用量、可能的部分产物。原地重启会清空证据重新生成；新结果出来后，上次为什么失败就查不到了。用户失去了对比两次运行的能力。

第三，运行进程已经不存在。失败往往意味着运行器退出，子会话里可能留下半截消息。把状态改回运行中，系统会声称一个不存在的进程还在跑；下一次重启收敛又会把它改回中断，用户看到状态来回跳。

第四，预算与并发计数会漂移。失败分支的预留已经归零，用量已经结算。原地重启相当于跳过准入，不检查当前并发、深度、子节点与预算，直接再花一笔钱。

所以问题不是「能不能改状态」，而是「改了之后还有没有一套自洽的解释」。

## 重试 = 新建分支

这一轮采用的定义很直接：重试是以旧分支为来源，新建一个分支。

新分支继承三样东西：父会话、目标、标题。它有自己的子会话、自己的状态、自己的事件与回传。旧分支完全不改：状态保持失败，证据保留，子会话保留，归档标记保留。

新旧之间只留一条引用：响应里的 `retriedFrom` 指向旧分支 id。界面上不强调这条引用，但它让排查时可以顺着找到上一次尝试。

### 为什么标题也继承

标题是用户对任务的命名，不是运行结果的一部分。重试同一个目标，沿用标题最符合直觉，也避免面板里出现一堆「未命名分支」。

允许重名是有意的。用户可能连续重试三次，三次标题相同但时间与状态不同；面板按创建时间排序，用户仍能区分。想改名的，面板本来就提供重命名入口。

### 为什么新分支不复制消息

子会话不是父会话的快照。新分支从目标开始独立生长，不继承旧子会话的消息。旧子会话可能停在半截，把它复制过来会让新运行从一段失败上下文继续，模型会受污染。

需要参考上次过程时，用户打开旧分支即可。重试是重新开始，不是接着跑。

## 复用准入，而不是绕开准入

新建分支必须走现有的创建流程。这条流程里有五道校验：环检测、深度、每父分支数、并发、会话树预算。

复用带来两个好处。第一，重试不会成为后门：并发满了、父会话分支数到顶、树预算不够，重试同样被拒绝，返回 422 与明确原因。第二，规则只有一份：新增入口如果自己写一套检查，迟早会和主流程漂移。

启动阶段还会再复检一次并发上限。创建成功不等于能立刻运行；如果此刻并发已满，新分支会停在排队，等前面的分支结束。这不是失败，是正常的排队语义。

### 只允许终态重试

接口的前置条件是分支必须处于五种终态之一。排队、运行中、等待中的分支调用重试会直接返回 422。

理由很实际：运行中的分支已经有进程、有预留、有事件流。再建一个同目标的分支，等于用户无意中把并发翻倍；而「重启原分支」又回到前面说的四个问题。

排队分支如果不想等，正确动作是取消，不是重试。取消之后再重试，语义清晰：旧的结束，新的开始。

## 一次请求里发生什么

伪代码如下：

```text
source = get(branchId)
if source.status not in TERMINAL:
    reject 422
result = create(source.parentConversationId, {
    goal: source.goal,
    title: source.title,
    autoStart: true
})
return 201 {
    branch: result.branch,
    childConversationId: result.childConversationId,
    retriedFrom: source.id
}
```

`create` 内部完成准入、子会话创建、分支关联、事件写入与自动启动。重试入口只做两件事：校验来源是终态，转交参数。

这也是为什么重试逻辑放在接口层而不是 core 服务层：core 已经有创建入口，再包一层「重试创建」只会重复实现校验与事务。

## 界面上的分寸

终态分支卡片才显示「重试」。运行中的卡片显示「取消」，排队中的卡片显示「启动」与「取消」。按钮旁边有提示：重试将新建分支。

这句提示不是多余的。用户看到「重试」，默认理解是「原来那条继续」；系统做的是「再开一条」。不写清楚，用户会在面板里看到两条状态不同的同名分支，以为自己点坏了。

失败、取消、中断、预算超限都提供重试。成功分支也提供——用户可能想用同样目标再跑一次，比较两次结果。重试不判断「值不值得」，只判断「能不能开始」。

## 刻意不做的事

不做自动重试。失败后自动再跑一次，会把预算、并发与图结构一起放大；连续失败时用户甚至不知道系统已经偷偷跑了三轮。

不做递归重试。重试产生的分支可以再重试，但必须由用户发起；自动递归会让准入的深度限制形同虚设。

不做「从失败处继续」。续跑需要保存运行器的中间状态，这套编排器目前只有最终结果，没有可恢复的检查点。强行续跑只能靠猜。

## 验证

接口与界面测试覆盖四个断言：排队分支重试返回 422；已取消分支重试返回 201，`retriedFrom` 指向旧分支；旧分支状态仍为已取消；父会话分支数达到上限时重试返回 422。

端到端覆盖了取消、重试与回传节点的组合，确认新分支独立出现，旧分支保留终态。

这些断言共同证明一件事：重试是创建，不是复活。
