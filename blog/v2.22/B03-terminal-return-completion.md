# 中断、取消、超预算：让每个终态都留下可核对的回传

一个分支被取消之后，父会话应该看到什么？

最自然的回答是「状态变成已取消」。但如果只有状态，用户看到的只是一个标签。这个分支跑过什么、有没有产物、消耗了多少，全部没有。更糟的是，取消和失败在界面上长得差不多，用户分不清是自己主动停的，还是系统坏了。

我们的桌面 AI 应用是本地优先的助手，分支会话允许父会话派生多条子会话并行推进。分支进入终态时，父会话拿到的是一份证据卡片，而不是自动插入的聊天消息。问题在于，这份证据长期只覆盖了成功和失败。

## 终态不止两种

状态机里有五种终态：

- 成功：运行器正常结束，有内容、有真实用量；
- 失败：运行器报错，有错误摘要；
- 取消：用户在排队阶段主动停止，还没开始运行；
- 中断：应用重启后收敛残留的运行中分支，原进程已经不存在；
- 预算超限：结算时发现会话树用量越过上限。

后三种都写入了状态，却没有写入回传。父会话于是面对一个「有终态、没交代」的分支：卡片还在，摘要空白，产物空白，用量空白。

这不是展示问题。回传是父会话判断下一步的依据。没有回传，用户只能打开子会话自己看；如果子会话还没开始运行，就什么都看不到。

## 补齐的目标：终态必须可识别

补齐的原则只有一句：每一种终态都要同时留下状态与回传，而且两种终态不能在语义上混在一起。

具体落到证据结构：

| 终态 | 状态 | 回传 | 摘要 | 用量 | 需核对 |
|---|---|---|---|---|---|
| 成功 | 写 | 写 | 运行结果 | 真实值 | 是 |
| 失败 | 写 | 写 | 错误信息 | 真实值 | 是 |
| 取消 | 写 | 写 | 空 | 空 | 是 |
| 中断 | 写 | 写 | 空 | 空 | 是 |
| 预算超限 | 写 | 写 | 已产生内容 | 真实值 | 是 |

「需核对」是固定值，不是根据结果质量动态计算。分支的结论本来就需要人来判断，系统不替用户背书。

### 空结果不等于失败

最容易被写错的一处，是把空摘要当成失败。

取消和中断确实没有运行结果：取消发生在运行之前，中断发生时原进程已经消失。它们不是错误，只是「没有产出」。如果给它们补一个「运行失败」的摘要，用户会去排查一个根本不存在的故障。

所以空结果的证据保持空摘要、空产物、空用量，状态原因单独写明：取消写「分支已取消」，中断写恢复原因。界面文案也分开：终态空摘要显示「无运行结果」，运行中的空摘要显示「暂无摘要」。

失败则不同。失败有错误信息，有运行器返回的用量，摘要里写的是错误原因。它和空结果共享「需核对」，但不共享语义。

## 三条写入路径

补齐不是在一个地方加一个字段，而是把三条原本绕过回传的路径接回同一条出口。

第一条是排队取消。分支还在队列里，用户点取消，状态改为已取消，预留归零，然后写状态事件与回传事件。事件顺序是创建、状态、回传，父会话能从上到下读到完整过程。

第二条是重启收敛。应用启动时扫描仍在运行或等待的分支，把这些分支改写为已中断，释放预留，补一份空结果证据，再写状态与回传。这里的「等待」是历史数据里可能存在的状态，当前运行器不会再产生它。

第三条是预算熔断。运行结束拿到真实用量后，如果会话树已用加预留超过上限，原本的成功结果会被改判为预算超限。它保留已产生的内容摘要与真实用量，只是状态与原因变了。

三条路径的入口不同，出口相同：分支表落状态与证据，事件表落状态与回传。父会话只认这一个出口。

## 为什么不直接插一条消息

最像「及时反馈」的做法，是往父会话转录里插一条「分支已取消」。技术上不难，产品上是错的。

父会话的主线是用户和助手共同维护的对话。自动插入系统消息会打断这条线，也会让分支结果看起来像主线结论。分支可能只完成一半，可能是错误的方向，甚至可能什么都没跑；把它包装成一条正常消息，等于替用户做了判断。

证据卡片则明确是「外部结果」：它标注来源分支、状态、是否需要核对，不进入消息序列。用户可以看，可以忽略，也可以据此重新派生。

### 回传不是审计

证据也不是越全越好。摘要截断到 4000 字，产物从子会话的工具轨迹里尽力提取并去重，提取不到就留空数组。没有为了「完整」去扫描全部消息，也没有把工具原始输出整段塞进证据。

回传的用途是让用户快速判断「这个分支值不值得打开」，不是替代子会话本身。细节仍然在子会话里。

## 失败隔离与预留

三条路径都要处理预留。取消和中断直接归零；预算超限在结算时归零。预留不清，会话树会一直显示有一笔「未来可能花掉」的额度，后续分支准入会被错误拒绝。

失败隔离同样重要。一个分支取消或超预算，只影响它自己：同树其他运行中的分支继续跑，父会话状态不变，子会话历史保留。终态是分支级的，不是会话树级的。

## 验证

单测覆盖三条路径：

1. 重启收敛把运行中与历史等待状态改写为中断，产生两条回传，证据为空结果；
2. 排队取消产生创建、状态、回传三段事件，摘要为空；
3. 结算超预算改判为预算超限，预留为零，写一条回传。

端到端另有一例：排队取消后状态为已取消，证据摘要为空、需核对为真，过程图出现回传节点；从该分支重试会新建分支，旧分支仍是已取消。

## 边界

这一轮没有为「没有运行结果」生成任何占位内容，也没有把中断自动转成重试。中断是中性的终止，下一步由用户决定。

同样没有做回传汇总：父会话不会自动把多条证据合并成一段结论。多条分支的结果如何取舍，仍然是人的工作。
