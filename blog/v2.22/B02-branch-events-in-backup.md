# 为什么分支事件也要备份：投影、顺序与截断

备份最容易让人误判的一点，是「表里有数据」不等于「恢复后能看到同样的东西」。

我们的桌面 AI 应用是本地优先的助手。分支会话有两份持久化数据：分支关系在分支表，分支的创建、启动、状态变化、回传在会话事件表。备份过去只导出前者，恢复后关系完整，事件为空。过程图从事件投影出来，于是车道、子会话节点、回传节点全部消失。

用户看到的不是一条报错，而是一张突然变简单的图。这比报错更难排查。

## 事件不是日志，是投影的输入

很多系统把事件当审计流水：主数据对了，日志缺几条可以接受。分支这里恰好相反。

分支关系回答「树长什么样」：谁是父、谁是子、目标是什么、当前状态是什么。事件回答「树怎么长成这样」：什么时候创建、什么时候启动、哪一刻进入终态、回传证据写了什么。

过程图不是分支表的直接渲染，而是事件的投影。少了事件，图就只剩下一个没有过程的骨架。

所以备份要带走的是投影的输入，而不是投影的结果。存一张渲染好的图看起来更直接，但布局规则、节点命名、折叠策略都会变；把某一版的渲染结果冻进归档，恢复出来的就是一张无法再解释的旧图。

## 为什么不并进分支文件

最省文件数量的做法，是把事件塞进已有的分支快照文件。结构上做得到，维护上不划算。

分支快照是「当前状态」，事件是「按时间增长的流」。两者的写入频率、体积增长和恢复规则都不同：快照可以覆盖，事件只能追加；快照按分支一条，事件按分支几百条；快照恢复失败可以跳过单条，事件恢复失败要保留已成功的部分。

合并之后，截断规则会和快照字段纠缠：一个分支被截断，同一文件里的关系记录要不要跟着标记？恢复时先读哪一段？这些问题没有技术难度，却会让每次改动都多一层判断。

独立文件把边界切干净：`branch-events.json` 只装分支作用域的事件，分支文件只装关系。恢复端可以分别计数、分别跳过、分别告警。

## 文件里装什么

事件文件的结构保持最小，只够恢复使用：

```json
{
  "schemaVersion": 1,
  "truncated": false,
  "events": [
    {
      "scope": "branch",
      "scopeId": "br-1",
      "seq": 1,
      "type": "branch_created",
      "payload": {},
      "createdAt": "2025-01-01T00:00:00.000Z"
    }
  ]
}
```

只导出 `scope = branch` 的事件，`scopeId` 是分支 id。事件保留类型、负载、创建时间和原序号，不导出数据库自增主键之外的内部字段。

备份清单里同步增加两个可选字段：事件条数与是否截断。预检结果则把事件条数作为一项固定统计，旧归档没有这个文件时按 0 处理。

这里的关键是「可选」。备份格式仍停留在第 7 版，新字段是加法；旧版本读到新归档会忽略未知字段，新版本读到旧归档则把缺失当成空。兼容靠的是缺省语义，不是版本分支。

## 恢复顺序：会话、分支、事件

恢复顺序不是文件在归档里的排列顺序，而是依赖顺序。

事件负载引用分支 id，分支又引用父会话与子会话。所以必须先恢复会话，再恢复分支关系，最后恢复事件。顺序反了，事件写入时找不到所属分支，只能整条丢弃。

恢复事件时还有三道过滤：作用域必须是分支；`scopeId` 必须在刚恢复的分支表里存在；单条写入失败只跳过这一条，不阻断整档恢复。

第一道防的是脏数据混入，第二道防的是跨档引用，第三道防的是单条损坏拖垮整体。三条都失败时，恢复统计里会留下跳过计数，用户至少知道有东西没回来。

### 序号重新分配，时间保留

恢复时不保留原事件 id，也不保留原序号。事件仓储的追加接口会为每条事件重新分配序号，数组顺序就是恢复后的先后顺序；创建时间保留原值。

这是有意的取舍。序号是库内排序细节，不是业务标识；跨库恢复时强行复用旧序号，反而可能和已有事件冲突。对外稳定的是「分支 id + 顺序」，图和测试都不依赖原始自增 id。

追加接口同时维护全文索引，因此恢复出来的事件不仅能投影，也能被检索。

## 截断：为什么是每分支两百条

事件是只增不减的流。一个长任务的分支可能积累几百上千条事件，全量导出会让归档膨胀，恢复也会变慢。

上限按「每个分支最近两百条」截断，而不是全档总条数。按分支截断保证每个分支至少有一段完整尾部：创建帧可能在很早以前，但状态流转与回传通常在尾部，恢复后图仍然能表达「它最后怎么了」。

按总条数截断则会出现另一种偏差：先遍历到的分支占满额度，后面的分支一条不剩。图会变成一半有过程、一半是空壳，比统一截断更难解释。

超过上限时，事件文件与备份清单都标记 `truncated = true`。恢复端不需要为截断做特殊逻辑，它只是少了一些早期事件；图会缺早期节点，但不会报错。

跨分支的总量不设硬上限，最终受归档体积约束。这是刻意的：单个归档有 500 MB 的总体限制，再叠一层事件条数上限，只会让规则更难解释。

## 旧档与坏档

旧备份没有这个文件，恢复结果是导入 0、跳过 0，不告警、不报错。缺失是正常的历史状态，不是错误。

文件存在但 JSON 损坏，或顶层不是对象、`events` 不是数组，同样按 0 处理。恢复是用户找回数据的最后一步，任何一处坏数据都不应该让整档恢复中止。

单条事件字段不合法、引用分支不存在、写入抛错，只影响这一条，计入跳过。能恢复的先恢复，恢复不了的留下计数。

## 验证

备份相关测试覆盖三个层面：导出清单的事件条数与截断标记、恢复后的分支数与事件数、旧档缺文件与缺失分支的跳过行为。

| 场景 | 断言 |
|---|---|
| 正常导出 | 清单事件条数正确，未截断 |
| 正常恢复 | 两个分支的事件按分支分别落库 |
| 旧档恢复 | 事件导入与跳过均为 0 |
| 异常事件 | 缺失分支、非分支作用域整条跳过并计数 |

备份导出的三个测试文件共 21 个用例通过。端到端另有一例：导出后恢复，清单事件条数不少于三条，恢复统计同样不少于三条。

## 取舍

这一轮没有把事件做成可查询的独立归档，也没有做增量备份，更没有为恢复重建所有二级索引。目标是让一次完整的导出与恢复能自洽，而不是把备份做成同步系统。

事件轨的价值不在体积，而在恢复后的解释力。一张能说明过程的图，比一堆只能证明「关系还在」的行更有用。
