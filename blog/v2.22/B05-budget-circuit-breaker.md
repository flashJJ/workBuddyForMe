# 预算触顶之后：为什么熔断发生在结算，而不是流式中

并行任务最贵的不是同时开几个分支，而是没人知道它们一共花了多少。

我们的桌面 AI 应用是本地优先的助手，分支会话共享一棵会话树的 Token 预算。早期只在准入阶段检查：派生之前算一算，已用加预留是否达到上限，达到就拒绝。这条规则能挡住「明知不够还要开」的请求，却挡不住「开着开着超了」的运行。

一个长任务开始时有额度，跑到一半把整棵树烧穿，结束时系统仍然把它记成成功。用户看到的是一份漂亮的回传，账单上却是一笔超出上限的消耗。

## 两道闸，而不是一道

预算控制需要两个时点。

准入时点回答「能不能开始」：会话树已用、已预留、并发数、父子深度、每父分支数，任何一项不满足就不创建。拒绝是干净的，不产生任何行，也不花任何 Token。

结算时点回答「实际花了多少」：运行器结束时拿到真实用量，重新计算会话树的总消耗，再决定这次运行是否越界。

只做第一道，等于只在起跑线量体重；只做第二道，等于允许所有人先跑完再算账。两道都要有，而且判断依据不同：准入看的是「还有没有名额」，结算看的是「有没有真的超」。

## 为什么不在流式中途叫停

最直觉的熔断是：运行时每收到一段增量，就检查一次预算，超了就中止。

这一轮没有这么做，原因不是不想，而是拿不到可靠的数据。当前编排器只在结束事件里提供用量；流式过程中没有逐段 Token 计数。没有增量数据，所谓「实时熔断」只能靠字符数估算，估出来的数字既不能结算，也不能向用户解释。

强行按估算中止还有两个副作用。第一，中止会留下半截内容，这部分内容算不算结果、要不要写回传、用量怎么记，都会变成新的边界问题。第二，估算偏差会让同一段内容在不同分支上得到不同的预算结论，用户无法复现。

所以在现在的数据条件下，可靠的做法是把熔断放在唯一能拿到真实用量的地方：结算。

### 结算时怎么改判

运行结束，先按正常路径拿到结果与用量，再重新聚合会话树：根会话加全部子会话的已用 Token，加上仍在运行分支的预留。

如果这次结果是成功，且已用加预留超过上限，就把状态从成功改判为预算超限。不是丢弃结果，而是保留：

- 内容摘要照常截断保留，用户能看到已经产出的部分；
- 真实用量照常写入，账单可核对；
- 状态原因写明「会话树 Token 超限：已用多少 / 上限多少」；
- 预留归零，结束时间补齐；
- 状态事件与回传事件都按预算超限写入。

改判只发生在成功结果上。失败的分支仍然是失败，取消的分支仍然是取消；预算超限是「本来成功但越界」的专用终态，不覆盖其他错误。

## 预留归零与失败隔离

结算时必须把 `reservedTokens` 归零。预留是「未来可能花掉」的占位，终态之后它不再代表任何未来；不清零，会话树会长期显示一笔虚拟占用，后续分支会被错误拒绝。

归零只影响当前分支。同树其他运行中的分支继续持有自己的预留，继续跑；父会话状态不变；已经结束的分支证据不改。预算超限是分支级终态，不是把整棵树停掉。

这一点和准入拒绝不同。准入拒绝发生在创建之前，根本不会有运行；结算熔断发生在运行之后，已经产生的消耗必须如实记账。两者都叫「预算控制」，但一个是预防，一个是善后。

### 为什么允许「超一点」

结算熔断天然允许越界：往往要等到某个分支结算时，才发现整棵树已经超了。越界幅度受同时在跑的分支数约束，不会无限增长；但并发分支也可能叠加，所以它不是精确到一分钱的刹车。

这不是理想状态，但在没有增量用量的前提下，它是可解释的上界。用户能接受「最后一次超了，系统明确告诉你超了多少」，不能接受「系统一直说还有额度，最后账单翻倍」。

换句话说，结算熔断牺牲的是及时性，不是准确性。它不能在花钱的过程中踩刹车，但能在花钱结束后把账认下来，并把状态、原因和用量一次写清。

以后运行器如果能提供增量用量，这套逻辑可以升级成两层：流式中途按阈值预警或中止，结算再做最终对账。当前版本把升级点留在用量来源，而不是把估算逻辑塞进结算。

## 状态原因要能回答三个问题

预算超限的 `statusReason` 至少要说清三件事：是谁超了、超了多少、上限是多少。

「会话树 Token 超限：已用 X / 上限 Y」这一句同时回答了后两个问题。第一个问题由分支本身回答：证据卡片指向具体分支，父会话知道是哪条子任务把树推过线。

没有这句话，用户只能看到一个「预算超限」标签，既不知道差多少，也不知道该调高上限还是缩小任务。可解释的失败，比一个干净的状态码更有用。

可解释也意味着不隐藏结果。预算超限的分支仍然保留已经产出的内容，用户可以选择采用、继续派生，或者放弃。

## 和准入的配合

同一套上限在两条路径上复用。设置页调整会话树预算后，准入立即按新值判断，结算也按新值改判；不存在「准入用旧值、结算用新值」的分裂。

启动时还有一次预留：取剩余额度与固定预估值中的较小者，写进分支的预留字段。固定预估是 1000 Token，不精确，但它表达的是名额而不是预测。预留的意义是让并发分支不能同时假设自己拥有全部剩余额度。

准入、预留、结算三层合起来，才构成一个能解释的预算系统。少任何一层，都会出现「大家都以为自己还有钱」的时刻。

## 验证

单测构造了一个已经接近上限的会话树，让分支正常成功结束，然后断言：状态变为预算超限，预留为零，只写一条回传，证据里保留摘要与真实用量。

端到端与界面侧则验证预算超限和取消、中断一样出现在终态卡片上，有状态原因，有「需核对」标记，不会退回运行中。

## 边界

这一轮不做流式中止，不做跨会话树的全局预算，也不做按供应商或模型分别计价。预算的单位仍然是 Token，范围仍然是根会话所在的树。

也不做自动调高上限。超限之后是用户决定继续加预算、缩小任务还是放弃；系统只负责把账算清。
