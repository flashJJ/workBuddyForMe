# 发送前就提示：草稿意图判定的边界

任务模式建议原先只出现在上下文面板里，而面板是一轮结束之后才更新的。

用户看到“本轮适合任务模式”的时候，消息早就以聊天模式发出去了。这个提示来得太晚，等于没有。

## 一、把判断挪到发送之前

真正有用的时刻，是用户在输入框里打字的时候。

要做到这一点，需要让 web 端能在本地判断草稿的意图。为此我们做了一次下沉，而不是复制。

## 二、规则下沉到 shared 包

意图识别原本在 core 包，属于服务端逻辑。web 端要用，只有两条路：复制一份规则，或者为一次本地判断起一个接口。

两条都不好。复制会分叉，接口会引入延迟和额外失败面。

于是把纯函数下沉到 shared 包：输入是文本和两个可选信号（是否带图、是否绑定知识库），输出是完整的意图对象。

```ts
detectTurnIntent({ text: draft }).suggestedTaskMode
```

零模型调用、无副作用、可在浏览器里同步执行。core 包改为从 shared 包引入，行为不变，但只有一份实现。

## 三、输入区的两种状态

- 未开启任务模式，且草稿命中：显示一行浅色提示，后面跟一个“切换”按钮；
- 已开启任务模式：提示消失，改为任务模式自身的说明文案。

判定用 memo 包住，依赖只有草稿文本和开关状态。空草稿不判断，避免刚清空输入就闪一下提示。

## 四、为什么不用模型

三个理由。

第一是成本：每敲一个字都调一次模型，无论本地还是远程都不合理。

第二是延迟：建议必须跟手，慢半拍的提示不如不提示。

第三是可解释：规则命中什么，用户点开一看就懂。模型的判断很难用一句话说清。

规则会误判，但误判的代价只是多一行提示，用户不理它就行。

## 五、边界：发送前只建议，发送后才是契约

这两件事必须分开。

发送前：纯本地、不写事件、不改会话、不切换模式。输入框里的一切都是建议。

发送后：core 包重新识别一次，把结果写进回合事件，由它决定上下文配额和行为提示是否注入。

两处用的是同一份规则，但职责不同。前端不能替代后端做记录，因为后端还要处理图片、知识库绑定等其他信号。

这里有一个刻意保留的差异：同一段文字，发送前和发送后的判断可能不完全一致。我们接受它，因为发送前的提示本来就只是提示。

## 六、提示而非替用户决定

不自动切换的理由在上一篇已经说过。发送前尤其需要克制——用户正在组织语言，界面此时自作主张地变形，比任何误判都更打扰人。

## 七、测试

输入区测试覆盖三件事：命中时出现提示、点击后切换为任务模式、已开启时不再提示。

shared 包的规则测试覆盖建议为真、建议为假与回落三种情况，保证下沉前后行为一致。

## 结果

现在，一句话还没发出去，用户就知道系统把它看成了什么。
