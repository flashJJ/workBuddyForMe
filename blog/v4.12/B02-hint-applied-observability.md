# 注入了什么，为什么要能看见

上一轮排查里，最刺眼的一条是：意图提示已经注进主智能体，但没有任何地方能看到它是否发生了。

这一篇讲怎么把这个“看不见的注入”变成一个可读的字段。

## 一、一段一直在跑的提示

意图识别完成后，有一层逻辑会根据意图类型，为主智能体拼一段行为提示。比如工具任务会提示按步骤推进，追问会提示衔接上文。

当来源是规则回落、或置信度低于阈值时，这段提示不注入。这是设计，避免用一次误判去误导整轮回答。

## 二、只有一半状态可见

上下文面板能看到：意图类型、置信度、来源（规则 / 分类器 / 回落）、命中信号。

这些都是“判断”，不是“动作”。

用户真正想知道的是：判断之后，系统实际做了什么。

## 三、做法：一个可选布尔

在共享契约里加一个可选字段：

```ts
hintApplied: z.boolean().optional() // 本轮是否注入了行为提示
```

意图阶段在写事件时，用同一段拼接函数的结果判断：

```ts
hintApplied: buildIntentHintBlock(intent) !== null
```

关键是不要复制判定条件。面板看到的值，和主智能体拿到的值，必须来自同一次调用。否则两边各写一份阈值，迟早会分叉。

## 四、为什么不是“注入了哪段文本”

把提示原文写进事件，看起来信息更多，实际有三个代价：

- 内部提示词会进入可被导出的日志；
- 文案一改，历史事件的语义就漂移；
- 事件体积随提示长度波动。

布尔值是一个稳定契约，回答的恰好是关键的那一个问题：注入了，还是没注入。

## 五、为什么必须可选

事件日志有历史。旧事件没有这个字段，如果新增必填，历史解析会直接失败，面板从“信息少”变成“打不开”。

可选字段还有一层好处：面板可以按存在性渲染。字段缺失时不渲染那一行，不补 `false`。

缺失是事实，`false` 是断言。把事实伪装成断言，排障时会误导人。

## 六、面板上的两句话

- 已注入：本轮判断置信度足够，主智能体收到了行为提示；
- 未注入（低置信度）：本轮走了回落路径，行为来自默认策略。

两句话都不带操作按钮，也不提供“手动注入”。观测的边界是不改变行为。

## 七、测试要覆盖真假两态

core 层断言两件事：高置信度回合记录为真，回落回合记录为假。

web 层断言两件事：字段存在时渲染对应文案，字段缺失时整块不渲染。

这四条合起来，才把“字段本身正确”和“展示不会因旧数据崩溃”同时锁住。

## 八、未注入不是错误

回落是保护机制：宁可让主智能体按默认策略走，也不要拿一个低置信度的判断去约束它。

所以文案用的是“未注入（低置信度）”，而不是“注入失败”。失败暗示系统出了问题，而这里系统运行得完全正确。

## 结果

现在一轮对话结束后，用户可以自己回答“意图有没有生效”，不用再靠开发者翻日志。
