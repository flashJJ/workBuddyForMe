# 清空记忆，为什么只能全清

记忆面板原来只有一个清空按钮。点下去，二次确认，然后一条不剩。

问题是，记忆是有状态的：活跃、已归档、已被取代。用户真正想删的，通常是那些已经归档的旧条目。

## 一、一个不合身的按钮

“全清”在语义上很简单，在体验上很粗暴。

用户为了删掉几条不再需要的归档记录，被迫把正在生效的记忆一起清掉，再靠后续对话重新建立。这个代价和需求完全不匹配。

更尴尬的是，接口早就支持了。

## 二、接口支持，面板没传

清空接口的请求体里一直有一个可选的状态字段。面板从头到尾只调用全量清空，从不带它。

于是能力存在，入口不存在——和上一批断点是同一种形状。

## 三、契约：可选参数，缺省行为不变

做法很克制：

```ts
{ status?: 'active' | 'archived' | 'superseded' }
```

不带状态，走原来的全量清空；带状态，只清这一类。

没有新建接口，因为这是同一个危险动作，只是范围不同。拆成两个接口，权限、二次确认、审计口径都要写两遍，迟早出现不一致。

## 四、级联清理不止一张表

一条记忆散落在五个地方：主表、关系边、全文索引、向量索引、审计事件。

按状态清理必须在同一事务里完成，顺序是：

1. 先按状态查出 id 列表；
2. 逐条删关系边；
3. 逐条删全文索引；
4. 逐条删向量（先确认向量表存在）；
5. 按状态删审计事件；
6. 按状态删主表。

先收集 id 再动手，是因为主表一删，就再也查不出这次操作的范围了。

## 五、事务边界为什么比单条删除更严

单条删除是“先提交主表事务，再清索引”，因为只有一条，失败后重试成本低。

按状态清理可能涉及成千上万条，中途失败的后果是大量悬挂索引：主表已经没有这条记录，全文索引还留着，搜索时会召回到不存在的内容。

所以索引清理也被放进了事务。

## 六、面板上的三处细节

- 按钮文字是“清空已归档”，不是“清理”，把范围写进名字；
- 归档数为零时禁用，并用 title 说明原因，而不是点了才告诉用户没有东西可删；
- 保留二次确认，使用危险样式。

禁用条件看的是数量，不是猜测用户意图。

## 七、这一版没做的

没有做按时间范围删除，没有做按来源删除，也没有做回收站。

这些都需要先回答“删错了怎么恢复”。在没有恢复机制之前，扩大删除维度只会放大风险。

## 八、测试

core 层断言：只删除指定状态，其他状态一条不少，索引与审计同步清理。

web 层断言：按钮只发送 `status=archived`；不带状态的全清路径仍然可用。

## 结果

同一个接口，多了一个可选参数，用户少了一次不必要的损失。
