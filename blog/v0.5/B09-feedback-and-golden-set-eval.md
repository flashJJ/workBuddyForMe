# 质量闭环：消息级 👍/👎 的最小设计，与一条手跑的 golden set 评估基线

## 问题：记忆好不好，谁说了算

在我们这个本地优先的桌面助手里，记忆链路做到这里已经全通：提取、去重、召回、遗忘。但一个元问题悬着：**这套东西的质量怎么度量？** 改一次提取 prompt、换一个嵌入模型、调一次召回阈值——效果是变好还是变坏？

单测回答不了这个问题。单测 mock 掉模型，测的是「代码逻辑对不对」，不是「记忆质量好不好」。我们用两个互补的机制回答：**消息级反馈（👍/👎）收集真实使用的质量信号，golden set 评估提供发版前的回归基线**。一个是持续的、被动的、来自真实分布的；一个是定点的、主动的、来自受控用例的。

## 反馈：消息属性，不是独立实体

👍/👎 的设计从一个数据归属问题开始：反馈存哪？

选项 A：独立 feedback 表（message_id + value + created_at）。选项 B：**加在 messages 表上**。我们选了 B（一次加列迁移）：

```sql
ALTER TABLE messages ADD COLUMN feedback TEXT;      -- up | down | NULL
ALTER TABLE messages ADD COLUMN feedback_at TEXT;
```

理由一句话：**👍/👎 是消息不可分割的评价属性，不是独立实体**。

这个归属决定带来一串免费的正确性：

**备份自动携带**。备份的 conversations 轨经 mapMessage 序列化消息，加列后反馈自然进备份、恢复时原样写回——零新增导出代码，只加了一条回归断言防漂移。如果选了独立表，备份轨要加第五个轨道，恢复要做反馈与消息的 join 重建，全是多余的复杂度。

**查询零 join**。消息列表渲染时反馈状态随行返回，前端不需要第二次查询。

**删除语义自洽**。消息删除（会话删除级联）时反馈随之消失，不会留下孤儿反馈行。

行为设计的两个细节：

**仅助手消息可反馈**。用户消息没有「质量好不好」的问题，路由层 422 拒绝对用户消息的反馈请求。反馈按钮也只渲染在 assistant 消息上。

**再点取消**。点 👍 后再点 👍，反馈清除（feedback 回 NULL）。反馈不是选票而是信号——用户改主意是常态，「取消」和「切换」必须和「设置」一样便宜。`message-feedback.tsx` 里三个状态（无/赞/踩）互斥切换，PATCH 路由接受 `null` 值清除。

归属校验值得一提：PATCH `/api/conversations/[id]/messages/[messageId]/feedback` 要验「消息属于该会话、会话属于当前数据空间」，404/422 边界各有测试。本地应用也要做这个校验——API 边界的一致性不和部署形态讨价还价。

## golden set：12 条种子记忆 + 12 个跨会话用例

评估基线（`memory-golden.json` + `eval-memory.mjs`）的结构：

**种子记忆**：12 条覆盖三类（fact/preference/event）、不同重要性、不同表述风格的记忆。例如「用户是不吃香菜的」「用户偏好简洁直接的回答风格」「用户 2026 年 3 月要晋升答辩」。

**召回用例**：12 个跨会话问句，每个挂预期命中的记忆 + 关键词。刻意覆盖了「问法与记法的语义鸿沟」——记忆是陈述句「用户不吃香菜」，用例是问句「我不吃什么蔬菜？」「帮我看看这份菜单有什么我不能吃的」。

执行流程：

```text
node scripts/eval/eval-memory.mjs --reset-memories
  1. --reset-memories 显式清空记忆库（破坏性，必须显式传入）
  2. 写入 12 条种子记忆（走真实嵌入管线）
  3. 逐用例新开对话发问题（走真实 SSE 流）
  4. 关键词命中判定：回答里是否出现预期关键词
  5. LLM-as-judge：评委模型对回答质量打 0-2 分
  6. 输出命中率 + judge 均分，可选 --out 写 JSON
  退出码：基础设施错误 = 2；关键词命中率 < 70% = 1；否则 0
```

**为什么两个判据都要**：关键词命中测「记忆有没有影响回答」（召回 → 注入 → 使用的全链路），judge 测「回答质量好不好」（注入的记忆有没有被得体地使用）。B07 的零召回事故里，关键词全灭但错误原因是阈值；而另一次调试中关键词全中但 judge 低分——记忆召回了，但模型在回答里生硬地罗列「根据我的记忆，你……」，这是 prompt 问题不是召回问题。两个判据的失败模式不重合。

**--reset-memories 为什么必须显式**：评估要先清空记忆库再写种子，否则用户真实记忆会污染用例（真实记忆可能命中用例问句，造成假阳性）。破坏性操作必须显式声明，这个约定从备份恢复功能贯穿到现在。

## LLM-as-judge：用模型评模型，小心什么

评委设计：让对话模型（同一个 qwen2.5:7b）对「问题 + 相关记忆 + 助手回答」打分：

```text
0 分：未使用记忆 / 使用了错误记忆
1 分：使用了正确记忆但生硬（罗列式、与问题结合弱）
2 分：自然得体地使用了正确记忆
```

用模型评模型的风险是评委本身不可靠，三个缓解措施：

**评分锚点具体化**。不打「好不好」（漂移大），而是定义 0/1/2 的具体行为标准——这和 B04 提取 prompt 的 importance 分段是同一个手法。

**judge 可关**（`--judge=off`）。只跑关键词命中，用于快速冒烟或评委模型不可用时。评估脚本不能因为自己依赖的模型挂了就不能跑——降级是这套系统的通用语言。

**结果人工解读**。均分 1.67/2 本身意义有限，价值在逐用例看：哪个用例 0 分、为什么。评估脚本输出逐用例明细，不是只有一个总分。

## 为什么是本地脚本，不是 CI

评估不跑在 CI 里，这是刻意定位：

**依赖真实模型**。CI 环境起 Ollama + 拉 7B 模型 + 拉嵌入模型，光环境准备就 10 分钟起步，且结果随模型版本漂移——CI 要的是确定性，评估给不了。

**结果需要人工解读**。「11/12 且失败的是跨记忆综合题」和「11/12 但失败的是单跳召回」是完全不同的信号，机器只能报数字，判断在人。

**频率不匹配**。评估的触发时机是「改了 prompt/阈值/模型」这类低频事件，不是每次提交。

定位是「发版前手跑的回归基线」：全量 12 用例约 5 分钟，发布 checklist 里的一项。B07 的阈值校准、以及历史上多次 prompt 调整的验证，都是靠它。

## 反馈与评估的分工

两个机制回答的问题不同：

| | 👍/👎 反馈 | golden set 评估 |
|---|---|---|
| 信号来源 | 真实使用 | 受控用例 |
| 覆盖 | 用户真实遇到的场景 | 设计者预设的场景 |
| 时机 | 持续积累 | 发版前定点 |
| 能发现什么 | 没预料到的问题（未知未知） | 已知能力的回归（已知已知） |

往后，反馈数据（随备份轨导出）会成为后续 golden set 的用例来源——真实踩过的坑变成受控用例，受控用例守住不再犯。质量闭环因此转动。

## 小结

反馈设计的最小化（消息属性而非独立实体）带来备份、查询、删除三重免费正确性；评估基线的本地化（手跑而非 CI）承认模型评估的内在不确定性。两者合起来，记忆质量从「拍脑袋」变成了「有信号、有基线、有回归」。

至此记忆系统的技术点全部拆完。下一篇 B10 收尾：复盘这套系统最深刻的一次排查——「零召回」的三层洋葱，以及它对「每次失败都值得追到底」这条工程信条的实证。
