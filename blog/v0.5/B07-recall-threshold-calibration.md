## 现象：功能全部上线，召回全军覆没

M3 收工时，链路是通的：提取 → 去重 → 入库 → 召回 → 注入 system → memories SSE 事件提示条。单测全绿（236 个 core 测试里几十个记忆用例），手测也「看起来能用」。

然后跑了 golden set（12 条种子记忆 + 12 个跨会话召回用例），结果：**0/12，全 FAIL，judge 全 0**。

这篇讲排查过程和最反直觉的结论：阈值从 0.78 放宽到 1.05——召回阈值应该是去重阈值的三倍宽，这个方向跟直觉完全相反。B10 会复盘整个「三层洋葱」的完整排查（评估脚本 bug、陈旧 dev server、真实缺陷），这篇只聚焦最后的几何问题。

---

## 定位：sqlite-vec 直查，把链路剥到只剩几何

排除评估脚本 bug 和服务陈旧两层假象后（过程见 B10），剩下的现象是：记忆在库里，向量在表里，查询无报错，但 `memories` SSE 事件从未发出——召回过滤后为空。

链路各环节单独验证都正常，于是直接绕过应用层，用 sqlite-vec 直查 kNN：

```sql
-- 用 golden 用例的问句嵌入，直查 memories_vec 最近邻
SELECT m.content, v.distance
FROM memories_vec v JOIN memories m ON m.id = v.rowid
WHERE v.embedding MATCH json(:query_vector) AND k = 5
ORDER BY v.distance;
```

结果（qwen3-embedding:0.6b，问句「我不吃什么蔬菜？」对记忆「用户不吃香菜」）：

```text
distance 0.91  ← 最近邻，正确记忆
distance 1.08
distance 1.15
...
```

**正确记忆就是最近邻，但距离 0.91 > 阈值 0.78，被过滤掉了。**

不是链路问题，不是模型问题，是**阈值的几何假设错了**。

---

## 0.78 的假设哪来的，为什么错了

`MEMORY_RECALL_MAX_DISTANCE` 初值 0.78，对应余弦约 0.70——这是从「通用语义检索」经验里拍的：嵌入模型在标准 benchmark 上，相关文本对的余弦相似度通常 0.7+。按「宁少勿多」的保守直觉，0.70 看起来是个合理的起点。

但这个假设依赖两个隐含前提，在 v0.5 的场景里都不成立：

**前提一：嵌入模型足够强**。benchmark 上的 0.7+ 是 bge-large、text-embedding-3 这个量级的模型跑出来的。本地小模型 qwen3-embedding:0.6b 的嵌入空间「分辨率」低得多——语义相近的文本对余弦普遍只有 0.5~0.65。「宁少勿多」的直觉在强模型上是对的，在小模型上直接零召回。

**前提二：查询与文档同形态**。benchmark 的相关性评估通常是「段落对段落」。而记忆召回是**「短中文问句」对「客观陈述句」**：「我不吃什么蔬菜？」vs「用户不吃香菜」。问法与记法之间存在系统性的语义鸿沟——疑问句式、指代、口语化，都在拉低余弦。这个鸿沟在小模型上被进一步放大。

用 B05 的换算表看实测数据：0.91 的 L2 距离 ≈ 余弦 0.59——在 0.5~0.65 的典型区间内。也就是说，**正确记忆与问句的距离天然就在 0.8~1.03 之间，0.78 的阈值把这个区间整个切掉了**。

---

## 校准：1.05 不是拍的，是 golden set 量的

调整为 1.05（≈余弦 0.45）的依据不是「再拍一次脑袋」，而是 golden set 的逐用例距离分布：

```text
12 个用例的正确记忆距离实测：
0.83 / 0.87 / 0.91 / 0.91 / 0.94 / 0.96 / 0.98 / 1.01 / 1.02 / 1.03 / 1.04 / (1 例 1.2+ 未命中)

取 1.05 → 11/12 命中（92%），judge 均分 1.67/2
```

唯一未命中的用例是跨记忆综合题（「200 元以内送什么礼物」需要综合「朋友喜欢手冲咖啡」+「预算 200」两条记忆）——正确记忆排在 top-6，属于单跳向量召回的能力边界，**登记为已知边界，不为它放宽阈值**（放宽会把噪声灌进每轮对话，见下文防噪声设计）。

校准后的注释写进了 [constants.ts](file:///e:/code/traeWork/workBuddyForMe/packages/shared/src/constants.ts)，把「为什么是这个数」永久留在代码里：

```typescript
/**
 * - 提问时按用户消息向量检索 MEMORY_TOP_K 条，L2 距离（单位向量）超过
 *   MEMORY_RECALL_MAX_DISTANCE 的丢弃——归一化向量 L2≈sqrt(2-2cos)，
 *   0.5~0.65 区间（实测），0.78（cos 0.70）会导致几乎零召回；放宽后由
 *   MEMORY_TOP_K 限量与 system 提示防噪声。
 */
export const MEMORY_RECALL_MAX_DISTANCE = 1.05;
```

---

## 阈值放宽了，噪声怎么办：三层防波堤

「放宽阈值 = 召回更多弱相关记忆 = 污染对话」是对的担忧，但防噪声从来不靠阈值一个参数。v0.5 的防波堤是三层：

**第一层：Top-3 硬上限**（`MEMORY_TOP_K = 3`）。无论阈值内有多少候选，注入 system 的最多 3 条。即使阈值放宽到 1.05，注入量不会膨胀。这个上限同时是预算保护的延伸——记忆块预留 512 token，3 条典型记忆（每条 100-200 字符）恰好装得下。

**第二层：system 提示的「无关不提」指令**。注入的【长期记忆】区块带明确指令：「以下是关于用户的已知信息，**与当前问题无关时无需提及**」。记忆是上下文，不是必须使用的素材——把「用不用」的判断留给模型，比用阈值替模型做判断更鲁棒。实测 7B 模型对这条指令的遵守度很好：问「今天天气」时即使注入了「用户不吃香菜」，回答也不会提香菜。

**第三层：重要性排序**。召回结果按距离排序后，同距离下重要性高的优先（检索 SQL 的 ORDER BY 可扩展）。重要性在写入时由提取模型评分、去重时取大（B05），在遗忘时决定归档（B08）——这一个字段贯穿了记忆生命周期的所有排序决策。

三层叠起来的效果：阈值管「能不能进候选池」，Top-3 管「最多进几条」，system 指令管「进了之后用不用」。**阈值从「唯一的噪声闸门」降级为「三层防波堤的第一道」**，这是它能被安全放宽的结构前提。

---

## 方法论：阈值类参数必须挂评估基线

这次校准最重要的产出不是 1.05 这个数，而是一条写进项目宪法的规则：

> **阈值类参数必须挂一条可重复执行的评估基线，否则调参就是玄学。**

0.78 这个值在单测里「绿」了整整两周——单测 mock 嵌入向量，距离是构造出来的，阈值真假无所谓。只有 golden set 用真实模型、真实问句、真实嵌入跑端到端，才能暴露「直觉阈值在小模型上零召回」这种系统级错误。

评估基线的形态（`pnpm eval:memory`，12 用例 + LLM 评委）和它的定位（发版前手跑，不进 CI）在 B09 细讲。这里只强调它对阈值的意义：**1.05 不是终点，是基线上的一个测量点**——未来换嵌入模型（比如升级到更大的 bge 系本地模型），重跑 golden set，阈值可能要回收到 0.9。数字会变，基线永存。

---

## 小结

0.78 → 1.05 的故事浓缩了本地小模型工程的一个普遍教训：**从大模型/benchmark 继承的经验参数，在本地小模型上可能是系统性错误的**。通用经验给出搜索方向，实测数据决定最终参数；而实测的前提是有一条可重复执行的评估基线——没有基线的调参，改了等于没改。

召回链路至此完整：提取（B04）→ 去重（B05）→ 存储（B06）→ 召回（本篇）。但记忆不能只进不出——下一篇 B08 讲遗忘：软归档的三个条件、7 天间隔保护、以及 post-turn-jobs 怎么把所有回合后作业收敛成一个统一入口。
