# 复盘：零召回的三层洋葱，与「每次失败都值得追到底」

## 复盘对象：一次 0/12 的评估运行

在我们这个本地优先、单人开发的桌面助手上，记忆功能全部收工、493 个单测全绿之后，golden set 首跑给出的是一个彻底的惨败：**12 个召回用例全 FAIL，judge 全 0**。

如果只修到「评估绿了」就停手，应用会带着一个真实缺陷发布——事后证明，0/12 背后是**三个独立问题叠加**，修好前两层后评估能绿，但第三层（真实缺陷）依然存在。这篇按排查顺序剥开这三层洋葱，它是这套记忆系统方法论价值最高的一小时。

## 第一层：评估脚本自己的 bug

**现象**：所有用例的回答内容为空字符串，judge 自然全 0。

**根因**：评估脚本解析 SSE 流时，把 `data:` 负载当信封解析。实际的 SSE 格式里 `event:` 和 `data:` 是同层的两行：

```text
event: delta
data: {"content":"我不"}

event: delta
data: {"content":"吃"}
```

脚本的初版把 `data` 当成嵌套在某个外层结构里的字段去取，`content` 永远拼不上。所有回答都是空的，所有用例都失败——**但这个失败和被测系统毫无关系**。

**教训一：评估工具自身要先验证有效性。** 修复方式不是改完就跑，而是先加一个探针用例：发一个「1+1 等于几」这种不需要任何记忆的问题，确认回答能正确拼出「2」。探针通过之前，评估结果一概不可信。工具测别人之前，先要证明自己能测。

这一层如果停在「哦是脚本 bug，修了」——第二层就看不见了。

## 第二层：陈旧 dev server 的幽灵行为

**现象**：脚本修好后重跑，回答有内容了，但仍然没有任何记忆被使用，`memories` SSE 事件从未出现。

**根因**：本地 3000 端口上跑着一个**两天前启动的 next dev server**——它持有记忆接线之前的旧编译产物。API 正常响应、页面正常打开、对话正常进行，一切「看起来活着」，但召回链路在那个代码版本里根本不存在。

而新启动的 `pnpm dev:web` 只会报 `EADDRINUSE` 失败，这个错误又被既有服务的健康检查掩盖——脚本连得上 3000，就认为服务是好的。

**教训二：验证功能前，先核对服务进程的启动时间与代码版本是否同代。** 这条后来写进了评估脚本的 docstring 使用前提。本地开发的「幽灵进程」问题（僵尸 dev server、残留子进程）在后续的 MCP 子进程管理里还会以另一种形式回来（树杀 vs TerminateProcess），这是后话。

这一层修掉（杀旧进程、起新服务）之后，评估能跑通了——但**召回依然全灭**。前两层修完评估依然是红的，这才是这次排查的关键时刻：如果第二层修完恰好绿了（比如凑巧某用例蒙对），第三层就会被带进发布。

## 第三层：真实缺陷——阈值的几何错误

**现象**：链路确认活着（探针请求确认服务版本、记忆确认在库、SSE 事件通道确认接好），但召回过滤后为空。

**定位**：sqlite-vec 直查 kNN（B07 详述），发现正确记忆就是最近邻，距离 0.91——但阈值 0.78，被过滤。

**根因**：0.78（≈余弦 0.70）是从通用 benchmark 经验拍的，隐含假设「嵌入模型足够强」+「查询与文档同形态」。本地小模型 + 「短问句 vs 陈述记忆」的场景下，正确文本对的余弦普遍只有 0.5~0.65。阈值把整个正确区间切掉了。

**修复**：0.78 → 1.05，golden set 实测 11/12（92%），唯一失败的是跨记忆综合题——登记为已知边界，不为它放宽阈值。

## 为什么「修到绿就停」在这里会失败

三层洋葱的危险性在于它们的**叠加结构**：

```text
第一层（脚本 bug）：所有用例失败，回答全空
  → 修好后：回答有内容了
第二层（陈旧服务）：所有用例失败，无记忆事件
  → 修好后：链路活了
第三层（阈值错误）：所有用例失败，几何过滤
  → 修好后：11/12
```

注意：**每一层的修复都不会让评估变绿**——因为下一层还在挡着。反过来，如果三个问题的严重程度稍有不同（比如第二层只影响部分用例），中间某次运行可能恰好「看起来绿了」，第三层就漏网了。

「每次失败都值得追到底」在这类叠加故障里不是口号，是唯一可靠的策略：**追到「失败的全部原因都被解释」为止，而不是追到「测试变绿」为止**。变绿是结果，解释才是目标。

## 另外三个坑

**坑：构建期的 Next tracing 警告（预先存在）**。standalone 构建按数据目录绝对路径 mkdir 产生 tracing 警告——这是个早已有之的问题，不影响产物。处理方式是登记为已知项而非顺手修：范围纪律，每轮改造只解决自己主题内的问题。

**坑：turbo 缓存掩盖的仓库不变量**。某模块硬编码了应用数据目录名，被 repo-invariants 测试拦截，但 turbo 缓存让它到后来一次 cache miss 才暴露。**缓存让测试变快，也让失败迟到**——门禁设计要保证关键不变量测试至少在全量发布流程中无缓存跑一次。

**坑：告警噪音**。B04 提过，早期实现把「空数组提取结果」也当失败 warn，日志被误报淹没。告警的唯一目的是触发行动，不触发行动的告警都是在训练人忽略告警。

## 取舍回顾：三个「不做」的理由

**跨记忆综合不做**（放宽阈值救回第 12 例）：top-4 实测正确记忆排第 6，放宽阈值能救这一例，但每轮对话会多注入几条弱相关记忆。单跳召回 11/12 全绿是必须，跨记忆综合登记为已知边界，等知识层演进。**不用噪声换分数**。

**遗忘不做物理删除**：软归档可恢复，删除权留给用户。隐私闭环的一致性（B08）。

**评估不进 CI**：真实模型依赖 + 结果需要人工解读。定位为发版前手跑基线（B09）。

## 留给后续的三样东西

1. **预算体系**（B02/B03）：摘要块与记忆块的预留席位制度，成为后续所有「往 system 里注东西」功能（比如技能注入）的标准做法。
2. **评估基线**（B07/B09）：golden set + judge 的范式从记忆扩展到其他需要实测校准的参数。阈值类参数必须挂基线，写进了项目宪法。
3. **回合后作业框架**（B08）：post-turn-jobs 的统一入口 + 失败静默原则，后续的工具熔断记录、任务日志落库都复用这个模式。

## 一句话总结

技术产出是记忆生命周期，方法论产出是两条：**阈值类参数必须挂可重复执行的评估基线；叠加故障必须追到「失败的全部原因都被解释」，而不是追到「测试变绿」**。下一站是「会接活」，把助手从「记得住」扩展到「什么都能接」——MCP 生态 + 技能包 + 权限分级，那是另一个故事了。
