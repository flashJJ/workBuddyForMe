# 让 7B 模型吐结构化记忆：强约束 JSON、zod 兜底、宁可少记不能记错

## 问题：从对话里「提炼记忆」是个格式问题

我们的桌面助手以本地 7B 模型为主。长期记忆链路的第一步，是从每一轮对话里提取值得长期保留的信息。输入很明确：本轮用户消息 + 助手回答。输出要求也很明确：一组结构化的记忆条目（类型/内容/重要性）。

难的是中间：**本地小模型的输出格式漂移是常态，不是异常**。

qwen2.5:7b 在「输出 JSON」任务上的实际表现（开发期实测记录）：

- 约 10% 的概率在 JSON 外面包一层 ```` ```json ```` 围栏；
- 约 5% 的概率在数组前后加解释性文字（「好的，提取结果如下：」）；
- 偶发把 `importance` 写成 `"0.8"`（字符串）、把 `kind` 写成中文（「偏好」）；
- 更隐蔽的：内容里带上「用户提到」「他说」这类视角词，把客观陈述变成转述。

每一种漂移单独看都是小问题，但记忆是要**入库并被反复召回**的——坏数据进库一次，污染后续所有对话。`extractor.ts` 的设计原则是：**宁可少记，不能记错**。这篇讲四层防线怎么把这个原则落成代码。

## 防线一：prompt 把「作文题」改成「填空题」

提取 prompt（`EXTRACT_SYSTEM_INSTRUCTION`）的结构是经过实测打磨的：

```text
你是长期记忆提取助手。阅读用户与 AI 助手的一轮对话，从中提取【值得长期保留】的信息。
只提取以下三类：
- fact：用户的身份、背景、长期事实（职业、项目、所在地、关系等）；
- preference：明确表达的偏好、习惯、约定（语言风格、工具选择、忌口等）；
- event：已发生且日后可能被提及的重要事件（考试、决定、计划）。
要求：
1. 只提取跨对话仍有价值的信息；寒暄、一次性问题、临时计算一律不提取；
2. 每条 content 是一句自包含的客观陈述（中文，1-500 字），不写"用户提到"这类前缀；
3. importance 取 0 到 1：0.8+ 核心身份/强烈偏好，0.5-0.8 一般重要，0.5 以下仅参考；
4. 最多 5 条；没有值得记忆的内容时输出 []；
5. 严格只输出 JSON 数组，不要代码块、不要解释。
```

四条关键约束，每条都对应一类实测翻车：

**枚举类型 + 实例**。不写「提取重要信息」（7B 会把「用户今天天气不错」当重要信息），而是枚举三类 + 每类给例子。kind 字段的值域被 prompt 和 zod 双重钉死。

**「自包含的客观陈述」**。这是针对视角词漂移的——「用户提到他不吃香菜」作为记忆是坏的，召回注入 system 后模型会困惑「他」是谁。要求「自包含陈述」让记忆脱敏于对话语境，任意会话召回都可直接使用。

**importance 分段语义**。不给语义的 0-1 评分是随机的；给了「0.8+ 核心身份/强烈偏好」的分段锚点后，7B 的评分稳定性明显提升。这个字段后来驱动了遗忘策略（<0.4 进入归档候选，见 B08），评分质量直接决定遗忘质量。

**上限 5 条 + 空数组显式合法**。「没有值得记忆的内容时输出 []」必须显式写——否则模型会硬凑（把「你好」提取成 `{"kind":"fact","content":"用户喜欢打招呼"}`）。上限 5 条（`MEMORY_EXTRACT_MAX_ITEMS`）控制单轮注入量，也控制嵌入调用成本。

## 防线二：解析器先容忍，再校验

模型侧的约束再强，也只是「请求」。解析层 `parseExtractedMemories` 的态度是「先尽力拯救，救不了就杀」：

```typescript
export function parseExtractedMemories(raw: string): ExtractedMemory[] {
  const text = raw.trim()
    .replace(/^```(?:json)?\s*/i, '')
    .replace(/```\s*$/i, '')
    .trim();
  const start = text.indexOf('[');
  const end = text.lastIndexOf(']');
  if (start === -1 || end === -1 || end < start) {
    throw new Error('记忆提取结果中未找到 JSON 数组');
  }
  const parsed: unknown = JSON.parse(text.slice(start, end + 1));
  return extractedMemorySchema.parse(parsed).map(...);
}
```

两步走：

**第一步，定位数组边界**。剥围栏之后，找第一个 `[` 和最后一个 `]`，切出中间部分。这一步容忍了「解释性文字包裹 JSON」——只要文本里存在一个完整的 JSON 数组，前后的废话都被切掉。实测救回了约 5% 的「话痨输出」。

**第二步，zod 严格校验**。切出来的内容过 schema：kind 必须是枚举值、content 必须 1-500 字、importance 必须 0-1 数字、数组最多 5 条。任何一条不合格，**整批抛错**——不是跳过坏条目留好条目，而是整批丢弃。

为什么整批丢弃这么狠？因为部分接受意味着要决定「哪几条算好」——这个决定本身又引入了判断逻辑和出错面。而且实测发现：一批输出里一条 schema 违规时，其他条目通常也有质量问题（同一次生成的整体漂移）。整批丢弃 + 静默失败的语义简单、可测试、不会错杀到可惜的程度——反正下一轮对话还会再提取。

最后有个细节：importance 落库前 `Math.round(x * 100) / 100`，把模型输出的 0.75000000001 归一成两位小数。展示和比较都干净。

## 防线三：temperature 0 + 失败静默

提取调用走 `chatStream` 且 **temperature 固定为 0**。记忆提取是确定性任务，不需要任何创造性——采样在这里只有害处。这和早先 OCR 功能固定 temperature 0 是同一个教训（采样波动导致同一张图两次识别结果不同），现在它已经是项目里所有「结构化输出」任务的默认约定。

失败处理链：

```text
chatStream 网络错误 → 抛错
raw 为空 → 抛错
找不到 JSON 数组 → 抛错
zod 校验失败 → 抛错
  ↓
extractTurnMemories 抛出
  ↓
turn-memory / post-turn-jobs 捕获 → console.warn('记忆提取失败：...') → 结束
```

用户侧完全无感。记忆是增强不是依赖——这条原则在 B03 的压缩降级里出现过，在 B08 的 post-turn-jobs 里还会看到它贯穿全部四步后台作业。

## 防线四：测试把漂移钉成回归用例

`extractor.test.ts` 的价值不在于测「正常 JSON 能解析」（那是废话），而在于把**实测中真实出现过的每一种漂移**钉成回归用例：

- 带 ```` ```json ```` 围栏的合法数组 → 解析成功；
- 数组前后带解释文字 → 解析成功；
- 完全没有数组 → 抛错；
- kind 不在枚举内 → 抛错；
- content 超 500 字 → 抛错；
- 数组超 5 条 → 抛错；
- 空数组 `[]` → 返回空数组（合法！不是错误）。

最后一条值得单独说：空数组是「本轮没什么可记的」的合法表达，必须和「输出格式坏了」严格区分。早期实现把空数组也当失败处理，结果日志里全是误报 warn——**告警噪音会掩盖真问题**，这是可观测性的基本常识。

## 小结

结构化提取的四层防线——prompt 填空化、解析先容忍后校验、temperature 0、失败静默——本质上是在承认一个现实：本地小模型的输出是不可信的输入源，必须按「对抗性输入」的标准做边界校验。zod schema 在这里扮演的角色，和它在 API 边界、备份恢复里的角色完全一样：**系统的每一道信任边界都需要显式契约**。
