# 先拆纯处理器，再谈状态机：会话 Hook 的减法

web 端的对话会话 Hook 有 294 行。

它要拿历史消息、维护流式期间的本地消息、跑计时、处理 SSE、管理任务模式、处理重试与停止，还要在结束时刷新缓存。

每加一个事件类型，这个文件就再长一截。

## 一、为什么不能直接抽状态机

状态机听起来更“正确”，但代价被低估了。

要抽状态机，先得把“流式会话到底有哪些状态”写清楚：空闲、发送中、首字未到、流式中、工具确认挂起、已停止、失败。

这些状态目前是隐式的，散在多个布尔值与回调里。贸然形式化，等于在拆分的同时改行为。

这一轮的目标是零行为变更，所以先做机械搬迁。

## 二、第一个切口：SSE 事件处理器

文件里最长的一段是一个事件分支：元信息、增量、引用、记忆、工具、确认、语音、完成、错误。

它们只做一件事：拿到载荷，调用已有的更新函数。

于是抽成一个纯工厂：外部把状态设置器、计时回调、缓存客户端和语音回调传进来，工厂返回一组命名处理器。

工厂不持有状态，不调用 Hook，也不读闭包。

## 三、第二个切口：回合编排

发送、重试、停止是另一段：它们共享“当前这一轮”的上下文。

抽成一个回合 Hook，入参是会话 id、历史、live 列表、计时接口、流式发送与停止、任务模式实例。

它负责：

- 开始计时、清空上一轮的召回与确认态；
- 构造待定助手消息并写入 live；
- 创建处理器，发起流式请求；
- 重试时判断是否挂着协作卡，走任务模式而不是普通重生成；
- 停止时中断请求、冲刷增量、结算计时、标记消息为已停止。

## 四、计时与合帧留在原处

有一个容易拆错的点：增量不是逐字写入状态，而是按动画帧合帧。

合帧队列与计时器留在原来的帧 Hook 里，只把“开始、首字、入队、冲刷、结算、重置”作为接口传下去。

这样拆分不会改变首字延迟的测量点，也不会改变渲染节奏。

## 五、通知与缓存刷新

完成与错误两个分支都会刷新会话列表和消息查询。

这段逻辑跟着处理器走，而不是留在会话 Hook 里。理由是同一条事件的所有副作用应该在同一处，否则以后加一个事件类型又要改两个文件。

## 六、任务模式仍然直接委托

任务模式有独立的会话创建、协作流与终态对账，没有塞进普通回合。

会话 Hook 只保留一行委托，并在任务轮开始前重置流式计时，避免末条消息挂上旧的首字指标。

这条边界是有意保留的：两种回合的失败语义不同，强行合并会让重试判断更难读。

## 七、测试保持

三个既有测试不动：会话 Hook、对话页、输入框。

它们覆盖的是“用户发一句话之后看到什么”，不是内部函数怎么组织。断言不改仍然全绿，是这次拆分最重要的验收。

## 八、结果

- 会话 Hook 从 294 行降到 181 行；
- 事件处理器 116 行，回合编排 185 行，各自可读；
- 计时、通知、重试、停止语义全部保持；
- 状态机留到下次：等状态真的需要被外部观察时再抽，而不是为了行数。
