# 常量也要分域：一个 293 行 API 文件的退场

前端有一个集中存放 API 路径的常量文件，293 行。

它长期挂在行数白名单里，理由写着“以后再说”。这个“以后”跨了十多个版本。

## 一、它为什么一直没被拆

表面看只是字符串常量，拆分应该很安全。

真正的问题是它同时承担了两种职责：

- 路径常量：接口地址与参数拼接；
- 查询键：缓存失效与预取的键工厂。

两者混在一个对象里，页面导入时往往两个都要，于是没人愿意动。

## 二、按“谁会一起改”分域

拆分维度不是按行数均分，而是按变更来源。

最后的四个域是：

- 对话域：会话、消息、分支、事件检索、流式入口；
- 知识域：知识库、文档、检索与编译；
- 系统域：模型、设置、助手、角色卡、能力包、MCP、技能、工具、语音；
- 工作域：目标、计划、任务、审批、审计、协作、会议与工作流。

判断标准只有一条：一次需求通常会同时改到哪些路径，它们就放一起。

## 三、barrel 保持兼容

拆完之后，原文件只留一个 barrel：

- 展开四个域对象，合成统一的 `API`；
- 查询键继续留在 barrel 里，因为它跨域使用，按域切反而会制造循环导入。

调用点一行不改，仍然是 `API.xxx` 与 `QUERY_KEYS.xxx`。

## 四、删除白名单条目

白名单原本只应容纳“配置或生成类文件”。

路径常量是手写业务代码，不应该长期豁免。拆分完成后，这条目被删除。

剩下两条豁免都是生成物或声明式配置：一份由接口生成的模型清单，一份顺序迁移注册表。

## 五、常量域化解决了什么

最直接的是并行改动冲突。

以前两个人同时加接口，几乎必然在同一个文件同一段末尾撞车；现在一个改对话域、一个改工作域，冲突面接近零。

其次是可发现性：想知道“知识库有哪些接口”，打开一个几十行的文件就够，不用在三百行里搜前缀。

第三是审查粒度：一个域文件的变化范围小，评审时更容易判断有没有越界。

## 六、机械替换，不改语义

整个过程只有三步：

1. 按域把常量搬进新文件；
2. 原文件改成 barrel 展开；
3. 删除白名单条目并跑全量检查。

没有改任何路径拼接方式，没有合并或重命名键，也没有顺手“优化”参数编码。

## 七、结果

- 常量文件从 293 行降到几十行的 barrel；
- 四个域文件各自不超过 90 行；
- 白名单只剩两条生成物或配置类豁免；
- 所有调用点与查询键语义不变。
