# 类型能过、生产才炸：一次子路径导出事故的排查

这个问题的表现很分裂：本地单测全绿，类型检查全绿，`next build` 却报一个符号不存在。

更奇怪的是，报错的符号在源码里明明存在，测试也一直在用。

## 一、报错长什么样

构建日志里反复出现同一句：尝试导入的符号在产物里找不到。

缺失的是上下文快照相关的两个函数。它们属于 core 包的一个域，页面通过子路径导入。

```text
Attempted import error: 'recordSceneSnapshot' is not exported ...
```

## 二、三个条件同时成立才会炸

把 `exports` 摊开看，问题就清楚了。

- `types` 条件指向源码入口；
- `development` 条件也指向源码入口；
- `import` 条件指向根产物。

而根入口的 barrel 并没有聚合这个域。

三者叠加的结果是：开发与类型检查走源码，生产走产物，两条路径的导出面并不一致。

## 三、为什么类型能过

TypeScript 解析的是 `types` 条件，拿到的是源码入口的完整导出。

它不会去执行生产 bundle，也不会校验“根产物里到底有没有这个符号”。

单测同理，vitest 走的是 `development` 条件，加载的仍然是源码。

所以“类型能过”不代表“产物能过”，只代表“源码自洽”。

## 四、第一反应：聚合进根入口

最直觉的修法是把该域加进根 barrel。

改完之后构建确实过了。但 `next start` 起来，健康检查直接 500。

原因是一个运行期循环：这个域的入口会 re-export 对话上下文里的一个工具函数，而对话上下文又依赖快照写入。

源码条件下循环可能被加载顺序掩盖；打包成单一产物后，初始化顺序被固定，循环立刻显形。

## 五、最终方案：独立入口

既然不能聚合，就给它一条自己的产物路径。

做法与语音、事件客户端两个域一致：新增一个 tsup 入口，`exports` 的生产条件改指这个独立产物。

- 根 barrel 保持不聚合，循环不存在；
- 子路径拿到的是完整域导出，符号存在；
- 类型与开发条件仍指向源码，编辑体验不变。

`next start` 健康检查恢复 200，构建日志里的缺失消失。

## 六、补上产物级冒烟

事故的根因不是“写错一行”，而是“没有任何检查站在产物这一层”。

新增的冒烟脚本做了三件事：

1. 读包的 `exports`，取 `import` 条件对应的真实文件；
2. 动态 `import` 这个文件；
3. 逐个子路径断言关键符号存在。

它不启动服务，不跑业务，只回答一个问题：生产条件下，这些名字在不在。

脚本挂在构建之后执行。顺序很重要：先有产物，才有冒烟。

## 七、再补一道日志门禁

冒烟能抓住“符号缺失”，但抓不住“构建过程中出现过告警”。

CI 里加了一条很土的规则：把构建输出 tee 到日志文件，命中固定错误串就失败。土，但有效，它拦的是“构建成功了，但过程中已经不对劲”这一类问题。

## 八、结果与代价

- 缺失符号的子路径恢复正常，健康检查 200；
- 冒烟覆盖从零扩到多个子路径，后来继续扩到六个；
- 构建日志门禁进入流水线，先于冒烟执行。

代价是 `exports` 多了一条独立产物路径，构建多了一个入口。这是有意的：循环不能靠加载顺序赌，只能靠模块边界切断。
