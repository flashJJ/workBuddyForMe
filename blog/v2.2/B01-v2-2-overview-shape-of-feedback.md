# 从「点一下弹一下」到「有形状」：桌宠反馈升级的六条主线

我们的桌面 AI 应用有一个透明置顶的桌宠窗，里面是 2D 或 3D 的虚拟形象。用户会去点它的头、摸它的身体、按住不放，也会把它拖到屏幕角落，甚至甩出去。

上一版把交互管道收口成了四段：事件归一化 → 纯函数门控 → 执行器分发 → 广播。管道是通的，但跑起来之后，反馈的问题暴露得很直接：**按住不放和点一下，区别只是换了一次表情。**

| 用户动作 | 当时的反馈 | 缺的东西 |
|---|---|---|
| 按住头部 | 和单击几乎没有区别 | 没有入场、维持、退场的层次 |
| 待机 | 每隔几秒随机换一段动作 | 与心情、关系无关 |
| 拖拽 | 跟手移动，松手即停 | 没有速度、惯性和边界 |
| 想改反应 | 只能改代码 | 反馈表不可配置 |

所以这一版的目标不是「增加更多动作」，而是让每一次交互**有形状**。形状有四种：

- **时间上的形状**：按住是一个过程，有抬起、维持、放下，而不是一帧表情；
- **状态上的形状**：待机动作跟着情绪档位和关系等级走，而不是纯随机；
- **空间上的形状**：甩出去会滑行，靠近边缘会回正，而不是松手即停；
- **结构上的形状**：哪个触发键对应哪段动作，由一张可配置的图决定，而不是散在事件回调里。

## 六条主线

| 主线 | 做了什么 | 作用域 |
|---|---|---|
| 段调度 | 一个动作条目 = 入场 A / 循环 B / 退场 C；按住进 B、松手走 C、缺段自动退化 | 仅 3D（VRM） |
| 状态驱动待机 | 情绪档位 + 关系等级分组挑选，兼容回退到 Default | 策略通用，候选集 3D 优先 |
| 拖拽物理与手势 | 主进程速度采样、惯性滑行、贴边双阈值、身体双击 | 两套后端通用 |
| 交互动画图 | 触发键 + 条件 + 动作条目 id，持久化并可视化编辑，内置条目可覆盖/停用 | 通用 |
| 事件链接线 | 感知、系统、关系事件接进同一条解析管道，并补齐系统信号源 | 通用 |
| 首帧门控 | 11 个「按查询态切结构」的组件统一补水合门控 | web 端 |

这六条不是并列的功能点。段调度解决「一次交互的时间结构」，状态驱动解决「两次交互之间的选择」，物理与手势解决「交互发生在窗口上的空间结构」，动画图解决「反应从哪里来」，事件链接线解决「哪些事件算交互」，首帧门控则是把配置面板本身的渲染稳定性补上。

顺序也不是随意排的。先做段调度，是因为没有它，「按住」在播放层根本不是一个可表达的状态；先做物理，是因为它完全不依赖形象后端，能在 2D 与 3D 上同时兑现手感；动画图放到后面，是因为它需要先有稳定的动作条目目录，否则配置只能指向一堆随时会变的字符串。

## 红线：策略通用，执行 VRM 优先

桌宠有两套渲染后端，动作模型根本不同：3D（VRM）侧是外部导入的骨骼动画片段，可以自由拆分、拼接、按池调度；2D 侧的动作是模型文件里固化的 motion group，一个 motion 自带循环标记与淡入淡出，没有「一段拆三段」的概念。

所以这一版划了一条红线：**与后端无关的部分共用，需要动作模型配合的部分只落 VRM（3D）。**

- 手势、门控、拖拽物理、配置数据与分组挑选，做成 shared 包里的纯函数，两套后端共用；
- 段调度、长按维持、按状态分档的待机候选集，只落 3D；
- 选定 2D 形象的用户，行为与这一版之前完全一致，能感知到的只有「手势变多、拖拽有惯性」。

这条线最容易被误读成「2D 也升级了」。**策略通用，指的是判断逻辑共用，不是指 2D 已经获得了同等效果。** 2D 要做到按状态分档待机或长按维持，得重导出 Cubism 工程、新增动作分组并准备带循环的 motion——成本主要在美术资源，不在代码，因此明确顺延。

## 最难的约束一：多动作不等于多播放器

three.js 里播放动画用 `AnimationMixer`。很自然的想法是：待机一个 mixer，交互一个 mixer，互不干扰。

这条路走不通。两个 mixer 绑定的是同一批规范化骨骼节点，各自每帧往里写四元数，最后生效的是后写的那个。所谓「叠加」实际是「覆盖」，表现就是模型猛地弹回 T-pose 再抖回来。

因此播放层只能有一个调度者：所有动作共用同一个 mixer，用 `crossFade` 做权重过渡，用 `LoopOnce` 加 `finished` 事件做一次性播放的收尾。段调度也是在这个前提下成立的——A 到 B 的衔接必须是一次 mixer 内部的淡入，如果换一个播放器，衔接处就会变成姿态跳变。

这条约束在只有一个动作时完全不可见，只在「动作变多」时以抽搐的形式跳出来。功能变多时，先找到那个唯一的调度者，往往比多写几个功能更值钱。

## 最难的约束二：为最坏情况设计

这一版的功能几乎每一项都有一个「理想输入」版本，但真正决定实现的是最坏输入：

| 功能 | 理想输入 | 最坏输入 | 实现必须给出的退化 |
|---|---|---|---|
| 段调度 | 动作带完整 A/B/C | 用户导入的整段动画只有一段 | 整段当循环段；缺 A 直接进 B，缺 C 直接回待机 |
| 状态待机 | 情绪与关系数据齐全 | 新用户没有任何状态数据 | 回落 Default 组；内置动作常驻池中 |
| 动画图 | 配置合法且完整 | 手改配置、未知动作 id、越界时段 | 服务端逐条丢弃非法项，不污染运行期 |
| 贴边 | 指针稳定、远离边界 | 在阈值附近来回抖 | 进入与维持用两套阈值 |
| 事件链接 | 事件稀疏且有意义 | 同一信号连续触发 | 按触发键冷却；查不到条目就返回空 |

「查不到就返回空」尤其重要。它不是兜底失败，而是配置语义的一部分：用户停用了某个触发键的全部条目，那个键就应该安静，而不是随便挑一个动作糊弄过去。

## 交付规模与验证

相对上一版，这次改动涉及 **78 个已有文件、+1631/−632 行，新增 24 个文件**。静态门禁方面，类型检查与 lint 全包通过，行数门禁的违规从 4 处回到 0。

单测 8 个包全部通过，择要：web 端 94 个文件 496 例、core 包 160 个文件 1082 例、shared 包 29 个文件 314 例、桌面壳 24 个文件 164 例、数据库 52 个文件 213 例。新增测试集中在段调度、动作挑选、投掷物理、拖拽控制器、动画图（触发键、条件、覆盖与停用）、配置钳制与事件中继净化。

浏览器侧的真机流程也逐项走了一遍：交互动画图面板能看到 10 条内置条目（6 条触摸 + 4 条非触摸），触发键四个分组共 35 个键，动作条目下拉 8 项；覆盖条目与停用开关跨刷新保持；清理后回到默认态；设置页与对话页全程没有出现水合相关报错。

还没做完的部分也记一笔：真实多显示器下的三尺寸手感验收、Electron 打包产物的端到端测试、锁屏/唤醒/空闲这类系统信号的真机验证，都需要在真实桌面上完成，本机浏览器环境覆盖不到。

## 刻意留下的空白

- **2D 不做同等能力**：按状态分档的待机、长按维持、档位过渡都需要重导出 Cubism 资源，这一版只承接与后端无关的手势、门控和物理；
- **情绪档位的过渡动画没做**：心情变了但形象直接换动作，缺少一段过渡素材，属于资源成本而不是代码难点；
- **非触摸事件只给了 4 条默认表现**：其余触发键在面板里留空，交给用户自己配，避免默认行为变成噪音；
- **系统信号没有真机验证**：锁屏、唤醒、空闲越阈需要真实 Electron 桌宠窗，留到多显示器验收时一起做；
- **对话事件没有接**：被提及、新消息要不要驱动表演，先要产品定口径，代码里有意不建触发键。

这些空白不是遗漏，而是先把「能表达」和「默认该不该发生」分开：能力先做出来，默认行为保持克制。

## 小结

这一版真正改的不是「动作数量」，而是反馈的结构：时间上有 A/B/C，状态上有档位与门槛，空间上有速度与边界，来源上有一张可描述的图。

把交互从「点一下弹一下」做成「有形状」，靠的不是更多 if，而是三件事：**唯一的播放调度者、所有分支都有退化路径、配置只描述选择不描述执行。**
