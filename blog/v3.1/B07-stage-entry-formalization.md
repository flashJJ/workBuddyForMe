# 深链能用，不等于用户能找到：舞台入口的正式化

一个功能做完，最常被忽略的是入口。

小剧场早就支持 `/stage?stage=play`，但除了手动改地址，用户没有任何按钮能进去。托盘里倒是有“打开全屏舞台”，打开的却是不带参数的裸舞台。

结果是：能用的功能像彩蛋，演示舞台反而成了正式入口。

## 一、先承认现状

舞台有四种模式，入口却不成体系：

| 模式 | 入口 | 用户能找到吗 |
|---|---|---|
| 自由舞台 | 托盘、应用菜单、裸 `/stage` | 能 |
| 小剧场 | 只有深链 | 不能 |
| 协作 run | 协作卡打开 | 能 |
| 会议 | 会议页打开 | 能 |

小剧场的问题不是技术，是产品入口。

## 二、两个可选方案

**方案 A：入口正式化**

保留现有模式边界，只补入口：

- 托盘“全屏舞台”改成子菜单：自由舞台 / 小剧场。
- 应用菜单同步。
- 舞台控制栏加“进入小剧场”，小剧场加“返回自由舞台”。

**方案 B：模式合并**

把自由舞台和小剧场合并成一个舞台，剧本只是可选状态；暂停时允许手动接管。

方案 B 体验更连续，但要改控制器状态机、cast 来源、计时器与音频 duck，回归面大。当前舞台不是高频核心，先做 A 更划算。

## 三、托盘子菜单

Electron 的托盘菜单每次弹出时重建，适合按实时状态生成。改造后：

```ts
{
  label: '全屏舞台',
  submenu: [
    { label: '自由舞台', click: () => openStage({ free: true }) },
    { label: '小剧场', click: () => openStage({ theater: true }) },
  ],
}
```

`free` 这个标记不是为了 URL，而是为了“已经开着的舞台窗”。

原来的逻辑是：窗口已存在时只聚焦，不重新加载。这对“打开舞台”是合理的，但对“切回自由舞台”不够——用户点了自由舞台，窗口还停在小剧场。

所以目标类型增加两个显式标记：

```ts
type StageOpenTarget = {
  runId?: string;
  meetingId?: string;
  theater?: boolean;
  free?: boolean;
};
```

窗口已存在且带目标时，重新导航；`free` 导航回裸 `/stage`。

## 四、IPC 白名单

舞台窗由主进程创建，入口目标来自渲染层。目标参数必须做白名单校验，不能把任意字符串拼进 URL。

规则很简单：

- `runId` / `meetingId` 只接受字母、数字、下划线、中划线。
- `theater` 只接受布尔 `true`。
- 观看现场优先于小剧场。

于是恶意输入无法变成任意 query，非法值直接丢弃。

## 五、舞台内切换为什么用整页导航

控制栏的“进入小剧场”没有走状态切换，而是：

```ts
window.location.assign('/stage?stage=play');
```

理由有三个：

1. 小剧场会重置 cast、播放进度、BGM 与语音队列；自由舞台也有自己的 cast 与台词状态。
2. 两套控制器的状态字段有重叠，同页切换要写大量清理逻辑。
3. 整页导航天然保证干净状态，不会出现“上一场的台词挂在下一场”。

代价是 VRM 重新加载。对低频的模式切换可以接受。

这也是为什么先做 A：入口收益立刻拿到，状态机改造留到真正需要无缝切换时。

## 六、文案也要跟着改

“演示舞台”改成“自由舞台”，省电档文案去掉 Live2D 限定——默认角色已经换成 3D。

## 七、测试锁住入口

桌面侧补了三类测试：

- 托盘菜单：有舞台能力时出现子菜单，两个子项分别传 `free` 与 `theater`。
- 舞台窗口：`theater` 生成 `?stage=play`，`free` 回到裸路径。
- IPC：只有显式 `theater === true` 才透传，字符串 `'yes'` 被丢弃。

这些测试不复杂，但能防止后续重构把入口语义改回去。

## 八、入口设计的通用检查表

新增一个模式或页面时，可以按这五项检查：

1. 有没有用户可见入口，而不只是深链？
2. 入口是否说明了“打开的是哪个模式”？
3. 已打开的窗口会不会忽略新目标？
4. 目标参数有没有白名单校验？
5. 返回路径是否同样可达？

深链适合自动化和分享，不应该成为唯一入口。

## 九、结果

- 托盘、应用菜单与舞台内都能直接切换自由舞台/小剧场；已开窗时会按目标重新导航。
- 桌面舞台与托盘 20 项测试通过。
