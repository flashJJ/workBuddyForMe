# 小步平台化复盘：七个让重构安全落地的做法

平台化很容易变成一句空话：听起来什么都能插，实际每加一个东西还是要改内核。

这轮改造没有做插件市场，也没有拆仓库。只做了三件事：把能力分发、模型协议、动效内容从硬编码改成注册表或快照。规模不大，但足够验证方向。

下面七条，是这轮最值得留下的做法。

## 一、先证明没变，再证明能变

重构的顺序很重要。

我们先锁默认行为：

- 动效 golden 16 项快照，改造前后零差异。
- 能力包六类现有测试原样通过。
- provider 三个现有测试原样通过。

然后才加新能力测试：

- 注册自定义能力 kind，可启停、可卸载。
- 注册 mock 协议，可创建适配器。
- 注入单姿势内容，运行时只看到注入项。

如果反过来先写新能力测试，很容易在默认路径已经变了的情况下继续往前，最后分不清是“重构成功”还是“碰巧能跑”。

## 二、用数据表替代 switch，但不引入框架

能力 effect 原来 140 行，六类各写两遍。改造后是“一张表 + 三个查表函数”。

我们没有引入依赖注入容器，也没有做生命周期框架。原因很实际：

- 现有调用方只想要一个字符串句柄。
- 六类 handler 的依赖是同一份聚合对象。
- 引入框架会带来启动顺序、作用域与调试成本。

`Record<kind, handler>` 已经能提供类型完备性：新增 kind 时 TypeScript 会逼你补全。框架不是必需品。

## 三、默认值必须同源，不能拷贝

动效快照最容易犯的错是“默认值也复制一份”。

复制会让后续修改静态表时，默认快照不跟随，观感慢慢漂移。我们直接引用原数组，并写了一条 `toBe` 断言锁住它。

同样的原则适用于舞台默认形象：三个模式原来各有一份默认值，改一处不够。先列“默认值来源表”，再统一，才不会漏。

## 四、一次只开一个扩展口

这轮只开放了三个注册点，没有顺手做：

- 动效包安装格式。
- provider 能力元数据。
- 依赖拓扑与热加载。

每多开一个口，就多一组要维护的契约。平台化的价值不是“口越多越好”，而是“每个口都能稳定工作”。

我们明确写了 Non-Goals，并且在发布说明里保留。这样下一轮评估时，能清楚知道哪些是刻意没做，哪些是遗漏。

## 五、门禁前置，目录与行数也是设计

两次撞线很有代表性：

- 运行时文件 303 行，压缩签名回到 297 行。
- 测试目录 13 个文件，建子目录后回到 12 个。

如果没有门禁，这两处都会以“以后再拆”的形式留下。门禁不是敌人，它让“顺手加一点”变成“先想清楚放哪”。

结构规则最好在写代码前就知道：新内容放子目录，跨 feature 走 barrel，注册表保持叶子依赖。

## 六、入口和默认值都是产品行为

技术上“支持 3D”和“默认是 3D”是两件事。

小剧场早就用 3D，但普通舞台仍默认 2D，用户看到的就是 2D。深链早就能进小剧场，但没有按钮，用户就是找不到。

这轮补齐了两件事：

- 三种舞台模式的默认形象统一为 3D。
- 托盘、应用菜单、舞台内都有了自由舞台与小剧场的入口。

代码改动不大，用户感知很强。做平台化时，不能只盯着内部扩展点，也要看用户能不能到达。

## 七、切换方式可以先用“重”，以后再变“轻”

自由舞台与小剧场的切换，最后用了整页导航，而不是同页状态机。

这是一个刻意选择的“重”方案：

- 好处是状态干净，cast、剧本、音频不会互相污染。
- 代价是 VRM 重新加载，切换有等待。

为什么不一次做到同页无缝？因为那需要统一两套控制器的状态、计时器与音频 duck，回归面远大于入口改造。

先拿到入口收益，再决定要不要为无缝切换付出状态机成本。这是小步迭代的核心：**先解决最贵的问题，不是最完整的问题。**

## 八、指标对账

| 项 | 结果 |
|---|---|
| 能力 effect | 6 类零回归，新 kind 可注册 |
| provider | 2 个内置协议零回归，新协议可注册 |
| 动效 | 默认 golden 16 项零差异，注入快照可播放 |
| 舞台 | 三模式默认 3D，入口双向可达 |
| 测试 | core 57、ai 5、web 动效/剧本 215、web 舞台 65、desktop 20 |
| 迁移 | 0 |
| 门禁 | typecheck / lint / 行数 / 结构 / 循环 / ASCII 全绿 |

## 九、Non-Goals 复盘

这轮明确不做的事：

- 运行时代码插件与沙箱。
- 动效包、场景包的安装格式。
- 拆多仓与独立 npm 包。
- provider 能力元数据。
- 依赖拓扑与热加载。

不做不是保守，而是把风险留在可回滚的范围内。注册表可以随时退回 switch，快照可以随时退回静态表；一旦引入运行时插件，回滚成本会完全不同。

## 十、下一轮可以做什么

优先把 `motion-pack`、依赖拓扑、内容快照刷新与 provider 能力元数据用真实内容包验证，再决定扩多宽。

## 十一、一句话收尾

平台化不是把所有东西都变成插件，而是把“新增实现必须改内核”的地方，逐个变成“登记即可”。

这轮只改了三处，但方法可以复用：先证明没变，再证明能变；默认值同源；一次只开一个口；门禁前置；入口也是产品。

小步不是慢，小步是每一步都能回滚。
