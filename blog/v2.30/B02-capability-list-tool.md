# 让助手说清自己装了什么：capability_list 的设计取舍

「你装了哪些技能？」这是个很自然的问题，但模型往往答不上来。

原因不在模型，而在工具：能力安装结果只存在数据库里，模型没有查询入口。

v2.17 做了 `capability_search` 与 `capability_install`，一个负责找、一个负责装，却没有「列出已装」这一步。

## 一版清单要回答什么

不是把所有字段都吐出来，而是回答用户最关心的四件事：

1. 装了什么：id、名称、种类；
2. 能不能用：启用 / 停用；
3. 会带来什么：权限、effects、新增工具；
4. 可不可信：版本与签名状态。

这四类信息足以支撑一次对话里的解释，也不会泄露安装路径、密钥或正文。

## 输出为什么限制 30 条

能力包数量可能增长。如果把所有条目一次性塞回模型，会占用大量上下文预算，还会让回答变得冗长。

单次最多 30 条，超出时提示「另有 N 项未展示，请用 kind 或 status 缩小范围」。

这不是分页，而是让模型学会先过滤再列举。过滤参数只有两个：`kind` 与 `status`，语义直观，模型不容易用错。

## 不访问网络、不触发安装

`capability_list` 标为 `read`，只读当前运行环境的内存视图。

它不请求目录服务、不校验上游、不写数据库；未装配能力目录时返回「能力清单不可用」而不是空数组。

空数组会让模型误以为「什么都没装」，可读的不可用说明才能让它如实告诉用户。

## 目录缺失时返回什么

第三方安装的能力包可能不在内置目录常量里。

这时清单仍然返回安装信息（id、版本、状态、权限、安装时间），但 `effects` 与 `toolNames` 为空，来源标记为 `local`，安装策略标记为 `manual`。

这是诚实降级：不假装知道，也不隐藏已安装事实。

## 与审批详情共用一份数据

`capability_list` 与审批 `details` 都依赖同一个「已安装能力 + 目录快照」投影。

差异只在消费方：清单纯文本回灌模型；审批框走结构化 SSE 字段。

共用投影避免了两套字段定义在后续版本里漂移。

## 设置页与调试台

工具白名单里新增了「已安装能力清单」，默认不勾选，由用户决定是否给助手这个能力。

调试台的内置工具清单从 25 个更新为 26 个，并补了中英文展示名。

这两处不是装饰：一个让用户知道有这个工具，一个让开发者能验证它确实注册成功。

## 边界

不返回正文、密钥、安装路径与完整清单 JSON。

不做跨助手汇总：清单只反映当前助手可见的能力，避免把租户边界做没。

不做历史版本对比：版本回退与降级另有链路，不在只读清单里展开。

## 收尾

能力可见不是「多一个工具」，而是把「系统知道的事实」变成「模型能说出来的事实」。

这一步做完，用户问「你装了什么」时，终于能得到一个可核对的答案。
