# 内容包更新检查：只比较 commit，不动一行正文

内容包的导入模型是「固定版本 + 强校验」。

每个文件带 SHA-256 与字节数，整包再算一次哈希。任何一个不一致，导入整体拒绝。

这个模型保证了可复现，也带来一个用户体验问题：上游更新后，用户只会看到「哈希不一致」，不知道原因。

## 先区分两类失败

导入失败可能来自两种完全不同的原因：

1. 网络或上游服务问题：文件下载失败、超时、404；
2. 上游内容真的变了：文件哈希与内置清单不一致。

原来的错误文案把两者都叫「下载失败」或「校验失败」，用户无法判断该重试、该换网络，还是该等应用更新内容包清单。

## 检查更新要回答什么

只需要一个事实：上游最新 commit 与内置版本是否一致。

不需要下载正文，不需要比较文件级差异，也不需要知道改了哪几节。

所以接口做得很薄：

- 输入：内容包 id；
- 输出：当前版本、最新版本、是否有更新、检查时间、来源链接；
- 失败时多一个 `status: 'unavailable'` 与可读原因。

## commit 从哪里来

内置内容包的 `version` 是上游 commit 的短哈希，`sourceUrl` 是 GitHub 仓库地址。

检查时把仓库地址转成 GitHub API 的 commits 端点，取第一条记录的 `sha`，截前 7 位与内置版本比较。

不依赖本地缓存，也不把结果写数据库：每次检查都是一次即时快照。

## 为什么只支持 GitHub 仓库

当前内容包只有内置的 GitHub 来源。

对非 GitHub 来源，接口返回「来源不是 GitHub 仓库，暂不支持检查更新」，而不是猜测一个通用协议。

这比做一个半成品适配器更诚实，也为后续支持其他来源留出了独立的契约空间。

## 超时为什么是 10 秒

导入下载的单文件超时是 30 秒，因为要传正文。

更新检查只取一条 commit 元数据，10 秒足够；再长会让用户以为按钮卡住。

超时后不重试：手动检查本来就是用户主动行为，失败后可以再点一次，自动重试只会放大上游压力。

## 结果怎么用

界面只展示三种状态：

- 已是最新：显示当前短哈希；
- 上游有更新：显示 `current → latest`，附来源链接，并说明重新导入需要先删除旧知识库；
- 暂时无法检查：显示原因，不引导用户反复点击。

不提供「一键更新」按钮，因为那会绕过删除旧知识库的确认步骤。

## 与导入校验的关系

检查更新不改变导入校验。

即使检查显示「有更新」，用户重新导入时仍然会被哈希校验拒绝，直到应用下一次内置新的文件清单与整包哈希。

检查的作用是解释失败原因，而不是放宽校验。

## 边界

不下载、不比较文件级差异、不自动替换。

不缓存检查结果：上游 commit 可能随时变化，缓存会让「已是最新」变成过期结论。

不在页面加载时自动检查：只有用户点击按钮才发请求。

## 收尾

更新检查不是自动更新，它只是把「为什么导不进去」从一句哈希错误，变成一个可核对的版本事实。

对本地优先的应用来说，少一次静默替换，比多一个自动更新按钮更重要。
