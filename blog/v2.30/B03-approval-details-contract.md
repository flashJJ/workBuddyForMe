# 给 SSE 加一个字段：可选 details 的兼容策略

审批框要展示能力包详情，最直接的做法是改 `tool_confirmation_required` 事件，把目录信息塞进去。

但这是一个已经存在的流式契约，桌面端、Web 端、旧版本客户端都在消费它。字段怎么加，比加什么更重要。

## 先看约束

审批事件原本是这样：

- `callId`：挂起项 id；
- `tool`：工具名；
- `permission`：权限级别；
- `argsSummary`：参数摘要。

客户端据此渲染通用确认框。allow / deny 的回执走另一个接口，与事件字段无关。

新信息只在一种工具上出现：`capability_install`。

## 三条设计原则

第一，**字段可选**。旧客户端不认识 `details` 就忽略，不能因为多了字段导致解析失败。

第二，**缺省不出现**。不是所有工具都有能力目录快照，其他工具的事件里不应该出现一个空的 `details`，让客户端误判。

第三，**只放事实**。名称、来源、版本、签名状态、权限、effects、工具名都来自目录常量或安装记录，不做推测、不做翻译。

## 为什么不做成通用 metadata

一个更「通用」的方案是给事件加 `metadata: Record<string, unknown>`，任何工具都能往里塞东西。

这看起来很灵活，但会把契约变成垃圾桶：客户端无法知道该渲染什么，类型也无法收窄。

这一版选择具名结构 `details`，并明确只有 `capability_install` 填充。后续如果其他工具需要，再单独定义各自的字段。

## 服务端怎么填

工具调用循环在拿到参数后，按 `catalogId` 在已安装清单里查找对应条目。

找到就构造快照，找不到就不填——审批框退回原来的 `argsSummary`，不阻塞审批。

查找只读内存视图，不请求网络、不查安装包正文。

## 前端怎么接

挂起项类型新增可选 `details`，`confirmationFromPayload` 只在字段存在时复制。

确认框接收 `details`，默认区域显示名称、来源、版本与新增工具数，展开区显示权限、effects、签名与工具列表。

没有 `details` 时，组件行为与升级前完全一致。

## 旧客户端会怎样

旧客户端解析事件时会忽略未知字段，仍然拿到 `callId`、`tool`、`permission`、`argsSummary`，确认框照常出现。

它看不到详情，但不影响 allow / deny 的正确性。

这是「可选字段演进」的标准收益：新客户端得到更多信息，旧客户端不被打断。

## 审计快照为什么不放进 details

审批审计是另一条链路，写入的是治理账本的 `outcome` 字符串。

把完整 `details` JSON 塞进审计会让账本膨胀，也会引入字段演进压力。

所以审计只写一行摘要：`catalogId@version`、来源与 effects。两者共享事实，但不共享载荷格式。

## 边界

不改变 allow / deny 的决策语义。

不把详情做成可编辑输入：审批是确认，不是配置表单。

不保证 `details` 永远存在：目录条目被移除或参数非法时，退回摘要。

## 收尾

契约演进最怕的不是加字段，而是加得让旧客户端无法忽略。

可选、具名、缺省不出现，这三个约束让一个新增字段变成真正的增量，而不是一次隐性破坏。
