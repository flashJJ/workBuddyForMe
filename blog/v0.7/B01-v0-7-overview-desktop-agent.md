# 桌面 Agent 总览：给本地 AI 助手装上眼睛、手和脑

对话里的 AI 助手能查知识库、抓网页、看时间，但这些「活」全在结构化 API 的边界内。面对记事本、资源管理器和各种第三方软件——一个没有 API 的桌面世界——它完全没有抓手。

我们做的是一个本地优先、单人开发、以桌面方式交付的私人 AI 助手。给它加上桌面操作能力，本质是回答三个问题：**看得见屏幕、动得了键鼠、长任务不失控**。这篇是总览：桌面 Agent 由哪几块拼成，关键取舍是什么。「让 AI 接管电脑」这类方向并不新鲜，我们的约束始终是本地优先，且每一步都在用户眼皮底下、经过授权。

## 四块能力，四个问题

| 能力块 | 做了什么 | 回答的问题 |
|--------|----------|-----------|
| 屏幕感知 + 控制通道 | desktopCapturer 截图 + UIA 控件清单双通道；主进程 ↔ web server 本地控制通道 | 看不见 |
| 键鼠执行 | @nut-tree-fork/nut-js + 键鼠/窗口工具 + UIA 控件树定位 + SoM 标记兜底 + HITL 任务级批量授权 | 动不了 |
| 任务 Agent 循环 | 观察→决策→门控→执行→再观察的循环；步数/失败双上限；急停热键；行动日志落库；任务模式 UI | 长任务无编排 |
| 收尾 | 备份轨加入 tasks；playwright-mcp 评估后决定暂不接入；打包发布 | 运维与发布 |

前三块是 P0 主线，最后一块是桌面能力就位之后的运维收尾。

## 架构总图

```text
┌────────────── 浏览器渲染进程（Next.js） ──────────────┐
│  任务模式 UI（时间线 + 控制条） /api/tasks/* SSE       │
└────────────────────┬─────────────────────────────────┘
                     │ 127.0.0.1 + token
┌────────────────────▼────────────── web server（fork 子进程）─┐
│  tool-runtime：注册 screen_snapshot / mouse_* / keyboard_*   │
│  task-loop：观察→决策→门控→执行→再观察                        │
└────────────────────┬─────────────────────────────────────────┘
                     │ APP_COMPUTER_CHANNEL（127.0.0.1 + token）
┌────────────────────▼──────────────── desktop 主进程 ──────────┐
│  computer/screen.ts（desktopCapturer 抓屏 + UIA 控件清单）      │
│  computer/input.ts（nut-js 键鼠执行 + 半透明指示圈）            │
│  globalShortcut：Ctrl+Alt+Esc → POST /api/tasks/stop-all       │
└───────────────────────────────────────────────────────────────┘
```

三个关键架构事实：

**桌面能力的宿主是 Electron 主进程，不是 web server**。web server 是纯 Node（打包后由主进程 fork），没有桌面 API。因此形态是「主进程做能力宿主，web server 经本地控制通道调用」——通道走 127.0.0.1 + 随机 token 鉴权；纯 web 模式（没有 desktop 壳）下，工具注册时即探测通道，缺失就隐藏。

**桌面工具与内置工具同链**。`screen_snapshot`、`mouse_click` 等直接注册进对话版已有的 tool-runtime 统一表，模型看到的 tool_calls schema 与 `current_time` 之类的内置工具没有区别。权限分级复用既有的 read/write/danger 三级——键鼠工具统一是 danger 级，整套 HITL 确认链路原样复用。

**任务循环是新的顶层状态机，不是 tool-call-loop 的扩展**。对话是「一问一答 + 工具调用」；任务是「给一个目标，循环观察决策直到完成或被喊停」。两者共用 SSE 事件通道，但循环骨架独立（`core/agent/task-loop.ts`），步数/失败双上限、熔断联动、急停都长在这个骨架里。

## 关键决策速览

**键鼠库选 nut-js 社区 fork，弃 robotjs**。robotjs 停更 5 年、NAN 老架构没有现代 prebuilt，新 Node ABI 下编译即炸；`@nut-tree-fork/nut-js` 是社区维护的 N-API prebuilt 版本，跨 ABI 稳定。选型过程后文单独展开。

**坐标定位混合分层：UIA 控件树优先 → SoM 编号标记兜底 → 纯坐标最终兜底**。qwen2.5vl 7B 纯视觉做 5 步复合任务成功率约 40%，不能单押。UIA 控件树能拿到目标应用的控件名和精确矩形，是确定性定位，覆盖标准 Win32/WPF/Qt 应用；遇到自绘 UI/Electron 窗口拿不到控件时，在截图上叠加编号标记，让模型选编号而不是输出像素坐标，把回归问题变成分类问题。后文展开。

**任务循环的生命周期归 SSE /events 所有，不是 POST 创建时启动**。`POST /api/tasks` 只创建一个 queued run；前端开 EventSource 订阅 /events 时才启动循环；客户端断线 → `request.signal` abort → 循环以 user_stop 终态退出。急停热键即使循环不活跃也安全（stopAll 返回 0）。后文展开。

**playwright-mcp 评估后暂不接入**。打包体积会涨约 280MB（chromium bundle），而核心场景已经被键鼠 + screen_snapshot + fetch_webpage 覆盖。架构上留了口子（allowedTools 已支持 `mcp:` 前缀），后续重新评估时无需动架构。后文有完整评估记录。

## 明确不做什么

- 完全无确认的自主执行（安全红线：danger 动作必须至少在任务级授权一次）
- 远程控制其他设备 / 移动端
- 游戏与 3D 应用操作（DirectX 独占渲染截图黑屏，投入产出比极低）
- 多智能体编排（留到后续）
- 强制依赖云端模型（任务模式可以用本地视觉模型全离线跑，云端只是可选加速）

## 测试基线

合入前全部门禁绿：check（typecheck + lint + 单文件 ≤300 行）/ 单测 12 包 390+ 测 / 集成 12 / E2E 7/7。其中任务循环模块含状态机、上限、熔断联动 60+ 测；UIA 控件树与 SoM 标记各 15 测；急停热键与 stop-all 路由在 tasks.test 里有 5 测覆盖。

手测验收：启动记事本写一段话再保存——走 UIA 定位「记事本」窗口、keyboard_type 输入、keyboard_press Ctrl+S 保存。

## 收尾

这一轮把助手的「手」和「眼」接到了桌面上——**屏幕感知给眼睛，键鼠执行给手，任务循环给脑**，并用「HITL 任务级授权 + 步数/失败双上限 + 全局急停热键」三层安全网回答了「桌面操作怎么不失控」。核心取舍仍是本地优先：宁可走 Electron 主进程作能力宿主的分层架构，也不依赖云端视觉服务。
