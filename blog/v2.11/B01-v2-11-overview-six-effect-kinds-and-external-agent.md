# 从两类到六类：把「能力装卸」做成统一约束，再让外部代理真的跑起来

一个本地优先的桌面 AI 应用，能力通常不是「没有」，而是「各走各的入口」：技能要手工放目录，MCP 要手填启动命令，工作流、桌宠动作、事件剧本、报告卡片各自有各自的页面。用户能感觉到功能在，却感觉不到「它被安装了、被启用了、也能被干净地撤掉」。

上一阶段把技能与 MCP 两类能力做成了可装卸的包。这一步要回答两个问题：**剩下四类资源能不能也装进同一个包？外部代理除了一个空接口，能不能真的运行一次、留下证据、再安全地停下？**

## 一、先看缺口，而不是先看功能

四类资源各有各的「半成品」：

| 资源 | 已有的能力 | 缺的那一步 |
|---|---|---|
| 工作流 | 图编辑、版本、发布、试运行 | 从包里的图到「可运行工作流」的接线 |
| 桌宠动作 | 动作导入、双校验、动作池 | 从包里的动画文件到「动作资产」的接线 |
| 事件剧本 | 声明式事件、导演三锁 | 用户安装剧本的存储与触发入口 |
| 报告卡片 | 运行汇总、Markdown/CSV 导出 | 声明式卡片的数据契约与渲染位 |

它们缺的不是新框架，而是四条「资源 → 可逆副作用」的接线。外部代理则连运行形态都没有：注册表默认为空，管理页只能显示「尚未接入」。

## 二、统一约束：每一类 kind 都有明确的副作用句柄

六类能力共享同一套生命周期：安装、启用、停用、卸载。启用时返回一个 `effectRef`，它必须指向一个真实存在的副作用对象，而不是一个状态字符串。

| kind | 启用后产生什么 | `effectRef` |
|---|---|---|
| 技能 | 技能目录与状态行 | 技能名 |
| MCP | 已注册的服务器 | 服务器 id |
| 工作流 | 已发布的图与版本 | 工作流 id |
| 桌宠动作 | 动作资产与文件 | 动作 id |
| 事件剧本 | 可被导演消费的剧本定义 | 剧本 id |
| 报告卡片 | 可被报告页渲染的声明 | 卡片 id |

这条约束看起来只是「多一个字段」，实际决定了停用与卸载怎么写：停用必须按句柄撤掉副作用，卸载必须先停用再清包。没有句柄，卸载只能靠猜。

## 三、回滚纪律：失败不能留下半启用状态

安装失败要回滚到 `disabled`，并且删除已经落盘的文件与数据库行。启用失败不能把状态写成「已启用但效果没生效」。停用失败则保留 `enabled` 状态与可读错误，让人还有机会重试。

工作流是最特殊的一类：停用不删行，卸载也要先判断「有没有运行记录或对外端点」。有历史的东西不能因为一次卸载就消失；没有历史且无人引用时才真正删行。这个策略不是宽容，而是数据归属问题——运行记录属于用户，不属于能力包。

## 四、外部代理：先定运行协议，再谈「接哪个 CLI」

外部代理不做市场，也不内置任何命令。它只支持一种最小实现：用户显式配置一个本地命令行程序，通过标准输入输出跑严格的行式协议。

三条红线先立住：

- **默认关闭**：配置为空时注册表为空，启动路径上没有「等待外部代理」的分支；
- **逐次审批**：每次运行先出现一条审批，拒绝或超时就不启动进程；
- **密钥不出机**：输入契约里没有凭据字段，外部程序用自己的登录态，宿主不读取也不传递供应商密钥。

在这三条之下，超时、输出上限、取消杀进程树才有意义。

## 五、把「证据」当成功能的一部分

外部代理最容易被忽略的不是执行，而是执行之后留下了什么。一次运行至少要在三个地方可见：运行记录表、工作信号（桌宠与审批页共用的实时状态）、会话事件时间线。终态还要能回到发起它的会话里，并且只回投一次。

如果只写「运行结束」四个字，用户无法回答三个基本问题：它跑了吗、失败在哪、下次还能不能复现。证据不是调试附件，是产品的一部分。

## 六、管理页把「可以装卸」变成可操作

管理页做了三件小事：按 kind 筛选，给每类 effect 句柄一个人话标签，提供六类示例包的下载；底部放入外部代理区，运行记录可按深链定位并高亮。设置页则列出「来自能力包的剧本」，试演跳到对话页播放一次。

这些不是装饰。没有筛选，六类混在一起像一团配置；没有示例，用户不知道一个合法的包长什么样；没有来源标注，用户分不清内置剧本和安装剧本。

示例包是契约的可执行样本，不是演示素材。六类各一个最小包：技能带清单与技能文件，MCP 带服务器配置，工作流带一张两节点图，动作带一段动画文件，剧本带一次台词演出，卡片带一个四指标声明。它们走的是与用户上传完全相同的校验链，所以「示例能装」等价于「最小合法包长什么样」有据可查；包坏在哪一步，返回的错误也能直接对照。

外部代理区放在同一页底部，而不是另开一个设置页，是因为它和能力包回答同一个问题：这台机器上到底有哪些外部能力被接入了。运行记录支持深链定位——从列表点进某次运行，页面滚动到对应行并高亮，找证据不需要用户自己翻日志。

## 七、验证：先证明坏包会被拒绝，再证明好包能回滚

这一阶段的门禁不只看功能能用，还看失败是否干净：

- 六类示例逐类安装、启用、停用、卸载；
- 坏包逐类拒绝：非法图、坏动画文件、非用户命名空间的剧本、未知指标、缺校验和、路径穿越；
- 剧本重复 id 返回冲突，停用后短语不再触发；
- 外部代理覆盖拒绝审批、超时、输出超限、取消、未知协议帧与提前退出；
- 生产模式的完整端到端与桌面冒烟不降级。

失败用例比成功用例更值得写。六类坏包逐类拒绝，意味着校验链在六个方向上都被真实数据走过一遍；外部代理的拒绝审批、超时、输出超限、取消、未知帧与提前退出，也都是「让坏路径先发生一次」。这些用例不会让功能变多，但会让「出错时系统还在不在」这个问题有答案。

最后一组数字是这样的：单元测试覆盖五个包，生产模式端到端 122 例全通过，桌面冒烟 10/11，未过的一项依赖真实桌面会话。

安装包第一次构建出来有 1.23GB，追查后发现构建产物把开发缓存也带进了发行目录，裁掉之后回到约 192MB。这个数字解释了为什么发布路径必须单独验证：开发态、单测、端到端都只证明代码正确，不证明「装到用户机器上的那一包东西」是干净的。发行目录里混进开发缓存，功能一切正常，代价只体现在下载与安装时间上。

## 八、这一阶段得到什么

能力包从「两类资源的装卸」变成了「六类资源的统一约束」；外部代理从「一个接口」变成了「一条可运行、可审批、可取消、可回投的本地进程链路」。

它仍然没有变成插件市场，也没有执行包里的任意代码。变化的是边界：每一类资源都知道自己的副作用句柄，每一次外部运行都知道自己的证据落在哪里。
