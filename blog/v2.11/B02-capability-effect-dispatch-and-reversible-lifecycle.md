# 六类能力，一个分派器：可逆 effect 的接口设计

能力包有六种 kind，但「启用」这件事只能有一个入口。否则每新增一类资源，安装服务里就会多一条 `if`，错误处理、回滚、日志也会各写一遍。

这次设计的核心不是「支持更多 kind」，而是把六类资源收进同一个分派器：**安装服务只负责校验、落盘、建行与状态；真正产生副作用的代码，按 kind 分文件、按依赖注入。**

## 一、分派器只做三件事

分派器暴露三个函数：启用、停用、卸载。每个函数的签名都只有三个参数：清单、包目录（仅启用需要）、依赖集合。

```ts
enable(manifest, packDir, deps): string;
disable(manifest, effectRef, deps): void;
uninstall(manifest, effectRef, deps): void;
```

返回值是 `effectRef`，也就是副作用句柄。它不返回「成功/失败」布尔值——失败一律抛领域错误，由上层转成 422 或 500。这样调用方只有一个错误通道，不会出现「返回 false 但没人处理」的中间态。

## 二、为什么按 kind 拆文件

六类 effect 的依赖完全不同：技能要目录服务，MCP 要注册表，工作流要仓储，动作要动服务平台，剧本与卡片要各自的表。把它们塞进一个文件，很快就会撞上单文件行数门禁，也会让测试无法只装配需要的依赖。

拆开之后，每个文件只依赖自己需要的东西：

```ts
interface WorkflowEffectDeps {
  workflows: WorkflowRepository;
}

interface PetActionEffectDeps {
  motions: MotionService;
}
```

分派器把总依赖收拢，再按分支收窄。测试可以只构造一个内存数据库与一个假注册表，不需要把六个服务全部实例化。

## 三、句柄必须可持久化

`effectRef` 会被写进能力包状态行，重启后仍然可读。这意味着停用与卸载不能依赖进程内缓存，也不能依赖「重新扫描」来发现副作用。

一个反例是技能：启用时复制目录，停用时如果只删数据库行，磁盘上的目录会变成孤儿。另一个反例是 MCP：注册表是进程内的，重启后注册丢失，但状态行还写着已启用。正确的做法是停用时按句柄重新执行撤销：技能删目录、MCP 按 id 移除、工作流按 id 置为禁用。

六类的撤销动作对照如下：

| kind | 启用时创建 | 停用时按句柄撤销 | 备注 |
|---|---|---|---|
| 技能 | 目录 + 状态行 | 删目录、删状态行 | 目录名即句柄 |
| MCP | 进程内服务器 | 按 id 从注册表移除 | 重启后需重新注册 |
| 工作流 | 已发布图与版本 | 置为禁用，不删行 | 有运行时保留 |
| 桌宠动作 | 动作资产与文件 | 删资产（含文件） | 与导入校验同源 |
| 事件剧本 | 启用行 | 把启用标记置 0 | 卸载才删行 |
| 报告卡片 | 卡片声明行 | 删声明行 | 同 id 允许先删后建 |

表里没有「改状态即完成」的行。每一行的停用都要落到一个真实对象上，这也是为什么句柄必须能跨进程读出来。

## 四、安装失败与启用失败的回滚不是一回事

安装分两段：先把包文件落到能力包目录、写一条 `disabled` 状态行，再调用启用。启用失败时，安装服务要删掉整个包目录与状态行，因为这次安装从未成立。

启用失败发生在「包已经安装」的前提下。此时不能删包，只能把状态改回 `disabled` 并记录 `lastError`。用户还能重试，或者卸载。

这个区别决定了错误信息的归属：安装失败的错误属于上传请求，启用失败的错误属于能力包状态。后者必须出现在列表里，否则用户只知道「点了一下没反应」。

## 五、卸载不是 disable 的别名

停用只撤副作用，保留包与状态；卸载要撤副作用、清包、删状态。工作流例外：如果它有运行记录或被端点引用，就不能删行，只能保留一条带来源标记的禁用行。

这条例外必须写在卸载层，而不是工作流 effect 里，因为只有卸载层知道「这一次是彻底不要了，还是只是暂时停用」。

```ts
if (manifest.kind === 'workflow') {
  uninstallWorkflow(effectRef, deps); // 有运行/端点 → 保留禁用行
  return;
}
if (manifest.kind === 'event-script') {
  uninstallEventScript(effectRef, deps); // 删行
}
```

其余 kind 的卸载等于「先 disable 再清包」，所以分派器只对两个需要额外清理的 kind 做分支。

## 六、冲突与占用要前置判断

剧本的 id 是全局的，来自用户命名空间（例如 `usr.` 前缀）。两个包声明同一个 id 时，安装不能「后者覆盖前者」。正确的时机是在启用前查一次行：已在其它包启用就返回冲突；同一个包重复启用则只把 `enabled` 置回 1。

卡片则允许同一 id 先删后建，因为它的配置以最新安装为准，且没有运行历史可丢。两类资源的策略不同，不能用一个通用规则糊过去。

## 七、状态机保持最小

能力包只有两个状态：`enabled` 与 `disabled`。没有 `installing`、`error`、`uninstalling`。安装过程中的中间态只存在于一次请求内，不需要持久化；失败要么回滚，要么落成 `disabled + lastError`。

状态越少，列表越可信。用户看到的每一行都对应一个确定的副作用状态，而不是「可能正在做什么」。

## 八、这套分派器的取舍

- 不为每类 kind 引入独立插件接口：六类都是内置资源，不需要动态加载。
- 不把 effect 写成事件：失败要同步返回给安装请求，事件总线会把错误变成异步噪声。
- 不允许 effect 自行改能力包状态：状态由安装服务统一写，effect 只负责副作用。
- 不追求「任意资源可扩展」：新增一类 kind 仍要改清单、权限映射、分派器与示例，这是有意的摩擦。

可逆不是一句设计口号，它由三样东西共同保证：明确的句柄、按句柄实现的撤销、以及在失败路径上不留半成品。分派器只是把这三样东西固定在一个入口上。
