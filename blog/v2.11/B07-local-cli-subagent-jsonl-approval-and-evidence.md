# 本地 CLI 外部代理：一行一 JSON、两层审批，和一条可回收的进程

上一阶段给外部代理留了一个接口，但没有实现：注册表默认为空，管理页写着「尚未接入」。这一阶段补上第一个实现——用户配置一个本地命令行程序，宿主通过标准输入输出与它通信。

它必须同时满足三个约束：默认关闭、每次运行先审批、密钥不出机。这篇讲协议、审批、进程回收与证据。

## 一、为什么是 CLI，而不是先接某个 SDK

外部代理的常见形态有四种：同进程子代理、协议客户端、命令行编码代理、桌面自动化。选 CLI 作为第一个实现，是因为它的边界最小：

- 不需要理解对方的模型与工具协议，只需要约定几行 JSON；
- 不需要宿主托管凭据，对方用自己的登录态；
- 可以用一个几十行的脚本做测试夹具，不依赖真实供应商；
- 失败模式清晰：超时、输出超限、提前退出、取消。

协议优先（ACP 之类）作为第二实现更合适，先接 CLI 能把「审批与证据」这套宿主逻辑跑通。

## 二、协议：严格 JSON Lines

宿主写一行运行请求：

```json
{"type":"run","protocol":1,"goal":"整理当前目录的 README","budget":{"maxRounds":6}}
```

子进程回四类帧，每行一个 JSON：

```json
{"type":"delta","text":"..."}
{"type":"permission","id":"p1","title":"写入文件","detail":"README.md"}
{"type":"done","summary":"..."}
{"type":"error","code":"FAILED","message":"..."}
```

约束是：单行不超过 64KB；未知 `type` 视为协议错误并终止；非 JSON 行忽略，但计入诊断（最多十条）。宿主不解析自然语言输出，只认这四个帧。

审批回写是另一行：

```json
{"type":"permission_result","id":"p1","allow":false}
```

## 三、进程：argv 数组、shell 关闭、最小环境

启动命令用 `spawn(command, args, { shell: false })`。命令只接受绝对路径或能在 PATH 中解析的可执行文件；参数数组原样传递，不做字符串拼接，也不经过 shell。

环境变量只保留最小集合：PATH、PATHEXT、系统根目录、临时目录、家目录、语言。供应商密钥、应用 token 一律不注入。

一个细节是 Windows 上的批处理脚本：`shell: false` 下 Node 无法直接启动 `.cmd`/`.bat`。把它们视为「命令不可用」，比「可用但必然失败」更诚实。

## 四、超时、输出上限、取消：三种失败都要杀进程树

一次运行有三个硬熔断：

- **超时**：默认十分钟，服务端钳制在 60 秒到 30 分钟；
- **输出上限**：默认 2MB，钳制在 64KB 到 8MB，统计的是标准输出原始字节；
- **取消**：用户点取消或关闭开关。

任何一项触发，都不能只结束父进程。Windows 用 `taskkill /T /F` 回收进程树，其它平台用进程组信号；确认回收后才写终态。否则会留下一个后台子进程，继续占用文件或端口。

终态只有三种：完成、失败、取消。失败带机器码：超时、输出超限、协议错误、启动失败、提前退出。

## 五、两层审批，不能合并

运行前有一条审批：标题是「运行外部代理」，参数摘要展示目标，关联运行 id，五分钟过期。拒绝或超时就不启动进程，运行记录收敛为取消。

子进程运行中可能发来 permission 帧，这是第二条审批：标题是具体的动作（例如「写入文件」），id 带运行 id 与帧 id 前缀。拒绝只回写 `allow:false`，不强制终止子进程——是否继续由对方协议决定。

两层不能合并成一条，因为它们的语义不同：

| 审批 | 时机 | 拒绝的后果 |
|---|---|---|
| 运行审批 | spawn 前 | 不启动进程，整次运行取消 |
| 帧审批 | 进程运行中 | 只拒绝该动作，进程可能继续 |

运行审批被拒绝时，不会出现任何 permission 帧，这个顺序也必须保证。

## 六、证据：三处留痕，一处回投

一次运行需要在三个地方可见：

- **运行记录表**：提供方、目标、工作目录、状态、摘要、错误码、输出字节、开始/结束时间；
- **工作信号**：桌宠与审批页共用的实时状态，运行中显示「请求外部代理」，等待审批时进入等待态；
- **会话事件**：`subagent_started` 与 `subagent_finished`，只记状态与摘要，不写逐帧 delta。

如果运行带了会话 id，终态还要回投一条助手消息。回投用「运行 id + 类型」作为幂等键：同一次运行无论触发多少次终态，只追加一次消息。

失败也要回投，内容是可读原因，而不是一句「出错了」。外部代理不是黑盒，它的失败必须能被人理解。

## 七、cwd 是安全参数，不是便利参数

工作目录必须由用户显式填写，并且经过校验：必须存在、必须是目录、必须绝对路径；拒绝 UNC、系统盘根目录、系统目录、应用数据目录。

这条规则看起来苛刻，但外部代理会以当前用户权限执行任意命令。工作目录决定了它能读写哪些文件，不能默认成家目录，也不能默认成应用自己的数据目录。

符号链接的真实路径校验留到后续阶段；当前先保证「用户明确选了一个目录」。

## 八、开关关闭要立刻生效

关闭外部代理开关时，不只是把设置字段置为 false：要注销提供方、取消在途运行、让列表变回空。否则用户以为关了，后台还有一个进程在跑。

设置变更后同步注册表，注册表按配置签名缓存：命令、参数、超时、输出上限任一变化就重建提供方；配置为空则注销。

## 九、验证用真实进程，而不是假接口

协议正确性不能只靠单元测试里的假对象。测试夹具是一个真实的 Node 脚本，通过命令行参数切换行为：

- 输出两段 delta 后 done；
- 发 permission 帧，按回写结果 done；
- 发 error 帧；
- 发未知 type；
- 不输出、等待超时；
- 狂刷输出触发上限；
- 直接退出；
- 等待取消。

这八条路径覆盖了协议、审批、熔断与进程回收。只有真实 spawn 才能证明「杀进程树」不是一句注释。

## 十、这一条链路的边界

外部代理现在能跑，但仍然只支持一个实现、一个协议、一个运行入口。它不共享宿主密钥，不内置任何命令，不自动安装，不在后台常驻。

「能跑」不是终点，真正的标准是：用户拒绝审批后什么都没发生，超时后进程被回收，运行结束后证据可查，同一次运行只回投一次。做到这四点，外部代理才算接进了产品，而不是接进了一个玩具。
