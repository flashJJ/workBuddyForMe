# 让台词能写死在包里：事件 schema 的向后兼容扩展

内置事件剧本一直用 i18n 键：标题是 `titleKey`，台词是 `lineKey`，运行时再查词典。用户安装的剧本没有词典条目，如果继续强制要求 key，安装者就要把自己的文案塞进应用的翻译文件——这显然不成立。

需要让剧本支持字面量标题与台词，同时不能破坏内置剧本、不能改变导演与播放器的行为。这篇讲这次 schema 扩展的取舍。

## 一、二选一，而不是「两个都可选」

最直觉的做法是同时允许 `titleKey` 和 `title`，有哪个用哪个。但这会留下一个模糊状态：两个都有时用谁？两个都没有时算合法吗？

正确的约束是**恰有其一**：

```ts
const def = z.object({
  titleKey: z.string().optional(),
  title: z.string().min(1).max(40).optional(),
  // ...
}).superRefine((value, ctx) => {
  if (Boolean(value.titleKey) !== Boolean(value.title)) {
    ctx.addIssue({ code: 'custom', message: 'titleKey 与 title 必须且只能有一个' });
  }
});
```

台词同理：`lineKey` 与 `text` 恰有其一。这样运行时没有「回退链」，每个剧本只有一种台词来源。

## 二、内置剧本零改动

内置剧本继续使用 `titleKey` / `lineKey`，schema 扩展对它们是透明的。标题读取统一走一个 helper：

```ts
function resolveTitle(def, t) {
  return def.title ?? t(def.titleKey);
}
```

UI 里有四处直接读 `titleKey`（设置事件面板、预览菜单、自定义规则列表与表单），全部改成走 helper。不这么做，安装剧本在这些位置会显示空标题。

## 三、台词运行时：从字符串到判别对象

原来的播放器接口接收一个字符串 `lineKey`，内部查词典。现在台词有两种来源，接口必须能区分，否则播放器会试图把一句中文当成 i18n 键去解析。

于是把入参改成判别对象：

```ts
type EventSpeechLine = { key: string } | { text: string };
```

导演执行每个 speech step 时组装对象：有 `text` 就给 `{ text }`，否则给 `{ key }`。播放器只对 `key` 走词典，`text` 原样呈现。

```ts
async speech(line, speak, signal) {
  const text = 'text' in line ? line.text : resolveLine(line.key);
  await present(text, speak, signal);
}
```

这是一个破坏性签名变更，但改动面可控：core 的运行器、web 的播放器、导演委托 sink、测试桩，全部同步。好处是类型系统会强制每个调用方想清楚「这是键还是文案」，不会再出现运行期误解析。

## 四、为什么不在播放器里做兼容

另一种方案是保留字符串入参，在播放器里判断「这个字符串像不像 key」：包含点号就当 key，否则当文案。这个启发式一定有错判：用户完全可能写一句包含点号的台词，内置 key 也可能没有点号。

判别对象把「来源」变成类型信息，而不是靠字符串形状猜测。多写一个字段，换来的是运行时没有歧义。

## 五、安装剧本的额外约束

字面量能力只对安装剧本开放，但安装剧本还有两条额外规则：

- id 必须在用户命名空间内（例如 `usr.` 加小写字母数字），避免与内置事件 id 冲突；
- 必须使用 `title` 与 `text`，不允许再引用词典键。

这两条由能力包负载的 schema 校验，而不是事件 schema 本身。事件 schema 要服务内置与安装两类定义，不能把「安装剧本的限制」写进通用契约。

反过来也要限制：安装剧本不允许保留 `titleKey` 回退。否则一个包可以声明 `titleKey` 指向应用内置词典，等于让外部包借用内置文案，既难排查也模糊归属。字面量要求把「这个包说什么话」完整写在包内。

## 六、兼容性验证要覆盖三种读者

- 内置剧本：仍然按 key 解析，行为零变化；
- 安装剧本：字面量直接呈现，不需要词典；
- 旧数据：数据库里已有的内置定义没有新增字段，解析仍然通过。

测试里专门保留一个「只有 lineKey」的步骤和一个「只有 text」的步骤，再加上「两个都有」「两个都没有」的负例。schema 的「恰有其一」是这次扩展的核心，负例比正例更重要。

还有一个隐性收益：类型系统把「键还是文案」变成编译期问题。以前播放器接收字符串，误传一句中文只会在运行时表现为「词典里找不到这个键」；改成判别对象后，调用方要么给出 key，要么明确标记 text，漏写字段直接编译失败。这类改动一次性疼，之后每一个新增调用点都被强制想清楚来源。

## 七、小结

向后兼容不是「加可选字段」这么简单，它要求同时满足三件事：旧数据不改、旧行为不变、新来源有明确类型。二选一约束解决了前两件，判别对象解决了第三件。

下一步是把这种定义真正接到导演：剧本怎么存、短语怎么匹配、三道锁为什么不能被能力包绕过。
