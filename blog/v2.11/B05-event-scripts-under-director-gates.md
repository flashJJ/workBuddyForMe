# 安装剧本为什么不能绕过导演：三条闸门与一次短语匹配

让能力包携带事件剧本，最容易走错的一步是「给安装剧本开一条直通车」：新剧本直接注册进导演，跳过内置剧本的白名单与冷却。功能上很快就能跑通，产品上却会破坏事件系统最贵的部分——**打扰控制**。

这篇讲安装剧本的接入方式：怎么存、怎么触发、为什么所有闸门都保留。

## 一、剧本存哪：一张只读表

安装剧本不写进内置常量，而是落到一张单独的存储表。每行包含：剧本 id、来源包 id、名称、完整定义 JSON、启用标记、创建时间。

读取时只取启用行，并且对定义做一次 schema 解析；解析失败的行直接跳过，不让一条坏数据拖垮整个列表。

```text
payload/script.json
  → { definition, trigger: { kind: 'phrase', phrases: [...] } }
  → 校验 → 写行（enabled=1）→ effectRef = definition.id
```

定义本身复用事件契约：八类步进、优先级、打断策略、冷却、每日上限、台词锁。能力包不能新增步进类型，也不能带自定义条件函数。

## 二、id 全局唯一，跨包占用要拒绝

剧本 id 是导演识别事件的键。两个包声明同一个 id，如果后者覆盖前者，用户会看到「装了一个新剧本，另一个悄悄变了」。

因此启用前先查：同 id 已存在且属于其它包、并且处于启用状态，返回冲突；同一个包重复启用，只把启用标记置回 1，不重建定义。停用只改标记，卸载才删行。

这条规则与「包是资源的归属」一致：同一份剧本可以随包重装，但不能被另一个包抢走。

跨包冲突的判断只看启用状态，不看安装状态：两个包都可以装着同一个剧本定义，但同时只能有一个生效。这样用户在换包时不必先卸载旧的，冲突错误也只会在真正抢占时出现。

## 三、触发：本地短语匹配，命中后按定义准入

安装剧本的触发方式只有一种：用户在对话里说了某个短语。匹配完全在本地完成：包含匹配、不区分大小写、不上网、不写正则。

命中之后，不能调用「按内置 id 触发」的入口，因为导演的该入口只认内置注册表。于是新增一条按定义准入的路径：

```ts
triggerDefinition(def) {
  bridgeEventFire(def.id);        // 观测总线仍可看到
  const ctx = buildConditionContext(...);
  return admit(def, ctx);         // 导演仍走完整闸门
}
```

关键在最后一行：安装剧本与内置剧本共用同一个 `admit`。导演内部的所有检查——总开关、勿扰、对话锁、冷却×频率档、每日上限、队列上限——一个都没有少。

约束在安装时就已经收紧：一个剧本最多五条短语，每条 2 到 24 个字符，去掉首尾空白后仍不能为空。上限不是拍脑袋——短语太短会在正常对话里频繁误命中，太长则几乎没人会说出完整句子。五条也够覆盖同一意图的几种说法，再多就该拆成两个剧本。

## 四、为什么不做「剧本注册表」

另一种设计是把安装剧本动态注册进导演的全局注册表，让内置与安装走同一张表。听起来更统一，实际会引入跨会话状态：注册表是进程内单例，切换助手、切换会话、热重载时都可能残留上一份定义。

按定义准入没有这个问题：定义来自本次请求的启用列表，准入是一次纯调用。导演不需要知道「有哪些安装剧本」，只需要知道「现在要执行这个定义」。

代价是触发器要自己拿到定义并判断是否启用，收益是状态不跨会话串。

## 五、设置页的列表与试演

设置页新增「来自能力包的剧本」：显示标题、触发短语、来源包，并提供一个试演入口。

试演不直接在设置页播放——那里没有形象与语音出口。它跳转到对话页，带一个剧本 id 参数；对话页拿到启用剧本后，按定义执行一次手动预览，然后清掉参数。

手动预览绕过冷却与勿扰，但仍受对话锁与「当前是否已有演出」限制。这与内置剧本的试运行口径一致。

试演参数播放一次后立即清除，也有实际原因：这个参数只用于「现在播这一次」，留在地址栏里会让刷新变成第二次播放，分享出去更会变成别人打开就播。手动预览的语义是用户主动要看，不该被一条 URL 复制。

## 六、停用后立刻不再触发

触发列表来自「启用行」查询，并带有短缓存。停用剧本后，缓存过期即不再返回它；更关键的是，准入之前没有额外的「是否启用」判断，因为列表本身已经过滤。

卸载则删行。已经排队但还没开始的演出怎么办？导演的队列按定义执行，不会回查存储；最坏情况是用户刚卸载，队列里还排着一次。这是可接受的窗口，因为卸载不是安全操作，不需要强同步取消。

这也解释了为什么不给触发列表加「立即失效」的强同步：导演执行的是已经取到的定义，而不是每次台词前回查数据库。停用与卸载影响的是「下一次取列表」，不是「已经开始的这一次」。把这条边界说清楚，比再加一层锁更可靠。

## 七、三道锁是产品边界，不是技术细节

事件系统里有大量「能不能现在演」的判断：深夜勿扰、用户正在对话、同一剧本刚演过、今天演太多次、队列已满。它们共同回答一个问题：**角色可以主动，但不能烦人。**

能力包是外部输入，最容易破坏这条边界。所以安装剧本的接入原则是：可以新增内容，不能新增权力。它可以决定演什么、说什么、做什么表情，但不能决定「什么时候必须演」。

具体到接入方式，三条约束就够了：内容由包提供、时机由导演决定、额度按剧本累计。冷却与每日上限的计数键是剧本 id，所以安装剧本和内置剧本用同一套额度账本，不会因为来源不同就多出一次机会。

## 八、验证清单

- 非法步进、未知表情、缺 `text` 的台词在安装时被拒绝；
- 同一个 id 跨包安装返回冲突；
- 停用后短语不再触发；
- 剧本受勿扰、对话锁、冷却、每日上限与队列约束；
- 设置页只列出启用剧本，试演能跳转并播放一次。

做到这里，「能力包能装剧本」才不只是多了一张表，而是多了一类受同一套产品纪律约束的内容。
