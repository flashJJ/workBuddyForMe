# 文档解析做完了，为什么用户还是不敢信

一个知识库功能上线后，最常见的落差不是「解析不出来」，而是「解析过了，但状态说不清」。

用户上传一份合同，问「付款比例是多少」。回答给了 30%，还带一个精确到单元格的引用。用户点开一看，表格错位，30% 其实属于另一行。

又或者，用户翻开一份两年前导入的文档，结构面板只有一句「尚未解析」，没有解释、没有入口，只能重新上传一遍。

这两种情况看起来相反，其实是同一个问题：系统没有把「解析结果可不可信」讲清楚。

## 一、存量文档停在旧版本

结构化解析是后来才有的能力。升级前的文档只做了文本分片，没有章节、表格与坐标。

升级后，新文档有结构，旧文档没有。但界面只显示「尚未解析」，用户不知道这是正常的、失败的，还是需要自己做什么。

唯一的重建按钮是单篇的。十份旧文档要点十次，中途还不能停。多数用户点两次就放弃了。

## 二、低置信表格仍在假装精确

扫描件表格由 OCR 文本启发式重建，置信度被压到 0.55。界面会给一条警告，但分片仍然带着表号和行号。

于是回答可以理直气壮地说「表 2 第 3 行」，而那个坐标并不可靠。警告被折叠在结构面板里，用户在对话里根本看不到。

这比没有表格能力更糟：没有能力时用户会去看原文；给了错误坐标，用户会相信它。

## 三、重建会悄悄改变历史引用

重建会替换分片与结构块，分片序号随之变化。历史消息里的引用只记录了文档 id 与片段序号。

用户点开一条半年前的引用，看到的可能是重建后另一个片段。界面不会提示，因为它不知道文档已经被重建过。

## 四、关系检索的边界是写死的

多跳检索固定 2 跳、12 条边。简单问题够用，复杂问题在第二跳断掉；用户没有任何可调入口，只能换一种问法。

## 这一版做四件事

1. **解析版本**：新增 `parse_version`，已有结构块的文档回填为当前版本，旧的空结构文档保持 0。
2. **待重建可见**：列表显示「待重建 N 篇」，单篇带徽标；结构面板解释原因。
3. **批量重建**：串行队列，可暂停、继续、取消，失败隔离，缺原始文件跳过。
4. **低质收口**：低置信表格降级为文本，不再给单元格坐标；历史引用在文档重建后提示定位可能变化；关系跳数与边数可配置。

一句话：**旧文档要能补齐，低质结构要退得回，历史引用要说得清。**

## 为什么先做「版本」而不是直接扫描

最直觉的方案是启动时扫描所有文档，发现没有结构块就重建。

这个方案的问题是不可控：用户打开应用，后台突然开始重解析几十份文档，CPU 被占满，对话变慢；中途关掉应用，下次又从头发一遍。

所以这一版先做版本标记，把「谁需要重建」变成一个可查询的事实，再由用户触发批量动作。

顺序反过来也能做，但会先制造一个性能问题，再回头补治理。

## 边界

不做单元格级编辑：整批替换的写入模型与局部修正冲突，需要版本化块才能安全回写。

不做 LLM 关系抽取：规则关系虽然漏，但可解释、零模型成本；换模型需要新的评测集，不在本版。

不自动重解析全库：批量必须由用户触发。

## 收尾

文档能力的第一版解决「能不能读」，第二版才解决「读得可不可信」。

这一版没有提升解析准确率，只是把「哪些文档可信、哪些表格不可信、哪些引用可能变了」讲清楚。对用户来说，知道自己站在哪里，比一个看起来更聪明的解析器更重要。
