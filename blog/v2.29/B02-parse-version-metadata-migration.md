# 解析版本号：一次只改元数据的迁移

给数据库加一个版本字段，通常意味着两件事：加列，然后给旧数据一个默认值。

这一次多了一步：不能简单地把所有旧文档都标成「待重建」。

## 默认值会把好文档也标脏

新字段叫 `parse_version`，默认 0，表示「尚未按当前解析器成功落库」。

如果只做这一步，所有升级前的文档都会变成 0。问题是，其中有一批文档其实已经用当前解析器解析过——它们在结构化解析上线后上传，有完整的 `document_blocks`。

把它们标成待重建，用户会看到几十篇「待重建」，点一遍批量重建，结果解析结果和原来一模一样。白耗 CPU，还制造了「系统觉得我的文档都有问题」的错觉。

## 回填只改版本号

迁移里加了一条按结构块回填：

```sql
UPDATE documents SET parse_version = 1
WHERE parse_version = 0
  AND EXISTS (SELECT 1 FROM document_blocks WHERE document_id = documents.id)
```

有结构块的文档视为已按当前版本解析，标为 1；没有结构块的保持 0。

这条语句只改版本号，不碰 `document_blocks`、不碰分片、不重写任何解析内容。它是一次元数据修正，不是内容迁移。

## 为什么迁移里可以出现 UPDATE

项目对迁移的默认要求是「纯加法」：只加列、加表、加索引，不改旧数据。

这次是一个例外，但例外的边界很窄：更新的是一列刚加的元数据，判断依据是既有结构块是否存在，结果只影响「是否待重建」这个展示与队列筛选。

它不会让旧备份失效，也不会让旧客户端读不懂——旧客户端根本不认识这一列。

真正的风险是回填条件写错。所以测试构造了两类文档：有结构块与无结构块，断言只有前者变成 1；再跑一次迁移，断言无结构块的仍然是 0。

## 版本号写给谁看

`parse_version` 有三个读者：

- **列表**：判断是否显示「待重建」徽标；
- **批量队列**：筛选候选文档；
- **未来版本**：解析器升级时，把常量从 1 提到 2，所有版本 1 的文档自动进入待重建。

第三个读者是这次加字段的真正理由。没有版本号，未来每次解析器升级都只能靠「结构块是否存在」判断，而这对已有结构的文档完全失效。

一个字段的价值，往往不在当下这一次筛选，而在下一次升级时能不能少写一套临时规则。

## 边界

回填只认「有没有结构块」，不判断结构质量。一份解析成功但表格全错的文档，仍然算版本 1。

这不是遗漏，而是分层：版本回答「有没有按当前解析器跑过」，质量回答「跑出来的结果可不可信」。两者由不同字段与不同界面承担，不混在一个数字里。

## 收尾

迁移最容易被当成体力活：加列、给默认值、写测试。

但默认值的选择本身就是一次产品判断。全标 0 最省事，却会让用户面对一堆假警报；按结构块回填多写三行 SQL，换来的是「待重建」列表里只有真正需要重建的文档。

元数据迁移不改变内容，但它改变了用户对系统的第一印象。
