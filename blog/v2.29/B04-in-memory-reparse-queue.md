# 不落库的批量队列：可暂停、可续跑、失败隔离

批量重建一份文档要跑解析、分块、嵌入、写索引，可能几秒到几分钟。

用户需要三个控制：停下来、接着跑、别因为一篇失败就全停。

## 队列状态放哪里

最完整的做法是建任务表，把每篇的状态、重试次数、错误落库。这样应用重启后能精确恢复。

这一版没有建表，而是把队列放在进程内，候选集每次开始时重新查询。

理由是：候选集本身是可推导的。需要重建的文档等于「版本落后或无结构块」，这个查询永远返回当前仍待重建的文档。

所以重启后不需要恢复「上次跑到第几篇」，只需要重新查询一次，从剩余文档继续。暂停状态会丢，但用户再点一次开始即可。

## 串行而不是并发

解析与嵌入都会吃 CPU 和网络。并发跑三篇，看似更快，实际会让每篇都变慢，还可能与用户正在进行的对话争资源。

队列固定并发为 1，逐篇执行。每篇之间让出 50 毫秒，避免长循环完全占住事件循环。

批量维护任务的正确目标不是「尽快跑完」，而是「跑的时候不影响正常使用」。

## 暂停与取消的边界

两个动作都只在「当前文档结束」后生效。

解析与索引写入是一个事务：新分片与结构块提交前，旧索引保持可用。如果在写入中途强行中断，就会留下半套索引。

所以暂停不是「立刻停」，而是「不再取下一篇」；取消同理。界面上显示的是「当前文档完成后暂停/停止」，而不是一个会骗人的瞬停按钮。

## 失败隔离

每篇包在独立的 try/catch 里。失败只记录文件名与错误消息，计数加一，继续下一篇。

缺原始文件的文档在进入重建前就被跳过，计入 skipped，不进入失败列表。

这样一次批量跑完，用户能看到三个数字：成功、失败、跳过。失败列表给出前几条文件名与原因，可以单篇重试。

## 重入保护

队列是进程内单例。用户重复点「开始」时，如果已有任务在跑，直接返回当前状态，不启动第二个循环。

否则两个循环会同时处理同一批文档，轻则重复解析，重则两个事务争同一份索引。

单飞不是优化，是正确性要求。

## 进度怎么给

不新增 SSE，界面每 1.5 秒轮询一次状态。

状态里包含：总数、完成数、失败数、跳过数、当前文档、暂停/取消请求标志。

完成后界面自动刷新文档列表，让「待重建」徽标消失。

轮询的代价是多几个请求，收益是不用维护一条新的长连接，也不用处理断线重连。对这种分钟级的维护任务，轮询足够。

## 边界

不做定时批量重建，不做跨设备任务，不做优先级队列。

不持久化暂停状态；重启后需要重新开始。

失败不自动重试，避免一份坏文档反复消耗 CPU。

## 收尾

队列的价值不在于「能批量」，而在于「能停、能续、坏一篇不拖累全部」。

不做任务表，是因为候选集可以被重新推导；不做并发，是因为维护任务不该抢用户的资源；不在写入中途取消，是因为索引事务需要一个完整的边界。

这些选择都不复杂，但它们决定了用户敢不敢点下「批量重建」。
