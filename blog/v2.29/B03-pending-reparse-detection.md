# 待重建：把「谁需要修」变成一个可查询的事实

批量重建最难的部分不是重建，而是决定重建谁。

如果候选集靠猜，用户就会看到两种极端：列表里空无一物，或者所有文档都被标红。

## 三个候选来源都不够

最直觉的判断是「没有结构块就重建」。它能覆盖升级前的旧文档，但有两个缺口。

第一，解析失败但后来修好的文档，也没有结构块；它需要重试，但和旧文档混在一起，分不清是「没跑过」还是「跑失败」。

第二，未来解析器升级时，已有结构块的文档也需要重建。只看结构块是否存在，会漏掉这一整类。

还有一个现实约束：状态为 pending 或 processing 的文档正在上传或解析，不能重复入队。

## 组合条件

最终的判定是三个条件的组合：

- 解析版本落后于当前版本，或没有结构块；
- 状态属于 indexed / partial / failed；
- 原始文件仍保留（否则重建必然失败）。

前两条在 SQL 里完成，第三条在进入队列前逐篇检查。

这样得到的候选集有几个性质：旧文档会被选中；当前版本已解析的文档不会被误选；正在处理的文档不会被打断；未来版本升级时，只要版本常量变化，候选集自动扩大。

## 为什么不用任务表

一个更「正规」的做法是建一张重建任务表，把每篇文档的状态、重试次数、错误写进去。

这一版没有这么做，因为候选集本身就可以推导：需要重建的文档 = 版本落后或无结构块。任务表只是把这个查询结果复制了一份，还要额外维护状态一致性。

不落库的代价是：暂停状态在重启后丢失。但用户重新点一次「开始」，候选集仍然正确，剩余文档会继续跑。对一个手动触发的维护动作，这个代价可以接受。

## 判定要能被测试

判定逻辑放在仓储层，测试构造四类文档：当前版本且有结构块、旧版本无结构块、失败无结构块、处理中无结构块。

断言只有中间两类进入候选，且处理中的文档被排除。

这类测试不依赖解析器，也不依赖文件系统，只验证 SQL 条件。条件写错时，测试会直接指出哪一类文档被误选。

## 边界

「待重建」不等于「解析质量差」。一份结构完整但表格错位的文档，不会因为质量差进入候选；它需要的是重新上传或未来的手工修正，不是无脑重建。

缺原始文件的文档会被计入候选，但在队列预检时跳过，不反复尝试。

## 收尾

治理功能的第一步不是执行，而是定义对象。

把「谁需要重建」写成一个可查询、可测试的条件，后面的批量、暂停、进度才有意义。否则队列跑得再顺，也只是在正确地处理错误的集合。
