# 一个提前返回，让字幕在模型没加载时集体消失

动作执行器里有一行很普通的守卫：拿不到表现控制器就直接返回。

它在那里放了很久，没人觉得有问题。直到清理动作契约时，才有人问了一句：字幕为什么也要依赖模型？

## 一、问题现场

动作链里有几类动作：字幕、交互、表情、动作、场景。

字幕是纯文本展示，不需要三维模型，也不需要表现控制器。但执行器的结构是：

```text
const controller = controllerRef.current
if (!controller) return
switch (action.type) { ... }
```

守卫在 `switch` 之前，于是控制器为空时，所有动作都被跳过，包括字幕。

模型加载失败、尚未初始化、或页面处于降级状态时，用户看到的是「什么都没有」，而不是至少一句字幕。

## 二、为什么一直没被发现

正常路径下控制器总是存在，测试也都在「控制器就绪」的前提下写。

这类缺陷不会在主干流程暴露，只在降级路径出现。而降级路径恰好是用户最需要反馈的时候。

它也不是类型错误，编译器不会提醒；只能靠读代码时问「这个守卫的范围是不是过大」。

## 三、修法：把守卫收窄到需要它的地方

调整后的顺序是：

1. 先处理字幕动作，直接返回；
2. 再读取表现控制器；
3. 控制器为空则静默跳过剩余动作；
4. 其余动作在控制器存在时逐条执行。

关键不是新增分支，而是把「谁需要控制器」这件事写清楚。

字幕不需要，就不该被控制器的可用性绑架。

## 四、补三条测试，把两类路径都钉住

原来的测试只覆盖「控制器存在」。这次补了三条：

- 没有控制器时，字幕动作仍然输出；
- 没有控制器时，控制器类动作静默跳过，不抛错；
- 有控制器时，动作逐条驱动，字幕顺序保持不变。

测试用的是最小依赖注入：一个记录调用的假控制器，一条动作链，一个可空的引用。

## 五、守卫写得早，不等于写得对

这是这次最值得记的一点。

提前返回本身是好习惯，但守卫的范围要和依赖的范围一致：

- 依赖整个执行环境的，放在最外层；
- 只依赖某一类动作的，放在分支内；
- 纯数据变换，不应该被运行时状态拦住。

守卫的位置，其实就是依赖边界的位置。

## 六、结果

模型未加载时，字幕恢复输出；控制器类动作仍然安全跳过。

行为变化只发生在降级路径，主干流程完全一致。新增测试把这条边界固定下来，后续再加动作类型时不容易踩回去。
