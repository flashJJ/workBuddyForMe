# 跨进程别传自由文本：语义键白名单的一次实践

桌宠要把一句话递给主窗。

最省事的做法是把文案直接塞进消息里：谁生成、谁发送、谁显示，一步到位。

这次没有这么做，而是只传一个语义键。

## 一、自由文本跨进程的三个麻烦

1. **注入面**：渲染层拿到任意字符串，可能被拼进 DOM、日志或请求；
2. **长度不可控**：脚本或异常状态可能塞进超长内容；
3. **多语言失效**：文案在主进程生成，就绕过了渲染层的语言设置。

语义键把这三个问题一次消掉：载荷是有限集合，长度固定，文案由接收方按当前语言解析。

## 二、白名单怎么定义

共享包里定义三个键：问候、求安慰、陪我玩。

同时提供：

- 常量数组，供菜单与映射复用；
- 类型守卫，判断任意输入是否属于白名单；
- 通道名常量，避免两端各写一份字符串。

键是稳定的，文案是可变的。换语言、改措辞，都不需要动 IPC。

## 三、接收端必须再校验一次

预加载层收到消息后，不是直接透传，而是先过类型守卫：

```text
subscribe(channel, (payload) => {
  if (!isKnownKey(payload)) return
  callback(payload)
})
```

主进程是自己人，也要校验。跨进程边界没有「绝对可信」的一方，校验成本只有一次比较。

## 四、渲染层做映射，不做拼接

主窗只维护一张「键 → 本地化文案」的表。

收到键之后：查表、写入草稿、聚焦输入框。

没有字符串拼接，没有把键当文案显示。未知键在预加载层已经被丢弃，渲染层不需要再防御。

## 五、测试覆盖拒绝路径

只测「合法键通过」不够，真正容易回归的是拒绝逻辑。

测试用例包括：

- 三个白名单键全部通过；
- 自由文本被拒绝；
- 未知字符串被拒绝；
- 数字、`null`、`undefined` 被拒绝。

类型守卫返回布尔值，测试可以直接断言，不需要构造完整消息链路。

## 六、什么时候可以传文本

如果未来要支持脚本生成动态文案，通道可以扩展，但需要额外的约束：

- 明确长度上限；
- 去除控制字符与标签；
- 只允许纯文本，不允许结构；
- 仍然保留「预填不发送」的语义。

在没有这些约束之前，语义键是更稳的默认。

## 七、结果

整条链路只传三个固定值。菜单、预加载、主窗三端共用同一份常量与守卫，新增语义项时只需要改一处。
