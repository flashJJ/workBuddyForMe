# 按需查询与首节点基线：任务与流程面板的接入方式

协作有现成的实时帧可以接，任务和流程没有。这两处的共同问题是：数据在事件日志里，但页面不该一直盯着日志。

## 一、任务：展开才查询

任务列表可能同时有几十行。如果每行都去拉事件，打开页面就是几十个请求。

所以查询挂在展开状态上：

```ts
useSceneSnapshots('task', expanded ? task.id : null, {
  enabled: expanded,
  refetchInterval: expanded && isActive ? 5_000 : false,
});
```

三个细节：

- 未展开时 id 为 null，查询不启用；
- 运行中每 5 秒刷新一次，让用户看到水位变化；
- 任务进入终态后停止轮询，不再打扰服务端。

## 二、查询失败不阻断详情

任务详情里还有步骤时间线，那是用户最常看的内容。

所以面板与时间线解耦：快照查询失败时，面板位置显示一行错误文案，时间线照常渲染。原有的事件查询和时间线深链都保留。

这条边界容易被忽略。把两个请求串成一个加载态，会让“快照服务抖动”变成“任务详情打不开”。

## 三、流程：面板打开才查

流程执行面板是覆盖层，打开时才存在。

```ts
const terminal = phase 属于 成功 / 失败 / 已取消;
useSceneSnapshots('flow', runId, {
  refetchInterval: terminal ? false : 5_000,
});
```

同样两条规则：运行中 5 秒，终态停止。终态之后用户仍可手动刷新，但不再自动请求。

## 四、流程原来只有截断才有快照

这是这一版改动最大的地方。

此前的写入策略是：只有发生截断才写一条快照。听起来很省，但它导致一个基本问题——正常运行的节点没有任何记录。

面板打开后只能显示“截断过”，无法回答“这个节点用了多少”。而后者才是用户最常问的。

## 五、改成首节点基线加截断追加

新的策略在单次运行内维护一个布尔量：

```ts
let hasBaseline = false;

record(payload) {
  if (hasBaseline && !payload.truncated) return;
  hasBaseline = true;
  events.record({ scope: 'flow', scopeId: runId, type: 'context_scene_snapshot', payload });
}
```

效果是：

- 第一个节点无论是否截断，都写一条，作为基线；
- 之后只有截断才追加；
- 事件量从“每节点一条”降到“1 加截断次数”。

基线让面板有东西可显示，节流让长流程不会写爆日志。这两个目标本来冲突，用“首条必写”把它们分开了。

## 六、上报与落库分开

节点执行器只负责上报：每次装配完成，把统计交给上下文回调。

是否真的落库，由运行层的 sink 决定。

这个分工让节点不需要知道“这是不是第一条”“要不要节流”。它只管如实上报，策略集中在运行层一处，改策略不用动节点。

也让测试变简单：节点测试只断言“每次装配回调一次”，不配置回调时不报错。

## 七、非 LLM 节点不写

只有做提示词装配的节点才有上下文预算。

条件分支、格式化、HTTP 请求这类节点不产生快照。面板里看到的所有行都能对应到一次真实的装配。

## 八、节流状态的生命周期

基线标记定义在单次执行的作用域里。运行结束即释放，不会污染下一次运行。

如果把节流状态放到模块级，第二个流程就会因为“第一条已经写过”而丢掉基线。这类状态必须跟着 run 走。

## 九、结果

- 任务展开即见启动块与决策快照，运行中自动刷新；
- 流程面板在正常运行时也有基线，不再只能看到截断；
- 两处都在终态停止轮询；
- 单次流程的事件量可控，节点代码无需感知节流策略。

按需查询的核心不是“少查一次”，而是把查询生命周期绑定到界面生命周期：面板存在时有数据，面板关掉后不打扰。
