# 把预算摆到眼前：一次只读的上下文可见性改造

上一版我们做了一件偏底层的事：把协作、任务、流程三类场景的上下文预算写进事件日志。每一步装配用了多少 token、预算多少、有没有截断，都有记录。

记录存在，不等于用户看得见。这一版只做一件事：把这些数字摆到用户排障时会看的地方。

## 一、一个没人打开的数字

用户最常提出的问题是“它怎么把前面说的话忘了”。在此之前，我们能给出的答案只有两种：要么让他去翻事件日志，要么我们自己查。

对话场景稍好，右侧栏有一块上下文面板，能看意图、快照和压缩记录。但协作卡、任务详情、流程执行面板这三个地方，只有预算条和步骤时间线，没有上下文。

于是出现一个尴尬的状态：数据已经落库，解释却停在日志层。

## 二、非对话域的三条路

三条路径各有各的断点。

- **协作**：服务端其实已经在 SSE 里推了快照帧，推送是通的，但前端的 reducer 对这个事件类型走了默认分支，帧到达后直接被丢掉。
- **任务**：任务行展开后只有步骤时间线和一条指向时间线页的深链。想确认“这一步是不是被截断了”，得复制 id、改地址、在时间线里翻。
- **流程**：执行面板只渲染节点事件，快照事件不在实时流里；而且此前只有发生截断才写快照，正常节点连基线都没有。

这三条路最后都通向同一个地方：事件日志。而事件日志不是一个普通用户会主动打开的地方。

## 三、把面板放到现场

做法是内嵌，不是新建页面：

- 协作卡：在已有的预算条下面，追加一块紧凑的上下文预算区；
- 任务详情：放在治理摘要之后、步骤时间线之前；
- 流程执行面板：放在执行时间线上方。

三处共用一个组件：一条总进度条，若干角色行或场景行，截断时整块变暖色。协作卡与流程用紧凑模式，减少纵向占位。

## 四、一块面板里放什么

面板刻意做得很薄，只有四层信息：

1. 标题与快照总数，截断时右上角多一个计数徽标；
2. 每行一条用量数字，例如 `667 / 3008`，下面一条细进度条；
3. 每行补充窗口与预留，字段存在时再加 system 与 input；
4. 截断行追加丢弃条数、截断条数与建议。

协作与流程使用紧凑间距，任务使用常规间距。没有图表、没有筛选、没有导出，也没有“点击跳转配置”的按钮。

## 五、数据从哪来

没有一个场景需要新接口。

```text
协作：已到达的 SSE 快照帧
任务：展开时查询 /api/events?scope=task
流程：打开面板时查询 /api/events?scope=flow
```

协作不额外请求，因为帧本来就在推；任务和流程按需查询，因为它们的详情页不常驻。

这条选择省掉了一整个后端改动面，也避免了“面板专用接口”和事件接口两套语义。

## 六、只读，是这一版最硬的约束

我们给自己划了四条线：

1. 不改提示词内容；
2. 不改预算公式与预留计算；
3. 不改截断算法；
4. 不新增数据库表或迁移。

原因不是保守，而是可验证。观测功能和调控功能混在一起时，面板上的数字会同时受“展示是否正确”和“装配是否变化”两个因素影响，回归时说不清是谁动了结果。

只读之后，验收标准变得很干净：面板数值与事件日志一致，装配行为逐字节不变。

## 七、为什么不做独立的上下文中心

我们讨论过做一个带导航入口的“上下文中心”，把所有场景的快照聚合到一起。最后没有做。

- 排障的现场在卡片和面板里，离开现场跳转一次，注意力就断了；
- 跨场景聚合需要先回答“不同 scope 的快照怎么排序”，这个问题本身不值得在这一版回答；
- 独立页面会立刻引来筛选、搜索、导出等需求，把一个观测小版本拖成产品模块。

内嵌三处，用户不需要学习新入口。

## 八、结果

- 协作卡出现 planner、executor、reviewer 三行预算；
- 任务展开即可看到启动上下文块与任务决策两步；
- 流程执行面板在正常运行时也有一条基线，不再只有截断记录；
- 截断时三处都会变暖色，并给出下一步建议；
- 没有任何提示词、预算公式、截断算法和表结构变化。

可见性改造的价值不在于多了一个面板，而在于把“为什么忘了”从口头解释变成用户自己能读到的证据。
