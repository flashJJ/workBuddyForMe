# 总量之外：给上下文快照补上构成

上一版落地场景快照时，我们只记了一个总数：这次装配用了多少 token、预算多少、有没有截断。

上线后第一轮排障就卡住了。用户看到“用了 900，预算 1000”，接着问：“那 900 是什么？”我们答不上来。

## 一、总量回答不了的问题

同样是 900，可能是三种完全不同的情况：

- 角色提示词写得太长，system 部分占了大头；
- 历史对话很长，system 很小；
- 知识库检索塞进来一堆观察文本。

这三种情况的处理方式完全不同：第一种要精简提示词，第二种要减少历史，第三种要调整检索。只有一个总数，用户只能猜。

还有一种更隐蔽的情况：两次装配总量接近，但消息条数差了一倍。用户会觉得“配置没变，怎么感觉不一样了”，而事件里没有任何字段能佐证。

## 二、只加三个可选字段

我们没有重做快照契约，只增量补了三项：

```ts
systemTokens?: number;  // system 消息占用，截断后的终值
inputTokens?: number;   // 非 system 消息占用
messageCount?: number;  // 最终消息条数
```

三项都声明为可选。这不是偷懒，是为了让旧事件、旧读取方、旧测试继续成立。

## 三、两条不变量

新写入的快照必须满足：

```text
systemTokens + inputTokens === promptTokens
messageCount === 最终 messages.length
```

第二条尤其重要。如果只记 token 不记条数，用户无法判断“是不是历史被砍了一半”，而这恰恰是最常见的截断表现。

这两条不变量在装配函数的出口统一计算，不在调用方各自拼装。调用方越多，越不能给它自由。

## 四、在截断之后计算

统计发生在丢弃与截断全部完成之后，反映的是最终真正下发的内容，而不是装配前的计划。

这个顺序很容易写错。如果在截断前算 systemTokens，面板上的构成和实际请求对不上，用户看到的是“计划中的上下文”。

另外两个边界：

- 空消息列表时，三项全为 0，而不是缺省；
- `promptTokens` 的旧含义保持不变，仍是估算总量，不改口径。

## 五、旧事件怎么读

事件日志里存着大量上一版写入的快照，它们没有这三个字段。

处理方式是“按存在性渲染”：

- 三个字段都在，面板追加一行 `system / input`；
- 字段缺失，只显示总量、窗口和预留；
- 解析不做兜底填充，不用 0 假装旧数据。

用 0 填充看起来让界面统一了，但它会制造一个假事实：旧事件明明是“没记录”，却显示成“system 占用为 0”。排障时这种假事实比缺失更糟。

这种退化是渐进的，不是一次性开关：同一次运行里如果前半段是旧格式、后半段是新格式，面板会前半段只显示总量、后半段显示构成。用户不会看到报错。

## 六、任务启动块不填这三项

任务在启动时会写一条上下文快照，描述的是“启动上下文块”的预算。

它和消息装配不是一回事：那是一个文本块的预算估计，没有 system 与非 system 的划分，也没有消息数组。

所以这条快照不填三个新字段。面板对它只显示总量。强行补零会让用户以为启动块的 system 占用真的是 0。

## 七、时间线详情也补一行

时间线页原本只显示总量、预算和截断标记。这次在详情里按存在性追加 `system=` 与 `input=`，字段缺失时保持旧格式。

改动很小，但它让“翻日志排查”和“看面板”两套路径给出的信息一致。

## 八、结果

- 新快照能回答“谁占了预算”：角色提示、历史、观察；
- 两条不变量在单测里被断言，覆盖未超预算、截断后、空列表三种情况；
- 旧事件照常解析，面板自动退化为只显示总量；
- 任务启动块保持原语义，不被强行补齐。

补字段这件事本身不复杂。真正需要克制的是：加字段时不要顺手改口径，也不要替旧数据编造缺失值。
