# 一套纯函数，三处面板：把展示逻辑从页面里拿出来

协作卡、任务详情、流程执行面板三处都要展示同一种数据：场景上下文快照。

最直接的写法是三处各写一份：各自过滤事件、各自挑行、各自算百分比。我们最后只用了一套。

原因不是抽象洁癖，而是这三处的数据形状本来就不一样，各写一份必然分叉。

## 一、三份代码会分叉在哪

- 协作：每次运行有多个角色，每个角色多轮，需要“每人最新一条”；
- 任务：同一次任务里混着“启动上下文块”和“执行决策”，一个有角色、一个没有；
- 流程：一个运行里只有一个节点场景，取最新即可。

如果每处自己写查找，很可能会出现三种“最新”的定义：按数组顺序、按时间戳、按角色分组后再取。平时结果一致，一旦事件乱序或缺失就开始互相矛盾。

## 二、解析：宽松优先

解析函数只做两件事：过滤和校验。

```ts
parseSceneSnapshotEntries(items) {
  for (item of items) {
    if (item.type !== 'context_scene_snapshot') continue;
    const parsed = schema.safeParse(item.payload);
    if (!parsed.success) continue;   // 跳过，不抛错
    push({ value: parsed.data, at: item.at, id: item.id });
  }
}
```

三个决定：

1. 用 `safeParse` 而不是 `parse`。事件日志里可能有历史格式、半写入或未来版本的数据，一条坏数据不应该让整个面板白屏。
2. 跳过而不是占位。无效载荷不渲染“未知行”，因为它不携带任何可用信息。
3. 保持输入顺序。事件接口已按序号升序返回，解析不重新排序。

## 三、汇总：只保留最近 N 条

汇总函数接收条目数组，默认只取最近 20 条参与统计。

```ts
summarizeSceneSnapshots(entries, limit = 20)
```

保留最近 N 条的理由是噪声：长任务可能写入几十条快照，全量渲染既慢又没有阅读价值。上限也保护了截断计数的含义——它统计的是“最近这段窗口里有几条被截断”，不是“历史上总共截断几次”。

## 四、按角色取最新

协作场景需要每个角色一行。做法是从后往前扫描，命中即停：

```ts
for (role of ['planner', 'executor', 'reviewer']) {
  entry = 从 recent 末尾往前找第一个 role 匹配的;
  if (entry) push({ role, entry });
}
```

两条规则：

- 顺序固定为 planner → executor → reviewer，不按到达顺序排，避免用户每轮看到行位置变化；
- 缺角色就跳过，不显示“未记录”行。没参与的阶段不该占一行。

同一角色出现多次时，只显示最新一条；其余条数体现在面板标题的“本次共 N 条快照”里。

## 五、混合场景按场景分行

任务面板是这版最容易写错的地方。

一次任务里，启动上下文块没有角色，执行决策有角色。如果统一按“有没有角色”来分行，启动块会被直接丢掉。

所以我们补了一个按场景分行的函数：

```ts
latestByScene(entries)
```

它按场景首次出现的顺序收集，再为每个场景取最新一条。任务面板因此得到两行：“启动上下文块”和“任务决策”。

这两个函数不是重复实现：按角色取最新解决“同一场景多角色”，按场景分行解决“多场景混合”。组件先判断本次运行是否全部带角色，再决定用哪一个。

## 六、空 summary 返回 null

组件的第一行是：

```ts
if (summary.entries.length === 0) return null;
```

没快照就不渲染，不占位、不显示“暂无数据”。三处面板都在信息密集的区域，一个空卡片会持续挤占纵向空间，而它传递的信息为零。

这与“加载中”是两回事：加载态由 hook 的状态负责，组件只在拿到结果后决定画不画。

## 七、为什么坚持纯函数

- 可以被穷举测试：无效载荷、角色缺失、超过上限、全部截断，都是普通输入；
- 组件只剩渲染，没有“顺手取数”的分支；
- 三个页面共享同一套语义，改动只需改一处。

## 八、结果

- 一处解析、一处汇总、一套组件，三处消费；
- 无效事件被跳过，面板不会因为一条坏数据整体失败；
- 任务面板同时保留启动块与执行行；
- 无快照时返回 null，不制造空态噪声。
