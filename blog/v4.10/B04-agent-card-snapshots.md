# 已经推过来的帧，别再丢掉

协作运行的界面是 SSE 驱动的。前端有一个事件联合类型，列出了所有会到达的帧，其中就包括场景上下文快照。

类型检查通过，编译不报错。但 reducer 的 switch 里没有这个分支。

## 一、一个编译器发现不了的丢弃

reducer 的结构是：命中已知事件就返回新状态，其余落到默认分支，原样返回旧状态。

快照帧到达后走的就是这条默认分支。它不报错、不告警、不留下任何痕迹，只是安静地消失了。

这类问题比崩溃更难发现：崩溃会有人报，静默丢弃只会表现为“这个功能好像没做”。

## 二、为什么一直没暴露

三个原因叠在一起：

- 快照帧是新事件，服务端先上，前端后接；
- 预算条本身有数据，走的是另一条通道，所以卡片看起来不是空的；
- 类型联合里已经声明了该事件，代码搜索时容易误以为“已经处理”。

最后一点最危险：类型声明只保证“可能到达”，不保证“被消费”。

## 三、给状态加一个数组

卡片状态增加一个字段：

```ts
interface AgentCardState {
  // ...
  contextSnapshots: SceneContextSnapshotPayload[];
}
```

初始化时置为空数组，所有构造点同步补上。这里没有用可选字段，因为“没有快照”和“还没收到快照”在界面上是同一件事，用空数组表达足够，也免去到处判空。

## 四、追加并封顶

reducer 增加一个分支：

```ts
case 'context_scene_snapshot':
  return {
    ...state,
    contextSnapshots: [...state.contextSnapshots, frame.data].slice(-24),
  };
```

几个考虑：

- **追加而不是覆盖**：面板需要“每角色最新一条”，覆盖会让先到的角色行消失；
- **上限 24 条**：一次运行三角色，24 条约等于 8 轮，足够覆盖面板展示窗口；长任务不会让数组无限增长；
- **不可变更新**：保持原有 reducer 风格，避免就地修改带来的渲染问题。

上限不是精确的科学，而是一个防御性数字。真正的展示只用到每角色最新一条，其余只是为了让“本次共 N 条”有意义。

## 五、不额外请求

协作卡不走事件查询接口。

理由很直接：帧已经在推了。再发一次请求，会得到和内存里几乎相同的数据，还多了一次网络往返和一套加载态。

这也意味着一个边界：从历史记录还原的协作卡没有实时快照帧。这种情况下面板缺省隐藏，需要回看时走时间线页。我们没有为了历史卡片再补一条查询路径——那会让“实时”和“历史”两套数据源在同一张卡片上打架。

## 六、渲染位置

卡片里原本已有一条预算条，展示整体水位。快照面板放在它之后，使用紧凑模式：

```text
[预算条]
[上下文预算 · 本次共 N 条快照]
  planner   667 / 3008
  executor  ...
  reviewer  ...
```

复用同一个汇总函数，卡片只负责把状态里的数组映射成条目。没有快照时组件返回 null，卡片布局不变。

## 七、测试怎么写

三条断言足够：

1. 初始化后数组为空；
2. 两帧到达后顺序与角色正确；
3. 连续 30 帧后只保留最近 24 条，且首尾值符合预期。

第 3 条要断言具体数值，而不只是长度。只断言长度的话，把切片方向写反的实现也能通过。

## 八、结果

- 快照帧不再被丢弃，运行中即可看到每角色水位；
- 数组有上限，长任务不会累积；
- 卡片不额外发请求，加载路径不变；
- 历史卡片行为与之前一致。

这次修复提醒我们：在事件驱动的界面里，类型联合只是清单，不是实现。清单上的每一项都要有人真正接住。
