# 失败分类与补偿队列：什么时候该自动重试

「失败就重试」听起来简单，真做起来最先遇到的是：**哪些失败可以重试**。

网络抖动、超时、限流可以重试；配置错误、鉴权失败、数据格式错误、版本缺失重试一百次也不会变好。如果统一重试，只会把一次失败放大成多次无效调用，还可能产生重复副作用。

v5.0 先做错误分类，再做补偿队列。

## 一、九类错误

| 类别 | 典型场景 | 可自动补偿 |
|---|---|---|
| `config` | 节点配置缺失、参数非法 | 否 |
| `auth` | 密钥无效、权限不足 | 否 |
| `network` | 连接失败、DNS、上游不可达 | 是 |
| `timeout` | 调用超时、执行超时 | 是 |
| `rate_limit` | 限流、配额耗尽 | 是 |
| `tool` | 工具内部错误 | 否 |
| `data` | 输入/输出结构不符 | 否 |
| `version` | 版本/节点缺失 | 否 |
| `unknown` | 兜底 | 否 |

判定顺序：显式错误码映射 > 消息关键词 > 节点类型兜底 > `unknown`。分类结果是 `FlowRunError` 上的 `category/retryable/hint`，运行中心直接展示。

## 二、补偿状态机

```text
pending --claim--> retrying --成功--> recovered
   ^                  |
   |                  +--失败且未满 3 次--> pending（退避）
   |                  +--失败且已满 3 次--> exhausted
   +--流程停用/删除--> cancelled
```

一条失败链只有一行补偿记录，`root_run_id` 唯一。每次补偿重放写 `last_run_id`，不新建补偿行，避免失败链越滚越多。

`attempt` 的含义是「下一次重试编号」：创建时为 1，表示第一次补偿即将发生；每次真正发起重放前 +1。

## 三、退避与单飞

固定退避阶梯：

```ts
const BACKOFF = [30_000, 120_000, 600_000];
```

流程内单飞：如果同一流程已有在途运行，本次补偿顺延 60 秒，**不消耗尝试次数**。这样不会因为上游运行太久而把三次机会浪费在「busy」上。

补偿扫描每 60 秒一次，启动后先扫一次；重启后 `pending` 记录继续生效，不需要额外恢复逻辑。

## 四、谁可以进入补偿

只允许无人值守触发：

```text
api / mcp / schedule / webhook / file
```

人工触发（`manual/chat`）不自动补偿。原因很直接：人在现场，应该由人决定是否重放，而不是后台悄悄再跑一遍可能带副作用的流程。

同时要求：

- 运行状态是 `failed`；
- 不是重放产生的子运行（`parentRunId` 为空）；
- 错误 `retryable=true`；
- 流程未停用/删除。

## 五、审计与可见性

- 创建补偿：`flow_compensation_scheduled`；
- 补偿耗尽：`flow_compensation_exhausted`；
- 运行中心统计卡展示「补偿中/耗尽」，行内展示补偿状态与下一次时间；
- 耗尽后仍可人工批量重放，不把用户锁死。

## 六、边界

- 补偿不保证副作用幂等：可重试错误通常发生在调用前/连接阶段，但工具内部仍应自行幂等；
- 不做无限重试，也不做按流程自定义策略；
- 不做分布式锁，单进程内的单飞足够本地应用；
- `exhausted` 不是终态错误，运行仍可人工重放。
