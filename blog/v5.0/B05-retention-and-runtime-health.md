# 运行历史只增不减？保留策略、清理保护与健康面板

本地应用的好处是数据都在自己机器上；坏处也是。运行记录、节点执行、事件缓冲如果只增不减，SQLite 文件会越来越大，备份越来越慢，最后用户只能手动删库。

v5.0 加了两件事：可配置的运行保留与清理，以及一个只读的运行健康面板。

## 一、保留策略

默认值：

```ts
{ enabled: true, successDays: 30, failureDays: 90, maxPerWorkflow: 500 }
```

- 成功运行保留 30 天；
- 失败运行保留 90 天，给排查留更长时间；
- 每个流程最多保留 500 条终态运行，防止单流程高频把库撑大；
- 设置页可改，范围分别是 1–365 天、每流程 50–5000 条。

策略存在 `settings` 表，键前缀 `flows.runRetention.*`，不新增配置表。

## 二、清理顺序与保护

清理不是简单 `DELETE WHERE created_at < cutoff`，要按顺序处理：

1. 只扫终态运行（成功/失败/取消/中断）；
2. 先按时间淘汰：成功用 30 天阈值，失败用 90 天阈值；
3. 再按每流程上限淘汰最老的终态；
4. 排除 `pending/retrying` 补偿引用的运行（root 与 last 运行都保护）；
5. 分批删除，每批 ≤200，避免一次长事务锁库；
6. 实际删除才写审计 `flow_retention_cleanup`。

`dryRun=true` 只统计不删除、不写审计，设置页用它做预览。

## 三、清理定时器

- 启动后 5 分钟执行第一次，避开启动高峰；
- 之后每 24 小时一次；
- 单飞锁，避免与手动清理并发；
- 失败只告警，不影响应用主流程。

保留策略关闭时，定时器仍会跑，但 `cleanup` 直接返回 0，不扫描。

## 四、健康面板看什么

`GET /api/flow-runs/health` 返回一个只读快照：

| 区域 | 字段 |
|---|---|
| 调度器 | running、startedAt、lastTickAt、tickCount、stalled、lastError |
| 文件监听 | active、watchingCount、lastEventAt、lastError |
| 补偿 | pending、exhausted、lastSweepAt |
| 端点 | 启停、最近使用、策略是否需重新确认 |
| 定时 | 下次执行、最近状态、missedCount、lastMissedAt |
| 触发器 | 最近触发时间、最近运行、最近状态 |
| 保留 | 最近清理时间、累计删除数 |

`stalled` 的判定是 `now - lastTickAt > 3 × 30s`。调度器 30 秒一跳，连续三次没跳才认为停摆，避免一次慢查询就误报。

## 五、错过次数

定时器启动时会发现「本来该跑但没跑」的周期。v5.0 记录：

- `missed_count`：累计错过次数，上限 100；
- `last_missed_at`：最近一次发现错过的时间；
- 仍然只补跑一次，不逐周期补跑。

这样用户能看到「错过了 7 次」，而不是只看到「上次运行是三天前」。

## 六、边界

- 健康面板只读，不自动停用触发器；
- 文件监听状态重启后重置，不做历史推断；
- Webhook 只显示最近接收，不推断上游节奏；
- 清理不做跨表归档，删了就是删了；
- 保留策略不影响审计账本。

## 七、为什么不做通知中心

失败可发现优先用运行中心徽标、健康面板与审计，不引入独立通知中心、邮件/IM/出站 Webhook。通知通道涉及凭证、重试、去重与用户配置，属于另一个主题；v5.0 先把「看得到」做好。
