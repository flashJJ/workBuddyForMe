# 本地自动化要「跑得住」：v5.0 的五条兜底链路

前几个版本把可视化工作流从「能跑」推到「能定时、能被 Webhook 和文件事件唤醒」。但自动化真正上线后，问题会换一批：

- 夜里失败十条，早上只能逐条点重放；
- 流程升级后，旧运行续跑时读的是新图，节点对不上；
- 定时没跑，说不清是没到点、进程停了，还是触发器失效；
- 运行记录只增不减，失败也没有人知道；
- Agent 节点内部的写工具绕过了流程级策略；
- Webhook 只认 Bearer，外部系统只能明文带密钥。

v5.0 用五条链路补齐这些缺口：失败补偿与批量重放、运行图快照、运行治理与触发器健康、Agent 工具门控、Webhook HMAC。本文先给整体地图，后续文章逐条展开。

## 一、五条链路

| ID | 能力 | 一句话 |
|---|---|---|
| R1 | 失败可收 | 可重试失败自动补偿，运行中心批量重放 |
| R2 | 跨版本可续 | 运行开始即固化流程图，续跑不读生产图 |
| R3 | 运行可治理 | 保留清理、失败可发现、触发器健康 |
| S1 | 执行前拦截 | Agent 内部工具也走流程级无人值守策略 |
| S2 | 触发入口验真 | Webhook 可选 HMAC-SHA256 + 时间窗 |

## 二、设计原则

1. **只兜已有链路的底**：不引入分布式调度、不做自动改写流程图，也不做通知中心。
2. **失败必须可见**：错误分类、运行中心徽标、健康面板、审计事件四条出口。
3. **安全边界只加在无人值守侧**：人工试运行/对话触发保持原审批链，避免误伤。
4. **所有兜底都可回退**：快照缺失时按精确版本取，版本删了明确阻断，不静默用最新图。

## 三、一条失败运行会发生什么

```text
无人值守运行失败
  → 错误分类（可重试？）
  → 是：补偿行 pending（30s）
  → 到点 claim → 快照模式重放
  → 成功：recovered；失败：2m/10m，三次后 exhausted
  → 否：运行中心展示类别与建议，等待人工批量重放
```

补偿与人工重放共用同一条重放服务：固定图、固定版本、写 `parentRunId`。区别只在于补偿由定时器驱动，且一行失败链只建一条补偿记录。

## 四、代价与边界

- 迁移只做加法（v057），旧行新列为空，不重写历史；
- 快照只存图 JSON（KB 级），节点执行记录不复制；
- 保留策略默认开启，但只删终态，且排除待处理补偿；
- HMAC 需要服务端持有密钥，因此新增密文列，旧触发器先轮换再启用。

后续文章会分别讲快照与 canonical JSON、错误分类与补偿状态机、批量重放与版本差异、保留与健康、Agent 门控、Webhook HMAC。
