# Agent 节点里的写工具，也要过流程级无人值守门

工具节点和 Agent 节点是两种执行模型：

- 工具节点：图里明确写了工具名，执行前可以按流程策略裁决；
- Agent 节点：模型在运行时决定调用哪些工具，图里只有一个 `toolScopes` 列表。

如果只在工具节点做无人值守策略，Agent 节点就成了一条绕过路径：用户以为流程策略会拦住写操作，模型却可以在节点内部调用写工具。

v5.0 把门控下沉到 Agent 执行器的工具暴露层。

## 一、什么时候注入门控

只在无人值守触发时注入：

```text
api / mcp / schedule / webhook / file
```

`manual/chat` 不注入。人工试运行仍然走原来的审批链：该弹确认就弹确认，该拒绝就拒绝，不因为这次改动改变交互。

## 二、门控做什么

Agent 执行器在把工具列表交给模型之前，先过滤：

```ts
const allowed = tools.filter((tool) => gate(tool.name, tool.permission));
```

`gate` 内部复用流程级策略 `evaluateUnattendedPolicy`：

- `deny_all`：拒绝所有写/危险工具；
- `allowlist`：只允许白名单里的工具；
- 读工具不受影响。

被过滤的工具不会出现在模型可调用的列表里，模型无法「看到再尝试」。

## 三、拒绝要留痕

仅仅把工具藏起来不够：用户需要知道「模型本来想用，但被策略拦了」。

因此过滤时对每个被拒绝的工具写审计：

```text
flow_agent_tool_denied
  runId, nodeId, agentRunId, toolName, permission, reason
```

同时返回结构化工具错误，而不是抛异常。原因：

- 抛异常会让整个 Agent 节点失败，用户只看到一句节点错误；
- 返回工具错误可以让模型换一条路（例如改用读工具），也让审计保留完整上下文。

## 四、为什么不在 Agent 服务里拦

Agent 服务是通用协作通道，也被对话、任务等入口复用。流程级策略只属于 Flow，放在 Agent 服务里会污染其他入口。

放在执行器适配层（`executor-adapter`）有三个好处：

1. 只有 Flow agent 节点会走这里；
2. 工具列表在暴露前过滤，最靠近模型；
3. 审计字段（runId/nodeId/agentRunId）在这里最完整。

## 五、测试怎么覆盖

- 无人值守 + `desktop` 域：节点失败，协作不启动；
- 无人值守 + 写工具白名单：允许的工具可见，拒绝的工具写审计；
- `manual` + `desktop`：正常发起，审批链不变；
- 门控函数本身：`deny_all`、`allowlist`、读工具放行、空名单。

测试里用 mock 协作回调捕获入参，断言工具列表与审计调用，不依赖真实模型。

## 六、边界

- 门控只覆盖「工具暴露」，不覆盖模型生成的文本；
- 不替代工具自身的权限检查；
- 不做 OS 级沙箱；
- 不改变人工触发的审批行为；
- 白名单为空时等价于 `deny_all`，这是预期语义。
