# 陪伴型桌面应用的复盘：让「会演」变成「可解释地会演」的七条工程纪律

一个桌面 AI 应用的角色能站立、待机、被戳、说话之后，很容易陷入「散装触发」：动作、台词、表情各走各的，新增一段互动要同时改三处；主动说话只有冷却和预算，用户看不出「为什么选这场」。

这一轮改造把陪伴拆成四层，收口时的对账如下：

| 层 | 交付 | 结果 |
|---|---|---|
| 剧本 | 场景 / 节拍 / 指令三件套 + 导演 | 动作与台词共用一条时钟，新增互动只改数据 |
| 决策 | 硬门控 + 纯函数打分 + 理由码 | 设置页可回看最近 5 条选场理由 |
| 舞台 | 三席角色小剧场 + 分享卡 | 逐句语音、换幕换曲、桌面端导出 PNG |
| 资产 | 原创模型、表情目录、可分发曲库 | 三席模型 74.75MB 压到 22.29MB |

真正值得留下的不是功能清单，而是七条纪律。

## 一、表现层要有受约束的中间格式

不要让模型直接驱动骨骼与表情。模型输出的是「意图」，渲染需要的是「时间轴」，两者之间必须隔一层受约束的数据。

这一轮定义的中间格式是场景 / 节拍 / 指令：

```text
Scene = 触发键 + 优先级 + 冷却 + 门控 + beats[]
Beat  = { at, cue }
Cue   = pose / gesture / motion / expression / look / line / sound / prop / wait
```

约束是硬编码进 schema 的：beats 必须按 `at` 升序，单场最长 10 分钟；轨道由 cue 的 kind 推导，避免「轨道」和「cue」两处声明漂移；身体与世界轨道独占，表情、视线、语音可并行。

好处不是优雅，而是可验证。中间格式一确定，剧本就能被 lint、被快照、被回放，生成器只需要产出这个格式，不必理解渲染细节。

## 二、硬门控与排序分离

「要不要打扰用户」和「在能打扰的候选里选哪场」是两个问题。混在一起，权重调一次就会把勿扰规则调坏。

这一轮把否决权完全留给硬门控：勿扰、睡眠、忙碌、冷却、预算、关系等级、今日已播。它们只回答「能不能」，不产生分数。

Utility 只在合法候选之间排序，权重表是时段 0.20、心情 0.15、关系 0.15、工作信号 0.20、空闲与打扰成本 0.15、新鲜度 0.15。它是纯函数，没有额外定时器，也不调用模型。

平局处理同样要确定：先按上次播放时间，再按场景 id。否则同样的输入两次运行会选出不同结果，测试和复盘都无从谈起。

## 三、可解释性要落到数据结构

把理由拼进日志字符串，等于没有理由：用户看不到，测试断言不了，界面也无法结构化展示。

这一轮定义了决策记录：场景 id、来源、总分、粗粒度上下文，加上理由数组。每个理由是「白名单理由码 + 加权增量」，例如：

```text
score 0.538
  道具重复  -0.12
  今日未播  +0.075
  空闲陪伴  +0.07
  场景偏长  -0.06
  工作时段  -0.02
```

保留 20 条，界面展示最近 5 条，单条最多 6 个理由。被硬门控拒绝的候选只进开发日志——它们不是「决策」，不该占用解释名额。

好处很实际：调权重时能看出是哪一项把场景顶上去的；用户问「为什么突然演这个」，界面直接给出答案。

## 四、内容也要门禁

代码有类型检查和单测，剧本却常常靠肉眼。这一轮把剧本也纳入门禁。

跨场景 lint 检查：id 唯一、触发键与打断策略在白名单内、优先级与冷却合法、beats 时间单调且不超上限、cue 可感知、道具成对、`validateScene` 零丢弃。

在此之上加 golden 快照：内置场景导出为 `id → [{at, kind}]`，任何场景改动都必须显式更新快照。快照不比对权重与文案，只比对时间线的形状——它抓的是「有没有人悄悄挪了一拍」，而不是「文案改得好不好」。

这两类检查合起来 6 个文件 37 项，跑在一条命令里。内容改动的心理成本从「敢不敢动」变成「改完记得更新快照」。

## 五、资产许可当工程约束

角色、表情、配乐都是发布物的一部分，许可不能只在文档里写一句「已确认」。

这一轮的做法是把许可变成可执行的约束：

- 内置 11 首曲目全部 CC0，逐曲登记作者与来源；
- 统一转码为 MP3 192kbps、44.1kHz、-16 LUFS，合计约 30.4MB；
- 来源不清的个人曲目移出发布目录，不进入安装包；
- 设置页「关于」放原创角色与二创包合规声明。

同理，模型体积也是资产约束：morph 顶点稀疏化加贴图重编码后，三席从 74.75MB 降到 22.29MB，且表情与绑定回读一致。没有这一步，「可分发」只是口号。

## 六、验证要分层，别指望一层兜住

同一个功能，单测、浏览器、桌面壳能发现的问题完全不同。

这一轮的分层是：

- 纯函数单测：打分、剧本解析、音频状态机、表情强度，剧场域 49 项（另加舞台布局 8 项）；
- 浏览器真机：三席就绪后开演、逐句语音、暂停继续、换幕换曲；
- 桌面冒烟：11 项覆盖键鼠通道、记事本落盘、桌宠、窗口渲染、导航、安全基线、控制通道，50.3 秒跑完。

两个真实教训：跨幕音频不能只看「有没有声音」，要按秒采样音量，确认说话时从 0.3 压到 0.105、静音归零；内置 Chromium 不含 MP3 解码，音乐验收必须换系统浏览器，否则会把「解码器缺失」误判成「文件坏了」。

## 七、已知限制要写进发布物

限制不写出来，用户就会把它当 bug；写了，它才是边界。

这一轮明确记录：内置剧本 4 集各 6 句，尚未接入生成器队列；生成器的弱偏好（时段、心情）是可选输出，命中率仍需真实数据观察；分享卡只在桌面端导出；关系等级门槛待后续元数据接口。

这些不是「以后再说」，而是本轮设计的已知边界。把它们写进发布说明，等于提前回答了三类问题：能做多少、为什么没做、下一步看什么。

## 八、一句话

**陪伴型功能的完成度，不取决于角色能演多少种情绪，而取决于「为什么演、能不能演、演得对不对」这三件事是否都有数据结构兜底。**

剧本负责约束，门控负责边界，理由码负责解释，门禁负责不让它悄悄退化。
