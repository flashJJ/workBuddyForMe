# 不另做离屏渲染：把分享卡叠进舞台再截一张图

我们的桌面 AI 应用是本地优先、单人开发、Electron + Next.js 交付的私人助手。舞台窗口能演小剧场，也能把当前这一幕存成一张分享图。

做分享图，第一反应通常是上 canvas：把背景、角色、台词卡重画一遍。我们选了另一条路：卡面就是舞台上的一个普通 DOM 层，截图还是原来那个窗口截图。

## 一、已经有截图通道，就别再开一条

舞台早在之前就有一个「无 UI 截图」能力：渲染层先隐掉界面，主进程对窗口抓一帧，弹系统保存对话框写 PNG。

分享卡复用它，没有新增导出器、没有新增图片编码路径、也没有新增第二个保存对话框。

链路只有四步：

```text
按钮 → 隐 UI → 等一帧 → 主进程 capturePage() → 保存对话框 → 写 PNG
```

对上层来说，分享卡只是多挂了一个 DOM 层，截图流程一行没改。

## 二、hide 的粒度必须到按钮

截图要干净，但卡面本身必须留在画面里。所以「隐藏 UI」不能是一个全局开关一关了事。

这里把它拆成两层：

- 舞台控制栏、轮播角标、静音按钮：完全隐藏；
- 分享卡：卡面保留，只隐藏底部的「关闭」和「保存」两个按钮。

组件接收同一个隐藏标志，但只在那两个按钮上判断。页面结构不动，卡片的尺寸、圆角、渐变背景都不会因为隐藏按钮而重排。

如果偷懒把整张卡一起隐藏，截出来就是一张只有角色的舞台空镜，用户点保存得到的不是他想分享的东西。

## 三、等一帧再抓

设置隐藏状态到 DOM 真正提交，中间隔着一次渲染。主进程抓的是合成后的帧，如果立刻调用，很容易抓到按钮还没消失的那一瞬间。

所以调用前先等一次 `requestAnimationFrame`：

```text
setUiHidden(true)
await nextFrame()
result = await bridge.capture()
setUiHidden(false)
```

只等一帧而不是等几百毫秒，是因为隐藏只是 CSS 层面的可见性变化，不需要等待动画或网络。

## 四、卡面数据从哪来

卡面上的两组数字来自两个已有接口：今日主动播放场次与每日上限，来自播放统计接口；今日生成场景数，来自剧本队列接口。

两个查询都设了 60 秒的 staleTime，且不重试。第二次打开卡片不会再闪一次加载态，接口短暂失败也不会连续打三次。

失败时的处理是显示 `--`，不阻断卡面。分享图的价值主要是那句话和那一幕，两个统计数字拿不到不该让整张卡打不开。

卡面内容依次是：标题、日期与句序、三个席位名、当前说话人与台词、两个统计格、页脚说明。

## 五、桌面端与浏览器的分叉

截图依赖桌面壳注入的桥。桥不存在时（纯浏览器打开这个路由），点击保存只弹一条「当前环境不支持截图」的提示，不抛错、不留下半隐的界面。

桌面端的保存走系统对话框：默认文件名带时间戳，扩展名固定 PNG。文件名里的冒号和 `T` 会被替换成短横线，否则在 Windows 上直接非法。

用户在对话框点取消时返回「已取消」，提示语用 info 级，不算失败。

## 六、实测

在 1440×900 的舞台窗口上，桌面端抓出的 PNG 是 2561×1601，约 1.05MB。

尺寸大于窗口，是因为抓的是设备像素比换算后的画面。体积落在 1MB 左右，对聊天工具和社交平台都算友好。

验证方式不是手点，而是用 Playwright 启动 Electron、替换掉保存对话框，断言文件写出成功，再检查提示、界面恢复与主进程日志。

这条用例覆盖的正是最容易坏的部分：跨进程调用、对话框替换、文件落盘、UI 状态回滚。

## 七、几个坑

**坑一：截图后 UI 没恢复。** 一开始恢复逻辑写在成功分支里，用户点取消或主进程返回错误时，界面就永久停在无 UI 状态。后来改成无论结果如何都先恢复，再按结果给提示。

**坑二：抓到按钮残影。** 少了那一帧等待，截图上会留下半透明的按钮轮廓。等待一帧后消失。

**坑三：卡面被一起隐藏。** 隐藏标志传得太粗，卡面跟着消失，截出空舞台。修复就是把判断下放到按钮。

**坑四：文件名带冒号。** 时间戳直接拼进文件名，在 Windows 上写入失败。统一把冒号和 `T` 换成短横线。

## 八、为什么不走 canvas 重绘

canvas 方案的好处是可控：你可以导出任意尺寸、去掉任意元素、加上水印，甚至可以脱离窗口在后台生成。

但它要求把角色、表情、背景、文字全部重画一遍。VRM 的表情是 morph 组合，Live2D 是另一套参数，字体渲染也各有差异。等于维护两条渲染路径，还要保证两条看起来一样。

DOM 截图的代价也很明确：画面里有什么就只能截什么。想要干净，就得自己把该藏的东西藏好。

在这个场景里，分享图的默认用途就是「把眼前这一幕存下来」，一致性比可定制性更重要，所以选了复用。

## 九、一句话

**能复用现有通道时，最贵的往往不是截图本身，而是「要不要再维护一套渲染」。**

卡面是 DOM 层，截图是窗口截图，隐藏粒度到按钮，失败不阻断内容——四个决定加起来，就是一张能直接发出去的图。
