# 同步调用、超时转异步与只读 SSE：一套执行，三种观察姿势

本地 API 的调用方差异很大：shell 脚本希望「发一个请求拿到结果」，而耗时流程（LLM 多步、网页抓取）可能跑几十秒甚至几分钟，HTTP 连接和调用方耐心都撑不住。v0.9 的选择是**同一套队列执行，提供三种观察姿势**：同步阻塞、异步轮询、只读 SSE。这篇讲协议设计和那个等结果的小工具。

## 同步是默认，异步是显式或超时结果

```text
POST /api/public/flows/<key>/invoke
```

不带参数时服务端会等到 run 终态再响应（上限由端点的 `syncTimeoutMs` 决定，5–120 秒可配，默认 60s）：

```json
{ "runId": "...", "status": "succeeded", "output": "M2-OK" }
```

注意一个刻意的设计：**业务失败也是 HTTP 200**。传输成功（调用鉴权通过、入参合法、流程跑完了）和业务成功（流程输出符合预期）是两层语义。流程失败时响应体是 `{status:"failed", error:{...}}`，只有鉴权/限流/校验这类传输层错误才用 4xx/5xx。调用方不需要在 catch 分支里解析业务错误。

转异步有两个触发：

1. 调用方显式：`?mode=async`，服务端建完 run 立即返回；
2. 隐式：同步等待超过端点超时阈值。

两种情况响应完全一致：

```text
HTTP 202
X-WBFM-Async: 1
{ "runId": "...", "status": "queued", "async": true }
```

202 + 固定响应头让调用方无论用哪种 HTTP 库都能稳定识别「这不是终态，拿 runId 去查」。

## 等待者不是执行者

同步等待的实现是一个纯等待函数（`terminal-wait.ts`）：

```ts
export function waitForRunTerminal(deps, runId, timeoutMs) {
  // 事件总线为主：订阅到终态事件即 resolve
  // DB 轮询兜底：1s 一次，防缓冲缺失等极端时序
  // 超时返回 { timedOut: true, run: 当前状态 }
}
```

它只订阅 EventBus + 定时查库，不占执行者、不影响执行。多个同步调用可以同时等各自的 run（虽然 v1 执行串行，等待是完全并发的）。事件总线缓冲可能因为跨 chunk/模块重载拿不到（M2 初期的真实情况），DB 轮询保证等待最终一定收敛，不会把调用方吊死。

## 轮询：按密钥隔离的只读视图

```text
GET /api/public/flows/<key>/runs/<runId>
```

两个安全细节：

1. **归属校验**：run 的 `endpoint_id` 必须等于当前密钥所属端点。A 密钥永远读不到 B 端点的 run，404 不区分「不存在」和「不是你的」；
2. 响应只放状态/输出/错误/时间和节点摘要，不放内部会话 id 等无关字段。

节点摘要里带 status/durationMs/error/outputs，调用方轮询一次就能拿到完整执行画像，包括策略拒绝文本（见 B08）。

## 只读 SSE：观察者永不影响执行

```text
GET /api/public/flows/<key>/runs/<runId>/events
```

v0.8 已经有内部 SSE（画布用），v0.9 把它抽成了内部/公开共用的响应构造器，差别只在鉴权和归属校验：

- 进行中的 run：订阅 EventBus 实时事件；
- 终态 run：从 node_executions 一次性回放（node_succeeded×N → run_succeeded/failed），回放完关流；
- 支持 `?after=<n>` 断线补丢（v1 语义从简，先按序号跳过）。

关键不变量：**SSE 是只读的，断开不取消 run**。这和 v0.8「断线即 abort」是本质区别——执行已经在队列里，观察者连不连、断不断、开几个，都只影响它自己能看到什么。验收时我们开了两个 SSE 连接读同一条 run，两边收到的事件帧逐字一致，run 照常 succeeded。

## 入参校验在进队之前

对外入口的入参不能信任。invoke 的 body 按 start 节点声明的字段严格校验（`start-input.ts`）：

- 必填缺失、类型不符（含 `null`）→ 422，响应带字段级 details；
- 默认值在服务端回填，未声明字段一律剥离（不让多余参数混进流程作用域）；
- 字符串长度也有上限。

校验发生在建 run 之前，坏输入不会产生 queued 垃圾行，也不消耗限流之外的执行资源。MCP 通道复用同一套校验，非法入参映射成 JSON-RPC `-32602`。

## 为什么不做 webhook 回调

超时转异步之后，调用方要轮询拿结果，有人会问为什么不提供「完成后回调你的 URL」。答案是本地威胁模型不允许：让本机服务向任意外部 URL 发请求等于内置一个 SSRF 跳板，还要管理回调密钥和失败重试。轮询把主动权完全留在调用方，语义可预测。webhook/事件类触发整体登记在 v0.10，届时配合桌面常驻端一起设计。
