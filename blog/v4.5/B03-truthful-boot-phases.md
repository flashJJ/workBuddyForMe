# 不要假进度条：用主进程阶段事件驱动启动文案

很多启动页会显示一条从 0% 平滑走到 100% 的进度条。它看起来专业，但大多数时候是假的：开发者并不知道每一步要多久，只是用定时器把数字推到 90%，然后等真正完成再跳到 100%。

我们的启动链路有几个耗时不确定的环节：版本变更时清 session、启动密码桥、`fork` 本地服务、每 250ms 健康检查。任何一步都可能被磁盘、杀毒软件或机器负载拖慢。与其猜一个百分比，不如只显示**真实发生的事实**。

## 一、把“用户看到的阶段”和“系统内部的事件”分开

用户不需要知道 `cipher-ready` 是什么，也不需要知道 `server-forked` 和 `server-healthy` 的区别。我们只暴露三个阶段：

| 用户阶段 | 含义 |
|---|---|
| 准备环境 | 应用已就绪、版本缓存已处理、密码桥可用 |
| 启动本地服务 | 本地服务已 fork、健康检查通过 |
| 载入工作台 | 主窗口已创建、首帧已就绪 |

内部事件更细：

```ts
type BootStageId =
  | 'app-ready'
  | 'session-cleared'
  | 'cipher-ready'
  | 'server-forked'
  | 'server-healthy'
  | 'main-created'
  | 'main-ready';
```

内部事件只用于日志和阶段映射，不直接展示。这样既保留了排障所需的粒度，又不会把实现细节倒给用户。

## 二、阶段映射写成纯函数

映射逻辑只有几行，但它是主进程和测试的共同契约：

```ts
function phaseForStage(stage: BootStageId): BootPhaseId {
  switch (stage) {
    case 'app-ready':
    case 'session-cleared':
    case 'cipher-ready':
      return 'prepare';
    case 'server-forked':
    case 'server-healthy':
      return 'server';
    case 'main-created':
    case 'main-ready':
      return 'workspace';
  }
}
```

它不读数据库、不碰 Electron、不依赖时间。测试只需要给 stage，断言 phase；将来新增内部事件，也必须在这里决定归属。没有“默认落到最后一个阶段”的偷懒分支，避免新事件悄悄显示成“载入工作台”。

## 三、事件从主进程推，不由页面猜

页面不知道服务是否已经 fork，也不知道健康检查是否通过。它只能等主进程推送：

```ts
bootSession.phase('server-forked');
bootSession.phase('server-healthy');
bootSession.phase('main-created');
```

每个阶段事件带 `index/total` 和 `atMs`，但页面只用它更新文案，不拿它算进度。`atMs` 用于日志与排查，不用于 UI 动画时长。

主进程还维护最后一次阶段事件和页面是否 ready。页面加载完成后，先补发当前模式，再补发最后一次阶段，避免“服务已经好了，页面还停在等待中”。

## 四、慢与失败：给确定性，不给假承诺

除了三个阶段，启动画面还有三种状态：

- 超过 8 秒：显示“启动比平时慢，仍在继续”；
- 超过 20 秒：显示“可能被安全软件拦截，可查看日志”；
- 启动失败：显示错误原因与日志路径，再走系统错误对话框。

这些文案的共同点是：**不承诺时间**。我们不说“马上就好”，也不说“还需要 10 秒”，因为那都是猜的。用户只需要知道应用还在工作，或者知道失败原因在哪里。

失败路径还有一个顺序要求：先把错误显示在启动画面里，再关闭启动画面并弹出系统对话框。否则用户先看到系统弹窗，启动画面已经消失，反而不知道发生了什么。

## 五、阶段事件也写进本地日志

每次启动结束，主进程往 `userData/boot-timing.log` 追加一行 JSON，记录版本、模式、各阶段耗时和总时长。只保留最近 20 行，超过 32KB 就截断，任何 IO 失败都静默降级。

这份日志不联网、不上报，只用于：

- 用户反馈“启动慢”时，能拿到真实阶段耗时；
- 开发时对比不同版本的启动回退；
- 性能基线脚本复用同一套打点，不需要另写一套计时。

日志和 UI 共用同一份 stage 定义，但用途不同：UI 只关心三个阶段，日志保留全部内部事件。这样既不污染用户界面，也不丢失排障信息。

## 六、为什么不做百分比

百分比会带来三个问题：

1. **无法校准**：每一步的权重是主观的，用户无法验证；
2. **容易倒退**：服务重启或健康检查重试时，百分比可能要回退，观感很差；
3. **鼓励造假**：为了“看起来顺滑”，开发者会用定时器补进度，最终和真实状态脱节。

阶段文案没有这些问题。它可能从“启动本地服务”停留很久，但用户知道它停在哪个阶段；配合慢提示，至少不会误以为应用已经死了。

## 七、小结

启动进度条的本质是“用确定性的 UI 表达不确定的耗时”。我们的替代方案是：

- 内部事件细，用户阶段粗；
- 映射写成纯函数，主进程与测试共用；
- 事件由主进程推，页面不猜；
- 慢和失败都给可读文案，不承诺时间；
- 同一套打点写入本地日志，供排障与性能基线复用。

这套做法不炫技，但它让启动过程变得可解释。对本地优先的桌面应用来说，可解释比“顺滑”更重要。
