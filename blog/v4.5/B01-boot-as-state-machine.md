# 双击之后到底发生了什么：把启动体验做成一条状态链

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手。它用 Electron 做外壳，内部 `fork` 一个 Next.js standalone 服务，数据全部落在本机。功能越加越多，启动链路也越来越长：清版本缓存、起密码桥、拉起本地服务、每 250ms 健康检查、创建主窗、等 `ready-to-show`。

问题不在于慢，而在于**用户什么都看不见**。双击之后，桌面没有任何窗口，只有鼠标转圈。五秒、八秒、十五秒，用户开始怀疑：是不是没点开？是不是被安全软件拦了？是不是卡死了？

这一轮我们只做一件事：把启动过程变成一条用户能看懂的状态链。

## 一、启动不是“加载页”，是一组事实

最直觉的做法是放一个加载动画，再配一条从 0% 走到 100% 的进度条。但启动耗时并不均匀：有时候服务 2 秒就绪，有时候密码桥慢，有时候杀毒软件在扫盘。进度条只能假装平滑，用户一旦发现“卡在 80% 不动”，不信任感反而更强。

所以我们先定义了三个用户阶段：

- 准备环境：应用已就绪、版本缓存已处理、密码桥可用；
- 启动本地服务：本地服务已 fork、健康检查通过；
- 载入工作台：主窗口已创建、首帧已就绪。

这三个阶段背后还有更细的内部事件，例如 `app-ready`、`session-cleared`、`cipher-ready`、`server-forked`、`server-healthy`、`main-created`、`main-ready`。内部事件只进日志，用户只看到三段文案。映射关系是一个纯函数，主进程和测试共用同一份定义，不依赖 UI。

```ts
function phaseForStage(stage) {
  if (stage === 'app-ready' || stage === 'session-cleared' || stage === 'cipher-ready') {
    return 'prepare';
  }
  if (stage === 'server-forked' || stage === 'server-healthy') {
    return 'server';
  }
  return 'workspace';
}
```

纯函数的好处是测试不需要启动 Electron：给一个 stage，断言它落在哪个阶段即可。我们不需要为“文案是否跟得上真实进度”写脆弱的 UI 快照。

## 二、启动画面必须是一旁路

第二个决定是：启动画面不能成为启动的前置条件。

很多实现会把主窗先藏起来，等启动画面里的动画播完，再创建主窗。这样做的问题是，动画成了关键路径：动画掉帧、视频解码失败、字体加载慢，都会直接拖慢应用启动。

我们的顺序反过来：

1. `app.whenReady()` 后最先创建启动窗；
2. 启动窗只负责显示，不参与后续启动步骤；
3. 主进程继续清缓存、起密码桥、fork 服务、建主窗；
4. 每个真实事件通过 IPC 推给启动窗；
5. 主窗 `ready-to-show` 后，启动窗退场，主窗显示。

启动画面加载失败也不影响应用启动，只是少了一层可见反馈。这条边界让启动逻辑和视觉表现解耦，后面加动画、换素材都不会碰主流程。

## 三、最小可见时间解决“闪一下”

如果启动很快，启动画面可能出现 50ms 就消失，观感像闪屏。我们设了 500ms 最小可见时间：主窗早就绪，也要等启动画面稳定显示 500ms 再交接。

这个值不是拍脑袋：低于 300ms，人眼容易把它当成闪烁；高于 800ms，热启动会显得拖沓。500ms 是一个折中，并且只影响“已经就绪”的情况，不会拖慢真正慢的启动。

## 四、慢和失败都要有话说

启动画面不仅要好看，还要在异常时给出可读信息：

- 超过 8 秒：显示“启动比平时慢，仍在继续”；
- 超过 20 秒：显示“可能被安全软件拦截，可查看日志”；
- 启动失败：切到错误态，显示原因和日志路径，再走原来的系统错误对话框。

这些文案不暴露堆栈，也不承诺“马上就好”。用户至少知道应用还在工作，或者知道去哪里找原因。

## 五、首启与日常分开

首次安装或覆盖升级后的首次启动，除了等待，还承担品牌介绍。我们给首启加了一段 8 秒短片，日常启动只播精简的 SVG 动画。两者共用同一个窗口和阶段桥，区别只在内容层。

这里有一个容易忽略的边界：**“播放过”不等于“用户看见过”**。如果安装器在安装完成后自动拉起应用，而安装完成页正好挡在启动窗前面，短片确实播放了，但用户没看见；下一次手动启动如果按“已播放”处理，就永远不会再播。这个问题我们后来单独修了一轮，下一篇会展开。

## 六、结果

- 冷启动约 1 秒内看见启动画面，热启动约 0.5 秒；
- 日常启动从主窗就绪到可交互约 2.3 秒；
- 首启完整片 8 秒，主窗在后台并行加载，不额外增加可交互时间；
- 启动失败时用户先看到可读原因，而不是只有一个系统弹窗；
- 打包态 12 项 e2e 全部通过。

启动体验的终点不是“动画好看”，而是**用户在任何时刻都知道应用在启动、启动到哪、失败为什么**。这条标准确定之后，动画、视频、文案都只是实现细节。
