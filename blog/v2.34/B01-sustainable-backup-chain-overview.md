# 备份可续：从「每次全量」到「基线加补量」

备份系统做到「能加密、能核对」之后，下一个问题很快就出现了：每次都要全量。

消息在增长，附件在增长，任务记录在增长。每做一次备份，就把所有历史重新打包一遍。备份越频繁，重复的字节越多。

这一版把备份从一次性动作，改成可持续的链：全量基线 + 若干增量 + 按序恢复。

## 一、为什么全量会变成瓶颈

全量备份的假设是「备份不常做」。

一旦用户开始每周、甚至每天备份，这个假设就不成立：

- 附件二进制会被反复打包；
- 消息与任务记录会被反复序列化；
- 归档体积与耗时随数据线性增长。

更隐蔽的问题是，用户会因为「太慢」而减少备份频率，最终又回到「很久没备份」的状态。

## 二、链模型的最小定义

一条备份链由三类信息组成：

```text
全量基线（sequence 0）
  → 增量 1（parent = 基线）
    → 增量 2（parent = 增量 1）
      → ...
```

每一段归档都记录自己的身份、所属链、序号与父段。恢复时按序号从 0 开始，逐段应用。

这比「按文件名排序」可靠得多，因为文件名可以被修改，manifest 不会。

## 三、增量只补新增

这一版对增量的定义刻意保守：

- 只带 `since` 之后新创建的行；
- settings 与 skills 以全量快照写入；
- 不含既有行的修改、删除、文档重解析与记忆覆盖。

原因不是实现不了，而是语义要诚实。没有变更日志与删除标记，就无法可靠重放「修改」和「删除」。与其做一个看起来完整、实际会丢状态的增量，不如明确它是「补量包」。

## 四、水位为什么取父段开始时间

增量需要一个时间下界。

直觉做法是用父段归档的完成时间，但这会漏掉「导出过程中新写入」的数据。

这一版取父段的 `startedAt`，也就是导出开始时间。这样重叠部分会被下一段重复包含，但重复由主键幂等吸收，不会丢行。

原则是：宁可重复，不可遗漏。

## 五、链状态放在哪

链状态包括「当前链尾」和「本机已恢复到第几段」。

它们不应该进入备份，也不应该跟随设置迁移到另一台机器。

所以这一版把导出历史与恢复链状态都放在 `meta` 表，而不是 `settings_kv`。设置轨可以备份，`meta` 不会。

## 六、恢复为什么要逐段

链式恢复没有做成「一次上传所有归档」。

原因有三点：

- 多文件上传会把所有归档同时读进内存；
- 单段失败时，已完成段不应该回滚；
- 逐段调用可以复用现有的单文件恢复接口。

前端负责排序与连续性校验，服务端负责顺序闸门。恢复仍然是每段一个事务，失败可重试。

## 七、这一版带来的变化

- 日常备份只导出新增数据，归档更小；
- 迁移仍用全量，语义清晰；
- 恢复可以按链核对，知道缺了哪一段；
- 备份历史可见，用户知道上次全量是什么时候。

## 八、边界

没有做删除/修改增量、没有做自动定时备份、没有做云端托管、没有做跨链合并。

这些能力都需要更底层的变更追踪，属于下一阶段。

## 九、一句话

**可持续的备份不是「更大的归档」，而是「更小的增量 + 可验证的链」。**

全量负责完整，增量负责频率，核对负责可信。
