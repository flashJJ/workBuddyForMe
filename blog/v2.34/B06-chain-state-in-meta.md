# 链状态为什么放 meta：备份登记不能跟着备份走

增量与链式恢复需要两份本地状态：

- 导出历史：上次全量是什么、链尾到第几段；
- 恢复链状态：本机已经恢复到第几段。

直觉做法是把它们写进设置表。

这一版没有这么做，而是放进了 `meta` 表。

## 一、设置表会被备份

设置轨会导出 `settings_kv` 的全部键值。

如果链状态放在设置表：

- 导出时会进入归档；
- 恢复到另一台机器时会被写进目标库。

结果是：新机器还没恢复任何归档，就已经「继承」了源机器的链尾。

这会直接破坏顺序校验。

## 二、meta 表不进入备份

`meta` 是数据库内部的键值表，用于迁移版本、实例信息等。

它不属于任何备份轨，也不会被设置轨读取。

把链状态放进去，语义就变成了「本机的运行状态」，而不是「用户配置」。

## 三、两类状态分开存

```text
meta backup.history        导出历史（最近 20 段）
meta backup.restoreChain   恢复链状态（已应用段）
```

分开的原因：

- 导出历史描述「我导出过什么」；
- 恢复链描述「我恢复过什么」。

两者可能不一致：用户可能导出三段，但只恢复了第一段；也可能在另一台机器恢复同一份归档。

混在一起会让「链尾」有两个含义。

## 四、最近一次导出怎么来

原来的 `backup.lastExport` 存在设置表，用于界面展示最近一次导出。

这一版不再单独写这个键，而是从 `backup.history` 的第一条派生。

少一个键，就少一处不一致。

旧设置键保留但不再写入，避免旧数据影响新逻辑。

## 五、恢复链状态的结构

```json
{
  "chainId": "链 id",
  "segments": [
    { "archiveId": "...", "sequence": 0, "kind": "full", "declaredTotal": 10, "writtenTotal": 10 }
  ],
  "missingSequences": []
}
```

每成功恢复一段就追加一条，并重算缺失序号。

恢复核对直接读这份状态，生成链级摘要。

## 六、状态丢失怎么办

如果用户清了数据库、换了机器，或者手动删了 meta：

- 增量恢复会被拒绝，因为找不到前置段；
- 重新恢复一次全量基线即可重置链状态；
- 基线恢复是幂等的，不会重复写入数据。

这比「状态丢了就默默继续」安全得多。

## 七、为什么不做全局链注册表

也可以设计一张独立的「归档注册表」表，记录所有导出与恢复。

但那需要数据库迁移、外键、清理策略，而当前只需要最多 20 条记录。

`meta` 的键值结构足够，而且不增加迁移成本。

## 八、一条经验

判断一份状态该放哪，问三个问题：

- 它会随备份迁移吗？
- 它是用户配置还是本机运行状态？
- 丢失后能否重建？

链状态属于「本机运行状态、不随备份迁移、可通过重放基线重建」，所以放 `meta`。
