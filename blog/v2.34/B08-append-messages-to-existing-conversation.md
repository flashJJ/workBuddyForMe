# 已有会话追消息：恢复逻辑里的一个危险分支

全量恢复的语义很简单：会话已存在就跳过。

这个语义在增量恢复里会出事：增量中最常见的数据，恰恰是「已有会话里的新消息」。

如果恢复端仍然「会话存在即跳过」，这些消息会被整段丢弃。

这一版为增量模式增加了一个分支。

## 一、原逻辑

```text
for each conversation:
  if assistant missing: skip
  if conversation exists: skip entire entry
  insert conversation
  for each message: insert
```

跳过的是整个条目，包括消息。

全量恢复这样写没问题，因为全量里的会话与消息是一体的：会话存在，说明这份数据之前已经恢复过。

## 二、增量为什么不能照搬

增量里的会话可能是一个「旧壳」：

- 会话本身在基线里已经存在；
- 消息是基线之后新产生的。

这时候跳过整个条目，等于丢掉了增量里最重要的内容。

## 三、分支怎么写

增量模式下：

```text
if conversation exists:
  keep existing header
  for each message: INSERT OR IGNORE
  count skipped conversation, count imported messages
else:
  insert conversation and all messages
```

关键点：

- 会话头不覆盖，标题与时间保持本机版本；
- 消息逐条幂等插入，已存在的不重复；
- 计数分开：会话算跳过，消息算导入。

## 四、为什么不全量覆盖会话头

增量只承诺「补新增」，不承诺「同步修改」。

如果覆盖标题与时间，就会出现「增量悄悄改了本机数据」的行为，超出语义边界。

保持本机版本，才能让用户理解「这段归档只带来了新消息」。

## 五、消息 id 冲突怎么办

消息按主键 `INSERT OR IGNORE`。

如果增量里的消息已经在目标库存在，插入被忽略，计数不增加。

如果消息 id 相同但内容不同（理论上不应发生），以目标库为准。这是幂等恢复的代价，也是可接受的。

## 六、外键与顺序

消息写入依赖会话存在。

增量恢复时，会话可能已经存在，也可能在本次恢复中新建。

两种情况的处理：

- 已存在：直接写消息；
- 新建：先写会话，再写消息。

助手不存在时仍然跳过整个会话，因为消息也无法通过外键。

## 七、计数怎么对齐

核对的口径是「会话 + 消息 + 分支 + 分支事件」。

增量恢复一个旧会话时：

- 声明的会话数是 1（旧壳）；
- 写入的会话数是 0；
- 写入的消息数是 N；
- 跳过数是 1。

总声明与总写入可能不完全相等，这是增量语义的正常结果，核对只告警不阻断。

## 八、测试覆盖

- 基线恢复后，增量中的新消息能写入已有会话；
- 会话标题与时间不被覆盖；
- 新会话正常创建；
- 重复恢复同一增量不产生重复消息；
- 会话的助手不存在时整段跳过，不报外键错误。

## 九、一条经验

恢复逻辑的每个「跳过」都要问一句：跳过的是整条数据，还是只跳过它的某一部分？

全量恢复可以整段跳过，增量恢复往往只能跳过「头」，不能跳过「内容」。
