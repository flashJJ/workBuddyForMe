# 上下文溢出了，先缩一半再试一次

预算、分层、缓存，全都建立在一个前提上：系统知道模型窗口有多大。

但真实情况是，很多模型记录里根本没有这个字段。OpenAI 兼容协议的模型列表接口不返回上下文长度，用户也不会主动填。

## 一、窗口从哪来

解析顺序有四层：

1. 模型记录里的显式配置，最可信；
2. 没配置就按模型名匹配厂商提示表：DeepSeek 128K、Claude 200K、Gemini 1M、Qwen 与 Kimi 131072、GLM-4 128K、GPT-4.1/4o 128K；
3. 还是没命中，回落 8192；
4. 最终结果统一受一个环境上限约束，防止误填成天文数字。

返回值同时带上来源标记：显式、提示、默认。排障时能一眼看出“这个预算是按 8192 算的”，而不是靠猜。

## 二、为什么保留 8192 的保守回落

提示表覆盖不到的长尾模型很多。

在这种情况下，高估窗口的代价是请求直接失败，低估的代价只是提前折叠一些旧内容。两害相权，选保守。

而且低估有兜底：真的装不下，溢出重试会再缩一次。

## 三、先能认出“溢出”

不同厂商的错误措辞不一样：有的说上下文长度超限，有的说 token 数超过上限，有的只给一个 400。

所以在模型适配层暴露一个判定函数，把常见的错误码与错误信息归一成“上下文溢出”这一种语义。上层只处理这一种情况，不去猜字符串。

## 四、重试一次，只一次

识别到溢出后，做三件事：

1. 保留全部 system 消息；
2. 从最近的 user 边界开始，保留约一半的历史；
3. 重新发一次请求。

只重试一次。连续重试会把一个明确的错误变成长时间的无响应，用户不知道系统在干什么，最后还是会失败。

## 五、为什么按 user 边界切

不能简单地“保留后一半消息”。

工具调用是成对的：assistant 发出调用，tool 返回结果。从中间切开会留下一个没有结果的调用，或者一个没有调用的结果，请求直接被上游拒绝。

按 user 边界切，等于按“对话轮次”切，天然不会拆散工具配对。找不到边界就放弃重试，把原始错误抛给用户。

## 六、50% 是个粗略但够用的比例

为什么是一半，不是固定条数？

因为消息长度差异太大：一条工具结果可能上万字，一条用户消息只有十个字。按条数保留没有意义，按字符比例又需要先精确分词。

一半历史，配合“保留 system、按 user 边界切”，在实测里能覆盖绝大多数溢出场景；剩下的极端情况，交给用户换模型或减少携带内容。

## 七、预算侧还有一道折叠

窗口解决的是“装不下”，折叠解决的是“装得下但不该装”。

工具结果超过软预算时，从最旧的开始折叠：保留首 600 字符、尾 300 字符，中间换成一行标记，并注明原文字符数。

两条规则同时存在，顺序是：先折叠（每轮装配时），再发请求；如果仍然溢出，走缩容重试。折叠是常态，重试是兜底。

最新一条工具结果永远不折叠——它是模型下一步要用的内容，折叠它等于让模型重新抓一遍。

## 八、提示表不准怎么办

提示表是估值，不是事实。

估大了，请求溢出，重试兜底；估小了，预算算得偏紧，折叠早一点，不会出错。用户也可以直接在模型设置里手填窗口，显式配置优先级最高。

这套组合承认了一个事实：在第三方模型生态里，“窗口大小”本身就是一个不可靠的输入。与其追求一次算准，不如让系统在算错时还能继续工作。

## 九、结果

- 生效窗口按“显式配置 → 厂商提示 → 8192 → 环境上限”解析，并标记来源；
- 溢出错误被归一识别，保留 system、保留约一半历史、只重试一次；
- 缩容按 user 边界切，不破坏工具调用配对；
- 超预算时折叠最旧的工具结果，最新一条永不折叠。
