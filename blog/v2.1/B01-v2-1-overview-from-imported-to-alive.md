# 总览：3D 形象的动画从哪来——把「能导入」做成「会动」

我们做的是一个本地优先的桌面 AI 应用：Electron 壳 + Next.js 前端 + 本地 SQLite 存储，形象渲染有两套后端（2D 用 Live2D，3D 用 three.js）。上一个大版本刚开放了 3D 形象导入——用户可以把合法的 VRM 模型拖进来，应用本地渲染，不上传、不重分发。

上线后反馈很集中：**形象是站着的，但它不动。**

这不是 bug，是规范。VRM 的静止姿态被规范钉死为 T-pose（双臂水平伸直的建模姿态），而一个光秃秃的 `.vrm` 文件里通常**一条 AnimationClip 都没有**。换句话说，3D 形象导入这件事，只解决了「模型在哪儿」，没有解决「模型怎么动」——文件里没有动作，应用就只会把它按 T-pose 摆着，再叠一点程序化的呼吸和视线跟随。看起来像个展品。

这个版本要回答的就是这个问题：**形象怎么才算活着。** 三条线：外部动作可以自己带进来、带进来之后会自己换、点在哪儿就演出对应反应。顺带把本版涨起来的几个超大源文件拆回去。

## 一、动作从外部来：为什么不做「内置动作库」

最直觉的方案是自己做一套内置待机动作（一套骨骼动画），随包发布。这条路被否掉有两个原因。

第一个是授权。动作动画和模型一样有著作权，自研一套能看的不便宜，采购一套又不能随包重分发。

第二个更重要：**动作与模型是解耦的**。VRM 的动画通过一套「规范化人形骨骼」的约定来驱动，只要模型符合规范，任何一段符合规范的动作都能套上去。也就是说，动作天然是可插拔的资源——那么正确的做法不是内置一堆，而是**把导入通道做出来**：用户自己带动作进来，应用负责校验、存储、播放。

于是这个版本的导入通道和上一个大版本的形象导入长得几乎一样：

| 环节 | 做法 |
|---|---|
| 客户端预检 | 扩展名与体积上限先在浏览器侧拒绝，少一次无用上传 |
| 文件格式 | 只收 glTF 二进制容器，且必须带 VRM 动画扩展标记；裸 JSON 版一律不收 |
| 本地嗅探 | 上传前就在浏览器里读容器的 JSON 段，把动画条数、生成器直接显示给用户，先给人看一眼 |
| 合法性与授权 | 必须勾选使用声明才能提交；服务端再校验一次格式 |
| 存储 | 二进制落本机数据目录，数据库只登记元数据与文件引用 |

服务端是两条独立链路（形象一条、动作一条），只共用了一个「读 glTF 二进制容器」的小模块：魔数与版本校验、取 JSON 段解析。这个模块本来是两份逐行重复的实现，这次抽成一份，两条链路各自保留自己的扩展名判定。

## 二、动作池：一条 clip 到一组 clip

导入通道打通后，第二个问题立刻出现：**用户导了三个动作，界面里只能选一个当待机，另外两个躺在列表里没用。**

所以待机动作从「一段 clip」升级成「一个动作池」：

- 池里**永远包含一个内置动作**（自制素材，随包发布），排最后——这是兜底：用户一个动作都没导，形象也不能退回 T-pose 站着；
- 用户选中的那条排在池首，作为初始待机；
- 其余已导入动作按列表顺序进池；
- 并发加载上限 8 条，避免导了一堆动作时启动明显变慢；
- **任何一条加载失败只跳过它自己**，不牵连整池——这在早期版本里踩过：选中项加载失败就整条回落到内置，用户会以为自己的动作坏了。

然后是「轮播」：每隔几秒从池里随机挑一条不等于当前的 action，交叉淡入淡出切过去。开关和间隔秒数（3–60 秒，默认 8）放进设置，跟已有设置项同一份存储。

还有一个交互上的小设计：**点击形象时，从池里随机抽一条作为一次性动作播一次，播完自动回待机。** 这就让「动作池」不只是待机素材，同时成了互动素材——用户导入的动作越多，点击的反馈越丰富。

## 三、一个不在需求里的硬约束：只能有一个 AnimationMixer

上面两条都是产品需求，第三条是工程约束，而且它决定了实现长什么样。

three.js 里播放动画要用 `AnimationMixer`。很自然的想法是：待机动作一个 mixer，点击手势另一个 mixer，互不干扰。

**这条路走不通。** 两个 mixer 绑定的是同一批规范化骨骼节点，各自往里写四元数，最后谁在同一个节点上写的权重大，取决于渲染循环里调用的顺序与权重混合结果，而不是「两个动作叠加」。实测表现是点击之后模型猛地弹回 T-pose 再抖回来——因为手势 mixer 还没淡入，待机 mixer 写进去的姿态被覆盖了。

所以这个版本的播放层是**单 mixer + 动作池**：待机 clip 和一次性手势 clip 都在同一个 mixer 里，靠 crossFade 的权重过渡来做切换，靠 `LoopOnce` + `clampWhenFinished` + mixer 的 `finished` 事件来做「播完回退」。手势播放期间，轮播计时直接归零，不打断。

## 四、取景：动作变多之后，相机也得跟着改

形象渲染有个容易被忽略的环节：**取景**。容器宽度不定（对话页侧栏是细长条，桌宠窗是宽扁的小窗），所以模型要按容器比例算一个缩放，保证整身落在视锥里。

原来的取景只按「某一个姿态」的包围盒算缩放。这在只有一个待机动作时勉强能用，动作池一上线立刻暴露：轮到摆幅大的动作时，按小动作算出来的缩放会把手臂裁出画面。

正确做法是**采样整个动作池的包围盒并集**，用并集算缩放。这里还撞上了一个 three.js 的行为细节——逐帧采样包围盒时，如果不清掉网格自己的包围盒缓存，你拿到的永远是第一帧的盒子。修之前的采样宽度是 0.587，修之后是 1.089，差了将近一倍，四肢当然被裁。

## 五、顺手处理的另两件事

**交互管道收口。** 上一个大版本已经在做「桌宠点击反应」：按区域和手势查一张配置表，生成动作链，交给执行器去播放。这个版本把它补齐成四段式——事件归一化 → 纯函数门控（勿扰时段 / 关系等级 / 区域冷却）→ 执行器按类型分发 → 广播给事件导演与感知层。以前的「点一下弹一下」，现在点击会真的驱动一次动作演出。

**把涨起来的文件拆回去。** 我们仓库有一条硬门禁：手写源文件不超过 300 行。这个版本写胖了三个文件（740、419、404 行），加一个聚合导出的纯 barrel（304 行）。拆法只有一条原则——**只搬代码，不改逻辑**：一个负责编排的门面类，把「动作池与播放」「表情与口型」「姿态叠加」「三段式状态机」四条行为轴分别外迁成协作者；一个 400 行的舞台组件，把两个命中盒实体外迁成独立组件；一个 419 行的画布组件，把资源装载与取景算法外迁成模块。barrel 是纯转发、无逻辑，按白名单登记。拆完门禁从 4 处违规回到 0。

- 真机验证（Electron 开发态，两个窗口尺寸 255×643 与 262×342）：动作池每条 clip 的逐帧世界包围盒都落在视锥内、待机动作按 8 秒间隔切换、真实点击身体触发一次性动作并在播完后自动回待机、设置页 6 个目标节点全部挂载。

刻意不做的事：

- 动作池上限 8 条（并发装载与取景采样都按它封顶），导入更多动作时超出部分不参与轮播，但仍可被选中为待机；
- 动作元数据只读条数与时长，不臆造许可字段，也不做动作改名/备注编辑（表里留了列）；
- 手势仍以单击与长按为主，双击保留了「回到主窗口」的窗口行为，没有当成角色动作；
- 仍不放开外部 2D 模型导入（授权边界），不捆绑任何音视频素材。

## 七、这一版真正的收获

三条线里最难的不是功能，而是那条一开始没想到的约束：**多动作不等于多播放器。**

只要两段动画驱动的是同一批骨骼，它们就必须由同一个混音器统一调度权重，否则「叠加」会退化成「覆盖」。这条约束在只有一个动作时完全不可见——它只在你做「动作变多」这件事的时候才会以「模型抽搐」的形式跳出来。

同理，取景这件事的复杂度也不来自相机本身，而来自**动作集合的上界**：只要存在一条摆幅更大的动作，取景就必须按所有动作的并集算。功能变多时，先找到那个「唯一的调度者」，再找到那个「最坏情况的输入」，这两件事往往比多写几个功能更值钱。
