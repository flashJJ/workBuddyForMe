# 一个 three.js 场景里，为什么绝不该出现两个 AnimationMixer

我们的桌面 AI 应用里，3D 形象用 three.js 渲染。形象本身只是一堆骨骼网格，真正动起来靠 AnimationMixer 播放动画 clip。

做「待机动作导入」这个功能时，需求是这样的：用户可以导入多段动画，应用每隔几秒随机换一段当待机；点击形象时，再抽一段当一次性动作播掉，播完回到待机。

最直觉的实现是拆成两个播放器：一个管待机循环，一个管点击手势。**这个直觉是错的**，而且错得很隐蔽——它在只有一个动作的时候完全看不出来。

## 症状：点一下，模型抽一下

第一版实现里，待机动作有自己的 mixer，点击手势有另一个 mixer。点下去的现象是：角色先猛地弹回 T-pose（双臂平举），再抖一下恢复成待机姿态。

一开始怀疑是姿态叠加层（视线跟随、呼吸那种程序化修改骨骼的代码）在抢写入。把叠加层全关掉，症状依旧。于是把怀疑对象换成了「两个 mixer 的初始化顺序」，改了顺序，症状变成「先抖一下再弹回」。**顺序能改变症状的形状，说明问题不在顺序，而在两个写入者本身。**

根因是：两个 mixer 绑定的是**同一批规范化骨骼节点**。mixer 播放动画的方式是每帧计算自己所有 action 在这一帧的权重，然后按权重把四元数写进目标节点。两个 mixer 各算各的、各自写一遍，最后一个写的覆盖前一个写的。所谓「手势动作叠在待机动作上」这件事，根本不是混合，而是覆盖。

而 clip 之间那种「平滑过渡」，是**同一个 mixer 内部**才成立的机制：`crossFadeTo` 让两个 action 的权重在一段时间里从 1→0 与 0→1 互补，mixer 再把两份姿态按权重插值。跨 mixer 没有这回事。

所以结论是一条硬约束：**只要两段动画驱动同一批骨骼，就必须由同一个 mixer 统一调度。**

## 正确形态：单 mixer + 动作池

改成单 mixer 之后，整个播放层只剩一个「动作池」的概念：

```
池 = [ 用户选中的动作，其余已导入动作...，内置兜底动作 ]
```

几个设计取舍：

- **内置动作永远在池里，且排在最后。** 兜底优先于顺序直觉：用户一个动作都没导、或者导入的动作文件损坏，形象也必须有一段能播的动画，而不是退回 T-pose 站着。为此池的构建逻辑里专门有一条——如果裁剪到并发上限时把内置动作挤掉了，就把它替换回最后一位。
- **加载失败只跳过它自己。** 池是并发装载的（上限 8 条，避免导了一堆动作时启动肉眼可见地变慢），任一文件失败只从池里剔除，不影响其他成员。
- **初始待机取池首。** 用户选中的动作排在最前面，语义是「我明确选的就是我的默认样子」；没选过就用内置。

## 两种切换，两种生命周期

池里跑的东西分两类，生命周期完全不同，但都在同一个 mixer 里：

**循环待机**——`LoopRepeat`，无限循环，永不结束。切换时从当前 action 淡到下一个：

```
下一步动作.reset()
下一步动作.setLoop(LoopRepeat, Infinity)
下一步动作.setEffectiveWeight(1)
下一步动作.play()
当前动作.crossFadeTo(下一步动作, 0.4, warp)
```

这里有个容易踩的顺序问题：`crossFadeTo` 要求**目标 action 已经在播放**，否则淡入的其实是一个没被激活的 action，视觉上就是「卡一下再切过去」。所以必须先 `reset().play()` 再 `crossFadeTo`。最后那个 `warp` 参数会按两段 clip 的时长比调整播放速率，让过渡期间的动作幅度不突变——两个动作时长差得越多，这个参数越值得开。

**一次性手势**——`LoopOnce` + `clampWhenFinished`，播一次停在末帧。它必须自己知道什么时候结束：

```
手势.reset()
手势.setLoop(LoopOnce, 1)
手势.clampWhenFinished = true
手势.setEffectiveWeight(1)
手势.play()
当前待机.crossFadeTo(手势, 0.25)
// 等 mixer 抛出 finished 事件 → 淡回待机
```

回退这一步是异步的：给 mixer 挂一个 `finished` 监听，事件里比对「结束的是不是当前这个手势 action」，是的话再把待机 action `reset().play()` 并把手势淡出。**这里必须用 action 实例做比对**，因为 mixer 会对所有 action 抛 `finished`，用 clip 名比对会误伤同名的其他 action。

还有一个边界值得单独说：**如果随机抽到的手势恰好就是当前待机那条 clip**，`clipAction` 返回的是同一个 action 实例（three.js 对同一 clip 只缓存一个 action）。这时不能走「两个 action 交叉淡入」的路径——那是拿自己淡自己。代码里对这种情况单独分支：把手势标记与待机标记指向同一个 action，播完只做「把循环参数改回去、重置播放」即可。

## 手势和轮播的互斥

两个机制都会在同一个 mixer 上动手，所以要定优先级。

规则很简单：**手势优先，轮播让路**。一旦有一次性手势在播，轮播计时器直接归零重新计，不允许在这时候换待机动作——否则会出现「点击反馈播到一半，背景里的待机动作被换掉，两段动画在同一批骨骼上打起来」。

反过来，点击也不该打断正在播放的手势（用户连点两下，第二次没有反应），这对交互体验反而更自然：一个反馈完整播完，比两个反馈互相截断更像「有反应」。

## 一个统计口径的小坑

做验证的时候发现，池里几段动画在调试输出里名字全都一样（都叫 `Clip`）——因为播放器给的默认动画名就是它，用户的文件里没有额外命名信息。

结果就是「按名字采样确认轮播生效」这条验证方式失效了：日志里每一条看起来都一模一样，看上去像「从来没换过动作」。后来把采样口径从「clip 名」换成「clip 时长」，才看出待机动作确实在 5.97 秒和 7.27 秒两段之间按 8 秒间隔来回切。

**同一个容器解析出来的一批资源，命名往往是最不可靠的标识**。验证时优先用数值特征（时长、条数、文件大小），别用名字。

## 小结

- 同一批骨骼上的多段动画，必须共用一个 mixer，否则「混合」会退化成「覆盖」；
- 交叉淡入的目标 action 必须先激活再 `crossFadeTo`；
- 一次性动作的结束要靠 `finished` 事件 + action 实例比对，不能靠 clip 名；
- 池化资源时，兜底项要保证一定在池里，失败要局部化；
- 两个会互相干扰的机制（轮播 / 手势）必须有明确的优先级，而不是「谁先来谁赢」。

下一篇讲取景：动作变多之后，相机缩放为什么必须按「所有动作」来算，以及逐帧采样包围盒时那个差了一倍的陷阱。
