# 逐帧采样包围盒，为什么永远拿到第一帧的盒子

我们的桌面 AI 应用里，3D 形象（VRM）用 three.js 渲染。形象要放在一个尺寸不固定的容器里：对话页右侧是一条细长的侧栏（实测 255×643），桌宠模式是一个宽扁的透明小窗（262×342）。所以模型必须按容器比例算一个缩放，保证整身落在相机视锥里——这个环节我们叫**取景**。

取景一开始很天真：量一下模型的包围盒，按容器宽高比算缩放让模型刚好放进去。它需要包围盒，而包围盒这件事，在这条路上连踩了四个坑。

## 坑一：静态包围盒不等于动画包围盒

第一版取景量的是「当前那一帧」的包围盒。只有一个待机动作的时候勉强能用，动作一换成挥手的，问题立刻来了：**轮到摆幅大的那一帧，手臂被裁出画面。**

原因很直白——用一帧算出来的缩放，只能保证那一帧合适。其他帧的四肢摆到更外面，自然超框。

修法是：**取景之前先把整段动画跑一遍，逐帧采样包围盒求并集，用并集算缩放。**

```
acc = null
for 每一帧:
    mixer.update(步长)
    vrm.update(步长)
    box = 当前姿态的世界包围盒
    acc = acc ? acc.union(box) : box
用 acc 算缩放
```

## 坑二：逐帧跑完了，采到的宽度却没变

加上逐帧采样之后，日志里的采样宽度是 **0.587**——和一帧采样的结果几乎一样，看起来像「动画跑了但没影响包围盒」。

打出每一帧的盒才发现：**每一帧的盒完全一样，就是第一帧那个。**

根因在 three.js 的一个行为细节：`Box3.setFromObject` 遍历到 Mesh 时，**只有在该网格自己的 `boundingBox` 为空时才去 `computeBoundingBox()`，否则直接复用缓存的旧盒**。骨骼动得再欢，缓存的盒还是第一次算的那个。

所以逐帧采样必须先把缓存清掉：

```
遍历子树: 每个 Mesh 的 boundingBox = null
更新世界矩阵
再 setFromObject
```

把清缓存这一步加进去，同一段动画的采样宽度从 **0.587 变成 1.089**——差了将近一倍。差出来的这部分，就是之前被裁掉的手臂。

这个补丁后来被抽成一个共用小模块（「失效缓存 + 按当前姿态重算世界包围盒」），因为它在两条路径上都要用：取景前的采样，以及取景函数自己的兜底测量分支。

## 坑三：动作变多之后，并集必须覆盖「所有」动作

第三个坑是这个版本才出现的。形象从「一段待机动作」升级成「一个动作池 + 定时随机轮播」之后，取景的并集只覆盖当前那一段就不够了：**轮到摆幅更大的动作时，按小动作算出来的缩放会把四肢裁掉。**

也就是说，采样范围要从「一段动画」扩到「池里每一条 clip」。

直接遍历每条 clip 逐帧跑会有性能问题——导入的动作越多、单段越长，启动时卡得越久。所以加了一个按**时长占比**分配的采样预算：

- 总采样帧数上限 900 帧；
- 每条 clip 拿到的帧数 = 总上限 × （该 clip 时长 / 池内总时长），再和「该 clip 逐帧跑满所需的帧数」取小；
- 每条 clip 至少采 12 帧，避免极短的 clip 采不到极值。

结果就是：只有一段动作时，它基本能被逐帧采满（900 帧的预算足够 15 秒的动画按 60fps 采样）；动作池里有 8 段时，每段大约 110 帧——对 2 秒的短动作来说几乎是逐帧，对 8 秒的长动作则是每 70 毫秒采一次，配合 8% 的取景留边，够用且启动不卡。

## 坑四：取景函数必须幂等

取景函数会被反复调用：容器尺寸一变就要重算缩放。而它内部要做的第一件事是「把模型摆正再测量」，于是就有了一个隐蔽的幂等性要求——

```
先把 scale 置 1、position 置 0
更新世界矩阵
再测量/缩放/对齐
```

如果跳过「先归零」这一步，第二次调用时模型身上已经带着上一次算出来的缩放，测出来的包围盒是**放大之后**的盒，于是算出一个小得多的新缩放，再下一次调用又放大回去。表现是容器拖拽尺寸时模型反复放大缩小地抖——一个典型的「重复调用不幂等」bug。

顺手记一条相关的：测量和对齐必须**完全基于传入的包围盒**推导（相机位置、模型底部对齐都从盒算），不要掺任何「当前姿态」的信息。否则即使幂等了，不同调用时刻也会算出不同结果，尺寸变化时画面会跳。

## 怎么证明「不裁」是真的

这类几何问题不能靠肉眼看截图，因为裁掉一点点很难察觉。验证方式是把「模型」和「视锥」都变成数字：

1. 取当前相机的焦距、宽高比和距离，算出模型所在平面上的可视矩形（左/右/上/下边界）；
2. 对动作池里**每一条 clip**，逐帧推进动画，每帧失效网格包围盒缓存后重算世界包围盒；
3. 断言每帧的盒都落在可视矩形里。

实测结果（两个窗口尺寸都跑了一遍）：池里两段动作的逐帧世界包围盒分别在 x∈[-0.308, 0.310] / y∈[-0.003, 0.968] 与 x∈[-0.251, 0.266] / y∈[-0.011, 0.936]，可视矩形是 x∈[-0.375, 0.375] / y∈[-0.455, 1.437]，两条都是 fitsX / fitsY 双真。

## 小结

- three.js 的 `Box3.setFromObject` 会复用网格自己的包围盒缓存，**逐帧采样前必须置空**；这是「采样了但看起来没生效」类问题的第一嫌疑；
- 取景这类「算一个覆盖全场景的参数」的逻辑，输入必须是**最坏情况**（动作池里摆幅最大的那条），不是平均水平；
- 采样预算是可分配的资源：按时长占比分配 + 总帧上限，能在「精确」和「启动耗时」之间拿到可解释的折中；
- 会被重复调用的几何函数必须幂等：先把状态归零再测量；
- 几何正确性用数字验证（盒 vs 可视矩形），不要用眼睛看截图。
