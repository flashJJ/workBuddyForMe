# 把并行分支画进同一张图：三条边界与一个容量上限

我们的桌面 AI 应用是本地优先、单人开发的助手。分支会话跑起来之后，一个新的问题立刻出现：父会话的过程图该怎么画？

最直接的做法是把子会话的全部聊天事件也灌进父图。结果是一张几十个节点的网：用户想找「哪条分支失败了」，得先在一堆工具调用里分辨哪些属于哪个子会话。另一个极端是只在父会话挂一个「有 3 条分支」的徽标，图干净了，但形状、状态、回传全都看不见。

这一版选的是中间路线：**父图只当索引，不当复制品。** 分支用四个事件表达生命周期，图只投影这四类事件，子会话细节留在子会话里看。

## 分支事件是图的唯一事实来源

分支状态不靠 UI 内存，也不靠读分支表临时拼。每次派生、启动、终态、回传，都往 `session_events` 追加一条记录：

- `scope='branch'`，`scopeId` 是分支 id；
- 类型只有四种：`branch_created`、`branch_started`、`branch_status`、`branch_returned`；
- payload 带分支 id、父会话 id、子会话 id、根会话 id、标题、目标、深度，终态再带状态原因、摘要与 evidence。

这四类事件天然有顺序。服务测试直接断言落库顺序是 `created → started → status → returned`，而不是只看最终状态。顺序被固定下来，图投影才有稳定的因果链：先有分支节点，再有回传节点。

| 事件 | 投影出什么 | 关键字段 |
|---|---|---|
| `branch_created` | 分支车道、分支节点、子会话占位节点 | 标题、目标、子会话 id、深度 |
| `branch_started` | 分支节点状态改为运行中 | 状态 |
| `branch_status` | 分支节点状态与原因更新 | 状态、原因 |
| `branch_returned` | 回传节点（可附带错误节点） | evidence、摘要、原因 |

## 归属边界：父图只收直接分支

事件表是全局的，一条深度为 2 的分支也会写自己的事件。如果父图按「会话树」收集，嵌套分支就会串进来，父会话的图里出现别人的子任务。

第一道闸在收集层：图服务用 `listByParent` 取当前会话的直接分支，再逐条读事件。深度 2 的分支只挂在它自己的父会话下，因此只会出现在那一层的图里。

第二道闸在投影层：分支事件的 payload 里带 `parentConversationId`，投影时再校验一次。即使有人绕过收集层把事件塞进来，归属不符的也会被丢掉。两层过滤看起来冗余，但它防的是将来某个调用方「顺手」扩大收集范围。

投影单测里有一个专门的负例：给父会话投影一条 `parentConversationId` 指向子会话的嵌套分支事件，结果图里只剩根节点。这个断言比注释更能阻止串味。

## 粒度边界：占位节点不重放子会话

父图里每条分支固定产生三个节点：

| 节点 | 类型 | 挂载位置 | 说明 |
|---|---|---|---|
| 分支节点 | `branch` | 父会话根节点下 | 标题、目标、生命周期状态 |
| 子会话节点 | `run` | 分支节点下 | 占位，summary 存子会话 id |
| 回传节点 | `branch_return` | 分支节点下 | evidence 摘要、产物数量、原因 |

三条边对应三段关系：`parent_to_branch`、`branch_to_child`、`branch_to_return`。分支车道挂在根车道下，颜色用强调色，这样一眼能看出这一列是「派生出去的任务」，不是主线的步骤。

子会话节点是刻意做薄的。它不重放子会话的聊天事件，也不独立维护状态；状态以分支节点为准。用户想看具体跑了哪些工具、哪一步出的错，点「打开子会话」即可。**父图回答「有没有、到哪一步」，子会话回答「具体怎么做的」。**

一次「派生并成功回传」在图上大致是这样：

```text
根：父会话
├── 分支：竞品调研（succeeded）
│   ├── 子会话：占位
│   └── 回传：竞品 A 领先
└── 分支：写摘要（failed）
    ├── 子会话：占位
    └── 回传：上游超时
        └── 错误：上游超时
```

图接口还支持只取分支车道。父会话主线很长时，单独看分支可以避免主线节点把视野挤满；这也是「索引」定位的一部分：需要哪一层，就取哪一层。

## 回传节点写什么

回传节点只在 `branch_returned` 时创建。它先按 Schema 校验 evidence：合法就取摘要与产物列表，非法就回落成空，但节点仍然创建——图的形状不能因为一条坏证据而缺一块。

摘要截到 180 字，再拼上「产物 N」和状态原因。产物为 0 时不显示计数。一条失败分支的节点通常只剩原因，例如「上游超时」，用户不用展开就知道该不该点进去。

失败、预算触顶、中断这三类终态如果带原因，会额外生成错误节点，挂在回传节点下。成功的分支不生成错误节点，避免图里出现一堆「无错误」的空壳。

回传节点只投影产物数量，不逐项建节点。当前 evidence 的产物列表还没有从消息里提取，生产环境里通常是空数组；这是明确的欠账，逐项提取要回到消息的 tool trace 与 artifacts。节点宁可显示「没有产物」，也不编造产物。

## 容量上限：图是导航，不是审计

图服务给分支车道设了两道量：最多取最近 50 条直属分支，每条分支最多读 200 个事件。

这两个数字不是正确性边界，是可读性边界。一个父会话真有一百条分支时，全画出来没人看得懂；一条分支跑了几百步时，全部塞进快照也只会拖慢首屏。超出的事件仍在 `session_events` 里，只是不进这张快照。需要审计时查事件表，需要导航时看图。

容量上限的代价是「图可能不完整」，所以它必须可解释。上限写在服务常量里，而不是散落在 UI 的截断逻辑里；改动只有一处，行为可预测。

## 取舍：为什么不把子会话的事件也画进来

把子会话的聊天事件投影进父图，看起来信息更全，实际会破坏两件事。

第一是归属。子会话的聊天事件 `scope='chat'`、`scopeId` 是子会话 id，父图的根过滤规则会把它当成「别的会话」；要放进来就得为分支特设一套跨会话规则，规则一多，图就不再是「一个根的事件投影」。

第二是成本。子会话可能有几百条事件，父图乘上分支数就失控；而这些细节在打开子会话时本来就能看到。重复展示不会增加信息，只会增加噪声。

所以父图保持「索引」定位：形状、状态、回传三件事说清楚，其余交给子会话。

## 还没有实时帧

分支状态目前靠面板 5 秒轮询、图 10 秒快照收敛。实时帧总线仍只覆盖聊天、任务、流程与子代理运行，分支没有接进去。

这不是遗漏，而是排序：分支的状态变化是低频的（排队、运行、终态），轮询的延迟可以接受；把分支帧接进总线需要先定义稳定的帧契约，否则只是把轮询的抖动换成推送的抖动。取舍与代价会在讲界面时展开。

## 数字

core 包 1475 个单测里，分支与图投影覆盖了事件顺序、三类节点、三条边、嵌套过滤、错误节点与容量截断。数据库层 260 个单测保证事件表的 scope 枚举与索引可用，共享层 349 个单测锁住分支类型与 Schema。全量单测 3153 例。
