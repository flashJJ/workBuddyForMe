# 回传不是聊天消息：分支证据的六个部分与三条铁律

子会话结束之后，父会话需要知道什么？

最容易想到的答案是「把结果作为一条消息插进父会话」。我们明确不做。原因不是技术上做不到，而是那条消息会改变父会话的语义：它和用户自己说的话混在同一条转录里，后续上下文、检索、导出都会带着它走。

分支证据因此被做成了独立数据：展示在分支列表、回传卡片与图车道里，进不进父会话由用户决定。

## 为什么不能写成聊天消息

消息一旦插入转录，就默认被当成「对话的一部分」。父会话下一轮回复会把它纳入上下文，用户回顾时会分不清哪句是自己说的，导出时也无法区分结论来源。

失败与取消的分支更尴尬：它们可能没有正文，只能插入一句「该分支已取消」。这条消息没有信息量，却永久留在转录里，还会被检索命中。

最根本的问题是时机。自动插入意味着父会话在子会话结束的瞬间就接受了结论，用户失去了「先核对、再汇总」的机会。分支越多，这个风险越大——三条分支各说一套，父会话却已经把它们都当成事实。

## 证据的六个部分

| 部分 | 字段 | 为什么需要 |
|---|---|---|
| 身份 | 分支 id、父会话 id、子会话 id、根会话 id | 回答谁派生、谁执行、属于哪棵树 |
| 状态 | 终态枚举 | 成功、失败、取消、中断、触顶必须可区分 |
| 摘要 | 正文截断到 4000 字 | 父会话不必打开子会话就能判断价值 |
| 产物 | id、标题、类型，最多 50 条 | 后续挂载文件、报告、图片的引用位 |
| 用量 | 输入、输出、总 Token，可为空 | 预算复盘与成本解释 |
| 核对 | 固定为真，加上创建时间 | 强制父会话先核对 |

四个会话 id 里，根 id 最容易被忽略，但它决定了预算归属。只存父与子，想算整棵树的用量就得递归向上；根 id 让一次查询就能聚合。

摘要截断到 4000 是硬上限。截断是明确的、可预期的，比悄悄丢内容或让字段无限增长都好。用户想知道更多，可以打开子会话看完整正文。

产物上限 50 也是同样的思路：契约先给一个明确的容量，避免某次运行塞进几千条，把界面和传输拖垮。

## 只在终态生成

运行中的分支不写证据，哪怕已经积累了大段正文。

原因很简单：半成品摘要会被误读成最终结论。用户在面板上看到一段像样的总结，很容易忘记它还在跑，然后基于它做决定。

终态写入时，一次完成四件事：写证据、写结束时间、清空预留、写状态原因。四个字段同一次更新，不会出现「有证据但没有结束时间」或「结束了但预留还在」。

归档不改证据。归档只是把它从默认列表里收起来，恢复后一切原样。

## 失败与取消允许空摘要

成功的分支摘要取正文前 4000 字。失败与取消的分支可能没有任何正文，摘要允许为空。

但必须有状态原因。失败要写清楚是上游超时、供应商报错还是运行器异常；取消要写「已取消」；中断要写「进程重启，分支已中断」。

空摘要加明确原因，比编一段总结诚实。用户看到「失败：上游超时」，知道该重试还是该换供应商；看到一段编出来的「本次调研发现……」，只会被误导。

## 损坏数据不能阻断列表

证据以 JSON 文本存在数据库里。读取时先解析，再用 Schema 校验，任何一步失败都返回空。

这条容错不是防御性编程的洁癖，而是列表可用性的底线：一条证据损坏，最多让这一张卡片不显示回传区，不能让整个分支面板打不开，更不能让用户以为所有分支都丢了。

Schema 还承担契约职责：字段类型、长度、枚举、可空性都写死。旧数据缺可选字段时按默认值补齐；新增字段必须可选，否则旧行立刻失效。

## 三条铁律

第一条，核对标记固定为真。类型不是布尔，而是字面量真。系统不提供「已核对」的自动开关，也不根据成功状态推断可信度。父会话必须先看摘要、必要时打开子会话，再决定怎么汇总。

第二条，不自动重试。失败的分支停在失败，重试由用户点。自动重试会让一次上游抖动变成多次计费，也会让用户分不清看到的是第几次结果。

第三条，不自动派生。回传不触发新分支。否则一条分支成功后自动派生验证分支，验证分支再派生复盘分支，预算与图结构都会失去边界。

这三条共同回答一个问题：系统可以自动执行，但不能自动替用户下结论。

## 取舍：产物先只留结构

产物字段定义完整：id、标题、类型，最多 50 条。但当前回传的产物数组是空的。

原因是提取成本。产物信息散在消息的工具调用记录与附件引用里，要跨模块解析；一旦把这段解析塞进回传路径，证据生成就会耦合进聊天内部结构，任何消息格式调整都可能让回传失败。

所以这一版只做契约：字段先冻结，消费方按结构渲染，图车道先显示数量。逐项提取留到后续，从消息记录里稳定地抽出来，再填进这个已经存在的数组。

代价是用户暂时看不到具体产物列表；收益是回传协议不会因为提取逻辑反复改动。契约先行、实现分期，在单人维护的项目里通常比「一次做全」更稳。

## 父会话实际看到什么

分支卡片显示：标题、目标、状态徽标、深度、总 Token、「需核对」标记、摘要、产物数量。归档分支默认折叠，展开后仍可恢复或删除。

图车道里的回传节点显示状态与摘要，点击可以打开子会话。父会话本身不新增消息，转录保持干净。

子会话顶部则显示来源：父会话标题、分支目标、返回父会话的入口。用户从任何一侧都能回到关系里，不需要记 id。

## 数字

共享层 349 个单测里有 4 个覆盖证据 Schema 的边界与八态；数据库层 260 个单测覆盖证据损坏回落与归档过滤；core 层 1475 个单测覆盖终态生成与失败原因；API 集成 11/11；Web e2e 141/141；安装包约 202 MB，`/chat` 首屏 494 kB。

## 收口

分支会话的完整闭环，最后落在一个很朴素的判断上：并行可以提高吞吐，但只有可核对的回传才能提高可信度。

独立上下文解决「串味」，准入与预算解决「失控」，失败隔离解决「一颗老鼠屎坏一锅汤」，证据契约解决「结论从哪来、能不能用」。四件事都做完，用户才敢把长任务真正交出去。
