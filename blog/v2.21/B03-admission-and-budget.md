# 派生之前先算账：分支准入与预算的五个检查

分支功能最危险的时刻，不是创建失败，而是创建成功之后失控。

一个用户点了几次「从此分支」，很快就有七八条子会话同时跑模型；每条再派生一条，图变成一张网；预算没有人合并计算，直到某次调用突然失败，才发现整棵会话树已经消耗了几十万 Token。

所以准入不放在运行中，放在派生之前。顺序固定，任何一项不通过就拒绝，并给出原因。

## 五道门，顺序不能换

1. 环检测：新子会话是否已经在祖先链里。
2. 深度：新分支的 depth 是否超过上限。
3. 子节点数：父会话未归档分支是否已满。
4. 并发：整棵会话树里 running 与 waiting 是否已满。
5. 预算：整棵树已用加已预留是否触顶。

顺序不是随便排的。环与深度是结构错误，便宜且确定；子节点数是局部资源；并发是全局资源；预算需要聚合消息用量，最贵，放最后。

如果先查预算再查环，一次本该被结构规则立刻拒绝的派生，要先做一遍全树 Token 汇总，既慢又可能因为用量数据缺失而误判。把便宜且确定的判断前置，是准入函数最基本的效率纪律。

## 拒绝为什么必须是 422

超限不是服务器错误，也不是资源不存在，而是「请求本身合法，但当前状态不允许」。所以统一返回 422，并带原因码：

- `BRANCH_CYCLE`：祖先链成环。
- `BRANCH_DEPTH_EXCEEDED`：超过最大深度。
- `BRANCH_CHILDREN_EXCEEDED`：父会话分支数已满。
- `BRANCH_CONCURRENCY_EXCEEDED`：并发分支数已满。
- `BRANCH_BUDGET_EXCEEDED`：会话树预算用尽。

原因码的价值在于界面能给出对应文案。用户看到「父会话分支数已达上限」，知道该归档旧分支；看到「预算已用尽」，知道该调高上限或换棵会话树。如果只返回一句「操作失败」，用户只会反复点击。

## 四个上限各自防什么

并发统计的是 running 加 waiting，不只是 running。waiting 也占名额，否则等待中的分支可以无限堆积，一旦外部条件满足就同时恢复，瞬间打满。

子节点只数未归档分支。归档释放名额，这正是「归档优先于删除」的产品理由：用户想腾位置，不必毁掉历史。

深度以根为 1，默认上限 2。它意味着父会话可以派生子会话，子会话再派生会被拒绝。深度两层足够覆盖「主任务拆子任务」，再深就会让上下文层层转述，结论也越来越不可信。

Token 上限是整棵树，不是单条会话。父会话继续聊天也在这棵树里消耗，所有已完成子会话的消息也仍然在树里。按会话算预算，等于给每条分支单独发一张不限额度的卡。

## 预算怎么聚合

三个数决定一次准入：

```text
used     = 根会话消息用量 + 全部分支子会话消息用量
reserved = 所有未结分支的预留之和
limit    = 设置里的会话树上限
```

已用包含父会话，因为父会话与子会话共享同一棵树；也包含已经结束的子会话，因为它们的消息还在，成本已经发生。

预留只属于运行中的分支。它不代表真实消耗，代表「这笔钱已经承诺出去，别再用它做下一次准入」。

判断式很简单：`used + reserved >= limit` 就拒绝。不是 `>`，因为恰好等于上限时再派生必然超支。

## 先预留，再运行

只在启动前检查一次是不够的。假设上限还剩 3000 Token，三个分支几乎同时启动，每个都通过检查，然后各自消耗几千——检查通过，预算照样被击穿。

所以启动时要先写预留：按固定预估取一个值，再与剩余预算取较小者；剩余为零就返回零，准入直接拒绝。预留写入成功后状态才改成 running，运行结束按终态把预留归零。

这条顺序带来一个可验证的性质：任何时刻，`used + reserved` 都不会超过上限。它不是精确计费，而是把「并发启动」这个竞态条件收敛成一个先写后跑的串行承诺。

已用用量来自消息表汇总，不另存一份计数器。这样即使用户手工删除消息、恢复备份、切换会话，预算视图仍然跟真实数据一致，不会出现「计数器说用了十万、消息里只有一万」。

## 为什么上限要写成纯函数

准入与预留都被写成了纯函数：输入一份快照，输出通过或原因码；不读数据库、不写数据库、不取当前时间。

三个直接好处：

- 五类拒绝的顺序可以逐条断言，不用构造五套数据库状态。
- 边界值可以精确测试：子节点数恰好等于上限、已用加预留恰好等于上限、剩余预算恰好为零。
- 服务层只负责取快照和落库，判断逻辑没有副作用，出错时容易定位是数据问题还是规则问题。

反面写法是把判断散在服务里：每个拒绝分支都要先造父会话、造子会话、造消息、造设置，测试写得很长，覆盖仍然会漏。纯函数把「规则」和「取数」拆开，是这一版最划算的重构。

## 设置项也要有单一读取口

四项上限存在设置里，缺省回默认值。读取口做了一件容易被忽略的事：任何一个值非法，整体回落到默认，而不是只回落坏的那一项。

原因是「半套上限」比「没有上限」更难解释。如果并发读了 5、深度回落 2、子节点读了 10，用户以为自己在用一套自定义规则，实际是三套规则拼接。整体回落至少保证行为一致。

设置范围也写死：并发 1 到 10，深度 1 到 4，每父 1 到 20，树预算 1 万到 100 万。上限调整只影响下一次准入，不追溯已经在跑的分支。

## 一个具体的账

父会话已用 120000 Token，两条运行中的分支各预留 1000，上限 200000。此时第三次派生：已用加预留是 122000，低于上限，通过；启动再预留 1000。

如果父会话继续聊天，把已用推到 199000，下一次派生会在预算这一道被拒绝，原因码明确。已经在跑的分支不受影响，会继续跑到终态——上限拦的是新承诺，不是中途撕毁旧承诺。

## 数字

core 包 1475 个单测里，准入纯函数的 4 个用例覆盖默认通过、五类拒绝顺序与预留边界；API 集成 11/11 覆盖 422 与原因码；Web e2e 141/141 覆盖超限拒绝的主路径。
