# 从派生到终态：分支运行时的三条边界

一个分支从创建到结束，只有四个动作：派生、启动、取消、收敛。真正难的不是让它们成功，而是每个动作失败时留下什么。

留下脏数据，用户会看到永远 running 的幽灵；留下半条消息，父会话的转录会被污染；留下未释放的预留，整棵树的预算会慢慢漏光。运行时的设计，本质上是给这四种失败各准备一个出口。

## 派生是一个事务

派生做四件事：校验父会话存在、向上回溯根与深度、跑准入、创建子会话与分支关联。

前两步只读：从父会话沿分支关联一路向上，得到根 id、祖先链和当前深度。这里有一道上限为十的循环护栏，防止历史数据异常时无限回溯。

准入通过后才进入写操作。写操作必须在一个事务里：创建子会话、写入分支关联。两者要么都成功，要么都不落库。

为什么强调事务？因为「有分支行但没有子会话」会让列表指向一个不存在的会话；「有子会话但没有分支行」会让一个会话凭空出现、没有来源、也不计入预算。「半条记录」比彻底失败更难修。

子会话的标题默认取目标首行。它继承父会话的助手与角色设定，但不复制父会话的消息历史。派生不是克隆，子会话从目标开始独立生长。

## autoStart 的两种语义

服务层创建时，`autoStart` 缺省为 false：分支停在 `queued`，等显式启动。

界面上的创建对话框默认勾选自动开始，所以用户感受到的是「点一下就开跑」。如果用户想先把三个分支都准备好再统一启动，取消勾选即可。

这个分层不是多此一举。创建是数据操作，失败时只需要回滚事务；启动是资源操作，涉及预留、控制器和模型调用，失败后的清理完全不同。把两者分开，数据层可以保持纯净，启动路径也能被单独测试。

启动只接受 `queued` 与 `failed`。对 `running` 或 `waiting` 重复启动是幂等的，直接返回当前状态，不会开出第二条运行。终态里的成功、取消、中断、预算触顶都不允许直接启动。

## runner 只做一件事：把事件流收敛成三种终态

聊天编排器吐出的事件很多，分支运行器只关心三类：

- 增量文本：累加进正文。
- 完成事件：用最终正文覆盖累加值，并记录用量。
- 错误事件：记录错误码与错误消息。

循环结束后按固定优先级判定：

1. 信号已中止，返回取消。
2. 有错误消息，返回失败。
3. 否则返回成功。

取消优先于失败，是因为两者可能同时发生：用户点取消的同时上游报错。此时用户意图更可信，把结果记成取消，而不是失败，可以避免一条「用户主动放弃」的分支被误标为系统故障。

用量的处理也一样克制：完成事件可能不带用量，那就记为空，而不是编一个零。空表示「不知道」，零表示「确实没消耗」，两者在预算复盘时含义完全不同。

## 取消是协作式的

取消走 `AbortController`：信号传进运行器，事件流看到信号后自行结束，运行器再把结果收敛成取消。

本地应用里直接杀进程看起来更快，代价是留下半写消息、未落库状态和孤儿预留。协作式中止把「停止」变成一次正常的终态收敛：写完状态、写完原因、释放预留、补一条事件。

对还没启动的分支，取消不需要控制器，直接写取消终态即可。对运行中的分支，先中止再等落库。删除运行中的分支也走同一条路径：先中止，再删关联。

## 失败隔离：一条边失败，不是整棵树失败

一个分支失败时，只改自己的状态、原因与证据。

父会话不插入任何消息，转录保持原样。其他分支各自的控制器与 promise 不受影响，继续跑到自己的终态。子会话仍然可以打开，失败前写入的消息都在，用户可以看清它做到哪一步，再决定是否重试。

这条边界的价值在真实使用中才显现：同时派生三条调研分支，其中一条供应商超时。用户看到的是「一条失败、两条成功」，而不是「整次并行任务失败，三条结果都不敢用」。

失败隔离也让重试变简单。重试只针对当前分支，不需要重建整棵树，不需要重新派生兄弟分支。父会话仍然要先核对 evidence，再决定汇总哪些结论。

## 预算触顶：拒绝在启动之前

启动路径会先聚合会话树用量，再计算预留。预留为零时直接拒绝，状态不会被改成 running。

这条顺序保证不会出现「幽灵运行」：不会先宣布开跑，再发现没有预算；不会留下一个 running 状态却没有控制器；也不会让用户看到一个正在转圈、实际什么都没做的分支。

需要区分两种「预算触顶」：准入时拒绝新派生，启动时拒绝新运行。已经在跑的分支不会因为预算变化被中途掐断。上限约束的是新承诺，不是撕毁旧承诺。

状态枚举里保留了预算触顶这个终态语义，但当前实现主要通过「拒绝启动」表达。这是有意的简化：与其让运行到一半再终止、留下半截结果，不如在开始前就说清楚。

## 重启之后不能留下幽灵

进程退出时，内存里的控制器和 promise 一起消失，数据库里的 running 状态却还在。

启动收敛做一件很窄的事：把所有 running 与 waiting 改写成中断，预留归零，补一条状态事件。它不尝试恢复运行，也不猜测之前做到哪一步。

恢复备份走同一套语义：先恢复全部会话，再恢复分支；运行中的分支改写成中断，预留归零，证据保留。这样任何时刻打开面板，状态都能解释：要么在跑，要么已经结束，要么明确中断。

## 事件是旁路，不是事实源

分支创建、启动、状态变化、回传，都会写一条会话事件，作用域标为分支，作用域 id 是分支 id。

事件写入是尽力而为：写失败只告警，不阻断派生、运行或取消。状态的事实源始终是数据库里的分支行；事件只服务于图投影与复盘。

父图只收集直接分支的事件，嵌套分支出现在它自己的父图里。否则一条孙分支的状态会串到祖父图，读者无法判断它属于哪一层。

实时帧没有接入分支，面板五秒轮询、图十秒快照。这是明确的取舍：分支状态变化频率低于聊天流，为它单独开一条实时通道，收益不如把轮询做稳。
