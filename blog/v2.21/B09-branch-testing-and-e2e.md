# 怎么证明两个分支真的同时在跑：可控运行器与四条回归线

并行功能的测试最容易写成「睡两秒，断言两条都处于运行中」。这种测试证明不了并行：串行实现只要第一条跑得够慢，第二条也可能恰好在这个窗口里被创建并进入运行中。它唯一稳定证明的是「测试会偶发失败」。

这一版要回答的是一组更硬的问题：两个分支能不能同时越过准入、同时停在运行中？一个失败，另一个会不会被连带？预算被占满时，启动会不会被拒绝？重启与恢复之后，状态还会不会说谎？

答案不靠等待，靠一个可以手动放行的运行器。

## 可控运行器：把「跑多久」变成测试的开关

分支服务接受一个可注入的 runner。生产环境注入聊天编排器的流式方法，测试注入一个 async generator：每次被调用就登记一个 gate，然后停在 await 上，直到测试主动放行或注入失败。

```ts
const runner: BranchChatRunner = async function* (input) {
  const gate = registerGate();   // 每次调用产生一个开关
  await gate.wait;              // 不放行就永远停在这里
  yield { event: 'done', data: { content: `完成：${input.content}`, usage } };
};
```

测试先派生两条带自动启动的分支，然后立刻断言：两条都是 `running`，会话树预留是 2000。

这一步是整个测试的核心。如果实现是串行等待第一条结束再启动第二条，第二次派生根本不会进入运行中，断言会在任何时间点都失败；而只要两条都在运行中，就说明两个运行任务确实同时存在，不依赖调度速度。

接着放行第一条：它变成成功，evidence 摘要包含「完成：分支 A」，预留归零，第二条仍在运行。再让第二条失败：它变成失败，原因保留为「上游超时」，预留同样归零。

最后检查两件容易被忽略的事：父会话的消息数是 0，父会话标题没变。这说明回传没有偷偷写进主线，分支也没有改动父会话的内容。

## 失败隔离不是一句口号

上面的用例同时验证了失败隔离的三个面：

- 第一条成功时，第二条的状态没有被带着改；
- 第二条失败时，第一条已经是成功终态，没有被回滚；
- 两条分支的子会话都还在，父会话一条消息都没多。

失败隔离最容易被实现成「一个分支失败，整棵树标记失败」。那种做法在 UI 上看起来整齐，实际把独立任务又绑回了串行语义。断言「另一个仍在运行」比断言「失败分支是失败」更有价值，因为它证明的是边界，不是结果。

## 预算触顶：人工占满，不烧真实 Token

预算测试不该依赖真实模型消耗。做法是把会话树上限调到 10000，派生两条自动启动的分支（各预留 1000），再派生第三条但不启动。

然后直接改库，把第三条的预留写成上限值。叠加前两条分支各 1000 的预留后，总量已经超过上限，启动第三条会被准入拒绝，报「会话树 Token 预算已用尽」。

这个用例证明了两件事：启动路径会重新检查预算，而不是只在派生时检查一次；拒绝发生在预留之前，不会先写运行状态再失败。第三条分支是排队进来的，可能等了很久，期间预算被其他分支吃掉——所以启动时必须再算一遍。

它也暴露了一个设计取舍：预留是固定值，不是精确预估。1000 只能保证「有名额」，不能保证「跑得完」。真正的预算保护分两层：准入时拒绝超额派生，运行中按实际用量结算。两层都不完美，但都能解释。

## 备份 roundtrip：三种归档，三条断言

备份测试先造一个父会话和两个子会话，再写两条分支：一条成功并带 evidence，一条运行中、带预留、同时已归档。导出会话轨后，清单里的分支计数应为 2。

恢复到新库后断言：导入 2 条、跳过 0 条；成功分支的状态与摘要原样保留；运行中的分支变成中断，预留归零，原因写「恢复时运行中断」，归档时间还在。

第二条断言是关键。它同时覆盖了三件事：状态改写、预留释放、归档与状态正交。任何一处顺序错了，都会在这里露馅。

另外两条测试各管一个边界：旧归档没有分支文件时，导入 0、跳过 0，不报错；父会话或子会话缺失的孤儿分支，导入 0、跳过 1。前者验证兼容，后者验证跳过计数。它们不与 roundtrip 合并，因为失败时的定位成本完全不同。

## 端到端：让分支停在排队，避开真实模型

端到端用例不依赖模型供应商。它通过接口建一个父会话，再建一条 `autoStart=false` 的分支，让分支永远停在排队；后续所有断言都只碰 UI 与投影，不触发上游请求。

主路径是一条链：接口确认分支为排队 → 打开会话页 → 顶栏打开面板 → 卡片显示标题与「排队」→ 预算条显示上限 200000 → 图接口按分支范围能查到分支节点 → 归档后卡片收起、折叠区出现 → 恢复后卡片回来 → 删除并确认，关联消失，子会话仍能单独打开。

这条链的价值在于「接线」：它证明入口、面板、预算、图、归档、删除真的连在一起，而不是各自单测通过、组装起来缺一根线。真实模型的流式并行不放进这道门禁，因为本机没有稳定可用的供应商密钥；并行语义由可控运行器覆盖。

## 每一层只证明它能证明的事

测试不是越多越好，而是每一层只做它独有的事：

| 层 | 证明什么 | 不重复什么 |
|---|---|---|
| 纯函数 | 准入顺序、环检测、预留上限 | 不碰数据库 |
| 仓储与迁移 | 约束、唯一索引、级联、旧库升级 | 不测业务编排 |
| 服务 | 派生事务、并行、失败隔离、结算、收敛 | 不测 HTTP 信封 |
| 接口 | 状态码、原因码、子会话保留 | 不重复服务逻辑 |
| 端到端 | 入口到面板再到图的接线 | 不依赖真实模型 |

按这个分工，服务测试用注入 runner 证明并行与隔离；接口测试只断言创建返回 201、非法目标返回 422；端到端让分支停在排队，避开上游。每层都不去抢别层的活，失败时才能一眼判断问题在哪一层。

## 回归坑一：审计用例里的结构版本

新增迁移之后，一条历史审计用例失败。它断言归档里的结构版本常量是 44，而新迁移把常量改成了 45。

处理方式是把断言从 44 改成 45，而不是放宽成「任意数字」。这个断言是故意设置的绊线：每次结构变化都必须有人确认，并同步更新。放宽它，等于把「结构变了但没人知道」变成默认状态。

迁移是纯加法的，只新增一张表，不改旧表、不重建、不补数据，所以其他数据断言不受影响。失败的只有这一个版本锚点，也正好说明锚点在正常工作。

## 回归坑二：全量并发测试的资源竞争

全量单测按包并发跑时，出现过两次失败：一次是配置包扫描到 core 包正在写的覆盖率文件，读到半截内容；一次是 Web 包的 worker 报通道关闭与堆内存不足。

这两次都不是产品缺陷。逐包串行复跑全部通过；Web 包把并发降到 2 之后 724 例全绿。处理方式是不改产品代码，记录环境限制，改用受控并发复跑。

这里有一条需要写进流程的判断：**先区分「断言失败」与「资源竞争失败」。** 前者的证据是同一个用例稳定失败、错误指向业务逻辑；后者的证据是失败位置随机、单独复跑通过、并发降低后消失。把后者当产品 bug 修，会引入没有必要的「修复」；把前者当环境抖动忽略，会放过真问题。
