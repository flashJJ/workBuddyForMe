# 一张表撑起父子会话：分支数据模型与八态状态机

给会话加分支，第一反应通常是往会话表里加一个父会话字段。我们最后没有那么做。

不是因为它技术上做不到，而是因为一旦那么做，每条读取会话的路径都要开始分叉：这是普通会话还是分支会话？父会话被删了怎么办？分支关系归档了，会话本身还是不是活跃？这些问题会从一张表扩散到消息、检索、导出、备份、图投影。

最后的选择是：核心会话表一行不改，新增一张只描述「关系」的表。

## 为什么不改核心会话表

会话表承担的是内容生命周期：标题、助手、消息、归档。分支关系承担的是另一套生命周期：谁派生、跑到哪一步、花了多少 Token、回传了什么。

两者最关键的差异在删除语义上。删除一条分支时，子会话必须保留为普通会话，消息一条不能少；如果关系字段长在会话表上，删除关系就等于修改会话本身，语义立刻纠缠。

备份与恢复也会变复杂：会话表是恢复的第一轨，分支关系是第二轨。分开存，恢复顺序清晰；混在一起，任何一条坏行都可能阻断整个会话恢复。

所以数据模型的第一条原则是：关系归关系表，内容归内容表。

## 单表里放了什么

新表只做一件事：记录一条分支关联及其运行状态。

| 列 | 作用 | 为什么必须有 |
|---|---|---|
| 父会话 id | 派生来源 | 列表按父查询、图车道按父挂载 |
| 子会话 id | 实际执行的会话 | 打开、运行、删除都要落到它 |
| 根会话 id | 所属会话树 | 预算按树聚合，避免递归找根 |
| title / goal | 展示与启动输入 | 标题可改，目标不可变 |
| depth | 层级 | 根为 1，准入据此判断深度 |
| status / status_reason | 八态与原因 | 失败、取消、触顶都要能解释 |
| reserved_tokens | 准入预留 | 先预留再运行，终态归零 |
| return_evidence_json | 回传证据 | 只在终态写入 |
| archived_at | 归档 | 与状态正交 |
| ended_at | 终态时间 | 区分「多久没动」与「已经结束」 |

根 id 与 depth 都是冗余字段。它们本可以沿父链递归推出来，但读多写少：创建时算一次，之后永远不变，换来的是列表与预算查询不用递归。深度上限只有两层，为这点递归建闭包表是过度设计。

## 八种状态

状态只表达分支自己的生命周期，不表达归档、不表达父会话。

- `queued`：已创建，尚未启动。
- `running`：正在执行。
- `waiting`：等待子分支、审批或外部依赖。
- `succeeded`：正常结束。
- `failed`：执行出错。
- `cancelled`：用户取消。
- `interrupted`：宿主退出或恢复备份时中断。
- `budget_exceeded`：预算或上限触顶，不再继续调用模型。

后五种是终态。终态的共性是：不再消耗模型调用，必须写 `ended_at`，预留归零。

## 哪些迁移合法

```text
queued  -> running -> waiting -> running
queued | running | waiting -> succeeded | failed | cancelled | interrupted | budget_exceeded
```

- `waiting` 只由运行器写入：它代表「正在等外部条件」，不是用户手动设置的状态。
- 终态不可自动回到 `running`。这条规则约束的是自动流转与父会话，不约束用户显式重试；重试只针对当前分支，且必须由用户触发。
- 归档与状态正交：`archived_at` 非空不改变 `status`。归档一个成功的分支，它仍然是成功，只是默认列表不再显示。
- 恢复归档只把 `archived_at` 置空，不触碰状态与 evidence。

状态写进数据库时还有一层 `CHECK` 约束，枚举之外的字符串直接写不进去。应用层校验负责给用户可读原因，数据库约束负责最后一道防线。

## 一个子会话只能属于一条分支

子会话 id 上有唯一索引。含义很直接：一个会话最多被挂到一条分支关系上。

如果没有这个约束，同一个子会话可以被两个父会话派生，根 id、depth、预算归属立刻出现二义：它到底算哪棵树？哪条分支失败该改它的状态？唯一约束把这个歧义从运行时消灭掉。

代价是不能「复用」子会话再挂一次。这正是想要的：要复用结果，应该回传 evidence，而不是把会话重新挂到另一棵树上。

## 删除与归档不是一回事

归档是「先收起来」：保留关联、保留 evidence、保留子会话和消息，只是默认列表过滤。需要时恢复，一切原样。

删除是「断开关系」：只删这张表里的关联行，子会话降级为普通会话，消息不级联删除。图车道不再显示这条分支，但用户仍然可以单独打开子会话继续聊。

运行中的分支不允许直接删除。实现里的顺序是先中止运行，再删关联。这样不会出现「关联没了、运行还在写消息」的悬空状态。

## evidence 坏了也不能拖垮列表

回传证据以 JSON 文本存放。读取时先解析、再用 Schema 校验；任何一步失败都返回空，而不是抛错。

原因很实际：一条分支的证据字段可能因为旧数据、手工修改或写入中断而损坏。如果读取时抛错，整个分支面板都打不开，用户会以为所有分支都没了。回落空值的代价只是这一条不显示回传卡片，列表、状态、子会话入口都还在。

## 数字

数据库层 260 个单测覆盖建表迁移、CRUD、归档过滤、唯一约束、级联与证据损坏；共享层 349 个单测里有 4 个专门校验分支 Schema 的边界与八态；core 层 1475 个单测里靠服务测试验证状态流转。迁移是纯加法，旧库升级不重建表、不给旧行补数据。
