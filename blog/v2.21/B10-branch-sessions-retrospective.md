# 什么算真正并行：自由分支会话的七条方法论

我们的桌面 AI 应用是本地优先、单人开发的助手。这一版加了自由分支会话：从一个父会话派生多条子会话，让它们各自运行，再把结果结构化地汇回来。

功能清单看起来不长，但「并行」这个词很容易骗人。两个状态同时写着运行中，不等于两条任务真的独立；子会话能开，不等于失败不会串扰；界面上能看到分支，不等于重启后状态还诚实。这篇不复述功能，只做三件事：先对账交付，再从七个真实场景里提炼方法论，最后交代哪些事刻意没做，以及这些克制换来了什么。

## 交付对账

| 方向 | 交付 | 验收方式 |
|---|---|---|
| 数据 | 一张只描述关系的分支表，纯加法迁移 | 旧库升级不重建，唯一约束与级联生效 |
| 准入 | 环、深度、子节点、并发、预算五道检查 | 纯函数单测，拒绝返回明确原因 |
| 运行时 | 派生、启动、取消、失败隔离、终态结算 | 可控运行器证明两条同时运行 |
| 回传 | 终态生成 evidence，固定标注需核对 | 摘要、用量、状态原因可读 |
| 图 | 分支车道、分支节点、子会话占位、回传节点 | 三类节点三条边，嵌套不串味 |
| 管理 | 档案、恢复、取消、删除 | 删除保留子会话，运行中先停 |
| 预算 | 会话树已用、预留、上限与活跃数 | 先预留再运行，终态归零 |
| 恢复 | 备份带分支文件，重启收敛残留状态 | roundtrip、旧档兼容、幽灵运行清零 |

数字：单测 3153 例，API 集成 11/11，Web 端到端 141/141，桌面冒烟 10/11（缺项与历史基线一致），安装包约 202 MB。这些数字的作用不是发布报告，而是回答一个问题：新增并行能力，有没有把原来能用的东西弄坏。

## 方法论一：独立上下文要在一次事务里成立

分支最容易做成「复制一份会话」。复制看起来快，实际留下两份会漂移的历史：父会话改了标题，子会话还是旧的；子会话继续聊，父会话完全不知道。

这一版在派生时做的是另一件事：在同一个事务里创建子会话与分支关联。两者要么都成功，要么都不落库。子会话从目标开始生长，不复制父会话的消息；父会话也不插入任何「已派生」的提示。

测试断言很直接：父会话消息数为零，父会话标题不变，子会话能独立打开。**独立不是把数据分开放，而是两边的写入路径从一开始就不交叉。**

## 方法论二：准入必须先于创建

最省事的实现是「先建子会话，再看超没超限，超了就删」。它在正常路径上没问题，失败时会留下一个没有分支关系的空会话，用户会在会话列表里看到一条无来源的记录。

这一版把准入抽成纯函数，顺序固定：环检测、深度、子节点数、并发、会话树预算。任何一项不通过，直接拒绝，不产生任何行。拒绝原因映射成可读文案，接口返回 422 与原因码，界面在表单里显示。

顺序也不是随便排的。环检测必须在最前面：一旦祖先链成环，后面所有计数都可能被错误数据带偏。预算放最后，因为它是最容易被其他条件短路的一项，先算它等于浪费。

## 方法论三：预算要预留，不能等结算

如果只在终态扣预算，两条排队的分支可以同时通过准入，然后一起把树烧穿。这一版在启动时先预留：取剩余预算与固定预估值中的较小者，写进 `reserved_tokens`，终态按实际用量结算并归零。

固定预估是 1000，不精确，但它解决的是「名额」而不是「预测」。真正让预算可解释的是两层的组合：准入拒绝超额，启动再检查一次，运行结束结算。测试里人工把预留占满，再启动排队分支，必须被拒。

**先预留再 await，是并行系统里最便宜的一道保险。** 它把「未来可能花的钱」提前记在账上，避免多个任务在同一时刻都以为自己还有余量。

## 方法论四：回传必须是证据，不是消息

自动往父会话写一条「分支完成」看起来体验很好，实际是在替用户做判断。分支可能失败、可能只完成一半、可能给出错误结论；一条格式漂亮的消息会让它看起来像主线的一部分。

这一版的回传是一份 evidence：分支 id、父子会话 id、状态、摘要、产物引用、用量、固定的 `needsReview`。只在终态生成，只在分支卡片与图节点展示，父会话转录一条不加。

证据也有边界：摘要截到 4000 字，产物列表目前还没有从消息里提取，通常是空的；证据 JSON 损坏时回落为空，不阻断列表。**宁可承认证据不完整，也不把不完整的东西包装成结论。**

## 方法论五：事件只投影，不改写业务

分支的创建、启动、状态、回传都写进事件表，图再从事件投影。这条链有一个硬边界：投影永远只读。

事件写入本身是 best-effort 的，失败只打警告。因为业务状态在分支表里，事件只影响图好不好看。如果为了图完整而把事件写入和业务写入绑进同一事务，一次磁盘故障就可能回滚一条已经成功派生的分支——代价方向错了。

同理，父图的投影不重放子会话的聊天事件，只用占位节点表达。事件多的时候还有容量上限：最多 50 条直属分支，每条最多 200 个事件。图是导航，不是审计流水。

**事实源只能有一个。** 分支表是事实，事件是事实的影子；影子可以缺，事实不能错。

## 方法论六：恢复与收敛要分开，且都不留幽灵

备份恢复与启动收敛都会把「声称在运行」改成「已中断」，但它们不是同一件事。

恢复的输入是归档：先恢复全部会话，再恢复分支；父或子会话缺失就跳过并计数；`running` 与 `waiting` 改成 `interrupted`，预留归零，归档与终态保留，合法 evidence 原样留下。收敛的输入是本地库：只查运行中与等待中，逐条改写并补一条状态事件，返回收敛条数。

分开的原因是责任不同：恢复要面对别的机器、别的时间点，还要处理缺失与坏行；收敛只面对这次进程留下的残局。合并之后，测试构造服务就会误伤夹具，真实启动时也可能把正在导入的数据当成残留。

两者共同的底线是：**重启之后，系统不能声称自己还在跑一个不存在的进程。** 中断是终态，不自动续跑，也不偷偷重试。

## 方法论七：并行测试要可控，不靠等待

并行测试如果没有开关，只能靠 sleep 和概率。这一版注入了一个可手动放行的运行器：每次调用登记一个 gate，测试先让两条分支都停在运行中，再逐条放行或注入失败。

这组测试同时证明了三件事：两条分支真的同时越过准入；一条成功不影响另一条运行；一条失败不影响另一条的状态，也不污染父会话。预算触顶则用人工占满预留来验证，不烧真实 Token。

端到端让分支停在排队，避开模型供应商；备份 roundtrip 用真实归档文件，覆盖状态改写与旧档兼容。每层只证明它能证明的事，失败时才能一眼定位。

## 纪律：明确不做什么

- 不做 Git worktree、checkpoint、代码评审。分支会话是对话层的并行，不是仓库层的并行；
- 不做自动无限递归派生。派生必须由用户发起，否则预算与图都会失去可解释性；
- 不做团队共享、云同步、远程分支。本地优先是前提，不是待补的功能；
- 不接分支实时帧。面板 5 秒轮询、图 10 秒快照，先用可预期的延迟换稳定；
- 不做逐项产物节点。产物列表目前为空，回传节点只按数量展示，提取留待下一轮；
- 不做运行中删除的异步等待。当前是同步中止后删关联，风险已知且接受；
- 不自动续跑中断分支。重启后由用户决定继续、重派或放弃。

每条 Non-Goal 都对应一个诱惑：「既然有分支了，顺手做个 worktree 吧」「既然有事件了，顺手接个实时推送吧」。这些「顺手」单个都合理，加在一起就会把一个功能版本拖成半年工程。范围纪律不是不做，而是知道这一版不做。

## 什么算真正并行

回到标题。两个分支的状态同时是 `running`，只能证明进程并发；它证明不了这是一套可用的并行工作方式。

对我们来说，真正并行要同时满足四个条件：

- 每条分支有独立上下文，父会话不被复制也不被污染；
- 多条分支共享一套可解释的预算，先预留、后结算；
- 一条失败只影响自己，其他分支继续跑；
- 崩溃或恢复之后，状态不撒谎，已有结果能回看，下一步由用户决定。

少一条，用户就会退回到手工搬运：开几个窗口、复制结论、自己记住谁跑到哪。那种「并行」只是把复杂性转移给了人。

这一版把这四条做成了结构：关系表、准入、预留、证据、投影、恢复、可控测试。七条方法论说的其实是同一件事——**让多个任务同时存在时，系统仍然能解释每个任务发生了什么。**
