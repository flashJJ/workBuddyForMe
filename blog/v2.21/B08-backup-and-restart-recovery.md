# 崩溃之后分支还在「运行中」：备份与启动收敛的三道防线

本地优先应用最尴尬的故障不是崩溃本身，而是崩溃之后系统说一切正常。

分支会话把这种尴尬放大了。进程被强制结束、机器断电、用户直接关窗口，内存里的运行控制器随之消失，但数据库里的分支行还写着 `running`，预留的 Token 也没有释放。下次启动，这条分支看起来永远在跑：它占着并发名额，占着会话树预算，新分支一律被拒。用户找不到任何正在执行的进程，也没法把它改成别的状态。

另一条路径是换机器：备份恢复到新环境，父会话和子会话都在，分支关系没跟过来，子会话变成了没有来源的普通会话。

这一版用三道防线处理这两件事：备份带上关系、恢复按顺序、启动先收敛。

## 第一道：分支关系跟着会话轨走

备份的会话轨里新增一个可选文件 `branches.json`，内容是全量分支关联；清单里再记一个可选的 `branchCount`，方便恢复前核对数量。

为什么不给分支单独开一条轨？因为一条分支的三个关键外键——父会话、子会话、根会话——全部指向会话表。单独成轨就要处理跨轨顺序、跨轨部分恢复、只选分支不选会话时怎么办，复杂度立刻上升。放进会话轨，语义最简单：**恢复会话，就恢复附着在会话上的关系。**

备份格式的版本号没有动。新增文件与新增清单字段都是可选的加法，旧版本读新档时忽略它们，新版本读旧档时缺文件按空数组。这样升级和回退都不需要格式迁移。

恢复端也不假设文件一定存在。读取时先看归档里有没有 `branches.json`，没有就当零条，不报错、不中断会话恢复。

## 第二道：先父子会话，再分支

恢复顺序是硬约束：先把 `conversations.json` 里的全部会话写进去，再处理分支。

原因很直白：分支插入时数据库有外键约束，父会话或子会话任意一个不存在，插入就会失败。如果先恢复分支，正常归档也会因为「会话还没到位」而丢关系。

具体做法是先恢复会话，再逐条读分支。每条分支写入前检查父会话与子会话是否存在；任一缺失就跳过，并计入 `skipped`。根会话 id 只作为数据使用，不参与存在性检查——深度为 1 时它就是父会话，查它等于重复检查。

写入用 `INSERT OR IGNORE`。重复 id 不会覆盖已有关系，而是按跳过计数。这样同一份归档恢复两次不会产生重复分支，也不会悄悄改掉现网数据。

计数会返回给上层：导入了多少、跳过了多少。跳过不是致命错误，一条坏行不该让整份归档打不开；但用户需要知道「有东西没恢复」，所以计数必须可见。

## 第三道：把运行改成中断，不要伪造完成

恢复分支时，状态不能原样照搬。

`running` 与 `waiting` 代表「有一个进程正在推进它」。恢复环境里没有那个进程，照搬就是幽灵运行。做法是统一改写为 `interrupted`，原因写「恢复时运行中断」，结束时间设为当前，`reserved_tokens` 归零。

终态保持原值：成功还是成功，失败还是失败，取消还是取消，预算触顶还是触顶。归档时间也保留，即使这条分支同时被改写成中断——归档与状态正交，恢复不该顺手把归档取消。

evidence 重新过一次 Schema。合法就原样保留，摘要与用量都还在；非法就落成空，不让一条坏 JSON 阻断整条分支。非法条目（缺 id、缺标题、缺目标、深度小于 1）直接跳过；状态字符串不认识时按 `interrupted` 处理，而不是抛错。

这里有一个明确的底线：**不知道发生了什么，就说中断；不能因为「看起来像成功」就标成功。** 没有 evidence 的成功是假成功，比中断更危险。

## 一份归档恢复后的样子

| 归档中的状态 | 恢复后 | 预留 | 说明 |
|---|---|---|---|
| 成功 + evidence | 成功 | 0 | 摘要与用量原样保留 |
| 运行中 + 已预留 | 中断 | 0 | 原因写「恢复时运行中断」 |
| 运行中 + 已归档 | 中断且仍归档 | 0 | 归档与状态正交，不互相覆盖 |
| 等待中 | 中断 | 0 | 等待依赖的那个进程同样不存在 |
| 排队 | 排队 | 0 | 从未启动，恢复后仍可手动启动 |
| 父或子会话缺失 | 不导入 | — | 计入跳过，不阻断其他分支 |

排队状态特意不改成中断。它从未占用运行资源，恢复后仍然是一条合法可启动的分支；把排队也改成中断，会让用户失去「派生但还没跑」这个选项。

## 启动收敛：只碰运行中与等待中

备份恢复处理的是「导入的归档」，启动收敛处理的是「上次进程留下的现场」。两者改写的状态一样，入口不同。

仓储提供只查 `running` 与 `waiting` 的方法，启动时不全表扫描。逐条把状态改成 `interrupted`、预留归零、写结束时间，再补一条 `branch_status` 事件，最后返回收敛条数并打一行日志。

事件很重要：分支列表看到的是状态，图看到的是事件。只改表不写事件，图里那条分支会停在上次的状态，看起来像没收敛。

收敛入口单独抽出来，只在容器启动时调用。服务构造函数本身不收敛，否则测试里每建一个服务就会改动测试夹具，单测之间互相污染。这个边界看起来是洁癖，实际是测试可重复性的前提。

## 坑：事件写入是 best-effort，边界要写清楚

分支事件写入包在 try/catch 里，失败只打警告，不影响派生、启动、取消的结果。

这条规则容易被误解成「事件不重要」。准确的说法是：**业务状态是事实源，事件是派生视图的输入。**

分支表里的状态决定列表、预算、能不能再启动；事件只决定过程图长什么样。事件写失败时，分支仍然可用，只是图上缺一个节点。反过来，如果把两者放进同一个事务，磁盘写满或事件表约束失败会回滚一次成功的派生——为了让图好看而丢业务，代价更大。

所以边界是：业务写成功即成功，事件失败降级为「图不完整 + 一条警告」。恢复与收敛只读分支表，不依赖事件，因此事件缺失不会影响状态正确性。

同样的原则也适用于图投影：它只读事件，从不回写。投影出错最多图难看，不会改数据。

## 两条时间线，一个共同结论

备份恢复与启动收敛都做同一件事：把「声称在运行」改成「已中断」。但它们不能合并：

- 恢复的输入是归档，可能包含别的机器、别的时间点的状态；
- 收敛的输入是本地库，是这次进程真实留下的残局；
- 恢复要处理缺失的父子会话，收敛不需要；
- 恢复的错误要计数给用户看，收敛只需要日志与事件。

共同结论是：运行状态不能跨进程存活。中断是终态，系统不会在启动后偷偷重新调用模型。用户想继续，可以打开子会话看已有内容，或重新派生一条分支。代价是多一步手动操作，换来的是「重启不会产生意料之外的模型调用」。
