# 长任务只能串行：自由分支会话要解决的四个问题

我们的桌面 AI 应用是本地优先、单人开发的助手。用户很快会遇到同一类瓶颈：一个任务还没跑完，下一个任务已经在等。

无论是「先调研三家竞品，再各写一份摘要」，还是「把长文档拆成几个章节分别处理」，单条会话都只能排队。

排队本身不是错，错的是排队期间用户没有别的选择。想同时推进，只能开新的聊天窗口，然后手动把结论复制回来。

上下文断了，进度不可见，预算也没有统一口径。这一版要做的不是更快的模型，而是让一个助手把任务拆成多条真实会话并行推进，并把结果可靠地汇回父会话。

## 三种「看起来能并行」的旧办法

动手之前，先排除三种看似可用、实际不成立的替代品。

第一种是固定角色协作：规划者、执行者、审查者轮流发言。它解决的是「谁来检查」，不解决「谁来并行」。

角色是写死的，用户不能自由派生，也看不见多条独立任务之间的关系。

第二种是会话内的工作计划：把目标拆成待办，再逐条打勾。它解决的是「过程可见」，但所有步骤共享同一个上下文和同一条转录。

一步的输出会污染下一步的输入，失败也没有独立边界。

第三种是子代理运行：确实有独立的 run，也能并行，但 run 是一次性的。

它不能继续对话、不能被归档、结束后也不会留下可核对的回传证据。用户想追问一句，只能从头再来。

三者各有价值，但它们都不是可继续的会话。这一版补的正是这块空白。

## 并行不是多开几个聊天窗口

多开窗口看起来最省事，代价藏在后面。

每个窗口都有自己的上下文，父会话不知道子任务做到哪一步；结论靠人复制，复制错了没人发现。

Token 消耗分散在各处，没有会话树级别的预算；回看历史时，几个窗口的关系只能靠记忆。

所以真正的并行需要三项基础设施：独立的子会话、统一的准入与预算、结构化的回传。

缺一项，用户就会退回到手工搬运。

## 四个目标

### 父子会话

从当前会话或某条消息派生一个子会话。

子会话有自己的消息、模型、阶段计划与产物，父会话主线原样保留。

父子关系只是关系，不是复制——子会话不是父会话的快照，它从派生目标开始独立生长。

### 结构化回传

子会话进入终态时生成一份 evidence：谁派生、谁执行、结果状态、摘要、用量。

父会话拿到的是可核对的数据，而不是一段自动插入的聊天消息。

### 四项上限

并发、深度、每父分支数、会话树 Token。

四个维度分别防四种失控：同时跑太多、递归太深、一个父会话摊子太大、整棵树烧穿预算。

### 图车道

过程图里增加分支车道、分支节点与回传节点。

用户不必打开每个子会话，就能看到整棵树的形状与状态。

## 三条主线

第一条是独立上下文。派生事务里同时创建子会话与分支关联，两者要么都成功，要么都不落库。

子会话的消息写进自己的会话，不写父会话。

第二条是准入与预算。派生之前先算：会不会成环、深度够不够、父会话还有没有名额、树里还有没有并发额度、预算还剩多少。

任何一项不通过，返回明确原因，而不是先创建再失败。

第三条是回传可核对。evidence 只在终态生成，摘要与用量来自运行结果，产物先留结构。

父会话界面固定标注「需核对」，不自动重试、不自动派生。

## 四条上限的默认值

| 维度 | 默认 | 防的是什么 |
|---|---|---|
| 并发分支 | 3 | 同时运行的子会话过多，模型调用与磁盘写入互相拖慢 |
| 最大深度 | 2 | 分支再分支，图不可读、上下文层层转述 |
| 每父分支数 | 6 | 单个父会话的分支面板失控 |
| 会话树 Token | 200000 | 一次任务把整棵树的预算烧穿 |

四项都落在设置页，可调、可恢复默认。

上限不是产品限制，而是失败半径：它决定一次判断失误最多浪费多少资源。

## 刻意不做的三件事

- 不做 Git worktree。分支会话是对话层的并行，不是代码仓库的并行；把两者混在一起，会让「分支」同时背两种语义。
- 不搬外部工具的会话树宿主。那套做法把会话树当成插件容器，复杂度和单人维护不匹配。
- 不做自动无限递归派生。派生必须由用户发起；自动派生会让预算与图结构都失去可解释性。

范围纪律不是不做，而是知道这一版不做。每一条 Non-Goal 都对应一个诱惑，合在一起就会把功能版本拖成长期工程。

## 验收看失败路径

验收口径不看功能清单，看失败时会发生什么。

超限有原因、失败有隔离、取消有终态、重启不留下幽灵运行、删除不丢子会话——这五条都成立，功能才算落地。
