# 10 分钟短跑门禁：相对基线、硬件指纹与容差阈值

长跑能发现问题，但跑一次四小时，没法每次改代码都做。

短跑的目标不是“测出绝对性能”，而是“这次改动有没有让性能明显回退”。它只需要十分钟，适合在发版前或大改后跑一次。

难点在于阈值：同一份代码，在不同机器、不同渲染后端上的帧时间可以差一倍。设绝对帧率，门禁第二天就会失效。

我们把门禁做成相对基线比较。

## 一、基线是什么

基线是一份 JSON，记录：

- 版本与采集时间。
- 硬件指纹：CPU 型号、核心数、内存、平台、架构。
- 视口尺寸与模型 id。
- 四段场景的时间线。
- 汇总指标：p50、p95、长任务、堆峰值、资源峰值与末值、错误数。

基线不是“理想值”，而是“上一次确认可用的自己”。门禁只问：当前是否显著差于它。

## 二、场景时间线

十分钟被切成四段：

1. 待机 20%。
2. 主动播放 20%。
3. 模型热替换 30%。
4. 小剧场进出 30%。

每段都采样 p50/p95、长任务、堆与资源。热替换每 20 秒切一次模型；小剧场进出按阶段时长计算圈数，最多 10 次。

这样一次运行能覆盖持续渲染、动画播放、模型加载卸载与路由进出，比只开着桌宠更有代表性。

## 三、七项检查

门禁比较七项：

- p50 平均帧时间。
- p95 平均帧时间。
- 堆峰值。
- geometries 末值。
- textures 末值。
- programs 末值。
- 页面错误数。

前三项看性能，中间三项看回收，最后一项看稳定性。任何一项超阈值，退出码为 1。

## 四、阈值怎么定

阈值全部是相对值：

- p50 ≤ 基线 × 1.2 + 2ms。
- p95 ≤ 基线 × 1.25 + 3ms。
- 堆峰值 ≤ 基线 + 48MB。
- 每项资源末值 ≤ 基线峰值 + 4。
- 错误数必须是 0。

加常数项是为了照顾极小基线：基线 p95 只有 1.7ms 时，纯百分比会过于苛刻。加 2–3ms 给测量噪声留空间。

资源用“基线峰值 + 4”，而不是“基线末值 + 4”。峰值更能代表正常波动上限，避免一次 GC 或一次换模就误判。

## 五、3 分钟冒烟结果

先用 3 分钟生成基线：

- p95 1.757ms，堆峰值 227.9MB，资源峰值 24/56/6。

再复跑一次：

- p95 1.613ms，堆峰值 202.2MB，资源末值 20/48/5。
- 七项全部 PASS。

第二次数字更低，不代表代码变快，只代表运行波动。门禁只关心“没有超过上限”，不奖励“变得更快”。

## 六、硬件指纹不一致怎么办

基线在 A 机器上采集，换到 B 机器跑，绝对比较没有意义。

默认行为是警告并继续：打印基线 CPU 与当前 CPU，仍然输出七项检查结果，但退出码不因机器不同而失败。

需要严格比较时传 `--strict-machine`，机器不一致直接失败。这个开关留给固定机型或发布会话使用。

## 七、基线缺失怎么处理

如果基线文件不存在，门禁以退出码 2 结束，并提示先运行 `--write-baseline`。

它不会自动生成基线。自动生成会让“第一次运行”变成“既当运动员又当裁判”，门禁看起来通过，其实没有对照。

## 八、输出与归档

每次运行写一份 JSON，包含硬件、场景、指标、基线与逐项检查结果。控制台逐项打印：

```text
PASS p95: 当前 1.613 / 基线 1.757 / 阈值 5.196
```

失败时同样格式，只是前缀变成 FAIL。报告默认落临时目录，不提交；基线进版本目录，随版本归档。

## 九、边界

这是本地门禁，不接入 CI。当前构建环境没有稳定的 GPU 与固定机型，接进去只会制造偶发失败。

它也不检查内存泄漏的根因，只在资源未回收时失败。根因仍要靠长跑时间线与开发探针定位。
