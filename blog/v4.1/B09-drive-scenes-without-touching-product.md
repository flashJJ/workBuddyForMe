# 不侵入业务地驱动桌面场景：假桥、路由钩子与资源回收

性能脚本要测模型热替换，也要测小剧场进出。最直接的做法是给页面加一个测试 API，或者暴露一个“切换到下一个模型”的方法。

但测试钩子一旦进生产，就会变成永久维护面：要鉴权、要防误用、要写文档，还要担心被外部调用。

这一轮的约束是：不新增业务 API，不让测试钩子进生产，仍然能驱动真实交互链路。

## 一、页面本来就有入口

模型热替换不是测试专用能力。桌宠页面在运行时会监听一个桥回执：

```ts
bridge.onModelChange((next) => {
  setModelId(next);
  bridge.confirmModel(next);
});
```

主进程换模型时调用这个回调，页面重新加载 VRM，并回执确认。也就是说，页面已经有一条完整的“换模型”路径。

性能脚本不需要新入口，只需要在页面加载前提供一个桥，把回调接住。

## 二、假桥怎么做

脚本在页面初始化前注入一个最小的桥对象：

- 常用方法用空函数占位。
- `onModelChange` 把回调存进数组，并返回取消函数。
- `confirmModel` 是空函数。
- 额外暴露一个 `__perfSwapModel(id)`，遍历回调并触发。

页面启动时照常注册监听。脚本想换模型时，调用 `__perfSwapModel`，页面走的是与主进程完全相同的 `setModelId` 分支。

这样测到的不是“测试专用换模”，而是真实热替换。

## 三、为什么不会误导结果

关键在“同一条路径”。

如果测试直接改 React state，可能绕过模型加载、缓存清理与资源释放；通过回调触发，则必须经过页面原有的替换逻辑。

空实现的 `confirmModel` 也不会改变行为：它只是回执，不参与渲染。真实主进程收到回执后会做什么，与性能指标无关。

## 四、小剧场进出更难

模型热替换有现成回调，路由跳转没有。

小剧场是独立路由，进入与退出都要经过应用路由。脚本可以调用浏览器历史 API，但单页应用的路由不会因此重新渲染。

可以模拟点击，但选择器脆弱，界面一改脚本就断。也可以开新页面，但那会重置渲染进程，测不到资源回收。

最后选择加一个只在开发环境安装的组件。

## 五、dev-only 路由钩子

根布局挂一个不渲染内容的客户端组件：

```ts
useEffect(() => {
  if (process.env.NODE_ENV === 'production') return;
  window.__perfNav = { push: (href) => router.push(href) };
  return () => { delete window.__perfNav; };
}, [router]);
```

生产构建直接不安装，卸载时清理。它不接收用户输入，也不改变页面状态，只暴露应用自己的路由函数。

这样脚本可以在同一渲染进程内往返桌宠与小剧场，观察资源计数是否回到基线。

## 六、场景时间线

短跑按四段执行：

1. 待机：让桌宠持续渲染。
2. 主动播放：触发一场剧本，观察动画与道具。
3. 模型热替换：在两只内置模型之间来回切换。
4. 小剧场进出：进入舞台、停留、返回桌宠。

每段都采样。热替换与进出是“动作段”，待机与播放是“稳态段”，两类数据分开看。

## 七、10 次进出怎么排

十分钟里，最后 30% 是 3 分钟。如果固定每次 18 秒，刚好能跑 10 次；3 分钟冒烟只有 54 秒，只能跑 3 次。

脚本按阶段时长自适应：

```text
cycles = clamp(floor(stageMs / 18000), 1, 10)
```

这样冒烟不会因为“凑不够 10 次”而失败，正式门禁又能跑满 10 次。

每次进出后都读一次资源快照，最后比较末值与基线峰值。

## 八、失败时怎么表现

如果开发服务没有开启剧本引擎，主动播放阶段会跳过，并在日志里写明原因；其他阶段继续。

如果路由钩子不存在，小剧场阶段会失败，报告里会提示“需要开发环境”。这不是静默降级，因为资源回收是门禁的核心检查项之一。

页面错误与桥调用异常都会计入错误数，最终让门禁失败。

## 九、边界

这套驱动方式依赖开发服务器与应用内路由，不适用于打包后的静态页面。

假桥只覆盖性能脚本需要的方法，不是完整桥实现；如果页面新增启动依赖，脚本要同步补齐，否则会在初始化阶段报错。

这也是它的代价：无侵入不是零维护，而是把维护放在脚本侧，不放在产品侧。
