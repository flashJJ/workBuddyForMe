# 12 组固定上下文：把「调权重」变成可复现的排序实验

主动播放的打分器有几个可调权重。每次改完，最理性的验证方式是等真实场景发生，再看她选了什么。

问题是真实上下文不受控：今天忙碌、明天空闲，关系等级和心情也在变。等一周可能只覆盖两三种组合，还是没法判断变化来自权重还是来自样本。

这一轮加了一个固定场景矩阵：12 组上下文 × 一批候选，跑同一套打分器，输出排序。

## 一、矩阵解决什么

矩阵不追求“代表真实用户”，它追求“可复现”。

同一组上下文、同一批候选、同一套权重，连续跑两次必须得到完全一致的排序。只有先做到这一点，权重变化带来的差异才有解释力。

它也不能证明“新权重更好”。它只能告诉你：哪些场景换位了，哪些场景掉出了前排。判断仍然要人来下。

## 二、12 组上下文怎么定

上下文由四个维度组合而成：

- 时段：深夜、工作时段、晚间。
- 工作信号：忙碌、空闲、未知。
- 关系等级：初识与亲近两档。
- 心情：平静、愉快、低落。

不是做全排列，而是挑 12 组有代表性的组合。例如：

- 深夜 + 忙碌 + 初识 + 平静。
- 工作时段 + 空闲 + 亲近 + 愉快。
- 晚间 + 未知 + 初识 + 平静。
- 深夜 + 空闲 + 亲近 + 低落。

每组有固定 id、可读标签、空闲分钟与最近集合。最近集合默认留空，避免把去重惩罚混进基础排序。

## 三、候选从哪来

候选优先来自生成队列。队列里的场景天然带时长、道具、主题、标签与弱偏好，正好覆盖打分器需要的字段。

如果队列不足 3 条，就回退到一组固定样例候选。样例不是真实内容，只用于让矩阵在空库上也能跑通。

这个回退很重要：评测脚本不应该因为“今天没有生成新场景”而失败。样本少可以标注，不能直接不可用。

## 四、排序规则必须确定

排序函数有三层规则：

1. 总分降序。
2. 上次播放时间更早的优先。
3. 场景 id 字典序。

第二层是为了让“同样分数时，久未出现的先演”；第三层是为了兜底。没有第三层，同分场景的顺序会依赖数组插入顺序，不同运行可能不一致。

矩阵测试里专门断言“连续两次输出完全一致”，把确定性变成硬约束。

## 五、权重覆盖

矩阵默认使用线上权重，也支持命令行覆盖：

```text
--weights=hour=0.35,mood=0.05,work=0.05,...
```

没有传的维度补默认值。权重必须在 0–1 之间，未知键直接报错。

覆盖值只影响本次报告，不写回设置，也不改变线上行为。这一点必须明确，否则调参工具会变成隐形的配置入口。

## 六、差异报告

矩阵输出每一组上下文下所有候选的排名、分数与理由码。对比上一次报告时，只输出变化项：

- 新进入的候选：原排名为空，新排名为 N。
- 掉出的候选：原排名为 N，新排名为空。
- 换位：原排名与新排名不同。

差异按上下文 id 和场景 id 排序，保证报告稳定。一次权重覆盖产生几十条差异很常见，控制台只打印前几条，完整内容进 JSON。

## 七、一次真实实验

把时段权重从 0.2 提到 0.35，工作与心情权重降低，再跑同一批候选：

- 深夜与晚间上下文中，长场景明显上升。
- 工作时段忙碌上下文里，短场景仍然靠前，但优势缩小。
- 一共出现 22 处排名变化。

这些变化是否符合直觉，要人来判断。矩阵的价值是让判断有据可依，而不是替人做判断。

## 八、怎么读结果

建议按三步读：

1. 先看有没有“明显不合理”的换位，例如忙碌时长时间场景排第一。
2. 再看差异是否集中在预期维度，例如调时段权重不应让关系维度大面积换位。
3. 最后看稳定上下文，也就是那些两版排序都没变的组，确认改动没有外溢。

如果一次改动导致所有上下文都大幅换位，通常说明权重归一化或默认值出了问题。

## 九、边界

矩阵是代理实验，不是用户满意度。它不读聊天正文，不使用真实互动数据，也不做在线分流。

12 组上下文是人工挑选的，必然有盲区。后续如果要调参，应保留几组不参与调整的上下文做留出验证，这一轮先不做。
