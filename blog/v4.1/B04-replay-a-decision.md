# 只有上下文和理由码，怎么回放一次决策打分

想做“调权重前后对比”，最自然的想法是：拿历史决策重算一遍分数。

真正动手才发现，记录里没有当时的候选特征。只有小时、空闲分钟、关系等级、心情、工作信号、总分和几个理由码。候选场景多长、用了哪些道具、主题和标签是什么，全都不在记录里。

没有这些字段，完整重算做不到。但完全不重算，回放又没有意义。

这一轮采用了一个折中口径：**基础维度用当前权重重算，去重与偏好增量沿用记录。**

## 一、记录里到底有什么

一条决策记录包含：

- 时间与场景 id。
- 来源：主动播放、互动触发或环境低语。
- 加权总分。
- 最多六个理由码，每个带正负增量。
- 上下文：小时、空闲分钟、关系等级、心情、工作状态。

这些字段足够解释“为什么选这场”，但不包含候选的完整快照。

## 二、缺的是什么

打分器有六个基础维度：时段、心情、关系、工作、空闲成本、新鲜度。它们只依赖上下文和候选时长/道具数，理论上可以重算。

真正缺的是去重与弱偏好所需的集合：

- 最近用过的道具。
- 最近用过的主题。
- 最近用过的梗标签。

记录里没有这些集合，也没有候选的主题、标签与弱偏好。硬要重算，只能把这些维度当成空，结果会系统性偏高。

## 三、回放口径

折中方案分三层。

第一层：六个基础维度用当前权重重新计算。

第二层：去重、弱偏好、长场次的增量直接沿用记录里的理由码 `delta`。这些增量不依赖权重，记录时已经算好，精度足够。

第三层：把两部分相加，再截断到 0–1，与记录总分比较。

这个口径能回答“权重变化让分数移动了多少”，但不能回答“当时如果换一套集合会怎样”。报告会明确写清这一点。

## 四、基础维度怎么重算

基础维度是纯函数：

```ts
baseScore(context, candidate, weights)
```

上下文来自记录；候选只需要时长与道具数。生成队列里还能找到的场景，直接提取特征；找不到的，标记为缺失。

缺失是正常情况。历史记录可能来自内置场景，而生成队列只保留当天内容。报告里单独统计缺失条数，不把缺失当成零分。

## 五、增量为什么可以沿用

理由码里的增量已经是加权后的结果。例如：

```json
{ "code": "dedupe:theme", "delta": -0.15 }
```

它不依赖当前权重，也不依赖重新采集的集合。只要记录还在，这个惩罚就可以原样加回去。

弱偏好和长场次同理。唯一需要注意的是理由码有数量上限：如果记录时被截断，增量可能不完整。报告用均值差和最大差暴露这种偏差，而不是假装精确。

## 六、今日未播怎么反推

新鲜度依赖 `playedToday`，记录里没有这个布尔值。

可以从理由码反推：如果记录包含 `fresh:unplayed`，说明当时未播，重算时设为未播；否则设为已播。

这是一个近似，但比默认“全部未播”可靠得多。它保证同权重回放时，基础维度与记录一致。

## 七、伪代码

```ts
const playedToday = !record.reasons.some(r => r.code === 'fresh:unplayed');
const candidate = { ...snapshot, playedToday };
const adjustments = record.reasons
  .filter(r => RECORDED_ADJUSTMENTS.has(r.code))
  .reduce((sum, r) => sum + r.delta, 0);
const recomputed = clamp01(baseScore(ctx, candidate, weights) + adjustments);
```

排序、理由码与总分都保留三位小数，避免浮点尾差影响对比。

## 八、怎么验证

验证分两种。

同权重回放：用记录生成时的权重重算，差值应为 0。测试里用一条真实结构的记录断言 `delta === 0`。

换权重回放：把新鲜度权重拉满、其余归零，回放分应变成 1，均值差应大于 0。这能证明权重参数确实生效，而不是被忽略。

再加一条缺失候选的测试：候选找不到时，回放分为空、差值不计入均值。

## 九、真实报告

在本机库上跑一次：

- 3 条决策，可回放 2 条，缺失 1 条。
- 均值差 0.09，最大差 0.18。
- 缺失的是内置场景，生成队列里已经没有。

最大差 0.18 不是 bug，而是口径差异：记录时的去重集合、理由码截断与当前重算不完全等价。报告把它展示出来，比隐藏更有用。

## 十、边界

回放分不是线上原始分，不能拿来宣称“当时应该选另一场”。它只是权重变化的对照工具。

如果以后需要精确回放，得在记录里保存候选快照与最近集合。那会增加写入体积，也会引入新的隐私边界，这一轮刻意没做。
