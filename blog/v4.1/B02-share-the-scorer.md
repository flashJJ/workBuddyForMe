# 同一套打分器，浏览器和脚本都能用：契约下沉与零回归迁移

打分器本身不复杂：六个维度的加权和，加上去重、弱偏好和长场次惩罚。麻烦的是它住在浏览器业务目录里，而离线评测脚本跑在 Node 里。

复制一份最省事。但两份权重迟早漂移：页面改了常量，脚本还在用旧值，报告看起来正常，结论却是错的。

这一轮把打分与排序契约下沉到共享包，旧入口只留 re-export，页面代码和测试一行不改。

## 一、问题不在算法，在边界

原始实现是纯函数：输入上下文与候选特征，输出总分和理由码。它不碰 DOM、不碰 React、不碰渲染器。

但它所在的目录属于 web 业务域，脚本无法直接 import TypeScript 源码；用测试壳去跑脚本，又会让“评测”变成“测试的副作用”。

真正要解决的是边界：把可复用的纯逻辑放到两边都能依赖的位置，把渲染适配留在原地。

## 二、三条路

我们比较了三种做法。

1. **复制实现**：最快，但两套权重、两套测试，不可接受。
2. **用测试运行器承载脚本**：能跑，但报告生成依赖测试框架，退出码和参数都不自然。
3. **下沉共享包**：多一次迁移，但从此只有一套实现。

选择第三条。代价是迁移当天要改 import，收益是之后每次调权重都只改一处。

## 三、迁移顺序

迁移按“类型 → 权重 → 打分 → 排序”的顺序进行。

- 类型：上下文、候选特征、排序结果。
- 权重：六个维度的常量表。
- 打分：基础维度、去重、弱偏好、长场次、理由码排序。
- 排序：候选提取、同分规则、场景候选入口。

每搬完一层就跑一次旧测试，确保失败能在最小范围内定位。

## 四、旧入口只留 re-export

页面里有大量 import 指向旧文件。如果全量改 import，diff 会非常大，评审也很难看出行为有没有变。

做法是：旧文件保留文件名与导出名，内容改成一行 re-export。调用方完全无感，测试也不需要改。

唯一的签名变化是给打分和排序函数增加可选的 `weights` 末参，默认值仍是原常量。线上调用不传，离线脚本传覆盖值。

## 五、一个类型坑

第一次编译失败得很直接：

```ts
export const DEFAULT_WEIGHTS = { hour: 0.2, mood: 0.15 } as const;
export type Weights = typeof DEFAULT_WEIGHTS;
```

`as const` 把每个值推成字面量类型，`hour` 的类型是 `0.2`，不是 `number`。脚本传 `hour: 0` 覆盖权重时，类型检查报“0 不能赋给 0.2”。

修复方式不是去掉 `as const` 就完事，而是显式声明接口：

```ts
export interface Weights {
  hour: number;
  mood: number;
  // ...
}

export const DEFAULT_WEIGHTS: Weights = { hour: 0.2, mood: 0.15 };
```

默认值仍然是常量，覆盖值也可以是任意数字。类型表达的是“这是一组权重”，不是“这是六个固定小数”。

## 六、怎么证明零回归

迁移最怕“测试都过了，但行为变了”。我们用了三层证据。

第一层是旧测试不改。页面 Utility 的 12 项测试原样运行，覆盖忙碌选短、深夜偏好、去重回退与同分规则。

第二层是新测试补齐共享包。默认权重、同输入确定性、权重覆盖、理由码排序与上限、总分落在 0–1，共 5 项。

第三层是全量。迁移完成后跑 9 个包 724 个文件 4133 项测试，静态门禁六项全绿。

三层都过，才能说“只是搬家”。

## 七、边界

共享包只放纯数据与纯函数：不依赖 three.js、不依赖 React、不持有运行时状态。VRM 适配、动画混合器、页面缓存都留在 web。

这样做还有一个隐性收益：离线脚本不需要启动浏览器，也不需要 mock 渲染层，评测可以在几秒内跑完。
