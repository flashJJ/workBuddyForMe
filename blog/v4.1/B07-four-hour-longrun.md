# 4 小时长跑采样：p50、长任务、堆与 GPU 资源怎么一起看

桌面宠物是持续渲染场景。短时间看没问题，不代表四小时后没问题：动画混入内存、纹理没有释放、定时器越积越多，都可能在前十分钟完全看不出来。

我们早就有一个长跑脚本，每 5 分钟采样一次，记录 fps、rAF 均值/p95/最大值、GL 调用、堆和 DOM。但它有两个缺口：没有基线和门禁，也没有 GPU 资源计数。

这一轮先把观测补齐，再谈门禁。

## 一、长跑到底要看什么

一次四小时运行，至少要看四类指标：

- 帧时间：p50 与 p95，而不是只看平均 fps。
- 长任务：单次阻塞超过 50ms 的主线程任务。
- 内存：JS 堆的峰值与结束值。
- GPU 资源：geometries、textures、programs 的数量变化。

四类指标放在同一条时间线上，才能区分“一直慢”和“越跑越慢”。

## 二、原有采样有什么

原脚本在页面加载前注入探针：

- 包装 `requestAnimationFrame`，统计应用自身回调耗时。
- 统计 WebGL clear 与 draw 调用，判断画面是否真的在更新。
- 读取 `performance.memory` 的已用堆。
- 统计 DOM 节点数。

采样每 5 分钟一次，每次 10 秒，结果逐行写入 JSONL。这个结构很好用，问题只是维度不够。

## 三、补 p50

平均耗时会被极值拉高，p95 只反映尾部，p50 才能说明“大多数帧有多快”。

实现很直接：把采样窗口内的回调耗时排序，取 50%、95% 分位。汇总时再对各窗口的 p50 求平均。

这里遇到一个有意思的坑：**p50 经常是 0ms。**

原因是大量 rAF 回调本身极快，而浏览器计时分辨率有限，排序后中位数落在 0 上。它不代表渲染是零成本，只代表“一半回调低于可测精度”。

所以 p50 适合看趋势，不适合当绝对指标；p95 和长任务更有诊断价值。

## 四、补长任务

长任务用 `PerformanceObserver` 观测：

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    durations.push(entry.duration);
  }
}).observe({ type: 'longtask', buffered: true });
```

每次采样开始时清空数组，采样结束时统计次数与最大时长。这样每个窗口的长任务不会被重复计算。

浏览器不支持 `longtask` 时直接跳过，不阻塞其他指标。

## 五、补 GPU 资源

开发环境里，VRM 会话暴露了一个只读探针，可以读取渲染器的资源快照：

```ts
{ geometries: 24, textures: 56, programs: 6 }
```

每次采样读一次，汇总时保留峰值与末值。模型热替换、贴图切换、舞台进出之后，这三个数字应该回到基线附近；如果持续增长，就是回收链路有问题。

探针只在开发环境安装，生产构建不暴露。

## 六、汇总与归档

汇总包含：

- 采样数、运行分钟数。
- p50/p95 均值与 p95 最大值。
- 长任务总数与最大时长。
- 堆起始、结束、峰值。
- 资源峰值与末值。
- 页面错误数。

新增一个 `--summary-out` 参数，把汇总与全部采样写成独立 JSON。JSONL 继续保留，方便逐行分析；汇总文件用于版本归档和发布说明引用。

## 七、3 分钟冒烟

正式跑四小时前，先用 3 分钟验证脚本本身：

- 4 个采样窗口。
- p50 0.025ms，p95 1.725ms。
- 长任务 2 次，最大 87ms。
- 堆稳定在 189.8MB。
- 资源末值 24/56/6。
- 页面错误 0。

软件渲染下 fps 只有 20 左右，这是 SwiftShader 的限制，不是应用回退。报告里会标注渲染后端，避免拿这组数字和其他机器比较。

## 八、4 小时怎么跑

命令固定为 240 分钟、每 5 分钟采样 10 秒，约 48 组样本。报告按上面的结构归档。

运行期间要保持机器唤醒、开发服务不重启，否则采样会中断。脚本本身不判断“是否通过”，它只负责采集与汇总；门禁是另一个脚本的事。

## 九、4 小时结果

一次完整的 240.2 分钟运行，49 组采样：

- p50 0.008ms，p95 2.092ms，p95 最大 2.6ms。
- 长任务 1 次，最长 109ms，出现在启动阶段。
- 堆从 141.1MB 回到 141.1MB，峰值 168.8MB，呈锯齿而不是单调上升。
- 资源从 24/56/6 开始，125 分钟升到 34/56/8，185 分钟升到 38/56/9，之后 55 分钟不再增长。
- 页面错误 0。

两次资源台阶对应不同剧本加载的道具与动作，纹理始终稳定在 56。台阶之后长时间持平，说明是内容缓存而不是持续泄漏。

这组数字不能证明“绝对没有泄漏”，但足以说明：在当前场景组合下，没有出现随运行时间线性增长的资源曲线。

## 十、边界

长跑数字只适合同机比较。没有 GPU 的环境、软件渲染、不同分辨率都会改变结果。

脚本自身也可能泄漏。采集器与页面分离进程、定期校准探针，是后续要补的工程项；这一轮先把指标跑通。
