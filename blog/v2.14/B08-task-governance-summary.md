# 任务治理摘要：一个任务行为什么要显示模式、目录、策略哈希和来源

任务列表早期的展开区很简单：时间、状态、耗时、步骤。它能回答「这个任务跑了多久」，回答不了「它是怎么被允许跑的」。

这个差别在排障时会立刻显现。用户说「昨天那个整理任务改错文件了」，你需要的不是耗时，而是：当时用的是哪档模式？它有工作目录吗？当时的策略和现在一样吗？这次是用户手动点的，还是定时任务触发的？这四个信息一个都不在列表里，只能靠回忆，而回忆在事后几乎总是错的。

## 四个字段，每个回答一个问题

| 字段 | 回答的问题 | 为什么必须在这里 |
|---|---|---|
| 权限模式 | 这次运行有多严 | 同一套工具在不同模式下行为完全不同 |
| 脱敏工作目录 | 它被允许碰哪里 | 「改错文件」通常就是路径判断 |
| 策略哈希 | 当时的规则是哪一版 | 策略改过之后，现在的规则不等于当时的规则 |
| 来源定时任务 | 谁触发的 | 无人值守场景与手动场景的排障路径不同 |

再加一组：最近十条关联审计事件。摘要告诉你「上下文」，审计告诉你「发生过什么拒绝或批准」。

## 策略哈希：把「当时的规则」变成可比对的指纹

策略存在设置里，可以随时被编辑。这就带来一个经典问题：事后看到一次拒绝，拿现在的策略去推演，得到的结论可能完全相反——因为拒绝发生时用的是另一版规则。

所以在运行创建时把策略内容算成哈希写进运行记录。摘要里显示这个哈希，带来两个直接能力：

- **同一性**：两次运行哈希相同，说明用的是同一版规则，差异一定来自参数或环境；
- **可复现**：需要逐条重放时，用记录的哈希去对应策略快照，而不是猜「大概是那时候改的」。

不显示策略全文，只显示哈希，是因为摘要要在一行展开区里可读；全文属于审计页和诊断包的职责。摘要给线索，详情给证据。

## 脱敏目录：保留辨识度，隐藏隐私

路径显示用的是和任务时间线一致的折叠规则：保留首段与末级，中间省略。展开区是用户最常截图的地方，完整路径铺在这里等于把隐私默认公开。

折叠后的路径仍然够用：用户能认出「这是我那个项目目录」还是「那是个临时目录」，这两者对应完全不同的排障方向。需要精确值时，原始路径在悬停提示里。

另外，目录可能压根没设。这时不显示空白，而是一个明确的「未指定」——「没有目录」本身就是一条重要信息：在没有目录的写操作会被降级为询问，这解释了为什么那次任务问了一堆确认。

## 来源定时任务：把「没人操作」这件事说出来

运行记录里有来源字段，指向触发的定时任务。摘要把它翻译成一句人话：手动触发，或由某个定时任务触发。

这条信息在排障时价值很高。定时任务触发的运行没有人在场，遇到需要审批的操作会挂起、超时后按拒绝处理；这类「莫名其妙的失败」，如果不标来源，用户会以为是应用自己发疯。标出来之后，用户立刻知道该去看那个定时任务的配置。

来源为空不是缺失数据，是正常状态——大部分运行就是手动发起的。

## 最近十条关联审计：摘要的下一跳

治理摘要只给上下文，不够回答「具体拒绝了什么」。所以展开区后半段接一小段审计列表，按运行 id 过滤，固定取最近十条。

三个刻意的限制：

1. **复用既有查询**，不为摘要新增接口；参数就是运行 id 加一个条数上限；
2. **不做分页**，摘要不是审计页，十条足够看出「这次有没有异常」；
3. **给一个「查看审计」入口**，想看全部就跳过去。

这形成了一条很自然的路径：列表 → 展开看摘要 → 看到某条拒绝 → 跳审计详情。每一跳都只增加一层信息，不要求用户一次面对全量数据。

## 摘要不显示什么

刻意留白同样重要：不显示策略全文，只给哈希；不显示工具参数原文，那可能包含用户输入的文件名或文本；不显示对话与模型输出。展开区是一个高频率、易截图的界面，信息越少越安全。

需要细节时路径是明确的：策略全文去设置页，审计详情去审计页，运行过程去任务时间线。摘要只负责让人在三十秒内判断「这次运行大概是哪类问题」。

## 一次展开只有两个查询

摘要的四个字段都来自任务运行记录本身，不需要联表；最近审计只多一次按运行 id 的查询。展开一行不会触发任何后台任务，也不会拉取全量日志。

条数限制在十条，既是为了可读，也是为了让这次查询保持在毫秒级。真正需要全量的场景，走审计页的过滤，那里本来就分页。

## 空态与失败态要分开

最近审计有两种「没有」：

- **查到了，但没有事件**：显示「本次运行没有关联审计事件」。这是合法结果，说明这次运行没触发任何策略决策或审批。
- **查询失败**：显示「关联审计加载失败」并保留重试入口。这是异常，不能和上一种混在一起。

两者共用一句「暂无数据」，会让用户误判：他可能因此认为那次运行很干净，而实际上只是接口挂了。

## 只读，而且不新增写操作

摘要里的每一个字段都来自运行记录本身，没有一条是「顺便写的」。整个组件不调用任何变更接口，也没有「重试这次运行」「复制配置」这类看起来很方便的按钮。

这不是保守，是分层：任务列表的职责是展示事实，干预动作集中在审批中心和任务操作区。混在一起会让「只读页面」这个概念失效。

## 组件拆分与行数

这块内容放在任务行组件里会立刻把那个文件推过行数上限，所以拆成独立组件：摘要负责四个字段与最近审计的取数，行组件只负责展开/收起与挂载。拆分的收益不只是行数——摘要可以在别处复用（比如未来的运行详情），而不用把列表行一起搬走。

## 验证

新增三条用例：四个字段正确渲染（含目录未指定、来源为空两种边界）、最近审计正常展示十条以内、空态文案正确。另外沿用了任务时间线的路径折叠用例，保证两处显示规则一致。

## 边界

- 摘要不展示策略全文，只有哈希；
- 最近审计固定十条，不提供条数选择；
- 定时任务来源只显示「来自定时任务」，不展开该任务的配置快照——那是另一条链路的事。
