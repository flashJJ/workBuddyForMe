# 反向依赖与同版本修复：拒绝要说清对象，修复要证明内容真的变了

能力包之间可以声明依赖。升级时检查「我要装的东西，依赖的东西在不在」，这是正向依赖；还有另一半常被漏掉：**「我要动的东西，有没有别的包正依赖着」**，也就是反向依赖。

漏掉它的后果很具体。包 B 的清单写着「依赖包 A 的 2.0.0」，用户把 A 降级回 1.0.0，安装成功，运行时 B 加载失败——或者更糟，B 加载成功但按 2.0.0 的接口调用，在某个分支上直接报错。安装器当时的所有校验都通过了，因为它只往前看。

## 只认精确版本依赖

反向依赖只对「精确版本」生效：某个启用中的包声明依赖当前版本的精确号，才构成阻塞。写成区间、通配或干脆没写版本的依赖，不阻塞。

这个取舍有现实理由：本地优先的应用没有在线解析器，无法可靠求解区间依赖；一个写着 `>=1.0.0` 的声明，本质上是在说「我不关心具体版本」。把这种声明当作阻塞条件，会让降级几乎永远不可用——因为总有一个包写着宽松范围。

换个角度说：**精确依赖是包作者主动签下的兼容承诺，宽松依赖是把兼容判断留给运行时**。前者值得在安装时守，后者应该在运行时报错。

## 为什么不让安装器自动求解依赖

一个自然的想法是：检测到冲突后，自动把依赖方一起升级到兼容版本。本地优先的应用做不到这件事——升级包从哪来？没有在线仓库，没有版本索引，安装器手里只有用户刚选的这一个文件。

这也是「只认精确依赖」成立的原因：精确依赖是一个可以在本地判定的谓词，区间依赖则需要一个求解器和一个包源。没有后者，前者是唯一诚实的选择。

## 启用中拒绝，禁用中只提示

检查结果按依赖方的启用状态分两支：

| 依赖方状态 | 行为 |
|---|---|
| 启用中且精确依赖当前版本 | 409，回传依赖方 id 列表，不安装 |
| 已禁用，但精确依赖当前版本 | 不阻塞，仍然把列表回传给用户 |

第二支容易被写成「一律拒绝」，但那等于让一个关掉的包永久冻结别人的升级路径。用户禁用它，本来就是为了腾出空间；把它的声明当成否决票，是把「停用」误解成了「仍然生效」。

第一支的关键是**不自动停用**。遇到冲突时，安装器完全可以「顺手」把依赖方关掉，让升级继续——技术上两行代码，产品上是一次越权：用户没让你动别人的开关，尤其当那个包是他每天在用的。

所以拒绝时带上 `details.dependents`，让界面能说：「包 C 和包 D 仍依赖当前版本，请先停用或升级它们」。拒绝的责任落在用户身上，但也把下一步动作给全了。

## 检查位置：文件替换之前

反向依赖检查放在快照备份与原子换位之前。理由和方向判定一样：拒绝必须无副作用。一次 409 之后，磁盘、数据库、健康状态都应该和请求之前一模一样，用户停用依赖方后重试，不需要先收拾残留。

这也解释了为什么错误码要单独定义，而不是复用一条泛化的「冲突」：界面需要按码展示依赖方列表，一条没有结构的错误文本做不到这件事。

## 同版本修复：凭什么说「内容变了」

第二个死路是包损坏：文件内容坏了，版本号没变。修复安装要解决的问题是「同版本号重装一次」，但它必须有个前提判断——否则用户点两次修复按钮，第二次会得到一句「版本和内容都没变」，白等一轮。

判断依据是清单里的校验和集合，比较方式是 canonical JSON：

```text
if (canonicalJson(oldManifest.checksums) !== canonicalJson(newManifest.checksums)) → 可修复
else → 拒绝
```

用 canonical JSON 而不是直接比较字符串，是因为键顺序、空白、序列化方式都可能变化；这些差异不代表内容变化。把校验和集合当作比较对象，而不是整个清单文件，是因为清单里的描述、作者、更新时间都可能合法变动，而文件内容没变——那种情况重装没有意义。

三种结果对应三条路径：

| 情形 | 不带修复标记 | 带修复标记 |
|---|---|---|
| 版本相同、校验和变了 | 422，但回执里标 `repairAvailable: true` | 安装并返回 `repair` |
| 版本相同、校验和没变 | 422，`repairAvailable: false` | 仍然 422 |

第二行是这一版最容易写错的地方。直觉上「用户都要求修复了，就让他重装一次呗」，但结果是一个什么都没修的动作，却让用户以为问题解决了。明确拒绝并写「版本与内容均未变化，无需修复安装」，比假装成功诚实得多。

## 错误码要带下一步，不只是带原因

这两个判断共同的设计取向是：**拒绝的时候，把用户下一步需要的信息一起返回**。

- 版本未变但内容变了 → 回执带 `repairAvailable: true`，界面能直接渲染「修复安装」按钮；
- 反向依赖冲突 → 回执带依赖方 id 列表，界面能列出要处理的包名；
- 降级缺确认 → 回执带当前版本与目标版本，界面能生成勾选文案。

错误码只承载「为什么失败」，`details` 承载「接下来做什么」。两者分开，前端不需要为每条错误码写一套正则解析文案，也不需要为了猜原因去读日志。

## 修复仍然走同一条安装链路

修复不是特殊路径，它只是方向判定返回了 `repair`，之后照旧：验签、依赖检查、反向依赖检查、快照、换位、失败回滚。

这条一致性很重要。如果为了「只是修个文件」走一条轻量路径，失败处理、备份策略、健康刷新都会分叉，最终两套行为各自演化。把修复当普通安装的一个方向，所有安全机制自动继承。

另一条小边界：修复不重置已被禁用的从属能力。它修的是这个包自己，与别人的开关无关——和反向依赖「不自动停用」是同一条原则的两面。

## 修复之后怎么确认修好了

修复成功不等于健康。安装流程在换位之后会跑一次健康自检，把清单与内容的问题变成结构化问题码；面板据此显示红色或正常。

修复只负责把文件换对，能否工作由自检回答。两件事分开，失败时用户才知道下一步该重新下载包，还是去改配置。

## 验证名单

围绕这两块新增的用例覆盖四组关键组合：升级路径下反向依赖冲突、降级路径下反向依赖冲突、同版本可修复、同版本不可修复。加上方向判定本身的边界，一共九条。

其中「降级路径下的反向依赖」是后补的：最初只想到升级要被拦，忘了降级同样会让精确依赖失效。这条用例补上之后，整条链路才算对称。
