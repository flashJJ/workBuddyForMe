# 降级协议：一个「版本只能涨不能跌」的规则，挡住了两个真实场景

能力包的升级守卫曾经很简单：新版本号必须大于当前版本号，否则拒绝。这条规则在正常迭代里没出过问题，但它把两个真实场景堵死了：

- 新版本有 bug，用户想回到旧版——没法降，界面只能显示「版本未变化」；
- 包文件在下载或解压时损坏，内容坏了但版本号没变——没法重装，因为版本没增加。

两个场景的共同点是：**版本号是声明，内容才是事实**，而守卫只看了声明。

## 先判方向，再判权限

这一版把「这次操作是什么」抽成一个纯函数：输入当前版本、包内版本、若干确认字段，输出方向或抛错。它不碰文件系统、不读数据库，因此可以穷举测试。

| 方向 | 条件 | 是否改磁盘 |
|---|---|---|
| `upgrade` | 包内版本高于当前 | 后续流程继续 |
| `repair` | 版本相同，且清单校验和发生变化，且带修复标记 | 后续流程继续 |
| `downgrade` | 包内版本低于当前，且确认标记与目标版本都正确 | 后续流程继续 |
| 非法版本 | 版本号解析失败 | 422，立即中止 |
| 版本相同但校验和未变 | 无可修复内容 | 422，立即中止 |

判定函数返回方向而不是布尔值，是为了让上游能区分「升级成功」和「降级成功」的提示文案。返回一个 `true`，界面就只能写一句含糊的「安装成功」。

## 为什么把它写成纯函数

方向判定一旦碰数据库或文件系统，就很难穷举：要造真实包、临时目录、状态行，测一条用例的成本上升一个数量级，于是「几乎不会发生」的分支会被悄悄漏掉。

抽成纯函数之后，输入是当前版本、包内版本和三个可选字段，输出是一个枚举或一条错误。九条用例可以在毫秒级跑完，非法版本、同版本无变化、降级缺确认这些边界组合，才有机会被真正覆盖。

## 降级要两个字段，不是一个

降级是这一版里唯一需要用户主动承担风险的操作，因此协议要求两件事同时成立：

1. `confirmDowngrade = true`——用户明确知道自己在往下走；
2. `expectedVersion` 等于包内版本号——用户确认的那一版，确实是这个文件里的那一版。

缺第一个，返回「需要确认降级」；第二个对不上，返回「确认目标不一致」，两条错误码分开。

第二条看着多余：客户端不是刚上传了这个包吗，怎么会不知道版本？因为「确认」和「上传」在时间上可以分离——用户先在对话框里看到「将降级到 1.2.0」，再去选择文件；如果选择过程中拿错了包，落地的就是 1.1.0。用 `expectedVersion` 把用户看到的版本与文件里的版本对齐，这类错配当场失败，而不是装完才发现回退到了更旧的一版。

这也是「乐观确认」与「精确确认」的区别：前者只需要一个布尔值，后者要求用户确认的对象与即将发生的对象完全一致。

## 顺序：所有拒绝都发生在碰磁盘之前

一次安装的完整顺序是：

```text
解析 ZIP → 校验 id / kind → 方向判定（含确认字段）
→ 验签 → 正向依赖满足 → 反向依赖 → 快照备份 → 原子换位
```

把方向判定放在签名与依赖之前，是刻意的排序。方向错误是用户意图问题，依赖错误是环境问题，两类问题的修复动作完全不同；先判意图，用户不会被一条「依赖不满足」的错误带去排查一个根本不该开始的安装。

更重要的是：这些校验全部在「快照备份」之前。拒绝时磁盘一个字节都没动，用户重试不需要先恢复现场。

## 二次确认放在服务端，还是客户端

一个很容易走偏的设计是：客户端解析 ZIP，读出版本号，本地比较，弹对应对话框。它的问题是浏览器端要引入 ZIP 解析依赖，解析结果还得和真的安装路径保持一致——两套解析逻辑迟早会分叉。

这一版采用「探测 → 确认 → 重试」：

1. 首次提交不带确认字段，只带包文件；
2. 服务端在改动磁盘前拒绝，返回结构化细节：目标版本、当前版本、是否可修复；
3. 对话框按方向渲染——降级显示风险提示与勾选框，同版本变化显示「修复安装」按钮；
4. 用户确认后带字段重试，服务端再走一遍完整校验。

代价是一次多余的请求与一次重复解析，收益是浏览器端零解析依赖，且「第一次拒绝不产生任何副作用」成为可验证的承诺。

## 一次完整交互长什么样

```text
提交包（不带确认字段）
← 422 需要确认降级
   details：目标 1.2.0，当前 2.0.0，可修复 false
界面：显示「将降级到 1.2.0」＋风险说明＋勾选框

提交同一个包 ＋ confirmDowngrade ＋ expectedVersion=1.2.0
← 200 方向 downgrade，版本 1.2.0
界面：已降级到 1.2.0，数据未回滚
```

第二次提交会重跑完整链路，而不是复用第一次的解析结果。多一次解析换来一个确定性：用户确认的对象，就是这次真正落盘的对象。

## 确认框必须写清楚不保证什么

降级只保证代码、清单与随包资源回到旧版本。能力包写入的设置项、已产生的外部副作用、已经迁移过的数据结构，都不在回滚范围内——旧代码可能读不懂新数据。

这一句必须出现在确认文案里，而不是只在文档里。用户勾选的是「我知道我在降级」，不是「我勾选了一个魔法回滚」。

同样，修复安装也不重置已被禁用的从属能力：修的是这个包的文件，不是别人的开关。

## 成功之后还要说方向

安装成功的回执里带 `direction`。界面据此给出三种文案：升级成功、已降级到某版本、已用同版本内容修复。三者对用户的含义不同，尤其是第三个——它意味着「版本号没变，但文件变了」，用户需要知道这一点，否则下次看到版本号相同会以为刚才什么都没发生。

## 这一版的测试

核心用例集中在方向判定这个纯函数上：降级缺确认被拒、降级目标不一致被拒、同版本同内容即使带修复标记也被拒、同版本不同内容带标记成功。再加上升级路径下反向依赖冲突与降级路径下反向依赖冲突两组，一共九条。

纯函数的好处在这里体现得很直接：不需要造真实 ZIP、不需要临时目录、不需要数据库，九条用例瞬间跑完，边界组合可以放心穷举。
