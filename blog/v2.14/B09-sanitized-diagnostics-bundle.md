# 脱敏诊断包：为什么白名单组装比黑名单过滤更可靠

本地优先的桌面应用有一个特殊的排障成本：所有数据都在用户机器上，开发者拿不到任何东西。传统做法是来回几轮——让用户截图、让用户翻日志、让用户回答「供应商配了几个」「策略里有没有禁这条」——每一轮都消耗一次注意力，而用户往往已经因为功能出问题在生气。

另一条路是把日志和配置打包发出来，但日志里可能有 URL、密钥、对话片段，本机路径又暴露了目录结构。**便捷与隐私在这里是直接冲突的**。

这一版选择先解决隐私，再谈便捷：诊断包只包含固定字段，在本地生成，不上传。

## 组装方式决定泄露风险

脱敏有两种实现路径：

1. **先收集再过滤**：把数据库行、设置对象、日志全部拿到内存，然后递归删掉敏感键；
2. **白名单组装**：每个输出文件独立查询、独立构造，只放进去明确列出的字段。

第一种看起来更省事，但它把安全性交给了「过滤器是否覆盖了所有路径」。三个月后有人给设置加了一个 `apiKeyBackup` 字段，过滤器不知道，泄露就发生了——而且不会有任何测试报警，因为没人想到要测这个新字段。

第二种把方向反过来：**默认不输出，输出必须先被写一次**。新增字段不会自动流入诊断包，只会在你主动加一行代码之后才出现。代价是每次加内容都要改收集器，这恰好是想要的摩擦。

## 八个文件

| 文件 | 内容 |
|---|---|
| `manifest.json` | 格式版本、应用版本、实际数据库版本、平台与架构、生成时间、其余条目的路径/大小/哈希 |
| `versions.json` | 应用版本、最新数据库版本、实际数据库版本、运行时版本 |
| `audit-verify.json` | 审计链校验结果、校验条数、首个断链序号、是否截断 |
| `capabilities.json` | 每个能力包的 id、类型、版本、状态、健康问题码 |
| `runs-summary.json` | 最近七天的运行按状态计数、定时来源计数 |
| `settings-summary.json` | 供应商与模型数量、策略哈希、默认模式、是否存在带目录的运行、功能开关 |
| `errors.log` | 最近错误事件的类型摘要 |
| `README.txt` | 给人看的说明：这个包里有什么、没有什么 |

注意 `manifest` 里每个条目的 `sha256`：它让接收方可以验证「文件在传输中没有被改」。诊断包不是签名产物，但至少能自证完整性。

`README.txt` 也值得单独说：诊断包最常见的用法不是发给开发者，而是用户自己打开看。一段明确写着「不含密钥、对话正文、绝对路径」的说明，比任何隐私政策都更能让人敢点导出。

## 错误日志：只保留四个字段

`errors.log` 是最容易泄露的一个文件，因为错误信息天然会带上参数。它的构造过程是：

```text
1. 从追加式会话事件里取最近 1000 条
2. 用类型名筛选 error / failed / blocked / denied / timeout
3. 每条只输出：时间、作用域、净化后的事件类型、安全错误码
4. 单行截断到 500 字符，最多 200 条
```

事件类型先过一遍字符白名单，只保留字母、数字、点、下划线、冒号、连字符，超长截断；错误码必须匹配固定格式（长度有限、只含安全字符）才输出，否则整段丢弃。

**错误消息正文一行都不输出**。这是刻意的：消息文本是最难脱敏的部分，它可能包含用户输入的路径、文件名、请求参数。错误码 + 类型 + 时间已经足够定位到「哪一类失败、在哪个阶段」，具体消息让用户按需单独提供。

## 审计链校验：能截断，但要标注

审计账本的校验是逐条重算哈希链。数据量很大时，全量校验会拖垮生成预算，所以设了一个上限：超过十万条只校验最近十万条。

截断校验有一个技术难点：链是连续的，从中间开始校验时，第一条的 `prev_hash` 指向一条没有被校验的记录。正确做法是把这一条当作新的链起点，从它的 `prev_hash` 开始续算——否则会得到一堆假的断链。

同时输出 `truncated: true`。不标注截断，接收方会以为「链没问题」，而实际上前半段根本没看。**降级可以，静默降级不行。**

还有一个容易忽略的副作用：常规校验会顺手把校验结果写回数据库（表示这批记录已验证）。诊断场景明确传「不写回」——生成一个诊断包不应该改变任何业务状态，否则用户每点一次导出，审计表就多一次写入，这本身就污染了它要取证的对象。

## 运行统计与配置摘要：只给形状，不给内容

运行统计按最近七天、按状态分组计数，外加「其中由定时任务触发」的数量。不输出运行 id、不输出任务标题、不输出具体时间点。

这组数字能回答的问题其实不少：失败率是不是突然升高？是不是集中在定时触发的运行？有没有大量挂起等待审批的？这些问题用计数就能看出来，不需要任何个体信息。

配置摘要同理：供应商数量、模型数量、策略哈希、默认模式、功能开关状态，加上一个「最近是否有带工作目录的运行」。最后这一项的设计有个背景：设置里并没有全局的「工作目录」字段，目录是每次运行单独指定的，所以只能回答「有没有用过」，不能回答「配的是哪个」。

## 预算、上限，和「不上传」

生成过程带 30 秒预算，每个文件装配前检查一次剩余时间；超时直接返回明确的错误码，而不是返回一个内容不全的包——半成品比失败更危险，因为接收方不知道少了什么。

ZIP 由纯 JavaScript 实现在本地生成，不引入任何上传路径，打包后还有一道大小检查作为防御。文件名带应用版本与生成时间戳，方便用户同时保留多份对比。

前端是「请求 → 拿到 blob → 触发下载」，生成期间按钮禁用并显示进度提示。失败时按结构化错误码给出提示，而不是整页跳转到一个错误页。

## 用哨兵数据反向验证

脱敏最怕「看起来干净」。验证方式不能是人工翻一遍，而是造数据、跑一遍、机械搜索：

- 在供应商配置里写入一个占位密钥 `sk-SENTINEL-DEMO`；
- 在运行记录里写入一条带绝对路径的工作目录；
- 在会话事件里写入一条包含完整 URL 的错误；
- 生成诊断包，把全部内容拼起来 grep 哨兵值、路径前缀、运行 id 与对话 id。

断言零命中。这类测试的价值不在于覆盖多少分支，而在于它把「脱敏」从主观判断变成了可回归的断言——将来任何人不小心把设置对象整个塞进某个文件，这条测试会当场变红。

## 诚实边界

诊断包不包含业务正文，所以它不能复现「模型为什么这么回答」这类问题；审计账本尾部截断仍然无法通过包内校验发现，需要外部锚点；生成过程不做压缩优化，十万条级别的校验在低配机器上可能贴近预算上限。

把这些写进 README 和发行说明，反而减少了后续的沟通成本：用户知道这个包能回答什么，就不会拿它去问它答不了的问题。
