# 原子回退：把「换一个目录」做成一次可失败、可恢复的操作

技能快照解决了「回退到什么」，剩下的问题是「怎么换」。最直观的写法是先删正式目录、再把快照复制回去——两步，两行代码，也是这类操作最危险的一种。

它至少有三个窗口会出事：删完还没复制完时进程被杀，目录不存在；复制到一半磁盘满，得到一个残缺目录，扫描器读到的是半个技能；复制过程中用户正好打开技能面板，看到的是一个中间态。回退本身变成了故障源，这是维护工具最不能犯的错误。

## 换位，而不是复制

正式做法把「唯一一次不可再分的动作」压缩到目录改名：

```text
1. 复制快照 → staging 临时目录（可与正式目录并存）
2. 正式目录改名为 backup
3. staging 改名为正式目录
4. 删除 backup
```

第 2 步和第 3 步都是同一卷内的改名，操作系统层面是一次原子替换：任何时刻外部看到的要么是旧目录，要么是新目录，不存在「没有目录」或「半个目录」。

复制被前置到第 1 步，落到 staging 上。这一步可能耗时、可能失败，但它不碰正式目录，失败了清掉临时目录即可，现场完好。

删除备份放到最后，也是刻意为之：只要备份还在，任何一步失败都有回头路。

## 同卷改名为什么是关键

staging 与备份目录都建在技能目录所在的同一卷上，这不是随手选的路径。跨卷改名在多数文件系统上会退化成「复制 + 删除」，于是「原子替换」的前提直接消失，换位重新变成一个可能中途失败的长时间操作。

代价是快照与正式目录必须共用一块磁盘。对数据根固定在本机的应用来说这个约束几乎总是成立；如果未来允许把快照目录指到另一个位置，这条假设必须重新评估，而不是默认成立。

## 失败要怎么收场

一个能回退的系统，必须先能回退自己的回退。失败处理按位置分三种：

| 失败位置 | 现场 | 处理 |
|---|---|---|
| 复制到 staging 阶段 | 正式目录未动 | 删 staging，抛错 |
| 改名后、换位后 | 正式目录已是新版，backup 还在 | 删除 backup，视为成功 |
| 换位失败 | 正式目录不存在，backup 还在 | 把 backup 改回原名，恢复现场 |

第三种是唯一需要「反向改名」的分支。恢复动作本身包在独立的异常处理里：如果连恢复都失败（比如权限被外部进程占住），**保留备份目录不清除**，让用户或后续工具还能拿到原始内容。

这条规则的价值不在代码优雅，而在于承认一个事实：磁盘操作可能失败到无法自愈，此时「留下证据」比「假装成功」重要得多。备份目录名带固定前缀与状态标识，一眼能认出来是回退残留，不是技能本体。

## 回退与启用态：文件归文件，开关归开关

启用态存在状态行里，和磁盘内容是两个维度。用户回退一个版本，通常想的是「回到旧行为」，而不是「把这个技能关掉」；如果他之前特意禁用了它，回退完应该还是禁用。

所以回退只做四件事：

1. 校验目标版本存在（行存在、目录存在）；
2. 换位替换文件；
3. 更新状态行的当前版本指针；
4. 立即重新扫描，让面板与清单进入一致状态。

第 3 步放在换位成功之后，是唯一正确的顺序。反过来「先改指针再换文件」，一旦换文件失败，数据库会声称正在跑一个磁盘上并不存在的版本，之后的列表、回退、诊断全部基于错误事实。

第 4 步不是可选项。回退只保证文件对，不保证这份内容的清单仍然合法——比如用户回退到一个很早的版本，而那一版的清单里有当前已不支持的字段。重新扫描会把问题暴露成面板上的红色错误，由用户决定是否再换一版，而不是等到运行时才炸。

## 回退与降级不是一回事

技能回退换的是目录内容，能力包降级换的是安装包内容，两件事常被混为一谈。差别在数据：技能目录是自包含的，回退后不需要迁移任何状态；能力包可能已经写过设置项或外部资源，降级只能承诺代码与清单回去，不承诺这些数据一起回去。

所以两套流程的确认强度也不同：技能回退只需要一次「确定回到这一版」，能力包降级必须额外确认目标版本号，并在文案里写明数据不在回滚范围。

## 回退之后列表返回什么

回退接口成功时直接返回刷新后的版本列表，而不是一个空回执。界面不需要再发一次请求，也不会出现「操作成功但列表还是旧的」这种中间态；当前版本标记已经指向刚回退的那一版，用户可以立刻看到结果。

失败时只返回错误码与原因，不返回任何列表——避免「操作失败，但界面看起来变了」的误导。

## 边界条件：缺版本、缺技能、缺目录

三种「找不到」要分开报，因为用户的下一步动作不同：

- 技能本身不存在 → 404，检查名字；
- 技能存在但这个版本没有快照记录 → 409，版本列表刷新后重选；
- 有记录但快照目录被人为删掉 → 同样视为版本缺失，返回同一条错误码。

把「记录在、目录没了」和「记录不在」合并成一个错误，是刻意的：对用户而言两件事一样——这个版本回不去，请换一个。区分它们只会产生一条没人会用的分支文案。

另外，当前启用版本永远不会被保留策略清理，所以「回退到自己现在这一版」不会因为目录被删而失败；这条红线在快照侧守住，回退侧才敢假设目录存在。

## 重启之后还算数吗

回退不写任何缓存，事实全在磁盘和数据库里：正式目录是回退后的内容，状态行的当前版本指向目标版本。重启后扫描读到的是正式目录，面板显示的是状态行，两者天然一致。

测试里专门有一条「回退、关闭数据库、用同一个数据根重新扫描」的用例。它验证的不是代码路径，而是一个承诺：回退是持久操作，不是内存里的一个开关。

## 为什么不做「就地还原」

还有一种更省磁盘的做法：不复制快照，直接把备份目录换回来。它的问题在于快照目录只有一份——回退时如果把快照移走，这个版本就从历史里消失了，用户连「再回退一次」都做不到。复制一份到 staging，代价是一次磁盘写入，换来的是可重复：同一版本今天回退、明天再回退，结果一样。

原子性、可恢复、可重复，这三条是回退区别于「手工拷文件夹」的全部理由。
