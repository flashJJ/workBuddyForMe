# 技能版本快照：何时建、靠什么去重、留几版

一个技能就是一个目录：一份清单加若干提示词、脚本和资源文件。升级的方式很朴素——用新目录覆盖旧目录。这个动作在成功时毫无存在感，在失败时却几乎不可逆：用户手里没有旧内容，也没有「旧内容是哪个版本」的记录。

于是第一个问题不是「怎么回退」，而是「回退到什么」。没有快照，回退只是一句愿望。

## 快照的时机：扫描确认之后，不是安装过程中

最直觉的时机是安装或升级完成时——既然知道正在装什么版本，顺手存一份就行。但这个时机是错的，原因有三条：

1. 安装可能中途失败，留下的目录不完整，按不完整内容建快照等于把垃圾存成「历史」；
2. 技能目录允许用户在应用外手工修改，安装时机构不到这类变化；
3. 只有扫描时才会真正解析清单、校验字段、确认目录可用，这是唯一能保证「这份内容是可工作的」的时刻。

所以快照挂在扫描确认之后：manifest 解析成功、目录校验通过，才计算内容指纹并建档。安装路径不碰快照逻辑，外部修改也能被下一次扫描捕获，两条路径收敛到同一个入口。

## 快照放在哪：与扫描根隔离

快照目录默认与技能目录同级，结构是：

```text
<data-root>/skills/<name>/                       正式目录，扫描只认这里
<data-root>/skill-versions/<stateId>/<version>/  快照目录，不参与扫描
```

隔离有两个理由。一是防止快照被当成技能再扫一遍，形成自我复制的版本树；二是回退时可以安全地清空重写正式目录，不必担心误删历史。

版本号会进入目录名，而版本号来自清单，属于外部输入。目录名先做字符净化，只保留字母、数字、点、下划线和连字符；一旦净化改变了原值（或者净化后是空、`.`、`..`），就追加原版本号哈希的短前缀。这样既挡路径穿越，也避免 `1.0.0+build.1` 与 `1.0.0_build.1` 净化后撞名。

## 去重靠什么：目录内容指纹，而不是版本号

版本号是声明，内容才是事实。同一版本号完全可能对应两份不同内容：作者修了个热补丁但忘了改版本，或者两个渠道各发了一版。如果只按版本号判断，第二次出现的内容要么覆盖历史，要么产生两条互相矛盾的「同版本」记录。

所以身份是二元组：`版本号 + 目录内容指纹`。指纹的算法刻意做得很朴素：

```text
1. 递归遍历目录，收集每个文件的相对路径、字节数、单文件 sha256
2. 相对路径统一用 "/" 分隔，按字符串升序排序
3. 对 { files: [...] } 做 canonical JSON 序列化
4. 对整个序列化结果再取一次 sha256
```

三个细节各有理由。用相对路径，是因为快照根不同但内容相同的目录必须判等；先排序，是因为文件系统的遍历顺序不稳定，不排序会得到随机的指纹；canonical JSON，是因为键顺序和空白不该影响身份。

这个指纹同时被用来做另一件事：能力包升级会重建技能状态行，历史却必须连续。新状态行建立时，如果「同名 + 同版本 + 同指纹」的快照已经存在，就直接复用那个目录路径，只新增一行引用，不复制第二份磁盘内容。

## 三个分支

拿到指纹后，写入只有三种结果：

| 情形 | 动作 | 理由 |
|---|---|---|
| 同版本、同指纹 | 只更新当前版本指针 | 内容没变，重复复制是浪费 |
| 同版本、不同指纹 | 覆盖该版本快照内容并更新指纹 | 同版本只能有一个真相，否则回退有歧义 |
| 新版本 | 建快照（或复用同指纹目录）并更新指针 | 正常的历史增长 |

第二行容易被质疑：为什么不保留两份同版本内容，让用户自己选？因为回退的入口是「版本号」，列表里出现两个 `1.0.0` 而内容不同，用户没有任何判断依据。覆盖成最新内容是伤害最小的选择——代价是那一份中间态不可回退，收益是版本列表始终可解释。

## 保留策略：五版，加一条永不清除的红线

每个技能自动保留最近五版。清理时按版本代表行排序，前五名与「当前启用版本」进入白名单，其余的行与目录一起删除。

两个顺序细节值得写出来：

- 五版是**按创建时间**算的，不是按语义版本算。版本号里可能有 `1.10.0` 与 `1.9.0` 这种字符串序与语义序不一致的情况，用时间排序最不容易出错；
- 当前版本无论排第几都不删。否则会出现「最新版被清理、回退入口指向一个不存在的目录」这种自相矛盾的状态。

清理还要处理共享目录：如果某条旧行指向的快照目录仍被保留行引用，只删行不删目录。否则一次清理会把仍在服役的快照连根拔掉。

## 为什么不靠修改时间判断变化

用文件的修改时间或总字节数判断「内容变没变」，看起来能省一次全量读取，但在这个场景里几乎必然出错：

- 复制、解压、同步工具都可能重写修改时间，内容没变也显示为新；
- 同一秒内连续写入两次，时间戳的分辨率不够用；
- 总字节数相同而内容不同（改一个字段的取值）完全无法察觉。

指纹要读全部字节，成本是确定的，换来的是「相同」这个结论可以当作事实使用——回退时不会把一份内容相同的目录再建一遍，清理时也不会因为时间戳抖动误删。

## 快照不是备份

需要说清一条边界：技能快照只服务「回到某一份已知内容」，它不承担灾难恢复。它不加密、不跨技能去重、不参与整体备份导出，也不会被保留策略以外的东西清理。

真正的数据备份是另一条链路，按轨道导出与恢复，和快照互不替代：备份解决「机器没了」，快照解决「这一版改坏了」。

## 列表给用户看什么

版本列表只返回四件事：版本号、内容指纹、目录体积、创建时间，外加一个「是否当前版本」的标记。不返回文件清单，也不返回清单全文——那是技能详情的职责，版本列表只需要让用户选一个可以回去的点。

配套还有一个能力标记：当某技能从未成功建过快照（超限或复制失败）时，列表明确表示「不支持版本化」，界面据此显示空态文案，而不是一个看起来能点、点下去必然报错的回退按钮。

## 体积上限：宁可不建，也不悄悄降级

技能目录可能包含模型文件、图片、数据集。快照是整目录复制，没有上限的话，一次升级就能吃掉大量磁盘。

上限设在单目录 50 MB：指纹计算过程中累计字节数一旦越线，立即中止并返回空结果。调用方拿到空结果时做三件事——写一条带稳定问题码的日志、跳过本次快照、照常加载技能。

关键是第三条：**版本化是增强能力，不是加载的前置条件**。超限的技能仍然能正常使用，只是版本面板显示「暂不支持版本化」，而不是报错或者给一个空列表假装有历史。

## 失败隔离

快照链路上的异常（复制失败、磁盘满、权限不足）一律只记日志，不让扫描失败。反过来，扫描失败也不会写快照——因为清单没确认，内容就没有被承认的资格。

这条规则听起来像「少管闲事」，实际上是版本化系统能长期存在的前提：任何旁路能力一旦能阻断主流程，用户第一次遇到它出问题就会要求关掉它。

## 这一版的验证

这一块新增的测试集中在三件事：同版本同指纹只更新指针且不重复占盘；同版本不同指纹覆盖内容；状态行重建后历史仍然连续且复用同一目录。再加上保留五版、超限跳过、回退与重启的组合用例，一共七条核心用例，都在真实临时目录上跑，不打桩文件系统。
