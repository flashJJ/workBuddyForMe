# 可维护复盘：一个不加功能面的版本，到底买到了什么

这一版没有新按钮、没有新玩法、没有新的模型能力。它的全部产出是：技能能回退、工作流有明确的生产版本、能力包能降级也能修、证据链能一键下钻、故障能一键取证。

从这个角度看，它像一次大扫除。但封版对账后我更愿意用另一个说法：**它是把「出事之后」这一段路补齐了**。一个本地优先的私人助手没有云端兜底，出事时唯一在场的是用户；这段路修不好，前面所有功能的价值都要打折扣。

下面七条，是这一版真正带走的东西，每条都配一个这版本里的真实例子。

## 为什么这五件事必须集中做

分散做，每一件都会被排到队尾：技能回退「现在没坏」、生产版本「反正没人用端点」、降级「用户还没遇到」、下钻「手抄一下也行」、诊断包「截图也能看」。它们有一个共同特征——**收益出现在故障之后，成本却发生在当下**。

集中做还有一个技术原因：五件事共享同一批底层事实。技能快照与状态行的关系、工作流两个版本号的关系、审计 id 与任务主键的关系、诊断包读取的版本与迁移字段——这些口径必须先对齐一次，否则五个功能各写一套，之后每加一个入口都要重新对一遍。

所以动手前先冻结契约，明确四件事：版本模型、生产版本语义、降级确认字段、诊断白名单。冻结的价值在实施阶段显现：五个里程碑里没有一次因为「这个字段到底代表什么」而返工。

## 一、要能回退，先得有「可寻址的过去」

回退不是一个动作，而是一个前提。没有历史记录，回退只能靠人记忆里「好像是上一版」。

技能以前只有一个文件夹和启用开关。这一版的做法是：扫描确认清单之后，按「版本号 + 目录内容指纹」建档快照。指纹的算法很笨——遍历目录、逐文件哈希、相对路径升序、canonical JSON 再哈希。

笨在这里是优点：**用相对路径**，同一份内容换个位置仍然判等；**先排序**，文件系统的遍历顺序不会污染身份；**canonical 序列化**，键顺序与空白不参与判断。三条规则合起来，让「同内容」成为一个可验证的事实，而不是字符串相等。

它还顺手解决了一个额外问题：能力包升级会重建技能状态行，如果按行主键存历史，升级一次历史就断一次。按「名称 + 版本 + 指纹」查重并复用目录，历史跨状态行连续，磁盘也不重复占。

## 二、回退要「换位」，不要「删了再复制」

最早的写法是先删正式目录、再拷快照回来。它有至少三个失败窗口：删完被杀进程、拷一半磁盘满、拷一半被面板读到。回退本身成了新的故障源。

改成四步：复制到 staging、正式目录改名 backup、staging 换位、删 backup。关键是把所有耗时动作前置到 staging，正式目录只在两次同卷改名之间切换——外部看到的永远是完整目录。

失败处理按位置分三种，其中唯一需要反向操作的是「换位失败」：把 backup 改回原名。如果连恢复都失败，保留备份目录不清除。这条规则的语气很关键：**磁盘操作可能坏到无法自愈，此时留下证据比假装成功重要**。

## 三、兼容旧数据，要写成一行显式的默认

工作流的运行版本从「最近保存」切到「生产版本」，这是个语义变更。一刀切会让历史上所有「只保存过、没发布过」的流程在升级当天集体不可运行。

所以解析写成一行：`生产版本 ?? 当前版本`。后面那个回退分支不是临时补丁，它是兼容契约的一部分，必须能被读出来、被测试覆盖、被写进边界说明。

还有一层顺序：先看有没有生产版本，有就放行；没有才看状态位。反过来的话，一条设过生产版本的流程会因为「草稿状态」被误判不可用。**两个判断的先后，决定了兼容路径是兜底还是漏洞。**

## 四、拒绝要发生在碰磁盘之前

这一版把能力包的安装顺序固定成：解析 → 校验 id 与类型 → 方向判定（含确认字段）→ 验签 → 依赖满足 → 反向依赖 → 快照 → 换位。

方向判定排在最前，因为它属于「用户意图」问题；依赖属于「环境」问题。先判意图，用户不会被一条依赖错误带去排查一个根本不该开始的安装。

更重要的一层：所有拒绝都在快照与换位之前。一次 409 或 422 之后，磁盘、数据库、健康状态和请求之前一模一样，用户处理完冲突重试，不需要先收拾残留。

配套的界面设计是「探测 → 确认 → 重试」：首次提交不带确认字段，服务端在改盘前拒绝并回传目标版本与当前版本；对话框据此渲染降级勾选或修复按钮。浏览器端因此不需要 ZIP 解析依赖，也不会出现第二套版本判断逻辑。

## 五、错误码说原因，details 说下一步

同一批拒绝里，用户的下一步动作完全不同：

- 「版本未变」→ 如果内容变了，回执带可修复标记，界面直接渲染修复按钮；内容没变则告诉他无需修复；
- 「反向依赖」→ 回执带依赖方列表，界面能说清要先停用或升级哪几个包；
- 「降级缺确认」→ 回执带当前与目标版本，界面能生成一句准确的勾选文案。

如果只返回一句「操作失败」，前端要么靠正则猜原因，要么干脆不提示，用户只能去翻日志。把结构化细节放进 `details`，文案就能按方向生成，而不是按错误字符串模板拼。

另外两条同源的原则：反向依赖冲突**不自动停用**依赖方——用户没让你动别人的开关；修复重装也**不重置**已禁用的从属能力——修的是这个包，不是别人的状态。

## 六、只读下钻的三个约束

审计里有 `run_id`，审批里有 `runId`，时间线按 id 过滤，三处数据都在，唯独缺一个点击。补这个入口时守了三条：

1. **唯一关联键**：三处必须用同一个 id，否则跳过去只会得到空结果；
2. **空态显式**：没有 id 的行显示「无关联运行」，不渲染死链；有 id 但查不到事件，显示「该 id 无关联事件」而不是 404；
3. **只新增导航，不新增写操作**：审计与审批的可信度来自「只记录、不干预」，页面能顺手改状态，里面的内容就不再被相信。

连地址栏同步都有细节：过滤变化用 `replaceState` 而不是推入历史，避免后退栈被塞满；清空过滤时必须主动移除参数，否则用户刷新会莫名回到旧结果。

## 七、脱敏用白名单，并用哨兵数据反向验证

「先收集再过滤」的脱敏有一个致命弱点：安全性取决于过滤器覆盖了多少字段。设置里新增一个字段，过滤器不知道，泄露就发生了，而且不会有测试变红。

这一版改成白名单组装：每个输出文件独立查询、独立构造，只放明确列出的字段。新增字段不会自动流入诊断包，必须有人主动加一行代码——这份摩擦是刻意的。

验证也不靠人眼：写入占位密钥 `sk-SENTINEL-DEMO`、一条绝对路径、一条带完整 URL 的错误，生成包后全局搜索，断言零命中。把主观判断变成可回归的断言，是这一类功能唯一可靠的验收方式。

同一原则还体现在审计截断：超量时只校验最近一段，但必须标注 `truncated`。**降级可以，静默降级不行**——接收方要能知道「哪些没看」。

## 三处最初写错的地方

复盘如果只写对的，就只剩宣传。这一版有三处是在实施中被纠正的：

1. **只切了运行的读取点**。工作流的图还被流程工具、MCP 上下文、对外端点、能力健康、会议行动项用到。最初只改运行服务，结果是保存草稿后健康页把流程标成不可运行，而生产明明可用。判定口径只要有一个出口不一致，用户就会怀疑所有状态标记。
2. **同版本快照想保留两份**。一开始想让用户自己选「同版本但内容不同」的那一份，写完列表才发现无法解释：两个同名版本，没有任何判断依据。改成同版本只保留最新内容，代价是那份中间态不可回退，收益是列表始终可解释。
3. **清空过滤没移除地址参数**。开发时手动点着都正常，因为页面状态在内存里；一刷新就回到旧过滤结果。这类问题只有「复制链接、刷新、换标签页」这种真实动作才能测出来，后来补进了验收清单。

## 验收怎么取证

这一版的验收尽量不用「页面看起来对」当证据，而是走三条可复现的路径：

- 技能：升级 → 回退 → 重启 → 用同一个数据根重新扫描，版本与清单一致；
- 工作流：发布一版 → 保存草稿 → 运行仍是生产版 → 切生产 → 草稿不动；
- 诊断包：写入哨兵值 → 生成 → 全局搜索零命中，同时断链场景能正确标注。

三条都写成了端到端用例，而不是单元测试。原因是这些功能的价值全在链路：快照存对了但回退没接上，等于零；下钻链接能点但过滤参数没生效，也等于零。

## 为什么没有顺手加清理入口

保留策略做到五版之后，再加一个「手动删除旧快照」按钮看起来只差一步。没做，有两个原因：删除是不可逆操作，需要单独的确认、占用展示与失败处理；而这一版的主题是「能回退」，清理属于「敢删」，风险方向正好相反。

把它列进后续清单，而不是塞进这个版本，是为了让每个版本的风险方向一致：这一版所有操作都在「回到更安全的状态」，没有一步是永久删除。

## 这些方法论的适用边界

七条里有几条依赖「单机、单写者」这个前提：同卷改名、按目录内容取指纹、直接读生产版本指针，都不需要处理多节点并发。换到多实例部署，原子换位要换成分布式锁与版本协商，快照还要考虑共享存储的延迟。

也有几条是通用的：拒绝发生在副作用之前、错误码带上下一步、白名单组装而不是过滤、只读页面不新增写操作。这四条与部署形态无关，是任何系统都能直接搬的。

## 代价与没做成的事

对这版帮助最大的，是承认它没解决什么：

- 技能快照保留五版、永不删启用版本，但没有手动清理入口，重度用户仍会觉得占盘；
- 单目录超过 50 MB 干脆不建快照，这是明确的降级，不是遗漏；
- 降级与修复只回代码、清单与随包资源，不承诺设置与副作用数据回滚，确认文案里写明了；
- 审计账本能发现中间篡改与断链，整表尾部被截断时剩余链仍自洽，外部锚点只进了待办；
- 诊断包不含密钥、对话与记忆正文、绝对路径与运行 id，因此不能直接复现业务问题；
- 桌面冒烟 10/11，唯一失败项是输入链路的环境相关项，与上一版基线一致——记成已知边界，而不是当成「通过了」。

把这些写进发行说明，比在文档里写「已全部解决」更省事。用户看到边界，才不会在边界上浪费一次排障。

## 数字与对账

- 八个包单测 2842 例通过，其中这一版新增的运维用例覆盖升级回退、草稿隔离、降级与依赖、下钻与诊断包；
- 生产模式 Web 端到端 134/134，包含新增的六条运维场景；
- 数据库变更是纯加法：新增技能版本表、两个版本列，旧库升级与旧版本开库都验证过；
- 收尾时没有新增任何面向用户的新页面，新增的都是已有页面里的入口与区块。

数字不能证明可维护性，但它能证明闸门接进了执行链路。

## 一句话收口

可维护性不是「代码写得漂亮」，而是在出事的时候，你能不能**回到上一版、说清跑的是哪一版、点到那一次运行、把一个脱敏的证据包交出去**。

这四件事做成之后，下一个功能版本才敢放开手脚——因为最坏情况的处理路径，已经不是靠人记着了。
