# 凭证轮换：为什么顺序比实现更难写对

凭证轮换听起来像个体力活：把库里的密文解密、重新加密、写回。真正的难点不在密码学，而在顺序——同样几行代码，先后颠倒一次，就可能留下一批永远解不开的数据。

## 直觉写法为什么是错的

最容易写出来的版本是这样的：

```text
生成新 key 并设为 active → 逐行解密 → 逐行重加密 → 写回
```

它看起来也说得通：新 key 成了 active，重加密就用新 key，旧密文靠 fallback 解密。问题藏在两个地方。

第一，**「哪些行可解密」这个判断被推迟了**。如果某行的密文已经损坏，它在解密阶段就会失败；但在这个顺序里，新 key 已经落盘、active 已经切换。此时这行既没有新密文、也没有被记录，只剩一条谁也不知道的坏数据。

第二，**失败的行需要旧 key 继续可用**。解密失败的行不会被重封装，它的旧密文必须保留；保留的前提是旧 key 还在 keyring 里并且没被裁剪。先换 key 再决定要不要裁剪，等于把「是否需要 fallback」交给运气。

所以顺序要反过来：**先解密全部，再换 key，最后逐行重封装。**

## 五步执行序

整个服务只做五件事，顺序固定：

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 读取所有带密文的 Provider 行 | 没有可做的行，直接返回空结果 |
| 2 | 逐行解密，记录成功与失败 | 失败记为 skipped，不抛出 |
| 3 | 生成新 key、设为 active、原子写 keyring | 抛错，一条 Provider 行都不改 |
| 4 | 对可解密行重加密并写回 | 失败记为 failed，旧密文保留 |
| 5 | 按 failed 数量决定裁剪与旧文件同步 | 裁剪失败只影响下次，解密不受影响 |

第 3 步放在中间是关键。它前面已经有一份完整的「可解密清单」，后面所有写回都以这份清单为准；它本身又是原子的，要么新 keyring 生效，要么完全没变。

## skipped 与 failed：两种失败，两种语义

这两个计数经常被合并成一个「错误数」，但它们的处置完全不同。

- **skipped 是「解不开」**：解密返回空，说明这行密文和当前所有 key 都不匹配。它可能是历史遗留，可能是文件被手工改过。无论原因，这次轮换对它无能为力，跳过即可；它原本就不可用，轮换没有让它变坏。
- **failed 是「换不成」**：解密成功了，但加密或写回失败。这是本次操作引入的问题，行必须保持原状——旧密文不删除、不覆盖，等下一次重试。

区分它们的实际意义在于：skipped 只影响覆盖率，failed 影响结论。前者可以带着往前走，后者必须让整次轮换降级。

```text
plain = decrypt(cipher)         // null → skipped，不参与后续
if (plain === null) continue

next = encrypt(plain)           // 抛错 → failed
update(row, next)               // 写回失败 → failed
```

写回失败时不做任何补偿写，也就是说这行仍然是原来的密文。**「不写」本身就是最可靠的补偿。**

## failed 决定要不要同步旧文件

系统里还留着那份单文件的旧主密钥，它的唯一用途是让只认单文件格式的旧版本仍能解密。轮换结束时是否更新它，取决于 failed 是否为 0。

- `failed > 0`：不同步。因为旧版本读这份文件时只认一把 key，会拿它去解全部行；而那些重封装失败的行仍是用旧 key 封的。若此时把新 key 写进去，这些行在旧版本里会全部解不开——本来只是「这次没换成」，会变成「降级后整个配置不可用」。
- `failed === 0`：同步。所有行都已用新 key 重封装，旧版本用新 key 可以解开全部密文，降级路径完整。

注意这里用的是 failed 而不是 skipped。跳过项无论同步与否都解不开，它不该阻塞降级兼容；若用「总错误数」判断，一条本来就坏的历史数据就能把整次轮换的降级能力一起拖没。

同步失败也不回滚：返回的 `legacyKeySynced` 为 false，但当前版本仍能通过 keyring 解密全部密文，只是回退路径暂时不完整。下次轮换会再试。

## 为什么同步必须放在最后

如果同步提前，最危险的窗口就出现了：旧文件已经指向新 key，但还有行没重封装。此时旧版本启动会认为「所有密文都该用新 key」，把本来可用的行读成不可用。

放在最后还有一个好处：它天然幂等。同步只是把一个 32 字节的 key 原子写到旧文件，重复执行结果相同；即便上一次轮换在同步前崩溃，重启后一切仍由 keyring 解释，不会出现两份真相互相矛盾。

## 崩溃恢复的边界

这套顺序不承诺「轮换一定成功」，只承诺「任何时刻崩溃都不会让可解数据变少」：

- 第 3 步之前崩溃：什么都没换，重跑即可；
- 第 3 步之后、第 4 步中途崩溃：新 key 是 active，旧 key 仍在 fallback 位，新旧密文都能解；
- 第 4 步完成、第 5 步之前崩溃：全部行已是新密文，keyring 里还有 fallback，裁剪可以下次再做。

三种情况都不需要人工修库，重跑一次轮换就会收敛。

## 不可用报 503，写不进报 500

错误分层同样重要。加密能力不可用（例如桌面壳的系统密钥服务没起来）属于「现在做不了」，返回 503，用户重试可能就好了；keyring 写盘失败属于「做了但没做成」，返回 500，而且此时一条 Provider 行都没改——写 keyring 在第 3 步，它在任何行写回之前。

把这两类错误混成一个 500，用户就无法判断该重试还是该修环境。

## 审计只记计数

轮换是破坏性动作，必须留痕；但留痕本身不能变成新的泄露面。

审计事件只写四样东西：mode（Web 还是桌面壳）、rotated、skipped、failed。不写 Provider 名称，不写密文，不写明文，不写 key id。计数足以回答「什么时候、对多少条数据做了什么」，而任何一项多余字段都可能把密钥材料带进一个长期保存、还会被导出归档的账本里。

## 范围与收尾

这次只覆盖 Provider 的 API Key。MCP 配置里的环境变量和请求头是结构化数据，加密列与依赖顺序都要单独设计，不在同一条链路里顺手做。

顺序之所以值得单独写一篇，是因为它几乎无法靠测试兜住：测试可以验证「一次成功轮换」，却很难覆盖「在任意一步崩溃」的所有组合。把顺序设计成「每一步都可中断」，比补一堆异常用例更可靠。
