# 主密钥 keyring：一把钥匙如何变成一串

桌面 AI 应用里有一类数据不属于用户，却必须替他保管：第三方服务的 API Key。它们落库前要加密，加密用的主密钥又落在一个文件里。只有一个文件时，系统非常干净；一旦需要「换锁」，干净就变成了枷锁。

## 单一 master.key 的轮换困境

轮换的本意是让旧密钥失效。可手里的密文全部是用旧密钥封的，换锁的同时必须把每一行密文重新封一遍。这两件事无法在同一瞬间完成：

- 先换 key 再重封装：中途崩溃，剩下的旧密文既没有旧 key 也没有新 key，直接永久丢失；
- 先重封装再换 key：新密文用的还是旧 key，换完之后等于没换。

单文件格式没有第三个位置可以放「第二把钥匙」，所以它天然无法安全地轮换。**这不是实现得不够小心，而是文件结构里没有可回退的中间状态。**

解决办法只有一个：把「一把钥匙」改成「一串钥匙 + 一个指针」。

## keyring：用指针描述「谁是当前钥匙」

keyring 是一个 JSON 文件，核心只有两件事：当前用哪把钥匙（active），以及系统认识的全部钥匙。

```text
{
  formatVersion: 1,
  activeKeyId: "k-...",
  keys: [
    { id, key: base64(32 字节), createdAt, retiredAt }
  ]
}
```

约定很硬：

- **加密永远只用 active key**，不随机挑、不按行分散；
- **解密按 active → 其余 key 逐个尝试**，任一成功即返回，全部失败才认为密文不可解；
- 单把 key 固定 32 字节，base64 落盘；
- 最多 3 把，即 active 加两个 fallback。

「最多 3 把」是刻意的上限。保留全部历史 key，文件就变成永久密钥仓库，丢一次等于永久泄露；只保留 1 把，轮换失败后没有任何退路。3 把刚好覆盖「正在用」「刚退役」「上一轮失败留下的」三种状态。

## 旧 master.key 不是被删掉，而是被读进来

升级时磁盘上已有的还是那个 32 字节 raw 文件。格式迁移有两条路：一次性转换，或者并存读取。我们选后者。

启动逻辑按存在性分三种：

1. keyring 文件存在 → 直接解析，它就是唯一真源；
2. keyring 不存在、旧 master.key 存在 → 把旧文件读成一把 id 为 `legacy` 的 key，作为 active；
3. 两者都不存在 → 生成新 key，同时写 keyring 和旧文件。

第二种情况不立刻落盘改写。原因很简单：**读兼容不应该带来写风险**。第一次真正轮换时新 keyring 才写入，旧文件在那之前保持原样。这样即使新代码有 bug，旧文件仍是完好的。

解析侧也做了防御：`formatVersion` 必须是 1，`activeKeyId` 必须存在于 `keys` 中，key id 不许重复，每把 key 解出来必须正好 32 字节。任何一条不满足就抛错，而不是「尽量恢复」——密钥文件被猜着修，比直接拒绝启动危险得多。

## 原子写：临时文件加 rename

keyring 是单点真相，写坏一次等于全部密文报废。因此所有写入都走同一个动作：

```text
写 <file>.<pid>.<timestamp>.tmp（mode 0600）
→ chmod 0600
→ rename(tmp, file)
→ 失败则 unlink(tmp) 后抛错
```

三处细节值得解释：

- **rename 在同一文件系统内是原子的**，读方要么看到旧文件，要么看到新文件，不会读到半截 JSON；
- **临时文件名带 pid 和时间戳**，避免两个进程同时写时互相覆盖临时文件；
- **权限在创建时就设 0600**，而不是写完再 chmod，缩短密钥短暂可读的窗口。

失败路径要删临时文件，否则崩溃几次之后目录里会堆满没人认识的 `.tmp`。

## 轮换与裁剪：什么时候可以只留两把

轮换分两步，而且顺序不能靠自觉：

1. 生成新 key，加入 keyring 并设为 active，原子写盘；旧 active 自动降级为 fallback；
2. 全部密文重封装成功后，把 keyring 裁剪到 active + previous。

第 1 步写完的那一刻，磁盘上同时有新旧两把 key，任何一条旧密文都还能解开——这就是整个方案的安全垫。第 2 步的裁剪只在「干净轮换」时执行：如果还有行没换成功，它们的密文仍需要旧 key，裁剪就等于把它们变成永久垃圾。

所以裁剪携带的参数不是「轮换了几次」，而是「这一次是否全部成功」。失败时保留 fallback，下一次轮换再试。

## 桌面壳：只重封装，不换系统密钥

Web 端的主密钥由我们自己生成，桌面壳不是。它用的是操作系统提供的 safeStorage，系统密钥由 OS 管理，应用没有生成、替换或读取它的能力。

因此桌面端的「轮换」只有一个含义：把可解密的密文读出来，用同一个系统密钥重新加密封回去。它能换掉的是密文形态，不是密钥本身。

这不是能力不足的委婉说法，而是必须写进文案的事实：按钮叫「重新加密已存凭证」，不叫「更换系统密钥」。用户以为系统密钥被换掉，比什么都没换更糟。

## 收尾

keyring 解决的从来不是「怎么加密」，而是「换锁时旧锁还能不能开最后一次门」。指针、fallback、原子写、裁剪条件，四件事合起来才让轮换变成一个可中断、可重试、可回退的动作。下一篇把执行顺序摊开：为什么必须先把所有行解密，以及失败计数为什么决定要不要同步旧文件。
