# 区间归档：全量 JSONL 撞上的三堵墙，以及一个 ZIP 该装什么

审计账本是一条哈希链：每条事件带自增序号与哈希，后一条把前一条的哈希纳入自己的摘要。这条链能回答「账本内部有没有被改」。但它回答不了另一个更现实的问题——**怎么把某段时间的证据交出去，让对方能自己验证**。

最初的答案是「全量导出 JSONL」：把整张表一行一条吐出来。短账本时它很好用，账本长起来之后就会撞墙。

## 三堵墙

| 墙 | 表现 | 性质 |
|---|---|---|
| 体积无上限 | 文件随使用时长线性膨胀，一次导出可能几百 MB | 性能 |
| 没有边界 | 收件方拿到文件，不知道它覆盖哪一段、截止到哪一刻 | 语义 |
| 无法回答「之后有没有被删」 | 文件只含内容，不含生成时的账本位置 | 语义 |

前一条靠压缩能缓解，后两条不能。**一个不带边界的证据文件，天然是不可验证的**：你无法区分「导出时账本就只有这么多」和「导出之后被删掉了」。

所以目标不是「把数据倒出来」，而是「导出一次能自证的切片」。

## 一次切片应当自证四件事

- 覆盖哪段时间：起止时刻，且必须是带时区的 ISO 时刻；
- 有多少条：一个可被重新计数的整数；
- 首尾是谁：首条序号、末条序号、末条哈希；
- 生成那一刻账本停在哪：这一项来自区间之外，对应的是「位置对不对」。

前三项由区间自身给出，第四项必须由区间之外的视角提供，两者合起来才构成一次完整的取证。

## 筛选用 created_at，排序必须用 seq

区间语义定为 `created_at` 闭区间：`>= from` 且 `<= to`，两端都含。用户选的是时间而不是序号，闭区间比左闭右开更符合直觉，也便于「导出这一整天」。

但 SQL 的排序不能跟着走：

```text
SELECT ... FROM audit_events
WHERE created_at >= :from AND created_at <= :to AND seq > :afterSeq
ORDER BY seq ASC
LIMIT 1000
```

`created_at` 只做筛选，排序固定用 `seq`。理由有三条：同一毫秒可能写入多条事件，时间不唯一；系统时钟回拨会让时间序与写入序背离；而序号由账本自己单调分配，按序号排出的顺序才与哈希链完全一致。

顺序一致很关键——JSONL 要被逐行重放校验，一旦行序与链序错位，校验必然失败，而且失败原因会指向「有人动了数据」，属于假警报。

分页用序号游标而不是 `OFFSET`：每批 1000 条，取最后一条的序号作为下一批的下界，末批不足 1000 条即结束。`OFFSET` 在大表上越翻越慢，游标分页的成本则与页数无关。

## 三级闸门：能提前拒绝的，别读完再拒绝

| 闸门 | 阈值 | 判定时机 | 失败 |
|---|---|---|---|
| 区间跨度 | ≤ 366 天 | 解析参数后、查库前 | 422，`reason: range` |
| 事件条数 | ≤ 50,000 | 计数后、读取前 | 422，`reason: events` + 实际条数 |
| ZIP 体积 | ≤ 20 MB | 打包完成、响应前 | 422，`reason: zip` |

三级的顺序不是随手排的：前两级都能在付出读取成本之前拒绝；第三级只有把 ZIP 拼出来才知道大小，所以它天然是最后一道闸。

三处都返回同一个错误码，但 `details` 里带 `reason` 与实测值。这样 web 端可以直接说「你选的区间有 61,204 条，超过 5 万条上限」，而不是丢一句「导出失败」。**结构化报错的收益不在机器读，而在人能看懂下一步该改什么**：改时间范围、改筛选条件，还是接受「这一版就是导不出这么大」。

不做静默截断。截断后的归档比没有归档更危险——它看起来是完整的。

## yazl 只负责打包

打包用 `yazl`：一个纯写入的 ZIP 库，两个动作就够——按顺序 `addBuffer` 添加条目，`end()` 之后从 `outputStream` 拿数据。

这里的取舍要说清楚：**这是内存组装，不是流式落盘**。条目内容、ZIP 字节都在内存里成型，收集完 chunk 拼成一个 Buffer，量一次长度，作为响应体返回。

之所以敢这么做，是因为前面两道闸已经把峰值钉死了：条数上限与体积上限。代价是超过 20 MB 的区间没有 Zip64 或临时文件兜底——如果未来放宽上限，这里必须改成「写临时文件、边压边发」，否则内存峰值会跟着上限一起长。

`yazl` 的价值在于依赖少、条目顺序可控、`outputStream` 是标准 Node 流，错误能顺着流冒出来。换 `archiver` 也能做，但要为一份只有两个条目的归档引入一棵更深的依赖树，不值。

## ZIP 里为什么只有两个文件

| 文件 | 形态 | 用途 |
|---|---|---|
| `events.jsonl` | 一行一条，键序规范化 | 机器重放、逐条比对 |
| `anchor.json` | 两空格缩进 | 人可读，用户能直接选中它做校验 |

JSONL 每行都过一遍规范化序列化：键按固定顺序排、无多余空白。收益很实在——同一条事件在两个时刻导出，字节完全一致，两次归档可以直接 `diff`；否则键序抖动会让差异视图全是噪声。

`anchor.json` 反过来不做紧凑化。它是给人看的，也是给人从文件管理器里选中上传的，两空格缩进让「这一版到底覆盖到哪」肉眼可见。

文件名带本地时间戳到秒，避免多次导出在下载目录里互相覆盖。

## 只读导出，不是洁癖

归档不写审计事件，也不删账本。这不是「尽量别动数据」的谨慎，而是正确性要求。

如果导出本身写一条审计事件，而这条事件的 `created_at` 落在导出区间内，那么这份归档**永远无法通过它自己的校验**——区间计数多一条，区间尾也换了。证据在生成那一刻就自相矛盾。

同理，导出也不做自动清理：清理会改变账本尾，让已经发出的锚点立刻失效。保留策略是另一个动作，需要显式触发、单独留痕。

## 空区间也是有效证据

区间内没有事件时，归档依然成立：`count = 0`，`firstSeq / lastSeq / lastHash` 全为 `null`。

但另外两块不能空：`chain` 仍记录生成时的全账本链校验结果，`ledger` 仍记录全账本尾。这让「这一段时间确实没有事件，而账本当时到 3,214 条」成为一句可验证的陈述，而不是一份空文件。

## 怎么证明它是对的

- 正常区间：JSONL 行数、首尾序号、锚点字段与库内数据一一对上；
- 空区间：计数为 0，链与全账本尾仍有值；
- 两道闸：事件超限、区间超限都得到同一个错误码，但 `reason` 不同；
- 尾删 / 篡改：先删尾再校验得到「尾部缺失」，改一行哈希得到「哈希错位」；
- 断链与空账本：空账本锚点在后续追加事件之后仍然通过；
- 只读性：导出前后账本条数不变，也没有新增事件。

## 收口

全量 JSONL 的问题不是「文件太大」，而是「它不携带自己的边界与位置」。区间归档把这两件事补上：用闭区间定义范围，用序号定义顺序，用三级闸门把不可预期的输入挡在门外，用两个文件把「内容」和「位置」分开装。

而「位置」这一半靠的是锚点里那个不显眼的全账本尾——它才是让整份归档立得住的东西。
