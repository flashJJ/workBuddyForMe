# 工作流版本对比：先定义「什么算同一个东西」，再谈 diff

工作流编辑器里，一版图就是一段 JSON。想回答「这一版和已发布的那一版差在哪」，最直接的做法是把两份 JSON 丢进一个通用 diff 工具——然后你会得到一屏几乎全是噪音的结果：节点数组顺序变了、坐标动了、连线对象的 id 换了、画布缩放平移了。

这类噪音有一个致命的副作用：**用户会学会忽略整个差异面板**。当一个提示总是有 90% 的无关内容，剩下 10% 的真变化也就没人看了。

所以这个功能的起点不是「怎么写比较算法」，而是「哪些字段能代表一次真实的改动」。身份定义清楚了，算法只剩几十行。

## 差异结果里应该只有六个数

我们把差异收敛成六个计数：

| 分组 | 含义 |
|---|---|
| 节点新增 | 目标版有、基准版没有的节点 |
| 节点删除 | 基准版有、目标版没有的节点 |
| 节点类型变化 | 同一 id，执行类型变了 |
| 节点配置变化 | 同一 id、同类型，配置的键变了 |
| 边新增 | 目标版多了的连线 |
| 边删除 | 目标版少了连线 |

六个数之和为 0，就是「没有差异」。这个判据很省事：界面不必再逐个分组判断空态，服务端也不必返回整张图让前端自己算。

## 节点身份只能是 id

节点的可比身份有三个候选，其中两个是陷阱：

- **数组下标**：中间插一个节点，后面所有下标平移，会报出一串「删除 + 新增」；
- **显示名称**：用户把节点改个名字，业务上什么都没变，却会被误判为一次删除加一次新增；
- **节点 id**：编辑器里就存在、跨版本稳定、复制节点会拿到新 id（这恰好符合直觉：复制出来的是新节点）。

所以按 id 建映射，再逐个对齐。**id 缺席就是新增或删除，不做任何模糊匹配**——按类型和名字去猜「这两个节点是不是同一个」，在图上只会产生更难解释的结果。

## 类型变了，就不要再比配置

一个 id 的类型从 A 换成 B，它的配置结构通常完全换了一套：A 的键消失，B 的键出现。如果继续按键比较，会得到一份「删了五个键、加了六个键」的清单，用户看完仍然不知道发生了什么。

规则是：**类型变化优先，命中后跳过配置比较**，只报一条「A → B」。两类差异互斥，不是靠界面去合并，而是比较逻辑本身就不产生重复。

## 配置只比顶层键，用 canonical 判等

配置是自由形状的对象，嵌套多深都有可能。这一版只比较顶层键，但值用 canonical 序列化后判等：

```text
keys = union(before.config, after.config)
for key in keys:
    if key 只在一边存在            -> 记入变化
    if canonical(before[key]) != canonical(after[key]) -> 记入变化
返回按字母升序排列的 keys
```

canonical 的含义是「键顺序、空白、等价写法都不参与判等」。于是 `{a:1,b:2}` 与 `{b:2,a:1}` 不算变化，一个格式化动作不会制造差异。

反过来，嵌套对象内部改了一个字段，会命中它所属的那个顶层键，但**不展开子键**。这是明确的边界：告诉你「这个节点的 `model` 配置变了」，不告诉你变的是 `model.temperature`。

## 边的身份是 source → target → handle

连线对象自己也有 id，但 id 是渲染层的对象标识：复制粘贴、重新连线、前端重新挂载都可能换一个新 id，而拓扑一点没变。以 id 作身份，一次「把同一条线重画一遍」就会被报成删一条、加一条。

真正的语义身份是三个字段：

```text
edgeKey = source + "\0" + target + "\0" + (sourceHandle ?? "")
```

- **source / target**：连的是哪两个节点；
- **sourceHandle**：从源节点的哪个输出口出来。同一对节点可以有多条边，分别接不同分支，handle 不同就是不同语义；
- **空 handle 统一记成 `null`**：老数据里可能没这个字段，缺失与显式 null 必须判等，否则一次「补字段」会引发全图差异。

handle 变化被处理成「旧边删除 + 新边新增」，而不是「边被修改」。这和图引擎执行时的行为是一致的：改输出口等于换了一条路由，没有「同一条边改了口」这种东西。

分隔符用 `\0` 而不是冒号或箭头，是为了避免拼接歧义：`a` + `bc` 和 `ab` + `c` 在字符串拼接下会撞成同一个键，而节点 id 是用户可控的文本。

## 布局字段不参与比较

节点坐标、画布 viewport 都是视图状态。拖动一下、窗口尺寸变化、执行一次自动布局，业务语义一个字没改。

把它们排除在 diff 之外，代价是「只调排版」的改动看不见。这个代价可以接受：**排版不是可执行语义**，评审要看的是执行会变成什么样，而不是节点摆在哪。

## 稳定排序：让同一输入永远得到同一份输出

所有分组都按 id 或边键升序排列；请求里的基准、目标版本号只用于回显，不参与排序。

稳定性带来三个好处：单元测试可以做全等断言而不是「长度相等」；界面重复点按钮不会看到顺序乱跳；将来若要把差异存成快照做前后比对，也能直接逐字节比。

## 接口是一个只读的窄接口

```text
GET /api/flows/:id/versions/compare?from=<版本号>&to=<版本号>
```

- 两个参数由 schema 强转成正整数，缺参或非数字统一 422；
- 工作流不存在 404，任一版本不存在 404 并带独立业务码；
- 只返回差异摘要，不返回两张完整图；
- 全程只调用读取方法：不写审计、不改当前版本、不动生产版本指针。

不返回整张图是有意的：摘要体积小、语义明确，前端不需要再实现第二套比较逻辑，也就不会出现「界面算出来和服务端不一致」这种只能靠人眼发现的分歧。

## 怎么验证它没有骗人

单元测试覆盖的是口径本身：类型变化与配置变化互斥、键只在一边存在也算变化、handle 变化报成删加增、只改 edge id 与拖动坐标得到全零、同一版本对比全零。

端到端则造一组「每类差异都非空」的图：基准版发布、目标版保存，目标版新增一个模型节点、改掉结束节点的输出配置、把两条连线换向。断言六个数分别是 1 / 0 / 0 / 1 / 2 / 1，并且界面分组里能看到节点 id 与变化的键名。

## 已知边界

- 只到配置顶层键，不做字段级文本 diff，也不做行级高亮；
- 看不到纯排版调整；
- 不比较节点在数组中的顺序（顺序不是执行语义）；
- 差异是摘要，不包含「配置值改成了什么」，要看具体值得打开对应版本。

这些边界都写进了发行说明。用户知道差异面板不回答什么，就不会拿它当代码评审工具用。

## 一句话

工作流 diff 的难点不在于比较本身，而在于**先替「同一个节点」「同一条边」「同一个版本」给出可验证的定义**。定义站得住，算法就是一层薄薄的集合运算；定义站不住，再聪明的相似度匹配也只是把噪音换了个说法。
