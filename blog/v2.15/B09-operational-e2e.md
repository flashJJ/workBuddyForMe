# 运维动作怎么端到端验证：五条用例覆盖四类操作

功能测试有一条清晰的主路径：打开页面、点按钮、看结果。运维类动作没有这条路径——它们都发生在「已经有数据之后」，价值又在「出错那一刻」，而失败分支比成功分支多得多。

这一版要验证四类动作：删掉不再需要的技能旧版本、把审计账本按区间归档并留下可校验的锚点、轮换落库的供应商凭证、对比两个工作流版本。它们各自有 409、422、只读约束、掩码展示这些细节，靠手点一遍既不可重复，也覆盖不全。

下面是把它们压进五条端到端用例的做法，以及一个真实的发版坑。

## 四类动作与五条用例的映射

| 用例 | 覆盖的动作 | 关键断言 |
|---|---|---|
| ① | 技能版本占用与删除 | 两版并存、占用下降、启用版本与重复删除被拒 |
| ② | 审计区间归档 | ZIP 内两个文件、区间计数与行数一致、双锚点齐全 |
| ②b | 锚点校验 | 通过 / 尾部截断 / 区间错位 / 断链 / 非法格式，以及界面校验 |
| ③ | 供应商凭证轮换 | 计数不丢项、无失败项、掩码不变、界面入口可用 |
| ④ | 工作流版本对比 | 六项差异准确、同版全零、缺失版本 404、对比后版本状态不变 |

归档拆成两例不是凑数：生成失败通常是参数或数据问题，校验失败则是锚点或账本问题，混在一起失败时每次都要重跑才能分辨。

## 技能清理：造一个真的包，而不是 mock 一个目录

安装链路要校验清单、校验和、入口路径，所以测试不能伪造目录，必须在内存里拼一个合法 ZIP：

- 外层清单：id、版本、类型、入口、依赖、以及每个 payload 文件的 sha256；
- `payload/skill.json`：技能名、版本、权限、提示词模板；
- 用纯 JavaScript 的 zip 库在内存里打包，直接作为 multipart 上传。

先装 1.0.0，再升级到 2.0.0，磁盘上就有了两版，其中 2.0.0 是启用版本。随后要断言的顺序很有讲究：

1. 接口层先读版本列表：两版都在、启用的是新版本、总占用大于 0；
2. 界面层看面板：显示「共 2 版」、新版本行没有删除按钮、有「当前版本」标记；
3. 点删除旧版本，看到成功提示，列表里旧版本消失；
4. **再请求一次接口，确认总占用真的下降**。

第 4 步是这条用例的核心。只看界面无法区分两种情况：后端真的删了文件，还是前端只是从缓存列表里移掉了一行。占用数字是磁盘事实的投影，它变了才说明清理真的发生了。

拒绝路径同样要断言到业务码，而不是只断言「请求失败」：删除启用版本 409 且码为「启用中」，重复删除同一个已删版本 409 且码为「不存在」。两个 409 的用户动作完全不同，码混在一起文案就无法生成。

最后删掉自己安装的能力包，避免污染后续用例和本地数据目录。

## 归档与锚点：两个文件、两个尾巴

归档产物是一个 ZIP，里面只有两样东西：按时间升序的 `events.jsonl`，和一份 `anchor.json`。

断言四件事：

- `events.jsonl` 非空，区间计数等于它的行数；
- 锚点里同时有区间尾（最后一条的序号与哈希）和全账本尾；
- 锚点带格式版本与数据库版本字段；
- 响应确实是 ZIP，文件名带时间戳。

锚点的作用是把「这一天的账本长这样」固定下来，之后随时可以拿它回来对一遍。所以它必须同时记录两个尾：**区间尾**证明导出时这一段是完整的，**全账本尾**证明之后没有整段被截掉。

四态校验全部由测试自己构造，不依赖真实事故：

```text
把 ledger.lastSeq 抬高      -> 账本尾部被截断
把 range.lastHash 改一个字符 -> 区间内容与锚点不符
把 chain.ok 置为 false       -> 生成时链已断
提交一个空对象               -> 请求体非法，返回 422
```

每一条都断言业务码，而不是「返回不成功」。四种情况对应的处置完全不同：前两种说明有人动过账本，第三种说明数据在生成时就已损坏，第四种只是调用方写错了。

这里有一个真踩过的坑：**打开审计页时的链校验会往账本里写一条验证事件**。如果先归档、再打开页面、然后用那份锚点去做界面校验，区间计数必然对不上，用例会得到一条假失败。

正确顺序是：打开页面 → 等链校验落账 → 重新归档生成一份新锚点 → 把它喂给页面。这个顺序本身也说明了一件事：会写数据的「校验」不能当证据用，能当证据的是它落账之后的账本状态。

用例还要顺手验一下下载：点导出按钮，等待下载事件，断言文件名符合约定格式，并看到「已开始下载」的提示。下载链路和接口链路是两条代码路径。

## 轮换：用掩码证明「还能解密」

轮换的断言不是「接口返回成功」，而是四个计数加上一个可观察结果：

- 模式是 Web 端；
- 至少重封装了一条；
- 失败数为 0；
- 再读供应商列表，掩码里的尾四位没变。

为什么用掩码而不是解密后的明文：**掩码不变就是「仍能正确解密」的可观察证据**，而把明文写进断言，等于把密钥复制进测试代码、日志和 CI 输出，这比功能缺陷更严重。

界面层补一条：进入设置页，找到轮换区块，点按钮、确认，看到「已重新加密 N 个凭证」的提示。这条用例只证明入口通着，真正的语义由接口断言负责。

## 对比：只读这件事必须被断言

只读不能靠「我代码里没写 update」来保证，得有可复现的证据：

```text
第一次读详情   -> currentVersion=2, publishedVersion=1
执行对比
第二次读详情   -> 仍然是 2 和 1
```

前后完全一致。再加上同版对比六项全零、缺失版本 404 且带业务码，以及界面版本抽屉能展开并渲染出差异分组。

数据也要造得让每个分组都非空：新增一个节点、改掉一个配置值、把两条连线换向。否则某一条分组即使实现错了，也会因为空数组相等而通过。

## 一个真实的发版坑：把时间写进断言

上一版的运维用例里有一处断言写死了当时的应用版本号（诊断包里的版本字段）。新版本一打包，这条断言立刻变红，主分支流水线失败，看起来像应用坏了，实际只是测试把「当前版本」当成了常量。

修法是把字面值换成 semver 正则：断言这个字段是「三段数字的形状」，而不是「等于某个具体数字」。应用代码一行没动，已构建的产物也不受影响。

推广一下：门禁里任何写死的「当前值」都是定时炸弹——当前版本号、当前数据库版本、当前日期、当前条数。**断言形状，不要断言快照**。

## 自己写数据，自己清理

这五条用例之间有依赖，所以按串行执行：前一条产出的锚点交给后一条用。

- 开始时把首次使用向导标记为已完成，避免每条用例都被弹窗打断；
- 下载文件写到用例自己的输出目录，不落在仓库里；
- 每条用例结束都删掉自己创建的能力包、供应商、工作流；
- 断言尽量写成「状态码 + 业务码」，而不是 `!ok` 这种模糊判断。

自己造、自己删，换来的是这套用例可以在任何一台干净的机器上重复执行，也可以在本地数据目录里反复跑而不累积垃圾。

## 没能覆盖的那一格

「删除唯一剩余版本」的保护没有进端到端。原因是：用例里唯一剩下的版本必然是启用版本，请求会先命中「启用中保护」，永远走不到「最后一份」那个分支。这一格只能由单元测试直接构造状态来覆盖，端到端断言不了。

这不丢人，写进说明就行。**知道哪一格没测，比假装全绿安全得多。**

## 收口

五条用例不是「多打了几个接口」，而是把四个动作的三种形态——成功、被拒绝、不降级——钉在一条可重复执行的链路上。运维功能的可信度，就来自这条链每次都能重跑。
