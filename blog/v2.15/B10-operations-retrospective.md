# 可运营复盘：把一次性手工操作，变成可重复执行的动作

这一版没有新功能面。四件事——清理不再需要的技能旧版本、给审计账本留可校验的锚点、轮换落库的供应商凭证、对比两个工作流版本——都是用户本来就该做、以前只能「手工做一次」的动作。

所以这一版真正的交付物不是四个按钮，而是另一种判断标准：**不是「能不能做」，而是「能不能重复做、拒绝时说清为什么、失败时知不知道」**。

下面七条，是这一版真正带走的东西，每条配一个这次的真实例子。

## 一、零迁移优先：把兼容变成一个可验证的问题

四件事全部复用已有的表和字段，只补查询与删除方法，数据库版本号一个都不动。唯一的形态变化是主密钥从单个文件升级成 keyring 文件，做法是「新格式 + 旧文件保留作为降级路径」，并且只有在全部重封装成功时才同步旧文件。

判据只有两条，都必须能被实测：

- 新版本打开旧库，直接可用；
- 旧版本打开新库，忽略它不认识的新审计类型和新文件，且不删除任何数据。

零迁移的收益不在发版当天，在回滚当天。一旦动了 schema，回退就从「装回旧包」变成「先恢复备份、再确认版本」，而备份恰恰是用户最常忘的那一步。

## 二、只读校验不能污染它要取证的对象

锚点校验全程只读：不写「已校验」事件、不改账本、不落库。版本对比同理，只调读取方法，不碰当前版本与生产版本指针。

这条原则有一个很能说明问题的反例：常规的账本链校验会顺手写一条校验结果事件。于是端到端用例里必须先让页面把这条事件落账，再重新生成锚点，否则区间计数立刻失配，得到一条完全假的失败。

**一个会改变被检查对象的检查，不能再被当作证据。**

## 三、失败要计数，降级要显式

凭证轮换返回四个数：总数、已重封装、跳过、失败。语义必须先定清楚：

- 解不开的行算「跳过」，原密文仍然可用，不阻塞其他行；
- 写不回去的行算「失败」，保留旧密文，绝不留下半截新密文；
- 只有失败数为 0，才同步旧密钥文件做收尾。

顺序也是固定的：先解密全部 → 原子写新 keyring → 逐行重封装 → 成功才收尾。反过来先写后读，就把「随时能回滚」变成了「只能祈祷别崩」。

同一原则出现在归档上：超过区间上限时明确标记「已截断」，而不是悄悄少导出几条。**降级可以，静默降级不行**——接收方必须知道哪些没看。

## 四、跨状态行的数据，按业务身份处理

技能占用统计最容易错的地方，是同一个版本可能有多条状态行共享同一个目录。如果按行求和，一个版本会被重复计数，占用数字直接翻倍。

做法是每个版本先取一行代表（优先当前状态行），只对代表行求和。删除时也不是删一行，而是按「名称 + 版本」覆盖全部状态行；目录再做引用计数，归零才真正删盘。

这条规则背后的判断是：**用户眼里的「一个版本」是业务身份，不是数据库主键**。按主键处理，升级一次历史就断一次，占用统计也会随状态行数量漂移。

拒绝也要分层：启用中、唯一剩余、目标不存在、参数非法，各自一个业务码。四类拒绝让用户做的事完全不同，合并成一句「操作失败」等于把排查成本推给用户。

## 五、门禁要版本无关

上一版的运维用例里，有一处断言把当时的应用版本号写死了。新版本打包当天，主分支流水线变红，看起来像应用坏了，实际只是测试把时间钉在了过去。

修法一句话：把字面值换成 semver 正则，断言「三段数字的形状」而不是「等于某个数」。应用代码没改，已构建的产物也不受影响。

推论可以更宽一点：门禁里任何写死的「当前值」都是定时炸弹——当前版本号、数据库版本、日期、条数、文件大小。**断言形状，不要断言快照。**

## 六、安全语义不夸大

这一版有三处刻意写得保守：

- 桌面壳的凭证重封装只重新加密密文，不更换系统密钥。文案里不写「更换系统密钥」，因为那不是事实；
- Web 端 keyring 最多保留三把，正常轮换后裁剪到「当前 + 上一把」，而不是无限堆积；
- 这一轮只覆盖供应商 API Key，其他位置的凭证留到后续，不假装一次做全。

夸大安全能力的代价比不宣传更大：用户会按错误的前提做决策，比如以为换过系统密钥就可以放心导出旧备份。**写清楚的边界本身就是安全能力的一部分。**

## 七、测试要自己造证据，也要自己收场

这版的运维用例没有等真实事故来造状态，而是全部自己构造：

- 在内存里拼一个合法的技能包 ZIP（清单 + payload + 校验和），装旧版、升新版，得到两版真实快照；
- 分别篡改锚点的账本尾、区间哈希、链状态，外加一个空请求体，覆盖四种业务码；
- 删除后重新请求接口验证占用下降，而不是只看界面列表少了一行；
- 对比前后各读一次详情，用「版本号没变」证明只读。

配套的是自律：每条用例结尾删掉自己创建的能力包、供应商、工作流，下载文件写到用例自己的输出目录。**测试留下的垃圾，最后都会变成下一次调试时的干扰。**

## 三处写的时候被纠正的地方

复盘如果只写对的，就只剩宣传。这一版有三处是在实施中被改掉的：

1. **锚点一开始想落库**。落库看起来更「正式」，但锚点存在的意义是账本之外的独立副本，落库等于账本给自己盖章。最后只存文件。
2. **对比一开始想打开抽屉就请求**。这样每次打开版本历史都会拉一次差异，用户还没决定要看哪两版。改成点击「开始对比」才发请求，默认基准是「已发布版本 ?? 当前版本」。
3. **归档与校验原本想放一条用例**。合并后一旦失败，无法分辨是生成错了还是校验错了，重跑一次才能定位。拆成两例。

## 代价与没做成的事

- 删除不可逆，只提供逐条删除，不提供恢复。审计只留痕，不负责还原；
- 归档有区间与体积上限，账本本身不自动清理；
- 差异只到配置顶层键，没有字段级高亮；
- 桌面冒烟的输入链路仍有一项环境相关的失败，与上一版基线一致。我们把它记成已知边界，而不是算进「通过」。

把这些写进发行说明，比在文档里写「已全部解决」省事得多。用户看到边界，才不会在边界上浪费一次排障。

## 数字

- 八个包的单测规模与上一版持平，没有为了新功能削减覆盖；
- 生产模式的 Web 端到端全绿，其中新增的运维用例正好五条；
- 数据库版本号不变，旧库直接可开；
- 桌面冒烟与上一版基线一致，唯一失败项是环境相关。

数字证明不了「可运营」，但它能证明闸门确实接进了执行链路。

## 一句话收口

可运营的标志不是多了几个入口，而是每个动作都具备四件事：**可预判的拒绝、可读的失败计数、可回归的用例、写进说明的边界**。

这四件事凑齐之后，下一个功能版本才敢放开手脚——因为「历史怎么清、证据怎么留、凭证怎么换、版本怎么比」这些日常动作，已经不再依赖人记住步骤了。
