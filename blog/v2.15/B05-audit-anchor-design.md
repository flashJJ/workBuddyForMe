# 锚点为什么要记两个尾：截断、错位与断链的判别顺序

审计账本是一条哈希链：每条事件带序号与哈希，后一条把前一条的哈希纳入自己的摘要。链能证明「账本内部没被改」，但证明不了「导出之后没人从末尾砍掉一段」。

为了补这一刀，区间归档会在 ZIP 里放一份 `anchor.json`——一份脱离数据库、可以单独传递的外部锚点。这一篇讲它的字段设计：为什么必须记两个尾，四种结果怎么排，以及为什么校验本身不写账本。

## 只记区间尾，漏掉哪一种事故

设想导出上半年的归档，区间尾是 `seq = 1200`、`hash = A`，区间计数 1200。

后来有人把账本从 `seq = 3001` 之后整段删掉，账本只剩 3000 条。此时重新校验：

- 区间内 1200 条还在；
- `seq = 1200` 的哈希还是 `A`；
- 重新计数还是 1200。

**全部通过。** 被删掉的那 1800 条一条都没落进区间，所以区间尾对它一无所知。

问题的形状就在这里：**区间尾只能证明「这一段还在」，证明不了「这一段之后没被砍掉」**。它给出的是下界，而事故发生在边界之外。

## 双尾的分工

| 字段 | 证明什么 | 失效于 |
|---|---|---|
| `range.lastHash` | 区间末条内容未被改写 | 区间之外的删除 |
| `range.count` | 区间条数未被抽走 | 同上 |
| `ledger.lastSeq` | 生成那一刻账本的最远位置 | 单独看会被「正常追加」混淆 |
| `ledger.lastHash` | 那个位置上的内容未被替换 | 中间挖洞要配合按序号取行 |

区间这几项给出「内容下界」，全账本尾给出「位置上界」。合起来才能判定：上界之前的账本，现在还在不在。

## 「更长」是正常的，不能报错

全账本尾是**生成时**的快照，不是校验时的当前值。校验往往发生在几天后，账本一直在追加，当前尾几乎必然比锚点尾更大。

正确的写法只有一句：**只在当前尾短于锚点尾时报截断**。更长是追加，追加不是反证。若写成「长度必须相等」，正常校验每次都会失败；若写成「逐行全等」，成本就退化成全量重算，锚点也就失去了意义。

落到实现上是两次按序号取行：先看当前尾的序号是否小于锚点尾，不短就按序号取锚点尾那一行、比对哈希。取不到行（中间被挖掉）或哈希不等，都归「哈希错位」。

## 四种结果，与不能调换的顺序

| 结果 | 含义 | 触发条件 |
|---|---|---|
| 通过 | 锚点与当前账本一致 | 其余情况 |
| 尾部缺失 | 当前账本尾短于锚点尾，或账本已空 | 序号比较 |
| 哈希错位 | 锚点位置那一行不存在或哈希不等；区间计数不符 | 按序号取行 |
| 链已断 | 生成锚点时全账本链校验就已经失败 | 锚点内记录的链状态 |

判定顺序固定，每一步只在前面没结论时才继续：

```ts
// 1) 全账本尾：最便宜，覆盖面最大
if (anchor.ledger.lastSeq !== null) {
  if (tail === null || tail.seq < anchor.ledger.lastSeq) return TAIL_TRUNCATED;
  if (rowAt(anchor.ledger.lastSeq)?.hash !== anchor.ledger.lastHash) return MISMATCH;
}
// 2) 区间：更细的内容比对
if (anchor.range.count > 0) {
  if (countRange(from, to) !== anchor.range.count) return MISMATCH;
  if (rowAt(anchor.range.lastSeq)?.hash !== anchor.range.lastHash) return MISMATCH;
}
// 3) 生成时的链状态：最后兜底
if (!anchor.range.chain.ok) return CHAIN_BROKEN;
return OK;
```

为什么是这个顺序：

- 全账本尾只用两次单行查询，却能最先发现「整段消失」这种面积最大的事故；
- 区间比对更细，但只在账本尾没问题时才有意义——尾都没了，区间比对再多也只是重复同一个结论；
- 链状态放最后，因为它是生成时的事实，不随当前账本变化；当前账本若能给出更具体的结论（少了哪一段、哪一行被换），就不该被一句笼统的「当时链就断了」盖掉。

反过来排（先区间、再链、最后全账本尾）会带来一种典型误判：尾段被整段删除时区间完好，前两步全部通过，最后才报截断。结论是对的，排查路径却绕了一大圈。

## 空账本锚点：一个例外，不是漏洞

锚点生成时账本为空：`ledger.lastSeq` 为 `null`，`range.count` 为 0。

之后账本开始有事件，这份锚点还要不要通过？答案是**要**——它声明的是「此刻什么都没有」，后续追加并不构成反证。此时直接判通过，不再比对区间尾，也不再要求当前账本为空。若不这么定，任何一次空账本导出都会在校验时永远失败，锚点就成了「只在导出那一刻有效」的废纸。

## 校验是观察，不是维护

校验全程只读：不写 `audit_verified`，不写审计事件，不做自动修复。

第一，**观察不能改变被观察对象**。校验若写一行审计事件，账本就被自己的校验动作改掉了；之后拿同一个锚点再校验，看到的已经不是第一次校验时的那本账。证据一旦自指，讨论就结束了。

第二，**锚点可能来自外部**。用户从别处拿一份 `anchor.json` 上传，这份文件描述的可能是另一台机器、另一个时刻的账本。把外部输入转换成本地状态，等于用别人的结论污染自己的数据。

第三，**自动修复会掩盖事故**。「检测到断链，已重建」听起来贴心，实际是把取证变成修缮：事故的原始形态没了，后续再查什么都是修复后的样子。

原有的「校验完整性」按钮保持原行为，不被这次改动牵扯。

## 4xx 与 200+code：把「输入坏了」和「证据坏了」分开

| 情况 | 状态 | 语义 |
|---|---|---|
| 锚点 JSON 结构非法（版本、字段缺失、哈希格式、时间格式） | 422 | 我没法执行这个请求 |
| 截断 / 错位 / 断链 | 200 + `code` | 我执行了，结论是账本有问题 |

这条界线容易被合并成「反正都是错误，统一 400 或统一 500」，但那样 web 端没法区分两件事：**是工具坏了，还是证据坏了**。结构非法属于请求侧问题——文件不是锚点、被手改过、或干脆是别的格式，用户该做的是重新选文件。截断与错位属于结果侧问题——请求完全合法，账本确实对不上，用户该做的是去看审计、去排查。

所以业务失败用 200：前端拿到的是一个正常的校验结果对象，`ok: false` 加 `code`，可以直接渲染成一条横幅；如果走 4xx，它只会弹出「请求失败，请重试」，而用户多点几次并不会让被删掉的尾部回来。

## 链状态为什么要带 truncated

生成锚点时会对全账本做一次只读校验，但账本超过 10 万条时只校验最近 10 万条，并用 `truncated` 标记。

这是诚实标注：锚点里写 `ok: true`，只代表「我检查过的部分是好的」，不代表「整条链都好」。不标这个位，读者会把有限校验当成全量校验，锚点的可信度就被自己抬高了。

## 锚点证明不了什么

- 证明不了「区间之后新增的事件是合法的」——追加是正常行为，锚点不评价新内容；
- 证明不了「有人删除之后重算了整条链」——重算能让所有哈希自洽，那需要外部签名或异地存证；
- 证明不了「这份归档文件本身没被改」——`events.jsonl` 与 `anchor.json` 同在一个 ZIP 里，改文件不改锚点，要防这个得给 ZIP 做摘要并另存。

锚点能做的是一件事：**在给定时刻，把账本的位置钉住**。把这件事做扎实，比宣称能防一切有用。

## 怎么证明它是对的

- 正常账本：通过，且返回值里同时带锚点尾与当前尾两组数据；
- 删尾：尾部缺失；改一行哈希：哈希错位；
- 生成时链已断：链已断；空账本锚点追加事件后仍通过；
- 只读性：校验前后账本条数与尾完全不变；
- 结构非法：422，且不进入业务判定。

## 收口

单尾锚点看着够用，是因为大多数事故都发生在区间里；而最难发现的那一类，恰好发生在区间外。多加一个「全账本尾」，成本是两次单行查询，换来的是「整段尾部消失」也能被指出来。真正花时间的不是字段，而是三件小事：判定顺序、空账本的例外、以及把「证据坏了」和「请求坏了」用状态码分开——这三件才决定了校验结果能不能被信任。
