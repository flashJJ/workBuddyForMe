# 寒暄不该进记忆：快路径命中的收尾分流

v4.19 做了寒暄快路径：命中寒暄时跳过记忆召回。但收尾阶段仍会为每一轮创建「回合后记忆提取」任务——对「你好」这类对话，这是一次完全无效的模型调用。

## 一、问题不在召回，在收尾

一轮对话结束后，收尾通常会做三件事：

1. 压缩与检查点；
2. 写摘要记忆；
3. 启动回合后记忆提取。

第二、三件都属于记忆。寒暄轮没有值得提取的长期信息，产生 `memories` 事件只会污染审计与统计。v4.20 把快路径标记一路带到收尾：

```text
上下文装配（fastChitchat=true）
  → 编排器
  → 收尾任务
  → 跳过摘要记忆与记忆提取
```

压缩与检查点不受影响——它们服务于上下文与任务恢复，不是长期记忆。

## 二、为什么带到收尾，而不是收尾再判断

收尾时再判断一次「这句是不是寒暄」，需要重复输入分类逻辑，还可能出现两处判定不一致。把装配阶段的结果当成事实向下传递，只有一个判断点，也更容易测试。

单测直接断言：寒暄轮之后的记忆条数不变，记忆提取请求次数不增加。

## 三、副作用要提前想清楚

跳过提取后，有两件事必须保持：

- 对话本身的行为不变，回答照常流式返回；
- 语音链路不受影响，寒暄仍然可以朗读。

因此只在收尾的记忆分支上加条件，不碰消息落库、事件流与语音。失效模式被限制在「少一次记忆提取」，而不是「少一条消息」。

## 四、这条规则以后怎么扩展

当前只对寒暄快路径生效。如果以后增加「闲聊模式」或「临时会话」，可以复用同一个标记，而不必再改一遍收尾。规则保持单一来源：装配阶段决定，收尾阶段消费。
