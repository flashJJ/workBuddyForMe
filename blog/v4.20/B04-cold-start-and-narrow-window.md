# 冷启动不是「少加载」：先找关键路径，再谈延迟

桌面端的冷启动有一个容易被忽略的事实：用户真正感知的是「输入框什么时候能打字」，而不是「所有模块什么时候加载完」。v4.20 按这个终点重新划了启动关键路径。

## 一、关键路径只到输入区

`coldStartMs` 的终点定义为输入区首次可交互，而不是 `window.onload`。据此把启动阶段分成两类：

- 首屏必需：布局壳、会话列表、输入区、当前会话消息；
- 非首屏：设置面板、知识库、任务页、工具详情等。

第二类改为延迟加载。它们仍会被打包，只是不参与首屏 hydration 的关键路径。

## 二、为什么不做绝对值门禁

冷启动受磁盘、杀毒、首次解压与机器负载影响，绝对值在 CI 上波动很大。把「必须小于 2 秒」写进门禁，最终只会得到一条不断被放宽的阈值。

v4.20 只把 `coldStartMs` 记进本地报告，做同机相对回归：

```text
本次 coldStartMs vs 最近一次 coldStartMs
```

绝对值留给用户判断，回归交给报告。

## 三、窄窗与长文本一起复核

启动拆分后，最容易回归的是布局。v4.20 固定三档宽度与长文本场景：

| 场景 | 检查点 |
|---|---|
| 1024 | 无横向溢出、侧栏不遮挡输入区 |
| 1280 | 长文本换行不撑破气泡 |
| 1440 | 宽屏下内容不无限拉伸 |
| 长文本 | 超长无空格串可断行、复制按钮不遮挡 |

这些检查用生产模式 E2E 跑，避免 dev 首次编译把启动指标和超时搅在一起。

## 四、得到的数字

本机生产包冷启动单次样本 `2605ms`。这个数字不适合拿来和别人的机器比，但可以作为本机下一次改动的对照。更重要的是，从这一版开始，「冷启动变慢了吗」不再只能靠感觉。
