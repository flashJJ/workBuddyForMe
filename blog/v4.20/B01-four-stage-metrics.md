# 先量出来：聊天四段指标与本地性能报告

「感觉有点慢」不是一个可执行的结论。v4.20 先把「一次对话到底慢在哪」拆成四个可以复算的时间段，再谈优化。

## 一、四段指标

| 指标 | 起点 | 终点 |
|---|---|---|
| `coldStartMs` | 页面导航开始 | 输入区首次可交互 |
| `firstTokenMs` | 发送动作 | 首个非空助手 delta |
| `firstParagraphMs` | 发送动作 | 首个段落可见（换行或累计 ≥80 字符） |
| `completionMs` | 发送动作 | `done` 事件 |

打点名固定为 `wbfm:app-ready / send / first-token / first-paragraph / done`，全部使用 `performance.mark`。空 delta、心跳与状态事件不计入首字；错误与主动停止按终止时间计完成耗时。

## 二、为什么不用现成的 APM

本地优先的桌面应用有三个约束：

1. 指标不能离开本机，不能默认上报；
2. 不能读消息正文，否则隐私边界立刻失守；
3. 不能为了埋点引入新的运行时依赖。

因此指标只在本机计算，报告写进 `test-results/perf/`，并复用已有的敏感内容扫描。报告里只有耗时、平台与 Node 版本，没有正文、令牌或绝对路径。

## 三、报告结构与保留策略

一次运行写两份文件：

- `report-<ISO去分隔符>.json`：归档；
- `latest.json`：本次副本，便于脚本直接读取。

同时只保留最近 20 份，按文件名时间排序删除最旧。这样性能目录不会随着 CI 次数无限增长，也保留足够的历史做相对对比。

```json
{
  "suite": "chat-perf",
  "scenarios": [{ "name": "first-token", "metrics": { "firstTokenMs": { "p50": 0, "p95": 0 } } }],
  "budget": { "firstToken": { "p50": 0, "threshold": 0, "absoluteLimit": 10000 } }
}
```

同一输入两次运行，除 `at` 外结构一致——这是「可复算」的最低要求。

## 四、指标能回答什么

- 首字慢，是模型首包慢，还是本地渲染慢？
- 首段慢但首字快，是流式分片太碎，还是段落判定太保守？
- 完成慢，是工具链长，还是收尾任务拖住了 `done`？

把「慢」拆成四段之后，优化才有靶子，回归也才有对照。数值本身不上门禁，只做同机相对比较。
