# Edge TTS 增量解码：从「等整段」到「边收边播」

在线朗读的第一版是「收完整段 MP3 再解码」。首句要等整段返回，长句尤其明显。v4.20 把解码改成增量：音频分片一到就解，解出 PCM 立刻下发。

## 一、原来的链路

```text
WSS 音频分片 → 累积 Buffer → turn.end → mpg123 解码整段 → 一次性播放
```

问题有两个：

- 首块音频已经到达，但播放要等最后一块；
- 整段 MP3 常驻内存，长文本时占用明显。

## 二、增量链路

```text
WSS 音频分片 → mpg123 增量解码 → PCM 分片 → sink 逐块下发
```

`mpg123-decoder` 的底层是 `mpeg_decoder_feed`：数据不足一帧时返回 `NEED_MORE`，内部保留尾巴；凑够一帧就产出 PCM。因此可以安全地按任意分片喂入，不需要自己切帧。

每个音频请求创建一个解码器实例，`turn.end` 后释放。分片按到达顺序串行解码，避免并发写同一个 wasm 实例。

## 三、失败回退要防重复

在线引擎失败会回退本地引擎。流式之后多了一个新风险：如果已经下发过一部分音频，再回退本地重播，用户会听到重复的开头。

处理方式很简单：记录「是否已下发过分片」。

- 没有下发过：照旧回退本地；
- 已经下发过：直接抛错，不重复朗读。

回退仍然保留，只是不再无条件触发。

## 四、兼容旧路径

解码器被抽成两段：

- 增量解码器：生产默认；
- 一次性解码：单测注入与不支持增量时的兜底。

协议组装（`speech.config`、SSML、二进制帧解析）与解码拆成独立模块，引擎只负责连接、排队与收尾。这样增量逻辑可以单测：假 socket 发两个音频分片，断言 sink 收到两次、最终样本按顺序拼接、解码器只释放一次。
