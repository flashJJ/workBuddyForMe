# 循环背景视频的生命周期：静音、可见性与省电降级

一张背景图和一段背景视频，在代码里只差一个标签，在运行时差很多：视频要解码、要缓冲、要循环、要处理窗口隐藏，还要在用户开启“减少动态效果”时体面地停下来。桌面应用对资源又比网页更敏感——它会长时间挂在后台。

这一轮我们把视频背景的生命周期收在一个组件里，规则只有四条。

## 一、默认静音、循环、内联

```html
<video muted loop playsinline preload="metadata" />
```

- `muted`：背景视频永远没有音轨。不是“音量设为零”，而是连音频解码都不参与。
- `loop`：循环由浏览器负责，避免自己在 `timeupdate` 里手动改 `currentTime` 造成卡顿。
- `playsinline`：移动端与部分内核会尝试全屏接管，加上这个属性可以避免。
- `preload="metadata"`：只预加载元数据，首帧到了再播放，减少启动时的磁盘读取。

自动播放策略仍然生效。桌面壳里通常允许静音自动播放，但代码不能假设一定成功：`play()` 返回 Promise，失败时静默保留首帧，不弹错误、不重试循环。

## 二、窗口不可见就暂停

背景视频最容易被忽略的成本，是用户切到别的应用之后它还在解码。桌面壳的窗口不会自动停止渲染循环，必须显式处理：

```ts
const sync = () => {
  if (document.visibilityState === 'visible') {
    void video.play().catch(() => {});
  } else {
    video.pause();
  }
};
document.addEventListener('visibilitychange', sync);
```

同时监听 `prefers-reduced-motion`。用户开启减少动态效果时，视频不播放，只保留首帧或静态回退。这个偏好可能随时变化，所以用 `matchMedia` 的 `change` 事件跟随，而不是只在挂载时读一次。

暂停不是销毁。视频元素保留，`currentTime` 停在原处，恢复可见时继续播放。销毁再创建会带来重新缓冲与首帧闪烁，切换窗口的体验会明显变差。

## 三、测试环境里不存在播放能力

这段逻辑在浏览器里很普通，在测试环境里会直接报错：

- jsdom 没有实现 `HTMLMediaElement.prototype.play`；
- `matchMedia` 可能不存在；
- `play()` 返回的不是 Promise。

处理方式不是给测试环境加一堆 mock，而是让组件自身具备防御性：

```ts
const play = () => {
  try {
    const result = video.play();
    if (result && typeof result.catch === 'function') result.catch(() => {});
  } catch {
    // 无媒体能力的环境：保留首帧
  }
};
```

`matchMedia` 同理，先判断 `typeof window.matchMedia === 'function'`，不存在就当作“不减少动态”。这样组件在真实浏览器与 jsdom 下都能挂载，测试不需要模拟整个媒体栈。

## 四、降级顺序要写死

视频背景的降级顺序是：

1. 正常播放；
2. 自动播放被拒绝 → 保留首帧；
3. 窗口不可见 → 暂停；
4. 减少动态效果 → 暂停并回到首帧；
5. 资源 404 → 交给解析器回退到内置背景或透明。

这个顺序里，只有第 5 步会改变“背景是什么”，前四步只改变“背景怎么动”。把两类变化分开，调试时就能快速判断问题出在资源还是播放策略。

## 五、压暗与模糊不碰视频解码

视觉参数只有两个：`dim` 与 `blur`。实现上都是 CSS：

- `dim`：叠加一层黑色半透明遮罩，透明度即参数；
- `blur`：对媒体元素应用 `filter: blur(Npx)`，外层容器裁掉溢出。

两者都不修改视频源、不做离屏渲染、不引入 Canvas。原因是性能：背景层已经在解码视频，再叠加一次逐帧处理会让低配机器直接掉帧。

模糊会把边缘“吃”进容器外，所以容器固定 `overflow: hidden`；压暗层与媒体层同尺寸，避免出现一圈亮边。

## 六、为什么把生命周期放进一个组件

三处界面都需要视频背景：舞台、主窗口、桌宠。如果每处各写一遍暂停逻辑，最终一定会有两处忘记处理 `visibilitychange`。

因此生命周期被封装在一个 `BackgroundLayer` 里，三处只负责布局：

- 舞台决定是否让位给剧集背景；
- 主窗口决定铺内容区还是铺满；
- 桌宠决定内缩与圆角。

组件内部只回答“给定一个解析结果，怎么播放”。这条分工让性能策略只有一份实现、一份测试。
