# 桌宠窗改成 9:16 之后：取景、圆角木相框与层级

桌宠悬浮窗原来的比例是 13:20，接近竖屏但不是标准比例。这个数字没有设计依据，是早期随手定的。等到要给它做背景图与循环视频时，问题出现了：生成工具默认输出 9:16，导进来不是裁边就是留黑。

于是这一轮把桌宠窗改成 270×480，标准 9:16。改动只有一个常量，但连带要处理取景、相框与层级三件事。

## 一、窗口比例决定素材规格

先把数字说清楚：

- 窗口 DIP：270×480；
- 2x 素材：540×960；
- 3x 素材：810×1440；
- 视频：480×854 或 720×1280，H.264。

背景视频用 480×854 而不是 540×960，是体积与清晰度的折中：桌宠窗在屏幕上通常只占一小块，480 宽已经足够；再高只会增加解码压力。

比例统一之后，素材、窗口与相框三者才能用同一套坐标，不再需要“按比例缩放再裁切”的中间层。

## 二、取景仍然按容器算，不按比例写死

角色是 3D 模型，窗口变高之后不能简单放大。取景逻辑本来就按容器宽高计算视锥：

```ts
const aspect = hostW / hostH;
const visibleH = 2 * Math.tan(fov / 2) * DIST;
const visibleW = visibleH * aspect;
const scale = Math.min(
  (visibleH * (1 - pad * 2)) / modelHeight,
  (visibleW * (1 - pad * 2)) / modelWidth,
);
```

9:16 比原来的 13:20 更窄更高，宽度成为约束项，模型会按宽度缩小、脚底贴底，头顶留出余量。这个余量的作用是“被拎起或播放抬手动作时不裁头”。

桌宠专用的取景参数是 `bottomAlign + topHeadroom`：脚底贴底，竖直方向只保留顶部余量。主窗口仍然竖直居中，两套参数由路由决定，不靠运行时猜。

## 三、相框不是图片，是纯 CSS

木纹相框最初考虑用九宫格图片，最后改成纯 CSS：

- 外层容器：`border-radius: 22px`，木色渐变背景；
- 内层挖空：`border-radius: 15px`，用 `mask` 的 xor 组合挖出中间区域；
- 视觉边框宽度：7px；
- 投影：向外的柔和阴影，模拟相框压在桌面上的层次。

用 CSS 而不是图片有三个理由：不增加安装包体积、任意窗口尺寸下都不会模糊、颜色可以随主题微调。

挖空的实现需要小心。简单用 `border` 会得到四条直边，圆角处接不上；用两个圆角矩形做 xor 遮罩，内圆角比外圆角小 7px，边框宽度才在视觉上均匀。

## 四、背景层与相框共用一组常量

背景层有背景时内缩 7px、圆角 15px；相框外圆角 22px、内圆角 15px。这组数字必须来自同一处：

```ts
const FRAME_WIDTH = 7;
const FRAME_RADIUS_OUTER = 22;
const FRAME_RADIUS_INNER = 15;
```

否则调相框宽度时，背景会露出一条缝，或者被相框压住一圈。共享常量比共享组件更轻，也更容易在测试里断言。

## 五、层级与穿透同时验证

层级顺序在上一节已经列出：画布 → 背景 → 相框 → 字幕 → 菜单。实现时有两个容易错的点：

第一，相框必须在画布之上。如果放在画布下方，圆角内缘会被画布盖住，看起来像“背景有圆角但角色没有”。

第二，相框必须 `pointer-events-none`。相框覆盖了整个窗口边缘，一旦拦截指针，拖拽与穿透都会失效。

验证不是靠肉眼：回归测试覆盖命中盒上报与光标换算，真机验证则检查拖拽、双击回主窗、右键菜单三个动作。

## 六、没有背景时什么都不渲染

相框只在有背景时出现。无背景时：

- 背景层返回 `null`；
- 相框返回 `null`；
- 窗口保持透明，角色照常悬浮。

这条分支必须在组件最外层判断，而不是渲染后设 `opacity: 0`。透明元素仍然参与命中与合成，留着会带来不可见的性能开销与层级问题。

## 七、改比例带来的连锁检查

窗口比例是一个被很多地方引用的常量，改动后逐项确认：

- 位置钳制：按新宽高计算，副屏拔掉后仍能回到主屏；
- 命中盒：按比例计算，头部与身体的点击区域随高度变化；
- 拖拽：系统拖拽层按新窗口尺寸工作；
- 取景：按容器宽高重算，不写死比例；
- 素材：按 9:16 重新生成并压缩。

这些检查里，只有取景是运行时计算，其余都是常量引用。把比例收在一个常量里，改的时候才能一次改完。
