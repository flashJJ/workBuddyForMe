# 壁纸包：声明式资源包与内容快照

桌面应用的能力包体系已经跑了几轮：清单、校验和、签名、依赖、启用/停用、升级与回滚。这一轮要加的是“壁纸包”——一组图片或视频，安装后出现在背景来源里。

诱惑很明显：壁纸包能不能带一小段脚本，用来做动态效果？答案是不能。只要包能执行代码，安装校验、权限确认、崩溃隔离与回滚语义就全部升级成另一套复杂度。我们选择继续走声明式路线。

## 一、包只声明三件事

壁纸包的 payload 只描述资源和许可：

```json
{
  "name": "示例壁纸包",
  "backgrounds": [
    {
      "id": "wallpaper.pack.sample",
      "kind": "image",
      "file": "payload/assets/sample.webp",
      "license": "CC0-1.0"
    }
  ]
}
```

- `id` 强制 `wallpaper.` 前缀，且包内唯一；
- `kind` 只能是 `image` 或 `video`，必须与文件扩展名匹配；
- `file` 必须位于 `payload/` 下，不允许 `..`、绝对路径与远程 URL；
- `license` 限定在 CC0-1.0 与 CC-BY-4.0 白名单内。

数量限制 1–10 项，单文件 ≤50MB，整包 ≤200MB。这些数字不是审美，而是为了让“启用一个包”不会变成一次长时间的磁盘与内存冲击。

## 二、启用前校验，而不是启用后报错

能力包的 effect 在启用阶段做完全部检查：

1. 读取并解析 payload；
2. 逐项校验 id 前缀、重复、kind 与扩展名；
3. 校验文件存在、位于 payload 内、未越界；
4. 校验许可白名单；
5. 校验单文件与整包预算。

任何一项失败，启用操作整体失败，能力行保持停用。这样运行时永远不需要处理“包启用了但资源不合法”的中间态。

校验函数与读取函数分开：校验只读元数据与文件大小，读取才真正把资源流式返回。启用阶段不做全量读盘，避免大视频拖慢安装。

## 三、内容快照：版本不是包的版本

壁纸内容由多个已启用包聚合而成。聚合结果的版本不能简单等于“最后安装的包版本”，否则停用一个包、启用另一个包时，版本可能不变。

我们沿用内容服务的做法：把所有启用项的 `id@version` 排序后做 SHA256，取前 12 位：

```text
wallpapers:<sha256(sorted id@version)[:12]>
```

这个版本号有三个用途：

- 前端缓存键：内容变化时自动失效；
- 请求幂等：同一组启用项总是得到同一版本；
- 问题定位：日志里能看出当时是哪一组包在生效。

## 四、冲突必须 fail-closed

两个包声明同一个壁纸 id 时，不能“后者覆盖前者”。覆盖行为依赖安装顺序，用户无法预测，出问题也无法复现。

聚合层的处理是：检测到重复 id 时，整个壁纸内容标记为不可用，并记录 `lastError`。渲染层拿到空列表，解析器回退到内置背景。用户看到的是“壁纸没生效”，而不是“某一张图莫名其妙变成了另一张”。

fail-closed 在这里比“尽量可用”更重要，因为背景是视觉资产，错配比缺失更难被发现。

## 五、停用不热替换

包停用后，背景不会立刻切走。原因和场景包一致：正在播放的视频如果被中途替换，会出现黑帧、闪烁与播放状态错乱。

生效时机是“下一次读取”：

- 设置页重新拉取内容快照；
- 页面重新挂载；
- 用户重新选择背景。

这条限制写进了发布说明，也写进了设置页提示。它不是缺陷，而是把“内容边界”固定在一个可解释的时刻。

## 六、资源读取走独立路由

包内资源不能直接暴露文件路径。我们提供两条只读路由：

- 内容清单：返回当前聚合后的壁纸列表与版本；
- 资源读取：按包 id 与相对路径返回文件流。

资源路由只接受“已启用包”的声明文件，路径在 effect 启用时已经校验过；读取时再确认一次目标仍位于 payload 内。响应带长缓存与正确的 Content-Type，视频支持 Range 请求，浏览器才能正常循环播放。

## 七、为什么值得复用能力包管道

壁纸包没有自己的安装器、没有自己的签名逻辑、没有自己的升级路径。它复用的是：

- 清单校验与信任库；
- 启用/停用与回滚；
- 依赖与冲突检查；
- 健康检查与残留清理。

新增一种内容类型，只增加一个 payload schema 与一个 effect。对单人维护的项目来说，这条复用链路的价值远大于“支持更多格式”。
