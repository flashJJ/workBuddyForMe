# 背景功能收尾复盘：门禁先红后绿的一轮

一个功能做完、测试通过，并不等于可以发布。这一轮背景与壁纸功能在收尾阶段被自己的工程门禁拦了两次：一次是目录文件数超标，一次是循环依赖。两次都不影响运行，但都指向同一类问题——代码在“能跑”之后，还需要一次结构上的收口。

## 一、门禁拦住了什么

第一次红灯：背景域目录的直接文件数达到 13，超过 12 的上限。原因是三个 hook 与若干组件平铺在同一层。功能上没有问题，但目录已经不再是“一眼能读完”的规模。

第二次红灯：两个模块互相引用——内置清单需要解析结果的类型，解析器需要内置清单的数据。类型层面的循环，运行时不报错，打包也能过，但依赖方向已经不清楚。

这两次都不是“功能 bug”，而是结构债。门禁的价值就在这里：它不判断功能对不对，只判断结构有没有变坏。

## 二、修法一：把 hook 收进子目录

三个 hook 被移到 `hooks/` 子目录，引用路径同步更新。目录从 13 个直接文件降到 10 个：

```text
features/background/
  index.ts
  builtin.ts
  resolve.ts
  background-layer.tsx
  main-background.tsx
  pet-background.tsx
  stage-background.tsx
  pet-frame.tsx
  gallery.ts
  hooks/
    use-background.ts
    use-background-files.ts
    use-wallpaper-content.ts
```

这里没有做“大重构”，只是把一类职责放到它该在的层级。组件仍然平铺，hook 收进子目录，入口文件继续只做导出。

经验：目录预算不是让你拆组件，而是让你先分类。分类之后，超标往往自然消失。

## 三、修法二：把共享类型放到数据源头

循环依赖的根因是类型定义的位置。`ResolvedBackground` 描述“解析后的背景形态”，它既被内置清单使用，又被解析器返回。

最初的写法是类型定义在解析器里，内置清单反向 import 类型。修法是把类型移到内置清单模块，解析器改为从那里导入并重新导出：

```text
builtin.ts   定义 ResolvedBackground 与内置数据
resolve.ts   import type { ResolvedBackground } from './builtin'
index.ts     继续从 resolve 导出类型（对外 API 不变）
```

依赖方向变成单向：解析器依赖数据，数据不依赖解析器。对外导出保持不变，调用方一行不用改。

经验：类型循环通常不是“类型放错了”，而是“数据与算法谁依赖谁”没有想清楚。数据是底层，算法依赖数据，反过来就会成环。

## 四、修复之后重新跑全套

两次修复都只动了结构与导入，但验证不能只跑相关测试：

- 结构门禁：直接文件 10，循环依赖回到已登记基线；
- 类型检查：web 与 shared 全量通过；
- 相关测试：背景、设置、桌宠、舞台共 24 个文件 123 项通过；
- 全量门禁：typecheck、lint、行数、结构、循环、ASCII、资产全部通过；
- 全量测试：9 个包 745 个文件 4219 项通过。

只有最后两项都绿，才算收尾完成。局部的“应该没问题”不算证据。

## 五、安装包也是门禁的一部分

构建链路是固定的：前端 standalone 构建 → 桌面主进程构建 → 服务资源归集 → 安装包。任何一步失败，后面的数字都没有意义。

这一轮安装包 272.35MB，预算 300MB。归档脚本同时产出校验和、blockmap 与 `latest.yml`，再用独立脚本复算一遍。校验通过输出的是“3 个产物”，不是一句“成功”。

把体积与校验和写进发布说明，是为了让下一次构建有可比对象。没有基线的预算，第二年就会失效。

## 六、这一轮的五条经验

1. **先建模，再写组件。** 背景先成为 `kind + id` 的数据，三处界面才能共用解析器；如果先写三个组件，最后一定会出现三套回退逻辑。
2. **路径不要进设置。** 复制到数据目录、只存 id，一次性解决文件移动、路径泄露与权限越界三个问题。
3. **能力差异放在运行时。** 桌面端与 Web 共用一份数据模型，入口处探测桥是否存在，比在 schema 里加平台字段更稳。
4. **性能策略只写一份。** 视频暂停、减少动态、首帧回退集中在背景层，三处界面只负责布局。
5. **门禁红灯先修结构，再谈发布。** 目录预算与循环依赖不影响功能，但会影响下一次修改的成本；收尾阶段修，成本最低。

## 七、刻意没做的事

没有做在线壁纸市场，没有做运行时转码，没有做动态壁纸交互，也没有做背景热替换。这些都能让功能“更完整”，但每一个都会引入新的失败路径。

对一个单人维护的桌面应用来说，边界清晰比功能齐全更重要。背景是氛围，不是主功能；它应该安静地工作，出问题时安静地回退。

## 八、下一步

素材预算还没有完全接入自动门禁，背景媒体的体积目前靠脚本与人工核对。下一轮会把媒体预算表并入资产检查，让“图集多大、视频多大、安装包多大”也变成可重复执行的检查。

功能可以慢慢加，结构必须先站稳。这是这一轮最值得记住的一句话。
