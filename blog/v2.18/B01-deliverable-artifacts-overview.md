# 从会说话到能交付：Agent 产出物的四个断点

我们的桌面 AI 应用是本地优先、单人开发的私人助手，对话、工具调用、知识库全部跑在本机。它已经能回答得很长，但回答完就结束了：内容停在对话流里，用户拿不走、打不开，也带不进别的软件。

这就是「可交付」要解决的问题。模型能写 HTML、能画流程图、能引经据典，但如果没有一套把内容变成文件的机制，这些能力会在最后一厘米全部失效。下面按四个断点拆开。

## 一、四个断点

| 断点 | 现象 | 后果 |
|---|---|---|
| 生成的内容没有落点 | 模型会写 HTML/Markdown，但对话里没有「存成文件」的工具 | 用户只能全选复制，格式全丢 |
| 图表靠模型自由发挥 | 没有类型规范，没有坐标轴与箭头规则 | 同一张架构图十次十个样，元素经常越界 |
| 知识库只有空模板 | 模板页能建库，但没有可导入的示例内容 | 用户不知道「内容型知识库」能用来干什么 |
| 工具结果只有一段文本 | 没有来源、覆盖率、未知项 | 判断不了结论可信度，也追不回原文 |

这四个断点有一个共同特征：它们不影响「回答对不对」，只影响「回答能不能被使用」。这也决定了本轮的边界——不去做更大的能力市场，只把产出物这条链路补齐。

## 二、四件交付物

| 交付物 | 形态 | 用户拿到什么 |
|---|---|---|
| 产物文件 | 写产物工具 + 复用附件存储 + 专用预览路由 | 对话里出现卡片，点开能看、能下载 |
| 图表模板 | 渲染工具 + 十类结构化模板 + 内置图表技能 | 说一句「画一张时序图」，得到自包含的图 |
| 内容包 | 固定版本的 Markdown 集合 + 逐文件与整包哈希 | 在知识库模板页点一下，导入一套带署名的书 |
| 证据元数据 | 统一字段 + trace 展示 + 导出保留 | 每个联网或知识库结论旁边能看到来源与覆盖范围 |

四件交付物不是四个独立功能，而是一条链上的四段：图表由模板生成、经产物工具落盘、在预览页导出、结论再被证据标注。任何一段缺席，用户拿到的仍然是「一段话」。

这也决定了实施顺序，不是随便排的：

| 顺序 | 做什么 | 为什么必须先 |
|---|---|---|
| 1 | 产物管道 | 后面所有交付物都要落到「文件」这个终点上 |
| 2 | 图表模板 | 有了落盘能力，模板产物才有意义 |
| 3 | 客户端导出 | 有了图，才谈导出格式 |
| 4 | 内容包 | 与产物链路独立，但共用知识库与附件基础设施 |
| 5 | 证据元数据 | 要在既有工具结果上加字段，先得有稳定的结果结构 |

顺序错了会返工：先做导出，就要在没有产物卡片的情况下造一个临时入口；先做证据，就要在工具结果结构定型前就冻结字段。

## 三、全景：一条链的四段

```text
用户：画一张订单状态迁移图，导出成 PNG
        │
        ▼
模型（只做选择与填数据）
   type=state_machine, title=..., data={nodes, edges}
        │
        ▼
渲染工具：zod 校验 → 模板布局 → 自包含 HTML（内联 SVG）
        │  直接落盘，不回灌上下文
        ▼
产物服务：写文件 + 附件记录 → 返回产物引用
        │
        ▼
对话卡片（tool-trace 内）：预览 / 下载 / 导出 SVG / 导出 PNG
        │
        ▼
预览路由：CSP sandbox + nosniff → 带令牌取 Blob → iframe 预览
        │
        ▼
客户端导出：提取第一个内联 SVG → Canvas 2 倍图 → 存到本地
```

中间那条「直接落盘」很关键。图表动辄几十 KB 的 SVG，如果先回灌给模型、再让模型调一次写文件工具，既浪费上下文，又给了模型改坏模板的机会。

## 四、四个关键取舍

**① 产物不新建表，复用附件表。** 附件表本来就在存图片与文件，扩展三种 MIME 与扩展名映射即可。零迁移不是省事，而是让旧库直接打开就能用新功能——一旦为了产物新建表，所有老用户都要走一次迁移。

**② 图表由模板画，不让模型手写 SVG。** 模型只负责「选类型、填结构化数据」，布局、坐标轴、箭头、配色全部由模板生成。把自由度收进 schema，质量才可复现。

**③ 内容包运行时下载，不随包分发。** 正文不进安装包，用户确认后才从固定版本地址下载并校验哈希。包体不膨胀，许可与内容更新也留出了空间。

**④ 证据只进界面，不进模型上下文。** 来源、覆盖、未知项是给人看的，不是给模型推理用的。放进上下文只会增加 token，并诱导模型把「未覆盖」当成事实。

## 五、明确不做的边界

- 图表只做十类简化布局；节点超过九个建议拆图，不做四十五类全量参考；
- 通用 HTML 产物只保证预览与下载，不承诺 PNG；PNG 只针对图表产物里的内联 SVG；
- 产物卡片放在工具追踪区，不新增独立消息气泡，避免改动多模态消息协议；
- 单轮产物数量的上限写进了契约，但运行时尚未计数；
- 证据字段先覆盖联网搜索、网页抓取、知识库检索三类工具，其余工具暂不填。

边界写清楚的好处是验收时不用争论「这算不算没做完」——不做的部分本来就在清单上。
