# 内容包协议：用哈希锁住一本会变的书

我们的桌面 AI 应用（本地优先、单人开发）里，知识库模板过去只是一个空壳：能建库、能导入文件、能检索，但用户打开模板页不知道下一步该干什么。填入一份可选示例内容，看起来是最简单的产品动作——把书的内容打进安装包就行。

真做起来会发现麻烦在三个地方：安装包会因此膨胀几个兆；书的许可要求保留署名、允许再分发但不允许暗示作者背书；而书还在持续修订，今天导进来的版本和半年后的版本不是同一本。这三条都指向同一个结论：内容不能随包分发，必须运行时按版本获取。

## 一、内容包是一份声明，不是一堆文件

内容包的核心是一张清单，字段固定：

| 字段 | 值 | 作用 |
|---|---|---|
| 包 id | `how-to-live-better` | 全局唯一，状态判定的键 |
| 上游版本 | 固定提交 | 内容不可变，不会今天一个样明天一个样 |
| 正文 | 34 个 Markdown，按序编号 | 可逐篇展示、逐篇摄入 |
| 逐文件校验 | 字节数 + 单文件 SHA-256 | 定位到具体哪一篇坏了 |
| 整包校验 | 拼接后 SHA-256 | 防止缺篇、乱序、夹带 |
| 总体积 | 2,385,074 字节（约 2.3 MB） | 下载前告知用户 |
| 许可 | CC BY 4.0 | 决定署名页怎么写 |
| 目标知识库 | 固定 id | 存在即视为已导入 |
| 失败口径 | 下载失败或任一哈希不符 → 不建库 | 不留半成品 |

固定提交是关键决策。书的仓库有滚动更新的发布资产，但滚动意味着**同一份清单在不同时间下载到不同字节**，哈希就失去意义。改成锁定一个提交、逐篇取原始 Markdown，清单才真正可复现。

## 二、为什么不是「一个 HTML 文件」

上游也提供单文件电子书。没选它，有两个硬理由：

1. 现有文档导入链路不接受 HTML 输入，选它就得新写一条解析与分块路径；
2. 单文件哈希只能证明「整包对」，坏了不知道坏在哪；逐篇哈希能精确到第几篇，重试也只需要补那一篇。

34 篇 Markdown 的代价是请求数变多，收益是校验粒度与导入粒度都对得上。

## 三、下载与校验：先证明，再落库

流程刻意做成「校验全部通过之后才创建任何东西」：

```text
用户点击导入
   │
   ▼
确认框：来源、许可、34 篇、约 2.3 MB
   │ 用户取消 → 什么都不发生
   ▼
服务端分批下载（4 路并发，固定顺序拼接）
   │ 逐篇校验：字节数 + SHA-256
   │ 失败 → 报错退出，不建库
   ▼
整包 SHA-256 比对
   │ 不符 → 报错退出，不建库
   ▼
创建固定 id 知识库 + 登记 34 篇文档（待摄入）
   │
   ▼
返回知识库引用，后台逐篇摄入
```

三个设计点值得展开：

- **原子性**：所有校验在创建之前完成。失败的导入不留下一个空知识库，用户不会在侧栏看到一个「已导入但没有内容」的条目，也不用自己去删。
- **两种错误码**：下载失败与哈希不符分开。前者是网络问题，可以重试；后者是内容问题，重试没有意义。前端文案因此不同。
- **固定知识库 id**：状态判定不需要额外字段。库存在就等于已导入，按钮置灰。零迁移的约束下，这是一个很划算的复用。

## 四、后台摄入：不让用户等三十四篇

34 篇文档的分片、向量化、全文索引与自动编译，串行跑完要几分钟。如果整个导入接口同步等完，前端早就超时了。

所以接口在登记完文档后就返回，摄入放到后台逐篇进行：

| 特性 | 行为 |
|---|---|
| 顺序 | 按 01–34 顺序逐篇 |
| 隔离 | 单篇失败不影响其他文档 |
| 进度 | 复用既有的文档状态轮询，不新增聚合进度接口 |
| 可用性 | 先摄入完的篇目先可检索 |

没有聚合进度是已知缺口。用户看到的是一个文档列表陆续从「处理中」变成「可用」，而不是一根总进度条。对 34 篇这个量级可以接受，对上千篇就不行了——这也是为什么首版只做一个内容包。

## 五、零迁移怎么装下版本元数据

内容包的版本、哈希、导入时间这些信息总得有地方放。新建一张内容包表最直观，但那会打破零迁移。

实际落点是两处既有结构：知识库的描述字段记版本与哈希摘要；自动生成的「署名与免责声明」文档记完整来源、许可、固定版本、整包哈希与导入日期。前者的作用是让人在库列表里一眼看到版本，后者的作用是让版本信息跟着内容走——导出、分享、检索都能带上。

## 六、几个没做的事

| 不做 | 原因 |
|---|---|
| 检查更新 | 首版先固定版本；比对整包哈希、提示重新导入的策略留到后续 |
| 任意地址导入 | 只允许白名单清单里的包，避免把「下载任意 URL」变成攻击面 |
| 静默下载 | 必须用户确认，确认框展示来源与体积 |
| 内置正文 | 包体、许可、内容更新三条都不允许 |
| 内容包独立能力类型 | 复用知识库模板 + 文档导入 + 技能，不扩能力分类 |

「不做检查更新」有一个直接后果要提前说清楚：上游内容一旦变化，清单里的哈希就对不上，导入会被拒绝。这是设计使然——宁可拒绝，也不把一份来历不明的内容塞进知识库。

## 七、验证

服务层七例：清单查询、成功导入、单文件哈希不符、整包哈希不符、重复导入、未配置向量模型、下载失败、未知包 id。接口两例：清单返回篇数与体积且标记未导入、空 id 与未知 id 的拒绝。界面五例：卡片展示、确认框、请求体、导入提示，原有四例不回归。
