# 证据元数据：让每条结论都带着来源与「没覆盖什么」

我们的桌面 AI 应用（本地优先、单人开发）里，一次联网搜索的回答可能和一次纯模型记忆的回答长得一模一样。用户没法判断哪句来自网页、哪句是模型自己组织的，更没法知道搜索是不是只覆盖了前三条结果。

只加一句「以上信息来自网络」没有意义。可信度要能被检查，就得有结构：来源、覆盖范围、未知项、采集时间。这就是证据元数据的由来。

## 一、四个字段，只做四件事

```ts
// 说明性伪代码
interface ToolEvidence {
  source: string;          // 来源：搜索服务名、网页最终地址、知识库文档名
  coverage?: string;       // 覆盖：结果条数、片段数、正文字符数、HTTP 状态
  limitations?: string[];  // 未覆盖：失败原因、截断、空结果
  capturedAt?: string;     // 采集时间
}
```

四个字段都不是可选的美化项：

| 字段 | 回答的问题 | 缺失后的后果 |
|---|---|---|
| source | 这条结论从哪来 | 无法回溯，等于模型自述 |
| coverage | 看了多少 | 用户以为「全网都查过了」 |
| limitations | 哪些没看到 | 把局部结论当成完整结论 |
| capturedAt | 什么时候采的 | 时效性无从判断 |

`coverage` 与 `limitations` 保留可选，是因为不是所有工具都有「覆盖」这个语义——比如纯计算工具，来源就是本地执行，没有覆盖范围可谈。

## 二、只挂三个地方

证据的出现位置是刻意收窄的：

1. `ToolResult` 上，工具执行完就带上；
2. 工具追踪条目上，随消息一起持久化；
3. 流式响应的工具结束事件上，前端能即时显示。

除此之外不加第四个出口。原因很实际：多一处携带，就多一处可能在链路上丢失。而链路上丢失的证据不会报错，只会让界面少一行字——这种问题最难发现。

## 三、证据不进模型上下文

这是整个设计里最反直觉的一条：证据只进界面与导出，**不进模型消息**。

```text
工具执行
  ├─ output      → 给模型（可读摘要，受压缩层处理）
  └─ evidence    → 给界面 / 导出（来源、覆盖、未覆盖、时间）
```

三个理由：

- 证据是给人看的元信息，模型拿它推理不会更准，只会多花 token；
- 如果把 `limitations` 塞进上下文，模型容易把「未覆盖」当成事实的一部分，生成「根据未覆盖的资料……」这种怪句；
- 压缩层是为 `output` 设计的，证据混进去会让压缩规则多一类特例。

这条边界在实现上是结构性的：证据字段不参与 output 的序列化，压缩器看不到它，模型消息里也就没有它。

## 四、失败与空结果也要标「未覆盖」

最容易被糊弄的地方是失败路径。工具挂了、搜索没配置、知识库没绑定，返回一句「未找到相关内容」，用户会以为「世界上没有这个信息」，而不是「这次没查成」。

规则是：**任何非成功路径都必须带 limitations**。

| 场景 | limitations 文案方向 |
|---|---|
| 搜索服务未配置 | 未执行联网搜索 |
| 搜索返回空结果 | 检索无结果，未覆盖相关主题 |
| 网页抓取失败 | 抓取失败，未获得正文 |
| 知识库未绑定 | 未检索本地知识库 |
| 检索异常/超时 | 检索未完成 |

通用执行器也会在参数错误、超时、异常时补一条「未执行/未完成」的通用证据。这样即使某个工具忘了写，界面上也不会出现「看起来成功但什么都没有」的空白。

## 五、截断必须写明

静默截断是可信度的隐形杀手。三种截断都在 `limitations` 里明说：

- 搜索摘要截断，上限 300 字符；
- 工具输出截断，上限 8000 字符；
- 网页正文过长时截断，只保留前段。

用户看到「仅展示前 300 字摘要」，就知道结论可能建立在半段文字上；看不到这句，就会默认模型读完了全文。同样重要的是，截断事实也写进追踪记录，刷新后仍在。

## 六、界面：一个徽章加一块折叠区

工具追踪那一行加一个「证据」徽章；存在 `limitations` 时用警告色。点开是四行：来源、覆盖、未覆盖、采集时间。

设计上有两个克制：

- 不把证据铺在回答正文里。正文已经被引用角标占满，再塞元信息会毁掉可读性；
- 徽章只在有证据的工具行出现。不是所有工具都有证据，统一加一个灰徽章只会制造噪音。

分享导出时，证据跟随内容走：分享快照对来源字段做脱敏，Markdown 与 HTML 导出在末尾追加证据行，HTML 侧做转义。导出里保留证据的意义在于——别人拿到这份报告时，同样能判断结论的可信度边界。

## 七、先覆盖三类工具

证据字段没有一次性铺满所有工具，先做三个最需要来源的：

| 工具 | source | coverage 示例 |
|---|---|---|
| 联网搜索 | 搜索服务名 | 返回 5 条结果，摘要各截断至 300 字 |
| 网页抓取 | 最终地址（含重定向后） | HTTP 200，正文 12,340 字符 |
| 知识库检索 | 知识库名与命中文档名 | 命中 3 个片段 |

其余工具暂不填。这不是遗漏，而是排序：先让「结论可能来自外部世界」的工具带上证据，纯本地计算的工具优先级低。

## 八、零迁移

证据随工具追踪的 JSON 一起存，不新增表与列。老消息没有证据字段，界面上就是不显示徽章——向后兼容不需要写迁移脚本。

## 九、验证

定向用例覆盖：搜索未配置/成功含截断/空结果；抓取成功含最终地址与状态码/404 失败；知识库未绑定/命中/空命中；执行器的 artifacts 与 evidence 透传、超时通用证据；工具循环里追踪与流式结束同时携带证据；流式合并；追踪组件的徽章与四字段展开；导出序列化的证据行与转义；分享快照的脱敏。全部单测 2980 例一起跑，不降级。
