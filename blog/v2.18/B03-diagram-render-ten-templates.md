# 画图不该让模型手写 SVG：十类图表的模板化渲染

我们的桌面 AI 应用（本地优先、单人开发）里，用户说「画一张架构图」，最省事的实现是把 SVG 交给模型自由发挥。试过就知道这条路走不通：同一份需求，十次生成十个样；箭头穿过文字、节点互相压盖、坐标轴刻度对不齐；更麻烦的是，模型偶尔会编造一个不存在的节点，而图看上去毫无破绽。

图是一种有语法的东西。只要把语法写成 schema，渲染交给模板，质量就能从「看运气」变成「可复现」。

## 一、模型只负责两件事

图表工具把职责切成两半：

- **模型**：选类型、起标题、把内容整理成结构化数据（节点、边、序列、泳道）；
- **模板**：算布局、画坐标轴、连箭头、配颜色、输出自包含 HTML 与内联 SVG。

工具输入只有四个字段：类型、标题、数据、可选尺寸。数据形状由类型决定，用 zod 的判别联合描述——`type` 是判别键，选了 `state_machine`，校验器就只接受状态机那一支的字段，别的形状直接报错。

```ts
// 说明性伪代码：判别联合的骨架
const diagramInput = z.discriminatedUnion('type', [
  z.object({ type: z.literal('architecture'), nodes: NodeList, edges: EdgeList }),
  z.object({ type: z.literal('flow'),        nodes: NodeList, edges: EdgeList }),
  z.object({ type: z.literal('sequence'),    actors: NameList, messages: MessageList }),
  z.object({ type: z.literal('bar'),         labels: LabelList, series: NumericSeries }),
  // …其余类型同理
]);
```

判别联合的好处不只是类型收窄：错误信息能直接指向「你给的字段不属于这一类图」，模型下一轮就知道该改什么，而不是在自由 JSON 里瞎猜。

## 二、十类图，各有各的校验

| 类型 | 关键输入 | 校验重点 |
|---|---|---|
| 架构 | 节点、边、可选分组副标题 | 边的两端必须存在 |
| 流程 | 节点、边 | 边的两端节点必须存在 |
| 时序 | 参与者、消息序列 | 参与者名字必须已声明 |
| 状态机 | 状态、迁移 | 迁移的起点与终点必须是状态 |
| ER | 实体、关系 | 关系两端必须是实体 |
| 时间线 | 时间点、事件 | 时间点按序给出，事件挂在对应时间点 |
| 四象限 | 轴标签、条目 | 象限归属必须是四个之一 |
| 泳道 | 泳道、步骤 | 每个步骤必须属于已声明的泳道 |
| 柱状图 | 标签、数值序列 | 数值有限、非空、长度对齐 |
| 折线图 | 标签、多条序列 | 每条序列长度等于标签数、数值有限 |

数据图的校验最严，因为数字错一眼就能看出来：

- 空序列直接拒绝——没有数据的柱状图没有意义；
- 缺值拒绝，不用 0 兜底——0 是一个真实数值，替用户编一个会让图说谎；
- `NaN` 与 `Infinity` 拒绝——它们能通过 JSON 序列化，却会让坐标轴计算全部失效；
- 折线序列长度必须等于标签数，否则第 N 个点没有横坐标。

错误信息写成可执行的一句话，比如「第 2 条序列有 7 个点，但标签只有 6 个，请补齐或删掉一个点」。模型读到这句，下一轮基本能一次改对。

## 三、为什么是模板，不是图表库

引入一个图表库看起来很划算，但这里没有：

- 图表库默认输出 canvas 或带脚本的页面，而产物要能在沙箱里离线打开、还要能导出 SVG；
- 十类图的布局规则其实很朴素（网格、分层、坐标轴），用模板算比配置一个通用库更直接；
- 多一个运行时依赖，就多一份升级、打包、安全面的维护成本。

模板渲染的产出是一份自包含 HTML：样式内联、图形是内联 SVG、字体用系统字体栈（含中文），不引用任何外部字体、图片或脚本。这样它在应用内预览、下载后双击、塞进文档，表现都一致。

配色规则也写进模板，而不是交给模型：每张图一到两个焦点色，信息密度控制在中等，禁止暗色青紫发光、无意义的等宽字体和阴影堆叠。这些是设计规范，不是审美偏好——它们决定了图在投影仪和手机小屏上还能不能读。

## 四、模板化的代价：表达力有上限

十类简化布局意味着有些图就是画不好：

| 表达力限制 | 表现 | 应对 |
|---|---|---|
| 节点超过九个 | 自动布局开始拥挤，标签被截断 | 工具提示「建议拆成多张图」 |
| 架构分组容器 | 分组只作为节点副标题显示 | 分组框留到后续版本 |
| 数据图扩展形态 | 不支持堆叠、双轴、气泡 | 只做单轴与多系列折线 |
| 长标签 | 图内截断 | 详细说明放图外正文 |

这些限制不是缺陷清单，而是产品选择：一张塞了二十个节点的架构图，用户本来也读不懂。与其让模型硬塞，不如明确告诉它拆图。

## 五、工具语义的一个偏差

契约里这个工具被定为「只读」——生成内容，不写盘，再由产物工具落盘。实施时改成了「写」：渲染完成后直接调用产物服务落盘。

原因很实际。图表的 HTML 动辄几十 KB，如果先作为工具输出回灌给模型，再让模型复制一遍去调写产物工具，等于把同样的大段文本在上下文里搬两次，还给了模型篡改模板的机会。直接落盘后，模型只看到一句「已生成图表产物」，产物引用随工具追踪一起返回，卡片照常出现，权限门同样会弹确认。

这是一次明确的契约偏差，登记在案。偏差不可怕，可怕的是偏差悄悄发生、文档还写着旧语义。

## 六、技能负责「怎么选图」

模板解决「怎么画」，技能解决「该画哪种」。内置的图表技能只做三件事：根据内容推荐类型、把用户口语整理成结构化数据、提醒常见反模式（比如用饼图表达趋势、用折线图画分类对比）。

它不带四十五类全量参考，只有两段提示词。原因是技能模板的数量在回归里是一条硬清单：每加一个技能，就要同步加一条模板、一条播种断言、一条清单计数。少一处，播种数量就对不上——这个问题在后面的回归篇里会展开。

## 七、验证

十类图表各一例渲染通过是出口条件。定向单测二十例，覆盖：十类各一次、边引用不存在被拒、折线长度不匹配被拒、`NaN` 被拒、工具在产物服务不可用时的失败路径、参数错误。渲染器本身不依赖网络、不依赖 DOM，可以在纯 Node 环境里断言输出字符串里是否含内联 SVG 与系统字体栈。
