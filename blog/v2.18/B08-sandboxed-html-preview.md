# 不可信 HTML 该怎么打开：预览路由的三层沙箱

我们的桌面 AI 应用（本地优先、单人开发）里，产物 HTML 是模型写的。模型写的东西和陌生人发来的附件没有本质区别：里面可能有 `<script>`、有指向外部地址的图片、有试图读取同源数据的小动作。

如果直接把这份 HTML 交给浏览器在应用域名下打开，等于把 XSS 的入口交给了模型。所以产物预览走的是一条独立的、专门为「不可信内容」设计的路径。

## 一、独立路由：先从同源里摘出去

产物不复用图片附件的读取接口，也不挂在页面路由下，而是一条独立路径：按附件 id 取原始字节，只允许三种产物内容类型，图片仍然走旧接口。

独立的意义不在路径好看，而在于**响应头可以只为这一类内容收紧**。图片接口要允许缓存、允许内联展示；产物接口必须假设内容有敌意。两种信任级别混在一个接口里，早晚会为了兼容一方而放松另一方。

| 响应头 | 值 | 作用 |
|---|---|---|
| content-type | 产物声明的 MIME | 只允许 HTML / SVG / Markdown |
| content-security-policy | `sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:` | 禁脚本、禁外链、禁同源能力 |
| x-content-type-options | `nosniff` | 禁止浏览器猜类型 |
| cache-control | `private, max-age=3600` | 只允许本地缓存一小时 |

## 二、逐条拆开这段 CSP

这段策略只有四个指令，但每一个都不能省：

**`sandbox`**：让文档进入一个唯一的不透明源。即使它由应用的域名提供，浏览器也把它当成「来历不明」——读不到应用的 Cookie、碰不到同源的存储、发不出带凭据的请求。这一条是整段策略的地基。

**`default-src 'none'`**：默认全部禁止。脚本、样式表、字体、媒体、框架、连接，一律没有。要放行什么，必须单独写出来。

**`style-src 'unsafe-inline'`**：唯一的放宽项。模板产物把样式写成内联属性与内联 `<style>`，不放行就无法正确渲染。注意它只放行样式，不放行脚本——`unsafe-inline` 出现在 `style-src` 里和在 `script-src` 里完全是两件事。

**`img-src data:`**：只允许 data URI 图片。这样图表里的位图能显示，而指向外部地址的追踪像素一律加载失败，不会把「谁打开了这份报告」泄露出去。

四者合起来的效果是：文档能看，但不能动；能画，但不能联网；能在沙箱里活，但碰不到宿主。

## 三、两层沙箱，各管一段

很多人以为写了 CSP 就够了，或者以为 iframe 的 `sandbox` 属性就够了。这里两层都上：

| 层 | 位置 | 管什么 |
|---|---|---|
| 响应头 CSP | 服务端返回 | 文档自身的行为边界，包括被直接打开时 |
| iframe `sandbox=""` | 前端渲染 | 容器边界：不给脚本、不给表单、不给顶层导航、不给同源 |

iframe 的 `sandbox` 属性留空，等于开启全部限制。这意味着即使 CSP 因为某种浏览器差异没生效，容器这一层仍然拦得住脚本执行与同源访问。

反过来也成立：即使有人把 iframe 属性改坏，服务端的 CSP 仍然在。两层不是重复，是互备——**安全设计里，同一件事由两个独立机制各自保证一次，才叫可靠**。

## 四、为什么不把地址直接交给链接

前端取产物的方式是「带令牌 fetch → Blob → 交给 iframe 或下载函数」，而不是把路由地址塞进 `<a href>` 或 iframe 的 `src`。

三个原因：

1. 桌面壳的鉴权靠请求头，直接导航带不上令牌；
2. Blob 的源是当前页面，但 iframe 的 `sandbox` 属性依然生效，且不会因为导航而绕过中间层；
3. 中间层可以做错误处理：401、404、内容类型不对，都能在界面上给一句人话，而不是一个白屏。

Blob URL 用完要释放。预览面板关闭时释放，重新打开时重新取。长会话里不释放会累积一串再也用不到的 URL。

同一份字节有两种用法：预览进沙箱 iframe，下载走附件头。两者共用一次带令牌的取数，所以「能看到」和「能保存」不会出现一个成功一个失败的分裂状态。如果预览走一条路、下载走另一条路，任何一条鉴权或缓存策略变化，都会造成一半功能坏掉。

## 五、HTML 与 SVG 才是重点

三种产物里，安全模型只管前两种：

- **HTML**：完整沙箱，允许内联样式与 data 图片；
- **SVG**：同样沙箱。SVG 本身可以内嵌脚本与外部引用，所以 `default-src 'none'` 对它同样必要——不能因为它「看起来只是张图」就降级；
- **Markdown**：不在导出范围内，卡片不显示导出入口，本文不展开它的展示方式。

把规则集中在前两种，省掉的是一整类「为文本格式单独设计渲染白名单」的工作。

## 六、下载是另一个边界

预览安全，不等于下载安全。用户点下载拿到的是一个本地文件，离开应用之后由谁打开、在什么环境打开，应用管不着。

所以产品侧做了两件事：产物模板默认不含脚本（图表模板只输出内联 SVG 与样式）；下载文件名做净化，去掉路径分隔符与非法字符，扩展名强制与格式一致。

需要诚实说明的是：应用内预览有沙箱，用户把文件拿到别处打开就没有了。安全边界覆盖的是「在应用里看」，不是「文件在世界上任何地方都安全」。

## 七、离线打开也能用

产物被设计成自包含：样式内联、图形内联、字体用系统字体栈、图片只允许 data URI。这三个约定带来一个额外好处——下载后的 HTML 双击就能看，断网也能看，不需要加载任何外部资源。

反过来，如果模型在 HTML 里引了外部字体或 CDN 样式，预览会是一片空白。这不是 bug，是自包含约定的必然结果：外链在沙箱里被拦，在离线环境里也加载不到。产物要好看，就得自己带齐。

判断一份产物是否合格，有个很土但有效的办法：断网，双击打开，看它还是不是原来那张图。是，就说明它自包含了；不是，就说明它还依赖着外部世界，而这种依赖在沙箱里注定失败。

## 八、验证

预览路由三例：CSP 与 `nosniff` 头存在、`?download=1` 返回附件头与安全文件名、未知 id 与图片 id 被拒绝。卡片侧两例：预览走沙箱 iframe、下载走带令牌的接口。这些断言不检查「页面长得对不对」，只检查安全头与拒绝路径——因为安全属性的回归往往不表现为界面报错，而表现为头悄悄少了一个。
