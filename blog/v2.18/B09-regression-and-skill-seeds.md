# 全量回归抓到的两个旧缺口：清单少两条，透传少一环

我们的桌面 AI 应用（本地优先、单人开发）里，每个功能都会配定向单测，写完就绿。这容易制造一种错觉：功能完成了。全量回归的价值恰恰在于打破这种错觉——它不问「新代码对不对」，只问「新代码接进旧链路之后，还对不对」。

这一轮全量回归抓到的两个问题，都不是新代码写错，而是**新东西没有接上旧的地方**。

## 一、缺口一：技能清单 15 → 17

这一轮新增两条内置技能：一条负责图表类型选择与数据整理，一条负责内容包的检索与高风险分流。

播种逻辑本身没问题，两个技能都能建出来。问题出在另一份清单——用户新建技能时可选的模板列表。新技能只加进了「内置技能播种」，没加进「模板清单」，于是：

- 模板数量断言还停在 15，新加的两条让它变成 17；
- 用户在界面上看不到这两个模板，只能看到内置的那两个，概念上分裂成两套；
- 清单类测试一旦只断言「至少包含旧的那些」，这个缺口可以一直不被发现。

修复是补齐两条模板并对齐计数。教训不在「记得加」，而在**同一个概念存在两份清单时，必须有一条断言把两份钉在一起**。后来补的测试直接断言模板数量与内置技能数量各自为 17 与 5，删一条就红。

## 二、缺口二：执行器没透传产物

这个缺口更隐蔽，也更值得说。

产物工具的单测是绿的：调用工具，返回结果里带着产物引用，断言通过。图表工具的单测也是绿的。但真实链路是：

```text
模型发起工具调用
   ▼
工具执行器（统一包装：权限、超时、错误归一）
   ▼
具体工具 → 返回 { output, artifacts }
   ▼
执行器重新组装结果 ──✗ 这里把 artifacts 丢了
   ▼
工具追踪 / 流式事件 → 界面卡片
```

执行器在包装结果时只挑了它认识的字段，新加的产物字段不在其中。后果是：单元测试里工具返回了产物，生产链路里界面拿不到卡片。两个测试都绿，功能却不成立。

这是一处**旧缺口**，不是这一轮引入的：执行器一直只搬运它已知的字段，任何新字段都会默认被吞掉。修法是把产物与证据一起纳入透传，并补一条端到端断言——从执行器入口进，断言出口同时带 `output`、`artifacts`、`evidence`。

这条断言的形态很关键。如果只测工具本身，永远测不到执行器；只有让测试跨过执行器，缺口才有机会暴露。

## 三、为什么定向测试发现不了这两类问题

| 测试层级 | 覆盖 | 看不见什么 |
|---|---|---|
| 工具单测 | 工具内部逻辑 | 执行器是否搬运了新字段 |
| 服务单测 | 存储与校验 | 清单类数据是否两处一致 |
| 组件测试 | 渲染与交互 | 真实链路里数据是否能到达组件 |
| 全量回归 | 上述全部加跨层组合 | 环境差异（开发态 vs 生产态） |

前两类缺口都落在「跨层」这一格：每一层自己都对，接缝没人测。所以这一轮的结论不是「多写测试」，而是**新字段、新清单必须有一条跨过接缝的断言**。

## 四、验收数字

| 项 | 结果 |
|---|---|
| 静态门禁 | 类型检查、lint、行数、结构、循环依赖全部通过 |
| 单测 | 2980 例全绿：核心 1375、Web 675、共享 338、数据库 247、桌面 179、AI 77、语音 75、配置 14 |
| Web 端到端 | 139/139，生产模式，约 12 分钟 |
| 桌面冒烟 | 10/11 |
| 首屏包体 | `/settings` 483 kB（上一版 481，+0.42%）、`/chat` 467 kB、`/knowledge` 306 kB |
| 共享包体 | 103 kB |
| 桌面未压缩产物 | 约 640 MB（冒烟构建） |
| 数据库 | 零迁移，表结构版本号 42 |

桌面那条失败项是记事本 UI 自动化链路的环境问题，与既有基线一致。它被记录为「已知环境失败」，而不是「本次回归」。这个区分很重要：把所有红灯都当回归，团队会开始忽略红灯；把所有红灯都当环境问题，真正的回归会溜过去。判断依据是**同一项在上一版是否同样失败**。

## 五、端到端为什么要跑生产模式

首轮用开发模式跑 Web 端到端，在设置页重载类用例上出现两次编译超时。开发模式边编译边服务，首个访问页面会触发一次重编译，超时阈值很容易被踩到。

改成生产模式（先构建再启动）之后，139 例稳定通过，用时约 12 分钟。这不只是「换个命令」，而是验收口径的修正：**验收要跑用户实际使用的形态**。开发模式的绿灯不能为生产形态背书，这一点在桌面端已经被教育过一次——开发态与打包态是两个世界。

## 六、两端导出一致性

导出功能有一个容易漏的验收点：Web 与桌面是不是同一套实现。

答案是同一套：桌面壳加载同一份界面，导出在渲染进程的客户端代码里完成，主进程没有新增能力。因此不需要为桌面单独写一套导出测试，只需要在冒烟里确认「桌面里点导出能出文件」。

反过来说，如果两端各写一套，就要各测一套，还要额外测「两边产出的 PNG 是否一致」。共用实现省掉的不只是代码，还有一整类一致性测试。

## 七、这一轮的回归清单

- 新增技能：播种清单与模板清单同时断言数量；
- 新增工具字段：跨执行器的透传断言，出口同时校验产物与证据；
- 新增界面入口：组件测试断言入口出现与隐藏条件（Markdown 不显示导出）；
- 新增接口：安全头与拒绝路径都要断言；
- 新增内容包：哈希失败路径必须断言「没有创建知识库」；
- 全量：静态门禁、单测、生产模式端到端、桌面冒烟、包体、零迁移。
