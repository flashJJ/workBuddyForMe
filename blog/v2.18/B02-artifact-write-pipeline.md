# 一次工具调用如何变成可打开的文件

我们的桌面 AI 应用（本地优先、单人开发）里，模型生成的 HTML 报告原本只能停在对话里：用户全选、复制、粘到编辑器，样式全没了。产物管道要解决的就是最后一厘米——让工具调用的结果变成一个真正能打开、能下载、刷新后还在的文件。

难点不在「写文件」三个字，而在四个约束：写盘的东西不可信、存储不能新增表、产物不能回灌模型上下文、卡片必须和历史消息一起恢复。

## 一、工具契约：先定边界，再写实现

```ts
// 说明性伪代码
artifact_write({
  title:    "订单对账报告",       // 1–80 字，只用于展示与下载名
  filename: "reconciliation",     // 可省略扩展名，非法字符会被清理
  format:   "html" | "svg" | "md",
  content:  "<...>"               // ≤ 2 MB
})
```

三个约束值得单独说：

| 约束 | 值 | 原因 |
|---|---|---|
| 单文件大小 | 2 MB | 超过这个量级基本不是「一张图/一份报告」，而是数据倾倒 |
| 单轮数量 | 3 个 | 防止模型一次刷出十几个文件，让用户无从选择 |
| 权限 | 写操作，走人工确认 | 落盘是有副作用的行为，确认框展示标题、格式、大小 |

权限这一条很实际：读工具可以静默执行，写工具必须让人看到「即将生成什么」。确认框不需要预览全文，但要让用户知道产物类型和体积——这已经足够判断要不要放行。

## 二、为什么复用附件表

新功能最容易做的动作是「新建一张 artifacts 表」。这里刻意没做，理由有三层：

1. 附件表已经在管理「一条记录 + 一个磁盘文件 + 一个 MIME」这套关系，产物只是多了一种内容类型；
2. 零迁移意味着老库直接打开就能用，不需要在启动时跑一次结构变更；
3. 附件的生命周期管理（随对话、随导出）已经有现成路径，新表则要把这套逻辑再写一遍。

需要改的只有两处：MIME 到扩展名的映射表加上 `text/html`、`image/svg+xml`、`text/markdown`；服务层增加一个保存入口，绕过「只允许图片」的旧校验。图片附件继续走原来的读取路由，产物走新的预览路由，两条路径互不干扰。

| 类型 | MIME | 扩展名 |
|---|---|---|
| HTML | `text/html` | `.html` |
| SVG | `image/svg+xml` | `.svg` |
| Markdown | `text/markdown` | `.md` |

文件名会被规范化：去掉路径分隔符与非法字符，扩展名强制与格式对齐。用户传 `report.html` 但格式声明为 `svg`，最终落盘仍然是 `.svg`——扩展名跟着内容类型走，不跟着用户输入走。

## 三、落盘：不留半成品

写文件与写记录是两步，任何一步失败都可能留下「有记录没文件」或「有文件没记录」的残局。处理原则是把它当成一个整体：写入成功后再对外可见，任一步失败就清掉残留的文件与元数据。

```text
校验参数（格式白名单 / 大小 / 标题长度）
   │ 失败 → 返回可读错误，不抛未捕获异常
   ▼
生成安全的存储名 → 写文件
   │ 失败 → 清残留，返回失败
   ▼
登记附件记录（MIME、字节数、扩展名）
   │ 失败 → 删文件，返回失败
   ▼
返回产物引用（id / 标题 / 格式 / 大小）
```

工具失败分两类：参数不对抛参数错误，让模型能据此重试；服务不可用或校验不过返回 `ok=false` 加一句可读原因，不让异常穿透到编排层。这个区分很重要——前者是模型的错，后者是环境的错，混在一起模型会一直重试。

## 四、产物卡片为什么长在工具追踪区

最直觉的做法是给消息加一个新的内容片段类型，让产物像图片一样出现在气泡里。这条路被否掉了，原因是它要动多模态消息协议：历史消息的序列化、分享导出、压缩层、前端渲染器全都要跟着改。

实际方案是挂在工具追踪条目上：

- 工具追踪条目与流式结束事件各加一个可选的产物数组；
- 卡片展示标题、格式、大小，以及预览、下载、导出三个动作；
- 刷新后从消息表里的追踪 JSON 原样恢复，不需要额外的关联查询；
- 模型只看到一句「已生成产物：…」的摘要，看不到产物本体。

这样做的代价是卡片位置固定在工具调用那一行，不是独立的对话气泡；收益是整条链路没有新增协议分支。对一个单人维护的项目来说，少一个协议分支，就少一类将来会漏改的地方。

## 五、预览与下载：不要把 URL 直接交给链接

预览路由返回原始字节，并带上三个头：内容类型、`nosniff`、以及一段只允许内联样式与 data 图片的安全策略。前端不把产物地址写进 `<a href>`，而是带令牌 `fetch` 成 Blob，再交给沙箱 iframe 或下载函数。

原因有两个：

1. 桌面壳的鉴权靠请求头里的令牌，直接导航的链接带不上头，会 401；
2. 直接把地址交给浏览器，等于让不可信 HTML 获得与应用同源的执行环境——预览必须走沙箱。

下载走 `?download=1`，服务端返回附件头与安全的文件名。文件名里的中文保留，路径分隔符清理掉。

## 六、刷新恢复与清理

产物记录跟着消息走，刷新后从追踪 JSON 恢复卡片，这是「可交付」的最低要求——如果刷新一次图表就消失，用户会认为功能坏了。

清理策略刻意保守：

- 随对话删除而删除，随对话导出而导出，不单独维护一套产物生命周期；
- 不进入备份核心，避免备份体积被产物拖爆；
- 不做无限增长保护之外的额外回收，单文件 2 MB、单轮 3 个已经把上限压住。

## 七、这一轮踩到的边界

| 边界 | 现象 | 处理 |
|---|---|---|
| 单轮 3 个未运行时计数 | 契约与文案写了上限，实现没在编排层数 | 登记为已知边界，后续补计数 |
| 通用 HTML 不承诺 PNG | 用户点导出发现没有图表 | 卡片只对含内联 SVG 的产物显示导出入口 |
| 外链资源被阻断 | 模型在 HTML 里引了外部字体，预览一片空白 | 预期行为：产物必须自包含 |
| 卡片不是独立气泡 | 长对话里产物夹在工具行中间 | 接受这个位置，换取不改消息协议 |

定向单测覆盖了格式、文件名、大小、读取、图片拒绝、工具成功/失败/参数校验、预览路由的 CSP 与下载头、卡片的 iframe 与下载调用，合计四十余例。
