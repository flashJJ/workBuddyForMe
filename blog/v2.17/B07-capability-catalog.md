# 能力目录：让模型先看见「装什么、要什么权限」

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，能力包安装在本机，工具在每轮对话出站前装配。上一阶段的安装路径是：用户自己找到 ZIP、上传、校验、启用；MCP 服务则要自己填命令或从几个预置里挑。

这条路径的前提是「用户已经知道要装什么」。但真实对话里，用户往往只知道自己的需求：「能不能把每天的笔记整理成周报」「有没有办法定时检查某个目录」。模型如果不知道有哪些能力可装，就只能回答「我做不到」。

能力目录要解决的就是这件事：把「有什么可装、装了会怎样、要什么权限」变成模型可以检索的结构化数据，并在安装前让用户看清代价。

## 一、手动安装路径的尽头

| 环节 | 手动路径 | 缺了什么 |
|---|---|---|
| 发现 | 用户自己知道包名，或去翻文档 | 模型无法按意图找到能力 |
| 判断 | 看包描述，猜它要什么权限 | 权限、效果、新增工具不可见 |
| 安装 | 上传 ZIP，校验后自动启用 | 没有统一的安装代理 |
| 使用 | 手动去助手表单勾选工具 | 装完还要再走一步 |

四个环节里，真正难的不是上传，而是**发现与判断**。上传只是一次文件操作；发现需要目录，判断需要结构化的权限与效果声明。目录的价值就在于把这两件事前置。

## 二、`CapabilityCatalogEntry` 的字段

目录条目是一个纯数据 schema，不带任何安装逻辑：

| 字段 | 含义 | 谁在用 |
|---|---|---|
| `id` / `name` | 稳定标识与展示名 | 检索、安装、去重 |
| `kind` | 能力类型 | 过滤、展示分组 |
| `description` / `tags` | 用途与关键词 | 意图匹配 |
| `permissions` | 需要的权限集合 | 安装前展示 |
| `effects` | 会产生什么效果 | 用户判断风险 |
| `source` | 随应用内置，还是 MCP 预置 | 来源说明 |
| `version` | 版本号 | 展示、后续升级 |
| `toolNames` | 安装后预计新增的工具 | 判断能力边界 |
| `installStrategy` | 打包安装还是预置安装 | 安装代理分流 |

字段设计的取舍是**够用即可**：没有作者、没有下载量、没有评分，因为首批目录只有官方内置的精选包。等目录真能收第三方内容时，这些字段才需要被认真设计——现在加进去只会增加伪造空间。

`toolNames` 是这一版特意加的。用户批准安装时最关心的问题不是「这个包叫什么」，而是「装完我的助手会多出哪些手」。把预计新增的工具提前列出来，比任何一段描述都有说服力。

## 三、五个内置精选包

首批目录只收随应用发布的精选包，每类能力一个示例：

| 能力类型 | 这个包装什么 | 新增工具 |
|---|---|---|
| 技能 | 一段可复用的工作方法描述 | 以条目声明为准，多数不新增 |
| 工作流 | 一条可触发的流程定义 | 以条目声明为准，多数不新增 |
| 宠物动作 | 一组桌宠动作与触发条件 | 以条目声明为准，多数不新增 |
| 事件脚本 | 对本地事件的响应脚本 | 以条目声明为准，多数不新增 |
| 报告组件 | 一种可嵌入的报告视图 | 以条目声明为准，多数不新增 |

`toolNames` 一栏只有在条目确实会带来新工具时才非空，这个事实必须在候选里说清。用户看到「预计新增工具：无」时，风险判断会和看到「新增 3 个只读工具」完全不同——所以展示时不能把「未知」渲染成「无」。

## 四、检索是关键词打分，不是向量

目录检索没有引入向量库，用的是最朴素的关键词与标签打分：

```ts
searchCatalog(query, kind?) {
  // 1. 按 kind 过滤（可选）
  // 2. 对 name / description / tags 做关键词命中打分
  // 3. 合并安装状态：installed / not-installed
  // 4. 返回候选列表，按分数排序
}
```

选择关键词而不是向量的理由很实际：首批只有五个条目，向量检索的召回收益接近于零，却要引入嵌入模型、索引存储和一次额外的模型调用。目录规模小的时候，**可解释的打分比模糊的相似度更有用**——用户问「为什么给我推荐这个」，关键词命中能回答，向量相似度只能回答「因为算出来像」。

`kind` 过滤是独立参数而不是拼进查询词。模型说「我要一个工作流类的能力」时，这是结构化意图，不该被当成关键词去碰运气。

检索结果会带上安装状态，这样同一个能力不会被重复推荐。这一版没有实现独立的「列出已安装能力」工具，因为检索结果已经带了状态，够用。

## 五、候选必须展示什么

模型拿到候选之后，要在调用安装前把这些信息说给用户听：

| 展示项 | 回答用户的问题 |
|---|---|
| 名称与用途 | 这是干什么的 |
| 能力类型 | 它属于哪一类 |
| 权限 | 它要读什么、写什么 |
| 效果 | 装上之后会发生什么 |
| 预计新增工具 | 助手会多出哪些能力 |
| 来源与版本 | 从哪来、是不是随应用发布 |
| 安装状态 | 已经装了，还是可以装 |

这张表其实是审批的一部分。审批框能展示的空间有限，模型在调用前的说明才是用户真正读到的内容。所以「展示什么」不是 UI 细节，而是安装决策的信息基础。

## 六、为什么只收内置包

目录的第一版明确不开放远程市场：

- 只收随应用发布的精选包，目录数据是代码常量，不走网络；
- 不提供任意 URL 下载，不提供第三方上传入口；
- MCP 预置条目暂不进目录，安装会明确返回「暂不支持自动安装」。

远程市场的诱惑很大：一旦开放，目录会迅速变丰富。但代价是签名链、供应链审核、下架机制、版本回滚全都要跟着做，而这些东西在单人项目里没有足够的维护带宽。**先证明「目录 + 审批 + 绑定」这条链路能跑通，再谈内容规模**，是更稳的顺序。

## 七、两个工具与权限边界

目录本身不产生副作用，真正的动作由两个工具承担：

| 工具 | 权限 | 作用 |
|---|---|---|
| 检索 | `read` | 按意图返回候选与元数据 |
| 安装 | `write` | 经审批后安装并绑定只读工具 |

检索是只读的，不写审计、不改状态；它返回的安装状态只用于去重，不构成一次安装记录。安装则是这一版唯一一个「必须弹审批且无法跳过」的工具，下一篇专门讲。

把检索与安装拆成两个工具，而不是一个「帮我装个能力」的复合工具，是为了让审批点足够窄：用户批准的是「安装这个具体条目」，不是「让模型自己去挑一个装」。

## 八、目录规模与工具声明膨胀

工具声明会占用上下文预算。目录变大后，如果每个条目都往工具描述里塞，模型的选择质量反而会下降。

这一版的约束是：目录按意图召回，只把少量候选交给模型；条目描述限长；安装后默认只绑定只读工具，危险工具仍要手动勾选。三条约束合起来，保证「能力变多」不会直接变成「上下文变挤」。

## 九、验证

- 目录服务 **7 例**：关键词与标签命中、kind 过滤、空结果、安装后状态、重复安装拒绝、未知条目、预置条目拒绝；
- 工具层 **9 例**：目录不可用、候选展示、kind 透传、参数校验、安装成功绑定、无绑定能力提示、绑定失败不误报安装失败、安装失败不抛出；
- 权限门 **10 例**：含强制审批在完全放行条件下仍然生效；
- 内置工具总数 **23 个**。
