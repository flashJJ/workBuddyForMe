# 内置搜索：只返回标题、链接和摘要，正文交给网页读取

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，工具全部在本机服务进程里执行，联网只发生在用户明确配置过的通道上。在它能读网页、能查本地知识之后，还缺一个最朴素的入口：**搜索**。

没有搜索时，用户问「最近有什么行业新闻」，助手只能回答「我无法访问网络」。用户手里即使有一个具体 URL，网页读取工具也只能读那一个页面——它不知道去哪里找更多页面。

实现搜索有两条路：把搜索结果页整页抓回来塞进上下文，或者只取摘要、把正文交给另一个工具。这一版选了后者，原因写在下面。

## 一、为什么搜索必须是内置工具

能力包的边界是「携带配置与声明」，不携带任意可执行代码。它可以是技能描述、工作流、宠物动作、事件脚本、报告组件，也可以是一段 MCP 服务配置，但不会把一份搜索客户端塞进某个包里。

所以「自带搜索」只能做成内置工具：

- 不依赖任何能力包安装，开箱就存在于工具清单里；
- 受助手的工具白名单控制，用户可勾选、可关闭；
- 后端可替换，未配置时给出可执行的错误，而不是伪造结果。

这也解释了一个常见误解：把搜索做成「一种能力包」看起来更模块化，实际会让没装包的用户永远搜不到，而搜索恰恰是最不该有安装门槛的工具。

## 二、SearchProvider 抽象

搜索后端被抽象成一个很窄的接口，只有两个方法：

```ts
interface SearchProvider {
  id: string;
  search(input: SearchInput, signal?: AbortSignal): Promise<SearchResponse>;
  testConnection(): Promise<{ ok: boolean; message: string }>;
}
```

`search` 接受查询参数与取消信号，返回统一的结果结构；`testConnection` 只回答「这个后端现在能不能用」，供设置页的测试按钮使用。两个方法分开，设置页的测试结果就不会混进对话上下文，后端出问题时也能先分清是「连不上」还是「搜不到」。

首批只实现两个适配器：自建 SearXNG 与 mock。前者不需要 API Key，适合本地优先的场景；后者只用于测试与演示。带 Key 的云搜索后端留到后续版本，因为它们要先解决密钥加密存储，不能为了多接一家而把密钥管理做成半成品。

## 三、`web_search` 的契约

| 项 | 约定 |
|---|---|
| 权限 | `read` |
| 参数 | `query` 1–200 字；`maxResults` 1–8，默认 5；`freshness` / `site` / `locale` 可选 |
| 返回 | `{ results: [{ title, url, snippet, source, publishedAt? }], provider }` |
| 超时 | 10s |
| 错误 | 未配置 / 鉴权失败 / 限流 / 不可达 / 空结果 |
| 审计 | 记录 provider、结果数、耗时、成功或失败，不落查询正文 |

三个参数上限都写死在契约里，而不是交给模型自由发挥。查询词限长，是因为超长查询既没有检索价值，也会放大注入面；结果数上限 8，是因为搜索结果塞得越多，上下文里属于「外部不可信内容」的比例就越高。

返回值里有一个容易被忽略的字段：`provider`。它让模型和用户都知道「这批结果来自哪个后端」，也让审计能对上账。没有它，多后端切换后出问题就无法归因。

## 四、搜索与读取为什么分开

这是这一版最重要的一个设计决定：**搜索只返回摘要，正文由网页读取工具按需获取**。

| 方案 | 上下文成本 | 超时风险 | 注入面 |
|---|---|---|---|
| 搜索时抓取前 N 条正文 | 一次 N 个页面的正文 | 任一页面慢就拖垮整次调用 | N 个页面的全部内容 |
| 只返回摘要，按需读正文 | 5 条摘要，约几 KB | 单次请求 10s 封顶 | 只在用户或模型主动读取时出现 |

还有一层工程原因：搜索接口通常是聚合服务，抓正文要走另一套网络路径、另一套 SSRF 防护、另一套内容清洗。把它们揉进一个工具，等于让搜索工具承担两种失败模式，错误文案也会变得含混。

分开之后，两个工具各自有清晰的职责：搜索回答「有哪些相关页面」，读取回答「这个页面说了什么」。模型可以先看摘要，再决定读哪一条——这正是人使用搜索引擎的方式。

网页读取工具沿用既有的 SSRF 防护，不因为「搜索结果里的链接」就获得额外信任。搜索结果是外部输入，链接同样不可信。

## 五、默认关闭与助手开关

搜索是唯一一个会让查询词离开本机的能力，所以默认状态必须是关闭：

- 设置里的 provider 默认是 `none`，未配置时工具返回「未配置搜索后端」的可执行错误；
- 助手表单里 `web_search` 是独立勾选项，不随其他只读工具默认开启；
- 首次开启时明确告知：查询会发送到所配置的后端；
- 关闭后助手不会把它放进本轮工具集，需要时再回表单勾选。

「默认关闭」和「工具存在」并不矛盾：工具存在解决的是「装了能力包才能搜」的安装门槛，默认关闭解决的是「不问一声就把查询发出去」的隐私问题。

## 六、引用怎么落到回答里

搜索结果里的每一条都会被映射成引用对象：标题、链接、摘要，链接指向原文。回答生成后，界面按既有引用渲染方式展示来源列表，分享与导出沿用同一套渲染。

这里没有新建一套引用体系，而是复用既有结构。复用的好处是：引用在对话、分享、导出三处表现一致；坏处是搜索结果的字段必须收敛到既有引用字段，`publishedAt` 这类信息只能作为附加字段存在，不能改变渲染契约。

## 七、错误文案要对得上动作

| 错误 | 文案要点 |
|---|---|
| 未配置 | 去设置页选择搜索后端，并说明查询会离开本机 |
| 鉴权失败 | 检查后端凭据；不要提示「网络问题」 |
| 限流 | 稍后重试；不自动连续重试 |
| 不可达 | 检查 endpoint 与网络 |
| 空结果 | 换关键词或放宽条件，不表示「搜索坏了」 |

空结果是最容易被误报成故障的一种。搜索没有命中是正常结果，返回空列表并说明「没有找到相关结果」，比抛一个红色错误更准确。
