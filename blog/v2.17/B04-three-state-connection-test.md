# 连接测试不该只有成功和失败：三态语义与兼容字段

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，供应商配置全部存在本机。设置页里有一个「测试连接」按钮，用户点它，是想知道「我填的这些东西，到底能不能用」。

多数应用把它做成布尔值：成功或失败。这个抽象太粗，会在两个方向同时说谎——**把没验证过的说成成功，把端点不存在说成鉴权失败**。前者让用户带着一个坏配置进入对话，后者让用户去修一个根本没问题的 Key。

## 一、二元结果的两种谎言

| 实际情况 | 二元结果给出的结论 | 用户的下一步 |
|---|---|---|
| 端点可达，但账号下没有任何对话模型 | 成功 | 进入对话，第一条消息就失败 |
| 模型列表端点不存在 | 失败（通用错误） | 检查 Key、换套餐，全都无效 |
| 模型列表返回正常，但模型是别的套餐的 | 成功 | 对话时报模型不可用 |
| 首字探活成功 | 成功 | 正确，但无法区分是否只是列表可用 |

三态的价值不在「多一个枚举值」，而在于把**「能连上」和「能验证」拆开**。能连上是一个网络事实，能验证是一个能力事实，两者之间隔着「有没有模型」这道坎。

## 二、三态定义

| 状态 | 判定 | 界面文案 |
|---|---|---|
| `verified` | 模型列表成功，或首字探活成功 | 连接成功 |
| `reachable_unverified` | 端点可达，但没有可验证的对话模型；或厂商标为只能手填且用户还没添加模型 | 可达但无法验证，请先添加模型 |
| `failed` | 鉴权、网络、协议或首字探活明确失败 | 连接失败，附带原因 |

`reachable_unverified` 是这一版最重要的一个状态。它不是「失败」，也不是「成功」，而是**诚实地说「我只验证到一半」**。承认验证不完整，比给一个漂亮的绿灯更有用。

## 三、判定顺序与检查项

返回结构在既有字段上做加法：

```ts
interface ProviderConnectionResult {
  ok: boolean;                    // 兼容字段：status === 'verified'
  status: 'verified' | 'reachable_unverified' | 'failed';
  checks: Array<{
    step: 'models' | 'chat-probe' | 'protocol';
    ok: boolean;
    message?: string;
  }>;
  modelId?: string;
}
```

`checks` 是给用户看的证据链，不是内部日志。它的意义是：当结论是「可达但无法验证」时，界面能说清是哪一步没通过——模型列表没通过，还是探活没有可用模型。

检查项覆盖三个环节：

1. **协议**：请求能否按声明的协议组装；
2. **模型**：模型列表或厂商专用接口是否可用；
3. **探活**：用已配置的对话模型发一次最小请求。

任何一步得到明确失败，就停在 `failed`；模型步失败但端点可达，且没有模型可探活，则停在 `reachable_unverified`。

## 四、首字探活只用手动配置的对话模型

探活有两个诱惑，都必须抵住：

**第一，偷偷创建模型。** 发现列表为空时，顺手用推荐模型创建一个再探活，看起来能让测试「成功」。但这会在用户不知情的情况下改写他的模型列表，而且探活成功也不代表这个模型属于他的套餐。正确做法是：没有已配置的对话模型，就不探活，返回「可达但无法验证」。

**第二，对所有厂商都探活。** 探活会消耗真实额度、触发限流，也会让「只读检查」变成一次实际调用。它只应该在模型列表不可用、且用户已配置对话模型时启用——此时它是唯一能证明「这个模型真能用」的手段。

「只用手动配置的模型」这句话还有一层含义：自动发现出来的模型只是候选，用户选中并保存之后才算配置完成。测试的对象是用户的选择，不是应用的猜测。

## 五、兼容字段：保留一个 `ok`

返回结构从「抛错 / 返回 true」升级为三态，必然影响调用方。这一版的处理是：

- 新增 `status` 与 `checks`；
- 保留 `ok`，语义固定为 `status === 'verified'`；
- 既有调用方不改也能工作，只是看不到「可达但无法验证」这一层；
- 设置页改为读 `status`，展示三态徽章。

保留兼容字段不是永久兼容，而是给唯一消费方一个不需要同步改动的窗口。这个应用里连接测试只有设置页一个消费方，所以升级可以做得干脆；如果消费方很多，就得先做一轮调用点盘点，而不是靠兼容字段硬撑。

## 六、`failed` 为什么仍然走 HTTP 错误层

这里有一处刻意的「不统一」：服务端成功响应只返回 `verified` 与 `reachable_unverified`；明确的失败仍然走既有的错误响应，由界面映射成红色「连接失败」。

原因很实际：这个应用原有的错误处理、重试策略、日志与测试都建立在「非 2xx 即失败」上。把失败改成 200 加一个 `status: failed`，会让所有既有判断失效，收益只是「三种状态都在响应体里」这一点形式统一。

代价是文档里必须写清：三态中的 `failed` 不由成功响应表达。这不是遗漏，是**为了不破坏既有错误层而做的取舍**，也记录在契约偏差里。宁可承认不完美，也不要为了形式统一制造一批静默失效的错误分支。

## 七、徽章与文案

设置页把三态映射成三种视觉与文案：

| 状态 | 视觉 | 主文案 | 次要说明 |
|---|---|---|---|
| `verified` | 绿色 | 连接成功 | 显示验证用的模型 ID |
| `reachable_unverified` | 黄色 | 可达但无法验证 | 提示先添加对话模型，或该厂商不支持列表 |
| `failed` | 红色 | 连接失败 | 按鉴权 / 网络 / 协议给出具体原因 |

黄色这一档最容易被产品化地「优化」掉：设计评审时总有人说「用户不喜欢黄色」。但把黄色改成绿色，就等于把「没验证」说成「验证过」；改成红色，就等于把「能用一半」说成「不能用」。三态的意义就是拒绝这两种简化。

## 八、验证

- 服务层 **10 例**：覆盖列表成功、列表 404 回落、鉴权失败、限流、超时、空列表、只能手填无模型、只能手填有模型、探活成功、探活失败；
- 设置页 **6 例**：三态徽章与文案、兼容字段为真时的展示、失败映射；
- 静态门禁全绿。

这些用例里没有一条依赖真实厂商账号。三态是**语义测试**，只要能构造出响应，就能验证判定；这也是它比「连一次真 Key 看看」更可靠的地方。
