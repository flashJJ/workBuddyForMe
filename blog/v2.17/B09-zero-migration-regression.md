# 一次加三条能力线，为什么数据库一行没动

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，数据存在本机，用户可能是从两三年前的版本一路升上来的。对这类应用，「升级能不能直接打开旧数据」不是运维细节，而是产品能否被信任的前提。

这一版同时加了厂商描述、内置搜索、能力安装三条线。按常规节奏，至少会想加两张表：一张存搜索配置，一张存目录条目。实际结果是 **零迁移**：表、列、索引一个没加，schema 版本号原地不动。

## 一、新功能默认会想加表

| 诱因 | 常见的反射动作 | 这一版的选择 |
|---|---|---|
| 搜索有 provider、endpoint、密钥、上限 | 新建搜索配置表 | 写进既有设置 JSON |
| 目录有版本、权限、效果、工具名 | 新建目录表 | 目录作为代码常量 |
| 安装要记录来源、时间、状态 | 新建安装记录表 | 复用能力包表与审批审计 |
| 厂商描述要持久化 | 新建厂商表 | 仍由设置 JSON 承载选择结果 |

四个诱因里，前三个都指向「新实体」。但仔细看会发现，它们存的其实是**配置与引用**，不是新的业务对象：搜索是设置的一部分，目录是随应用发布的静态数据，安装状态本来就在能力包表里。

## 二、三条主线各自落在哪

| 主线 | 需要持久化的东西 | 落在哪 | 是否改 schema |
|---|---|---|---|
| 厂商 | 用户选中了哪家、填了什么 Base URL 与模型 | 既有设置 JSON | 否 |
| 搜索 | provider、endpoint、上限、超时、私网放行开关 | 既有设置 JSON | 否 |
| 能力 | 装了哪个包、启用了哪些工具 | 既有能力包表 + 助手工具白名单 JSON | 否 |

密钥不新建存储：它走既有的本地加密字段，和别的敏感设置共用同一套读写路径。这条复用尤其关键——如果为搜索单独做一套密钥存储，就要单独实现加密、掩码、迁移与清除，任何一处漏掉都是安全问题。

厂商描述本身也不落库。落库的只有「用户的选择」，描述数据随应用版本更新。这样厂商新增、改名、改推荐模型时，不需要写数据迁移，只要改描述文件。

## 三、为什么能不改 schema

三条线能复用，是因为它们都没有产生**新的关系**：

- 搜索配置是「一个全局设置」，设置 JSON 本来就是键值容器；
- 目录条目是「应用自带的静态清单」，代码常量比表更适合，还能跟着类型检查走；
- 安装结果是「一个能力包的启用状态」，能力包表已经记录；
- 工具白名单是「助手与工具的多对多」，既有 JSON 字段本来就存这个。

反过来说，如果这一版要做「目录服务端下发」「安装历史分页查询」「多设备能力同步」，那就必须加表——因为这些需求要的是查询、索引与关系。零迁移不是能力，而是**需求没有越界**的副产品。

## 四、零迁移怎么验收

零迁移不能靠一句「我们没写迁移」来证明，要有可检查的口径：

| 检查项 | 期望 |
|---|---|
| 数据库 schema 版本常量 | 保持 42，与上一版一致 |
| 新增表 | 0 |
| 新增列 | 0 |
| 新增索引 | 0 |
| 旧库启动 | 直接可开，不触发升级流程 |
| 新设置字段 | 缺省值由读取层兜底，不依赖迁移写入 |

最后一行是容易漏的：即使不加列，新增的配置字段也需要有缺省值。旧库读出来的设置对象里没有 `searchSettings`，读取层必须给出「未配置」的默认状态，而不是崩在 `undefined` 上。零迁移的完整含义是「旧数据能被新代码正确解释」，不只是「没跑迁移脚本」。

## 五、回归矩阵

| 项 | 结果 |
|---|---|
| 静态门禁（类型 / lint / 行数 / 结构 / 循环） | 全部通过 |
| 全量单测 | **2922 例**，8 个包 |
| 生产模式 Web e2e | **139/139** |
| 桌面冒烟 | **10/11**，1 项为环境相关失败 |
| 数据库迁移 | 零迁移，版本号 42 |
| 首屏包体 | `/settings` 481 kB |

单测的包分布也值得记一笔：配置 14、语音 75、桌面 179、数据库 247、ai 77、shared 338、core 1341、web 651。上一版是 2882 例，这一版增加 40 例，增量集中在 ai 的厂商与搜索、core 的工具与权限门、web 的设置面板。

桌面冒烟的那 1 项失败是记事本 UIA 保存链路，受本机环境影响，与上一版基线完全一致。**「和基线一致」是这里唯一有意义的判断标准**：如果上一版也失败，这一版再失败就不是回归；如果上一版通过、这一版失败，哪怕看起来像环境问题，也要先当回归查。

## 六、包体

| 路由 / 产物 | 大小 | 说明 |
|---|---|---|
| `/settings` | 481 kB | 上一版 479 kB，**+0.42%**，远低于 5% 门槛 |
| `/chat` | 463 kB | 对话主路由 |
| `/flows/[id]` | 388 kB | 流程编辑页 |
| 共享 First Load | 103 kB | 无明显变化 |

包体增长几乎全部来自设置页新增的搜索面板与三态徽章文案。没有引入新的 UI 库，没有把搜索适配器打进客户端，也没有为了「代码优雅」把服务端模块共享到前端。

## 七、客户端为什么只多了一个枚举

搜索适配器全部在服务端运行，客户端只拿到设置 schema 里的 provider 枚举，用于渲染下拉框。

这个边界是刻意守住的：

- 适配器依赖 Node 的 HTTP 栈与 DNS 解析，打进客户端既跑不起来，也会拖大包体；
- 密钥解密只在服务端发生，客户端拿到的是掩码；
- 搜索结果的清洗在服务端完成，客户端只负责渲染引用。

判断一个模块该不该进客户端，标准不是「它是不是 TypeScript」，而是「它运行时需要什么」。需要文件系统、DNS、密钥的模块，天然属于服务端。

## 八、这一版没覆盖的部分

- 没有浏览器端的安装审批 e2e：mock 模型不产出函数调用，无法稳定触发安装工具，审批路径由权限门与工具单测覆盖；
- 没有真实 Key 的搜索冒烟：默认 CI 不跑外部凭据，夜间或手动脚本留到后续；
- 桌面冒烟的环境失败项没有修，只确认「非本版回归」。

这三条都写进了验收记录。零迁移与回归不降级是这一版的硬指标，但硬指标达成不等于测试没有盲区——尤其是审批这种依赖交互形态的路径。

## 九、这一版的纪律

- 不新增运行时依赖；
- 不改表、列、索引；
- 不重写供应商表单；
- 不扩协议；
- 新增能力一律先问「能不能落在既有结构里」，不能才考虑迁移。
