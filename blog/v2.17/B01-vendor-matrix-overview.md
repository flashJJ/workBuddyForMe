# 接不上、搜不到、装不进：三个断点为什么必须分开修

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手：模型调用、工具执行、能力安装都跑在本机服务进程里，桌面壳只负责窗口与系统集成。当它能对话、能读网页、能调工具之后，用户遇到的「不能用」并没有变少，只是换成了三种更像故障的体验。

在配置面板里填好 Base URL 和 Key，点测试，转两秒，红字「连接失败」，可同一个 Key 在别处明明能用；问一句「最近有什么行业新闻」，助手只能回答「我无法访问网络」；在设置页看到一个能力包，点进去发现要自己上传 ZIP。

这三件事在用户眼里都是「缺功能」，在实现里却是三套完全不同的机制。把它们当成一个笼统的「兼容性」问题一起修，最常见的结局是每条都只修一半：搜索做成了半自动、安装还是手动、厂商仍然一家一家特判。

## 一、三个断点，三种问题归属

| 断点 | 用户看到的现象 | 真正的问题在哪 | 顺手修会怎样 |
|---|---|---|---|
| 接不上 | 测试连接失败、模型列表为空、只能手填 | 厂商差异没有被描述、发现策略只有一条路径、测试结果只有二元 | 每来一家厂商就加一个预设常量和一个 if 分支 |
| 搜不到 | 「我无法访问网络」、没有来源引用 | 内置工具集里没有搜索工具、搜索后端没有抽象 | 把搜索写进某个能力包，没装包的用户照样搜不到 |
| 装不进 | 需要手动上传 ZIP、手动填 MCP 命令 | 缺少能力目录、缺少安装代理、缺少审批与绑定 | 开一个远程市场，把供应链和审核成本一起背上 |

这张表的第三列是这一版所有取舍的起点：**先判断问题属于哪一层，再决定改哪里**。判断错了，代码量会翻倍，而用户体验只会前进一小格。

## 二、为什么搜索不能靠能力包解决

能力包的设计边界是「携带配置与声明」，不携带任意可执行代码：它可以是技能描述、工作流定义、宠物动作、事件脚本、报告组件，也可以是一段 MCP 服务配置，但不会把一份搜索客户端塞进某个包里。

于是「自带联网搜索」只能做成**内置工具**。它要满足三个条件：在没有安装任何能力包时可用；在助手的工具白名单里可勾选；在没有配置后端时给出明确的、可执行的错误，而不是伪造几条结果。

同样，「自主装能力」也不是新增一种能力类型能解决的。它需要三件东西：一个模型能检索的目录、一个必须走人工审批的安装动作、一条安装后把工具接进下一轮的绑定路径。缺任何一件，用户都还得回到设置页手动操作。

## 三、三条主线各自交付什么

| 主线 | 交付内容 | 明确不做 |
|---|---|---|
| 厂商可描述 | 厂商描述文件 + 查询层；模型发现按四级回落；连接测试三态 | 不新增第二套协议；不为单厂商 fork 聊天管线 |
| 联网可开箱 | 搜索 provider 抽象；内置搜索工具；设置面板与助手开关；来源引用 | 不做默认 HTML 抓取；不做云端搜索代理 |
| 能力可装载 | 能力目录；检索与安装两个工具；强制人工审批；下一轮只读工具绑定 | 不开放远程市场；不做同轮热替换 |

三条主线看起来彼此无关，其实共用一条纪律：**能用数据表达的，不要用分支表达；能交给审批的，不要交给默认值。**

## 四、每条主线的完整链路

```text
厂商： 填 Base URL / Key → 发现模型 → 三态测试 → 选模型 → 对话
搜索： 配置后端 → 助手勾选工具 → 搜索摘要 → 按需读正文 → 回答带来源
能力： 检索目录 → 说明权限 → 人工审批 → 安装 → 下一轮只读工具可用
```

注意三条链路各自的「最后一公里」：厂商那条要走到对话，搜索那条要走到带来源的回答，能力那条要走到下一轮真正能调用。任何一条停在「接口返回 200」，都不算交付完成。

## 五、三条主线共享的边界

- 协议仍是原来那两种，协议扩展留到后续版本评估，避免把「兼容」一次性做成大重构；
- 数据库零迁移，设置、工具白名单、能力包表全部沿用既有结构；
- 搜索适配器只在服务端运行，客户端 bundle 里只增加一个 provider 枚举；
- 能力安装只在交互式会话可用，无人值守运行一律拒绝；
- 不引入新的运行时依赖，HTTP 客户端沿用现有的。

这些边界不是保守，而是让「可连通」这件事能在一次交付里被完整验证。任何一条放开，验收口径就会变成「大部分场景能用」，而不是「每条路径都能走完」。

## 六、为什么这次不扩协议

「兼容更多厂商」最直觉的做法是新增第二套协议，比如再实现一套消息格式。但它会把改动面从「读一个字段」扩大到「重写请求组装、错误映射、流式解析、工具调用编码」。

这一版只做一件事：把厂商之间的差异收敛成描述数据，适配器仍然只按协议选择。协议本身没有增加，厂商数量却可以继续增加。取舍的标准很简单：**如果新厂商能用现有协议跑通，就只加数据；跑不通，再单独立项。**

## 七、三条主线怎么各自验收

| 主线 | 可验收的出口 |
|---|---|
| 厂商 | 新增一家 OpenAI 兼容厂商只新增一个描述文件；不提供模型列表的厂商能走完「配置 → 添加模型 → 三态测试 → 对话」 |
| 搜索 | 未安装任何能力包、只配置搜索服务，就能完成「搜索 → 读取正文 → 带来源回答」；未配置时明确报错 |
| 能力 | 模型能检索目录并说明权限与来源；用户批准后安装；未批准不落库；只读工具下一轮可用，危险工具手动 |

三条出口都写成了「用户能走完的一条路径」，而不是「某个函数被调用过」。这是验收口径和测试用例之间最容易被忽略的差别。

## 八、失败路径同样要设计

三条主线都有「不成功」的状态，而这些状态最容易被写成一句泛泛的错误提示：

| 场景 | 不允许的处理 | 应有的处理 |
|---|---|---|
| 厂商不提供模型列表 | 报「鉴权失败」 | 说明端点不存在，引导手填或使用推荐模型 |
| 搜索后端没配置 | 返回空结果列表 | 明确提示去设置页配置，错误可执行 |
| 能力安装被拒绝 | 静默失败或部分写入 | 不落库、不改白名单、留下审计记录 |

失败路径的设计质量，决定用户能不能自己把问题解决掉。把「端点不存在」误报成「Key 错误」，用户会去换一个根本不需要换的 Key，然后彻底失去信任。
