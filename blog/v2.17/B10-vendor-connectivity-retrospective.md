# 复盘：把「兼容」拆成三件事之后，留下了什么

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手。这一版没有交付一个能一句话说清的大功能，而是把三种「用不了」拆开修：模型接不上、网页搜不到、能力装不进。

三条线各自的代码量都不算大，难的是它们互相之间不能借用现成结论——搜索不能靠能力包，能力安装不能靠新增能力类型，厂商兼容不能靠复制聊天管线。下面先对账，再提炼这一版真正值得留下来的七条方法论。

## 一、收益对账

| 承诺 | 对账 |
|---|---|
| 新增一家 OpenAI 兼容厂商只改一个描述文件 | 描述数据集中到一份目录，查询层只做匹配；既有预设 id 与设置页表单零变化 |
| 不提供模型列表的厂商能走完全链路 | 「配置 → 添加模型 → 三态测试 → 对话」走通，404 归一化为端点不存在并回落 |
| 连接测试不再二元 | 三态：已验证 / 可达但无法验证 / 失败；保留兼容字段 |
| 未装能力包也能联网搜索 | 内置搜索工具；配置后端后可「搜索 → 读取 → 带来源回答」 |
| 能力可按意图发现并安装 | 五个内置精选包；检索 → 审批 → 安装 → 下一轮只读工具可用 |
| 搜索隐私与审计 | endpoint 准入、密钥掩码、审计不落查询正文、结果按不可信内容处理 |
| 零迁移、回归不降级 | schema 保持 42；单测 2922（基线 2882）；e2e 139/139；桌面 10/11；`/settings` 481 kB（+0.42%） |

对账里没有「覆盖率提升」这类软指标，因为这一版的目标不是把测试做厚，而是把三条用户路径走通。测试数是结果，不是目的。

## 二、方法论一：厂商差异是数据，不是逻辑

把厂商差异写成描述文件，最大的收益不是「少写代码」，而是**差异变成可测试、可复用、可展示的数据**。

这一版的落地很具体：描述数据放在共享包，因为设置页引导与服务端请求必须读同一份；查询逻辑放在 ai 包，只提供列出、按 id 查、按 Base URL 匹配、取发现策略四个入口，不复制数据。预设常量表保留，但改为由描述目录派生，于是既有 id 一个不变，设置页行为也不变。

对照组是「给单厂商 fork 一份适配器」。它的代价在表里看得很清楚：聊天管线复制一份、错误语义分叉、测试矩阵翻倍、协议演进受阻。厂商数量会继续增长，协议不该跟着长。

描述文件里还有一个刻意的空白：**没有厂商级回调，没有「特殊处理」钩子**。一旦允许往配置里塞代码，它就会慢慢长成第二套适配器，只是换了个文件名。

## 三、方法论二：三态诚实，不把「没验证」说成「成功」

二元连接测试会在两个方向说谎：端点可达但没有模型时给绿灯，端点不存在时给「鉴权失败」的红灯。前者让用户带着坏配置进对话，后者让用户去修一个没问题的 Key。

三态的意义是把「能连上」与「能验证」拆开。`reachable_unverified` 这个状态最难做产品化，因为它既不好看也不干脆；但它准确表达了「我只验证到一半」。界面用黄色徽章与「请先添加模型」的文案承接它，而不是把它折叠成绿色或红色。

这条方法论还有两个硬约束：

- 首字探活只使用用户手动配置的对话模型，绝不偷偷创建模型再探活——那会在用户不知情时改写他的配置，而且探活成功也不代表模型属于他的套餐；
- `failed` 仍走既有的 HTTP 错误层，不为了「三种状态都在响应体里」把错误改成 200。形式统一不值得让一批既有错误分支静默失效。

诚实是有成本的：文档里必须写清「`failed` 不由成功响应表达」，验收记录里也要登记这处不统一。但不写清楚，下一个人就会把它当 bug 修掉。

## 四、方法论三：搜索与读取分离，别让一个工具承担两种失败

搜索工具只返回标题、链接、摘要和后端标识，正文交给网页读取工具按需获取。这个决定同时解决三件事：

- **上下文**：5 条摘要只有几 KB，抓 5 个页面正文可能是几十倍；
- **超时**：搜索 10s 封顶，不会被某一个慢页面拖垮整次调用；
- **注入面**：外部内容只在用户或模型主动读取时进入上下文，而不是每次搜索都灌进来。

工程上还有一层原因：搜索是聚合服务，抓正文要走另一套网络路径、另一套私网校验、另一套内容清洗。揉进一个工具，等于让搜索承担两种失败模式，错误文案也会含混——用户分不清是「没搜到」还是「搜到了但读不了」。

分开之后，两个工具各自有清晰语义：搜索回答「有哪些相关页面」，读取回答「这个页面说了什么」。空结果也不该报错，它是正常结果；报成故障会让用户以为搜索坏了。

## 五、方法论四：安装这类动作，要让所有自动放行失效

权限体系里有一堆减少打扰的机制：完全放行、按工具策略 allow、持久授权。它们对普通工具调用是合理的，对能力安装必须全部失效。

这一版的做法是在权限门里把强制审批判断放在所有放行分支之前：只要工具带了这个标记，就直接发起人工审批，原因为专用代码。顺序不能反——放在后面等于没做，任何一个 `allow` 分支先返回，审批就被绕过了。

配套的三条边界同样重要：

- 无人值守运行没有确认界面，按「无审批界面」直接拒绝，不降级成默认允许；
- 审批框这一版复用了通用工具确认，只带工具名、权限与参数摘要，目录来源、签名、效果与新增工具没有进去——这些信息改由检索工具在调用前说清。这是明确登记的能力缺口，不是「已经做完」；
- 安装后只绑定只读工具，写与危险工具保持手动勾选；同一轮多次安装共享白名单快照，避免后一次覆盖前一次。

还有一条容易被忽略：**绑定失败不等于安装失败**。包已经装好、只是没能自动并入白名单时，必须照实报成功并提示手动勾选；报成失败会让用户重复安装，最后撞上「已安装」的拒绝，前后矛盾。

## 六、方法论五：零迁移是设计约束，不是事后检查

零迁移不是运气好，而是每条主线在设计时都被问过一句「这个东西能不能落在既有结构里」。

答案在这一版里很一致：搜索配置写进既有设置 JSON；工具白名单继续写助手的工具列表字段；安装状态落在既有能力包表；目录条目是随版本发布的代码常量，不落库。厂商描述也不落库，落库的只有用户的选择。

这样做的直接收益是旧库能直接打开。但零迁移的完整含义不止「没跑迁移脚本」，还包括「旧数据能被新代码正确解释」：旧设置里没有搜索配置，读取层必须给出「未配置」的默认状态，而不是崩在空值上。所以验收要同时检查 schema 版本不变、无新增表列索引、旧库可开、新字段有缺省兜底。

反过来说，如果这一版要做目录服务端下发、安装历史分页、多设备同步，那就必须加表——那些需求要的是查询、索引与关系。零迁移的正确表述是「需求没有越界」，而不是「我们有能力不加表」。

## 七、方法论六：契约先冻结，偏差必须登记

三条线都在动手前冻结了契约：厂商描述字段、发现顺序、三态返回结构、搜索工具的参数与上限、目录条目字段、安装后的绑定规则。冻结之后，实现中的每一处偏离都要写进记录，而不是悄悄改掉。

这一版逐条登记了实现偏差，其中三处值得单独说：

- **失败的连接测试仍走 HTTP 错误层**：为了不破坏既有错误处理与测试，放弃了「三态全在响应体里」的形式统一；
- **审批框复用通用确认，不展示目录元数据**：信息由检索工具在调用前说明，结构化审批载荷留到后续；
- **目录只收内置包，MCP 预置条目安装直接拒绝**：首批不接入预置安装，避免把未验证的路径混进发布。

登记偏差的价值在于：它把「知道但没做」和「不知道所以没做」区分开。前者是排期问题，后者是风险。发布文档里那些「已知边界」，其实就是偏差登记的对外版本。

## 八、方法论七：回归只认基线，不认感觉

这一版的回归账目全部对着上一版基线：

| 项 | 基线 | 本版 | 结论 |
|---|---|---|---|
| 单测 | 2882 | 2922 | 增加 40 例 |
| Web e2e | 139 | 139/139 | 持平 |
| 桌面冒烟 | 10/11 | 10/11 | 同一项环境失败，非回归 |
| `/settings` 首屏 | 479 kB | 481 kB | +0.42%，门槛 5% |
| schema 版本 | 42 | 42 | 零迁移 |

「和基线一致」是唯一有意义的判断标准。桌面冒烟那一项失败如果上一版也失败，这一版再失败就不是回归；如果上一版通过而这一版失败，哪怕看起来像环境问题，也要先当回归查。感觉「应该没事」是最贵的判断方式。

包体也一样：`/settings` 只涨了 2 kB，因为新增的只是一个搜索面板与几段文案，搜索适配器完全留在服务端，客户端只多了一个 provider 枚举。判断一个模块该不该进客户端，标准不是语言，而是运行时需要什么——需要 DNS、文件系统、密钥解密的，天然属于服务端。

## 九、纪律：这一版明确不做什么

- 不新增第二套协议，协议扩展另开版本评估；
- 不做供应商原生搜索、不做云端搜索代理；
- 不开放远程能力市场、不做任意 URL 下载、不做静默安装；
- 不做同轮工具热替换；
- 不重写供应商表单、不改对话主结构；
- 不新增运行时依赖、不做数据库迁移。

这些「不做」不是保守清单，而是让这一版能在一个交付周期内被完整验证的前提。任何一条放开，验收就会从「每条路径都能走完」退化成「主要场景可用」。

## 十、账目的另一面

收益对账之外，还有几笔要记：

- 没有浏览器端的安装审批 e2e，审批路径靠权限门与工具单测覆盖。单测能证明判定顺序正确，但证明不了「用户真的看到了审批框」；
- 没有真实 Key 的搜索冒烟，外部后端的错误分类只在 mock 上验证过；
- 审批框的信息密度不足，用户的风险判断依赖模型转述，这是一处明确的产品欠账；
- 桌面冒烟的环境失败项没有修，只确认了「非本版回归」。

这些不是否定收益，而是标出下一版该往哪里使劲。一个版本最危险的时刻，是账目全部为绿的时候——它容易让人以为盲区不存在。

这四笔账里，前两笔是测试形态的缺口：单测能证明判定顺序，证明不了用户真的看见了审批框、真的收到了一条可读的失败原因。后两笔是信息完整度的缺口：审批框信息不足、环境失败项未修，都会让「已完成」这三个字打折扣。

分清「没做」和「做不到」也很重要。审批 e2e 不是做不到，是 mock 模型不产出函数调用、绕不过去；真实 Key 冒烟不是做不到，是不该把外部凭据放进默认 CI。这两类属于工具形态限制，下一版要么换测试手段，要么明确接受它作为长期边界。

## 十一、回到那个问题

三条线拆开做，最直接的代价是交付物不「性感」：没有一个大到可以单独演示的新功能，只有三段各自变顺的路径。

但它们买来的是**下一层能力的地基**：厂商再多一家，只加一个描述文件；搜索换一个后端，只实现一个接口；能力目录想扩容，安装与审批链路已经跑通。对一个还要继续长能力线的单人项目，这比多一个演示功能更值钱。

三态里的那盏黄灯，是这一版最喜欢的一个设计：它不漂亮，但它不撒谎。这个系列到这里收口。
