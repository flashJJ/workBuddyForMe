# 把厂商差异从适配器里抽出来：一份描述文件，一个查询层

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，模型供应商配置写在本机设置里，请求由本机服务进程直接发出。这类应用接厂商的常规姿势是：一个 OpenAI 兼容适配器打天下，再为每家厂商准备一条预设常量。

一开始这很划算：Base URL、Key 申请地址、推荐模型，三行数据就能接一家。等到厂商多起来，麻烦不再来自协议，而来自**厂商之间的差异本身**：有的厂商没有模型列表端点，有的把 Key 按套餐分作用域，有的模型 ID 必须从控制台复制而不能靠补全。

这些差异全是数据，却被散落在三个地方：共享常量里一份、适配器里的 if 分支一份、设置页的表单提示里还有一份。加一家厂商要同时改三处，漏一处就出现「预设里有、但测试始终失败」的怪象。

## 一、厂商之间到底差在哪

把已知厂商列成一张表，差异其实只有五类：

| 差异维度 | 具体表现 | 如果写死在代码里 |
|---|---|---|
| 连接地址 | Base URL 不同，有的还按套餐分路径 | 每加一家改一次常量 |
| 密钥作用域 | Key 属于数据面、套餐还是编码套餐 | 错误提示无法解释「Key 不匹配套餐」 |
| 模型来源 | 有的有模型列表，有的只能抄控制台 | 发现逻辑里长出一堆特判 |
| 模型 ID 形态 | 普通 ID、带前缀的 ID、接入点 ID | 校验规则按厂商分叉 |
| 推荐模型 | 首用该给用户哪个模型 | 引导文案与常量各写一份 |

这五类都不涉及「请求怎么发」，只涉及「这家厂商是什么样」。所以它们应该待在一个可读、可测试、可被 UI 复用的地方，而不是躺在请求代码的分支里。

## 二、描述文件里有什么

厂商描述沿用既有的预设结构，只做加法，不重命名、不改既有字段语义：

| 字段 | 含义 | 主要消费方 |
|---|---|---|
| `id` / `name` | 稳定标识与展示名 | 设置页、已保存供应商 |
| `baseUrl` / `keyUrl` | 请求地址、Key 申请入口 | 请求层、引导文案 |
| `models` | 推荐模型及其能力标签 | 添加模型引导、回落候选 |
| `protocol` | 走哪套请求协议，缺省 OpenAI 兼容 | 适配器选择 |
| `discovery` | 模型发现策略 | 发现流程、测试流程 |
| `modelIdHint` | 模型 ID 从哪来、怎么填 | 表单提示 |
| `keyScope` | 密钥作用域 | 错误文案、套餐说明 |
| `notes` | 厂商特有的注意事项 | 设置页说明 |

关键是**只加数据字段，不加速度字段**：描述文件里没有「怎么发请求」的钩子，也没有「某厂商特殊处理」的回调。一旦允许回调，描述文件就退化成了配置文件里的代码，测试和复用都会重新变难。

## 三、数据放 shared，查询放 ai

这里有一个容易踩的边界：描述数据放在哪、查询逻辑放在哪。

- **数据放 shared 包**：设置页的引导流程和服务端请求层必须读同一份数据，否则「页面上显示的推荐模型」和「服务端实际回落的模型」会分叉；
- **查询放 ai 包**：ai 包只提供查询与匹配，不复制数据，也不反向依赖 UI。

查询层只有四个入口，语义都很窄：

```ts
listVendors()                  // 全部描述
getVendor(id)                  // 按 id 精确查找
findVendorByBaseUrl(baseUrl)   // 归一化尾部斜杠后匹配已保存供应商
resolveDiscovery(vendor)       // 取发现策略，缺省 openai-models
```

`findVendorByBaseUrl` 是唯一带一点「聪明」的函数：用户保存的 Base URL 经常多一个或少一个尾斜杠，直接字符串比较会匹配失败。归一化只处理尾斜杠，不做协议猜测、不做域名模糊匹配——匹配错了比匹配不上更危险，因为它会让一家厂商套上另一家的发现策略。

## 四、预设由 registry 派生

存量代码里还有一份「预设常量表」，直接被设置页和引导流程引用。这一版没有删掉它，而是让它由 registry 派生：

```text
描述文件（唯一真源）
      │ listVendors()
      ▼
PROVIDER_PRESETS（派生视图，保留既有 id 与展示名）
      │
      ├── 设置页下拉与表单
      └── 服务端已保存供应商的匹配
```

这样做的收益很具体：既有 id 一个不变，设置页表单行为不变，外部看到的选项顺序也不变；但新增厂商时只需要往描述目录里加一个文件，派生视图自动多一项。

如果反过来让预设常量做真源、registry 做视图，就等于把「两份数据」的问题留在了原地——迟早有人只改其中一份。

## 五、新增一家厂商要改什么

完整的接入清单只有五步，且全部落在一个文件里：

1. 在描述目录新增一条记录，填地址、Key 入口、推荐模型；
2. 声明发现策略：有模型列表、走厂商专用接口，还是只能手填；
3. 声明密钥作用域，让错误文案能说清「Key 与套餐不匹配」；
4. 写清模型 ID 的获取方式，填进表单提示；
5. 跑一遍单测，确认预设 id 未变、派生视图多了一项。

**适配器不需要改。** 只有当这家厂商的请求格式与现有协议不兼容时，才需要另开一项协议工作——那是另一个量级的事，不该混进「接入一家厂商」里。

## 六、为什么不给单厂商 fork 适配器

「这家厂商特殊，给它复制一份适配器」是最容易走的路，代价却很实在：

| 代价 | 具体后果 |
|---|---|
| 聊天管线复制 | 流式解析、错误映射、工具调用编码各维护一份 |
| 错误语义分叉 | 同一类 404 在两条管线里给出不同结论 |
| 测试矩阵翻倍 | 每条管线都要单独覆盖超时、限流、鉴权 |
| 协议演进受阻 | 想统一升级时，先要合并 N 份分叉 |

适配器只按 `protocol` 选择，这是把「厂商数量」和「协议数量」解耦的关键。厂商可以无限增加，协议保持稳定；真要扩协议，就单独评估、单独验收，而不是伪装成一次厂商接入。

## 七、这一版的边界

- 协议仍然只有两种：OpenAI 兼容与 Ollama，不新增第二套消息格式；
- 发现策略只有三种：模型列表、厂商专用接口、只能手填；
- 已有厂商全部保持原有行为，其中接入点型厂商仍然先试模型列表，404 再回落；
- 套餐型厂商标为「只能手填」，因为它们的模型列表不在数据面端点上；
- 描述文件不承载任何请求逻辑，也不允许厂商级回调。

## 八、验证

- 查询层单测 **4 例**：列出、按 id 查、按 Base URL 匹配（含尾斜杠）、缺省发现策略；
- 服务层单测 **10 例**：覆盖三种发现策略与回落路径；
- 设置页单测 **6 例**：覆盖表单行为与三态展示；
- 静态门禁全绿，既有预设 id 与展示名零变化。

这些测试的共同点是：它们验证的是「描述数据被正确读取」，而不是「某个厂商的请求成功」。前者稳定，后者依赖网络和账号。
