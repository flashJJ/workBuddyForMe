# 搜索会离开本机：endpoint 准入、密钥掩码与审计边界

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，绝大多数能力都在本机完成：模型推理可以走本地服务，知识检索读本地库，文件操作不出磁盘。搜索是这一版里唯一一件**主动把数据发出去**的事。

也正因为如此，搜索的工程重点不是「怎么搜得更多」，而是「怎么让用户知道发生了什么，并且让代码守住承诺」。这一版围绕三件事做约束：endpoint 准入、密钥管理与审计边界。

## 一、先把承诺说清楚

在设置页开启搜索时，界面必须明确说明：**查询词会离开本机，发送到你配置的搜索后端**。这句话不是免责声明，而是产品契约的一部分——用户有权在知道这件事之后再决定是否开启。

配套的默认值是关闭：provider 默认 `none`，未配置时搜索工具返回可执行错误。默认关闭不是保守，而是因为搜索的隐私成本和别的只读工具完全不同：读本地文件不会把内容送给第三方，搜索会。

## 二、endpoint 准入的四道门

用户填的 endpoint 是一个外部输入，而且会被服务端直接请求。它必须经过四道门：

```text
1. 协议白名单：只允许 http / https
2. 公网要求 https：明文 http 只允许回环或显式放行的私网
3. DNS 解析后校验：解析出的地址必须不是私网 / 回环 / 链路本地
4. 显式放行：自建 SearXNG 需打开「允许私网 endpoint」开关
```

| 门 | 规则 | 拦住的典型输入 |
|---|---|---|
| 协议 | 只接受 http / https | `file://`、`javascript:`、`data:` |
| 传输 | 公网必须 https | 明文公网地址，查询与结果可被中间人读取 |
| 地址 | 解析后拒绝私网、回环、链路本地 | 内网服务、云元数据地址、本机管理端口 |
| 放行 | 私网需显式开关 | 用户自建在内网的搜索服务 |

第 4 道门是必要的例外。本地优先的应用里，用户完全可能在自己的机器或局域网跑一个 SearXNG；如果一律拒绝私网，这个最符合产品定位的后端反而用不了。例外通过一个独立开关表达，默认关闭，开启时设置页给出风险提示。

## 三、为什么不能只做字符串匹配

`http://127.0.0.1` 这种写法，字符串匹配一眼就能拦住。但下面这些写法都能绕过朴素的域名判断：

- 十进制或十六进制表示的 IPv4；
- 带用户名、带端口、带片段的变形 URL；
- 解析后指向私网的域名（DNS 重绑定）；
- 先解析到公网、请求时再跳转到私网的重定向；
- IPv6 的回环与映射地址。

所以校验必须发生在**解析之后**，对实际要连接的地址做判断，而不是对用户输入的字符串做判断。这也是「公网要求 https」的原因之一：明文请求无法保证中间没有人改写响应，而搜索结果是会被喂给模型的。

重定向同样要谨慎：跟随到新地址之前，新地址仍应过一遍同样的准入。否则第一跳合法、第二跳进内网，前面的校验就白做了。

## 四、密钥不出本机

搜索后端目前只实现了不需要 Key 的自建服务，但设置结构里已经预留了 Key 字段，并沿用既有的本地加密存储：

- Key 写入时加密，只在服务端读取使用，不出现在前端状态里；
- 设置页只展示掩码，不提供「查看完整 Key」；
- 不做云端搜索代理，不把 Key 上传到任何中转服务；

这三条里，第三条是产品边界：一旦提供云端代理，密钥就从「用户与本机之间的事」变成「用户与第三方之间的事」，隐私承诺随之失效。宁可少支持几个带 Key 的后端，也不做代理。

## 五、审计只记元数据

搜索的审计记录刻意不含查询正文，也不含结果正文：

| 记录项 | 用途 |
|---|---|
| provider 标识 | 归因到具体后端 |
| 结果数 | 判断是空结果还是解析异常 |
| 耗时 | 发现后端变慢或超时 |
| 成功 / 失败与错误类别 | 统计可用性 |
| 查询长度或哈希 | 关联同一查询，但不还原内容 |

为什么这么克制？因为审计页会被打开、被截图、被导出、被同步到别处。查询正文往往包含用户的真实意图、内部项目名、甚至个人信息；一旦落进审计，它就从「一次临时请求」变成了「一份长期留存的记录」。

只记长度与哈希，既能做聚合分析（同一查询重复失败、平均长度异常），又不构成内容留存。这是「可观测」和「可追溯个人意图」之间的一条线。

## 六、搜索结果按不可信内容处理

搜索结果来自外部，必须按不可信输入处理，哪怕后端是用户自己搭的：

- 去 HTML 标签与脚本，只保留纯文本摘要；
- 摘要限长，超出截断，避免一条结果吃掉大量上下文；
- 保留来源链接，但在上下文里标注为外部内容；
- 不因为搜索结果里出现指令性文本就改变工具调用策略；
- 危险工具仍然需要显式勾选，不因搜索结果自动获得权限。

最后一条尤其重要：提示注入的常见手法是把指令藏进网页正文，诱导模型去调用高权限工具。搜索只返回摘要、正文由读取工具按需获取，本身就把注入面收窄了一层；再加上危险工具不自动绑定，攻击者能拿到的最多是「让模型多说几句」。

## 七、限流与退避

搜索是外部依赖，必须假设它会限流、会抖动：

- 每会话每分钟有查询上限，超过后返回明确文案；
- 单轮结果数有上限，避免一次调用把上下文塞满；
- 收到 429 不自动连续重试，只提示稍后重试；
- 超时固定 10s，不让一次慢请求拖住整个对话轮次。

退避策略刻意做得很轻：这是一个交互式应用，用户就在屏幕前，自动重试既不能提升成功率，还会在限流期间制造更多请求。把「现在不行」快速、清楚地告诉用户，比在后台偷偷重试更诚实。

## 八、这一版没有做完的部分

- 搜索工具还没有专用审计事件，当前只保证「查询正文不落审计」，事件粒度留待后续补齐；
- 首批只实现自建 SearXNG 与 mock，带 Key 的云后端需要先解决密钥存储；
- 审计里保留查询哈希，但不做跨会话关联分析。

把没做完的部分写出来，比在文档里假装「已覆盖」更有价值。安全相关的边界尤其如此：读者需要知道防线在哪里结束。
