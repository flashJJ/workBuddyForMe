# 当厂商不提供 /models：模型列表的四级回落与错误分类

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，供应商配置由用户填在本机，模型请求从本机服务进程直接发往厂商。厂商接入最初只有一个假设：**OpenAI 兼容的厂商一定提供 `GET /models`**。

这个假设在大多数厂商成立，但在两类厂商身上失效：一类把模型列表放在控制台或套餐页面上，数据面端点只接受对话；另一类按套餐拆分路径，不同套餐的 Key 连到不同前缀，模型清单根本不在同一处。

失效时的表现很糟：用户点「获取模型列表」，得到的却是一句「鉴权失败」。他会去检查 Key、重新复制、换套餐，最后发现 Key 从来没问题——只是这个端点不存在。

## 一、只假设一条路径的代价

| 现象 | 用户的理解 | 真实原因 |
|---|---|---|
| 获取列表报鉴权失败 | Key 填错了 / 套餐没买对 | 端点不存在，404 被当成通用错误 |
| 列表一直转圈后超时 | 网络很差 | 厂商压根没有这个端点，请求白等到超时 |
| 列表返回空 | 账号没有权限 | 端点存在但不返回数据，需要手填 |

三种现象的共同点：**用户没有任何可执行的下一步**。错误分类不做，用户就只能靠猜；而猜错的成本是换掉一个本来正确的 Key。

## 二、四级发现顺序

发现逻辑按优先级尝试，前一级失败就落到下一级，全部失败才要求手填：

| 顺序 | 来源 | 适用 | 失败后 |
|---|---|---|---|
| 1 | `GET /models` | 绝大多数 OpenAI 兼容厂商 | 落到下一级 |
| 2 | 厂商专用接口（如 Ollama 的 `/api/tags`） | 本地推理服务 | 落到下一级 |
| 3 | 描述文件里的推荐模型 | 只能手填的厂商、接入点型厂商 | 落到下一级 |
| 4 | 手动填写 | 任何情况 | 永远保留 |

第四级「永远保留」不是兜底口号，而是产品约束：无论自动发现做得多好，用户都必须能自己填一个模型 ID。厂商随时可能改端点、改套餐、改命名，自动发现只能降低摩擦，不能成为唯一入口。

第 2 级的存在说明「厂商专用接口」不是特例，而是抽象的一部分：发现策略被写进描述文件，取值为「模型列表」「厂商专用」「只能手填」三种，发现流程只读这个字段，不认厂商名字。

```text
resolveDiscovery(vendor)
      ├── openai-models → GET /models
      ├── ollama-tags   → GET /api/tags
      └── manual-only   → 直接用推荐模型，不发请求
```

## 三、错误语义必须先分类

同一个「失败」，背后的动作完全不同。分类发生在错误归一化层，UI 只读语义，不读 HTTP 状态码：

| HTTP / 情况 | 内部语义 | UI 动作 |
|---|---|---|
| 404 / 405 | 端点不存在 | 提示手填模型 ID，**不显示鉴权失败** |
| 401 / 403 | 鉴权失败 | 提示检查 Key 与套餐作用域 |
| 429 | 限流 | 提示稍后重试，不自动连续重试 |
| 超时 / 网络错误 | 不可达 | 提示检查 Base URL 与网络 |
| 200 但列表为空 | 无模型 | 引导手填或使用推荐模型 |

这张表里最容易做错的是第一行和最后一行：404 被通用错误处理吞掉，空列表被当成成功。前者让用户去修一个不存在的鉴权问题，后者让用户面对一个空下拉框，以为应用坏了。

分类必须集中在错误层，而不是散在各处。如果每个调用点自己判断 `status === 404`，迟早会出现一处判 404、一处判 405、第三处只判 `!ok` 的分叉。

## 四、manual-only 不是「不支持」

把某家厂商标成「只能手填」，很容易被误解成「这家不支持模型发现」。实际语义是：**这家厂商的模型清单不通过数据面端点暴露，但对话端点是可用的**。

所以这条路径的行为要精确：

- 不发任何网络请求；
- 直接返回描述文件里的推荐模型；
- 如果用户还没有添加任何对话模型，连接测试返回「可达但无法验证」，并提示先添加模型；
- 绝不因为「没有列表」就断言厂商不可用。

套餐型端点尤其需要这个语义。用户在控制台看到模型、复制了 ID、填进应用，整个流程是通的；此时如果应用说「发现失败」，那是在否定一个本来正确的事实。

## 五、404 回落与首字探活

接入点型厂商的情况介于两者之间：部分账号的模型列表可用，部分账号 404。这类厂商不能直接标成「只能手填」，否则会丢掉一部分用户本可以享受的自动发现。

处理方式是「先试、再回落」：

1. 先按模型列表请求；
2. 收到 404 / 405，归一化为「端点不存在」，不报鉴权失败；
3. 回落到描述文件里的推荐模型；
4. 如果用户已配置对话模型，用首字探活确认可用性。

探活的成本是一次最小的对话请求，收益是把「列表拿不到」和「模型不能用」区分开。没有这一步，用户只能靠反复发消息来试错。

需要强调的是：**回落只发生在确认端点不存在时**。401 不回落，429 不回落，超时不回落——这三种情况回落只会掩盖真正的问题，把「Key 错了」伪装成「厂商不支持列表」。

## 六、空列表与限流

「200 但 `data` 为空」是一个独立语义。它可能来自账号权限、套餐范围、厂商灰度，应用无从判断，也不该猜。

正确动作是：把空列表当作「没有可用模型」，引导手填或使用推荐模型；不自动填入任何模型，也不把空数组渲染成一个看起来正常的下拉框。

429 的处理同样要克制。限流意味着「现在别问」，不是「再问一次可能就有了」。自动重试会把一次限流放大成一串请求，让恢复时间更长；正确做法是给出明确文案，让用户稍后手动重试，同时把这次失败按「限流」记录，而不是归到网络错误里。

## 七、这一版踩到的两个细节

**第一，错误归一化必须保留原始信息。** 归一化到「端点不存在」后，UI 不再需要 HTTP 状态码，但日志和检查项里仍要能看到原始状态，否则排查时无法区分「真的 404」和「被代理改写的 404」。

**第二，发现结果要带上来源。** 用户看到的模型列表究竟来自端点、来自厂商专用接口，还是来自推荐模型，必须能说清。三者混在一起时，用户会误以为「列表里的模型都是账号可用的」，而推荐模型只是「建议先试这个」。

这两个细节都不改变主流程，却决定了出错时能不能自证。
