# 安装一个能力包，为什么必须弹一次无法跳过的确认

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，工具权限分 `read`、`write`、`danger` 三档，配合全局放行开关、按工具的策略与持久授权一起工作。这套机制的设计目标是减少打扰：用户信任某个工具后，不必每次调用都点确认。

安装能力包是这套机制里唯一的例外。**它必须弹一次审批，而且任何已有放行都不能替代这次审批。**

## 一、自动放行机制本来是为效率设计的

| 放行来源 | 常规作用 | 对安装是否有效 |
|---|---|---|
| 完全放行模式 | 不逐次确认，适合可信的自动化 | 无效 |
| 按工具策略 allow | 对某个工具长期放行 | 无效 |
| 持久授权 | 用户曾批准过同类调用 | 无效 |
| 无人值守运行 | 没有界面，按既定策略执行 | 直接拒绝 |

前三行的失效不是设计缺陷，而是刻意为之。安装动作和普通工具调用的风险量级不同：一次文件读取只影响一个文件，一次安装会**扩大助手未来的能力边界**。前者可以「信任一次、后续放行」，后者每次都必须重新判断，因为新增的工具集是新的。

第四行的处理更硬：无人值守运行没有确认界面，就没有「用户批准」这一事实，于是按「无审批界面」拒绝，而不是降级成默认允许。

## 二、`alwaysConfirm` 的判定位置

这个约束做在权限门里，不靠调用方自觉：

```ts
// 权限门伪代码
if (tool.alwaysConfirm) {
  return requestApproval({ reasonCode: 'HITL_REQUIRED', ... });
}
if (mode === 'full_access') return allow();
if (policy[tool.name] === 'allow') return allow();
if (persistentGrant(tool.name)) return allow();
```

顺序上，`alwaysConfirm` 的判断放在所有放行分支之前。放在后面等于没做——只要有一个分支先返回 `allow`，强制审批就被绕过了。

审批原因固定为一个专用代码，审批中心与审计都能看到。这样做的好处是：事后翻审计时，能一眼区分「用户批准了一次普通写操作」和「用户批准了一次能力安装」。

## 三、无人值守没有确认 UI

定时任务、后台代理这类运行形态没有交互界面。它们的权限模型必须承认这一点：

- 不弹审批框，因为没有人能点；
- 不静默安装，因为没有取得同意；
- 返回「需要交互式会话」的明确错误，让用户回到对话里再发起。

这条规则听起来保守，但它避免了一类最难排查的问题：某个后台任务在夜里装了一个包，第二天用户发现助手的行为变了，却找不到是谁批准的。

## 四、审批框该展示什么，实际展示了什么

一个理想的安装审批应该包含：

| 信息 | 回答的问题 |
|---|---|
| 来源（内置 / 预置） | 这个包从哪来 |
| 版本与校验信息 | 内容有没有被改过 |
| 权限集合 | 它会读什么、写什么 |
| 效果 | 装上之后会发生什么 |
| 预计新增工具 | 助手会多出哪些能力 |
| 安装理由 | 模型为什么建议装它 |

这一版的实际实现有一处明确的不足：审批框复用了通用工具确认，只带工具名、权限和参数摘要，**没有展示目录来源、签名、效果与新增工具**。这些信息由检索工具在调用前返回给模型，并由模型在对话里说明。

所以真实的信息链条是：检索工具负责把元数据说清楚，模型负责转述，审批框负责拿到「同意」这个动作。这不是理想形态，但它保证了一个底线——审批确实发生，且用户至少看到了工具名与权限。

把这条不足写进文档而不是藏起来，是因为它直接影响用户的风险判断。后续版本需要扩展结构化审批载荷，让审批框本身就能承载这些信息。

## 五、安装复用既有链路，不新写一套

安装代理没有重新实现一遍安装，而是调用既有能力服务的安装入口：

```text
条目解析 → ZIP 校验 → 签名校验 → 权限检查 → 依赖检查
        → 落盘 → 启用 → 记录安装状态
```

每条失败都在对应环节 fail-closed：校验不过不落盘，验签不过不启用，依赖缺失整体回滚。这套语义在能力包功能里已经存在，安装代理只是多了一层「从目录条目到包」的映射。

复用带来两个好处：安全策略只有一处实现，不会出现「手动安装校验、自动安装不校验」的双标；失败回滚的行为也一致，用户不需要为两条入口记两套规则。

## 六、下一轮绑定：只读自动，危险手动

安装成功后，工具怎么进白名单，是这条链路最容易做错的地方。规则是：

- 只把权限为 `read` 且能解析到实现的工具，追加进当前助手的工具白名单；
- `write`、`danger` 与无法解析的工具全部跳过，并提示用户手动勾选；
- 同一轮里多次安装，共享同一份白名单快照，避免后一次覆盖前一次；
- 返回文案明确写「已安装，下一轮可用」。

为什么只自动绑定只读工具？因为安装的批准范围是「装这个包」，不是「授权它做任何事」。只读工具的失败代价可控，写工具可能改文件，危险工具可能操作系统；后两者的授权必须是独立的一次决定。

同轮多次安装共享快照这个细节，来自一个很容易漏的场景：模型在一轮里连续装两个包，如果每次都从持久化状态重新读白名单再写回，第二次写入会覆盖第一次的结果。共享快照让增量累积，而不是互相覆盖。

## 七、为什么不做同轮热替换

单轮的工具集在出站前构建一次，之后不再变化。安装完成后，本轮仍然用旧工具集，下一轮才重新构建。

不做同轮热替换有三个原因：

| 原因 | 后果 |
|---|---|
| 声明与执行不一致 | 模型在同一个响应里既看到新工具，又基于旧声明规划 |
| trace 失真 | 同一轮的工具调用记录无法对应到一份确定的工具集 |
| 权限门无法复核 | 新工具在本轮没有经过完整的权限检查流程 |

「下一轮可用」听起来像延迟，其实是把一次状态变更钉在一个确定的边界上：轮次。用户感知到的差别通常只有一句话的间隔，换来的是可复现、可审计的执行记录。

## 八、失败回滚与两种失败的区分

安装链路有两种失败，必须分开报告：

- **安装失败**：校验、验签、依赖、落盘任一步失败，整体回滚，白名单不变；
- **绑定失败**：安装成功，但工具没有成功并入白名单，此时不能报「安装失败」。

第二种最容易被写错。工具层捕获绑定异常后如果直接向上抛，用户会以为包没装上，然后重复安装，最后得到一个「已安装」的拒绝提示，前后矛盾。正确做法是：安装结果照实返回成功，附带「未能自动绑定，请手动勾选」的说明。
