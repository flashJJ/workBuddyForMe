# 图表理解做成可选能力：没配视觉模型时，明确说不

对一个本地优先、单人开发的桌面 AI 应用来说，文档里最关键的信息经常不在文字里。财报的增长曲线、规格书的尺寸图、流程文档的结构图，答案都画在图上。纯文本链路对此无能为力：解析器能拿到图注文字，拿不到图形内容。

一个直觉的解法是「接一个视觉模型」。但这个解法带进来三个新问题：谁的模型、谁付成本、图像去了哪里。对一个本地优先的桌面应用，这三个问题不回答清楚，就不该把功能默认打开。所以这一版的做法是：**图表理解作为可选能力存在，没配置时明确返回「不支持」，绝不静默降级成编造的描述。**

## 先判断有没有能力，再决定发不发请求

结构接口多返回一个布尔值：`visionAvailable`。查看器打开时读这个字段：

- 为真：每个图注旁出现「理解图表」按钮，用户点击才触发；
- 为假：图注列表照常展示，但内联提示「未配置视觉模型」，按钮禁用。

关键在于「照常展示」。没有视觉模型，不代表图注没有价值——「图 1 季度营收趋势」这行字本身就是结构信息，能帮用户判断该不该去看原页。能力缺失只影响「解读」，不影响「阅读」。

这条设计也避免了一类常见的糟糕体验：用户点了按钮，转了三秒圈，最后弹一个「请求失败」。能力不可用时，入口就该是禁用的，并且给出原因。

## 按需渲染：只画需要的那一页

解读请求只带一个块 ID：

```json
{ "blockId": "b3" }
```

服务端做的事情是确定的：

1. 校验块存在、类型是图注（不是随便一个段落块）；
2. 找到图注所在的 PDF 页码；
3. 用 PDF.js 把那一页渲染成图片，缩放 2 倍；
4. 单页像素总量封顶 120 万，超出就降低缩放；
5. 把图片交给已配置的视觉模型，超时 60 秒，随请求的中止信号取消。

只渲染一页，而不是整份文档，是因为整份渲染既慢又没必要。像素上限和超时都是硬约束：一张 A4 页面在 2 倍缩放下已经能看清图表细节，再高只会增加传输和推理成本；60 秒是用户可接受的等待上限，超过就该失败，而不是让请求挂着。

## 一次解读的完整调用链

```text
查看器读结构 ──► visionAvailable?
    │ false                        │ true
    ▼                              ▼
内联提示 + 按钮禁用            用户点「理解图表」
                                   │ POST { blockId }
                                   ▼
                        校验块类型 → 取页码 → PDF.js 渲染该页
                                   │ scale 2 / ≤120 万像素
                                   ▼
                        已配置视觉模型（60s 超时 / 可中止）
                                   │
                                   ▼
                        摘要（剥代码围栏）→ 前端展示 + 免责声明
```

链路里没有任何「自动」环节：没有后台预取，没有打开文档就批量解读，没有把摘要塞进检索。每一次调用都对应一次明确的用户动作。

## 未配置时返回 422，而不是降级

未配置视觉模型时，接口返回可读的 422，提示「请在设置中选择支持图片理解（vision）的模型后再试」。查看器把它显示为内联提示，不弹窗、不阻塞阅读。

为什么不返回一个「没有模型，所以无法解读」的 200 响应？因为那会把「能力缺失」混进「业务结果」里，调用方要分辨两种情况，UI 要做额外判断，日志也看不出区别。用状态码区分「请求不成立」与「请求成功但没内容」，是 HTTP 语义本来该做的事。

同类的 422 还有四种：非 PDF 文档、原始文件未保留、图注缺少页码、块 ID 非法。每一种都有明确文案，不做「渲染失败」这种笼统提示。用户看到具体原因，才知道下一步该做什么——重新上传、手动重建、还是换一份文档。

## 不阻塞文本链路：摘要不落库、不进检索

视觉摘要生成后直接返回给当前会话，**不写数据库、不进检索上下文**。这个决定有三层考虑：

- **成本**：视觉模型调用通常比文本贵，自动把摘要塞进每次检索会让成本失控；
- **一致性**：同一页图在不同时间解读可能得到不同文字，落库后新旧摘要混杂，反而降低可信度；
- **可控**：用户点一次就调一次，重复点击会重新调用，成本由主动行为产生。

摘要里附带模型名与一句免责声明：「由视觉模型生成，可能存在误差」。这不是客套话，是在告诉用户这段文字的性质——它是模型的观察，不是文档原文。

## 只对「真的能看」的文档看图

能力边界写得很死：

- **PDF 且原始文件仍在**：可以渲染页面，可以解读；
- **DOCX / PPTX / Markdown / TXT**：只展示图注文字，不提供解读按钮；
- **旧文档、原始文件未保留**：先提示重新上传或重建，不尝试猜测。

后面这条尤其重要。很多文档早期入库时没有保留原始文件，如果为了「功能看起来完整」而去拼接一个空白页或截取缩略图，得到的就是假解读。**假装能看图，比承认看不了更糟。**

图注本身也不是图像检测的产物，它来自解析器对文本行的启发式识别（`图 N`、`Figure N` 这类模式）。所以这个功能的准确定位是「**给已识别出的图注配一次看图**」，不是「自动发现文档里所有图片」。后者需要版面模型和图像对象检测，明确不在这一版的范围里。

## 隐私边界：图像会离开本机

这是整篇文章最需要说清楚的一段。

渲染出来的页面图像会发送给**用户自己配置的视觉模型**。如果配置的是线上服务，图像就离开了本机；如果是本地模型，图像不出本机。应用无法替用户决定这件事，能做的是：

- 不默认开启，不偷偷调用；
- 只在用户点击时发送，不做后台预取；
- 摘要标注模型名与「可能存在误差」的免责说明，让用户知道这段文字由哪个模型生成；
- 不把图像或摘要写入知识库、不进入检索、不进入导出产物。

对本地优先的产品，这条边界比功能本身更重要。用户选择本地优先，往往就是为了控制数据流向；一个默认开启的云端视觉调用会把这份信任一次性透支。

## 两个实现细节

**代码围栏清理。** 视觉模型有时会把摘要包在 ``` 里返回，直接展示会破坏排版。服务层在返回前剥掉代码围栏，并拒绝空摘要——空字符串不是「解读结果」，应当按失败处理。

**块 ID 与序号的映射。** 结构视图里的块 ID 是 `b3` 这种形式，数据库里存的是 `ordinal`。服务层需要一份明确的映射，非法 ID 直接返回可读错误，而不是回落到「第一块」。回退会让用户以为解读的是图注，实际解读了别的内容。

## 验证方式

用例覆盖七类失败与一类成功：视觉模型未配置、非 PDF、无原始文件、图注缺页码、非图注块、非法块 ID、空摘要被拒；成功路径验证摘要剥壳、模型名回传、页码正确。路由层再验 422/404 与错误文案；UI 层验「未配置时禁用按钮 + 内联提示」「已配置时展示摘要与免责声明」。

失败路径比成功路径多，是这类可选能力的正常比例。真正会伤到用户的，几乎都在失败路径上。
