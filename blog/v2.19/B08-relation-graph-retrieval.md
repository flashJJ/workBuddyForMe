# 规则关系抽取加两跳检索：知识库里的「图」能做到什么程度

在一个本地优先、单人开发的桌面 AI 应用里，向量检索擅长回答「哪段文字和问题最像」，不擅长回答「这两个东西是什么关系」。合同里 A 公司收购了 B 公司，另一份文档里 B 公司又和 C 公司签了供应协议——问「A 和 C 有什么联系」，相似度检索几乎不可能把两段文字同时找出来，因为它们字面上毫无共同点。

图检索就是为这类问题准备的：把实体和关系抽出来，沿着边遍历。但「图」这个词很容易让人高估能力。一个单人的桌面应用不可能维护一套 GraphRAG：没有 LLM 关系抽取的预算，没有指代消解的标注数据，也没有社区检测的算力。这一版选择的是**规则抽取 + 有上限的两跳遍历**，并且把边界写进产品行为里。

## 先落一张最小的关系表

```sql
CREATE TABLE knowledge_relations (
  id TEXT PRIMARY KEY,
  knowledge_base_id TEXT NOT NULL,
  from_entity_id TEXT NOT NULL,
  to_entity_id TEXT NOT NULL,
  relation TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  source_document_id TEXT,
  source_chunk_id INTEGER,
  confidence REAL NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);
```

三个索引分别建在知识库、起点实体、终点实体上。表虽小，但三个字段决定了整套能力的下限：

- `source_document_id` / `source_chunk_id`：没有来源的关系不可引用，等于没有价值；
- `confidence`：规则抽出来的关系有强弱之分，必须能排序、能被阈值过滤；
- `description`：存原句片段，用户点开引用时能看到「凭什么说它们有关系」。

写入策略与实体编译绑在一起：同一次编译事务内，先把该文档的旧关系整批删掉，再写入新关系；重新摄取文档时同步清理。关系不会脱离实体单独存在，也不会在重编译后留下孤儿边。

## 抽取规则：同句、相邻、有动词

抽取的输入是已经编译好的实体列表和文档分块文本。规则只有三条：

1. **同句**：两个实体必须出现在同一个句子里，跨句关系不做；
2. **相邻**：按实体在句中的出现顺序取相邻对，每句最多 3 对，避免一句话里五个实体产生十对噪声；
3. **有标签**：关系标签优先取两个实体之间的动词或连接词——收购、合作、供应、签署、includes、supports 这类；没有明确动词时回落成「共同提及」。

置信度随之分两档：动词关系 0.75，共同提及 0.55。描述截断到 240 字符，标签截断到 40 字符。这两个截断不是随手定的，而是为了保证资料块抬头和引用列表不被一条超长关系撑爆。

还有两条硬门槛：

- 两端实体都必须已经落库，否则这条边无法被检索到，写了也是垃圾；
- 关系描述必须是原句的逐字片段，且能映射回具体的 chunk。做不到就不写——**关系必须可回指原文，否则就是模型的臆测**。

实体本身来自既有的引号、型号、括号别名规则。这意味着关系抽取的质量上限由实体覆盖决定：实体没抽出来的公司名，不会出现在任何关系里。这是规则方案的天花板，也是它可解释的原因。

## 检索：从命中实体出发，两跳封顶

查询进来后，先走既有的实体命中逻辑，拿到一组起点实体，然后做广度优先遍历：

```text
起点 {A, B}
第 1 跳：A —收购→ B，B —供应→ C
第 2 跳：C —签署→ D（通过 B 展开）
去重：同一条边只保留一次；总边数 ≤ 12
注入：最多 2 条关系事实
```

几个参数值得解释：

- **两跳**：一跳只能回答直接关系，三跳开始噪声迅速超过收益。两跳是「A 和 C 通过 B 连起来」这类问题的刚好够用深度；
- **12 条边**：遍历必须封顶，否则一个高频实体能牵出半个知识库；
- **注入 2 条**：图上下文比文本片段更容易污染回答。两条精选关系比十二条「可能相关」的关系有用。

排序规则：两端都在命中实体集合里的直接边优先，其次是跳数少的，再按置信度。这个顺序符合直觉——用户问 A 和 B，最该看到的就是 A 到 B 的直接边。

**无来源的边只参与遍历，不进入引用。** 这一条是硬约束：遍历可以借它当中转，但回答里不能出现一条「不知道从哪来的」关系。

## 关系事实长什么样

注入到模型上下文的格式是固定的一行：

```text
关系：A —[收购]→ B。原句：A 于当季度完成对 B 的收购。
```

抬头是「关系知识：《文档名》」，引用类型标记为 `relation`，聊天里显示「关系知识」徽标，点开能看到来源文档、页、段。用户核对的不只是「有关系」，而是「这句话出自哪里」。

这个格式也限制了模型的自由度：它看到的是「标签 + 原句」，不是一个可以被自由发挥的知识图谱三元组。回答里如果写出别的谓语，就和原句对不上，用户一眼能看出来。

## 为什么不做 LLM 关系生成

这是被问得最多的一个问题。答案不是「没想到」，而是三条成本：

- **一致性**：同一份文档编译两次，LLM 可能抽出不同的边。知识库需要可重建、可 diff，随机性会破坏这一点；
- **可追溯**：LLM 很容易生成「A 与 B 存在战略协同」这种没有原文支撑的关系，而这一版要求每条边都能回指原句；
- **成本与延迟**：编译是批量操作，逐句调用模型的费用和耗时都不适合本地优先的产品。

代价是召回有限：只能抽显式实体对，处理不了「该公司」「其子公司」这类指代，也抽不出事件级关系。这些被明确写进已知边界，而不是用一句「支持智能关系抽取」盖过去。

## 旧库零差异

没有实体、没有关系的历史知识库，走图检索时直接回落到普通分片检索，结果与升级前一致。这一点靠两层保证：关系表对旧库是空表，遍历起点为空时提前返回；检索链路的最终排序仍然是向量、全文、重排那一套，图上下文只是**额外的两三条事实**，不是替代品。

这很重要。图检索是增强项，不能成为单点故障；任何一个知识库没有图，问答都必须照常工作。

## 踩过的坑

**坑一：一句话里的实体对爆炸。** 早期不限制每句对数，一份罗列了十个供应商的文档产生了四十多条「共同提及」边，全部置信度 0.55，检索时把真正有价值的收购关系挤掉了。加上「每句最多 3 对」之后才恢复正常。

**坑二：没有来源的边。** 有些关系是在实体编译的中间态产生的，原句还映射不到 chunk。这种边如果进入引用，用户点开会是空白。最终规则改成「宁可只遍历，不可引用」。

**坑三：跳数越多越像噪声。** 试过放开到三跳，结果「A 的供应商的竞争对手」也会被当成相关事实注入。限制在两跳、两条之后，回答的准确感明显提升——少即是多。

## 验证方式

用例按层拆：抽取（中英文动词、共同提及回落、别名自关系跳过、多句、实体不足）、遍历（两跳展开、边去重、12 条上限、空起点与单跳退化）、编译（关系随编译写入、重编译整批替换、来源坐标）、引用（`relation` 类型与「关系知识」抬头）。

每条用例都在验证一个具体约束，而不是「图检索能跑」。约束守住了，能力边界就是可预期的。
