# 纯文本 RAG 为什么读不懂财报：结构、引用与可信度的三件事

我们的桌面 AI 应用是一个本地优先、单人开发的 AI 助手，文档知识库是它最常用的入口之一。把 PDF 丢进去、问一句话、拿回一段带页码的答案，这套流程在散文类文档上工作得很好；一旦换成财报、合同、规格书，问题就集中暴露。

最常见的抱怨不是「答错了」，而是「答对了但我不敢用」：答案说营收增长，引用指向第 37 页；你翻过去，那一页有六张表，不知道是哪张表的哪一行。再追问「表 3 第二行是多少」，它开始含糊。更麻烦的是，改了分块策略或提示词之后，没有任何可重复的手段判断这次改动是变好还是变坏。

这一版只回答一件事：**让知识库不只读到字，还能读懂章节、表格与出处**。先拆清楚纯文本链路丢掉了什么，再给出这一版的验收口径与三条主线。

## 纯文本 RAG 丢掉的四样东西

| 丢掉的 | 具体表现 | 后果 |
|---|---|---|
| 章节层级 | 所有文字合并成一条线性文本流 | 分块跨章节合并，块里看不出自己属于「付款条款」还是「违约责任」 |
| 表格边界 | 表格按行拆成普通段落 | 一张表被切成两三个块，表头与数据行分离 |
| 图注 | 图注当正文 | 「图 1 季度营收趋势」变成一句没有主语的话 |
| 出处坐标 | 只有页码或段落序号 | 引用落不到「表 3 · 第 2 行 · C3」 |

纯文本管线的隐含假设是：文档等于一串字符。但真实文档是有层级、有区域、有指向的二维结构，字符流只是它的一种投影。投影丢掉的信息，靠更大的模型和更长的提示词补不回来——模型再强，也只能看到你喂进去的那一版文本。

## 引用只能到页码，等于没有引用

页码是「阅读器」的坐标，不是「文档」的坐标。同一个 PDF 在不同阅读器、不同缩放、不同打印设置下，页码会漂移；而「合同第三章付款条款」在任何设备上都指向同一件事。

更要命的是表格。财报里一页可能并列六张表，页码只告诉你「在这一页」，表格序号和行号才告诉你「是这一行」。当模型说出一个具体数字却只能引用到页码时，用户要花几分钟自己找回那一行，这个成本足以让「引用」这项功能失去意义。

所以这一版把引用从「页/段」推进到「章节路径 + 表号 + 行号 + 单元格」。它不是为了好看，而是为了让「答案—证据」之间的路径短到可以一眼核对。

## 表格被切断，检索就命中不了

表格在向量检索里天然吃亏：一行数据单独看几乎没有语义（「首付 30%」这种行离开表头就是废话），而整张表放在一起又往往超过 chunk 预算。纯文本管线两头不讨好，最后把表切碎，于是「去年第四季度营收多少」这种问题永远检索不到正确的块。

结构化的做法是反过来：先认出这是一张表，再决定怎么切。表格要么整体进一个块，要么按数据行切开但每片都重复表头。**绝不允许一个 chunk 横跨两张表，也不允许表头和数据行落在不同的块里。**

## 改动没有质量回归，就只能靠人眼

解析、分块、重排、提示词，任何一个环节动一下，问答质量都可能变化。没有固定用例时，唯一的验证方式是开发者自己挑几份文档手动问一遍——这种验证既不可重复，也不覆盖边界。

这一版把评测当作交付物的一部分：固定文档 fixture、固定问题、固定期望，连同 mock provider 一起进 CI。它不能证明「回答一定正确」，但能证明「这次改动没有悄悄破坏已经守住的东西」。

## 一个具体场景：问「首付比例是多少」

在一份施工合同里，付款条款是一张两列表：阶段对应比例，首付 30%、封顶 50%、验收 20%。用户问「首付比例是多少」，纯文本链路通常给出三种答案：

- 检索到「付款」段落，回答「按合同约定支付」，没有数字；
- 检索到数据行「首付 30%」，但没有表头，模型把 30% 解释成进度款；
- 引用指向第 3 页，用户翻过去发现有两个相似的表格。

结构化链路的目标很具体：检索时认得这是表格意图，分块时保证表头与数据行在同一块，生成引用时能落到「表 1 · 第 1 行 · B2」。用户点一下引用，查看器展开「付款条款」章节，高亮 B2，核对完成。整个过程不需要理解 PDF 的版面，只需要一条稳定的坐标。

## 这一版守住的 8 条验收口径

1. 8 份 fixture（多栏 PDF、合同、财报表格、扫描页、Markdown、DOCX、PPTX、无结构文本）均能解析或明确降级；
2. 表格块不跨 chunk 切断；超长表格按行切分且保留表头、表号、行范围；
3. 引用可展示章节路径、表号、行号、单元格，并能在文档结构面板定位；
4. 旧库升级后旧文档检索不降级，备份恢复通过；
5. 表格问答与跨文档对比在 fixture 上可复现，空结果标明未覆盖；
6. 实体关系支持多跳检索，关系可追溯来源；
7. RAG 评测进入 CI；`pnpm check`、单测、Web e2e、桌面冒烟不降级；
8. 迁移只有一条；`/knowledge` 首屏包体增长不超过 5%。

这 8 条里有 5 条与「可验证」直接相关：可解析、可定位、可复现、可追溯、可回归。功能清单可以砍，这五条不能砍。

## 三条主线

**第一条是结构。** 从 PDF 的文字层坐标、DOCX 的 HTML 标题、PPTX 的页标题、XLSX 的工作表里，抽出一份统一的「页—章节—块—表格—图注」模型，落进 `document_blocks`。解析是 best-effort 的：失败回退纯文本，但必须留下警告。

**第二条是引用链。** 结构感知分块负责让块自带章节上下文，Citation 增加四个可选字段，检索、消息、分享导出、文档查看器四处必须同步。表格问答和跨文档对比都是这条链的下游应用：前者要定位单元格，后者要匹配章节与表格。

**第三条是可信度。** 表格置信度回答「这张表有多可能是错的」，关系检索回答「两个实体之间有没有可追溯的联系」，Promptfoo 用例回答「这些能力有没有退化」。三者都遵循同一个原则：**宁可说不知道，也不给出无法核对的结论。**

## 一条链路串起来

```text
上传原始文件
  │
  ▼
结构解析（PDF 文字层坐标 / DOCX HTML / PPTX 页标题 / XLSX 工作表）
  │  ParsedDocument：text + blocks + tables + warnings
  ▼
落库 document_blocks（按文档整批替换）+ 结构列写进 document_chunks
  │
  ▼
结构感知分块：表格原子化、超长按行切、章节前缀、标题当地界
  │
  ▼
向量 + FTS + RRF + 重排（表格意图小幅加权）
  │
  ▼
Citation：sectionPath / tableNo / tableRow / tableCell
  │
  ├── 对话引用 → 文档查看器点击定位
  ├── 分享导出 → Markdown/HTML 脚注同步
  └── 跨文档对比 → 章节/表格差异产物
```

这条链路里任何一环偷懒，下游都补不回来。比如分块不重复表头，单元格定位算法再精巧也拿不到列名；Citation 字段在导出时漏传，查看器里的高亮就成了摆设。所以这一版在契约冻结阶段就把字段和降级口径写死，实现只能按契约走。

## 刻意不做的四件事

- **不引入版面模型和新 OCR 引擎。** PDF 表格只做坐标启发式重建，复杂跨页表、合并单元格不承诺准确率，只保证降级与警告；
- **不做 LLM 关系生成。** 关系抽取用规则：同句相邻实体对加动词标签，不做指代消解、事件抽取、社区检测；
- **不自动重解析全库。** 旧文档默认保留原文本检索，结构重建由用户手动触发，避免升级当天把整个知识库重跑一遍；
- **视觉模型不做默认开启。** 图表理解是可选项，没配置就明确返回「不支持」，绝不静默降级成一句编出来的描述。
