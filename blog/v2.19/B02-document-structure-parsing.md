# 从字符流到结构块：PDF、DOCX、PPTX、XLSX 怎么被解析成「页—章节—表格—图注」

在我们这个本地优先、单人开发的桌面 AI 应用里，文档进知识库的第一步，是把文件变成可检索的文本。绝大多数实现做到这里就停了：抽出一大段字符串，按长度切开，送进向量库。对散文够用，对合同、财报、规格书不够用，因为这类文档的语义大量存在于**位置关系**里——谁是谁的上级标题、哪几行属于同一张表、图注说的是哪幅图。

解析的目标不是「还原版面」，而是给检索一套稳定的坐标系。坐标系不需要像素级准确，它需要三件事：层级清楚、边界明确、失败可解释。下面按格式拆解这套坐标系是怎么建起来的。

## 先定契约，再选实现

所有格式最终都收敛到同一个中间模型：

```ts
type BlockKind = 'heading' | 'paragraph' | 'list' | 'table' | 'figure';

interface ParsedDocument {
  text: string;                              // 规范化后的全文，所有坐标的基准
  blocks: DocumentBlock[];                   // 每个块带 kind / 页码 / 章节路径 / 字符区间
  tables: DocumentTable[];                   // 表号、表头、数据行、表注、页码
  warnings: string[];                        // 解析警告，不阻断入库
}
```

契约里有三个容易被忽略的约定，后面每一篇都会用到：

- **章节路径最多 4 层**，超出截断。层数不设上限会让路径无限长，前缀挤占分块预算；
- **表号按文档内出现顺序从 1 递增**，重建解析后可能变化，引用以重建后为准；
- **字符区间以规范化文本为基准**：换行统一、首尾空白裁剪，与分块函数同一口径。

如果解析器直接返回原始字节偏移，分块器又按自己清洗过的文本计算位置，两套坐标就会错位，引用高亮会落在错误的位置。这个坑在动手前就值得用契约堵住。

## PDF：只有文字层，也要做出结构

PDF 没有语义标签，只有一堆带坐标的文字片段（TextItem）。能用的是四类信号：y 坐标、字号、x 间距、文本模式。

**分行。** 同一页里按 y 坐标把文字片段归并成行；y 变化或字号变化就切行。这样能避免把页眉、正文、页脚粘成一行。

**分列。** 同一行内，相邻片段的 x 间距超过 `max(12pt, 1.5 倍字号)` 就认为跨了列。这个阈值看起来随意，但它解决的是「两列表格被读成一句话」这种最常见的问题。

**标题。** 同时满足两个条件才算标题：字号高于正文中位字号的 1.15 倍，且长度不超过 80 字符。再加一层文本模式匹配——`第X章`、`一、`、`1.1` 这类编号即使字号没放大也认。标题层级决定章节路径，最多保留 4 层。

**表格。** 连续至少 2 行、每行至少 2 列的片段，拼成一张表；首行当表头；紧邻的 `表 N` 或 `Table N` 文本挂成表注。识别不出来时不要硬凑：降级成段落，同时写一条警告。

**多栏。** 页面里出现「至少 4 行、固定 2 列」的稳定结构，极可能是双栏排版而不是表格。这种情况给出明确的多栏警告，让用户知道结构可能不准，而不是假装解析成功。

一个真实的取舍：这套规则对规整的合同和财报足够，对跨页表、合并单元格、扫描件就不够。我们没有引入版面模型，原因是它的体积、延迟和许可成本都超出这个版本的预算。**不承诺准确率，承诺降级可见**，是这次定下的底线。

## DOCX：不要自己去啃 OOXML

DOCX 是压缩包里的 XML，标题、表格、列表都有样式标记。自己解析 XML 听起来可控，实际要处理样式继承、编号定义、文本框嵌套，工作量远超收益。

现成的做法是先用 mammoth 把 DOCX 转成 HTML，再复用 HTML 解析器：`h1` 到 `h6` 直接映射标题层级，`table` 直接映射表格，`ul/ol` 合并成一个 list 块。这样做的代价是丢失一些 Word 特有的版式信息，收益是**一套 HTML 规则同时服务 DOCX 和网页剪藏**。

需要注意的是，mammoth 依赖 Word 的标题样式。很多真实文档是「手动加粗放大」而不是「应用标题 1」，这种文档解析出来没有标题，章节路径为空。这时不要猜，写一条「未检测到标题」的警告即可——用户看到警告，就知道为什么结构面板里没有章节树。

## PPTX 与 XLSX：各取自己最强的信号

PPTX 的结构天然简单：一页一个主题，页标题就是章节名。把每页标题作为一级章节，页内文本按段落切块，页内表格按行列拆分。不要试图从版式坐标推断层次，幻灯片本来就不靠字号表达层级。

XLSX 则相反：工作表名就是天然的章节，每个有数据的区域就是一张表。解析时保留工作表名、表头行、数据行，表号按工作表内顺序编号；表头行单独保留，数据行逐行写入。这样即使某些行缺值，也不会破坏列对齐。

这两类格式的共同点是「结构唾手可得」，所以解析器里几乎没有启发式。真正难的是 PDF，这也是为什么 8 份 fixture 里有 3 份是 PDF 变体。

## 落库：整批替换，不做增量

解析结果写入 `document_blocks`，策略是按文档整批替换：删除旧块、插入新块、同一个事务里完成。块表有 11 列，核心是 `ordinal`、`kind`、`page_no`、`section_path`、`content`、`char_start/char_end`、`table_json`，外加文档 ID 上的联合索引。

选择整批替换而不是增量更新，理由很实际：解析是纯函数式的，同一份文件重跑应该得到同一份结果；增量 diff 只会引入「旧块残留」和「序号错位」两类 bug。块与文档是级联删除关系，删文档时不会留下孤儿行。

同时，分块表新增五个结构列：`section_path`、`block_kind`、`table_no`、`table_row_start`、`table_row_end`。解析阶段只填前三个，行范围留给分块阶段——因为「这张表会被切成几片」是分块决定的，不是解析决定的。

旧文档没有结构块，读出来就是空数组，检索照旧走原文本。这一点在升级路径上非常关键：迁移不能让任何一个旧文档「消失」或「降级」。

## 降级路径比成功路径更重要

解析器有一半代码在处理失败。归纳起来是四类：

| 情况 | 处理 | 用户看到什么 |
|---|---|---|
| 整个文件解析失败 | 回退旧纯文本抽取，照常入库 | 文档可用，结构面板提示「未解析结构」 |
| 扫描件 | OCR 后按页重建，表格仅靠文本分隔符识别 | 保留 OCR 警告；表格可能降级为段落 |
| 多栏版面 | 不强行重排，按单栏读取 | 多栏警告，提示结构可能不准 |
| 表格错列 | 保留原样入库 | 「表 N 第 M 行单元格数与表头不一致」 |

降级不是隐藏错误，而是把错误变成可读的提示。用户看到「未检测到标题」，会知道这不是文档坏了，而是解析器没找到样式；看到「扫描件表格由 OCR 文本启发式重建」，会对数字多一分怀疑。**没有警告的降级，等于静默失败。**

## 8 份 fixture 各自考什么

| fixture | 考察点 |
|---|---|
| 合同 PDF | 编号标题、章节路径、两列表、表注 |
| 多栏 PDF | 多栏警告不被误判成表格 |
| 扫描页 | OCR 文本重建、降级不阻断 |
| Markdown | 管道表格、分隔行不计数据、列表合并 |
| DOCX | HTML 标题层级、表格、无样式告警 |
| PPTX | 页标题作章节、页内分段 |
| 财报 XLSX | 工作表名作章节、表头与数据行 |
| 无结构 TXT | 明确返回「未检测到标题」，不编造层级 |

fixture 的作用不是证明「解析很准」，而是证明「每种格式都有确定的出口」：要么解析出结构，要么给出可读的降级理由。这比追求一个漂亮的准确率数字更适合单人维护的项目——准确率会随文档变化，出口是稳定的。

## 验证与代价

解析侧的覆盖集中在契约而不是实现细节：8 份 fixture 是否都有确定结果、块坐标能否回溯到规范化文本、合同 PDF 的章节和表头是否逐项正确、迁移前后旧库行数是否一致、备份恢复后旧分片是否保持空结构。这些用例跑在单测层，不依赖真机。

代价也很清楚：多栏 PDF 的阅读顺序仍可能不理想，跨页表不合并，扫描表格只保证降级。它们被写进已知边界，而不是藏在实现里。
