# 引用从「第 37 页」到「表 3 · 第 2 行 · C3」：字段、透传与定位

在这个本地优先、单人开发的桌面 AI 应用里，引用是 RAG 回答里最容易被做浅的一环。很多实现把引用理解成「附上来源链接」，于是回答末尾挂着一段文档名和页码，看起来有出处，实际无法核对。用户真正需要的不是「来源存在」，而是「**这句话能在这份文档的哪个位置逐字找到**」。

这一版把引用从页码/段落推进到「章节路径 + 表号 + 行号 + 单元格」。难点不在字段设计，而在**全链路透传**：从数据库查询到检索结果，再到消息里的引用、分享导出的脚注、查看器里的高亮，任何一站漏掉字段，后面的能力就全部失效。

## 四个可选字段，而不是四个必填字段

```ts
interface Citation {
  // 既有：文档 ID、文档名、页码、段落序号、片段文本……
  sectionPath?: string[];   // ['合同', '付款条款']
  tableNo?: number;         // 文档内表号，从 1
  tableRow?: number;        // 数据行号，从 1，表头不计
  tableCell?: string;       // Excel 风格地址，如 C3
}
```

全部可选，是这次最重要的设计决定。旧消息里已经存着大量引用，改 messages 表结构或给旧数据补默认值的代价都不可接受；可选字段让旧引用「缺省即不存在」，序列化时不产生新键，读取时按缺省逻辑处理。

配套的测试不是「新字段能写进去」，而是两条反向断言：

- 新引用序列化后包含四个字段，反序列化后逐项相等；
- 旧引用（不含这些字段）序列化后**不产生新键**，字节级与升级前一致。

第二条比第一条重要。它保证了升级不会改变历史消息的存储形态，也就不会因为某处的严格校验、diff 比较或导出模板而炸掉。

## 全链路透传：四个站点都要接

```text
document_chunks(section_path / table_no / table_row_start / table_cell 来源)
        │  查询分片详情时解析 section_path JSON
        ▼
检索结果 → Citation（toCitableChunks 负责映射，表格问答时补 tableCell）
        ▼
消息落库 → SSE 推送到 web 端 → 引用列表渲染
        ▼
分享导出（Markdown / HTML 脚注）
        ▼
文档查看器（点击引用 → 展开章节 → 高亮行/单元格）
```

四处中任何一处「暂时不传」，功能都会以奇怪的方式退化：

- 检索不映射：回答里连表号都没有；
- 分享导出不映射：站内能看到单元格，导出的文件又退回页码；
- 查看器不接：引用变成纯文本，点击没有反应。

所以这一版的验收口径直接写成「检索→引用→分享导出全链路透传」，而不是「Citation 类型加了字段」。类型加字段是几行代码，透传是一条链。

## 展示优先级：表格优先于页码和段落

同一个引用可能同时有页码、段落、章节、表号、行号、单元格。展示时按信息密度排序：

1. 有 `tableNo + tableRow + tableCell`：显示「表 3 · 第 2 行 · C3」；
2. 有 `tableNo + tableRow`：显示「表 3 · 第 2 行」；
3. 没有表格信息：回落到页码或段落；
4. 章节路径单独一行展示，不参与上述优先级。

为什么表格优先？因为页码对表格几乎没有定位价值——一页可能有多张表，而「第 2 行」在任何缩放和打印条件下都指向同一行。章节路径则提供「这段话在讲什么」的背景，适合和定位信息并列，而不是互相替代。

## 表格引用的坐标口径

这里有一处必须写清楚的换算：`tableRow` 和 `tableCell` 用的是两套行号。

- `tableRow` 是**文档内数据行号**，从 1 开始，表头不计；
- `tableCell` 是 **Excel 地址**，表头占第 1 行，所以数据行 1 对应 Excel 第 2 行。

有表头时：数据行 1 → `A2` / `B2`；无表头时：数据行 1 → `A1` / `B1`。这个偏移规则必须由生成方（表格问答定位）和消费方（查看器高亮）共享同一份实现，否则「引用说 C3，高亮停在 C2」。

另一处是超长表格的分片偏移。同一张表被切成三片，每片的 `tableRowStart` 不同；用户说「第 15 行」时指的是原表第 15 行，所以定位逻辑要按分片起始行做换算，而不是按分片内序号。这也是为什么表格引用存的是行号元数据，而不是字符偏移。

## 查看器：点击引用之后发生什么

本地文档引用（没有外部网址）在消息里渲染成按钮，点击打开统一的文档查看器：

1. 读取该文档的结构（页、章节、块、表格、警告）；
2. 按 `sectionPath` 精确匹配章节树节点，自动展开祖先节点；
3. 原文面板只展示该章节路径下的结构块，滚动到目标；
4. 若有 `tableNo`，定位到对应表卡；
5. 若有 `tableRow`，高亮该数据行；若有 `tableCell`，按表头偏移换算出列与行，同时高亮单元格；
6. 顶部显示「已定位到引用」以及「章节 / 表 / 行 / 单元格」的可读文本。

几个边界情况：

- 只有章节没有表格：正常展开章节，不报错；
- 只有表号没有行号：定位到表，不强行猜行；
- 字段全部缺省（旧引用）：查看器仍展示完整结构，只是不做定位；
- 外部网页引用：保持原来的链接行为，不尝试拉取结构，避免把「引用」变成一次网络请求。

安全上还有一条：查看器里的所有结构内容按纯文本渲染，不注入 HTML，URL 不自动激活。文档内容是不可信输入，表格里的一个 `<script>` 不应该有机会执行。

## 分享导出：脚注也要带结构

Markdown 和 HTML 导出各有各的脚注格式，但都必须展示章节与表格定位：

```text
[1] 《施工合同》 · 第三章 付款条款 · 表 1 · 第 2 行 · B3
```

旧引用的脚注保持原格式，不出现空的「表 · 第 行」。这一点和序列化是同一个原则：**新能力只增不减，旧数据保持原样**。HTML 导出延续既有的安全口径：不执行脚本、不自动激活外链，避免导出文件变成钓鱼载体。

## 踩过的坑

**坑一：以为加了字段就完成了。** 最早只改了类型和检索映射，站内引用看着没问题，导出后却发现表格定位消失。根因是序列化器按白名单拷贝字段，新字段没进白名单。修复方式不是补一处，而是把「引用字段清单」收敛成单一来源，四处的序列化都从这里派生。

**坑二：前缀改变了坐标。** 章节前缀加在块内容前面，如果同时把它算进字符区间，查看器高亮会整体右移。解决方式是前缀只影响展示文本，坐标始终指向规范化原文。

**坑三：表格分片共享字符区间。** 一开始想用字符偏移定位表格行，很快发现同一张表的多片共享同一区间，偏移无法区分。最终改为「表号 + 行号」定位，字符区间只用于普通块。

## 验证方式

引用链的用例分散在四个层：序列化（新旧字段往返、旧条目零新键）、检索（表格分片转 Citation 带章节/表号/行范围）、导出（Markdown 与 HTML 脚注格式、转义）、UI（点击引用打开查看器、章节展开、行/单元格高亮、未配置能力时的提示）。每层都只测自己那一站，合起来才是整条链。

这种分层的好处是定位失败点很快：导出对了但查看器不对，问题一定在查看器消费侧，不在检索。
