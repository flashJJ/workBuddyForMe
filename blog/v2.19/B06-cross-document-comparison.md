# 跨文档对比：只比结构、不比数值，为什么反而更可靠

一个本地优先、单人开发的桌面 AI 应用，知识库里可能躺着二十份合同，你想知道新版本和老版本的付款条款差在哪；或者两份财报，想快速看出表格结构变没变。分别问答当然也能凑出答案，但人要的是**并排的差异**：哪些章节只在左边有、哪些表格对得上、对上的那张表少了几行。

跨文档对比最容易走偏的路是「让模型总结两份文档的差异」。这条路听起来聪明，实际不可控：模型可能漏掉一章、可能把数值看错、可能用一段流畅的话掩盖「其实没对上」。这一版选择另一条路：**纯函数、只比结构、产物可下载**。

## 对比的对象是结构，不是全文

产物里只有四类信息：

| 部分 | 内容 |
|---|---|
| 概览 | 两侧文档名、章节数、表格数、生成时间 |
| 章节并集 | 共有章节、仅左侧、仅右侧 |
| 表格匹配 | 表号与标题、表头是否一致、两侧行数、行标签差异计数 |
| 明细与警告 | 匹配表仅左/仅右的行标签；未匹配表格清单；解析警告 |

注意这里没有「语义差异」。不判断「这一条比那一条更严格」，也不算「金额涨了还是跌了」。理由很简单：**没有列语义的情况下，任何数值比较都可能得出错误结论**。两列都叫「金额」，一列是含税价、一列是不含税价，自动相减就是在制造错误。

章节对比则相对安全：章节名是作者显式写下的结构，同名大概率同义。即便如此，产物也只陈述「共有/仅有」，不替用户判断重要性。

## 表格匹配：先精确，再相似

两张表怎么算「同一张」？两步：

1. **精确匹配**：按表头签名比对，表头完全一致就算同一张；没有表头时退化为按表注标题比对；
2. **相似匹配**：剩下未匹配的表，两两计算表头 Jaccard 相似度，达到 0.6 以上、且一对一（一张表只能匹配一张）才认。

Jaccard 的直觉是「交集除以并集」：表头 `[阶段, 比例, 付款条件]` 与 `[阶段, 比例, 备注]` 的交集是 2、并集是 4，相似度 0.5，不够；如果只差一列，通常能过 0.6。这个阈值不是拍的，它需要在「漏配」和「错配」之间取舍——阈值低会把不相关的表配在一起，阈值高会让改了一列表头的同一张表配不上。0.6 是当前 fixture 下的折中。

匹配后比较三项：表头是否一致、数据行数、前两列的行标签差异。前两列通常是「阶段/项目/科目」这类稳定标识，适合做行对齐；后面的数值列不参与比较。

**一对一约束**是必须的。财报里常有结构完全相同的多张表（比如四个季度的分部数据），如果允许一对多，一张左表会匹配到所有右表，差异统计立刻失真。

## 为什么是纯函数

整个对比逻辑不读数据库、不调模型、不发网络请求，输入是两个 `ParsedDocument` 的结构，输出是一个可序列化的对比模型。这样做换来四件事：

- **确定性**：同一对文档、同一份结构，两次生成的产物逐字节一致，可以 diff；
- **可测试**：章节并集、Jaccard 匹配、行标签差异、转义，全部是纯函数用例；
- **零成本**：不消耗模型额度，不增加时延；
- **可回退**：出问题只需要回退这一版，不牵连检索链路。

代价是它不会「理解」文档。它说不出「这份合同的付款节奏更激进」，只能告诉你「表 1 在左边有 5 行、右边有 4 行，右边少了『质保金』这一行」。对核对场景来说，后者才是用户真正要的。

## 产物落盘：Markdown 与 HTML 双格式

对比结果同时支持两种格式：

- **Markdown**：纯文本，适合复制到文档、邮件、工单里继续编辑；
- **HTML**：带样式，适合直接阅读和归档。

产物走既有的附件（attachments）通道落盘，返回附件 ID、格式、文件名、MIME 类型、字节数、标题；预览和下载复用既有的产物路由。这样做的收益是「对比」不是一个孤立的页面状态，而是一份可以被引用、被分享、被再次打开的产物。

安全上有两条硬约束：导出的 HTML 遵守既有的 CSP，禁止脚本执行、禁止外联；文件名与文档名做转义，不让标题里的引号或尖括号破坏输出结构。产物超过 2MB 会被既有产物服务拒绝，避免一次对比把磁盘写满。

接口形态很朴素，一次请求带两份文档和一个格式：

```json
{ "leftDocumentId": "a", "rightDocumentId": "b", "format": "html", "locale": "zh" }
```

响应里既有产物引用，也有正文和统计：章节总数、共有数、仅左、仅右，表格左右数量与匹配数，以及警告列表。UI 不需要再请求一次文档结构，就能把「差异概览」画出来；需要看细节时再打开产物。

## 稳定排序，让两次结果可对比

产物里的章节与表格都按固定顺序排列：章节按路径、表格按表号。用户今天对比一次、明天再对比一次，只要文档没变，两份产物的段落顺序就一致，可以直接用 diff 工具看变化。

「稳定」这件事在小功能里常被忽略，但在对比场景里是刚需：如果每次生成顺序都不同，diff 里全是噪声，用户还是得肉眼找差异。

## 空结果与降级：照样出产物

对比的两种「不完整」状态都被显式处理：

- **文档没有结构**（旧文档或解析失败的文档）：产物里写入「尚未解析结构」的警告，章节/表格部分为空，但产物仍能生成。用户至少知道「不是没有差异，是这份文档还没解析」；
- **两边都解析了但没有任何匹配表**：产物里保留「未匹配表格清单」，并给出统计上的 0 匹配，而不是一个空白页。

同一份文档和自己对比返回 422，未知文档返回 404，都是可读错误而不是 500。这些状态在 UI 里对应不同的提示，避免用户以为是系统坏了。

## 交互：格式切换与预览

知识库页的「文档对比」入口只做三件事：选两份已索引文档、选格式、生成。生成后展示统计与警告，HTML 用 iframe 内嵌预览，Markdown 直接展示可复制的正文，两种格式都提供下载。

iframe 预览看起来是小事，实际是安全边界：产物是本地生成的 HTML，仍然不应该获得脚本执行权限。用 iframe 加 CSP，比「信任自己的模板」更稳妥。

## 边界：不自动重解析，不做数值差异

两个明确的 Non-Goal：

- **不自动重解析**。对比发现「右侧没有结构」，提示用户去结构面板手动重建，而不是在对比接口里偷偷跑一次解析。解析是重操作，触发权应该在用户手里；
- **不做数值差异**。原因前面说过：没有列语义，数字不可比。将来如果要做，前提是先有稳定的列类型标注，而不是先有减法。

这两个边界让功能保持「小且确定」：它只回答结构问题，结构问题的答案永远可核对。

## 验证方式

用例集中在纯函数与路由两侧：章节并集（共有/仅左/仅右）、表格精确匹配、Jaccard 边界、行标签差异计数、Markdown/HTML 转义、结构缺失警告、英文与文件名处理；路由侧覆盖两种格式的产物、统计字段、同文档 422、未知文档 404；UI 侧覆盖文档选择、请求体、统计与警告展示、HTML iframe 与 Markdown 正文、下载。

这套用例的共同点是「不需要模型也能跑完」。这正是纯函数设计的红利。
