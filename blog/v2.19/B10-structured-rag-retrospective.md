# 结构化 RAG 深化之后：七条把「看起来能用」变成「错得起」的方法论

功能版本和加固版本的区别，往往不在写了多少代码，而在**失败时会发生什么**。这一版给我们的桌面 AI 应用（本地优先、单人开发）加了文档结构解析、表格问答、跨文档对比、图表理解、关系检索和评测基线。功能清单看起来很长，但真正决定它能不能长期用的，是七个反复出现的选择。

这篇不复述功能，只做三件事：先对账交付了什么，再从七个真实场景里提炼方法论，最后交代哪些事刻意没做，以及这些克制换来了什么。

## 交付对账

| 方向 | 交付 | 验收方式 |
|---|---|---|
| 结构解析 | PDF/DOCX/PPTX/XLSX 的页、章节、表格、图注 | 8 份 fixture 全部解析或明确降级 |
| 结构持久化 | 块表整批替换、分片结构列、一条纯加法迁移 | 旧库行数不变、备份恢复通过 |
| 结构分块 | 表格原子化、超长按行切、章节前缀、标题边界 | 表格不跨块、行范围连续 |
| 引用粒度 | 章节路径、表号、行号、单元格 | 检索到分享导出四站透传 |
| 表格问答 | 意图识别、重排加权、单元格定位 | 单元格引用可定位到 C3 |
| 跨文档对比 | 章节并集、表格匹配、双格式产物 | 同一对文档产物可复现 |
| 图表理解 | 可选视觉模型、按需渲染、明确 422 | 未配置时不阻塞文本链路 |
| 关系检索 | 规则抽取、两跳遍历、来源引用 | 关系事实可回指原文 |
| 质量回归 | 8 个 RAG 用例、6 类指标、CI 门禁 | 基线全通过 |

数字方面：单测 3067 例，Web 集成 11/11，生产模式 e2e 139/139，RAG 评测 8/8，桌面冒烟 10/11（缺项与历史基线一致），备份恢复 39 个用例全绿。首屏 `/knowledge` 314 kB，增长 2.6%，在 5% 预算内。

这些数字不该被堆成发布报告。它们的作用是回答一个更朴素的问题：**新增能力有没有把原来能用的东西弄坏。**

## 方法论一：结构解析必须 best-effort，并且留下 warning

解析器最容易走的两条极端是「全有或全无」：要么解析成功，要么整份文档失败。前者会让复杂 PDF 永远进不了知识库，后者会让用户在上传时看到一个红色错误，却不知道错在哪。

这一版的选择是中间态：**尽力解析，失败降级，但降级必须留下可读的警告。** 8 份 fixture 里有 3 份天生不完整——多栏 PDF、扫描页、无结构纯文本。它们的作用不是证明解析器强，而是证明「不完整的文档也有确定出口」：

- 解析失败 → 回退旧纯文本抽取，文档照常可检索；
- 扫描件 → OCR 后重建，保留 OCR 警告；
- 多栏 → 不强行重排，给出多栏警告；
- 无标题 → 章节路径为空，提示「未检测到标题」。

这套设计的价值在升级路径上体现得最清楚：旧文档不会被自动重解析，也不会因为「没有结构」而检索降级。解析是增强，不是前置条件。

反面教材也很具体：如果解析失败时直接抛错、阻断入库，用户会认为「这个知识库不支持我的 PDF」，而实际上只是标题识别没做出来。**把一个可降级的问题做成硬失败，是产品设计上的自伤。**

## 方法论二：迁移只做纯加法，回滚靠应用回退

一次版本要改三处数据库：分片表加结构列、新建块表、新建关系表。做法全部是 `ADD COLUMN` 和 `CREATE TABLE IF NOT EXISTS`，不重建表、不修改旧列、不给旧行补非空默认值之外的任何逻辑。

纯加法带来三个直接好处：

- **旧库升级零风险**：分片行数不变，旧行结构列为空数组、块表为空，检索照旧；
- **回滚成本极低**：应用退回旧版本，新列新表留着但旧代码忽略，数据一行不丢；
- **备份恢复可预测**：恢复后按当前结构版本正常升级，结构块不随备份导入，需要时从原文档重建。

验证方式也跟着变简单：迁移用例只断言「升级前后行数一致」「旧行默认值正确」「迁移幂等」「级联删除生效」；备份恢复用例覆盖 39 个场景。它们不需要模拟复杂的字段变换，因为根本没有字段变换。

这条方法论可以推广到所有本地优先应用：**当你不确定新结构会不会长期存在时，先只加不删。** 删除和重建应该留给有充分验证的版本，而不是顺手做掉。

## 方法论三：引用粒度必须全链路透传，不能只改类型

给 `Citation` 加四个可选字段是半小时的事，让它们真正可用是一个版本的事。

这一版在实现中真实踩过一次：类型改了、检索映射改了，站内引用看起来完全正常；导出分享后，表格定位却消失了。根因是导出序列化器按白名单拷贝字段，新字段不在白名单。修复不是补一处，而是把「引用字段清单」收敛成单一来源，让四处序列化都从这里派生。

由此得到两条硬规矩：

- **验收口径写成链路，不写成类型**。不是「Citation 增加了字段」，而是「检索→引用→分享导出全链路透传」；
- **旧数据保持字节稳定**。序列化用例特意断言「旧引用不产生新键」，保证升级不会改变历史消息的存储形态。

四个站点分别是：数据库分片查询、检索结果映射、消息与导出序列化、查看器消费。任何一站偷懒，用户看到的都是「有时候能点、有时候不能点」的薛定谔引用。**引用的价值等于它最短的那一段链路。**

## 方法论四：表格原子化是分块的硬约束，不是优化项

分块器最自然的写法是「按长度切」，表格在这种写法下必然被切碎。这一版把表格设成硬约束：一个表格不跨 chunk；超长表格按数据行切，每片重复表头，行范围用原表行号。

三个细节决定了它是否真的能用：

- 重复表头，否则数据行失去列语义；
- 行号是文档级，不是分片级，否则「第 15 行」在不同片里指向不同数据；
- 所有分片共享原表的字符区间，引用靠表号加行号定位，而不是字符偏移。

第三条初看是妥协，实际是稳定性设计。给每片算独立字符区间，重建解析或调整切分参数时区间就会漂移，引用跟着失效；共享区间加行号元数据，反而稳定。

被放弃的方案是语义分块：按 embedding 相似度找断点。它会把一张表的前半段和后半段判成两个话题，因为它只看文字相似度，不看「这是一张表」。结构信号是硬约束，语义信号是软优化，冲突时硬约束优先。

## 方法论五：可选能力必须显式不可用，不能静默降级

图表理解依赖视觉模型。这一版没有把它做成默认能力，而是做成「配置了才可用」：结构接口返回可用性布尔值，未配置时查看器内联提示、按钮禁用，接口返回可读的 422。

这条设计的核心不是状态码，而是**能力缺失必须显式**：

- 不在后台预取、不自动批量解读；
- 摘要不落库、不进检索，成本由用户主动触发；
- 只对保留原始文件的 PDF 渲染页面，其他格式只展示图注文字；
- 界面上说清楚图像会发送给用户配置的模型，线上模型意味着图像离开本机。

为什么值得这么谨慎？因为静默降级最伤信任。用户点「理解图表」，系统返回一段看似合理的描述，实际是模型在模糊图像上的猜测——这比直接说「未配置」糟糕得多。**可选能力的正确形态是：能用时明确可用，不能用时明确不可用。**

## 方法论六：评测当契约，用 mock 锁住口径

RAG 的质量有两个层面：真实模型答得好不好，和链路契约有没有被破坏。前者天然波动，后者必须稳定。这一版只把后者做成门禁：Promptfoo 配 8 个 fixture，provider 是零网络的 mock，按 caseId 返回固定 golden 输出，CI 在 `pnpm check` 之后执行。

六个 metric 分组把「什么叫没坏」写成了可执行断言：引用可追溯、空结果识别、对比产物、关系可追溯、表格置信度、降级说明。任何一处字段丢失或文案删除，都会让对应用例变红。

这里有个必须承认的局限：mock 评测证明的是管线没坏，不是答案变好。把它当质量上限会自欺，当回归下限才合适。真实模型质量仍靠单测、集成和人工抽检。

但即便如此，它仍是这一版性价比最高的投入。**没有回归门禁的功能版本，每次改动都在赌；有了门禁，赌局变成了工程。**

## 方法论七：降级要看得见，警告要有统一出口

七个方法论里，这一条最不显眼，却贯穿了所有能力：

- 表格置信度低于 0.75，查看器显示「置信度 N%」徽标；
- OCR 重建的表格统一压到 0.55，并追加来源警告；
- 空结果返回 `limitations`，明确「未检索到相关片段」，不编造；
- 跨文档对比遇到未解析文档，产物里写明「尚未解析结构」；
- 结构面板把警告汇总展示，而不是埋在日志里。

同一份警告数据进入结构接口、查看器、对比产物三个展示面，共用一份生成逻辑。这样就不会出现「接口说有警告、界面没显示」的割裂。

一句话总结：**没有警告的降级，等于静默失败。** 用户不需要知道解析器内部发生了什么，但他需要知道「这个结论有多可信、下一步该做什么」。

## 纪律：明确不做什么

这一版的范围锁得很死，中途没有破：

- 不整库移植重型 RAG 框架；
- 不引入 Python/Go/Rust 常驻服务，不引入版面模型或新 OCR 引擎；
- 不做文档编辑器、协同批注、云端同步；
- 不自动重解析全库历史文档；
- 不做 LLM 关系生成、指代消解、社区检测；
- 不把 Ragas 作为运行时依赖，只借指标命名；
- Promptfoo 只作为开发依赖，不进安装包。

每条 Non-Goal 都对应一个诱惑：「既然表格都结构化了，顺手做个计算吧」「既然有实体了，顺手接个图数据库吧」。这些「顺手」单个看都合理，加在一起就会把一个功能版本拖成半年工程。**范围纪律不是不做，而是知道这一版不做。**

## 这笔投入买到了什么

对一个单人维护的本地应用，结构化 RAG 的收益不在演示时的那一声「哇」，而在三件很朴素的事：

- 新上传的财报、合同能直接看出章节和表格，答不出来时能说清「为什么答不出来」；
- 每条引用都能点到具体章节、表、行、单元格，用户核对成本从几分钟降到几秒；
- 改动分块、重排、提示词之后，有一组固定用例告诉你「哪些行为被碰到了」。

代价同样明确：复杂版面仍不承诺准确率，扫描表格仍可能错位，关系抽取仍受实体覆盖限制。这些边界写在产品里，而不是留给用户去猜。

从「看起来能用」到「错得起」，差的不是更多功能，而是每个失败路径都有出口、每个能力边界都有提示、每个不变量都有断言。结构解析、迁移、引用、分块、可选能力、评测、降级——七条方法论，说的其实是同一件事：**让系统在不确定的时候，仍然给出可核对的答案。**
