# 表格置信度与 RAG 评测：把「可能不准」说清楚，把回归变成契约

在一个本地优先、单人开发的桌面 AI 应用里，结构化检索最大的风险不是「没有能力」，而是「能力看起来有，结果却是错的」。PDF 表格靠坐标启发式重建，遇到合并单元格、跨页表、扫描件，行列都可能错位。这时系统仍然会给出一个漂亮的表格引用，用户看一眼就信了——这比直接报错危险得多。

这一版用两套机制对冲这个风险：**表格置信度**负责在单张表上告诉用户「这张表有多可能是错的」，**Promptfoo 评测**负责在整体上告诉开发者「这次改动有没有破坏已经守住的行为」。前者面向用户，后者面向自己。

## 置信度是一个启发式分数，不是概率

先澄清定位：`confidence` 不是「这张表正确的概率」，而是「根据可见信号，这张表有多值得信任」的相对分数。它不看图像、不做版面识别，只检查表格自身的一致性。

分数落在 `[0.25, 1]`。下限不是 0，因为一张再糟的表也仍然是从文档里抽出来的，不该被当成完全无效；上限是 1，因为规则解析永远不能声称「绝对正确」。

五个降分信号：

| 信号 | 说明 |
|---|---|
| 缺表头 | 没有表头，列语义无法确定，引用到单元格也解释不清 |
| 数据行 ≤ 1 | 只有一行数据，和段落没有本质区别，却会被当成表格引用 |
| 表头与行单元格数不一致 | 典型的错列信号，说明列切分失败 |
| 空单元格比例 > 30% | 大面积空白通常意味着合并单元格或列错位 |
| 列数 < 2 | 单列结构可能只是一个列表，被误判成表格 |

这些信号全部可以用一次遍历算出来，纯函数、无副作用。它们的共同点是「能从表格自身观察到」，不依赖外部信息——这是启发式分数能被解释、能被单测的前提。

## 0.75 以下写警告，徽标展示

低于 0.75 的表，在结构 API 的警告列表里写入一条结构化警告；查看器在表卡上展示「置信度 N%」徽标。用户不需要理解算法，只需要知道这张表该不该直接信。

为什么阈值是 0.75？因为单个信号通常只扣一档：缺表头或错列会明显掉分，稀疏扣得少一点。0.75 大致对应「至少有一个明显问题」。它不是统计出来的最优值，而是一个**可解释的分界线**——低于它，用户应该去看原页；高于它，可以先信，但引用仍然可点。

置信度不影响检索，也不影响回答。表格仍然按原文参与召回、按原文回答，警告只是叠加在展示层。这一点是刻意的：如果低置信度直接阻断检索，用户问「这张表写了什么」时会得到一个「表格不可信」的拒答，而他明明可以自己判断。

## OCR 表格统一压到 0.55

扫描件是另一条路径：没有文字层，先 OCR 得到文本，再从文本的分隔符启发式重建表格。这条路径的不确定性远高于文字层解析，所以规则很直接——**凡是 OCR 重建的表格，置信度一律压到不超过 0.55**，并追加一条警告「扫描件表格由 OCR 文本启发式重建」。

为什么用上限而不是再算一遍信号？因为 OCR 文本本身就可能丢列、串行，表格内部一致性看起来再好也不代表正确。这时再精细地打分，会给出一种虚假的精确感。统一保守降分，反而诚实。

这条规则也解释了「为什么不做版面模型」：如果引入版面模型，OCR 表格的置信度就该由模型给出，而不是拍一个上限。当前没有模型，就用最保守的规则兜底，并在已知边界里写明「扫描件结构可能不准确」。

## 警告进入三个展示面

同一份警告数据会出现在三个地方：

- **结构接口**：`warnings` 数组，附带可读文本；
- **文档查看器**：表格卡上的置信度徽标、警告文案；
- **跨文档对比产物**：继承两侧文档的解析警告，避免用户在对比报告里把「结构没解析」误读成「没有差异」。

三个展示面共用一份生成逻辑，避免「接口说有警告、界面没显示」这种割裂。多栏 PDF 的警告沿用解析阶段的结果，这一版不新增版面模型，只做置信度与降级说明。

## 评测：为什么要用 mock provider

Promptfoo 是一个开源的提示词与评测工具，配置用 YAML，断言可以分组。这一版用它建立 RAG 的回归基线，但做了一个不寻常的选择：**provider 是 mock 的，零网络**。

理由不是「省事」，而是把两个问题分开：

- 真实模型回答质量：受模型版本、温度、上下文影响，本身就在波动；
- **链路契约**：引用字段有没有丢、空结果有没有说、对比产物有没有生成、关系有没有来源。

后者才是这一版改动最容易破坏的东西。用固定 golden 输出加 mock provider，可以把「链路契约」从「模型质量」里剥离出来，让 CI 稳定、可重复、零成本。真实模型的质量仍然靠单测、集成和后续扩展用例保障。

## 8 个用例覆盖什么

| 用例 | 考察点 |
|---|---|
| 章节定位 | 回答能引用到具体章节路径 |
| 表格单元格 | 能引用到表号、行号、单元格 |
| 空结果 | 无依据时明确说「未检索到」，不编造 |
| 跨文档对比 | 产物生成、统计字段正确 |
| 关系检索（直接） | 一跳关系可引用、带来源 |
| 关系检索（多跳） | 两跳可达、边数受限 |
| 扫描表格置信度 | 低置信度有警告，仍可回答 |
| 旧文档无结构 | 不报错、明确提示未解析 |

这八条不是随机抽样，而是这一版新增能力的边界清单：结构、表格、对比、图、降级、兼容，每一条都对应一个可能悄悄坏掉的环节。

## 六类 metric 分组

断言不止校验文本，还按指标分组：

- `citation_traceability`：回答里的每个事实都能在引用中找到；
- `empty_result_recognition`：该说不知道的时候说了不知道；
- `comparison_artifact`：对比产物存在且统计正确；
- `relation_traceability`：关系事实带来源文档；
- `table_confidence`：低置信表格有明确标识；
- `degradation_explained`：降级路径有可读说明。

这套分组借鉴了 Ragas 的指标命名思路（faithfulness、context precision 这类），但没有引入 Python 或 Ragas 包——只在断言层面借用「按维度分组」的组织方式。对单人项目，少一个运行时依赖就少一份维护成本。

## 进 CI 的方式

Promptfoo 只作为开发依赖，不进运行时，不影响安装包体积。根脚本提供一条 `eval:rag` 命令，CI 在 `pnpm check` 之后执行，并设置 `PROMPTFOO_DISABLE_TELEMETRY=1` 关闭遥测。当前基线 8/8 全通过。

这里有个值得说明的取舍：评测放在 `check` 之后，而不是之前。`check` 管类型、lint、行数、结构、循环依赖，是更快的第一道闸；评测更慢，放在后面可以在明显错误上先省时间。

## 评测作为契约的意义

一个评测用例最有价值的时刻，是它**在改动后失败**。比如有人重构序列化器时漏了 `tableCell`，单元格用例会红；有人把空结果的 `limitations` 删了，空结果用例会红；有人给关系事实去掉了来源文档，关系可追溯用例会红。

这比「文档里写着要透传」有用得多。文档会过期，断言不会——除非有人主动改 golden，而改 golden 本身就是一次需要解释的动作。

当然，mock 评测证明的是「管线没坏」，不是「答案变好了」。把它当成质量上限会自欺，把它当成回归下限才合适。

## 局限

- 置信度是启发式分数，无法识别「表头正确但数据列串位」这类内部错误；
- OCR 表格统一压分，保守但粗糙；
- 评测 fixture 只有 8 份，覆盖边界不等于覆盖真实文档分布；
- mock provider 不评估真实模型质量，提示词改动的收益仍需人工抽检。

这些局限被写进版本边界，而不是藏在「已通过 8/8」的结论后面。
