# 结论要有下文，记忆要有来路

一个私人 AI 应用最容易出现的尴尬，不是功能不够，而是**信息在产生之后没有去处**：会议聊得很热闹，散会后什么都没留下；记忆存了很多条，被召回时却说不清它从哪里来。这一版我们只盯两条链路，把它们的最后一公里接上。

本文是系列总览，先讲清两条链路解决了什么、边界在哪，再给出门禁数字；具体实现拆到后续六篇。

## 一、两条「做完就散」的链路

第一条是**讨论 → 结论 → 行动项 → 提醒 / Flow**。此前的会议能转录、能多人（多助手）轮流发言，但会议结束即终点：没有结论沉淀，也没有任何东西被推进到执行层。用户想「会后跟进」，只能自己复制粘贴。

第二条是**记忆 → 来源会话 → 来源消息 → 召回理由**。此前的长期记忆能自动提取、能语义召回，但召回结果是一条孤立文本：用户看到「你偏好深色主题」，无法判断这是自己说过的、助手推断的，还是系统编的。

两条链路的共同点：**数据已经存在，缺的是可追溯性和下一步动作。**

## 二、链路一：从讨论到执行

一条会议要走到执行，中间有四个明确的状态转换：

| 环节 | 触发条件 | 产物 |
|---|---|---|
| 生成结论 | 会议已结束 + 用户显式点击 | 摘要、决策、未决问题、行动项 |
| 编辑结论 | 结论已存在 | 人工修订的摘要 / 决策 / 未决问题 |
| 行动项流转 | 会议已结束 | `open → done / cancelled`，可回退 |
| 转提醒或跑 Flow | 行动项满足前置条件 | 一次性提醒，或一次已发布 Flow 运行 |

三个边界值得单独强调：

- **只有已结束的会议才能生成结论**，进行中或已打断的会议一律拒绝；
- **生成必须由用户显式触发**，不会在每轮发言后自动调用模型；
- **结论调用不启用工具、MCP 与知识库**，它只读会议转录，避免总结过程被外部检索污染。

行动项的落点也被刻意收窄：只有「转提醒」和「运行已发布 Flow」两种，不创建通用待办，也不派发桌面 Agent 任务。会议域的事情在会议域收口。

```text
转录 → [用户显式触发] → 结论 JSON → 行动项
                                  ├─ 转提醒：需截止时间 + 助手是会议成员
                                  └─ 运行 Flow：仅限已发布 + 参数自动映射
```

之所以把「结论」和「执行」拆成两层，是因为它们的失败模式不同：结论生成失败只需要重试或手改，执行失败却会在外部留下半截动作。分开之后，前者可以整体回滚，后者可以逐条审计。

## 三、链路二：让记忆说清来路

记忆侧的目标不是「记得更多」，而是「每条记忆都能回答三个问题」：

1. 它来自哪次会话？
2. 它对应哪条助手消息？
3. 这一轮为什么被召回？

对应到实现，是来源字段、召回计数与召回理由三件事。新提取的记忆写入来源会话与本轮助手消息；会话摘要类记忆只记来源会话，不伪造单一消息；手工创建和升级前的旧记忆显示「来源未知」。

召回时返回一个归一化分数与 `reason=semantic`，界面只把它翻译成「相关度高 / 中 / 低」，不展示伪精确的百分比。来源会话或消息被删除后，界面给可读提示，但记忆本身保留——**删除来源不等于删除事实**。

溯源没有引入新的存储引擎：只是在既有记忆表上增加来源消息与召回次数字段，召回命中时同步刷新访问时间。这样做的代价是旧数据无法补齐，收益是升级不需要回填、也不会为了「看起来完整」而猜测来源。数据仍然只在本机，来源链接指向的也是本地会话与消息，不上传任何审计信息。

## 四、同一版里完成的三项 P1

链路之外，这一版还补了三个直接影响可信度的小口子：

- **截图粘贴引导**：视觉模型下可直接粘贴截图；无视觉模型或处于任务模式时，给出明确、可执行的提示，而不是静默丢弃；
- **跨链路运行报告**：把任务、工作流、协作运行三张既有表汇总成成功率、中位耗时与失败 Top 5，支持时间窗、链路筛选与 Markdown / CSV 导出；
- **桌面性能基线**：在打包产物上采样启动、首窗、首页可交互与空闲内存，让「感觉变慢了」变成可比较的数字。

## 五、平台迁移：桌面壳换到新平台

这一版同时把桌面壳迁到 Electron 45。两个破坏性变化必须一起处理：

- `safeStorage` 的同步加解密 API 被标记弃用，密钥全链路改成可 `await`；
- 沙箱 preload 移除 `Buffer / events / timers / url` 等 Node 全局。

迁移策略是「先升级平台，再做破坏性改造，最后用打包态冒烟验证」，而不是把平台升级与业务功能揉成一次提交。旧版本写入的密文在新版本仍可解密，这一点在真机上单独验证过。

## 六、门禁数字

| 项 | 结果 |
|---|---|
| 类型检查 / 静态检查 | 全仓通过，lint 0 error |
| 行数门禁 | 手写文件 ≤300 行 |
| 数据库单测 | 226 例 |
| core 单测 | 1130 例 |
| web 单测 | 581 例 |
| 浏览器端到端 | 全量 112/112（空载复跑 22.8 分钟） |
| 桌面端到端 | 11/11（打包目录产物） |
| 性能基线 | 启动 2832 ms · 首窗 5576 ms · 首页可交互 5910 ms · 空闲 470→477 MB / 15s |

首轮浏览器端到端曾出现 110/112，唯一失败是一条首字等待型 flaky；定向复跑 5/5 通过后，全量再跑得到 112/112。我们没有把「复跑通过」直接当成结论，而是保留了两轮数字。

验证不是只跑单测：桌面侧另有打包目录上的冒烟，覆盖窗口、四个模块导航、安全基线、控制通道、托管访问凭据、桌宠与键鼠；真机侧再做安装、覆盖升级、卸载保留数据重装与旧密文解密。单测证明逻辑，冒烟证明封装，真机证明升级路径。

## 七、这一版真正的取舍

- **不做自动总结**：每场会议自动生成结论会制造大量无人阅读的文本，也会把模型成本藏进后台；
- **不做结论版本历史**：重新生成覆盖当前结论，覆盖前二次确认，避免用户面对一堆近似版本；
- **不建通用待办系统**：行动项只在会议域，产品边界比功能数量更重要；
- **不伪造来源**：旧记忆无法补齐来源消息时，如实显示「来源未知」；
- **不把迁移和功能混为一谈**：平台升级单独验收，业务链路单独验收，出问题时能快速定位是哪一层。

## 八、后续拆解

接下来六篇按机制展开：先用一篇讲会议结论如何被约束成可落库的数据，再用一篇讲行动项状态机与提醒 / Flow 的边界；随后两篇分别讲记忆溯源与召回理由、桌面壳新平台的异步化迁移；最后两篇讲备份恢复与发布前的运行报告、性能基线。

两条链路看起来一个在会议域、一个在记忆域，其实是同一个工程原则的两面：**任何被系统生成的东西，都要能回答「它从哪来、下一步去哪」。**
