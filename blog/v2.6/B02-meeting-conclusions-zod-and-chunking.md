# 让模型输出变成可落库的结论：Zod 校验与长转录分块

会议结论听起来是个提示词问题，真正难的是另一件事：模型返回的是**一段文本**，而产品需要的是**一行可直接渲染、可编辑、可备份的数据**。这两者之间如果只靠 `JSON.parse`，迟早会把半截结论写进数据库。

这篇讲我们如何把「讨论」压成「结论」，以及三个必须存在的闸门：状态、并发与校验。

## 一、问题：LLM 输出不是数据源

最直觉的做法是让模型返回 JSON，然后直接解析入库。它会在四个地方坏掉：

- 模型在 JSON 外包了 Markdown 代码围栏，或者先写一段「好的，以下是结论」；
- 字段名对但类型错，比如 `decisions` 返回字符串而不是数组；
- 缺必填字段，或者 `summary` 为空；
- 会议很长，转录超出模型上下文，调用直接失败。

这些都不是「提示词再写清楚一点」能根治的。提示词是概率约束，代码需要确定性约束。所以我们把模型输出当成**不可信输入**，在入库前设三道闸门。

## 二、第一道闸门：状态

只有**已结束**的会议才能生成结论。进行中或已打断的会议请求生成，直接返回 409，而不是「先生成一半等会议结束再补」。

理由很实际：进行中的会议还在产生新发言，此时生成的结论必然过期，而且会给用户一种「结论已经定了」的错觉。打断的会议同理，它的转录不完整，总结出来的东西没有决策价值。

会议结束之后，输入区隐藏，结论面板出现。这个 UI 变化本身就是状态的可见表达：**能生成结论，意味着这场讨论已经封口。**

## 三、第二道闸门：显式触发与并发

生成不会随每轮发言自动发生。原因有三：

1. 自动生成会把模型成本藏进后台，用户不知道钱花在哪；
2. 每轮都生成会产生大量中间结论，绝大多数没人看；
3. 自动生成与用户手动编辑会互相覆盖。

点击生成后，服务端用进程内集合记录「正在生成」的会议 id：

```text
if meeting.status != finished        → 409
if generating.has(meetingId)          → 409「结论正在生成，请稍候」
generating.add(meetingId)
try   { …调用模型、校验、落库… }
finally { generating.delete(meetingId) }
```

这个锁只在单进程内有效，够用：桌面应用只有一个内置服务进程。它的目的不是分布式互斥，而是防止用户连点两次生成、写出两份结论。

## 四、第三道闸门：Zod

模型输出先经过一层容错解析，再交给 Zod：

| 阶段 | 处理 | 失败结果 |
|---|---|---|
| 取 JSON | 忽略前后杂文本与代码围栏，取第一个 `{…}` | `no_json` |
| 解析 | `JSON.parse` | `no_json` |
| 形状校验 | Zod schema 校验字段与长度 | `invalid_shape`，附 issue 列表 |

Zod schema 约束了四组字段：

- `summary`：必填，1–2000 字符；
- `decisions` / `openQuestions`：允许空数组，各最多 20 条；
- `actionItems`：最多 30 条，每条 `content` 必填且 1–500 字符；
- `ownerMemberId` / `dueAt`：Zod 校验类型与格式（字符串或 `null`、带时区的 ISO 时间），成员身份由服务层再校验一次。

校验失败时抛出 `PROVIDER_ERROR`，**不写任何伪结论**。这一点是硬约束：宁可让用户看到「生成失败，可重试」，也不要在数据库里留一份半成品，让后续导出、备份、提醒全都建立在脏数据上。

## 五、长转录：先分块压缩，再总结

单次结论调用最多携带约 **2.4 万字符**的转录。超过这个长度，先压缩再总结，而不是硬塞给模型。

| 参数 | 值 | 作用 |
|---|---|---|
| 单次上限 | 24,000 字符 | 超过即进入压缩路径 |
| 单块预算 | 8,000 字符 | 按消息边界切，尽量不拆单条消息 |
| 最大块数 | 6 块 | 更多时保留首 3 块 + 末 3 块 |
| 省略标记 | 显式插入 | 中间内容被省略时告知模型 |

压缩提示词只要求保留明确决策、分歧、行动项、负责人、截止时间、关键事实与数字，删掉寒暄、重复与跑题。压缩结果按「片段 1 / 片段 2 …」拼接，再交给结论提示词。

这里有一个取舍：**压缩会丢信息，但不压缩会直接失败。** 我们选择保留首尾、显式标注省略，让模型知道中间有缺口，而不是让它以为看到的就是全部。

## 六、重新生成：替换自动项，保留手工项

行动项有两个来源：`generated` 与 `manual`。重新生成时：

- 自动生成的行动项被整体替换，并重置为 `open`；
- 手工添加的行动项原样保留；
- 结论主体（摘要 / 决策 / 未决问题）被覆盖。

替换与保存结论在同一个事务里完成，避免出现「结论更新了、行动项还是旧的」的中间态。覆盖前 UI 必须二次确认，并明确提示这两条语义。

不保留结论版本历史是刻意的：会议结论不是文档协作，保留一堆近似版本只会让用户不知道该信哪一份。要留痕，就手工编辑，`edited_at` 会记录人工修订。

## 七、可编辑字段与失败恢复

结论落库后只开放三个字段的行内编辑：摘要、决策、未决问题。行动项单独编辑，不走结论更新接口。

编辑不经过模型，直接写库并刷新 `edited_at`。这样用户对模型输出不满时，有一条确定性的修正路径，而不是只能反复重新生成、祈祷这次好一点。

失败路径也被明确成可恢复状态：

- 无可用模型：提示配置模型，保留转录；
- JSON 非法 / 形状错误：提示生成失败，保留转录，可重试；
- 并发冲突：提示稍候，不产生副作用。

**转录永远不因为总结失败而丢失**，这是整个设计的底线。

## 八、测试与三条教训

测试分三层：协议层用 golden 转录验证解析与分块；服务层用 mock 模型验证状态、并发与事务；路由层验证 201/200/409 与非法 JSON 的降级。

三条教训值得带走：

1. **提示词不是 schema。** 再详细的「请只输出 JSON」也挡不住模型加围栏，校验必须写在代码里。
2. **失败要不写，而不是写空。** 空结论比没有结论更危险，它会被导出、被备份、被当成事实。
3. **长输入要设计降级路径。** 分块压缩不是优化，是让长会议仍然可用的必要条件。

到这里，「讨论」已经变成了一份可编辑、可备份的结论。下一步是让它产生动作——那是行动项状态机与提醒 / Flow 要解决的问题。
