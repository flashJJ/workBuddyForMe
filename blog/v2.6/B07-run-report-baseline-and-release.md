# 发布前的三件小事：运行报告、性能基线与截图粘贴

一个功能版本收尾时，最容易剩下三类工作：用户不知道怎么用、出问题说不清、变慢了没证据。它们单看都不算功能，合起来却决定发布后的第一周好不好过。

这一版在主线之外补了三件小事：跨链路运行报告、桌面性能基线、截图粘贴引导。这篇按「做了什么、为什么这么做、留下了什么」复盘。

## 一、运行报告：只读三张旧表

运行数据其实一直存在，只是散在三个地方：任务运行、工作流运行、协作运行。用户想知道「最近一周成功率怎么样」，只能分别打开三个页面自己心算。

运行报告做的事情很朴素：把三张既有表汇总成一份只读报告。

**不新增运行表**是硬约束。新增一张「运行汇总表」意味着所有写入路径都要多写一次，任何一条漏写都会让报告与实际不一致。只读聚合的代价是查询时多扫一点数据，收益是**报告永远不会与真实运行分叉**。

### 1.1 状态归一

三张表的状态命名各不相同，报告层先做一次映射：

| 链路 | 原始状态 | 归一结果 |
|---|---|---|
| 任务 | `completed` | 成功 |
| 任务 | `failed` | 失败 |
| 任务 | `stopped` 且原因为用户停止 | 已取消 |
| 任务 | `stopped` 其他原因 | 失败 |
| 工作流 | `succeeded` | 成功 |
| 工作流 | `failed` / `interrupted` | 失败 |
| 工作流 | `cancelled` | 已取消 |
| 协作运行 | `done` | 成功 |
| 协作运行 | `failed` / 超预算 | 失败 |
| 协作运行 | `cancelled` | 已取消 |

剩余状态一律归为「运行中」，不计入成功率分母。这一点很重要：把运行中的任务算成失败，会让报告在长任务多的时候显得特别难看，而用户无法据此做任何决策。

### 1.2 指标口径

- 成功率 = 成功 /（成功 + 失败 + 已取消），只算终态；
- 耗时取中位数，而不是平均值，避免个别超长运行拉偏；
- 失败按错误码聚合成 Top 5，同数量按错误码字典序稳定排序；
- 时间窗按 UTC 自然日，默认最近 7 天，支持 `all / task / flow / agent` 四种链路筛选。

导出支持 Markdown 与 CSV。Markdown 给人看，CSV 给表格工具看；两种格式共用同一份聚合结果，避免「页面上的数字和导出文件不一致」这种低级但致命的问题。

后端只有一个汇总服务与一个查询接口，前端是侧栏里的运行报告页：日期窗、链路筛选、汇总卡、链路表、失败 Top 5、导出按钮。测试覆盖 core 3 例（汇总 / 窗口校验 / 导出）、API 2 例、页面 3 例。

## 二、性能基线：把「感觉慢」变成数字

性能问题在桌面应用里特别容易变成口水仗：开发机上有缓存、有热更新、有调试器，感觉不准；用户机器上是冷启动、真实数据、杀毒扫描，感受完全不同。

所以基线脚本只跑**打包产物**，不跑开发态：

```text
启动 → 首窗 → DOMContentLoaded → 首页可交互 → 空闲内存采样
```

测量项与真机数字：

| 指标 | 数值 |
|---|---|
| 启动 | 2832 ms |
| 首窗 | 5576 ms |
| DOMContentLoaded | 5646 ms |
| 首页可交互 | 5910 ms |
| 空闲工作集（早期 → 15s） | 470 MB → 477 MB（+7 MB） |
| 峰值工作集 | 498 MB |
| 进程数 | 4 |

采样条件是打包目录产物、临时数据根、空闲 15 秒。临时数据根意味着这是一个「干净首启」的数字，不含用户历史数据的影响；它适合做版本间对比，但不能直接当成用户机器上的体感。

三个使用原则：

- **同一台机器、同一份数据根类型下比较**，跨机器比绝对值没有意义；
- **看趋势，不看单点**，一次 5.9 秒不代表慢，连续三个版本往上走才是信号；
- **基线脚本要能在旧包上跑**，否则没有对照，只有孤零零一个数字。

这一版没有采集上一个版本的对照基线，是已知残余。脚本已参数化，可以在旧包上补跑，但不应该在发布总结里假装已经比过了。

## 三、截图粘贴引导：三条路径，三句人话

截图粘贴原本就有实现，问题在边界：不是所有模型都能看图，任务模式也不接受图片附件。用户粘贴后没反应，只会以为功能坏了。

这一版把三条路径显式化：

| 场景 | 行为 |
|---|---|
| 视觉模型 + 普通对话 | 剪贴板图片进入待发预览，可直接发送 |
| 无视觉模型 | 提示「当前模型不支持图片理解，请切换到视觉模型后再粘贴截图」 |
| 任务模式 | 提示「任务模式暂不支持图片附件，请退出任务模式后再试」 |

关键不是提示文案，而是**不静默失败**。图片粘贴是一个用户已经完成动作的操作，如果系统不接受，必须当场说明原因和下一步，而不是让预览区空着。

测试覆盖有视觉模型与无视觉模型两条路径，避免以后换模型能力探测逻辑时，提示悄悄失效。

## 四、发布产物与已知残余

安装包约 190.8 MB，覆盖升级在本机验证通过：升级后 40 篇文档、3901 个分块、6 个知识库、6 条工作流仍在；上一版本写入的密钥在新版本正常解密；卸载保留数据后重装也能恢复。自动更新元数据已生成，发布态的更新检查连通。

已知残余有三条，都写在发布说明里：

1. 自动更新的真实检测留到发布后手动触发。草稿态对更新客户端不可见，这不是代码问题，是发布流程的时序问题。
2. 记忆溯源的浏览器端到端没有单列，由 core 集成测试、对话页深链测试与面板测试覆盖。覆盖是够的，但形态不统一。
3. 上一版本的性能对照基线未采集，只能在旧包上补跑。

把残余写清楚，比假装没有残余更有用。用户看到「已知问题」时，至少知道这不是自己操作错了。

## 五、五条方法论

1. **报告只读，不新增写路径。** 任何汇总表都会引入双写一致性问题，能用聚合解决就不要落表。
2. **成功率只算终态。** 运行中不是失败，把它算进分母只会制造焦虑。
3. **性能只在打包态测。** 开发态的数字不能代表用户，甚至不能代表下一个版本。
4. **边界要给出下一步。** 提示「不支持」不够，要告诉用户切模型或退任务模式。
5. **残余要写进发布说明。** 没做的、没测的、没比的，都比「一切正常」更值得记录。

这三件小事没有一条能上功能列表，但它们共同回答了一个问题：**发布之后，用户能不能自己判断这个应用靠不靠谱。** 运行报告给证据，性能基线给刻度，截图引导给反馈——可信度就是这样一点点攒出来的。
