# 备份的第三条轨：让记忆与会议结论可恢复

备份功能最容易产生一种虚假安全感：文件导出成功、恢复也显示成功，但真正重要的东西——长期记忆、会议结论、行动项——根本不在归档里。

这一版把备份格式升了一版，在既有的事件轨里补上三份负载，并重新定义了恢复时的合并语义。核心目标只有两个：**旧归档能读，重复恢复不炸。**

## 一、旧备份覆盖了什么，又漏了什么

原有备份按轨道组织：配置、知识库、任务、事件等，各自有 manifest 计数与 precheck。会议转录在，但会议之后的结论与行动项不在；记忆表在，但新增的来源与召回次数不在。

漏掉的恰恰是最难重建的部分：

- 结论是模型生成 + 人工编辑的结果，重新生成未必一致；
- 行动项带着状态、负责人、回链，重建成本高；
- 记忆带着来源与召回次数，丢了就退化成「来源未知」。

所以这次不是加一个导出按钮，而是把这三类数据纳入归档契约。

## 二、事件轨新增的三份负载

| 文件 | 内容 | manifest 计数 |
|---|---|---|
| `memories.json` | 长期记忆，含来源与召回次数 | `memoryCount` |
| `meetingConclusions.json` | 会议结论：摘要、决策、未决问题 | `meetingConclusionCount` |
| `meetingActionItems.json` | 行动项：状态、负责人、截止、回链 | `meetingActionItemCount` |

manifest 里的计数不是装饰：precheck 会用它与实际文件条目比对，数量对不上就提示归档可能损坏，而不是让用户恢复一半才发现缺数据。

三份文件都放在事件轨，而不是新开一条轨，是因为它们与「事件」共享同一套恢复顺序与事务边界：会议先恢复，结论与行动项才能找到外键；记忆没有外键，可以独立恢复。

## 三、旧归档：缺文件按 0，不报错

新版本必须能读旧归档。做法很简单：读取时如果文件不存在，返回空数组，计数按 0 处理。

```text
readArray(files.get('memories.json')) → 缺文件 → []
precheck: memoryCount 缺失 → 0
```

这条规则看起来平淡，却是兼容性的关键。如果缺文件就抛错，用户手里所有旧备份都会在新版本里变成「损坏归档」，这比少恢复几类数据糟糕得多。

反过来，新归档在旧版本里会被拒绝：旧版本看到更高的格式版本号，会提示先升级。这是有意的单向兼容——**新读旧可以降级，旧读新不能猜。**

## 四、恢复顺序：先会议，再结论与行动项

恢复顺序是硬约束：

```text
会议 → 会议结论 → 行动项
记忆（无外键，独立恢复）
```

结论与行动项都带 `meetingId`，恢复前会检查目标会议是否存在。会议不存在就跳过，不产生悬空结论——否则用户会看到一条没有上下文的总结，点进去什么都没有。

记忆的来源会话与来源消息则允许悬空。它们没有外键约束，恢复后如果来源已不存在，界面按「来源会话 / 消息已删除」降级展示，记忆本身仍然可用。这是有意的差异：结论离开会议没有意义，记忆离开来源仍然是一条事实。

## 五、幂等：INSERT OR IGNORE 而不是覆盖

所有恢复语句都使用 `INSERT OR IGNORE`：

- 目标库已有同 id 行 → 跳过，不覆盖；
- 目标库没有 → 插入；
- 单条校验失败或外键拒绝 → 跳过并计数。

这带来一个重要性质：**同一份归档恢复两次，结果一致。** 用户误点两次恢复、或者恢复中途失败后重试，都不会产生重复数据，也不会把本机较新的编辑覆盖掉。

恢复结果按类返回「导入 / 跳过」计数，而不是只给一个总数。用户需要知道是「全部已存在所以跳过」还是「格式不对被丢弃」，这两种情况的处理方式完全不同。

## 六、记忆恢复保留什么，不保留什么

保留：

- 记忆 id、类别、内容、重要性、状态；
- 来源会话 id、来源消息 id；
- `recallCount` 与 `lastAccessedAt`；
- 创建与更新时间。

不保留：

- 向量。

向量不入档与知识库的口径一致：嵌入向量与具体嵌入模型绑定，换一个模型维度就变了，存进归档反而制造「看起来能召回、其实不可比」的假象。恢复后的语义召回需要重新嵌入，这是明确的已知代价。

界面不会假装向量还在：恢复后的记忆可以正常展示与管理，但在重新嵌入完成前，语义召回可能召回不到它。这个行为写进了发布说明，而不是留给用户猜。

## 七、为什么按轨合并，而不是整库覆盖

整库覆盖的实现更简单：删掉目标库，把归档整个倒进去。我们没这么做，原因有三个：

1. **用户可以只恢复一部分。** 备份按轨道选择，恢复也应尊重选择；整库覆盖会让「只恢复知识库」变成「清空其他所有数据」。
2. **本机数据可能更新。** 用户在两台机器之间迁移时，目标机可能有更新的会话或设置，整库覆盖会静默丢失它们。
3. **失败不可回滚。** 整库覆盖一旦中途失败，目标库处于半空状态；按轨合并 + 事务 + 幂等，最坏情况只是少导入几条。

代价是合并语义更复杂：需要处理 id 冲突、外键缺失、字段版本差异。但这些复杂度集中在恢复层，用户侧只看到「导入 / 跳过」两个数字，比一个不可解释的「恢复成功」更可信。

## 八、验证：四类用例

| 用例 | 验证点 |
|---|---|
| 往返 | 来源消息、召回次数、结论、行动项在导出再恢复后保留 |
| 旧档兼容 | 缺文件的旧归档按 0 降级，不报错 |
| 幂等 | 同一归档重复恢复，数据不重复、不覆盖 |
| 异常数据 | 悬空会议、非法记忆条目被跳过并计数 |

这四类用例比「导出文件能打开」重要得多。备份的价值不在导出成功，而在**恢复之后数据仍然说得清来路**。
