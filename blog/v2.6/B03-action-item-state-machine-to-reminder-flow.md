# 结论之后的执行层：行动项状态机、提醒与 Flow

一张会议结论写得再漂亮，只要没有「谁、在什么时候、做什么」，它就只是一段摘要。行动项是把结论变成动作的最小载体，但它一旦开始流转，就会牵扯状态、权限、时间与时区。

这篇讲我们如何给行动项设边界：哪些状态允许流转，什么条件下才能转成提醒或触发 Flow，以及为什么结论与执行必须是两层。

## 一、为什么把结论和执行拆开

如果让模型直接输出「已创建提醒」「已运行工作流」，会有三个问题：

- 模型没有权限判断助手是不是会议成员；
- 模型不知道提醒服务是否可用、Flow 是否已发布；
- 一旦执行到一半失败，无法区分「结论错了」还是「执行错了」。

所以我们把链路拆成两段：**结论只负责描述，执行只接受确定性指令。** 模型输出行动项文本与负责人候选，真正的提醒创建、Flow 运行由服务层在用户点击后执行。

这样失败模式也分开了：结论失败可以重试或手改，执行失败可以逐条审计、逐条重来。

## 二、行动项的字段

| 字段 | 含义 | 约束 |
|---|---|---|
| `content` | 行动项内容 | 必填，1–500 字符 |
| `ownerLabel` | 负责人显示名 | 可为空 |
| `ownerMemberId` | 负责人助手 id | 只能是本会议成员或 `null` |
| `dueAt` | 截止时间 | ISO 8601 或 `null` |
| `status` | 状态 | `open / done / cancelled` |
| `source` | 来源 | `generated / manual` |
| `linkedReminderId` | 已转提醒的回链 | 只写不覆盖 |
| `linkedFlowRunId` | 已运行 Flow 的回链 | 只写不覆盖 |

负责人只允许本会议成员，是为了避免「把任务派给一个不在场、也不了解上下文的人」。生成阶段的非法 owner id 会被自动降级为 `null`，而不是让整次生成失败；手工添加时则直接报错，因为那是用户主动输入。

## 三、状态机：只允许四种流转

```text
open ──→ done
open ──→ cancelled
done ──→ open
cancelled ──→ open
其余组合一律 409
```

对应的约束：

- 不提供物理删除，取消用 `status=cancelled`，保留会议审计；
- 已完成可以回退到 `open`，允许「以为做完了、其实没做」的修正；
- 已取消可以回到 `open`，允许误取消后恢复；
- 任何跨状态跳跃（例如 `done → cancelled`）都拒绝。

状态机写在服务层，不写在 UI。UI 只根据当前状态决定显示哪些按钮，但真正的合法性判断在服务端，避免有人绕过界面直接调 API。

## 四、转提醒：三个前置条件

行动项转提醒不是「点一下就行」，它要求：

1. 会议已结束；
2. 行动项有 `dueAt`；
3. 出声助手必须是本会议成员。

任一不满足返回 422，重复转换返回 409。这三个条件分别对应三类错误：会议没结束就派活、没有截止时间就提醒、派给一个不在会议里的助手。

时间换算也在这里发生：把 `dueAt` 按请求时区换算成墙钟的年月日与时分，当前只支持 `Asia/Shanghai`。仅日期不满足条件，必须选择具体时间——「明天提醒」在提醒系统里不是一个可执行的时间点。

提醒文本取行动项内容，超过 200 字截断，避免一次性提醒被塞进一整段会议记录。创建成功后写 `linkedReminderId`，重复点击会被回链检查挡住。

## 五、运行 Flow：只认已发布版本

行动项也可以变成一次工作流运行，但只接受**已发布**的 Flow：

| 检查 | 不满足时 |
|---|---|
| 会议已结束 | 409 |
| Flow 存在 | 404 |
| Flow 状态为已发布 | 422 |
| 该行动项未运行过 | 409 |

未显式传输入时，行动项内容会同时映射到四个常见输入键：

```text
{ actionItem: content, query: content, topic: content, question: content }
```

这是一种「宽匹配」：不同 Flow 对输入键的命名不一致，同时提供四个键，让大多数 Flow 直接可用，而不要求用户在会议里手动填参数。需要精细控制时，仍可显式传 `input`。

运行以 `trigger=manual` 创建，入队后立即写 `linkedFlowRunId`。回链只写对应列，提醒回链与 Flow 回链互不覆盖。这样一条行动项可以清楚地回答：它被执行过几次、分别落在哪个提醒或哪次运行上。

## 六、导出 Markdown：给外部看的那一份

会议可以导出为 Markdown，内容包含：

- 议题、状态、创建时间、参会成员；
- 完整转录，按发言人与顺序排列；
- 结论：摘要、决策、未决问题；
- 行动项：勾选状态（`[ ] / [x] / [-]`）、负责人、截止时间；
- 人工编辑标记（存在 `edited_at` 时）。

明确不包含：

- 任何密钥、供应商配置、内部提示词；
- 模型调用参数与内部 id 之外的调试信息；
- 备份中的原始 JSON 结构。

导出的文件名由后端 `content-disposition` 决定，前端不自己拼。这样 zh / en 两种标签切换时，文件名与内容保持一致，不会出现「中文标题、英文正文」的错位。

## 七、审计与可回退

执行层的每个动作都留下回链，而不是只留一个布尔值「已处理」。这带来三个能力：

- 提醒或 Flow 出问题时，可以沿着回链找到对应运行；
- 取消行动项不会删除历史，会议审计仍然完整；
- 备份恢复后，回链 id 原样保留，虽然目标可能已不存在，但界面能给出可读提示。

这也是为什么行动项没有「删除」：会议是一次性事件，行动项是它的证据链。证据可以被标记无效，但不应该消失。

## 八、边界总结

- 行动项只在会议域，不创建通用待办，也不派发桌面 Agent 任务；
- 转提醒要求截止时间与成员身份，不做「猜一个时间」的兜底；
- 运行 Flow 只认已发布版本，避免拿草稿做真实副作用；
- 导出是只读快照，不触发任何执行。

结论回答「我们决定了什么」，行动项回答「接下来谁做什么」。两层分开，才能让前者可编辑、后者可审计。
