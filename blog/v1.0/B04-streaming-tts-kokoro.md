# 流式语音合成实战：让回复一边生成一边被念出来

这是本系列最核心的一篇。

「会说话」最难的不是把文字合成成音频——本地引擎一行调用就能出声——难的是**让朗读跟上一条还在流式生成的回复**：首句要在全文写完之前就响起来；某一句合成失败不能卡住整条回答；用户开口打断时，在途合成、排队音频、上游大模型调用要一起作废。

这一篇讲四块：语音旁路的结构、切句与播放队列、单句降级、引擎从 MeloTTS 换到 Kokoro 的选型实战，以及那个逼我们放弃 int8 的真机性能坑。

## 最关键的决定：语音是旁路，不是接管

最直觉的做法是让语音进对话主流程：文本增量先合成，再带着音频推给前端。第一版就被否了，因为它焊死了两个耦合：TTS 一坏文字对话就坏；关掉语音开关后主流程仍经过语音代码，「纯文字零回归」只能靠测试保证——而测试保证不了你没想到的分支。

最终结构是**旁路**。对话文本在原来的写入点**先放行**进对话流，上屏永远不受语音影响；同一写入点再把增量差分喂给语音旁路：

```text
orchestrator 文本增量 delta
   ├──► 主路：照常写入对话流（上屏、落库、复制分享，与上个版本完全一致）
   └──► 语音旁路（仅语音开关开启时才创建）
         增量差分 → 流式切句器 → 文本清洗（剥表情标签等）
                   → 逐句送 TTS → SSE 推 voice_audio / voice_state 帧
```

「仅语音开关开启时才创建」是字面意义：语音关闭（默认）时，代码路径上连语音会话对象都不存在。**纯文字路径零语音事件是结构性质，不是回归测试堆出来的性质。**

## 切句器：半标点快出首句

大模型逐字吐，合成却必须以句为单位。切句器是个有状态纯对象：吃增量文本，吐出已闭合的句子，半截留缓冲。关键优化是**半标点快出**——只认句号，首句可能要等一大段写完才出声；于是逗号、分号在「缓冲已足够长」时也允许先切：

```ts
push(delta: string) {
  this.buf += delta;
  const out = [];
  while (true) {
    const hard = findIndex(this.buf, '。！？.!?');
    const soft = findIndex(this.buf, '，、；,;');
    if (hard >= 0) { out.push(this.cut(hard)); continue; }       // 句末标点：切
    if (soft >= 0 && this.buf.length >= SOFT_LIMIT) { out.push(this.cut(soft)); continue; }
    break;                                                       // 半截留着等下次增量
  }
  return out;
}
```

代价是句子略碎，收益是首句延迟从「等第一段」降到「等第一个语气停顿」。切句器还负责 TTS 文本清洗：表情标签、Markdown 符号在合成前剥离，念的内容与上屏文本共用 shared 包的同一套规则。

## SSE 两种帧与播放队列三语义

旁路只发两种新事件，挂在既有 SSE（服务器单向推送文本事件的 HTTP 流式协议）通道上：

```text
voice_state { state: 'thinking' | 'speaking' | 'idle' }
voice_audio { fragment, spoken, audio: string|null, sampleRate, final }
```

`voice_state` 驱动 Live2D 状态与界面徽标；`audio` 是 base64 WAV 帧，`spoken` 供字幕；`audio=null` 是合法形态——纯表情、清洗后为空的片段只驱动字幕和形象，不出声；`final` 表示全文切完。

播放必须严格串行且可打断，队列只有三个原语：

```ts
enqueue(frame)  // 串行：上一句播完才播下一句
cancel()        // 作废一切：清队列、停当前声音
finalize()      // 不再有新帧：存量播完即收尾
```

逐帧 decode 成 AudioBuffer 顺序播放，播放时经 AnalyserNode 取音量 RMS 喂口型。cancel 用于停止朗读、切会话、开口打断；finalize 防止队列傻等超时。首句在第一句闭合时就独立推来，**用户听到第一句话时，模型往往还在写后半段**——这是「流式朗读」体感成立的根本。

## 单句失败：只降级这一句

合成会失败：引擎初始化失败、某句文本异常。旁路对每句单独 try/catch：

```ts
for await (const sentence of splitter.push(delta)) {
  let audio = null;
  try { audio = await tts.synthesize(stripForTts(sentence), sid); }
  catch { audio = null; }                 // 这一句退化为纯字幕
  emit('voice_audio', { spoken: sentence, audio, /* …… */ });
}
```

这一句发字幕帧：看得到文字、形象状态照常，后面的句子继续合成。失败被严格限制在一个句子的粒度内，文本流不断、不弹错误。

## 引擎选型：MeloTTS 到 Kokoro

先上线的是 **MeloTTS 中英双语**：17 个文件约 191MB，只有一个女声，44.1kHz，真机稳态约 **1.1s 合成一句**（约 1.4 倍实时）。有它先把旁路、切句、播放、打断整条链路跑通，之后引擎换成 **Kokoro 多说话人版本**：

- **103 个说话人音色**，24kHz，中英双语，fp32，377 个文件共 **394MB**；
- 真机加载约 1.7s，4 线程合成约 1 倍实时；
- 每个角色可以绑定固定声线，助手终于「有自己的声音」。

换代时接口一行没动——ASR/TTS 抽象在 M0 就定好了，换引擎只是换实现类，这是先做接口骨架后填引擎的回报。

## 引擎四件套：缺一个都不出声

Kokoro 运行时同时依赖四样东西，缺任何一样都不是干脆报错，而是静默异常或空输出：

1. **voices.bin**（约 54MB）：103 个说话人的音色数据；
2. **espeak-ng 数据目录**：355 个小文件的音素数据，路径必须显式配置；
3. **中英双词典**（约 14.4MB）：中文、英文各一份，少一份对应语种就念错；
4. **规则 FST**：日期、数字、电话等读法的有限态转换规则。

另有一个易忽略的参数：**`maxNumSentences` 必须设为 1**。设成 2 不会坏，但每次合成都刷一条原生警告，日志被污染且难排查。这些约束全部固化成引擎构造时的必填检查，而不是写在文档里靠人记。开发态还有一坑：voice 包在 Next 里以 external 方式消费的是构建产物，改完清单必须重建 voice 包再重启开发服务器，否则不生效。

## 为什么 TTS 不敢用 int8：一个指令集的实测课

量化是否真提速，取决于 CPU 有没有对应的整数指令。Node 版 onnxruntime 在我们的真机 CPU（不支持 AVX512-VNNI）上，两个内核表现分裂：

| | int8 | fp32 |
|---|---|---|
| ASR 内核 | 不受影响，热态 256ms（上一篇数据） | — |
| TTS 内核 | **退化到约 0.25 倍实时，不可用** | **约 1.5 倍实时，可用** |

没有 VNNI 整数指令加持，int8 TTS 算子退化成低效模拟，fp32 反而吃满浮点单元。结论很硬：**TTS 选 fp32，体积涨到 394MB 是真机数据逼出来的，不是模型洁癖**。线程数同样以实测为准：**4 线程最优，8 线程反而更慢**——超出物理收益后线程切换与内存带宽成了瓶颈，默认锁 4。「量化一定更快、线程越多越快」两个直觉，真机上各被打脸一次。

## 角色绑定声线：映射沉到 shared，sid 三级解析

103 个音色不能让用户面对一个数字下拉框。设计是「换角色即换声」：5 套官方样本角色各自绑定默认音色（含两个男声），映射表沉到 **shared 包 schema 里作为唯一真源**，web 端、服务端、桌宠读到同一份。音色 id 解析顺序固定三级：

```ts
const sid =
  request.voiceSid        // ① 请求显式指定（试听等场景），最高优先
  ?? avatarVoice(roleId)  // ② 角色绑定的默认音色
  ?? 3;                   // ③ 兜底音色（schema 上限 102）
```

UI 上没有独立的「选声音」入口，只在形象设置里提供「绑定声线 + 试听」。同文本波形取证也确认了路由正确：自动 sid 与显式 sid 的波形平均差异仅 0.006（同一声线），与不同音色之间为 0.062，数量级分明。

## 预告

旁路保证文字永远先活着，切句器让首句不等全文，三语义队列管住播放，单句降级兜住失败，fp32 与 4 线程是真机量出来的答案——会说的故事完整了，但还得用手按按钮。下一篇解决最后一块：不做唤醒词、不做回声消除，如何用一个纯能量状态机实现免手聆听，以及开口打断时 epoch 作废与 abort 如何一路透传到大模型。
