# 五个角色与一条授权红线：多形象注册表里的参数命名、空动作组与防漂移测试

单形象立住之后，多角色几乎是被用户推着做的：有人想要安静的少女，有人想要少年，还有人直言「我就想养只狗」。但多形象这件事的第一道坎不是技术，是授权——角色模型不是我们画的，能用谁、能怎么用，边界在写代码之前就已经定死了。

这一篇讲 v1.0 的五套官方角色怎么进注册表，以及三张模型描述文件照抄会踩的坑：三种口型参数命名、一个空的 LipSync 组、六个表情如何演八种情绪。

## 授权红线即产品边界

Live2D 官方 Web 样本自带了一批免费原创角色，授权条款随样本分发——我们最终选用的正是其中五套：**Haru、Hiyori、Mark、Mao、Wanko**（一位接待员、两位少年少女、一位魔法少女，还有一只柴犬）。每套角色目录里都带着模型描述、网格、贴图、动作、表情和许可证文件，整套自包含，体积从 **0.66MB 到 4.70MB** 不等，作为静态资源随 Web 端分发，桌面打包时由打包归集脚本一并拷入。

真正要想清楚的是「不做什么」：**v1.0 明确不支持外部模型导入，不做模型市场。**

这不是能力问题，是授权定性问题。免费样本的授权覆盖的是「把这些角色作为应用固定内容分发」；一旦应用开放了用户自行导入任意 Live2D 模型的入口，产品在授权意义上就从「内容应用」变成了「可扩展性应用程序」，触发的是另一档付费授权要求。一个本地优先、不想给用户增加任何强制费用的应用，不该让用户为一个导入功能背上合规成本。所以五套角色既是全部选择，也是产品边界本身——About 面板逐角色署名致谢。

## 一张注册表，五个白名单元素

所有角色差异收进一张注册表，字段刻意保持扁平：

```ts
interface AvatarModelSpec {
  id: string;                 // haru / hiyori / mark / mao / wanko
  label: string;              // 选择器展示名
  url: string;                // 模型描述文件 model3.json 的 URL
  expressions: Partial<Record<ExpressionTag, string>>; // 8 标签 → 模型内表情名
  idleGroup: string;          // 待机动作组名
  tapGroup: string;           // 点击动作组名（无专用组时回落待机组）
  lipParam: string;           // 口型参数名（各模型不一致，后面详述）
  license: string;            // 许可证说明
}
```

配套一条五元素白名单。服务端收到的形象 id 一律先过白名单，**任何未知 id（包括旧版本残留值、手改存储的脏值）都回落默认角色 Haru**，不报错、不白屏。选择器的渲染顺序也由注册表数组决定，UI 不写死任何角色知识。

## 三种口型参数命名，与一个空的 LipSync 组

张嘴参数是口型同步的落点，我们本以为模型描述文件里有统一的 LipSync 动作组，照读即可。现实是五套样本存在**三种命名风格**：

```text
ParamMouthOpenY      → Haru / Hiyori / Mark（驼峰）
ParamA               → Mao（日语五元音体系，「あ」即张嘴）
PARAM_MOUTH_OPEN_Y   → Wanko（大写下划线）
```

这还算客气的，真正的坑在 Mark 身上：他的模型描述文件里 LipSync 组是一个**空数组**。如果照抄描述文件，结论会是「这角色没有口型参数」，然后狗都在张嘴了，少年面无表情。我们没有相信描述文件，而是打开模型的参数声明文件（cdi3.json）逐个核实——`ParamMouthOpenY` 这个参数在 Mark 的参数表里真实存在，只是 LipSync 组漏配了。最终注册表硬编码核实结果，并在注释里写明「描述文件此处为空，以参数声明为准」，防止后来人「修正」回错误值。

Mao 的 `ParamA` 是另一类差异：它绑定的是五元音口型体系而非单一张嘴度，驱动时把整体电平写给「あ」这一个参数，口型观感同样成立——但前提是参数名不能想当然。

## 六个表情，怎么演八种情绪

上一篇的 8 个语义标签是跨层契约，而模型侧的表情资源并不整齐：

- **Haru** 有 8 个表情，f00–f07 与官方序号的语义还不完全对应（笑眼、瞪眼、焦虑混在序号里），最终映射是真机逐个表情比对出来的，不是看名字猜的；
- **Mao** 也有 8 个，`exp_01`–`exp_08`，但没有真正的「惊讶」，surprise 回落笑眼，嫌弃回落生气嘴型，得意对应挑眉的 07；
- **Hiyori / Mark / Wanko 只有 6 个语义词表情**（Normal / Smile / Blushing / Sad / Wronged / Angry），缺的四个按近义回落：惊喜→Smile、嫌弃→Angry、不安→Wronged、坏笑→Blushing。

近义回落全部写在注册表里、逐行注释，不做隐藏的魔法映射。语义有损是事实——狗确实没有「坏笑」——但近义表情总好过标签到了脸上毫无反应。差异概览：

```text
Haru   8 表情 f00–f07（真机逐个比对，序号与语义不对应，smirk 回落严肃脸）
Mao    8 表情 exp_01–08（无真惊讶，surprise→笑眼 02，smirk→挑眉 07）
Hiyori 6 表情（surprise→Smile  disgust→Angry  fear→Wronged  smirk→Blushing）
Mark   6 表情（回落同 Hiyori）
Wanko  6 表情（回落同 Hiyori）
```

Mark 还有第二个「空」：他没有 TapBody 点击动作组，连点击命中区声明都是空的。处理方式同样是回落——点击组直接指向待机组，点他至少会动一下，而不是像坏了。

## 13 个直接读真实模型文件的测试

注册表这种东西，最怕的是「代码里写的名字和资源文件里的实际名字对不上」：贴图改名、动作组拼写差一个大小写、表情文件漏带，全都要到真机点一下才暴露。

防漂移测试的思路是**不 mock 任何模型文件**：13 个用例直接读 `public` 下每套角色的真实 model3.json，顺着文件引用去断言——

```text
每个注册的角色：
  ✓ 描述文件存在且可解析
  ✓ idleGroup / tapGroup 在动作组里真实存在
  ✓ 表情映射引用的每个表情名都在 Expressions 列表里
  ✓ 贴图、网格文件物理存在
  ✓ 许可证文件存在
```

测试数据从注册表本身生成，所以新增第六个角色时，测试一行不用改；而谁要是把 `ParamMouthOpenY` 拼成小写、或引用了一个被官方删掉的动作，单测立刻红。Mark 的空 LipSync 组之所以不会被「好心修回去」，也靠这类测试钉住实际参数。

## 选择器的一个 UI 小坑：受控组件别等远端回写

形象选择器本身还踩过一个前端时序坑：选项状态由远端存储驱动（发 PUT、等回包、再刷新状态），e2e 里连续操作时，测试框架的勾选可能在 React 提交渲染之前校验状态，偶发把选项又「点回去」。

根治方式是让受控控件持一份本地态：onChange 时先同步 `setState` 让界面立即响应，PUT 在后台发出，再由一个 effect 把服务端值回同步校准。本地态负责手感，effect 负责一致性，两笔账分开。这个模式后来复用到同面板的所有开关行。

## 切换即整体重建

切角色不是换贴图那么轻：模型实例、绑定、动作状态机都不同。实现上切换走一个以 modelId 为依赖的 effect——新模型整体构建，旧实例走完整 dispose（模型、Application、canvas、观察器一个不漏），杜绝双 WebGL 上下文和显存堆积。

e2e 则用抓包给切换行为上锁：在选择器里切到 Hiyori，断言**只请求 Hiyori 的资源，Haru 资源零请求**；刷新页面后选择仍是 Hiyori，设置已落库回读。选择器五个选项、刷新持久化、旧资源不重拉，一条链路走完。最后五套角色在系统 Chromium 上逐个真机渲染：角色实际绘制、描述文件/网格/贴图全部 200、控制台零错误，5/5 通过。

## 收尾

多形象这一篇没有炫技，全是与「外部内容」打交道时的笨功夫：授权边界先想清楚，描述文件不能全信，命名差异全部显式登记，测试直接读真实资源防漂移。下一篇，角色要走出网页右栏，站到桌面上——那是一个透明、置顶、平时还会从你鼠标下「穿过去」的小窗。
