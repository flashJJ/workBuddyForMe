# v1.0 复盘：八个把「能跑」打回原形的坑，与五条留下来的方法论

会听、会说、有形、伴身、还会主动开口——v1.0 是这个项目第一次做音频、图形渲染和桌面透明窗，踩坑密度自然是系列至今最高的一档。有意思的是，这些坑几乎没有一个是「算法太难」，全部出在开发体验与生产现实的缝隙里：dev 说没事、文档说应该、日志说能出声——但它们都不算数。

这一篇挑出传播价值最高的八组坑，每个按现象→根因→教训讲清楚，最后收口五条方法论。

## 一、dev 热更新照过，运行时整页崩溃

**现象**：设置页一改受控组件就白屏，错误边界兜成「页面出了点问题」，连带所有设置相关 e2e 全红。

**根因**：状态变量定义的是 `enabled`，JSX 里手误写成了 `checked={checked}`。Next dev 的 SWC 编译**不做类型检查**，热更新照常通过；直到浏览器运行时才抛 ReferenceError。

**教训**：dev 能跑不算绿。类型错误在这个技术栈里是运行时错误，受控组件的改动必须过 typecheck 或 e2e——这条后来直接变成了提交前肌肉记忆。

## 二、语音门控「看起来生效」，其实从未生效

**现象**：朗读开关、麦克风门控全部静默失效，设置存了也像没存。

**根因**：请求层的 `apiGet<T>` 已经把响应包络的 `data` 解包过一次，调用方又取了一遍 `.data`——拿到的恒为 `undefined`，所有门控读到默认 falsy 值。全仓统一为直接消费解包后的 T 才根治。

**教训**：双重解包不报错、只给默认值，是最隐蔽的那类 bug。包络解包只允许存在一层，谁解的写在类型签名里。

## 三、Live2D 的两个「不能信」

**现象与根因**：其一是 pixi 锁版（前文详述，一句话回顾）——绑定库 peer 是 v6，配 v7 产生双份 DisplayObject，交互刷 `isInteractive is not a function`，版本矩阵必须锁死。其二是多形象时照抄模型描述文件：某个角色的 LipSync 组在描述里是空数组，差点被判成「没有口型」，最后是打开参数声明文件逐个核实才发现张嘴参数真实存在。

**教训**：第三方样本的元数据不是契约，实际参数声明才是。注册表测试改成直接读真实模型文件，改名、拼写漂移、漏配全部当场红。

## 四、AudioWorkletNode 不连 destination，就不会被调度

**现象**：VAD 采集节点挂上后，`process()` 一次都不 tick，音频时钟完全不动。

**根因**：WebAudio 规范里，未连通到 destination 的节点不会被调度渲染——只连输入源不落地，节点就是死的。改成经过一个 **0 增益 GainNode 连到 destination**（声音不出，但图是通的）。顺带处理了 StrictMode 重挂导致的握手重复：握手消息只发存活链、取消检查前移。

**教训**：音频图是「有向图 + 可达性」问题，不是「挂上就行」。这种规范级行为，Spike 阶段就该验证。

## 五、e2e 连续两个 PUT，waitForResponse 串了台

**现象**：一条 e2e 里先勾选开关、再切形象下拉，两个 PUT 紧挨着发出，断言偶发失败。

**根因**：`waitForResponse` 夹在中间时，捕获到的是**前一个**开关 PUT 的响应，读出来的请求体自然没有目标形象 id。

**教训**：连续同端点请求不能靠「等下一个响应」匹配，必须用精确谓词——先消费掉开关 PUT，再用请求体谓词锁定目标：

```ts
// 伪代码：匹配「切形象」这一个 PUT，而不是「下一个 PUT」
await page.waitForResponse(
  async (r) =>
    r.request().method() === 'PUT' &&
    (await r.request().postDataJSON())?.avatarModelId === 'hiyori',
);
```

匹配条件描述的是「这个请求本身长什么样」，而不是「它排第几」——顺序假设在异步系统里一律不可靠。

## 六、int8 内核在这颗 CPU 上退化到 0.25x 实时

**现象**：TTS「能出声」，但速度完全不够，按句流式朗读根本跟不上。

**根因**：本机 CPU 没有 int8 内核依赖的那代向量指令集，onnxruntime 静默退化到慢速实现——int8 只有 **0.25x 实时**，而 fp32 反而有 **1.5x**；另实测 8 线程比 4 线程更慢。最终 TTS 选 fp32、默认 4 线程，而 ASR 的 int8 不受影响（热态约 18x 实时），两个引擎分开决策。

**教训**：真机数据是选型的一部分，「量化更快」只是有前提的平均值。验收记录合成速率数字，不接受「能出声」。

## 七、改了源码却不生效：external 消费的是 dist

**现象**：改了本地 voice 包的模型清单，重启、重测全无变化，一度怀疑下载器坏了。

**根因**：voice 包在 Next 里以 **external 方式消费构建产物 dist**，不经过 Next 的编译——只改源码不重建，运行的还是旧 dist；且模型清单变更还要求重启 dev 才重新加载。另外还踩过「磁盘文件已就绪、数据库状态仍 missing」的分离问题，重跑一次下载接口（大小匹配即跳过）才复验通过。

**教训**：monorepo 里「我改了」不等于「运行的改了」。哪些包走源码、哪些走 dist，必须写进开发说明。

同一类「配置缺一不可」的坑还出现在 Kokoro 语音引擎上：说话人音色库、espeak 数据目录、中英双语词典、规则 FST 必须四件同时配齐，且单句合成数强制为 1（传 2 每句都刷原生警告）。这类「多文件本地引擎」没有合理默认值，缺一件的报错往往在很深处——把前置条件在初始化处一次性校验并给出可读提示，比让用户对着原生警告猜强得多。

## 八、主动轮的三个测试技巧陷阱

为主动功能写测试时连踩三个，全部属于「测试环境骗了你」：

1. **TS 把嵌套回调里赋值的外层变量窄化成 never**：spread 时报错，解法是用 holder 对象的属性中转，不直接闭包赋值裸变量；
2. **fake timer 下 `waitFor` 也被挂起**：轮询定时器被假时钟冻住导致超时，改用 `advanceTimersByTimeAsync` 推进，并手动冲洗微任务队列；
3. **ReadableStream abort 用例的时序**：必须让 fetch 先 resolve 出 Response、再在 abort 事件里让流 error；写成 fetch Promise 永不 resolve，用例必挂 5 秒超时。

**教训**：异步测试失败先怀疑测试环境的时间与顺序假设，再怀疑产品代码。

## 五条方法论

1. **结构性零回归比测试补更可靠。** 纯文字路径在代码结构上就不创建任何语音对象——不是「测了没有语音事件」，而是物理上无从创建。最好的零回归是让错误状态无法表达。

2. **真机数据是选型的一部分。** int8 还是 fp32、4 线程还是 8 线程，答案在具体 CPU 上，不在 benchmark 平均值里。选型决策必须附带真机测得的速率数字。

3. **主动功能的失败必须无声。** 用户没有发起的动作，就没有资格向用户报错。静默收起、冷却重试，是主动功能唯一体面的失败姿态。

4. **模型与重库都不该出现在首屏关键路径。** 564KB 的渲染重库独立 chunk、语音模型首用下载、形象关闭零请求——默认路径的轻量，要靠分层懒加载和抓包测试共同保证。

5. **dev 能跑不算绿，描述文件也不是契约。** 类型检查、e2e、直接读真实产物的防漂移测试，三道关卡补的都是「文档与运行时之间的谎言」。

v1.0 到此收口：一个全程本地推理、能听会说、有五张脸、能站上桌面、还会适时主动开口的桌面伙伴。下一个版本要还的债也很清楚——真人免手聆听标定、跨平台桌宠、打包态断网验收。功能会继续长，但这五条会留下来。
