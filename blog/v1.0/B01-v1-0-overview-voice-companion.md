# v1.0 总览：让工作台变成会说话的桌面伙伴

上个版本，我们的桌面 AI 应用已经能闭环对话、动手执行任务，还能把画出来的流程变成本机网络上的一个服务。但真正用久了，有三个别扭藏不住：**只能打字、没有形、不在桌面**。

回复再长也得盯着屏幕读完；助手是侧栏里的一串配置项，应用一最小化就「人走茶凉」；你手头正忙着操作键盘鼠标，根本腾不出手切回去敲一行字。

v1.0 要回答的就是这三件事：**全离线语音、有形象、伴身桌面**。语音全程跑在本机 sherpa-onnx 上，不引入任何云语音服务；回复按句流式朗读，你随时可以开口打断；Live2D 角色口型随声音张合、表情随回复切换；说完停顿即自动发送的半双工免手对话，让手可以留在工作上；外加透明置顶的桌宠，和空闲时的主动搭话。

## 能力断点与回答

| 上个版本的断点 | v1.0 的回答 |
|---|---|
| 只能打字，无法边干活边听 | 本地 Kokoro 多说话人 TTS 按句流式朗读，103 个音色按角色绑定，首句不等全文生成 |
| 全仓零音频输入 | SenseVoice 本地 ASR：热态 256ms 识别 4.6s 音频，约 18 倍实时，自带数字日期归一 |
| 说话必须按住按钮 | 浏览器端纯能量 VAD：停顿自动发、播放态回声门控、开口即打断，零新增模型 |
| 助手没有「在场」形象 | 懒加载 Live2D：5 套官方样本角色、RMS 口型、8 标签表情、待机与点击动作，另有透明置顶桌宠 |
| 助手只被动应答 | 空闲达阈值主动搭话一两句，走同一条语音通道，用户一有操作立即中止 |
| 云语音的隐私与费用顾虑 | 模型在本机推理，音频不出本机、不入库；模型首用下载，不进安装包 |

## 先把不做的边界划清楚

做语音最容易失控的地方是范围，所以边界在动手前就写死了：

- **半双工**：不做免耳机场景的回声消除（AEC）、不做唤醒词、不做连续流式 ASR。听和说不同时进行，但可以「停止/开口即打断」；
- **形象只用内置官方样本**：5 套 Live2D 官方样本角色，不支持外部模型导入——这是授权红线，不是技术偷懒；
- **语音跑在服务进程**：识别和合成都在内置 Node 服务进程里，不碰桌面壳（Electron）的原生 ABI；
- **桌宠 Windows 先行**：透明置顶小窗这一版只做 Windows，其他平台顺延。

边界之外，体验反而更完整：不做唤醒词，就用能量 VAD 覆盖「手在忙、嘴来说」的 80% 场景；不做流式 ASR，就把整句识别做到 256ms 热态延迟，停顿即发，体感同样连贯。

## 全景一张图

```text
麦克风（web 端）                          扬声器
  │ 16k 单声道 PCM                          ▲ 音频帧串行队列
  ▼                                        │（音量 RMS → 口型）
POST 语音识别接口（multipart WAV）         SSE voice_audio 帧
  │ SenseVoice 本地（int8）                 ▲
  ▼                                        │
识别文本 → 既有对话编排（记忆/技能/工具/流程全部复用）
                 │ 文本增量 delta
                 ▼
           语音旁路：切句 → 清洗 → Kokoro（fp32 本地，角色绑定音色）
                 │
                 ▼ SSE voice_state：thinking → speaking → idle
          Live2D（主窗右栏 / 桌宠小窗）：表情同源、口型、待机动作
```

关键在于中间那行「既有对话编排」：语音不是另起炉灶的新通道，而是挂在原有对话流上的一个旁路。

## 五个最关键的架构决策

**① 语音跑在服务进程，不碰桌面壳 ABI。** 语音接口与既有路由同进程，生产态由内置的官方签名 Node 托管。sherpa-onnx 的 `.node`/DLL 以 external 方式保留、靠 standalone 文件追踪加打包脚本兜底归集进产物，因此不需要 electron-rebuild，从根上规避了 Electron ABI 不匹配这类老坑，web 端也零原生依赖。

**② 沿用 HTTP+SSE，不换 WebSocket。** SSE 是服务器单向推送文本事件的 HTTP 流式协议，上个版本的对话流本来就跑在它上面。这一版只新增 `voice_audio` / `voice_state` 两种事件，记忆、技能、工具调用、Flow 编排全部白得。语音开关默认关闭，关闭时代码路径上不创建任何语音对象——**纯文字路径的零回归是结构保证的，不是靠测试补出来的**。

**③ 模型不进安装包，首用下载，默认国内镜像。** ASR 228MB 加 TTS 394MB，塞进安装包既不现实也不该强迫断网用户买单。模型首用时下载进应用数据目录，带大小校验、可断点重来；Live2D 作为小体积静态资源随 public 分发，但重库保持独立懒加载 chunk——模型和重库都不在首屏关键路径上。

**④ 半双工加浏览器端纯能量 VAD，把复杂度挡在版本外。** 不做唤醒词/AEC/流式 ASR，用播放态回声门控加开口打断覆盖 80% 的免手场景。VAD 就是一个纯前端状态机：零新增模型、零网络请求，全部参数可单测。

**⑤ 表情标签成为跨层契约，而不是渲染细节。** 8 个表情标签在 shared 包定义，提示词注入、消息上屏、复制、分享、TTS 朗读文本共用同一套「解析 → 剥离」逻辑，多个形象只在注册表里做语义映射，从结构上杜绝标签泄漏到用户可见的文本里。

## 节奏：先定契约，再长器官

整个版本按里程碑推进，顺序刻意安排成「先把接口和最坏假设验证完，再填功能」：

| 里程碑 | 主题 | 关键出口 |
|---|---|---|
| M0 | 契约与 Spike | voice 包接口骨架（ASR/TTS 抽象、WAV 编解码、切句器、语音状态机、模型清单）、纯加法迁移；两个真机 Spike：引擎「合成→重采样→识别」闭环、透明置顶窗，先证伪再投入 |
| M1 | 会说 | TTS 引擎、模型下载器、语音旁路、播放队列，语音对话全闭环 |
| M2 | 能听 | 本地 ASR、录音链路、按住说话，真机中文进对话 |
| M3 / M3.5 | 有形 | Live2D 单形象，再到 5 套官方角色可选，口型与表情齐活 |
| M4 | 免手与伴身 | 能量 VAD、打断，透明置顶桌宠 |
| M4.5 | 声线换代 | MeloTTS 换 Kokoro，103 音色按角色绑定 |
| M5 | 主动搭话 | 空闲轻量轮、临时气泡、同一条语音通道 |

M0 的价值在事后看格外清楚：正因为 ASR/TTS 抽象、SSE 事件、播放队列语义在写任何引擎之前就定了，M4.5 整体换掉 TTS 引擎时，上层链路一行没动。

## 数字

- ASR：SenseVoice int8，2 个文件共 **228MB**；冷启 3.2s，热态 **256ms 识别 4.6s 音频（约 18 倍实时）**；
- TTS：Kokoro 多说话人 fp32，377 个文件约 **394MB**，**103 个音色**，24kHz、中英双语，加载约 1.7s；
- 形象：pixi/Cubism 重库约 564KB 原始 / **157KB gzip 独立 chunk**，形象关闭时对话首屏对形象资源零请求；
- 新增运行时语音云服务：**0 个**。音频不出本机、不入库，服务只绑回环地址；
- 数据库 2 个纯加法迁移，老版本的真实库直接启动升级。

## 这个系列

接下来的四篇按链路顺序展开：

1. **模型分发与打包**：600MB 模型如何不进安装包、首用下载怎样防半截文件，原生 `.node` 绑定怎么归集且不用 electron-rebuild；
2. **本地语音识别**：从麦克风采集、降采样、WAV 封装到 256ms 热态识别的完整录音链路，以及为什么 ASR 敢用 int8 量化；
3. **流式语音合成**（本系列最核心一篇）：语音旁路、按句切分、串行播放队列、MeloTTS 到 Kokoro 的换代实战，和 TTS 为什么反而不敢用 int8；
4. **免手聆听与打断**：纯能量 VAD 状态机的全部参数、半双工回声门控、开口打断时 epoch 作废与 abort 全链路透传。
