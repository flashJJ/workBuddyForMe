# 给助手一张脸：Live2D 渲染、564KB 懒加载链与八个表情标签的跨层契约

语音解决了「会说」，但光有声还不够——你听到一个没有画面的声音，和看到一个会张嘴、会笑、会在你沉默时自己发呆的角色，是两种完全不同的关系。v1.0 的第三块，是让我们的桌面 AI 应用第一次「有形」：对话页右栏立着一个 Live2D 角色，嘴型随朗读张合，表情随回复内容切换，没人理她的时候她会自己做小动作。

这一篇讲单形象的渲染机制：一次锁版事故、一条把重库挡在首屏之外的懒加载链、舞台上的口型与动作调度，以及一个看起来像渲染细节、最后却做成跨层契约的东西——表情标签。

## 锁版事故：pixi v7 里的双份 DisplayObject

Live2D 在 Web 上的组合是固定的三件套：pixi.js 做渲染层，pixi-live2d-display 做模型绑定，Cubism Core 负责读模型参数。我们按「装最新」的直觉先拉了 pixi v7，然后交互就开始报一个非常怪的错：

```text
pointermove 处理中：
  obj.isInteractive is not a function
```

模型能加载、能渲染、静止画面一切正常，唯独鼠标一碰就崩。排查到最后，根因在 peer dependency 上：pixi-live2d-display 0.4 的 peer 声明的是 **pixi v6**。在 v7 环境里，绑定库内部 `instanceof DisplayObject` 拿到的是它自己 node_modules 里那份 v6 类，而页面上真实运行的显示对象是 v7 类——两套 DisplayObject 构造函数同时存在于内存，原型对不上，v7 实例上自然找不到绑定库预期的方法。这不是用法错误，是版本矩阵不成立。

结论没有商量余地，直接锁死：

```text
pixi.js                  6.5.10
pixi-live2d-display       0.4.0
Cubism Core               5.1
```

锁版写进依赖清单不算完，我们在 README 和依赖注释里都记了一句「升级 pixi 大版本前必须先验证绑定库」——这种坑第二次踩是不可接受的。

## 懒加载链：2KB 的控制器，564KB 的重库

第二个硬约束来自首屏。pixi + 绑定库 + Cubism Core 加起来约 **564KB 原始 / 157KB gzip**，而形象功能默认是关着的——让一个没开形象的用户为半兆重库买单，没有道理。

最终的加载链分三级：

```ts
// 1) Cubism Core 是普通脚本文件（非 npm 模块），注入必须幂等：
//    热更新/ StrictMode 双挂时不能重复插 <script>
function ensureCoreScript(): Promise<void> {
  if (window.__cubismCoreReady) return ready;
  const s = document.createElement('script');
  s.src = '/live2d/cubismcore.min.js';
  // ...append 一次，所有调用方等同一个 promise
}

// 2) 舞台组件 next/dynamic 加载，服务端零渲染，命名 chunk 便于抓包审计
const Live2dStage = dynamic(() => import(/* webpackChunkName: "live2d-renderer" */ './live2d-stage'), {
  ssr: false,
});
```

拆包结果是刻意的：页面侧的控制器只有 **2.3KB**，负责开关、props 转发和生命周期；pixi、绑定库、Cubism Core 全部沉到 `live2d-renderer` 这个独立 chunk，只有舞台真正挂载时才下载。模型资源又是更下一层，连 chunk 都不进，作为静态资源按需请求。

「形象关闭时首屏零请求」不是口头保证，而是一条 e2e：默认配置打开对话页，拦截全部网络请求断言其中**没有任何** live2d / cubismcore / pixi / 模型资源的请求。后来这条测试还顺手挡住过一次「顶层 import 重库」的回归——代码审查没看出来的，抓包一眼就红。

## 舞台：脚底对齐、RMS 口型与说话静默窗

舞台组件本身不复杂，但每一项都是真机上反复调过的：

- **等比、脚底对齐**。角色不是居中铺满容器的贴图。ResizeObserver 监听容器尺寸，按模型原始比例缩放，并让锚点定在底部中央——窗口怎么变，角色始终「站」在同一地面线上，不会飘。
- **口型每帧喂**。播放链路的 AnalyserNode 持续输出音频电平（RMS），渲染层用 requestAnimationFrame 每帧读一次最新电平，写进模型的张嘴参数。值做了平滑，停句立即归零——嘴比声音慢半拍是最出戏的。
- **待机动作要挑时机**。待机动作随机播放，但有一个「说话静默窗」：正在朗读、以及朗读结束后的短时间内不插待机动作，否则会出现「嘴上在说严肃的事，身体突然开始挥手」的撕裂感。
- **点击有回应**。点角色播一组点击动作；组件卸载走完整 dispose——销毁模型、销毁 PIXI Application、摘掉 canvas、移除观察器，切会话和关开关都不留 WebGL 上下文。

舞台同时订阅语音状态机的四态（idle / listening / thinking / speaking）：听的时候角色保持专注，思考时不出嘴型，进入 speaking 才由电平接管。状态来源是单一的语音状态机，舞台只负责把状态翻译成表现，不自己推断「现在该不该说话」。

形象栏只在 lg 断点（1024px 以上）出现，小屏直接让位给对话本身。About 面板里放了 Live2D、pixi 与官方样本角色的许可声明，用的是 Live2D 官方 Web 样本自带的 Sample Content License——致谢与许可和功能一起交付，是这类内容的本分。

## 八个表情标签：跨层契约，而不是渲染细节

真正值得展开的是表情。最朴素的做法是渲染层自己猜心情，但我们反了过来：让模型在回复里插结构化标签，例如：

```text
[joy] 太好了，这个版本终于能跑通了！[surprise] 等等，你刚才说测试也全绿了？
```

规范定义了 **8 个语义标签**：`neutral`、`joy`、`sadness`、`anger`、`fear`、`surprise`、`disgust`、`smirk`。模型对提示词的遵循并不稳定，会写 happy、会写 angry、甚至会写 smiling，所以解析器先做**近义词归一**——一张别名表把这些口语化写法收敛到规范标签，不认识的词一律不当表情。

流式场景还有半个标签的问题：`[joy` 已经到了、`]` 还在路上。剥离逻辑专门处理「流末尾是已知标签前缀」的情况，把这半个也先藏掉，避免用户屏幕上先闪现一帧 `[joy` 的乱码。

关键决策是：**标签规范和剥离逻辑只有一份，沉在 shared 包里，客户端服务端同源**。因为同一份带标签的文本，要过至少四道消费口：

```text
提示词注入      → 告诉模型标签规范，由开关控制是否启用
消息上屏        → strip 后渲染，标签不可见
复制 / 分享导出 → strip 后再导出，HTML 和 Markdown 都不能漏
TTS 朗读文本     → 去括号净化后再送语音合成，标签不出声
```

四处只要有一处忘了剥，`[surprise]` 这种字串就会泄漏到用户能看见或听见的地方。「四处各写一份正则」必然漂移，单一真源从结构上消灭了这个问题。表情开关还对应一次纯加列的数据库迁移，关掉后提示词不再注入标签，角色回到中性脸——功能是可退出的。

## 收尾

形象这块的方法论和语音一脉相承：重库不进首屏关键路径、默认关闭零负担、零回归靠抓包测试而不是靠自觉。单形象立住之后，下一个问题立刻来了——只给一个角色是不够的，而一旦想支持多角色，授权红线、三套口型参数命名、空动作组这些现实问题会一起涌上来。那是下一篇的故事。
