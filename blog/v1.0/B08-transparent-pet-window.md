# 让角色走上桌面：透明置顶窗、180ms 穿透滞回与一个吞事件的拖拽区

形象住进对话页右栏之后，有个遗憾始终在：她被关在网页里。你切到别的窗口干活，她就消失了——而「伙伴」这个词的含义，恰恰是人在忙别的时候，她还在桌面角落待着。

v1.0 的桌宠伴身窗做的就是这件事：一个透明、无边框、永远置顶的 Electron 小窗，角色站在桌面上；你不找她时，鼠标会直接从她身上穿过去点到下层窗口，像她不存在一样。这一篇讲这个小窗怎么做到「看得见、点得穿、拖得动、还不出声抢戏」。

## Spike 先行：先证明透明窗在真机成立

动手写功能之前，我们先写了一个几十行的冒烟脚本，只验证一件事：这套窗口参数在目标系统上真机成立。

```js
new BrowserWindow({
  width: 240, height: 240,
  transparent: true,       // 透明背景
  frame: false,            // 无标题栏无边框
  alwaysOnTop: true,       // 置顶
  skipTaskbar: true,       // 不占任务栏
  // setIgnoreMouseEvents(true, { forward: true }) 往返
});
```

透明窗在不同系统、不同合成器上的表现差异很大，置顶层级、穿透后能否继续收到鼠标移动事件，都是文档写不清、真机才知道的事。Spike 过了，才批准正式排期——正式窗口尺寸定为紧贴角色的 260×340（DIP）。这个版本桌宠只做 Windows，macOS/Linux 的适配明确推到后面，透明窗的平台差异正是原因之一。

## 穿透滞回：平时是空气，悬停 180ms 才是实体

核心矛盾是：一个置顶窗口如果老老实实接收点击，角色周围的透明区域就会挡住下层操作，全屏都是「死区」；如果全程穿透，你又永远点不到她。

解法是 Electron 的 `setIgnoreMouseEvents(true, { forward: true })`：穿透态下点击落到下层应用，但窗口**仍然能收到鼠标移动事件**。于是页面里放一个与角色身体重合的矩形命中盒——约窗口宽的 70%、高的 85%，底对齐，尺寸常量集中配置留着真机微调（不做逐像素 alpha 读取，那会同步阻塞渲染管线），配合一个带滞回的小状态机：

```text
鼠标进入命中盒
  → 立刻取消「离开计时」，报告 hovering=true
  → 主进程切 setIgnoreMouseEvents(false)：角色变可点
鼠标离开命中盒
  → 不立即穿透，启动 180ms 计时
  → 180ms 内鼠标又回来（边缘抖动）→ 取消计时，保持可交互
  → 180ms 到 → 切回穿透
```

180ms 这个滞回是整个体验的关键：没有它，鼠标在角色边缘快速划动会让窗口在穿透/可交互之间疯狂翻转，下层应用也跟着焦点错乱。控制器是一个注入了定时器的纯逻辑类，start/update/force/dispose 四个入口，配 **8 个单测**把进入、离开、抖动手势、强制切换全部钉死，主进程只负责把状态翻译成 `setIgnoreMouseEvents` 调用。

## 一个真坑：拖拽区会吞掉所有指针事件

无边框窗的标准拖拽做法是给元素加 CSS：

```css
.hit-box { -webkit-app-region: drag; }
```

开发到右键菜单时撞上一个隐蔽事实：**app-region drag 区域会吞掉所有指针事件**。渲染层的 contextmenu、click 都不再按常规派发——拖拽系统在 Chromium 层面接管了输入。我们原计划在渲染层监听右键弹菜单，结果在拖拽区上怎么都收不到。

规避方式是把右键菜单整条搬到主进程：Electron 的 webContents 自带 `contextmenu` 事件，由它直接 `Menu.popup()`。穿透态下右键根本进不来，天然不需要自己做命中判断；菜单三项——回主窗、切换鼠标穿透（勾选态回写偏好）、隐藏桌宠。拖拽继续交给 app-region，两条链路互不干扰。双击回主窗则在命中盒上监听 `dblclick`，调桥显示并聚焦主窗。

## 瘦终端：小窗只收表现，不碰对话与音频

桌宠最容易做重的地方是语音：让小窗自己订阅对话流、自己建 AudioContext 播放？我们明确否决了。那会产生第二个对话订阅者——双份语音合成、双份轮次状态，竞态不可接受。

定案是**瘦终端**：主窗保持唯一的对话会话和唯一的音频管线，桌宠只通过白名单 IPC 收「表现事件」：

```text
level       音频电平 0~1，播放期约 30Hz（一个浮点数，不是音频帧）
state       idle / listening / thinking / speaking
subtitle    切句并剥掉表情标签后的字幕，限长
expression  8 个表情标签之一
```

注意中继的是电平数值，不是音频数据本身——没有大体积音频帧走 IPC。桌宠页无麦克风、无 AudioContext、不发任何聊天请求；preload 暴露的桥不含任何文件系统或壳能力，频道名统一白名单前缀。裸浏览器直接访问桌宠路由会因为检测不到桥而回落跳走，不初始化任何东西。

口型和表情也因此零成本复用：桌宠挂的就是主窗同一个 Live2D 舞台组件，props 还是模型 id、表情、电平、说话态，五套角色切换一行不用改。为避免两个 WebGL 上下文双倍显存，桌宠打开期间主窗形象栏卸载——但电平仍由主窗播放链路产出，与形象栏是否挂载无关。

## 主窗隐藏后，声音为什么不断

桌宠应用的标准语义是「关主窗 ≠ 退出」：桌宠活着时，主窗点关拦截为隐藏而非销毁，朗读继续；双击桌宠，主窗回来。

这里有个 Chromium 的坑：**不可见窗口的 requestAnimationFrame 和定时器会被节流甚至冻结**。如果电平靠 rAF 轮询，主窗一隐藏口型就僵了。我们的电平源从一开始就放在 WebAudio 图的音频处理回调上——它跟随音频渲染线程，只要在播放就持续触发，窗口可见与否无关。电平 30Hz 节流后经 IPC 发出，idle 时不发。

位置与穿透偏好写入独立的状态文件，加载时做损坏回落（文件坏了就用屏幕右下留白的默认位）；坐标统一 clamp 到最近显示器的工作区，处理多屏、125%/150% 缩放和「窗口拖到副屏后副屏被拔走」的情况——窗会自动回到主屏可见区域。小窗一律 `showInactive()` 显示，绝不抢走你正在用的应用的焦点。

「关闭主窗」的语义也跟着重定义：桌宠存活时，主窗的关闭被拦截为隐藏而非退出，应用真正退出只走菜单退出等显式路径；反过来，从右键菜单关闭桌宠时，如果主窗正处于隐藏态，会先把主窗显示出来——避免用户关了宠物后整个应用「找不到了」。

中继频率上也留了预算：idle 时不发任何电平，播放期 30Hz 的载荷只是单个浮点数，低端机实测 CPU 增量若超过 3% 就降到 20Hz——这是写在真机验收清单里的数字，不是拍脑袋的频率。字幕气泡带 listening/thinking/speaking 状态点，切会话时收到清空信号立即清字幕，避免上一轮的话残留在新会话上。

## 验收与边界

桌宠的交互逻辑由单测保证（穿透滞回 8 例，shared 与桌面壳侧共新增二十余例），窗口生命周期则进了打包态 e2e：IPC 开窗后窗口数变 2 且属性（透明/无边框/置顶/不占任务栏）正确、位置移动后关窗重开与状态文件一致、穿透 IPC 往返无错、关窗后窗口数干净回落——4 个用例全部在 pack:dir 产物里跑，而不是只在开发模式下绿。

边界同样写在明面上：v1.0 桌宠 Windows 先行；小窗里没有输入框和麦克风，对话仍在主窗发起；不做逐像素命中、不做多宠物、不做换装成长。透明窗这种离系统最近的功能，先把窄场景做扎实，比铺三个平台半成品强。

## 收尾

到这里，角色能听、会说、有形，还能站在桌面上了。但她仍然只在你说话之后回应——一个真正的伙伴，会不会在你忙到忘了她的时候，主动开口说一句话？这是 v1.0 最后一个功能，也是失败处理最如履薄冰的一个：主动搭话，任何一次打扰都是事故。
