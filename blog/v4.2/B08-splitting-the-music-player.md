# 拆开一个 345 行的音乐播放器：按副作用归属，而不是按行数

单文件行数门禁最容易催生一种坏拆分：把代码从第 150 行切开，塞进两个文件，行数达标，复杂度原样保留。

全局音乐播放器撞到 300 行上限时，我们没这么干。它从 345 行降到 292 行，只搬走了两类副作用，UI 与播放控制仍留在原处。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手。音乐播放器同时承担了播放、偏好持久化、舞台恢复、静音接入四件事，行数只是这些职责的表症。

## 一、先列出它到底在做什么

拆之前把职责写在纸上：

1. 持有 `HTMLAudioElement`，处理播放、暂停、切歌、循环模式。
2. 注册为音乐 sink，把本地音量乘上导演系数。
3. 背景互斥时暂停，恢复时按播放意图重试。
4. 首次手势后重试被拦截的播放。
5. 读写音量、循环模式、当前曲目到本地存储。
6. 读写“是否在播”到会话存储，用于舞台往返。
7. 刷新曲库、渲染列表与迷你播放器。

前六项里，三、四属于音频会话副作用，五、六属于持久化副作用，一、七是播放器本体。

## 二、为什么按副作用拆，而不是按行数

按行数切，会得到两个互相依赖的片段：一边读状态，一边改状态，谁都离不开谁。

按副作用归属拆，边界是“谁拥有外部世界”：

- 与导演、`HTMLAudioElement` 的交互归一个 hook。
- 与 `localStorage`、`sessionStorage` 的交互归另一个 hook。
- 只跟 React 状态和 JSX 有关的留在组件。

这样每个文件都能用一句话说明自己为什么存在，而不是“因为第 345 行太长了”。

## 三、sink hook：只和声音会话打交道

第一个 hook 接收音频元素引用、当前音量、当前是否在播，做四件事：

- 注册 `music` sink，`setGain` 时把本地音量乘系数后写回元素。
- 实现 `setSuspended`：暂停，或在有播放意图时重试播放。
- 注册解锁回调，处理自动播放被拦截后的重试。
- 挂载时声明背景乐为音乐，卸载时清空并暂停。

它不读写任何存储，也不知道 UI 上有没有静音按钮。它只保证“导演说什么，元素就怎么响”。

## 四、偏好 hook：只和存储打交道

第二个 hook 负责两组键：

- 本地偏好：音量、循环模式、当前曲目，启动时读取，变化时写入。
- 会话意图：是否在播，用于舞台返回后恢复。

读取发生在挂载时，写入发生在值变化时。它不碰音频元素，也不决定要不要播放；它只把“用户上次的选择”和“本次会话的愿望”交给组件。

两个 hook 的依赖方向很清楚：组件同时调用它们，它们彼此不知道对方存在。

## 五、ref 解决“最新值”问题

sink 的回调是在注册时创建的闭包。如果直接捕获 `volume` 和 `playing`，注册之后它们就固定了：用户拖动滑块，`setGain` 仍用旧音量。

解法是用 ref 保存最新值，回调里读 `ref.current`。注册逻辑只依赖音频元素引用，不会因为音量变化反复注销、重注册 sink。

这个模式看起来笨，但它把“订阅生命周期”和“值的变化频率”解耦了。音频元素引用稳定，sink 就稳定；音量怎么变都不影响注册。

## 六、mountedRef 防止首帧覆盖

持久化 hook 有一个经典顺序问题：

首次渲染时，状态是默认值；挂载 effect 读取存储并 `setState`；而写入 effect 也在这轮渲染后执行。如果写入先跑，就会用默认值覆盖刚读出来的偏好。

解法是用一个挂载标记：第一次写入 effect 直接跳过，读取完成后的变化才落盘。标记在读取 effect 里置位。

这不是优雅的写法，但比重构整棵状态树便宜。它只在一个地方出现，注释写清原因即可。

## 七、拆完还有 292 行

拆完不是“变小”了，而是“剩下的是真正属于组件的东西”：曲目列表、播放控制、进度、迷你播放器布局、错误与拦截提示。

292 行仍然接近上限，但它是一个连贯的整体：所有代码都在描述同一个界面。再拆就需要引入子组件，而不是继续搬 hook；那是另一种重构，不该混在这一轮做。

行数门禁的价值不是逼出最小文件，而是逼你回答“这段代码为什么在这里”。

## 八、回归怎么保证

拆分前后，行为必须完全一致。验证分三层：

- 类型检查：hook 的入参与返回值明确，搬家后类型错误会立刻暴露。
- 定向测试：音乐与音频相关用例全部通过，覆盖 sink 增益、静音、舞台恢复。
- 手动路径：播放、切歌、拖音量、进舞台、返回、静音刷新。

这一轮音乐与音频相关测试共 20 项通过，web 类型检查通过。没有新增行为，所以测试也不需要新增断言，只需要证明没退化。

## 九、拆分的时机

不是一到 300 行就拆。先看这个文件是否还在快速变化：如果明天就要重写播放逻辑，今天拆只是把 diff 摊薄。

这次拆分的触发点是“音频导演接入”——播放器本来就要改 sink、静音和恢复，顺势把两类副作用搬走，改动集中在一轮里，回归范围清楚。

重构最好的时机，是功能改动本来就要经过这片代码的时候。

## 十、边界

没有把播放器改成 headless hook 加纯展示组件。那会带来更大的收益，也会带来更大的回归面；当前 UI 仍在演进，过早抽展示层会让两端都难改。

也没有引入状态管理库。两组持久化加一个音频会话，用 React 自带能力足够；复杂度应该花在规则上，而不是花在同步框架上。
