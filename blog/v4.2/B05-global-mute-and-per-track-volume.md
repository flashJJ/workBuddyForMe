# 全局静音与分轨音量：两个正交的维度

“把音量拖到 0”和“按下静音”看起来结果一样，实际上是两种不同的用户意图。前者是调音，后者是暂时闭嘴；恢复时，前者应该回到原来的音量，后者只需要取消静音。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，音频入口分散在音乐迷你播放器和剧场控制栏。这一轮先把静音做成全局单一状态，再把每条音轨的音量留在各自手里。

## 一、混在一起的后果

旧实现里，音乐和剧场各存一份静音，音乐还有自己的音量滑块。

于是出现了这些组合：音乐静音、剧场没静音；音量拖到 0、静音按钮却是关闭；刷新页面后静音丢了，音量还在。用户无法预测“现在到底会不会出声”。

根因不是 UI 不好看，而是把两个维度压成了一个值。

## 二、静音是布尔，音量是数值

静音是全局的、暂时的、二值的：要么全部不出声，要么恢复各轨原本的音量。

音量是分轨的、长期的、连续的：音乐可以 40%，剧场 BGM 可以更轻，语音沿用合成侧的音量。

两者相乘得到最终输出，但存储与交互必须分开。静音不修改任何一条音轨的音量值，取消静音时也就不会出现“音量被重置成 100%”的意外。

## 三、一个静音状态，两个入口

导演持有唯一的静音布尔，音乐迷你播放器与剧场控制栏都读同一份快照、写同一个方法。

任何一个入口切换，另一个入口立刻同步，因为它们订阅的是同一个源，而不是互相调用 setState。这里不需要事件总线，也不需要把状态提升到页面级 Context。

同步的另一个好处是刷新后一致：只持久化一个值，不存在“两个键写入顺序不同”导致的短暂错位。

## 四、有效音量 = 本地音量 × 导演系数

音乐的音量计算只有一行：

```ts
element.volume = clamp(localVolume * gain);
```

`localVolume` 是用户拖动滑块得到的 0 到 1；`gain` 是导演给的系数，已经包含静音与 duck。

这样分工很干净：导演不知道音乐音量是多少，音乐也不知道为什么系数变成 0.35。两者相乘，得到最终值。静音时 `gain = 0`，无需暂停播放，取消后立刻回到原音量。

## 五、剧场 BGM 的基础音量是 0.3

剧场 BGM 没有用户滑块，它有一个固定基础音量 0.3，再乘导演系数。

0.3 的选择与场景有关：BGM 是台词的情绪底色，不能盖过人声；同时它又要在安静段落里可感知。这个值写在播放器内部，不暴露给用户，也不进入导演。

导演给出的系数对它同样适用：静音时为 0，语音活跃时变 0.35，算下来目标音量约 0.105，用 120 毫秒线性淡变过去，不会产生突兀的断崖。

## 六、持久化只存意图

静音需要跨刷新保留，所以写入本地偏好键。

写入时捕获异常：隐私模式、存储被禁用、配额耗尽，都可能让 `setItem` 抛错。失败就静默降级为“本次会话有效”，不影响播放，也不弹提示。音频偏好不值得用一个错误弹窗打断用户。

读取同理：拿不到就当作未静音。启动时导演在构造函数里读一次，之后只通过 `setMuted` 修改，避免多处读取造成状态漂移。

## 七、为什么语音没有音量滑块

语音是信息载体，不是背景氛围。给它一个音量滑块，会引出“调到 10% 听不清是谁的责任”这类问题。

语音沿用合成侧的音量，只接受全局静音与 duck 的间接影响。用户想安静，按全局静音；想听清，取消静音。入口少，心智负担小。

这也是优先级的一种体现：语音不需要让用户调，它需要的是不被别的音轨盖住。

## 八、UI 上必须看得出区别

两个控件如果在视觉上太像，用户就会混。所以设计上做了区分：

- 静音是一个带状态的图标按钮，出现在音乐迷你播放器与剧场控制栏，两处状态一致。
- 音乐音量是滑块，只在音乐播放器里出现。
- 剧场 BGM 没有滑块，只有静音后的视觉反馈。

不要把静音做成“音量拖到最左”，也不要把音量滑块拖到 0 时自动点亮静音。保持两个维度独立，用户才能建立正确预期。

## 九、测试要覆盖组合

这类状态最容易在组合处出错，测试至少覆盖：

- 静音时，音乐的 `volume` 为 0，但播放未暂停。
- 取消静音后，恢复到静音前的本地音量。
- 语音活跃且未静音时，音乐音量为本地音量乘 0.35。
- 静音且语音活跃时，结果仍是 0，不出现 0 乘 0.35 之外的额外分支。
- 存储写入抛错时，静音仍在本次会话生效。

这些都是纯计算或假元素断言，不需要真实音频设备。

## 十、边界

全局静音不控制系统音量，也不影响桌面壳的其他提示音；它只作用于应用内的四条音轨。

输出设备选择、单轨独奏、响度均衡都不在这一层。静音与音量只解决“谁出声、多大声”，不解决“从哪个设备出声”。
