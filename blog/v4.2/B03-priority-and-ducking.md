# 优先级与 duck：语音说话时，谁该让路

多个声音同时存在时，最糟的不是吵，而是不可预测：这一次说话音乐停了，下一次没停；这一段剧场 BGM 压低了，下一段没有。用户说不清哪里不对，只觉得“这个应用有点乱”。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，音频需求长到四条音轨之后，才开始需要一个明确的让路规则。

这一轮把优先级与 duck 写成一个纯函数：输入是静音、语音来源集合、音轨类型，输出是一个 0 到 1 的系数。

## 一、优先级不是音量大小

优先级描述的是“资源冲突时谁保留表达权”，不是“谁默认更响”。

语音是信息本身，错过一句就听不懂；剧场 BGM 是情绪铺垫；全局音乐是用户主动选择；音效是点缀。它们的可替代性依次上升，所以优先级定为：

`voice > theater-bgm > music > sfx`

这个顺序不用于排序播放，也不用于抢占，只用于解释为什么 duck 只作用于背景乐：语音说话时，背景乐让路，音效不让，因为它短、稀疏，且不承载语义。

## 二、0.35 这个数字怎么来的

duck 的目标不是“听不见”，而是“还在，但不抢”。

压到 0 会让用户以为音乐被关掉了，恢复时又像突然开始播放；压到 0.7 在语音较轻时仍然糊在一起。0.35 大致相当于下降九分贝左右，是常见的背景避让量级。

它不是从某个标准推导出来的，而是一个可调常量。重要的是它只有一个值，由导演统一给出，而不是每个播放器各自写一个 `0.35`。这样以后想改成 0.3，只改一处，测试也只需要改一处断言。

## 三、线性系数与听感

导演输出的是线性增益，不是分贝。0.35 的线性增益在听感上已经是明显降低，但不会消失。

各播放器拿到系数后怎么应用，仍由自己决定：音乐直接乘到 `volume`，剧场 BGM 用 120 毫秒线性淡变到目标值。快速淡变很关键，语音起始通常没有前奏，硬切会有一个“咯噔”的爆音感。

音效不乘这个系数。它要么发，要么不发，取决于静音与并发名额。

## 四、布尔值不够：多来源语音

最初的想法是给导演一个 `speaking: boolean`。单窗口时完全够用。

但语音来源不止一个：主窗的助手、桌宠、舞台里的角色，都可能说话。如果各自把自己的布尔写进去，就会出现覆盖：

- 主窗开始说话，设为 true，背景乐压低。
- 桌宠开始说话，也设为 true。
- 主窗说完，设为 false，背景乐恢复——但桌宠还在说。

用户听到的是背景乐在两句语音之间突然弹回来。这不是边界情况，而是多窗口应用的常态。

## 五、用来源集合代替计数

导演内部用 `Set<string>` 记录来源 id。语音播放开始时加入，结束时移除；`size > 0` 就表示有人正在说话。

相比计数器，集合多了一个能力：同一个来源重复上报不会重复计数，卸载时可以按 id 精确清理。语音组件用稳定 id 作为来源标识，卸载时无论播放是否正常结束，都把自己的 id 删掉，避免留下幽灵 duck。

这条清理逻辑比 duck 本身更容易出错。一个没有结束回调的异常路径，就能让背景乐永远压在 0.35，而用户只会觉得“音乐声音坏了”。

## 六、只在跨越边界时重算

集合每次变动都重算增益会很浪费，也会让淡变反复启动。真正需要处理的只有一种变化：从“没人说话”到“有人说话”，或者反过来。

所以导演在增删来源后比较前后状态，只有跨越 0 的边界才应用增益并通知订阅者。中间来源的增减不触发声音变化。

这带来一个可预测的性质：无论同时有几个来源，背景乐只 duck 一次、只恢复一次。用户听到的过渡是干净的。

## 七、音效为什么不参与 duck

音效不 duck，但受另一条规则约束：同时最多两个。

原因在于音效的语义是“事件提示”，不是持续背景。把它压到 0.35，短促的提示音会变得几乎听不见，等于白触发；而真正会打扰人的是叠加，不是单次音量。

所以对音效用限流而不是 duck：第三个直接丢弃，不排队。这条规则放在下一篇展开，但它和优先级是同一套思路——不同音轨用不同手段治理，而不是一把音量推子推到底。

## 八、duck 不是压缩器

需要说清边界：这不是动态范围压缩，也不看实际响度。

它不知道语音此刻有多响，不知道背景乐的电平，也不做侧链。它只知道“语音在不在”，然后给背景乐一个固定系数。

对单人桌面应用，这个精度足够：语音是清晰的 TTS，背景乐是预置曲目，两者电平相对稳定。真正的侧链压缩、响度归一和总线限制，需要一条完整 WebAudio 图，成本和收益都不在当下。

## 九、规则可测，才敢改

把优先级与 duck 写成纯状态后，测试可以非常直接：

- 静音时，四条音轨的系数都是 0。
- 一个语音来源活跃时，音乐与剧场 BGM 为 0.35，音效为 1。
- 两个来源先后结束，只在最后一个结束时恢复为 1。
- 同一个来源重复上报，不会改变状态。

没有音频设备也能跑，规则改错会立刻暴露。对一个没有 QA 团队的项目，这是唯一可持续的验证方式。

## 十、留给未来的空间

当前优先级是硬编码的常量。如果以后出现导航播报、闹钟等新音轨，可以把它扩展成一张类型到等级的映射表。

但暂时不需要。四条音轨、一个 duck 比例、一个并发上限，已经能覆盖全部现有场景；过早抽象只会增加阅读成本。
