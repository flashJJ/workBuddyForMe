# 一次手势解锁所有音频：把监听从各模块收回来

浏览器不允许页面在没有用户交互的情况下自动发声。这条规则本身没问题，问题在实现方式：每个音频模块都自己挂一个 `window` 监听，等用户“第一次点击”。

当应用里有语音、剧场 BGM、剧场音效和全局音乐四套音频时，就会出现四个监听、四套解锁状态，以及“为什么语音能播了，音效还没声”的碎片化体验。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，这一轮把解锁收到根布局，只做一次。

## 一、自动播放策略到底拦什么

不同浏览器的细节不同，但共同点是：音频上下文或媒体元素在“没有用户激活”的页面上启动，会被挂起或拒绝。

被拦时不一定是抛错。WebAudio 的上下文可能创建成功但处于 `suspended`，`resume()` 需要手势；`HTMLAudioElement.play()` 则返回一个被拒绝的 Promise。

所以“解锁”不是设置一个布尔就完事，而是要在用户手势的调用栈里，真正触发各子系统的恢复动作。

## 二、四个监听带来的三个问题

旧实现里，剧场和语音各自监听首次手势，音乐则在播放失败时自己重试。问题很具体：

- 监听顺序不确定。谁先绑谁先跑，后绑的可能已经被前一个移除。
- 状态不共享。语音解锁了，音效仍认为没解锁。
- 清理不彻底。组件卸载后监听还在，路由切换多次就累积多个。

还有一个隐蔽问题：手势监听的移除条件写得不一致，有的用 `once`，有的手动移除，边界情况会漏。

## 三、根布局只挂一次

新增一个不渲染任何内容的客户端组件，挂在根布局。它在挂载时注册两个一次性监听：

```ts
window.addEventListener('pointerdown', unlock, { once: true });
window.addEventListener('keydown', unlock, { once: true });
```

任一事件触发后调用导演的 `unlock()`，并同时移除另一个监听，避免键盘和鼠标各触发一次。组件卸载时清理剩余监听。

它不区分开发与生产，也不依赖任何业务 Context。放在根布局，意味着无论用户从哪个页面进入，第一次手势都会经过这里。

## 四、导演只负责分发

导演不自己创建音频上下文，它持有的是回调集合。

音乐、剧场音效、语音队列在初始化时各自注册一个解锁回调：

- 语音队列恢复 WebAudio 上下文；
- 剧场音效确保上下文存在并 `resume()`；
- 音乐播放器在“意图为播放但元素暂停”时重试 `play()`。

`unlock()` 遍历集合并逐个调用。子系统的知识留在子系统，导演只知道“该叫醒它们了”。

## 五、失败必须隔离

解锁回调可能失败：上下文不可用、浏览器拒绝、音频设备被占用。

每个回调都包在独立的 try/catch 里。一个失败不能阻断后面的回调，否则语音的异常会让音效永远解锁不了。

失败不弹错，也不把全局解锁状态回滚。下一次用户手势会再次触发解锁；如果仍然失败，那就继续安静地失败。音频不是关键路径，报错只会制造焦虑。

## 六、解锁不等于播放

这是最容易混淆的一点。

解锁只是让“之后可以播”成为可能；它不应该顺便播放音乐，也不应该触发一段测试音。用户点一下按钮，突然响起声音，是比不能播更差的体验。

所以音乐的回调只做重试：如果播放意图是“在播”，且元素确实处于暂停，才尝试恢复；否则什么都不做。语音与音效的回调只恢复上下文，不主动发声。

## 七、为什么同时监听键盘

只用 `pointerdown` 会漏掉键盘用户，也不覆盖某些辅助技术触发的激活。

`keydown` 覆盖回车、空格等按键操作。两个监听都带 `once`，并在任一触发后移除另一个，保证只解锁一次。

不用 `click` 的原因是需要更早：某些浏览器要求音频在 pointerdown 的调用栈内恢复，等到 click 可能已经错过最佳时机。

## 八、幂等与重复触发

`unlock()` 可以安全地被调用多次。子系统回调可能重复执行，但恢复上下文和重试播放本身是幂等的。

导演内部记录“是否已解锁”，只用于快照展示与调试，不作为是否执行回调的开关。这样即使第一次解锁时某个子系统还没注册，后续注册的子系统也能在下一次手势时被叫醒。

这个细节很重要：根布局的手势可能早于懒加载模块完成初始化。如果解锁是一次性的布尔开关，后注册的模块就永远等不到解锁。

## 九、怎么验证

解锁链路很难用真实浏览器自动化稳定复现，测试分两层：

- 状态层：注册两个会抛错/正常的回调，调用 `unlock()`，断言正常回调仍被执行，异常被吞掉。
- 组件层：挂载监听组件，派发一次 `pointerdown`，断言导演收到解锁，且再次派发不会重复。

真实设备上再补一次手动验证：冷启动后不点击，语音应无声；点击任意位置后，语音、BGM、音效都能播。

## 十、边界

这一轮不做“解锁前预加载并静音播放”这类技巧。它依赖浏览器实现细节，容易在黑盒更新后失效。

也不做跨窗口共享解锁状态。每个渲染进程有自己的用户激活状态，主窗解锁不代表桌宠窗口解锁；这属于后续多窗口协调的问题。
