# 四条音轨，一个导演：音频状态该住在哪里

一个桌面应用里同时存在几种声音，是很容易被低估的复杂度。音乐在后台播，小剧场有自己的配乐，助手说话要压背景，换句时还有两声提示音。单独听都正常，合在一起就会互相打架。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，声音正是按功能长出来的：谁需要播放，谁就自己管一个播放器。功能没做错，但四套实现之间没有共同语言。

这一轮做的事情，是把“谁在响、谁该让路、谁被静音”从各播放器里抽出来，交给一个只持有状态的音频导演。

## 一、四类声音，四份真相

先看原来的四套实现，它们各自都合理：

- 全局音乐持有一个 `HTMLAudioElement`，音量和曲目写 `localStorage`。
- 小剧场 BGM 自己维护音量、静音和“说话时压到 35%”的 duck 状态。
- 语音走播放队列加 WebAudio，逐句合成、逐句播放，并提供口型电平。
- 剧场音效用 WebAudio 现场合成，静音状态存在一个模块级变量里。

问题不在单个模块，而在状态被复制了三份：音乐不知道剧场静音了，剧场不知道语音正在说话后音乐是否该压，音效只认自己那个变量。

## 二、曾经的互斥是“碰巧成立”

全局音乐和剧场 BGM 不能同时响。旧实现靠的是路由：进入小剧场是独立页面，主布局连同音乐 Provider 一起卸载，音乐自然停了。

这看起来像规则，其实是副作用。它只在“舞台必须是独立路由”这个前提下成立；一旦舞台改成同页弹层，两首背景乐就会叠在一起。更直接的缺陷是返回：Provider 重新挂载，播放状态归零，用户得再点一次播放。

## 三、导演只回答四个问题

新的音频导演不播放声音，只保存四件事实：

1. 当前是否全局静音。
2. 哪些来源正在说话。
3. 当前背景乐是音乐、剧场 BGM，还是都没有。
4. 是否已经完成首次手势解锁。

其余全部由派生计算得到：每条音轨的有效增益、某条背景乐是否应当暂停、音效还能不能再开一个。状态少，组合才可预测。

## 四、sink：一个只有两个方法的契约

播放器不把控制权交出去，只注册一个音量出口：

```ts
interface AudioSink {
  setGain(gain: number): void;
  setSuspended?(suspended: boolean): void;
}
```

`gain` 是导演算好的 0 到 1 的最终系数，不解释原因，也不带单位。音乐拿到它，乘上自己的本地音量；剧场 BGM 拿到它，乘上 0.3 的基础音量；音效拿到它，决定这一声要不要发。

`suspended` 解决背景互斥：暂停发声，但不销毁播放器。两个方法各管一件事，播放器内部的淡变、队列、重试都留在原地。

## 五、注册与注销都是一等公民

导演内部按音轨类型存一个集合，而不是只存一个 sink。同一类音轨可能有多个消费者，例如主窗和桌宠各有一条语音；用集合就不必假设“每种音轨只有一个”。

注册时立刻下发一次当前增益，避免播放器在等待下一次状态变化前用了旧音量。注销函数随组件卸载调用，同时把空集合删掉，防止长期运行后留下僵尸引用。

这条规则听起来琐碎，但它决定了导演能不能在热更新、路由切换和窗口重建中保持干净。

## 六、单例为什么放在 web 层

音频导演放在 web 应用的特性目录，没有下沉到共享包，也没有单独发包。

理由很实际：所有消费者都在浏览器里，导演需要 `window`、`localStorage` 和浏览器音频 API 的类型。共享包目前保持纯数据与纯函数，不应该为了一个单例引入 DOM 类型。依赖方向也简单：音乐和剧场单向依赖导演，导演不反向依赖任何业务模块。

代价是未来如果桌面壳也要同源调度，需要再抽一次。这个代价可以接受，因为现在没有第二个运行时。

## 七、收益不在代码量，在可解释性

改造后，四条规则都能用一句话说清，也都能单独写测试：

- 静音时所有音轨增益为 0。
- 语音活跃时，音乐与剧场 BGM 乘 0.35。
- 同一时刻最多一条背景乐。
- 音效同时最多两个，第三个直接丢弃。

以前这些问题要靠“去三个文件里找找看”，现在只需要读一个状态机。

## 八、边界：导演不是混音器

这一轮刻意没有做三件事：不把所有音频迁到一条 WebAudio 图，不加压缩器，不做输出设备选择。

各播放器仍保留自己的淡变、队列与重试；语音的取消与代际语义没有改变；音乐也不进入语音队列，只共享 duck 与解锁。

导演的职责到“算出一个系数”为止。越界去接管播放，就会把一次低风险的状态收拢，变成一次高风险的播放链路重写。

## 九、这套结构的适用条件

如果你的应用只有一条音轨，导演是多余的。当声音开始跨模块互相影响，尤其是出现“说话时要压背景”“进某个页面要停另一条”这类规则时，集中状态才划算。

判断标准不是音轨数量，而是同一件事是否需要在多个地方各存一份。只要答案是肯定的，就值得先收状态，再谈混音。
