# 音效并发与 WebAudio 生命周期：第 3 个音效为什么直接丢掉

小剧场的音效很短：幕布拉开是一段低频噪声，换句是一声提示音。单听都克制，连续触发就会叠成噪音——尤其当台词切换很快时，三四个提示音同时响，听起来像故障。

我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，音效由 WebAudio 现场合成，不依赖外部素材。这一轮给它加了并发上限，也顺手把上下文的生命周期理清了。

## 一、叠音不是音量问题

直觉方案是把音效音量调小。但问题不在单次音量，而在密度：三个短音叠在一起，峰值会上升，频谱也会变乱，调小只会让每个都听不清。

另一种方案是排队。但音效是事件提示，晚 300 毫秒播放就失去了与画面同步的意义。排队会把“提示”变成“延迟噪音”。

所以选择限流：同时最多两个，第三个直接丢弃，不排队、不报错、不改语义。

## 二、名额必须在发起前占用

限流的核心不是计数，而是“先占位，后播放”。

如果先检查有没有名额，再异步创建音频节点，中间有一段空窗：连续触发时多个调用都看到“还有名额”，最后一起播放，上限形同虚设。

正确顺序是同步占位：

```ts
if (!director.tryPlaySfx()) return;
const ctx = ensureContext();
if (!ctx) {
  director.endSfx();
  return;
}
```

`tryPlaySfx` 在同一个调用栈里完成检查与自增，只有一个调用能拿到最后一个名额。

## 三、每一条退出路径都要归还

占位之后，任何不播放的路径都必须调用结束，否则名额会泄漏，最终所有音效都发不出来。

至少有三类出口：

- 上下文不存在或不可用；
- 上下文处于挂起且 `resume()` 失败；
- 音频正常结束。

前两类是同步或异步失败，要显式归还；第三类挂在音频源的 `onended` 上。合成音效都设了明确的 `stop()` 时间，所以 `onended` 一定会来，不会出现“节点还在、计数不还”的悬挂。

## 四、静音时不占名额

全局静音时，`tryPlaySfx()` 直接返回 false，不增加计数，也不创建节点。

这条顺序很重要：如果先占位再检查静音，静音期间频繁触发会占满名额，取消静音后的第一声反而被丢弃。用户会觉得“刚取消静音，音效坏了”。

静音是全局状态，音效模块不需要自己再存一份；它只问导演“现在能不能开一个新音效”。

## 五、AudioContext 懒创建且复用

上下文在第一次真正需要时创建，之后复用同一个实例。

不要在每次播放时 `new AudioContext()`：浏览器对同时存在的上下文数量有限制，频繁创建还会带来额外的线程与缓冲区开销。也不要在模块加载时就创建，那会撞上自动播放策略，得到一个永远挂起的上下文。

复用带来的副作用是状态需要检查：上下文可能因为系统休眠、设备切换或页面不可见而变成 `suspended`。每次播放前检查状态，必要时 `resume()`，比假设它一直 running 更稳。

## 六、resume 失败要静默归还

`resume()` 返回 Promise，可能被拒绝。这时不能继续调度音频节点，否则会在挂起的上下文里堆积无人播放的源。

处理方式是等待结果后再判断状态：失败就把名额还回去，静默结束本次播放。下一次用户手势后的音效再试。

这里不需要重试队列。音效是即时事件，错过就错过；补播反而会和当前画面错位。

## 七、上下文不随路由关闭

小剧场是独立路由，退出时组件卸载、音效模块的引用可能被清理。但模块级的 `AudioContext` 不主动 `close()`。

原因是上下文创建成本高，重进剧场时再建一次会带来明显延迟；同时关闭后不可恢复，必须重新创建。对一个反复进出的场景，复用比“干净”更实际。

代价是上下文会一直占用少量资源。对桌面应用可以接受；如果未来音效种类变多，再考虑按需挂起而不是销毁。

## 八、合成音效的取舍

音效没有用音频文件，而是用振荡器和噪声缓冲现场合成。

好处是体积为零、参数可调、无版权登记负担；坏处是音色上限有限。幕布的噪声靠低通滤波与包络做出“拉开”的感觉，换句提示音靠两个频率的短滑音区分剧种。

这套实现的前提是音效只做提示，不做表现力主角。如果以后需要更丰富的音色，仍应走素材库，而不是把合成器写成一个小型音源。

## 九、可测的部分

WebAudio 本身不适合在单测里跑，但并发规则可以脱离它测试：

- 连续申请三个名额，前两个成功，第三个失败。
- 申请后结束一个，再申请成功。
- 静音时申请直接失败，且不改变计数。
- 上下文创建失败时，名额被归还。

把 `tryPlaySfx/endSfx` 留在导演里，正是为了让这些断言不需要真实音频环境。音效模块只负责“拿到名额之后怎么发声”。

## 十、边界

没有做音效优先级：两个名额先到先得，不区分幕布与换句。当前场景里两者不会同时高频触发，先到先得足够。

也没有做全局音效音量。音效只有开与不开，音量由合成参数决定。等到用户真的提出“音效太响”，再引入分轨音量，而不是现在先造一个没人调的滑块。
