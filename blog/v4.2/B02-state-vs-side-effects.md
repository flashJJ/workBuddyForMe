# 状态与副作用分离：音频导演为什么不创建播放器

把音频收进一个“管理器”是常见做法：它创建播放器、加载曲目、调节音量、做淡入淡出，顺便处理静音。代码集中了，问题也集中了——任何一条音轨的行为变化，都要改这个管理器；测试它需要真实音频环境。

这一轮我们选了相反的方向：导演只持有状态，副作用留在各自模块。我们的应用是本地优先、单人开发、Electron + Next.js 交付的桌面 AI 助手，这个选择决定了后面所有实现细节。

## 一、先定义什么算“状态”

状态是那些会影响多条音轨、且必须在同一处判断的事实：

- 全局是否静音。
- 哪些语音来源正在说话。
- 当前哪条背景乐拥有发声权。
- 首次手势解锁是否已经发生。

它们共同的特征是：不只属于某一个播放器，且变化会影响别人。只要一个值满足这两点，就应该放进导演。

反过来，当前曲目、播放进度、淡变计时器、音频节点连接关系，都是某个播放器自己的状态，不进来。

## 二、副作用必须回到生产者手里

播放器最清楚怎么处理自己的副作用：

- 音乐的 `HTMLAudioElement` 会因自动播放策略失败，需要重试。
- 剧场 BGM 需要 800 毫秒淡入、120 毫秒快速避让，还要处理换幕。
- 语音队列有代际与取消语义，不能随便暂停。
- 音效要创建振荡器与增益节点，并在结束时释放并发名额。

如果导演直接调用 `pause()`、`play()` 或 `setInterval`，它就必须理解这四种完全不同的生命周期。那不是统一，是把四份复杂度搬到一个文件里。

## 三、sink 是唯一的副作用入口

导演与播放器之间只有一个契约：

```ts
interface AudioSink {
  setGain(gain: number): void;
  setSuspended?(suspended: boolean): void;
}
```

`setGain` 只表达“最终系数是多少”，不表达“为什么”。播放器自己决定怎么应用：音乐直接赋值 `volume`，剧场 BGM 走线性淡变，音效根据系数决定是否发声。

`suspended` 是可选能力。只有背景乐需要“暂停但保留播放器”，语音和音效不实现它，导演也不会调用。

## 四、注册即同步，注销即清理

注册 sink 时，导演立刻下发一次当前增益和暂停状态，而不是等下一次状态变化。否则播放器在注册后的第一段时间里会用默认值发声，出现一次可听见的错音。

注销时从集合里移除；集合空了就删掉对应音轨的键。这个清洗动作让导演在长期运行中不会累积失效引用，也让测试可以断言“注销后不再收到增益”。

同一类音轨允许注册多个 sink。语音天然有多个来源，音乐未来也可能有主窗与迷你窗两个出口，集合比单个字段更接近事实。

## 五、快照让 UI 不必猜

导演对外提供一个不可变快照：是否静音、语音是否活跃、当前背景乐、是否已解锁。订阅者只在快照变化时收到通知。

快照不是把内部字段直接暴露，而是每次变化重新构建。这样 UI 拿到的是一个稳定值，不需要读一堆 getter，也不需要自己组合条件。音乐迷你播放器的静音按钮、剧场的静音按钮，读的是同一份快照。

订阅返回取消函数，和注册 sink 的形态一致。组件卸载时取消，避免路由切换后旧组件继续响应。

## 六、为什么导演不做淡变

淡变看起来很适合集中：所有音轨都用同一条曲线，多优雅。

但淡变的时间常数是场景相关的。剧场 BGM 的避让要快，否则语音已经说完了音乐还没降下来；换幕要慢，否则情绪断裂；音乐的暂停与恢复又受浏览器策略影响。把它们统一成一个参数，只会让每个场景都不合适。

所以导演只输出目标系数，淡变留在播放器。状态变化是瞬时的，声音变化可以有过渡，这两件事本来就不该绑在一起。

## 七、依赖方向决定可维护性

依赖是单向的：音乐、剧场、语音依赖导演；导演只依赖浏览器 API 和自身类型。

这条约束带来两个直接好处。第一，导演可以被任意模块引用而不会形成环，循环依赖检查也能过。第二，导演的测试不需要挂载 React 组件，不需要真实 `Audio`，只需要断言状态与系数。

如果导演反过来 import 了音乐模块的常量，环就出现了；如果它 import 了剧场的类型，音频内核就被业务语义污染了。

## 八、纯状态带来的测试形态

测试可以只做三件事：

1. 注册一个假 sink，改变静音，断言收到 0 或 1。
2. 上报两个语音来源，逐个结束，断言只在最后一个结束时恢复增益。
3. 设置背景乐，断言另一条背景 sink 收到暂停，切回空值后恢复。

没有 DOM，没有音频解码，没有计时器。规则错了，测试立刻失败；实现改了，只要契约不变，测试不用动。

这比“启动应用听一下”可靠得多，也让后续新增音轨有地方落脚。

## 九、分离的代价

代价是调用方要多写一点：每个播放器都要实现 sink，注册、注销、处理增益。原来只要在管理器里加一个分支。

但这份成本是一次性的，而且落在最了解副作用的模块里。集中管理器的成本则是长期的：每加一条音轨，所有条件判断都变复杂一分。

## 十、一条判断标准

当你想把某个能力放进“统一管理器”时，先问：它需要知道播放器的内部生命周期吗？

如果不需要，它属于状态，可以集中。如果需要，它属于副作用，应该留在生产者身边，通过一个窄接口接受指令。

这条标准比“代码放在一起比较整齐”更难满足，但能让系统在增加第三条、第四条音轨时仍然可读。
