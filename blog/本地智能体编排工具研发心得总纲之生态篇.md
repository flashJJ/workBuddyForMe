## 为什么叫「生态」

v3.0 之后，项目里已经有角色、剧本、动效、声音、场景、道具。但它们全是内置的：想加一个姿势、一段剧本、一张背景，只能改代码重新发版。

生态篇讲的是把这些东西从「内置资源」变成「可安装内容」的整个过程。它不是一上来就做插件市场，而是按顺序回答四个问题：

1. 内核里还有哪些硬编码，必须先把口子留出来？
2. 内容包怎么声明依赖、怎么排序、怎么拒绝坏包？
3. 装完之后，运行时怎么在不重启的情况下看到新内容？
4. 发布出去的包，用户凭什么相信它没被改过？

这四个问题分别对应 v3.1、v4.0、v4.3 和 v4.0 的发布校验。

## 六个关键取舍

### 1. 先做注册表，再做内容包

v3.1 没有直接上安装器，而是先做三个低风险探针：能力 effect 从 `switch(kind)` 改成 handler 表、provider 从 `switch(protocol)` 改成 factory 表、动效内容从静态 import 改成 `MotionContent` 快照。

这一步的价值是**把「新增能力要改内核」变成「新增能力要注册」**。没有这一步，后面的内容包安装会变成给 `switch` 打补丁。

### 2. 内容包只允许数据

`motion-pack` 的 payload 里只有 poses / motions / behaviors，没有可执行代码；VRMA 资源仍由 `pet-action` 承载。安装管线复用能力包已有的 ZIP、manifest、校验和、签名、健康检查、升级与回滚。

代价是表达力受限，换来的是：坏包不会执行任意代码，卸载和回滚有明确的补偿路径。

### 3. 依赖只表达「包依赖」

manifest 里的 `dependencies` 只指向能力包 id，不引入「服务标识」依赖；`coreVersion` 单独表达最低应用版本。环检测覆盖「已安装 + 待安装」的完整图，启用顺序只在预检和健康报告里输出，不自动批量启用。

### 4. 内容刷新以「会话快照」为单位

安装或停用内容包后，不热替换正在播放的模型，而是生成新的 `MotionContent.version`；当前会话继续用旧快照，下一次打开舞台、桌宠或主窗形象栏时读取新快照。

这是为了避免运行中替换内容导致骨骼与轨道错位。**「不重启就生效」和「不打断当前演出」并不矛盾，关键是选对刷新边界。**

### 5. 发布校验解决的是「信任」

`pnpm release:win` 归档后会生成 `SHA256SUMS.txt` 和 `build-info.json`（版本、commit、分支、构建时间、平台、架构与逐文件哈希）。发布说明引用安装包哈希与构建信息，用户可以自己复算。

它不解决代码签名，也不解决自动更新源，但它让「这个包是不是我构建的那个」变成一个可验证的问题。

### 6. 平台化之后，质量要能回归

v4.1 把陪伴质量与长跑性能做成门禁：12 组固定上下文的场景矩阵、决策回放、4 小时长跑采样、10 分钟短跑相对基线。v4.2 把音频收成一个导演，v4.10 把上下文预算做成可见面板。

这些版本看起来不像「平台」，但它们决定了平台上的内容能不能被信任地评估。

## 阅读路线

- 想理解平台化起点：v3.1 的《不改内核也能加能力》；
- 想抄内容包方案：v4.0 的《从注册口到内容包》和《内容包 payload 契约》；
- 想做可安装资源：v4.3 的场景包、道具包与资产预算；
- 想做质量门禁：v4.1 的场景矩阵与长跑采样；
- 想做上下文治理：v4.8 → v4.10 的意图路由、预算统一与可见性。

## 这一卷之后

生态篇把「内容可安装」跑通了，但还没有做运行时代码插件、第三方目录、自动更新与代码签名。这些是 v4.1 之后继续评估的方向，也是「生态」真正长成之前的最后几块地基。

如果你是第一次看到这个系列，建议先读基座篇的总览，再回到这一卷挑感兴趣的版本看。
