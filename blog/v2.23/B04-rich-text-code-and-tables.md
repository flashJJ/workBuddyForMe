# 富文本的最后一公里：代码块、表格与中文长文的排版节奏

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，聊天页的回复由 Markdown 渲染。语法高亮早就有了，但「能渲染」和「读起来舒服」之间，还差三段路。

代码块是一个裸的 `pre`，没有语言标识，也没有复制入口；表格在窄窗口里把中文压成竖排；标题、段落、列表、引用之间没有稳定的间距，长回复像一整块砖。

这一轮只处理这三个细节，不换渲染器，也不引入新的 Markdown 依赖。

## 代码块：从裸 pre 到两层结构

裸 `pre` 的问题是它只有内容，没有「这是代码」的元信息。读者不知道语言，想复制还得手动选中，移动端几乎没法选准。

改成两层：上面是标题栏，左边显示语言，右边是复制按钮；下面是原来的代码区。标题栏和代码区共用同一个外框，代码区不再有自己的边框和圆角。

语言名从代码节点的 `language-xxx` 类名里取，取不到就回退成 `text`。这样不需要维护语言映射表，也能覆盖大多数高亮场景。

## 复制为什么读 DOM，而不是读 props

这是这一块最容易写错的地方。

代码块在渲染前是纯文本，渲染后会被高亮插件拆成一堆嵌套的 `span`。如果复制逻辑去读 React 的 children 或原始 props，拿到的是节点树，不是用户看到的文本；拼接稍有遗漏，粘出来就会少字符或多换行。

正确做法是给 `pre` 挂一个 ref，复制时直接读它的 `textContent`。浏览器会把所有嵌套标签的文本按顺序摊平，得到的正好是原始代码。高亮结构怎么变，复制都不受影响。

复制成功后按钮切换成对勾，1.5 秒后恢复；定时器在组件卸载时清理，避免在已卸载组件上更新状态。按钮同时提供 `aria-label` 与 `title`，图标之外还有可读名称。

代码区自己限高并滚动，长代码不会把整条消息撑到几屏；横向滚动留在代码区内部，不带动页面。

## 表格：先给滚动容器，再谈首列粘性

表格在聊天正文里最常见的坏形态，是中文被压成竖排。

原因是浏览器默认会按容器宽度压缩列，长中文没有断词机会，只能一个字一行。解决方式不是给单元格加省略号，而是让表格保持内容宽度，把横向滚动交给外层容器。

所以渲染时给 `table` 外包一层滚动容器：容器负责横向滚动，表格自身按内容撑开。窄窗口下整表可以左右滑，而不是把每一列挤扁。

父级也要允许收缩。消息正文列如果带着最小内容宽度，表格会把整列撑出容器；加上 `min-w-0` 之后，滚动才会发生在表格容器里，而不是发生在整个页面上。

## 首列粘性：背景必须是不透明的

表格能横向滚动之后，新的问题是滚动时丢失行锚点。第一列通常是名称或序号，它应该固定在左边。

给首列加 `position: sticky` 之后，立刻会暴露一个视觉 bug：滚动到后面的列时，被固定的单元格是透明的，后面的内容会从它下面穿过去。

原因是粘性只改变定位，不改变背景。必须给首列显式的不透明底色，而且要按表头、普通行、偶数行分别给：

- 表头首列用表头的底色；
- 普通行首列用卡片底色；
- 斑马纹的偶数行首列，必须跟着换成斑马底色。

漏掉第三条，偶数行的首列会在滚动时突然变白，斑马纹断掉。这类问题不是逻辑错误，是层叠顺序的视觉债，只能靠逐条写清楚背景来还。

## 斑马纹与粘性是一对矛盾

斑马纹靠行背景色实现，粘性首列靠单元格背景色实现。两个规则作用在同一块区域，后者会覆盖前者。

处理方式不是提高选择器权重硬压，而是把「偶数行首列」当成一个独立状态显式声明。规则多一条，但语义清楚：每个可能被粘性覆盖的组合，都有自己的底色。

## 纵向节奏：preflight 抹掉了默认间距

Markdown 渲染出来的标题、段落、列表、引用、分割线，在浏览器默认样式里本来有上下 margin。但 Tailwind 的 preflight 会把它们统一清零。

清零本身是对的：应用界面不应该被浏览器默认排版绑架。代价是 Markdown 正文也失去了节奏——标题贴着上一段，段落之间没有呼吸，列表和引用糊成一片。中文没有西文的词间空格，视觉上会比英文更挤。

所以要在正文容器里重新建立一套纵向节奏：

- 标题的上间距明显大于下间距，让标题归属于下面的内容；
- 段落之间给一个稳定的小间距，不靠空行；
- 列表统一左缩进，列表项之间留一点缝；
- 引用用左边框加次要文字色，和正文拉开层次；
- 分割线上下留白，不用默认的粗线；
- 第一个和最后一个子元素的上下 margin 清零，避免容器出现双倍留白。

这套规则不复杂，但必须由正文容器统一声明。让每个 Markdown 元素自己在组件里带 margin，最后一定会互相打架。

## 流式渲染不能被排版拖慢

排版变复杂之后，最需要盯住的是流式性能。

做法没有变：消息按块切分，每块单独 memo，流式期间只有最后一块在变；代码高亮也跟着块走，不会每来一个 token 就重新解析整条消息。

表格与代码块的容器样式都是纯 CSS，不参与 React 渲染计算，因此不会因为「加了标题栏」而增加流式开销。

## 验证

聊天与消息相关单测覆盖了代码块渲染、复制反馈、表格容器与语言识别；聊天、形象与通用组件合计 126 例通过，中英文案对等测试通过。

类型检查、Lint、行数与依赖检查全部通过，没有新增 Markdown 或高亮依赖。

## 小结

富文本的最后一公里，往往不是解析能力，而是三件很土的事：给代码一个可复制的入口，给表格一个能滚动的容器，给中文长文一套稳定的间距。

这三件事都不新，但它们决定了用户读到后半段时，还愿不愿意继续读。
