# 骨架屏、回到底部与一次全局的 reduced-motion 降级

流式生成最难受的不是等，而是不知道自己有没有点上。点了发送，列表还是空的，光标还没出现，一两秒里界面没有任何变化——用户会再点一次，或者以为卡死。

我们的桌面 AI 应用是本地优先、单人开发的私人助手，聊天页所有内容都来自本机服务。这一轮没有加动画库，只补了三处状态反馈，以及一条全局的动效降级规则。

## 骨架屏：只在「真的有东西要来」时出现

空列表有两种含义：会话是新的，或者第一条消息正在生成。前者该给引导，后者该给占位。

判断条件写成 `messages.length === 0 && streaming`，两个都成立才渲染骨架屏。少了 `streaming`，刷新一个空会话也会闪骨架；少了长度判断，正常对话里会莫名其妙出现占位块。

骨架不是一根灰条，而是四条宽度递减的线：1/3、全宽、11/12、2/3。形状对齐真实的消息段落，加载完成时不会有明显跳变。容器同样是 `max-w-3xl` 居中，和后面真正的内容同轴。

没有给骨架屏设「最少展示时长」。本地首字通常来得快，硬留 300ms 只是为了让动画好看，实际是把用户的等待拉长。占位块的任务是消除空白，不是表演。

## 回到底部：200px 阈值

长对话里往上翻，新消息还在后面追加。列表底部的锚点元素配一个判据：

```ts
// scrollHeight - scrollTop - clientHeight：距底部还有多少像素
setAtBottom(el.scrollHeight - el.scrollTop - el.clientHeight < 200);
```

按钮只在 `!atBottom` 时挂载，定位在容器底部居中。三个决定值得记下来。

**为什么不是 0。** 贴底 1px 的抖动就会让按钮闪烁。留出 200px 的缓冲，大约半条到一条消息的高度，用户确实已经离开底部了。

**为什么不是常驻。** 常驻会盖住最后一条消息的 hover 操作条，也占掉正文的视觉空间。它是一次性的回归入口，不是导航。

**为什么用挂载而不是透明。** 透明元素仍然占据命中区域，滚动区底部的拖拽会打到它。条件挂载最省心。

点击用 `scrollIntoView({ behavior: 'smooth' })`。系统开启减弱动态效果时，浏览器和全局降级都会让这段滚动变成瞬时，不需要单独判断。

## 空态：三张卡，点击只填不发

新会话的空态原本只有一句「开始对话吧」，信息量为零。改成品牌图标 + 标题 + 说明，再加三张示例卡：做计划、总结长文、查资料。

关键在点击行为：只把文本写进输入框，然后把焦点移过去，不自动发送。

```ts
onUsePrompt={(text) => {
  setDraft(text);
  setComposerFocus((value) => value + 1);  // 自增计数，用来触发聚焦副作用
}}
```

不自动发送有两个理由。示例是起手式，用户多半想改一两个词；直接发送会消耗一次真实的模型调用，而这次调用大概率不是用户想要的。另外，输入框里可能已经有草稿，替换之前至少要让用户看见。

聚焦用自增数字而不是布尔值，是为了让「同一张卡连点两次」也能再次触发副作用——布尔值第二次就不变了。这类小机关在单测里很难体现，但用户一试就能感到差别。

## toast 入场：和弹层共用一套节奏

通知统一走一条入场动画：从下方 8px、缩到 0.98、透明开始，180ms 落到原位。

```css
@keyframes toast-in {
  from { opacity: 0; transform: translateY(8px) scale(0.98); }
  to   { opacity: 1; transform: none; }
}
```

时长取自设计令牌（120 / 180 / 240ms 三档），缓动统一用 `ease-out-quint`。三档够了：微交互用快档，入场用基础档，大面积位移用慢档。散落的 `duration-200`、`duration-300` 会被逐步替换，最终组件里只出现令牌名。

小位移配轻微缩放，是为了让通知「从哪里来」有方向感；不加旋转和弹跳，短时反馈越少花招越不打扰。

## reduced-motion：一条规则胜过十个组件

系统设置里开了「减弱动态效果」，用户的意思是：别用动画换我的注意力。实现上很容易只改自己刚写的那个组件，漏掉 Tailwind 自带的 `animate-pulse`、历史遗留的关键帧、以及第三方组件里的内联过渡。

所以做了一条全局兜底：

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

为什么压到 0.01ms 而不是 `none`：有些逻辑依赖 `animationend` / `transitionend` 收尾，直接禁用动画，事件可能永远不来。保留一个极短时长，事件照常触发，视觉上等同瞬间完成。

为什么用 `*` 而不是逐个组件写：动画来源有三类，组件作者、Tailwind 工具类、第三方库。逐个改要求你能穷举所有来源，而漏一个就等于没有降级。全局规则是覆盖所有现在和以后新增动画的底线。

但全局规则只压时长，不保证「停在正确的那一帧」。有些动画的第一帧并不是它想要的静态形态，必须单独覆盖：

```css
@media (prefers-reduced-motion: reduce) {
  .message-enter { animation: none; }
  .stream-caret { animation: none; opacity: 0.6; }
}
```

流式光标的呼吸条压到 0.01ms，会停在一个半透明的中间态；消息入场被压扁还可能留下位移残影。这类「动画即语义」的元素，要显式换成静态样式：光标变成一根静止的竖条，入场直接显示。弹层、运行边框、过程图连线同理，各自补一条 `animation: none`。

顺序很重要：先全局兜底保证不漏，再逐个把「必须静态」的地方钉死。反过来做，永远在追新加的动画。

## 取舍

不引入动画库，不为了过渡加 `will-change`，也不做滚动位置恢复——这三件事都会牵扯性能和状态管理，收益却不如一次清楚的占位和一条可靠的降级。

验证上，这套行为由聊天与公共组件相关的单测覆盖：骨架屏与空态互斥、点击示例卡只写入不发送、滚离底部后浮标出现；126 例通过。
