# 一次「质感升级」的七条方法论

把「能用」做成「看起来可靠」，最难的不是写样式，而是决定先改哪一处、改到什么程度算完、以及怎么证明改对了。

我们的桌面 AI 应用是本地优先、单人开发的私人助手，前端是 Next.js + Tailwind + Radix，桌面壳是 Electron。这一轮的题目很虚——质感——但落下来全是具体判断：令牌、布局、动效、空态、托盘。做完之后，值得留下的不是改了哪些类名，而是七条下次还能用的判断方式。

## 交付对账

先看这一轮实际交付了什么，以及拿什么证明。

| 方向 | 交付 | 证明方式 |
|---|---|---|
| 设计基座 | 三级表面、三档阴影、三档动效时长与统一缓动，五套主题逐套补齐 | 组件里不再出现散落的阴影与时长 |
| 组件基元 | Button 四态齐备并支持 loading，Input/Select 高度与焦点环对齐，Dialog 纯 CSS 入场 | 设置页与聊天页对比一致 |
| 聊天页骨架 | 正文列限宽居中，会话列可收成图标条，形象栏窄屏默认收起，阶段条窄屏折叠 | 布局口径与单测 |
| 消息与富文本 | 用户消息胶囊、hover 操作条、代码块语言栏与复制、表格斑马纹与首列粘性 | 交互断言 |
| 动效与空态 | 首轮骨架屏、200px 回到底部、三张示例卡、toast 入场、全局降级 | 126 例前后端单测 |
| 桌面常驻 | 托盘菜单按实时状态重建，驻留提示一次，失败降级 | 6 例菜单单测 |
| 兼容 | 无数据库迁移，schema 保持 45，旧库直接用 | 版本号未变 |

共同点是：几乎没有新增入口，全部是在已有路径上补状态、补一致性。

## 方法论一：先建令牌，再改组件

改样式最省事的顺序是「打开哪个组件就改哪个组件」。这一轮如果把顺序倒过来，会立刻欠下三类债：颜色写成 `emerald-500` 这样的硬编码、阴影写成 `shadow-sm`/`shadow-lg` 随手挑、过渡写成 `duration-200`/`duration-300` 混用。等改到第十个组件，想统一已经来不及了，只能全局搜索替换。

所以先补令牌：三级表面（页面底、卡片、浮层）、三档阴影、三档时长（120 / 180 / 240ms）加一条统一缓动，中文优先的字体栈，数字统一等宽。组件只允许引用令牌名。

这里有个容易漏的坑：令牌只在 `:root` 定义，命名主题会继承错误的亮暗基线。五套主题必须逐套核对，尤其是深色主题下的浮层——阴影在深色背景上几乎不可见，需要靠表面色差补层级。

**令牌不是设计规范文档，是编译期的约束。** 先有约束，改组件才是一次性投入；没有约束，改组件就是把债摊到每个文件里。

## 方法论二：用户感知最强的先做，但结构改动要一次做完

计划表上的顺序是按模块排的：基座、骨架、消息、动效、空态。实际投放时把「消息与富文本」提到了骨架之前。

原因很直接：对话框是用户停留最久的地方，气泡、代码块、表格的质感提升，用户当天就能感觉到；而骨架屏和留白，用户感受到的是「不那么挤」，说不出具体变化。

但有个前提——结构和样式不能分两次动。骨架（列宽、可收起的侧栏）和消息（气泡宽度、hover 操作条定位）共用同一套空间假设。先做骨架再改消息，气泡的最大宽度要重算一遍；先做消息再做骨架，代码块的语言栏位置又要挪。所以两者放在同一批里看，一次到位。

这一批里最典型的三个改动都不增加功能：用户消息改成右对齐胶囊、代码块加上语言栏和复制按钮（复制成功反馈 1.5 秒）、表格加斑马纹并让首列在横向滚动时粘住。它们解决的都是「读长内容时不断丢失位置」，用户不会说出原理，但会立刻觉得顺。

**排序看用户感知，合并看依赖关系。** 这两件事不冲突，冲突的是「只按计划表顺序执行」。

## 方法论三：行数门禁要在动工前算

仓库有一条硬门禁：单文件不超过 300 行，260 行开始预警。聊天页最核心的三个文件——顶栏、消息项、页面容器——都在 250 行上下。

这意味着「顺手加一个 hover 操作条」不是加十几行，而是先把文件拆开。消息项里的代码块、工具卡、操作条各自独立成子组件，页面容器里的阶段条在窄屏下换成独立的紧凑组件。

如果动工前不算这笔账，就会改到一半发现文件 304 行，然后被迫在「删注释凑行数」和「临时抽组件」之间选一个——前者是自欺，后者会把一次样式改动变成一次结构重构，回归范围凭空翻倍。

**行数门禁的价值不在拦住提交，而在逼你提前设计边界。** 预警线是给动工前看的，不是给提交前看的。

## 方法论四：没有动画库时，用纯 CSS 关键帧，而不是偷偷加依赖

这一轮所有动效都是 CSS：弹层从 0.98 缩放入场、毛玻璃遮罩淡入、toast 从下方 8px 浮起、消息位移 4px 加透明度、流式光标呼吸。

没有引入动画库。理由不是「CSS 更高级」，而是这笔依赖不划算：一个动画库会带来自己的运行时、自己的调度、自己的一套 API，而这里需要的只是「进入时动一下」。用 React 状态去驱动这些动画，还会让消息列表在流式渲染时多出一层重渲染的风险。

代价是动画能力有限：没有编排、没有弹簧、没有退出动画的统一管理。但这一轮的动效全是 200ms 内的入场，不需要这些。

需要克制的地方反而在细节：动画时长必须来自令牌，不能这个组件 150ms、那个 200ms；遮罩用 `backdrop-blur` 而不是再加一层半透明 div。**加依赖是显性成本，散落的魔法数字是隐性成本，后者更贵。**

同一套思路也用在降级上。`prefers-reduced-motion` 没有在每个组件里各写一遍，而是一条 `*` 规则把动画和过渡压到 0.01ms，再对「压扁之后会停在错误形态」的元素单独覆盖。规则写在能被穷举的地方，例外写在需要解释的地方。这比「改了二十个组件，漏了第二十一个」可靠得多。

## 方法论五：测试里「允许 undefined」，等于没测

开发态的窗口图标一直回落到 Electron 默认图标，测试却全绿。

原因是断言写成了「有值就检查后缀，没值就跳过」。开发态恰好没值，整段断言被跳过。测试看起来覆盖了图标解析，实际上只覆盖了「不崩溃」。

改成硬断言之后，规则变成：图标文件存在时，解析结果必须精确等于那个绝对路径；只有文件确实不存在（精简产物）才允许为空，而且这个例外由文件系统判断，不由解析结果判断。

**任何带条件分支的断言，都要问一句：分支没进的时候，我到底验证了什么。** 如果答案是「什么都没验证」，那就不是测试，是注释。

## 方法论六：验不了的，写进遗留项，不要假装验过

方案里定了三条硬指标：1280 / 1440 / 1920 三档截图无溢出、无控件错位；五套主题明暗全检；对比度不低于 4.5:1。

实际执行时，本机端口被占用，前端起不来，截图巡检没法做。

处理方式不是「看着差不多就行」，而是在方案和发行说明里明确写成遗留项：哪一档没验、为什么没验、下次怎么补。单测能证明行为，证明不了「1280 下按钮有没有换行」——这类只能靠眼睛的验收，缺了就是缺了。

**验收清单上最危险的不是红叉，是没跑却打了勾。** 把它写成遗留项，团队和用户都知道边界在哪；假装验过，问题会在用户机器上替你验收。

## 方法论七：给已有行为补入口，不改行为

桌宠活着时关主窗只是隐藏，应用还在后台跑。看起来该顺手把「关窗」统一成「最小化到托盘」，但那会改变用户已经形成的预期：点叉就是退出。

这一轮只补托盘：可见的图标、按实时状态重建的菜单、一次驻留提示、一个明确的「彻底退出」。关窗语义一个字没改。

**补入口和改行为，成本差一个数量级。** 改行为要重新解释所有相关路径（关窗、退出、重启、桌宠恢复），补入口只需要把已有状态暴露出来。先用最低成本消除「不知道退没退」的焦虑，再谈要不要统一策略。

## 明确不做的事

- 不引入新的 UI 框架或动画库，沿用 Radix + Tailwind；
- 不改业务数据流，不动流式渲染的 memo 策略；
- 不为动效牺牲性能，消息列表的渲染路径保持原样；
- 不做数据库迁移，新令牌只是 CSS 变量；
- 不做可拖拽分栏、不做按页面自定义断点。

每条 Non-Goal 都对应一个诱惑：既然有令牌了，顺手换套组件库；既然做动效了，顺手加个弹簧；既然改布局了，顺手把分栏做成可拖拽。单看都合理，叠在一起就会把一次质感升级拖成一次前端重构。

## 剩下的债

做完不等于做完所有页面。这一轮把聊天页和设置页迁到了新令牌上，知识库、任务页只改了容器与列表，业务逻辑一行没动。更早的页面里仍然散落着旧的阴影与时长写法。

这是有意的：一次全站迁移会把回归面铺到整个应用，而收益是「一致」，不是「可用」。先把高频路径做对，剩下的按页面被访问的频率排队。

另一笔债是视觉回归没有基线。仓库目前没有截图对比工具，每次改样式都靠人眼。这一轮结束时留下的三档截图巡检待办，本质上是在替这套缺失的基建还利息。下一轮如果还要动布局，应该先补基线，再改样式。

## 什么算做完

这一轮没有新增业务能力，衡量标准只有四条：

- 任意界面最多三级表面，层级靠令牌而不是边框；
- 正文有明确的最大宽度，1280 不挤、1920 不散；
- 所有动效都能被系统设置一次性关掉，且关掉之后不缺信息；
- 后台还在跑的时候，用户看得见、退得掉。

类型检查、Lint、行数门禁、目录预算、循环依赖检查全部通过，126 例前端单测与 6 例托盘菜单单测通过，中英文案对等。

数字只能说明「没有弄坏」，不能说明「变好看了」。后者要等三档截图补上，才算真正验收。

## 最后一句话

质感不是加更多效果，而是让默认值可解释：为什么正文是 768px，为什么回到底部是 200px，为什么收起是 48px 而不是 0，为什么动画是 120/180/240 三档。

每一个数字背后都有一个用户动作。说不清动作的数字，就只是审美偏好；说得清，才有资格写成令牌，交给下一个人复用。
