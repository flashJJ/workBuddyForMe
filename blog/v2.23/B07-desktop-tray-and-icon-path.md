# 关掉窗口之后：桌面托盘与一个图标路径 bug

用户点了窗口右上角的叉，界面消失了。这时他面对两个问题：应用到底退没退？如果没退，怎么让它退？

没有托盘之前，这个问题只能去任务管理器回答。桌宠还活着的时候，关闭主窗只是隐藏，进程继续在后台跑——这是有意的设计，桌宠还要留在桌面上。但任务栏没有入口，用户会以为已经退出，直到发现麦克风提示还亮着。

我们的桌面 AI 应用是本地优先、单人开发的私人助手，桌面壳用 Electron。这一轮补的不是新能力，是让已有状态变得可见、可退出。

## 先不动的部分：关窗语义

关窗其实有两种语义：没有桌宠时直接退出，有桌宠时隐藏主窗。

最容易想到的改法是「一律最小化到托盘」，把两种语义统一。但这会把「点叉即退出」变成「点叉后偷偷活着」，用户更没底。真正缺的是入口，不是策略。

所以这一轮只做两件事：常驻一个托盘图标，提供「彻底退出」。关窗行为保持原样。

## 菜单每次弹出都重建

托盘用 Electron 自带的 `Tray`，菜单用 `Menu.buildFromTemplate`。关键决定是：不在启动时构建一次菜单然后复用，而是每次弹出前按实时状态重建。

```ts
tray.on('click', () => popMenu());
tray.on('right-click', () => popMenu());

function popMenu() {
  const menu = Menu.buildFromTemplate(buildTrayMenuTemplate(readState(), actions));
  tray.popUpContextMenu(menu);
}
```

状态只有三个字段：主窗是否可见、桌宠是否开启、舞台是否就绪。菜单据此生成：

| 菜单项 | 规则 |
|---|---|
| 显示主窗口 | 主窗不可见时可用 |
| 隐藏主窗口 | 主窗可见时可用 |
| 桌宠 | 勾选项，读实时状态 |
| 打开全屏舞台… | 仅在舞台管理器就绪时出现 |
| 彻底退出 | 调用 `app.quit()`，复用既有退出清理链 |

如果启动时只建一次菜单、之后手动翻 `checked`，状态一定会过期：用户从主窗里关掉桌宠，托盘的勾还亮着；舞台还没初始化，菜单里却有一个点了没反应的入口。重建一次菜单的成本可以忽略，换来的是永远不会显示旧状态。

菜单模板写成纯函数（状态进、模板出），就能在单测里直接断言「主窗可见时显示项禁用」「桌宠项是勾选类型」「舞台不可用时入口不出现」，不需要真的创建一个托盘。

左键也弹菜单，是照着用户的第一反应做的：点图标，找退出。不区分单击双击，也不做「左键唤回、右键菜单」那套约定，减少一次学习成本。

## 驻留提示只弹一次

主窗因为桌宠驻留而隐藏时，用户需要一个明确信号。做法是监听窗口的 `hide` 事件，满足条件时弹一次气泡：

- 平台是 Windows（`displayBalloon` 是 Windows 的托盘能力）；
- 桌宠确实开着——其余情况关窗就是退出，不需要解释；
- 本次运行还没弹过。

第三个条件由一个布尔字段守住，不持久化。下次启动再提示一次是合理的，用户可能换了使用场景。反复弹才是打扰。

托盘 tooltip 同步跟着状态走：桌宠开着时标注「桌宠运行中」，收起时回到应用名。鼠标悬停就能确认后台在跑什么。

## 失败要降级，不能拖垮启动

托盘是增强能力，不是启动依赖。两处可能失败：

一是图标文件不存在（精简产物、CI 环境）。解析不到就直接返回 false，不创建托盘。

二是 `new Tray()` 抛错。无桌面会话、远程终端、权限受限的环境都可能出现。这里必须 `try/catch`，否则一个装饰性图标会让整个应用起不来。

```ts
start(): boolean {
  if (this.tray) return true;              // 幂等
  const icon = resolveWindowIcon(app.isPackaged);
  if (!icon) return false;
  try {
    this.tray = this.createTray(icon);
  } catch {
    return false;                          // 只记录，不抛出
  }
  ...
}
```

返回值是布尔而不是抛异常，调用方也就不需要包一层 try。启动链只关心「有没有托盘」，不关心为什么没有。

## 图标为什么一直是默认的

托盘做完之后发现另一个问题：开发态和端到端测试里的窗口图标，一直是 Electron 的默认图标；打包后的安装版却正常。

先取证：把 `resolveWindowIcon` 的候选路径打印出来，开发态解析到的是应用目录上一层的 `build/icon.ico`——那个目录里根本没有 `icon.ico`，文件在应用目录下面。

根因是 `__dirname` 的布局差异。源码直接运行时，入口在 `src/main`，向上两级正好是应用根目录；但构建产物是 `dist/index.js`，`__dirname` 变成了 `dist`，向上两级就越过应用目录，落到了一个不存在的位置。旧逻辑把「源码布局」当成了唯一事实。

修复不是改层数，而是同时接受两种布局：先试 `../build`，再试 `../../build`，取第一个真实存在的文件。打包态仍然走 `resources` 目录，逻辑不变。

## 测试为什么没拦住

更值得复盘的是测试。

原来的断言大致是：解析结果有值，就断言它以 `icon.ico` 结尾；没有值，就跳过。开发态恰好是「没有值」，于是断言被整段跳过，测试永远是绿的。

这不是断言写错，是断言给了被测代码一个逃生门。**只要测试允许 undefined，它就永远发现不了「本该有值却没有」。**

修复后改成硬断言：图标文件在仓库里存在时，解析结果必须精确等于那个绝对路径，不允许后缀匹配这种宽松比较。唯一保留的例外写得很明确——CI 的精简产物里确实没有图标文件，此时才允许 undefined；而且这个例外由「文件是否存在」判定，不是由「解析结果是否为空」判定。

打包态另有一条：注入一个假的 `resourcesPath`，断言候选路径指向 `resources/icon.ico`。文件当然不存在，但路径规则被钉死了。

教训可以浓缩成一句：**回归测试要先能红。** 写完新断言，回到旧实现上跑一遍，它必须失败；否则你写的是文档，不是测试。

## 验证与遗留

托盘菜单 6 个单测用例通过，覆盖显示/隐藏互斥、桌宠勾选切换、舞台入口可选、退出回调；图标解析回归测试通过；类型检查、Lint、行数门禁全绿。

托盘的真实点击没有做成自动化——单测里注入的是假托盘实例，覆盖的是菜单模板与状态流转。真实 Windows 会话下的气泡、图标缩放、DPI 表现，仍属于人工验收范围。
