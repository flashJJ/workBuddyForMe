# 复盘：事件触发的边界与下一站

这一版把「事件 → 运行」接通，但刻意留了不少边界。复盘一下哪些取舍是值得的，哪些是下一版应该补的。

## 一、做对了什么

**复用而不是另起一套。** 单飞、状态回写、无人值守门控全部沿用既有能力，新增代码集中在「触发器配置 + 事件源 → 一次运行」这一层。结果是：定时任务与事件任务的行为一致，用户不需要学两套语义。

**安全默认值。** Webhook 只允许回环 Host、Secret 只存哈希、body 有上限、写工具默认拒绝。这些限制在原型阶段看似麻烦，但避免了「先上线再补安全」的返工。

**观测字段足够用。** `last_fired_at / last_run_id / last_status` 三个字段就能回答「上次什么时候触发、有没有跑、为什么没跑」。没有引入复杂的指标系统。

## 二、风险与不足

**文件监听依赖平台。** Linux 下递归监听降级为根目录，用户可能误以为子目录也会触发。状态里虽然有提示，但 UI 还没有把平台限制显式画出来。

**幂等只在内存。** 应用重启后同一 `Idempotency-Key` 会再次创建运行。对本机脚本场景可接受，但不适合作为跨重启的精确一次语义。

**事件触发不重试。** 流程创建失败（例如未发布）只记录 `error`，不会自动重放。用户需要自己重新投递事件。

**agent 内部工具仍是独立安全面。** 流程级无人值守门能拦住 tool 节点，但 agent 节点内部的写工具走协作运行时自己的确认流程。要完全统一，需要把 trigger 语义继续下沉。

## 三、下一站

按价值排序：

1. **HMAC 签名与 Secret 轮换**：为未来跨设备/公网场景做准备；
2. **事件重试与死信**：至少支持可配置的有限重试；
3. **可视化字段映射与条件过滤**：让事件源不必严格适配流程入参；
4. **多触发器独立变量**：同一事件源按内容路由到不同流程；
5. **统一观测面板**：把定时、Webhook、文件、端点调用放在同一视图里看。

## 四、工程收口

- 迁移 v055 纯加法，旧数据零影响；
- 新增单测覆盖契约、迁移、仓储、服务、监听器与路由；
- `pnpm check` 与 `pnpm verify:local` 全绿；
- 运行中心补齐 `schedule` 的历史文案缺口。

事件驱动不是终点，而是把「流程」从人手里的工具，变成能对世界做出反应的组件。下一步要做的，是让这种反应更可控、更可观测。
