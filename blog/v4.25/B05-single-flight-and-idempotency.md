# 单飞与幂等：事件风暴下怎么不重复跑

定时触发是「到点一次」，事件触发则可能在短时间内来很多次：批处理脚本连发 20 个回调、解压目录一次落下几百个文件。如果没有收敛策略，流程会被瞬间打爆。

## 一、单飞：同流程只允许一个在途运行

判断直接复用运行仓储：

```sql
SELECT 1 FROM workflow_runs
WHERE workflow_id = ? AND status IN ('queued','running','waiting_human')
LIMIT 1
```

存在在途运行时：

- Webhook 返回 `409 flow_busy`；
- 文件事件记录 `skipped_busy`，不创建运行。

这里选择「跳过」而不是「排队」：事件往往有时效性，堆积一批过期事件再依次执行，反而放大副作用。需要补跑时，用户可以手动触发或等下一次事件。

## 二、幂等键：调用方主动去重

Webhook 支持可选的 `Idempotency-Key` 请求头：

- 长度 1–128；
- 每个触发器一份进程内 Map，最多 500 条；
- TTL 10 分钟，过期懒清理；
- 命中直接返回 `200 { duplicate: true }`，不创建运行。

顺序很重要：**先查幂等，再查单飞**。否则第一次请求创建运行后，第二次带同一个键会被误判为 busy，调用方无法区分「重复投递」与「真的忙」。

## 三、为什么不做持久幂等

持久化幂等需要一张额外的表、过期清理与唯一索引，换来的收益是「应用重启后仍能识别重复投递」。本地应用的事件源通常是本机脚本或单进程工具，重启窗口内的重复投递概率很低。第一版用内存 Map 控制在可接受范围，未来有跨重启需求再迁移。

## 四、状态回写

每次触发都会更新触发器的观测字段：

| 字段 | 含义 |
|---|---|
| `last_fired_at` | 最近一次事件到达时间 |
| `last_run_id` | 最近创建的运行 id |
| `last_status` | created / skipped_busy / error / disabled |

这样用户在编辑器里能看到「上次触发是什么时候、是否被跳过」，而不是只能翻运行记录。

## 五、并发边界

单飞检查与创建运行之间不是数据库事务，但本地应用是单进程、单队列，事件处理同步执行，不存在两个 tick 同时通过检查的窗口。多进程/多实例互斥明确列为非目标，避免为不存在的部署形态增加复杂度。
