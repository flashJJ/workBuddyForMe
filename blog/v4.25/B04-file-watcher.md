# 文件监听：递归、防抖与平台差异

文件监听看起来简单，真正落地时会遇到三个问题：平台差异、事件风暴、以及「应用重启后监听还在不在」。

## 一、平台差异

Node 的 `fs.watch` 在 Windows 与 macOS 上支持 `{ recursive: true }`，Linux 上不支持。这一版的处理是：

- Windows / macOS：按配置递归监听；
- 其他平台：降级为根目录监听，并把限制写入触发器状态，避免用户以为子目录也会触发。

监听能力通过一个可注入的 adapter 隔离：

```ts
interface FileWatchAdapter {
  watch(path, options, listener): { close(): void };
  stat(path): { isDirectory(): boolean } | null;
}
```

生产环境包装 `node:fs`，单测注入假实现。这样文件监听的核心逻辑不依赖真实磁盘，也不会在测试里留下句柄。

## 二、事件过滤

不是所有文件变化都值得跑一次流程：

- 只处理 `add` / `change`；
- 扩展名必须命中白名单，统一小写、去点；
- 忽略 `.git`、`node_modules`、`dist`、`.next`；
- 忽略点文件、`~$` 临时文件、`.tmp` / `.swp`。

这些规则先于防抖执行，避免编辑器保存一次产生一串无意义事件。

## 三、防抖与去重

同一路径在 800ms 内的事件合并为一次；触发后 2 秒内同路径的重复事件丢弃。效果是：

- 编辑器连续保存只跑一次；
- 解压一批文件时，每个文件各自触发一次，但不会因为元数据抖动重复触发；
- 每触发器同时只处理一次，繁忙时直接丢弃并记录 `skipped_busy`，不排队堆积。

## 四、启动重建与释放

监听句柄不能跨进程存活，所以服务启动时 `reconcile()`：

1. 读取所有启用中的文件触发器；
2. 关闭已删除、禁用或配置变化的监听；
3. 为缺失项建立新监听。

触发器增删改后也会立即 reconcile；流程删除时同样释放句柄。`dispose()` 幂等，E2E 重置数据前会先调用它。

## 五、为什么不用 chokidar

引入第三方监听库会带来额外依赖与打包体积。当前需求（目录、扩展名、防抖）用 `fs.watch` 足够，且更容易控制递归与释放行为。未来如果需要重命名跟踪或跨平台一致性，再评估替换。

## 六、边界

这一版不跟踪文件内容 diff、不处理重命名、不做目录规则继承。监听的目标是「有新文件/文件变了就触发」，不是做文件索引器。
