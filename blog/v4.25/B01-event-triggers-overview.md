# 会来事：让外部事件叫醒流程

一个工作流引擎成熟的标志，不是能画多复杂的图，而是**不需要人记得去点运行**。

在此之前，流程的开始方式已经覆盖了手动、对话、HTTP/MCP 同步调用和 cron 定时。剩下的空白很明确：外部世界发生了某件事，流程应该自己开工。

- 下载目录多了一个 PDF，自动提取要点并归档；
- 笔记目录里的 Markdown 被修改，自动重建摘要；
- 另一个本地工具跑完，回调一个 URL 继续后续流程；
- 自动化脚本把一个 JSON 放进约定目录，触发整理。

这一版把这类需求收敛成两种触发器：**Webhook** 与**本地文件监听**。

## 一、为什么不直接复用现有端点

同步端点解决的是「调用方等着结果」；事件触发解决的是「事件来了就排队跑」。两者在语义上不同：

| 维度 | 同步端点 | 事件触发 |
|---|---|---|
| 调用方 | 等待响应 | 只关心是否接收 |
| 并发策略 | 按请求执行 | 同流程单飞、繁忙跳过 |
| 失败处理 | 返回错误 | 记录状态，不阻塞事件源 |
| 配置 | 一流程一端点 | 一流程多触发器 |

如果硬把事件语义塞进端点，会出现「一个流程只能有一套密钥」「无法文件监听」「无法多来源区分」的问题。所以这一版新增独立表与独立服务，只复用端点的回环 Host 守卫、限流与错误包络。

## 二、四条设计原则

1. **复用优先**：单飞、状态观测、无人值守门控沿用前几版，不新建第二套调度。
2. **默认关闭**：触发器必须显式创建并启用；没配置时行为与之前完全一致。
3. **本机可达**：Webhook 只接受 `127.0.0.1` / `localhost`，不提供公网暴露。
4. **事件不等于权限**：事件触发是非交互运行，写/危险工具默认拒绝。

## 三、数据模型

新增一张纯加法表：

```sql
CREATE TABLE workflow_triggers (
  id TEXT PRIMARY KEY,
  workflow_id TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,           -- webhook | file
  enabled INTEGER NOT NULL DEFAULT 1,
  config_json TEXT NOT NULL,
  secret_hash TEXT,
  last_fired_at TEXT,
  last_run_id TEXT,
  last_status TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

配置、密钥哈希与最近一次触发状态都在库里。进程重启后不需要用户重新配置，文件监听也能按启用项重建。

## 四、运行语义

事件触发创建运行时会写入新的 trigger 值：

- `webhook`：外部 POST 触发；
- `file`：本地文件变化触发。

两者与 `schedule` 一样，属于无人值守运行：不弹窗等待人工确认，写/危险工具默认拒绝。这样即使事件源被伪造，也不会在无人看守时执行高危操作。

## 五、边界

这一版刻意不做公网暴露、HMAC 签名、可视化字段映射、文件内容 diff 与事件重试队列。先把「事件能可靠地变成一次运行」做扎实，再在后续版本扩展安全与映射能力。
