# 单飞与补偿：错过只补一次

调度器有两个容易被忽略的策略问题：

1. 上一次还没跑完，这一次又到了，怎么办？
2. 应用关了三天，错过的执行怎么补？

这两个问题没有标准答案，只有适合场景的取舍。这一版的选择是：**单飞跳过，错过只补一次**。

## 一、三种常见策略

面对「上一次还在跑」的情况，通常有三种做法：

| 策略 | 行为 | 代价 |
|---|---|---|
| 排队 | 本次入队，等上一次结束再跑 | 延迟累积，可能雪崩 |
| 并发 | 同时跑两份 | 同一流程并发，副作用难解释 |
| 跳过 | 本次不跑，记录原因 | 丢掉一个周期 |

定时任务的语义通常是「周期性检查」，而不是「每一次都必须执行」。如果一次执行花了二十分钟，而周期是十分钟，那说明这个周期本身设置得不合理——此时排队只会让积压越来越长。

所以选择跳过，并把它记录下来。

## 二、单飞怎么判断

「在途」的定义沿用运行状态：

```text
queued / running / waiting_human
```

这三种状态都表示「这个流程已经有一份在执行或等待中」。调度器在创建新运行前查一次：

```text
同流程存在在途运行 → 记录 skipped_busy，不创建
```

不排队、不并发、不取消旧的。用户看到的是「本次未执行，因为上一次还在跑」，而不是「莫名其妙有两条时间线」。

## 三、为什么不并发

技术上并发是可行的：上一版已经支持同一个流程内的并行节点，创建两次运行也没有硬性障碍。

但定时并发会带来三个解释不了的问题：

- 两次运行会写同一份业务数据，谁覆盖谁取决于完成顺序；
- 同一个流程的两条运行记录在 UI 上并排出现，用户无法判断哪条是「这次」；
- 如果流程里有写操作，重复执行的副作用无法用「周期到了」来解释。

定时触发的目标是「按计划检查」，不是「必须同时开工」。单飞是对这个目标的忠实表达。

## 四、错过的定义

什么算「错过」？

- 应用关闭期间，`next_run_at` 到期但没有人扫描；
- 应用启动后，第一个 tick 扫描到这条过期记录。

这时调度器不会去数「到底错过了几次」，而是直接把它当作一次到期处理：

```text
now = 启动时刻
补跑一次 → next = nextCronTime(spec, now)
```

例如配置是「每小时整点」，应用从 10:30 关到 14:20，期间错过了 11、12、13、14 四个整点。启动后只会在 14:20 补跑一次，然后下次时间是 15:00。

## 五、为什么不做逐次补跑

逐次补跑听起来更「正确」，但对这个场景有三个副作用：

1. 补跑会连续创建多条运行，而单飞策略会让后面的全部跳过，等于制造一堆 `skipped_busy`；
2. 如果流程有写操作，连续补跑会重复写同一批数据；
3. 用户真正需要的是「现在补上最新状态」，而不是「把过去四小时的检查各跑一遍」。

所以「只补一次」不是偷懒，而是把「补偿」的语义收敛到「恢复到一个最新状态」。

## 六、补偿与幂等

补跑本身会不会重复？

不会，因为补跑走的还是同一条认领逻辑：先推进 `next_run_at`，再创建运行。启动时只有一个 tick 在跑，认领会成功一次；后续 tick 看到的时间已经在未来，不会再触发。

这也是为什么调度器要有「一次 tick 正在运行」的保护：即使定时器与启动补跑同时触发，第二个 tick 会直接返回。

## 七、用户怎么知道跳过了

`last_status` 会记录 `skipped_busy`，UI 在定时对话框里展示：

```text
上次运行：2026-11-23 09:00:00 · 在途跳过
```

这条信息比日志更直接：用户不需要理解调度器，只需要知道「这次为什么没跑」。

## 八、边界与未来

这一版的策略有明显的适用边界：

- 周期较短、执行较快的流程，体验最好；
- 周期短于执行时间的流程，会频繁出现跳过，需要用户调整 cron；
- 需要「每次都必须执行」的场景，应该排队而不是定时——那是任务队列的语义，不是调度的语义。

未来的扩展方向可以是「允许配置跳过策略」：跳过、排队、并发三选一。但在没有真实需求之前，固定为跳过更可控。
