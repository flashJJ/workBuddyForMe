# 把 cron 藏进对话框：定时配置的最小 UI

后端做完之后，剩下的问题是：怎么让一个不写代码的用户，配出一个正确的定时。

cron 表达式对大多数人来说是劝退的。这一版的策略不是做一个可视化编排器，而是「一个输入框 + 足够的即时反馈」。

## 一、入口放在哪

流程编辑器顶部已经有一排按钮：保存、发布、对外服务、运行。

定时被放在「对外服务」旁边，图标是日历时钟，只有已发布流程可点。理由：

- 定时只使用生产版本，草稿配置没有意义；
- 与「对外服务」同属「让流程在编辑器之外运行」的能力，放在一起符合心智；
- 未发布时按钮置灰，并用 title 说明原因，而不是点了才报错。

## 二、对话框里放什么

最小但完整的信息：

```text
cron 表达式输入框
启用开关
下次运行时间
上次运行时间与状态
[删除] [立即运行] [保存]
```

没有的东西也很重要：

- 没有「每定时时区」；
- 没有「错过补偿策略」；
- 没有「并发策略」；
- 没有「多个定时」的列表。

这些都是有意省略的：第一版只暴露已经定死的语义，避免用户配出一个系统解释不了的状态。

## 三、输入框的即时反馈

保存时服务端会做两件事：

1. 解析 cron；
2. 计算下次执行时间。

任何一步失败，都会返回可读的错误，UI 直接展示。例如：

```text
分钟字段超出范围 0–59：60
未来 5 年内没有匹配的执行时间
```

这比「保存失败」有用得多。用户改一个字符就能修正，而不是去查 cron 语法。

## 四、为什么要显示下次时间

「下次运行时间」是这个小 UI 里最重要的一个字段。

原因很简单：cron 表达式是对是错，看下次时间最直观。

- 用户写 `0 9 * * *`，看到「下次：明天 09:00」——对了；
- 用户写 `0 9 * * 1`，看到「下次：下周一 09:00」——也对了；
- 用户写 `0 9 1 * *`，看到「下次：下月 1 日 09:00」——如果他想要的是每天，立刻能发现。

下次时间由服务端计算并返回，客户端不做第二套解析。这样「保存成功」与「下次时间」永远一致。

## 五、立即运行为什么不改变下次时间

对话框里有一个「立即运行」按钮。它的语义是「现在手动跑一次」，而不是「把定时提前」。

所以：

- 点击后创建一次 `trigger=schedule` 的运行；
- `next_run_at` 不变；
- 如果同流程有在途运行，返回 `busy`，提示稍后再试。

如果把「立即运行」实现成「触发一次定时」，用户点两次就会把下次时间推到两个周期之后，行为很难解释。

## 六、删除要二次确认

删除定时是一个不可逆动作（至少对普通用户来说）。对话框里用内联二次确认：

```text
第一次点击：按钮文案变成「删除后不再自动运行，确定删除？」
第二次点击：执行删除
```

不用系统弹窗，是因为 Electron 下原生确认框会抢走键盘焦点，体验很差。内联确认更轻，也更容易做样式。

## 七、状态怎么表达

上次运行结果有四种：

| 状态 | 文案 |
|---|---|
| created | 已触发 |
| skipped_busy | 在途跳过 |
| error | 触发失败 |
| disabled | 已停用 |

这四种状态覆盖了用户需要知道的全部信息：跑了、没跑因为忙、没跑因为配置有问题、被停用了。

不需要在 UI 里解释「为什么 error」——运行中心能看到具体错误。对话框只负责告诉用户「这个定时最近一次是什么结果」。

## 八、没有做的部分

- 没有 cron 可视化编辑器：5 字段的可视化编辑器成本高，收益有限；
- 没有常用表达式模板：第一版先观察真实使用，再决定要不要加；
- 没有多定时列表：一个流程一条，等真有需求再扩展。

最小 UI 的价值不是「少做」，而是「把已经想清楚的语义，用最少的界面表达出来」。下一篇是复盘。
