# 会守时：让流程自己开始

前两版分别解决了「跑得动」和「摔了能爬起来」。但流程要开始，仍然需要有人或外部系统先动手：点一下试运行、在对话里问一句、或者由另一个系统发 HTTP 请求。

这一版补上最后一块：让流程按时间自己开始。

## 一、问题：所有触发都依赖外部

一个本地优先的私人助手，最典型的自动化需求往往和时间有关：

- 每天早上把资讯整理成一份摘要；
- 每周五下班前生成周报草稿；
- 每小时检查一次某个目录有没有新文件；
- 每晚把当天的对话整理进记忆。

这些事有一个共同点：用户不想每次都记得点一下。

在改造之前，流程只有三种开始方式：

| 触发方式 | 前提 |
|---|---|
| 手动试运行 | 打开编辑器点运行 |
| 对话调用 | 用户提问，助手决定调用 |
| HTTP / MCP | 外部系统主动请求 |

它们都要求「先有人」。定时触发要解决的，就是把这层依赖拿掉。

## 二、为什么不能只写一个 setInterval

最直觉的做法是在内存里存一份「流程 + 间隔」，用定时器触发。原型阶段这没问题，但一旦应用会重启，就会暴露三个问题：

1. 进程退出后定时器消失，下次打开应用时「错过的时间点」没人处理；
2. 配置不落库，重启后用户要重新配一遍；
3. 上一次运行还没结束，下一次又到了，是排队、跳过还是并发，没有定义。

所以这一版的第一原则是：**配置与下次执行时间落库，内存里只跑一个扫描器**。

## 三、范围：先只做 cron

触发方式有很多种：cron、webhook、文件监听、事件订阅。这一版只做 cron。

原因很实际：

- cron 是最通用的「按时间」表达；
- webhook 需要处理鉴权、重放与公网暴露，属于另一条安全线；
- 文件监听在不同平台的行为差异大，需要单独设计去抖与批量。

把 cron 做扎实，比一次铺开四种触发更有价值。范围定得窄，语义才能写得清楚。

## 四、四条必须写死的规则

在写代码之前，先把几个容易含糊的点定下来：

### 1. 一个流程一条定时

第一版不做「一个流程多个定时」。多定时会带来命名、优先级与冲突处理，收益不大，复杂度不低。

### 2. 系统本地时区

不提供每定时时区。对一个单机桌面应用来说，用户就在本地，系统时区就是他的时区。引入时区库只会增加解释成本。

### 3. 错过只补一次

应用关了一整天，第二天打开时，不应该把错过的十几次全部补跑一遍。只补一次，下次时间从当前时刻重算。

### 4. 单飞，不排队

上一次还没跑完，这一次直接跳过并记录原因。排队会让延迟累积，并发会让「同一个流程同时跑两份」变得难以解释。

## 五、调度循环长什么样

```text
每 30 秒：
  查出 enabled 且 next_run_at <= now 的调度
  对每条：
    以旧 next_run_at 为条件，推进到下一次
    推进成功才继续（原子认领）
    检查流程已发布
    检查没有在途运行
    创建 trigger=schedule 的运行
    记录结果
```

启动时立即执行一次，用来处理应用关闭期间到期的配置。

这个循环很短，但每一行都对应一个前面定过的规则：落库、原子认领、单飞、补偿。

## 六、无人值守意味着什么

定时触发没有人在场，所以它天然属于「无人值守」。这意味着：

- 写操作与危险工具默认拒绝；
- 人工审核节点不会挂起等待，而是按拒绝处理；
- 需要授权的流程，要么改成只读，要么通过现有授权机制预先放行。

这不是限制，而是保护：一个凌晨三点自动运行、又没人确认的写操作，风险远大于收益。

## 七、这一版之后

流程终于可以「自己开始」：

- 配置保存在数据库里，重启不丢；
- 到期自动触发，错过补一次；
- 上一个没跑完就跳过，不排队、不并发；
- 触发结果可查：下次时间、上次时间、上次状态。
