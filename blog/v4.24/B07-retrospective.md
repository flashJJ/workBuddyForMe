# 复盘：定时任务最容易踩的五个坑

定时触发看起来是「到点创建一次运行」，真正做下来，问题集中在几个时间窗口与状态边界上。这一版踩过的五个坑，记下来。

## 一、只存 cron 会吞掉错过的那一次

第一版设计里，表里只存 cron 表达式，下次时间每次启动时现算。

看起来更「干净」——cron 是唯一事实源，下次时间只是派生值。但它带来一个隐蔽问题：应用在 9:00 关闭、9:05 打开，配置是「每天 9:00」，启动时计算出的下次时间是「明天 9:00」。今天那次被静默吞掉，用户永远不会知道。

修复是存 `next_run_at`。它不是缓存，而是状态：记录「调度器承诺的下一次触发时刻」。启动时看到它已过期，才知道「有一次该跑没跑」。

## 二、先创建后推进，会重复触发

最初的 tick 逻辑是：

```text
查到到期 → 创建运行 → 更新 next_run_at
```

崩溃或并发时，如果进程在「创建运行」之后、「更新 next_run_at」之前挂掉，下一次 tick 会再创建一次。

改成先推进、后创建：

```text
查到到期 → 条件更新 next_run_at → 成功才创建运行
```

代价是极端情况下「时间推进了但没跑」，需要用户手动补。但这个方向的错误是可见的、可恢复的；反过来则是静默重复执行，危险得多。

异步系统里，两条写入无法做到真正的原子，只能选择「错误的方向」。

## 三、启动补跑与定时 tick 会打架

调度器启动时执行一次补跑，同时挂上 30 秒的定时器。如果补跑还没结束，定时器已经触发，就会出现两个 tick 同时扫描。

两条防线：

1. 一个进程内只允许一个 tick 正在执行，第二个直接返回；
2. 认领用条件更新，即使真的并发，也只有一条能推进成功。

第一道是效率，第二道才是正确性。只做第一道不够——将来如果真的多个实例，第一道就不存在了。

## 四、失败后回滚 next_run_at 会形成日志风暴

一个自然的想法是：创建运行失败（比如流程未发布），就把 `next_run_at` 退回去，下次再试。

但在「流程被取消发布」这种持续状态下，每个 tick 都会重试、失败、再退回，形成无限循环与日志风暴。

这一版的规则是：**失败也推进时间**，只记录 `last_status = error`。让它在下一个周期再试，而不是同一个周期里反复撞墙。

对用户来说，看到的是「上次触发失败」，而不是日志被刷屏。

## 五、把「跳过」当成成功会误导

单飞跳过的实现一开始只写了日志，没有落状态。结果 UI 上「上次运行」还停留在几天前，用户以为定时没生效。

修复是增加 `skipped_busy` 状态，并让它出现在对话框里：

```text
上次运行：2026-11-23 09:00:00 · 在途跳过
```

「跳过」不是成功，也不是失败，而是一种需要被看见的结果。状态设计里如果没有它的位置，用户就只能猜。

## 六、方法论

1. **状态优先于派生值**：下次执行时间要落库，不能只存表达式；
2. **先认领后副作用**：有副作用的动作放在幂等更新之后；
3. **失败也前进**：持续失败不能让调度器陷入重试循环；
4. **跳过要留痕**：跳过是一种结果，不是沉默；
5. **单飞优先**：定时任务默认不排队、不并发，除非有真实需求；
6. **无人值守要保守**：没人在场时，写操作默认拒绝。

## 七、遗留与下一步

- 没有 webhook 与文件监听：它们需要各自的鉴权与去抖设计；
- 没有多定时：一个流程一条，避免优先级与冲突；
- 没有每定时时区：统一系统本地时区；
- 没有分布式互斥：单机应用暂不需要。

如果继续沿着「会守时」走，最自然的一步是 **webhook 触发**：让外部系统能推事件进来。那会带来新的问题——签名校验、重放防护、限流——正好可以复用 API 端点已有的密钥与限流机制。

再往后是「文件监听」：本地目录变化时触发流程。它更贴近私人助手的场景，但跨平台行为差异大，需要单独一版。

## 八、这一版的位置

把三版连起来看：

- 上一版让流程「跑得动」，能并行；
- 再上一版让流程「摔了能爬起来」，能续跑；
- 这一版让流程「自己知道什么时候开始」。

到这一步，一个本地流程引擎的三个基本问题——执行、恢复、触发——都有了可验收的答案。下一步才有资格谈更复杂的东西：多触发源、事件驱动、跨设备。
