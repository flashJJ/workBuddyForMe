# 定时触发为什么默认拒绝写操作

定时任务最容易出事故的地方，不是「没跑」，而是「在没人的时候跑了不该跑的东西」。

这一版把定时触发定义为无人值守，并沿用已有的门控：写操作与危险工具默认拒绝。这篇解释这个决定。

## 一、有三个时刻，人不在场

流程的触发方式决定了「有没有人能确认」：

| 触发方式 | 人在场 | 能否弹授权 |
|---|---|---|
| 手动试运行 | 是 | 能 |
| 对话调用 | 是 | 能 |
| 定时触发 | 否 | 不能 |
| API / MCP | 否 | 不能 |

定时触发与 API / MCP 属于同一类：运行开始时没有人在看，运行过程中也不该假设有人会回来点「同意」。

## 二、挂起等待是更糟的选择

理论上可以让定时流程在遇到写操作时「挂起」，等用户下次打开应用再确认。

但这会带来一串问题：

- 运行状态会长期停在 `waiting_human`，占用单飞名额；
- 用户第二天打开应用，看到一个昨天凌晨的授权弹窗，上下文已经丢了；
- 如果用户不处理，这条运行会一直挂着，后续定时全部被跳过。

所以无人值守场景下，挂起不是「更安全」，而是「把问题推迟到一个更差的时刻」。

## 三、默认拒绝的具体表现

定时运行遇到写 / 危险工具时：

- 不弹窗、不挂起；
- 工具节点返回 `ok: false` 与说明文字；
- 节点本身算成功（它确实执行到了「拒绝」这个结果）；
- 流程继续往下走，或按图的分支处理。

这与 API / MCP 的现有行为一致：拒绝是一种正常结果，不是异常。

## 四、只读流程为什么不受影响

如果流程只包含：

- LLM 节点；
- 知识检索；
- 条件分支；
- 只读工具；
- 结束节点。

那么定时触发完全可用。这也是大多数「定时整理 / 汇总 / 检查」类流程的形态：

```text
每天 9:00
  → 检索昨天的资讯
  → LLM 汇总
  → 输出到结束节点
```

不需要写文件、不需要发消息，自然不需要授权。

## 五、需要写操作怎么办

有三种可行路径，按推荐程度排列：

1. **把产物留在流程输出里**，由用户打开运行记录查看，需要时手动导出；
2. **拆成两段**：定时段只做采集与整理，写操作放到用户在场时手动触发；
3. **使用只读的替代方案**，例如把「写文件」改成「生成内容并保存在运行输出」。

不推荐的做法是给定时运行放开写权限。那等于把「用户确认」这个安全边界，换成「cron 写对了」这个假设。

## 六、与节点超时、取消/中断的关系

有人会问：如果定时流程跑太久，能不能自动取消？

当前没有「运行级总超时」。定时流程如果卡住，会一直占用单飞名额，后续周期被跳过。这是已知限制，处理方式是：

- 给节点配置超时（节点级超时已提供）；
- 避免在定时流程里使用长任务或人工节点；
- 必要时在运行中心手动取消。

把这些边界写进文档，比悄悄加一个「默认十分钟超时」更诚实——后者会让用户以为流程被取消了，实际上后台还在跑。

## 七、安全的默认值

这一版没有新增一套权限系统，只是把「定时 = 无人值守」这个事实接进已有的门控。

好处是：

- 行为一致：API、MCP、定时三种无人值守触发共用同一套规则；
- 可解释：用户看到拒绝时，知道原因是「没人在场」，而不是「系统坏了」；
- 可扩展：将来如果要做「定时授权白名单」，也只需要在现有策略上加一层。
