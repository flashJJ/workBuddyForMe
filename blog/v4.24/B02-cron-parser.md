# 5 字段 cron：自己写一个够用的解析器

给流程加定时，第一反应是找一个 cron 库。但真正去看需求，会发现只需要一个很小的子集：5 字段、本地时区、下次时间计算。

这一版没有引入依赖，自己写了一个约 150 行的解析器，换来了完全可控的语义与可测试性。

## 一、需求边界

先列出「要支持什么」：

```text
分 时 日 月 周
0-59 0-23 1-31 1-12 0-7
```

语法只支持四种：

- `*`：任意值；
- `n`：单值；
- `a-b`：范围；
- `*/n`、`a-b/n`：步长；
- 逗号列表组合以上。

不支持 `L`、`W`、`#`、月份英文缩写这些扩展语法。原因是：它们使用频率低，但会让解析与解释成本翻倍。对个人自动化来说，5 字段足够表达「每天九点」「每周一八点半」这类需求。

## 二、解析成集合，而不是保留字符串

解析结果不是字符串，而是五个数字集合：

```ts
interface CronSpec {
  minutes: Set<number>;
  hours: Set<number>;
  daysOfMonth: Set<number>;
  months: Set<number>;
  daysOfWeek: Set<number>;
  domRestricted: boolean;
  dowRestricted: boolean;
}
```

这样做的好处是：判断某个时刻是否命中，只需要五次 `has`；计算下次时间，可以逐级跳过不匹配的年月日时分。

最后两个布尔值是给「日/周组合」用的，下面会讲。

## 三、周字段的 0 与 7

不同系统对周日的表示不一致：有的用 0，有的用 7。用户的直觉也各不相同。

处理方式是：解析时允许 0–7，解析后把 7 归一成 0。

```text
0 和 7 都表示周日
```

这样内部只维护 0–6，判断时直接 `date.getDay()`，不需要再分情况。

## 四、日与周的 OR 语义

标准 cron 有一个容易踩的坑：

- 当「日」和「周」都写成具体值时，满足**任一**即可；
- 当其中一个写成 `*` 时，只看另一个。

例如 `0 0 1 * 1` 表示「每月 1 号或每周一」，而不是「既是 1 号又是周一」。

实现上用两个布尔值记录「这个字段是否被限制」：

```ts
if (domRestricted && dowRestricted) return dom || dow;
if (domRestricted) return dom;
if (dowRestricted) return dow;
return true;
```

这里的「限制」定义为字段不是单独的 `*`。`*/2` 视为受限，虽然有些实现会把它当 unrestricted；这一版把规则写进注释与测试，避免歧义。

## 五、下次时间怎么算

最直接的做法是「从下一分钟开始，逐分钟加，直到命中」。这对 `* * * * *` 很快，但对「每年 1 月 1 日零点」这种表达式会循环几十万次。

所以用逐级跳跃：

```text
月不匹配 → 跳到下个月 1 号 00:00
日不匹配 → 跳到下一天 00:00
时不匹配 → 跳到下一个整点
分不匹配 → 加一分钟
```

每次跳跃都可能跨过大量不可能命中的时间，最坏情况也只是按天/小时循环。

为了避免「2 月 30 日」这种永远不可能命中的表达式把循环卡死，设了一个 5 年上限；超过就抛错，保存时直接拒绝。

## 六、本地时区的取舍

所有判断都用 `Date` 的本地方法：`getMonth`、`getDate`、`getHours`、`getMinutes`、`getDay`。

好处是：

- 不需要时区数据库；
- 用户看到的「每天九点」就是系统时间的九点；
- 夏令时切换由系统负责。

代价是：没法表达「纽约时间九点」。对单机桌面应用来说，这个能力暂时不需要；真的需要时，再引入时区参数，而不是现在就把复杂度背上。

## 七、测试怎么写

cron 的测试重点不是覆盖率，而是「语义是否可预测」：

1. 通配与列表的集合内容；
2. 范围与步长的边界；
3. 7 归一为 0；
4. 日/周 OR 的三种组合；
5. 跨月、跨年；
6. 非法表达式与无解表达式。

其中最有价值的是第 4 条：它把一个容易含糊的语义变成了几条断言。以后任何人改动判断逻辑，测试会立刻告诉他「你把 OR 改成 AND 了」。

## 八、小结

自己写 cron 解析器的理由不是「炫技」，而是：

- 需求边界清楚，5 字段就够；
- 语义需要可解释，不能依赖库里未文档化的行为；
- 保存时就要计算下次时间，解析器必须能被同一套代码复用。
