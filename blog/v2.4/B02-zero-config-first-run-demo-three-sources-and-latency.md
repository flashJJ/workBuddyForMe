# 零配置首启：不填 Key，也能先跑通一条真实链路

首启向导一直存在，问题是它把用户当成了模型专家。

第二步只有两个 tab：云端和本地。云端要求手填 Base URL、API Key、模型名；本地要求先装 Ollama、再拉一个几百 MB 的模型。两边的共同点是——**用户必须先理解模型世界，才能看到产品本身。**

代码里确实留了兜底，但那是一个只给开发用的环境变量。用户看不到它，产品里也点不到它。而向导的最后一步只有三条提示，没有一个「现在就问一句」的出口。

结果就是：配置完成了，但第一次对话没有发生。价值兑现链条断在最后一百米。

## 一、演示模式不是假数据

先把最容易误解的一点说清楚：演示模式**不是假数据**。

SSE 流式推送、知识库检索、引用标注、工作流节点执行，全部走真实链路；唯一被替换的是模型输出——它变成确定性文本。也就是说，用户看到的是「产品如何工作」，而不是「一张演好的截图」。

做法上不新造假模型，而是复用已有的 mock provider，只补三件事：

| 补的东西 | 作用 |
|---|---|
| 用户可见的开关 | 把开发环境变量变成向导里可勾选的一项 |
| 供应商落库 | 在本机创建 `demo` 供应商，对话模型 `demo-chat`、向量模型 `demo-embed` |
| 全程徽标 | 凡使用演示模型处显示「演示模式（非真实模型）」 |

设置页可以一键关闭，关闭时清理演示供应商，不留残留配置。整个能力只在本机运行，不引入账号，不外发任何数据。

这一步的价值不是「让用户看个热闹」，而是让**30 秒内看到产品在干什么**成立。用户先理解价值，再决定要不要投入配置成本。

## 二、三条来源并列，探测结果决定顺序

向导第二步从二选一变成三选一：

| 来源 | 前置条件 | 是否出网 | 适合谁 |
|---|---|---|---|
| 演示模式 | 无 | 否 | 第一次打开、想先看看 |
| 本地模型 | 已装 Ollama 或愿意装 | 仅拉模型时 | 追求离线与长期免 Key |
| 云端 API | 一个 API Key | 是 | 已有供应商、想要更强模型 |

默认聚焦演示模式，但三条都并列可改选。真正的顺序由探测结果决定：**本机检测到 Ollama 时，本地来源置顶并默认选中**。理由很直接——用户已经具备可用的真模型，最短的可用路径就是本地，没必要再让他先看演示。

云端路径不再从一张空表单开始。厂商卡片预填 Base URL、推荐模型名与能力（对话 / 视觉 / 向量），用户选中卡片后只需要补 Key，添加模型一步完成。自定义入口仍然保留。

这里有一条边界：预设只存 Base URL 与模型名建议，**不写价格、不做计费承诺**，页脚注明以厂商官网为准。

## 三、本地小模型：只做引导，不替用户下载

本地路径被拆成两态：

- **没装 Ollama**：给系统级安装路径与安装向导说明，而不是一句「请先安装」；
- **已装 Ollama**：给「一键拉取推荐模型」，按钮上明示体积、预计耗时档位与磁盘占用。

推荐型号收窄到两个：`qwen2.5:7b`（主，约 4.7GB）与 `qwen2.5:3b`（轻量，约 1.9GB）。选型门槛是中文可用、纯 CPU 或 4–8GB 显存可跑、体积可控。

两条硬约束：**不内置权重，不静默下载**。权重随包发布会让安装包和首启带宽同时失控；静默下载则违背「显式同意」原则。所以所有下载都必须由用户点一次确认，耗时只给档位，不承诺具体分钟。

## 四、向导的终点是第一次成功对话

步骤序列变成五步：

```text
welcome → provider（三来源） → voice（可选） → firstAsk → finish
```

`firstAsk` 是新增的一步，给三个示例问题，按已就绪的能力动态显隐：

1. 通用：「帮我写一条把这件事说清楚的周报」
2. 有知识库模板时：「用『产品需求』模板总结一段需求」
3. 有语音时：「用语音和我聊两句」

点选任意一个，应用会创建对话、以默认助手发出这个问题，并跳到对话页看到流式回复。**这一步才是首启的终点。**

示例问题与模板画廊共用同一份模板清单，不另写一套。否则两处各维护一份数据，第一次改模板就会不一致。

## 五、自检：给三档人话结论，而不是一个毫秒数

来源就绪后，向导会跑一次极短 prompt 的首字延迟自检。三个约束：只在用户已选定的来源上测、prompt 是固定常量、不含任何用户数据。

结论按三档给出：

| 首字延迟 | 结论 | 用户能做什么 |
|---|---|---|
| ≤ 1.5s | 体感流畅 | 直接开始 |
| ≤ 5s | 偏慢但可用 | 继续，或看看本地模型 |
| > 5s | 建议换来源 | 一键「换一个来源」 |

为什么不是直接显示毫秒数？因为「2.3 秒」对大多数用户不构成体感判断，而「流畅 / 偏慢 / 建议换」可以立刻转成行动。阈值也不拍脑袋：它同时被对话页的首字指标复用，首启时看到的结论和日常使用时看到的判断是同一套。

## 六、TTFV：四个时间戳，一条验收线

首启链路落四个本机时间戳：

| 字段 | 含义 |
|---|---|
| `first_launch_at` | 第一次启动 |
| `first_model_ready_at` | 第一条来源就绪 |
| `first_answer_at` | 第一条回答到达 |
| `ttfv_ms` | 前两者到「首答」的间隔 |

验收线是 `ttfv_ms ≤ 60_000`，端到端测试直接走演示模式断言，不依赖外网。关于页展示一行 TTFV，可清除。

隐私边界同样明确：只记时间戳与计数，**不含任何对话内容**，也不新建任何云上报。这条指标的意义在于，把「首启体验」从一句主观评价变成可回归的数字。

## 七、空态与向导接上

原来的空对话页只有一句说明加一个「去设置」。现在按钮改成「打开配置向导」，文案写明「三种搞法，最快 30 秒」。

这看起来是小改动，实际解决的是入口分裂：向导和空态原本是两套语义，都把用户丢进设置页。接上之后，用户在任何一条路上都能回到同一个起点。

## 八、这一版的原则

零配置首启不是「把复杂度藏起来」，而是**把复杂度排好顺序**：先给一条零成本的可用路径，再让用户按自己的条件升级；专家决策全部延后，且每一步都有可执行的下一步。

不内置权重、不静默下载、不做免费云兜底、不引入账号——这四条不让步。能做到「不填 Key 也能跑通」，靠的是把演示链路做成真链路，而不是造一个更漂亮的空壳。
