# 模板可触达：把「已经播种了」变成「现在就能点」

内置模板其实一直在库里：知识库 3 个、工作流 6 个、技能 3 个，角色卡还有 6 张。

但用户打开列表看到的是：一个空态、一句说明、一个「新建」按钮。模板在数据库里，不在用户的视线里。于是「内置模板」这件事对产品内部是事实，对用户是零。

这就是「功能有、入口浅」最典型的形态——**不是缺货，是货没摆出来。**

## 一、先承认：模板不是没有，是没被看见

| 已有资产 | 数量 | 原来的空态 |
|---|---|---|
| 知识库模板 | 3 | 一句空文案 + 新建按钮 |
| 工作流模板 | 6 | 同上 |
| 技能 | 3 | 只有列表与启停，没有模板区 |
| 角色卡 | 6 | 有内置 / 自建分区，但没有「从这里开始」 |
| 助手预设 | 0（未定义） | 只有空白新建表单 |

问题不在于资产少，而在于三件事同时缺失：**不知道有、不知道怎么用、不知道用了会得到什么。**

## 二、单一事实源：15 条

模板清单收敛到一份 web 侧映射，形状固定为：

```ts
interface StarterTemplate {
  kind: 'knowledge' | 'flow' | 'skill' | 'assistant';
  id: string; name: string; description: string;   // id 与内置对象同 id
  recommended?: boolean;                          // 该列表「推荐先用」
  startAction: 'clone' | 'enable' | 'prefill';
}
```

条目固定为 15 条：

| 类型 | 数量 | 条目 | 推荐先用 |
|---|---|---|---|
| 知识库 | 3 | 产品需求、会议纪要、研究资料 | 产品需求 |
| 工作流 | 6 | 资料研究助手、周报流水线、网页摘要器、会议纪要整理、竞品对比、知识库问答 | 资料研究助手 |
| 技能 | 3 | 周报生成、纪要整理、文件检索 | 周报生成 |
| 助手预设 | 3 | 资料研究助手、周报助手、会议助手 | 资料研究助手 |

角色卡的 6 张不进这份清单。它已经有成熟的「内置 / 自建」分区，复用既有实现，不重写。

助手预设的绑定只选确定可用的能力：资料研究助手 = 调研先锋 + 研究资料；周报助手 = 干练同事 + 周报生成；会议助手 = 沉稳顾问 + 纪要整理。文件检索需要先接 MCP filesystem，所以不做预设默认绑定——**只绑定开箱就能生效的东西**，否则用户点完会发现能力是空的。

还有一条容易被忽略的划分：模板的 `name` 与 `description` 是数据，不是界面文案。它们与内置对象同名同源，保持原名；只有标题、徽标、按钮、提示这些骨架文案走中英双档。这样不会出现第二份数据，也不会让「创建出来的对象」和「卡片上写的名字」对不上。

## 三、一个画廊，五个落点

统一组件 `TemplateGallery` 的接口很薄：标题、说明、分组、启动回调。每张卡只放四样东西——名称、一句适用场景、来源徽标、主按钮「以此开始」。

几个刻意的取舍：

- **不按跨类全局分组**。每个画廊只含一类模板，再分组只会增加心智负担；只有助手预设内部按用途分组。
- **每个列表首条标「推荐先用」**，不给用户一排同等权重的选项。
- **说明写适用场景，不写功能名**。比如「研究资料：把网页与文档整理成带引用的结论」，而不是「RAG 模板」。
- **新组件 ≤150 行**，避免撞上仓库 300 行的硬门禁。

为什么不做一个统一的「模板市场」页？因为这是本地优先产品：不下载、不联网、不分享。模板的价值在于**在用户正站着的那个列表里出现**，而不是被集中到另一个需要主动访问的页面。

## 四、出现时机：空态一次，顶部常驻

模板区只出现在两个位置：

1. **列表空态**：在空态动作区下方展示卡片区，让首启用户第一眼看到现成货；
2. **列表顶部**：一个可折叠的「内置模板」入口，常驻但不展开。

这是一个很窄的窗口设计。空态时它足够显眼，用户一旦有了自己的数据，它就自动退成一个不打扰的入口。既不会每次进列表都弹一遍，也不会在用户需要时找不到。

验收上有一条硬要求：**卡片数量必须等于接口返回的内置条目数，不允许前端硬编码。** 播种逻辑将来增加一条模板，画廊要自动跟上，而不是等下一次改 UI。

## 五、以此开始：四类语义，一个共同点

「以此开始」不是一个动作，而是四类：

| 列表 | 数据源 | 语义 | 产物 |
|---|---|---|---|
| 知识库 | 3 个内置库 | `clone` | 复制为自建库，改名后可删 |
| 工作流 | 6 个已发布流 | `clone` | 复制为可编辑草稿，保留节点图、另存新 id |
| 技能 | 3 个内置技能 | `enable` | 直接启用（技能是全局启停） |
| 助手 | 3 个预设 | `prefill` | 预填新建表单，用户可改后保存 |
| 角色卡 | 6 张内置卡 | 复制 | 沿用既有实现 |

共同点是：**不复用「内置对象本身」作为用户资产。**

内置对象是只读的，用户真正需要的是一份能改的副本。直接让用户去编辑内置模板，就会撞上「播种只增不改、不覆盖用户改动」的契约；而复制一份出来，用户怎么改都不会影响下一次播种。角色卡早就采用了这个范式，这一版只是把它推广到其余四类。

技能是唯一例外：它是全局启停的开关，没有「副本」的概念，所以「以此开始」就是启用。助手则刻意不直接落库——预填表单让用户先看见「这个助手会绑什么」，再决定保存。

## 六、工作流复制为什么要走服务端

知识库复制可以在客户端完成，工作流不行。

工作流的节点图与执行语义在 core 包里，属于 Node 侧模块，web 端不能安全导入。所以新增了一条服务端路由 `POST /api/flows/:id/clone`：服务端读取源流、复制节点图、生成新 id，副本名称由客户端按当前语言给出。

还有一个必须处理的边界：**源流可能已经被用户删了。** 内置流允许用户删除，这是既有契约。如果空态入口仍然指向一个不存在的 id，用户点「以此开始」就会得到一个 404。

做法是源缺失时回落到播种定义：服务端直接用内置的 `STARTER_FLOWS` 定义重建一份副本。这样「空态里能点的每一个入口」都保证可用，不会指向空气。

## 七、内置只读的准确含义

这里需要澄清一个容易混淆的口径：**只读的是播种定义，不是用户手里的实例。**

- 内置模板的 id 固定、播种幂等、只增不改；
- 下一次启动不会用内置内容覆盖用户改过的名称、节点或内容；
- 但用户对自己列表里的那个实例，仍然可以改名、可以删除。

所以这一版没有隐藏内置行的删除与编辑入口，只补了一个「内置」来源徽标。隐藏操作会与既有契约、单测和端到端用例冲突，而且对用户没有实际好处——他删掉的是自己的副本，不是模板定义。

徽标承担的是「知情」：这是内置来的，和自建的不一样；模板定义不会被你改坏。

## 八、验收与意义

验收只看四件事：五个列表的空态都出现模板卡片；每张卡的「以此开始」都能产出一个可打开的实例；内置与自建可区分；卡片数与播种结果一致。

模板可触达的本质，不是多写一个组件，而是承认一个事实：**空态不是终点，是用户第一次判断「这产品有没有货」的时刻。** 在那个时刻把货摆出来，比在设置页深处写十行说明都有效。
