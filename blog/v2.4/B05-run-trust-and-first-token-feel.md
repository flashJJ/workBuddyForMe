# 运行可信与首字体感：失败能解释，慢也能看见

这个产品的运行链路有三条：任务、桌面 Agent 运行、工作流运行。

三条都做了可观测：任务能看到每一步的状态、工具、参数、结果与耗时；工作流能从任意节点重放；协作有预算条、授权记录和只读舞台。但问题也很明显——三套状态词、三种耗时口径、失败时直接抛原始错误。用户看完只知道「它挂了」，不知道「为什么挂、我该做什么」。

偶发失败因此被泛化成「这功能不可信」，然后整个能力被回避。可信不是靠成功率数字喊出来的，是靠每一次失败都能被解释。

## 一、三套状态，一个词汇表

三条链路的状态归一成 8 个结果，共用同一个状态徽标：

| 结果 | 含义 | 用户语言 |
|---|---|---|
| `queued` | 已入队，尚未开始 | 排队中 |
| `running` | 正在执行 | 运行中 |
| `waiting` | 等待授权、输入或外部条件 | 等待中 |
| `succeeded` | 正常结束 | 已完成 |
| `failed` | 执行失败 | 失败 |
| `cancelled` | 用户主动取消 | 已取消 |
| `interrupted` | 进程或连接中断 | 已中断 |
| `budget_exceeded` | 触及预算或步数上限 | 已超限 |

两个区分值得单独说：

- **`waiting` 不是 `running`**。等待授权时任务没有在干活，用「运行中」描述会让用户以为它卡住了，也让耗时统计失真。
- **`budget_exceeded` 不是 `failed`**。它是策略主动叫停，不是 bug；把它归进失败，会让用户误以为系统不稳定。

## 二、耗时只认一个口径

统一口径是：`startedAt`（缺失时回退 `createdAt`）→ `finishedAt`。

Agent 运行没有单独的结束时间，终态用 `updatedAt` 代替；仍在运行中的，按「至今」实时计算。

为什么必须统一？因为耗时会被三种场景同时消费：列表排序、运行详情、以及用户自己比较「同一个任务昨天和今天差多少」。如果三条链路各用各的起点，跨链路比较就没有意义，排查也会从「慢在哪」退化成「看起来都差不多」。

时间戳缺失时回退，而不是显示空值——空值会让排序把这条记录丢到最前或最后，制造新的困惑。

## 三、失败归因：从原始错误到下一步

失败统一由一个纯函数分类，覆盖权限、鉴权、限流、超时、网络、模型、工具、节点、驳回、预算、步数、熔断、中断、取消与未知等十余类。

UI 不直接展示这个分类，而是输出两句话：**为什么失败 + 你能做什么。**

| 原始错误 | 为什么失败 | 下一步 |
|---|---|---|
| 401 / 403 | 鉴权失败或没有权限 | 检查 Key 与供应商权限 |
| 429 | 触发限流 | 稍后重试，或换一个模型 |
| 超时 | 模型或网络在限定时间内没有返回 | 换更小模型，或缩短上下文 |
| 工具调用失败 | MCP 服务不可达或参数不合法 | 检查服务状态与工具配置 |
| 节点失败 | 工作流某个节点执行出错 | 从该节点重放，不必重跑全图 |

原始错误仍然保留，但折叠起来。默认给结论，需要排查的人再展开——这比把一坨堆栈丢给所有人更合理。

用纯函数而不是在组件里散落 `if/else`，是为了三件事：三条链路得到同一套文案、分类可单测、以后新增错误码只改一处。

## 四、协作舞台：默认只读

协作卡只提供一个「只读观看」入口，并明确写着：不影响运行；写操作仍需在授权弹窗中显式允许。

这一版没有新增任何写入口。原因不是保守，而是信任的建立顺序：**先让用户看见它在做什么，再让用户决定要不要放权。** 直接给一个「全部允许」的开关，短期省事，长期会让用户在一次意外操作后彻底关掉整个能力。

原有的授权弹窗仍然逐项确认，只读观看只是把「观察」这一步前移成默认起步。

## 五、流式渲染：合帧，而不是逐 token

原来的流式消费每来一个 delta 就触发一次消息树渲染。短回复没问题，长回复会把主线程切得很碎。

现在 delta 先进入缓冲，按 `requestAnimationFrame` 合帧提交：一帧内到达的多个片段合并成一次渲染。

但合帧带来一个必须处理的边界：**终态不能等下一帧。** 所以 `done`、`error`、停止、重置四个事件都同步冲刷缓冲，保证最后一段文本不丢、停止立即生效。合帧是为了省渲染，不是为了延迟状态。

## 六、长回复：按顶级标题切块

长回复的 Markdown 全量重解析，是另一个隐性成本。现在的做法是按顶级标题切块，逐块缓存（memo）：

- 代码围栏内不切，避免把一段代码劈成两个不完整的块；
- 小于 1.6k 字的回复仍按单块处理，切块本身也有成本；
- 流式期间只重新解析发生变化的那一小节，其余块直接复用。

按标题切而不是按固定字数切，是因为标题是语义边界，块与块之间的内容不会互相影响；固定字数切会把一句话、一个列表甚至一个表格拆开，渲染结果反而不稳定。

## 七、首字：从「转圈」到「已等待 X 秒」

等待首字超过 1.5 秒，界面显示已等待秒数；超过 5 秒，追加一条建议：停止，换更小模型，或缩短上下文。

助手消息头部常显首字延迟小指标。它和首启自检用的是同一套阈值：≤1.5 秒流畅、≤5 秒偏慢但可用、>5 秒建议换来源。

为什么要把「等了多久」显式说出来？因为无信息的等待会被感知得更长。用户不怕慢，怕的是不知道还要等多久、也不知道自己能做什么。给出秒数和动作，等待就从「失控」变成「可选」。

## 八、一致性收口

三个运行页统一使用同一套空态与错误态组件，加载、空、错误同一套语气。权限类错误落到错误态，不再各页各写一句。

命令面板补齐任务与工作流导航，以及新建知识库、工作流、助手、角色卡；`?new=` 深链接进入即打开创建表单，不用先到列表再点一次。

快捷键浮层补上舞台组：H、F11、Esc、Ctrl+滚轮，并与真实绑定同步。响应式端到端扩到三种尺寸 × 六个列表与运行页，长文本统一截断收口。

浏览器端到端共 109 例全部通过，包含命令面板深链接、三尺寸复核、协作与关键路径。新增测试集中在运行结果映射与归因、长回复切块的无损性、合帧与首字计时。

## 九、可信是怎么长出来的

可信不是一个百分比，而是三个连续的回答：**发生了什么、为什么失败、我现在能做什么。**

状态统一回答第一个，归因回答第二个，下一步建议与只读舞台回答第三个。首字体感则是同一套逻辑在「慢」这个维度上的延伸——把不可见的等待，变成可见的数字和可执行的选项。

回到最初那个问题：用户装完之后，为什么能一路用下去——因为每一步都有可解释的状态、可执行的下一步，以及看得见的等待。
