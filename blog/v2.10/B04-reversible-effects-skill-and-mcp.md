# 可逆的副作用：技能与 MCP 的启用/停用如何成对

能力包最容易做假的地方，是把「启用」实现成一个 `status = enabled` 的字段更新。界面立刻变绿，用户以为生效了，但系统里什么都没发生；点停用时也一样，字段变灰，副作用还在。这种实现能过 UI 测试，却过不了「停用后效果消失」的验收。

这篇讲这次只接入的两类 effect：技能与 MCP 服务器。它们如何注册、如何撤销、失败时如何回滚，以及为什么另外四类能力明确不接。

## 一、effect 的契约：返回句柄，成对执行

启用与停用不是两个独立函数，而是一对必须配平的契约：

```ts
enableCapabilityEffect(manifest, packDir, deps): string   // 返回 effectRef
disableCapabilityEffect(manifest, effectRef, deps): void  // 用同一个句柄撤销
```

`effectRef` 是撤销时唯一的凭据。技能包返回技能目录名，MCP 包返回服务器 id。它被写进数据库行，所以停用、重启、卸载都能从持久化状态恢复，而不依赖进程内变量。

契约里还有一条隐含规则：**enable 要么完整成功并返回句柄，要么抛错且不留下任何已注册副作用。** disable 则相反，要么撤销成功，要么保持原状并报错，不能出现「撤了一半」。

## 二、skill effect：复制目录，再让技能重扫

技能包的 payload 就是一份技能目录。启用分三步：

1. 读取 `payload/skill.json`，用技能清单 schema 校验；不合法直接拒绝；
2. 检查目标技能目录是否已存在；同名则返回冲突，绝不覆盖用户已有技能；
3. 把整个 `payload/` 递归复制到技能目录，然后触发技能重扫（reconcile），让新技能进入可用列表。

停用按相反顺序做：

1. 删除该技能目录；
2. 再次触发重扫；
3. 在技能状态表里找到同名记录并移除。

第 3 步容易被忽略。只删目录不删状态行，会出现「文件没了但列表还挂着一个空技能」的幽灵记录；只删状态行不删目录，则下次启用会撞上「目录已存在」。两者必须一起做。

这里有一个刻意保留的不对称：启用时目录已存在就直接冲突，停用时目录不存在却不算错误——因为停用的目标是「让它消失」，已经不存在的目录本来就满足目标，只需要把状态行清掉。

## 三、mcp effect：把配置变成服务器

MCP 包的入口是一份 `payload/server.json`，字段在 effect 阶段用 zod 再校验一次：

| 字段 | 约束 |
|---|---|
| `name` | 1–60 字符 |
| `transport` | `stdio` 或 `http` |
| `command` / `args` / `env` | stdio 传输必填 command；args 最多 50 项 |
| `url` / `headers` | http 传输必填 url |
| `enabled` | 可选布尔 |

启用时读取配置、校验、调用 MCP 注册表的 `createServer`，把返回的服务器 id 作为 `effectRef` 存下来。停用时按这个 id 调 `removeServer`。

停用这里有一个容错决定：如果服务器已经不存在，`removeServer` 抛错会被吞掉，视为「已撤销」。原因和技能目录相同——撤销的目标状态是「不存在」，已经不存在就不该让用户卡在一条永远失败的重试上。但吞错只针对「找不到」，其他错误仍然向上抛。

## 四、失败语义：三种场景，三种回滚

| 场景 | 失败点 | 回滚动作 | 最终状态 |
|---|---|---|---|
| 安装时自动启用失败 | 复制目录冲突、MCP 配置非法、注册表拒绝 | 删除包目录、删除数据库行 | 等于没装 |
| 手动启用失败 | effect 抛错 | 状态回 `disabled`、句柄清空、写入 `lastError` | 包还在，但明确未生效 |
| 手动停用失败 | 撤销 effect 抛错 | 状态保持 `enabled`、只写 `lastError` | 原状保持，可重试 |

三种场景的回滚方向不一样，是因为「承诺」不一样。安装的承诺是「装上一个可用的包」，启用失败就必须整体退回；启用的承诺是「让它生效」，失败就退回未生效；停用的承诺是「让它失效」，失败时最危险的做法是假装已失效，所以必须保持原状并报错。

## 五、effectRef 落库，而不是放内存

句柄存进 `capability_packs` 行，和状态、`last_error` 放在一起。这样带来三个直接好处：

- 进程重启后，停用仍然知道该删哪个技能目录、该移除哪个服务器；
- 列表页能展示「生效句柄」，用户看得到它具体挂了什么；
- 卸载时即使包目录已被外部改动，也能先按句柄撤销，再清文件。

如果把句柄只放在内存 Map 里，应用一重启，所有「已启用」的包都变成无法撤销的孤儿记录。这是本地应用里很常见的一类隐性泄漏。

## 六、为什么先做这两类

选 skill 和 mcp，不是因为它们简单，而是因为它们已经具备三个前提：

1. **有稳定的注册入口**：技能服务有目录扫描与 reconcile，MCP 注册表有 create/remove；
2. **有确定的作用域**：一个技能目录、一个服务器 id，撤销目标明确；
3. **副作用可观察**：技能会出现在列表，MCP 服务器会出现在设置与工具列表，验收能直接断言。

换句话说，这两类的 effect 是「登记既有资源」，不是「新造运行时」。能力包机制本身不执行包里自带的代码，它只把包里声明的资源交给既有服务去加载。

## 七、另外四类为什么这次不接

`workflow`、`pet-action`、`event-script`、`report-widget` 在清单层保留，但安装直接返回 422「该能力类型尚未接入」。理由不是工期，而是风险：

| kind | 缺什么 |
|---|---|
| `workflow` | 需要定义流程草稿的导入、版本冲突与运行中引用的处理 |
| `pet-action` | 需要桌宠动作的资源格式、播放互斥与卸载后的动画状态收尾 |
| `event-script` | 需要事件脚本的权限沙箱与触发范围，不能等同于「装个文件」 |
| `report-widget` | 需要报告卡片的渲染契约、数据源声明与失败降级 |

这四类如果先「假装启用」，用户会得到一个状态为 enabled、实际什么都不会发生的包。那比明确拒绝更糟：拒绝至少诚实，假装生效会污染所有后续排障。所以清单先留位置，effect 留空，安装明确报错。

## 八、可逆性怎么测

core 包里这次有 3 个能力包用例，专门证明 effect 成对与失败回滚：

| 用例 | 断言重点 |
|---|---|
| 示例技能包 | 安装即 enabled、句柄是技能目录名、技能出现在列表；停用后技能消失；再启用恢复；卸载后列表与技能都为空 |
| MCP 包 | 启用时 `createServer` 被调用一次；停用时 `removeServer` 收到同一个句柄；状态变 disabled |
| fail-closed | 错误哈希、缺权限、缺依赖、未接入类型、重复安装分别报错 |

测试依赖是注入的：临时数据目录、独立技能目录、以及一个假的 MCP 注册表。这样用例既不启动真实子进程，也不碰网络，跑得快且可重复。假注册表能验证「调用了几次、传了什么参数」，但验证不了真实 MCP 握手——那属于集成测试的边界，不塞进单测里假装覆盖。

可逆性测试的关键不是「启用成功」，而是**启用后再停用，系统是否回到启用前的样子**。所以每个正向用例都成对跑：install → enable → disable → enable → uninstall，中间每一步都断言列表与状态，而不是只测第一条路径。

## 九、可逆不是附加功能，是设计前提

这次实现里，每个 effect 都先回答两个问题：启用后系统多了什么？停用后怎么把这个「多了什么」精确拿掉？答不上来的能力类型，就不应该出现在可安装列表里。
