# 安装、启用、停用、卸载：一条不留半成品的生命周期

能力包有四个动作：安装、启用、停用、卸载。单独看每个都不难，难的是它们共享两份状态——磁盘上的包目录和数据库里的记录。任何一步只改其中一份，都会留下「文件在、记录没了」或「记录说启用、副作用不在」的裂缝。

这篇讲这四个动作的执行顺序、每一步的失败回滚、卸载前的依赖闸，以及 API 面怎么把这些状态翻译成状态码。

## 一、顺序不是随便排的

```text
install   校验 → 落盘 → 建行（disabled）→ 自动 enable（失败则删包删行）
enable    查行 → 查清单 → 查目录 → 注册 effect → 更新 status/effectRef
disable   查行 → 撤销 effect → 更新 status=disabled/effectRef=null
uninstall 查依赖 → 先 disable → 删包目录 → 删记录
```

四个动作里有两个关键顺序：

- **先落盘再建行**：如果反过来，先建行后写文件失败，就会留下一条指向不存在目录的记录，列表页点启用只会得到「文件缺失」；
- **卸载先停用再删文件**：撤销 effect 需要包目录里的清单与 payload，先删目录就等于把撤销凭据一起删了。

## 二、install 的七步

安装是一个带补偿的事务，步骤固定：

1. 解析 ZIP 并完成清单、结构、哈希、权限、类型校验；
2. 查同 id 是否已存在，存在返回 409；
3. 检查依赖：必须已安装且处于启用状态，写了版本则精确匹配；
4. 若目标目录已存在（通常是上次异常退出的残留），先整体删除；
5. 创建 `capabilities/<id>/`，把内存文件表逐条写入；
6. 插入数据库行，状态先记为 `disabled`；
7. 调用 `enable` 自动启用。

第 7 步失败时执行补偿：删掉整个包目录，再删掉刚插入的记录，然后把原始错误抛给调用方。这样「安装成功」只有一个含义——包在磁盘上、记录在库里、effect 已注册。

第 4 步的重建也值得说明。它不为「覆盖安装」服务，因为同 id 已经在第 2 步被拒绝；它只处理「目录存在但数据库没有对应行」的残留。这种残留通常来自进程在写文件途中被杀，清掉再写比试图续写安全得多。

## 三、enable：前置条件先于副作用

手动启用不是直接调 effect，而是先确认三个前提：

- 记录存在，否则 404；
- 状态已是 `enabled`，直接返回，不重复注册（幂等）；
- 清单能从数据库读出来、包目录还在，否则提示「清单损坏/文件缺失，请重新安装」。

三个前提都满足后才注册 effect。注册成功更新 `status`、`effectRef`，清空 `lastError`；注册失败则把状态写回 `disabled`、句柄清空、`lastError` 记录原因。

这个「先回写失败态再抛错」的顺序很重要。如果先抛错、回写交给调用方，任何没接住错误的调用路径都会留下一个状态仍是 `disabled`、但界面上说不清为什么的记录。服务层自己负责把失败写进可展示的位置。

## 四、disable：撤销优先，状态其次

停用的顺序与启用相反：

1. 记录不存在 404；已是 `disabled` 直接返回（幂等）；
2. 有清单且有 `effectRef` 时，调用撤销 effect；
3. 撤销成功才把状态改为 `disabled`、句柄清空、错误清空。

撤销失败时**状态保持 `enabled`**，只写入 `lastError` 并抛出。这是一个刻意选择的失败姿态：停用的目标是「让它真的失效」，撤销没成功却把状态改成 disabled，等于向用户谎报。保持原状至少让用户知道它还在生效，可以重试或手动处理。

## 五、uninstall：先看谁依赖它

卸载不是「删就完了」，前面有一道依赖闸：

- 遍历所有已启用能力包，看谁的 `dependencies` 里包含当前 id；
- 有依赖者则返回 409，错误信息列出具体 id；
- 只有无人依赖时，才允许继续。

依赖闸只看**已启用**的包，和安装时的依赖解析口径一致：停用的包不产生 effect，也就不构成运行前提。这样不会出现「安装时说依赖它，卸载时却因为一个停用的包被拦住」的矛盾。

通过依赖闸后，顺序是：

1. 如果当前是 `enabled`，先执行 `disable`；
2. 删除 `capabilities/<id>/` 整个目录；
3. 删除数据库行。

如果第 1 步失败，流程在这里中断，目录和记录都保留。卸载要么完整完成，要么完全不动；不存在「effect 还在、记录没了」的中间态。

## 六、磁盘与数据库各自负责什么

| 位置 | 内容 | 谁写 |
|---|---|---|
| `capabilities/<id>/` | 清单 + payload，安装后的唯一真源 | 安装流程 |
| `capability_packs` 行 | id/kind/version/name/权限/清单快照/status/effect_ref/last_error/时间 | 生命周期各步 |
| 技能目录 | 技能 effect 复制出来的运行时副本 | 启用 effect |

清单同时存在两处：包目录里的原文件和数据库里的快照。启用时读数据库快照来判断 kind 与依赖，读包目录来判断文件是否完整；两者不一致时以「目录缺失」或「清单损坏」拒绝，而不是猜哪份是真的。

`last_error` 是给人看的，不是给程序判断的。状态判断只认 `status` 与 `effect_ref`，错误文本只负责解释「为什么现在是这样」。

## 七、API 面：把状态翻译成状态码

服务层的方法很薄，路由层负责参数校验与状态码：

| 方法与路径 | 行为 | 成功 | 失败 |
|---|---|---|---|
| `GET /api/capabilities` | 列出全部能力包 | 200 数组 | — |
| `POST /api/capabilities/install` | multipart 上传 ZIP，校验后自动启用 | 201 视图 | 422 校验失败 / 409 重复 |
| `POST /api/capabilities/:id/enable` | 注册 effect | 200 视图 | 404 / 422 |
| `POST /api/capabilities/:id/disable` | 撤销 effect | 200 视图 | 404 / 422 |
| `DELETE /api/capabilities/:id` | 卸载 | 200 `{ deleted: true }` | 404 / 409 有依赖 |
| `GET /api/capabilities/sample` | 下载示例包 | 200 ZIP | — |

服务方法签名也保持同一组动词：`list`、`install(buffer)`、`enable(id)`、`disable(id)`、`uninstall(id)`、`sample()`。路由层不直接碰文件系统，也不自己拼清单；它只做「取参数 → 调服务 → 包响应」。

## 八、重复与幂等的边界

三个动作的重复语义不一样：

- **install**：同 id 第二次安装是冲突（409），因为安装意味着「换一份内容」，而当前机制不支持覆盖升级；
- **enable**：已启用时再调是幂等，直接返回当前视图；
- **disable**：已停用时再调是幂等，直接返回当前视图；
- **uninstall**：记录不存在是 404，不当作「已删除」静默成功。

之所以安装不做幂等，是因为同一个 id 的两份 ZIP 可能内容不同。若把第二次安装当作「已安装」直接返回，用户会以为新内容生效了，实际磁盘上还是旧包。宁可让他先卸载，也不做隐式覆盖。

## 九、生命周期是一份可核对的账

这四个动作合起来，实际在维护一份账：磁盘目录、数据库行、effect 句柄三者的对应关系。每一步的设计目标都是「账目要么同时更新，要么都不更新」。
