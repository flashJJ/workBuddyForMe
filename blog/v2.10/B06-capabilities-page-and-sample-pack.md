# 能力包管理页：把「装了没生效」变成可读状态

服务端把能力包的生命周期做对以后，界面上仍然可能一团糟：用户装完不知道装到哪了，不知道它需不需要权限，不知道它到底生效没有，出了问题只看到一句「操作失败」。管理页的价值不是「有个地方点按钮」，而是把这四个问题逐条回答清楚。

这篇讲这个页面的四块结构、上传限制、示例包的构造方式、错误展示的层级，以及导航与双语文案怎么收口。

## 一、页面只有四块

管理页刻意不做信息分层，一屏之内只有四块：

1. **页头**：标题、说明、右侧「下载示例包」；
2. **上传区**：文件选择 + 安装按钮 + 一行格式提示；
3. **能力列表**：每条能力一张卡片；
4. **外部代理区**：说明可用性与当前为空的状态。

没有 tab、没有二级详情页。能力包数量在单机场景下很少超过两位数，把状态摊平比做导航更深一层更有效。

## 二、上传安装：入口只有一条

安装入口就是一个文件选择框，接受 `.zip`。选中文件后按钮才可用，点击时用 `FormData` 把文件 POST 到安装接口，成功返回 201 后刷新列表并清空选择。

服务端对上传的限制很硬：

| 情况 | 结果 |
|---|---|
| 字段不是文件、缺少 `file` | 422 |
| 文件大小为 0 | 422 |
| 文件超过 20MB | 422 |
| 内容不是合法能力包 | 422，带具体原因 |

前端不预校验 ZIP 结构，也不在本地解压。原因很简单：校验逻辑只有服务端一份，前端再实现一份就会产生两套口径；而且浏览器里解压一个不可信压缩包，本身就是不必要的攻击面。前端只做两件轻量检查——是不是 `.zip`、大小是否明显超限——其余交给服务端。

## 三、列表：每条回答四个问题

每张能力卡片按固定顺序展示：

- **身份**：名称、id、版本号；
- **类型与状态**：kind 徽章（技能、MCP 服务器、工作流等）、已启用/已停用；
- **权限**：逐个权限徽章；未声明时显示「未声明权限」，而不是留空；
- **生效句柄**：技能显示目录名，MCP 显示服务器 id，未生效显示「无」；
- **最近错误**：有 `lastError` 时用错误色单独一行展示。

这五项对应了排障时最常问的五个问题：它是什么、它现在算不算生效、它要什么权限、它挂到了哪里、上次为什么失败。把这五项固定成模板，比让用户点进详情页找要快得多。

## 四、按钮跟着状态走

操作只有两个：启停切换与卸载。

- 已启用时主按钮是「停用」（次要样式），已停用时是「启用」（主样式）；
- 无论状态如何，「卸载」都是危险样式，并和启停按钮并排；
- 请求进行中禁用按钮，避免重复提交；
- 任何操作成功后都让列表查询失效并重新拉取，不做本地乐观更新。

不做乐观更新的理由是：能力包的启用可能失败并回写 `lastError`，本地先改状态再等服务端纠正，会让用户看到一次「先变绿又变红」的闪烁。宁可多一次请求，也不要展示一个未经服务端确认的状态。

## 五、示例包不是截图，是可安装的 ZIP

「下载示例包」指向一个返回 ZIP 的接口，包内是一份最小但真实的能力包：

```json
{
  "id": "com.example.sample.capability-demo",
  "version": "1.0.0",
  "kind": "skill",
  "name": "能力包示例技能",
  "permissions": ["skill:install"],
  "entry": "payload/skill.json",
  "dependencies": [],
  "checksums": { "payload/skill.json": "<sha256>" }
}
```

payload 里的技能声明了 `current_time` 工具、一段提示模板和一条示例对话。它不依赖任何外部模型或网络，装完就能在技能列表里看到，停用后立刻消失。

示例包由同一个纯函数生成，测试与下载接口共用同一份构造逻辑。这样做避免了「文档里的示例」和「真的能装的示例」漂移：示例一旦构造逻辑坏了，单测会先红，而不是等用户下载后才发现。

## 六、错误展示分两层

页面上有两种错误，来源不同：

| 层级 | 来源 | 展示位置 | 内容 |
|---|---|---|---|
| 操作级 | 上传/启停/卸载请求失败 | 页面顶部一行 | 「安装失败：清单/校验和/权限/依赖不满足」或「操作失败，请重试」 |
| 能力级 | 某条能力某次启用失败 | 该卡片内 | `lastError` 原文 |

操作级提示负责告诉用户「这次动作没成功」，能力级错误负责告诉用户「这条能力为什么没生效」。两者不能合并成一句「出错了」：前者是瞬时的，后者是持久化的，混在一起会让用户以为错误已经随着刷新消失，实际它还在数据库里。

## 七、外部代理区：说清楚「没有」也是状态

页面底部单独有一块「外部代理」，写两句话：外部代理是可选依赖、默认关闭，未接实现时核心功能不受影响；当前尚未接入任何提供方。

这块不是占位符。它回答的是一个容易被误解的问题：用户看到「能力包」页，会自然期待「能接外部 agent」。明确写出「默认关闭、未接入」，比放一个点了没反应的「添加」按钮诚实。

## 八、导航第 11 项与双语文案

侧栏导航从 10 项变成 11 项，新增「能力包」，位置在计划与会议之间，图标用 Package。导航项仍然只有一个事实源：数组里声明路径、标题键、描述键与图标，组件只负责渲染。

文案全部走 i18n 命名空间，中英文各一份，键必须一一对应：

- 页面级：标题、说明、空态、安装/安装中、上传提示；
- 状态级：已启用、已停用、权限、未声明权限、生效句柄、无、最近错误；
- 类型级：六类 kind 的显示名；
- 操作级：启用、停用、卸载、下载示例包、两类失败提示；
- 外部代理：标题、说明、空态。

双语文案不写在组件里，是为了让「新增一种 kind」只改一处命名空间，而不是在页面里到处找中文。这次新增的命名空间也进了双语一致性测试，缺键会直接失败。

## 九、验收数字

| 项 | 结果 |
|---|---|
| web 单测 | 594 例，含能力包 API 2 例、导航 11 项 |
| 能力包端到端 | 2/2：示例包安装→技能出现→停用→卸载；非法包 422 |
| 全量 Web 端到端 | 120/120，生产模式产物 |
| shared 单测 | 321 例，含新增命名空间的双语一致性 |

端到端没有只测接口，而是真的打开管理页、点安装、看技能列表变化、再停用卸载。页面的价值只有在真实交互里才能被验证。

## 十、界面只是账本的显示层

管理页不持有任何能力状态，它只把服务端账本翻译成可读信息：状态来自 `status`，句柄来自 `effect_ref`，失败原因来自 `last_error`。页面做得再漂亮，如果账本本身不可逆、不一致，用户看到的仍然是假象。
