# 接口缝与生产导出坑：默认无实现，和只在生产产物里缺的符号

这次能力包迁移有两个工程侧的决定，表面看互不相关，底层是同一种思路：**不要让「当前没有」变成「运行时才知道」。**

第一个决定是外部代理只留接口缝，默认没有实现；第二个决定是新增域必须同时补齐根导出。前者是主动留白，后者是被生产环境打了一巴掌之后补上的。这篇把两件事放在一起讲，因为它们都指向「默认路径之外的那条路」。

## 一、接口缝的形状

外部代理的接口只有四个成员：

```ts
export interface SubagentProvider {
  id: string;
  label: string;
  available(): boolean;
  run(
    input: SubagentProviderInput,
    signal?: AbortSignal,
  ): Promise<SubagentProviderResult>;
}
```

输入是目标（可选会话 id、可选预算上限），输出是三种状态之一：完成、失败、取消，外加一段摘要与可选错误。接口里没有模型、没有密钥、没有传输方式——这些都属于具体实现，不该写进缝里。

`available()` 是一个同步方法，回答「当前环境能不能用」：命令不在、授权没给、运行时版本不匹配，都返回 false。它不负责启动探测，也不抛错；调用方拿到 false 就当作「这个提供方暂不可用」，不影响其他功能。

输入与输出也被刻意压到最小：

```ts
export interface SubagentProviderInput {
  goal: string;
  conversationId?: string;
  budget?: { maxRounds?: number; maxTotalTokens?: number };
}

export interface SubagentProviderResult {
  status: 'done' | 'failed' | 'cancelled';
  summary: string;
  error?: string;
}
```

预算用「上限」表达，而不是具体计费单位，因为不同提供方对轮次与 token 的解释不一样；结果只区分三种终态，不把中间流式事件写进接口，避免实现被迫适配某一种输出协议。

## 二、注册表：默认是空的

注册表是一个极薄的 Map 封装：

- `register(provider)` 注册并返回一个反注册函数；同 id 重复注册直接抛错；
- `list()` 返回 `{ id, label, available }`，其中 `available` 在**调用时**才计算；
- `get(id)` 找不到返回 null，不抛错。

`available` 延迟计算是刻意的。启动时算一次并缓存，会让「用户稍后安装了命令行工具」这种情况永远显示不可用；每次列表都实时问一遍，代价很小，状态却是新的。

重复注册抛错而不是覆盖，是为了让「同一个 id 被两个实现抢占」在启动期就暴露。`register` 返回的反注册函数则保证了测试与热插拔场景能干净地撤销：注册与撤销成对，不在全局留下隐藏状态。

默认没有任何提供方注册。于是启动路径上不存在「等待外部代理就绪」的分支：注册表为空，列表为空，核心功能照常工作。这不是容错，而是结构上没有依赖。管理页读到的就是这份空列表，显示「尚未接入任何提供方」，而不是一个永远转圈的加载态。

## 三、为什么先留缝，不接具体实现

外部代理有四种常见形态：同进程子代理、通过 ACP 协议通信的客户端、命令行式编码代理、以及各类桌面端 agent。它们至少在三处不一样：

| 维度 | 差异 |
|---|---|
| 运行形态 | 进程内、子进程、长连接、一次性命令 |
| 预算表达 | 轮次、token、时长，各家语义不同 |
| 审批与证据 | 有的自带审批流，有的需要宿主代管 |
| 凭据 | 各自读取自己的配置，不能共用宿主密钥 |

这四件事没有定论之前接任何一个实现，都会把它的临时形状写成事实标准。更糟的是，外部代理一旦默认开启，就会改变「本地优先、密钥不出机、审批 fail-closed」三条红线的前提。

所以这次只做三件事：定义接口、提供注册表、在管理页写明「默认关闭、未接入」。未来接入时必须复用统一的预算、审批与证据回传，不共享密钥；`available=false` 时不阻断核心。缝留好了，实现可以后补；缝留错了，实现会被迫绕着它长。

这里的「不共享密钥」不是一句口号，而是接口形状的直接结果：`SubagentProviderInput` 里没有凭据字段，实现只能自己从自己的配置里取。宿主不替外部代理保管密钥，也不把宿主密钥传给它，供应链风险被限制在「装了什么」而不是「整个应用的主密钥」。

## 四、生产导出坑：症状只在最后一步出现

能力包功能开发完成后，单测全绿，定向端到端也全绿。第一次跑 CI 模式的全量端到端时，页面直接报错：

```text
createSessionLogService is not a function
```

同一个页面在本地开发服务器上完全正常。单测里也正常——测试直接按域子路径导入服务，拿到的就是真实函数。只有用生产模式启动（打包产物 + `next start` / standalone）时，这个符号才变成 undefined。

这类错误最迷惑人的地方是错误信息指向业务函数名，看起来像「服务没初始化」或「依赖注入漏了」，实际和业务逻辑一点关系都没有。

## 五、根因：子路径注册了，根 barrel 没聚合

core 包的导出有两层：

- **域子路径**：`core/capabilities`、`core/session-log`、`core/work-plan` 等，每个域自己的 barrel；
- **根 barrel**：把所有域聚合到一个入口，供历史代码与跨域消费者使用。

这次新增的三个域只登记了子路径，没有聚合进根 barrel。开发态的条件导出会解析到源码，根 barrel 缺失某个域也能从别处间接拿到；生产态则把根入口指向打包后的 `dist/index.*`，那里没有这个符号，于是调用方拿到 undefined，一调就炸。

修复本身很小——在根 barrel 里补上三行聚合导出：

```ts
export * from './work-plan';
export * from './session-log';
export * from './capabilities';
```

但真正要理解的是为什么它必须补。根 barrel 是兼容面：只要还有消费者从根入口导入，它就必须包含所有公开域。子路径只是「更精确的入口」，不是「替代根入口」。两者不同步，生产产物就会出现「按子路径能拿到、按根入口拿不到」的分裂。

还有一个容易忽略的事实：缺的不止能力包一个域。同一批新增的另外两个域也只登记了子路径。报错里出现的 `createSessionLogService` 属于会话日志域，最先崩的是它，不代表只有它缺。修复时必须把三个域一起补齐，否则只是把下一个错误推迟到下一次运行。

## 六、为什么开发态完全无感

开发态和生产态走的是两条解析路径：

| 环境 | 解析目标 | 结果 |
|---|---|---|
| 开发服务器 | 源码条件（对应 `src`） | 根 barrel 缺失也能从模块图里间接拿到 |
| 单测 | 直接导入域子路径或源码 | 根本不经过打包产物 |
| 生产启动 | `dist/index.*` | 缺失的聚合导出变成 undefined |

单测覆盖的是「函数逻辑对不对」，端到端在开发态覆盖的是「页面流程通不通」，两者都不会碰「打包后的根入口是否完整」。这不是测试写得不够多，而是测试跑在了另一条解析路径上。

## 七、修复与验证

修复分三步：

1. 补齐根 barrel 的聚合导出；
2. 重新构建 core 包，确认 `dist/index.*` 里能看到三个域导出的符号；
3. 用生产模式跑全量端到端，而不是只跑定向用例。

最终结果是 120/120 全通过，耗时 10.9 分钟。定向用例只能证明能力包页面能用，全量用例才能证明「所有从根入口取服务的旧页面」在生产产物里都还能启动。这个坑是首次全量生产模式运行时暴露的，也说明这条门禁不能省。

验证时还有一个顺序细节：先重建，再启动生产模式，最后跑全量。跳过重建直接跑，命中的还是旧产物，修了等于没修；只跑定向用例，则只能覆盖新页面，覆盖不到那些从根入口取会话日志、工作计划的旧页面。失败一次之后，我们把「重建 + 生产启动 + 全量」固定成一条命令，避免下次又靠记忆拼步骤。

## 八、五条方法论

1. **子路径导出必须在生产产物上验证。** 源码条件、单测导入、开发服务器都不算数；至少要有一次 `build + 生产启动` 的真实调用。
2. **根 barrel 是契约，不是可选聚合。** 新增域要么同时登记子路径与根入口，要么明确废弃根入口；不能只登记一半。
3. **CI 至少保留一套全量、生产模式的门禁。** 定向用例证明新功能可用，全量生产用例证明旧功能没被打包边界弄坏。
4. **把开发态与生产态当成两个构建目标。** 条件导出是便利，也是分歧源；凡是有条件解析的地方，就要有成对验证。
5. **看到 `X is not a function` 先查导出聚合与打包边界。** 业务函数名只是症状；真正要问的是「这个符号在产物里到底有没有被导出」。

## 九、两件事其实是同一件事

接口缝回答的是「没有实现时，系统怎么正常运转」；生产导出坑回答的是「实现都在时，产物怎么才算完整」。前者靠默认空注册表，后者靠生产模式门禁。

它们共同的反面教材都是「开发态看起来没问题」。默认无实现要在启动路径上验证，根导出要在打包产物上验证——**验证必须发生在用户真正会遇到的那条路径上，而不是我们最方便的那条路径上。**
