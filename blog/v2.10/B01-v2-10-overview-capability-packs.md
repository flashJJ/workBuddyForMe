# 把能力做成可装卸的包：清单、可逆副作用与管理页

我们的桌面 AI 应用一直有两类能力：技能和 MCP 服务器。它们能做的事不少，但接入方式一直很原始——用户要在设置页里手填 MCP 的启动命令，或者把技能文件手工放进应用数据目录。能用，但不像产品：能力不能打包分发，不能一键装卸，也看不到「它现在到底生效了没有」。

这次能力包迁移只回答一个问题：**怎样让能力像积木一样装上、停用、再拿走，而且每一步都可回滚。**

## 一、痛点不是「没有插件」，而是「没有边界」

手动配置的问题不止是麻烦，而是三件事同时缺位：

- **不可分发**：一个调好的技能，只能靠截图和口述交给别人；
- **不可逆**：手工放进目录的东西，卸载时没人知道该删哪些文件；
- **不可核对**：配置完只能「感觉它在」，没有状态、没有句柄、没有错误记录。

如果直接做插件市场，这些问题会被放大：市场意味着远程分发、自动更新、任意代码执行，而我们的产品是单机、本地优先、无账号的。于是方向被收窄成一条：**先做一个本地、显式、可逆的能力包机制，市场以后再说。**

## 二、一个能力包长什么样

能力包就是一个 ZIP，根目录只允许两个东西：清单文件 `capability.json`，以及 `payload/` 目录。清单声明它是什么、需要什么权限、入口在哪、每个文件的内容哈希是多少。

精简后的清单形状如下：

```json
{
  "id": "com.example.weekly-review",
  "version": "1.0.0",
  "kind": "skill",
  "name": "周复盘助手",
  "permissions": ["skill:install"],
  "entry": "payload/skill.json",
  "dependencies": [{ "id": "com.example.base", "version": "1.0.0" }],
  "checksums": { "payload/skill.json": "<sha256>" }
}
```

清单之外的一切都放在 `payload/` 里，结构固定，解析器不需要猜。ZIP 里出现第三个散落文件，安装直接拒绝。

## 三、安装是一条 fail-closed 校验链

安装入口只有一个：用户自己上传 ZIP。没有后台拉取，没有「检测到新版本自动装」。上传之后依次过这些检查：

1. 是不是合法 ZIP、清单是不是合法 JSON；
2. 清单字段是否满足 schema（id、version、kind、权限白名单）；
3. 该 kind 是否已接入 effect；
4. 必需权限是否声明；
5. ZIP 内路径是否安全、是否只有清单与 `payload/**`；
6. `checksums` 是否覆盖 `payload/` 全部文件，且逐一 sha256 匹配；
7. 依赖包是否已安装且版本匹配、同 id 是否冲突。

任何一步不通过，返回 422，**磁盘上不会落下任何文件**。校验是纯函数，落盘发生在校验全部通过之后，这个顺序是刻意的。

## 四、effect 必须可逆

「启用」不是改一个状态字段，而是真的向系统注册副作用；「停用」必须把同一个副作用撤干净。两类已接入的能力，副作用都很具体：

| kind | 启用时做什么 | 停用时做什么 | 记录句柄 |
|---|---|---|---|
| `skill` | 把 `payload/` 复制到技能目录，触发技能重扫 | 删除该技能目录并移除技能状态行 | 技能目录名 |
| `mcp` | 读取 `payload/server.json`，创建 MCP 服务器 | 按句柄移除 MCP 服务器 | 服务器 id |

句柄（effectRef）落在数据库行里，所以停用不依赖进程内缓存，重启后也能撤销。启用失败会把状态退回 `disabled` 并记下 `lastError`；安装阶段启用失败则连包目录和记录一起删掉，不留半启用状态。

## 五、管理页把状态摆到台面上

管理页做四件事：上传安装、列表、启停/卸载、下载示例包。列表里每条能力都展示权限徽章、kind、版本、状态、effect 句柄和最近一次错误。这样「装了但没生效」不再是一个只能靠猜的问题。

上传有明确上限：单个 ZIP 不超过 20MB；空文件、缺少文件字段、非 ZIP 都按 422 拒绝。安装成功后列表自动刷新，失败则显示「清单/校验和/权限/依赖不满足」，而不是一句笼统的「出错了」。

## 六、外部代理：只留接口缝

外部代理（能在本机跑任务的第三方 agent 运行时）这次不接实现，只留一个接口：提供方声明 `id`、`label`、`available()` 和 `run(input, signal)`，注册进注册表后才可被发现。默认注册表为空，`available()` 为假，核心功能完全不受影响。

为什么先留缝不接实现？因为具体实现会牵出预算、审批、证据回传、密钥隔离四套约定。这些约定没定下来之前接任何一个实现，都会把临时形状固化成契约。

## 七、刻意不做的三件事

- **不做插件市场**：不做远程索引、不做评分、不做一键分发；能力包只能由用户本地选择。
- **不做静默安装/自动更新**：安装永远是显式上传，更新等同于重新安装，不后台替换用户文件。
- **不把能力包做成任意代码入口**：本期只登记既有资源类型（技能、MCP 配置），不执行包里自带的脚本。

## 八、门禁数字

| 项 | 结果 |
|---|---|
| 类型检查 | 14/14 包通过 |
| 静态检查 | 0 error，单文件 300 行门禁通过 |
| shared 单测 | 321 例 |
| database 单测 | 236 例（含能力包登记表迁移） |
| core 单测 | 1162 例（含能力包 3 例） |
| web 单测 | 594 例（含能力包 API 2 例、导航 11 项） |
| Web 端到端 | 120/120，生产模式产物 |
| 桌面冒烟 | 10/11，未过的一项依赖真实桌面会话 |

能力包专项端到端是 2 例：示例包安装→技能出现→停用→卸载，以及非法包返回 422。

## 九、这一版回答了什么

它没有让产品变成插件框架，只把「能力」从手工配置变成了有清单、有校验、有句柄、可撤销的本地对象。下一步的难点不在功能，而在契约：清单每个字段到底拦什么、错误码怎么给、哪些失败必须拒绝而不是降级。

接下来一篇先把清单契约讲透：六类 kind 为什么只支持两类、必需权限怎么映射、依赖与冲突在什么时机拒绝，以及签名为什么只记录不验证。
