# ZIP 不是压缩包，是攻击面：能力包解析的四道闸

能力包安装器最容易写错的地方，不是解压，而是解压之后。ZIP 是一个允许任意相对路径的容器：条目名可以是 `../../.ssh/authorized_keys`，可以带反斜杠、NUL 字节、盘符冒号，也可以以 `/` 开头。解析器如果直接把条目名拼到目标目录上，压缩包就成了写文件原语。

这篇复盘能力包解析的实现顺序：四道闸分别拦什么、为什么非法包必须 422 且一个字节都不落盘、测试用例怎么设计，以及我们为什么把「拒绝路径」放在「正常路径」之前写。

## 一、解析在落盘之前，全部在落盘之前

安装流程的边界很清楚：

```text
上传字节 → 解析 ZIP → 校验清单 → 校验结构 → 校验哈希 → 返回内存中的文件表
                                                     ↓
                                          服务层才开始 mkdir / writeFile
```

解析是一个纯函数：输入字节，输出「清单 + 文件表」，不做任何磁盘写入。这个划分不是为了好看，而是为了让「失败不落盘」成为结构上的必然，而不是靠每个分支记得清理。只要校验函数没返回，后面的目录创建代码根本不会执行。

它的返回类型本身就是一份「已通过校验」的声明：

```ts
interface ParsedCapability {
  manifest: CapabilityManifest;          // 已通过 schema、类型与权限检查
  files: Record<string, Uint8Array>;     // 已通过路径、结构与哈希检查
}
```

调用方拿到的文件表不需要再判断「这个 key 安不安全」，因为不安全的东西根本进不了这个返回值。把校验责任收束在一个函数里，比在落盘循环里到处 `if` 更不容易漏。

## 二、闸一：这个 ZIP 能不能解开

第一道闸只有一件事：`unzipSync` 能不能成功返回条目表。失败就当作「不是有效的 ZIP」拒绝。

这里不做「尽量解析」的容错。一个损坏的压缩包如果被部分解析，后面所有校验都建立在残缺的文件表上，等于用不可信输入做可信判断。宁可整体拒绝，也不接受半份包。

## 三、闸二：路径逐条拒绝

这是最关键的一道闸。ZIP 条目名在解压后仍是字符串，必须自己判断它能不能变成安全的落盘路径。我们逐条拒绝五类输入：

| 输入特征 | 例子 | 为什么危险 |
|---|---|---|
| 反斜杠 | `payload\..\x` | 基于 `/` 的判断会被绕过，Windows 下反斜杠同样是分隔符 |
| NUL 字节 | `payload/skill.json\0.txt` | 下游 API 可能在 NUL 处截断，校验的名字和实际写出的名字不一致 |
| 冒号 | `payload/abc:/x`、`payload/file:stream` | 盘符与备用数据流语法，可能写出目标目录之外 |
| 绝对路径 | `/payload/skill.json` | 拼接时可能丢弃基目录，直接落到系统根 |
| `..` 段 | `payload/../../x` | 最经典的目录穿越，逐段上跳即可逃出包目录 |

判定用的是「段」而不是字符串包含：把路径按 `/` 拆开，只要某一段恰好是 `..` 就拒绝。这样 `payload/..hidden/x` 这种合法文件名不会被误杀，而 `payload/../x` 一定被拦住。

反斜杠和冒号看起来像 Windows 细节，但它们是同一类问题的不同写法：**校验时看到的路径，和实际写文件时解释的路径，必须是同一个路径。** 只要两者可能产生分歧，就必须在入口拒绝。

一个恶意包可能同时混用多种写法：

```text
payload/skill.json          # 正常入口，用来让清单看起来合法
payload/../../../notes.txt  # 用 / 逐段上跳
payload\..\..\notes.txt     # 用反斜杠绕过按 / 的判断
payload/abc:/x.txt          # 用盘符语法改写目标位置
```

注意第一行：攻击包通常会保留一个合法的 entry 和正确的哈希，让清单校验通过，把恶意条目藏在其它文件里。所以路径校验必须覆盖**所有条目**，不能只检查 `entry` 指向的那一个。

## 四、闸三：根目录结构白名单

路径安全之后，还要限制「允许出现什么」。规则只有一条：除清单文件外，所有条目都必须以 `payload/` 开头。

这条规则拦住的不只是杂文件，还包括一种常见的伪装修复：包里放一个 `payload/` 之外的 `skill.json`，指望加载器「顺手找一下」。结构白名单让入口唯一，也让后面的 checksums 覆盖范围有明确边界——只有 `payload/` 下的文件需要被哈希覆盖。

目录条目（以 `/` 结尾）会被单独排除，不参与文件校验。否则一个空目录就能让「checksums 必须覆盖全部文件」的规则失效。

## 五、闸四：checksums 必须全覆盖，逐一比对

清单里的 `checksums` 不是抽样，而是全集。校验逻辑可以压成四步：

```ts
for (const file of payloadFiles) {
  const expected = manifest.checksums[file];
  if (!expected) reject(`checksums 缺少文件：${file}`);
  if (sha256(files[file]) !== expected) reject(`校验和不匹配：${file}`);
}
const extra = Object.keys(manifest.checksums)
  .filter((file) => !payloadFiles.includes(file));
if (extra.length > 0) reject(`checksums 声明了不存在的文件`);
```

这里有三个容易漏的点：

1. **缺失要拒绝**：payload 里有、checksums 里没有，说明这个文件未经声明，不能装；
2. **多余要拒绝**：checksums 里声明了、payload 里没有，说明清单和内容对不上，同样不能装；
3. **entry 必须在内**：清单的 `entry` 除了要真实存在，还必须在 checksums 里，否则入口文件本身没有完整性保护。

比较用的是文件字节的 sha256，不是文件名、不是大小、也不是压缩前的原始内容。压缩包里的内容就是最终落盘的内容，哈希必须对这份字节负责。

## 六、非法包：422，且不落任何文件

所有解析期错误统一走 422，错误信息带上具体文件和原因：

- 不是合法 ZIP；
- 缺少清单文件、清单不是合法 JSON；
- 清单 schema 不通过；
- kind 未接入、缺少必需权限；
- 路径非法、根目录有散落文件；
- entry 悬空、checksums 缺失/多余/不匹配。

因为解析在落盘之前完成，这些错误发生时目标目录还没有被创建。安装器不需要「先写再删」，也不存在清理不干净的中间态。这一点在测试里是可以直接断言的：安装失败后，能力包根目录下不应该出现以该 id 命名的目录，数据库里也不应该有对应行。

统一用 422 而不是 400，是因为这些输入在语法上「像一个请求」，只是内容不满足契约。前端据此可以把错误归到「这个包不合格」，而不是「请求发错了」；两者对用户意味着完全不同的下一步动作。

## 七、测试用例怎么设计

正常路径只有一条，异常路径有一串。我们按「闸」分组设计用例，每个用例只验证一件事：

| 用例 | 构造方式 | 期望 |
|---|---|---|
| 非 ZIP 字节 | 直接传一段文本 | 422，无落盘 |
| 缺清单 | ZIP 里只有 payload | 422，无落盘 |
| 清单非 JSON | 清单写坏一个括号 | 422，无落盘 |
| 未知 kind | kind 填一个不在枚举里的值 | 422，无落盘 |
| 未接入 kind | kind 为 workflow | 422，提示「尚未接入」 |
| 缺必需权限 | permissions 为空 | 422 |
| 路径穿越 | 条目名 `payload/../../escape` | 422，且目标目录外无文件 |
| 根目录散落文件 | 多一个 `README.md` | 422 |
| 哈希缺失 | checksums 为空对象 | 422 |
| 哈希不符 | checksums 写一个错误哈希 | 422 |
| 哈希多余 | checksums 多声明一个不存在的文件 | 422 |
| entry 悬空 | entry 指向 payload 里没有的文件 | 422 |
| 重复安装 | 同一份包安装两次 | 第二次 409 |

这些用例共用同一个 ZIP 构造器：在测试里用 `zipSync` 现场拼包，而不是把二进制 fixture 提交进仓库。好处是每个用例的文件名、内容、清单都能就地可读，出问题时不需要再解压一个黑盒样本。

## 八、真实哈希，不要占位符

正常路径的测试必须用**真实字节算出来的哈希**：

```ts
const bytes = strToU8(JSON.stringify(skill, null, 2));
const checksums = { 'payload/skill.json': sha256(bytes) };
```

不能用 `'a'.repeat(64)` 之类的占位串。占位串能让「哈希不符」的用例通过，却会让正常路径永远装不上；更隐蔽的是，它掩盖了编码、换行、序列化顺序这些真实差异——测试以为在验证安装，实际只验证了「错误分支会报错」。

反过来，负向用例可以故意写一个固定错误哈希，因为它的目的就是触发不匹配。**正向用例用真哈希，负向用例用假哈希，两者的意图必须在代码里看得出来。**

## 九、教训：先把拒绝路径写完

这次实现最有用的一条顺序经验：**先写拒绝路径，再写正常路径。**

先写正常路径，人会本能地让代码「跑通」：路径拼接能写、ZIP 能解、文件能落盘，于是所有边界都变成事后补丁。先写拒绝路径则相反：先把「什么样的包绝对不许进」列成清单，再把每条拒绝写成断言，最后才让合法包通过。这样正常路径是通过闸门的结果，而不是绕过闸门的默认行为。

配套还有三条：

- 校验保持纯函数，磁盘操作只发生在校验之后；
- 每个拒绝都带具体文件与原因，不做笼统的「安装失败」；
- 失败用例不只断言状态码，还要断言「没有留下文件/记录」。
