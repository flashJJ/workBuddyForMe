# 能力包清单的契约设计：一切不明确的地方都拒绝

能力包能不能安全地装，取决于清单有没有把话说清楚。清单不是一个「描述文件」，而是一份安装前的承诺：我是谁、我要什么权限、我的入口在哪、我带来的每个字节的哈希是多少。安装器的任务只有一件——**逐条核对承诺；核对不了，就拒绝。**

这篇讲清单字段的硬约束、六类 kind 的权限映射、依赖与冲突的判定时机，以及签名为什么只记录不验证。

## 一、固定结构：清单 + payload

一个合法能力包的 ZIP 根目录只有两种条目：

```text
capability.json         # 能力包清单（根目录唯一允许的散落文件）
payload/                # 能力内容，全部文件必须被 checksums 覆盖
  skill.json            # skill 包的入口
  server.json           # mcp 包的入口
```

这不是风格偏好，而是为了让解析器只处理一种形状。只要 ZIP 里出现 `README.md`、`docs/` 或任何不带 `payload/` 前缀的文件，安装即被拒绝，不会「顺手忽略」。忽略未知文件看似宽容，实际上是在替攻击面做减法时给自己留后门。

## 二、字段与硬约束

清单用 zod 校验，字段不是随便填的：

| 字段 | 约束 | 拒绝时机 |
|---|---|---|
| `id` | 3–80 字符，小写字母或数字开头，仅允许小写字母、数字、点、下划线、中划线 | 解析清单时 |
| `version` | 形如 `1` / `1.0` / `1.0.0` 的数字段 | 解析清单时 |
| `kind` | 六类之一，且必须是已接入 effect 的类型 | 解析清单时 |
| `name` | 1–80 字符 | 解析清单时 |
| `description` | 最多 500 字符，缺省为空串 | 解析清单时 |
| `permissions` | 只能取自权限白名单，缺省为空数组 | 解析清单时 |
| `entry` | 必须匹配 `payload/...`，且真实存在、被 checksums 覆盖 | 解析清单时 |
| `dependencies` | 最多 20 条，每条含 id 与可选 version | 安装前 |
| `checksums` | 相对路径 → 64 位小写十六进制 sha256 | 解析清单时 |
| `signature` | 可选，最长 4096 字符 | 只记录，不验证 |

id 的大小写与字符集限制不是洁癖。它会直接变成磁盘目录名（`capabilities/<id>/`），也会变成数据库主键。放开大小写和大字符集，就等于允许两个视觉相同、字节不同的 id 共存，后面所有按 id 查找的逻辑都会出现「明明装了却找不到」。

清单里未声明的字段不会进入解析结果，`description`、`permissions`、`dependencies`、`checksums` 都有明确缺省值。缺省不等于放行：checksums 缺省为空对象，但安装时 entry 必须能在其中找到哈希，空对象会在后续校验里被拒绝。

## 三、entry 是唯一入口，不能悬空

`entry` 指向 payload 里真正被加载的那个文件。三条规则同时成立才算通过：

1. 必须位于 `payload/` 下；
2. 该文件必须真实存在于 ZIP 中；
3. 该文件必须出现在 `checksums` 里，且哈希匹配。

对 skill 包还多一条：`entry` 必须恰好是 `payload/skill.json`。这是为了让技能加载器只认一个已知形状，而不是在包里猜「哪个 JSON 才是技能定义」。MCP 包则要求入口是 `payload/server.json` 形状的配置，字段在 effect 阶段再校验一次。

## 四、六类 kind，两类可执行

清单层保留六种能力类型，但这次只有两种真正接入 effect：

| kind | 必需权限 | 这次是否可安装 |
|---|---|---|
| `skill` | `skill:install` | 是 |
| `mcp` | `mcp:connect` | 是 |
| `workflow` | `workflow:install` | 否，422 |
| `pet-action` | `pet:action` | 否，422 |
| `event-script` | `events:write` | 否，422 |
| `report-widget` | `report:widget` | 否，422 |

这里有一个有意的双层设计：schema 接受六类，解析器只放行两类。前者保证未来扩展时清单格式不用改；后者保证现在不会出现「清单合法、安装成功、但什么都没发生」的假象。对未接入类型，错误信息必须明确到「该能力类型尚未接入」，而不是含糊的「安装失败」。

## 五、权限是声明白名单，不是授权结果

`permissions` 数组只表达「这个包声明自己需要什么」，安装侧做的是**覆盖检查**：清单里必须出现该 kind 的必需权限，否则拒绝。未知权限字符串会直接被 schema 拒绝，因为白名单之外没有「先装着以后再说」的语义。

需要说明的边界是：通过权限检查不等于用户授权。能力包的权限目前是「安装即接受」的本地契约，安装动作本身就是用户的显式选择；运行时的高风险操作仍然走既有的工具权限闸门。把这两层混在一起，会让「装了一个包」被误读成「允许它做任何事」。

## 六、依赖必须已安装且已启用

依赖检查发生在写入任何文件之前，规则有两条：

- 依赖 id 必须能在当前**已启用**的能力包里找到；
- 若清单写了 `version`，则必须与已安装版本**精确相等**（不做 semver 范围匹配）。

精确匹配是保守选择。范围匹配需要一套版本比较与冲突求解，而这次的目标是「能可靠地装卸」，不是「做一个包管理器」。写死版本至少保证：同一个依赖 id 不会因为不同范围解析出两个版本，进而让 effect 行为不可预测。

代价也很直接：依赖升级时不能自动跟随，下游包必须显式换一份清单再安装。这个约束在单机、小规模能力包的场景里可以接受；一旦包数量上来了，就需要真正的版本求解，而不是把精确匹配悄悄改成前缀匹配。

依赖缺失或版本不符都返回 422。已安装但被停用的依赖同样算缺失——停用的包不产生 effect，不能拿来当别人的运行前提。

## 七、两种冲突，两个时机

冲突分两类，处理时机不同：

| 冲突 | 判定点 | 结果 |
|---|---|---|
| 同 id 重复安装 | 解析与依赖检查之后、落盘之前 | 409，磁盘不变 |
| 技能目录同名 | 启用 effect 内、复制之前 | 409，安装回滚删包删行 |

同 id 冲突早拒绝，因为它是纯数据问题；技能同名冲突只能在 effect 执行时发现，因为要读技能清单才知道名字。后者失败时，安装流程会把已经写入的包目录和数据库行一起清掉，避免留下一个「装了但永远启不来」的记录。

## 八、失败即拒绝，不留半成品

下面是这次实现里明确拦截的失败面，全部 fail-closed：

- 不是合法 ZIP、清单缺失、清单不是合法 JSON；
- 清单 schema 不通过、kind 未知、权限未知；
- kind 未接入 effect、缺少必需权限；
- 路径不安全、根目录有散落文件；
- entry 悬空、checksums 缺文件/多文件/哈希不符；
- 依赖缺失或版本不符、同 id 重复安装。

这些错误统一走 422（冲突走 409），并且都在落盘之前或回滚之后发生。换句话说，**失败不会在磁盘上留下半个包，也不会在数据库里留下一个「看起来装了」的行。**

## 九、签名只记录不验证

清单允许带 `signature` 字段，本期只做长度与类型校验，然后原样存进数据库，不参与安装决策。

这是一个明确的取舍：校验和解决的是「文件有没有被改动」，签名解决的是「这份清单是谁发的」。前者已经能防住解包后内容被替换，后者需要密钥分发、信任根和撤销机制，单机产品在没有账号体系的前提下很难做对。与其做一个半吊子的签名验证，不如把字段先留出来，并在文档里写清楚「现在不验证」。

字段也不是完全没用。它随清单一起存进数据库快照，未来接入验证时，历史记录里至少还有原始签名可查；只是当前任何签名值都不会改变安装结果。这种「记录但不决策」的字段，必须在契约里写明，否则调用方会误以为它是一道闸。

## 十、契约的价值在于拒绝得清楚

这份清单的设计原则可以压成一句话：**凡是安装器无法核对的东西，都不允许它悄悄通过。** 字段有边界、权限有白名单、入口有唯一形状、依赖有精确版本、失败有明确错误码。等未来要接 workflow、桌宠动作、事件剧本、报告卡片时，新增的是 effect，而不是把契约放松。

下一篇换到更底层的位置：ZIP 本身是一个充满陷阱的容器，路径穿越、反斜杠、NUL、盘符、绝对路径、校验和覆盖不全，任何一条漏掉，前面的契约都白写。
