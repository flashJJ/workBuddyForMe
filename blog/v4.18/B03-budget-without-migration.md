# 给会话加 token 预算，但不改数据库

成本护栏是典型的「有比没有好，但不知道放哪」的功能。

新建一张预算表最直接，但它意味着数据库迁移、备份格式变化和升级顺序问题。对一个本地优先、单人维护的桌面应用来说，这些成本远高于功能本身。

这一版的目标很明确：**预算可用、可见、可关闭，但零迁移。**

## 一、预算到底算什么

第一版只算 token，不做金额换算。

原因很实际：金额依赖供应商计价表，价格会变、套餐会变、缓存命中规则也会变。把金额写进预算，等于把一个持续变化的外部契约固化进本地数据库。

token 口径则稳定得多：每轮请求实际消耗的 prompt 与 completion token 已经由供应商返回，直接累加即可。

预算作用在会话级：

- 未设置上限时完全不影响旧行为；
- 设置后，累计消耗达到 80% 提示，达到 100% 拦截；
- 拦截返回独立错误码，与模型失败码互不混用。

## 二、存在哪：复用设置 JSON

应用已经有一个键值设置表，用来存助手备用模型、界面偏好等轻量配置。预算沿用同一模式：

- 助手备用模型：`assistant-fallback-models`，助手 id 映射到模型 id；
- 会话 token 预算：`conversation-token-budgets`，会话 id 映射到上限；
- `null` 表示取消限制。

这带来三个好处：

1. 零数据库迁移，覆盖安装即可；
2. 备份与恢复自动包含，不需要单独处理新表；
3. 删除会话时顺手清理对应键，不会留下孤儿数据。

代价是查询不如独立表灵活。但预算只在会话设置与每轮请求两个位置读取，完全不需要复杂查询。

## 三、阈值为什么是 80 / 100

80% 是提醒，100% 是拦截。

- 只做 100% 拦截，用户会在毫无预警的情况下被中断；
- 只做 80% 提醒，用户可能忽略提示，下一轮直接撞墙；
- 两个阈值配合，给用户留出一到两轮的调整时间。

提醒出现在对话页，而不是设置页：用户在聊天过程中才会感知到成本，跑到设置页看数字是反直觉的。

拦截时保留输入并提供调整入口，不直接丢弃用户已经写好的内容。

## 四、和上下文预算不是一回事

这里有两个容易混淆的预算：

- **上下文预算**：这一轮能装多少历史与证据，决定回答质量；
- **会话 token 预算**：这段会话总共能用多少 token，决定成本上限。

前者是每轮的装配问题，后者是跨轮的累计问题。两者共用 token 口径，但作用域与失败方式完全不同：

- 上下文预算不足时，系统压缩或截断历史，对话继续；
- 会话预算耗尽时，系统拒绝发起新一轮请求，明确告诉用户原因。

实现上不要把它们塞进同一个配置对象，否则以后调整其中一个会误伤另一个。

## 五、累计从哪里来

每轮完成后，供应商会返回 usage。把 prompt 与 completion 累加，写入会话的累计计数。

需要注意两个边界：

- 流式中断时可能没有完整 usage，按已收到的部分计入，不阻塞下一轮；
- 供应商未返回 usage 时，不做估算，避免把猜测写进成本账。

宁可少算，也不要让用户看到一个无法解释的数字。

## 六、可见性怎么保证

三个位置足够：

1. 会话设置里显示当前上限与已用比例；
2. 对话页在 80% 时出现一行提示；
3. 100% 拦截时错误态给出「调整预算」入口。

不做独立仪表盘。预算是一个护栏，不是分析产品；真正的成本分析需要按模型、按供应商、按时间段聚合，那是另一个版本的事。

## 七、测试怎么写

预算逻辑适合纯函数测试：

- 未设置上限时不触发任何提示；
- 79% 不提示，80% 提示，99% 仍提示；
- 100% 拦截且返回独立错误码；
- 取消限制后恢复可用；
- usage 缺失时按已收到部分累计，不抛错。

再补一条 API 集成测试：设置预算、跑一轮、检查提示事件，再跑一轮直到拦截。

## 八、零迁移的边界

零迁移不等于零成本。设置 JSON 方案有两个已知限制：

- 不支持按时间范围聚合查询；
- 并发写入需要依赖设置服务本身的串行化。

这两点在当前规模下都不是问题。如果未来要做成本报表，再引入独立表也不迟；那时数据模型已经稳定，迁移反而更安全。

## 九、小结

预算功能的关键不是算法，而是位置：

- 存在既有设置里，避免迁移；
- 只算 token，不绑定计价表；
- 80% 提醒、100% 拦截；
- 只在用户真正感知成本的位置展示。

下一篇换一个方向：当一个关键词同时存在于会话、任务、流程、会议和知识库里，怎么让用户一次找到。
