# 一个入口，五种深链：跨域检索怎么不变成第二个列表

内容散落是本地应用的通病：会话在对话页，任务在任务页，流程有运行记录，会议有纪要，知识库还有自己的文档列表。

用户真正想要的不是「每个页面都能搜」，而是「输入一个词，告诉我它在哪，点一下就过去」。

这一版把五类内容收进一个检索弹层。

## 一、先统一结果契约

检索最怕每个域返回不同的结构。UI 到处写 `if (domain === 'chat')`，三周后没人敢改。

所以第一步是定义统一结果项：

```text
{
  domain,      // chat | task | flow | meeting | knowledge
  id,          // 域内稳定标识
  title,
  snippet,     // 单行压缩，≤240
  timestamp,
  deepLink,    // 站内深链
  action       // open | resume | copy
}
```

有了这个契约，分组、键盘选择、深链跳转都能写成一套通用逻辑。

上限也写进契约：单域最多 10 条，总计最多 50 条。这不是性能数字，而是产品决策——结果太多等于没有结果。

## 二、数据源分两层

五类内容看起来一样，底层只有两种数据源：

- 会话、任务、流程、会议：追加式事件日志，带作用域与全文索引；
- 知识文档：文档表，只有文件名、来源、摘要。

所以检索分两条路径：

1. 事件四域走现有的全文检索接口，按作用域过滤；
2. 知识域先列知识库，再逐个查询文档列表的 `q` 参数。

知识文档刻意不读正文、不触发解析：一次检索不应该引发后台编译任务。

## 三、知识库为什么要并发

知识库数量不确定，串行查询会让弹层随着库数量线性变慢。

实现上限制并发 4、单库最多 5 条：

- 并发 4 足以覆盖常见规模，不会把本地数据库压垮；
- 单库 5 条防止某个大库占满结果；
- 单库失败静默跳过，不让一个坏库拖垮整个知识域。

最终结果按文档 id 去重、按时间排序，再截到单域上限。

这里有个容易忽略的细节：知识库列表本身失败与单库查询失败要区别对待。前者让整个知识域标记失败，后者只跳过当前库。

## 四、单域失败不能拖垮全部

检索弹层最糟糕的体验是：四个域都有结果，但界面一片空白，因为第五个域超时了。

所以按域并发，每个域独立结算：

- 成功的域正常展示；
- 失败的域记录名称，在结果底部显示「某域检索失败」；
- 用户仍然可以打开其他域的结果。

这不是容错细节，而是检索产品的基本要求：部分可用好过整体不可用。

## 五、深链是最后一公里

结果不可点击，检索就只是列表。五类内容各自的深链：

- 会话：会话 id + 消息 id，打开后定位到具体消息；
- 任务：任务详情；
- 流程：优先运行详情，缺少工作流 id 时回落到时间线；
- 会议：会议记录；
- 知识：知识库 id，页面自动选中目标库。

深链统一由结果契约的 `deepLink` 承担，UI 不拼路径。这样以后新增域只需要加一个映射函数。

## 六、最近搜索只存本机

最近搜索能显著减少重复输入，但它也是隐私敏感数据。

这一版的做法：

- 只存本机 localStorage，最多 5 条；
- 存储损坏时静默降级为空列表；
- 提供一键清除；
- 界面明示「本机检索」。

不存服务端，不进事件日志，不参与任何同步。

## 七、键盘与过滤器

弹层打开后自动聚焦输入框，300ms 防抖，输入变化时中止上一次请求。

键盘操作：

- 上下选择；
- 回车打开；
- `Ctrl+Enter` 在新面板打开。

域过滤器是一排 chips，选择某个域后只查该域。空结果时分两种文案：全部域为空时建议换关键词，当前域为空时建议去掉过滤器。

这两种空态看起来只是文案差异，实际决定了用户下一步会不会继续用。

## 八、为什么不建新索引

最直接的方案是为五类内容建一套统一索引。但代价是：

- 需要同步五个写入路径；
- 需要处理历史数据回填；
- 需要新增迁移与一致性校验。

而现有事件日志已经带全文索引，文档表加一个 `q` 参数就能覆盖标题/来源/摘要。接线足够解决问题，就不值得再养一套索引。

## 九、怎么验证

- 五个域各至少一条结果与正确深链；
- 单域失败时其他域仍可用；
- 空结果引导可点击；
- 键盘操作与鼠标一致；
- 检索不发送远端请求。

端到端用同一个关键词同时命中会话事件与知识文档，断言分组出现，再分别打开两类深链。

## 十、小结

跨域检索的难点不在搜索，而在收口：

- 统一结果契约；
- 数据源分两层；
- 单域失败隔离；
- 深链由契约驱动；
- 最近搜索只留本机。
