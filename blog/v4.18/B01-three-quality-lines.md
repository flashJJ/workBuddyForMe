# 三条质量线放进同一个版本：稳、找得到、可评测

一个本地优先的桌面 AI 应用，功能列表已经很长之后，继续加能力的收益会越来越低。真正让人卡住的，是三类问题：失败后只能重来、内容散落在十几个入口里找不到、改了上下文策略却不知道有没有变差。

这一版把这三件事放进同一个版本：故障恢复、跨域检索、离线 A/B 回放。

## 一、三个问题，其实是三条线

复盘近几轮使用记录，问题可以归成三类：

- 供应商限流或超时，整轮对话直接失败，只能手动换模型；
- 会话、任务、流程、会议、知识库各有一套列表，找一个关键词要挨个点；
- 上下文预算与压缩策略改完后，只能靠单元测试和主观体验判断有没有退化。

逐个修也能交差，但放在一起看，会发现它们都需要同一件东西：**把「坏消息」变成可观察、可行动、可复算的信号**。

- 失败要分类，才能决定能不能自动恢复；
- 检索要有统一结果契约，才能给出可点击的深链；
- 回放要有固定指标，才能判断策略改动是否真的变差。

所以这一版不是三个功能，而是三条质量线。

## 二、目标怎么写才可验收

每一条线都写成能验收的句子，而不是「优化体验」：

1. 可重试故障能自动恢复，且每次切换在界面上看得见；
2. 五类内容能被一个入口检索，结果可直接行动；
3. 同一组 golden 用例能跑两套策略，退化超阈值时命令退出码非 0。

三句话对应三个里程碑，每个都能独立验收，不要求另外两条线完成。

这样做的好处是范围可控：任何一条线卡住，另外两条仍然可以交付，不会把整个版本拖成半成品。

## 三、明确不做什么

版本范围膨胀通常不是因为做得太少，而是因为「顺手也做了」太多。这一版的非目标与需求同权重：

- 不做云同步、云索引、跨设备检索；
- 不做语义/向量全文检索；
- 不做跨供应商负载均衡、自动购买额度、云密钥托管；
- 不改数据库 schema，不引入新的运行时依赖；
- 不做完整的工作流引擎重构、并行/DAG 编排；
- 不做首答性能专项与窄窗视觉复核。

最后一条尤其重要：性能与窄窗复核需要真机和视觉基线，硬塞进这个版本只会让三条线都收不了尾。

## 四、复用优先于新建

判断一个需求要不要做，先问三个问题：

1. 服务端协议已经有了吗？
2. 数据已经写进本地日志了吗？
3. 现有组件能不能加一个参数解决？

以跨域检索为例：会话事件日志、全文检索接口、知识库文档列表都已经存在，缺的只是统一的 UI 消费与深链。正确做法是接线，而不是新建一套索引。

再以故障恢复为例：错误归一化、供应商错误码、SSE 事件通道都已具备，本版只补分类表、备用模型路由和一条可见提示。

回放同理：已有的 golden 夹具、mock 供应商与报告工具都能复用，新增的只是策略参数、指标聚合与阈值判定。

## 五、三条线怎么互相支撑

三条线不是并列的功能，而是有依赖方向：

- 稳与找得到是用户可感知的主线；
- 可评测是质量底座，用来证明前两条线的后续改动没有让上下文变差。

所以回放不追求「跑一次好看」，而追求三件事：

- 同一输入两次运行结果一致；
- 退化用例必须失败；
- 报告本身不含绝对路径、正文与密钥。

只有做到这三点，回放才有资格进入夜间巡检，未来才可能升级为合并门禁。

## 六、度量与验收

没有度量的质量改版容易变成主观争论，这一版留了四个硬指标：

- 静态门禁全绿：类型、lint、行数、目录预算、循环依赖、测试桩、资源与 E2E 隔离；
- 全量单元测试与 API 集成测试通过；
- 两条定向 E2E：429 自动切换、跨域检索并打开结果；
- 回放命令默认策略通过，退化策略按预期失败且退出码非 0。

验收不只看「跑通了」，还要看「失败时能不能定位」：切换有事件、检索有分域失败提示、回放报告有失败项列表。

## 七、风险与回退

每一项改动都写明了回退方式：

- 备用模型是助手级可选字段，不配置时完全沿用旧行为；
- token 预算是设置 JSON 里的可选项，未设置时不生效；
- 检索是独立弹层，关掉入口不影响命令面板与原有列表；
- 回放是独立脚本，不接入主链路，夜间巡检非阻断。

风险最大的部分是自动切换：它改变的是失败后的默认行为。缓解办法是三个边界——只在首字前、只对可重试错误、单轮最多两次——加上每次都可见。

## 八、结果

最终交付没有数据库迁移，没有新增运行时依赖，也没有新增侧栏入口。

留下的是三类可复用能力：统一的失败分类与切换事件、统一的检索结果契约与深链、可复算的上下文保真报告。
