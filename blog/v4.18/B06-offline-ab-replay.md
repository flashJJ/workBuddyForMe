# 离线 A/B 回放：把「上下文变差了」变成可复算的数字

上下文策略是最难验收的一类改动。

改小历史配额、调整压缩水位、限制证据块预算，单元测试都会过，但回答质量可能悄悄下降。人工体验又不可复现：同一段对话，第二次跑出来的上下文可能已经不同。

这一版补了一个离线 A/B 回放入口：同一组用例，跑两套策略，输出保真差异报告。

## 一、为什么不用线上指标

线上指标（点赞率、追问率、会话长度）噪声太大，而且需要真实用户量。

单人维护的本地应用没有这个条件，也不应该把对话内容上传去做评测。所以回放的目标不是「证明回答更好」，而是：

- 同一组固定输入；
- 两套可解释的策略参数；
- 一组可复算的代理指标；
- 退化时命令能失败。

代理指标只用于相对比较，这一点必须在报告里写清楚，避免被当成用户满意度。

## 二、策略怎么定义

策略只切上下文预算，不切模型行为：

```text
名称、上下文窗口、历史条数上限、是否预判压缩
```

- 基线：默认窗口，预判压缩开启；
- 候选：更大窗口，其他参数一致；
- 退化样例：极小窗口、关闭预判压缩。

参数放在 golden 文件里，脚本只负责按名字读取。这样新增策略不需要改代码，也方便以后把不同版本的参数冻结成基线。

两个策略各自新建会话，避免历史互相污染。

## 三、用例怎么跑

一组用例包括三个阶段：

1. 写入两条硬约束记忆（项目代号、文档规范）；
2. 灌入多轮历史与填充对话，其中包含一个只出现在早期的关键事实；
3. 最后用探针读取真实入模消息。

探针不是读数据库，也不是读事件日志，而是让模型报告「它在本次请求里看到了什么」。这是最接近真实上下文的观测点。

探针格式是一行分组标记：

```text
memory=标记A|标记B;citation=标记C;constraint=标记D
```

回复是一组 0/1，表示每个标记是否还在上下文里。

作用域也要区分：约束与引用只认系统提示词，记忆允许出现在历史，但必须排除探针自身——否则探针里的关键词会自己命中自己。

## 四、五项指标

| 指标 | 口径 | 方向 |
|---|---|---|
| 预算占用 | 每轮（系统 + 工具 + 预留 + 历史）÷ 可用窗口的均值 | 越低越好 |
| 截断率 | 触发历史截断的轮次占比 | 越低越好 |
| 记忆保留 | 记忆标记命中率 | 越高越好 |
| 引用保留 | 证据标记命中率 | 越高越好 |
| 约束保留 | 约束标记命中率 | 越高越好 |

预算占用与截断率来自每轮的上下文快照事件，保留率来自探针。

指标全部保留三位小数，避免浮点尾差让两次运行结果不一致。

## 五、门禁分三层

只设一个阈值不够：

1. **绝对下限**：记忆、引用、约束保留率低于设定值直接失败；
2. **相对退化**：候选相对基线下降超过阈值失败；
3. **预算硬上限**：预算占用超过 0.95 失败。

三层分别防三种问题：本来就很差、比之前更差、预算已经失控。

失败时退出码非 0，并打印每条失败项。报告同时落 JSON 与 Markdown：JSON 给机器复算，Markdown 给人看。

## 六、确定性怎么保证

回放报告最容易出的问题是「同一输入跑两次结果不同」。

三个措施：

- mock 模型与 embedding 完全确定性；
- 指标由固定顺序的用例采样聚合，并按固定精度取整；
- 报告除时间戳外不包含任何运行期信息。

测试直接构造两份同输入报告，去掉时间戳后逐字节比较。

真实运行也验证过：同一基线策略在两次独立回放中预算占用完全一致。

## 七、隐私怎么保证

报告只包含数值与固定名称：

- 不含绝对路径；
- 不含聊天正文；
- 不含令牌与密钥。

写入前扫描三类模式：盘符路径、`Bearer` 令牌、常见 API Key 前缀。命中则不写报告并失败。

这条检查不是形式主义：回放脚本很容易顺手把用例正文写进报告，一旦进入夜间产物就会被上传。

## 八、反向验证

回放本身也必须被验证。

用一个退化策略跑同一组用例：

- 窗口缩到很小；
- 关闭预判压缩。

结果是预算占用上升、记忆保留下降，命令按预期失败，退出码为 1。

这证明阈值不是恒真：策略真的变差时，门禁会拦住。

## 九、为什么先接夜间

回放需要起服务、跑多轮对话，耗时明显高于单元测试。

首期接入夜间巡检，标记为非阻断。等报告连续稳定一段时间，再考虑升级为合并门禁。

这个顺序很重要：一个不稳定的门禁会让人开始忽略红灯，比没有门禁更糟。

## 十、小结

回放的价值不是「跑出一个好看的分数」，而是三件事：

- 退化必失败；
- 同输入可复算；
- 报告可安全归档。

做到这三点，上下文策略的改动才从「凭感觉」变成「有证据」。
