# 过程图与阶段化会话之后：七条把「看得见」变成「对得上」的方法论

功能版本和加固版本的区别，往往不在加了多少东西，而在**新增的东西能不能被核对**。这一版给我们的桌面 AI 应用（本地优先、单人开发）加了过程图、节点光线和阶段化会话。三件事看起来都很「展示层」，但真正决定它们能不能长期用的，是背后那几个不太显眼的选择。

这篇不复述功能。先对账交付了什么，再从七个真实场景里提炼方法论，最后交代哪些事刻意没做、哪些边界仍然存在。

## 交付对账

| 方向 | 交付 | 验收方式 |
|---|---|---|
| 过程图 | 五域事件统一投影、两个只读接口、聊天右侧与时间线双入口 | 五域事件夹具可投影；刷新后与事件日志一致 |
| 光线 | 几何、SVG、图层、流动边框四个模块 | 单测覆盖取消、缺失锚点、并发上限与减弱动效 |
| 阶段计划 | 1–8 阶段 Schema、服务端校验、会话/助手/角色卡三处落点 | 边界用例与非法配置拒绝 |
| 会话模型 | 会话覆盖 > 助手绑定 > 系统默认、保存时同事务写入 | 切换、清空、无效模型三类用例 |
| 迁移与备份 | 一次纯加法迁移、备份只加可选字段 | 旧库升级、旧备份恢复、阶段回环 |

数字方面：单测 3122 例、532 个文件；Web 集成 11/11；生产模式 Web e2e 140/140；桌面冒烟 10/11，缺项是与环境相关的历史用例；核心页面 a11y 6/6。首屏 `/chat` 489 kB（较上一版增长 3.2%）、`/settings` 488 kB、`/timeline` 306 kB，都在预算内。

这些数字不该被写成发布报告。它们只回答一个更朴素的问题：**新增能力有没有把原来能用的东西弄坏。**

## 方法论一：事件是唯一真源，图只做投影

过程图最容易走偏的地方，是让它自己维护一份状态：前端收到事件就改图，刷新后再从运行表拼一次。两套来源，迟早对不上。

这一版把边界写死：图不产生事件、不改运行状态、不参与调度。事件日志由聊天、任务、工作流、协作、会议各自写入；图只读它，按业务 id 去重。刷新后的图与事件日志一致，出现差异时去查事件，而不是去查界面。

实时追加也遵守同一套身份规则：快照给一个生成时间作为历史基线，基线之前的事件不补演，基线之后的新身份才进图。这样刷新不会「重放」一遍动画，也不会出现幽灵节点。

**图的可信度等于它和事件日志的一致程度。** 只要还有第二条写入路径，这个一致程度就守不住。

## 方法论二：纯函数投影，历史和实时共用一套规则

投影函数不查库、不读 UI 状态，输入只有事件数组和根信息。同一份事件调用两次，输出必须一样。节点身份全部按业务 id 派生，例如消息是「会话 + messageId」、任务步骤是「runId + stepId」、会议轮次是「会议 id + 轮次序号」。同一身份只更新状态与摘要，不重复建节点。

历史与实时只差输入方式：历史是完整事件数组，实时是一条一条追加。身份表、状态归一、排序规则完全共用。否则最典型的 bug 就是「实时第 3 轮、刷新后第 5 轮」。

纯函数还有一个隐性收益：测试不需要数据库。给一组事件夹具，断言节点数、边、状态即可。**能被纯函数表达的状态，才配叫可回归。**

## 方法论三：未知 payload 必须降级，不能抛错

事件日志是跨版本、跨域写进来的。旧事件缺字段、新事件多字段、某个域载荷被截断，都是常态。投影如果假设「字段一定存在」，一张图就能让整个页面白屏。

这一版做了几层兜底：

- 所有 payload 先过「是不是对象」的判断，取字段失败返回空值；
- 状态归一遇到不认识的值返回 `unknown`，而不是异常；
- 产物引用只在形状完整时才建节点；递归查找限制深度、键数量与数组长度；
- 超过事件载荷上限的内容截断成预览；
- 节点超过上限时保留最近的节点，并把「已截断」标在图上。

这里的原则不是「尽量不崩」，而是**降级必须可见**。`unknown` 状态、截断标记、缺失摘要，都是给用户的证据；静默跳过才是真正的失败。

## 方法论四：同一个组件复用，两个入口只换容器

过程图有两个入口：聊天时从右侧打开，回看时进时间线页。最省事的做法是写两个面板，一个轻一个全。看起来快，维护时会立刻分裂：节点 id 规则、折叠逻辑、截断提示各改各的。

这一版只有一个面板组件。聊天入口把它放进抽屉，时间线入口把它放进页面容器；聚焦车道、折叠运行、截断徽标、错误隔离都在组件内部。两个入口传的是同一个根类型与根 id。

复用带来的不是省代码，而是**同一张图在两个地方不会给出两种解释**。用户从聊天右侧看到的节点，进时间线还能找到同一个节点，因为渲染逻辑只有一份。

## 方法论五：动效必须可关、可暂停、可清理

节点光线是这一版最容易「看起来炫、用起来烦」的部分。所以它从一开始就按可关闭的能力设计：

- 系统开启减弱动效时，不飞行，直接完成；
- 页面不可见时暂停，回来再继续；
- 同一身份正在飞行时重复发射，直接取消，不叠加；
- 同时最多 12 条，超出丢弃新发射，不排队；
- 目标锚点缺失时重试一次，仍失败就放弃，不射向邻近节点；
- 组件卸载时取消全部光线，移除 SVG 与监听器；
- 每帧进度不进 React 状态，图层自己维护。

流动边框只做视觉提示，且对辅助技术隐藏；节点状态必须有文字或徽标，不能只靠动效表达。**动效的及格线是「关掉之后信息仍然完整」。**

## 方法论六：迁移只做加法，备份只加可选字段

这一版动了三个位置：新建会话阶段计划表、给助手与角色卡加可选阶段列、给会话加可空模型列。全部是建表与加列，不重建表、不改旧列、不给旧行补业务默认值。

纯加法带来三个直接结果：

- 旧库启动自动升级，旧行新列为空，行为与升级前一致；
- 应用回退到旧版本时，新列新表留着但旧代码忽略，数据不丢；
- 备份结构不升版，只加可选字段；旧归档缺字段按空值恢复，不阻断其他会话。

计划整份存 JSON，不把选中阶段拆成独立列。拆列会制造双真源：计划里有一个选中项，列里又有一个，任何一次更新都可能只改一边。

**当不确定新结构会不会长期存在时，先只加不删。** 删除与重建应该留给验证充分的版本，而不是顺手做掉。

## 方法论七：门禁写成链路，不写类型

验收最容易糊弄的地方，是把「有 Schema」当成「校验完成」。这一版的口径全部写成可执行链路：

- 不是「阶段计划有上下限」，而是 1/8/9 个阶段、40/41 字标题、12/13 个技能、4000/4001 字文本、越界的选中下标都有用例；
- 不是「图接口存在」，而是未知载荷不抛错、同一身份不重复、超限截断有标记；
- 不是「载入任务能用」，而是非空草稿被阻止、运行中被锁定、载入后不自动发送；
- 不是「模型能切」，而是写入会话字段、切回无模型阶段清空、无效模型被拒绝；
- 生产模式 e2e 140/140 覆盖图面板、会议图与阶段操作；桌面冒烟与历史基线持平；辅助功能检查 6/6。

把口径写成链路，测试才有地方落。**没有回归门禁的功能版本，每次改动都在赌。**

## 纪律：明确不做什么

这一版的范围锁得很死，中途没有破：

- 不做按 token 的光线，不做 Git 提交树、工作树与轮次检查点；
- 不做自由分支会话；
- 不替代工作流编排，不自动连续执行全部阶段；
- 不复制第三方光线组件源码，不引入新的运行时依赖；
- 不做云同步、团队共享、远程能力市场。

每条非目标都对应一个诱惑：「既然有图了，顺手画个提交树吧」「既然有阶段了，顺手自动跑完吧」。单个看都合理，加在一起就会把一个功能版本拖成半年工程。**范围纪律不是不做，而是知道这一版不做。**

## 仍然存在的边界

- 长会话的图仍可能密集，靠聚焦当前运行、折叠其他运行、默认 500 节点上限（最多 1000）与截断提示来控制，而不是承诺「永远清爽」；
- 会议事件是 best-effort 写入，失败不阻断会议，图可能落后于转录；
- 阶段技能只展示名称，不支持拖拽排序；
- 没有计划的会话不显示阶段条，需要助手或角色卡默认阶段先落地；
- 载入任务只写输入框，不自动发送；运行中硬锁阶段条，不排队。

这些边界写在产品里，而不是留给用户去猜。

## 收口：四条可核对的原则

这一版真正想留下的不是三个功能，而是四条能在下一次改动时复查的原则：

1. 每个节点都能找到一条事件，身份可由业务 id 推导；
2. 每个投影同样输入得到同样输出，历史与实时共用规则；
3. 每个降级都有可见标记，未知、截断、缺失都不静默；
4. 每个闸门都有服务端断言，而不只依赖界面禁用。

如果一条结论找不到对应的事件、用例或断言，它就不该出现在图上，也不该出现在这篇复盘里。
