# 一个会话为什么需要「过程图」

我们的桌面 AI 应用是一个本地优先、单人开发的 AI 助手。一次对话不只产生消息：它可能触发任务步骤、工作流节点、多个角色的协作与评审，甚至开一场会议。每一种能力都有自己的时间线，但用户真正停留的聊天页，看到的仍然只是一串气泡。

于是最简单的问题反而最难回答：这条消息触发了哪次运行？产物是哪个步骤生成的？失败发生在第几步？过程图要解决的不是「再加一个图」，而是把散落在各处的运行事件，收束到一条会话之下。

## 四条时间线，各自为政

| 位置 | 已有表达 | 缺什么 |
|---|---|---|
| 聊天页 | 消息、内嵌工具卡片 | 看不到这次会话触发了哪些运行 |
| 任务页 | 步骤时间线 | 回不到触发的消息与上下文 |
| 工作流页 | 节点执行记录 | 与对话、协作运行不连 |
| 协作卡 | 角色轮次与交接 | 无法与会话主线对齐 |
| 会议页 | 发言记录 | 与普通会话完全分离 |

这些页面各自都能用，但用户要做的是「沿一条线往回走」：从产物回到步骤，从步骤回到运行，从运行回到那条消息。数据其实都在 `session_events` 里，缺的是一层把事件翻译成「节点与边」的投影。

## 为什么不让前端自己拼

第一反应是让每个页面查自己关心的事件，再在前端拼成一张图。这个方案很快就会失控：

- 同一份事件在聊天页、时间线页、会议页各拼一次，节点 id、状态归一、排序规则必然漂移；
- 历史加载要靠前端补演，刷新一次就多出一批「幽灵节点」；
- 任何新事件类型都要改多个消费方，测试也无从下手。

所以这一版把投影放到服务端：事件是唯一真源，图是它的只读视图。前端只负责展示与实时追加。

## 三条主线

**第一条是统一投影。** 把消息与工具、任务步骤、工作流节点、协作阶段/交接/评审、会议轮次/发言，都映射到同一套节点、边、车道结构。同一条会话只有一张图，会议则有自己的独立根。

**第二条是实时的光线。** 新节点出现时，从消息气泡或父节点射出一条短光，指向图上的新节点；运行中的节点有流动边框。它只回答一个问题：刚才发生了什么，发生在哪里。

**第三条是阶段化会话。** 一条会话可以保存一组阶段，每个阶段带目标、技能、交付要求与可选模型。阶段不是工作流的替代品，而是普通对话里「先调研、再分析、再交付」的轻量表达。

## 边界：只读投影，不动业务写入

这条边界必须写死：图不产生事件、不改运行状态、不参与调度。`session_events` 仍然由聊天、任务、工作流、协作、会议各自写入；投影只读它，按业务 id 去重，按时间与序号排序。

只读带来三个直接结果：

1. 刷新后的图与事件日志一致，不存在「图上成功、库里失败」的双真源；
2. 某个域的载荷损坏时，投影跳过或降级，不阻断其他域；
3. 回滚只涉及展示层，业务写入路径不受影响。

代价也明确：图只能看到事件里有的东西。运行表的补充字段、未落事件的瞬时状态，不会凭空出现在图上。这条取舍会在后面的接口篇里展开。

## 一个具体场景

用户让助手「调研三个方案并给出对比表」。这一次会话里实际发生了这些事：

- 助手先发一条消息，触发协作运行；
- 协作运行分规划、执行、审查三个角色，执行阶段调用工具检索；
- 工具返回两条结果，其中一条生成了对比表产物；
- 最后一条消息把产物挂回对话。

在没有过程图时，用户看到的是三个气泡和一个附件。产物从哪来、哪一步慢、审查有没有驳回，都要去别处找。有了过程图，节点按时间排开：消息 → 工具 → 产物，协作运行 → 阶段 → 交接 → 评审。点击产物节点能打开文件，点击错误节点能看到错误码。

这个场景也解释了为什么根节点必须单独保留：无论截断掉多少历史节点，用户都要能一眼确认「这是哪条会话的图」。

## 过程图不替代什么

它不替代任务页的完整步骤列表，不替代工作流的画布编辑，也不替代会议的完整纪要。那些页面面向「操作」与「编辑」，过程图面向「回看」与「追查」。两者的信息密度和目标不同，硬合并会让每个场景都变差。

图也不承担调度。点一个等待中的节点，不会让运行继续；点一个失败节点，不会自动重试。它只显示状态，不提供操作入口——这是只读边界的延伸，也是这一版刻意保留的距离。

## 三种读法，一张结构

- **顺读**：从会话根向下，按时间看消息、工具与运行节点，回答「这一路发生了什么」；
- **聚焦**：只看某次运行的车道，查看阶段、交接、评审与错误，回答「这次运行为什么慢/为什么失败」；
- **对照**：在会议页打开独立图，按轮次与发言核对，回答「这个结论是哪一轮谁说的」。

三种读法共用节点、边与车道的语义，用户不需要为每个场景学一套新交互。这也是统一快照结构最实际的收益。

## 验收口径

这一版不按「做了几个页面」验收，而按四个词验收：

- **可读**：一条真实会话能在同一张图里看到消息、工具、任务、工作流与协作节点；节点有状态、有摘要、有车道归属；
- **可定位**：点节点能看到 kind、scope、错误码与产物入口；会议图独立，不混进会话根；
- **可降级**：未知或缺失载荷不抛错，超出上限时保留最近节点并明确标记截断；
- **可回归**：投影、追加、光线都有纯函数用例；全量门禁不降级。

单测 3122 例、532 个文件；Web 集成 11/11；生产模式 Web e2e 140/140；桌面冒烟 10/11，缺项是与环境相关的历史用例；核心页面 a11y 6/6。首屏 `/chat` 489 kB、`/timeline` 306 kB，均在预算内。

这些数字不证明图「好看」，只证明新增的投影与展示没有把原有路径弄坏。
