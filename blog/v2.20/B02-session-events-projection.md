# 从追加事件到过程图：一次纯函数投影要处理的五件事

过程图的数据从哪来？最直觉的答案是「查库」：消息表、任务表、工作流表、协作表、会议表，各查一遍，前端拼起来。我们最后没有这么做，因为图需要的是「发生过什么」的稳定叙述，而不是五张表的当前快照。

这一版只认一种输入：`session_events` 的追加事件。图是它的纯函数投影——不查库、不改事件、不依赖 UI 状态。

## 事件是唯一真源

`session_events` 按 `(scope, scopeId, seq, type, payload, createdAt)` 记录业务事件。聊天写消息与工具轨迹，任务写步骤开始/结束，工作流写节点状态，协作写阶段/交接/评审，会议写轮次/发言/状态。写入方各自负责，读取方只有一个投影函数。

```ts
projectRunGraph({
  rootKind: 'conversation',
  rootId,
  events,          // 已按根过滤
  limit: 500,
  generatedAt,     // 可选，便于测试固定输出
})
```

函数内部只有三步：过滤出属于当前根的会话图事件，按时间稳定排序，交给各域的 apply 函数往同一个 builder 里写节点、边、车道。返回的是一份快照，调用方拿不到任何可变引用。

## 第一件事：节点身份按业务 id 派生

图里最怕的是「同一件事出现两次」。投影给每类节点定了一个由业务 id 拼成的身份，而不是自增序号：

| 节点 | 身份 |
|---|---|
| 会话消息 | `chat:<会话>:message:<messageId>` |
| 工具调用 | `chat:<会话>:tool:<callId>` |
| 任务步骤 | `task:<run>:step:<stepId>` |
| 工作流节点 | `flow:<run>:node:<nodeId>` |
| 协作轮次 | `agent:<run>:round:<round>:<role>` |
| 协作交接 | `agent:<run>:handoff:<handoffId>` |
| 会议轮次 | `meeting:<会议>:turn:<index>` |
| 产物 | `artifact:<attachmentId>` |

节点存在 Map 里，写入即覆盖。`message_started` 建节点，`message_completed`、`message_error`、`message_stopped` 命中同一个 id，只更新状态与摘要。工具、步骤、工作流节点同理。

所以 SSE 重连、历史重放、同一帧到达两次，都不会让节点变多。**幂等不是靠去重数组实现的，而是靠身份本身可推导。**

## 第二件事：未知载荷不能抛错

事件载荷来自五条不同的写入路径，历史数据还会有字段漂移。投影对载荷的态度是「读不到就当没有」：

- 非对象载荷统一转成 `null`，字段读取返回 `undefined`；
- 缺关键 id（messageId、callId、stepId、nodeId、attachmentId）就跳过，不造空节点；
- 状态无法识别时落到 `unknown`，而不是猜一个 `running`；
- 工具轨迹数组最多取前 100 条，产物递归查找限深度 4、数组 50、键 30，防止异常大载荷拖垮投影。

这些限制不是为了「容错好看」，而是为了让损坏数据的影响局部化。一个坏掉的工具条目，不该让整张会话图返回 500。

## 第三件事：排序要稳定，且 seq 不能跨域比较

排序键是 `at → scope → seq → id`。`at` 是业务时间，`scope` 给五域一个固定顺序（chat、task、flow、agent、meeting），`seq` 只在同一个 scope 内可比，最后用 id 兜底。

为什么强调「seq 只在同 scope 内可比」？因为不同写入方各自从 0 递增，跨域比较没有意义。把它当成全局序号，短会话看起来没事，长会话就会把不同域的事件排成一条假的因果链。

## 第四件事：limit 是展示预算，不是查询预算

投影默认最多 500 个节点，上限 1000。超出时保留根节点和最近的 `limit - 1` 个节点，`truncated` 置为 true；只保留两端都还在的边。

这样做的原因很实际：长会话的节点数会远超一屏。全量返回既撑大响应，也让图变成毛线球。截断保留「最近」，是因为用户最关心刚刚发生了什么；根节点单独保留，是为了让图始终有锚点。

## 第五件事：纯函数才配拥有两套调用方

同一份事件，服务端用来生成快照，客户端用来追加实时帧。两边如果各写一套规则，节点身份和状态映射迟早分叉。这一版把「身份表 + 状态归一 + 产物识别」做成共享口径，客户端追加时复用同样的 id 规则，并用快照的 `generatedAt` 作为历史基线。

纯函数带来的可测性也很直接：固定 `generatedAt`、固定事件夹具，同一输入多次调用结果完全一致；重复事件、未知载荷、截断、跨域排序都能写成断言。3122 例单测里，投影与追加的用例就是靠这个性质守住的。

## 一个反例：为什么不能用自增序号

假设节点 id 用「第几个事件」生成。第一次构建时，消息节点是 `node:1`；SSE 重连后同一条消息又到一次，变成 `node:2`。图上立刻出现两条一模一样的消息，所有指向它的边也分裂成两份。

更隐蔽的是历史重放：刷新后前端从旧事件重新拼，编号顺序稍有变化，节点 id 全变，用户收藏的定位、面板选中的节点、光线的去重 id 全部失效。

按业务 id 派生也不完美：如果业务对象本身没有稳定 id（比如某些工具轨迹缺 callId），投影会跳过它。这是有意的——宁可少一个节点，也不要一个每次刷新都换身份的节点。

## 验证方式

投影的测试不需要数据库，也不需要浏览器。夹具是若干条事件，断言只有四类：

- 同一输入调用两次，快照深度相等；
- 同一业务 id 的事件重复到达，节点数与边数不变；
- 缺字段或非对象载荷，不抛错且不产生空节点；
- 超过 limit 时，根节点在、最近节点在、`truncated` 为真、悬空边被移除。

这四类断言覆盖了投影最容易退化的地方，也让「新增一个事件类型」这件事有了固定动作：先补夹具，再补映射。

## 取舍

我们放弃了「从运行表补全摘要」。事件里没有的字段，图上就不显示。好处是没有双真源，坏处是某些运行摘要只能停留在事件载荷的粒度。下一步如果要补，也应该是让写入方把该写的事件写全，而不是让投影去猜。
