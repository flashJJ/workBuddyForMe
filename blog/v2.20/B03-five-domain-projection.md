# 五个域，一张图：过程投影的映射与取舍

聊天、任务、工作流、协作、会议，五个域有五套词汇：消息、步骤、节点、阶段、轮次。如果给每个域各做一张 UI 图，用户要学五套交互，开发者要维护五套布局与状态。

过程图的选择是反过来：先把五域翻译成同一种快照结构，再用一个面板呈现。翻译层就是这一篇要讲的东西。

## 映射总表

| 域 | 事件 | 节点 | 主要边 |
|---|---|---|---|
| 聊天 | 消息开始/完成/失败/停止 | message | root → message |
| 聊天 | 工具轨迹 | tool，可能带 artifact | message → tool → artifact |
| 任务 | 运行开始/结束 | run | conversation → run |
| 任务 | 步骤开始/结束 | task_step | run → step |
| 工作流 | 运行开始/结束 | run | conversation → run |
| 工作流 | 节点状态 | flow_node | run → node |
| 协作 | 阶段 | agent_phase，按角色分车道 | run → phase |
| 协作 | 交接 | agent_handoff | phase → handoff |
| 协作 | 评审 | agent_review | run → review |
| 会议 | 轮次开始 | meeting_turn | meeting → turn |
| 会议 | 发言 | meeting_message | turn → message |
| 会议 | 状态 | meeting_status | root → status |

这张表看起来只是字段对应，真正的难点在三个地方：谁是父节点、什么时候建运行节点、同一业务对象如何保持身份。

## 聊天：消息是主线的骨架

聊天节点全部挂在会话根或消息节点上。消息按 `messageId` 去重，工具按 `callId` 去重。工具轨迹一次可能带多条，投影最多处理前 100 条，并把工具节点挂到触发它的消息下；没有 messageId 时退回根节点。

产物不单独由「产物事件」创建。投影只在工具、步骤、交接等载荷里递归寻找符合形状的产物引用，以 `attachmentId` 建节点并去重。这样做的原因是：产物不是一个独立发生的事件，它是某个动作的结果。把结果挂回动作，图才有因果。

## 任务与工作流：运行是容器，步骤/节点是内容

任务和工作流都先建 `run` 节点，再往下挂步骤或节点。运行节点的状态由运行事件更新，步骤节点由步骤事件更新。失败时额外补一个错误节点，并用 `node_to_error` 连到出错的步骤或节点。

工作流有一个特殊入口：`node_agent_event`。工作流节点内部又跑了协作运行时，内部事件不是挂到工作流运行，而是挂到那个 `flow_node` 下。这样图上的层级是「运行 → 工作流节点 → 协作阶段」，而不是把所有协作事件平铺。

## 协作：角色分车道，轮次与交接各自有身份

协作运行先建 run 节点，再按 `round + role` 建阶段节点，按 `handoffId` 建交接节点，按 `round` 建评审节点。角色会生成独立车道，车道名从 planner/executor/reviewer 映射为「规划/执行/审查」。

交接节点的父节点优先挂到同轮次的阶段节点；找不到就退回运行节点。这是「父节点只指向已存在节点」规则的具体体现：历史事件顺序不保证先有阶段再有交接。

预算事件只更新运行摘要，不建节点。它不改变「发生了什么」的叙事，只改变一个数字。

## 会议：独立根与稳定轮次

会议不混进会话根，而是有独立的 `rootKind`。轮次节点优先使用服务端写入的稳定 `turnIndex`；旧事件没有这个字段时，回落到该 scope 内的 `seq`。

这里踩过一次坑：早期用「自动轮数」当兜底，手动模式下多轮都会落到 `turn:0`，实时帧和快照各建一个节点，图上出现重复轮次。修复方式不是在前端合并，而是让服务端在落消息时生成 `turnIndex`，实时与快照使用同一个身份。**跨端一致的前提是身份来源一致。**

## 边只表达六类关系

边不是装饰，而是因果的最小集合：

- 根到节点：会话/会议主线；
- 会话到运行：一次会话触发了哪次运行；
- 运行到节点：运行内部步骤；
- 节点到节点：工具挂在消息、协作交接挂在阶段；
- 轮次到交接/会议到轮次/轮次到发言：协作与会议的层级；
- 节点到产物/错误：结果与失败。

没有「相关」边，也没有按语义相似度连的线。边的种类少，才能保证布局稳定、测试可断言。

## 一套 builder，五套 apply

实现上只有一份通用 builder，负责建根、建运行、建角色车道、加产物、加错误、写节点与边。五个域各自一个 apply 函数，只解释事件，不直接操作集合。好处很具体：

- 节点去重、边去重、父节点兜底只写一次；
- 新增域时不用复制布局逻辑；
- 单测可以只测某个 apply，也可以测整条投影链。

## 一个具体场景：协作运行怎么落图

一条会话触发协作运行时，事件通常按这个顺序到达：

```text
run_started            → 建 run 节点，挂到会话根
agent_phase(planner)   → 建阶段节点，开规划车道
agent_handoff(plan→exec) → 建交接节点，挂到规划阶段
agent_phase(executor)  → 建执行阶段，开执行车道
tool_trace             → 该工具属于聊天主线，不挂进协作运行
agent_review           → 建审查节点，开审查车道
done                   → 更新 run 节点为成功
```

这里有一个容易误判的地方：工具轨迹是聊天事件，不会自动挂到协作阶段。协作产物只从协作事件载荷里的引用创建。跨域的「谁调用了谁」由边表达，而不是把所有子事件强行平铺到同一个父节点。

## 失败与错误节点

失败不只改状态，还要留下可读的原因。任务步骤失败时，投影在步骤下补一个错误节点；工作流节点失败、聊天消息失败、协作运行报错同理。错误节点的 id 带 scope、scopeId 与事件序号，因此同一失败重复到达不会叠加。

错误节点不是日志的替代品。它只保留压缩后的一句话摘要与错误码；真正的堆栈仍然在原运行记录里。图负责指路，不负责完整取证。

## 取舍：为什么不给每个域做一套图

每域一套图听起来更「贴合业务」：任务看甘特、工作流看 DAG、协作看泳道、会议看纪要。但它会带来四个成本：五套布局、五套交互、五套空态与错误态、五套测试。更关键的是，用户在一张会话里需要的是「串起来看」，而不是在五个视图之间跳转。

统一快照结构牺牲了各域最专业的可视化，换来的是一致的学习成本与一致的降级行为。工作流的 DAG 仍然留在工作流页面，过程图只回答「这次会话里发生了什么」。
