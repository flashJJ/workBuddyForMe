# 会话级模型优先级：为什么把模型绑到阶段，而不是绑到每轮请求

一条会话里的不同阶段，成本结构往往不一样。调研阶段要读大量材料、做长链推理，适合能力更强的模型；整理与格式化阶段只需要遵循格式，用本地小模型就够。如果模型只能在创建助手时选一次，用户想换模型就得换助手，人格、工具、默认阶段全部跟着变——为了省一点推理成本，付出的是重建上下文的代价。

另一个直觉方案是每轮请求带一个模型 id。灵活，但把「这条会话用什么模型」变成了请求参数：客户端能改、审计看不到、同一条会话的模型可以每分钟变一次。出了问题很难回答「刚才那轮到底用的哪个模型」。

这一版选择第三条路：模型绑在阶段上，落到会话级字段。这一篇讲它的优先级、写入时机和几个真实的坑。

## 三级优先级

解析顺序只有一条链：

```text
会话 model_id  >  助手绑定 model_id  >  系统默认对话模型
```

会话字段为空时，行为与没有这个功能时完全一致；助手绑定为空时，继续回落到设置里的默认模型。三个来源的职责也不同：

| 来源 | 作用域 | 谁写入 |
|---|---|---|
| 会话覆盖 | 仅当前会话 | 保存阶段计划时同步 |
| 助手绑定 | 该助手的每条会话 | 创建/更新助手 |
| 系统默认 | 全局 | 设置页 |

这样分层的好处是：临时调整只影响一条会话；换助手仍然是换人格与默认能力；全局默认继续做兜底。三层都为空时，解析直接报「未配置对话模型」，而不是让某条会话悄悄失败在模型调用阶段。

## 写入时机：和阶段保存在同一个事务

保存阶段计划时，服务端先校验整份计划，再取出当前选中阶段，最后做两件事：

```ts
db.transaction(() => {
  plans.upsert(conversationId, plan);
  conversations.setModelId(conversation.id, active?.modelId ?? null);
})();
```

两件事必须在同一个事务里。否则会出现「计划保存成功、模型还是旧的」：界面显示第三阶段，实际请求仍用第二阶段绑定的模型；用户以为切换生效了，账单和输出却对不上。

这里有一个实现上的收紧：设计时只要求「选中阶段变化时同步模型」，落地时改成**每次保存都以当前选中阶段的模型同步**。原因是计划的其他字段也可能变，而只要选中阶段没变，旧模型未必仍然正确——比如用户在同一次编辑里把当前阶段清空了模型。每次都同步，规则更简单，也更容易测。

切到没有绑定模型的阶段时，写入的是空值，不是「保持上一个模型」。空值会让解析回落到助手或系统默认；保留上一个模型则会让「跟随助手默认」这个选项名不副实。**清空覆盖是一种明确的状态，不是缺失。**

## 无效模型为什么必须报错

存在性校验有两道：

- 保存计划时，阶段引用的模型必须存在，且能力列表包含对话；否则返回参数错误；
- 真正开始对话时，解析出的模型还要再检查供应商存在且启用。

为什么不静默回落到默认模型？因为静默降级会改变用户预期：他以为自己切到了一个更强的模型，实际用的是另一个；成本、速度、输出风格全变了，却没有任何提示。相比之下，保存时直接拒绝、并说明是哪个阶段绑定的哪个模型不可用，是更诚实的失败。

模型被删除时，数据库外键把会话字段置空，下一次解析自然回落到助手或系统默认。这是唯一合理的「自动降级」：模型实体都不存在了，保留一个悬空 id 没有意义。

## 为什么不做「每轮传模型」

聊天请求的结构没有改，客户端不能逐轮指定模型。三个理由：

1. **可复现**。同一条会话在阶段不变时使用同一个模型，出了问题能按阶段回放；
2. **可审计**。模型变化是一次计划变更，会写进阶段计划的保存记录；逐轮传参则是一次隐形的运行时改动；
3. **上下文成本可见**。切换阶段不新建会话、不清空消息，模型换了但历史还在。把这件事放在阶段上，用户切换时就知道自己在做什么；藏在请求参数里，等于鼓励用户频繁试探。

代价是灵活性：用户不能在同一阶段里临时换一次模型。这个需求可以用「编辑当前阶段的模型」解决，成本是多一次保存，收益是状态始终有一条可查的记录。

## 切换阶段，切换的是上下文成本

阶段切换只改两样东西：选中下标与会话模型。消息不删、上下文不清、会话不重建。这意味着：

- 从强模型切到弱模型，弱模型仍要读完整段历史，输入成本不一定下降，下降的是输出与推理定价；
- 从弱模型切回强模型，强模型会看到弱模型阶段产生的全部内容，前后风格可能断裂；
- 因此阶段应该在长上下文积累之前切换，而不是等到几万字之后再换。

这不是实现缺陷，而是「阶段化」与「分支化」的区别。阶段是在同一条线上换挡，分支才是另起一条线。这一版只做换挡，不做分支。

另一个细节是「准备任务」不改模型。准备接口返回当前阶段绑定的模型（没有就用会话当前模型），但不会写会话字段。用户可以先看第三阶段会用哪个模型，再决定是否真的切过去；如果准备就顺手切换，点一次「载入任务」就会产生一次隐形模型变更。

## 一个真实验收回归

验收阶段发现过一个空会话残留：新建会话的流程先落库会话，再解析模型；模型校验失败时接口报错，但会话已经建好了，列表里留下一条打不开的空会话。

修复不是加一个删除，而是把顺序改对：先解析模型，解析成功后再创建会话，失败时不产生任何行。相关的流式用例 4/4 恢复通过。

它说明一条顺序原则：**先做会失败且无副作用的校验，再做会产生持久状态的操作。** 事务能解决一半问题，但顺序错了，事务边界也救不回来。

## 边界与兼容

- 会话模型只影响当前会话，不改助手绑定，也不改角色卡；
- 备份里带会话模型字段；恢复时缺失或目标库没有该模型，按空值处理；
- 旧归档没有这个字段，恢复后行为与升级前一致；
- 阶段 UI 显示「当前生效模型」；会话没有覆盖时显示「跟随助手默认」，并附上实际生效的模型名，避免用户误以为没有模型。
