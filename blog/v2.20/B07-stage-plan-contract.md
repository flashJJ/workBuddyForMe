# 阶段计划为什么不能只是一段提示词：Schema、服务端校验与三处落点

在对话里加「阶段」，最容易的做法是给模型一段模板：先把调研、分析、写作、交付写进系统提示，再让用户每次手动改一遍。演示时它看起来能用；用一周就会暴露三个问题：用户不想重复输入、模型会漏掉交付要求、引用的技能路径可能根本不存在。

更麻烦的是「谁负责保证这份计划是合法的」。前端可以拦住空标题，但拦不住一个已被删除的模型 id；保存时可以校验，但技能可能在两轮对话之间被停用。只要有一处没校验，坏配置就会在真正执行时才炸，而那时已经消耗了上下文和 token。

这一篇讲这一版的阶段计划怎么做成一份**可存储、可校验、可复制**的契约，而不是一段靠自觉维持的提示词。

## 先把上限写死

| 字段 | 约束 | 为什么 |
|---|---|---|
| 阶段数 | 1–8 | 顶部阶段条要能横向扫完，超过 8 个就退化成菜单 |
| 标题 | 去空格后 1–40 字 | 阶段 chip 只显示一行，太长会挤掉其他阶段 |
| 技能 | 去重后最多 12 个 | 每个技能都要进提示词，上限即上下文预算 |
| 目标 | ≤4000 字 | 阶段目标是一段任务说明，不是一整篇文档 |
| 交付要求 | ≤4000 字 | 与目标同一量级，避免提示词无限膨胀 |
| `activeStep` | `null` 或合法下标 | 下标越界在服务端直接判非法 |

上限写进共享常量，Schema 与 UI 读同一份。这样「编辑器最多加 8 个」和「服务端拒绝第 9 个」不会漂移。

Schema 里有几个容易被忽略的细节：

- 标题先 `trim` 再判长度，避免「两个空格」被当成合法标题；
- 技能名数组先判长度再 `Set` 去重：数组超过 12 个就拒绝，重复项不会进提示词两次；
- `modelId` 可以为 `null`，表示这个阶段跟随助手或系统默认；非空时要求非空字符串；
- `activeStep` 用 `superRefine` 校验范围，因为它是「相对 steps 长度」的约束，单字段 Schema 表达不了。

## 保存与准备是两种校验强度

同一份计划，在「保存」和「载入任务」两个时机的要求不一样：

- 保存允许目标为空。用户可能先搭出四个阶段的骨架，再逐段补内容；此时强行要求目标非空，会逼用户乱填；
- 载入任务要求当前阶段目标非空。空目标组装出来的提示词只有一句「执行阶段：某标题」，模型无法执行；
- 准备可以指定非当前阶段。用户想先看看第三阶段的任务文本，不需要先切过去；
- 准备的阶段序号必须存在。越界直接拒绝，不做「回落到第一个阶段」这种猜测。

这是有意的非对称：**存储宽松，执行严格。** 宽松让计划可以被逐步完善，严格保证真正送进模型的东西是可执行的。

## 服务端必须查库，Schema 查不了

Schema 能管形状，管不了「这个模型还在不在」「这个技能还能不能用」。这一版把存在性校验放在 core 服务层，保存和准备都调用同一个函数：

- 阶段的 `modelId` 非空时，模型必须存在，且能力列表包含对话；否则返回参数错误，并带上阶段标题与模型标识；
- 阶段的技能名必须在当前技能清单里，且同时满足「已启用、目录存在、清单可解析」；缺一个就失败，错误里列出所有缺失的技能名。

为什么要在两个时机都校验？因为约束会过期。保存时模型可用，不代表下一轮对话时仍可用；保存时技能启用，不代表用户不会在设置里关掉它。保存时校验是「别让坏配置进库」，准备时校验是「别让过期配置进提示词」。

错误信息也要为定位服务：只说「阶段计划不合法」没有用，用户需要知道是第几个阶段、哪个字段、哪个技能名。服务端返回结构化错误，编辑器把它显示在对话框内，同时弹一条提示，避免用户只看到 toast 而看不到具体位置。

## 三处落点，一份计划

| 落点 | 存什么 | 谁写入 |
|---|---|---|
| 会话阶段计划表 | 完整计划 JSON，主键是会话 id | 保存接口、创建会话时快照 |
| 助手默认阶段 | 可选 JSON | 助手创建/更新、应用角色卡 |
| 角色卡默认阶段 | 可选 JSON | 内置卡播种、卡片编辑 |

会话表用独立行存整份计划，而不是把每个阶段拆成列。原因很直接：阶段是有序数组，拆列会引入「第几个阶段」这种位置主键，增删阶段就要重排一片数据；整份 JSON 只有一份真源，`activeStep` 也不单独建列，避免计划与选中阶段各说各话。

会话表与角色卡、助手的关系是「复制」，不是「引用」。创建会话时把默认计划深拷贝一份；之后用户改会话里的阶段，不会改到角色卡；改角色卡，也不会回头改已经创建的会话。这条规则听起来保守，实际是唯一能让历史稳定的做法。

## 只填空缺，不回溯覆盖

默认阶段有明确的优先级：会话自有 > 助手显式 > 角色卡默认 > 空。复制只发生在目标为空的时候：

- 创建会话：助手有计划就用助手的；没有就取当前角色卡的默认；仍为空就不建计划行，会话照常可用；
- 应用角色卡到助手：仅当助手自己的计划为空时，才复制卡片的默认阶段；已有计划不动；
- 内置角色卡：六张卡各带四个默认阶段，模型为空、技能为空，留给用户自己绑；
- 老库升级：内置卡只在阶段为空时补齐，不覆盖用户已经改过的内容。

为什么不做「同步更新」？因为默认阶段是模板，会话是实例。模板更新后自动改写所有实例，会让用户昨天调好的阶段今天悄悄变样；而如果用户希望用新模板，重新建会话即可。**复制的是快照，不是引用。**

## 提示词怎么组装

准备接口返回的是一段可直接放进输入框的文本，顺序固定：

```text
执行阶段：{标题}

要解决的问题：
{目标}

使用以下技能；先读取各技能说明并遵循其中适用的要求：
- {技能名}：{技能目录}

交付要求：
{交付要求}

沿用当前会话上下文。完成后给出交付物、验证结果与仍未解决的问题。
```

技能段与交付段在为空时整段省略，而不是留一个空标题。技能路径取自当前技能清单里的真实目录，不让模型自己猜。技能命令前缀暂不可用，因为技能清单里还没有这个字段；宁可不加，也不拼一个不存在的命令名。
