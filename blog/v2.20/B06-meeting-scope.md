# 会议为什么不能挂进会话图：独立根、独立 scope 与 best-effort 事件

我们的桌面 AI 应用是一个本地优先、单人开发的 AI 助手。它能开会：几个不同的助手围绕一个话题轮流发言，有主持人、有转录、有开始和结束。既然会话已经有一张过程图，把会议也接进去似乎很自然——反正都是「一次运行」。

但真正动手时，第一个问题就卡住了：会议的根是谁？如果挂在某条会话下，那这条会话被删了，会议图怎么办？如果一场会议从会议页直接发起、根本没有对应会话，它又该挂到哪？更隐蔽的问题是串味：同一场会议的轮次、发言、状态，如果和会话的消息、工具、任务节点混在同一条根下，用户看到的是一张语义混乱的图。

这一篇讲这一版怎么把会议接进同一套图结构，又保证它不和会话混在一起。

## 会议不是会话的子运行

| 维度 | 会话 | 会议 |
|---|---|---|
| 根身份 | 会话 id | 会议 id |
| 参与者 | 用户 + 一个助手 | 用户 + 多个助手 |
| 主要数据 | 消息 | 会议转录 |
| 生命周期 | 删除会话 | 删除会议，事件保留 |
| 图入口 | 聊天右侧、时间线 | 会议页 |
| 状态机 | 流式、停止、错误 | 进行、结束、中止 |

把会议当子运行，意味着它必须有所属会话。但产品上会议可以独立创建，也可以先有会议再有对话。更麻烦的是，会议的一轮发言不是「一次工具调用」，它有轮次、有发言人、有会议级状态。硬塞进会话根，节点归属和排序都会变得没法解释。

## 三条独立：根、scope、快照

这一版的处理是让会议并行，而不是从属：

- **独立根**：图根分两类，`conversation` 与 `meeting`。会议图的根节点是会议 id，不是任何会话 id；
- **独立 scope**：事件日志的 scope 增加 `meeting`，`scopeId` 直接用会议 id。事件的 scope 字段本来就是文本，扩枚举不需要建表或迁移；
- **独立快照**：会议图接口只取该会议的 `meeting` 事件，不读会话事件；会话图则明确排除 `meeting`。

投影里的根匹配只有几行，但决定了双向隔离：

```ts
if (kind === 'meeting') {
  return event.scope === 'meeting' && event.scopeId === id;
}
if (event.scope === 'meeting') return false;
```

第一行是会议图只认自己的会议；第二行是会话图遇到会议事件直接丢弃。两个方向都写死，才不会有「在会话图里看到别的会议」这种事故。

## 只写图需要的事件，不写转录

会议事件只有三类：

| 事件 | 时机 | 图上的作用 |
|---|---|---|
| 轮次开始 | 一位发言人开始前 | 建会议轮次节点，记录发言人 |
| 消息落库 | 一条发言写入后 | 建发言节点，挂到最近轮次 |
| 状态变更 | 会议状态机变化后 | 更新会议状态节点 |

流式增量帧不落图，错误事件也不落图。前者如果按 token 建节点，一场十分钟的会议能产生上万节点；后者在图里没有稳定的身份，错误本身会通过状态节点与会议页提示表达。这两个过滤发生在装配层，而不是投影里——投影看到的是已经落库的事件，装配层才决定什么值得落。

另一条边界是「不复制完整转录」。事件里只带图需要的字段：会议 id、发言人、正文摘要、时间、轮次。完整转录仍然只在会议消息表里。图是过程视图，不是会议的权威记录。

## 轮次身份为什么必须由服务端给

轮次节点最容易做错。三个看起来可用的字段都不能当身份：

- `autoRounds`：只有自动接龙才累加，手动发言时它不变，同一场会议会出现多个「第 0 轮」；
- 客户端收到的帧序号：流式重连、页面刷新、多个观察者都会让序号漂移；
- 数组下标：删除或补写消息后，下标指向的轮次会变。

这一版用「落库消息数」作为轮次序号：每轮发言开始前读取当前会议的消息总数，随事件一起写入。轮次节点 id 由此派生，实时帧和刷新后的快照看到的是同一个轮次。旧事件没有这个字段时，回落到该 scope 内的递增序号；发言节点挂到最近一个轮次，找不到轮次就挂会议根。

这条规则的价值只有在刷新后才看得出来：实时追加时轮次是「第 3 轮」，刷新后如果变成「第 5 轮」，用户会以为系统丢了两轮发言。身份一致，图才可信。

## best-effort：图坏了，会议不能坏

会议事件的写入是 best-effort。事件日志服务在写入外层包了 try/catch，失败只打一条警告并返回空值，调用方继续发言、继续落消息。会议主链路是模型调用与消息落库，图是旁路观测；把观测做成强依赖，等于让「图画不出来」升级成「会议开不成」。

代价必须说清楚：

- 某一轮的事件写失败，轮次节点缺失，该轮发言会挂到会议根，图看起来少一层；
- 状态事件缺失，会议状态节点停在旧值；
- 事件载荷超过上限会被截断成预览，图上的摘要可能只有前半段；
- 没有自动补写，只能靠后续事件继续追加，图会落后于转录。

所以图只作为过程视图，不当作会议记录。用户核对内容仍然看转录，图只回答「这场会议大致怎么走过来的」。观测数据的正确姿态是：有用时有用，坏了也不改变业务结果。

## 取舍：不新增表，不新增端点

- 不为会议图新增表：scope 与 scopeId 已经够用，投影只读事件；
- 不为会议图新增 SSE 端点：复用会议页已有的轮次、增量、消息、状态帧，客户端用同一套追加 reducer；
- 会议删除时不级联删事件：与事件日志既有的保留策略一致，图按事件回放；
- 不在会话图里显示「关联会议」摘要：那需要跨对象聚合，图和会话就不再是同一真源。

这几条都指向同一个原则：**图的边界等于事件的边界。** 事件在哪里，图就在哪里；事件没写，图就不编。

## 数字

全书单测 3122 例、532 个文件；Web 集成 11/11；生产模式 Web e2e 140/140；桌面冒烟 10/11，缺项是与环境相关的历史用例；核心页面 a11y 6/6。会议图与阶段相关的页面都在 e2e 覆盖内，首屏 `/timeline` 306 kB。

这些数字不证明会议图好看，只证明新增的 scope、投影与入口没有把会议主链路和原有页面弄坏。
