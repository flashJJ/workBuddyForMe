# 给备份归档加一层密码：容器格式与密钥派生怎么做

给文件加密不难，难的是让加密后的归档仍然可解析、可恢复、可演进。

这一版没有改内层备份格式，而是在外面套了一个容器。归档仍然是 tar.gz，只是先被加密成一段密文。

## 一、容器布局

```text
magic "WBFM-ENC1"        9 字节
头长度                    4 字节（大端）
JSON 头                   version / kdf / salt / N / r / p / iv
AES-256-GCM 密文          ciphertext + tag
```

JSON 头是明文，因为解密前需要知道 salt、iv 与 KDF 参数。头里不含任何用户数据。

密文是「内层 tar.gz 的全部字节」，tag 附在密文末尾。解密时先校验 tag，再解压。

## 二、为什么用 scrypt

口令派生需要抗暴力破解。

scrypt 是内存硬函数，攻击者很难用 GPU 大规模并行。参数选择：

- N = 2^15（32768）
- r = 8
- p = 1
- keylen = 32

这组参数在普通笔记本上派生一次需要可感知但可接受的时间；对本地备份这种低频操作来说，安全收益大于耗时。

头里记录 N/r/p，是为了未来可以在不破坏旧归档的前提下调整参数。

## 三、每次导出都换 salt 与 iv

salt 与 iv 都随机生成，随归档保存。

原因很直接：同样的密码与同样的明文，如果 salt/iv 固定，密文就会相同。攻击者可以据此判断两个归档是否内容一致。

每次导出换新值，避免这种泄露。

## 四、参数校验防内存炸弹

解密时，KDF 参数来自归档头，也就是来自不可信输入。

如果直接按头里的 N 派生，一个恶意归档可以把 N 写成极大值，让 scrypt 申请巨量内存。

所以解密前先校验范围：

```text
N ∈ [2^14, 2^17]
r ∈ [1, 16]
p ∈ [1, 4]
```

超出范围直接按「归档损坏」处理。

## 五、未加密归档保持原样

`openArchive` 对未加密输入直接返回原 Buffer。

这样调用方不需要判断「这个归档有没有加密」，始终调用同一个函数即可。加密是可选能力，不是新格式分支。

## 六、密码不落盘

密码只在请求内存中存在：

- 不写数据库；
- 不写日志；
- 不进 manifest；
- 不进入归档明文。

加密在整包缓冲上完成，随请求结束释放。

## 七、为什么不做流式加密

内层归档本身已经在内存中完成打包，加密再复制一份，峰值约为归档的两倍。

在 500MB 上限内，这个峰值可以接受；引入流式加密会让容器格式、tag 校验与错误处理都复杂一档。

这是一个明确的取舍：先保证正确与简单，再考虑大文件优化。

## 八、可复用的结论

给已有格式加加密层，可以遵循四条规则：

- 外层容器自描述，内层格式不变；
- KDF 参数随归档保存，但必须校验范围；
- 每次加密使用新 salt/iv；
- 未加密输入保持兼容，不让调用方分支。

这样加密是加法，不是迁移。
