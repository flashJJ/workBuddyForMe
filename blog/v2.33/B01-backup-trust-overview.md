# 备份可托付：加密、引用计数与恢复核对的三层闭环

备份能导出、能恢复，只说明数据「可以带走」。

用户真正需要的是「敢不敢把它放到别处」：放到网盘会不会被直接打开？删掉一条消息后附件到底还有没有人用？恢复完成后怎么确认 manifest 里的条目真的落库了？

这一版围绕这三个问题，补了三层能力：容器加密、附件引用计数、导出与恢复核对。

## 一、加密解决「外放」

备份归档原本是明文 tar.gz，manifest 与轨道 JSON 都可以直接读取。

这一版在容器层增加密码加密：内层仍是原来的归档结构，外层多一个 `WBFM-ENC1` 容器。没有密码时，看到的只是一段密文。

加密不改变备份内容，也不改变恢复流程，只是多了一个可选的口令参数。

## 二、引用计数解决「说不清」

附件与消息原本是松耦合：消息的 JSON 里存附件 id，附件表里存文件元数据。

删除消息只删 JSON 引用，附件行与文件还在。判断孤儿只能看「文件在不在附件表」，无法回答「这个附件还被谁用着」。

这一版新增 `attachment_refs` 表，把消息与产物对附件的引用显式记录下来。写入时登记，删除时由触发器清理，启动时回填历史数据。

有了引用计数，清理判定才能从「文件级」升级到「引用级」。

## 三、核对解决「恢复完不知道对不对」

恢复原本只返回导入与跳过计数。

用户无法确认：manifest 声明了多少、实际写入多少、哪些被跳过、附件是否齐全。

这一版让导出与恢复都产出核对报告：

- 导出报告：逐轨条目、字节、耗时、总字节、是否加密；
- 恢复核对：声明 vs 写入 vs 跳过、缺失附件、恢复后未引用附件数。

报告只读，不改变恢复语义。差异只告警，不让整次恢复失败。

## 四、三层之间的关系

这三层不是并列功能，而是递进关系：

```text
加密：让归档离开本机也安全
  → 引用计数：让清理与迁移有依据
    → 核对：让恢复结果可验证
```

没有引用计数，清理只能停在文件级；没有核对，加密与迁移都缺少最后一步确认。

## 五、为什么回收清单也要补

引用计数建立后，会出现一类新的孤儿：附件行存在，但引用数为 0。

这类附件不能直接删行，否则用户恢复时会丢元数据。所以回收目录补了一份 `manifest.json`，记录附件行快照；恢复时先重建行，再移回文件。

这让「回收」第一次具备了完整的可逆性。

## 六、边界

这一版没有做：增量备份、云同步、密钥托管、密码找回、附件物理删除、附件合并视图。

加密只发生在容器层，内层备份 schema 不变；数据库只增加一次纯加法迁移。

## 七、一句话

**可托付不是一句口号，而是三个可验证的动作：打不开、说得清、核得上。**

加密让归档打不开，引用计数让附件说得清，核对报告让恢复结果核得上。

## 八、用户路径

导出侧：

```text
选择轨道
  → 可选启用密码
    → 下载归档
      → 看到是否加密、总大小与逐轨报告
```

恢复侧：

```text
选择归档
  → 预检（需要时输入密码）
    → 看到版本、计数、警告与缺失附件
      → 确认恢复
        → 看到导入/跳过与核对结果
```

加密与核对没有改变主流程，只是在关键节点增加了信息与确认。

## 九、验收口径

- 正确密码可预检与恢复，错误密码与损坏统一拒绝；
- 引用行数与消息/产物一致，删除后自动清零；
- 回收后可从清单恢复文件与附件行；
- 核对能指出缺失附件与跳过项，恢复仍返回成功；
- 旧归档与旧备份结构继续可读。

## 十、为什么先做这三层

备份系统的能力可以排很长：增量、云同步、密钥托管、自动备份。

这一版选择先做「安全、可解释、可验证」，因为它们是其他能力的基础：

- 没有加密，增量归档同样不敢外放；
- 没有引用计数，增量也无法判断附件是否重复；
- 没有核对，链式恢复更无法确认完整性。

先把这三层做扎实，下一版才有可靠的起点。
