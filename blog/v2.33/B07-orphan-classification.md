# 孤儿附件为什么要分两类：文件级与引用级

有了引用计数之后，孤儿不再只有一种。

一类是「目录里有文件，但附件表没有记录」；另一类是「附件行还在，但没有任何引用」。

这两类的处理方式不同：前者可以只移文件，后者必须连行一起回收，否则恢复时会丢元数据。

## 一、第一类：无记录文件

判定条件：

```text
attachments/ 下的文件名
  不在 attachments.storage_path 集合中
```

这类文件通常来自历史版本的残留、手工拷贝或写入中断。

它们没有元数据，恢复时也只能恢复文件本身。

## 二、第二类：无引用附件

判定条件：

```text
附件行存在
  AND 引用数为 0
  AND 创建时间早于 7 天前
```

7 天保留期是为了避免误伤「刚上传、消息还没写完」的在途附件。

引用数为 0 通过 `attachment_refs` 查询，而不是扫描消息 JSON。

## 三、任务截图为什么要排除

任务执行过程会产生截图，截图路径记录在 `task_steps.screenshot_path`。

这些截图通常不进入 `attachment_refs`，因为它们是任务步骤的内部产物，不是消息图片或用户产物。

如果只看引用数，它们会被误判为「无引用」，然后被回收。

所以扫描时额外读取任务步骤的截图路径，建立排除集合。

## 四、两类候选的展示

前端分两行展示：

```text
无记录文件 3 个 · 12.4 MB
未引用附件 5 个 · 48.2 MB
```

用户可以看到两类各有多少、占多少空间，再决定是否回收。

这比只给一个「孤儿总数」更有信息量。

## 五、回收动作的差异

- 无记录文件：移动到回收目录，清单记录文件名映射；
- 未引用附件：移动到回收目录，清单记录附件行快照，然后在同一事务里删除附件行。

删除行时带一个条件：

```sql
DELETE FROM attachments
WHERE id = ?
  AND NOT EXISTS (SELECT 1 FROM attachment_refs WHERE attachment_id = ?)
```

即使扫描与回收之间新增了引用，也不会误删。

## 六、为什么保留 7 天

三类风险：

- 上传后尚未写入消息；
- 消息写入失败但文件已落盘；
- 用户刚删消息，可能还想找回附件。

7 天是一个折中：足够覆盖常见误操作，又不会让回收候选无限堆积。

## 七、扫描是只读的

`scanOrphanAttachments` 不移动文件、不写数据库。

它返回候选清单与字节数，供前端展示。真正的移动发生在用户确认之后。

这条边界让「扫描」可以随时执行，不会产生副作用。

## 八、一条经验

清理功能的第一问不是「怎么删」，而是「怎么分类」。

分类清楚了，回收、恢复、保留期才有意义；分类含糊，任何删除策略都会误伤。
