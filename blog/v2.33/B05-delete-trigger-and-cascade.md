# 删除侧兜底：触发器、外键级联与「总有一条路径会漏」

引用表建好之后，真正的难点不是插入，而是删除。

消息可以删、会话可以级联删、附件可以删、产物可以删。每一条删除路径都要记得清理引用，漏一条就会留下悬空行。

这一版用两层机制兜底：外键级联与删除触发器。

## 一、附件删除由外键级联

`attachment_refs.attachment_id` 指向 `attachments(id)`，并声明 `ON DELETE CASCADE`。

附件行被删除时，数据库自动删除所有指向它的引用，不需要应用层再写一次 DELETE。

这是最可靠的一层，因为它不依赖调用方记得清理。

## 二、消息删除由触发器兜底

消息删除没有外键关系可用：`owner_id` 是多态字段，无法指向 `messages` 表。

实现上增加一个 `AFTER DELETE ON messages` 触发器：

```sql
DELETE FROM attachment_refs
WHERE owner_type = 'message' AND owner_id = OLD.id;
```

无论消息是直接删除，还是会话级联删除，只要行被删掉，引用就会被清理。

## 三、为什么写入侧还要登记

触发器只负责删除，不负责创建。

引用必须在消息写入时登记，否则历史数据与新数据会出现两套语义。

写入侧统一走仓储方法，解析 `content_parts` 后批量插入，避免不同调用方各写一套。

## 四、写入与删除的时序

```text
消息写入 → 登记引用
消息删除 → 触发器清理
附件删除 → 外键级联
```

三条路径互不依赖，任何一条单独执行都不会留下不一致。

这也是为什么没有选择「在应用层手动删引用」：手动路径越多，漏掉的机会越大。

## 五、悬空引用怎么处理

`owner_id` 没有外键约束，理论上可能出现指向不存在消息的引用。

处理方式是不让悬空引用影响主流程：

- 查询引用时按 owner 过滤；
- 清理时只关心引用数为 0 的附件；
- 悬空引用不会阻止消息或附件的其他操作。

要彻底消除悬空，需要多态外键或定期清理任务，这一版没有做。

## 六、为什么不用软删除

软删除可以保留历史，但会让所有查询都带一个 `deleted_at IS NULL` 条件。

对一个本地单用户应用来说，硬删除 + 触发器清理更简单，也不会让引用表随时间膨胀。

## 七、测试覆盖

- 删除消息后，该消息的引用行消失；
- 删除会话后，其下所有消息的引用行消失；
- 删除附件后，所有指向它的引用行消失；
- 重复删除不报错；
- 删除后重新统计引用数，结果为 0。

测试的重点不是「触发器写对了吗」，而是「从任意入口删除，引用都能收敛」。

## 八、一条经验

清理逻辑要假设调用方会犯错。

外键与触发器不是银弹，但它们能把「必须记得做」变成「数据库自动做」。在引用关系上，这种兜底值得。
