# 备份可托付的复盘：把「放心」拆成可验证的小闭环

这一版的主题是「可托付」。

复盘下来，最重要的不是加密算法，也不是引用表，而是把「放心」拆成了几个可以验证的动作。

## 一、先定义威胁，再选方案

加密有很多种做法：本地密钥、口令派生、系统密钥链、云 KMS。

这一版选择口令 + scrypt + AES-GCM，原因不是它最安全，而是它匹配场景：归档要离开本机，接收方可能没有本机的密钥链。

如果把「加密」理解成「用系统密钥加密」，归档换一台机器就打不开，与「可带走」矛盾。

**经验：安全方案要先定义敌人和使用场景，再谈算法。**

## 二、错误提示也是攻击面

密码错误与归档损坏合并成同一个错误码，是这一版刻意做的取舍。

分开报错对用户更友好，但会给攻击者一个密码判定器。

在本地应用里，这个风险不大，但设计习惯应该一致：错误信息只告诉用户下一步做什么，不泄露内部状态。

**经验：错误码是接口的一部分，要考虑它会告诉调用方什么。**

## 三、引用关系要显式化

附件与消息原本靠 JSON 字符串关联。

这种隐式关系的问题不是查不到，而是「无法确定有没有漏」。

引用表把关系写成事实，计数可以随时重算，清理也有了依据。

**经验：能被查询的关系，不要只存在字符串里。**

## 四、历史数据必须能补齐

新增引用表时，历史消息已经存在。

如果只处理新数据，旧附件会被误判为孤儿。

回填的三个条件是：不阻塞、可重试、可重复。单飞锁 + 完成标记 + 幂等插入，刚好满足。

**经验：任何新增的派生数据，都要回答「历史数据怎么办」。**

## 五、清理必须可逆

回收只移动、不删除；回收目录保留 7 天；未引用附件要超过 7 天才进入候选。

这些限制会让清理看起来「不够彻底」，但它们让用户敢点按钮。

**经验：不可逆操作的入口，应该比可逆操作更窄。**

## 六、核对要成为默认动作

导出报告与恢复核对不是调试工具，而是用户界面的一部分。

没有它们，用户只能相信「成功」两个字；有了它们，用户能看到声明、写入、跳过与缺失。

**经验：完成提示应该带证据，而不是只带结论。**

## 七、还没解决的问题

- 每次备份仍是全量，附件与消息重复打包；
- 删除与修改不会进入增量；
- 恢复只能单文件，无法表达「基线 + 补量」的链。

这些是下一版的方向：增量归档与链式恢复。

## 八、一句话

**「可托付」不是一次性功能，而是一组可验证的小闭环：打不开、说得清、核得上、找得回。**

这一版把四个动作都做了一遍，也留下了下一步的入口。

## 九、工程门禁的收尾

这一版改动跨 core、database、web 与 shared，收尾时跑的是全量门禁：

- 类型检查与 lint；
- 单文件 300 行上限；
- 目录直接文件数预算；
- 循环依赖检查；
- 文档 ASCII 框图检查。

备份相关文件本来就很长，新增功能时最容易被门禁拦住。处理方式不是提高阈值，而是把职责拆出去：收尾逻辑、链信息、增量筛选各自独立。

这条经验与功能无关，但决定了版本能不能顺利收口。

## 十、下一版的前置条件

增量归档需要三个前置条件：

- 基线必须完整，不能有静默截断；
- 归档必须有稳定的身份与序号；
- 恢复必须知道上一段是否已经应用。

这一版建立的核对报告与引用表，正好为这三件事提供了基础。

下一版把「全量基线 + 增量补量 + 链式恢复」接上，备份生命周期才算真正闭环。

## 十一、最后的判断

如果只能保留这一版的一个改动，我会保留核对报告。

加密很重要，引用计数很重要，但它们最终都要回答同一个问题：用户凭什么相信这次恢复是对的。

核对报告就是那个「凭什么」。
