# 启动回填：历史引用如何一次性补齐且可重复执行

新增引用表时，历史消息已经存在。

如果不回填，旧消息里的图片永远不会出现在引用表里，清理功能会把它们当成「零引用」——这是危险的错误。

这一版在服务启动后做一次幂等回填。

## 一、回填要扫什么

两类来源：

1. 消息的 `content_parts` 中的图片片段；
2. 产物 MIME 对应的附件行。

消息扫描只取 `content_parts`，不加载正文与工具轨迹，减少内存占用。

产物扫描直接看附件表，按 MIME 判断是不是产物格式。

## 二、单飞锁

回填是进程内的异步任务，可能被多次触发：启动、恢复旧归档、手动调用。

用一个模块级 `running` 标记做单飞：

```ts
if (running) return { skipped: true, inserted: 0 };
running = true;
try { ... } finally { running = false; }
```

同一时刻只允许一个回填，后来的调用直接跳过。

## 三、完成标记

回填完成后写一个设置项：

```text
attachmentRefs.backfilledAt = 完成时间
```

下次启动看到标记就跳过，不重复扫描。

这不是为了省一次扫描，而是为了避免「每次启动都全表扫描」长期消耗。

## 四、强制回填

恢复旧归档后，归档里的 refs 文件可能缺失，需要立即补齐。

所以回填函数提供 `force` 参数：跳过完成标记，重新扫描一次。

重复扫描不会产生重复行，因为插入使用 `INSERT OR IGNORE`，主键天然去重。

## 五、过滤不存在的附件

消息里的附件 id 可能指向一个已经被删除的附件。

直接插入会触发外键错误，导致整批回填失败。

实现上先读取全部附件 id 到内存集合，逐个校验后再插入。附件不存在时静默跳过。

## 六、失败只告警

回填在服务构造时触发，不阻塞对话。

失败时只记录告警，不写完成标记。下次启动会重试。

这是一个有意的取舍：回填是后台修复，不应该让应用启动失败。

## 七、幂等怎么证明

三个层面：

- 主键保证同一引用不会重复；
- `INSERT OR IGNORE` 保证重复执行不报错；
- 完成标记保证正常启动不会反复执行。

测试覆盖：连续回填两次，第二次 `inserted = 0`；强制回填两次，结果一致。

## 八、为什么不用数据库迁移做回填

迁移应该只改结构，不做大数据扫描。

把回填放在应用启动，有三个好处：

- 迁移失败不会卡住数据库打开；
- 回填失败可以重试；
- 回填逻辑可以随业务变化调整，不需要新增迁移版本。

## 九、一条经验

历史数据补齐要满足三个条件：不阻塞、可重试、可重复。

单飞锁 + 完成标记 + 幂等插入，是最小可用组合。
