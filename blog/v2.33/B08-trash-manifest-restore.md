# 回收清单：让「移走的附件」还能连数据库行一起恢复

只移动文件的回收站，恢复出来仍然是孤儿。

文件回到了 `attachments/`，但附件表里没有对应行，应用查不到它，下次扫描还会把它列为候选。

这一版在回收目录里补了一份 `manifest.json`，记录附件行快照。

## 一、清单结构

```json
{
  "version": 1,
  "trashedAt": "回收时间",
  "files": [
    { "name": "回收后的文件名", "originalName": "原始 storage_path", "bytes": 1234 }
  ],
  "attachments": [
    {
      "id": "附件 id",
      "filename": "展示名",
      "mimeType": "image/png",
      "byteSize": 1234,
      "storagePath": "原始路径",
      "contentHash": "内容哈希",
      "createdAt": "创建时间"
    }
  ]
}
```

`files` 解决文件映射，`attachments` 解决数据库行重建。

## 二、为什么先落清单再删行

回收顺序是：

```text
移动文件
  → 写清单
    → 删除附件行
```

清单先落盘，即使删除行失败，也能从清单恢复文件与元数据。

如果顺序反过来，删了行但清单没写，附件就真的不可恢复了。

## 三、同日多次回收怎么合并

同一天可能执行多次回收。

清单采用「读取已有 → 合并 → 写回」的方式，按文件名与附件 id 去重。

这样日期目录下始终只有一份清单，恢复时不需要遍历多个文件。

## 四、恢复的顺序

```text
读取清单
  → 按快照重建附件行（已存在则跳过）
    → 把文件移回 attachments/
      → 返回 restored / recreatedRow / manifestApplied
```

先重建行、再移文件，是因为文件移动失败时，行仍然存在，用户可以重试；反过来则会出现「文件在、行不在」的中间态。

## 五、文件重名怎么办

回收时如果目标目录已有同名文件，会给文件名加时间戳与前缀。

清单里同时记录 `name`（回收目录中的实际名字）与 `originalName`（原始路径）。

恢复时按 `originalName` 移回，避免把带前缀的名字带回附件目录。

## 六、清单缺失时的降级

旧版本生成的回收目录没有清单。

恢复逻辑读到 `manifestApplied = false` 时，退回「仅移文件」语义，并在结果里标注。

用户仍然能拿回文件，只是需要自己处理数据库记录。

## 七、安全边界

- 文件名必须是 basename，拒绝路径分隔符与 `..`；
- 日期目录必须匹配 `YYYY-MM-DD`；
- 清单解析失败按缺失处理，不阻断其他目录。

这些校验避免恢复动作被错误文件名带到数据根之外。

## 八、测试覆盖

- 回收后清单条目与移动文件一致；
- 恢复后附件行重建，文件回到原路径；
- 重复恢复幂等；
- 清单损坏时退回仅移文件；
- 同名文件恢复不覆盖已有文件。

## 九、一条经验

可恢复的回收站，必须同时保存「文件去了哪」与「数据库原来有什么」。

只保存文件，恢复的是字节；保存清单，恢复的才是数据。
