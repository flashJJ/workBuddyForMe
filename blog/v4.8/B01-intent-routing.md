# 先问“这轮在问什么”：对话意图路由的规则优先设计

我们的桌面 AI 应用在很长一段时间里，对所有对话轮次使用同一套上下文装配：不管用户说“嗨”，还是贴一段日志要求分析，流程都是先检索知识库、再召回长期记忆、再装上最近原文与摘要。

这套流程在知识问答里表现不错，但在另外两类场景里明显吃亏。闲聊时，检索和记忆召回纯属浪费 token；追问时，最近几轮原文反而被摘要和事实块挤掉，模型答不上“刚才那个端口是多少”。

我们决定在装配之前先回答一个问题：这一轮用户到底想做什么。

## 一、把“想做什么”变成数据结构

意图识别的输出不是一句自然语言标签，而是一个固定结构：

```ts
TurnIntent {
  kind, confidence, signals[], suggestedTaskMode
}
```

`kind` 是七类之一，`confidence` 是置信度，`signals` 保留全部命中依据，`suggestedTaskMode` 只是一个建议信号。内部还有一个 `source` 字段，标记这个结果来自规则、分类器还是回退。

把它定义成结构，是因为下游要消费它：配额、检索、记忆召回、事件日志都读同一份判断，而不是各写一套 if-else。

## 二、七类意图

| 意图 | 典型说法 | 装配侧重 |
|---|---|---|
| 闲聊 | 晚上好、随便聊聊 | 少检索、少召回 |
| 知识 | 什么是 RAG、两者区别 | 资料块优先 |
| 追问 | 那它呢、继续、刚才说的 | 最近原文优先 |
| 工具任务 | 帮我整理、导出、做个表 | 工具结果与原文并重 |
| 澄清 | 没听懂、你刚才说什么 | 原文优先、轻检索 |
| 记忆写入 | 记住、忘掉 | 确认与审计 |
| 提醒 | 提醒我、到时候叫我 | 交给提醒链路 |

这七类覆盖了对话侧最常见的分歧。再细分就会让规则互相打架，再粗分又不足以表达“追问怕丢原文”这种差异。

## 三、规则优先：能确定的不要问模型

第一层永远是正则与关键词。它不是权宜之计，而是最稳定的那部分：

- 句首“记住 / 忘掉 / 记一下”，置信度 0.88；
- “提醒我 / 叫我 / 闹钟”，置信度 0.90；
- “没听懂 / 你刚才说 / 再说一遍”，置信度 0.80；
- “帮我 / 整理 / 生成 / 导出 / 查一下”，且长度足够，置信度 0.76；
- “那 / 这个 / 它 / 继续 / 之前 / 刚才”，置信度 0.72；
- “什么是 / 为什么 / 怎么 / 区别 / 定义”，或整句以问号结尾，置信度 0.70。

同时会记录辅助信号：是否带图片或附件、助手是否绑定知识库、消息长度、是否包含 URL 或文件路径。这些信号本身不决定意图，只用于加权和事后分析。

规则之间也可能同时命中。做法不是先写先赢，而是把全部候选收集起来，取置信度最高者：

```ts
for (const rule of rules) {
  if (rule.match(text)) candidates.push({ kind, confidence });
}
best = candidates.sort(byConfidenceDesc)[0];
```

“之前那个端口”会同时命中追问和知识，但追问的 0.72 高于知识的 0.70，最终落到追问。这个排序是显式写死的，不靠运气。

## 四、小模型只做兜底

规则覆盖不了所有说法。比如一句很短的“就这个吧”，既没有关键词也没有问号。这时才轮到本地小模型分类器。

它不是主路径，有三道限制：

1. 只有规则最高置信度低于阈值时才调用；
2. 未配置分类器就完全不调用，纯规则零成本运行；
3. 调用带超时，超时、报错、空结果一律回退规则结果。

分类器返回的结果也要过同一道置信度门槛，低于门槛不采用。这样即使小模型给出一个奇怪的标签，也不会污染装配。

我们没有让主模型顺带判断意图。主模型本来就要生成回答，先让它分类再让它回答，等于把一次请求拆成两次，延迟和成本都不划算；而规则加小模型的组合，已经能覆盖绝大多数轮次。

## 五、低置信度就是默认策略

置信度低于 0.6 时，不做任何激进解释：

```ts
if (!best || best.confidence < 0.6) {
  return { kind: 'chitchat', confidence: best?.confidence ?? 0.3,
           source: 'fallback', signals };
}
```

注意这里的 `source` 是 `fallback`，不是 `rule`。下游看到这个标记，会直接使用默认配额，而不是“闲聊配额”。也就是说，系统不会因为一次没把握的判断，把知识问答误当成闲聊而关掉检索。

`confidence` 仍然保留原值，`signals` 也保留。它们不参与决策，但会进入事件日志，供离线统计哪类说法最容易误判。

## 六、意图只加资源，不减资源

这是整个设计里最重要的一条约束。

意图可以做的事情：把原文配额从 50% 提到 60%，把资料块从 15% 提到 40%，给出“建议进入任务模式”的信号。这些都是加法。

意图不能做的事情：因为一次低置信度的判断，减少检索、关闭工具、跳过记忆召回。所有“减法”都必须回落到原有默认行为。

高置信度的闲聊确实会减少召回，但那是规则确定性结果，不是概率猜测。只要判断带不确定性，系统就宁可多花一点 token，也不冒漏信息的风险。

## 七、意图要被看见，但不进正文

每一轮的意图都会写入一条 `turn_intent` 事件，包含类型、置信度、信号与来源。它不进入用户可见的回答正文，只用于两处：

- 上下文面板展示“这轮被理解成什么”；
- 离线评测断言意图与配额是否一致。

这样做的好处是，误判可以被复盘。用户觉得答非所问时，我们能查到当时是规则命中、分类器命中，还是回退到了默认策略。

## 八、边界

提醒是一个特殊类型。它在到达意图链路之前，会被本地提醒解析先行短路，所以实际的提醒创建不依赖这里。意图里保留这一类，是为了让统计与面板上的分类完整。

分类器默认关闭。开启后会多一次本地小模型调用，超时即回退。我们宁愿默认少一次调用，也不愿让一个可选能力影响主链路的稳定性。

规则集是人工维护的，必然有覆盖不到的说法。但它的行为可解释、可测试、零延迟，这正是上下文装配最需要的性质：先保证不添乱，再谈更聪明。
