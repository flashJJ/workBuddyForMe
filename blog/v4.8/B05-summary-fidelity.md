# 摘要弄丢数字之后：结构化摘要的保真与小窗口妥协

摘要是有损压缩。有损不是问题，问题在于“哪些信息可以丢”没有定义。

在对话里，最不该丢的是数字、日期、端口、版本号、金额和字段名。它们通常只出现一次，却决定后续所有回答是否正确。一段文字被改写得再通顺，只要把 8443 写成 8080，这次压缩就是失败的。

这一轮我们围绕“保真”做了三件事：结构化摘要、数字校验、小窗口妥协。

## 一、摘要不只是段落

压缩产出的不是一段纯文本，而是一个结构：

```json
{
  "summary": "本段对话的叙述性摘要",
  "facts": [{ "key": "端口", "value": "8443", "unit": null }],
  "decisions": ["确定使用本地模型"],
  "open_loops": ["待确认部署环境"]
}
```

`summary` 负责叙事，`facts` 负责可检索的事实键值，`decisions` 记录已经定下的结论，`open_loops` 记录还没闭环的事项。

分开存储的原因是下游用法不同。摘要进入中段叙述块，事实进入结构化事实块，未完成事项可以在下一轮提醒模型继续。全部揉成一段文字，就再也拆不出来了。

## 二、先定义什么叫“保真”

保真校验只盯一类目标：原文中的数字与日期。

校验前先做归一化，尽量减少“写法不同但含义相同”造成的误报：

- 全角数字转半角；
- 斜杠日期统一成连字符；
- “2026 年 3 月 1 日”压成“2026-3-1”；
- 数字与单位之间的空格去掉；
- 千分位逗号去掉，连续空白合并。

归一化之后抽取 token，覆盖日期、时间、百分比、带单位的数量，以及两位以上的独立数字。太短的个位数不纳入，否则“一共 3 条”这种噪声会淹没真正的关键值。

然后把摘要、事实、结论、遗留项渲染成一段可比对文本，逐个检查 token 是否仍然存在。缺失的 token 就是这次压缩的风险清单。

## 三、校验之后是重试与兜底

发现缺失，不做无限重试，只做一次有针对性的重试：

```ts
const first = await summarize(folded);
const missing = checkFidelity(first, source);
if (missing.length > 0) {
  const second = await summarize(folded, { mustKeep: missing });
  if (worseThan(second, first)) keep(first);
}
```

重试时把缺失 token 明确告诉模型，要求保留。只有新结果不比旧结果更差才采用，避免“越改越丢”。

如果重试后仍然缺失，就走最后一道兜底：从原文里挑出包含缺失 token 的片段，最多 3 行、200 字符，追加到摘要末尾，并加上统一的片段标记。

这相当于承认摘要失败，但拒绝丢掉关键数字。多占一点预算，比让模型在下一轮凭空猜测要好。

## 四、小窗口上的 JSON 幻觉

结构化摘要在正常窗口上工作得不错，到了 4096 窗口的 7B 模型上就变形了。

真机观察到两类问题：摘要里出现与对话无关的内容；保真缺失项一度达到 38 条。不是校验逻辑错了，而是这个规模的模型很难稳定输出符合结构的 JSON，也很难在重试中理解“必须保留这些 token”。

继续加提示词、加示例、加校验，收益越来越小。最后我们做了一个看起来倒退的决定：

窗口小于 8192 时，跳过 JSON 抽取与保真重试，直接请求纯文本摘要。

```ts
if (window < SMALL_CONTEXT_WINDOW) {
  const summary = await requestPlainSummary(folded);
  return { summary, facts: [], decisions: [], openLoops: [] };
}
```

代价是失去结构化事实与遗留项；收益是摘要不再编造，也不会产生几十条无法消化的保真缺失。

4096 窗口实测：摘要正确保留了端口 8443 等关键信息，`facts=0`、`fidelityMissing=0`、`degraded=false`。对小模型来说，一段可信的纯文本，比一份不可信的 JSON 更有用。

## 五、预算被固定块吃光

小窗口还暴露了另一个问题：历史预算算出来是 0。

4096 窗口下，系统提示 1721 token、工具声明 1030 token、输出预留固定 2048 token。三项一减，留给历史的只剩负数，装配侧只能全部丢弃。

修复分两步。

第一步，输出预留按窗口比例化：

```ts
reserve = clamp(window * 0.15, 512, 2048);
```

再用上一次真实 completion 校准，但校准值不允许超过窗口的 40%。小窗口不再被固定的 2048 吃掉一半。

第二步，如果算出的历史预算低于 512，先裁掉技能提示块与技能工具声明，再重新装配一次。技能是可选能力，原文是对话本身，预算紧张时先保后者。

4096 窗口修复前后的实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| system | 1721 | 378 |
| tools | 1030 | 0 |
| reserve | 2048 | 552 |
| historyBudget | 0 | 1843 |
| 单轮 promptTokens | 3330 | 497 |

历史预算从 0 回到 1843，单轮提示从 3330 降到 497。这不是微调，而是让小窗口从“不可用”回到“能用”。

## 六、取舍

小窗口放弃结构化摘要，是一个明确的取舍：宁可少一层结构，也不要一层错误的结构。大窗口仍然保留 JSON、事实与保真重试。

保真校验也不是万能的。它只能证明数字和日期还在，不能证明语义没有被扭曲。语义保真仍然要靠真机体验验收，而不是离线断言。

还有一个已知的遗留：摘要有时偏冗长，折叠 2620 token 只换回 2392 token，收益有限。后续需要约束摘要长度，例如不超过被折叠原文的 30%。这一版先把“不丢关键信息”做对，再谈“压得更狠”。

## 七、结果

结构化摘要让压缩结果可拆分、可检索；数字校验与重试把“摘要改错数字”从随机事故变成可检测、可兜底的问题；小窗口则退回到纯文本，用确定性换掉幻觉。

三件事共同指向一个原则：压缩可以丢叙述，不能丢事实；模型能力不足时，降低结构复杂度，而不是降低校验标准。
