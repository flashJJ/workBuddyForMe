# 上下文不是一锅炖：按意图切块分配预算

长对话里最典型的一次失败是这样的：用户先给了一段日志，问“这个服务监听哪个端口”，模型答对了；隔了两轮，用户只问“那刚才那个端口是多少”，模型却答不上来。

不是模型记不住，而是我们在装配时把最近原文当成可压缩的普通内容，让摘要和结构化事实先占满了位置。追问最需要的恰恰是那几句逐字原文。

这一轮我们做了一件事：不再用一个固定比例装所有轮次，而是按意图给不同区块分配预算。

## 一、先把上下文分成五块

装配结果不是一个扁平的消息数组，而是五类来源：

- `HEAD`：系统提示、人设、硬约束、当前目标；
- `TAIL`：最近的逐字消息；
- `MIDDLE`：更早历史的摘要，以及从摘要里抽出的结构化事实；
- `MEMORY`：长期记忆召回；
- `EVIDENCE`：知识库检索片段或工具返回结果。

以前的配额只区分“历史、摘要、事实、记忆”，追问和知识问答拿到的比例完全一样。分块之后，才有地方表达“这一轮该多看原文，还是该多看资料”。

## 二、配额是意图的显式表达

| 意图 | TAIL | MIDDLE | MEMORY | EVIDENCE |
|---|---|---|---|---|
| 追问 | 60% | 15% | 10% | 15% |
| 知识 | 35% | 15% | 10% | 40% |
| 工具任务 | 40% | 15% | 10% | 35% |
| 默认 | 50% | 25% | 10% | 15% |

中段那 15% 或 25% 还会再拆：摘要大约占 71%，结构化事实占 29%。这个比例沿用旧行为，保证升级前后的摘要与事实不会突然争夺空间。

四个数字相加是 100%，但它们不是“必须花完的预算”，而是“最多能占的上限”。某一轮没有检索结果，EVIDENCE 的空闲配额不会被强行填满，其他块仍可使用剩余空间。

## 三、为什么追问要把尾部拉到 60%

追问的特点是指代多、依赖近处原文：“那它呢”“这个方案的风险”“刚才那个数字”。

摘要擅长保留结论，不擅长保留精确字符串。端口、版本、字段名、错误码这些内容，一旦被摘要重述，就可能变形或消失。把 TAIL 提到 60%，等于优先保证最近几轮逐字可达。

知识问答则相反。用户问的是外部事实，答案主要来自资料块，所以 EVIDENCE 提到 40%，TAIL 降到 35%。这不是说历史不重要，而是历史只需要提供对话背景，不需要占大头。

工具任务介于两者之间：既要看最近的指令和参数，也要看工具返回的结构化结果，于是 40/15/10/35。

## 四、默认档位是安全网

默认档位是 50/25/10/15。它服务两种轮次：没有识别出明确意图的，以及置信度不足回退的。

把默认值设得接近旧行为，是为了让策略升级不改变大多数轮次的体感。意图识别不准时，最坏结果只是“和以前一样”，而不是“比以前更差”。

## 五、ContextPlan 是一个纯函数

配额计算没有做成服务，也没有读数据库。它是一个纯函数：

```ts
buildContextPlan({ intent, contextWindow, estimatedHistoryTokens })
  -> { quotas, clipOrder, preflightCompact }
```

输入只有三样：意图、模型窗口、本轮装配前的历史估算。输出只有三样：配额、裁剪顺序、是否需要预判压缩。

窗口会先乘一个安全系数，得到可用窗口：

```ts
usableWindow = floor(contextWindow * 0.9);
```

剩下的 10% 留给真实分词与消息结构的误差。纯函数的好处很直接：给定输入就能穷举输出，配额逻辑可以单独测试，不必启动一次完整对话。

## 六、裁剪顺序也是策略的一部分

配额只说明“每块最多多少”，当所有块加起来仍然超窗口时，还需要一个明确的裁剪顺序：

1. 先压 `MIDDLE`，也就是摘要与事实；
2. 再压 `MEMORY`；
3. 然后压 `EVIDENCE`；
4. 最后才动 `TAIL`。

`HEAD` 永远不裁。系统提示、人设和硬约束一旦被裁，模型的行为会直接跑偏，这比丢一点历史严重得多。

把中段放在第一位，是因为它有摘要兜底；把尾部放在最后，是因为它没有替代品。追问答不上来的根因，正是以前尾部会先被挤掉。

## 七、配额和裁剪要一起看

只改配额、不改裁剪顺序，效果会打折。假设追问拿到了 60% 的尾部预算，但裁剪时仍然优先砍尾部，那 60% 只是一个好看的数字。

所以这两件事必须由同一个计划输出。`ContextPlan` 同时给出配额和顺序，装配侧只负责执行，不再各自判断“谁更重要”。

## 八、边界与取舍

配额是硬上限，不是填充目标。没有内容时不会为了凑比例而重复、扩写或塞入低相关片段。

小窗口下，知识问答的原文预算会比追问更紧。4096 窗口里，35% 的尾部配额本来就不多，这是用“资料优先”换来的显式取舍，而不是遗漏。

这一版只把计划接入了对话侧。接口设计时刻意没有绑定对话特有的字段，后续任务侧、协作侧可以复用同一个函数，而不必再写第二套配额逻辑。

## 九、结果

追问不再被摘要挤掉最近原文，知识问答有更大的资料块，工具任务能同时保留指令和结果。更重要的是，这些差异不再藏在若干处 if-else 里，而是集中在一张表和一个纯函数里。

上下文策略变得可讨论：觉得追问答得不好，就看尾部配额和裁剪顺序；觉得知识问答资料不够，就看证据块比例。每个决定都有名字，也都有落点。
