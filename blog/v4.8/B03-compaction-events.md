# 压缩不是删消息：把上下文折叠变成可回放的事件

用户问过一个问题：为什么聊到后面，你把我前面说的细节忘了？

以前我们很难回答。数据库里其实一条消息都没删，但对话里能看到的只有一段摘要，而且没人记录“当时为什么压、压掉了哪几条、压完少了多少 token”。

这一轮我们把压缩从一次写回动作，改成一个可回放的事件。

## 一、压缩到底发生了什么

先把概念说清楚。压缩不是删除消息，而是选择“不再逐字发送”。

原始消息仍然在 SQLite 里，按会话顺序保存。压缩做的是三件事：

- 挑出最旧的一段消息，不再放进本轮上下文；
- 为这段消息生成摘要与结构化事实；
- 后续轮次只带摘要，不带那几条原文。

所以“被压掉”的消息仍然可以按 id 读回来，只是默认不参与当前请求。用户看到的“忘记”，本质上是模型这一轮没有看到原文，而不是数据消失。

## 二、只有一个投影的问题

以前压缩的结果只写在会话表的两个字段里：摘要正文，以及摘要覆盖到第几轮。

这两个字段是读取投影，服务读取很快，界面也能直接展示。但它回答不了四个问题：

- 这次压缩是阈值触发的，还是用户手动点的？
- 具体折叠了哪几条消息？
- 压缩前后各占多少 token？
- 摘要有没有丢关键数字，是否降级过？

没有这些信息，就无法回放一次压缩，也无法比较两个版本之间的压缩质量。投影适合读，不适合当审计真源。

## 三、事件里有什么

新增的事件叫 `context_condensed`，载荷大致如下：

```json
{
  "trigger": "threshold",
  "foldedMessageIds": ["..."],
  "summary": "合并后的摘要",
  "facts": [{ "key": "...", "value": "..." }],
  "decisions": ["..."],
  "openLoops": ["..."],
  "beforeTokens": 12000,
  "afterTokens": 7000,
  "fidelityMissing": [],
  "degraded": false
}
```

`trigger` 记录触发原因，`foldedMessageIds` 是被折叠消息的 id 列表，`summary` 是合并后的摘要，`facts` 是结构化事实，`decisions` 与 `openLoops` 记录已定结论和未完成事项。`beforeTokens` 与 `afterTokens` 让收益可量化，`fidelityMissing` 记录摘要遗漏的数字或日期，`degraded` 标记这次是否降级。

事件里没有原始正文。原文已经在消息表里，事件只存 id。这样既不会重复存储，也不会让事件日志膨胀。

## 四、投影与事件的分工

两者的职责被明确拆开：

- `conversations.summary` 与覆盖轮次是读取投影，负责快速装配；
- `context_condensed` 是审计真源，负责解释与回放。

它们在同一事务里写入。摘要写回成功、事件写入失败时，不阻断摘要本身。读取路径不能因为观测失败而不可用。

同样，事件也不能替代投影。每次装配都去扫事件流、重放摘要，既慢又容易和消息表不一致。投影是缓存，事件是账本，各做各的事。

## 五、四种触发原因

同一个事件结构，承载四种来源：

- `threshold`：回合结束后历史超过阈值；
- `preflight`：下一轮装配前估算占用过高，先压再请求；
- `model_change`：切换到了窗口更小的模型；
- `user_explicit`：用户在面板上主动点“压缩”。

触发原因不是装饰字段。它决定了这次压缩是否可预期、是否多花了一次模型调用，也决定了排查时该看哪条路径。

## 六、折叠 id 让原文可回读

`foldedMessageIds` 是这次设计里最实用的字段。

它至少有三个用途：

1. 用户或开发者可以按 id 找回原文，确认摘要有没有歪曲；
2. 离线评测可以断言“折叠的正是最早的那 N 条”，而不是任意 N 条；
3. 面板可以展示“这次压掉了哪几条”，而不只是一个抽象的比例。

如果只存摘要，不存 id，事后就无法证明压缩范围是否正确。id 列表很便宜，却把可回溯性从口号变成了事实。

## 七、失败也要留痕

摘要不是每次都能成功。模型超时、返回空、JSON 解析失败，都可能发生。

这时的策略是降级而不是中断：保留最早一条加最近若干条，中间部分放弃，事件标注 `degraded: true`，回答继续。

降级事件同样包含前后 token 与折叠 id。它告诉后来的人：这次不是正常压缩，而是兜底路径。没有这个标记，一次失败的压缩会伪装成一次成功的压缩，后续所有对比都会失真。

## 八、代价与边界

事件日志沿用既有的保留策略，不会因为新增一种类型就无限增长。压缩事件本身也很小：摘要最多几千字符，id 列表有上限，事实与遗留项都有条数限制。

话题切换目前不触发压缩，只记录信号。我们不想在语义还没验证的情况下，让一次“看起来换话题了”自动改写历史。

这一版解决的是“压缩可解释”，不是“压缩更聪明”。摘要质量、压缩比例、话题边界，仍然是后续要单独处理的问题。
