# “记住”和“忘掉”应该是一条命令，而不是一次猜测

长期记忆此前只有一个写入通道：抽取器。

对话结束后，抽取器从文本里判断“哪句值得记”，然后写进记忆库。它在大多数时候工作得不错，但也带来两个问题：用户明确说“记住这个”时，没有一条确定的路；用户说“忘掉那个”时，更没有审计。

于是出现了典型的不对称：记错了很难发现，删错了无法追溯。

这一轮我们把“记住 / 忘掉”升级成一等意图。

## 一、显式命令与隐式抽取并存

抽取器没有下线。它仍然负责从普通对话里提炼值得长期保留的事实。

变化在于优先级：显式命令先执行，抽取器随后仍然可以工作，但同一个内容不会因为两条通道重复写两遍。

显式命令的识别很克制，只匹配句首的命令式：

- “记住：我的常用端口是……”
- “帮我记一下，周三要交……”
- “忘掉关于……的记忆”
- “删除……的这条记录”

像“我忘记带钥匙了”这种句子，虽然包含“忘记”，但不是命令，不会被当成删除请求。判断依据不是关键词出现与否，而是它是否出现在句首、后面是否跟着一段可被清理的内容。

内容太短也不动作。一句话只留下一个“它”或“这个”，既无法检索，也无法审计。

## 二、记住的时候，到底写什么

写入的不是一段自由文本，而是带元数据的记忆：

```ts
rememberOne({
  kind: 'fact',
  content,
  importance: 0.8,
  scope: 'assistant',
  source: 'manual',
  sourceConversationId,
  sourceMessageId,
})
```

`kind` 可以是事实，也可以是约束。约束会置顶，并且不参与衰减；事实按重要度、时间与使用频率衰减。

`importance` 给 0.8，高于自动抽取的默认值。理由很直接：用户亲自说“记住”，这本身就是最强的相关性信号。

`subjectKey` 用来表达“这条记忆在说哪个对象”。同一个对象的同类事实命中时，优先合并，而不是堆出一串互相矛盾的记录。

来源消息 id 必须写。它让“这条记忆从哪句话来”可以被回答，也为后续的冲突处理留下依据。

## 三、忘掉为什么不是删除

“忘掉”走软归档：把状态改成已归档，不执行物理删除。

原因有三个：

1. 误删要能恢复。用户说“忘掉那个端口”，可能只是想删掉某一条，不应该把相关记忆全部清空；
2. 需要审计。谁在什么时候、因为哪句话归档了什么，必须留痕；
3. 归档和删除在语义上不同。归档是“不再参与召回”，删除是“数据不存在”，前者可逆，后者不可逆。

还有两道保险。

第一道是召回分门槛。只有召回分达到 0.55 的候选才会被归档，避免一句模糊的“忘掉那个”误伤无关记忆。

第二道是数量上限。单次命令最多归档 3 条，防止一句话清空整个记忆库。

如果召回结果不可信，宁可不动作。用户会再补一句更具体的指令，这比静默删掉一堆东西安全得多。

## 四、冲突保留双方

同一个 `subjectKey` 出现两个不同值时，系统不静默覆盖。

做法是保留双方，把旧的一条标成 `superseded`，新的继续保持 active。读取时默认只取 active，但旧值仍然可查。

这看起来不如“后写覆盖”干净，但对记忆系统是必要的。用户可能说“改成 8443”，也可能只是说“另一个环境是 8080”。如果直接覆盖，第二种情况就丢了信息；如果两条都留着并标注状态，后续还能解释“为什么我记得两个端口”。

硬约束永远优先。它是用户明确设定的边界，不参与这种“更新时间 + 置信度”的竞争。

## 五、用户必须看得到来源

记忆面板展示三类信息：记住了什么、来自哪句话、为什么被记住。

每条记忆都可以单独删除。删除同样走软归档，并写审计事件。

这一步不是锦上添花。一个不可见的记忆系统，用户无法纠正，也无法建立信任。把来源摆出来，误记就从“玄学”变成了“可以指出的错误”。

## 六、为什么不做常驻记忆守护进程

我们考虑过让一个后台进程持续整理记忆：合并重复、清理过期、检测冲突。

最后没有做。原因是收益不确定，而常驻进程带来的生命周期、资源占用和一致性问题都很具体。

当前的做法是回合内写入、召回时读取、面板里治理。所有动作都发生在用户可感知的边界内，出错也容易定位。

## 七、结果

- 用户说“记住”，会得到一条带来源的事实或约束，而不是等抽取器猜；
- 用户说“忘掉”，相关记忆被归档而不是删除，可从面板恢复；
- 同一个键的冲突会保留双方，并标注取代关系；
- 每条记忆都能看到来源，支持逐条清理；
- 显式写入失败不会影响本轮回答，只记录失败，不阻塞主链路。

真机的一次五轮对话里，第一轮就是“记住”类意图，后面三轮追问、一轮知识问答。记忆在后续追问中被正确召回，说明显式写入与召回链路是通的。

记忆治理的难点从来不是存储，而是“谁有权改写、改写后能否解释”。把“记住 / 忘掉”做成显式意图，本质上是在给用户这个权利，也给系统留下可审计的痕迹。
