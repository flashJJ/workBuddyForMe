# 看得见的上下文：本地快照、面板与一次载荷超限的修复

上下文策略做得再细，如果用户看不见，就仍然像黑箱。

以前我们只有外部 trace 里一个预算 span。开发时能看，用户看不到。回答变短、追问失忆、压缩发生，都没有本地证据。这一轮补上了三样东西：轻量快照、会话面板、离线评测。

## 一、快照只存统计

新增的事件叫 `context_snapshot`，每轮装配后写入一条。

它记录的是：

- 本轮意图；
- 模型窗口与可用窗口；
- 系统提示、工具声明、输出预留各占多少 token；
- 原文预算与实际原文 token；
- 保留与丢弃的消息条数；
- 是否发生截断。

它不记录任何正文。摘要、用户消息、模型回答都不进快照。

这个边界很重要。上下文观测很容易滑向“把整份 prompt 存下来”，那样既贵又危险。只存统计，已经足够回答“这轮上下文为什么这么紧”，也足够做聚合与告警。

## 二、面板读事件流

对话顶栏的上下文面板不维护独立索引表，而是直接读会话事件接口：

```text
GET /api/events?scope=chat&scopeId=<conversationId>&limit=500
```

前端在客户端做汇总：取最近的意图标签、最近一次快照、最近的压缩记录，拼成一块面板。

这样做有三个好处：

- 不新增存储，事件只有一份；
- 面板与审计读的是同一数据源，不会出现“面板说压了、事件里没有”；
- 沿用既有的 180 天保留策略，不需要额外的清理任务。

代价是只读最近 500 条，没有分页。对单会话的日常排查够用，对超长历史不做全量分析。这是有意的范围控制。

面板展示四类信息：意图、配额构成、压缩历史（触发原因与前后 token）、以及一个“立即压缩”按钮。深链打开某个会话时，面板也能正确选中对应上下文，而不是落到默认会话。

## 三、九个离线用例

观测之外，还需要可回归的断言。我们新增了一个上下文评测脚本，共 9 条用例。

前 4 条验证意图与配额，每条独立会话：

| 输入 | 期望意图 | 期望原文占比 |
|---|---|---|
| 一句晚间问候 | 闲聊 | 0.50 |
| “某个术语的定义是什么” | 知识 | 0.35 |
| “那它和另一种方案有什么区别” | 追问 | 0.60 |
| “没听懂，你刚才说什么” | 澄清 | 0.55 |

第一行值得单独说。这句问候的规则置信度只有 0.3，低于阈值，所以系统回退到默认策略，原文占比是 0.50，而不是闲聊档的 0.60。这条用例验证的正是“低置信度不启用意图配额”这个边界。

配额断言带 ±0.04 容差，因为系统提示与工具声明的实际占用会让比值轻微偏移。

中间 2 条验证记忆治理：说“记住”后，按关键字查询能看到 active 记忆；说“忘掉”后，同样的查询看不到它。

最后 3 条用例验证压缩与预算，断言包括：

- 显式压缩产生 `user_explicit` 事件，摘要非空，未降级；
- 折叠的消息 id 恰好是消息顺序里最早的 N 条，且压缩前 token 大于压缩后；
- 压缩后再发一轮，原文 token 低于压缩前的 75%；
- 所有快照满足预算不变量：系统、工具、预留、原文之和不超过可用窗口，原文不超过原文预算，至少保留一条消息。

评测只做结构化断言，不断言“压缩后仍能引用具体数字”。mock 模型不回放历史语义，这类保真只能靠真机验收。这个边界写在用例设计里，避免用一个假通过的测试冒充质量保证。

## 四、真机数据

真机环境同时跑了两个模型：一个大窗口模型，一个 4096 窗口的本地 7B。

第一个场景是五轮长对话，其中四轮带长日志。意图序列是：

```text
memory_write -> follow_up -> follow_up -> follow_up -> knowledge
```

第一轮“记住”被识别为记忆写入，随后三轮连续追问，最后一轮转为知识问答。最近一次快照显示 `historyTokens=2605`，保留 9 条消息。追问的端口与负责人回答正确。

第二个场景是手动压缩。事件触发原因是 `user_explicit`，折叠最早 6 条消息，token 从 2620 降到 2392。压缩后继续追问，关键字段仍然答对。

第三个场景是模型切换。大窗口积累 4103 token 后切到 7B，触发 `model_change`，4237 token 降到 1580。7B 依据摘要仍然答对了关键数字。

三个场景证明的是链路连通与范围正确，不是摘要文笔。后者仍然要靠人工阅读。

## 五、一次载荷超限导致的“丢事件”

面板上线后遇到一个典型问题：明明压缩过，面板却显示“尚未触发压缩”。

排查发现不是没写事件，而是事件被前端整条丢弃了。

压缩事件的保真缺失列表在长对话里达到 38 条，而事件契约给这个字段的上限是 20 条。前端用严格校验解析，超出上限就 `safeParse` 失败，于是整条事件被跳过。

根因是观测载荷没有按契约裁剪。业务数据可以不设上限，但事件是跨进程契约，必须在写入前收敛。

修复分两处：

1. 写入前裁剪：摘要最长 8000 字符，折叠 id 最多 500 条，事实最多 20 条，结论与遗留项各 10 条，保真缺失最多 20 条；
2. 读取时宽松归一：对历史上已经写入的脏事件，先做容错处理再展示，避免旧数据继续让面板空白。

两处都有单元测试。第一处保证新事件一定合规，第二处保证旧事件不会永久破坏面板。

这次事故的教训很直接：审计事件必须“写得进去”。如果观测本身会因为数据规模而失败，那它就不是观测，而是另一个故障源。

## 六、还没做什么

- 压缩收益仍然有限，2620 降到 2392，摘要偏冗长；后续要约束摘要长度；
- 小窗口下知识问答的原文预算偏紧，这是配额取舍，不是缺陷；
- 面板只读最近 500 条事件，没有分页与独立索引；
- 语义保真没有自动化门禁，仍依赖真机体验验收。

## 七、结果

现在，一轮对话结束后，可以回答四个问题：这轮被理解成什么、预算怎么分、有没有压缩、压缩前后差多少。用户看到的是面板，开发看到的是事件，评测看到的是断言，三者读的是同一份数据。

上下文治理从“调参数”变成了“看证据再调”。这才是可观测性真正的价值：不是多一块图表，而是让每一次策略选择都有据可查。
