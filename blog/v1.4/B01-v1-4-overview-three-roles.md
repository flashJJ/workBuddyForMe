# 会分工：规划者、执行者、审查者——单人项目的最小多智能体协作

我们做的是一个本地优先的桌面 AI 应用：Electron 壳、Next.js 前端、本地 SQLite，模型走 OpenAI 兼容协议，可以接云端也可以接本机模型。在知识库能「答得准」之后，下一个暴露出来的瓶颈不是模型不够聪明，而是**一件复杂任务全压在单轮对话上**。

## 断点：一条消息里，模型同时干三份工作

让模型「把这个产品的竞品调研做了，给出结论」，在旧形态里发生的事情是：多步拆解、调用工具取证、对着自己的产出自检返工，全部混在同一条回复的生成过程中。模型一个人既当规划者（先做什么、后做什么），又当执行者（调检索、读结果），还当裁判（自己做得行不行）。

这带来四个具体的断点：

- **多轮返工不可见**：它心里推翻重来了几遍，界面上只有最后一段文字，过程没有任何轨迹；
- **花费不可见**：一轮到底调了多少次工具、烧了多少 token，用户和开发者都只能事后估算；
- **交接是自由文本**：就算把多个角色塞进同一段提示词，角色之间传递的也是自然语言，无法回放、无法审计、无法校验；
- **自检靠自觉**：审与不审、审多细，全凭模型本次的发挥，没有任何结构保证它真的逐条核对了。

这个版本要回答的不是「怎么让更多智能体一起聊天」，而是：**能不能让一次复杂任务的分工过程变得确定、可见、可回放？**

## 取向：只做固定三角色的串行拓扑

社区多智能体演示的常见形态是 N 个角色群聊、并行执行、运行时自由拼系统提示词选角色。我们一个都没做。这个版本的拓扑小到可以用一句话讲完：

```text
规划者 → 执行者 → 审查者
                ↓
          通过  → 用户（终态）
          返工  → 回到规划者（沿同一条边再来一轮）
          驳回  → 终止（失败终态，附驳回理由）
```

角色是三个枚举常量，不是自由文本；角色之间只允许四条预定义的合法交接边：规划者到执行者、执行者到审查者、审查者回规划者、审查者到用户。任何其他配对在落库前直接判非法。**执行者不能把结果绕过审查直接交给用户，规划者不能跳过执行者自己宣布完成。**

刻意不做的还有：并行多执行者（首期串行单执行）、自由系统提示选角色、自动模型采购。单人项目维护一套角色都吃力，维护一个角色议会不现实。

## 一轮协作实际跑起来是什么样

从用户视角，整件事只有一个动作：在对话输入区打开「任务模式」开关，像平时一样发一句话。开关是会话级的，默认关闭，切换助手、切换会话、新建对话都会复位；开启后图片附件入口隐藏——协作通道只接收目标文本，不支持多模态任务。

之后看到的不再是一条慢慢生成的回复，而是一张内联在消息流里的泳道卡：

1. 规划卡出现：子任务标题、背景、验收条逐条列出；
2. 执行卡接在下方：工具以 chip 形式逐个亮起，证据带着引用角标汇拢；
3. 审查卡收口：每条验收后面跟一个通过或不通过的标记，最后盖上裁决徽标；
4. 裁决「返工」时，泳道不新增气泡，而是在同一组卡片下方追加新一轮；顶部预算条始终显示当前轮次、步数与 token 的实时用量。

任务中心另有一个「协作任务」区段，支持按状态筛选、展开逐条交接详情、对运行中的任务直接急停。工作流画布上的 agent 节点试运行时，节点在时间线上聚合成单行，展开是同一只读协作卡——三处入口，渲染同一份结构化数据。

可回放的含义值得说清楚：终态之后任何时刻发一个 GET 详情请求，拿到的是运行记录加全部交接载荷，前端用与实时帧流完全相同的归并函数把它重建成同一张卡。实时画面与历史画面不是两套实现，因此不存在「看着它跑是一个结果、回头看是另一个结果」的缝隙。

## 四块回答

| 旧断点 | 这个版本的回答 |
|---|---|
| 无拆解、无自检 | **结构化子任务单**：规划者产出经 zod 校验的对象——标题、背景、逐条验收标准、允许的工具域、指定知识库；字段不齐、验收为空、长度超限，整包退回，不存在「差不多行」的任务单 |
| 返工与花费不可见 | **三重预算硬治理**：轮次默认 3、硬区间 1–5；执行步数默认 20、区间 1–50；总 token 默认 8 万、区间 1 万–20 万。任一触顶不是报错，而是要求执行者交付「当前最佳结论 + 未竟事项清单」，运行收敛到预算超限终态 |
| 交接无法回放审计 | **结构化交接落库**：交接表带轮次、序号、方向、载荷 JSON，序号在运行内自增、轮次加序号唯一；终态可通过 GET 接口连同全部交接逐条回放，实时过程则走 SSE 帧推送 |
| 没有用户入口 | **三处可视化**：对话输入区的「任务模式」会话级开关（默认关、不跨会话、不持久化）；消息内联的角色泳道卡，带实时预算条与终态样式；任务中心的「协作任务」区段；可视化工作流画布上的 agent 节点，试运行时可展开只读子泳道 |

子任务单是整件事的枢纽。规划者的自由发挥被关在一个带校验的对象里：标题最多 100 字、背景最多 2000 字、每条验收最多 500 字、验收 1–10 条——既防爆 token，也防模型把交接载荷当成无限容量的草稿纸。

## 安全边界：无人值守，永不放行桌面工具

这个应用能操作桌面（截图、键鼠），所以协作引入的第一个安全问题是：**当协作不是由人盯着发起的，怎么办？**

工作流支持 API 与 MCP 的无人值守触发。agent 节点如果在这种触发方式下声明了桌面工具域，引擎的策略门控**直接拒绝，且根本不发起协作**——不是警告，不是可配置项，是永久策略。只有人在画布上手动试运行时才放行；放行也不是静默执行：写操作与危险操作的授权弹窗照常弹出，并标注「协作任务 · 执行者发起」的任务归属，决策仍按调用标识走全局确认通道解决。

协作运行记录不进应用备份，与工作流运行记录同级——它们是可重建的过程数据，不是用户资产。

## 边界清单：第一版明确不做什么

把「不做」写得和「做」一样显式，是单人开发控制范围的唯一办法。这一版的协作边界有：

- 不做 N 角色群聊，角色集合是封闭枚举，增角色等于改契约、改状态机、改评测；
- 不做并行执行，同一时刻只有一个执行者，返工是串行循环，没有并发合并问题；
- 不做自由系统提示选角色，角色行为由固定协议定义，不接受用户临场塞人设；
- 不做协作多模态，通道只收目标文本；
- 不做自动模型采购，三个角色的模型走固定回落链，由配置决定；
- 无人值守触发桌面工具永久禁止，这条没有灰度期。

每一条「不做」对应的都是一类状态空间：群聊引入消息顺序的不确定性，并行引入合并与竞争，自由提示引入不可回放的角色漂移。第一版先把这些状态空间整个删掉。

- golden 评测 15 例分四类全过，外加三开关反向验证：去掉审查者（返工题不再有拦截裁决）、关掉知识库（知识题必须全部无证据降级）、预算压到 1 轮（返工题必须收敛到预算超限终态并附未竟清单）；一道纯时间工具的护栏题在任何开关状态下都必须通过；
- 静态检查门禁全过：类型检查、ESLint 零错误，文件行数门禁全绿。

评测不是一次性脚本，而是随仓库保留的命令：任何改动之后都能把同一批 golden 用例在四个开关状态下重跑一遍，输出正向加三个反向的通过率。对单人开发来说，这比任何设计文档都更能防止「改着改着把协作改坏了」。

## 为什么「最小」比「强大」重要

单人项目做多智能体，最容易掉进的陷阱是追求角色数量和拓扑花样。这个版本最核心的取舍恰恰相反：**拓扑越固定，状态机越确定；状态机越确定，评测才可能做成确定性断言。** 返工沿哪条边走、终态有几个、交接载荷长什么样，全部写死在契约里，于是「审查拦截成功」「预算触顶必交付」这类行为才能用 mock 角色协议回放成可重复的测试，而不是靠人盯着界面看它这次灵不灵。

模型只负责拓扑允许它负责的那一小段：拆任务、执行、给裁决。至于角色怎么连、几步必须停、失败怎么收敛，是代码的承诺，不依赖模型本次的心情。
