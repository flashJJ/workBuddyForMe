# 协作内核：结构化交接、异步生成器状态机与三重预算治理

上一篇讲了固定三角色的整体设计，这篇钻进内核：角色之间到底传什么、状态怎么存、一次协作运行怎么被驱动、预算触顶时具体发生什么。

## 契约先行：枚举、schema 与判别联合

协作的第一行代码不是编排器，是 shared 包里的类型定义。整个内核建立在几组写死的契约上：

- 角色枚举只有三个值：规划者、执行者、审查者；阶段常量与终态枚举同样是封闭集合；
- 子任务单 schema：标题、背景、验收数组、工具域、知识库；
- 执行者产出 schema：总结、工具调用序列、证据数组、未竟事项数组；
- 审查裁决枚举：通过 / 返工 / 驳回，返工与驳回必须附理由，另有与验收下标一一对齐的逐条结论；
- 交接载荷按方向区分：子任务、产出、裁决三类字段各出现一次，至少包含其一，再由编排器按「谁交给谁」的角色对做强校验。

SSE 侧的帧分五族：阶段切换、交接、审查、预算、增量；后来为桌面工具的人工授权又加了一族授权帧，线上一共 19 个事件。载荷形状在 shared 包单一真源定义，后端产出、前端归约、mock 回放共用同一份类型。

## 存储：两张表，外键可空

存储只有两张核心表：协作运行表与角色交接表。

交接表的序号在运行内自增，轮次加序号构成唯一约束——同一条时间线上不可能出现两个「第二轮的第三次交接」。运行表的终态化由仓储层的生命周期守卫把关：已终态的运行不能再被终结第二次。

一个容易忽略的设计是协作运行与桌面任务的关系。执行者每轮都会建一条桌面任务记录，它外键归属当前协作运行；但这个外键**可空，删除策略为置空**：删掉协作运行记录，桌面任务记录原样保留，只是协作归属变为空。协作过程数据可弃，任务执行历史是用户的资产。

落库前还有一道拓扑强校验：载荷形状对了不够，还要按「谁交给谁」配对检查——规划者交出的载荷必须带子任务单，执行者交出的必须带产出，审查者交出的必须带裁决，方向不在四条合法边内的交接直接拒收。schema 管形状，角色对管语义，两层分开。

## 监督状态机：转移表只有六行

编排器循环的背后是一个纯函数状态机，阶段只有规划、执行、审查三个，加上两个终态，全部合法转移可以列成一张小表：

| 当前阶段 | 事件 | 下一阶段 |
|---|---|---|
| 规划 | 子任务单产出 | 执行 |
| 执行 | 产出完成 | 审查 |
| 审查 | 通过 | 完成（终态） |
| 审查 | 驳回 | 失败（终态） |
| 审查 | 返工且仍有轮次 | 规划（轮次加一） |
| 审查 | 返工但轮次用尽 | 预算超限（终态） |

表外的任何转移直接抛错——那只可能是编排器在错误阶段调了转移，属于编程错误，由测试全覆盖防回归。状态机不碰模型、不碰数据库，编排器是它唯一的驱动方：模型产出什么，就喂给它什么事件，它只回答「现在该在哪个阶段」。

## 编排器是一个异步生成器

协作运行的驱动形态是一个异步生成器：每步 yield 一个 SSE 帧，生成过程中全程落库，终态时 return 一个运行视图。四条终态路径——完成、失败、取消、预算超限——有同一个硬性要求：**都必须显式 return 终态视图**。

```text
async function* 运行协作(...): AsyncGenerator<帧, 运行视图> {
  while (未终态) {
    yield 阶段帧; 规划(); yield 交接帧;
    yield 阶段帧; 执行(); yield 交接帧;
    yield 阶段帧; 审查(); yield 裁决帧;
  }
  仓储.终态化(...);
  return 仓储.取详情(runId);   // 四条路径，条条 return
}
```

这里踩过一个很隐蔽的坑。生成器外面包了一层清理包装器，写法是「把内层生成器 `yield*` 委托出去，并 return 委托结果」。这个写法只有在**内层显式 return** 时才会把终态值透传给消费方；早期有一条终态路径只 yield 了完成帧、没有 return，结果消费方 await 到的生成器结果是 undefined——帧看起来都发完了，程序却永远等不到终态值。

由此引出第二条铁律：**SSE 的完成帧不带终态枚举，不能信最后一帧。** 完成帧只表示流结束了，并不告诉你这算完成、失败还是预算超限。客户端在流结束后必须再发一次 GET 详情请求，回读权威终态做对账。帧是实时画面，GET 才是权威状态；两者不一致时，以 GET 为准。

## 服务层：先建行，再订阅

HTTP 侧沿用桌面任务既有的模式：POST 只负责预建运行行并立即返回运行标识，真正的协作由事件订阅驱动。这样设计解决了一个时序问题——客户端可以先拿到标识、建好 SSE 订阅，再看着运行从第一帧开始跑，不会漏掉开场事件。

配套的防护有四条：同一运行的并发双启有先占注册，第二个启动请求直接拒绝；客户端断开订阅联动取消信号，但取消语义还保留独立的取消接口兜底（订阅可能从未建立）；启动前有 422 预检，通道没接好时给明确错误而不是启动后挂死；工作流画布上的 agent 节点走无会话入口，不经过对话 API。对外一共四个路由：启动、列表、详情（运行加全部交接）、事件流，外加快照式取消。

## 协议失败：显式降级，不是抛错

模型不按协议返回 JSON 是常态，不是意外。处理原则是连续两次协议失败后**显式降级**，而且降级必须在交接记录与界面上都看得见：

- 规划者连续两次产不出合法子任务单 → 降级为「原目标直派」：把用户原始目标包成一张明确标注过的降级派单，执行者拿到完整目标自行裁量；
- 审查者连续两次产不出合法裁决 → 裁决降级为自动通过，但备注里明确标注「未经完整审查」。

降级不是异常分支，而是一种用户可见的终态语义。打开泳道卡，用户能清楚看到「这轮没经过完整协作」，而不是一切如常地显示通过。取消信号触发时则立即上抛，不计失败、不重试，避免把用户急停误记成一次协议事故。

## 预算治理：三个纯函数计数器

轮次、步数、token 是三个独立计数器，推进逻辑全是无副作用纯函数：消费一次用量、进入下一轮、判定首个触顶项（检查顺序固定为轮次 → 步数 → token）。负数输入按零处理，防上游脏数据；外部传入的预算配置还要再过一遍硬区间防御校验。

触顶后的行为是整个设计里最重要的产品决定：**不报错，保交付。**

```text
if (首个触顶项 !== null) {
  要求执行者输出：当前最佳结论 + 未竟事项清单（系统自动补一条预算注记）;
  运行落在「预算超限」终态;
  交付物 = 最后一轮产出 + 注记;
}
```

预算花完不等于任务白跑。执行者在循环中一直被要求维护「未竟事项」，它天然就是为这种时刻准备的交付通道：资料缺口、没来得及验证的假设，列进清单随结论一起交付，比烧光预算后甩一个异常体面得多。预算帧在每次消耗后实时下发，前端预算条显示「已用 x/N」，触顶后超限指标变红。

## 执行者适配：每轮一条桌面任务，两种观察模式

执行者复用既有的桌面任务循环，但每轮新建一条桌面任务记录，归属当前协作运行。观察模式由子任务声明的工具域决定，只有两种：

- **截图模式**：截图加视觉门控，要求视觉模型，桌面域任务专用；
- **工具模式**：合成观察加白名单工具——知识库检索、MCP 服务器限定工具、工作流节点、以及按具体限定名放行的工具，其余一律不暴露。

证据由系统侧收敛，不靠模型自报：跨步骤去重（同一条原文只保留一个引用），引用角标在最终结论的证据集上连续重排；工具调用序列按首次出现顺序记录。审查者拿到的因此是可核对的材料，而不是模型声称自己干过什么。

## 角色模型的回落链

三个角色可以各配各的模型，解析顺序是一条固定回落链：节点显式覆盖 → 助手的角色级覆盖 → 助手的通用模型 → 系统默认；画布上没有助手的节点则只有显式覆盖与系统默认两级。每次角色调用的 token 用量经用量回调计入预算账本，降级调用（没有真发请求）计零。

## 为什么协作原语全是纯函数

预算推进、规划协议解析、审查协议解析、监督状态机——这些全部独立成无依赖的纯函数模块。原因很实际：**协议解析是脏活。** 模型返回的 JSON 外面可能套着 markdown 围栏、前面缀着「好的，这是结果」、后面跟着一段解释，解析器要从这堆脏输出里抠出合法对象。脏输出的形态可以枚举几十种，纯函数才可能用单测把它们逐个钉死；状态机同理，非法转移直接抛错，由测试全覆盖防回归。

编排器本身因此保持很薄：它只负责按状态机驱动、落库、发帧，不做提示词装配，也不做 JSON 解析。哪一层出问题，就去哪一层的纯函数测试里复现。
