# 一次工具输出几十万字符：内容寻址溢出与 spill:// 引用

先看一条真实形状的故障。用户让助手读一份构建日志，工具返回了 32 万字符。下一次模型请求直接把上下文顶满，回答被截断；界面里那条工具卡片也卡住了，因为它试图把整段文本塞进一个折叠区。

这不是某个工具的 bug，是**工具输出没有尺寸纪律**。任何能返回文件内容、命令输出、网页正文的工具，都可能一次吐出几十万字符。

## 一、现象拆成两半

| 症状 | 直接后果 | 更深一层 |
|---|---|---|
| 上下文被一次工具结果占满 | 模型没有空间放对话历史与指令，回答质量骤降 | 压缩机制要花一轮去处理一段本来就不该进来的文本 |
| 原文原样进入持久化路径 | 消息/轨迹行体积失控，列表查询变慢 | 备份、导出、迁移都被一条异常大的记录拖累 |
| 界面渲染整段文本 | 页面卡顿，折叠区展开要等 | 用户其实只想看开头判断「这结果对不对」 |

两半的共同点是：**全量文本既不是模型需要的，也不是人第一时间需要的。** 模型需要的是「这段输出大概是什么、值不值得继续看」；人需要的是「能定位、能按需打开全文」。

两类后果还会互相放大：上下文被占满后，压缩机制被迫在信息量最高的一轮里做摘要；而一旦原文落库，备份与导出也跟着变慢。一次异常输出，同时抬高了运行时成本和存储成本。

## 二、三个直觉方案，都否决了

**方案一：直接截断。** 超过阈值就砍掉尾部。问题是信息不可恢复：模型不知道后面还有没有关键行，人也没法复核。截断只解决了内存，没解决复盘。

**方案二：整段塞进消息表。** 让数据库承担存储。问题是把「上下文问题」换成了「数据库问题」：一条几十万字符的行会拖慢按会话取消息的查询，也会让备份与导出体积失控；而模型仍然只看得到窗口内的部分，问题没消失。

**方案三：让模型自己分段读。** 给工具加 offset/limit，模型循环读取。问题是每一次读取都是一次模型请求，几十万字符要读几十轮，成本和延迟都不可接受，而且模型很可能在中途忘记自己要找什么。

最终选的是第四种：**全文落到文件，上下文里只留预览与一个可解析的引用。** 存储与上下文分开治理，两边都不勉强。

## 三、内容寻址：文件名就是内容指纹

```js
const THRESHOLD = 100_000;   // 字符
const PREVIEW   = 2_000;     // 字符

function maybeSpillOutput(output) {
  if (output.length <= THRESHOLD) return { output, ref: null };
  const hash = sha256(output);
  const file = join(spillDir(), `${hash}.txt`);
  if (!existsSync(file)) writeFileSync(file, output, 'utf8');
  return {
    output: `${output.slice(0, PREVIEW)}\n\n[输出过长，已溢出到 spill://${hash}（原 ${output.length} 字符）]`,
    ref: `spill://${hash}`,
  };
}
```

选内容寻址而不是「按时间戳命名」，有三个直接好处：

- **幂等。** 同一段内容第二次出现时，文件已存在，跳过写入。不需要额外的去重表。
- **可校验。** 引用里的哈希就是内容指纹，读取方可以重新计算比对，确认文件没有被替换。
- **无状态。** 不需要维护「哪个会话、哪次调用对应哪个文件」的映射；引用本身自带全部定位信息。

目录放在应用数据目录下的 `spills/`，和其他本地数据一起备份，不散落在临时目录。文件名里没有时间戳、没有会话 id，也是为了清理时按内容去重，而不是按时间堆积。代价是文件名不可读，人一眼看不出这是哪次调用的输出；需要看全文时由界面打开，而不是让人去翻目录。

## 四、为什么阈值是 100,000，预览是 2,000

这两个数字不是拍的，它们各自回答一个问题。

**阈值回答「什么时候该溢出」。** 定在 100,000 字符，是因为它明显高于常规工具输出的正常范围，也明显高于既有压缩机制的预算区间：

- 正常的长输出（几千到一两万字符）仍然原样进上下文，压缩机制照常工作；
- 只有病理级的输出才走溢出，两者处理的样本不重叠，不会互相抢占。

如果阈值压到压缩预算的量级，普通的长文档也会被溢出，压缩就永远见不到它们；反过来，如果阈值太高，模型仍会被一次超大输出顶爆。100,000 字符按常见分词器换算大约是数万 token，已经足以吃掉一次对话的大半预算，再高就没有保护意义了。

**预览回答「模型至少要知道什么」。** 2,000 字符足够看出这是一份日志、一段代码还是一张表格的前几行，也足够判断要不要换个更精确的查询重跑。给更多预览，等于把阈值悄悄抬高；给更少，模型只能盲猜。

这里统计的是字符数，不是字节数。按字节算，同样的中文文本会提前一半触发溢出；按字符算，「看起来多长」才和阈值对得上。代价是代理对（emoji、部分生僻字）在长度里算两个单位，边界会略微提前，但不会误判。

## 五、模型看到什么，人看到什么

模型看到的是预览加一行标记：

```text
<前 2,000 字符>

[输出过长，已溢出到 spill://<sha256>（原 320,184 字符）]
```

标记里带原始长度，是给模型的一个信号：「这里被截断了，不是工具没返回内容。」没有这行字，模型容易把预览当成完整结果，然后基于残缺信息下结论。

人看到的是全文。界面通过 `/api/spills/:hash` 打开，返回纯文本，不缓存。模型引用、界面打开、接口读取三处共享同一个哈希，不存在「模型看到的是 A、人打开的是 B」。

需要明确一点：**模型不能自己去读溢出文件。** 它没有这个工具，只有引用字符串。这不是缺陷，而是设计——溢出是为了让模型承认「我没看全」，然后选择更精确的工具调用，而不是假装读完了。

## 六、失败时往哪降级

写入可能失败：磁盘满、目录不可写、权限不足。这一段的处理方式是「不降级成原始输出」。

溢出发生在工具执行的返回值处理路径里，和工具本身在同一个 try 块。写入抛错时，整个调用走统一的工具失败分支，回灌给模型一条可读错误（例如「执行失败：磁盘空间不足」），而不是把 32 万字符原样塞回去。

这个选择的理由：**溢出失败时，最危险的动作恰恰是「那就算了，直接给全文」。** 那会把一个存储问题升级成上下文问题，而且用户完全不知道发生了什么。宁可让这次工具调用失败、让模型重试或换工具，也不要静默地破坏上下文。

读取侧还有两道防护：

- 哈希必须是 64 位十六进制，否则直接返回空。这挡住 `../../` 这类路径穿越。
- 文件不存在时返回「未找到」，不抛内部错误。溢出文件可能被用户手动清理，这不是异常状态。

读取不做缓存，也不做分块。文件可能被手动删除，缓存会让「删了还能打开」的假象持续存在；不做分块，是因为全文读取的瓶颈在渲染而不是 IO，切块只增加接口复杂度。

## 七、幂等与附件去重

同一段内容重复溢出只落一份文件，这一点单测直接数目录里的文件数：连续两次溢出同一段文本，`spills/` 下只有一个文件。

附件走的是另一套已有机制：内容哈希去重、同内容秒传。这次没有重做，只是确认溢出文件与附件去重不会互相对撞——前者按内容哈希命名文本，后者按内容哈希复用已有附件记录，两者都以「内容相同即同一份」为前提，语义一致。

## 八、踩坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 用字节数判断 | 中文早早触发溢出，英文迟迟不触发 | 统一按字符长度（UTF-16 码元） |
| 预览切在代理对中间 | 末尾出现半个 emoji，显示成方块 | 接受；预览只用于判断，不做语义解析 |
| 重复写入 | 同一段日志每次调用都落一份 | 写入前检查文件是否存在 |
| 哈希直接拼路径 | 构造特殊哈希可越权读文件 | 只接受 64 位小写十六进制 |
| 把引用当成链接 | 以为模型能自己打开 `spill://` | 它只是标记，不提供读取工具 |
| 阈值边界含糊 | 恰好 100,000 字符是否溢出说不清 | 用 `<=` 不溢出，严格大于才溢出，测试覆盖 +1 |
| 溢出文件无回收 | 删除事件后文件仍占空间 | 记录为已知边界，清理不随事件保留策略走 |

最后一条要展开说：事件表的保留策略是按时间清事件，溢出文件不在这套策略里。它们按内容寻址、没有「属于哪个会话」的索引，清理需要单独的扫描与引用计数。这一轮没有做，属于明确的欠账，而不是「已经自动处理」。

## 九、验证

| 用例 | 断言 |
|---|---|
| 超阈值溢出 | 返回引用 `spill://<hash>`；返回文本显著短于原文且包含引用；按哈希读回的内容与原文完全一致 |
| 路径防护 | `../../etc/passwd` 与一个 64 位但不存在的哈希都读出 null |
| 未超阈值 | 原样返回，引用为 null，不落盘 |
| 幂等 | 连续两次溢出同一内容，目录里只有一个文件 |

接口侧也有一例：通过 `/api/spills/:hash` 能取回全文。端到端没有专门覆盖溢出，因为它需要一个真的产出几十万字符的工具；这一层由单测和接口测试兜住。

## 十、边界

- 不做分块读取：没有 range 接口，打开就是全文。
- 不做溢出文件压缩：文本本身可压缩，但读的时候要多一步解压，收益与复杂度不划算。
- 不做远程上传：全文不出机。
- 不做自动清理：欠账已记录，后续要么按引用计数，要么按时间扫描。
- 不改变工具契约：工具仍然返回字符串，溢出发生在执行器的返回处理层，工具作者不需要知道这件事。

这几条里，「不做自动清理」最容易被低估。溢出文件不会因为事件过期而消失，也不会因为会话删除而消失；它们只会随着用户手动清理应用数据目录而减少。这不是理想状态，但比「假装已经处理」诚实。
