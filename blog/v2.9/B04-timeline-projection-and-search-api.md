# 事件到时间线：一份投影，两个消费者

事件表里躺着的是一行行 JSON。直接渲染它，用户看到的是 `{"messageId":"...","role":"assistant"}`；直接导出它，拿到包的人还得自己写脚本解析。

中间缺的那一层，是把事件翻译成人话的投影。它必须只有一个：如果页面和导出各写一套，迟早出现「页面上写失败、导出里写异常」。

## 一、投影的契约

投影的输出是一个纯数据条目，字段固定：

| 字段 | 含义 | 来源 |
|---|---|---|
| `id` | 事件 id | 事件行 |
| `seq` | 同一范围内的序号 | 事件行，用于展示 `#12` 与增量游标 |
| `scope` / `scopeId` | 归属 | 事件行，供搜索结果跳转 |
| `type` | 原始事件类型 | 事件行，调试时仍要看得到 |
| `label` | 一句话标题 | 按类型映射 |
| `detail` | 一行详情 | 按类型取载荷字段，压缩空白，200 字截断 |
| `at` | 发生时间 | 事件行 |
| `payload` | 原始载荷 | 原样保留，供折叠展开 |

`payload` 保留是刻意的。投影只负责「让人一眼看懂」，不负责「替人判断」。觉得标题不对、想知道原始字段，展开就能看到，不必回头查库。

## 二、标题只有一张映射表

标题按事件类型分支，覆盖对话、任务、工作流、协作四类：

| 事件类型 | 标题 | 详情来源 |
|---|---|---|
| `message_started` | 用户消息开始 / 助手消息开始 | 消息内容 |
| `message_completed` | 助手回答完成 | 回答内容 |
| `message_error` | 回答失败：错误码 | 错误信息 |
| `message_stopped` | 回答已停止 | 停止时的内容 |
| `tool_trace` | 工具调用轨迹 | 轨迹载荷（压缩成一行） |
| `run_started` / `run_paused` / `run_resumed` | 运行开始 / 暂停 / 继续 | 载荷摘要 |
| `run_finished` | 运行结束：状态 | 运行状态 |
| `step_started` / `step_finished` | 步骤开始 / 结束 | 步骤种类、工具名、原因 |
| `node_started` / `node_finished` / `node_failed` | 节点开始 / 完成 / 失败 | 节点 id 或名称 |
| `agent_handoff` | 角色交接 | `来源角色 → 目标角色` |
| `done` / `error` / `budget_exceeded` | 协作完成 / 失败 / 预算耗尽 | 载荷摘要 |

规则很简单：**未知类型直接显示原始 type**。这样新增一种事件时，最坏情况是标题不好看，而不是页面崩掉或显示空白。投影永远不 throw。

详情统一走同一个压缩函数：字符串原样，对象序列化，空白折叠成单空格，超过 200 字截断加省略号。时间线是「扫一眼」的界面，不是阅读器；详情负责提示，展开负责求证。

## 三、界面：筛选、搜索、列表、折叠

时间线页只有一个页面，承载三件事：

- **范围筛选。** 下拉框可选全部、对话、任务、工作流、协作。选「全部」只影响搜索；不选具体范围与 id 时，时间线列表不加载。
- **检索。** 输入框回车触发查询，结果按事件维度列出：范围徽标、事件类型、时间、归属 id。点任意一条，页面切到该归属的时间线。
- **时间线。** 每条一行：`#seq` 徽标、标题、时间；下面一行灰色详情；再下面一个折叠区，展开是格式化后的原始载荷，最高 256 高度、内部滚动。

页面 URL 带 `scope` 与 `id`，从任务详情或报告页跳进来时直接落在对应时间线。搜索里点一条结果时，页面用替换历史记录的方式更新 URL，不新增历史条目——避免用户点五条结果后要按五次返回。

导出按钮在未选定范围时禁用。它直接把浏览器跳到导出接口，由服务端返回 ZIP，不在前端拼字节。

这三块不是并列的三个页面，而是同一个页面的三种状态：没有选定范围时只显示提示；提交搜索后切到结果态；选定范围后展示时间线。状态切换靠组件内条件渲染，不靠路由跳转，避免每点一次就整页重载。

## 四、三个接口

| 方法 | 路径 | 参数 | 默认与上限 |
|---|---|---|---|
| GET | `/api/events` | `scope`（必填枚举）、`scopeId`（必填）、`after`（seq，可选）、`limit` | limit 默认 500，最大 2000 |
| GET | `/api/search` | `q`（必填）、`scope`、`from`、`to`、`limit` | limit 默认 100，最大 500 |
| GET | `/api/export/session` | `scope`、`scopeId`、`redact` | `redact` 缺省为 1 |

三个接口都只读本地数据库，不依赖网络。`/api/events` 返回 `{ events, items }`：原始事件与投影条目一次给全，前端不用二次转换。

参数在入口处统一校验：枚举不合法、`scopeId` 为空、`limit` 越界，直接拒绝并返回 400，不把非法值带进查询。查询层只接受已通过校验的参数，非法输入不会变成 SQL 片段。

## 五、分页用游标，不用 offset

时间线是「一直往下长」的数据，offset 分页会踩两个坑：新事件插进来导致页码漂移；深翻页时数据库仍要跳过前面所有行。

所以读接口用游标：带上 `after`（上一批最后一条的 seq），查询条件是 `seq > after`，按 seq 升序取 `limit` 条。断线重连只补差量，重复与漏读都不会发生。

检索接口则是另一种形态：它没有游标，用时间窗（`from` / `to`）加 `limit` 截断。理由是搜索结果按时间倒序，用户关心的是「最近命中」，不是「把全部命中翻完」。需要更多时缩小时间窗，而不是翻页。

## 六、搜索是入口，时间线是目的地

这两件事的职责必须分清，否则会做出一个「搜索结果里也带时间线」的怪页面。

- 搜索回答「哪里提到过」：返回事件行，带 scope 与 scopeId，足够定位归属。
- 时间线回答「那次到底发生了什么」：按 seq 展示完整过程。

所以搜索结果不带片段高亮，也不内联展开载荷。它只做一件事：点一下，把你送到那条归属的时间线。少做一层，搜索结果与时间线的字段就不会出现两套解释。

## 七、为什么不给每条事件都做富文本

时间线第一版很容易滑向「每条事件一张卡片，带图标、带耗时、带重试按钮」。我们没有这么做：

- **未知事件会破相。** 四种范围、二十多种类型，卡片模板无法覆盖全部；模板一多，维护成本立刻超过收益。
- **排序与筛选会被卡片吃掉。** 卡片占的垂直空间越大，同屏能扫的事件越少，而复盘最需要的是「一眼看到顺序」。
- **原始载荷必须可达。** 任何富文本都会丢字段；折叠区是唯一不会丢信息的设计。

所以列表保持克制：一行标题、一行详情、一个折叠。需要细节时展开，不需要时它不占地方。

克制还有一个副作用：页面看起来很朴素，没有一眼就能截图展示的东西。但复盘页的使用场景本来就是「查问题」，不是「展示成果」。朴素换来的是加载快、扫视快、不会因为某个事件类型没覆盖而破相。

## 八、边界

- 不提供编辑与删除：时间线是只读视图，事件不可改写。
- 不做实时推送：页面按需拉取，不做 SSE；增量靠 `after` 游标。
- 不做跨范围合并：一次只看一个 `scope + scopeId`，跨范围用搜索。
- 不做相关度排序：搜索按时间倒序，精确性交给范围与时间窗。
