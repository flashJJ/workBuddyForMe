# 导出一个 ZIP：manifest、事件 JSONL 与默认脱敏

有了事件日志，下一步是「带得走」。用户要把一次运行发给同事、贴进工单、存档备查，截图和复制粘贴都不合格：前者不可检索，后者会丢结构。

导出因此不是附加功能，而是复盘的出口。它必须满足三条：结构稳定、能人工核对、默认不泄露。

## 一、包里放什么

一个 ZIP，按范围决定内容。四种范围的条目不同，但前两件永远在：

| 范围 | 条目 | 说明 |
|---|---|---|
| 全部 | `manifest.json` | 账本：条目、条数、时间、是否脱敏 |
| 全部 | `events.jsonl` | 事件原文，一行一条 |
| 对话 | `messages.json` | 消息投影，含角色、内容、状态、引用 |
| 任务 | `run.json`、`steps.json` | 运行行与步骤列表 |
| 协作 | `run.json`、`handoffs.json` | 运行行与角色交接 |
| 工作流 | `run.json`、`nodes.json` | 运行行与节点执行 |

业务投影不是冗余。事件表回答「按序发生了什么」，业务表回答「这条消息现在是什么状态」「这一步最终归到哪个工具」。人工核对时，两份材料放在一起才能发现「事件说完成、消息还是流式中」这类不一致。

反过来，只给业务投影也不行：业务投影丢掉了事件之间的间隔与顺序，看不出「先报错再重试」这种关键过程。

包里不含附件二进制，也不含系统凭据。导出只读本地数据库与文件元数据。

## 二、manifest 是账本

清单在包里的作用，等价于发票的明细页。字段固定：

- `version` 与 `schemaVersion`：包格式与事件载荷版本，两者独立；
- `generatedAt`：生成时间，ISO 格式；
- `scope`、`scopeId`：这份包属于谁；
- `redacted`：布尔值，明确告诉接收方内容是否脱敏；
- `entries`：每个条目的名字与字节数；
- `counts`：事件、消息、步骤、节点、交接的条数。

有一个细节：`manifest.json` 自己也列在 `entries` 里，字节数写 0。原因很简单——清单要先写进包，才能算出自己的字节数；写真实值需要二次计算并回填，收益为零。接收方看到 0 就知道「这是自引用占位」，不会被误导成空文件。

测试直接断言「清单条目名排序后等于包里实际文件名排序」。这条断言比任何文档都可靠：以后新增一个条目忘了记账，测试立刻红。

## 三、events.jsonl 为什么不是 JSON 数组

事件写成 JSON Lines，不是一个大数组。三个理由：

1. **可增量处理。** 一行一条，`head`、`tail`、逐行解析都不需要先读完整文件；数组必须整体解析才能取第一条。
2. **可 diff。** 两次导出做文本比较时，JSONL 的差异是行级的；数组的差异常常因为一个逗号位置而整段变红。
3. **可追加。** 将来如果要支持「在已有包上补新事件」，JSONL 追加一行即可，数组要重写整个文件。

细节也处理了：事件按 seq 升序输出（底层跨范围查询是时间倒序，导出前显式重排）；文件以换行结尾，空集合时输出空文件而不是 `[]`。这样 `wc -l` 得到的数字就是事件条数，和清单里的 `counts.events` 对得上。

## 四、默认脱敏的三层

脱敏不是正则一把梭。实现分三层，各管一件事：

| 层 | 作用 | 例子 |
|---|---|---|
| 键名剔除 | 递归遍历对象，命中敏感键名整条丢弃 | `apiKey`、`authorization`、`secret`、`password`、`accessToken` |
| 文本掩码 | 字符串里形似令牌的片段替换为 `[REDACTED]` | `sk-...`、`Bearer ...`、`ghp_...`、`xoxb-...` |
| 参数占位 | 工具参数原文整体替换为占位 | `argsJson` / `args_json` → `[REDACTED]` |

递归有深度上限：超过 6 层直接替换为 `[DEPTH_LIMIT]`。这不是为了防攻击，而是防止异常深的对象把导出拖成栈溢出；事件载荷理论上可以嵌套任意结构，导出不能假设它规整。

默认导出走全部三层。这也是 `redact` 参数缺省为 1 的原因：**默认安全，显式才放宽。**

## 五、redact=0 不等于裸奔

关掉脱敏常被误解成「原样导出」。实际语义是：

- 保留字段名与结构，不再整条剔除敏感键；
- 仍然掩码形似令牌的值；
- 仍然保留工具参数的原文。

这样做的理由是分层：字段名本身不是秘密，值才是。用户想看完整的工具调用参数来排查问题，那就给他；但一段明显长得像密钥的字符串，不管出现在哪个字段里，都不该原样进包。

系统凭据在任何模式下都不进导出。这一条不提供开关——它不是用户的偏好问题。

## 六、为什么用 fflate，而不是引入 archiver

选型理由按优先级排：

1. **它已经是 core 包的依赖。** 项目里解包 Office 文档、读写能力包、打包 mod 都要 ZIP；导出复用的是同一个库，不新增一棵依赖树。
2. **纯 JS，同步 API。** `zipSync` 接受「文件名 → 字节」的映射，一次调用出包。没有原生编译，不需要在 Windows 上折腾构建工具链。
3. **体量小。** 引入 `archiver` 这类流式库会带来一串传递依赖，而导出是低频操作，不值得为它扩容依赖。
4. **测试友好。** 同一个库的 `unzipSync` 可以反过来解包，单测里直接断言条目与内容，不需要落临时文件。

代价是同步压缩会阻塞当前调用。导出是用户主动触发的一次性动作，阻塞几百毫秒到几秒可以接受；我们没有为了「不阻塞」去引入流式管线。

## 七、内存与体积边界

导出全部在内存里完成：事件、业务投影、清单先变成字节，再一次性压缩成 ZIP，最后作为响应体返回。峰值内存大致是「原始字节 + 压缩结果」。

为控制峰值，做了三件事：

- **事件与消息各有条数上限**，避免一次导出把整库读进来；
- **不包含附件二进制**，否则一个包可能是几百 MB；
- **响应不缓存**，`no-store`，避免中间层留存副本。

要诚实说明的边界：

- 单条事件载荷有截断上限，但条数上限乘以载荷上限，理论上仍可能拼出一个很大的包；
- 同步压缩期间会同时持有原始数据与压缩结果，历史特别大的会话导出时内存会明显上升；
- 不做分卷、不做流式下载。需要更激进的边界时，正确的做法是缩小时间窗分批导出，而不是把单次导出做得更复杂。

## 八、验证

导出这一块的测试集中在契约，而不是界面：

| 用例 | 断言 |
|---|---|
| 清单一致性 | `manifest.entries` 的名字集合等于 ZIP 实际条目集合；`counts` 与内容条数一致 |
| 默认脱敏 | 消息与事件里都不出现 `sk-` 开头的密钥；敏感键名整条消失；出现 `[REDACTED]` |
| 关闭脱敏 | 工具参数字段保留；令牌仍被掩码；`manifest.redacted` 为 false |

浏览器端到端也走了一遍真实链路：发起一次对话、检索、查看时间线、点击导出。它验证的不是解压逻辑，而是「按钮 → 接口 → ZIP」这条路在真实页面里是通的。

## 九、边界

- 不做增量导出：每次都是当前范围的全量快照。
- 不做导入：ZIP 是只读产物，不承担恢复职责。
- 不做加密包：本地文件系统是边界，包里没有额外口令层。
- 不导出附件内容：只导出引用与元数据，二进制仍留在应用数据目录。
