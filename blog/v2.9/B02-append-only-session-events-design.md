# 只追加的事件表：字段、序号与写入点

决定把事件日志做成一张 SQLite 表之后，最先要回答的不是「怎么查」，而是「怎么保证它永远只往前走」。

因为这张表一旦允许改写，它就不再是时间线真源：今天补一条、明天改一条，重建出来的「当时发生了什么」随时会变。复盘的可信度，全靠「写过的东西不会再变」这一条撑着。

## 一、为什么不直接读业务表拼时间线

最省事的做法是查询时把消息、步骤、节点、交接几张表按时间排序合并。我们试过在心里过一遍这条路，三个问题立刻出现：

1. **排序键不可靠。** 业务表的时间戳是「记录创建时间」，不是「事件发生时间」。流式回答的开始与完成、步骤的入队与执行，常常落在同一秒甚至同一毫秒，排序结果不稳定。
2. **形状不可统一。** 四张表的字段各自为业务服务，拼出统一条目要在查询层写四套映射，且每加一种运行类型就要改一次。
3. **无法增量。** 页面想要「从第 51 条开始继续拿」，业务表没有单调序号，只能靠时间戳猜，重复与漏读都会发生。

所以顺序反过来：先把事件按序写下来，查询再读事件；业务表退回它擅长的位置。

## 二、表结构

表是这次迁移里新增的，纯加法，不改任何旧表：

```sql
CREATE TABLE session_events (
  id             TEXT PRIMARY KEY,
  scope          TEXT NOT NULL,      -- chat / task / flow / agent
  scope_id       TEXT NOT NULL,      -- 会话 id 或运行 id
  seq            INTEGER NOT NULL,   -- 同一 scope+scope_id 内从 1 起单调递增
  type           TEXT NOT NULL,
  payload_json   TEXT NOT NULL,
  schema_version INTEGER NOT NULL DEFAULT 1,
  created_at     TEXT NOT NULL
);

CREATE UNIQUE INDEX idx_session_events_seq
  ON session_events(scope, scope_id, seq);
CREATE INDEX idx_session_events_created
  ON session_events(created_at);
```

| 列 | 用途 | 注意点 |
|---|---|---|
| `scope` | 区分四种运行形态 | 固定枚举，不自由填 |
| `scope_id` | 会话 id 或运行 id | 与业务表主键对齐，便于下钻 |
| `seq` | 排序与增量游标 | 唯一索引是真正的护栏 |
| `type` | 事件类型 | 决定投影文案 |
| `payload_json` | 结构化载荷 | 超限截断并打标记 |
| `schema_version` | 载荷版本 | 只前向，不回头改历史 |
| `created_at` | 展示时间 | 允许由调用方传入，便于导入与测试 |

唯一索引不只是「防重复」，它还是并发下的最后一道保险：如果序号发重了，插入直接失败，不会出现两条 seq 相同、顺序无法判定的事件。

## 三、三条纪律

- **只插入。** 写入路径上没有任何 UPDATE 或 DELETE。清理是另一个独立动作，按时间批量删，不混进写入。
- **版本只前向。** `schema_version` 固定从 1 开始；将来载荷形状变化，新事件带新版本，旧事件原样保留。读取方按版本分支解析，而不是回写迁移历史。
- **载荷有上限。** 单条载荷序列化后超过 200 KB 就截断，落成 `{ truncated: true, preview: ... }`。宁可留一段带标记的残片，也不让一条异常载荷把写入拖死。

截断标记很关键。它让读取方知道「这里本来还有更多」，而不是把残片当成完整事实。

## 四、seq 在事务里发

序号不能由客户端给，也不能靠时间戳推。做法是把「取当前最大值」和「插入」放进同一个事务：

```text
append(scope, scopeId, type, payload):
  id   = newId()
  text = JSON.stringify(payload)
  tx:
    next = SELECT COALESCE(MAX(seq), 0) + 1
             FROM session_events
            WHERE scope = ? AND scope_id = ?
    INSERT INTO session_events(..., seq = next, ...)
    INSERT INTO session_events_fts(...)
  return 该行
```

几个细节：

- **读放大可接受。** 每次追加多一次 `MAX(seq)`，走的是 `(scope, scope_id, seq)` 唯一索引，代价很小。
- **不承诺无空洞。** 事务回滚时序号自然不会被占用，但也没有「补号」逻辑。时间线只关心相对顺序，空洞无害。
- **单进程写。** 写入集中在同一个服务进程内，SQLite 的事务把两步串起来；这不是为多进程并发写设计的。
- **增量游标。** 读取接口带 `after` 参数，查询条件是 `seq > after`，按 seq 升序返回。页面断线重连时只补差量，不重拉全量。

## 五、写入点：一个服务加三个回调

事件不是靠一个全局中间件拦出来的，而是挂在已有的业务动作上。对话走会话服务，三类运行走各自的容器回调。

| 来源 | 触发动作 | 事件类型 |
|---|---|---|
| 对话 | 追加消息 | `message_started`（带 messageId、role、content、status、引用） |
| 对话 | 回答完成 | `message_completed`（内容、用量、引用） |
| 对话 | 回答失败 / 停止 | `message_error`（code、message）、`message_stopped`（内容） |
| 对话 | 工具轨迹回写 | `tool_trace`（轨迹数组） |
| 任务 | 容器 `onEvent` | 取载荷里的 type，缺省用事件名 |
| 工作流 | 容器 `onEvent` | 直接使用流程事件信封的类型 |
| 协作 | 容器 `onEvent` | 使用协作事件的事件名 |

对话侧有个小设计：完成、失败、停止、轨迹回写拿到的都是消息 id，先按 id 反查会话，再写 `chat` 事件。这样写入点不必层层透传会话 id。

三类运行侧**没有新建第二套事件总线**。任务、工作流、协作的容器本来就有 `onEvent` 回调，用来把工作信号喂给桌宠与状态页；事件日志就挂在同一个回调里，先喂信号，再落库。一个回调两个消费者，避免同一件事在两处触发、字段渐渐长歪。

## 六、写入是 best-effort

日志服务对外只暴露一个 `record`，内部包了 try/catch：失败时打一条警告，返回 null，**不向上抛**。

理由很直接：事件日志是「事后复盘」的基础设施，不该成为「当下对话」的单点故障。磁盘满、数据库锁冲突这类问题，让日志静默降级，比让用户的一次回答直接失败要好。

代价是可能出现「业务成功了、事件缺一条」。这是刻意接受的：真源优先保证可用，完整性靠监控与后续校验补，而不是靠强一致把主链路拖下水。

对话服务还有一个可选注入点：事件服务未注入时不写。测试与轻量场景可以完全省略事件日志，不必为了跑一个用例去搭一套依赖。

## 七、索引与事件同事务

全文索引不是触发器，也不是后台任务，而是在 `append` 的同一个事务里顺手插一行：

- 事务成功，事件与索引都在；
- 事务回滚，两边一起消失；
- 不存在「事件有了、索引还没建」的中间态，也就不需要补偿脚本。

索引文本是 `type + payload` 的归一化串，超过 200,000 字符先截断再归一化。索引列用 `event_id` 回连事件表，`scope` 与 `scope_id` 冗余存一份但不分词，供过滤时少一次 join 之外的判断。

## 八、代价

- **写入放大。** 一次对话会产生开始、完成、轨迹多条事件；一次任务可能几十条。这是复盘的必然成本。
- **数据增长。** 事件与业务表存了部分重叠的信息。默认保留 180 天，清理能力只给接口，不自动跑。
- **顺序语义的边界。** seq 只在单个 `scope + scope_id` 内单调，跨会话不能拿来比大小；跨范围排序一律用 `created_at`。
- **payload 不是无限真相。** 截断标记存在，说明某些事件只保留了残片。需要完整原文的东西（比如大工具输出）走内容寻址文件，而不是硬塞进事件。
