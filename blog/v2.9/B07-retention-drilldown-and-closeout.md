# 复盘入口、保留策略与收尾：这次没做什么

功能做完之后还有两个问题：用户能不能找到它，以及数据会不会无限长大。

这次的事件日志、时间线、检索、导出，技术上都能跑通；但如果入口藏在设置页第三层，用户仍然会觉得「没这个功能」。同样，只写不删的追加表，迟早会把本地库撑成负担。

所以收尾阶段做的不是新功能，而是把入口接进已有页面，把保留策略的边界写清楚，再把「没做的事」一条条列出来。

## 一、入口比页面重要

最先做的直觉方案是做一个独立的「复盘中心」，从导航栏进去。想了想否掉了：用户不会为了复盘专门去一个地方，他是在**看到结果觉得可疑的那一刻**才想复盘。

这个判断有个推论：入口要出现在「结果」旁边，而不是「工具」旁边。任务详情、运行报告都是结果页；设置页、导航栏都是工具入口。功能放在工具入口，等于要求用户先想起它，再去找它。

所以入口挂在用户已经在看的两个位置：

| 入口 | 位置 | 跳转 | 形态 |
|---|---|---|---|
| 打开时间线 | 任务详情展开后的操作行 | `/timeline?scope=task&id=<任务 id>` | 一行文字链接 |
| 复盘时间线 | 运行报告页顶部工具条 | `/timeline`（不带范围） | 一个描边按钮 |

第一个入口带全参数，点开直接是那次任务的时间线，不需要再选范围。第二个入口只落到时间线首页，因为报告页本身是跨运行的聚合视图，用户在那里关注的是「这一批运行」，进来之后自己选范围更合理。

两个入口都不做弹窗、不做侧栏。时间线是一个需要纵向阅读的页面，塞进抽屉里会失去「顺序感」。

## 二、为什么报告页只给入口，不做单运行页

理想形态是「报告里的每一行都能点进去看那次运行的时间线」。这次没有做，原因不是工期，而是**数据形状不支持**。

运行报告是一张链路聚合表：它按时间窗把任务、工作流、协作的统计合在一起，行是「链路 × 时间段的汇总」，不是「某一次运行」。表里根本没有一个稳定的单次运行标识可供下钻。

这不是字段漏了，是聚合表的定义如此：聚合的结果本来就不再指向个体。行里有条数、成功率、耗时分位，唯独没有能唯一定位一次运行的 id。

硬要做，只有两条路：一是改报告的数据源，让每行都带 runId，这等于重做报告页；二是在报告行里反查事件，猜一个「最相近的运行」，那是在制造不可信的下钻。两条都不划算。

所以这次的选择是：**先给入口，让用户从报告跳到时间线，用范围与时间自己定位。** 单次运行的 Flow/协作下钻，留到下一阶段随报告结构调整一起评估。

这是一个典型的「先接通，再精确」的取舍。入口的价值是让功能被看见；精确下钻的价值是少点两次，优先级明显更低。

还有一层现实原因：报告页的时间窗是跨链路的，用户从「过去 24 小时」的报告里点进某一行，未必对应到一次具体运行，可能是一批运行的合计。带错参数的下钻，比不带参数更糟。

## 三、保留策略：能力给了，开关没装

追加式日志的默认保留期是 180 天。清理能力的实现有三点值得写下来：

- **只提供接口与服务。** 服务层提供「清理某个天数之前的事件」，返回删除条数；没有挂定时任务，也没有在启动时自动跑。什么时候清，由调用方决定。
- **批量删除。** 每次最多删 5000 条，避免一次大事务把数据库锁住；需要清更多时重复调用。
- **先删索引行，再删事件行。** 全文索引不是外部内容表，删事件不会自动带走索引；顺序反了就会留下搜得到、点不开的幽灵结果。

为什么不做成「启动即自动清理」？因为删除是不可逆的，而「180 天」是一个产品假设，不是用户的明确选择。在设置页给出开关之前，自动删数据是不礼貌的。当前状态是：**能力就绪，入口未接。** 这是一条明确的欠账，不是遗漏。

## 四、为什么默认是 180 天

180 天不是法规要求，也不是行业标准，而是一个产品判断：它要覆盖「用户还会想翻」的时间跨度，又不能让本地库无限增长。

按使用强度粗估：每天几十条事件的活跃用户，半年大约是万级到十万级事件行。180 天刚好是半年的可回溯窗口，覆盖「上个月那个报错」这类真实诉求；再长收益递减，再短用户会觉得「刚想复盘就没了」。

这个数字只写在默认值里，没有出现在界面上。一个用户看不见、也改不了的默认值，不应该被当成承诺。等设置页接入，它才真正变成用户的选择。

## 五、这次没做的事

| 项 | 状态 | 原因 |
|---|---|---|
| 一键诊断包 | 未做 | 失败运行的事件、配置、日志打包涉及日志脱敏与体积控制，单独评估 |
| 压缩预算可视化面板 | 未做 | 既有摘要与预算记账继续生效，但没有把「预算用了多少」画出来 |
| 单次运行下钻页 | 未做 | 报告是聚合表，缺少稳定的单次运行行 |
| 溢出文件清理 | 未做 | 内容寻址文件不随事件保留策略删除，需要单独的引用计数或扫描 |
| 云同步 / 跨设备检索 | 不做 | 数据不出机是红线 |
| 永久保存所有原文 | 不做 | 口径是可重建、可审计，不是全量归档 |

把「未做」和「不做」分开写，是有意的：前者是欠账，后者是边界。混在一起，下次评审就分不清哪些该补、哪些不该提。

另外三项欠账有一个共同触发条件：都得先有一个明确的入口。没有入口的能力，做了也没人用；有入口但没有数据形状支撑，做了也不可信。所以它们不是排期问题，而是依赖顺序问题。

## 六、验证

| 项 | 结果 |
|---|---|
| 类型检查 | 14/14 包通过 |
| 静态检查 | 0 error |
| 行数门禁 | 单文件 300 行上限通过 |
| shared / database / core / web 单测 | 321 / 234 / 1159 / 592 例全绿 |
| 浏览器端到端 | 2 例通过：真实对话 → 检索 → 事件 → 导出 → 时间线页；报告页入口 |

端到端这条用例的价值不在覆盖率，而在于它把六个环节串成了一条真实链路：对话产生事件、检索能命中、时间线能渲染、导出能下载、页面能跳转。任何一环断了，这条用例都会红。它证明的是「接线正确」，不是「每个函数正确」——后者由单测负责。

## 七、五条方法论

这五条里，前三条是结构性的，后两条是工程纪律。结构错了，纪律只能补救表面；纪律缺了，结构也守不住。

1. **先定真源方向，再动表。** 事件是时间线真源、业务表是查询投影，这个方向必须在写第一行代码前定死。方向不定，双写就会变成两套互相矛盾的真相。
2. **投影写成纯函数，文案只留一处。** 事件到人话的映射不碰数据库、不碰界面，输入事件输出条目。页面与导出共用同一份口径，避免出现两套描述。
3. **把分词差异关在边界内。** 中文检索的复杂度不应该泄漏到业务代码；写入与查询调用同一个归一化函数，上层只知道「能搜到两字词」。
4. **脱敏默认开，关掉也不裸奔。** 默认剔除敏感字段；显式放宽时仍然掩码令牌。分层设计让「方便排查」和「不泄露」不必二选一。
5. **门禁要能自证。** 单测锁契约边界（截断、幂等、清单一致），端到端锁接线。只有数字没有断言，等于没有门禁。

这五条不是这次发明的，是这次被验证过的。它们都指向同一个判断：**可复盘不是「多存一份数据」，而是让数据在写入、读取、导出三条路上都保持同一套语义。**

## 八、收尾

复盘能力最终落在三句话上：过程按序可重建，内容按词可检索，整包可带走。入口让它被找到，保留策略让它不失控，边界清单让它不假装万能。

剩下的欠账已经写在这里：诊断包、预算可视化、单次运行下钻、溢出文件回收。它们都有明确的触发条件，不需要靠记忆维护。
