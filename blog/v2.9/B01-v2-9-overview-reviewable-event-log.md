# 让每一次回答都能被复盘：事件日志、检索导出与上下文治理

用户给过一句很具体的抱怨：跑完了只剩一条结果，中间它看了什么、调了什么工具、为什么失败，全没了。

这不是缺一个「日志页面」。消息表里有内容，任务表里有步骤，协作表里有交接，运行报告里有结果与耗时——每条信息都在，只是它们各自躺在自己的表里，没有任何一条时间线按发生顺序把它们串起来。想复盘一次运行，只能靠人脑把几张表拼起来；想搜「上次那个报错的回答」，只能一页页翻会话。

所以这一轮只做一件事：**把「发生过什么」变成可重建、可检索、可带走的数据。**

## 一、痛点：结果留下了，过程没留下

| 现象 | 真实原因 |
|---|---|
| 跑完只看到最终回答 | 过程只活在流式响应的内存里，结束即散 |
| 想查某次失败为什么失败 | 错误码写进了消息状态，但当时的工具轨迹与步骤不在一条时间线上 |
| 想找两周前说过的一句话 | 会话列表只能按时间翻，没有全文检索 |
| 想把一次运行发给别人看 | 没有导出，只能截图 |

四件事的共性不是「没存」，而是**没有一条统一的、按序排列的事实流**。业务表各自为查询而设计：消息表按会话取、步骤表按运行取、节点表按 run 取。它们都缺一个「这次到底依次发生了什么」的视角。

## 二、三件事

| 要做的事 | 解决什么 | 落点 |
|---|---|---|
| 追加式事件日志 | 过程可重建 | SQLite 追加表，按 scope + scopeId + seq 排序 |
| 时间线、检索、导出 | 过程可查、可带走 | 统一投影 + FTS5 检索 + ZIP 导出 |
| 上下文溢出治理 | 过程别被一次大输出撑爆 | 内容寻址溢出文件 + 引用 |

三件事是一条链：事件先落库，投影把事件变成人看得懂的行，检索与导出都消费同一份事件。少了第一件，后两件就是给业务表做二次加工，越做越分叉。

## 三、事件是时间线真源，业务表是查询投影

两张表同时存在，必须先把方向定死，否则双写迟早打架。这次的口径是：

- **事件日志是时间线的唯一真源。** 按 seq 升序读出来，就是这次发生过什么。
- **业务表继续做查询投影。** 消息列表、任务步骤、节点执行、交接记录仍按各自的索引服务页面。
- 两边不一致时以事件为准；业务表用于快速查询，不用于重建。

为什么不让业务表兼任真源？因为它们为「列表」优化：分页、筛选、按外键取。把时间线压在它们身上，等于要求每张业务表额外维护一套顺序语义，而顺序恰恰是它们最不擅长的东西。

反过来，事件表也不适合替代业务表：它只有结构化载荷，没有业务字段的索引，拿它做列表查询会很慢。两张表各司其职，是这一轮最重要的结构决定。

判断标准可以压缩成一句：**这张数据会不会被用来「事后重建」？** 会，就进事件表；只用于「此刻展示」或「按条件列表」，就留在业务表。按这条标准过一遍，归属几乎没有争议。

## 四、时间线是投影，不是日志原文

事件落库后是一段 JSON，直接给人看没有意义。中间加一层纯函数投影，把事件折叠成统一条目：序号、类型、一句话标题、一行详情、发生时间。

标题按事件类型映射成人话，例如「用户消息开始」「助手回答完成」「节点失败」「角色交接」。详情取载荷里最有信息量的字段，超过 200 字截断并加省略号。原始载荷不丢，折叠在条目下面，需要时才展开。

这一层的价值在于**文案只有一份**。页面渲染用它；导出给的是事件原文与业务投影，不在导出里另写一套中文描述。少一套文案，就少一处「页面说成功、导出说失败」的可能。

## 五、检索与导出：让记录带得走

检索不是可选项。不能搜的日志，等于只读的日志。这一轮把全文索引和事件表放在同一个事务里写：事件插入成功，索引一定也在；不需要后台补偿任务，也不会出现「搜得到但点不开」。

中文检索单独处理了一件事：SQLite 的 FTS5 默认分词器把连续汉字当成一个 token，两字词查不到。解法是在写入与查询两侧做同一套归一化：中文逐字拆成单字 token，拉丁字母数字串保留成整词。

导出做成一个 ZIP：事件原文、业务投影、一份清单。默认脱敏——密钥字段直接剔除，疑似令牌掩码，工具参数原文换成占位。清单记条目名、条数与是否脱敏，拿到包的人可以先核对清单再读内容。

## 六、上下文治理：别让一次工具输出挤爆上下文

复盘的前提是那次运行真的跑完了。一次工具输出几十万字符，直接回灌模型会挤占上下文，落进消息表又会把表撑大。

所以给工具输出加了一道闸：超过 100,000 字符，全文写进内容寻址文件，模型只看到前 2,000 字符加一个引用。同一段内容重复出现只落一份文件；附件复用早先已有的内容哈希去重，不重复落盘。

阈值刻意定得比常规压缩预算高。两者如果挤在同一个量级，普通的长输出会被溢出抢走，压缩永远见不到它们，等于两个机制互相拆台。

换来的代价是文件系统里多了一类需要管理的产物。它不是缓存，删了会影响复盘完整性；也不是数据库行，不跟着保留策略走。这一点在收尾时单独记了一笔。

## 八、为什么不用每会话一个 JSONL 文件

另一种常见做法是每个会话写一个 JSONL 文件，按行追加。它更接近「日志」的直觉，也便于直接用文本工具查看。我们没有选它，理由有三条：

- 检索要跨文件扫，无法用索引；
- 文件与数据库之间要维护两套一致性，删会话时容易漏文件；
- 保留策略按时间清理，散落的文件比一张表难管。

SQLite 追加表把「顺序、索引、清理」三件事收进一个事务边界，代价是数据库会变大。对一个本地优先的私人应用来说，这个代价比「一堆没人管的文件」更低。

## 九、保留策略与边界

- **默认保留 180 天。** 清理只提供接口与服务能力，没有挂定时任务；什么时候清、清多少，由调用方决定。
- **只追加，不在写入路径删除。** 写入永远是插入；清理是独立动作，按时间批量删除，先删索引行再删事件行。
- **不记密钥、不记系统凭据、不记附件二进制。** 本地优先不等于可以无限记录。
- **不做云同步、跨设备检索。** 数据不出机是红线。
- **不追求永久保存所有原文。** 口径是可重建、可审计，不是全量归档。

## 十、这一轮回答的问题

复盘不是加一张日志表就结束。它要求三件事同时成立：事实按序可重建、内容按词可检索、整包可带走；再叠一条底线——这个过程不能把上下文和数据库撑坏。
