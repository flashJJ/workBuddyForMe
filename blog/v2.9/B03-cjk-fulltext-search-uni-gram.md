# FTS5 不认中文：写入侧 uni-gram 归一化怎么做

给会话加全文检索，第一版实现只用了三行：建一张 FTS5 虚拟表，写入时把文本塞进去，查询时拼一个 MATCH。英文一切正常，中文全军覆没——搜「混合」零结果，搜「知识」零结果，搜整句反而能中。

这不是配置漏了，是分词器的语义与中文不匹配。

## 一、现象：两字词一条都搜不到

SQLite 的 FTS5 自带 `unicode61` 分词器。它的规则是「按空白与标点切分，连续的字母数字算一个词」。对中文来说，一句话里没有空格，于是**一整段连续汉字被当成一个 token**。

| 索引里的原文 | 实际 token | 查询「混合」 | 查询「知识编译层混合检索」 |
|---|---|---|---|
| 知识编译层混合检索 | 整段一个 token | 0 条 | 1 条 |
| 混合检索重排 | 整段一个 token | 0 条 | 0 条 |

第二行值得注意：搜整句能中，是因为整句恰好等于索引里那一个 token。换句话说，只有「一字不差地记住原文」才搜得到，这跟没有检索差不多。

也考虑过 FTS5 的 `trigram` 分词器。它按三字符滑窗建索引，确实能处理中文，但查询串必须至少 3 个字符：**「混合」「知识」这类两字词直接被拒**。中文里两字词是最常见的查询单位，这条限制等于把最常用的场景砍掉。

## 二、方案：写入与查询用同一套归一化

既然两个内置分词器都不合用，就绕开分词器本身：**在进 FTS 之前，自己把文本切成它认识的形状；查询串走同一个函数。**

规则只有四条：

| 输入片段 | 归一化结果 | 说明 |
|---|---|---|
| `混合` | `混 合` | 汉字逐字成 token |
| `qwen2` | `qwen2` | 连续字母数字保留整词并小写 |
| `qwen2.5:7b` | `qwen2 5 7b` | 冒号、点号作分隔符 |
| `约228MB` | `约 228mb` | 中文与拉丁混排时各自成段 |

标点、空白、符号全部当分隔符丢弃。归一化后的字符串以空格连接，再交给 `unicode61`——此时它看到的已经是一串「正常单词」，不会再犯「整段中文当一个 token」的错。

关键在于这个函数是**纯函数**，不碰数据库、不依赖环境。写入侧、查询侧、测试侧调用的是同一份实现，所以「索引怎么切」与「查询怎么切」不可能漂移。

## 三、写入侧：索引文本从哪来

索引内容不是原始载荷，而是「事件类型 + 载荷 JSON」的归一化串：

```text
ftsContent(type, payloadJson):
  raw = type + " " + payloadJson
  return normalizeForFtsIndex(raw.slice(0, 200_000))
```

三点说明：

- **带上类型。** 搜「失败」既能命中错误事件，也能命中任务失败的步骤事件；类型进索引让「按事件种类找」成为可能。
- **先截断再归一化。** 单条索引文本上限 200,000 字符，避免一段异常大的载荷把索引写入拖慢。截断发生在归一化之前，省掉一次无用的分词。
- **索引与事件同事务。** 写入事件与写入索引在同一个事务里完成：要么都在，要么都不在，不需要后台补索引，也不会出现「搜得到、点不开」。

索引表除了 `content`，还冗余存了事件 id、scope、scopeId 三列，且都不参与分词。它们的作用是过滤与回连：搜到之后按 scope 缩范围，或直接拿事件 id 回查原文。

## 四、查询侧：拼一个「只含被引号包住的词」的表达式

查询同样先归一化，再把每个 token 用双引号包住，用 OR 连接：

```text
buildFtsQuery("混合")      → "混" OR "合"
buildFtsQuery("qwen2.5")   → "qwen2" OR "5"
buildFtsQuery("qwen*")     → "qwen"
buildFtsQuery("：。，！")   → null   （调用方跳过检索）
```

四个行为都是刻意的：

- **全引号包裹是安全边界。** 用户输入里的 `AND`、`OR`、`NEAR`、`*` 不会被当成 FTS 操作符执行，只会被当成普通词或被丢弃。查询串永远不会因为一个星号变成语法错误。
- **空 token 返回空。** 纯标点或纯空白归一化后没有 token，直接返回 null，调用方跳过 FTS 通道，返回空结果而不是抛异常。
- **OR 连接是召回优先的选择。** 中文两字词被拆成两个 token 后，用 AND 会要求两个单字都出现在同一条事件里；用 OR 则任一命中即可。前者更准，后者更容易搜到东西。
- **大小写统一。** 写入与查询都小写，`QWEN` 与 `qwen` 不会有差异。

## 五、实测

这不是「理论上应该行」。落地的验证有三处：

| 验证 | 断言 |
|---|---|
| 分词纯函数单测 | `混合` → `混`、`合` 两个 token；`知识编译层` 逐字成 token；纯标点返回空 |
| 索引命中单测 | 写入「知识编译层混合检索」后，用两字词查询能经 MATCH 命中 |
| 事件检索单测 | 对话写入「暗号是青鸟」与回答后，搜「青鸟」返回 2 条事件 |

第三条同时验证了另一件事：检索结果与时间线同源。搜出来的事件按 id 回查，与时间线接口读的是同一张表、同一批行，不存在「搜到的是索引副本、点开是另一份数据」。

再补一个边界：索引命中的是「事件」，不是「会话」。一个对话里命中多条事件，就逐条列出，不折叠成「这个会话命中」。复盘要的是具体那一条，而不是会话级的相关度。

## 六、取舍：召回与索引体积

把中文拆成单字，代价是索引膨胀。一行 40 字的句子，索引里变成 40 个 token；中文事件的 postings 列表会明显变长，索引体积接近原文体积再加一部分。

我们的判断是：**在本地优先、数据量以万条计的私人应用里，索引体积换可用性是划算的。** 用户不会因为磁盘多了几十 MB 而抱怨，但会因为「搜不到自己两周前说的话」而认定这个功能是假的。

另外两个取舍也要写明：

- **不追求相关度排名。** 结果按 `created_at` 倒序、同秒按 seq 倒序，不接相关度打分。复盘场景的默认意图是「最近发生的」，时间序比相关度更符合直觉；精确找某一条，靠 scope 与时间窗收窄。
- **OR 语义会带来噪声。** 查询词越多，命中的事件越杂。这是召回优先的必然结果，用过滤条件补偿，而不是把查询改成 AND 去牺牲召回。

还有一个不写在代码里的取舍：**索引只覆盖事件表，不覆盖知识库分块。** 两套 FTS 表的分词函数相同，但各自独立写入与清理。合并成一张表，范围过滤要多一层判断，知识库重建时也会牵连事件索引。

## 七、踩坑清单

| 坑 | 现象 | 处理 |
|---|---|---|
| 中文整段一个 token | 两字词零结果 | 写入侧逐字归一化 |
| trigram 最少三字符 | 两字词被拒 | 不用 trigram，走 uni-gram |
| 查询含 FTS 操作符 | 语法错误或语义跑偏 | 每个 token 双引号包裹 |
| 纯标点查询 | MATCH 报错 | 归一化后为空直接返回空结果 |
| 型号被标点切开 | `qwen2.5` 变成 `qwen2` / `5` | 接受；两段都在索引里，仍可命中 |
| 清理只删事件 | 索引残留、搜到幽灵结果 | 按 event_id 先删索引行再删事件行 |

最后一条容易被忽略：索引表不是外部内容表，事件删了不会自动带走索引行。清理必须显式两步，顺序是先索引后事件。

## 八、边界

- 不做同义词、拼音、繁简转换；搜「检索」不会命中「查找」。
- 不做跨语言重排；中英混合查询按 token 平权。
- 不做实时高亮片段；结果返回事件本身，详情由统一投影渲染。
- 索引里存的是归一化串，不是原文；想还原原文必须回连事件表，不能只读索引。
- 不做云端索引；FTS 表就在本地库里，跟着数据库一起备份。
