# DST 的两个坑：不存在的 02:30 与出现两次的 01:30

只要支持 IANA 时区，就绕不开夏令时。

中国区用户平时感知不到，但用户可能把定时设成 `America/New_York`、`Europe/Berlin`，也可能带着笔记本跨时区工作。这一版必须把两个边界说清楚。

## 一、春季：02:30 不存在

美国东部时间在 3 月第二个周日从 02:00 跳到 03:00。也就是说，当天 02:30 这个墙钟从未发生。

如果 cron 是 `30 2 * * *`，算法会先算出 3 月 8 日 02:30 这个候选墙钟，再换算回 UTC。回读校验会发现：

```text
换算后的墙钟 = 01:30 或 03:30，不等于 02:30
```

于是跳过这个候选，继续找下一个匹配。实际的执行点变成 3 月 9 日 02:30（EDT）。

**语义：不存在的时刻跳过，不补跑，不挪到 03:30 执行。**

## 二、秋季：01:30 出现两次

11 月第一个周日，01:00 会走两遍：先 EDT，再 EST。本地时间 01:30 因此对应两个瞬时。

`30 1 * * *` 应该跑几次？

这一版的选择是**只跑一次**：墙钟换算会落到其中一个瞬时；如果该瞬时已经过去，下一次搜索直接跳到第二天的 01:30，不会在第二遍 01:30 再跑一次。

理由：

- 用户配置的是「每天 01:30」，不是「每个 01:30」；
- 一天跑两次会让「每日简报」类任务出现重复内容；
- 与主流 cron 实现的常见行为一致。

## 三、测试怎么写

DST 用例不能依赖开发机的本地时区。测试显式传入 IANA 时区与 UTC 瞬时：

```ts
// 春季：跳过后顺延到次日
nextCronTimeInZone(
  parseCron('30 2 * * *'),
  new Date('2026-03-07T12:00:00.000Z'),
  'America/New_York',
); // → 2026-03-09T06:30:00.000Z

// 秋季：同一墙钟只执行一次
const first = nextCronTimeInZone(spec, from, 'America/New_York');
const second = nextCronTimeInZone(spec, first, 'America/New_York');
// second 是次日，而不是同日的第二个 01:30
```

## 四、把语义写进文档

代码只能保证行为，用户需要知道行为是什么。

因此定时对话框的时区提示、v4.26 的 spec 与发行说明都明确写了这两条规则。将来如果要做「补跑两次」或「跳过当天」，应当作为显式选项，而不是悄悄改默认值。

DST 不是边缘 case，它是时区功能的必修课。把它想清楚，剩下的只是把测试写扎实。
