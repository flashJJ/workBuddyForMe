# 会排班：从一个闹钟到一张班表

v4.24 让流程有了第一只闹钟：一个流程、一条 cron、系统本地时区。

真正用起来，需求很快变成「工作日早上九点发简报、每晚十点归档、每月一号出月报」。在旧模型里，只能复制三个流程，图会漂移，运行记录也被拆散。

v4.26 把「一个流程只能有一条定时」这个约束去掉了：**每流程最多 5 条，各自独立的 cron、时区、入参与启停**。

## 一、为什么是 5 条

不是技术上不能更多，而是配置面板与调度扫描需要一个明确边界：

- 超过 5 条，用户很难在一屏内核对「我到底排了什么」；
- 调度器每 30 秒扫描一次到期项，单流程条数直接决定一次 tick 的工作量；
- 真正需要更多班次的场景，通常应该拆成不同流程，让运行记录与版本各自独立。

上限写进 shared 常量 `FLOW_SCHEDULE_LIMIT`，服务层与 UI 共用，避免两处各写一个数字。

## 二、一条定时的完整语义

每条定时包含：

| 字段 | 作用 |
|---|---|
| `name` | 可读名称；为空时 UI 显示 cron |
| `cron` | 5 字段表达式 |
| `timezone` | IANA 时区，默认 `Asia/Shanghai` |
| `enabled` | 独立启停 |
| `input_json` | 该条目专属入参 |
| `next_run_at` / `last_*` | 独立的下次时间与最近结果 |

调度器扫描的是行，不是流程。因此两条定时同一分钟到点，会各自走一遍「到期 → 认领 → 创建运行」；第二个会发现流程已有在途运行，记录 `skipped_busy` 并推进到下次。

## 三、单飞没有变

多定时很容易让人以为需要并发执行同一个流程。这一版仍然坚持按流程单飞：

- 同一个流程同一时刻只允许一个在途运行；
- 多条定时同时到点，先到者创建运行，其余跳过；
- 跳过的条目仍推进 `next_run_at`，不会在下一次 tick 里反复重试。

这是可靠性版本的边界：先保证「不会因为班表变多而并发打架」，逐次补齐与并发执行留给 v5.0 的可靠性主题。

## 四、升级不是推倒重来

数据库迁移 v056 重建了定时表，但旧行的 id、cron、入参和历史状态全部保留，只回填 `timezone = 'Asia/Shanghai'` 与空的 `name`。

对用户来说，升级后原来那条定时仍然在、仍然按原来的时间跑；只是现在可以再添加第二条、第三条。

## 五、这一版不做什么

- 不做 HMAC、事件重试、死信与心跳；
- 不做错过多个周期的逐次补齐；
- 不做运行保留、失败通知与统一观测面板；
- 不做安全沙箱与运行治理。

这些都在 v5.0「会兜底」里。v4.26 只把配置层的「排班」做顺，让可靠性版本有一个干净的起点。
