# 语音运行时下沉 core，与 Next standalone 的跨盘符文件追踪坑

这篇记两件事。前半是一次「教科书式搬家」：长在 web 应用层的语音运行时整体下沉到 core 包独立子路径，测试断言零修改、页面路由零改动。后半是这次打包验证时撞上的 Next.js standalone 文件追踪（nft）大坑——一个只在打包态发作、开发态完全正常的跨盘符路径陷阱，排查体验和玄学无异，但根因异常朴素。

## 为什么搬：运行时长在了消费层

语音能力是上个版本一口气长出来的：运行时、设置、模型路径解析、引擎配置、模型文件管理、类型定义——全在 web 应用里。能跑，但结构是歪的：

- **core 无法复用语音**。core 是对话编排所在，语音 TTS/ASR 本该是编排可调用的基础能力，却住在它上层的 web 里，依赖方向倒着；
- **边界不清**。web 页面组件直接握着引擎句柄和模型文件路径，HMR、UI、运行时三件事缠在一组模块里。

v1.1 的决定是整体下沉到 core 的 voice 域，而不是在 core 里重写一份。

## 搬家过程：测试跟着代码一起走

搬的不是单个文件，是一整个运行时簇：

```text
voice-runtime（运行时）/ voice-settings（设置）
model-paths（模型路径）/ engine-config（引擎配置）
voice-model-files（模型文件）/ 类型定义
+ 7 个测试文件，整体随迁
```

落地数字是这次搬家最有说服力的部分：**7 个测试文件随迁，断言零修改；页面路由零改动。** 测试断言不改，证明搬过去的行为和原来逐项等价；路由不改，证明消费方只是换了 import 来源。web 侧最后只剩三样东西：

- 一个挂在 globalThis 上的 **HMR 单例薄壳**（开发态热更新时不重复初始化引擎）；
- 设置的 re-export；
- 一层 `withVoice` SSE 桥，把 voice 事件挂进对话流。

运行时逻辑一行没留在 web。

## 入口形态的刻意设计：不进根 barrel

下沉有个诱惑：顺手挂进 core 的根 barrel，消费方写一行 import 就完事。我们刻意**没有**这么做，而是让构建产出多入口：

```js
// tsup 多入口
entry: { index: 'src/index.ts', voice: 'src/voice/index.ts' }
```

包的 `exports` 里为 `@app/core/voice` 配子路径，**生产条件指向独立的 voice 产物，类型/开发条件才指向源码**。voice 域成为一个需要显式伸手才能拿到的边界，而不是根 barrel 里免费可得的公共物。

放行多入口有一个硬条件，来自本系列前面讲 barrel 子路径化时踩过的坑——**类身份分裂**：如果子路径产物是独立 chunk，同一个 `ApiError` 类会在两个 chunk 里各有一份副本，`instanceof` 跨副本失效，错误判断悄无声息地全部走偏。所以双入口产物构建出来后，我们核对了 chunk 构成：**两者的共享块只有 esbuild 注入的 export helper**，没有任何业务类被复制。满足这个条件，独立入口才放行。

## 打包真机收口：TTS → ASR 回环

搬家是纯结构调整，但「行为等价」不能只靠单测声明，最终取证在打包真机：

- 打包准备脚本零改动；
- 真机上跑完整语音闭环：**TTS 合成语音 → 播放 → ASR 回环识别，逐字正确**。

开发态通过不代表打包态通过——这句话在后半篇会以更惨烈的方式再验证一次。这里还固化了一个打包常识：真机语音依赖模型文件，打包态默认数据根在应用自己的 userData 下，需要显式指定数据根才能复现开发机的模型资产。

## 后半篇：standalone 打包后，所有路由首窗超时

语音回环通过后，打包验证还有一道关：内置 Next 服务以 standalone 形态起在桌面壳里。就在这里翻车了——**打包态打开任意页面首窗全部超时，而开发态同样的代码完全正常。**

Next standalone 的工作原理是 nft（文件追踪）：构建时静态分析每个路由依赖了哪些文件，生成 manifest，再把这些文件归集进 standalone 产物。问题出在「静态分析」这四个字上。

## 根因：manifest 字面量与 homedir() 被追踪到了真实数据根

语音引擎的模型清单里带有**字面量绝对路径**（指向语音数据目录），代码里还有 `homedir()` 这样的调用。nft 追踪器在构建机上做静态求值时，把这些路径当真解析到了**磁盘上真实存在的数据根**——而数据根在另一个盘符上。

跨盘符路径无法相对化，追踪器就造出了这种嵌套条目：

```text
.next/server/C:/<跨盘符的嵌套路径>/...
```

字面意思是：在 `.next/server/` 目录下，试图按一个带盘符的绝对路径再嵌套出一整串目录。更致命的是归集行为：**单个这样的文件 ENOENT 复制失败，会中断该路由后续所有文件的归集**——包括 `.next/server/chunks` 下被多个路由共享的 chunk。

于是现象被层层放大：

1. 某个路由的归集撞上嵌套路径，抛错中断；
2. 该路由本该复制的共享 chunk 缺失；
3. chunk 是全局共享的，**打包态所有路由启动时都 MODULE_NOT_FOUND**，首窗集体超时；
4. 开发态 Next 直接从源码和 node_modules 起服务，根本不做归集——所以开发态永远复现不了。

## 修复：只有 picomatch 语义的 ignores 能用

方向很明确：让运行时数据根彻底离开追踪视野。但配置选型连踩一坑：

- `outputFileTracingExcludes` 在 Next 14 上会被 `path.join(项目根, glob)` 处理——盘外路径和项目根拼死在分隔符上，**语言层面就表达不了「另一个盘符的目录」**；
- 最终可用的是 `outputFileTracingIgnores`：glob 原样交给 picomatch，不做路径拼接。在 Windows 上 picomatch 的 `/` 同时匹配 `\` 和 `/` 两种分隔符，一条忽略规则就够：

```js
experimental: {
  // 运行时数据根（模型/语音数据/附件）绝不进 standalone
  outputFileTracingIgnores: ['**/<运行时数据根目录>/**'],
}
```

配上之后重新打包：嵌套条目消失，共享 chunk 归集完整，打包态所有路由恢复。规则连同原因注释固化进了 Next 配置。

## 两条收口

其一，**重构的安全姿势是行为外迁而非重写**：整簇代码连同测试一起搬、断言零改、路由零改，最后用真机 TTS→ASR 回环给等价性盖章，结构调整才算闭环。

其二，nft 这一坑再次提醒：桌面应用里「开发态正常」几乎不提供信息。构建期的静态求值、打包期的文件归集、运行期的数据根解析，是三段只在打包态才连起来的链路——任何一段把**开发机上的磁盘真相**当成了**用户机器上的事实**，都会以「只有装出来的应用才坏」的形式偿还。下一篇讲的两个真机热修，把这条教训推到了极致。
