# 评估平台化：让每个 golden set 先证明自己不是恒真

上个版本我们只有一个评估脚本：记忆 golden set。它忠实地跑了很多个版本，但它有一个结构性问题——**断言、接线、造数、报告全揉在一个文件里**。这个版本做「零新功能」加固，评估平台化是我最想写的一篇：它逼出了一条比覆盖率更重要的规矩——**评估必须证明自己不是恒真**。

## 一个脚本的三个身份

旧的记忆评估脚本一个人干三份活：

1. **基础设施**：发 HTTP 请求、拼 SSE 流、等 done 帧、取 usage；
2. **裁判**：判断召回对不对、judge 给几分；
3. **布景**：起 mock 供应商、灌模型、写 golden 数据，跑完还得收拾。

想开第二个评估域时，唯一的复用方式是整文件复制粘贴改断言。断言措辞各不相同（有的返回布尔，有的直接 `process.exit`），报告只在控制台飘过，跑完想和上次对比只剩翻终端。

## 五件套：评估脚本退化为纯消费方

本版本在 `scripts/eval/lib` 抽出五件：

| 件 | 职责 |
|---|---|
| HTTP 客户端 | 统一信封解析、非 2xx 抛出、基础设施错误与断言失败分开 |
| SSE 客户端 | 事件帧解析、按事件名取帧、流错误挂在结果上而非直接崩 |
| 断言 | 每个断言返回 `{ pass, reason }`，失败原因说清「实际看到了什么」 |
| 报告 | 汇总成控制台 PASS/FAIL 行 + `{pass,reason}` JSON 落盘，退出码 0/1/2 |
| 幂等造数 | mock 对话供应商与嵌入供应商按能力装配，重复跑不产生重复数据 |

消费方脚本瘦成了线性的「布景 → 触发 → 断言 → 出报告」：

```js
const seed = await ensureMockStack(baseUrl);        // 幂等布景
const stream = await streamChat(baseUrl, url, req); // 触发
checks.push(promptTokensBelow(stream.usage?.promptTokens, budget));
const summary = summarize(cases, { name: 'eval-tool-compact', meta });
const code = printSummary(summary);
if (args.out) await writeReport(args.out, summary);
process.exit(code); // 0 全过 / 1 断言失败 / 2 基础设施挂了
```

退出码区分 1 和 2 是刻意的：**断言失败说明被测系统有问题，基础设施失败说明这次评估本身无效**，两者绝不能混为一个 exit 1——无效评估绿了比没有评估更危险。

旧的记忆脚本改造成消费方后，报告格式和退出码一字不变，基线连续性保住了。

## 三个 golden set 域

平台就位后，评估域从 1 个扩到 3 个：**记忆、工具压缩、主动轮**。三个域共享同一套五件套，每个脚本只描述自己的链路与断言。

记忆域沿用旧基线；另外两个是本版本的新压缩层与主动轮协议量身定做的，下面细讲。

## 工具压缩集：600 条 fixture 上的 4 条断言

压缩层（本系列前面讲过的中央工具结果压缩）最大的风险是：**它是一个「悄悄改变模型所见」的层**。压得太狠模型丢信息，等于没压；不压则 100KB 工具结果原样回灌。必须有端到端评估钉死。

布景是一个 fixture MCP server：吐 **600 条记录，每条含 id/code/status/payload，整体约 120KB**。mock 模型负责按脚本触发工具调用，并在第二轮引用压缩视图里的首个 id 作答。4 条断言：

1. **入模 token 显著下降**——`done.usage.promptTokens` 必须低于 golden 预算（120KB 原样入模约 4 万 token）；
2. **双视图存在**——落库 trace 里有 `compacted:true` 的条目，且 `originalTokens > modelTokens`：模型见到压缩视图，而完整事实仍在 trace 里；
3. **首个 id 能二次引用**——回答必须引用第一条记录的身份 id，且读到了压缩视图里的省略标记。模型被压掉的内容，靠编号句柄还能查回来；
4. **UI 看到完整结果**——界面上呈现的是未压缩全文，压缩只发生在入模边界。

四条断言分别钉住预算、双视图、可回查、对用户透明，缺一条压缩层都可能「看起来在工作」。

## 反向验证：回退压缩器，断言必须如期变红

断言写完跑通，只是「评估能跑」；评估**有效**的取证是另一步——**反向验证**：

> 故意回退被测代码，断言应当按预期失败。如果代码都回退了断言还绿，这条断言就是恒真的废话。

我把压缩器整体回退成原样透传，重跑 golden set：

- 120KB fixture 以 **40949 token 原样入模**，预算断言 FAIL；
- trace 里再也找不到 `compacted:true`，双视图断言 FAIL；
- 入模视图没有省略标记，mock 模型无法引用它，二次引用断言 FAIL；
- UI 仍显示完整结果，第 4 条如期保持 PASS。

**3 条变红、1 条保持绿**，每条断言的行为都和设计预期精确一致。这一步的价值和测试里的变异测试同源：删掉被测行为，裁判必须立刻翻脸。一个从来没见过红灯的断言，没有资格守门。

## 主动轮：2 条断言钉住「轻量、无痕」

主动轮是空闲时的 skip-history 轻量对话，它的协议承诺是两条：

1. **标记正确**——meta 帧带 `proactive:true`，且 messageId 是 `proactive-` 前缀的临时 id，一眼可辨、绝不与真实消息混用；
2. **轮次后消息数不变**——先经正常对话建立消息数基线，主动轮跑完再数一遍，必须严格相等：用户指令和助手搭话都不落库。

第二条是对「无痕」承诺最硬的取证：不去读任何内部状态，只数用户可见的消息行数。

## 覆盖率分级门禁：好钢用在压缩器上

平台之外，本版本第一次给覆盖率设了**分级**门禁，而不是一条全局线：

```js
// core：全局语句/行 70%，压缩模块四指标（statements/branches/functions/lines）95%
thresholds: {
  '**/tools/tool-result-compact.ts': { statements: 95, branches: 95, functions: 95, lines: 95 },
  // 全局兜底 70
}
```

实测水位：压缩模块 **100 / 98.8 / 100 / 100**，27 个测试喂出来的。其余包不搞一刀切。

web 是**第一次接覆盖率**：只给三个关键域（服务端 lib、chat、voice）设 60% 的语句/行门槛，实测 **64 / 80 / 67**，全部贴着线过。其余包本版本只出报告、不设卡——先看见水位，下一个版本再谈卡在哪，不为了凑数写水测试。

## 配套经验一：glob 门槛会静默放过你

分级门禁上线当天学到一课：**vitest 的 glob 门槛匹配是静默的**。glob 拼错、路径对不上文件，门槛不报错、不警告，等于这条门槛不存在——全局绿得毫无意义。

自检方式固定下来：配完门槛，**临时把阈值抬到不可能值（比如 99%），必须观察到 exit 1，且报错精确打印出 glob 与实际水位**，确认它真的在抓人，再改回目标值。门槛配置本身也需要一条「故意被抓住」的探针，和边界 ESLint 门禁的做法一脉相承。

## 配套经验二：95 而不是 100，照真实分支结构设

压缩模块的分支覆盖是 98.8%，唯一没走到的臂，是一个 hint 预留分支。hint 会预先扣除固定的提示 token，这使得「触发了压缩、但正文一个字都没被裁」的分支在**数学上不可达**。

它是刻意保留的防御代码（未来 hint 规则变化时兜底），但不该为了覆盖率数字去构造一个数学上不存在的输入。所以门槛按真实可达分支结构设 **95%**，而不是拍一个好看的 100%。**门槛数字必须能回答「未覆盖的那一臂是什么、为什么允许它不被覆盖」。**

## 收口

这一篇两件事：评估平台化让「加一个评估域」从复制粘贴变成写消费方；反向验证让每条断言自证不是恒真。覆盖率分级则是同一种哲学的延伸——**门禁要对照真实结构设定，而门禁自身也得被测试**。裁判和规则都不是天生可信的，它们的可信度同样需要证据。
