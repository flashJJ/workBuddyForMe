# 把分层架构焊进 ESLint：方向 zone、internal 全配对和两个语义坑

上个大版本结束时，我们的分层依赖方向是「写在设计文档里」的：core 包是唯一可以聚合全部领域的编排层，桌面壳只碰共享契约，web 应用不能引用桌面壳。规则本身很朴素，执行方式全靠评审时肉眼抓。

当时实际违例是零。那为什么还要花力气配 lint？因为零违例只证明「过去记得」，不证明「将来不会忘」。v1.1 的 M0，我们用 import/no-restricted-paths 把这张依赖图变成了硬门禁。这篇讲配置形状、两个真实踩到的语义坑，以及门禁怎么证明自己真的在干活。

## 要守的两条不变量

第一条是**分层方向**：

- 底层包（shared、config）不依赖任何业务包；
- 各业务包单向依赖，packages 不许反向依赖 apps；
- 桌面壳禁止碰数据库、AI、core、voice 包和 web 应用——壳只负责进程生命周期与 IPC；
- web 应用禁止引用桌面壳。

允许的方向画出来是一张单向图：

```text
core 包     ── 可以聚合 shared/config/database/ai/voice（唯一的编排层）
voice 包    ── 只认 shared/config
ai 包       ── 只认 shared
database 包 ── shared/config
桌面壳       ── 只认 shared/config 的公开契约
web 应用     ── 各包公开面，禁引桌面壳
```

对桌面壳最苛刻是有意的：壳是打包后持有全部系统权限的进程，它一旦直接碰数据库和业务逻辑，IPC 这道天然的审查缝就消失了。让它只认识契约，等于在进程边界上保住一次强制序列化。

第二条是 **internal 私有目录**：A 包的 `internal/` 只有 A 包自己能碰，跨包消费只能走域公开面（根 barrel 或域子路径）。这条防的是另一种常见腐化：有人图省事深路径引了别人内部文件，等那个内部文件重构时，谁也不知道外面还挂着多少消费者。

两条都用同一个 ESLint 规则表达：`import/no-restricted-paths` 的 zones。zone 的语义是「from 这一侧的文件，不许 import target 这一侧的文件」。我们没有手写十几条容易过期的规则，而是按六个包的依赖白名单，逐目录生成「所有不在白名单里的发起方」禁入 zone。精简后的形状长这样（包名为占位）：

```js
// 桌面壳不许碰数据库
{
  target: './packages/database/src',
  from: './apps/desktop',
  message: '桌面壳只能依赖 shared/config 的公开契约',
},
// web 应用不许引桌面壳
{
  target: './apps/desktop',
  from: './apps/web',
  message: 'web 应用不能引用桌面壳',
},
```

配的时候，我们结结实实踩了两个语义坑。

## 坑一：方向 zone 的 from 必须是具体目录，不能写 glob

第一反应是图省事，from 写成 glob 通配。结果规则行为开始飘忽：同包内的正常引用被误伤，真正的跨层越界反而漏掉。

原因在规则的判定方式：它用路径包含关系判断一次 import 是否落在 target 内，**同包目录是被天然放行的**——from 是一个确定目录时，「目录内的文件引目录内的文件」包含关系清晰；一旦 from 写成 glob，包含判定失去基准，这套放行语义就不再成立。

结论很简单：方向 zone 的 from 一律用非 glob 的具体目录，一个目录一条 zone。矩阵大一点没关系，它是按白名单生成的，不需要人手维护。

## 坑二：except 只认「被引物」，不认识「发起方」

internal 限制更绕。我们想要的语义是「A 的 internal，只有 A 自己能引」。规则虽然提供 except，但 except 匹配的是**被引模块的路径模式**，没法表达「当发起方恰好是 A 时放行」——它根本不知道这次 import 是从哪个文件发起的。

绕不过去，只能把笛卡尔积枚举出来：对每个拥有 internal 的包 A，把「其他每个包加两个 app」各配一条指向 A/internal 的禁入 zone：

```text
for (const A of packagesWithInternal)
  for (const B of everyDomainExcept(A))
    zones.push({ target: 'packages/<A>/**/internal', from: '<B 的目录>' })
```

全配对矩阵看着笨，但有两个好处：语义无歧义；新增一个包时，生成器会逼你显式决定它和所有 internal 的关系，没有「默认放行」的模糊地带。测试文件需要访问 internal 做白体测试，用 ESLint overrides 对 `**/*.test.ts` 单独放行，不混进生产规则。

## 两个工程配套

这两个不解决，规则配了也是静默失效：

- **eslint 直跑 .ts 探针必须显式带 `--ext .ts,.tsx`**。ESLint 默认只认 .js，不显式给扩展名，探针文件会被静默跳过——你以为规则在跑，其实它什么都没检查；
- **resolver 固定 TypeScript resolver**，并显式给出 project 列表，否则包 exports 子路径和 tsconfig paths 都解析不出来，规则同样形同虚设。

## 灰度：先 warn，观察一个完整大版本

规则上线的方式也有讲究。带着存量违例直接翻 error，结果只有两个：要么立刻修一堆不相干的东西，要么被 disable。我们的节奏是：

- M0 以 **warn** 落地，贯穿 M0–M4 整整五个里程碑观察，实际结果是零违例；
- M5 才同批翻成 **error** 进 CI。此时全仓 0 error，只剩 22 条与边界无关的历史 warning。

warn 期不是走过场，它是在收集「规则不误伤」的证据。证据不够，就不翻硬门禁。

那确实存在合理越界怎么办？规矩是走架构评审、调整白名单和 zone 生成结果，让新方向显式进图；**不接受行内 eslint-disable 开口子**。口子一开，「禁止」就退化成「默认禁止但到处都是例外」，图又重新回到脑子里。

## 门禁必须自证：故意违例探针

最后一条经验：任何边界规则都要配「故意违例」探针。我们放了两个探针文件——web 应用里引一下桌面壳、包外文件引一下别人的 internal——单独跑 ESLint，**必须 exit 1**。

这一步直接呼应前面两个坑：glob 写错、`--ext` 漏写、resolver 没配，任何一种「规则其实没生效」都会让探针 exit 0。探针不红，规则就等于没配。最终 CI 里探针和门禁成对存在：一个证明好代码能过，一个证明坏代码过不了。
