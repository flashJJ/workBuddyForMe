# 28 到 1：483 行的桌宠管理器，和一条不阻断的 260 行预警线

很早的版本我们就给这个单人项目立过一条硬规则：手写文件超过 300 行不许提交。起因很简单——在一个 800 行的组件里加按钮加到崩溃之后，我发现 300 行是「一屏能看个大概」和「必须靠搜索定位」之间的分界线。这条规则跑了很多个版本，直到上个大版本三条能力线并行，白名单开始变长。

v1.1 开工盘点时，260 行以上的手写热点有 28 个，最长的桌宠管理器 483 行，在白名单里续着命。白名单每个条目虽然都写了理由，但它本质上是债，不是资产。M2 我们集中还了这笔。

## 先加一档：260–299 预警，不阻断

硬规则只有一个 300 行的悬崖，副作用是文件到 295 行时没有任何信号，等撞线再拆，往往已经错过了最好拆的时机。这次在检查脚本里加了一个预警档：

```text
260 ≤ 行数 ≤ 299  → 打印 warning，不阻断
行数 == 300       → 正常放行，也不预警
行数 ≥ 301        → 检查失败，退出码 1
```

三个数字各有理由。预警不阻断，是为了让热点在形成前就可见，而不是制造新的提交摩擦；整 300 不预警，是因为 300 本来就是硬规则的合法边界，不该在边界上制造噪音；退出码只由「超过 300」决定，预警档永远卡不了 CI——档位语义必须这么干净，否则大家很快会学会忽略所有输出。

## 白名单只认三种身份

加预警档的同时，白名单的准入理由也收紧了，只承认三类：

1. **自动生成**——清单、manifest 一类，行数不是人写出来的；
2. **barrel 聚合**——纯 re-export 的出口文件；
3. **已登记的技术阻塞**——确属单一不可拆状态机，允许留，但必须附拆分计划和到期版本。

第三类是逃生舱，不是常态。它承认「有些文件此刻拆不动」这个现实，但拒绝让现实变成永久豁免——每个条目都必须回答「什么时候还」。

## 检查脚本刻意保持很笨

和边界 lint 一样，行数检查就是一个零依赖 Node 脚本：扫 apps 和 packages 下的手写 `.ts/.tsx`，按三个档位输出，超过 300 就非零退出，挂进日常检查和 CI。

它不做任何「聪明」判断：不折算注释行、不按目录放宽、不识别框架样板。这种笨是故意的——任何智能豁免都会制造灰色地带，而灰色地带一定会被用满。脚本只认物理行数，「这个文件为什么特殊」全部留给白名单评审，机制和判断分离，两边都没法糊弄对方。

## 拆分的四个模式

拆文件不搞运动，逐个热点按职责归位，翻来覆去只用四种手法：

1. **纯函数外迁**——任务循环的步骤拼装、mapper 里的映射分支这类不碰状态的逻辑，搬成独立函数模块，输入输出明确，搬走即可测；
2. **类型外迁**——大段 interface 和类型联合搬到同名类型文件，主文件立刻瘦一圈，阅读时也不再被类型声明打断；
3. **UI 子组件外迁**——流程编辑器、端点对话框里的大段 JSX 抽成同目录子组件，class 名和样式一个不动；
4. **测试夹具外迁**——造数工厂和大 fixture 从测试主体剥离，测试文件本身也受 300 行规则管。

没有新抽象、没有新框架，只有搬代码加注入依赖。判断标准也很朴素：搬走之后主文件的描述应该读得像一个目录，而不是仍然塞满实现细节。

## 主案例：桌宠管理器 483 行拆四件套

桌宠管理器是最典型的「什么都管」文件：拖拽、悬停轮询、右键菜单、IPC 注册、窗口生命周期全塞在一个类里。按职责切成同目录四个协作者：

| 新文件 | 搬走的职责 | 行数 |
|---|---|---|
| 拖拽控制器 | 拖拽起止、光标读取、手势阈值、DIP 定位 | 87 |
| 悬停轮询器 | 系统拖拽宽限窗、move 事件轮询 | 65 |
| 菜单 | 右键菜单模板与动作类型 | 46 |
| IPC | channel 到方法的注册表（身份校验仍归管理器） | 80 |

主文件只留生命周期、换窗和广播，降到 260 行以下，**当场移出白名单**。

有个细节能说明「外迁」的分寸：拖拽控制器连 3px 的手势阈值、屏幕坐标到 DIP 的换算一起原样搬走，没有顺手「优化」；悬停轮询器搬走时连「系统拖拽宽限窗」的常量一起搬——系统级拖拽进行中时，应用自己收不到常规 move 事件，必须留一个宽限轮询窗口，这种时序补丁一旦在搬迁中走丢，复现要按小时算。IPC 四件套里只放 channel 到方法的注册表，**身份校验仍留在管理器的入口**——注册表可以是纯数据，但「这个调用是不是来自可信窗口」是管理器的权责，不能跟着搬散。

拆这种文件最怕「拆着拆着变成重写」。我们的纪律是行为外迁而非重写：代码原样搬走，协作者需要的上下文通过参数注入，管理器的公开方法签名一个不动。原测试文件 366 行，用例按主题迁到拖拽控制器和悬停轮询器各自的测试里，23 个测试断言**零修改**——断言面向的是公共行为，内部文件怎么切与它无关。测试不动，反过来又证明了行为真的没被改。

## 桌面壳主入口：297 → 147

另一处代表是桌面壳的主入口。入口文件天然是杂物间，这次把启动引导、全局快捷键注册、更新引导分别外迁，入口只留两件事：进程生命周期和启动序列。297 行降到 147 行，「启动顺序」第一次能从头顺着读下来。

外迁的三个模块也各自单一：引导模块管数据库与配置就绪，快捷键模块只管注册与注销，更新引导只在启动序列里被调一次。入口不再知道它们的内部步骤，只知道按什么顺序调谁。

## 先判断：是杂物间，还是单一状态机

不是所有长文件都该拆。动手前先问一个问题：这文件长，是因为塞了太多不相干的职责（杂物间），还是因为它确实是一个内聚的、状态转换密集的单一状态机？

杂物间大胆拆，四模式套上去就行；后者如果硬拆，只会把一个完整的状态转换表切成几个互相传内部状态的碎片，可读性反而更差。这类文件允许走前面说的第三类白名单，但必须登记拆分计划——区别在于，我们要能说出「它为什么不能拆」，而不是「它一直这么长」。实际盘点下来，28 个热点里绝大多数是杂物间，真正需要登记的技术阻塞几乎没有。

## 结果：28 → 1

- 260 行以上手写文件 28 个 → **1 个**，降幅 96%，零新增白名单；
- 唯一剩下的预警是压缩器单测 285 行——它落在预警档，只提示、不阻断，且这是测试文件，不是生产热点；
- 白名单里只剩自动生成的清单和 barrel 聚合类，每个条目都有「不可手写」的客观理由。

拆完还有个意外收益：下一篇要讲的 barrel 域子路径化，正是在这批小文件上做的——文件职责单一时，「这个导出归哪个域」的答案几乎是白送的。

## 收口

回头看，这批拆分真正起作用的不是某个模式，而是三条顺序：

- 先加预警档看见全貌，再动手——28 这个数字是脚本扫出来的，不是感觉出来的；
- 先搬行为、不改行为，测试零修改是搬迁合格的验收单；
- 白名单只出不进，拆完一个摘一个，到最后名单本身就是「什么不是手写代码」的说明书。

行数不保证设计正确，但它保证烂味道会在固定的时间点被看见——对一个人维护的项目，这就够了。
