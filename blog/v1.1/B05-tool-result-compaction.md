# 工具结果中央压缩层：100KB JSON 只给模型看 4%，事实一个不改

先说一个真实场景。一个 MCP 工具返回结构化查表结果：600 条记录，序列化后约 120KB，折合约 4 万 token。上个大版本的处理方式堪称耿直——这 120KB 原样拼进下一轮请求，和记忆、对话正文抢同一个上下文窗口。表大一点，模型这轮就只剩「读表」的份，多轮对话直接被挤没。

v1.1 的 M1 我们加了工具结果中央压缩层。它是这个版本唯一的核心新模块，但设计原则从第一天就钉死了：

> 压缩只造视图，不改事实。

## 双视图：模型看预算视图，其他一切看完整结果

压缩器是一个**零依赖、无状态的纯函数**：输入完整工具结果加预算，输出给模型看的文本。预算在上下文装配期统一下发——模型窗口的 20%，保底 256 token——压缩器不读任何全局状态，同样的输入永远得到同样的输出。

预算数字不是压缩器自己拍的。上下文窗口本来就有一本统一账：系统提示、记忆、对话正文、工具结果各占多少，装配时一次性算清。压缩器只是这本账的一个执行末端，接到多少花多少。接线点也因此只有一个：工具结果入模的那个边界，把原来的「原样 output」换成「压缩视图」，其他链路一行不碰。

还有两条语义边界提前讲清：工具结果的 `summary`（UI 卡片用的短摘要）维持原样，压缩只作用于回灌入模的 `output`，不碰双字段语义；图片走既有的多模态通道，根本不进文本压缩器。

完整的 ToolResult 一切照旧：

```text
工具执行 ── 完整 ToolResult ──► trace / SSE 事件 / UI / 消息记录（原样保留）
                │
                └─ 入模前过压缩器 ──► 只给模型的预算视图
                     并标记 compacted / originalTokens / modelTokens
```

用户在界面上看到的、trace 里回放的、调试时核对的，全是未删改的原文；只有发给模型的那一份是压缩视图，条目上还带着三个标记：压没压、原始多少 token、给模型多少 token，一目了然。

## 三个标记让压缩可审计

「悄悄改变模型所见」的层，最大的风险是不可审计：模型答错了，你不知道是它自己的问题，还是它看到的世界本来就被裁过。所以 trace 条目上的三个标记是硬要求，不是调试彩蛋：

- `compacted`——这一条到底有没有压，布尔值，不许靠「对比长度」猜；
- `originalTokens`——完整结果本来值多少；
- `modelTokens`——模型实际看到多少。

eval 里「双视图存在」的断言直接查这三个字段：`compacted:true` 且 original 大于 model，才说明压缩真的在入模边界发生、而完整事实仍留在 trace。无状态纯函数在这里又帮了一次：压缩器不持有上下文、不写任何存储，trace 标记由调用方在装配时记录，想回放某一轮决策，把同样的结果和预算再喂一遍，输出逐字一致。

## 六套策略，按结果形状分流

一个纯函数内部分六套策略，各管一类：

| 策略 | 适用 | 做法 |
|---|---|---|
| 直通 | 计算器工具、错误结果、极短文本 | 不压——错误被截断会误导模型 |
| 知识库检索 | RAG 片段列表 | 保编号的特化压缩（见下） |
| JSON 结构取样 | 可解析的结构化 JSON | 数组识别形状后头部取样，标出省略量 |
| 身份类 | 末级记录对象 | 保留 userId、status 等身份字段 |
| 网页 | 网页抓取结果 | 保首行来源头，预算更紧时二次裁 |
| 文本 | 通用兜底 | 长字符串裁到 120 字，带省略标记 |

直通同样是策略的一种，不是「没走到压缩逻辑」。计算器结果要原样给模型算数，错误结果被裁掉半截只会让模型误判失败原因，桌面控制、截图类工具的文本本来就极短——这些情况下压缩的收益是零、风险是真的，所以显式直通，而不是依赖下游策略「恰好什么都没做」。

## 知识库特化：编号句柄一个都不能丢

知识库检索的压缩最讲究，因为片段编号是模型下一轮**引用的句柄**。编号丢了，模型就没法说「请展开第 37 条」，工具连环调用直接断链。这里做了三级降级：

```text
预算充足  → 编号 + 文档名 + 短摘录，贪心装入
装不下了  → 只保留纯编号行（id 清单完整，内容全弃）
再不行    → 文本兜底，附一句固定提示：可用 id 二次查回
```

注意降级方向：先弃内容，最后才弃句柄。无论压到哪一级，模型被压掉的信息永远能用具体 id 再查一次。JSON 策略同理——头部取样之外，末级记录的身份字段（userId、status 这类）白名单保留，长字符串统一裁 120 字；网页结果保留首行来源，保证模型始终知道内容出处。

## 出口硬保证：消灭分段 ceil 误差

如果每段压缩各自估算 token，会有个隐蔽问题：每段向上取整留一点余量，十几段累加起来，总输出照样超预算。预算约束不能靠各段自觉，收口放在唯一出口。

还有个容易忽略的配套：压缩器用的 token 估算器，和 prompt 装配用的是同一个。如果两边各写一套估算，「压缩器认为没超」和「装配时认为超了」会永久对不上，预算账就成了两本账。复用同一个估算函数，零依赖也指的是不引新东西，连估算口径都不另起炉灶。

```ts
// 分段策略只负责「尽量省」，最终由出口统一保证不超
let view = compactByShape(result, opts);
view = guaranteeBudget(view, opts.maxTokens); // 超了就在这里最后一刀
```

效果用 eval 的真实 fixture 说话：600 条、约 120KB、约 4.1 万 token 的工具结果，入模视图降到约 1600 token——大约是原来的 **4%**；首个 id 可二次引用、UI 完整结果可见、trace 双视图标记，断言全过。为了证明这些断言不是恒真，我们还做了反向验证：把压缩器回退掉，入模 token 立刻涨回 40949，四条断言里三条变红——压缩确实在起作用，而不是测试在自嗨。

## 27 个测试盯边界

压缩模块一共 27 个测试，行覆盖 100%、分支覆盖 98.8%。因为压缩器是纯函数，每个用例都只是「给输入、对输出」，造畸形数据的成本极低，所以火力刻意全部压在边角上：

- 空结果、纯字符串、嵌套四层的 JSON——确认分流不被形状骗到；
- 100KB 大 JSON、数组形状识别、身份字段保留——结构取样的主路径；
- 知识库片段畸形、编号溢出、没有分隔头的脏数据——三级降级的每一级；
- 中文 token 预算边界、随机感长文连续多次运行——**恒定**不超预算，而不是「大多数时候不超」；
- 预算充足时结果必须原样通过——专门防双重截断的一条。

唯一没走到的分支是一个数学上不可达的防御臂：hint 会预先扣除固定提示 token，使得「触发压缩但正文一个字没裁」不可能发生。防御代码保留，但覆盖率门槛因此实事求是地设在 95%，而不是为了数字去构造一个不存在的输入。

一个纯函数、一份装配期下发的预算、两个视图，换来上下文窗口里约 96% 的腾退，而事实层面零改动。这个系列的前五篇到此为止；后面会继续写 SSE 契约如何从载荷真源机械派生、语音运行时怎么下沉 core 包，以及三个 golden set 为什么都必须带反向验证。
