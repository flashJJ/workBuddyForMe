# barrel 域子路径化：954 个成员大迁徙，和两个差点翻车的坑

v1.1 之前，core 包和 shared 包各有一个「巨无霸」根 barrel：core 的唯一出口聚合了 374 个具名成员，shared 聚合了 408 个。所有消费方都从同一个口子取东西，写法很省事，代价有两个：

- 任何一个成员改动，理论上牵动所有消费方的模块图——牵一发动全身；
- 打包器看到的是「整包都可能被用到」，tree-shaking 和模块图都是虚胖的。

M2 我们做了 barrel 域子路径化：成员按域归属，消费改成 `@app/core/errors` 这样的子路径。迁移量是 954 个成员、401 个文件，靠人工分类必然出错，所以第一件事是写 codemod。

## 零主观分类：用 TS checker 枚举归属

脚本零依赖，思路极其机械：用 TypeScript checker 把根 barrel 的全部具名导出名枚举出来，沿 re-export 链追溯到每个成员的真实定义文件，再按定义所在目录归属到域——core 15 个域、shared 9 个（errors、api、types、schemas 加 constants 等叶子），一个不多一个不少：

```text
枚举 barrel 全部 export 名
  → checker 沿 re-export 链追定义位置
  → 按目录机械落域
  → 改写消费侧 import 说明符
```

374 加 408 是两个根出口的直接成员数；沿 re-export 链完整展开后，迁移覆盖 954 个成员、401 个文件。整个过程**没有做过一次主观分类**。主观分类的问题不是慢，是同一个东西两个人会归到不同域，而且争论无法证伪；目录位置是客观事实，归属结果可复现、可复查。

域子路径通过包的 exports 声明暴露：

```jsonc
// packages/core/package.json（示意片段）
{
  "exports": {
    "./errors": { "types": "./src/errors/index.ts", "import": "./dist/index.js" },
    "./api":    { "types": "./src/api/index.ts",    "import": "./dist/index.js" }
  }
}
```

根 barrel 兼容保留（还 re-export 全部成员），但脚本额外验证**内部消费侧归零**——留着它只是防漏网，不是让大家继续用。

## 迁移顺序：先拆文件，再划域，最后改消费

954 个成员的大改性能一次成，靠的是顺序刻意保守，每步都可独立验证：

```text
1. 热点拆分：文件先变小、职责变纯（上一篇的内容）
2. 建域：在包内按目录立 15 + 9 个域，每个域配自己的子 barrel
3. 开口子：package.json exports 声明子路径
4. 改消费：codemod 批量把 import 说明符改到子路径
5. 验归零：全仓扫描根 barrel 说明符，内部消费必须为 0
```

任何一步出问题，范围都被锁在那一步内：域划错了消费侧还没动，消费改错了类型检查立刻报，不会出现「全仓一起红、不知道哪步引入的」。

「消费归零」也不是靠 grep 肉眼确认，而是 codemod 的最后一遍扫描直接统计：全仓还存在多少个根说明符 import，数字必须是 0 才算这一批次完成。根 barrel 文件本身继续 re-export 全部成员，是因为它还承担兼容期的保险；但只要内部没人再用，它将来删掉时就不会有任何涟漪。

## 大坑一：所有子路径必须指向同一个 bundle

上面配置有个反直觉的点：每个子路径都指向已有的 dist 单 bundle，而不是各自产出独立 chunk。这是刻意的。

迁移中途我们试过让子路径各自成 chunk，随即踩中类身份问题：`ApiError` 这样的 class 在多个 chunk 里各有一份构造器副本，跨 chunk 抛出的错误做 `error instanceof ApiError` 全部返回 false——异常分支静默失效，而且没有任何编译报错，运行到错误处理路径才会发现判断没进去。

为什么偏偏是 class 出问题：函数和普通对象比较的是结构，class 比较的是构造器身份。tsup / esbuild 按入口切 chunk 时，每个 chunk 会把自己依赖的类各打包一份，于是「同一个类」在运行时有了多个构造器。这个坑在单 bundle 世界里不存在，也不会在类型层暴露任何征兆，只能靠理解打包产物去预判。

所以 import/require 条件刻意统一指向既有单 bundle，只有 types 和 development 条件指向源码：

```jsonc
{
  // 生产：所有子路径共享同一份类身份
  "import": "./dist/index.js",
  "require": "./dist/index.cjs",
  // 只有类型检查与本地开发走源码
  "types": "./src/errors/index.ts",
  "development": "./src/errors/index.ts"
}
```

也就是说，子路径在生产态主要承担「边界表达」而非「物理切包」。域边界先立住，物理拆 chunk 是以后确认不存在跨块类比较之后的事。这条规则在后来语音包独立入口的改造中又被验证了一次：那次是确认共享块只有 esbuild 的导出 helper、不会产生类副本后才放行的。

## 大坑二：vi.mock 按模块说明符拦截，mock 静默失效

第二个坑全部出现在测试里。vitest 的 `vi.mock` 是按**模块说明符字符串**拦截的：以前所有东西都从根 barrel 走，mock 根说明符就能拦住；拆成子路径后，被测代码内部 import 的是 `@app/shared/constants`，测试里若还 mock 旧的根说明符，拦截根本不发生——代码静默落到真模块。

最坑的是它**不报错**：mock 像生效了一样，断言却开始飘，排查时第一反应永远是「被测代码坏了」。规矩因此很简单：

```ts
// 必须和被测代码的 import 说明符逐字一致，写全完整子路径
vi.mock('@app/shared/constants', () => ({ ... }));
```

迁移期这类用例逐个按完整子路径修正。之后我们养成一个自查习惯：mock 的说明符必须在本文件 import 列表里出现——mock 一个根本没人引的说明符，本身就是错误信号。

## 收尾

954 个成员、401 个文件迁移完成，根 barrel 消费归零，测试断言零修改。它和热点拆分放在同一个里程碑做完不是巧合：先让文件变小、职责变纯，域归属就是机械动作；反过来，子路径边界又让「谁也别碰别人 internal」的 ESLint 门禁有了明确的落脚点——门禁和域边界是同一套结构的两面。
