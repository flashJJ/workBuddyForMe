# 封版后的两记闷棍：一个永远发不出去的请求，和一场 28GB 的自杀

v1.1 封版那天，所有该绿的都绿了：14 个 typecheck、lint 零 error、207 个测试文件、e2e、打包冒烟。然后我们在真机上随手抽测了两次，连续翻车。这篇讲这两个**只在打包态、只在真机、只在有真实数据时**才现形的故障。它们是这个零功能版本里信息量最大的两小时。

## 背景：三层防护为什么一起失明

先说为什么三层防护都没挡住：

- **开发态**根本不走故障链路。两个问题都长在「桌面壳 → 内置 Node 服务」的打包注入路径上，开发态服务是直接起的；
- **e2e（Playwright）**窗口存活时间短。一个故障要闲置几十秒才发作，一个故障需要真实密文才触发，e2e 两个条件都不满足；
- **打包冒烟**用的是空数据根。没有历史数据就没有密文可解，请求压根不会发出，链路在冒烟里从未被真正走过一遍。

于是一条「在 Node 22/24 上从未完成过一次 HTTP 往返」的桥，和一个 40 秒能繁殖 700 个线程的启动路径，全绿地进到了封版状态。

---

## 故事一：发不出去的请求

### 现象：供应商列表加载失败

真机打开设置页，供应商列表转圈后报「加载失败」。这个列表要读供应商配置，配置里的密钥是密文——密文由操作系统提供的凭据保管库（Electron 的 safeStorage 封装）解密，而 safeStorage 只能在桌面壳主进程里调用。

内置 Next 服务是独立 Node 进程，拿不到 safeStorage。架构上用一个同步桥补上：服务层的加解密是**同步**接口（调用散布在各处，不可能改成异步），桥在服务进程启动时经 `node --require` 注入，内部派一个 Worker 线程发 HTTP 请求给主进程，调用方线程用 `Atomics.wait` 把异步请求「包装」成同步返回。

### 取证：TCP 能握手，HTTP 永久挂起

最初怀疑是冷启动竞态（主进程还没就绪），但很快排除：

- 端口连得上，**TCP 三次握手成功**——主进程在听；
- 请求发出后**永久挂起**，没有响应、没有超时报错、没有拒绝；
- 主进程侧的请求计数是**零**：一个 HTTP 请求都没完整到达。

握手成功但 HTTP 请求永远完不成，这个组合把矛头从「网络不通」指向了「请求方的 I/O 回调没有机会执行」。

### 根因：wait 冻死的是 worker 自己的事件循环

旧实现里，Worker 的结构是一个「Atomics.wait 命令循环」：父线程把命令投递给 Worker，**Worker 自己发出 fetch 后，在自己线程里 `Atomics.wait` 等结果**。

这是致命的误解。`Atomics.wait` 阻塞的是当前线程的事件循环——而 fetch（undici）的 DNS 解析、TCP 数据到达、响应读取，**全部依赖同一个事件循环上的回调**。于是：

```text
worker 线程：postMessage 拿命令 → 发 fetch → Atomics.wait 阻塞
           → undici 的 I/O 回调永远排不上 → fetch 永远 pending
           → wait 永远等不到通知 → 死锁
```

TCP 握手由内核完成，所以连得上；但 HTTP 请求/响应的用户态推进需要事件循环，它已经被自己冻死了。**这座桥在 Node 22/24 上从来没有真正完成过一次 HTTP 往返。** 开发态直接调本地实现、不过桥；打包冒烟用空数据根、没有密文可解——两侧都恰好绕开了它，直到真机打开一个带着真实供应商配置的设置页。

### 修复：让等待只发生在调用方，worker 永远保持自由

修复把阻塞职责彻底搬回调用方：

```text
worker：parentPort.on('message') 驱动，收到命令 → 异步 fetch → 回写 SAB
        线程内绝不出现 Atomics.wait，事件循环始终自由
调用方：每次尝试 new 一块独立 SharedArrayBuffer，postMessage 下发
        自己 Atomics.wait 等结果——冻的是自己，不欠 worker 任何回调
```

两个配套设计：

- **每次尝试独立 SAB**。超时重试就换一块新缓冲，迟到响应只能写进已经没人读的旧缓冲，从物理上隔离了迟到数据，绝不污染下一次调用；
- **单次 fetch 8 秒超时 × 最多 3 次、总截止 30 秒**。覆盖桌面壳启动繁忙窗口（窗口/桌宠/控制通道初始化时主进程事件循环紧张）。

契约对齐上，decrypt 重试耗尽后**返回 null** 而不是抛出——这正是密钥仓契约：解不出就是「未配置密钥」。服务端再加一层兜底：**单条密文解密失败，降级为空密钥并告警，不再让一条坏密文拖垮整个供应商列表**。encrypt 则相反，保存密钥失败必须抛出让调用方感知。

## 故事二：28GB 的自杀

### 现象：闲置几十秒，整窗黑屏

第二个故障更夸张：打包态应用放着不用，**几十秒后整窗黑屏**，内置 Next 服务子进程没了。看进程数据完全反直觉：**JS 堆只有 5MB，进程内存却涨到 28GB**，退出码 134（V8 OOM 自杀）。

### 取证：高频采样 + 子进程二分 + 假 server 反证

排查手段是纯体力活：用 PowerShell **高频采样进程的内存、句柄数、线程数**，盯着数字起飞的时间窗；同时按「网络 / 子进程」两个方向二分。

关键反证来自一个**假 cipher server**：它接受连接但一个正经响应都不回，只计数。结果应用照样在几十秒内自爆，而**请求计数始终是零**——这证明爆炸与网络、与加解密业务逻辑完全无关，问题在启动路径本身。

采样数字同时给出了线索：故障同期，进程 **30GB+ 内存、7855 个句柄、1929 个线程**。线程数失控，指向 Worker 被无限创建。

### 根因：Worker 默认继承 --require，指数自举

还记得故事一的桥吗——引导脚本通过 `node --require 引导脚本` 注入内置服务进程。引导脚本顶层会 `new Worker` 起桥接 worker。

Node 从 **22.10 起，Worker 默认继承父进程的 `process.execArgv`**——实测这份继承里包含了那个 `--require`。后果是一条指数链：

```text
服务进程启动 → --require 执行引导 → new Worker
  子 worker 继承 --require → 又执行一遍引导 → 又 new Worker
    孙 worker 同样继承 → ……每一代都翻倍
```

纯 node 环境复现：**4 秒繁殖 139 个 worker**；Electron 真机上启动更慢、窗口约 40 秒：**700+ worker、28GB 全花在线程栈上**（所以 JS 堆才 5MB——堆里什么都没有，死的是线程栈内存），随后 V8 OOM，服务子进程 134 退出，窗口失去服务端，黑屏。

开发态没有 `--require` 注入；e2e 窗口活不到它发作——又是那两个盲区。

### 修复：一行显式置空

```js
const worker = new Worker(workerSource, {
  eval: true,
  execArgv: [], // 切断 preload 继承：子 worker 不再执行引导脚本
  workerData: { /* … */ },
});
```

Node ≤20 时 Worker 的 execArgv 默认本就是空数组，所以这行在全版本上都是安全的，不影响任何旧行为。

### 真机复测：85 秒零增长

修复后真机复测，应用空闲 **85 秒**：**158MB 内存 / 290 句柄 / 38 线程，全程零增长**。对照故障同期的 30GB+ / 7855 / 1929，数量级的差就是「健康」与「指数自杀」的差。

## 防回归测试：两个来之不易的教训

这种故障不配上测试，下次 Node 升级还会回来。测试设计本身也踩了两个坑，值得单独记。

**其一，fork 炸弹的判据：用文件计数，别用资源 API。** 测试 spawn 一个带 `--require 引导脚本` 的子进程，并在引导顶层注入一行「向计数文件 append 一行」的探针。健康态引导只在主线程执行一次，文件必须**恰好 1 行**；回归态每个 worker 各执行一次，文件多行。最初想用 `getActiveResourcesInfo()` 数 worker，结果不可靠——递归出来的 worker 退出太快，采样瞬间根本不计入，健康态和炸弹态都数不到东西。文件 append 是持久痕迹，进程死了也留着，可靠得多。

**其二，同步桥的 mock HTTP server 必须放在独立 Worker 线程。** 桥的调用方在自己线程 `Atomics.wait`，如果 mock server 图省事起在同一线程，wait 会把**自己的 mock server 一起冻死**——TCP 照样能握手（内核干的），请求处理却被挂起，现象与真实死锁一模一样。这个测试一度以「fetch 超时」的假象误导排查方向。生产拓扑里 server 与调用方本就跨进程，测试也必须跨线程隔离事件循环，才测得出真行为。

## 方法论：按环境差异矩阵审计「测试全绿」

两个故事本质上是同一个盲点：**我们一直在测开发态的系统，却发布打包态的系统。** 两者不是同一个世界，差异点至少有三张表：

| 差异点 | 开发态 | 打包真机态 |
|---|---|---|
| 启动注入 | 直接起服务，无 `--require` | 引导脚本经 `--require` 注入，Worker 继承链成立 |
| 数据根 | 开发目录，通常无历史密文 | userData 下真实数据根，密文、模型齐全 |
| 凭据通道 | 本地实现直连 | 跨进程同步桥 → 主进程 safeStorage |
| 生命周期 | 随调试启停，秒级 | 可能闲置数十秒以上 |

从此「测试全绿」要过一道审计：**每条测试路径模拟的是哪个环境的差异组合？** 凡是只覆盖「无注入、空数据根、短生命周期」的测试，都不能为打包态背书。这两个热修补的不只是两处代码，更是把环境差异矩阵补成了测试设计的固定输入——封版前的真机抽测也因此从「随手点点」升级为按矩阵取差异项。

零功能版本的最后一课竟然是两个线上级故障，这很讽刺，但也合理：工程债版本把人逼到平时不会走到的链路上，而那里的东西，迟早要还。
