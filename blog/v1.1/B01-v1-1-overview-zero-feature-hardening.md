# v1.1 总览：零新功能的一版，把「靠自觉」全部换成「工具强制」

上个大版本，我们的桌面 AI 应用在一个版本里同时长出了语音、Live2D 形象、桌宠三条能力线。功能上线那天当然高兴，但高兴完回头看代码，速度优先留下的结构债已经很具体：包能不能反向依赖，靠评审时眼睛尖；工具返回 100KB 的 JSON，原样塞进下一轮请求；几个 400 行往上的热点文件全靠行数白名单续命；SSE 事件联合类型在三个地方各手写一遍，漏列一个事件名，编译器一声不吭。

v1.1 我们交付了零个用户可见功能。对，一个都没有。

这篇讲清楚：一个单人项目为什么敢（也需要）花一整个版本做这件事，做了什么，以及我们给自己画的硬边界。

## 为什么是「现在」，而且是「一整个版本」

单人项目没有架构组，不变量只存在一个地方：作者脑子里。代码量小的时候这没问题；但三条能力线并行之后，脑子里能同时盯住的不变量明显不够用了——这不是纪律问题，是容量问题。

债不会因为不看就消失，它以两种方式收利息：每次改动多花的定位时间，和「不敢动」的区域越来越大。越往后还，利息越高。所以我们决定停一个版本，专门回答一个问题：

> 当代码规模继续增长时，哪些不变量应该由工具强制，而不是靠人记住？

最典型的是 SSE 事件。core 包有一份事件联合，web 应用有一份，wire 边界还有一份窄化，三份全靠人手保持同步。加一个事件要记得改三个地方；漏改其中任何一处，类型不报错、编译不报错，只有运行到那条事件流时才发现前端收到了不认识的事件。这类问题的共同点是：犯错的那一刻没有任何反馈，等反馈出现时，犯错的上下文早就丢了。

## 四类债，和这个版本的七项回答

| v1.0 留下的债 | v1.1 的回答 |
|---|---|
| 跨层依赖靠自觉，违例只能评审时肉眼抓 | ESLint 方向 zone 加 internal 全配对门禁，warn 观察一个完整版本后翻 error 进 CI |
| 100KB 工具结果原样回灌，和记忆、对话正文抢上下文窗口 | 中央压缩层：模型只见预算视图，trace/SSE/UI 保留完整 output |
| 28 个超 260 行热点靠白名单续命，最长 483 行 | 纯函数/类型/子组件/夹具外迁加热点拆分，28 → 1，白名单仅余自动生成类 |
| SSE 事件三方手写联合，漏列无编译错误 | 条件类型从载荷真源机械派生，配穷尽 switch 与运行时镜像 |
| eval 只有一个单脚本，断言和接线揉在一起 | eval 平台五件库加 3 个 golden set，每个都带反向验证 |
| 覆盖率只有一条 70% 全局线 | 分级门禁：core 全局 70%、压缩模块 95%；web 三个关键域 60% |
| 语音运行时长在 web 应用层，core 包无法复用 | VoiceRuntime 全量下沉 core/voice 独立子路径，web 只留 HMR 薄壳与 SSE 桥 |

## 核心哲学：强制力分层

关键不是「多上点工具」，而是让每种不变量归最合适的强制层：

- **依赖方向归 ESLint**——import 写出来的瞬间就能报错，不用等编译、不用等评审；
- **事件契约归 TypeScript**——联合类型不许手写，用条件类型从载荷真源机械派生，再配穷尽 switch，漏列就是编译错误；
- **「不能漏列」归运行时镜像加变异测试**——类型管不到的运行时枚举，用「删掉一项映射，测试立刻变红」来证明清单完整；
- **预算约束归纯函数出口硬保证**——token 预算不靠每段自觉估算，而是在压缩器出口统一收口，超了就是函数返回超了，没有第二种解释。

共同特征是：每条不变量都有一个「不依赖人记得」的执行点，而且规则本身要被反向验证过。一条永远不会触发的 lint 比没有规则更危险，因为它制造了安全感。

注意表里七项回答不是七件孤立的家务事。barrel 域子路径化让 internal 边界有处可落，分层门禁才有意义；压缩层是纯函数，分级覆盖率才知道该把 95% 的高门槛押在哪里；SSE 契约派生又反过来让 eval 录制的事件帧可以逐帧断言。它们是一套互相咬合的齿轮，这也是为什么得用一整个版本、按里程碑顺序做，而不能零碎掺在功能迭代里。

## 硬边界：什么坚决不做

零功能版本最怕顺手「改好看一点」。我们提前划了四条线：

- **零产品行为变更**：HTTP/SSE 线上协议、`{success, data}` 响应信封、UI 交互一律不动，改动只发生在内部结构与类型层；
- **不引入 DI 容器、不搬装饰器框架**——强制力用现有工具链解决，不新增架构范式；
- **不做视觉层重构**——前端只做同目录内抽子组件，不换样式体系；
- **每个里程碑独立提交批次，任一关卡不过，整批 revert**——不许带债进入下一个里程碑。

## 重构而不是重写：证据是什么

「内部重构」最容易滑成「顺手重写」。我们给自己定了三种取证方式，每搬一次家都要拿得出证据：

- **测试跟着搬家，断言一行不改**。语音运行时下沉、桌宠拆分、barrel 迁移，全都要求原有测试零修改通过——行为变没变，测试比人诚实；
- **协议层用契约测试钉死**。SSE 事件从载荷真源派生出唯一类型，再做变异验证：删掉一项映射，测试必须立刻变红，而不是相信「类型应该没问题」；
- **新行为用反向验证收尾**。压缩层的 golden set 在回退被测代码后必须按预期失败，证明断言本身不是恒真的废话。

于是到版本收尾，对账可以简化成一句话：协议零变更、信封零变更、UI 零变更；变的只是这些东西在仓库里的组织方式，以及「越界」从一个评审动作变成了一个退出码。

## 数字

- 相对上个大版本基线：变更 496 个文件，+7741 / -4298 行，增量主要来自测试与 eval 资产；
- 全仓 207 个测试文件全绿（core 包 554 个用例、web 应用 278 个用例），关键迁移全部做到「测试断言零修改」；
- 新增运行时依赖 **0 个**，数据库迁移 **0 个**——纯内部重构，没有 schema 和契约变更；
- 唯一的 dev 侧变化，是启用了仓库里既有覆盖率工具的分级门禁；
- 日常关卡 `pnpm check` 全绿：14 个工程的 typecheck 全过、lint 0 error、行数检查通过。

## 接下来

前面五篇是这条主线，逐篇对应：

1. 本篇总览；
2. **ESLint 边界门禁**——方向 zone、internal 全配对矩阵，以及两个规则语义坑；
