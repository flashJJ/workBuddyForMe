# 召回解释：只留元数据的内存环形缓冲

「为什么这条记忆出现在上下文里？」这个问题，用户问过，开发也问过。

一个直觉方案是把召回结果落库，做历史查询。但记忆解释有一个特殊约束：它最容易泄露隐私。只要把 query 原文或记忆正文写进解释表，隐私边界就破了。

这一版选择另一条路：解释只保留元数据，只存在内存里。

## 一、解释需要回答什么

真正需要回答的不是「召回了什么内容」，而是：

- 这一轮用了什么场景？
- 候选多少、入选多少？
- 有多少条因为分数、预算、冲突被丢弃？
- 各通道分别贡献了几条？
- 冲突裁决选了谁、理由是什么？
- 这次召回花了多久？

这些都不需要正文。把它们结构化，已经足够解释「为什么是这几条」。

## 二、轨迹结构

```ts
interface RecallTrace {
  scene: 'chat' | 'task' | 'intent-forget';
  at: string;
  queryLength: number;      // 只记长度，不记原文
  durationMs: number;
  candidates: number;
  selected: number;
  dropped: { byScore: number; byBudget: number; byConflict: number };
  channels: { semantic: number; lexical: number; pinned: number; neighbor: number };
  resolutions: Array<{ memoryId: string; reason: ConflictReason }>;
}
```

`queryLength` 是刻意的设计：知道查询多长有助于判断延迟与候选规模，但原文没有解释价值，只会带来风险。

## 三、为什么不落库

三个理由：

1. **零迁移**：不新增表，不新增列；
2. **隐私**：内存数据随进程结束消失，不进入备份、不被导出；
3. **成本**：解释是诊断功能，不需要历史归档，保留最近几次即可。

环形缓冲只保留最近 5 次召回。重启后为空，这是可接受的：解释面板服务于「刚刚发生了什么」，不是审计账本。

## 四、为什么不是越多越好

保留更多次数听起来更完整，但会带来两个问题：

- 内存常驻数据变多，且没有清理策略；
- 面板变成「历史列表」，用户要自己找哪一次，反而更难用。

5 次刚好覆盖「我刚才试了几种问法」的调试场景。超过这个范围，用户真正需要的是审计或日志，而不是召回解释。

## 五、接口与界面都保持只读

- `GET /api/memories/explain?limit=5`，limit 限制在 1 到 5；
- 设置页「最近召回」只展示白名单字段；
- 没有开关、没有编辑、没有导出。

只读意味着它不会成为新的写入路径，也不会改变召回行为。解释面板失败不影响对话——它只是一个观察窗口。

## 六、测试怎么断言隐私

单测直接检查序列化结果：

```ts
expect(JSON.stringify(traces)).not.toContain('用户喜欢猫');
expect(Object.keys(traces[0])).not.toContain('query');
expect(Object.keys(traces[0])).not.toContain('content');
```

同时断言环形缓冲只保留 5 条、`queryLength` 与输入一致。隐私约束用断言表达，比写在文档里更可靠。

## 七、这个设计的边界

- 重启后看不到上一次召回；
- 只覆盖记忆召回，不覆盖知识检索与工具调用；
- 只能看到数量与理由，看不到具体候选内容。

这些限制是有意的。解释面板的定位是「让召回可讨论」，不是「让所有上下文可回放」。把范围收窄，才能在不破隐私边界的前提下长期保留这个能力。
