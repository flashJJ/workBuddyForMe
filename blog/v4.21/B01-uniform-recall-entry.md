# 一个入口：把散落的记忆召回收成场景预算表

长期记忆最容易被低估的不是「存」，而是「取」。同一套记忆，在不同调用点有不同取法：有的只看向量相似度，有的只看关键词，有的额外塞几条置顶。功能能用，但结果无法解释，也无法复算。

这一版做的第一件事，是把召回收成一个入口。

## 一、问题：召回逻辑散在调用点

在一个本地优先的桌面 AI 应用里，记忆召回至少会被三类场景调用：

1. 回合前装配上下文，最多注入几条；
2. 任务执行前取任务相关记忆；
3. 「忘掉刚才那条」这类意图，需要定位目标，但不需要注入。

过去这些调用点各自传参：候选数量、是否含置顶、token 上限都不同。结果就是同一句提问，从聊天入口和任务入口召回的结果可能不一样，出了问题也不知道该改哪一处。

## 二、做法：请求对象 + 场景预设

入口改成一个请求对象：

```ts
recall({
  query,
  scene: 'chat',        // chat | task | intent-forget
  budget: { maxItems: 3, maxTokens: 600 },
  assistantId,
  conversationId,
  signal,
});
```

`scene` 决定默认预算，`budget` 只做覆盖，不再让每个调用点自己拼参数：

| 场景 | 条数 | token | 用途 |
|---|---|---|---|
| `chat` | 3 | 600 | 回合前召回（默认） |
| `task` | 3 | 600 | 任务上下文 |
| `intent-forget` | 5 | 750 | 定位要遗忘的目标，不注入 |

场景是语义，预算是约束。把两者放在一起，调用方只需要回答「我在什么场景」，而不是「我要几条、多少 token」。

## 三、预算为什么是双上限

只限条数不够：三条很长的记忆一样能把上下文撑爆。只限 token 也不够：几十条短记忆会让提示词碎片化。

所以预算是「条数 + token」双上限。token 不引入 tokenizer，直接用字符数近似：

```ts
estimateTokens = (content) => Math.ceil(content.length / 2);
```

中英混排下这个近似会偏保守，但它换来三个好处：无额外依赖、计算稳定、同一输入永远得到同一预算结果。对本地应用来说，「可复算」比「精确」更重要。

## 四、裁剪必须稳定

超预算时的丢弃规则：

1. 按融合分升序丢弃；
2. 同分按 id 升序，保证稳定排序。

置顶条目不参与 token 裁剪——用户明确固定过的记忆，不应该因为这一轮上下文紧张就被静默丢掉；但它仍受条数上限与置顶数量上限约束，避免置顶无限膨胀。

空 query 直接返回空数组，不写召回统计。这一条看似琐碎，实际是统计可信度的前提：没有查询就没有召回，不应污染命中率。

## 五、失败不是阻塞

召回失败不影响对话。入口内部沿用「告警但不抛出」的策略：拿不到向量就降级到纯关键词，通道异常就返回已得到的候选。记忆是增强项，不是对话的前置条件。

## 六、验收关注什么

- 同一输入、同一场景，召回集合与顺序可复算；
- 置顶不会被 token 预算裁掉；
- 空查询不写统计；
- 无嵌入模型时，语义权重并入关键词，结果仍稳定。

把入口收成一处之后，后面才有条件谈冲突裁决、治理动作和解释——因为它们都挂在这条管线上，而不是散在各处。
