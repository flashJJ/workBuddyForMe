# v4.21 复盘：从「能召回」到「可解释、可治理」

记忆系统做到「能存、能取」并不难，难的是让用户敢用：为什么是这条？我能不能改？改了会不会丢？

这一版的主题就是回答这三个问题，而不是继续堆召回通道。

## 一、这一版真正新增的东西

| 方向 | 交付 |
|---|---|
| 入口 | `recall(request)` 单一入口，`chat` / `task` / `intent-forget` 三套场景预算 |
| 预算 | 条数 + token 双上限，字符近似，置顶不计 token，裁剪稳定可复算 |
| 裁决 | 同主体只注入 1 条，固定 > 新鲜度 > 置信度 > 稳定顺序，理由可枚举 |
| 治理 | 固定、升降权、合并、归档、恢复，全部 `actor='user'` 且幂等 |
| 解释 | 最近 5 次召回轨迹，只在内存，只含元数据 |
| 导出 | Markdown / JSON，白名单字段，用户主动触发 |
| 验证 | 定向 E2E、离线回放对比、全量门禁 |

## 二、三个做对了的选择

### 1. 先收入口，再谈治理

如果召回仍然散在调用点，治理动作就没有统一的生效位置。固定一条记忆后，聊天入口生效了、任务入口没生效，用户会立刻失去信任。

所以顺序是：先做统一入口与预算，再做冲突裁决，最后才接治理动作。每一步都能独立验收，也都能回退。

### 2. 幂等写进审计，而不是写在接口说明里

治理动作全部先算目标值：目标值不变就不写事件。这让「重复点击不产生重复审计」成为一个可测试的事实，而不是一句约定。

统计也从同一份事件聚合，在线与轮转后都能复算。审计、统计、界面三者同源，才不会出现「统计有、审计查不到」的裂缝。

### 3. 解释与导出用两套隐私策略

- 解释是系统自动展示，只给元数据，连 query 原文都不留；
- 导出是用户主动动作，可以包含正文，但字段用白名单。

两个功能都碰记忆，却用了不同边界。判断标准不是「哪个更安全」，而是「数据因为谁的意志离开系统」。

## 三、一次误判：E2E 失败不等于数据没写入

定向 E2E 第一版失败时，页面上的记忆列表是空的。第一反应是「接口没写进库」。

实际排查后发现：写入是成功的，问题在页面查询被可见性门控拦住了。设置页很长，面板进入视口才触发查询；深链的平滑滚动在测试环境并不可靠，于是列表一直是初始空态。

修正方式不是改产品，而是让测试先显式把面板滚进视口，并加一条服务端列表断言来区分「没写入」与「没查询」。这件事的教训是：

- 先确认数据层事实，再怀疑 UI；
- 懒加载与可见性门控要在 E2E 里显式触发；
- 失败快照只能证明「当时页面是这样」，不能证明「数据不存在」。

## 四、两个刻意没做的事

**合并生成摘要**：听起来很智能，但需要一次模型调用，失败路径变长，摘要还可能丢信息。这一版只做「保留目标、归档来源」，把融合留给未来。

**解释落库**：落库意味着新表、新迁移、新隐私面。最近 5 次的诊断需求，用内存环形缓冲就够。重启丢失是可接受的代价。

克制不是保守，而是把复杂度留在能验收的地方。

## 五、验证方式

- 门禁：类型、lint、行数、目录、循环依赖、ASCII、资产、surface、E2E 隔离；
- 单测：治理幂等、冲突裁决、预算裁剪、轨迹隐私断言；
- 定向 E2E：固定 / 取消固定、降权、合并归档、导出、轨迹面板；
- 回放：16 条 golden 用例 hit@3 与基线一致，命中集合逐条相同；
- 全量：`check` 与 `verify:local` 全绿。

验证的重点不是「功能跑通」，而是「边界没破」：置顶没被裁、落选没被删、轨迹没正文、导出没路径。

- 评估把解释轨迹写成不含正文的本地诊断文件的收益；
- Controller Pipeline / DAG 并行、视觉巡检 L2/L3 继续留待后续；
- 记忆社区聚类与主题簇摘要维持长期挂账。

「记得住」是存储问题，「管得住」是信任问题。这一版把后者补上了半程，剩下的交给真实使用数据来判断。
