# 回放对比：策略换了，命中集合有没有变

召回策略的改动有一个隐蔽风险：单测全绿，线上体感却变差。

原因是单测通常只断言「某条记忆能被召回」，而真实的召回是一个排序、裁剪、裁决的复合过程。权重调 0.05、候选池缩小 5 条、冲突顺序换一层，单测都不会响，但命中集合已经变了。

这一版用离线回放把这件事变成可对比的。

## 一、回放不启动服务

回放脚本不启动 Web 服务，不调用对话模型，也不调用 LLM 评委。它直接在内存数据库上复用召回管线：

```text
读取 golden 种子 → 写入内存库 → 逐条 recall(question)
  → 取 top-3 → 关键词命中判定 → 写报告
```

没有嵌入模型时自动走纯关键词通道，报告会标注 `channel=keyword`。这让回放可以在任何机器上稳定重复，不受模型供应商影响。

## 二、报告要留下「命中集合」

只记录一个总命中率是不够的。两次运行都命中 14/16，也可能是不同的 14 条。

所以报告保留每条用例的细节：

```json
{
  "id": "recall-city",
  "question": "我现在住在哪个城市？",
  "hit": true,
  "topContents": ["用户住在杭州", "..."],
  "topReasons": ["keyword", "keyword"],
  "elapsedMs": 2.61
}
```

`topContents` 用来对比命中集合，`topReasons` 用来看通道构成，`elapsedMs` 只做同机噪声参考。

## 三、和上一版怎么比

脚本在写入前先读取同路径的上一份报告，输出三项差值：

- hit@3 变化；
- 零召回率变化；
- 平均召回耗时变化。

这一版的结果：

| 指标 | 上一版 | 本版 |
|---|---|---|
| hit@3 | 0.875 | 0.875 |
| 零召回率 | 0 | 0 |
| 关系邻居命中 | 4/4 | 4/4 |
| 平均召回 | 0.48ms | 1.46ms |

命中集合逐条一致，耗时差异在毫秒级，属于机器噪声。结论明确：这一版改了召回结构与预算，但没有改变离线 golden 集上的结果。

## 四、为什么不做成强制门禁

回放依赖固定的 golden 集与纯关键词通道。它擅长发现「结构性回归」，不擅长判断「语义质量提升」。

如果把它设成硬门禁，会逼着每次改动都维持同一组数字，反而阻碍合理调整。所以它现在是：

- 每次改动后手动运行，结果写入固定路径；
- 报告与上一版对比，差值写进控制台与 JSON；
- 退出码恒为 0（读取失败除外）。

它的价值在于「让变化可见」，而不是「阻止变化」。

## 五、性能数字要克制

回放报告里也有耗时，但只做同机相对比较。一次运行平均 1.46ms，不代表线上召回就是这个量级——线上还要叠加向量检索、数据库 IO 与提示词装配。

同理，max 耗时 4.43ms 可能只是首次 JIT 预热。报告保留这些数字，是为了发现数量级变化，而不是承诺 SLA。

## 六、这套方法能复用到哪

任何「有输入、有排序、有裁剪」的本地管线都适用：

- 知识检索的 top-k 变化；
- 工具选择的候选集变化；
- 上下文装配的截断顺序变化。

共同点是：不要只断言「有没有」，要保存「这一次到底有什么」。命中集合是回放的最小事实单位。

策略变化不可怕，可怕的是变化没有被看见。回放做的事，就是把「感觉变了」变成一份可以逐条对比的报告。
