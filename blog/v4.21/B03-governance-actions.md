# 固定、降权、合并：把治理做成幂等审计动作

记忆系统早期只有两个操作：写入和删除。用户面对一条不想要的记忆，要么忍，要么删。但真实需求往往在中间：这条别删，但别再优先；这两条其实是一件事，合并；这条很重要，永远带上。

这一版补上了中间地带，但刻意没加新表、没加新列。

## 一、动作表

| 动作 | 语义 | 审计 action |
|---|---|---|
| 固定 | `pinned=true` | `pin` |
| 取消固定 | `pinned=false` | `unpin` |
| 降权 | `importance` 减 0.1 | `downweight` |
| 升权 | `importance` 加 0.1 | `upweight` |
| 合并 | 保留目标，归档来源 | `merge` |
| 归档 | `status='archived'` | `archive` |

所有动作复用现有字段：`pinned`、`importance`、`status`、`version`。数据库零迁移。

## 二、幂等不是「再执行一次不报错」

幂等的最低标准是「重复调用结果不变」，但对审计系统还不够：重复点击不应该产生两条相同的审计记录。

所以每个动作都先判断目标值：

- 已经固定，再点固定：不写 `pin`；
- `importance` 已经是 0，再点降权：不写 `downweight`；
- 来源已经是归档状态，再合并一次：不重复计 `mergedFrom`。

实现上，先算「这次操作真正要改的字段」，如果没有任何变化，直接返回当前记录，不落审计。这样统计口径才可信。

## 三、硬约束要拒绝，而不是静默修正

`constraint` 类记忆（例如「用户对花生过敏」）默认固定。取消固定会把它从每次召回中降级，风险高于普通记忆。

这一版选择显式拒绝：

- 服务层抛治理错误 `constraint_pinned`；
- API 映射为 409；
- 设置页内联提示「硬约束不支持取消固定，请归档或删除」。

为什么不直接允许？因为这类记忆的价值就在于「永远在」。如果用户真的不再需要，归档比取消固定更清晰，也留下完整审计。

## 四、合并只归档，不做摘要

合并的语义容易做重：调一次模型，把两条记忆总结成一条新记忆。听起来美好，但会带来三个问题：

1. 需要一次模型调用，失败路径变长；
2. 摘要可能丢信息，且不可逆；
3. 新记忆的来源无法对应到原记录。

这一版只做最小语义：保留目标，来源归档，审计 after 快照记录 `mergedFrom` 的 id 列表。不复制正文，不生成摘要。用户看到的是「来源已归档」，仍可查询原文。

合并不是去重，也不是知识融合。它是一个收纳动作。

## 五、审计与统计同源

统计卡新增三项：当前固定数、累计降权数、累计合并数。

后两项不新建计数表，而是从 `memory_events` 聚合；事件轮转后，再从轮转聚合表累加。这样：

- 在线事件与历史轮转都能计入；
- 不需要额外的写路径；
- 统计口径与审计口径一致，不会出现「统计有、审计查不到」。

## 六、前端只做三件事

设置页对治理动作的接线保持克制：

1. 按钮直接对应动作，不引入模式切换；
2. 成功后失效列表与统计查询；
3. 失败内联提示，不弹全局错误、不阻断其他操作。

治理是低频操作，重要的是「点了会发生什么」足够明确，而不是动画和流程。

## 七、验证

- 重复固定两次，审计只有一条 `pin`；
- 降权到 0 后再降，不新增审计；
- 取消固定后重新固定，回到原状态；
- 合并后来源 `archived`，再次合并不重复计数；
- 硬约束取消固定返回 409，状态不变。

治理动作做小、做幂等、留审计，比做多更重要。用户信任记忆系统，靠的是「我改过的它记得」，而不是功能列表。
