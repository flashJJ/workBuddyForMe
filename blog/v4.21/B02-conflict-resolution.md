# 同主体多值：只注入一条，并给出理由

「用户住在杭州」和「用户住在上海」同时存在时，模型应该看到哪一条？

如果两条都注入，回答会自相矛盾；如果按写入顺序取第一条，用户搬家后就会一直拿到旧地址。更糟的是，用户无法知道系统为什么选了这条。

这一版把这个问题收成一个明确的裁决过程。

## 一、先定义什么算冲突

不是所有记忆都参与裁决。候选必须同时满足：

- 有相同的 `subjectKey`（例如 `city`、`job`、`pet`）；
- 作用域完全相同（全局对全局，助手对助手）；
- 状态为 `active`，且未过期。

没有 `subjectKey` 的记忆不参与合并，按普通候选参与预算裁剪。这个边界的意义是：裁决只处理「同一件事的多个值」，不猜测两段自然语言是不是在说同一件事。

## 二、裁决顺序

```text
用户固定 > 新鲜度（lastConfirmedAt ?? createdAt，降序）
        > 置信度（confidence，降序）
        > 稳定顺序（version 降序，再 id 降序）
```

四层依次比较，先命中先胜：

1. **用户固定**：用户手动钉住的记忆优先。这是显式意志，高于任何自动推断；
2. **新鲜度**：最近被确认或创建的值优先，解决「搬家后还用旧地址」；
3. **置信度**：同一时间写入的两条，信更高的那条；
4. **稳定顺序**：仍然相同则按版本与 id 排序，保证结果可复算。

最后一层不是为了选出「更对」的那条，而是为了同一输入每次得到同一结果。没有稳定顺序，裁决就不可测试。

## 三、只注入，不删除

裁决结果只影响「这一轮注入什么」：

- 每个主体最多注入 1 条；
- 落选值保留在库中，设置页仍可查询；
- 落选值不进入提示词。

这一点很重要。冲突裁决不是数据清洗，它不应该悄悄删掉用户的记忆。用户可能确实在两个城市都有住址，系统只是在这一轮选择一个更可能相关的值。

## 四、理由要能落到界面

每次裁决都记录：

```text
memoryId + reason
reason: pinned | fresher | higher-confidence | stable-order
```

理由不进提示词，只进解释面板。用户看到的是「这轮为什么选它」，而不是一段模型生成的解释。理由枚举有限、可断言，也就意味着它可以被测试覆盖。

## 五、几个容易踩的坑

**置顶与新鲜度冲突**：置顶优先。否则用户固定过的值会被一条刚写入的自动记忆顶掉，治理动作失去意义。

**时间字段缺失**：用 `lastConfirmedAt`，没有就退回 `createdAt`；两者都无效时按稳定顺序处理，不抛错。

**同主体但不同助手**：作用域不同，不参与同一轮裁决。助手 A 的城市记忆不应该影响助手 B。

**裁决与预算的顺序**：先裁决，再按预算裁剪。否则可能出现「两个值都进了候选，裁剪时丢掉胜者」的荒谬结果。

## 六、怎么验证

golden 用例覆盖五类场景：同主体冲突、过期、固定、降权、合并。断言不看自然语言，只看：

- 注入集合里同一主体只有一条；
- 胜者 id 与理由符合顺序表；
- 落选值仍能通过列表接口查到。

把「为什么是这条」变成结构化的理由，是这一版最重要的变化。它让记忆从「黑盒召回」变成「可讨论的决策」。
