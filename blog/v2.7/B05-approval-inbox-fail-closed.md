# 审批默认拒绝：一次性决策与失败关闭的收件箱

审批是这个产品里唯一一个必须由人来做完的动作。工具要写文件、工作流要人审核、协作要授权一次高风险调用——这些都不是模型能自己决定的。

早期实现里，审批分散在各处：对话页有工具确认弹窗，工作流页有人工节点表单，协作有自己的确认入口。用户要处理审批，得先知道它出现在哪个页面。这次把它们收进一个收件箱，并且把「没人处理时怎么办」写成了硬规则。

## 一、三处入口，一种信封

| 入口 | 触发点 | 来源标记 |
|---|---|---|
| 聊天与任务的工具确认 | 权限门控判定需要人工介入时 | `tool` |
| 工作流工具节点 | 节点要求工具授权时 | `flow` |
| 工作流人工节点 | 节点要求人填写或审核时 | `flow` |

三者的差别被压进同一个信封：来源、标题、工具名、权限级别、参数摘要、关联运行、关联会话、创建时间、过期时间、站内深链。消费者不需要知道它是哪一种，只需要知道「谁在等、等什么、点哪里」。

信封里的两个字段值得单独说：

- **参数摘要**是给用户判断用的，不是给模型用的。它是截断后的可读片段，不含完整参数，更不含密钥。
- **深链**只允许站内相对路径。审批项永远不该把用户带到外部地址。

## 二、注册表：注册、决策、摘除

统一注册表只暴露四个动作：

```ts
register(input, onResolve) => { id, remove }   // 登记一笔待办
resolve(id, { action, values? }) => boolean    // 一次性决策
remove(id)                                     // 底层结束时摘除
list()                                         // 按创建时间升序
```

`onResolve` 是注册表与原对话框之间的唯一联系。注册表不关心「允许之后运行怎么继续」，它只把决策原样交回去；底层拿到决策后，去唤醒它自己的等待者。

这样做的好处是：审批中心可以随时上线或下线，而运行侧完全不需要知道它的存在。注册表缺失时，运行仍走原来的弹窗。

## 三、决策即摘除

「一次性」在这里是字面意思：

- 决策成功时先从表里删除，再调用回调，最后通知订阅者；
- 之后再决策同一个 ID 会返回 `false`；
- 同一 ID 被重复注册时，旧条目的回调会先收到一次拒绝，然后才被替换。

最后这条规则防的是一种真实缺陷：同一个确认被两处同时等待，用户点了一次「允许」，两个等待者都以为自己也该继续，于是同一笔操作被执行两次。**先拒绝旧的，再让新的接管**，比事后去重可靠。

## 四、超时、断线和结束时，一律拒绝

这是整篇最重要的一条：**失败关闭（fail-closed）。**

底层确认有超时，连接会断，运行会被用户取消。这三种情况下，注册表不会「等一等再说」，而是立刻摘除条目并让等待方收到拒绝。拒绝的理由会被写成一句可读的话回给模型，而不是一个空异常：

- 超时：告知用户授权超时，本次调用未执行；
- 断线：告知授权通道中断，需重新发起；
- 运行结束：直接视为未授权。

为什么要这么严？因为审批的本质是「授权」。一次没有明确授权的写操作，风险不是「多跑了一步」，而是「用户从没同意过」。默认放行等于把「没人看」当成「有人同意」。

在本地优先的产品里，这个区别尤其重要：数据不出机，但机器上的文件、命令、凭据都是真实的。

## 五、审批中心：列表、来源、打开

页面本身很朴素——列表、来源徽标、参数摘要、关联运行、允许、拒绝、打开来源。

三个细节值得记：

1. **空态是一等公民。** 「没有待处理的审批」是常态，不是错误，所以它有自己的文案与测试。
2. **决策后立即失效。** 决策成功后刷新列表；决策失败（比如条目已结束）提示「审批可能已结束」，而不是把用户留在一个永远不会成功的按钮上。
3. **打开来源是只读导航。** 它把用户带到运行所在页面，但不会替用户做任何决定。看清楚再决定，比一键处理更重要。

## 六、为什么审批不能「默认放行」

把这个问题摊开，有三个层次：

| 层次 | 默认放行的后果 |
|---|---|
| 安全 | 未经同意的写操作被执行，且用户无从追溯 |
| 信任 | 用户一旦发现「没点也算同意」，之后所有审批都会变成无脑点允许 |
| 产品 | 一个会自动同意高风险操作的产品，不配被称为「你自己掌控的助手」 |

第二层最容易被低估。审批的价值不只是「拦住这一次」，而是「让用户相信每一次都拦得住」。一次静默放行就会摧毁这种信任，而信任重建的成本远高于多弹一次窗。

## 七、这次的边界

- **「以后都允许」的策略仍留在原对话框。** 收件箱只做一次性决策；持久授权涉及另一个风险等级，不在这次范围。
- **桌面控制授权没有并入。** 那条链路的权限面与工具调用不同，留在后续单独处理。
- **不做审批历史。** 已处理的审批直接消失，不留审计记录；审计属于事件日志的职责。
- **不做批量处理。** 一次性决策加上批量按钮，等于把「逐个确认」变成「一次全同意」，与失败关闭的精神冲突。

## 八、可测性从哪来

注册表是纯结构，不碰数据库与网络，所以测试可以直接断言四件事：

- 注册后能列出，决策会调用回调并移除；
- 摘除之后不可再决策；
- 重复 ID 会先拒绝旧条目；
- 变更会通知订阅者。

四条用例对应四个真实风险：僵尸审批、二次决策、重复等待、界面不刷新。数量不多，但每一条都对应线上会疼的地方。
