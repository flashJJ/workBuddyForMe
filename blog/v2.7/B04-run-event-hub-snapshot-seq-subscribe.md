# 进程内那一个 Hub：快照、序号与订阅

前面两篇讲的是「怎么算」，这一篇讲「放在哪、怎么给」。

工作信号是高频、短命、只关心当下的数据。这三条特征决定了它不该进数据库，而应该待在一个进程内的单例里。这个单例就是 Hub。

## 一、Hub 的职责只有五条

| 职责 | 说明 |
|---|---|
| 接收 | 三条链路的事件各自调用对应的摄入方法 |
| 存储 | 以「来源 + 运行 ID」为键，只保留每个运行的最新信号 |
| 成帧 | 每次变化构造一份完整快照，序号加一 |
| 广播 | 向所有订阅者推送新快照；建连时先给当前快照 |
| 清理 | 定时剔除过期终态；整体清空用于测试与退出 |

它不做业务判断，不做持久化，也不做权限。它就是一个「当前视图」的持有者。

## 二、推快照而不是推增量

大多数实时系统推增量事件，Hub 推完整快照。原因很实际：

- 消费方是桌宠和审批页，它们只需要「现在是什么样」，不需要「怎么变成这样」；
- 增量需要客户端维护状态合并逻辑，一旦漏帧就会长期漂移；快照是自愈的，下一帧就对；
- 信号总量很小（同时在跑的运行通常个位数），整包推送的成本可以忽略。

快照的形状是固定的四段：

```ts
interface WorkSignalSnapshot {
  seq: number;              // 每次变更递增
  generatedAt: string;      // 生成时间
  signals: WorkSignal[];    // 已按优先级排序
  approvals: WorkApproval[];// 待处理审批
}
```

排序放在服务端，而不是让每个客户端各排一遍。这样「谁是主运行」只有一个答案。

## 三、seq 的作用

`seq` 每次快照变更递增。它不承担「断点续传」的职责，只做两件事：

1. **让客户端能判断新旧。** 网络抖动时可能收到乱序帧，比较 `seq` 就能丢弃旧帧。
2. **让测试能断言「有没有发生变化」。** 「订阅后收到一帧，且序号大于建连时的值」是一个稳定可测的性质。

真正的续传靠「重连后拿到的当前快照」，而不是补发历史帧。这也是为什么订阅语义是「只收订阅之后的新快照」，而不是「回放最近 N 条」。

## 四、订阅：先首帧，再增量

订阅接口返回一个异步可迭代对象。调用方的顺序固定为：先取一次当前快照作为首帧，再进入增量循环。流式路由就是这么写的：

```ts
send(hub.snapshot());            // 首帧：建连时的事实
while (!cancelled) {
  const next = await iterator.next(); // 之后：有变化才推
  send(next.value);
}
```

为什么不交给 Hub 在订阅时自动补一帧？因为两件事的时机不同：首帧是「建连那一刻的事实」，增量是「建连之后的变化」。混在一起，客户端会在重连时收到重复帧，还得自己去重。

底层用一个固定容量的环形缓冲（50 帧）承接突发。它不是为回放准备的，而是为了在消费端短暂阻塞时不丢最新变化——满了就丢最旧的，因为旧快照本来就没有价值。

## 五、页面和桌宠是各自独立的订阅者

这是整个设计里最关键的一条：**桌宠不依赖主窗是否打开。**

主窗里的页面可以订阅，也可以不订阅；桌宠窗口有自己的连接，自己拿快照，自己聚合。主窗最小化、切页、甚至关掉，桌宠的工作态照常。

反过来也成立：桌宠关掉不影响页面。两个消费者之间没有共享状态，只有一个共同的上游。

代价是连接数变多（主窗一个、桌宠一个），但每条连接推送的是同一份快照，服务端的成本是「多一次序列化」，而不是「多一套逻辑」。

## 六、SSE 断线与重连

SSE 不是可靠通道。Hub 不做补发，客户端必须自己处理断线：

- 连接失败或流中断时，客户端把状态标记为未连接，桌宠据此显示断开态；
- 3 秒后自动重连，重连成功后收到的首帧就是最新快照，直接覆盖本地状态；
- 重连期间不缓存增量，因为增量本来就不存在。

这带来一个重要的产品语义：**桌宠显示断开不是故障，而是事实。** 它比「假装还在工作」诚实。

## 七、为什么不把这些高频状态落库

三个成本，按量级排序：

1. **写入放大。** 一次任务循环几十帧，一次工作流可能上百帧。每帧一行，数据库的写入量与清理压力都会跟着涨，而用户能感知的收益是零。
2. **清理成本。** 短期数据必须配保留策略，否则数据库会被「昨天的工作状态」撑大。有了策略，就要有清理任务、失败重试、边界测试。
3. **真源冲突。** 一旦落库，就会有人问「信号表和运行表不一致时信谁」。这个问题没有好答案，只能靠「不落库」从源头消掉。

判断标准还是那句：**会不会被用于事后重建？** 会，就属于事件日志；不会，就留在内存。

## 八、与事件日志的分界

这次不建事件表，也不打算把 Hub 当成半个日志。两者的分工写清楚：

| 维度 | 工作信号 Hub | 事件日志（下一步） |
|---|---|---|
| 时间范围 | 当下 | 历史 |
| 是否落库 | 否 | 是 |
| 是否可回放 | 只回放「当前快照」 | 可回放完整时间线 |
| 典型问题 | 它现在在干什么 | 它当时为什么失败 |
| 生命周期 | 进程内，随进程消失 | 跨重启保留，按策略清理 |

把这条界线画出来，是为了防止一种常见的膨胀：为了让 Hub「顺便」支持历史，开始在内存里堆事件，最后既不是缓存也不是日志。

## 九、生命周期收尾

两个细节，都关于「别拖住进程」：

- 清理定时器每 15 秒跑一次，只做一件事——剔除过期终态；如果没有任何信号被剔除，就不产生新快照，避免空转推送。
- 定时器调用 `unref()`，不阻塞进程退出。桌面应用退出时不应该因为一个定时器多等一轮。

清空接口则是测试与整体退出的入口：清空信号、清空审批、发一帧空快照，让所有订阅者同步归零。
