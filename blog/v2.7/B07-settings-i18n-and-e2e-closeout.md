# 设置、双语与收尾：把「没做」写成边界

功能做完不等于交付完成。用户要能关掉它、调轻它、看懂它；维护者要知道哪些是边界，哪些是欠账。

这一篇讲三件收尾工作：设置面板如何做到「点了就生效、失败就退回」，中英双语与导航如何补齐，以及为什么要把「没做」写进文档而不是留给猜测。

## 一、七个字段，一套默认值

新增的设置都是扁平字段，没有嵌套对象。理由是：扁平字段的补丁语义最简单——改一个键就是一次更新，不会出现「合并嵌套对象时把兄弟字段覆盖掉」。

| 字段 | 取值 | 默认 |
|---|---|---|
| 总开关 | 布尔 | 开 |
| 气泡模式 | 有工作才显示 / 始终 / 隐藏 | 有工作才显示 |
| 完成提示音 | 布尔 | 开 |
| 错误提示音 | 布尔 | 开 |
| 待审批提示音 | 布尔 | 开 |
| 减少动态 | 布尔 | 关 |
| 待机节奏 | 安静 / 标准 / 活泼 | 标准 |

默认值的取向很清楚：**默认打开「能被看见」，默认关闭「会打扰」**。提示音默认全开是因为它们是「有事发生」的信号；减少动态默认关是因为它属于无障碍偏好，不该替用户决定。

待机节奏是唯一一个「字段在、入口还没开」的项，原因见后面「明确未做的三件事」。

## 二、乐观更新，失败回滚

设置面板最容易踩的坑不是样式，而是受控输入被旧值弹回：用户点了开关，请求还在路上，设置查询恰好重拉了一次，复选框又跳回去。

做法是三层：

```ts
// 本地覆盖：先改 UI，再发请求
setLocal((prev) => ({ ...prev, [key]: next }));

update.mutateAsync({ [key]: next }).catch(() => {
  // 失败：删掉这一条覆盖，回到服务端值
  setLocal((prev) => { const copy = { ...prev }; delete copy[key]; return copy; });
});
```

1. **本地覆盖表**只存「用户刚改过的键」，不复制整份设置；
2. 读取时按「覆盖值 → 服务端值 → 默认值」三级回落；
3. 请求成功后，服务端数据刷新会把覆盖表清空，UI 自然收敛到真值。

这套写法解决的是「一致性」而不是「速度」：用户看到的永远是「我点的那个值」，直到服务端明确否定了它。

## 三、面板放在哪，为什么

面板归到「对话互动」分组，因为它调的是桌宠的行为，而不是模型或工具的能力。分组错了，用户找不到；分组对了，用户不需要读文档也能猜到它在哪。

面板内部有层级：总开关在上，关闭时整块子项收起；子项按「可见性 → 声音 → 动效」排列。顺序不是随意的——用户最常改的是「要不要显示」，最不常改的是「动效强弱」。

## 四、中英双语与导航

三处文案同时补齐：设置面板、桌宠气泡、审批中心。

- 气泡文案带占位符（标题与计数），中英文各自处理标点与语序；
- 审批中心有来源徽标、空态、错误态、处理中态等十余条键；
- 侧栏新增一项导航，与其余入口同构，不搞特殊样式。

双语在这里不是「翻译任务」，而是「口径检查」。写英文时经常发现中文里含糊的地方——比如「等待处理」到底在等谁。被迫写清楚，是件好事。

## 五、端到端覆盖了三件事

浏览器端到端只加了两条用例，但覆盖了三条最容易回归的路径：

| 用例 | 断言 |
|---|---|
| 快照接口与审批空态 | 信号接口返回数组结构；审批列表为空；侧栏导航可见 |
| 设置落库 | 关闭总开关后设置接口返回 false；再打开后返回 true |

第一条特意没有断言「信号必须为空」。原因是全量套件共享同一个应用数据目录，前面跑过的用例会留下最近的成功信号。断言「为空」会在机器快时随机失败——**测试要断言的是一致性，不是某个瞬间的洁净。**

第二条做了复位：验证完关闭，再改回开启，避免污染后续用例。

## 六、明确未做的三件事

| 项 | 现状 | 为什么现在不做 |
|---|---|---|
| 待机节奏接控制器 | 字段、默认值、双语文案都在，未接角色控制器，面板未出入口 | 现有角色控制器的待机计时器签名要改，改动面大于收益 |
| 桌面控制授权并入审批 | 仍走原有授权路径 | 权限面与工具调用不同，需要单独的风险评估 |
| 会议信号纳入工作状态 | 会议仍由舞台与会议页自身状态展示 | 会议的「进行中」语义与运行不同，硬塞会让信封变形 |

把这三条写进验收记录，有两个作用：第一，避免下一位维护者把它们当成缺陷去「顺手修」；第二，让「这次的范围」变成可讨论的对象，而不是靠记忆。

## 七、为什么「未做」是边界而不是遗憾

遗憾是「本该做却没做」；边界是「明确决定不做」。

区别在于有没有理由。上面三条都有明确的技术或产品理由：一条是改动面，一条是风险面，一条是语义不匹配。写清楚理由，读者就能判断「以后要不要做、什么时候做」。

反过来说，如果一份交付文档只写做成了什么，读者会默认「没写的都做完了」。这种默认会在下一次改动时变成事故。

## 八、五条可以带走的方法

1. **先统一口径，再谈呈现。** 三套状态各自渲染，只会得到三套文案；把差异收在翻译层，下游才会简单。
2. **正交维度胜过大枚举。** 「运行到哪」和「是否等人」是两件事，合成一个状态机就会指数膨胀。
3. **纯函数放在共享包。** 前后端同口径、可测、可替换，代价是它必须保持零依赖。
4. **默认值表达产品立场。** 默认开什么、默认关什么，比设置项的数量更能说明这个产品怎么看用户。
5. **把「未做」写成带理由的清单。** 没有理由的未做是欠账，有理由的未做是边界。

## 九、收束

一条工作信号从产生到被看见，要经过四层：事件映射、纯函数 reducer、进程内 Hub、订阅端聚合。每一层都只做一件事，层与层之间用固定形状交接。

这套结构解决的问题很朴素：用户不在那个页面的时候，仍然知道那里发生了什么；需要他拍板的时候，能被他找到；没人在的时候，默认拒绝。

剩下的事——让运行在关窗后继续、把历史变成可回放的时间线——都需要新的归属模型与新的存储，不属于这次的边界。
