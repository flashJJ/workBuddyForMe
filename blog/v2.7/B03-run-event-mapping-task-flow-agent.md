# 三套运行事件，一张信号表：任务、工作流与协作的字段对齐

reducer 只认一种形状。但上游给的是三种完全不同的事件。

任务运行按步循环，事件里有步号、工具名、步骤种类；工作流按节点图走，事件里是节点 ID 与节点类型；协作按轮次推进，事件里是阶段、角色、轮次。三者唯一的共同点是：都希望用户看到「它在干什么」。

这一层的工作就是翻译。原则只有一条：**翻译层承担全部差异，下游不再知道源类型。**

## 一、原始形状的差异

| 维度 | 任务运行 | 工作流运行 | 协作运行 |
|---|---|---|---|
| 进度单位 | 第 N 步 / 最大步数 | 节点 | 轮次 |
| 步骤标签 | `第 3 步 · web_search` | `node_2 执行中` | `第 2 轮 · 执行者` |
| 活动线索 | 工具名 | 节点类型 | 阶段名 |
| 归属 | 任务 ID（可带会话） | 工作流 ID + 运行 ID | 会话 ID（可选） |
| 终态来源 | 状态 + 停止原因 | 运行级事件 | 完成或错误事件 |

如果让 UI 直接吃这三种事件，那么「一个步骤开始」在任务页是进度加一，在工作流页是节点高亮，在协作页是轮次加一。三套渲染逻辑、三套边界判断，迟早会出现三套文案。

## 二、映射层做了什么

三条链路各有一个映射函数，签名一致：

```ts
applyXxxEvent(prev, fallbackRun, event) => WorkSignal | null
```

`prev` 是上一次的信号（没有就新建），`fallbackRun` 是调用方手里的运行快照，`event` 是这一帧。返回 `null` 表示这一帧不影响工作信号，调用方直接跳过。

三条链路各自的差异被收在这几个点里：

1. **进度。** 任务侧用步骤序号：开始时显示「第 N 步」，结束时写完成数；工作流侧没有总节点数，只累加完成节点数，总步数保持未知；协作侧用交接次数累加。
2. **标签。** 任务侧拼「第 N 步 · 工具名」，工作流侧拼「节点 ID + 动作」，协作侧拼「第 N 轮 · 角色」。
3. **归属与会话。** 协作运行可能带会话 ID，深链就指向那个对话；任务与工作流则指向各自列表，并附运行 ID。
4. **终态。** 任务要同时读状态与停止原因（后者区分「用户停」与「超步数」）；工作流直接用运行级事件；协作看完成或错误事件。

## 三、缺失字段的兜底

上游事件并不总是字段齐全，尤其是中间帧。兜底策略分三档：

| 情况 | 处理 |
|---|---|
| 事件本身不带运行快照 | 用调用方传入的运行兜底 |
| 事件缺步骤或节点细节 | 返回 `null`，不改信号（宁可不动，也不写入半条记录） |
| 标题为空 | 用固定占位（任务 / 工作流 / 协作任务），并截断到 120 字 |

第三档看起来最不起眼，但它防的是一类真实事故：把工具参数甚至密钥拼进标题。所以标题由服务端统一清洗与截断，任何调用方都不能直接塞原文。

还有一条兜底是关于失败语义的：工作流的节点失败不一定意味着运行失败，因为可能有错误分支把它接住。因此节点失败只记录错误原因，终态仍由运行级事件决定。**局部失败不等于整体失败，这层判断必须留在这里，不能交给 UI。**

## 四、runner 不改，只加一个可选回调

最干净的做法当然是让 runner 直接吐出统一信号。但那意味着三个 runner 的签名全部要改，所有调用方、所有测试都要跟着动，风险与收益完全不成比例。

所以接入方式是「旁路」：

```ts
// 伪代码：在 runner 的创建参数里加一个可选回调
createTaskRunnerService(deps, runtime, (run, event) => {
  hub.ingestTask(run, event);
});

createAgentRunService({ ..., onEvent: (run, event) => hub.ingestAgent(run, event) });

createFlowRunService({ ..., onEvent: (run, event, title) => hub.ingestFlow(run, event, title) });
```

三个回调都由容器注入，runner 内部只负责在原来的广播点顺手调用一次。没有回调时，行为与之前完全一致——这是「可选」两个字的实际含义：旧调用方不需要知道这个特性存在。

工作流的回调还多一个标题参数。原因是工作流事件里没有名字，只有 ID，而用户认识的是流程名。这个名字由容器在创建运行时一并带上，而不是在每个事件帧里重复查询。

## 五、为什么不要求所有 runner 改签名

三个理由：

1. **改动半径。** runner 是被多处复用的核心，改签名等于让所有装配点重新编译、重新验证。旁路回调只影响装配点。
2. **可回退。** 如果某条链路的事件质量不达标，摘掉它的回调即可，其余链路照常工作。改签名做不到这种粒度。
3. **职责清晰。** runner 的职责是「执行」，不是「汇报」。汇报是观察者的需求，用回调表达最贴切。

代价是：回调点必须找得准。任务在启动包装器里逐帧回调，工作流在队列发布处回调，协作在代理总线上回调。找错位置不会报错，只会表现为「信号偶尔不动」——这类静默问题只能靠集成测试兜住。

## 六、容器的接线顺序

接线本身也有一条约束：Hub 必须先于三条 runner 创建。

原因是 runner 在构造时就要拿到回调，而回调闭包引用了 Hub。如果顺序反过来，回调里拿到的是空引用，信号会静默丢失。容器里的顺序因此是固定的：审批注册表 → Hub → 任务运行 → 协作运行 → 工作流运行。

工作流放在最后，还有一个额外原因：它的运行可能发起协作节点，而协作服务必须先就位。

## 七、这一层的测试怎么写

映射函数是纯的，所以测试也是纯的：给定一个旧信号和一帧事件，断言输出的字段。

三条链路各写了用例，重点不在「每种事件都覆盖」，而在三件容易错的事：

- 中间帧缺字段时返回 `null`，而不是产生半条信号；
- 终态帧能正确区分「取消」与「超预算」；
- 标签与标题都做了截断，不把长文本原样透出。
