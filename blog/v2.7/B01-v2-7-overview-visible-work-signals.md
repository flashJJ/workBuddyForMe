# 让它自己汇报：统一工作状态、桌宠工作态与审批收件箱

用户的反馈只有一句：任务在跑，但界面各说各话；把窗口一关，就不知道结果了。

这不是功能缺失。任务页有步骤进度，工作流页有节点状态，协作页有轮次与交接，运行报告里也有统一的结果与耗时。问题在于这些信息各自长在不同的页面里，只在用户「正好盯着那一页」时才成立。一旦切到编辑器、浏览器或别的窗口，桌面 AI 应用就退回成一个安静的图标。

所以这次只做一件事：**把已经开始的工作，变成窗口关掉之后仍然看得见的信号。**

## 一、痛点的两个层次

| 层次 | 用户看到的现象 | 真实原因 |
|---|---|---|
| 各说各话 | 任务页说「第 3 步」，工作流页说「节点执行中」，协作页说「第 2 轮」 | 三套事件形状不同，UI 各写一套解读 |
| 关窗即失联 | 最小化主窗后桌宠毫无反应，回来才知道失败 | 状态只活在当前页面的 SSE 连接生命周期里 |

第一层是「口径分散」，第二层是「载体绑定」。只修第一层，用户仍然得盯着主窗；只修第二层，桌宠会把三套互相矛盾的文案搬到你桌面。两件事必须一起做，而且顺序不能反：先统一口径，再谈呈现。

## 二、三件事

| 要做的事 | 用户感受 | 落点 |
|---|---|---|
| 统一工作状态 | 不管在哪跑，都能用同一句话描述 | shared 包的纯函数 reducer + core 包的进程内 Hub |
| 桌宠工作态 | 不打开主窗也知道它在干什么 | 桌宠窗口独立订阅 + 七态 + 气泡 + 提示音 |
| 审批注意力中心 | 要我拍板的时候，它能找到我 | 审批注册表 + 收件箱页面 + 失败关闭 |

三件事共享同一条数据链路：运行事件 → 映射成工作信号 → 聚合快照 → 订阅者。桌宠和审批页不是两个系统，而是同一条链路上的两个消费者。

## 三、为什么复用，而不是新建一张运行表

最直觉的做法是新建一张运行状态表，每次状态变化写一行，谁要看状态就查表。

我们没有这么做，原因有三条：

1. **已经有真源。** 任务运行、工作流运行、协作运行各有自己的表，运行报告也是从这些表投影出来的。再建一张「状态表」，等于同一件事存两份，两边一旦不一致，没人知道该信谁。
2. **工作信号是短命的。** 它的价值在「现在」，不在「曾经」。写进数据库意味着要设计清理策略、索引与迁移，而这些成本换不来用户能感知的收益。
3. **写入放大。** 一次任务循环可能产生几十帧事件（步骤开始、工具调用、步骤结束）。把每一帧都落库，等于给一次运行配一条高频日志。

所以这次的取舍是：**运行真源仍然是原来的运行表，工作信号只存在于进程内存里，作为「当下视图」的缓存。** 它不是新的事实，只是旧事实的另一种读数。

判断标准可以浓缩成一句：这张数据是否会被用于「事后重建」？如果会，它属于下一步的事件日志；如果只会被用于「此刻展示」，它就不该进数据库。

## 四、八个统一结果与耗时口径

结果口径直接复用运行报告已有的八个值，一个字都没改：

| 结果 | 含义 | 桌宠是否继续呈现 |
|---|---|---|
| `queued` | 已排队，尚未开始 | 是（排队态） |
| `running` | 正在执行 | 是（思考或工作） |
| `waiting` | 暂停，或等待人工介入 | 是（等待态） |
| `succeeded` | 成功结束 | 保留 60 秒脉冲 |
| `failed` | 失败结束 | 保留 60 秒并可提示 |
| `cancelled` | 用户取消 | 保留 60 秒 |
| `interrupted` | 被动中断 | 保留 60 秒 |
| `budget_exceeded` | 步数或失败次数超限 | 保留 60 秒 |

这套口径之所以不能另起一套，是因为它已经出现在列表、报告与失败归因里。工作信号如果自创状态名，用户会看到「同一件事在报告里叫失败，在桌宠上叫异常」，而解释这种差异的成本远高于复用。

耗时也只有一个口径：信号里带 `startedAt`、`updatedAt`、`endedAt` 三个时间戳；结束时按「开始 → 结束」算，未结束时按「开始 → 现在」算。界面不自己计时，避免三处各跑一个秒表。

## 五、一条链路的四层分工

| 层 | 职责 | 具体形态 |
|---|---|---|
| 映射 | 把三套事件压成同一形状 | core 包里的三个映射函数 |
| 计算 | 排序、聚合、过期 | shared 包里的纯函数 |
| 分发 | 持有当下快照并广播 | 进程内 Hub 与流式接口 |
| 消费 | 翻译成状态、气泡、提醒 | 桌宠与审批页各自订阅 |

四层之间只传结构，不传页面状态。所以任何一层都可以被替换或测试，而不牵动其余三层。

## 六、门禁数字

| 项 | 结果 |
|---|---|
| 类型检查 | 14/14 包通过 |
| 静态检查 | 0 error |
| 行数门禁 | 单文件 ≤300 行通过 |
| shared 包单测 | 321 例（工作信号纯函数 7 例，SSE 契约 24 事件） |
| core 包单测 | 1140 例（审批 4、事件映射 3、Hub 3） |
| web 端单测 | 全量通过（工作气泡 3 例、侧栏 9 项导航、英文覆盖） |
| Web 端到端 | 2 例通过：快照与审批空态、设置落库 |

数字之外还有一条自证：工作信号的纯函数全部独立于 React、数据库与 Node 运行时，因此可以被任意一侧直接引用而不引入依赖。

## 七、这次刻意不做的

- **不做运行归属改造。** 任务运行仍绑定页面连接，关页即中断。这次只保证「看得到」，不保证「接着跑」。
- **不做事件日志。** 工作信号不是审计材料，它只回答「现在」。
- **不做桌面控制授权并入。** 这条链路的风险面太大，先留在原处。
- **不做会议信号。** 会议有自己的舞台状态，不硬塞进同一个信封。

把这些写进清单不是为了显得克制，而是为了让下一位维护者知道边界在哪：一条信号越过了这些线，就不再是这次定义的东西。

## 八、后面几篇的分工

按数据流拆开讲：先讲那个把三类事件收成一套口径的纯函数 reducer，再讲三类运行事件各自的字段差异与兜底，然后是进程内 Hub 的快照、序号与订阅，接着是审批收件箱为什么必须默认拒绝。桌宠与设置面板放在最后，因为它们消费的正是前面所有环节的产物。

一句话概括这次的立场：**用户不需要更多页面，他需要在他不在那个页面的时候，也知道那里发生了什么。**
