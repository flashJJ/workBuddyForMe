# 循环依赖不是零容忍：用强连通分量建立可执行的基线

「禁止循环依赖」是一条听起来很正确、执行起来很难的规则。

一个成熟代码库里，循环依赖往往不是某个人写错了，而是多种合理设计叠加的结果：类型文件互相引用、barrel 转发、依赖注入容器装配、事件回调反向注册。要求一次清零，通常只会得到一份长期豁免名单。

这一轮的做法是：先测出全部环，冻结成基线，只禁止新增。

## 一、循环依赖为什么值得管

循环依赖的危害分两类。

**运行时风险。** 两个模块在初始化阶段互相引用，先执行的那个可能拿到 `undefined`。这类问题在测试环境不一定复现，在打包、按需加载或模块顺序变化时才暴露，排查成本很高。

**认知风险。** 即使没有运行时问题，一个环也意味着「这几块代码无法单独理解」。你想改其中一个模块，必须同时理解另外几个模块的初始化顺序。

barrel 会把第二种风险放大：一个入口转发十个文件，其中任何一个与入口形成环，整个域的加载顺序都变得更难推理。

## 二、环的数学定义：强连通分量

模块依赖可以看成一个有向图：模块是点，`import` 是边。循环依赖就是图中的环。

检测环不需要逐个找路径，可以用强连通分量（SCC）：如果一组模块两两之间都能沿着有向边到达对方，它们就属于同一个 SCC。一个 SCC 的规模 ≥2，就至少包含一个环；规模为 1 的模块如果有自引用，也算环。

Tarjan 算法可以在一次深度优先遍历里求出全部 SCC，复杂度与点、边数量线性相关。这次扫描了 2028 个模块、7334 条依赖边，耗时可以忽略。

实现上的关键点：

| 点 | 处理 |
|---|---|
| 别名引用 | `@/...` 按 web 源码根解析到真实文件 |
| 相对引用 | 相对引用文件解析 |
| 包子路径 | `@pkg/domain` 映射到包内入口或具体文件 |
| 动态 import | 单独归类，默认不参与静态 SCC，避免误报 |
| 测试文件 | 参与扫描，但可以按需排除，避免测试 mock 制造假环 |
| 构建目录 | 忽略，避免 standalone 副本重复计数 |

## 三、基线怎么存

基线不是「允许这些环存在」的免责声明，而是一份**待办清单**：

```json
{
  "sccs": [
    { "id": "C1", "size": 9, "modules": ["..."], "reason": "类型与依赖注入环，待逐域拆分" },
    { "id": "C2", "size": 7, "modules": ["..."], "reason": "共享类型与 barrel 转发" }
  ]
}
```

每条记录至少包含规模、代表模块与原因。检查逻辑：

```text
求当前全部 SCC（规模 ≥2 或自环）
与基线按模块集合比对：
  当前有、基线无 → 新增环，失败
  基线与当前都有 → 通过（warning 可选）
  基线有、当前无 → 已消除，提示更新基线
```

「基线有、当前无」要允许并提示，而不是失败。否则每次修好一个环，CI 反而报错，没人有动力去修。

## 四、为什么当前还有 8 个环

基线测量时测到 9 个 SCC，收拢过程中有一个语音清单环自然消失，剩下 8 个。它们大致分四类：

| 类型 | 例子 | 风险 |
|---|---|---|
| 类型环 | 共享类型文件互相引用类型 | 运行时通常无害，但边界模糊 |
| barrel 转发环 | 入口与子模块互相转发 | 加载顺序敏感 |
| 依赖注入环 | 容器与调度器互相装配 | 初始化顺序必须稳定 |
| 真实运行时环 | 两个服务在调用时互相依赖 | 可能出现半初始化对象 |

这四类不能用同一种方式修：

- 类型环可以靠 `import type` 与类型文件下沉解决；
- barrel 环要拆入口，避免入口反向依赖子模块；
- 依赖注入环需要把装配移到单独的组合层；
- 真实运行时环要引入事件、回调或第三方协调者。

一次全改，等于同时动四类设计。风险远大于收益。所以这一轮只做「不再新增」，把清零留给后续按域处理。

## 五、门禁怎么防止「假装修好」

循环门禁最容易被绕过的三种方式：

1. **把 import 改成动态 import。** 静态图上看不见了，运行时仍然循环；
2. **把依赖移到测试文件。** 测试不计入图，生产代码的问题被隐藏；
3. **把模块合并成一个大文件。** SCC 消失了，但可读性更差。

对应的约束：

- 动态 import 单独统计，新增动态环也报警（可按需分级）；
- 测试文件与实现分开统计，不因测试豁免生产环；
- 行数门禁仍然生效，合并大文件会被另一条规则拦住。

门禁不是数学证明，它只能约束它看得见的东西。多条门禁交叉，才能减少「绕过去」的空间。

## 六、自测与输出

和结构门禁一样，循环脚本也带自测：构造一个三模块环，断言能检出；再把环登记进基线，断言能放行。

输出分成两部分：

```text
存量循环（已登记，不阻断）：8
  规模 9  C1：类型与依赖注入环
  ...
新增循环：0
```

存量部分每次 CI 都打印，作用是提醒「这些债还在」。新增部分为空才通过。

## 七、这套做法的适用边界

「冻结基线 + 禁止新增」适合存量复杂、增量可控的项目。它的前提是：

- 基线可维护，不会半年后变成一份没人看的 JSON；
- 每条基线有原因与责任人，到期复核；
- 新增环的失败信息足够具体，开发者知道怎么拆；
- 团队接受「先不修完」，但不接受「继续变坏」。

如果项目刚起步、环很少，直接要求零环更简单。如果项目已经有很多环，一刀切清零通常不现实。

结构规则要和项目阶段匹配，不能拿理想状态做当前门禁。
