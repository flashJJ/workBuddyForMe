# 什么情况下不该上聚合端点：一份准入清单

页面请求一多，最容易得到的建议是「加一个聚合接口，一次返回所有数据」。

这个建议在很多场景成立，但在本地优先的桌面应用里，它经常是错的：聚合端点会把页面的数据需求固化到服务端，让一次前端改版变成一次后端契约变更；更常见的结局是聚合端点上线后，旧端点仍然保留，系统里多了一条必须同步维护的路径。

这一轮给聚合端点写了一份准入清单，最后的结论是「不用」。

## 一、聚合端点的真实成本

把多个资源合成一个响应，收益看起来是「少发几条请求」，成本却分散在四个地方：

| 成本 | 具体表现 |
|---|---|
| 契约耦合 | 页面字段变化要改服务端聚合逻辑，前端不能独立演进 |
| 复用风险 | 聚合层容易复制 SQL，而不是复用既有 service / repo |
| 失效复杂 | 一个 mutation 可能要让聚合 key 与多个明细 key 同时失效，漏一个就出现旧数据 |
| 回退困难 | 聚合失败时页面要么整页不可用，要么实现一套分区降级逻辑 |

如果收益只是「请求数从 7 降到 3」，这些成本并不划算。

## 二、先走代价更低的两级

聚合端点不是第一选择，它前面还有两级更便宜的方案：

```text
第一级：页面级 facade hook
  把页面需要的查询组合成一个 hook，内部仍可并行多个 query
  统一 loading / error / 失效策略，页面只依赖 facade

第二级：可见区触发查询
  面板照常挂载，但不可见时不发请求
  只改请求时机，不改接口与 DOM

第三级：只读聚合端点
  仅当前两级之后仍不达标时启用
```

第一级解决的是「页面代码到处散落查询」，第二级解决的是「未见面板提前请求」。两级都不改服务端契约，回退成本接近零。

这一轮的设置页只有两条顶层查询：供应商列表与设置。页面已经直接消费它们，再包一层 facade 不会减少任何请求，只会多一层间接。所以第一级也没有启用，直接做了第二级。

## 三、准入清单

如果确实要考虑聚合端点，至少要同时满足下面这些条件：

| 项 | 要求 |
|---|---|
| 方法 | 只读 GET，不聚合 mutation |
| 范围 | 只覆盖页面首屏最小字段，不把整页数据都塞进去 |
| 复用 | 服务端复用既有 service / repo，不允许复制 SQL |
| 契约 | 响应 schema 放在共享包，字段按页面最小集定义 |
| 兼容 | 既有端点全部保留，旧页面零影响 |
| 失效 | 明确「哪个 mutation 失效聚合 key，哪个只需失效明细 key」 |
| 预算 | payload 不超过原请求总和 +10%，p95 不劣于基线 |
| 效果 | 首屏 distinct GET 下降 ≥50% |
| 降级 | 聚合失败可按分区回退到明细端点，不拖垮整页 |

这份清单里最容易被忽略的是「兼容」与「失效」。聚合端点一旦成为页面唯一数据源，旧端点就变成 dead code；但删除旧端点又会影响其他页面，最后两条路径长期并存。

## 四、把清单用在设置页上

门控之后，设置页首屏只剩 7 条 distinct 路径：

```text
供应商列表
应用设置
助手列表
动作清单
形象清单
语音设置
系统信息
```

逐条看，它们分属不同资源与不同消费方：供应商与助手是页面基础区，动作与形象是全局形象能力，语音设置是全局语音能力，系统信息是壳层信息。它们没有一个共同的「页面资源」边界。

如果硬做聚合，服务端需要同时知道供应商、助手、形象、语音、系统五套服务的组装顺序与失败语义；任意一个服务变慢，整页首屏都变慢。收益是少发 6 条本地请求，成本是把页面生命周期交给服务端。

所以结论是明确否决，而不是「以后再说」。否决也要写进验收文档：有数据、有理由、有回退路径。

## 五、什么情况下聚合是合理的

反过来，如果页面满足下面几个特征，聚合端点值得做：

- 首屏仍有四个以上独立资源，且门控后依旧超出目标；
- 这些资源服务于同一个页面语义，且几乎总是同时被需要；
- 服务端已有稳定的组合服务，聚合层不需要复制查询；
- 页面契约相对稳定，不会频繁增删字段；
- 有明确的失效矩阵与降级方案。

典型例子是移动端首屏、强实时仪表盘、需要把多次往返压成一次的低带宽场景。它们的共同点是「网络往返成本远高于服务端组装成本」。

本地桌面应用恰好相反：请求走本机回环，往返成本很低；服务端组装与失效维护的成本反而更高。技术选型要看成本结构，不能只看请求条数。

## 六、否决之后留下什么

这次否决聚合端点，留下三样东西：

1. **一份可复核的数据**：首屏 22 → 7，峰值 15 → 4，响应体 45 KB → 5.6 KB；
2. **一份准入清单**：后续页面想加聚合端点，先逐条对照，而不是凭感觉；
3. **一条零成本回退路径**：全部改动都在前端请求时机，服务端零改动，出问题直接回退。

这比「先加一个聚合接口试试」更稳，也更符合本地优先的取舍。

## 七、判断顺序总结

遇到页面请求扇出，按这个顺序判断：

1. 先量 distinct 路径、并发、响应体，不看总请求数；
2. 找出「未进入视口却已请求」的部分，优先改时机；
3. 页面查询散落时，考虑 facade，但先确认它真的减少请求；
4. 前两步之后仍不达标，再按准入清单评估聚合端点；
5. 无论做不做，都把数据和理由写进文档。

请求优化不是「接口越少越好」，而是「让每次请求都发生在正确的时机，并且有明确的归属」。
