# 目录预算门禁：从「单文件 300 行」到「目录 12 个文件」

单文件行数门禁解决的是「一个文件太长」，但代码库变大的过程中，另一种膨胀更常见：每个文件都不长，目录里的文件却越来越多。

一个目录有 84 个文件时，没有任何一个文件违反 300 行规则，代码评审也看不出问题，但新增文件已经不知道往哪放。行数门禁看不见这种债，所以需要第二条预算：目录的直接文件数。

## 一、先定预算，再定基线

预算不是「理想值」，而是「还能一眼扫完的上限」。这次取 12：

- 低于 12 个直接文件，目录列表不需要二次索引；
- 超过 12 个，就应该按子能力再分一层；
- 子目录同样受 12 的限制，避免把胖目录变成「胖子目录」。

但存量代码不可能一夜达标。如果门禁一上来就要求全部 ≤12，结果只有两种：要么大规模移动，风险失控；要么规则被永久豁免，等于没有。

所以把「存量」和「新增」分开：

| 状态 | 处理 |
|---|---|
| 新增目录超过预算 | 直接失败 |
| 存量目录超过预算 | 按基线冻结为 warning |
| 存量目录继续增长 | 失败 |
| 存量目录缩小 | 通过，可更新基线 |
| 豁免目录 | 跳过，但必须登记原因 |

这套规则的核心是**只约束增量**。存量可以慢慢降，但不能继续涨。

## 二、基线文件长什么样

基线是一个放在仓库里的 JSON，而不是脚本里的硬编码：

```json
{
  "budget": 12,
  "exemptDirs": [{ "path": ".../migrations", "reason": "append-only 历史" }],
  "legacyDirs": [{ "path": "packages/core/src/tools", "count": 25 }],
  "legacyEntries": [],
  "deepImportExemptions": []
}
```

四个字段各管一类例外：

- `exemptDirs`：永远不参与预算的目录，例如数据库迁移（只追加、不重排）；
- `legacyDirs`：当前超标但允许暂时存在的目录，记录当时的文件数；
- `legacyEntries`：暂缺公开入口的多文件 feature；
- `deepImportExemptions`：确需保留的跨域深引用，数量有上限，必须写原因与到期版本。

基线进仓库的好处是可 review：每次有人降低存量或新增豁免，diff 里看得见。

## 三、检查算法

目录预算的检查很直接：

```text
扫描 web/src、desktop/src、各 package 的 src
忽略 node_modules、dist、.next、coverage、release 等构建目录
统计每个目录的直接 .ts / .tsx 文件数（不含 .d.ts）
对每个目录：
  未超预算 → 通过
  已豁免 → 通过
  在 legacy 中：
    数量 > 基线 → 失败（存量增长）
    数量 ≤ 基线 → warning（存量冻结）
  不在 legacy → 失败（新增超标）
```

三个细节：测试文件也计数（否则会出现「实现 8 个、测试 20 个」的假达标）；构建目录必须忽略；只算直接文件，子目录各受自己的预算约束。

## 四、入口检查与引用检查

结构脚本不只数文件，还检查两件与导航有关的事。

**入口存在性。** 一个 feature 如果有多个模块，就必须有 `index.ts`；单文件 feature 豁免。判断「多模块」时排除测试文件，避免「只有一个实现 + 五个测试」也被要求建入口。

**引用边界。** 跨 feature 只能引用目标入口，不能引用具体文件。实现上不是简单的字符串匹配，而是把模块说明符解析成真实文件：

`@/features/x/y` 依次尝试 `.ts`、`.tsx`、`/index.ts`；相对引用按引用文件解析。

解析后再判断目标所属的 feature。这样别名、相对路径、目录入口三种写法都能覆盖。

同时检查三个容易遗漏的边界：

- 同域内不得从自己的 barrel 反向导入（防循环）；
- `@/lib/hooks` 只能引用域入口，不能引用具体 hook 文件；
- 客户端 feature 不得引用服务端目录（防数据库驱动进客户端包）。

## 五、门禁要能自测

门禁脚本最大的风险不是漏报，而是「规则写错了但没人发现」。所以脚本内置了自测：

构造临时目录：A 有入口、B 没有且深引用 A 的具体文件、A 内部反向导入自己的 barrel；断言两类错误都被检出。

自测不依赖真实仓库，能在 CI 里独立跑。规则调整时先跑自测，避免「改规则把检查改瞎了」。

## 六、失败信息要能指导修复

门禁失败时，输出不能只有「检查不通过」。每条错误至少包含：

| 信息 | 例子 |
|---|---|
| 错误码 | `DIR_NEW_BUDGET` / `DEEP_IMPORT` / `SELF_BARREL` |
| 位置 | 目录或文件路径 |
| 实际值 | 直接文件 15 > 12 |
| 处理建议 | 按能力建子域；确需例外时登记原因与到期版本 |

错误码让 CI 日志可检索，位置让开发者能直接跳过去，建议让第一次遇到的人知道下一步做什么。

## 七、接入一键检查

新增脚本最终要进 `pnpm check`，否则它只是一个「可以手动跑」的工具。

顺序是 `typecheck → lint → 行数门禁 → 结构门禁 → 循环门禁`。

结构门禁放在行数之后、循环之前：先保证单文件与目录规模，再保证模块依赖没有环。任何一步失败都阻断，不继续往下跑。

## 八、存量冻结之后

门禁上线时，仓库里仍有 25 个超标目录。它们不会让 CI 失败，但每次有人改动其中一个目录，warning 都会提醒「这里已经超预算」。

这条 warning 的作用不是羞辱存量，而是告诉后来者：**不要再往这里加文件**。新增文件应该去新的子域，存量目录只会随迁移慢慢变小。

结构治理需要这种「允许不完美，但禁止继续变坏」的中间状态。一步到位的规则通常活不过一次迭代。
