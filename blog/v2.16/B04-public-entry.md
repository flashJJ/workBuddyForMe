# 公开入口不是 `export *`：页面级根入口与能力子域

前端 feature 目录最常见的状态是：目录里什么都有，但没有一个明确的「入口」。

调用方想用某个组件，只能写 `@/features/settings/some-panel`；想过一个 hook，只能写 `@/features/chat/hooks/use-session`。文件名于是变成了公开 API 的一部分。改一个文件名，不是改实现，而是改契约。

这一轮给全部多文件 feature 补上了公开入口，但不是「一个 `index.ts` 导出所有东西」那么简单。

## 一、入口要回答两个问题

一个 feature 的入口，实际要回答两个不同的问题：

1. **页面路由该引用什么？** 答案通常是页面级组件，一个 feature 最多一两个。
2. **其他 feature 需要什么能力？** 答案可能是渲染路由、查询 hook、桥接函数，按能力分成若干组。

把这两个问题合成一个入口，会得到两种坏结果：入口太小，跨域能力只能继续深引用；入口太大，页面路由一引用就把整个域拉进包体。

所以采用两级入口：

```text
features/voice/
  index.ts          // 只导出页面/宿主级组件
  runtime/index.ts  // hook、队列等运行时能力
  ui/index.ts       // 控件
  settings/index.ts // 设置面板
```

根入口负责「这个 feature 作为一个页面怎么用」，子域入口负责「这个 feature 作为一项能力怎么被别人用」。

## 二、第一版为什么把包体做大了

第一版很整齐：每个 feature 根入口 `export *`，每个子域也 `export *`。类型检查通过，但生产构建出现了明显回退：

| 页面 | 第一版 | 收紧后 | 改动前 |
|---|---:|---:|---:|
| 设置页 | 513 kB | 472 kB | 457 kB |
| 工作流详情 | 541 kB | 387 kB | 386 kB |
| 任务页 | 465 kB | 310 kB | 308 kB |
| 桌宠页 | 318 kB | 258 kB | 255 kB |

问题不在入口数量，而在入口的求值范围。一个页面引用了形象域的根入口，根入口又 `export *` 了 Live2D 画布，画布再拉入 Cubism 运行时；即便页面只用了一个表情枚举，打包器也很难证明其余模块没有副作用。

这不是打包器不聪明，而是入口给了它一个过大的起点。入口的导出面越小，摇树越可靠。

## 三、收紧后的四条规则

**规则一：根入口只导出页面级组件。** 页面路由用根入口；其他 feature 不用根入口拿能力。

**规则二：跨域能力走子域入口。** 例如对话页需要形象栏，就引用形象域的 `ui` 子域，而不是形象域根入口。桌宠和舞台不需要对话形象栏，就不会被牵连。

**规则三：高风险依赖单独成子域。** Markdown 渲染运行时体积大、依赖多，就从消息组件里拆出来单独入口；只需要附件预览的页面不必拉入整套 Markdown。

**规则四：内部实现不导出。** 内部组件、内部 hook、测试夹具不进任何 barrel。barrel 只承诺「跨域需要的能力」，不承诺「目录里的所有文件」。

这四条规则有一个共同效果：入口变多了一点，但每个入口的语义更清楚，包体也可控。

## 四、入口存在之后，还要能拦住深引用

有了入口不等于大家会用入口。只要深引用还能编译，旧代码就会继续按文件名引用。

这次没有只靠 ESLint，而是加了一个结构脚本。原因是 ESLint 的 `import/no-restricted-paths` 能表达「A 目录不能引用 B 目录」，但表达不了「只允许引用 B 目录的 `index.ts`」——它没有「目录入口白名单」这个概念。

脚本的做法是解析真实模块：

```text
specifier 是 @/ 开头 → 相对 web/src 解析
specifier 是 ./ 或 ../ 开头 → 相对引用文件解析
依次尝试：<base>.ts、<base>.tsx、<base>/index.ts
若解析结果的归属 feature 与引用方不同，且目标不是 index.ts → 报错
```

这样别名、相对路径、目录入口三种写法都能覆盖，误报率为 0。

脚本还检查三种容易漏的边界：

| 检查 | 规则 |
|---|---|
| 自身 barrel 反向导入 | 同域内禁止 `from '@/features/x'`，避免 barrel 循环 |
| hooks 深引用 | `@/lib/hooks/<域>/<文件>` 必须落到域入口 |
| 客户端引用服务端 | feature 不得引用 `lib/server`，防止数据库驱动进客户端包 |

第三条同时用 ESLint zone 兜底：结构脚本负责精确白名单，ESLint 负责编辑器内的即时提示。

## 五、改写 70 条深引用之后

这一轮把 70 条跨 feature 深引用改成了入口引用：49 条别名深引用、21 条相对深引用。改写后：

- 多文件 feature 入口覆盖 31/31；
- 跨 feature 深引用 0；
- `@/lib/hooks` 深文件引用 0；
- 剩余 35 条引用全部落在能力子域入口上。

改写过程中遇到两个典型问题：

**同名 hook。** 一个域里有两个同名 hook，一个是对外主 hook，一个是内部数据 hook。入口只导出主 hook，内部 hook 留在文件里；如果两者都导出，调用方无法从名字判断该用哪个。

**测试 mock 路径。** 测试原来 mock 具体文件，改走域入口后，mock 需要 `importOriginal` 保留真实导出，再覆盖目标函数。断言不变，但 mock 写法要跟着入口调整。

## 六、入口设计的判断清单

给一个 feature 设计入口时，可以按下面五问检查：

1. 页面路由是否只需要一个根入口？
2. 其他域真正需要的能力有哪几组？每组是否值得一个子域入口？
3. 有没有体积大、依赖重的模块被根入口带出去？
4. 有没有内部实现被误导出，变成事实上的公开 API？
5. 同域内部是否还在反向引用自己的 barrel？

五个问题都回答清楚，入口才是「导航层」，而不是「又一个把所有东西塞在一起的桶」。
