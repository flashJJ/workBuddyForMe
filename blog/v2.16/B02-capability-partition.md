# 按能力分区，而不是按表分区：84 个契约文件的收拢

一个 shared 包里放着全应用共享的契约定义，目录里有 84 个 `.ts` 文件，全部平铺。

它们大多是一张表对应一个文件：会话、消息、任务、审批、审计、供应商、模型、语音、形象……单看每个文件都合理，放在一起就失去了导航能力。新增一个契约时，第一反应不是「它属于哪个能力」，而是「找一个名字最像的文件，放在它旁边」。

这一篇讲这次分区的判断依据、执行顺序，以及哪些事情刻意没有做。

## 一、先区分「按表」和「按能力」

按表分区是最自然的做法：数据库有什么表，契约目录就有什么文件。它在早期很有效，因为表名就是业务名。

但到后期会出现三个问题：

| 问题 | 表现 |
|---|---|
| 一张表分裂成多个契约 | `task.ts`、`task-run.ts`、`task-event.ts` 各自平铺，读代码时要来回跳 |
| 一个能力横跨多张表 | 「知识库」需要文档、分片、编译状态、检索结果四个契约，按表看是四个域 |
| 纯逻辑没有表 | 权限策略、事件触发、工作信号并不对应单表，却同样需要归属 |

所以分区依据换成「能力」：一个能力是一组会被同一批页面、同一批服务同时消费的契约。表只是能力的一种落地方式，不是分类依据。

这次分出的 12 个子域大致是：

```text
agent/        代理、绑定、权限、策略、子代理
chat/         助手、会话、消息、记忆、关系
knowledge/    知识库、文档、分片、工具、技能
capability/   能力包、健康、签名、角色卡
provider/     供应商、模型
work/         任务、计划、信号、定时、事件、用量、会议、报告
flow/         工作流、差异、服务化
interaction/  动作、动作链、事件、图、命中区
emotion/      情绪、领域、表情、信号文本、桌宠互动
media/        语音、形象、动作、浏览器、桌面、舞台
ops/          审计、归档、诊断、密钥、包、设置
base/         通用、规范化 JSON
```

每个子域的文件数（含自己的入口）都控制在 12 个以内。12 不是神奇数字，它只是「一眼能扫完、不需要二级索引」的经验上限。

## 二、分区前先做一次「消费者盘点」

只按文件名分类，很容易把「看起来属于 A」但实际被 B 大量消费的文件放错位置。分错一次，后面要么出现跨子域的深引用，要么被迫把文件搬第二次。

这次的做法是先盘点，再分组：

1. 列出目录内全部文件的导出符号；
2. 用引用搜索统计每个文件被哪些包、哪些目录引用；
3. 把「被同一批消费者同时引用」的文件归到一组；
4. 对只有一两个消费者的文件，按它定义的契约归属，而不是按消费者归属。

第三步是能力分区的核心。**同一个能力的契约，通常会被同一批代码一起消费**；如果两个文件从来没有被同一批代码引用过，它们大概率不属于同一个能力。

第四步则防止另一个极端：不能因为「只有设置页用」就把审计契约放进设置域。契约的归属看它描述谁，不看谁在读它。

## 三、移动的顺序：先文件，再入口，最后根 barrel

移动式重构最怕一步到位：文件移动、入口生成、根导出改写同时发生，一旦编译失败，很难判断是哪一步的问题。

这次拆成三步，每步都能独立回滚：

| 步骤 | 动作 | 验证 |
|---|---|---|
| 1 | 只用 `git mv` 把文件移到子域目录，批量改写相对引用 | typecheck 通过 |
| 2 | 每个子域生成纯 re-export 的 `index.ts` | 子域入口可被单独引用 |
| 3 | 根 `index.ts` 改为转发子域入口 | 包级公开导出面不变 |

第一步的关键是 **不改文件名**。移动和重命名混在一批，review 时 Git 的 rename 检测会失效，diff 会变成「删除 84 个文件、新增 84 个文件」。只移动、不改名，`--find-renames` 还能看出每个文件去了哪里。

第二步的子域入口只允许两种语句：

```ts
export { agentSchema } from './agent';
export type { Agent } from './agent';
```

不写函数调用、不做常量计算、不注册副作用。入口一旦有运行逻辑，它就不再是导航层，而是隐藏的初始化点。

第三步把根入口从「逐个文件转发」改成「逐个字域转发」。原来 500 多行的根入口缩到 20 行，公开符号一个不少。

## 四、刻意没有做的三件事

**没有新增包级子路径。** 子域入口已经在包内可用，但没有把每个子域都暴露成 `package.json` 的 exports。理由很简单：每增加一个公开子路径，就多一份长期兼容负担；等确有外部消费者时再开，比一开始开一堆更稳。

**没有改任何契约字段。** 这一轮只移动位置。schema 的字段、默认值、校验规则、类型推导全部保持原样；测试数量与断言也没有变化。

**没有顺手重命名。** 目录里确实存在一些命名不一致的文件，但重命名会把「结构移动」变成「结构 + 语义」两类改动。命名规范从新增文件开始执行，存量留到单独批次。

## 五、结果与代价

收拢后的直接文件数从 84 降到 1（只剩根入口），12 个子域全部 ≤12。根入口从 523 行降到 20 行。

代价是 208 个文件的相对引用被批量改写。这个量听起来大，但改写是机械的：只改模块路径，不改符号名。跑一遍 typecheck 和 338 个 shared 单测，就能确认没有漏改。

另一个代价是**心智模型的迁移**。旧代码里习惯写「去 schemas 找某个文件」，现在要改成「先想能力，再进子域」。这需要一次适应，但适应之后，新文件的落点不再依赖记忆。

## 六、可复用的判断规则

如果要把这套方法搬到另一个大目录，可以按下面五条执行：

1. **分类依据是能力，不是存储形态。** 表、接口、页面都只是能力的表现。
2. **先盘点消费者，再分组。** 被同一批代码一起消费的文件，才属于同一个能力。
3. **移动和重命名分开。** 一批只做一件事，review 才看得见。
4. **子域入口只做 re-export。** 入口是导航，不是初始化。
5. **根公开面保持不变。** 移动式重构的成功标准是「消费者零改动」，不是「目录看起来更整齐」。
