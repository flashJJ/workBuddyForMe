# 把几百个文件搬走，行为一行不改：移动式重构的边界

结构收拢听起来像一次大规模重构，实际做起来更像一次搬家：东西换位置，功能不换。难的不是搬，而是搬完之后证明「真的什么都没变」。

这一轮共移动了 561 个文件，跨三个包和一个前端应用。没有改一个接口、没有改一条 SQL、没有改一句界面文案，单测数量与断言保持原样。

## 一、先定义「什么都没变」

「行为不变」不能靠感觉，要落成可检查的约束：

| 维度 | 约束 | 检查方式 |
|---|---|---|
| 对外导出 | 包级公开符号不变 | 全量 typecheck + 消费者编译 |
| 运行时行为 | 无逻辑改动 | 单测数量与断言不变 |
| 数据 | 无迁移、无表结构变化 | schema 版本号不变 |
| 构建产物 | 页面包体不超阈值 | 生产构建对比 First Load JS |
| 用户路径 | 页面与接口可用 | 生产模式 e2e 全量 |

只要有一条没有对应检查，搬家就可能悄悄带走行为。

## 二、一批只做一件事

最容易出问题的做法，是在移动文件的同一批里顺手做三件事：改目录、改文件名、改导出。三者叠加后，代码评审看到的是一大团无法对应的 diff。

这次把每批拆成固定顺序：

```text
1. git mv 文件到目标子域（不改名）
2. codemod 改写相对引用
3. 跑 typecheck / 单测 / 构建
4. 生成子域 barrel（纯 re-export）
5. 根 barrel 改为转发子域
6. 再跑一遍全量检查
```

前 3 步和后 3 步各自可回滚。如果第 3 步失败，只需要撤销移动；如果第 6 步失败，只需要撤销 barrel 调整。不会出现「移动和入口改坏混在一起，只能整批回退」的局面。

移动时不改文件名还有一层好处：Git 的 rename 检测能继续工作。评审时用 `--find-renames` 看，每个文件都能对上「从哪来、到哪去」，而不是一片删除和新增。

## 三、barrel 不是 `export *` 的堆叠

第一版子域入口生成得很整齐：每个子域一个 `index.ts`，内容是对目录内所有文件 `export *`；根入口再对所有子域 `export *`。

编译通过，单测通过，但生产构建暴露了问题：

| 页面 | 第一版 | 收紧后 | 改动前基线 |
|---|---:|---:|---:|
| 设置页 | 513 kB | 472 kB | 457 kB |
| 工作流详情 | 541 kB | 387 kB | 386 kB |
| 能力中心 | 510 kB | 278 kB | 278 kB |

原因是 barrel 的求值范围。`export *` 会把子域内所有模块都拉进模块图，哪怕页面只用其中一个导出；前端打包器很难把没有被引用的副作用安全地摇掉。一个页面引用了「形象域」的入口，就可能把整个 Live2D 运行时一起拉进来。

收紧后的规则：

1. **feature 根入口只导出页面级组件。** 页面路由引用根入口，跨域代码引用能力子域。
2. **子域入口只导出真正跨域需要的符号。** 内部组件、内部 hook、测试夹具不导出。
3. **高风险能力单独开子域。** 对话里的 Markdown 渲染从消息组件里拆出来，避免只需要附件的页面拉入整套 Markdown 运行时。
4. **根入口不导出重型 UI。** 形象域的根入口只保留轻量能力，具体的画布组件由真正需要它的页面直接引用子域。

这套规则的代价是入口不再「什么都有」，收益是页面包体回到基线附近。barrel 的职责是导航，不是把整个域打成一个大包。

## 四、codemod 要可核对，不要可聪明

批量改写引用最危险的地方，是「看起来都改了」。这次的做法很笨，但可核对：

- 先 `--dry-run` 输出将要改写的文件数与每一条替换；
- 只改模块说明符，不改导入/导出的符号名；
- 每批结束后统计「改写文件数」和「剩余旧路径数」，后者必须为 0；
- 对测试里的 `vi.mock` 路径单独检查，因为 mock 字符串不会被 typecheck 发现；
- 对动态导入、`require`、配置文件里的路径单独搜索。

测试 mock 是最容易漏的一类。某个 hook 的测试原来 mock 具体文件路径，文件搬走之后 mock 仍然指向旧路径，测试会「通过但测的是空实现」。这类问题必须靠单独的路径搜索，而不是靠测试结果。

还有一类是包的子路径入口。某个独立入口原来指向 `agents/stage-client.ts`，文件移动到 `agents/stage/` 后，`package.json` 的 exports、构建工具的 entry、产物文件名都要一起改；只改源码 import 不够。

## 五、测试跟随，断言不动

移动文件时，测试文件跟实现一起移动。只改 import 路径，不改用例名、不改断言、不改 mock 的返回值。

这条规则看起来只是纪律，实际是「行为不变」的主要证据：如果测试数量不变、断言不变、全绿，那么至少被测试覆盖的行为没有变。

这次唯一一次例外不是断言变化，而是一个与时间有关的测试：它把「今天」写死在用例里，下午运行就会因为「时间已过」失败。修复方式是把日期改成固定的未来日期，断言完全不变。这类问题在搬家时暴露，但不属于搬家本身。

## 六、什么时候该停

移动式重构需要一个停止条件，否则很容易从「收拢目录」滑向「重写模块」。

这次的停止条件写在契约里：

- 只做文件位置与入口调整；
- 发现业务 bug 只记录，不顺手修；
- 测试失败先判断是路径问题还是行为问题，前者修路径，后者回退；
- 每批移动后必须能通过 typecheck、单测与生产构建；
- 页面包体增长超过 5% 就停下，先收紧入口，不继续搬。

有了停止条件，搬家才是可交付的工程动作，而不是一次没有边界的重构。
