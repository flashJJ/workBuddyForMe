# 目录也是一种架构：当 84 个文件平铺在同一个目录里

一个本地优先的桌面 AI 应用，代码量到几千个文件之后，最先崩掉的通常不是运行速度，而是「找代码」的速度。

功能没坏、测试也绿，但每次要改一个设置项，都要先猜它属于哪个文件；每次要加一个新面板，都要先翻一遍目录，看看有没有「看起来差不多」的旧实现；每次移动一个文件，都会在几个毫不相干的页面里触发编译错误。问题不在某一段代码，而在代码的摆放方式。

目录结构是架构的一部分。它不决定系统能不能跑，但它决定每一次修改要付多少认知成本。下面这一轮工作没有新增功能，只做了四件与结构有关的事。

## 一、大目录是怎么长出来的

单文件行数门禁能拦住「一个文件写到 3000 行」，但拦不住「一个目录塞进 84 个文件」。后者更隐蔽：每个文件都不长，每个文件都有明确职责，代码评审时看不出问题，目录却慢慢变成了一个没有索引的仓库。

典型的形成过程是这样的：

| 阶段 | 做法 | 当时看起来 | 后来变成 |
|---|---|---|---|
| 起步 | 一个领域一个文件 | 清晰 | 文件越来越多 |
| 扩展 | 同领域新增文件，继续平铺 | 省事 | 目录里出现十几个近义文件 |
| 混合 | 工具、类型、测试、适配器都放一起 | 不用建目录 | 不知道哪个是入口 |
| 固化 | 新文件复制旧文件的摆放方式 | 一致 | 结构债被复制 |

真正的问题不是文件数量，而是**目录内没有二级语义**。看到一个目录里有 `provider.ts`、`provider-adapter.ts`、`provider-demo.ts`、`provider-probe.ts`，人还能靠命名猜；到几十个文件时，命名本身的区分度已经不够了。

## 二、四个结构性断点

这一轮把结构问题拆成四个可以独立验收的断点。

**第一，目录没有预算。** 单文件有 300 行门禁，目录却没有「最多几个直接文件」的约束。没有预算，胖目录会继续变胖，因为新增文件时最省事的做法永远是放在当前目录。

**第二，能力没有入口。** 一个前端 feature 目录里有几十个组件和 hook，但只有极少数目录有 `index.ts`。跨域引用只能写到具体文件，于是「改一个文件名」会牵动多个域；更糟的是，引用方开始依赖目标域的内部实现细节。

**第三，页面在替服务端拼装数据。** 一个设置页挂载几十个面板，每个面板自己发请求。页面本身没有做错什么，但首屏请求的扇出没有人量化，也没有人知道哪些请求是「打开页面就必须发」、哪些只是「滚到那里才需要」。

**第四，规则只写在文档里。** 「新文件放哪里」「能不能跨域引用」「入口导什么」如果只靠口口相传，下一次迭代就会重新长出一个胖目录。规则必须变成脚本和 lint，才有持续约束力。

## 三、四件事的收口方式

| 断点 | 收口动作 | 可验收的结果 |
|---|---|---|
| 目录无预算 | 按「域 > 子能力 > 文件」分区；直接文件 ≤12 | 12 个重点目录从 23–84 降到 1 |
| 能力无入口 | 每个 feature 一个纯 re-export 的 `index.ts` | 多文件 feature 入口 100%；跨域深引用归零 |
| 页面拼装数据 | 页面级 facade + 可见区触发查询 | 设置页首屏 distinct GET 下降 68% |
| 规则不可执行 | 目录预算、引用边界、循环依赖进 `pnpm check` | 新违例直接阻断 |

四件事有一个共同前提：**不改行为**。这一轮没有改 UI 文案、没有改 API 契约、没有改错误码、没有数据库迁移。移动文件只做 `git mv` 和 import 改写，测试断言零改动。结构治理最容易失控的地方，就是顺手把业务逻辑也改了，最后既无法 review，也无法回滚。

## 四、为什么四件事要按顺序做

四件事看起来可以并行，实际有依赖关系：

| 顺序 | 动作 | 依赖 |
|---|---|---|
| 1 | 目录分区 | 必须先有稳定位置，入口才有意义 |
| 2 | 公开入口 | 依赖分区结果，才知道每个入口导出什么 |
| 3 | 页面请求 | 依赖入口稳定，页面才能按能力引用 |
| 4 | 门禁 | 依赖前三步形成基线，规则才有数字可冻结 |

如果先做门禁，会得到一份无法执行的规则；如果先改页面，入口还在频繁变动，页面引用会反复改。按顺序做，每一步都能独立验收，出问题也能回退到上一个稳定状态。

这也是里程碑拆分的意义：不是把工作切成四份，而是让每一份都有一个可以停下来的出口。

## 五、为什么先动目录，而不是先动接口

一个自然的反应是：既然页面请求多，为什么不直接合并接口？

因为请求多不等于接口设计错。前端的数据获取库本来就会对相同 key 去重；同一个接口被多个面板消费，并不一定是浪费。真正需要先回答的是三个问题：

1. 首屏到底发了多少条 **distinct** 请求？
2. 这些请求里，哪些是页面基础区必需，哪些只是「面板挂载了所以顺手发」？
3. 如果只是改变请求时机就能达标，还需要新增聚合端点吗？

先量化，再决策。这一轮实测发现，设置页首屏 22 条 distinct 路径里，真正属于基础区与全局壳层的只有 7 条；其余 15 条都来自尚未进入视口的分组面板。把「挂载即请求」改成「进入视口才请求」，请求扇出就下来了，接口一个都不用动。

这也是结构治理的一般顺序：**先消除无意识的耦合，再考虑合并有意识的接口**。前者是免费的，后者有契约成本。

## 六、结构工作的验收标准

结构工作最怕「感觉清爽了」。清爽不是验收标准，下面这些才是：

- 重点目录的直接文件数、子目录文件数都能被脚本数出来；
- 前端 feature 的入口覆盖率、跨域深引用条数能被脚本统计；
- 首屏请求数、峰值并发、响应体大小有前后对比；
- 构建产物的 First Load JS 没有超过约定阈值；
- 全量单测、生产模式 e2e、桌面冒烟不降级；
- 旧数据库不需要迁移就能打开。

这六条里，任何一条没有数字，结构工作就还停留在审美层面。

## 七、这一轮留下的边界

结构治理不是一次性把全部目录压到 12 个文件。这一轮只做重点目录，剩余的大目录按「存量冻结、新增阻断」处理：允许它们暂时存在，但不允许继续增长。后续版本再按域逐个下降。

同样，循环依赖没有追求「零环」。存量环先建立基线、逐条登记，新增环直接失败；清零是后续版本的事。把「存量」和「新增」分开，是让门禁能落地的前提——一上来就要求零环，只会得到一份被永久豁免的规则。
