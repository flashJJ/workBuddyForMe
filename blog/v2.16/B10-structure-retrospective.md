# 结构治理复盘：七条能落地的规则

这一轮没有新增功能，只做了目录收拢、入口统一、页面请求时机与三条门禁。回头看，真正可复用的不是某个目录怎么分，而是下面七条规则。

## 一、结构成本必须先量化

「目录太乱」不是问题描述，「84 个文件平铺、24 个目录超过 20 个文件、22 条首屏请求、9 个循环」才是。

量化带来三个好处：

- 知道先做哪一块，而不是从最显眼的目录开始；
- 改完能对比，不靠「感觉清爽了」；
- 基线可以进文档，后来者能复核。

这一轮在动手前先做了取证：目录规模、引用方式、首屏请求、包体、循环分量。没有这组数字，后面的验收就无法成立。

## 二、存量与新增必须分开

成熟代码库不可能一次达标。规则如果要求「立刻全绿」，结局通常是被整体豁免。

更可执行的做法是：

| 对象 | 策略 |
|---|---|
| 新增代码 | 严格按新规则，违规即失败 |
| 存量代码 | 按基线冻结，不增长即可 |
| 存量下降 | 允许，并更新基线 |
| 豁免 | 必须登记原因与到期版本 |

这条规则适用于目录预算，也适用于循环依赖、深引用例外与公开入口缺失。它的本质是**把「理想状态」拆成「当前不许变坏 + 逐步变好」**。

## 三、入口要回答两个不同的问题

一个 feature 的入口同时承担两种职责，很容易做坏：

- 页面路由需要「这个页面怎么用」；
- 其他域需要「这个能力怎么复用」。

前者通常只需要一个页面级组件，后者可能按能力分成若干组。把两者合成一个 `export *` 入口，就会出现「页面引一个组件，整个域都被拉进包体」的问题。

两级入口是更稳的结构：

```text
根入口  → 页面 / 宿主级组件
子域入口 → 跨域能力（runtime / ui / settings / bridge ...）
```

根入口小，页面包体可控；子域入口清晰，跨域引用有明确落点。

## 四、barrel 是导航层，不是收纳桶

`export *` 写起来最省事，但它给了打包器一个过大的起点。

这一轮的实测回退很典型：第一版全量 `export *`，设置页从 457 kB 涨到 513 kB，工作流详情从 386 kB 涨到 541 kB；收紧为「根入口只导页面、子域只导必要能力」后，回到 472 / 387 kB。

barrel 的正确用法：

- 只做 `export` / `export type`，不写运行逻辑；
- 只导出跨域确实需要的符号；
- 内部组件、内部 hook、测试夹具不导出；
- 超过行数上限时按子域再拆一层；
- 同域内部禁止反向引用自身 barrel。

## 五、先改请求时机，再谈合并接口

页面请求多，默认建议往往是「加聚合接口」。但在本地优先的桌面应用里，请求走本机回环，往返成本低；聚合端点带来的契约耦合与失效维护成本反而更高。

更便宜的路径是先做两级：

1. 页面级 facade，把散落的查询收进一个 hook；
2. 可见区触发查询，未进入视口的面板不发请求。

设置页做到第二级后，首屏 distinct GET 从 22 降到 7，峰值并发从 15 降到 4，响应体从 45 KB 降到 5.6 KB；接口零改动。

聚合端点不是被「感觉不需要」否决的，而是按准入清单逐条对照后否决：剩余 7 条请求分属不同资源与消费方，聚合会让页面生命周期耦合到服务端编排，收益不抵成本。

## 六、门禁要能自测，错误要能指导修复

门禁脚本本身也会写错。没有自测的规则，很容易变成「看起来在检查，实际什么都没查」。

这一轮的两个脚本都带 `--self-test`：构造临时目录，放入一个跨域深引用、一个自身 barrel 反向导入、一个三模块环，断言能检出；再把环登记进基线，断言能放行。

错误输出也要可操作：

| 要素 | 作用 |
|---|---|
| 错误码 | CI 日志可检索，文档可引用 |
| 位置 | 开发者能直接跳过去 |
| 实际值 | 知道差多少，不是只知道失败 |
| 处理建议 | 第一次遇到的人知道下一步 |

门禁的价值不在于「拦住」，而在于「拦住之后知道怎么改」。

## 七、规则要和项目阶段匹配

同一个规则，在不同阶段应该有不同的强度。

项目刚起步、只有几个环时，直接要求零循环是合理的；项目已有大量存量时，先冻结基线、禁止新增更现实。

目录预算也一样：新项目可以直接 ≤12；成熟项目先冻结存量，再按域下降。

这一轮结束时，仍有 12 个目录 ≥20 个文件、8 个循环分量。这不是「没做完」，而是按阶段选择的结果：先解决最影响迭代的 12 个重点目录，其余登记为后续版本。把边界写进验收文档，比假装全部达标更可信。

## 八、哪些做法这次不成立

复盘也要记录失败或代价：

| 做法 | 结果 | 调整 |
|---|---|---|
| 全量 `export *` 入口 | 包体回退 10%–40% | 根入口页面级，子域按能力收敛 |
| 一步完成移动 + 入口 + 根导出 | 失败时无法定位 | 拆成移动、子域入口、根转发三步 |
| 只靠 typecheck 找引用 | mock 路径漏改 | 单独搜索 `vi.mock`、动态导入、夹具路径 |
| 只改测试超时 | 门控后仍失败 | 增加「滚到分组」的等待辅助函数 |
| 追求一次清零循环 | 不现实 | 基线冻结 + 禁止新增 |

这些调整都不是理论推导，而是构建、测试或 e2e 实际失败后做出的。

## 九、下一步

结构治理没有终点，但可以有明确的下一批：

1. 继续分区剩余的大目录，优先 `core/ingestion` 与一个 P1 目录，把 ≥20 文件目录降到 10 个以内；
2. 按域清理存量循环，先处理真实运行时环，再处理类型环与 barrel 环；
3. 把架构文档的目录地图与门禁基线做成可更新流程，避免文档落后于代码；
4. 新功能按「落点、入口、跨域依赖、测试位置、目录预算」五项清单检查。

结构工作的最终目标不是「目录好看」，而是让下一次修改的认知成本可预测。只要这个成本在下降，结构治理就是有效的。
