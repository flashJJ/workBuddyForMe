# 首屏 22 条 distinct 请求：先改请求时机，再谈合并接口

一个设置页，一次挂载三十多个面板。每个面板都有自己的查询，打开页面后，网络面板里很快出现一长串 GET。

直觉会说：接口太碎了，合并一下。但这个直觉跳过了两个问题：首屏到底发了多少条 **不同** 的请求？其中有多少是「打开页面就必须发」的？

这一轮只改了请求时机，没有合并任何接口，就把设置页首屏的 distinct GET 从 22 条降到 7 条。

## 一、先把「请求多」拆成三个指标

总请求数会骗人。数据获取库本来就会对相同 query key 去重，同一个接口被多个面板消费不一定浪费；真正影响首屏的是另外三个指标：

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| distinct GET 路径 | 首屏请求了多少个不同资源 | 决定服务端压力与瀑布深度 |
| 峰值并发 | 同一时刻最多有多少请求在飞 | 决定首屏争抢带宽与连接池的程度 |
| 响应体总量 | 首屏拿回多少字节 | 决定解析与渲染成本 |

测量口径必须固定，否则前后数字不可比。这次统一为：生产构建 + 本地启动 + mock 模型 + 全新数据根 + 已完成首启引导 + 1280×800 视口 + 水合后观察 8 秒。

基线结果：

| 指标 | 数值 |
|---|---:|
| API GET 总次数 | 29 |
| distinct GET 路径 | 22 |
| 峰值并发 | 15 |
| 响应体总量 | 45,219 B |

29 次请求里只有 22 条不同路径，说明去重已经在工作；但 22 条不同资源同时出现在首屏，仍然过高。

## 二、请求是从哪来的

把 22 条路径按来源分组，会发现一个很朴素的事实：**大部分请求来自还没被看到的面板**。

设置页在视觉上分成四个大分组：外观、对话、工具、数据。打开页面时只显示顶部基础区，四个分组都在下方。但代码里所有分组是一次性挂载的，每个面板的查询在挂载时立即执行。

于是首屏请求的构成是：

```text
页面基础区 + 全局壳层：7 条
尚未进入视口的分组面板：15 条
```

也就是说，用户还没滚到那里，数据已经在路上。这不是接口设计问题，是挂载与请求绑定的问题。

## 三、只改「何时请求」，不改「请求什么」

最直接的方案是懒挂载：不可见的分组不渲染，滚到了再挂载。但它会带来副作用：

- 面板 DOM 不存在，页面内锚点跳转找不到目标；
- 设置页的搜索/定位逻辑依赖面板已渲染；
- 折叠、展开与滚动的布局高度会跳变。

所以这次选择更小的改动：**面板照常挂载，只把查询的 `enabled` 与可见性绑定**。

实现分三层：

```text
PanelVisibilityGate   容器：IntersectionObserver 观察，首次进入视口后置可见
usePanelVisible       读取当前门控状态；没有 Provider 时默认 true
useVisibleQuery       包装 useQuery，把 enabled 与可见态合并
```

关键参数与语义：

| 项 | 取值 | 理由 |
|---|---|---|
| `rootMargin` | 200px | 提前约一屏预取，滚到分组时不出现空白 |
| 可见态 | 一次性，滚出不回退 | 避免来回滚动导致查询反复启停 |
| 无 Observer 环境 | 直接可见 | 失败安全，不因门控丢数据 |
| 不在门控内的页面 | 默认可见 | 对话、工作流等页面行为零变化 |

`useVisibleQuery` 不改变 query key、不改变请求函数、不改变缓存策略，只把 `enabled` 变成「可见且原 enabled 为真」。调用点因此可以机械替换，不需要理解业务。

## 四、三处绕过数据获取库的请求

大部分面板走统一的查询 hook，替换是机械的。但有三处直接在 `useEffect` 里发请求：

- 情绪详情；
- 关系等级；
- 语音设置里的系统信息。

这些请求不经过查询库，门控管不到。处理方式是让它们也读取 `usePanelVisible`，不可见时不发。否则会出现「查询被门控拦住，但直接请求仍然照发」的漏洞。

## 五、结果与「没有丢数据」的证明

改造后的首屏：

| 指标 | 基线 | 改造后 | 变化 |
|---|---:|---:|---:|
| GET 总次数 | 29 | 9 | −69.0% |
| distinct 路径 | 22 | 7 | −68.2% |
| 峰值并发 | 15 | 4 | −73.3% |
| 响应体 | 45,219 B | 5,651 B | −87.5% |

只看首屏数字还不够，还要证明「该有的数据仍然会到」。验证方式是滚到其余三个分组，统计累计路径：累计 22 条，与基线全量一致。

这说明门控只改变了时机，没有丢面板数据。如果累计路径少于基线，就说明有面板被永久跳过，那是 bug，不是优化。

## 六、e2e 为什么要改等待方式

设置页有十个左右的 e2e 用例，原来在页面打开后直接断言分组内的数据或控件。门控之后，这些分组还没进入视口，请求没发，断言自然失败。

处理原则是：**只改测试的等待方式，不改产品文案与结构**。

做法是加一个辅助函数，把目标分组滚入视口，再等待数据出现。断言内容、持久化语义、交互步骤都不变。这样测试仍然在验证用户真实路径——用户也是滚到那里才会看到那些控件。

## 七、包体为什么没有明显变化

门控本身只增加了一个很小的 Context 与包装函数，不引入新依赖。设置页 First Load JS 从 457 kB 到 472 kB，主要来自入口拆分与少量共享代码，仍在 5% 门槛内。

这也说明「减少请求」和「减少包体」是两件事：前者靠时机，后者靠依赖边界。不要指望一个方案同时解决两个问题。

## 八、可复用的做法

如果另一个页面也有类似问题，可以按这个顺序处理：

1. 固定测量口径，先量 distinct 路径、峰值并发、响应体；
2. 按视觉分组找出「未进入视口却已请求」的部分；
3. 优先用可见性门控，保留 DOM 与锚点；
4. 门控做成一次性，避免滚动抖动；
5. 检查绕过数据获取库的直接请求；
6. 用「累计路径与基线全量一致」证明没有丢数据；
7. 最后才评估是否需要聚合端点。
