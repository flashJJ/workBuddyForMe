# 移动式重构怎么保证测试断言零改动

判断一次「只移动文件」的重构是否安全，最有力的证据不是代码评审，而是测试：用例数量不变、断言不变、全部通过。

这句话说起来简单，做起来要处理很多细节。测试和实现之间的耦合，往往比实现与实现之间更深：导入路径、mock 路径、快照位置、夹具相对路径，任何一处没跟着搬，测试就可能「通过但测的是空气」。

## 一、测试是行为不变的证据

搬家前先定一条硬规则：**测试文件跟着实现文件一起移动，只允许改 import 路径，不允许改断言。**

为什么断言不能改？因为一旦允许「顺手调整期望值」，就无法区分两种情况：

- 文件真的只是换了位置，行为没变；
- 文件换了位置，同时行为被悄悄改了，测试被改成配合新行为。

前者是重构，后者是伪装成重构的功能变更。评审时几乎看不出来，但风险完全不同。

所以流程是：

```text
移动实现文件
移动对应测试文件
只改写 import / mock 路径
跑该包单测
比较用例数量与断言内容
```

比较断言内容可以很机械：统计 `expect(` 行数、快照文件数量、用例标题列表，前后必须一致。不一致就停下来查原因。

## 二、测试会耦合哪些东西

搬家时容易断的耦合点，比想象中多：

| 耦合点 | 例子 | 是否会被 typecheck 发现 |
|---|---|---|
| 静态 import | `import { x } from '../foo'` | 是 |
| `vi.mock` 字符串 | `vi.mock('@/lib/hooks/use-x')` | 否 |
| 动态 import | `await import('../foo')` | 有时 |
| 快照文件位置 | `__snapshots__/foo.test.ts.snap` | 否 |
| 夹具相对路径 | `readFileSync(new URL('./fixture.json', ...))` | 否 |
| 测试环境初始化 | setup 文件里的全局 mock | 否 |
| 包级子路径 | `@pkg/domain/subpath` | 是 |

`vi.mock` 是最危险的一类：字符串不参与类型检查，路径错了测试仍然能跑，只是 mock 不再命中，代码走了真实实现。如果真实实现刚好也能返回预期结果，测试会静默通过；如果返回不同结果，测试失败的位置又看起来像业务 bug。

## 三、mock 路径的三次修正

这次搬家遇到三类 mock 问题，处理方式不同。

**第一类：mock 具体文件，文件搬走了。**

```text
原：vi.mock('@/lib/hooks/use-provider')
新：vi.mock('@/lib/hooks/provider')
```

目标从文件变成域入口后，mock 路径要跟着入口走。这里还有一个副作用：域入口会聚合多个 hook，mock 整个入口可能把不相关的 hook 也替换掉。

**第二类：需要保留真实导出。**

域入口聚合后，测试只想覆盖其中一个函数，其余保持真实：

```ts
vi.mock('@/lib/hooks/provider', async (importOriginal) => {
  const actual = await importOriginal<typeof import('@/lib/hooks/provider')>();
  return { ...actual, useProviders: vi.fn() };
});
```

`importOriginal` 保住其余导出，避免「mock 一个入口，整个域都变成空实现」。

**第三类：同名 hook。**

一个域里有两个同名 hook，一个对外、一个内部。入口只导出对外那个；测试如果还 mock 内部文件，会与入口引用不一致。处理方式是让测试也走入口，内部 hook 不进入公开面。

## 四、快照与夹具要一起搬

快照文件的位置通常跟测试文件绑定。测试文件移动到子域后，快照目录也要一起移动，否则测试会生成一份新快照，旧快照留在原地变成垃圾。

夹具同理。相对路径的夹具引用不会报类型错误，搬家后路径失效，测试在运行时才失败。处理方式是把夹具与测试放在同一子域，或者把公共夹具上移到测试工具目录。

这次有一个测试的快照目录随测试一起移动，移动后快照内容零变化，测试直接通过。这是最好的结果：说明快照只依赖输入，不依赖文件位置。

## 五、唯一一次「改代码不改断言」的例外

搬家过程中有一个与时间有关的测试失败：它把「当天」写死在用例里，下午运行会因为「时间已过」而失败。

这不是搬家引入的问题，而是原本就存在的脆弱测试，只是恰好在这个时间点暴露。修复方式是把日期改成固定的未来日期，断言完全不变。

这类修复要单独记录，不能混进「搬家很顺利」的叙事里。它提醒我们：测试全绿不等于测试健康，时间、时区、随机数、文件系统顺序都可能让测试在不同时刻表现不同。

## 六、e2e 的等待方式与断言

单元测试之外，生产模式 e2e 也会受影响。设置页改成可见区触发查询后，十个左右的用例在页面打开后立即断言分组内容，而分组还没进入视口。

处理原则与单测一致：**只改等待方式，不改断言。**

做法是加一个辅助函数，把目标分组滚入视口并等待数据出现，然后再执行原来的断言。用户真实路径也是先滚到分组才看到内容，所以这不是「为测试而测试」，而是让测试更贴近真实使用。

## 七、如何核对「只改了 import」

搬家完成后，可以做一次机械核对：

1. 统计每个包的用例数量，与搬家前一致；
2. 搜索测试文件里是否还有旧路径字符串；
3. 搜索 `vi.mock` 的路径，逐个确认目标存在；
4. 检查快照目录是否还有孤立文件；
5. 用 diff 查看测试文件变更，除了 import / mock 行，不应有其它改动。

这五步都不需要理解业务，适合在每一批移动后重复执行。

## 八、结果

最终全量单测从 2879 增加到 2882，增加的三例来自两个真实 bug 修复，不是搬家；搬家本身没有删除、跳过或改写任何用例。生产模式 e2e 139 例全部通过，桌面冒烟保持 10/11 的既有基线。

测试没有变成搬家的阻力，反而成了搬家的验收工具。这正是「移动式重构」能成立的原因：**用不动的断言，证明动了的位置没有带走行为。**
