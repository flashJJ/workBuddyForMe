# 复用能力包管道：新增一个内容类型为什么不用新安装器

给应用加“可安装内容”，最直觉的做法是写一套新安装器：新目录、新清单、新校验、新升级逻辑。

我们的桌面 AI 应用是本地优先、单人开发、Electron + Next.js 交付的私人助手。能力包管道已经跑了很久，安装、校验和、签名、升级、回滚、健康检查都在。内容包如果另起一套，等于把这些能力再实现一遍。

所以这一轮的原则是：**内容包就是能力包，只增加一个 kind。**

## 一、新 kind 需要补什么

现有管道按 `manifest.kind` 分发 effect。新增 `motion-pack` 只需要补四样：

1. 能力类型枚举增加 `motion-pack`。
2. 权限枚举增加 `motion:pack`。
3. entry 固定为 `payload/motion-pack.json`。
4. 注册一个 effect handler。

其余全部复用：

- ZIP 解包与路径白名单。
- manifest 校验。
- 文件校验和与可选签名。
- 安装、启用、停用、卸载。
- 升级预检、回滚与健康检查。

管道没有为内容包开特例，这是刻意的：特例一多，升级与回滚就会出现两套行为。

## 二、payload 体积也要有上限

内容包与其它能力包共用单包体积上限，动效 payload 额外限制在 256 KB。

为什么单独限制？因为动效内容会被聚合进运行时快照，体积直接对应解析与内存成本。256 KB 足够放下几十个姿势与动作，又能阻止“把整个动作库塞进一个包”。

上限在安装前检查，不满足直接拒绝，不落盘。

## 三、enable 只做校验，不搬运内容

很多能力的 enable 会把资源搬到目标目录、写数据库行或发布版本。`motion-pack` 的 enable 很轻：

```ts
export function enableMotionPack(manifest, packDir): string {
  const payload = readMotionPackPayload(packDir);
  assertUnique('姿势', payload.poses.map((p) => p.id), builtinPoseIds);
  assertUnique('动作', payload.motions.map((m) => m.id), builtinMotionIds);
  assertUnique('行为', payload.behaviors.map((b) => b.id), builtinBehaviorIds);
  return manifest.id;
}
```

它只做三件事：解析 payload、检查类型内重复、检查与内置内容冲突。内容本身仍然留在包目录里，等聚合时再读。

这样做的好处是 enable 与 disable 对称：启用不搬资源，停用也不需要清理资源。

## 四、disable 为空不是偷懒

`disableMotionPack` 是空函数。第一次看到会以为是漏了实现。

实际上内容的可见性由能力行状态决定：聚合服务只读取 `status = enabled` 的包。停用后，下一次读取快照自然不包含它。包目录仍然保留，重新启用不需要重新安装。

这与“把内容复制到全局目录、停用时删除”的方案相比，少了一次拷贝、少了一类残留、也少了一类“删除失败”的错误路径。

## 五、升级与回滚为什么不用改

现有升级流程会：

1. 用新 ZIP 做依赖与版本预检。
2. 替换 manifest 与版本元信息。
3. 状态回落 disabled，effect 置空。
4. 重新启用时再次执行 enable 校验。

对 `motion-pack` 来说，这套流程天然成立：

- 新 payload 在启用时重新解析。
- 重复 id 与内置冲突会重新检查。
- 回滚到旧版本后，旧 payload 仍然在旧目录里。

没有内容缓存需要失效，也没有聚合表需要迁移。这是“复用管道”带来的最大收益。

## 六、签名与校验和不需要新协议

内容包与其它能力包使用同一套文件校验和与签名逻辑：

- manifest 声明文件清单与哈希。
- 安装时逐文件校验。
- 可选签名验证。
- 健康检查可以重新计算。

如果内容包另起格式，签名验证就要写第二套 canonicalization，很容易出现“两个包都签名了，但只有一种能被验证”的情况。

复用管道让安全边界保持一致：能力包能做的事，内容包才能做；能力包不能做的事，内容包也不能做。

## 七、样例包与生命周期测试

仓库里保留了一个最小样例包，只含一个右臂姿势。它有两个作用：

- 文档示例：用户知道最小合法包长什么样。
- 生命周期测试：安装 → 启用 → 停用 → 再启用 → 卸载。

测试重点不是“内容能播”，而是“状态转换不残留”：

- 停用后聚合结果不再包含该包。
- 重新启用后内容回来。
- 卸载后目录与能力行都消失。
- 重复启用不会产生重复内容。

## 八、这个选择的代价

复用管道不是没有代价：

- 内容包必须遵守能力包的 manifest 结构，哪怕有些字段对它没意义。
- 单包体积上限与权限模型也一并继承。
- 安装仍然是本地 ZIP，不做在线目录。

这些代价换来的是：一条链路、一套测试、一套回滚。对单人开发的项目，这比“每个内容类型都定制”更可持续。

## 九、结果

- `motion-pack` 完整复用 ZIP、校验和、签名、升级、回滚与健康检查。
- 启用只校验，不搬资源；停用无需清理。
- 坏包整包拒绝，不改变现有能力行状态。
- 原有六类能力零回归，零数据库迁移。
