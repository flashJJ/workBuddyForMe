# 抽出内部动效包：纯数据、多入口与默认同源

动效内容最初长在 web 端的一个目录里。

我们的桌面 AI 应用是本地优先、单人开发、Electron + Next.js 交付的私人助手。动效相关代码在 `animation/` 下，姿势、动作、行为、执行器、渲染适配全混在一起。功能能用，但有两个问题越来越明显：

- 目录有直接文件数量预算，再加内容类型就会顶到上限。
- core 包要校验内容包 payload，却无法引用 web 端的类型。

这一轮把“纯数据部分”抽成内部包，渲染适配继续留在 web。

## 一、先划线：什么进包，什么不进

抽包最怕把运行时一起搬走。我们先用一句话划线：**包只放数据与纯函数，放不下 three.js 与 PIXI。**

进包的内容：

- 姿势、动作、行为的类型定义。
- 三张注册表与查表纯函数。
- `MotionContent` 快照与默认内容。
- payload 的 zod schema。
- 版本号生成等纯计算。

不进包的内容：

- VRM 动画运行时。
- Live2D 与 VRM 的适配器。
- 执行器注册与渲染循环。
- React 组件与 hooks。

这条线定下来之后，包可以同时被 core 与 web 引用，而不会把渲染依赖拖进服务端。

## 二、多入口导出，按用途拆

内部包不是只暴露一个 index。我们用子路径导出把用途拆开：

```json
{
  "exports": {
    "./contracts": "./dist/contracts.js",
    "./poses": "./dist/poses/index.js",
    "./motions": "./dist/motions/index.js",
    "./behaviors": "./dist/behaviors/index.js",
    "./content": "./dist/content.js",
    "./pack": "./dist/pack.js"
  }
}
```

这样调用方可以只引用自己需要的部分：

- 运行时只引用 `/content`，不碰 zod。
- 校验侧只引用 `/pack`，不碰渲染相关类型。
- 具体内容表按 `/poses`、`/motions`、`/behaviors` 分开。

多入口构建用 tsup，每个入口独立产物。好处是 tree-shaking 更彻底，也避免“引一个 schema 把整张动作表带进来”。

## 三、Next.js 的接线

内部包是 workspace 依赖，Next.js 默认不会转译 `node_modules` 里的 TS 产物。需要在配置里显式声明：

```js
transpilePackages: ['@app/motion']
```

同时在 web 的 `package.json` 增加 workspace 依赖。两处缺一不可：只加依赖会在构建时报“无法解析”，只加转译会在安装时报“找不到包”。

这一步没有运行时魔法，但很容易漏。我们把构建验证放进常规门禁，避免下次再加内部包时重复踩坑。

## 四、兼容入口：先让旧 import 继续工作

web 端原来有一批从 `animation/` 深层引用的模块。一次性改完所有 import，风险大且噪音多。

这一轮先保留同名兼容入口：

```ts
// animation/content/index.ts
export * from '@app/motion/content';
```

`contracts`、`poses`、`motions`、`behaviors` 也各有一个 re-export 文件。这样旧代码不需要改，新代码可以直接引用包。

真正需要改的只有两个深层引用：手势与执行器直接拿了手指相关的常量。包在 `/poses` 入口里显式导出这些符号之后，改两行 import 即可。

兼容入口不是永久的。等目录预算或依赖检查提示时，再逐步把调用方迁到包入口。

## 五、默认内容必须同源

抽包最容易出现的隐性回归，是“默认内容复制了一份”。

如果包里的默认表是拷贝，web 静态表后续修改时，两边会慢慢漂移。表现是默认观感变了，但测试还在过。

我们的做法是：包直接引用原静态表，不拷贝、不重排；再写一条断言锁住引用相等：

```ts
expect(DEFAULT_MOTION_CONTENT.poses).toBe(POSES);
```

这条断言看起来很笨，但它能防止未来有人为了“解耦”而偷偷深拷贝，导致默认路径分叉。

## 六、验证顺序

抽包属于重构，验证顺序比新功能更严格：

1. 默认内容与内置表同引用。
2. 动效 golden 快照零差异。
3. web 端原有动效与剧本测试不改，直接通过。
4. core 侧 payload 校验可以引用包类型。
5. 构建产物能同时被 Next.js 与 Node 侧解析。

全量测试最终覆盖 717 个测试文件、4108 项。抽包本身没有新增运行时行为，所有断言都应保持原样。

## 七、抽包的边界

- 不拆多仓，不发布 npm。
- 不把执行器搬进包。
- 不改动效的公开数据结构。
- 不改变默认内容的顺序与引用。

内部包的价值是“共享契约”，不是“共享一切”。只要渲染适配还在 web，包就能保持轻量、可测试、可被服务端引用。

## 八、结果

- 动效类型与默认内容成为可复用契约。
- core 与 web 读同一份类型，payload 校验不再靠手写镜像。
- 旧 import 通过兼容入口继续工作。
- 默认 golden 零差异，零数据库迁移。
