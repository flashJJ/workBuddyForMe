# 能力依赖拓扑：环检测、稳定排序与健康报告

能力包一多，依赖就会变成真实问题。

我们的桌面 AI 应用是本地优先、单人开发、Electron + Next.js 交付的私人助手。能力包 manifest 里一直有 `dependencies`，但早期只做存在性检查：被依赖的包没装，报错；装了但没启用，启用时再报错。没有版本约束，也没有环检测。

当内容包开始引用其他包时，这套检查不够用了。这一轮把依赖关系升级成一张可计算的图：安装、启用、升级前统一预检，健康报告也能解释“为什么这个包不可用”。

## 一、依赖边只有一种解释

设计依赖图时，最先要定的是“边代表什么”。

我们的选择是：**依赖就是能力包 id。** 不引入“服务标识”依赖，也不允许一个包声明“我需要一个提供某能力的实现”。

原因很实际：同一条边如果既能按包 id 解析，又能按服务标识解析，安装期就会出现两套图、两种错误、两套测试。当前没有跨包服务发现的需求，不值得为假设的需求增加解析分支。

manifest 的样子大致是：

```json
{
  "id": "example.pack",
  "version": "1.2.0",
  "dependencies": [
    { "id": "example.base", "version": "1.0.0" }
  ],
  "coreVersion": "3.5.0"
}
```

`dependencies[].version` 可选，表示精确版本；`coreVersion` 可选，表示最低应用版本。

## 二、环检测：返回一条人能看懂的路径

环检测用 DFS 三色标记。发现回边时，不是只返回“有环”，而是把栈里从该节点到当前节点的一段截出来，再补上起点，得到首尾相同的路径：

```ts
// a → b → c → a
findDependencyCycle(graph);
// ['a', 'b', 'c', 'a']
```

这条路径很有用：错误信息可以直接展示“哪个包经由哪条链依赖回自己”，用户不需要自己翻 manifest。

检测范围是“已安装 + 待安装”的完整图。只在安装处检查不够，因为升级可能引入新的依赖边；启用也可能因为状态变化形成环。

## 三、稳定排序：同层按 id 排序

拿到无环图之后，用 Kahn 算法做拓扑排序。关键细节是：**同一层的节点按 id 排序后再入队。**

如果不排序，结果依赖 Map 的插入顺序，同一组包在不同机器上可能得到不同顺序。顺序不稳定会带来两类问题：

- 测试偶发失败，难以复现。
- 启用顺序在用户界面上跳动，看起来像随机。

排序本身只多几行代码，但把“可复现”变成了默认属性。

## 四、预检放在三个入口，而不是一个

依赖预检最终收敛成一个函数：`assertDependencies`。安装、启用、升级三处都调用它。

三处的检查内容一致：

- 依赖包是否已安装。
- 依赖包是否已启用。
- 版本是否匹配。
- 整张图是否有环。
- `coreVersion` 是否高于当前应用版本。

把检查放在服务层而不是路由层，好处是测试可以直接调用服务，不需要构造 HTTP 请求；也不会出现“某个入口忘了检查”的情况。

## 五、不自动启用依赖

有人会问：既然知道依赖顺序，为什么不一键把依赖都启用？

我们刻意没做。原因是启用不是无副作用的动作：

- 不同能力类型的启用会写不同资源。
- 权限与用户授权绑定在启用动作上。
- 自动启用会让用户在不了解副作用的情况下扩大权限面。

所以预检只输出两样东西：拒绝原因，以及依赖优先顺序。是否启用依赖，仍然由用户决定。

## 六、健康报告：把图的问题说清楚

健康检查原来只覆盖目录、校验和、effect 目标与孤儿目录。这一轮增加依赖问题：

- 依赖缺失。
- 依赖未启用。
- 依赖版本不匹配。
- 依赖环，新增问题码 `dependency_cycle`。

环检测按整张已安装图计算一次，而不是每个包各算一次。这样报告里不会出现同一个环被多个包重复描述，也不会因为遍历起点不同给出不同路径。

健康报告仍然是只读的：它解释问题，不自动修复。修复动作留给用户，避免“检查一次就改了状态”的惊吓。

## 七、测试怎么覆盖

依赖拓扑的测试分四层：

1. 纯函数：环路径、排序稳定性、版本比较。
2. 服务：安装缺依赖、启用禁用依赖、升级引入环。
3. 健康：四类问题码与路径可读性。
4. 回归：原有六类能力的安装、启用、停用、卸载测试不改。

其中排序稳定性用“同层多个节点”的图来测，连续跑多次断言结果一致。环检测则同时测自环、双节点环与三节点环，确保路径截取没有差一错误。

## 八、结果与边界

- 缺依赖、依赖未启用、版本不匹配与环都在安装/启用/升级前拒绝。
- 依赖顺序稳定可复现，不依赖 Map 插入顺序。
- 健康报告能定位到具体包与具体环路径。
- 原有能力行为零回归，零数据库迁移。

边界也很明确：这一轮只做“包依赖”，不做服务发现；不自动启用依赖；不做依赖图的可视化编辑器。
