# 平台化一期复盘：七条让“可安装内容”安全落地的做法

平台化很容易停在演示阶段：注册表有了、接口有了，但真实内容装不进来，或者装进来运行时读不到。

这一轮做的事情不算小：能力依赖拓扑、动效契约抽包、内容包类型、会话快照、发布校验。做完之后，一个内容包可以从 ZIP 进来，经过预检、安装、启用，最后进入骨骼动画。

下面七条，是这轮最值得留下的做法。

## 一、先接管道，再接内容

新增内容类型时，最贵的不是 payload 设计，而是安装链路。

现有能力包管道已经有 ZIP、校验和、签名、升级、回滚与健康检查。如果内容包另起一套，每一条都要重写，而且要维护两套安全边界。

我们的顺序是：

1. 确认现有管道能承载内容。
2. 只增加 kind、权限、入口与 effect。
3. 用样例包跑通生命周期。
4. 最后才设计内容格式的细节。

先接管道的好处是风险前置：如果管道承载不了，早就会发现，不会等到 payload 写完才推翻。

## 二、契约只放数据，执行器留在内核

内容包一旦允许代码，安全模型就完全变了：沙箱、权限、资源限制、崩溃隔离，全部要重新设计。

这一轮把 payload 限定为数据：

- 姿势是骨骼旋转。
- 动作是关键帧。
- 行为是阶段与轨道。
- 所有字段用严格 schema 校验。

执行器仍然由内核注册，内容只能引用已注册的 id。这样“内容包能做什么”由内核决定，而不是由包里的代码决定。

## 三、刷新用会话边界，不用热替换

热替换听起来体验更好，但实现成本高：

- 正在播放的动作可能引用旧内容。
- 姿态层缓存了上一帧。
- 混合器有淡入淡出队列。

会话级快照把复杂度挡在边界外：会话内不变，下一次挂载读取新内容。

这不是妥协，而是明确的产品语义：内容更新是“下次打开生效”，不是“当场变形”。用户能理解，测试也好写。

## 四、默认值必须同源

抽包时最容易出现的隐性回归，是默认内容被复制一份。

复制之后，原表更新不会同步，默认观感慢慢漂移，而测试仍然通过。我们的做法是直接引用原表，并写一条引用相等的断言。

同样的原则适用于默认版本约束：`coreVersion` 缺省时不检查，保证旧包不因新增字段全部失效。

默认值同源，是“重构不改变行为”的最低保障。

## 五、门禁前置，行数也是设计

这轮有两处很典型的撞线：

- 控制器文件 302 行，超出门禁 2 行。
- 姿态层文件 306 行，超出 6 行。

处理方式不是调高上限，而是压缩：合并 import、去掉多余空行、把单行语句合并。改完都回到 300 行以内。

门禁的价值不在于数字本身，而在于它迫使你在提交前想清楚“这段代码放哪里”。如果没有门禁，这两处会以“以后再拆”的形式留下，最后没人再拆。

## 六、校验和要能复算，不是只生成

生成一个 `SHA256SUMS.txt` 很容易，难的是让别人能复核。

这一轮把复核做成脚本的一部分：

- `--check` 重新计算所有产物。
- 与清单逐行比对。
- 核对构建信息的版本与文件集合。
- 任何不一致退出 1。

我们还用篡改文件的方式验证了失败路径。只测成功路径的校验工具，等于没有校验。

## 七、先证明没变，再证明能变

这一轮改动跨 core、shared、web、构建与脚本，回归面很大。

验证顺序是：

1. 默认内容与内置表同引用。
2. 默认动效 golden 零差异。
3. 原有能力测试不改，直接通过。
4. 再验证新能力：安装、启用、停用、卸载、升级。
5. 最后验证运行时与发布校验。

如果反过来先测新能力，很容易在默认路径已经变了的情况下继续往前，最后分不清是重构成功还是碰巧能跑。

## 八、指标对账

| 项 | 结果 |
|---|---|
| 能力类型 | 原有类型零回归，新增内容包类型 1 类 |
| 依赖预检 | 缺失、禁用、版本不匹配、环、最低应用版本 5 类 |
| 内容快照 | 默认 + 启用包；无包时同引用 |
| 刷新方式 | 会话级，下次挂载生效 |
| 测试 | 9 个包 719 文件 4115 项 |
| 迁移 | 0 |
| 门禁 | 类型 / lint / 行数 / 结构 / 循环 / 文档框图全绿 |
| 发布校验 | 每产物 1 行 SHA256；构建信息可回溯 commit |

## 九、Non-Goals 复盘

这轮明确不做的事：

- 运行时代码插件与 JS 沙箱。
- 内容热替换、场景包与道具包。
- 代码签名、自有更新源与双通道；拆多仓与独立 npm 发布。

不做不是保守，而是把风险留在可回滚的范围内。内容包可以随时退回静态表，快照可以退回默认内容，校验清单不影响安装本身。

## 十、下一轮可以做什么

优先把场景包/道具包、工具描述符与 provider 能力元数据用真实内容验证，再评估代码签名与自有更新源。顺序原则仍然是：先接管道，再放内容；先证明没变，再证明能变。

## 十一、一句话收尾

平台化不是把所有东西都变成插件，而是把“新增内容必须改内核”的地方，逐个变成“安装即可”。

这一轮把动效内容走通了。下一步要做的，不是把口开得更大，而是让每个已经打开的入口都能稳定工作。

小步不是慢，小步是每一步都能回滚。
