# 记忆不只要记得住，还要管得住

一个本地优先的桌面 AI 应用用上三个月，长期记忆会变成这样：设置里躺着一长串条目，用户不知道总共有多少、哪些已经被更新取代、上一轮到底有没有召回成功。

再往后会遇到三个更具体的问题。

用户说「我不吃香菜」，系统记住了，但把「不吃香菜」和另一条偏好合并错了。用户想改，只能去记忆列表里一条条翻，没有「刚才那条识别错了」的入口。

开发者想调召回权重，翻遍项目只找到一组 golden 用例和单测。改之前是多少、改之后是多少，没有对照。

数据库里的审计事件每个月涨几万条，只写不删。用户不会感知，但备份越来越大、查询越来越慢。

这四件事看起来分散，其实是同一个主题的四个面：记忆已经能写、能召回，但还缺一层治理。

## 一、数据在接口里，用户看不见

上一版已经把统计接口做出来了：总量、活跃、归档、被取代比例、零召回率、召回总轮次、用户纠正次数。

问题是它只到接口层。设置页的记忆分组仍然只有一个列表和几个按钮，用户想知道「我的记忆健康吗」，得自己发请求看 JSON。

对普通用户，这等于没有。对开发者，这也意味着一个尴尬的事实：接口写完了，但没人验证它在真实页面上是否说得通。

## 二、事件表只写不删

每次记忆写入、取代、归档、召回失败，都会往审计表里写一条事件。它让「这条记忆怎么来的」可追溯，是上一版刻意做的能力。

但审计表没有清理策略。一条记忆被修改十次，就有十条事件；一次会话召回五次，又有五条。长期运行，这张表线性增长，而且是只增不减。

直接删是最省事的做法，但会带来一个副作用：用户纠正次数会突然变少。因为这个数字原先就是数事件条数得来的。

## 三、约束写入没有撤销入口

过敏、忌口、带时间前缀的禁止、显式「记住」，这几类实时约束走的是纯规则，命中即写，优先级最高。

规则换来的高召回，必然有误判。比如「我最近有点过敏」不该被当成具体过敏原，「以后别给我推荐恐怖片」也可能只是一次性的说法。

误判一旦写进置顶约束，就会在之后每一轮被注入。用户唯一的补救是去记忆页找到那条、手动改状态。路径太长，而且用户未必知道该去哪找。

## 四、评测只靠单测

召回相关的 golden 用例一直在，但跑起来要起服务、调模型、请一个 LLM 当评委。成本高，所以平时不跑。

结果是：单测能保证「融合公式没写错」，却不能回答「这次调整之后，十二条问题里还有几条能进前三」。调权重只能凭感觉。

## 这一版只做四件事

1. **统计卡**：把已有接口接到设置页，七项指标加最近审计，前端只格式化。
2. **审计轮转**：过期事件先聚合成计数再删除，保留期可配，启动与每日各执行一次。
3. **约束撤销**：约束提前到完成帧之前写入，本轮就给出内联提示与撤销入口。
4. **本地评测**：一条命令跑 golden 集，输出命中率、零召回率与耗时，写本地报告。

一句话：**已有数据先让人看见，长期运行要能收口，识别错了要能撤回。**

## 为什么顺序是「读、清、撤、测」

统计卡只读，风险最低。先做它，可以尽早建立「页面数字等于接口数字」的信心，也能顺手发现接口字段的缺口。

审计轮转涉及一次迁移和计数一致性，单独一段做。它改的是数据生命周期，出问题时影响面比展示层大。

约束撤销要动完成帧契约和消息渲染，放在轮转之后，避免契约反复改。

评测是本地脚本，不参与发布门禁，最后补。

## 一条共同约束：不新增写入链路

四件事都在现有链路上做，没有新增记忆写入方式，没有改召回权重，也没有新增独立删除接口。

- 统计卡只读现有接口，最多给同一响应补一个可选字段。
- 轮转只新增一张聚合表和一条索引。
- 撤销复用已有的归档语义，不新开 DELETE 路径。
- 评测复用现有召回管线，不另写一套检索。

这条约束决定了成本：整版一次迁移、零接口破坏。

## 边界

不做线上评测看板，也不做服务端定时跑评测。

不做记忆图关系边与空闲整理。

轮转之后只保留聚合计数和最近审计，不保证逐条永久可回溯。

不做跨设备同步。

## 收尾

「记得住」是模型与检索的能力，「管得住」是工程能力。

前者决定用户愿不愿意继续聊，后者决定这个功能能不能跑上一年。这一版没有让记忆变聪明，只是让它变得可读、可清、可撤、可对照。

这四件事做完，长期记忆才算从「有个功能」变成「可以长期用」。
