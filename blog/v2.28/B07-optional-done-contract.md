# 给完成帧加一个可选字段

流式协议里，完成帧原本只做一件事：告诉前端「这一轮结束了」，附上完整正文与用量。

这一版要在它身上多带一样东西：本轮新记住的实时约束。

改动不大，但涉及一条老规则——已经发出去的帧，字段只能加，不能改。

## 完成帧的语义比字段更重要

完成帧不是普通数据帧，它是状态的终点。

前端收到它之后，会把流式中的临时内容替换成最终正文，结算耗时，清理等待态。任何一处解读不一致，都会导致「消息结束了但界面还在转圈」或者「正文丢了一截」。

所以给完成帧加字段，第一原则是：不能改变它作为终点的语义。

## 只加可选字段

新增字段长这样：

```ts
interface DonePayload {
  // 既有字段
  content: string;
  usage?: Usage;
  // v2.28 新增
  memoryNotices?: Array<{ id: string; content: string }>;
}
```

三条约束：

- 可选：没有新约束时，这个键根本不出现；
- 只读展示：前端不依赖它做任何状态判断；
- 不落库：它只存在于本轮的消息对象里，刷新后消失。

旧前端收到不认识的字段会忽略，完成语义不变。新前端在没有这个字段时，不渲染任何提示。

这就是「零接口破坏」的具体含义：不是接口没变，而是变化对旧消费方不可见。

## 为什么不下发完整记忆对象

完成帧里只放两个字段：记忆 id 和正文。

没有 kind、没有 score、没有审计信息、没有来源会话。原因有三个：

第一，提示只需要这两样。界面上要显示「已记住：用户对花生过敏」，再加一个撤销按钮，按钮只需要 id。

第二，流式契约越小越稳。每多一个字段，就多一份兼容责任。内部管理字段（重要度、召回分数）不应该出现在展示协议里。

第三，避免误用。如果下发了 score，前端迟早会有人拿它排序或过滤，而它的含义只有召回层清楚。

## 为什么不复用已有的 memories 事件

协议里已经有一个 `memories` 事件，为什么不再复用它？

因为两者语义相反：

- `memories` 是**回合前**的召回结果，回答还没开始生成，告诉前端「这一轮参考了哪些记忆」；
- `memoryNotices` 是**回合后**的写入结果，回答已经完成，告诉前端「这一轮新记住了什么」。

一个是输入，一个是输出。合并成一个事件，前端就要靠字段猜当前处于哪个阶段，反而更复杂。

事件按生命周期分，比按数据形状分更清楚。

## 不落库是刻意的

提示只在当前这一轮有效。

消息落库时，不保存 `memoryNotices`。刷新页面或重新打开会话，这条提示不会再出现，但记忆本身仍在，可以在设置页的记忆列表里看到。

为什么这样设计？

提示的作用是「此刻告知并允许撤销」。过了这一刻，用户已经进入下一轮，再显示一条历史提示没有意义，反而会让消息流变吵。

而记忆是持久的，撤销入口也不止一个：设置页的记忆列表同样可以归档。

所以这里做了一个明确的取舍：提示是临时的，记忆是持久的。两者不绑定。

## 空值与空数组都不渲染

前端组件的判断很简单：字段不存在、或者是空数组，都直接返回 null。

不加占位、不显示「本轮没有新记忆」。没有新约束是常态，常态不需要提示。

## 测试要覆盖三条路径

- 完成帧带两条提示：消息末尾渲染两段，带撤销按钮；
- 完成帧不带字段：消息结构与升级前完全一致；
- 完成帧带空数组：同样不渲染。

再加一条：旧消息从数据库读出来时没有这个字段，渲染不能报错。

这四条用例锁住的不是样式，而是契约的兼容边界。

## 边界

不保证提示与记忆条目一一对应到永久：撤销后记忆被归档，提示里的文字仍然保留在当前消息中，只是按钮变成「已撤销」。

也不做「本轮新增常规记忆」的提示。常规抽取在后台完成，时间上晚于完成帧，而且数量不可控，不适合塞进完成提示。

## 收尾

协议演进最安全的方式，是让新信息成为旧消费方可以忽略的附加项。

完成帧仍然是那个完成帧：收到它，这一轮就结束了。新增的字段只是让前端在结束的瞬间，多说一句「我记住了」，并且允许用户立刻反悔。
