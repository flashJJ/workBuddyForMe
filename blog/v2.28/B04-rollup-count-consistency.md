# 轮转之后，纠正次数不能变少

一个用户很认真地纠正过 42 次记忆。

某天应用做了一次审计轮转，把超过保留期的事件清理掉。用户再打开设置页，纠正次数变成 9。

数字没有报错，页面也没有异常。但用户的第一反应是：我的数据是不是丢了？

这类问题比崩溃更难解释，因为它看起来一切正常。

## 原来的计数方式

用户纠正次数原先是一个简单的计数查询：数审计表里 actor 是用户、动作是修改 / 归档 / 恢复 / 删除的事件条数。

简单，准确，只要事件还在。

问题是事件会被轮转清理。清理之后，这个数字就少了一块。

## 计数要改成两段相加

新的口径是：**在线事件 + 聚合存量**。

- 在线事件：还没过保留期、仍然逐条存在的事件；
- 聚合存量：已经过保留期、被压缩成计数的那部分。

两者相加，才是用户真正纠正过的次数。

这个改动只在一个查询函数里，但它决定了轮转能不能被接受。如果轮转会让用户看到数字缩水，那这个功能无论多省空间都不该上线。

## 轮转前后必须相等

用公式表达更清楚。

轮转前，计数等于全部在线事件：

`before = live`

轮转把其中过期的那部分 `expired` 搬进聚合表，于是：

`after = (live - expired) + rolled`

而 `rolled` 正好等于 `expired` 的条数。所以：

`after = live - expired + expired = before`

这个等式看起来是废话，但它是实现的目标。轮转代码只要漏掉一次「UPSERT 到聚合表」，等式就不成立，数字就会少。

测试也因此很直接：构造三条过期事件和两条在线事件，跑一次轮转，断言纠正次数仍然是五；再跑一次，仍然是五；清空记忆后，变成零。

## 清空也要同步

用户清空全部记忆时，会删除记忆条目和审计事件。

如果只删事件、不删聚合，统计卡上的纠正次数会保留一个永远清不掉的历史值。用户已经清空了一切，却还看到「纠正过 42 次」，这显然不对。

所以清空逻辑也改了：在一个事务里同时清空事件表和聚合表。

这类「同一份数据存在两个地方」的改动，最容易漏掉其中一个写入路径。轮转写入、清空删除、计数读取，三处必须同时改到。

## 幂等是必须的

轮转每天跑，也可能因为重启在启动时补跑一次。

对没有过期数据的情况，函数应该返回删除 0 条、聚合 0 个键，不产生任何副作用。

对同一批过期数据重复执行，第一次会聚合并删除，第二次查不到过期事件，自然返回 0。不会重复计数。

幂等不是额外功能，而是定时任务的基本要求：任何一次执行都可能被打断、重试、并发触发。

## 谁算用户纠正

计数只认四类动作：修改、归档、恢复、删除，并且 actor 必须是用户。

系统自己写入、取代、生命周期归档都不计入。这个口径在轮转前后保持一致——聚合表里也按同样的条件和动作过滤。

否则会出现另一种偏差：在线时只数用户动作，聚合后却把所有动作都算进去，数字突然变大。用户不一定能发现，但统计就失去了意义。

## 为什么值得为这个数字花力气

纠正次数是统计卡上唯一一个「用户参与度」指标。

总量、归档数、零召回率描述的是系统状态；纠正次数描述的是「用户愿不愿意维护这份记忆」。它下降，用户会怀疑数据丢失；它虚高，用户会觉得统计不可信。

一个指标要能用，前提是它在任何维护动作前后都稳定。轮转是这类维护动作里最容易破坏稳定性的一种，因为它真的在删数据。

## 边界

聚合只保留计数，不保留时间分布。也就是说，轮转之后无法回答「上个月纠正了几次」，只能回答「一共纠正过几次」。

如果以后需要时间分布，正确的做法是新增按月的聚合维度，而不是停止轮转、让原文无限增长。

## 收尾

删数据和保数字看起来矛盾，解法是把「数字」从「数据」里提前抽出来。

轮转删掉的是原文，留下的是计数；计数表和原文表由同一个事务维护，所以轮转前后能对上。

用户不需要知道后台做了什么，他只需要看到那个数字没有变。
