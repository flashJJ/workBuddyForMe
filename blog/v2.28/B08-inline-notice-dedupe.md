# 内联提示：一次最多两条，同一会话只说一次

系统记住了一条约束，用户理应知道。

但「知道」的方式有很多种：弹窗、toast、消息流里插一条系统消息、或者在助手回答末尾加一行小字。

这一版选的是最后一种，并且加了两条限制：一次最多两条，同一会话只说一次。

## 为什么不用弹窗和 toast

**弹窗**会打断流式输出。用户正在读回答，突然要处理一个对话框，体验很差；而且弹窗通常需要点「确定」，等于强迫用户为一条后台行为付出操作成本。

**toast** 会自己消失，且无法承载「撤销」这种需要二次确认的动作。用户还没看清就没了，撤销更无从谈起。

**系统消息**会把一条附带信息升级成对话内容，污染上下文，下一轮模型还可能把它当成用户说的话。

内联提示的好处是：它属于这一轮回答，跟着消息走，不打断、不消失、不占独立位置。

## 放在助手消息末尾

提示渲染在助手消息正文和用量信息之后，是一行小字：

`已记住：用户对花生过敏 · 撤销`

命中多条时用分号连接：

`已记住：用户对花生过敏 · 撤销；用户不吃香菜 · 撤销`

每条约束都有自己的撤销按钮，而不是一个「全部撤销」。因为用户可能只想撤掉其中一条。

放在末尾而不是开头，是因为它的优先级低于回答本身。用户先看答案，需要时再处理记忆。

## 去重键是记忆 id

同一会话里，用户可能反复提到同一个约束。

「我对花生过敏」说一次，系统提示一次；下一轮用户又说「记得我花生过敏」，如果再次提示，就会变成骚扰。

去重的键是记忆 id。前端在追加新提示之前，先扫描当前会话里已有的提示，收集所有出现过的 id，新的只保留没出现过的。

为什么用 id 而不是正文？因为同一条约束可能被合并、改写，正文不完全一致，但 id 不变。id 才是「是不是同一条记忆」的可靠标识。

## 最多两条

core 在返回提示时先截断到两条，前端渲染时也不再追加更多。

为什么是两条？

一条提示是常态，读起来像一句附注。两条还能接受，用分号连起来仍然是一行。三条以上就会变成一个小列表，把消息末尾撑得很高，而且用户根本记不住这一轮到底命中了哪几条。

限制条数的另一个作用是控制写入反馈的噪音：一次消息里说「我过敏、我不吃香菜、别推荐恐怖片、记住我周五跑步」，系统确实都记住了，但没必要逐条播报。

被截断的约束仍然写入成功，只是不提示。用户可以在设置页看到完整列表。

## 撤销后的状态

点击「撤销」后，按钮文字变成「已撤销」，不再可点。

这个状态是本地维护的：撤销请求成功，就把这条 id 加进一个集合，用集合决定渲染按钮还是文字。

为什么不在撤销后重新拉取记忆列表再判断？因为提示要立刻反馈，等一个网络往返会让用户以为没点上。本地状态足够表达「这次操作成功了」。

如果撤销失败，按钮保持原样，并弹一个错误 toast，用户可以重试。

## 为什么只提示一次就够

提示的目的是「让用户知道并有机会纠正」，不是「持续提醒」。

用户在看到的当下没有撤销，就说明他认可这条记忆。之后再反复提示，只会制造噪音。

如果用户后来反悔了，入口仍然在：设置页的记忆列表可以归档任何一条。

## 测试锁住的行为

- 一次返回三条，只渲染前两条；
- 同一会话里已经提示过的 id，不再追加；
- 没有提示、空数组、消息为空时，返回原对象引用，不触发重渲染；
- 撤销成功后，对应条目变成「已撤销」；
- 撤销失败时，按钮仍可用。

这些用例都不依赖真实记忆服务，输入是消息数组和提示数组，输出是新的消息数组，属于纯函数测试。

## 边界

提示不落库，刷新后消失；记忆仍在。

不做「撤销全部」，也不做「查看详情」跳转。

不提示常规抽取产生的记忆，只提示实时约束。

## 收尾

一条好的提示应该满足三个条件：出现得及时、说得足够短、给了反悔的机会。

内联、两条上限、按 id 去重，分别对应这三点。

它不试图让用户记住系统做了什么，只试图让用户在需要的时候，一眼看到、一键撤回。
