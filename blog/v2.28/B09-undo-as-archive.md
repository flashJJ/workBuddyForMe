# 撤销不是删除：复用归档语义

用户看到「已记住：用户对花生过敏 · 撤销」，点了一下。

接下来应该发生什么？

最直接的想法是把这条记忆删掉。但这一版没有新增删除接口，而是把它归档。

## 用户要的是「别再用了」

「撤销」这个词容易让人联想到删除，但用户真正的诉求通常是：这条记错了，别再拿它影响回答。

删除也能达到这个效果，但代价不同：

- 删除不可恢复，点错了就没有了；
- 删除绕过了已有的审计路径；
- 删除需要新接口、新权限判断、新测试。

归档则刚好对应「不再使用」：记忆还在，状态变成 archived，召回只取 active，所以下一轮不会再注入。

## 复用已有的 PATCH

归档走的是已有的记忆更新接口：

```text
PATCH /api/memories/:id
{ "status": "archived" }
```

这个接口此前就存在，用于在记忆列表里手动归档。撤销只是从消息末尾调用了同一个能力。

复用带来的好处是行为一致：不管用户从设置页归档，还是从消息提示撤销，结果都是同一条记忆变成 archived，服务层写入同一种审计。

不需要为「撤销」单独定义一套状态机。

## 审计要记在用户头上

归档时，服务层会写入一条 action 为 archive、actor 为 user 的审计事件。

这条审计有三个用途：

- 统计卡底部的最近审计能看到「用户在什么时候归档了这条」；
- 用户纠正次数会加一，因为归档属于用户纠正动作；
- 排查时能区分「系统生命周期归档」和「用户主动归档」。

如果撤销走一条独立的删除路径，这条审计就不存在了。用户做了一个动作，系统却没有留下痕迹，这在可追溯性上是倒退。

## 下一轮为什么不再注入

召回和置顶注入都只读 active 状态的记忆。

归档之后，这条记忆不再满足查询条件，自然从下一轮的上下文里消失。

不需要额外的「排除列表」，也不需要前端做过滤。状态本身就是过滤条件。

这也是复用归档语义的另一个好处：所有读取路径已经理解 archived 的含义，不需要逐处适配。

## 提示变「已撤销」，但记忆不消失

撤销成功后，消息末尾的按钮变成「已撤销」。

记忆条目本身仍然存在，只是状态变了。用户如果去设置页把过滤条件切到「归档」，还能看到它，也可以恢复。

这个设计保留了反悔空间：撤销是「暂时不用」，不是「永远抹掉」。

## 幂等

重复归档同一条记忆，结果仍然是 archived。

这一点对网络不稳定的场景很重要：用户点了一次没反应，又点一次，两个请求都到达服务端，不应该报错，也不应该产生两条重复语义的审计。

现有更新逻辑对「状态已经是目标值」是幂等的，撤销直接继承了这个行为。

## 为什么不做硬删除入口

硬删除的需求存在，但它的位置不在这里。

消息末尾的提示是一个轻量交互，适合「我记错了，先别用」。真要彻底删除，用户应该去记忆管理页，那里有明确的列表、筛选和二次确认。

把危险动作放在轻量入口里，迟早会出事故。

## 测试

- 点击撤销后，调用更新接口，body 是 `{ status: 'archived' }`；
- 成功后，提示文字变为「已撤销」，按钮消失；
- 失败时，按钮保留并显示错误提示；
- 归档后的记忆不出现在下一轮召回结果里。

最后一条是服务层测试，前三条是组件测试。两层都覆盖，才能保证「点得动」和「真的不再用」是同一件事。

## 收尾

撤销与删除，看起来只差一个按钮的文案，实际差的是整套语义。

删除回答「怎么让它消失」，归档回答「怎么让它不再生效」。后者可恢复、可审计、可复用现有路径，正好匹配用户按下撤销时的真实意图。

一个轻量入口背后，最好接的是一条已经存在的、语义清楚的重路径。
