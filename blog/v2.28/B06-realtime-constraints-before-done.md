# 把实时约束挪到 done 之前

用户说「我对花生过敏」。

系统识别出这是一条硬约束，写进记忆，标记置顶。之后每一轮对话，这条约束都会被注入，优先级高于其他记忆。

但用户看不到这件事发生。写入排在回合结束之后，完成信号已经发出去，界面没有任何提示。用户不知道系统记住了，也不知道记错了没有。

这一版把写入提前到完成信号之前。

## 原来的顺序错在哪

原来的回合流程大致是：生成回答、落库、发送完成帧、后台抽取记忆。

实时约束也走后台。它和常规记忆抽取一起，在完成帧之后执行。

这个顺序对常规抽取是合理的：模型抽取慢、要调模型、失败也不该影响回答。但对实时约束不合理，因为它根本不是模型抽取。

结果是：完成帧已经发出去，前端拿不到「本轮新增了哪些约束」，自然也没法提示。

## 实时约束不是模型抽取

过敏、忌口、带时间前缀的禁止、显式「记住」，这四类走的是窄规则。

- 过敏：匹配「我对 X 过敏」这类句式；
- 忌口：匹配「我不吃 X」「忌口 X」；
- 禁止：只认「以后 / 今后 / 之后 + 不要 / 别 / 禁止」；
- 显式记住：匹配「记住：……」后面的内容。

全是正则，没有模型调用，耗时在毫秒级。命中即写 `constraint`，置顶，重要度取高值。

规则的设计原则是宁可漏判，不做宽泛猜测。比如「我最近有点过敏」不会被当成具体过敏原，因为主语里带程度副词。

既然是纯规则，就没有理由把它排在耗时的后台任务里。

## 新的位置：回答之后，完成之前

新的顺序是：生成回答、落库、**同步写入实时约束**、发送完成帧、后台做常规抽取。

为什么放在回答之后，而不是回答之前？

如果在生成之前写，会拖慢首字延迟。虽然只有几毫秒，但它依赖的是用户输入，不需要等回答。

放在回答完成之后、完成帧之前，有两个好处：不拖慢生成；写入结果能随完成帧一起返回。

这里的关键判断是「完成帧」的语义：它不只是「生成结束」，也是「这一轮所有需要用户知道的事都齐了」。约束提示属于后者。

## 跳过嵌入，零模型成本

实时约束写入时显式跳过嵌入。

这不是优化，而是语义选择：这条路径不调用嵌入模型，也不访问网络，只做一次数据库写入。它因此可以在完成帧之前同步执行，而不引入不可控的延迟。

跳过嵌入的代价是：这条记忆不能参与向量召回。但它本来就会被置顶、每轮固定注入，不依赖向量相似度。关键词召回也仍然能命中。

所以这里不存在「为了快而牺牲质量」，只是选了一条本来就够用的通道。

## 失败静默

写入包在 try/catch 里，失败返回空数组，只写一条警告。

完成帧照常发送，回答照常展示。用户不会因为一次数据库写入失败而看不到已经生成的内容。

这个边界很重要：约束提示是增强信息，不是完成条件。它可以缺失，但回答不能缺失。

## 常规抽取仍然在后台

和实时约束不同，常规抽取需要调模型，耗时不可控。

所以它保持在完成帧之后，走后台任务。两类写入的分工是：

- 实时约束：纯规则、同步、完成前、零模型成本；
- 常规抽取：模型、后台、完成后、失败静默。

一条用户消息可能同时命中两者，但它们服务的目的不同：前者保证「这一轮就能提示和撤销」，后者保证「更丰富的记忆慢慢沉淀」。

## 为什么值得提前这几毫秒

从技术上看，提前只是把一次数据库写入挪了个位置。

从体验上看，区别很大：用户在说「我对花生过敏」的下一屏，就能看到「已记住：用户对花生过敏 · 撤销」。

这个提示把一次隐式的后台行为变成了可见的、可纠正的动作。没有它，用户只能相信系统记住了；有了它，用户可以在第一时间说「不对」。

## 边界

只覆盖窄句式，不做语义理解，不猜言外之意。

写入失败不重试，下次用户再说一遍会重新命中。

不改变置顶约束的注入规则：仍然是每轮最多固定注入三条。

## 收尾

同一件事放在不同的时间点，价值完全不同。

约束写入在完成帧之后，是一次不可见的后台操作；在完成帧之前，是一次可提示、可撤销的交互。

挪动的位置只有几行代码，但它让「记住」从系统行为变成了用户可确认的事实。
