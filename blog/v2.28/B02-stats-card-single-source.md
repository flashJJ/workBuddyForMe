# 统计卡：前端只格式化，不重算

接口返回了总量和「被取代的条数」，前端顺手做了个除法，显示 17%。

半年后后端改了统计口径：被取代比例不再包含已归档的记忆。接口返回值变了，前端那行除法没变，页面上的 17% 和接口里的 14% 从此对不上。

这类问题不会报错，只会让用户慢慢不相信页面上的数字。

## 一个数字只能有一个来源

统计卡的第一条规则是：比例字段由后端算好，前端只负责格式化。

接口返回的不是「分子和分母」，而是已经算完的比例值。前端拿到 0.176，按当前语言格式化成 17.6%，不碰任何除法。

这样做的好处很直接：口径只有一份。哪天统计规则改了，改的是服务层的一个函数，页面自动跟着变；不会出现「接口改了、页面还在按老公式算」的分叉。

## 空库显示 0，不是空白

没有记忆时，接口返回的总量是 0，比例字段也是 0。

前端要保证 0 被正常渲染成数字，而不是被当成「没有值」省略掉。否则用户第一次打开设置页，看到的是几块空白，会以为统计坏了。

同样的道理适用于百分比：0 显示 0%，不显示破折号。

空状态本身也是一条信息：它告诉用户「系统是好的，只是还没有记忆」。

## 最近审计：扩展同一响应，不新开接口

统计卡底部要展示最近五条审计。

最直觉的做法是加一个 `/api/memories/audit` 接口。但这会让一个卡片发两个请求，出现两套加载态、两套失败重试，还要处理两者到达顺序不一致。

所以这一版把最近审计做成同一个统计响应的可选字段。卡片只发一次请求，加载、失败、刷新都是一个状态。

可选字段还有一层兼容意义：旧的消费方读不到这个字段时照常工作，不需要同步升级。

## 三种状态都要有

统计卡不是「有数据就渲染」这么简单。

- **加载中**：用骨架占位，形状和最终指标块一致，避免内容到达时页面跳动。
- **失败**：显示错误说明和一个重试按钮，不显示半截数据。
- **成功**：七个指标块、最近审计列表、底部保留期与轮转时间。

还有一个容易被忽略的细节：这张卡是客户端组件，查询状态在服务端渲染和客户端首帧可能不一致。直接按加载态切换结构会触发水合失配，所以挂载完成之后才渲染数据区域。

这不是统计卡独有的问题，但它的结构（骨架与内容形状不同）最容易把它暴露出来。

## 轮转时间与保留期为什么放在卡里

统计卡展示的是「记忆的健康状况」，审计轮转是维持健康的手段。

把最近一次轮转时间和保留期选择放在同一张卡底部，用户看到「上次轮转是三天前」，顺手就能改保留期，不需要跳到另一个设置分组。

治理动作和治理数字放在一起，才容易被使用。

## 测试锁字段映射

这类卡片最值得测的不是样式，而是映射关系。

用例可以这样写：构造一份固定的统计响应，断言七块指标分别显示了对应字段的格式化结果；断言百分比直接使用后端返回值，而不是用分子分母重算；断言空库时显示 0；断言失败态出现重试按钮。

这些断言不依赖真实数据库，也不依赖网络，改口径时如果前端偷偷重算，测试会先失败。

## 边界

统计卡只读，不负责写记忆、不提供批量删除、不做历史趋势图。

它也刻意不做「刷新即重算」：刷新只是重新请求，数字仍然来自服务端。前端不缓存、不推导、不补偿。

## 收尾

一张统计卡看起来是纯展示工作，真正决定它可靠与否的是一条纪律：**页面上的每个数字，都能指回唯一的计算处。**

守住这条纪律，卡片就只是接口的一面镜子；守不住，它就会变成第二套统计口径，而且没人知道哪一套是对的。
