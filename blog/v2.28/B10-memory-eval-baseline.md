# 一条命令看清召回基线

调召回权重是一件很容易自我感觉良好的事。

改完融合公式，随手问几个问题，感觉都答上来了，于是提交。过几天遇到一个答不上来的问题，又开始怀疑是不是改坏了——但已经没有任何对照。

这一版补了一条本地命令，专门回答「改之前和改之后，到底差多少」。

## 与线上评测的区别

项目里已经有一个记忆评测脚本，但它要起服务、调对话模型、再请一个 LLM 当评委。它评的是端到端回答质量，成本高、耗时长，不适合频繁跑。

新命令只测召回：给定一组问题和种子记忆，看期望的记忆有没有进前三。

它不生成回答，不调模型，不调评委。直接在内存 SQLite 上复用 core 的召回管线，几秒钟跑完。

两者不是替代关系：一个看最终回答，一个看检索环节。调权重时，先看后者。

## 十二条 golden 用例

用例文件里有种子记忆和问题，每条问题带期望命中的关键词。

例如「我养宠物了吗？它叫什么？」期望召回里出现「橘猫」「橙子」；「我最近在准备什么考试？」期望出现「PMP」。

十二条覆盖了姓名、城市、职业、语言偏好、回答风格、宠物、忌口、考试、作息等常见记忆类型。

用例不求多，求稳定：每条都能用关键词判断命中，不依赖语义相似度的主观判断。

## 四个指标

报告输出四项：

- **hit@3**：期望记忆进入前三的用例占比；
- **零召回率**：一条记忆都没召回的用例占比；
- **平均召回耗时**；
- **最大召回耗时**。

hit@3 衡量「找得到」，零召回率衡量「完全找不到」的严重程度，两个耗时衡量「找得快不快」。

分开看的原因是不同的退化方式需要不同的修法：命中率下降可能是排序问题，零召回上升可能是过滤条件太严，耗时上升可能是候选集太大。

## 报告写成文件，并和上一版比

结果写到本地 JSON 文件，包含每条用例的命中情况、前几条召回内容和耗时。

每次运行前先读上一版报告，算出差值。控制台表格直接显示 `+0.083`、`-0.020` 这样的变化。

差值比绝对值更有用：hit@3 是 0.833 还是 0.917，单看没有方向感；比上一版涨了还是跌了，一眼就能判断这次改动值不值得保留。

文件放在版本目录下，跟着代码一起提交。这样每次调整都能在历史里找到对照。

## 没有嵌入模型时走关键词通道

本地环境不一定配置了嵌入模型。

这时召回会自动降级为关键词通道。报告里用一个字段标注当前通道，避免读者把关键词结果误认为向量效果。

这个标注很重要：同一组用例，关键词和混合召回的命中率不可直接比较。不标通道，差值就会误导人。

## 为什么退出码恒为 0

评测脚本不是门禁。

指标会受环境、种子数据、甚至随机性影响，把它设成 CI 必过项，只会让无关改动因为一个用例波动而失败。

所以脚本只在读取失败时返回非零，其余情况一律成功退出，报告照常生成。它提供的是参考，不是判决。

## 当前基线说明了什么

十二条用例里，十条命中前三，hit@3 为 0.833；没有一条完全零召回；平均召回 0.49 毫秒，最慢 1.3 毫秒。

两个信息值得注意。

第一，hit@3 不是 1.0。还有两条期望记忆没进前三，说明排序或关键词覆盖仍有改进空间。这是下一版调权重的起点。

第二，零召回率是 0。也就是说，系统至少能找回一些相关记忆，问题出在「排得够不够前」，而不是「完全找不到」。这个区分决定了优化方向。

## 边界

只测召回，不测回答。召回对了，回答仍可能跑偏。

用例只有十二条，覆盖面有限，不能代表全部真实对话。

只跑本地，不上传、不做跨机器对比。

不进 CI。

## 收尾

基线的作用不是证明现在很好，而是让下一次改动有参照。

没有基线时，「感觉变好了」是唯一标准；有了基线，至少能回答三个具体问题：命中率变了多少、零召回有没有增加、耗时是否可接受。

一条命令、一个 JSON 文件、四个数字，成本很低，但它把「调参」从手感变成了可以复盘的过程。
