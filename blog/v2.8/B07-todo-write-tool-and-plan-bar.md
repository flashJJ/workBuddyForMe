# 让模型自己维护待办：`todo_write`、对话顶部计划条与桌宠信号

计划系统有一半的价值在存储与评审，另一半在**日常可见**。用户不会每轮都打开计划页，但每一轮都在看对话。

这篇讲三个投影：模型侧的 `todo_write` 工具、对话顶部的计划条、桌宠上的计划信号。它们共享同一份数据，但服务三个不同的注意力层级。

## 一、`todo_write`：一个只写本地状态的工具

工具定义很短：

```text
name: todo_write
permission: read
参数: { todos: { title: string, status?: pending|running|done|skipped|blocked }[] }
```

行为按会话做**原子替换**：传入的清单就是全部清单，旧条目不再保留。返回给模型的是 `已完成/总数`，摘要行也只用这个数字。

几个容易被忽略的实现细节：

| 细节 | 处理 |
|---|---|
| 清单为空 | 拒绝，报「待办清单不能为空」 |
| 超过 50 项 | 拒绝，避免模型输出一次几百项的清单把界面撑爆 |
| 标题为空 | 拒绝，逐条校验而不是整批丢弃 |
| 状态非法 | 回落为 `pending`，不报错 |
| 当前回合没有清单通道 | 返回 `ok: false`，文案是「当前回合没有可用的待办清单通道」 |

最后一条是给测试与无会话场景准备的。工具在装配时通过上下文注入一个 `writeTodos` 回调，只有存在会话 id、且计划服务可用时才会注入。没有通道时工具不能抛错——抛错会让整轮对话失败，而它只是一个可选的进度记录器。

工具默认关闭，由助手白名单显式启用，和其他内置工具一致。这个默认值很重要：一个不关心待办的助手，不该因为系统升级突然开始往对话里写清单。

## 二、为什么是「全量替换」而不是「增量更新」

增量接口（加一条、改一条、删一条）看起来更省 token，但对模型不友好：它需要在多轮之间维护步骤 id，而 id 是服务端生成的，模型只能靠回读上下文获得。一旦某轮上下文被压缩，id 就丢了，接下来的更新会全部落到错误条目上。

全量替换把这个负担换成了「每次重写一遍清单」。代价是 token 稍多，收益是**模型永远不需要记住 id**，清单也不会因为一次错误的合并而错位。

副作用也有：步骤的 id 每次都会变（旧的删掉、新的插入）。所以任何外部系统都不能把待办步骤 id 当稳定引用；要引用计划，用计划 id。

## 三、对话顶部计划条：一个只读摘要

计划条不是一个卡片，是一个胶囊：

```text
[图标] 把三份季度报表整理成一页结论   3/5   待评审
```

它读三样东西：当前 active 目标、当前正式计划、当前待办。取标题的顺序是「目标 → 计划 → 待办」，取进度的顺序是「计划 → 待办」。待评审时在末尾追加一个琥珀色的状态词。整条点击进计划页。

计划的挑选优先级和上下文装配一致：执行中 → 已批准 → 待评审 → 草稿。这样提示词里讲的那份计划和用户眼前看到的这份，永远是同一份。

## 四、为什么不在消息流里塞卡片

最初的设计是「计划卡直接出现在助手回复下方」，像工具调用卡片那样。做完之后改成了顶部条，原因有四条：

1. **消息流是追加式历史，计划是可变状态。** 一条历史消息里的卡片，要么显示旧状态（撒谎），要么实时刷新（历史被篡改）。两种都别扭。
2. **重交互会污染阅读节奏。** 评审、改写、勾选步骤都是多步操作，塞在对话中间会让「读回复」变成「操作系统」。
3. **一份状态两个入口必然分叉。** 消息卡和计划页各自维护按钮状态，迟早出现「这边能点、那边不能点」。
4. **顶部条的成本极低。** 它只读、只跳转，不承担写操作，出错面几乎为零。

于是界面被切成两层注意力：**顶部条负责「知道」，计划页负责「操作」**。用户想快速确认进度就看条，想批准或改写就点进去。

## 五、桌宠：计划也是一种工作信号

桌宠本来消费的是任务、协作、工作流这几类运行。计划接入时，我们把它当成第四种来源，标记为 `source=chat`。

映射规则很短：

| 计划状态 | 工作信号 |
|---|---|
| 草稿 / 待评审 | 不产生（尚未进入执行） |
| 已批准 / 执行中 | 运行中，气泡显示 `已完成/总数` |
| 已完成 | 成功脉冲 |
| 已驳回 / 已放弃 | 取消 |

信号键是 `chat:<计划 id>`，深链指向计划页，标题前缀「计划：」，超长截断到 120 字。

两条特殊规则值得单独说：

**草稿与待评审不上桌宠。** 一个还没被认可的计划，如果让桌宠显示「工作中」，等于在替用户宣布一件他还没同意的事。桌宠的信号必须对应真实工作，而不是意图。

**待办全未开始时也不上桌宠。** 待办是模型随手维护的清单，经常在回复开头就写下来，此时一步都还没做。如果这就算「工作中」，桌宠会在大量纯问答场景里频繁闪一下，变成噪音。规则是：待办只有在已有进度时才进入信号；全部完成时转成一次成功脉冲，而不是继续挂着。

## 六、三层可见性，一套数据

把三个投影放一起看，结构很清楚：

```text
同一份 work_plans / work_plan_steps
   ├─ 模型视角：system 段折叠摘要（一条计划、十条步骤）
   ├─ 用户视角：对话顶部胶囊（标题 + x/y + 待评审）
   └─ 环境视角：桌宠信号（仅执行中的计划与有进度的待办）
```

三者的取舍方向不同：模型需要「下一步该做什么」，所以给状态标签与禁令；用户需要「现在到哪了」，所以给进度与评审提示；桌宠需要「是否该表现出在工作」，所以只在真实推进时出现。

但它们的数据源只有一个。这不是为了省代码，而是为了让「模型以为的进度」和「用户看到的进度」不可能分叉。

## 七、这一篇的结论

`todo_write` 的价值不在于让模型输出一份漂亮的清单，而在于**把「进度」变成一个可被读取的状态**。有了这个状态，提示词能写「保持清单与真实进度一致」，计划条能显示 x/y，桌宠能判断该不该工作。
