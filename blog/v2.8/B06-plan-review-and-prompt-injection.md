# 计划进提示词：一段折叠的上下文，和一句「勿执行高风险步骤」

计划系统最容易做错的地方，是把它当成一个执行器：批准之后自动开跑，跑完自动勾选。

我们走的是另一条路——**计划只影响提示词与界面，不直接执行**。这篇讲这段上下文长什么样、为什么要有「未批准」标注、以及批准到底解除了什么。

## 一、注入点只有一个：system 段

每轮对话装配时，服务端读一次当前工作上下文，折叠成一段文本，拼进 system 段。它和技能提示块并列，中间空一行：

```text
【当前工作上下文】
当前目标：把三份季度报表整理成一页结论（成功标准：口径一致、可追溯）
当前计划《数据核对》状态：待评审（待评审，勿执行高风险步骤）
- [待办] 导出源数据
- [进行中] 比对口径差异
- [待办] 生成结论页
待办进度：1/3
- [完成] 导出源数据
- [待办] 补一列同比
需要更新待办时调用 todo_write，保持清单与真实进度一致。
```

这里有几个刻意的取舍。

**不放进用户消息。** 工作上下文不属于任何一轮用户输入，它跨回合存在。塞进用户消息会让历史记录里出现大段重复文本，也会让「用户说了什么」变得不可信。system 段天然是「每轮重新装配、不进入历史」的位置。

**不按条数堆叠。** 最多一条计划、最多十条步骤，超出只留一行「…共 N 步」。上下文预算有限，而计划的价值在于「当前在哪一步」，不在于完整清单。完整清单在计划页里。

**没有内容就返回空串。** 没有目标、没有计划、没有待办时，这段完全不出现，不会给模型一段「（空）」的噪音。

这段文本和技能提示块拼接后一起进入 system 段，中间空一行。拼接顺序是「工作上下文在前、技能在后」：前者是这一轮的任务约束，后者是长期的能力说明，越靠近任务的内容越应该靠前。

## 二、状态标签是给模型看的，不是给用户看的

计划状态在提示词里被翻译成中文标签：草稿、待评审、已批准、执行中、已完成、已驳回、已放弃。步骤状态同样翻译：待办、进行中、完成、跳过、受阻。

这不是本地化问题，而是**给模型一个稳定的词汇表**。模型看到「待评审」和看到 `pending_review`，理解成本不一样；前者能直接对应到「现在不该动手」。

真正关键的只有一句附加语：当计划处于草稿或待评审时，状态后面追加「（待评审，勿执行高风险步骤）」。

为什么是这两条状态？因为上下文选择器根本不会把已驳回、已放弃的计划选为「当前计划」——它们不是候选。所以能出现在提示词里的未批准状态，只有草稿与待评审两种。这也解释了为什么很多实现会把「已驳回」也写进判断却永远不触发：它们其实不在同一条链路上。

三种常见的误用，可以当成反面清单：

| 写法 | 问题 |
|---|---|
| 把整个计划页内容塞进提示词 | 步骤越多越挤占预算，模型反而忽略当前步 |
| 用状态英文枚举名直出 | 模型能做，但容易把它当成内部字段乱引用 |
| 只在批准后才注入计划 | 模型在评审阶段看不到计划，无法参与改写 |

第三条尤其反直觉：评审阶段恰恰最需要模型看到计划，因为它要根据用户的驳回理由改写。把「未批准」等同于「不该看见」，会让评审退化成纯人工操作。

## 三、为什么评审不自动执行

三个理由，按重要性排序。

**第一，计划与执行是两类风险。** 计划是一段文字，批准它只表示「方向我认可」。执行会调工具、写文件、发消息，每一步的副作用都需要单独判断。把两者绑在一起，等于用一次点击授权了一串未知操作。

**第二，执行链路已经有自己的闸门。** 高风险工具逐次走审批弹窗，预算有服务端硬上限，桌面操作在无人值守时直接拒绝。如果计划批准能直接触发运行，这些闸门就被绕到了上层。

**第三，自动执行会让「驳回」变成不可能。** 用户刚点批准，运行已经开始，此时再想反悔只能中断——而中断留下的是一条失败记录，不是一次干净的取消。

所以批准的动作被压到最小：状态改为已批准、记下批准时间、上下文里的「待评审」提示消失、步骤推进按钮变为可用。仅此而已。

## 四、批准解除了什么，没解除什么

这张表值得写清楚，因为它决定了用户预期：

| 能力 | 批准前 | 批准后 |
|---|---|---|
| 出现在模型上下文 | 是（带「勿执行」标注） | 是（不带标注） |
| 可改写步骤 | 是 | 否 |
| 可推进步骤状态 | 否 | 是 |
| 自动触发运行 | 否 | 否 |
| 高风险工具免审批 | 否 | 否 |
| 桌宠显示计划 | 否 | 是（已完成/总数） |

最容易被误解的是最后两行。很多用户会以为「批准 = 允许它开始干活」。实际发生的是：模型下一轮对话时知道「这个计划已经被认可」，于是可以更主动地按步骤建议下一步；但每一次真正有副作用的调用，仍然要在工具审批里过一遍。

换句话说，**计划批准改变的是语气与优先级，不是权限**。

这个边界最好在界面上也说出来。计划页的评审提示不是「批准后开始执行」，而是「批准后可推进步骤」；按钮文案的差别，比任何文档都更能防止误解。

## 五、待办为什么不需要评审

待办走的是另一条通道：模型调用 `todo_write`，服务端原子替换清单，返回 `已完成/总数`。它创建时直接是已批准状态。

理由是写入者与粒度不同。计划是「要做什么」的承诺，通常由用户提出或需要用户认可；待办是「做到哪了」的记录，产生于执行过程中，如果每一步都要求评审，这个工具就没人会用。模型维护进度，本身是一种自我校准，出错成本也只是清单不准，而不是执行了错误动作。

不过待办同样受约束：它不能为空（空清单直接拒绝），最多 50 项，状态必须是五个合法值之一。这些校验写在工具层，而不是提示词里——提示词是建议，校验才是边界。

## 六、多个计划并存时，只讲当前那一个

一个会话里可能同时存在多份计划：上个月做的、这次驳回重写的、还有一个待办清单。提示词只取一份正式计划，选择优先级是：执行中 → 已批准 → 待评审 → 草稿。

这个顺序表达的是「当前正在做的事优先」。已批准但尚未开始的计划，比还在评审的计划更该占据模型注意力；而执行中的计划不用多说，它是事实。

其余计划不是被删除，只是不进提示词。计划页仍然全部可见，用户想切回来，把它设为当前即可。把多份计划同时塞进上下文有两个副作用：预算被摊薄，以及模型开始在不同计划之间做它没被要求的协调。

一个会话同一时刻只有一个活跃待办清单，这条约束也是同一个道理——清单是「这一轮做到哪了」，不是「所有想做过的待办合集」。

## 七、注入之外，还有一条实时路径

system 段是「模型看到的」，而用户看到的是对话顶部的计划条。两者数据源相同、刷新时机不同：提示词每轮重算，计划条随计划变更实时推。

这种「一份数据、两个投影」的结构，避免了最常见的分叉：计划页显示 3/5，提示词里写着 2/5，模型于是按 2 继续做。评审状态也一样——计划条上出现「待评审」时，提示词里必然带着「勿执行」，不会出现一边警示一边放行。

## 八、这一篇的结论

把计划折叠进提示词，技术上只是拼一段字符串。真正的设计量在三个判断上：放哪里（system 而不是消息）、放多少（一条计划十条步骤）、以及怎么表达「还没批准」（一句显式的禁令，而不是靠模型自己从状态名里推断）。
