# 完成只回写一条消息：把幂等键放在写入之前

后台运行结束后，结果要回到它会话里，否则用户回来后只能看到一个「已完成」的状态，却不知道完成了什么。

听起来只是「追加一条助手消息」。但后台作业带来了三个新条件：**终态可能被多次观测**（作业收尾、恢复收敛、容器回调都会看到终态）、**观察者可能有多个**、**回投本身可能失败**。任何一条没处理好，用户就会在会话里看到两条甚至三条重复的总结。

## 一、重复是从哪来的

先枚举真实的重复来源，否则幂等键会拍脑袋：

| 来源 | 说明 |
|---|---|
| 作业正常收尾 | 运行循环结束，触发终态回调 |
| 生成器异常收敛 | 抛错时先补一次失败收敛，再走收尾 |
| 重启恢复 | 批量把遗留 running 改成中断态，每条都触发回调 |
| 单个孤儿收敛 | 路由层发现非活跃但非终态，就地收敛 |
| 容器重复装配 | 测试或热更新下回调可能被接两次 |

这些路径共享同一个「终态回调」，所以幂等不能放在调用方，只能放在写入点。放在上层意味着每个调用点都要自己判断「这条是不是已经写过」，而漏一个就是一次重复。

## 二、幂等键：先占位，再写消息

写入点只有两步，顺序不能反：

```text
claimCompletion(run_id, kind, status):
  INSERT OR IGNORE INTO run_completions(run_id, kind, status, created_at)
  返回 changes > 0   // 首次插入才算抢到

append(...):
  如果没抢到 → 直接返回
  如果会话不存在 → 直接返回
  追加一条 assistant 消息
```

建表时主键就是 `(run_id, kind)`：

```sql
CREATE TABLE run_completions (
  run_id     TEXT NOT NULL,
  kind       TEXT NOT NULL,
  status     TEXT NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (run_id, kind)
);
```

`run_id` 加 `kind` 而不是加 `status`，是因为一次运行只该有一条结果消息。如果键里带上状态，一条先被收敛成 `stopped`、后来又被标成 `failed` 的运行，会合法地写两条互相矛盾的总结。这不是幂等，是允许了两次真相。

「先占位再写」而不是「先写再记」，是为了让竞争在最便宜的地方失败：两条并发路径里只有一条能插入成功，另一条在写消息之前就退出了。反过来做的话，两边都写完消息，才在记账时发现冲突，已经晚了。

键的候选方案与淘汰理由也值得记下来，因为它决定了后续能不能改：

| 候选键 | 结果 | 为什么不行 |
|---|---|---|
| `run_id` | 未采用 | 把「一次运行」等同于「一份结果」；将来同一运行要产出多种结果时会撞键 |
| `run_id + status` | 淘汰 | 允许一条运行写两条矛盾总结，等于放弃「一份结果」 |
| `run_id + kind + status` | 淘汰 | 同上，只是把冲突范围缩小 |
| `run_id + kind` | 采用 | 一次运行的每一类产出（任务/协作/跟进）各一份结果 |

注意最后一行里的 `kind` 不是为了区分任务和协作——它们本来就不会同 id——而是为了给「定时跟进」留位置：跟进用合成 id，kind 固定为 `follow_up`，共用同一张表与同一套占位逻辑。

## 三、文案不是错误日志

回投消息只有一两句，但有明确的写法约束：

- 任务完成：`任务「<目标>」已完成，共 N 步。`
- 任务失败：`任务「<目标>」执行失败，共 N 步。`
- 任务 interrupted：`任务「<目标>」因应用重启被中断，可重新发起。`
- 任务被停止：`任务「<目标>」已停止（原因）。`
- 协作完成：`协作「<目标>」已完成：<结论摘要>`，无摘要时省略冒号后半段。

约束有三条：目标截断到 60 字（超出加省略号），失败原因截断到 120 字，**文案不包含工具参数原文、密钥、截图内容**。运行卡是给用户看的结果，不是给开发者看的日志；把原始参数塞进去，迟早会泄露一次带凭据的调用。

消息落库时直接带完成状态，不走流式。它是一次性写入的成品，不是正在生成的回复，界面不该为它显示光标或「停止生成」。

会话不存在时只写状态、不写消息。这覆盖了「运行是在工作流节点里创建的、本来就没有归属会话」的情况。判断顺序是先看会话 id 是否为空，再确认会话行还在——会话可能已经被用户删了。

## 四、Task 与 Agent 各自接线

两类运行的接线点相同，内容不同：

| 运行 | 接线位置 | 终态判定 | 会话来源 |
|---|---|---|---|
| 任务 | 作业服务收尾时读最新运行行 | `completed` / `failed` / `stopped` | 运行行上的会话 id |
| 协作 | 作业服务收尾时读最新运行行 | 任何非 `running` 状态 | 运行行上的会话 id，可空 |

任务服务在收尾时重新读一次数据库，而不是用启动时那份快照。原因是收尾可能由异常路径触发，内存里的对象可能还停留在 `running`。读最新行是最便宜的「以库为准」。

协作服务同理，并且额外做了一层兜底：如果循环异常退出、库里还写着 `running`，先把它终结为失败并带上错误码，再走清租约与回调。否则回调会拿到一条 `running` 的运行，被终态判定直接挡掉，结果就是「运行结束了但什么都没回投」。

## 五、为什么失败也必须可重试

一个容易被忽略的点：回投失败不该让运行失败。

运行已经结束，状态已经落库，这时候如果因为「写消息」这一步抛错就把整条链路标成失败，等于让一个展示层的问题污染了执行层的事实。所以回投里的每一步都是「失败即放弃本次」：会话不存在就跳过，占位没抢到就跳过，写消息抛错就记日志。

但「放弃」不等于「永不重试」。因为幂等键先落库，重试是安全的：只要占位成功过、消息没写成功，下次任何一条走到终态回调的路径都会重新尝试写消息——占位已经在表里，`claimCompletion` 会返回 false，于是不会重写。

这里有个细节要承认：当前实现把「抢到占位」与「写入成功」当成一个原子意图，如果写消息那一步失败，占位仍然留着，后续重试会被自己挡住。这是一个已知的小缺口，取舍是「宁可不重复，不可重复」——重复的总结比缺失的总结更伤害信任。真正要修的话，正确做法是把占位与写入放进同一个数据库事务，或者给占位加一个「已投递」标记，让重试能分辨「占位但未投递」。

## 六、通知也只该响一次

回投还会触发一次工作信号的终态脉冲。它和消息共用同一套幂等前提：同一次运行只产生一次「完成」通知。桌宠的完成动作、提示音、系统通知都挂在这个脉冲上，重复触发就会变成连续两次庆祝。

验收时的检查很直接：完成一次任务，会话里多一条助手消息，桌宠响一次；再手动调用一次恢复或收尾，消息数不变，提示音不响。

## 七、这一篇的结论

幂等不是「加个去重判断」，而是**把唯一的写入点找出来，把键设计成业务事实，再让所有路径都撞在这一个点上**。

`(run_id, kind)` 这个键表达的业务事实是：一次运行只有一份结果。状态、观察者数量、回调次数都不该改变这件事。下一篇转向另一条线：目标、计划、待办这三样东西到底怎么存，以及为什么待办不是第四个状态机。
