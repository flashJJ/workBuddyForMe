# 重启之后没有幽灵 running：恢复只收敛状态，不重放步骤

后台作业把「关页不中断」解决了，同时引入一个新的失败面：**进程整个没了**。

进程内注册表随进程消失，但数据库里的运行行还在，状态写着 `running`。如果没有恢复逻辑，用户下次打开会看到一个永远转圈的任务，桌宠也会一直显示「工作中」。我们内部把这种行叫幽灵 running。

## 一、恢复面对的不是一种状态，而是一个矩阵

恢复不能一刀切。至少要区分「从没启动过」和「跑了一半」：

| 崩溃时状态 | 是否可能已有产出 | 恢复动作 | 最终状态 |
|---|---|---|---|
| 任务 `queued`（从未启动） | 否 | 收敛，不启动 | `stopped(interrupted)` |
| 任务 `running` | 是 | 收敛 | `stopped(interrupted)` |
| 任务 `paused` | 是 | 收敛 | `stopped(interrupted)` |
| 协作 `running` | 是（可能有交接记录） | 收敛 | `cancelled` + `INTERRUPTED` |
| 任意终态 | — | 不动 | 原样回放 |

注意第一行：`queued` 也收敛。有人会问，既然从没启动，为什么不干脆启动它？因为「启动」是一个有副作用的决定，恢复逻辑没有资格替用户做。用户可能早就不想要这次运行了；重启时静默开跑，比留下一条中断记录更糟。

也不做自动重跑。中断是事实，不是需要被抹掉的污点。

## 二、两类运行的收敛方式不同，但语义相同

任务的收敛很直白：把状态改成 `stopped`，终止原因写 `interrupted`，清空租约。它复用了已有的停止状态，只新增一个终止原因，不新建状态值——状态机越短，UI 与统计口径越不容易分叉。

协作运行没有「停止」这个状态，它的终止表达是 `cancelled` 加一个错误码。所以恢复时写入的是 `cancelled` / `INTERRUPTED` / 「应用重启，运行中断」。**已落库的交接记录一律保留**，因为那是这次运行唯一留下的东西。

两条路径共用一个返回结构：本次收敛了多少个任务、多少个协作。容器装配时打一条结构化日志，数字为 0 就不吵。

具体的写入字段也列清楚，避免恢复逻辑顺手多写：

| 字段 | 任务 | 协作 |
|---|---|---|
| 状态 | `stopped` | `cancelled` |
| 终止原因 / 错误码 | `interrupted` | `INTERRUPTED` |
| 结束时间 | 写入 | 写入 |
| 错误说明 | 空（原因已足够） | 「应用重启，运行中断」 |
| 租约列 | 清空 | 清空 |
| 步骤 / 交接 / 消息 | 不动 | 不动 |

## 三、只做一次，而且必须幂等

恢复挂在容器首次装配时执行一次，不是一个定时任务，也不是每次请求都跑。

这个选择的理由是：恢复的输入是「进程启动」这个事件，输出是「把上次遗留的非终态行改掉」。它天然只该发生一次。如果做成周期性扫描，就会和正常运行竞争——一个刚开始跑、还没写租约的作业，可能被扫描器误判成幽灵。

幂等性由查询条件保证：只查非终态行。重复调用时第二次查询结果为空，不会产生副作用。这一点在测试里是显式断言的，因为容器在某些运行模式下可能被装配多次。

## 四、还有一条漏网路径：容器重载

首次装配的批量恢复覆盖了「进程重启」。但还有一种更隐蔽的情况：进程没重启，容器却被重新装配了（开发热更新、测试里重建容器、某些启动路径的二次初始化）。

此时注册表是空的，数据库里却可能有一行刚被创建、状态为 `running` 的运行。批量恢复已经跑过了，不会再跑第二次。

所以我们补了一个单条收敛入口：路由发现某个运行「不在活跃注册表里，但库里还是 running / paused / queued」时，就地把它收敛为中断。判断条件写得很窄——必须同时满足「非活跃」与「非终态」，避免误伤正常结束但尚未回写的行。

这条路径同样只改状态与租约，不改步骤、不删消息。

## 五、不重放：这是最难的取舍

恢复逻辑最自然的冲动是「接着跑」。既然步骤表里记着第 3 步没完成，那就从第 3 步继续。

我们没有这么做，理由有三条：

1. **副作用不可重入**。任务步骤里可能有写文件、调用外部工具、发送消息。重放第 3 步意味着把这些动作再做一次，而恢复逻辑无法判断哪些已经生效。
2. **上下文已丢失**。进程内的模型会话、工具句柄、临时缓存都随进程消失。仅凭数据库里的步骤行，重建不出当时那一轮对话的完整上下文，强行续跑会得到一个「记得目标、忘了过程」的运行。
3. **失败要可解释**。一条明确写着「因应用重启被中断，可重新发起」的记录，比一次行为诡异的续跑更容易被用户接受。

所以恢复的职责被压到最小：**把状态收敛到终态，把结束时间补上**。步骤、交接、消息全部保留，供后续复盘与用户自查。重新发起是用户的动作，不是恢复的动作。

这也解释了一个容易被误读的现象：恢复之后打开那条运行，时间线看起来是「完整但停在中间」。这不是数据损坏，而是如实记录——它确实跑到那里，然后整个进程消失了。删掉尾部步骤，反而会让这段历史变成一次「正常结束」。

## 六、收敛之后，回投要跟上

状态改完还不算结束。一次被中断的运行同样需要一个结果落回会话，否则用户只会在运行列表里看到一个红点，而对话里什么都没有。

完成回投因此接在恢复之后：批量收敛会对每一条被改写的运行调用终态回调，回投服务再按幂等键写入一条助手消息。中断文案是专门的，不会和「失败」「用户停止」混在一起：

```text
任务「整理本周数据」因应用重启被中断，可重新发起。
协作「核对三份报表」已结束（cancelled）。
```

这两句都不是错误堆栈的翻译，而是**下一步动作的提示**。中断不是异常，是产品必须如实交代的一种结果。

## 七、怎么证明没有幽灵

验收里这一条最直接：把服务跑到任务进行中，直接杀掉进程，重启，然后看运行列表。

- 所有非终态运行必须变成中断态，没有一条还在转圈；
- 旧步骤、旧交接仍可打开回放；
- 桌宠不显示任何「工作中」；
- 再点一次「开始」，是一次全新的运行，不复用旧 id。

自动化层面靠两条单测兜底：一条断言重启后任务收敛为 `stopped(interrupted)`、协作收敛为 `cancelled(INTERRUPTED)`；一条断言重复调用恢复不产生额外改动。

手工验收再补四条，因为它们比单测更能暴露真实状态：

- 收敛后的运行在列表里显示为「已中断」，不是「运行中」；
- 打开详情能看到最后一次成功的步骤，不是空白；
- 桌宠没有任何工作态残留，也没有完成脉冲；
- 重新发起得到新的运行 id，旧记录不被覆盖。

## 八、这一篇的结论

中断处理有一个常见的错误方向：把它当成一次「需要被修复的失败」，于是自动重试、自动续跑、自动补状态。我们的方向相反——**把中断当成一类正常终态来设计**，给它独立的终止原因、独立文案、独立回投路径。

好处是系统里没有「半死不活」这个第四态。运行要么在跑，要么已经结束，而结束的每一种原因都能被解释。下一篇讲结束之后那一条消息：怎么保证它只出现一次。
