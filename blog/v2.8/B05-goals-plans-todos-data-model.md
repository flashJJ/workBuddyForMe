# 目标、计划、待办：三张表，而不是三套状态机

「让 AI 会做计划」听起来像是提示词工程。真做下去会发现，难点几乎全在数据模型：目标与计划是什么关系、待办要不要单独建表、步骤状态能不能回退、评审状态怎么和计划状态共存于同一行。

这一轮的原则可以先说出来：**能用一个状态机表达的，就不建第二个**。

## 一、三层结构，四个表

关系画出来很朴素：

```text
会话 conversation
  └─ 目标 goal          这一场对话要达成什么 + 成功标准
       └─ 计划 plan      有序步骤，可评审、可改写
            └─ 步骤 step  pending → running → done / skipped / blocked

会话 conversation
  └─ 待办 todo          计划的一种 kind，轻量视图，自动批准
```

落到库里是四张表（其中一张是回投幂等表，和计划系统共用同一个仓储）：

| 表 | 关键列 | 说明 |
|---|---|---|
| `conversation_goals` | `id, conversation_id, title, success_criteria, status` | 状态只有 `active / achieved / dropped` |
| `work_plans` | `id, conversation_id, goal_id, kind, title, status, origin, approved_at` | `kind` 取 `plan` 或 `todo` |
| `work_plan_steps` | `id, plan_id, step_index, title, status, note` | 按 `step_index` 升序读取 |
| `run_completions` | `run_id, kind, status` | 完成回投的幂等键 |

几个刻意的选择：

- **目标可以没有计划**。单独立项时用户只想说清楚「我要什么」，不强迫他拆步骤。
- **计划可以没有目标**。模型提出的计划常常先于目标形成，`goal_id` 可空。
- **步骤不单独建状态机字段**。它就是计划行的一部分，读计划时按 `plan_id` 一次性取出，不做懒加载。计划规模被提示词上限压在 10 步以内，没必要为分页付代价。

## 二、Todo 是 Plan 的轻量视图

这是本轮最重要的一个决定：待办不是第四张表，而是 `kind='todo'` 的计划。

理由来自「谁在写」这个问题。计划是人和模型共同编辑的结构化对象：评审、改写、逐步推进，状态机完整。待办是模型在一次回复期间反复覆盖的短清单：内容变得快、结构很浅、没有评审。它们**写入节奏完全不同，但读取语义相同**——都是「一串有序的、有状态的条目」。

如果给待办建独立表，就要再建一套状态常量、再写一套进度计算、再让 UI 判断当前该显示哪一个。而实际上 UI 想显示的东西是一样的：`已完成/总数` 加上条目列表。

复用之后得到两条硬约束：

1. 同一会话同一时间最多一个活跃的 `todo` 清单，用 `status NOT IN ('abandoned','rejected')` 加倒序取第一条来保证；
2. 待办创建时直接是 `approved`，因为它不需要评审；模型写的正式计划则进入 `pending_review`。

`todo_write` 的写入是**全量替换**而不是增量合并：模型每次传入完整清单，服务端把旧步骤删掉、按新顺序重建。这样模型不需要记住步骤 id，也不会出现「上一次的第 2 步被合并进这一次的第 2 步」这种错位。

## 三、步骤只前进，不回退

步骤状态机只有四个值加一个失败态，转移规则被写成一张等级表：

| 从 | 允许到 | 说明 |
|---|---|---|
| `pending` | `running` / `done` / `skipped` / `blocked` | 可以跳过，适合不适用项 |
| `running` | `done` / `skipped` / `blocked` | 正常推进 |
| `done` / `skipped` / `blocked` | 无 | 终态，不可再改 |

实现方式是给每个状态一个等级分：`pending=0, running=1, done/skipped/blocked=2`。校验时只要「目标是终态」或「目标等级低于当前等级」，就拒绝并返回「步骤状态只能前进，不能回退」。

为什么要禁止回退？因为回退会让进度数字变得不可信。`已完成/总数` 是一个单调量，一旦允许勾销，用户看到的进度就会反复横跳，桌宠的信号也会跟着抖动。真要重来，正确操作是**新建一个计划**，而不是把旧计划拨回去——旧计划是一段历史，历史不该被改写。

计划级状态则比步骤多一层评审：

```text
draft ──submit──▶ pending_review ──approve──▶ approved ──▶ running ──▶ done
  ▲                    │
  └────── reject ◀─────┘        rejected ──submit──▶ pending_review
```

`rejected` 回到 `draft` 的能力用「提交评审」表达：草稿与已驳回都可以提交，提交后统一进 `pending_review`。这样不需要一条 `rejected → draft` 的边，状态图少一条边，UI 也少一个按钮。

只有一个地方自动化：当计划处于 `approved` 或 `running`，且**所有步骤都到达终态**时，计划自动转为 `done`。否则用户得在完成最后一步之后再点一次「完成计划」，纯属多余。

## 四、可编辑性跟着状态走

改写（标题、步骤增删改）只在三个状态下允许：`draft`、`pending_review`、`rejected`。批准之后不允许改步骤，因为批准的对象是「这份步骤」，改了就等于绕过了评审。

`replaceSteps` 的实现是按 id 对齐的差量更新，而不是先清空再插入：

- 带 id 且属于本计划的步骤 → 原位更新标题、状态、备注、序号；
- 不带 id → 新增；
- 旧集合里没被保留的 id → 删除；
- 最后统一重排 `step_index`。

整个过程在一个事务里，任何一步失败都不会留下半个计划。

## 五、评审的边界：只落库，不执行

服务层对外只做三件事：校验、落库、发变更通知。它**不下发工具、不触发运行、不调用执行器**。

这不是保守，而是职责划分。计划是意图，执行是另一条链路。如果「批准」直接触发运行，那么计划页就变成了一个隐形的执行入口，绕过工具审批、预算控制与工作信号。所以批准只做一件事：把状态改成 `approved`、记下批准时间，并让上下文里的「待评审」提示消失。

## 六、查询投影：三个读口

写模型复杂，读模型要简单。对外只暴露三个投影：

| 投影 | 用途 | 取数规则 |
|---|---|---|
| `listGoals(conversationId)` | 计划页目标区 | 按创建时间倒序 |
| `listPlans(conversationId?)` | 计划页计划区；不带会话 id 时全量取最近 200 条 | 按创建时间倒序 |
| `activeContext(conversationId)` | 对话装配 | 一个 active 目标 + 一个非终态正式计划 + 一个活跃待办 |

`activeContext` 里「哪个计划算当前计划」的优先级是：`approved` → `running` → `pending_review` → `draft`。这个顺序和对话顶部的计划条一致，避免出现「提示条显示 A、提示词里写 B」的分叉。

## 七、这一篇的结论

目标、计划、待办看起来是三个产品概念，落到数据上只有一个真正的状态机：`work_plans` 加 `work_plan_steps`。目标是最上面一层不太变的意图，待办是同构的轻量实例。

省下来的不只是两张表，而是**两套进度口径、两套状态文案、两套 UI 判断**。下一篇讲这份数据怎么进入模型上下文，以及「待评审」这四个字为什么会写进提示词里。
