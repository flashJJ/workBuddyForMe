# 后台作业怎么被观察：总线、seq 续传与单例 owner 租约

把运行挪到服务端之后，真正难的不是「让它继续跑」，而是**让多个观察者看到同一份、顺序一致、可续传的事件流，同时保证谁都不能顺手把它启动第二次**。

这篇讲三件事：后台消费循环的形状、观察总线的订阅语义、以及单例 owner 租约如何把「谁拥有这次运行」变成一条数据库事实。

## 一、作业的形状：一个注册表，五个字段

进程内的活跃作业表是这次改造的核心数据结构。每个运行对应一条记录：

```text
ActiveRun {
  control   // 暂停 / 恢复 / 停止的协作控制柄
  abort     // 中断信号，只有显式停止与致命错误会触发
  bus       // 本次运行的事件总线（带缓冲）
  done      // 消费到底的 Promise
  seq       // 已广播帧数，也就是观察者续传用的序号上界
}
```

启动时先查表：同一个运行 id 已经在表里，就直接返回这条总线的订阅迭代器。**重复订阅不是错误，也不会二次启动**——这是一个接口语义上的决定，而不是防御性补丁。旧实现里重复打开会抛冲突，前端被迫自己做去重；现在由服务端保证幂等。

这条总线要同时服务三类观察者，它们的订阅时机完全不同：

| 观察者 | 何时订阅 | 真正关心什么 |
|---|---|---|
| 对话页 | 启动后立刻 | 全过程时间线，一帧不漏 |
| 桌宠 | 常驻，且不依赖主窗 | 聚合后的状态变化 |
| 协作舞台 | 中途加入 | 从开头补齐，再跟实时 |

三类需求最后收敛成同一组接口：完整回放、从某帧续传、只收新帧。差别在起始游标，不在事件内容。

## 二、消费循环：先广播，再继续

作业的后台循环只有四步，但顺序很关键：

```text
启动 → 写租约
循环:
  step = await 运行生成器.next()
  如果结束: break
  seq += 1
  先把这一帧发布到总线
  再回到循环
结束:
  关闭总线 → 从注册表摘除 → 清租约 → 终态回调
```

「先发布再继续」保证了广播序号与生成器产出严格同序。总线内部是同步入缓冲、唤醒等待者，不阻塞 owner；观察者各自持游标，慢的观察者只会落后，不会拖住运行。

异常路径单独处理：生成器抛错时，先读一次最新运行行，如果还不是终态就收敛成失败，并补发一帧 `run_finished`，避免出现「注册表已经摘除、库里还写着 running」的窗口。最后无论正常、异常还是中断，都走同一个收尾：关总线、清租约、调一次完成回调。

## 三、`since` 续传：序号是运行内的，不是全局的

观察者可以带一个 `since` 参数回来。约定很朴素：

| 传入 | 行为 |
|---|---|
| 不带 `since` | 从缓冲头开始，整场回放，然后接新帧 |
| `since = 1` | 等价于整场回放（序号从 1 开始） |
| `since = n > 1` | 从第 n 帧开始，之后的帧照常推送 |
| `since` 超过缓冲末尾 | 只收新帧，等下一次广播 |

实现上把起始下标钳在 `[0, 当前帧数]` 区间，所以越界不会报错，只会降级成「从最新处继续」。这比抛错更符合实际：页面重连时手上的序号往往比服务端旧，它要的是「别丢帧」，不是「证明你序号合法」。

序号的作用域是**单次运行**，不是全局递增。全局序号会逼出一条永远增长的序列，还要处理跨运行乱序；而观察者的真实需求只是「这场运行我看到第几帧」。

还有两个边界值得记住：

- **`since` 只在作业存活期内有意义**。作业收尾后总线关闭，缓冲一并释放，这时再拿旧序号来续传，得到的不是历史，而是「没有这个作业」。历史要靠落库数据回放。
- **缓冲不是日志**。它默认不设上限，因为一次任务的事件量天然有界（步骤、工具调用、状态变化加起来是几百帧量级）。真正的上限是内存，不是吞吐；有界缓冲只留给跨多轮的长连接场景，那时由调用方从库里的历史补齐，live 订阅只收新帧。

## 四、断线不 abort：把「离开」和「停止」拆开

这是整篇最容易被写错的一条。订阅的生命周期和运行的生命周期必须彻底解耦：

| 动作 | 是否影响运行 |
|---|---|
| 页面关闭 / 刷新 / 网络断 | 否 |
| 第二个观察者加入 | 否 |
| 观察者读到一半退出迭代器 | 否 |
| 用户点停止 / 全部停止 | 是 |
| 暂停、恢复 | 是（但不终止） |
| 预算耗尽 / 致命错误 | 是 |

所以「停止」不能靠浏览器关页来推导，必须是显式控制指令。相应地，作业服务对外暴露的不是一个「流」，而是一组动词：启动、观察、等待完成、停止、暂停、恢复、全部停止、是否活跃。

协作运行这里多一层历史包袱：它的旧接口把客户端信号合并进中断信号，断线会 abort。这一轮保留了那个拥有型的启动入口，只给工作流节点内部消费——队列所有方持有它，语义成立。面向页面的入口换成后台持有版本，页面拿到的只有总线的订阅权。

顺带解决一个竞态：协作运行在「客户端解析还没完成」的窗口里就被急停。做法是注册总线的那一刻就发布一个等待柄，让先开窗的观察者挂上去；客户端解析失败则让等待柄失败，观察者回落到终态回放，而不是空等到超时。

## 五、租约：一条数据库事实，不是一把锁

作业启动时写两个列：`lease_owner`（进程实例 id，形如 `web-<pid>-<启动时间戳>`）和 `lease_expires_at`（当前时刻加 90 秒）。终态、异常、恢复收敛时都清空。

按契约，租约到期 90 秒、心跳周期 30 秒。但必须说清楚它在这一轮**不做什么**：

- 不做跨进程抢占：单进程部署没有第二个候选人；
- 不做选主与接管：重启后不存在「另一个进程来接手」的场景；
- 不做分布式锁：SQLite 的写事务已经保证了同一行不会被并发改坏。

它唯一的用途是重启后的判别：**这行 running 有没有一个活着的 owner**。没有，就收敛；有，理论上还在跑——但因为进程内注册表随进程消失，重启后必然没有，所以恢复逻辑可以直接按「全部收敛」处理，租约列则作为下一阶段做接管时的接缝保留下来。

## 六、为什么 Task 与 Agent 共用一套作业语义

两套运行原本的差异不小：任务有步骤、有工具、有暂停；协作有角色、有交接、有预算。如果按差异去做两套生命周期，会得到两套订阅语义、两套终止原因、两套回投入口。

我们选择只统一「作业层」，不统一「业务层」：

- **统一的部分**：注册表、单例启动、总线、序号续传、租约、完成回调；
- **不统一的部分**：事件类型、状态取值、终止原因、失败归类。

这样页面上「关掉再回来」的行为对两类运行完全一致，而各自的业务语义不被拉平。差异被限制在映射层：任务收敛成 `stopped(interrupted)`，协作收敛成 `cancelled` 加错误码 `INTERRUPTED`，观测者不需要知道这个区别。

## 七、这一层留下了什么

后台作业层最终只暴露两样东西给上层：一个可以反复订阅的事件流，和一份可以查询的状态。页面不再拥有生命周期，桌宠不再依赖主窗是否打开，协作舞台只是第三个观察者。
