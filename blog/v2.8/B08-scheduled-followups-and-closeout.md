# 到点了才说话：定时跟进如何做到「最多一次」

「三十分钟后提醒我继续」「明早把这个结果发我」——这类需求看起来是定时器问题，实际是两个问题叠在一起：**什么时候算到点**，以及**怎么保证同一时刻只说一次**。

这一轮没有新增任何服务端定时器。所有到点判定仍然复用已有的客户端心跳，我们只给提醒加了一个载荷，以及在「确实到点」时向会话注入一条消息。

## 一、提醒原本只是一个通知

既有的提醒模型很简单：一条 `scheduled_tasks` 记录，带触发时刻、重复规则、启用状态、文案。tick 每 10 秒跑一次：

```text
listDue(now) → 逐条 markFired（once 停用，daily/weekly 重算下次时刻）→ 投递
```

顺序是「先标记，后投递」，这个顺序决定了幂等口径：投递失败不回滚触发时刻，避免同一条提醒反复打扰。错过就跳过，和日历应用的行为一致。

这一轮要加的是「到点时额外往会话写一条助手消息」。所以只需要一个字段：载荷。

```text
payload = {
  kind: 'follow_up',
  conversationId?: string,
  planId?: string,
  runId?: string,
}
```

`payload_json` 可空，为空就是原有行为（只提醒，不写会话）。只有 `kind='follow_up'` 的提醒会在投递时追加消息。加一个可空字段而不是新建表，是这次迁移的原则：**纯加法，旧库可读，回退不破坏数据**。

## 二、`/fire` 的三步：读旧值、标记、再判断

到点动作被拆成三步，顺序不能换：

```text
before = 读取提醒（此刻 nextRunAt 还是本次预定时刻）
updated = markFired(id)            // 推进 nextRunAt / 停用
due = before.nextRunAt <= now && before.enabled
if (due && updated.payload?.kind === 'follow_up')
    向 payload.conversationId 注入一条助手消息
```

第二步先标记，是为了让「谁赢了这次触发」在数据库里立刻可见。第三步用**标记前的旧值**判断「是否真的到点」，这是整段代码里最不直观、也最必要的一处。

原因在多标签页：两个页面同时跑 tick，都会对同一条提醒发起触发。第一个页面把 `nextRunAt` 推进到明天，第二个页面读到的旧值仍是今天，但标记后返回的新值是明天。如果拿新值判断，第二次会被判成「还没到点」——这正确；如果拿旧值判断但没先标记，两次都会判成到点，就会注入两条消息。

所以判据必须是：**旧值显示已到点，且标记成功**。

## 三、幂等键 = 提醒 id + 本次预定时刻

会话消息的追加走的是和运行回投同一条路径，幂等键换成：

```text
schedule:<提醒 id>:<本次预定时刻>
```

加上 kind `follow_up`、状态 `fired`，最终落在同一张 `run_completions` 表里。同一个提醒的同一个预定时刻，永远只可能抢到一次占位。

为什么不只用提醒 id？因为重复提醒（每日、每周）会在同一个 id 上产生多次到点。只用 id 会让第二天的那次被第一次挡住，用户从此再也收不到跟进。把「本次预定时刻」拼进键，等于把「第几次触发」变成业务事实。

为什么不只用时间戳？因为不同提醒可能在同一秒到点，时间戳不唯一。两个维度必须一起用。

## 四、为什么沿用客户端 tick，而不是加服务端定时器

这个决定在评审里被反复讨论，最后保留原方案，理由有三条：

1. **桌面应用没有常驻服务端进程。** web 端跑在本地，主窗关闭、桌宠也退出时，进程里没有任何东西在运行。加一个服务端定时器，等于要求一个「永远在」的宿主，而这与本地优先的产品形态冲突。
2. **已有心跳就在做这件事。** 调度 tick 每 10 秒一次，主窗或桌宠页面存活时就在跑。再起一套独立定时器，会出现两个时钟、两套补偿逻辑，以及它们之间的竞态。
3. **漏触发是可接受的。** 应用没开时不该假装提醒发生。下次打开时，过期的提醒会按「错过即跳过」处理——这与用户对本地应用的预期一致，也避免了开机瞬间补发一堆过期提醒。

代价要写清楚：**应用完全没运行时，跟进不会发生**。这是产品边界，不是 bug。所以跟进文案里不承诺「准时送达」，只说「到点提醒」。

## 五、和工作信号的复用关系

定时跟进不新造通知通道。到点后仍然走既有的提醒投递：勿扰时段只留通知不出声，无人值守时桌面操作继续被拒绝。新增的那条会话消息则挂在计划/待办的同一条追加路径上，所以：

- 计划条刷新时能看到跟进带来的新消息；
- 桌宠的完成脉冲只响一次，不因为「提醒 + 消息」变成两次；
- 回投失败只告警，不回滚触发时刻。

一个额外的接线是 `planId` 与 `runId`：载荷把它们带回来，是为了让后续实现「跟进时自动续做」时有稳定的指针——但这一轮**没有**用它触发任何运行。

## 六、与契约的五处偏差

交付时对照开工前冻结的契约，有五处主动偏离，都已记录：

| 项 | 契约原意 | 实际交付 | 原因 |
|---|---|---|---|
| 对话内计划卡 | 消息内卡片 | 顶部计划条 + 计划页集中操作 | 历史消息不适合承载可变的重交互 |
| 计划执行 | 批准后可执行 | 批准只解除提示，不触发运行 | 执行必须逐次过工具审批闸门 |
| 待办桌宠信号 | 计划/待办都显示 | 待办全未开始不显示，完成转成功脉冲 | 避免空闲误报噪音 |
| 定时跟进触发 | 服务端调度 | 沿用客户端 tick（主窗或桌宠存活时） | 桌面形态无常驻服务端 |
| 子运行树 | 父子运行与聚合 | 延后 | 先保证单层作业的可靠性 |

偏差不是妥协清单，而是**把「做不到」提前写清楚**。最危险的状态是没做但看起来做了。

## 七、五条可复用的方法

**一、先冻结故障矩阵，再写代码。** 崩溃、断网、重启、重复订阅、用户取消，五种情况各画一行「之前是什么、之后应该是什么」。这一轮返工最少的部分，就是先画了矩阵的部分。

**二、幂等键先于功能。** 不要等出现重复再补去重。先问「这件事的业务唯一标识是什么」，把它建成主键，再写写入逻辑。键选错（比如带上了状态），后面所有补救都是错的。

**三、优先复用既有心跳，而不是新增组件。** 多一个定时器就多一个时钟、一套补偿、一类竞态。先看现有循环能不能承载，实在不行再加。

**四、恢复只做状态收敛。** 中断是终态，不是待修复的异常。不重放步骤、不自动重跑，把「重新发起」留给用户。

**五、把前置条件写成判据。** 「确实到点才注入」不是一句注释，而是一个可测试的布尔表达式：旧值已到点、且标记成功。写不出这个表达式，说明幂等还没想清楚。

## 八、收尾

这一轮交付的东西，抽象出来只有两类：

- **所有权**：运行归服务端，页面只是观察者；中断是一类正常终态；结果必须回到会话，且只回一次。
- **意图**：目标、计划、待办让「它在做什么」变成可读状态；评审让人保留决定权；提示词与界面读同一份数据。

两类都指向同一个产品判断：**本地优先的桌面应用，可靠性不来自更多基础设施，而来自更少的假设**。假设「用户会一直开着页面」被删掉了，假设「进程不会死」被删掉了，假设「提醒一定准时」也被删掉了。剩下的每一条，都能在断网、关窗、崩溃、重复点击之后仍然成立。
