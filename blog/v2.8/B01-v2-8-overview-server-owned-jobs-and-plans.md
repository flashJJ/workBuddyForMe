# 关掉页面，任务还在跑：把长任务的所有权从浏览器收回来

用户提过一句很朴素的话：我在任务跑到一半时切去写文档，回来发现它停了，也不知道停在哪。

这不是一个界面问题。我们查下去，发现任务类运行的生成器生命周期挂在一个 SSE 请求上——请求断开，`AbortController` 就 abort，运行随之终止。页面既是观察者，也是所有者，而浏览器标签页从来不是可靠的进程宿主。

这一轮我们只做两件事：**把运行的所有权从页面收回到服务端**，以及**给对话装上目标、计划与待办，并让人能评审**。前者修可靠性，后者修「它在替我干什么、干到哪了」的可见性。

## 一、断点很具体：生命周期绑在连接上

桌面 AI 应用天然会遇到这几种断线：

| 场景 | 旧行为 | 用户感受 |
|---|---|---|
| 关闭主窗 | 流断开，运行 abort | 任务白跑，还得重来 |
| 刷新页面 | 同上 | 时间线丢失，只看到半条 |
| 切到别的应用 | 多数情况没事，但网络抖动会断 | 时好时坏，不可预期 |
| 另一个页面也想看 | 第二个观察者会触发重复启动或冲突 | 不敢多点 |

根因只有一句话：**谁发起了那个 HTTP 请求，谁就拥有了这次运行**。而 HTTP 请求的寿命由浏览器决定，不由业务决定。

## 二、第一件事：运行改成服务端持有的作业

改造后的模型分成三层，职责单一：

- **进程内作业注册表**是唯一的运行现场：持有控制柄、中断信号、事件总线、完成 Promise、当前帧序号；
- **数据库**只记录可观测状态与租约，不承担调度；
- **页面、桌宠、协作舞台**全部降级为观察者，订阅事件、随时离开、随时回来。

任务与协作共用同一套作业语义，这一点是刻意的：它们对用户是同一类东西——「我交代了一件事，它得继续做，做完告诉我」。分开做两套生命周期，只会得到两套边界条件。

服务端启动作业时做三件事：登记注册表、写一条租约、在后台把运行循环消费到底。观察者拿到的只是一个迭代器，拿走或扔掉都不影响运行。

## 三、三件套：归属、恢复、回投

光有「后台跑」还不够。一个没有归属、没有恢复、没有回投的后台任务，只是把「不知道结果」藏得更深。所以三件事必须一起交付：

| 能力 | 解决的问题 | 关键约束 |
|---|---|---|
| 运行归属 | 关页不再中断；多观察者不重复启动 | 单例 owner + 租约，启动写、终态清 |
| 重启恢复 | 进程崩溃后不留幽灵 running | 只收敛状态，不伪造成功、不自动重跑 |
| 完成回投 | 回来能在会话里看到结果 | 幂等键 `(run_id, kind)` 唯一，只追加一次 |

租约只回答一个问题：这行 `running` 是不是本次进程还在跑。单进程部署下它不做跨进程抢占，也不承担选主——把复杂度留给用不上的场景，是这一轮最重要的减法。

三件事在代码里其实是一条链：

```text
启动   → 写租约 → 后台消费 → 逐帧广播
终态   → 清租约 → 读最新运行行 → (run_id, kind) 占位 → 追加助手消息
崩溃   → 首次装配扫描非终态行 → 收敛为终态 → 走上面同一条回投
```

后两条共用同一个写入点。回投不是三套代码，而是所有终态的公共出口——这一点决定了重复消息的防线只需要建在一处。

## 四、第二件事：给对话装上目标、计划与待办

可靠性和可见性是同一个问题的两面。任务能跑到底了，用户下一个问题必然是「它到底打算怎么做」。

于是对话多了三层结构：**目标**（这一场对话要达成什么、成功标准是什么）、**计划**（有序步骤，可评审、可改写）、**待办**（模型自己维护的轻量清单）。待办不另建状态机，它就是计划的一种视图。

计划有评审：草稿提交评审、批准或驳回，驳回后可改写再提交。未批准的计划只会以一段提示出现在模型上下文里，并明确标注「勿执行高风险步骤」——**评审不是执行开关，批准也不绕过工具审批闸门**。

## 五、为什么不引入队列中间件

这是评审时被问得最多的一点。我们的答案是不引入，理由按重要性排：

1. **部署形态决定的**。这是单人开发、单机运行、Windows 桌面交付的产品，没有第二个消费者，也没有横向扩展的需求；引入消息中间件等于给自己加一个必须运维的进程。
2. **真相已经只有一个**。SQLite 里的运行行就是唯一事实，进程内注册表只是现场。再叠一层队列，会出现「队列说在跑、库里说结束」的第三套真相。
3. **故障模式反而变多**。中间件带来投递语义、重复消费、死信、连接重建；而单进程的故障模式只有一种——进程没了，重启后统一收敛。
4. **既有队列语义不动**。工作流运行本来就由队列所有方持有，这一轮明确不改它的语义，避免一次改动同时动两套所有权模型。

代价我们也认：进程内注册表意味着**不支持多实例并行**。这是有意的取舍，写进了不做清单，而不是留成隐形假设。

## 六、门禁数字

| 项 | 结果 |
|---|---|
| `pnpm check` | 类型检查 14/14 包通过，静态检查 0 error |
| 行数门禁 | 手写文件 ≤300 行 |
| shared 包单测 | 321 例 |
| database 包单测 | 229 例（含新表与新列 3 例） |
| core 包单测 | 1154 例（作业 8、恢复 2、计划/待办/回投 9） |
| web 端单测 | 588 例（含计划 API 4 例、任务观察流、导航 10 项） |
| 浏览器端到端 | 计划评审与步骤推进 2/2 |

新增用例集中在最容易出错的地方：重复订阅不重复启动、断线不中止、重启后状态收敛、回投只追加一次、非法状态转换被拒。

这些数字不是装饰。作业层真正的风险不在功能缺失，而在竞态：两个页面同时打开、进程恰好在写状态时被杀、恢复与正常收尾同时看到终态。用例全部压在竞态上，功能路径反而写得少。

## 七、刻意留下的空白

- 不做子运行树：父子运行关系、子代理聚合与父级中断，明确延后，先保证单层作业可靠。
- 不做自动批准：计划不自动触发运行，高风险工具仍逐次审批。
- 不做云端调度与跨设备作业：与「数据不出机」冲突。
- 不做计划依赖图与甘特图：那是项目管理工具，不是陪伴型应用该背的复杂度。

## 八、这一轮真正改变的东西

表面看是两个功能：后台作业与计划系统。实质是把一条隐含假设改掉了——**「用户必须待在那个页面上，工作才成立」**。

改完之后，页面退回它该在的位置：一个观察窗口。关掉它，运行继续；再打开，时间线完整；到点了，结果已经躺在会话里。
