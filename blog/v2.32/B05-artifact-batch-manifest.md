# 产物批量打包：用一份清单把「带走什么」说清楚

单张图片导出解决的是「这一张我要用」，跨会话批量打包解决的是「这一批我要归档」。

两者的设计目标不同。单张导出可以只关心格式与画质；批量打包必须回答另外三个问题：包含哪些、有多大、来源在哪里。

这一版用 tar.gz + manifest 的组合来解决。

## 一、为什么不是 zip

zip 更常见，但项目里已经有一套 tar.gz 打包实现，用于备份归档。

复用现有实现有三个好处：

- 不引入新的原生依赖；
- 压缩与解压路径已经过测试；
- 产物包与备份包使用同一种容器，用户不需要记两种格式。

格式选择不是技术优劣，而是维护成本。

## 二、manifest 记录什么

每一条记录包含：

```json
{
  "id": "产物 id",
  "title": "展示标题",
  "format": "svg / png / html",
  "bytes": 12345,
  "conversationId": "来源会话",
  "createdAt": "创建时间",
  "archivePath": "artifacts/001-xxx.svg"
}
```

`archivePath` 是关键字段。它把用户看到的标题与归档里的实际文件对应起来，避免同名文件互相覆盖。

## 三、文件名怎么安全化

产物标题可能包含斜杠、冒号、问号、控制字符，甚至以点开头。

打包前统一清洗：

- 控制字符与路径分隔符替换为短横线；
- 去掉开头的连续点，避免隐藏文件；
- 加三位序号前缀，保证同名不覆盖；
- 清洗后为空时回落到 `artifact.<扩展名>`。

这条规则看起来琐碎，但它决定了解压后的文件是否可预测。

## 四、限额为什么放在读取之前

批量导出设置了两条硬上限：最多 100 条、累计不超过 200MB。

校验顺序很重要：先检查数量，再读取元数据计算总字节，最后才读文件。任何一步超限都直接拒绝，不生成半份归档。

如果把限额放在打包完成之后，用户会得到一个「下到一半失败」的压缩包，还需要自己清理。

## 五、来源会话怎么找

产物表本身不存会话 id，只存附件元数据。

来源会话是从消息的多模态片段里反查的：查找包含该附件 id 的消息，取第一条的会话 id。找不到就写 `null`。

这是最佳努力，不保证 100% 准确，但足够支撑「这个产物大概来自哪次对话」的展示需求。

## 六、前端多选的状态

前端要维护一份选中集合，并实时显示「已选 N 个 · 总大小」。

超过上限时不禁用整个面板，而是提示「请减少选择」，让用户可以自己调整。直接禁用会让用户不知道哪一步出了问题。

## 七、适用场景

- 把一次项目讨论里的所有图表打包，交给同事；
- 归档一组 SVG 源文件，保留标题与来源；
- 迁移前先导出重要产物，不依赖整库备份。

它不是备份的替代品，而是备份之外的一条轻量出口。

## 八、边界

这一版没有做：产物去重、跨包增量、压缩级别选择、单文件流式下载。

批量打包的定位是「一次带走一批」，不是「长期同步」。
