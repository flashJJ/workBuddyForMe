# 数据可带走：备份预检、补全、打包与清理的四条链路

本地优先的桌面 AI 应用，数据存在用户自己的机器上。这听起来很安全，但「数据在你的磁盘里」和「数据随时能带走」是两回事。

早期版本已经能导出备份、能从归档恢复，但整条生命周期只完成了一半：

- 恢复预检写在恢复请求里，用户点下按钮之后才看到版本与条数，实际上是「先恢复再看结果」；
- 备份不含协作运行与角色交接，换一台机器恢复后，任务历史里的一段关系是空的；
- 产物只能一张一张导出，跨会话收集素材只能手工点；
- 附件删了消息也不清理，数据根占了多少空间没有入口可看。

这一版补四条链路：预检前置、备份补全、产物批量打包、存储统计与孤儿回收。

## 一、预检为什么要独立

预检本身早就存在，问题是它和恢复绑在同一个请求里。

设计上把它抽成一个只读接口，只做三件事：解析 manifest、判断版本兼容、统计各轨条数。它不写数据库，也不把归档解压到磁盘。前端改成两步：选文件后先预检，用户确认后才恢复。

这个改动看起来只是接口拆分，实际改变的是责任边界：预检失败不会留下半恢复的数据，版本不兼容也不会先写一半再报错。

## 二、备份补全为什么只做加法

协作运行和角色交接是两张已有表，只是没有进入备份轨。

处理方式是只做加法：在 tasks 轨里增加两个可选文件和两个可选计数。旧归档没有这些文件时按空数组处理，恢复端不做强制校验。

这样带来两个好处：旧归档仍可恢复；新归档在老版本里即使被忽略这些文件，也不会破坏其他轨的读取。

## 三、产物打包的清单思路

产物导出原本是单张图片的格式转换。批量打包换了一个思路：不改变产物本身，只把多张产物装进 tar.gz，再附一份 `manifest.json`。

清单记录条目 id、标题、格式、字节数、来源会话与创建时间。对用户来说，这是一份可读的「这次带走了什么」；对后续处理来说，它是一个稳定的索引。

上限放在读取文件之前：最多 100 条、累计 200MB。超限直接拒绝，不生成半份归档。

## 四、清理为什么先移后删

附件回收最怕误删。

流程被固定成三步：扫描候选、展示数量与字节、确认后移动到 `.trash/<date>/`。移动不是删除，回收目录保留 7 天，期间可以恢复。

这个设计牺牲了一点磁盘空间，换来的是可逆性。对一个单人开发的本地应用来说，可逆比省空间重要。

## 五、四条链路的共同点

预检、补全、打包、清理看起来是四件事，底层是同一种取舍：把不可逆操作变可逆，把隐式行为变显式。

- 预检把「恢复后才知道」变成「恢复前就知道」；
- 加法轨把「新归档必须配新应用」变成「旧应用也能读」；
- 打包清单把「一堆文件」变成「一份可核对的清单」；
- 回收目录把「删除」变成「移动 + 保留期」。

## 六、这一版没有做什么

没有做云同步、没有做自动定时备份、没有做备份加密、没有做物理删除。

这些不是遗漏，而是边界。数据可带走的下一步才是数据可托付：加密、引用计数、恢复核对，留给下一版。

## 七、用户路径怎么变化

改动之前，用户恢复一份归档只有一步：选文件、点恢复、等结果。

改动之后，路径变成：

```text
选择归档
  → 看到版本、轨道条数与警告
    → 勾选要恢复的轨道
      → 确认恢复
        → 看到导入/跳过统计
```

多了一步，但每一步都更可控。

导出侧的变化更轻：新增模式与密码入口，产物面板多了一个「打包下载」。

## 八、验收时看什么

这一版没有引入新的数据库迁移，验收集中在行为：

- 预检调用前后，数据库记录数与文件修改时间不变；
- 旧归档恢复后，协作轨按 0 处理，其他轨正常；
- 批量打包的清单条目数与实际文件一致；
- 存储统计的分项之和等于合计；
- 回收 dry-run 不移动任何文件。

这些都是可观察的行为，不依赖日志或内部状态。

## 九、下一版的入口

数据可带走的终点，是用户愿意在另一台机器上按下恢复。

要走到那一步，还缺三件事：归档不能被随便打开、附件要能说清引用、恢复结果要能核对。

这正是下一版的三条主线。
