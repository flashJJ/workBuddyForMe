# 恢复预检为什么必须前置：把「先恢复再看」改成两步确认

恢复备份是一个高风险动作：它要写数据库、要落盘附件、要覆盖或跳过已有数据。用户在这一步最需要的不是速度，而是确定性。

早期实现里，预检逻辑是有的，但它运行在恢复请求内部，结果和恢复结果一起返回。也就是说，用户必须先按下「恢复」，才能看到版本是否兼容、各轨有多少条、有没有需要重新填写的凭证。

这在交互上等于没有预检。

## 一、预检应该回答什么

一个合格的预检至少要回答四个问题：

1. 这个归档来自哪个版本，当前应用能不能读；
2. 各轨道分别有多少条数据；
3. 有没有需要人工处理的内容，例如被脱敏的凭证；
4. 归档结构是否完整，manifest 是否能通过 schema 校验。

这四个问题都不需要写数据库。它们只依赖归档本身。

## 二、拆成只读接口

实现上新增一个独立接口，输入是归档文件与可选密码，输出是兼容性、源版本、轨道计数与警告列表。

关键约束是「只读」：

- 不打开数据库事务；
- 不创建解压目录；
- 不写任何临时文件；
- 解压只在内存中完成，随请求结束释放。

这样即使预检失败，也不会留下任何需要清理的状态。

## 三、两步恢复的状态机

前端把恢复拆成两个阶段：

```text
选择归档
  → 预检（只读）
    → 不兼容：禁用确认，展示原因
    → 兼容：展示计数与警告，允许勾选轨道
      → 用户确认
        → 执行恢复
          → 返回导入/跳过统计
```

版本不兼容时，确认按钮直接禁用。用户不需要先触发一次失败请求才知道「这个归档太新」。

## 四、预检结果的兼容性

恢复接口仍然返回预检结果，而不是强制前端只走新接口。

原因是兼容性：旧前端、脚本调用、历史客户端可能仍然依赖「一次请求拿到预检 + 结果」的行为。新增只读接口是加法，不是替换。

这也是一个常用的接口演进策略：新流程走新接口，旧流程保留原语义，等旧调用自然消失后再考虑收缩。

## 五、预检与恢复共用同一套判断

预检和恢复都调用同一个核心函数，只是预检不进入写库阶段。

这样做避免了两套逻辑漂移：如果恢复端新增了一种警告，预检端不需要单独实现；如果版本兼容规则变化，两边同时生效。

## 六、什么时候预检不够

预检是静态检查，它不能保证恢复一定成功。

例如目标库缺少外键依赖、附件文件在归档中缺失、磁盘空间不足，这些问题只有在恢复阶段才会暴露。

所以预检的定位不是「保证成功」，而是「提前排除明显不该继续的情况」。真正的兜底仍然是恢复事务与恢复后的核对报告。

## 七、可复用的经验

任何「导入 / 恢复 / 迁移」类功能，都值得问三个问题：

- 用户能不能在写数据之前看到结果？
- 只读检查能不能不产生副作用？
- 旧调用方能不能不被破坏？

预检前置不是新功能，而是把已有能力放到了正确的位置。
