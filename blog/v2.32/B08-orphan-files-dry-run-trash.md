# 孤儿附件回收：为什么只移动、不删除

附件是本地应用里最容易膨胀的数据。

用户删了一条消息，消息里的图片引用没了，但附件行和磁盘文件还在。时间一长，`attachments/` 目录里堆着一批谁也不认识的文件。

这一版补了孤儿附件扫描与回收，但做了一个刻意的限制：只移动，不删除。

## 一、什么叫孤儿

这一版的判定很窄：`attachments/` 下的文件，在附件表里找不到对应记录。

注意它不判断「有没有被消息引用」。那个能力要等到引用计数建立之后才有。

窄判定的好处是误杀概率低：只要表里有记录，就不动它。

## 二、三步流程

```text
扫描候选（只读）
  → 展示数量与字节（dry-run）
    → 用户确认
      → 移动到 .trash/<date>/
```

扫描不产生任何文件或数据库变更。用户看到的是候选清单，不是已经执行的结果。

确认之后才移动，移动目标按日期分目录，方便后续恢复与到期清理。

## 三、为什么移到回收目录

直接删除不可逆。

移动到 `.trash` 之后，文件仍然在磁盘上，只是离开了活跃目录。用户可以在 7 天内恢复，也可以手动去目录里找。

这个设计牺牲了「立即释放空间」，换来了「误操作可挽回」。

对单人开发的本地应用来说，后者更重要。

## 四、文件名冲突怎么办

回收目录按日期分桶，同一天可能移动多个同名文件。

处理方式是冲突时加时间戳与前缀，保证不覆盖已有文件。清单里同时记录原始文件名与回收后的文件名。

## 五、dry-run 的价值

dry-run 不只是「先看看」。

它把「系统认为的孤儿」与「用户认为的孤儿」放在一起对照。如果候选里出现用户认识的文件，说明判定规则需要调整，而不是直接执行。

这也是为什么扫描结果要显示字节数：让用户判断这次回收值不值得。

## 六、到期清理

回收目录保留 7 天。

到期清理只删除日期早于「今天减 7 天」的目录，不删除当天的目录。这样即使清理逻辑被误触发，也不会把刚移动的文件删掉。

清理入口与回收入口分开，避免用户在一处完成不可逆操作。

## 七、这一版没解决什么

- 没有判断「附件行存在但没有被引用」；
- 没有记录附件行快照，恢复只能恢复文件，不能恢复数据库行；
- 没有引用计数，无法回答「这个文件还被谁用着」。

这些是下一版的重点：先把引用关系建起来，再让回收清单可恢复。

## 八、一条经验

清理功能的第一版，应该尽量窄。

窄判定 + 只移动 + 保留期，让用户敢用。等数据关系更清楚之后，再扩大判定范围。

## 九、和下一版的衔接

这一版的判定只看「文件在不在附件表」。

下一版建立引用计数后，会多出一类候选：附件行存在、但引用数为 0。

那类候选不能只移文件，因为回收后恢复会丢元数据。所以下一版还会给回收目录补一份清单，记录附件行快照。

这说明清理功能的演进顺序：先保证不误删，再扩大判定范围，最后补可恢复的元数据。

## 十、什么时候不该用这个功能

- 附件目录还在被其他进程写入时；
- 用户刚导入一批文件、还没生成消息时；
- 数据根正在迁移或备份时。

这些场景下扫描结果可能瞬时变化。功能本身不阻止执行，但 UI 应该提示「稍后重试」。
