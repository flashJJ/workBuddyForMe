# 恢复后的 id 回填：旧协作运行如何映射到新任务行

备份恢复经常遇到一个隐蔽问题：数据都恢复了，但关系断了。

这一版补协作运行与角色交接时，就遇到了这种情况。任务行里有一个 `agent_run_id`，指向协作运行；协作运行和交接记录恢复后，id 可能已经不是原来的值。

如果不回填，任务列表能看到，点进去却没有协作过程。

## 一、id 为什么会变

恢复不是简单复制数据库文件，而是逐行写入。

写入时有两种策略：

- 保留原 id：适合有稳定业务含义、且目标库不会冲突的数据；
- 重新生成 id：适合需要避免冲突、或 id 由本地生成的数据。

这一版对协作运行采用保留原 id、按主键幂等写入的方式。理论上 id 不变，为什么还需要回填？

因为任务轨的恢复顺序与协作轨分离：任务行可能先写入，协作运行后写入；也可能恢复的是旧归档，任务行里根本没有协作 id。回填的作用是「在两边都就绪之后，统一校对一遍关系」。

## 二、回填需要什么

回填需要两张映射表：

```text
旧协作运行 id → 新协作运行 id
旧步骤 id     → 新协作运行 id
```

实现上从 `agent_runs` 与 `agent_handoffs` 的原始行里读取 id，再按任务负载中的旧 id 查找。

如果 id 保留不变，映射是恒等的；如果未来引入 id 重写，映射层不需要改调用方。

## 三、为什么在事务内做

回填发生在恢复事务里，顺序是：

```text
写 agent_runs
  → 写 agent_handoffs
    → 写 tasks / task_steps
      → 回填 task_runs.agent_run_id
```

放在同一个事务里有两个好处：

- 任一步失败，整体回滚，不会留下「任务有、协作没有」的半状态；
- 回填只需要执行一次，不需要额外的后台修复任务。

代价是事务时间变长。对一个本地单用户应用来说，这个代价可以接受。

## 四、幂等怎么保证

重复恢复同一份归档时，回填不能产生重复或错误覆盖。

做法是：

- 协作运行与交接按主键 `INSERT OR IGNORE`；
- 任务行本身也按主键幂等；
- 回填只在目标行存在且字段为空或指向旧 id 时更新。

这样第二次恢复不会改变第一次的结果。

## 五、旧归档怎么办

旧归档没有协作轨，任务行里的 `agent_run_id` 可能是一个已经不存在的 id。

恢复端不强行清空它，也不因为外键失败而中断。任务行按原样写入，协作 id 保持悬空，后续由查询侧忽略。

这是一个有意的取舍：备份恢复优先保证「能恢复的尽量恢复」，而不是「恢复后所有关系都必须完美」。

## 六、怎么验证

测试覆盖三类场景：

1. 新归档 roundtrip：协作运行、交接、任务行的 id 全部对上；
2. 旧归档：缺协作文件时任务正常恢复，不报错；
3. 重复恢复：第二次不产生重复行，回填结果不变。

验证的重点不是「有没有回填」，而是「回填后关系是否可查询」。

## 七、一条经验

备份里的关系字段，恢复后要单独校对一次。

不要假设「按原 id 写入」就等于「关系自动成立」。写入顺序、外键约束、旧归档缺字段，都会让关系在某个中间态断掉。

回填不是补丁，而是恢复流程的一部分。
