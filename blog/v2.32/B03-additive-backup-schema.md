# 备份 schema 的加法升级：新字段如何不破坏旧归档

备份格式一旦发布，就同时面对两类用户：用新版本导出的人，和拿旧归档恢复的人。

这两类需求会打架：新版本想多带一些数据，旧版本不认识这些数据；如果直接改结构，旧归档可能读不了。

这一版需要在 tasks 轨里补协作运行与角色交接，选择的原则是「只做加法」。

## 一、旧结构缺什么

任务轨原本只包含任务运行与步骤日志。协作运行与角色交接是后来引入的两张表，记录的是多角色 Agent 的运行过程与轮次交接。

这两张表不在备份里，导致换机器恢复后，任务列表看起来正常，但协作关系全空，任务行上的协作运行 id 也回落到 `NULL`。

问题不是数据丢失，而是「看起来恢复了，实际少一层」。

## 二、加法升级的具体做法

改动集中在三处：

1. manifest 的 tasks 对象增加两个可选计数；
2. 归档根目录增加两个可选 JSON 文件；
3. 恢复端在文件缺失时按空数组处理。

旧归档没有这些字段，解析时得到 `undefined`，恢复端按 0 处理。新归档在老版本里即使不认识这两个文件，也不会影响其他轨的读取，因为 manifest 的主结构没有变化。

## 三、为什么不做版本分支

备份 schema 有版本号，但这一版没有为「有协作轨 / 无协作轨」写两套解析逻辑。

原因是可选字段已经把差异表达清楚了：字段存在就恢复，不存在就当没有。版本号只用来拒绝「比当前应用更新」的归档，不承担字段级分支。

这是一条重要边界：版本号负责兼容性判断，可选字段负责能力差异。两者混用会让解析逻辑迅速复杂化。

## 四、恢复顺序比字段更重要

新增两张表后，恢复顺序变成硬约束：

```text
agent_runs
  → agent_handoffs
    → 回填 task_runs.agent_run_id
```

交接记录依赖协作运行，任务行又依赖协作运行 id。顺序错了，外键会失败，或者回填找不到目标。

因此恢复端把这三步放在同一个事务里，并固定执行顺序。

## 五、计数放在 manifest 的意义

manifest 里的 `agentRunCount` 与 `agentHandoffCount` 不只是展示。

它们让预检可以在不解析大文件的情况下告诉用户「这个归档里有多少协作记录」；也让恢复后的核对报告可以对比「声明多少、实际写入多少」。

如果没有这两个计数，预检要么读取整个 JSON，要么只能显示 0。

## 六、旧归档的恢复体验

旧归档缺文件时，恢复端不会报错，也不会给出「数据损坏」的误导。

它会把协作轨按 0 条处理，其他轨正常恢复。恢复完成后，任务行没有协作 id，但任务本身、步骤、消息都还在。

这是一种降级，而不是失败。对备份系统来说，能恢复多少就恢复多少，比「缺一个可选文件就整体拒绝」更符合用户预期。

## 七、可复用的结论

备份格式演进可以遵循三条规则：

- 新能力优先用可选字段表达，不轻易改必填结构；
- 版本号只做兼容性闸门，不做字段级分支；
- 计数与清单先于大文件解析，让预检和核对有轻量依据。

加法升级的代价是 manifest 会越来越长，但收益是旧归档一直能读。

## 八、旧归档怎么测

测试不能只测新归档 roundtrip，还要专门构造旧归档。

做法是拿一份新归档，删掉新增的可选文件与可选计数，再重新打包。恢复端读到的就是「旧结构」。

断言三件事：

- 预检不因缺字段报错；
- 恢复不因缺文件失败；
- 其他轨的计数与内容不受影响。

这比单独维护一份旧归档更可控，因为旧结构是从新结构显式降级出来的，差异一目了然。

## 九、一个容易忽略的点

恢复端读取可选字段时，不能用「字段存在就一定是新版本」来判断。

旧归档可能因为手工修改或第三方工具带上同名字段，但内容不完整。

正确做法是先做结构校验，再做业务判断：字段缺失按 0，字段存在但类型不对按损坏处理。
