# 存储占用统计：一次目录遍历如何把空间分清楚

设置页里最容易被忽略、但最影响长期使用的，是「空间去哪了」。

本地应用的数据根会同时包含数据库、上传文档、附件、溢出内容、能力包、日志和一堆临时目录。只显示一个总数，用户无法判断该清理什么。

这一版补了分项占用统计。

## 一、分桶规则

统计按数据根的顶层目录分桶：

| 顶层目录 | 归入 |
|---|---|
| `db` | 数据库 |
| `files` | 文档 |
| `attachments` | 附件 |
| `spills` | 溢出内容 |
| `capabilities` | 能力包 |
| `logs` | 日志 |
| 其他 | 其他 |

规则放在一个映射表里，新增目录时只需要改表，不需要改遍历逻辑。

## 二、一次遍历而不是多次

实现上只遍历一次数据根，边走边累加当前顶层的桶。

如果对每个桶单独 `du`，目录越大越慢，而且多次遍历之间数据可能变化，分项之和会对不上总数。

一次遍历保证同一时刻的快照一致。

## 三、边界：深度与文件数

递归遍历设置了两条边界：

- 最大深度 8 层；
- 最多扫描 10 万个文件。

达到上限后标记 `truncated`，前端提示「文件过多，统计已截断」。

这不是完整的磁盘分析工具，而是设置页里的一个概览。边界让它在异常目录结构下也不会卡死。

## 四、短时缓存

统计结果缓存 30 秒。

原因是设置页可能在多个组件里同时请求，或者用户来回切换标签。每次都全盘遍历会让页面明显变慢。

缓存的代价是数据可能滞后 30 秒。对一个占用统计来说，这个误差可以接受。

## 五、失败降级

扫描时文件被删除、权限不足、目录不存在，都可能抛错。

处理方式是逐项 `try/catch`：单个文件失败跳过，顶层目录不存在返回 0，整体不因为一个坏文件而失败。

前端拿不到结果时显示「无法统计」，而不是空白。

## 六、分项之和与总数

总数不是单独读磁盘，而是分项之和。

这样做保证「分项加起来等于总数」，不会出现用户看到三个数对不上的情况。

代价是总数不包含扫描失败的项，但这一点在前端用截断提示已经说明。

## 七、它能回答什么问题

- 附件是不是主要占用？
- 日志是不是该清理了？
- 能力包是不是装得太多？
- 数据库本身有多大？

这些问题不需要精确到字节，只需要量级正确。分桶统计正好满足。

## 八、边界

这一版没有做：按文件类型统计、按时间分布、自动清理建议、磁盘剩余空间。

先把「大类去哪了」说清楚，再谈更细的分析。
