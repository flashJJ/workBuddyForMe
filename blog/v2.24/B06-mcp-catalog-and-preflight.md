# MCP 目录不是一张列表：运行环境预检与批量安装的契约设计

用户想给助手加一个本地文件工具。他在设置页看到一个「安装」按钮，点下去，进度转了几秒，状态变成失败。

失败原因是一行退出码。他不知道是没装 Node、没装 npx、路径写错，还是包本身已经不存在。

这不是某一个服务器的问题，而是安装流程缺了一层：**在写配置之前，先确认这台机器能不能跑。**

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，MCP 服务器在设置页管理。这一篇讲能力目录怎样从「预置命令列表」变成一份可校验的安装契约。

## 旧预置为什么不可靠

旧的预置服务器只是几条写死的命令：命令、参数、可能还有一个固定路径。它有三个问题。

第一，命令可能已经失效。有些包已经归档或迁移，`npx` 拉取时直接 404；有些服务其实是 Python 实现，应该用 `uvx`，却写成了 `npx`。

第二，参数写死了本机路径。换一台机器，路径不存在，服务器启动后立刻退出。用户看到的是「安装成功但连接失败」。

第三，没有声明运行依赖。用户不知道自己要装 Node、uv、还是 Chrome；安装器也不检查，直接把配置写进库。

这一版把预置改成目录，并且明确了目录项的字段。

## 目录项的六个必要字段

一个能安装的目录项，至少要说清六件事：

| 字段 | 作用 |
|---|---|
| 传输方式 | `stdio` 还是 `http` |
| 启动命令或地址 | stdio 用命令与参数，http 用地址 |
| 参数占位符 | 目录、文本或密钥，安装时由用户填写 |
| 运行依赖 | Node / uv / Chrome，以及最低 Node 主版本 |
| 许可证 | 让用户知道使用条件 |
| 说明 | 首次运行、额度、局限性等 |

这一版收录了 14 个服务器，按推荐、可选、需凭证三档展示。档位只影响排序与默认勾选，真正决定能不能装的是运行依赖。

参数不再写死。目录用 `{{dir}}` 占位，密钥用 `{{key}}` 占位；安装器在创建配置前把用户填的值替换进去。这样同一个目录项可以在任何机器上使用，不需要改代码。

## 预检：先探测，再写库

安装前第一步是运行环境预检。三个命令并行执行：

- `node --version`
- `npx --version`
- `uvx --version`

每个命令 4 秒超时，只读版本号，不执行用户输入。Chrome 不走命令，而是按平台查常见安装位置：Windows 查程序目录与本地应用目录，macOS 查应用包，Linux 查几个常见可执行路径。

探测结果是一份结构化状态：

```ts
{
  platform: 'win32',
  node: { available: true, version: '24.x', major: 24 },
  npx:  { available: true, version: '11.x', major: 11 },
  uvx:  { available: false, version: null, major: null },
  chrome: { available: true, path: '...' },
  checkedAt: '...'
}
```

预检失败不抛错。命令不存在、超时、输出为空，都归一成 `available: false`。安装器据此给出可读原因，比如「未检测到 uv / uvx」「需要 Node 24+（当前 20.x）」。

这里有一个重要取舍：**预检只探测固定命令，不探测目录项里的自定义命令。** 目录项来自本地常量，命令是受控的；如果允许任意命令进入预检，等于给设置页开了一个执行入口。

## 批量安装：失败不阻断

目录支持多选。安装器逐项执行，状态机大致是：

```text
idle → installing → ok
                 → failed（缺依赖 / 创建失败 / 连接失败）
                 → skipped（同名服务器已存在）
                 → needs_auth（需要 OAuth 授权）
```

三个细节值得展开。

第一，同名服务器直接跳过，不覆盖已有配置。用户可能已经手动调过参数，覆盖会让他的修改消失。

第二，创建后不立刻判定成功，而是每 2 秒轮询一次服务器状态，最长 90 秒。原因是 `npx` 首次下载依赖经常超过默认连接超时；如果只看创建接口的返回，会把「正在下载」误判成失败。

第三，单项失败不阻断后续条目。批量安装最常见的场景是「勾了五个，其中两个缺依赖」，这时应该把能装的装完，再把两个缺依赖的标出来，而不是整批回滚。

轮询超时也有明确文案：配置已创建，但连接超时，可以到下方服务器列表点「测试连接」重试。不把「已创建」说成「安装失败」，避免用户重复创建同名服务器。

## 为什么鉴权失败要单独标

远程服务器连接失败时，错误文本里可能出现 401、鉴权或 OAuth。安装器会把这类失败标成 `needs_auth`，而不是普通失败。

原因不是文案好看，而是下一步动作不同：

- 普通失败：检查命令、路径、依赖；
- 鉴权失败：去点「授权」，在浏览器完成 OAuth，再回来测试连接。

如果两者都显示「安装失败」，用户会反复重装，而真正缺的是一次授权。

## 启用给助手：默认不勾

安装完成不等于助手能用。MCP 工具需要进入助手的工具白名单，模型才会在对话里看到它们。

这一版装完之后提供一个「启用给助手」入口：列出助手，勾选后把本次安装发现的工具并入 `enabledTools`，默认全不勾。

默认不勾是有意的。安装一个服务器可能带来十几个工具，如果自动启用，等于替用户做了一次权限扩散。用户应该明确选择「哪个助手、在什么场景下」使用这些工具。

实现上只做并集，不覆盖助手原有工具；工具名使用限定名，避免不同服务器的同名工具互相冲突。

## 验证与边界

实机验证覆盖了两类服务器：文件系统服务器发现 14 个工具，记忆服务器发现 9 个。安装流程、预检失败提示、同名跳过、轮询超时与批量安装的组件测试通过。

边界也要写清楚：目录只收录维护方明确支持、Windows 可用、安装方式清晰的服务器；预检只能判断命令是否存在与版本号，不能判断网络是否能下载包；90 秒是经验值，极慢网络下仍可能超时，此时保留「已创建」状态供手动重试。

目录项里的说明不是装饰。首次运行可能要下载浏览器、免费额度可能有限、某些服务只支持特定浏览器——这些信息如果等到失败后才让用户知道，安装体验就会变成一次试错。

## 一条可复用的判断

**安装器的本质是契约，不是列表。**

列表只告诉用户「有什么」，契约要告诉用户「需要什么、缺什么、失败后怎么办」。当目录项把依赖、占位符与失败语义都声明清楚，安装才从「点一下试试」变成一件可以预期的事。
