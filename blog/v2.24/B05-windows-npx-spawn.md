# 一行引号让 MCP 起不来：Windows 下 npx 启动排查实录

一个 MCP 服务器在设置页显示安装成功，状态却一直是失败。进程退出码 1，stderr 里没有有用的堆栈。

同样的命令复制到终端，回车，正常启动。换一台机器，还是 Windows，还是失败；换到非 Windows 环境，正常。

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，核心逻辑跑在 Node 侧，通过 stdio 拉起 MCP 子进程。这一篇完整记录这次排查：现象、取证、反证、根因、修复，以及为什么原来的测试没有拦住它。

## 现象：只有 Windows 失败

失败路径很固定：

1. 在能力目录里勾选一个基于 `npx` 的服务器；
2. 创建配置成功，服务器开始连接；
3. 子进程很快退出，`code=1`；
4. 状态变成 `error`，详情只有「进程退出（code=1）」。

没有超时，没有握手失败，也不是工具列表为空。进程根本没活到握手阶段。

第一反应是网络问题：`npx` 首次下载包失败。但把同样的包在终端里跑，几秒就下载完；再回到应用里重试，依旧退出。

第二个怀疑是环境变量。stdio 子进程只继承一份白名单环境，`PATH`、`APPDATA`、`LOCALAPPDATA` 这些都在。为了排除，临时把完整环境注入，问题依旧。

第三个怀疑是参数转义。服务器参数里有一个目录，路径包含空格。但换成零参数的服务器，还是失败。问题不在参数，而在命令本身。

## 取证：把真实命令行打出来

排查这类问题，最有用的动作不是继续猜，而是把真正执行的命令行完整记录下来。

启动逻辑在 Windows 上并不是直接 `spawn('npx', args)`。Node 对 `.cmd` / `.bat` 有安全限制，直接 spawn 会报 `EINVAL`，所以要走一层 `cmd /d /s /c` 包装。包装之后，真正执行的是这样一串：

```text
cmd.exe /d /s /c ""npx" -y <package>"
```

注意最外层的引号，以及 `npx` 两侧的引号。前者是 `cmd /s /c` 的规则要求，后者是构造参数时加上的。

把这串命令原样贴进终端，复现了退出码 1。把 `npx` 两侧的引号去掉：

```text
cmd.exe /d /s /c "npx -y <package>"
```

同一个包，正常启动。

到这里可以确认：**问题出在裸命令名被加了引号，而不是网络、环境或包本身。**

## 反证：为什么终端里直接敲 npx 没事

终端里执行 `npx -y <package>` 时，命令没有引号，`cmd` 按正常规则解析到 `npx.cmd` 包装脚本。

加上引号之后，`cmd` 对第一个 token 的解析路径变了：它把带引号的名字当成当前目录下的文件来对待，而不是按普通命令去搜索。`npx.cmd` 包装脚本里的 `%~dp0` 是「脚本所在目录」，解析路径一变，它落到了项目目录，而不是 npm 自己的安装目录。

于是 `npx` 找不到 npm 自身的模块，进程直接退出。退出码 1，没有堆栈，因为失败发生在 Node 启动之前。

这个解释能同时对上三个现象：

- 只有 Windows 失败，因为只有 Windows 需要 `cmd` 包装 `.cmd`；
- 终端直接执行正常，因为终端里的命令没有引号；
- 零参数服务器也失败，因为问题在命令解析，不在参数。

## 根因：转义规则用错了对象

原来的构造逻辑很简单：只要是 Windows，就把命令和每个参数都做一次 Windows 引号转义，然后拼成命令行。

```ts
// 修复前（伪代码）
const commandPart = escapeWindowsArgument(command); // 永远加引号
const cmdline = [commandPart, ...args.map(escapeWindowsArgument)].join(' ');
```

这段逻辑对「路径」是对的：路径可能包含空格，必须加引号。但它被用在了「命令名」上，而命令名有两种形态：

- 可能是完整路径，比如带空格的安装目录，这时必须加引号；
- 可能是一个裸命令名，比如 `npx`、`uvx`，这时加引号反而改变了 `cmd` 的解析。

真正需要的规则不是「Windows 就加引号」，而是「**只有包含空格或引号的命令才加引号**」。

## 修复：让引号回到该在的位置

修复后的逻辑只改了一个判断：

```ts
function buildSpawnCommand(command: string, args: string[]) {
  if (process.platform !== 'win32') {
    return { file: command, args, windowsVerbatimArguments: false };
  }
  if (/\.(exe|com)$/i.test(command)) {
    return { file: command, args, windowsVerbatimArguments: false };
  }
  const commandPart = /[\s"]/.test(command)
    ? escapeWindowsArgument(command)
    : command;
  const cmdline = [commandPart, ...args.map(escapeWindowsArgument)].join(' ');
  return {
    file: process.env.comspec ?? 'cmd.exe',
    args: ['/d', '/s', '/c', `"${cmdline}"`],
    windowsVerbatimArguments: true,
  };
}
```

三个分支各自明确：

| 平台 / 命令形态 | 处理 |
|---|---|
| 非 Windows | 直接 spawn，不包装 |
| `.exe` / `.com` | 直接 spawn，不经过 cmd |
| 其余（`.cmd` / `.bat` / 裸命令） | 经 `cmd /d /s /c` 包装 |

参数仍然逐个转义，因为参数里出现空格、引号、反斜杠的概率远高于命令名。`windowsVerbatimArguments` 保持开启，由我们自己负责最终命令行的引号规则，避免 Node 再转义一次。

这里有一个容易忽略的点：`cmd /s /c` 要求整条命令再包一层引号。所以最终命令行会出现「外层引号 + 内层按需引号」的结构。外层引号是协议要求，内层引号只在需要时出现，两者不能混为一谈。

## 为什么原来的测试没拦住

原来的测试覆盖了「含空格路径要加引号」「参数里的引号要成对转义」，但**没有一条断言裸命令名不能加引号**。

更糟的是，测试对命令部分的期望是「Windows 下总是带引号」。这等于把错误行为写成了契约：实现改成正确行为，测试反而会红。

修复时补了四类断言：

1. 裸 `npx` 在 Windows 下不加引号；
2. 含空格的命令路径加引号；
3. 参数里的引号与结尾反斜杠按 Windows 规则成对转义；
4. 非 Windows 平台原样透传，不做任何包装。

第一条是回归的核心。写完新断言后，回到旧实现上跑一遍，它必须失败；否则写下的只是文档，不是测试。

## 验证：工具数量对上

修复后重新安装两个服务器：

- 文件系统服务器：连接成功，发现 14 个工具；
- 记忆服务器：连接成功，发现 9 个工具。

这两个数字比「状态变成 connected」更有说服力，因为它们是握手之后真正拉到的工具列表。进程能启动、能完成 initialize、能响应 `tools/list`，才说明整条 stdio 链路是通的。

## 方法论：平台差异要落到「最小可复现命令」

这次排查沉淀出四条，后来在远程 MCP 与 OAuth 上又用了一遍：

**第一，先记录真实命令行，再讨论原因。** 应用里的 `spawn` 经过包装、转义、环境注入，和终端里手敲的命令往往不是一回事。把最终 `file + args` 原样打出来，很多问题当场就能复现。

**第二，平台专属逻辑要有明确分支表。** 非 Windows、`.exe/.com`、`.cmd/.bat` 三种情况的行为不同，就不要用一条「Windows 就怎样」的规则覆盖。

**第三，转义要针对对象，而不是针对平台。** 路径需要引号，裸命令名不需要；参数需要转义，命令名可能不需要。把「需不需要」的判断写进函数，而不是写进平台分支。

**第四，测试要能红。** 一条回归断言如果对旧实现也成立，它就没有防住任何东西。写完先让它在旧代码上失败，再让它在新代码上通过。

## 边界与遗留

这个修复只覆盖 `npx` / `uvx` 这类 `.cmd` 包装命令与普通可执行文件。如果某个服务使用自定义 `.bat` 启动器，仍然会走 `cmd` 包装，参数规则相同，但没有逐个实机验证。另外，Windows 的 `cmd` 解析规则本身有很多历史包袱，这次只钉住了「裸命令名不加引号」这一条；更稳妥的长期方案是尽量使用 `.exe` 形式的启动器，或者在文档里明确要求提供绝对路径。对当前目录里的服务器来说，前者不现实，后者对用户太苛刻，所以先把包装层做对。

## 一条可复用的判断

**跨平台 bug 的根因，经常不在业务代码，而在「你以为等价的两条命令」。** 终端里能跑，不代表应用里能跑；应用里能跑，不代表换一种引号还能跑。把最终命令记录下来，把平台分支列成表，把「不该加引号」也写成测试——这三件事做完，问题就不再靠运气。
