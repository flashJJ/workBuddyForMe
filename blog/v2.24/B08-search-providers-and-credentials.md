# 搜索接入带 Key 的服务：密钥不是设置项，是凭证

用户把搜索地址填成某个公共实例，问了一句时效性问题，界面报 `Unexpected token '<'`。

这个错误的字面意思是「JSON 解析失败」，真实原因却是实例返回了一张反爬网页。代码对响应直接调用 `response.json()`，于是把一张 HTML 页面当成了 JSON。

公共实例不可靠，自建又有门槛。更稳的路是接带 API Key 的搜索服务，但这就要求应用先回答一个更基础的问题：**密钥存在哪里，怎样保证它不会被设置接口顺手带出去。**

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，搜索服务在 core 包，设置页在 web 端。这一篇讲新增两家带 Key 的搜索服务，以及凭据的存取边界。

## 先把「搜索后端」抽象干净

搜索适配器的接口很小：输入查询、条数与语言，输出统一的结果列表。两家新服务各自实现这个接口，差异被挡在适配器内部。

第一家是 GET 风格，密钥放在请求头里：

```text
GET /res/v1/web/search?q=...&count=5
X-Subscription-Token: <key>
```

第二家是 POST 风格，密钥同时出现在 Authorization 头与请求体里：

```ts
body: JSON.stringify({
  api_key: apiKey,
  query: input.query,
  max_results: 5,
  search_depth: 'basic',
  include_answer: false,
})
```

两者的返回结构也不同，但最终都映射成同一份结果字段：标题、URL、摘要、来源域名，有发布时间就带上。条数上限统一压到 8 条，避免一次搜索把上下文撑爆。

## 错误要归一，不要透传

外部服务的错误形态很多：401/403 是密钥问题，429 是限流，某些服务还有自己的额度耗尽状态码，其余是网络或格式问题。

如果把这些原文直接抛给用户，设置页会出现一屏英文。适配器因此把错误收敛成几个稳定的原因：

| 原因 | 触发 |
|---|---|
| `auth_failed` | 401 / 403，密钥无效或无权限 |
| `rate_limited` | 429，或额度耗尽 |
| `invalid_response` | 返回结构缺少结果数组 |
| `unreachable` | 超时、连接失败、其他 HTTP 错误 |

上层再把这些原因翻译成用户能执行的动作：换 Key、稍后重试、检查服务地址。错误归一不是为了让日志好看，而是为了让设置页能给出下一步。

## 密钥不放进设置对象

最直接的做法是把 API Key 加进搜索设置，和 provider、条数、超时放在一起。这一版没有这么做。

原因有三个。

第一，设置对象会被设置接口整包返回。密钥一旦进入这个对象，就很容易出现在响应、缓存、导出或日志里。哪怕前端做了脱敏，服务端的序列化路径也多了一条。

第二，密钥的生命周期和设置不同。设置可以随时改、随时读；密钥需要「写入、脱敏展示、清除」三个明确动作，不应该跟着一次保存被覆盖。

第三，备份与迁移的语义不同。设置可以随备份走，密钥是否随备份走需要单独判断。混在一起会让边界变模糊。

所以密钥单独存进设置键值的一个独立键里，值是加密后的密文。读取时只暴露两种形态：

```ts
{
  brave:  { hasKey: true, masked: 'BSA...x9' },
  tavily: { hasKey: false, masked: null }
}
```

明文只在服务端构造 provider 的那一刻读取，不进入前端状态，也不进入通用设置对象。

## 密文损坏也要能降级

加密存储有一个必须处理的边界：密文可能损坏，或者换了机器、换了主密钥之后解不开。

这时的正确行为不是抛错，而是当成「未配置」：`hasKey: false`，用户可以重新填。设置页不应该因为一条坏记录而打不开。

清除则直接删除对应字段，不写空字符串。空字符串会在「是否配置」的判断里制造歧义。

## 设置页的三个动作

搜索设置页围绕密钥提供三个动作：

1. **保存**：如果输入框里有新 Key，先加密保存，再保存搜索设置；
2. **测试连接**：同样先保存新 Key，再发一次最小查询（`ping`，只取 1 条）；
3. **清除**：删除该服务的密钥，界面回到未配置。

还有一个容易被忽略的细节：切换搜索服务时清空输入框里未保存的 Key。否则用户先填了 A 服务的 Key，又切到 B 服务点保存，Key 就会被存到 B 名下。这类错误不会报错，只会在下一次搜索时表现为「鉴权失败」，很难排查。

测试连接复用同一个适配器，不单独写一套探活逻辑。这样测试通过就意味着真实查询路径可用，而不是「端点能连通」。

## 公共实例的提示也要改

既然带 Key 的服务更稳，设置页就不应该继续把公共实例当成推荐路径。

这一版的文案调整为：优先配置带 Key 的服务，或者自建实例；公共实例只作为临时试用，不保证可用性。这不是技术限制，而是产品判断——把不稳定的选项放在推荐位，用户迟早会用一次失败来发现它不稳定。

## 验证与边界

两家适配器的映射、错误归一、超时、凭据加密与解密降级都有单测覆盖；搜索服务的设置读取与 provider 构造也有测试。core 包 MCP 与搜索相关单测共 10 个文件、42 例通过。

边界：没有做多 provider 自动降级，一家失败不会自动切另一家；没有做额度统计；密钥轮换需要用户手动清除后重填；公共实例的反爬问题只做了错误可读化，没有做 HTML 解析兜底。

## 一条可复用的判断

**密钥不是设置项，是凭证。**

凭证需要独立存储、脱敏展示、明确清除、损坏降级，以及「明文只在最后一刻出现」的纪律。把这些当成默认规则，接入下一家服务时就不需要重新讨论一遍安全边界。
