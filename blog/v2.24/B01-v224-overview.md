# 从「未能形成回答」到可读的过程：一次对话体验与能力生态的收口

用户问了一个需要联网搜索的问题。界面转了几圈，最后只回了一句「未能形成回答」。

抓包之后发现更尴尬的事实：搜索其实成功了，结果也已经进入上下文，只是模型把五轮工具调用全部用完，轮数耗尽时正文仍然是空的。应用没有把「已经拿到的结果」变成回答，用户看到的是「什么都没查到」。

同一时期还有另一个方向的反馈：在设置页安装一个 MCP 服务器，进度转完，状态变成失败，进程退出码 1。命令行里手动执行同样的命令却完全正常。

两个问题看起来无关，指向的却是同一种体验缺口：**用户不知道应用做了什么，也不知道还能不能继续。**

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，web 端用 Next.js，桌面壳是 Electron，核心编排、MCP 与搜索都在 core 包里。这一轮没有加新的业务域，只做两件事：让对话过程可读，让能力装得上、用得起。

## 先拆问题，不先加功能

对话侧的问题可以列成四条：

| 现象 | 用户实际感受到的 |
|---|---|
| 工具轮用尽后只回兜底文案 | 搜了等于没搜 |
| 工具行一屏几十行 | 不知道哪一步成功了 |
| 失败原因是一段自由文本 | 不知道是超时、限流还是没权限 |
| 用量不可见 | 不知道这一轮花了多少 |

能力侧的问题同样具体：预置命令在 Windows 上起不来；远程 MCP 只会解析 JSON 回包，遇到 SSE 就失败；需要 OAuth 的远程服务完全接不进来；想用带 Key 的搜索服务，却没有安全的存放位置。

这两组问题都不适合用「再加一个按钮」解决。它们需要把状态、错误和安装流程重新设计一遍。

## 为什么先做「可见」，而不是先做「更强」

这两组问题有一个共同点：能力其实已经存在，只是没有被表达出来。

搜索能返回结果，工具能执行，MCP 服务也能启动——失败发生在最后一公里：结果没有变成回答，状态没有变成可读的界面，进程没有活到握手。

在这种情况下继续加能力，收益会被浪费。用户不会因为多了一个工具而更信任应用，只会因为新工具也以同样的方式失败而更失望。

所以这一轮的顺序是：先把已有能力的状态讲清楚，再补能力的入口。前者决定用户是否愿意继续用，后者决定用户能不能用上。

可见不是美化。它要求把状态、错误与下一步动作都做成结构，而不是在界面上加一句更温柔的提示。

这也是为什么验收里没有「新增多少功能」这一项，而是「失败是否可读、安装是否可预期」。

## 对话侧：把过程做成可读的结构

第一件事是工具轮收尾。轮数用尽且正文为空时，不再直接落兜底文案，而是追加一条「只基于已获得结果作答」的指令，以空工具集再调用一次模型。只有收尾轮仍然拿不到文本，才允许出现兜底。

第二件事是时间线。同一回合的调用聚合为一张可折叠卡片，头部只留一句「工具调用 · N 次 · 成功 X · 失败 Y」；流式期间自动展开，完成后自动收起。成功、失败、被拒绝、已熔断从同一种红色里拆出来，失败原因归一成超时、限流、鉴权、页面过大、网络、被拒、熔断。

第三件事是相位。工具正在跑的时候，界面不再统一显示「正在思考」，而是按当前工具给出「正在搜索网页」「阅读网页」「检索知识库」「执行工具」「整理结果」。这些相位由前端从已有工具轨迹推导，不需要后端新增事件。

第四件事是可见用量。助手消息完成后，底部显示本轮 token 总数，悬停可以看到输入、输出与合计。数字不大，但它让「这一轮为什么慢、为什么贵」有了落点。

桌面侧还补了一条一致性链路：设置保存后通过 `BroadcastChannel` 广播，其余窗口收到就失效查询。桌宠的勿扰开关、互动短句因此即时生效，不需要重开桌宠。桌宠气泡也只渲染包含文字或数字的整句碎片，空闲时清空并加超时兜底，不再留下一个几乎空白的框。

## 能力侧：把「装一个服务」做成契约

MCP 能力目录不是一张静态列表，而是一份安装契约。每个目录项要声明：传输方式、命令或地址、参数占位符、运行依赖、最低 Node 主版本、许可证与说明。推荐、可选、需凭证三档只是展示分组，真正决定能不能装的是运行依赖。

安装前的第一步是预检，而不是直接写库。`node`、`npx`、`uvx` 三个命令并行探测版本，4 秒超时；Chrome 按平台查常见安装位置。探测失败一律降级为「不可用」，不抛错，也不阻断设置页。

第二步才是创建服务器。同名服务器直接跳过；创建后每 2 秒轮询一次连接状态，最长 90 秒，因为 `npx` 首次下载依赖经常超过默认连接超时。鉴权类失败单独标成 `needs_auth`，引导用户去授权；其余失败不阻断后续条目。

装完之后还有一个容易被忽略的动作：启用给助手。默认不勾选，用户明确选择后才把新工具并入助手白名单，避免一次安装把所有权限都扩散出去。

远程 MCP 的补齐分三层：SSE 回包解析、会话头与协议版本、401 刷新重试。这三层缺任何一层，都会表现为「服务明明存在，但连不上」。

OAuth 则是完整的一条链：从受保护资源元数据发现授权服务器，动态注册客户端，PKCE S256，一次性 state，回调页交换令牌，加密存储，到期前刷新，401 时刷新并重试一次。令牌与待处理事务都复用现有加密能力写入设置键值，不新增表。

搜索侧新增两家带 Key 的服务。密钥单独加密保存，界面只显示脱敏串；保存、测试、清除三个动作都在设置页完成。公共 SearXNG 实例的提示也改了：不再鼓励依赖公共实例，优先配置带 Key 的服务或自建。

## 为什么放在同一个版本

对话过程与能力生态看似两块，实际是一条链：对话要消费能力，能力装不上，过程再漂亮也只是空转；能力装上了但过程不可读，用户仍然会以为它坏了。

所以验收也不分开看。一个搜索类问题必须能在工具轮用尽后产出基于结果的回答；一次安装必须能在失败时给出可读原因，而不是只留一个退出码。

## 刻意没做什么

方案里排在后一阶段的项目没有进这一版：行内引用角标、来源卡片定位、子 Agent handoff 泳道、回合运行摘要、抓取失败降级。它们都需要额外的交互设计与验收口径，不应该为了凑一个「完整版本」而半成品上线。

也没有新增 UI 依赖，仍然沿用 Radix 与 Tailwind；没有数据库迁移，结构版本保持 45；没有重写多 Agent 编排内核，只修过程与安装链路。

## 验收与遗留

`pnpm check` 的类型检查、Lint、单文件行数、目录预算、循环依赖与 ASCII 框图检查全部通过。

core 包 MCP 与搜索相关单测 10 个文件、42 例通过，覆盖 OAuth 授权流程、SSE 回包解析、搜索凭据加密与解密降级；web 端 MCP 设置面板与搜索设置 3 个文件、13 例通过。

实机验证拿到了具体数字：文件系统服务器发现 14 个工具，记忆服务器 9 个，远程文档检索服务器 2 个。OAuth 发起授权返回的地址里能看到 PKCE S256、资源标识与默认 scope。

没有做的是视觉回归巡检。这一轮的界面改动集中在消息区与设置页，主要靠组件测试与人工路径验证，截图基线仍然缺位。
