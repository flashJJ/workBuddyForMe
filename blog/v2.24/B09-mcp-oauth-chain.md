# 从 401 到已连接：一条 MCP OAuth 发现链的完整走法

一个远程 MCP 服务，地址填对，网络也通，连接却始终停在「要求鉴权」。

它没有静态 API Key，也不接受自定义 Headers。唯一的入口是浏览器授权：用户点开一个页面，同意权限，再回到应用。

要把这条链走通，客户端需要依次完成发现、注册、授权、换令牌、存储与刷新。任何一步偷懒，都会表现为同一句「连接失败」。

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，MCP 支持远程 HTTP 传输。这一篇按链路顺序讲 OAuth 2.1 的实现，以及每一步为什么不能省。

## 第一步：从 401 里读出线索

OAuth 的起点不是猜端点，而是向 MCP 地址发一次 `initialize`，然后读 401 响应里的 `WWW-Authenticate`。

这个头可能包含两个关键参数：

- `resource_metadata`：受保护资源元数据的地址；
- `scope`：本次授权需要的范围。

如果服务器直接返回成功，说明它不需要 OAuth，应该提示用户「可以直接使用」，而不是继续走授权。

拿到 `resource_metadata` 之后，还要准备候选地址。规范允许服务器把元数据放在标准路径下，也允许按端点路径派生。实现上先试响应头给出的地址，再试路径感知的 well-known 地址，最后退回根路径。

## 第二步：发现授权服务器

受保护资源元数据里最重要的是 `authorization_servers`。取第一个，继续查它的授权服务器元数据。

候选顺序是：

1. 路径感知的 `oauth-authorization-server`；
2. 根路径的 `oauth-authorization-server`；
3. 路径感知的 `openid-configuration`；
4. 根路径的 `openid-configuration`。

找到同时包含 `authorization_endpoint` 与 `token_endpoint` 的那份，才算发现成功。

这里有三道安全门：

- **协议**：OAuth 端点必须使用 https，本机回环除外；
- **SSRF**：每一跳都做私网地址校验，重定向手动处理，最多三跳；
- **PKCE**：如果服务器声明支持的方法里没有 `S256`，直接拒绝授权。

第三道门经常被忽略。没有 PKCE 的授权码流程，在桌面应用里等于把授权码暴露给本机其他进程。宁可拒绝，也不降级到 `plain`。

## 第三步：动态注册客户端

桌面应用没有预先备案的 client id，只能走动态客户端注册。

请求体只放必要字段：客户端名称、回调地址、授权码与刷新令牌两种 grant、响应类型 code、认证方式 none。注册成功后拿到 `client_id`，有些服务器还会给 `client_secret`，那就按它声明的方式使用 Basic 或 POST 认证。

回调地址由服务端根据当前请求生成，指向本机的 OAuth 回调路由。它必须和注册时提交的完全一致，否则令牌端点会拒绝。

## 第四步：PKCE 与一次性 state

授权 URL 携带五个关键参数：

```text
response_type=code
client_id=<注册得到的 id>
redirect_uri=<本机回调地址>
state=<一次性随机串>
code_challenge=<S256 挑战>
code_challenge_method=S256
```

再加两个可选参数：`scope` 与 `resource`。

`scope` 来自 401 响应；服务器没给就不发，让它用默认范围。`resource` 是 RFC 8707 的资源标识，告诉授权服务器「这个令牌是给哪个 MCP 端点用的」，避免令牌被挪用到别的服务。

`code_verifier` 是 32 字节随机串，`code_challenge` 是它的 SHA-256 摘要再做 base64url。`state` 是另一条随机串，24 字节。

待处理的授权事务要落盘，但不能明文落盘。实现把 state、verifier、client 信息、端点与 scope 一起加密存进设置键值，10 分钟过期。回调时先取出并删除，保证 state 只能用一次。

## 第五步：回调页不是装饰

授权服务器会把浏览器重定向回本机回调地址。这个路由不能走应用常规的令牌守卫，因为请求来自浏览器跳转，不带应用令牌。

它的安全边界由 state 保证：state 必须存在、未过期、未被使用。回调里如果带了 `iss`，还要和发起授权时记录的签发方比对，防止跨签发方的混淆攻击。

回调页做四件事：

1. 校验 code 与 state；
2. 用 code 加 verifier 换令牌；
3. 保存令牌；
4. 立刻测试一次服务器连接，把结果渲染成一张 HTML 页。

页面会区分「授权完成」「授权已保存但连接失败」「授权失败」。成功时显示发现的工具数量，用户回到应用就知道下一步该做什么。

## 第六步：令牌存哪里、什么时候刷新

令牌按服务器 id 单独存一条设置记录，整体加密。记录里不只有 access token，还包括刷新令牌、过期时间、令牌端点、client 信息、scope 与账户标签。

为什么不存成一张全局表？因为并发刷新时，多个服务器读改写同一份 map 会互相覆盖。按服务器拆键，写入范围最小。

刷新有两个触发点：

- **到期前**：访问令牌距离过期不足 60 秒时，先刷新再发请求；
- **401 时**：请求层收到 401，刷新一次并重试同一请求。

刷新做了单飞控制：同一服务器同时只有一个刷新任务，其他调用等待同一个 Promise。否则多个并发工具调用会各自发起刷新，把刷新令牌用废。

如果刷新返回 `invalid_grant`，说明授权已被撤销，直接清除本地令牌，让状态回到未授权。这比保留一条永远刷不新的记录更诚实。

## 设置页要显示什么

授权状态不能只有一个布尔值。设置页展示三种状态：

| 状态 | 含义 | 动作 |
|---|---|---|
| 未授权 | 没有令牌 | 授权 |
| 已授权 | 有令牌且未过期，或可刷新 | 重新授权 / 清除 |
| 已过期 | 令牌过期且没有刷新令牌 | 重新授权 |

状态每 10 秒轮询一次，回调在独立浏览器完成，应用不需要阻塞等待。清除授权后会强制重连一次，让服务器状态同步回到未授权。

## 验证与边界

实机验证覆盖了两条路径：一个笔记协作类服务返回的授权地址包含 `S256`、资源标识与默认 scope；一个项目管理类服务的元数据发现成功。

边界：只支持授权码 + PKCE，不支持设备码；动态注册是硬要求，服务器不提供注册端点时无法自动授权；回调依赖本机服务可被浏览器访问；令牌随设置键值存储，不随备份迁移。

## 一条可复用的判断

**OAuth 不是「弹个浏览器」，而是一条每一步都要取证的协议链。**

发现失败、注册失败、PKCE 不支持、state 过期、令牌交换失败，最终都会显示成「连接失败」，但修复动作完全不同。把每一步的错误单独暴露出来，用户和开发者才知道该改哪里。
