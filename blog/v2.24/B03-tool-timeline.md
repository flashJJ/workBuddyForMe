# 一屏几十行工具调用：把过程收成一张卡片

搜索一个问题，界面里滚出几十行工具记录：搜索、打开网页、再搜索、再打开。每一行都写着结果摘要，看起来都像成功了，但最终回答不知所云。

用户真正想知道的只有三件事：这一步成了没有？如果没成，为什么？我还能做什么？

原来的工具行回答不了这三个问题。它把每次调用平铺出来，状态靠 `resultSummary` 里的文字猜；失败只有一种红色；错误原因原样展示，可能是超时，也可能是一整段服务端 HTML。

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，聊天界面在 web 端。这一篇讲这次怎么把工具过程从「日志」改成「可读的界面」。

## 先聚合，再谈细节

第一个决定是同回合聚合。一次任务里调用了几次工具，不再渲染成 N 行，而是收成一张可折叠卡片：

> 工具调用 · 6 次 · 成功 4 · 失败 2

流式期间卡片自动展开，让用户看到正在发生什么；回合完成后自动收起，把空间还给回答。想追细节再展开，每次调用仍然能看到工具名、参数摘要、耗时与结果。

这个决定背后是一个取舍：**聚合不是隐藏，而是排序。** 用户先要一个结论，再决定要不要看过程。把结论做成卡片头部，把过程放进展开区，比默认铺开所有细节更接近真实阅读习惯。

## 四态：把「失败」拆开

原来的状态只有运行中、成功、失败。问题是「失败」里混着三种完全不同的东西：

- 工具真的执行失败，比如超时、网络错误；
- 用户或策略拒绝了这次调用；
- 连续失败触发了熔断。

三者的处理方式不同。执行失败可以重试；被拒绝要改权限或换做法；熔断要先等冷却或检查服务。全都标成红色，用户只能反复点重试。

所以状态拆成五种展示态：运行中、成功、失败、被拒绝、已熔断。后三种都是终态，但颜色与文案分开。

状态推导集中在一个纯函数里：

```ts
function traceState(entry) {
  if (entry.status === 'running') return 'running';
  if (entry.status === 'ok') return 'ok';
  const text = `${entry.error ?? ''} ${entry.resultSummary ?? ''}`;
  if (/熔断|breaker/i.test(text)) return 'breaker';
  if (/拒绝|未授权|策略|denied|approval/i.test(text)) return 'denied';
  return 'failed';
}
```

它不完美，但它把「猜状态」这件事从多个组件里收回到一个地方，测试可以直接覆盖。

## 失败原因归一

状态回答「成没成」，原因回答「为什么」。服务端返回的错误是自由文本，可能来自工具、模型、HTTP 层或策略层，直接展示会非常碎。

这里做了一层归一，把文本收敛成八类：

| 原因 | 典型信号 |
|---|---|
| 被拒绝 | 拒绝、未授权、策略、approval |
| 已熔断 | 熔断、breaker |
| 超时 | 超时、timeout |
| 限流 | 429、限流、rate limit |
| 鉴权 | 401、403、鉴权、auth |
| 页面过大 | 200K、过大、超过上限 |
| 网络 | 抓取失败、连接、fetch |
| 未知 | 其余 |

归一发生在展示边界，不改变服务端原始错误。展开详情仍然能看到原文，方便排查。这是一个有意的折中：**不追求分类百分百准确，只追求用户第一眼能看懂，并且永远能回到原文。**

## 失败之后给一个动作

只告诉用户「失败了」仍然不够。两类高频失败各配了一个动作：

- 抓取网页失败：如果参数里有合法 URL，提供「用浏览器打开」。隔离网页工具打不开的页面，系统浏览器往往能打开，至少能让用户确认链接是否有效。
- 联网搜索失败：提供「检查搜索服务」，直接跳到设置里的联网搜索面板，而不是让用户自己找。

动作只在能确定目标时出现。拿不到 URL 就不渲染按钮，避免点开一个空页。这个判断也放在纯函数里，输入是参数摘要，输出是 URL 或空。

## 为什么用正则而不是错误码

更干净的做法是让每个工具返回结构化错误码。但这一版面对的是已有工具：内置搜索、网页抓取、知识检索、MCP 工具、子 Agent，各自的错误格式并不统一，短时间改不完。

所以选择在 UI 层先归一，同时保留原文。它让界面立刻可读，也为后续把错误码下沉到工具层留了空间。等结构化错误铺开，这一层可以逐类替换，不需要重写组件。

## 组件拆分：别让主组件继续长

工具时间线所在的主组件原本已经在行数门禁的高位。这一版把状态推导与详情渲染拆出去：

- `tool-trace-state.ts`：状态、失败原因、目标 URL 的纯函数；
- `tool-trace-detail.tsx`：展开区的单次调用详情；
- 主组件只保留聚合、折叠与事件接线。

拆分的判断标准不是「文件大小好看」，而是「能不能独立测试」。状态与原因的映射现在可以脱离 React 直接断言，主组件则回到它该做的事：组织数据与交互。

## 验证与边界

组件测试覆盖了聚合计数、四态标签、展开收起、失败动作的出现条件；`pnpm check` 的行数、目录预算与循环依赖检查通过。

边界同样明确：自动收起只在回合完成后发生，用户手动展开后不会被抢走；聚合只作用于同一回合，跨回合不会混在一起；失败原因的分类是启发式的，遇到新错误文本会落到「未知」，而不是猜一个看起来合理的答案。

## 一条可复用的判断

**过程展示的目标不是「记录完整」，而是「让用户知道下一步」。**

当界面能在一行里说清「几次、成了几次、败了几次」，再在展开区保留全部细节，用户就不需要从几十行日志里自己拼结论。工具越强，这一点越重要——因为工具越多，失败的可能性也越多。
