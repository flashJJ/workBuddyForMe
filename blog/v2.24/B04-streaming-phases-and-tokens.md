# 「正在思考」不够用：把流式相位、用量与桌面状态讲清楚

工具正在跑的时候，界面通常只显示一句「正在思考」。用户不知道它是在搜网页、读网页、查知识库，还是已经拿到结果正在组织语言。

这句话在短回合里问题不大，一旦工具链变长，它就会变成焦虑来源：转了很久，到底是在干活，还是卡住了？

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，聊天页在 web 端，桌宠跑在 Electron 桌面壳里。这一篇讲三件小事：流式相位、token 用量，以及设置改动怎样即时传到桌面。

## 相位从哪里来

相位没有新增后端事件，而是从已有的工具轨迹推导：

```ts
function streamingPhase(message) {
  if (message.status !== 'streaming') return null;
  for (let i = message.toolTrace.length - 1; i >= 0; i -= 1) {
    const entry = message.toolTrace[i];
    if (entry?.status !== 'running') continue;
    if (entry.tool === 'web_search') return 'searching';
    if (entry.tool === 'fetch_webpage') return 'reading';
    if (entry.tool === 'knowledge_search') return 'retrieving';
    return 'tool';
  }
  // 工具都结束了但还没有正文：模型在整理结果
  if (message.toolTrace.length > 0 && !message.content.trim()) return 'organizing';
  return null;
}
```

五个相位分别对应「正在搜索网页」「阅读网页」「检索知识库」「执行工具」「整理结果」。

为什么不加后端事件？因为前端已经拿到了工具名、状态与正文，再让服务端发一套 `phase` 事件，只会增加协议面和同步成本。推导逻辑是纯函数，测试可以直接喂消息对象断言。

代价是相位比较粗。它只知道「当前正在跑哪个工具」，不知道这个工具执行到哪一步；如果模型连续调用同一个工具，相位不会变化。这是有意的：相位是给用户的方向感，不是进度条。

## 「整理结果」为什么值得单独存在

最容易让人以为卡住的时刻，不是工具在跑，而是工具全部结束、正文还没开始。

这段时间里没有任何运行中的工具，界面如果只按「有没有工具在跑」判断，就会回到空白或「正在思考」。但用户刚刚看到工具全部完成，期待的是答案马上出现。

所以加了一条兜底：有工具轨迹、没有运行中的工具、正文为空，就显示「整理结果」。它不一定百分百准确——模型也可能在准备下一轮工具调用——但它比空白更诚实。

## token 用量放在消息底部

用量展示只做一件事：助手消息完成后，在底部显示「本轮 N tokens」。悬停可以看到输入、输出与合计。

三个约束：

- 只对助手消息显示，用户消息不显示；
- 只在状态为完成后显示，流式中的数字会跳，意义不大；
- 只在总量大于零时显示，避免旧消息或异常回合出现「0 tokens」的噪音。

为什么不做累计？累计数字适合账单，不适合对话。用户想知道的是「刚才这一轮花了多少」，而不是「这个会话从开始到现在花了多少」。前者能帮助判断一次搜索值不值，后者只会变成一个不断增长的数字。

数据本身来自模型返回的 usage，不需要额外估算。缺失时不显示，不用字符数反推，避免给出一个看起来精确但其实错误的数字。

## 设置改动怎样传到桌宠

桌宠是一个独立窗口，它读设置的方式和主窗一样，但主窗保存设置后，桌宠不会自动重新请求。

原来的表现是：用户在设置里关掉勿扰，桌宠还在勿扰；改了互动短句，要重开桌宠才生效。

修复没有引入新的状态管理，而是用 `BroadcastChannel`：

```ts
function broadcastSettingsChanged() {
  if (typeof BroadcastChannel === 'undefined') return;
  const channel = new BroadcastChannel(SETTINGS_SYNC_CHANNEL);
  channel.postMessage('settings-updated');
  channel.close();
}
```

保存成功后广播一次；其他窗口监听同一个频道，收到就失效设置查询，让 React Query 重新拉取。没有频道支持的环境直接跳过，不影响主流程。

这个方案的好处是没有新增依赖，也不需要主进程转发。缺点是它只覆盖同源窗口，跨进程或跨设备仍然要靠轮询或事件总线。对这一版的需求来说，够用。

## 桌宠气泡：只显示有意义的整句

还有一个看起来很小、但很打扰人的问题：桌宠头顶偶尔出现一个几乎空白的气泡，过很久才消失。

根因有两层。第一层，语音合成会把文本切成碎片，纯标点或空白也会被当成一段字幕送进气泡。第二层，朗读结束后没有清空气泡，空闲状态也没有兜底清理。

修复分两步：

1. 气泡只渲染包含文字或数字的整句碎片，纯标点直接丢弃；
2. 进入空闲状态时清空气泡，并加一个 8 秒兜底，防止某个事件没有到达导致残留。

这不是视觉问题，而是状态生命周期问题。气泡的内容来自语音链路，但它的清理不能只依赖语音链路的结束事件——事件可能丢，状态必须有超时。

## 验证与边界

相位推导、用量渲染条件、设置广播与气泡过滤都有对应的组件或纯函数测试；`pnpm check` 全绿。

边界也需要说明：相位是客户端推导，不保证与服务端真实步骤一一对应；token 用量依赖模型返回，缺失时不展示；`BroadcastChannel` 在不支持的环境下降级为不广播；气泡过滤只处理「有没有意义」，不判断语义是否完整。

## 一条可复用的判断

**过程反馈的最小单位不是「在忙」，而是「在忙什么、花了多少、什么时候结束」。**

相位回答「在忙什么」，用量回答「花了多少」，状态清理回答「什么时候结束」。三件事都不需要新协议，只需要把已有数据放到用户能看见的位置。
