# 工具轮用尽之后：为什么值得再打一次模型

一个需要联网搜索的问题，前五轮模型都在调工具，正文一个字没写。第五轮结束，编排器触发轮数上限，界面出现「未能形成回答」。

从链路看，这个结果并没有 bug：轮数确实用完了，正文确实为空，兜底文案确实是按要求落下的。但从用户视角看，这就是一次彻头彻尾的失败——搜索做了，网页读了，token 花了，最后一句话都没换来。

我们的桌面 AI 应用是一个本地优先、单人开发的私人助手，聊天编排在 core 包。这一篇只讲一件事：**工具轮用尽时，怎样把已经拿到的结果变成回答，而不是直接认输。**

## 为什么会出现「只有工具调用」的回合

模型在工具调用模式下，一次回复可以包含正文，也可以只包含 `tool_calls`。很多模型在搜索类任务里会连续只发工具调用：先搜，再读，再搜，再读，直到它认为信息够了才写正文。

问题在于轮数上限是按「模型调用次数」算的。前五轮如果都在调工具，第六轮就没有机会了。编排器看到正文为空，只能落兜底。

这里有两个常见的错误修法。

第一个是调高轮数上限。它确实能让一部分问题过关，但代价不可控：复杂问题会把上限继续顶满，延迟和 token 线性上涨，真正的死循环反而更难暴露。

第二个是让工具结果直接拼成回答。这会把「模型组织语言」降级成「程序拼字符串」，遇到需要取舍、对比、引用来源的问题，质量会明显下降。

## 收尾轮：多一次不带工具的调用

真正缺的不是更多工具轮，而是**一次没有工具可调、只能写答案的调用**。

做法很直接：检测到「轮数用尽 + 正文为空 + 已有工具结果」时，在消息列表末尾追加一条收尾指令，然后以空工具集再调用一次模型。

```ts
const ROUND_SYNTHESIS_PROMPT =
  '工具调用轮数已用尽。请只基于上文已获得的工具结果直接给出最终回答，' +
  '不要再调用工具；若信息仍不足，请说明还缺什么。';

async function* synthesizeFinalAnswer(input) {
  const turn = runProviderTurn({
    messages: [...input.outgoing, { role: 'user', content: ROUND_SYNTHESIS_PROMPT }],
    tools: [],           // 关键：这一轮不允许再调工具
    signal: input.signal,
  });
  // ...把流式增量照常转成事件
}
```

三个细节决定了它是否可靠。

第一，收尾指令放在消息列表最后，而不是塞进系统提示。系统提示离当前回合太远，模型很容易忽略「不要再调工具」这种临时约束；最后一条用户消息更接近即时指令。

第二，工具集必须显式传空数组。只写「不要再调工具」并不够，模型仍然可能返回工具调用；空工具集从协议层断掉了这条路。

第三，收尾轮仍然走流式。它和普通回合一样把增量交给前端，用户看到的是回答在生成，而不是界面卡住后突然出现一大段文字。

## 兜底文案什么时候才允许出现

收尾轮不是万能的。它可能返回空文本，也可能只返回一句「信息不足」。所以调用方要保留原来的兜底，只是把触发条件往后挪了一层。

```ts
const result = yield* synthesizeFinalAnswer(input);
if (!result.content.trim()) {
  yield { event: 'done', data: { content: ROUND_LIMIT_FALLBACK } };
}
```

这样兜底的含义就变了：它不再是「轮数到了」，而是「连一次专门写答案的调用都没能产出文本」。这两种失败对用户的价值完全不同，前者是流程限制，后者才是真的没答案。

## 为什么不复用最后一轮

一个自然的疑问是：第五轮模型已经拿到了全部工具结果，为什么不直接把第五轮的调用改成收尾？

因为第五轮发出时，模型仍然带着完整工具集，它的决策空间里「继续调工具」是合法选项。等到轮数用尽再改工具集，已经来不及了。收尾轮的价值就在于它发生在一个**工具不可用**的上下文里。

## 测试要盯住三个点

收尾逻辑的单测没有铺得很广，但三个点必须钉死：

| 断言 | 防的是什么 |
|---|---|
| 收尾调用不携带任何工具 | 模型仍然返回工具调用，收尾轮空转 |
| 收尾指令位于消息列表末尾 | 指令被历史消息淹没 |
| 收尾轮返回空文本时走兜底 | 空回答被当成成功 |

第三个点尤其容易写松。如果测试只断言「函数被调用」，它永远发现不了「调用完还是空」。断言必须落到最终返回的文本上。

## 验证与边界

这一版把收尾轮接到了真实编排链路里。搜索类问题在工具轮用尽后，能基于已获得的网页摘要成文；只有收尾轮也失败时，界面才出现兜底文案。

边界也要说清楚：收尾轮会增加一次模型调用，成本和延迟都会上升。它只在「正文为空且已有工具结果」时触发，不会对每个回合都执行。如果工具结果本身为空，收尾轮也只能说明还缺什么，不应该被包装成一次成功回答。

## 一条可复用的判断

**兜底文案不是失败提示，它应该是「最后一次尝试也失败了」的结论。**

在此之前，所有还能尝试的路径都应该走完。多一次不带工具的调用，成本可控，却能把「搜了等于没搜」变成「搜到了但没有完全回答」——这两件事对用户的差别，比多花的那点 token 大得多。
