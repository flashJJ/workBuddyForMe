# 过程可读、能力可用：七条从真实返工里长出来的工程判断

这一轮开始时，摆在我们面前的是两组反馈。

一组关于对话：搜索做了，结果也拿到了，最后却只回「未能形成回答」；工具过程一屏几十行，看不出哪一步失败。

另一组关于能力：MCP 服务器在 Windows 上装不上；远程服务只支持 JSON 回包，遇到 SSE 就失败；需要 OAuth 的服务完全接不进来；带 Key 的搜索服务没有安全的存放位置。

两组问题最后收在同一个版本里，不是为了凑主题，而是因为它们共享同一条验收线：**用户是否知道发生了什么，并且还能继续。**

下面七条判断，每一条都对应这次真实的返工或取舍。

## 一、兜底之前，再问一次「还有没有最后一次尝试」

「未能形成回答」原来在工具轮用尽时立刻出现。从代码看完全合理：轮数到了，正文为空，落兜底。

但链路里还有一个没被用掉的机会：模型已经拿到了工具结果，只是没有机会写正文。追加一条「只基于已有结果作答」的收尾指令，以空工具集再调一次，成本是一次模型调用，收益是把「搜了等于没搜」变成真正的回答。

这条判断可以推广到很多「兜底」场景：**兜底文案不是失败提示，而是最后一次尝试也失败的结论。** 在它之前，所有还能试的路径都应该走完。

## 二、聚合是排序，不是隐藏

工具过程原来按调用平铺。每一次调用都真实、完整，但用户读不出结论。

改成同回合一张折叠卡片后，头部先给「几次、成几次、败几次」，细节放进展开区。流式时自动展开，完成后自动收起。

有人会担心聚合藏掉了信息。事实相反：信息一条没少，只是顺序变了。用户先拿到结论，再决定要不要看过程，这比默认铺开几十行更接近阅读习惯。

**界面的第一职责是排序，不是穷举。**

## 三、错误先归一，再谈重试

工具失败原来只有一种红色，原因是一段自由文本；搜索失败会把反爬 HTML 直接抛成 JSON 解析错误。

这一轮做了两层归一：工具侧把失败收敛成超时、限流、鉴权、页面过大、网络、被拒、熔断、未知；搜索侧收敛成密钥无效、限流、格式错误、不可达。

归一的目的是让「下一步动作」可计算：鉴权失败去授权，限流稍后重试，网络失败检查地址，页面过大换抓取方式。**没有归一的错误，只能让用户反复点重试。**

归一发生在展示边界，原始错误仍然保留在详情里。这是有意的折中：不追求分类百分百准确，但保证永远能回到原文。

## 四、平台差异要用「最小可复现命令」钉住

Windows 上 `npx` 起不来，终端里却正常。根因是构造命令时给裸命令名加了引号，`cmd` 对 `.cmd` 包装的解析路径变了，包装脚本里的 `%~dp0` 落到了项目目录，`npx` 找不到 npm 自身模块。

修复只改了一个判断：只有包含空格或引号的命令才加引号。

这次排查最值钱的动作不是修复，而是把最终的 `file + args` 原样打印出来，在终端里复现。应用里的 `spawn` 经过包装、转义、环境注入，和手敲的命令往往不是一回事。

**先记录真实命令，再讨论原因。** 平台分支要列成表，转义要针对对象而不是平台，回归测试要能在旧实现上失败。

## 五、安装器是契约，不是列表

旧的预置服务器只是几条写死的命令：包可能已归档，路径可能写死，运行依赖没有声明。用户点安装，失败后只看到一行退出码。

这一版把目录项做成契约：传输方式、命令或地址、参数占位符、运行依赖、最低版本、许可证、说明。安装前并行探测 `node`、`npx`、`uvx` 与 Chrome；缺依赖直接给出可读原因，不写库。

安装状态机也明确了失败语义：同名跳过、连接轮询 90 秒、鉴权失败单独标记、单项失败不阻断后续。

**列表告诉用户「有什么」，契约告诉用户「需要什么、缺什么、失败后怎么办」。**

## 六、安全边界要在每个新入口重做一遍

这一轮新增了三个入口：搜索 API Key、远程 MCP Headers、OAuth 令牌。每一个都可能把密钥带出本机。

对应的处理分别是：搜索 Key 单独加密存储，只暴露脱敏串；OAuth 端点强制 https（回环除外），每一跳重定向都重新做私网校验；显式配置的 Headers 优先于 OAuth 令牌，避免用户自带的身份被悄悄覆盖。

还有一个容易被忽略的边界：令牌与待处理授权事务都按服务器拆键存储，加密落盘，不新增表，也不进入通用设置对象。

**新增一个入口，就把已有的安全规则重走一遍。** 不要假设「之前做过了，这次可以复用」。

## 七、可见性优先于自动重试

远程 MCP 的 401 只重试一次，刷新失败就退回错误；工具失败不会自动无限重试；流式相位、失败原因、token 用量都直接展示给用户。

这不是偷懒，而是取舍：自动重试能解决一部分瞬时问题，但它也会把「一直失败」伪装成「有点慢」。用户看不到重试次数，只看到界面转很久，最后仍然失败。

**能看见的状态，比看不见的重试更有价值。** 一次明确的重试加上清晰的失败原因，比三次静默重试更接近可信。

## 这一轮刻意没做什么

方案里排在后一阶段的项目没有进这一版：行内引用角标、来源卡片定位、子 Agent handoff 泳道、回合运行摘要、抓取失败降级。它们需要额外的交互设计与验收口径，半成品上线只会增加噪音。

没有新增 UI 依赖，仍然沿用 Radix 与 Tailwind；没有数据库迁移，结构版本保持 45；没有重写多 Agent 编排内核，只修过程与安装链路。

## 对账：数字与结果

`pnpm check` 全绿。core 包 MCP 与搜索相关单测 10 个文件、42 例通过；web 端 MCP 设置与搜索设置 3 个文件、13 例通过。

实机验证：文件系统服务器 14 个工具，记忆服务器 9 个，远程文档检索服务器 2 个；OAuth 授权地址包含 PKCE `S256`、资源标识与默认 scope。

这些数字不大，但它们对应的是用户能感知的变化：搜索不再轻易落兜底，工具过程能一眼看出成败，服务器装得上，远程服务连得通。

## 最后一条

**把「用户不知道发生了什么」当成一类 bug 来修。**

它不会抛异常，不会出现在错误日志里，也不会被单元测试捕获。但它会消耗信任，而信任是本地优先应用最贵的资产。

下一篇不会有了——这一轮该讲的，已经讲完了。
