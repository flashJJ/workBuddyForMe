# 让知识库「用你存的原文回答」：编译式 RAG 与知识治理（v1.3 总览）

我们的桌面 AI 应用做的是本地优先的私域知识库：Electron 壳、Next.js 前端、SQLite 加 sqlite-vec，所有知识数据只在用户本机。上一代检索链路是教科书式的纯向量 RAG——文档切块、嵌入、top-k 召回、拼上下文、挂引用角标。上线头两周演示效果很好，真正用了两个月之后，错误开始高度集中地出现。而且没有一种错在模型。

## 纯向量 RAG 的「切片漏斗」

把一份设备手册丢进知识库，切块、嵌入，然后提问。检索阶段实际发生的事是：型号、参数、别名这类硬事实，和切块时碰巧相邻的噪声片段挤在同一个向量空间里一起排名。问「ZK-900 的额定电压是多少」，召回的常常是一段语义相近但数值完全不对的文字——可能是另一台设备的参数表，也可能是维护注意事项里顺带一提的半句。模型拿到什么就引用什么，于是它诚实地引用了一个「语义邻居」。

中文精确词的问题更隐蔽。型号、编号、英文缩写这类符号，纯向量召回极不稳定：同一个型号，这次问得回来，换个问法就沉底。而引用栏只写着「片段 3」——片段是切块的产物，不是文档的自然结构，用户拿着「片段 3」根本无法回到原文核对。

内容侧还有两个安静的腐烂过程。同一件事在新旧文档里说法矛盾，系统照单全收，矛盾静默共存；重新导入文档时新切片整体覆盖旧切片，谁新谁赢，跟对不对毫无关系。

## 这个版本的四块回答

这一版的主题叫「知识变厚」，针对上面四个断点各给一块回答：

| 上一代的断点 | v1.3 的回答 |
|---|---|
| 单通道向量召回，精确型号、编号查不准 | **混合检索**：向量 + FTS5 全文双路并行，RRF 倒数排名免标定融合，再上规则重排把真正含查询词的片段顶上去 |
| 答案引用「语义邻居」而不是存储事实 | **无模型知识编译器**：摄入后机械抽取实体事实与文档要点，提问时静态条目置顶注入，编译路由可开关 |
| 引用只有「片段 N」，无法核对出处 | **语句级引用**：页码、段落号、字符起止坐标从数据库一路贯通到界面角标，静态条目带独立徽标 |
| 矛盾静默共存，重新导入赢者通吃 | **知识治理**：冲突检测、重复文档检测、同名替换；编译动作收进后台编译队列 |

## 四块不是功能清单，是一条流水线

这四块之间不是并列堆砌，而是按文档生命周期串起来的：

```text
摄取期：切块带 overlap，chunk 写好页码/段落归属，向量与 FTS 双索引就位
编译期：重叠分片缝合成虚拟文档 → 规则抽取要点与实体 → 逐字定位提及 → 世代事务写入
查询期：向量 + FTS 双路召回 → RRF 融合 → 规则重排；静态事实按实体名置顶注入，与片段分区
回答后：页/段/字符坐标化的引用透传到界面，「文档陈述」与「片段检索」可区分
治理线：冲突检测、重复检测、同名替换随时对编译产物体检
```

任何一环出问题，症状都能沿这条流水线定位到具体阶段，而不是笼统地归咎于「检索不准」。

## 编译器默认零模型调用

本地优先应用不能假设用户永远挂着强模型、有着无限额度。因此第一版知识编译器是纯确定性的文本工程：切句、过滤、模式匹配、打分排序，全程不花一分模型钱，导入一篇文档的额外成本只是一点本地 CPU。结果可复现——同一份文档编译十次，产物逐字节一致，这让世代切换和回归测试才谈得上。

模型增强做成了一层默认关闭的可选项，纪律非常硬：增强结果必须逐字回指原文，但凡零有效增强、超时 30 秒、解析失败，一律丢弃增强结果、回落到规则种子。开不开增强，编译器都一定交得出东西，区别只是质量上限。

另外几条边界是开工前就定死的：

- 中文全文检索**不引入外部分词器或词典**，单字一元方案全部内建，不背词典维护和打包体积的债；
- 不做图检索、表格检索、多模态检索，不做跨库联邦检索；
- 不做云端知识库和多端同步，知识数据仍然只在用户本机。

## 一个核心判断：瓶颈不在模型，也不在嵌入

做完这个版本回头看，大约 80% 的工作量是确定性的文本工程：重叠分片怎么缝合、字符坐标怎么归属、两路排名怎么合、规则重排怎么打分、编译产物怎么做世代切换、矛盾怎么用纯函数判出来。

这背后是一个可能反直觉的判断：**RAG 的质量瓶颈往往不在模型，也不在嵌入模型，而在「喂给检索的索引结构」和「检索结果怎么合」。** 文档切块之后，硬事实和噪声在索引里就是平权的，再贵的嵌入也救不回一个根本没有精确词通道的索引；两路召回各自都对，但加权求和的权重靠拍脑袋，合出来的榜单照样把噪声顶在前面。

把索引结构做厚（全文通道、实体表、摘要表、坐标字段），把合并规则做成免标定的确定性函数，质量提升是立竿见影且可回归测试的——这比换一个更强的模型或更贵的嵌入便宜得多，也可靠得多。

## 引用第一次能「指回原文」

这一版的引用不再是「片段 3」。每个 chunk 在摄取期就写好页码与段落归属，编译器在重建文本上记录字符区间，引用对象最终带着页码、段落号、字符起止坐标和静态条目类型，穿过事件流、数据库快照一路透传到 web 端。界面上两类证据有明确的视觉区分：「文档陈述」是编译器抽出的静态事实，带独立徽标；「片段检索」是实时召回的上下文。用户一眼能看出模型这句话是在引用文档写明的事实，还是在临时拼凑的检索结果上发挥。

## 治理与队列：让知识库长期用得下去

光有编译没有治理，知识库用久了照样烂。这版的三个治理手段全部是确定性的：冲突检测用纯函数比对版本、标量、标题三个维度，同文档双值按版本升级豁免；重复文档检测直接复用库存向量做采样 KNN，相似度够高且至少两片对撞才判定，零新增模型调用；同名重新导入复用原文档行做内容替换，文档 id 不变，历史引用不失效，再做世代重置与重编译。

编译动作本身收进一个后台队列：单并发 FIFO、同库去重、可取消、SSE 推送进度，导入文档后自动编译默认开启。嵌入式 SQLite 的写锁和本地嵌入模型的 CPU、内存都扛不住并发编译，单并发是对运行环境的诚实，配合明确的进度反馈，体感是稳而不是慢。

## 怎么证明不是自欺

知识链路的改动最容易写出恒真断言——只要开关全开，什么题都能「通过」。知识 eval 准备了 22 份种子文档和 15 个用例，分实体、摘要、护栏、反向标注四类，用同一条命令在三种开关态下各跑一遍：

| 开关态 | 判定结果 |
|---|---|
| none（纯向量，模拟旧链路） | 15/15 |
| fts（混合检索开、编译关） | 11/11，4 题 SKIP |
| compile（混合检索与编译全开） | 8/8，7 题 SKIP |

标注题只在它所标注的开关态做反向判定，其余态显式 SKIP，而不是凑一个虚假的通过数；护栏题在所有状态下都必须正向通过。反向验证逼出了一个真实的标注错误（下一篇细讲），这套矩阵的设计过程和代码一样有价值。

整体质量口径：静态门禁 14/14 全绿；243 个测试文件、1452 个单测用例全绿；端到端 37/37，其中新增的知识链路场景覆盖五件事——上传到自动编译、静态引用断言、同名替换的世代与内容双验证、治理冲突的版本徽标。

1452 个单测在各包的分布也值得一看，知识链路的增量主要压在 core 包：

| 包 | 测试文件 / 用例 |
|---|---|
| core | 101 / 658 |
| web | 61 / 326 |
| database | 30 / 122 |
| desktop | 17 / 129 |
| shared | 13 / 97 |
| ai | 10 / 43 |
| voice | 7 / 63 |
| config | 4 / 14 |
| 合计 | 243 / 1452 |

集成测试 12/12 随既有任务保持全绿。确定性文本工程最大的好处就在这里：缝合、抽取、融合、重排、冲突判定全部是纯函数，不需要模型、不需要界面，给输入断言输出即可，所以知识链路敢在一个版本里塞进上千字的新规则而不崩盘。
