# 错误提示只有「重试」，为什么还不够

一个操作失败时，用户需要知道三件事：发生了什么、为什么会这样、我现在能做什么。

大多数错误组件只回答了第一件，少数回答了第二件。第三件通常被简化成一个「重试」按钮——如果失败原因不是偶发故障，这个按钮点多少次都没用。

## 一、先看错误组件的结构

旧的错误态组件接收两个参数：标题与描述，外加一个可选的 `onRetry`。

这带来一个隐含假设：所有失败都是可重试的。于是「模型未配置」也显示重试，「本地搜索未启动」也显示重试，用户点了几次之后只会更困惑。

## 二、加一个动作插槽，而不是加十个分支

修复方式很小：增加一个可选的 `action` 节点。

```ts
interface ErrorStateProps {
  title: string;
  description?: string;
  onRetry?: () => void;
  action?: React.ReactNode;
}
```

渲染时优先使用传入的动作；没有动作时，才回退到原有的重试按钮。

这个顺序很重要：它保证了已有调用方零改动，同时让新场景可以给出「打开设置」「去下载」「一键启动」这类具体动作。

## 三、四类高频故障怎么接

不是所有错误都值得定制，所以只挑高频且修复路径明确的四类。

**模型未配置。** 对话区直接进入阻断式空态，给出三条路：配置模型、使用演示模式、从模板开始。这里没有用「发送前弹提示」，因为让用户先输入再被打断，比一开始就说清楚更差。

**MCP 连接异常。** 沿用服务卡片的「测试连接」作为重试动作，同时保留启用开关，让用户可以主动停用。没有新增日志查看器——现有详情已经能看到状态与错误信息，再加一层只会增加维护成本。

**本地搜索未启动。** 复用已有的一键启动组件，启动成功后继续原来的请求。用户不需要理解本地索引是怎么工作的，只需要知道点一下就能继续。

**语音模型未下载。** 复用下载引导：先说明需要多少空间，再提供下载与重试入口。这里最重要的不是按钮，而是体积提示——用户需要在下决心前知道代价。

## 四、为什么强调「原因 + 下一步」

只写原因，用户知道发生了什么但不会修；只写下一步，用户不知道为什么要这么做。

所以每一类都要求两句都在：

- 原因：默认模型不存在，或连接健康检查失败；
- 下一步：去设置里添加一个模型，或先用演示模式体验。

动作按钮是这两句话的延伸，而不是替代。

## 五、复用带来的副作用

四类故障里，有三类在早期版本已经具备修复能力：供应商测试连接、本地搜索一键启动、语音模型下载。

这意味着这一项的真实工作量不在「做功能」，而在「把已有能力放到错误发生的位置」。写新组件反而更简单，但会造成两套入口，维护成本更高。

最终的选择是：只在缺少动作插槽时改公共组件，其余全部复用。

## 六、测试怎么写

错误路径的测试容易写成「断言错误文案存在」，但那只验证了渲染。

这一项的验收标准是「动作可见且可点击」：

- 模型未配置时，三个入口都存在；
- 每个动作能触发预期跳转或状态变化；
- 无动作时仍保留原有重试行为。

这样测试才真正覆盖了用户从失败中恢复的路径。

## 七、一个错误只给一个主动作

动作插槽支持传入任意节点，但接入时遵守一条规则：只给一个主按钮，其余用次要链接或文字提示。

原因是错误发生时用户已经受挫，多个同等权重的按钮会制造新的选择负担。主按钮应该是最可能解决问题的那一个，其他选项退后。

以模型未配置为例：主按钮是「配置模型」，演示模式与模板作为次级路径并列展示，但视觉权重明显更低。

## 八、动作失败之后怎么办

动作本身也可能失败。比如点击「测试连接」，结果仍然异常。

这时不应该回到一个没有反馈的静态页面。现有卡片会更新健康状态与错误信息，用户能看到第二次尝试的结果，并决定是否停用服务。

换句话说，动作不是终点，而是一次新的状态查询。界面要能承接这个结果，而不是只负责把用户送到某处。

## 九、边界

不是所有错误都应该给动作。网络瞬时失败、接口超时这类情况，重试仍然是最合理的默认。

判断标准是：如果同一原因导致的失败可以稳定复现，就值得给一个具体动作；如果只是偶发，就不要用固定动作误导用户。
