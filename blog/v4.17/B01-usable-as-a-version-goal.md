# 把「用得顺」当成一个版本目标

功能清单已经足够长之后，继续加能力的边际收益会快速下降。真正让人卡住的，往往不是缺一个按钮，而是：上限到了却不知道、失败了不知道怎么修、常用动作每次都要多点两下。

这一版只做一件事：把关键路径上的感知、恢复与复用补齐。

## 一、六个问题，其实是三类缺口

一次用户复验暴露了六个问题，表面看彼此无关：

- 多选工具保存后勾选消失；
- 技能、知识库、流程入参达到上限没有任何提示；
- 能力中心里「已安装」的服务仍然可以被勾选；
- 本地搜索没启动时，对话直接失败，没有下一步；
- 桌宠有背景时点击空白会穿透到桌面；
- 拖动侧栏或按钮会弹出浏览器原生的链接浮层。

逐个修也能交差，但把它们放在一起看，会发现只有三类：

1. **限制不可感知**：数量上限存在于代码里，用户看不见；
2. **状态有歧义**：一个徽标同时表达「安装了」和「能选」；
3. **失败不可恢复**：错误只有一句结果，没有原因与动作。

剩下的两个属于交互命中区与原生行为，单独收口即可。

## 二、目标怎么定

这一版把目标写成四句话，每条都能验收：

1. 任何数量上限、能力状态、异步进度，界面上都要有唯一、可读的表达，禁止静默截断；
2. 四类高频故障都能看到「为什么 + 下一步」，并能一键跳到修复位置；
3. 已有数据与已有接口要接到界面上，而不是继续躺在代码里；
4. 跳过首启向导的用户，仍能在对话空态通过三条路产生第一条回答。

四句话对应四个里程碑：感知层、恢复层、首启收口、效率层。

## 三、明确不做什么

易用性版本最大的风险是范围失控，所以非目标与需求同权重：

- 不做图片/视频生成、不做全双工实时语音；
- 不做云同步、移动端、团队协作；
- 不引入新的 UI 框架、图标库或状态管理库；
- 不改数据库 schema 与备份格式，目标零迁移；
- 不重做视觉风格，只做信息层级与反馈；
- 不重复建设已具备的能力。

最后一条尤其重要。首启向导、供应商「测试连接」、命令面板、模板中心、技能与 MCP 徽标、流式渲染帧节流，这些在两年前就已经存在。本版只补缺口，不重造轮子。

## 四、复用优先于新建

判断一个需求要不要做，先问三个问题：

1. 服务端协议已经有吗？
2. 数据已经写进本地日志了吗？
3. 现有组件能不能加一个参数解决？

以消息检索为例：搜索接口与本地事件日志都已存在，缺的只是 UI 消费。这种情况的正确做法是接线，而不是新建一套索引。

再以错误恢复为例：四类故障里，MCP 重试、本地搜索一键启动、语音模型下载都已经有现成组件，本版只统一口径与入口。

## 五、度量与验收

没有度量的易用性改版容易变成主观争论，所以这一版留了三个硬指标：

- 质量门禁全绿：类型、lint、行数、目录、循环依赖、测试桩、资源、E2E 隔离；
- 单元测试覆盖新增组件与关键路径；
- 首启实测：新数据根下，从打开应用到第一条回答不超过 5 分钟，演示模式路径不超过 60 秒。

第三个指标用开发态埋点记录，不进入生产界面，也不上传任何数据。

## 六、为什么不做一次大重构

看到「状态语义不清」「上限不统一」这类问题时，最自然的反应是重做一套设计系统。

这一版明确拒绝了这条路。原因有三个：

1. 重做设计系统会影响所有页面，回归成本远高于收益；
2. 真正造成困惑的只有少数几个共享组件，改它们就够了；
3. 单人维护的项目里，大重构意味着长时间无法交付，反馈闭环会断。

所以最终只新增了两个公共组件、扩展了一个错误态组件，其余全部是接线与文案调整。

这也是易用性版本和架构版本的区别：架构版本追求结构正确，易用性版本追求用户少走一步。后者应该尽量少动结构。

## 七、风险与回退

每一项改动都写明了回退方式：

- 上限提示与状态徽标是新增组件，出问题可以直接卸掉接入点；
- 错误态新增的是可选参数，删掉参数即可恢复旧行为；
- 检索弹层是独立模块，关闭入口不影响原有命令面板；
- 空态改动集中在消息列表的一个分支，回退范围可控。

风险最大的其实是视觉基线：空态与设置页变化会触发截图差异。这一版保持视觉巡检非阻断，并计划在真机阶段统一更新基线。

## 八、结果

最终交付没有新增数据库迁移，没有新增依赖，也没有新增侧栏入口。

留下的是四类共享能力：限制提示、能力状态徽标、可带动作的错误态、以及一组把已有接口接到界面的入口。

下一篇从最容易被忽视、但造成数据丢失的一项讲起：多选上限的静默截断。
