# 一个徽标只说一件事

「已安装」这三个字，在不同页面意味着不同东西。

在目录页，它表示服务已经装好；在能力中心，它表示服务存在但未必启用；在助手配置里，它又变成了「可以勾选」。同一个状态，三种颜色，四种文案。

用户看到的结果是：一个显示「已安装」的服务，仍然可以被勾选第二次。

## 一、问题不是文案，是语义

最初的想法是统一文案，把「已安装」改成「已启用」之类。但改完发现没有用，因为底层状态本身就没有定义清楚。

一个能力至少可能处于这些状态：

- 可用，但尚未启用；
- 已启用，运行正常；
- 已启用，但连接异常；
- 已停用，或文件已不存在。

旧代码把后三种混在两个布尔值里，不同页面各自解释，于是同一个服务在不同位置得到不同结论。

## 二、先定义四态，再谈颜色

与其继续修补文案，不如先把状态收成一个枚举：

```ts
type CapabilityStatus = 'available' | 'enabled' | 'disabled' | 'error';
```

四个值分别对应：

- `available`：具备条件，但未启用；
- `enabled`：已启用且运行正常；
- `disabled`：用户主动停用，或不满足启用条件；
- `error`：已启用，但健康检查失败或资源缺失。

颜色只由状态决定，不由页面决定。这样「异常」在任何地方都是同一种颜色，不需要记忆。

映射表本身也很短，短到可以一眼看完：

```ts
const VARIANT = {
  available: 'info',
  enabled: 'success',
  disabled: 'outline',
  error: 'danger',
};
```

短是有意的。状态一旦变多，映射表会先变得难读，这本身就是「不该继续加状态」的信号。

## 三、组件只做映射

共享组件的职责被刻意压到最小：接收状态，输出徽标。

```tsx
<CapabilityStatusBadge status="error" />
```

内部只做两件事：把状态映射到统一的视觉变体，把状态映射到统一的翻译键。

调用方仍可以覆盖文案，但颜色与语义不能覆盖。这个约束很关键——允许改文案，是为了兼容各页面已有的业务描述；不允许改颜色，是为了让用户形成稳定的直觉。

## 四、三个接入点，各自怎么判定

接入时没有追求「一次改完所有页面」，而是先改三处真实存在歧义的地方。

**能力中心**：服务启用但健康检查为异常时，判为 `error`；已启用且正常为 `enabled`；其余为 `disabled`。

**MCP 目录**：已安装但停用为 `disabled`；安装状态异常为 `error`；连接正常为 `enabled`；仅可安装为 `available`。

**技能列表**：文件不存在或加载报错为 `error`；已启用为 `enabled`；其余为 `available`。

三处的判定逻辑不同，但输出同一套状态，界面就能用同一种方式解释。

## 五、为什么知识库没有接入

原本计划把知识库列表也接进来，最后没有做。

原因是知识库只有文档处理状态：等待解析、解析中、已索引、失败。这些描述的是「文档进度」，不是「能力是否可用」。硬套四态会造成新的混淆，比如把「解析失败」显示成能力异常。

这是一个主动放弃：统一不等于把所有东西都塞进同一个枚举。语义不适用时，不接比硬接更正确。

## 六、顺带解决的交互问题

状态统一之后，「已安装仍可勾选」的问题自然消失了。

因为「已安装」不再是可勾选状态的文案，而是一个明确的 `enabled` 或 `disabled` 状态。可勾选的列表只展示 `available` 项，已经启用的项从候选里移除。

这比在点击时弹一个「已经添加过了」更干净，也更符合用户对「安装」这件事的理解。

## 七、验收

- 四种状态各有一条渲染断言；
- 三处接入点分别有判定逻辑的测试；
- 文案中英双档齐全；
- 不新增依赖，不修改数据库。

留下的经验是：当一个界面元素需要解释三种以上含义时，先别改文案，先去定义状态。
