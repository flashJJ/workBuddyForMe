# 别再静默截断用户的选择

一个很隐蔽的缺陷：用户在弹窗里勾了 23 个工具，点保存，提示成功；重新打开，只剩 20 个。

没有报错，没有提示，甚至保存接口返回的也是成功。被丢掉的三项像是从未存在过。

## 一、问题不在保存，而在截断

排查时先怀疑前端状态没同步，后来才在保存路径里看到类似这样的代码：

```ts
toolNames: selectedTools.slice(0, TOOL_LIMIT),
```

上限确实存在，但它的表达方式只有两个：未选项被禁用，以及保存时切片。

前者依赖用户自己数还剩几个；后者在用户绕过了 UI 限制时静默丢弃。两条路径合起来，结果就是「看起来成功，实际少了数据」。

## 二、先审计，再动手

修复之前先做一次全量审计，范围包括三类写法：

1. 保存 payload 里的 `slice(0, N)`；
2. 表单 schema 里的 `.max(N)`；
3. 组件内部维护的数量常量。

审计的判定标准只有一条：超过上限时，用户是否能在提交前看到明确说明。

结果分成三种：

- 已经禁用未选项、有文案提示的：保留；
- 只禁用、没文案的：补提示；
- 保存时切片、UI 完全不拦的：必须修。

真正需要改代码的是第三类，前两类只需要统一表达。

## 三、把上限做成一个组件

与其在每个表单里各写一套提示，不如做一个共享组件。它的输入只有两个数字：

```ts
interface LimitHintProps {
  current: number;
  limit: number;
}
```

渲染逻辑也简单：

- 未达上限：显示「还可选 N 项」；
- 达到上限：显示「已达上限 N」，并使用警示色。

组件本身不带业务判断，所有选择逻辑仍留在表单里。这样它既能被助手工具选择复用，也能被知识库、流程入参复用，而不会把业务耦合进公共层。

## 四、禁用之外，还要说清楚

只在视觉上禁用未选项是不够的。用户看到灰掉的复选框，第一反应通常是「坏了」，而不是「到上限了」。

所以接入时做了两件事：

1. 达到上限后，未选项保持禁用；
2. 在同一区域显示统一的限制提示，说明当前已达上限。

这两件事必须同时存在。只有禁用没有说明，用户会尝试刷新；只有说明没有禁用，用户会继续点。

## 五、用不变量守住未来

这次修完，下一次仍可能有人在新的保存路径里写回切片。

所以把规则写成测试，而不是写成文档。测试扫描用户多选字段的保存路径，匹配这类切片写法：

```ts
/\b(skills|knowledgeBases|inputs|enabledTools|toolNames)\.slice\(0,\s*\d+\)/
```

匹配到就失败，除非显式加入允许清单。

允许清单当前为空。这意味着规则不是「尽量遵守」，而是「新增一处就红」。

## 六、为什么不改成服务端拒绝

有人会问：既然超限，为什么不让接口直接报错？

因为这不是接口契约问题，而是交互问题。接口拒绝会让用户丢掉整次提交，还得重新勾选；前端在提交前讲清楚，成本更低，体验也更好。

接口侧的数量校验仍然保留，作为最后一道防线，但它不再承担「告诉用户」的职责。

## 七、验收

这一项最终留下：

- 一个不超过 50 行的共享限制提示组件；
- 助手工具选择接入并补测试；
- 一条扫描保存路径的不变量用例，允许清单为空；
- 中英双档文案。

验收时特意回到最初的场景：勾满上限、再尝试多选、保存、重开。四步都能看到同一句说明，数据不再变少。
