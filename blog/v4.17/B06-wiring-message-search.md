# 已有的搜索接口，为什么用户用不到

后端有一个全局搜索接口，前端有一个「搜索会话」命令，两者都在，但用户点了命令之后，只是被带到对话页。

接口没有接界面，命令没有接行为。这类「半成品接线」在长期项目里非常常见：每一部分都能单独自证存在，合起来却不构成功能。

## 一、先确认数据在哪

做检索之前先确认三件事：搜的是什么、存了多久、能不能定位回原消息。

排查后发现，对话消息在写入时会记录事件：消息开始时写一条，完成时再写一条，payload 里包含消息 id、角色与内容，作用域就是会话 id。

这意味着搜索结果天然带有两个定位信息：会话 id 与消息 id。只要界面把这两个值带到对话页，就能直接定位到具体消息。

不需要新建索引，也不需要改服务端协议。

## 二、搜索状态怎么管

检索弹层是一个典型的「输入即搜索」场景，需要处理四个状态：输入、加载、结果、失败。

实现上使用固定间隔的防抖，并在每次新请求前中止上一次请求：

```ts
const timer = setTimeout(run, 300);
const controller = new AbortController();
fetch(url, { signal: controller.signal });
```

三个细节决定体验：

1. 防抖避免每次按键都打一次接口；
2. 中止避免旧请求晚到覆盖新结果；
3. 组件卸载时同时清理定时器与请求。

结果按消息 id 去重。同一段内容可能被开始与完成两条事件各写一次，不去重会出现重复条目。

## 三、结果列表要展示什么

一条结果展示三样东西：角色、内容片段、时间。

内容片段需要截断，否则一条长回答会撑满整个弹层。截断长度取 120 个字符，并在视觉上保持单行或两行，保证列表节奏稳定。

空结果不是简单的一句「无数据」，而是给出下一步：换一个关键词，或者扩大搜索范围。这两个建议对应真实可行动作，而不是安慰文案。

## 四、跳转要落到消息

如果点击结果只跳到会话首页，用户还要自己滚动寻找，检索的价值就减半。

所以跳转链接同时携带会话与消息：

```text
/chat?conversation=<id>&message=<id>
```

对话页原本已经支持深链参数，这一项不需要新增协议，只需要把参数拼对。

## 五、三个入口，同一套行为

检索只在命令面板里出现，等于把它藏起来。所以这一版接了三处入口：

- 命令面板中的「搜索会话」，保留原命令 id，只替换动作；
- 对话页头部的搜索按钮；
- 侧栏会话区域的搜索按钮。

三处都调用同一个打开函数，弹层组件只有一份。这样后续改搜索行为时，不需要追三份实现。

## 六、隐私要说清楚

全局检索容易让人担心「内容是否上传」。

这一项在界面上明确标注本机检索，因为接口只查本地事件日志，不调用远端模型，也不产生网络请求。说明放在弹层里，而不是埋在帮助文档。

## 七、测试绕开了一个门禁

最初的弹层测试直接替换全局请求函数，结果被仓库的请求桩门禁拦下。

门禁的意图是：新增测试应通过统一的请求模拟层，而不是各自替换全局函数。

修复没有去改门禁，而是把测试改成模拟检索 hook 的返回值。这样测试关注的是弹层如何展示与回调，而不是网络层；网络层由 hook 自己的逻辑与类型保证。

这也说明一个原则：门禁不是障碍，它在提醒测试分层是否清楚。

## 八、验收

- 输入后 300 毫秒触发检索，旧请求会被中止；
- 结果按消息 id 去重，片段截断稳定；
- 空结果显示换关键词引导；
- 点击结果携带会话与消息两个参数；
- 三个入口调用同一弹层；
- 无服务端改动、无数据库迁移。
