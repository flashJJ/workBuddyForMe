# v5.0 遗漏项盘点与处置建议

> 输入：v4.22–v4.25 版本总结「后续方向」、v4.25 已知边界、路线图永久关闭清单、当前开放 issue（0 条）。
> 目的：决定哪些进大版本、哪些用小版本收口、哪些继续遗留或永久关闭。

## 1. 处置分层

| 层级 | 含义 | 节奏 |
|---|---|---|
| P0 立即补丁 | 已发布产物的品牌/文档错误 | v4.25.1，立即 |
| S 小版本收口 | 独立、低耦合、能降低支持成本 | 调研期最多一个 v4.26 |
| M 大版本内 | 只保留支撑 v5.0 主题的 2–3 项 | v5.0 |
| D 继续遗留 | 有价值但不在当前主线 | v5.0 后按需 |
| X 永久关闭 | 与本地优先/产品定位冲突或收益不足 | 不再登记 |

## 3. 推荐节奏

### 3.1 立即：v4.25.1 品牌与文档补丁

只含 P0-1～P0-3，不新增功能、不迁移 schema。目的：让已发布的安装包与文档和产品名一致。

### 3.2 调研期：最多一个小版本 v4.26

建议主题：**会排班**（触发配置层收口）。

范围：S-1（多定时 + 每定时独立时区）与 S-3 的 Secret 轮换部分。
约束：一次迁移（v056）以内；不改 Flow 编译器；不引入新领域；不阻塞 v5.0 调研。
明确不做：HMAC、逐次补齐、事件重试/死信、心跳、运行治理、安全沙箱（全部留给 v5.0）。

理由：这些项独立于大版本主题，且能直接降低「定时不够用、时区说不清、换钥要重建」的支持成本；同时避免把 v5.0 变成杂烩。

### 3.3 v5.0：主题优先，只带 2–3 项支撑能力

大版本只允许包含：

1. 调研选出的一个主题（用户价值与差异化双高）；
2. 最多 3 项直接支撑该主题的遗漏项（从 M 层选）；
3. 必要的可靠性/安全收口（例如 M-3）。

明确拒绝：把所有 S/D 项打包进 v5.0。

## 4. 不推荐的做法

- **先做功能对齐再找主题**：会把大版本做成竞品清单的复刻；
- **把 D 层全部塞进大版本**：范围失控、验收困难；
- **为大版本预埋架构**：调研未结论前不动核心编译器与调度模型；
- **在调研期承诺发布日期**：先验证假设，再排期。

## 5. 决策门

调研结束评审时，逐项回答：

1. v5.0 主题是什么？用一句话说清「为什么是我们」；
2. 哪 2–3 个 M 项被纳入？为什么必须现在做；
3. S 层是否已完成？未完成项是否影响主题；
4. D/X 层是否有项被重新激活？理由是什么。

未通过则回到调研，不带病开工。
