# v2.13 规划前置：竞品对比与可借鉴点

> 调研日期：2026-10-30｜用途：v2.13 版本规划输入，不构成发布承诺
> 范围：7 个近期活跃的桌面/本地 AI 工作台与个人 Agent 产品；数据以官方文档与官方博客为主，第三方评述单独标注
> 方法：先定能力面，再逐项对照；只记录可验证事实，推测性判断标注置信度

## 1. 结论摘要

1. **本地优先不再是小众卖点，而是共同基线。** AnythingLLM、Cherry Studio、OpenClaw、Goose、LM Studio 都以「模型与数据留在本机」作为第一卖点，差别转向「在本机之上能做什么」。
2. **竞争焦点已从「聊天」转到「Agent 执行」**：工作目录、多步任务、子 Agent、权限模式、无人值守调度，是 2026 年新版本共同补齐的能力 [cite:8][cite:9][cite:12][cite:14][cite:15]。
3. **安全治理开始「代码化」**：OpenClaw 把权限模式、工具策略、审批绑定与审计做成可执行策略，而不是提示词约定 [cite:5][cite:6]；Goose 增加提示注入检测、沙箱与对抗评审 [cite:15]。
4. **「随叫随到」成为新入口**：OpenClaw 用 29 个消息渠道，Cherry Studio 用飞书/微信/Telegram 等渠道，把 Agent 从桌面扩展到 IM [cite:3][cite:10]。
5. **能力资产正在版本化**：Open WebUI 对模型、工具、函数、技能逐个保存版本，可 `Set as Production` 回滚 [cite:19]；OpenClaw 对运行时状态做 schema 契约与受控升级 [cite:7]。
6. **对我们最有价值的借鉴不是「再加功能」，而是「把 Agent 做成可治理的执行体」**：权限模式、策略即代码、隔离执行、审批绑定、审计与版本回滚，正好承接 v2.12 的信任收口。

## 2. 竞品选择与定位

| 产品 | 形态 | 定位 | 本次关注点 |
|---|---|---|---|
| Claude Cowork | 云端 + 桌面/移动客户端 | 通用办公 Agent | 插件包、内置浏览器、定时任务、并行子任务 [cite:1][cite:2] |
| OpenClaw | 开源自托管 Gateway + 桌面/移动节点 | 个人 Agent 网关 | 渠道、策略即代码、沙箱、版本化状态 [cite:3][cite:4][cite:5][cite:6][cite:7] |
| Cherry Studio | 本地桌面 AI 工作台 | 多模型聚合 + Agent 工作区 | Agent 权限模式、技能、定时任务、IM 渠道 [cite:8][cite:9][cite:10][cite:11][cite:12] |
| AnythingLLM | 本地桌面 / Docker | 文档工作区 + Agent | Workspace RAG、Agent Flows、定时作业、系统级听写 [cite:13][cite:14] |
| Goose | 本地桌面 + CLI + API | 通用开源 Agent | MCP 扩展、Recipes、子 Agent、安全评审 [cite:15][cite:16] |
| LM Studio | 本地桌面 / 无头守护进程 | 本地模型运行时 | 有状态 REST、MCP、权限密钥、并行推理 [cite:17][cite:18] |
| Open WebUI | 自托管 Web 平台 | 多用户 AI 平台 | 实时语音、VRM 形象、技能版本化 [cite:19][cite:20] |

定位上可分两轴：**本地自主 ↔ 云端托管**、**通用工作台 ↔ 专项运行时**。我们与 AnythingLLM、Cherry Studio、OpenClaw 同处「本地 + 通用工作台」象限；Cowork 在「云端 + 通用 Agent」；LM Studio 在「本地 + 模型运行时」；Open WebUI 在「自托管 + 多用户平台」。

## 4. 值得借鉴的十个点

排序依据：与我们路线的契合度、对用户体验的增量、实现风险。

| # | 借鉴点 | 来源 | 我们现状 | 借鉴方式 | 优先级 |
|---|---|---|---|---|---|
| 1 | **Agent 五档权限模式**：每次确认 / 自动接受编辑 / 智能审批 / 仅计划 / 完全放行，并绑定工作目录 [cite:9] | Cherry Studio | 桌面 Agent 只有逐步审批 | 给桌面 Agent 与能力包 effect 引入统一权限档位；默认「每次确认」，无人值守才放宽 | P0 |
| 2 | **策略即代码 + deny wins + 审批绑定**：工具策略按名称过滤，审批绑定命令、cwd、环境哈希与文件操作数，无审批入口默认拒绝 [cite:5] | OpenClaw | 审批是一次性确认，不绑定具体操作 | 把「本次允许」升级为「允许这一条命令/这一组文件」；策略文件可导出、可审计 | P0 |
| 3 | **隔离执行**：沙箱默认无网络、只读根、非 root；沙箱运行时禁止单次逃逸到宿主 [cite:6] | OpenClaw / Goose | Electron 沙箱 + 桌面 Agent 直操宿主 | 为网页类任务提供独立浏览器会话（独立登录态），不碰用户主浏览器 | P0 |
| 4 | **定时 Agent 任务 + 运行历史 + 通知目标**：触发条件 → Agent 执行 → 通知渠道 → 运行记录 [cite:11] | Cherry Studio / Cowork | 有事件与提醒，没有「无人值守跑一次 Agent」 | 复用现有任务与事件底座，增加「任务 + 频率 + 复用会话 + 结果通知」 | P0 |
| 5 | **技能/工具版本化 + Set as Production**：每次保存留版本，回滚前校验依赖仍存在 [cite:19] | Open WebUI | 能力包可升级回滚；技能/工具本身无历史 | 把能力包的升级状态机下沉到「技能/工作流/卡片」级；回滚前做依赖可用性校验 | P1 |
| 6 | **技能包多文件与来源导入**：SKILL.md + 脚本/引用/模板，ZIP/JSON、GitHub 链接导入 [cite:12][cite:19] | Open WebUI / Cherry | 能力包已支持 payload 文件与 ZIP | 扩展清单表达能力：文件树、脚本声明、来源标注；仍坚持本地签名与信任库 | P1 |
| 7 | **便携 Recipes / 子 Agent**：工作流存为可分享 YAML，子 Agent 并行处理子任务 [cite:15] | Goose / Cowork | Flow Studio 有 DAG 与版本；会议有角色协作 | 增加「工作流/Agent 配方」导出导入；把长任务拆给临时子 Agent，主会话保持干净 | P1 |
| 8 | **实时语音 + 形象三态**：实时语音模型负责对话，工具审批回到聊天；形象有 Idle/Listening/Speaking 与命名手势 [cite:19] | Open WebUI | PTT/VAD + TTS；VRM 有动作但无通话态机 | 引入实时语音会话（可打断）与形象三态；手势由语音模型按描述选择 | P1 |
| 9 | **全局快捷助手 / 划词**：全局快捷键提问；任意应用划词后浮动工具条 [cite:8] | Cherry Studio / AnythingLLM | 有命令面板，无系统级划词 | 桌面壳增加全局快捷键与划词入口，复用现有对话与工具链 | P2 |
| 10 | **无头守护 + 有状态 API + 权限密钥**：核心与 GUI 分离，`/v1/chat` 支持 `previous_response_id` 与 MCP [cite:17] | LM Studio | 有 Flow Serving 与 MCP Server，但依赖桌面进程 | 评估「无头模式」作为进阶部署形态，先做权限密钥与有状态会话 | P2 |

补充观察（不进前十，但值得记录）：

- **MCP 已成为事实标准**：AnythingLLM、Cherry、Goose、LM Studio、Open WebUI 都支持 MCP；生态整合比自建连接器更重要 [cite:13][cite:15][cite:18][cite:20]。
- **插件包形态趋同**：Cowork 把 skills、connectors、sub-agents 打成一个插件包 [cite:1]；我们的能力包已经在做同一件事，差别在「生态来源」与「版本治理」。
- **多窗口/分屏**：Cherry 2.0 与 LM Studio 都提供分屏或多窗口 [cite:17][cite:21]，对「一边对话一边看运行」有直接价值。
- **会议与听写**：AnythingLLM 把会议转写、说话人标注与系统级听写做进同一个应用 [cite:13]；我们的会议能力目前偏多智能体讨论，不是真实会议记录。

## 5. 不建议照搬的部分

1. **远程技能市场与一键安装**：Cowork、Cherry、Open WebUI 都有在线技能来源；我们坚持「本地能力包 + 签名 + 信任库」，不引入远程市场，避免把供应链风险带进来。
2. **多用户 SaaS 化**：OpenClaw 的团队与身份体系、Open WebUI 的多用户与 MFA，服务的是团队部署；我们的宪法是单机单用户，不为此改造数据模型。
3. **云端执行与云 Worker**：Cowork 的跨设备续跑、OpenClaw 的云 Worker 都依赖云端；本地优先版本不做默认云端执行。
4. **包内任意代码执行**：技能可以带脚本，但「能不能执行」应由权限模式与沙箱决定；不把「安装即执行」作为默认行为。
5. **自动依赖安装**：依赖仍是显式前置，缺依赖就拒绝，不做传递闭包与自动安装。

## 6. 对 v2.13 的主题建议

### 候选 A：可治理的 Agent（推荐）

**一句话**：v2.12 让能力包可信，v2.13 让 Agent 的每一次执行都可授权、可约束、可审计。

- 范围：五档权限模式 + 工作目录；策略即代码（工具白名单/黑名单，deny wins）；审批绑定具体操作；独立浏览器会话；执行审计账本；定时 Agent 任务 + 运行历史。
- 承接关系：直接复用 v2.12 的签名、健康与升级底座；不新增云端依赖。
- 风险：中。主要是权限语义与桌面 Agent 的既有审批路径需要统一，工作量集中在 core 与 UI。
- 差异化：竞品里只有 OpenClaw/Goose 把「策略、沙箱、审计」做成系统能力；本地桌面 + 陪伴属性 + 可治理执行，是空位。

### 候选 B：随叫随到（渠道）

**一句话**：让 Agent 从桌面扩展到飞书/微信/Telegram，人不在电脑前也能派活与收结果。

- 范围：IM 渠道接入、来源白名单、渠道级权限、定时任务结果回投、会话与桌面端同步。
- 价值：差异化最大，直接对标 OpenClaw/Cherry 的增长点。
- 风险：高。引入网络暴露、凭证管理、身份与多用户语义，可能触碰「仅回环、单用户」的宪法；需要先做安全设计再排期。

### 候选 C：能力生态 II（版本化与配方）

**一句话**：把能力包从「可装卸」推进到「可版本化、可组合、可迁移」。

- 范围：技能/工作流/卡片级版本历史与回滚；多文件技能包；Recipes 导出导入；子 Agent 并行。
- 价值：延续 v2.10–v2.12 的能力包主线，工程量可控。
- 风险：低到中。主要风险是「版本历史」带来的数据模型增量，与零迁移偏好冲突。

**建议**：v2.13 选 **候选 A**，把「可治理」做成版本主题；候选 B 先做安全预研与最小 PoC，不进入本版；候选 C 中「技能版本化」可作为 A 的配套子项（与能力包升级共用状态机）。
