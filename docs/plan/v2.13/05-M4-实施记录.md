## 2. 触发与投递口径

1. **服务端只接管 `agent_task`**：每 10s 扫描到期项 → `markFired` → `startScheduledAgentTask`。
2. **渲染进程只接管提醒 / `follow_up`**：`/api/schedules/due` 过滤 `agent_task`，双端不会抢同一条的标记。
3. 服务端 tick 同时执行关系等级检查点与共同里程碑扫描，行为与旧 `/due` 一致。
4. 先标记后投递：错过即跳过，不补跑；同一任务同一时刻只触发一次。
5. 启动前复核：`full_access` 永不允许；`policy.unattended.allowedModes` 可在运行前收紧并生效。
6. 同一任务已有 `queued/running/paused` 运行 → `SKIPPED_ACTIVE_RUN`；并发 ≥ `maxConcurrentRuns` → `MAX_CONCURRENT_RUNS`；均写 `unattended_blocked`。
7. 创建运行后立即 `taskRunner.start` 后台启动，不依赖 SSE 观察者；终态由任务运行服务写 `scheduled_run_finished`。
8. 请求审批时进入审批中心挂起；5 分钟超时由既有确认链路按拒绝收敛。

## 3. 运行时限额（M2 遗留收口）

| 限额 | 实现 |
|---|---|
| 步数 | 创建运行时 `min(payload.maxSteps, TASK_MAX_STEPS, policy.limits.maxSteps)`，任务循环既有 `max_steps` |
| 时长 | 每轮循环检查 `createdAt + maxRuntimeMs`，超限 → `stopped/policy_limit` |
| 写入 | 工具执行前按 `permission='write'` 累计，超限 → `policy_limit` |
| 外部调用 | `source='mcp'` 或 `fetch_webpage` 累计，超限 → `policy_limit` |

限额只在本次运行内存累计；步数上限仍以 `task_runs.max_steps` 为唯一持久事实。

## 4. API / UI

- `POST /api/schedules` 接受 `payload.kind='agent_task'`；非法模式返回 422 `UNATTENDED_MODE_NOT_ALLOWED`；无视觉模型返回 422 `VISION_MODEL_REQUIRED`。
- `PATCH /api/schedules/:id` 禁止 payload 类型切换（422 `SCHEDULE_PAYLOAD_KIND_IMMUTABLE`）；同类可改目标 / 会话 / 模式 / 目录 / 通知。
- 设置页提醒面板：新建时可切换「提醒 / Agent 任务」；编辑时类型锁定并显示提示；列表展示 `Agent` 标记。

## 6. 已知边界

- 调度只在应用进程存活时运行；不做开机自启、系统服务、云调度与失败重试 / 补跑。
- 窗口全关时无人处理审批，超时按拒绝；WorkSignal 是可靠通知，桌面通知尽力而为。
- `notify='desktop'` 复用既有工作信号提示（失败弹系统通知、成功提示音）；本版不新增独立通知队列。
- 服务端调度在首次 `getServices()` 时启动（Next 懒初始化），不是进程启动瞬间；首个请求后即进入 10s 节拍。
- 运行时长从 `task_run.createdAt` 起算；长时间排队的手动任务会更快触发时长限额。
- 外部调用限额按工具来源粗分（MCP / `fetch_webpage`）；浏览器工具在 M5 接线后纳入同一计数。
