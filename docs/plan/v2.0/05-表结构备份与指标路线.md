## 2. v029 迁移（纯加法，IF NOT EXISTS 幂等）

### 2.1 relationship_milestones

里程碑**定义在代码**（core 常量数组，可随版本增加，不做用户编辑 UI——纪念日历 P1 才做自定义）；表只存「某助手 × 某里程碑」的达成记录，防重复触发。

```sql
CREATE TABLE IF NOT EXISTS relationship_milestones (
  id           TEXT PRIMARY KEY,
  assistant_id TEXT NOT NULL REFERENCES assistants(id) ON DELETE CASCADE,
  milestone_key TEXT NOT NULL,          -- 代码常量，如 'day_100'/'collab_10'/'first_kb'
  achieved_at  TEXT NOT NULL,           -- ISO
  payload_json TEXT NOT NULL DEFAULT '{}' -- 轻量上下文（如当时触发的剧本 id），不存对话原文
);
-- 同一助手同一里程碑只达成一次
CREATE UNIQUE INDEX IF NOT EXISTS idx_milestone_unique
  ON relationship_milestones(assistant_id, milestone_key);
```

首版内置 key（M2 实现时按此冻结，数值可评审调）：

| key | 达成条件（只读统计，不新埋执行链路） |
|---|---|
| `day_1` / `day_30` / `day_100` / `day_365` | 距助手首次正向互动自然日数（首次互动时间从 emotion_events 最早一条推算，不额外建字段） |
| `collab_10` / `collab_50` | 该助手参与且 done 的 agent_runs 数（只读统计，M2 定稿表名口径） |
| `first_kb` | 用户创建第 1 个知识库（全局里程碑，assistant_id 取当时主助手——M2 若语义牵强可砍此项，保守冻结前四个日类+两个协作类） |

### 2.2 mod_installs

```sql
CREATE TABLE IF NOT EXISTS mod_installs (
  id            TEXT PRIMARY KEY,
  pack_id       TEXT NOT NULL,           -- manifest.pack.id
  name          TEXT NOT NULL,
  pack_version  TEXT NOT NULL,
  author_name   TEXT,
  imported_at   TEXT NOT NULL,
  summary_json  TEXT NOT NULL            -- 各类型导入条目 id 清单（供卸载/排查，不做级联删除内容）
);
CREATE INDEX IF NOT EXISTS idx_mod_installs_pack ON mod_installs(pack_id);
```

- 卸载包**不级联删除**已导入内容（内容导入后即独立本机数据，删除只清记录；防误删用户二次编辑过的卡/剧本）。
- 重复导入同一 pack_id：登记第二条记录（带时间），内容冲突按 04 §5 副本策略落新 id。

### 2.3 仓储与测试纪律

### 3.2 文件与恢复顺序（events 轨事务内）

沿用 v1.9 v5 恢复顺序后追加：assistants → cards → schedules → usage → triggers → stageScenes → meetings → **relationshipMilestones → modInstalls**。

- 两负载均 `INSERT OR IGNORE` 幂等；
- 里程碑恢复：assistant 已存在才导入（外键拒绝即跳过并计数）；
- modInstalls 只是历史记录，无外键依赖（pack_id/name 文本），任何库可恢复；
- v5 及更早归档缺文件按 0 降级（沿用 v5 对 stageScenes/meetings 的模式）；
- precheck schema 同步加两个必填计数（v5 教训：precheck tracks 字段是 required，漏填会 zod 500）。

### 3.3 情绪轨的版本兼容

- emotion 轨存的是**完整 state_json**：v6 恢复时对 schemaVersion=1 的旧状态读侧惰性补 relationship 默认块（恢复不强制改写，首次写入时迁移）；
- emotion_events 含未知 type（旧档恢复到更新版本反向场景）：宽松保留（TEXT 不校验枚举）。

## 4. 「重新认识」（选择性重置）

与全量重置/备份恢复严格区分的**第三类操作**：

| 数据 | 重新认识 | 全量重置 |
|---|---|---|
| assistant_emotion_states（情绪/关系/等级地板/counters） | **清空** | 清空 |
| emotion_events 流水（含 level_up/down） | **清空** | 清空 |
| relationship_milestones | **清空** | 清空 |
| 记忆（memories，v0.5） | **保留** | 清空 |
| 对话/消息 | **保留** | 清空 |
| 助手/角色卡/主题/设置/知识库/会议/舞台场景 | 保留 | 清空 |

- 语义：「忘掉我们的关系与情绪历史，但记得你告诉过我的事实与经历」；
- 实现：一个 service 方法（删三表/状态行，单事务），设置页二级确认（输入「重新认识」确认或同等强度，避免误触）；
- **备份恢复不触发重置**，两者互不自动调用；重置操作写本地审计日志（settings/audit，不进情绪流水）；
- M3/M4 接线；M0 冻结数据边界与文案（文案避免「删除/清空」冷感，用「重新认识」并明示保留记忆）。

## 5. 指标路线（G7 本地读数，无埋点）

**M0 决策：不新建埋点表**。全部指标从既有表做 read-model 聚合（纯函数 + 单测，M1 顺等级功能落地，M3 面板只读呈现）。

| 指标（路线图 §4） | 数据源 | 聚合口径 |
|---|---|---|
| 连续使用天数 | emotion_events（或 messages，M1 定稿，倾向 emotion_events 零正向也有 chat 事件） | 按本地日 distinct count，当前连续段 |
| 关系等级分布 | assistant_emotion_states.state_json | displayLevel 分桶（0/1/2/3 × 助手数） |
| 解锁项触达 | emotion_events type=level_up | 各等级达成助手数/去重计数 |
| 升级耗时（辅助） | level_up/down 事件对 | 相邻升级间隔中位数（报告素材，不做 UI 焦虑展示） |
| 打扰率（负向北极星，v1.7 续） | event_usage outcome/reason | admitted vs suppressed（quiet_hours/cooldown/max_per_day）+ 10 分钟回应率（v1.7 既有口径复核） |
| 舞台使用（v1.9 续） | 现有统计 | 协作开台比例、会议场次/平均轮次 |
| 关系事件量 | emotion_events 四 soulEvent + level_* | 日桶序列，供 G4 关系曲线 |

- 聚合器位置：`core/emotion/relationship-report.ts`（纯函数，入参行数组，出参 JSON），不连 DB；M4 G4 报告生成器直接消费。
- 首读接受「eval + 真机人工读数」（路线图允许），M5 给出一份本地只读快照作为 G7 证据；全部本地、零网络请求（单测断言）。
