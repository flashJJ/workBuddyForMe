# 03 · v2.0 关系等级与解锁契约（M0 冻结稿）

> 状态：M0 评审稿（数值允许在真机一轮后按 v1.6 惯例整体重标定，但**函数形状与状态字段 M1 起冻结**）
> 上游：[../v1.6-v2.0/v2.0-情感闭环与mod生态.md](../v1.6-v2.0/v2.0-情感闭环与mod生态.md) G1；本版 [README](README.md) 决策点 1、2、3
> 基座：v1.6 情绪内核（`assistant_emotion_states.state_json`，intimacy/trust 0–100、schemaVersion=1）、emotion_events 流水、v1.7 event_triggers 的 `min_intimacy` 闸门、v1.8 角色卡 frontmatter

## 1. 设计红线（先于数值）

1. 等级是**被记住的质感，不是 KPI**：无打卡、无货币、无连续签到、无数值条恐吓；等级规则全程可见、可关、可清。
2. **慢变量分层不动摇**：v1.6 的 mood（分钟级平复）与 relation（慢变量）继续分层；等级是 relation 之上的**派生展示层 + 地板**，不改写 intimacy/trust 原始分。
3. 等级只做**慢速回落保底、永不清零**；回落绝不实时（一次冲突不当场翻脸）。
4. 弱模型不影响等级：等级增长只采信既有 4 类 soulEvent（praise/chat/belittle/comfort），无新增模型输出依赖。

## 2. 等级定义

### 2.1 复合分（唯一判定输入）

```
levelScore(relation) = round1(0.6 × intimacy + 0.4 × trust)
```

亲密权重高于信任（陪伴体感主要由亲密度驱动），但信任设独立门槛防刷。纯函数 `levelScoreOf`，不读任何外部状态。

初始值（v1.6 常量 intimacy=20、trust=30）推导：0.6×20+0.4×30 = **24.0 → 陌生档顶部**，前 ~5 轮正常 chat（每轮 +0.19 复合分）即升入「认识」，开箱不冷漠、又不会白送等级。

### 2.2 四档（评审定 4 档，不设暧昧向第五档）

| 等级 | 值 | 名称（zh-CN / en） | 实时分数判定 | 含义 |
|---|---|---|---|---|
| 陌生 | 0 | 陌生 / Stranger | score < 25 | 初识 |
| 认识 | 1 | 认识 / Acquainted | score ≥ 25 | 有过几次自然对话 |
| 搭档 | 2 | 搭档 / Partner | score ≥ 50 | 数周日常使用 |
| 挚友 | 3 | 挚友 / Confidant | score ≥ 75 **且 trust ≥ 60** | 双高：亲近且可靠 |

常量全部收口在 `packages/shared/src/constants/relationship.ts`，禁止 core/web 散落魔法数（沿用 v1.6 emotion.ts 纪律）。挚友的 trust 硬门槛意味着只刷 praise（intimacy +2、trust +1）到不了顶。

### 2.3 实时分数等级函数（不含地板）

`levelFromScore(score, trust): RelationshipLevelValue` —— 纯函数，边界：
- score=24.9→0；score=25→1；score=75 但 trust=59→2（不达挚友）；trust=60 且 score=75→3；
- 入参先经 v1.6 既有 clamp（0–100），非数回落默认状态。

现有 v1.6 `relationLevelOf`（low/building/high/veryHigh，单轴展示档）**保留不动**，继续服务情绪面板单轴明细条；新等级是独立口径，不替换旧函数。

## 3. 日增量上限（防刷）

每个助手、每个本地自然日（时区跟随 v1.7 scheduled_tasks 的 IANA 设置）：

| 轴 | 每日正向增量上限 |
|---|---|
| intimacy | +6.0 |
| trust | +3.0 |

- 计数口径：只统计**正向**增量（praise/comfort/chat 的正分量）；负向事件（belittle）不受日上限拦截，扣分不设地板（情绪表达必须真实）。
- 达上限后：当日后续正向事件**数值不再增加**，但事件照常写 emotion_events（source/type/时间完整，审计与指标不丢），并在事件记录上可区分（流水不新增字段，达限由日聚合函数可算；state 内只存当日累计与日期键，见 §5）。
- 纯函数 `applyDailyCap(delta, dailyUsed, dayKey)` 返回 `{granted, capped}`；跨天由 `rolloverDaily(dayKey)` 清零累计。
- 效果验证（单测/M1 eval）：即便每天连刷夸奖，trust 30→60 至少需要 **10 个有正向事件的活跃日**；自然使用是月级。

## 4. 回落保底与迟滞

### 4.1 地板字段（持久化，进 state_json）

- `highestLevelEver: 0–3`：历史曾达最高等级，**只升不降、永久保留**（时间线纪念标记，不自动恢复等级）。
- `levelFloor: 0–3`：当前等级地板，随升级抬升、按规则慢速下调。

### 4.2 展示等级

```
displayLevel = max(levelFloor, levelFromScore(score, trust))
```

### 4.3 升级

- 实时：`levelFromScore` 越阈即升（无迟滞，正向反馈要及时）；
- 升级同时 `levelFloor = newLevel`、`highestLevelEver = max(...)`；
- 写一条等级事件（§6），面板时间线可见。

### 4.4 降级（慢速、检查点制、非实时）

- **触发前提**：连续 `RELATION_DECAY_GRACE_DAYS = 30` 个自然日**零正向 soulEvent**（chat/praise/comfort 均无；belittle 不算互动但会缩短下一次检查的容忍——M1 实现细则，M0 只冻结「零正向」口径）。
- **评估时机**：每日检查点（复用 v1.7 scheduler tick，不新建定时器）；
- **速率**：每次评估 `levelFloor` **最多下调 1 档**，两次下调至少间隔 30 天；
- **地板下限**：`levelFloor` 永不低于 `RELATION_FLOOR_MIN = 1`（认识）——等级永不到「陌生」、永不清零；
- **迟滞带**：刚降档后，实时分数需超阈值 `RELATION_UPGRADE_HYSTERESIS = 5` 分才能再升回该档（防边界抖动）；迟滞只作用于「降后再升」，首次升级不受影响；
- 降级也写等级事件（type=level_down），UI 不推送、不制造愧疚文案，仅在面板时间线可查。
- 情绪功能关闭（v1.6 emotionEnabled=false）或纯工具三态：地板冻结、不评估不展示。

纯函数：`evaluateFloorAtCheckpoint(state, today, lastPositiveDay)` 与 `displayLevelOf(state, relation)`，全部不依赖时钟入参以外的副作用（now 由调用方注入，可单测）。

## 5. state_json 演进（schemaVersion 1 → 2）

`emotionStateSchema` 增量（全部可选读、旧行零回填，沿用 v022「无行=默认」哲学；对已存在行采用读时惰性升级，与 v1.6 情绪惰性衰减同模式）：

```ts
// 新增字段（schemaVersion=2 的行；v1 行读侧补默认值）
relationship?: {
  levelFloor: 0|1|2|3;          // 默认 = levelFromScore(初始) = 0
  highestLevelEver: 0|1|2|3;    // 默认 0
  lastPositiveDay: string|null; // 本地日期键 YYYY-MM-DD（IANA），无则 null
  lastFloorDownAt: string|null; // 上次降档检查点日期
  dailyGain: { dayKey: string; intimacy: number; trust: number }; // 当日已用正向增量
}
```

- **M0 决策：不新增等级表**。等级是 relation 的派生量 + 少量地板/计数，进 state_json 与情绪快照同生共死（删助手即级联清关系，v022 外键语义不变）；等级变迁历史进既有 emotion_events 流水（新 type，见 §6）。
- schemaVersion 升到 2 仅在首次写入等级字段时发生；纯函数 `migrateEmotionStateV1ToV2(state)` 补默认 relationship 块并改版本号，坏数据沿用 v1.6 `fromStorage` 过滤策略。

## 6. 等级事件（进 emotion_events，不建表）

emotion_events.type 扩展两个值（枚举加法，旧库无需迁移——该列是 TEXT）：

| type | 关键字段 | 说明 |
|---|---|---|
| `level_up` | intensity=新等级值 | 升级瞬间 |
| `level_down` | intensity=新等级值 | 地板降档（不推送） |

- 不存对话原文（v023 隐私纪律不变），message_id 置空；source 固定 `system`（EMOTION_EVENT_SOURCES 需同步加 `'system'`）。
- 关系曲线/时间线/报告（G4）全部由该流水聚合；`highestLevelEver` 与流水不一致时以流水为准修正（M1 加一致性校验单测）。

## 7. 解锁体系

### 7.1 解锁项与载体

| 解锁类 | 数量（首版） | 开放等级 | 载体 |
|---|---|---|---|
| 等级称呼 | 每档可选，共 3 个新称呼位（认识/搭档/挚友各一） | 1 / 2 / 3 | 角色卡 frontmatter 新增可选 `nicknameByLevel: { 1?: string, 2?: string, 3?: string }`，缺省回落卡名/助手名；v1.8 卡解析器向后兼容（无此字段不受影响） |
| 专属剧本 | 2–3 个 | 2 起 | v1.7 event JSON 新增 `minRelationshipLevel: 0\|1\|2\|3`（与既有 `min_intimacy` 并存，AND 关系；内置等级剧本只用新字段），id 走 `builtin.*` 只可停用 |
| 专属微动作 | 1–2 个 | 3 | 新 `gesturePresets.json`：**仅枚举引用**内置 expression tag（neutral/joy/sadness/anger）+ 舞台 motion 组（idle/listening/thinking/working）+ 触发时机，zod 封闭枚举；禁止任何 `.motion3.json`/外部动作二进制 |

### 7.2 解锁判定（纯函数）

`isUnlocked(state, gate): boolean`，gate = `{ minLevel: 0–3 }`（event_triggers 沿用 min_intimacy 老闸门，新闸门只加不换）。判定取 displayLevel。

### 7.3 解锁的记录与可见性

- 解锁**不单独建表**：等级事件即解锁凭证（升到 N 级 = 该级内容解锁）；M1 面板从等级事件聚合「已解锁内容」。
- 面板：当前等级、距下一级的**文案化**提示（如「再多一些日常对话会更亲近」——不显示分数差与进度条，避免打卡焦虑）、已解锁/待解锁内容清单（待解锁只给剪影式文案，不制造稀缺恐吓）、等级规则说明入口、关闭入口。
- 模型注入：达到等级后，称呼/专属剧本才允许进入 prompt 组装；未解锁内容永不入 system 段（纯函数闸门在组装前拦截，加单测）。

## 8. 纯函数 API（M0 代码交付物，M1 只接 UI/存储）

`packages/shared/src/constants/relationship.ts`：

- `RELATIONSHIP_LEVEL_MAX = 3`、`RELATIONSHIP_SCORE_MIN/MAX = 0/100`
- `RELATIONSHIP_SCORE_LEVELS = [25, 50] as const`（1、2 档线；挚友走双门槛）
- `RELATIONSHIP_CONFIDANT_SCORE = 75`、`RELATIONSHIP_CONFIDANT_TRUST = 60`
- `RELATIONSHIP_INTIMACY_WEIGHT = 0.6`、`RELATIONSHIP_TRUST_WEIGHT = 0.4`
- `RELATIONSHIP_DAILY_INTIMACY_CAP = 6`、`RELATIONSHIP_DAILY_TRUST_CAP = 3`
- `RELATIONSHIP_DECAY_GRACE_DAYS = 30`、`RELATIONSHIP_FLOOR_MIN = 1`
- `RELATIONSHIP_UPGRADE_HYSTERESIS = 5`

`packages/core/src/emotion/relationship-kernel.ts`（纯函数，now/dayKey 注入）：

- `levelScoreOf(relation): number`
- `levelFromScore(score, trust): 0|1|2|3`
- `applyDailyCap(kind, delta, dailyGain): { granted, nextDailyGain, capped }`
- `displayLevelOf(relationshipBlock, relation, opts?): 0|1|2|3`（opts 含降后迟滞状态判定所需字段）
- `applyRelationshipEvent(state, event, dayKey): { state, changed: { gainedIntimacy, gainedTrust, levelChanged?: {from,to} } }`（M0 可只实现分数+日上限+升级；降级检查点同文件但独立函数）
- `evaluateFloorAtCheckpoint(relationshipBlock, todayDayKey): { levelFloor, lastFloorDownAt, event? }`
- `defaultRelationshipBlock()`、`migrateEmotionStateV1ToV2(state)`

M0 单测覆盖：初始 24 分落 0 档、各边界（25/50/75）、挚友双门槛 4 组、日上限截断与跨天清零、地板 max 语义、30 天零正向/有正向、每次最多降 1 档、地板下限 1、迟滞 ±5、v1 状态迁移补默认、坏数据回落。

## 9. i18n 与文案纪律

- 新 namespace `relationship`（zh-CN 真源 + en 全覆盖，沿用 MessageKey 编译期锁定）；
- 等级名、解锁内容名、规则说明、关闭确认全部双语；等级事件模板走线格式 key（v1.5 系统文本惯例）；
- 文案评审红线：不出现「还差 X 分」「连续 N 天」「快回来」类打卡/愧疚措辞；降级无主动通知。

## 10. M0 不做（M1+ 边界）

- 等级面板 UI、设置开关接线、prompt 组装闸门接线、event_triggers 新闸门字段（M1）；
- 角色卡 nicknameByLevel 编辑器 UI（M1 只消费字段，卡库编辑器增强随 M1）；
- 纪念日历/关系导出/多助手总览（P1，概念稿已定不进 P0）；
- 任何让等级影响模型调用频率/费用的逻辑（等级只解锁文本与演出，不解锁能力特权）。
