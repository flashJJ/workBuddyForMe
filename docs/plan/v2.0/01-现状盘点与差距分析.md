# v2.0 现状盘点与差距分析（规划草案附件）

> 盘点基准：`main` `7fb5b50`（v1.9.0 已发布）。本文只陈述代码现状与差距，
> 不含最终契约——阈值、manifest、表结构以 M0 冻结分册为准。

## 1. 关系养成（G1）现状与差距

### 1.1 已有（v1.6，勿重写）

- `assistant_emotion_states`（v022）：每助手一行，`state_json` 内含
  mood（happiness/anger/sadness）、relation（**intimacy 初值 20、trust 初值 30，值域 0–100**）、
  need、counters、recentEvents（近 10 条）、schemaVersion=1；读侧惰性衰减，无行=默认态。
- 数值契约集中在 [shared/constants/emotion.ts](../../../packages/shared/src/constants/emotion.ts)：
  事件增量（praise/chat/belittle/comfort）、情绪分钟衰减因子、
  **关系分级阈值已存在**（building 30 / high 55 / veryHigh 80），但只有数字档。
- `emotion_events`（v023）：不可变追加流水，只存 type/source/emotion/intensity/message_id/时间，
  **不存对话原文**——天然是关系曲线与年度回顾的数据源。
- 情绪面板（v1.6）已可读数值/来源，可重置、可关情绪。

### 1.2 差距（v2.0 M1 要补）

| 差距 | 说明 | 倾向方案（待 M0 拍板） |
|---|---|---|
| 无等级命名与解锁 | 30/55/80 三档没有用户可感知的名字，也不解锁任何内容 | 等级映射纯函数（双门槛组合），常量仍收口在 emotion.ts 或新 relationship 常量文件 |
| 无回落保底 | 现状 intimacy/trust 只有情绪平复逻辑，关系慢变量的长期不互动回落未定义 | 等级降档不清零、保底档、N 天零互动才启动、周级速率 |
| 无防刷日上限 | praise 每次 +2/+1 亲密与信任，连刷可冲值 | 每助手按自然日增量封顶 + 事件来源全记录；纯函数单测 |
| 解锁内容无载体 | 等级称呼、专属剧本、微动作无处声明/判定 | 解锁记录表；角色卡 frontmatter 可声明等级称呼（扩卡 schema，向后兼容）；剧本用 minIntimacy 类闸门（event_triggers 已有 min_intimacy 先例） |
| 等级事件不可见 | 升级/降级瞬间无记录 | 等级事件写 emotion_events 新 type（或独立 relationship_events，M0 定），面板时间线可读 |

## 2. 记忆 × 情绪联动（G2）现状与差距

### 2.1 已有

- 记忆类型 `MEMORY_KINDS = ['fact','preference','event']`（shared/types/domain.ts）；
  提取器 prompt 已按三类引导（身份事实/偏好约定/重要事件），有 zod 校验与每轮 ≤5 条上限。
- 召回走 v1.3 RRF(k=60) 双路融合 + 向量软阈值，台词引用有来源列表机制。
- 会话压缩摘要以 `event` 类入库（固定 importance 0.6）；软删除/遗忘（30 天）链路完整。
- v1.7 剧本引擎（EventDirector/runner/8+ 内置剧本）与 schedules 调度可直接承载里程碑剧本。

### 2.2 差距

- **无 `relationship` 记忆类型**：「共同经历」目前只能勉强归入 event，
  提取 prompt 没有「共同完成/低谷时刻/专属约定」引导 → M2 加枚举值（加法，旧记忆不受影响）+ 提取 prompt 增量。
- 情绪/剧本台词生成目前不主动引用记忆 → M2 在剧本/情绪台词组装处注入关系记忆软引用，
  规则：模型没把握不提、引用必须可溯、用户删除后立即不再命中（复用现有删除一致性）。
- 无里程碑计数：首日/30/100/365 天、第 N 次协作成功、第 N 个知识库均无计数器
  → 本地 counters（state_json 已有 counters 位）或独立里程碑表，M0 定口径；
  协作成功数需从 agent_runs/task_runs 做只读统计，不新埋执行链路。

## 7. VRM 导入决策（G6，评审已定向：GO）

- 结论（2026-10-15 评审）：**VRM 可导入能力要做**——用户自有 VRM 形象是 VTuber/桌面陪伴生态的主流资产，不支持会削弱竞争力。完整论证见 [02 VRM 导入可行性调研报告](02-VRM导入可行性调研报告.md)。
- 关键事实：VRM 是基于 glTF 的开放格式（VRM Consortium），官方库 `@pixiv/three-vrm` 为 MIT（gzip 约 35 kB，three 本体 gzip 约 170 kB，可动态 import）；模型文件 meta **内嵌机器可读许可**（演绎者范围/商用/暴力/性/再分发 CC 类型），导入器可强制展示并由用户确认——责任框架与 VSeeFace/Warudo 一致；Animaze、3tene 已有同应用 Live2D+VRM 并存的商业先例。
- 与现有红线的关系：**红线不对称且必须在 UI 明示**——VRM 开放导入（开放格式+MIT），Live2D `.moc3` 外部模型导入继续永久禁止（Cubism 专有授权）。
- 产品形态收口：只做「导入器」——不内置模型、不做市场/下载/云传输；文件存 `data/vrm-avatars/`（60MB 上限、glTF 魔数+VRM 扩展双校验）；备份与 .wbfm-pack 只带引用不带二进制（延续 v1.9 背景图策略）。
- 工程缺口（M4 实现量）：three.js 第二渲染器与 PIXI canvas 双分层、cast 形象类型 `vrm:<id>`、口型（五元音简化为电平→aa）与四表情映射、导入向导与 meta 许可面板、舞台/桌宠两形态适配；web 新增 `three` + `@pixiv/three-vrm` 依赖（路由级动态 import，不进首屏）。
- 排期（2026-10-15 评审调整）：VRM 导入**收回 v2.0 内交付**。M0 做门控真机工装（8MB/60MB 样本的首帧/内存/混排帧率 + 负例校验链 + 免责声明定稿，阈值见 02 报告 §3.4），作为 M4 开工关卡；**M4 形象开放：VRM 导入**（双 canvas 分层/导入向导/许可面板/口型表情/舞台与桌宠），原收口工作（关系报告/.wbfm-pack/封版）顺延至 **M5**，里程碑扩为 M0–M5。关卡纪律：M0 不达标则 M4 砍除、M5 照常封版，大版本不被单一特性拖期。

## 8. 风险初判（概念稿 §5 的工程化细化）

1. **游戏化反噬**：等级 UI 必须过文案评审（无打卡焦虑措辞）；三态中「纯工具模式」
   等级相关 UI/触发全部不可见——e2e 断言。
2. **错误记忆尴尬引用**：软引用 + 可溯 + 删除一致性；关系记忆提取走弱模型 eval（7B 档），
   提取失败不阻塞主回合（v1.6 立规延续）。
3. **感知滑向监控**：触发源代码内枚举封闭、系统事件默认关、授权文案具体、原始信号不落盘。
4. **mod 红线绕过**：解包层魔数校验 + 伪装包 eval + 导入向导明示红线。
5. **范围爆炸**：VRM/外部事件只产出决策结论，做不成立刻砍；M3 末若指标/三态未达标，
   M4 先保 G1–G5 封版，G6 文档结论不占功能工期。
6. **现网阈值无数据**：M0 需要从开发机 `~/.workbuddy-for-me` 情绪数据做一次性分布抽样
   （只读脚本，不入库不外发），避免等级阈值拍脑袋；样本不足则在发布说明标注阈值为经验初值。
