# v2.2 M0 冻结稿：动作段、情绪档位与关系门槛契约

> 本稿冻结 v2.2 的**策略层契约**。生效得先满足一条口径：**策略通用 + 执行 VRM 优先**——这些字段与挑选规则两个渲染后端共用，但「谁提供候选集、谁负责播放」由各后端自行实现（见 [README.md](README.md) 第 2 节）。
>
> 代码锚点（均已在 M0 落地）：`packages/shared/src/schemas/motion-asset.ts`、`packages/database/src/migrations/v033-motion-segments.ts`、`packages/core/src/services/motion-service.ts`。

## 1. 契约总览

| 概念 | 取值 | 缺省 | 语义 |
|---|---|---|---|
| 动作段 `segment` | `single` / `a_start` / `b_loop` / `c_end` | `single` | 对齐开源桌宠模拟器 VPet 的 `AnimatType`：入场 / 循环 / 退场三段；`single` 表示整段既入场也是循环段 |
| 情绪档位 `mood` | `good` / `normal` / `low` | `normal` | 策略层维度，由情绪状态机推导；挑选时按「精确 → 更差档位 → 更好档位 → 任意」回退 |
| 动作条目键 `entryKey` | 1–80 字符 | 无（自成条目） | 同键的多个 clip 组成一个三段式动作 |
| 关系门槛 `minRelationshipLevel` | 0–3 整数 | 无（不设门槛） | 0 陌生 / 1 认识 / 2 搭档 / 3 挚友，与 `packages/shared/src/schemas/relationship.ts` 的数值口径一致 |

两条派生规则（写进契约，避免实现各自解释）：

1. **条目派生**：`entryKey` 相同的行属同一条目；`entryKey` 为空的行自成条目。
2. **条目属性取值**：条目的档位与关系门槛按段优先级 `b_loop → single → a_start → c_end` 取**第一条有值的行**（同键各行应写相同值，导入向导统一写入）；因此单段动作（`single`）的档位就是它自己的档位。

**为什么不强制拆段**：用户导入的 VRMA 就是一段循环动画，天然没有 A/B/C。契约把「缺段」定义为**按顺序退化**——缺 A 直接进 B、缺 C 直接回待机、整段只有 `single` 时它自己就是循环段。这样「三段式」是可选叠加能力，而不是导入门槛。

## 2. 数据层：v033（纯加法）

```sql
ALTER TABLE motion_assets ADD COLUMN entry_key TEXT;
ALTER TABLE motion_assets ADD COLUMN segment TEXT NOT NULL DEFAULT 'single';
ALTER TABLE motion_assets ADD COLUMN mood TEXT NOT NULL DEFAULT 'normal';
ALTER TABLE motion_assets ADD COLUMN min_relationship_level INTEGER;
```

- **旧行降级路径**：`single` + `normal` + 无门槛 = 「整段即循环段、任何档位都可播」，与 v2.1 行为完全一致，**不需要回填**。这条已在 `v033-motion-segments.test.ts` 里用「先造 v032 形状的表 + 写入旧行 → 再跑迁移」的方式断言。
- **必须可重复执行**：仓库的迁移测试用「全量迁移后回退 `user_version`」来模拟老库，同一个迁移会在已具备新列的库上再跑一次。因此 v033 逐列检查 `PRAGMA table_info` 后再 `ALTER`，表不存在时直接跳过。（M0 首次实现漏了这一点，13 个迁移测试文件当场红掉——这属于必须先踩明白的仓库约定。）
- 未新增索引：动作总量是个位数到几十条，按 `entry_key` 过滤在应用层做即可。

## 3. 读取规则：坏值不炸整条记录

`motion-service.ts` 的行映射对 `segment` / `mood` / `min_relationship_level` 一律走 schema `safeParse`，失败即回落缺省（`single` / `normal` / 无门槛）。理由与仓库既有「读兼容、写收敛」一致：库里出现词表外的值（老库被外部改坏、未来枚举收缩）应该退化成「这条动作照常可播」，而不是让整条动作读不出来。

写入侧的缺省由 `importMotion` 补齐（未传即缺省值），条目键会 trim 并截断到 80 字符。

## 4. 作用域：哪些字段两个后端都用

| 字段 | 落点 | Live2D | VRM |
|---|---|---|---|
| `mood` / `minRelationshipLevel` | 策略层（挑选候选集） | 可共用策略，但候选集需另做（motion group 分档） | 本版落地 |
| `segment` / `entryKey` | 执行层（播放调度） | 不适用：Cubism 一个 motion 自带 loop 与淡入淡出 | 本版落地（M1） |

## 6. M0 顺带发现的现状缺陷（v2.1 遗留）——**已于 M2 修复**

> 修复方式：关系等级真源改为主窗经 pet IPC 中继的展示等级（`displayLevelOf` → `relationship` 表现事件 → `PetRuntime.relationshipLevel` → `relationshipLevelName`），不再读 `settings` 上不存在的字段。

`apps/web/src/features/pet/pet-stage.tsx` 构造 Resolver 上下文时读的是 `settings.relationshipLevel`：

```ts
const relationshipLevel = (settings as any)?.relationshipLevel ?? 'stranger';
```

但应用设置里**并不存在** `relationshipLevel` 这个键——关系等级的真源是情绪状态里的 `relationship.levelFloor / highestEver`（数值 0–3，见 `packages/shared/src/schemas/relationship.ts`）。也就是说这条门控**恒为「陌生人」**，v2.1 管道里「陌生人不可长按头部、不可提起」的规则一直在生效，而「搭档以上才能提起」这条永远不会因为关系升级而放行。

这不是本版引入的问题，但它正好卡在 P0-2 的路径上：**状态驱动挑选必须拿到真实档位**。M2 落地时需要一并给出等级/情绪的真源接线（建议由主窗与服务端各提供一个只读入口，而不是继续读 `settings` 上的臆想字段）。
