## 1. 本版解决什么

v4.23 让流程摔了能爬起来，但流程仍只能被「人」或「外部请求」发起：

1. 手动试运行要人点；
2. 对话调用要有人提问；
3. HTTP / MCP 要外部系统先请求。

本地私人助手最典型的需求——每天早上整理资讯、每周五生成周报、每小时检查目录——都需要「按时间自己开始」。

本版不引入外部调度服务，用一张表 + 进程内调度器完成定时触发，并复用 v4.23 的恢复经验处理重启与并发。

## 3. 关键设计

### 3.1 cron 只做 5 字段

`分 时 日 月 周`，系统本地时区，不引入时区库：

- 支持 `*`、单值、`a-b`、`*/n`、`a-b/n`、逗号列表；
- 周字段 0 与 7 都是周日；
- 日与周都被限制时按标准 cron 语义「任一匹配」；
- 保存时校验并计算下次时间；5 年内无解直接拒绝。

### 3.2 一条流程一条定时

`workflow_schedules` 以 `workflow_id` 唯一约束，配置包含 cron、启用开关、入参与下次执行时间。调度只使用生产版本，与 API / MCP 一致。

### 3.3 原子认领 + 单飞

```text
tick：查到期 → 以旧 next_run_at 为条件推进下次时间
      → 推进成功者才创建运行
      → 同流程有在途运行则记录 skipped_busy
```

- 条件更新保证同一次触发不会被两个 tick 重复处理；
- 单飞不排队：上一次没跑完，这一次直接跳过并留痕；
- 创建失败（未发布、版本缺失）记录 `error`，不重试。

### 3.4 错过只补一次

应用关闭期间跨过多个执行点时，重启后的首个 tick 会把 `next_run_at` 从「当前时刻」重新计算，只补跑一次，不做逐次回放。

这是本地桌面场景的刻意取舍：用户需要的是「现在补上」，不是「把错过的十次全部补一遍」。

### 3.5 触发门控

定时触发视为非交互：

- 写 / 危险工具沿用无人值守门控，默认拒绝；
- 人工节点不会挂起，按拒绝处理；
- 运行事件不新增类型，`run_started.trigger = schedule`。

## 4. 验收不变量

1. cron 解析覆盖通配、列表、范围、步长与 dom/dow OR；
2. 到期调度在 tick 后创建 `trigger=schedule` 的运行；
3. 重启后到期项只补跑一次；
4. 同流程在途运行时跳过并记录 `skipped_busy`；
5. 禁用 / 删除后不再触发；
6. 未配置定时的流程行为与 v4.23 一致；
7. `pnpm check`、`pnpm verify:local` 与定向测试全绿。

## 5. 迁移与兼容

- v054 纯加法：新增 `workflow_schedules` 与到期索引，不动现有表；
- `LATEST_SCHEMA_VERSION` 53 → 54；备份/恢复沿用整库机制；
- 新表对旧版本无害，回退代码后定时不再触发，配置残留不影响运行；
- 不新增运行时依赖。

## 6. 验证结果

- cron 解析 11 条单测；
- 调度服务与调度器 9 条单测 + 1 条端到端集成；
- 仓储 5 条单测，覆盖率保持阈值以上；
- 迁移测试覆盖表、索引与唯一约束；
- 全量 `pnpm check` 与 `pnpm verify:local` 通过。

## 7. 后续方向

- webhook / 文件监听触发；
- 一个流程多个定时；
- 每定时独立时区；
- 错过多轮的逐次补齐；
- 分布式调度互斥。
