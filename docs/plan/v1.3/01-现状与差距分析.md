# v1.3 现状与差距分析：知识摄取—检索—引用全链路取证

> 方法：只以 main `9ff38c7`（v1.2.0）工作树源码为证据，逐文件读现有摄取、存储、检索、引用、备份、eval 链路。文中符号均可在仓库定位；行号取证于 2026-10-10。SQLite/FTS 行为结论来自本机用仓库 better-sqlite3 实跑（SQLite 3.53.2）。

---

## 1. 链路全景（v1.2 现状）

```
上传/剪藏
  └─ POST /api/knowledge-bases/[id]/documents
       └─ createIngestionPipeline.ingest()                 core/ingestion/ingestion-pipeline.ts
            ├─ extractDocumentText()（PDF/Office/网页/OCR） core/ingestion/extract-with-ocr.ts
            ├─ chunkText()（段落贪心，记 charStart/End）    core/ingestion/chunking.ts
            ├─ provider.embed()（批量向量）                 core/services/provider-adapter
            └─ ensureVectorTable + chunks + chunks_vec      database/repositories/chunk-repo.ts, vector.ts
对话
  └─ createRagRetriever()                                  core/retrieval/rag-retriever.ts
       └─ retrieval.retrieve() → embed → searchChunks(top4) core/retrieval/retrieval-service.ts
            └─ sqlite-vec L2（单位向量，等价余弦）          database/vector.ts
       └─ formatContextBlock() + toCitations()             core/retrieval/context-formatter.ts
```

**一句话概括**：单跳向量检索，top-4 原始 chunk 拼进系统提示词，引用粒度到「文档 + 片段序号」。无关键词通道、无重排、无静态知识、无页级坐标、无知识编译。

## 3. 存储现状

### 3.1 文档与分片表（v001）

- `documents`：id/kb_id/filename/file_type/byte_size/content_hash/status(pending|processing|indexed|partial|failed)/error_message/chunk_count/source/source_url/ocr_*/created_at/indexed_at。
- `document_chunks`：`id INTEGER PK AUTOINCREMENT`、document_id(FK CASCADE)、ordinal、content、char_start、char_end、created_at；索引仅 `idx_chunks_document`。
- 知识库 `knowledge_bases`：name/description/chunk_size(默认 500)/chunk_overlap(默认 80)；**无版本号、无编译配置字段**。

### 3.2 向量（sqlite-vec）

- 虚表 `chunks_vec USING vec0(embedding float[D])`，rowid = chunk.id；写入前 L2 归一化（单位向量下 L2 排序等价余弦），见 `vector.ts:1-7,73-84`。
- 检索 SQL 单条：`v.embedding MATCH ? AND k=? ORDER BY v.distance`，按知识库过滤（`vector.ts:106-123`）。

### 3.3 全文检索：**完全不存在**

全仓检索 `fts5|FTS5|bm25` **零命中**。型号、编号、错误码、人名这类「精确字面」问题只能靠向量语义近似——专有名词 embedding 不稳定时是直接短板。

### 3.4 本版需要的 SQLite 能力实测（better-sqlite3 链接 SQLite 3.53.2）

| 方案 | 实测结果 | 结论 |
|---|---|---|
| FTS5 `tokenize='trigram'` | 建表成功；中文 **≥3 字**查询命中（`混合检索`✓、`编译层`✓），**2 字词不中**（`混合`✗、`知识`✗） | 子串强、短术语弱 |
| FTS5 默认 unicode61（不处理） | 中文连续汉字被当一个 token，`知识` 查不到 | 不可用 |
| unicode61 + **写入时中文逐字插空格**（uni-gram），查询同样归一化 | `混合`✓、`编译层`✓、`WorkBuddy`✓ 全部命中 | **2 字词可命中、中英混合兼容**；代价是索引 token 数膨胀（每汉字一 token） |

→ M0 中文分词 spike 有了实测结论：采用 **unicode61 + CJK uni-gram 归一化**（保留英文/数字整词），不依赖 trigram；最终以 M0 基准表确认召回与索引体积。

## 4. 检索现状（核心差距）

| 维度 | 现状 | 证据 |
|---|---|---|
| 通道数 | 仅向量 1 路 | `retrieval-service.ts:36-45` |
| top-k | 固定常量 `DEFAULT_RETRIEVAL_TOP_K = 4` | `retrieval-service.ts:5` |
| 相似度阈值 | 无——哪怕距离很大也照单返回 4 条 | 同上，无 distance 过滤 |
| 重排 | 无 | 全仓无 rerank 概念 |
| 查询改写/扩展 | 无 | 直接用原始 query embed |
| 预算适配 | 注入侧有 token 预算装配（v1.1 压缩层），但**召回条数不自适应**：固定取 4 条再由 `fitContextBlock` 截断 | `context-formatter.ts:34-74` |
| 静态知识 | 无摘要/实体/关系层；每次问答都对同一批 chunk 重新 embed+排序 | 全仓无 compiled/entity 知识表 |
| 多知识库 | 助手只绑一个 kb，单库检索 | rag-retriever 仅用 `assistant.knowledgeBaseId` |

**可复用**：v1.1 的 token 估算/预算装配（`context-budget.ts`）、归一化向量约定、`resolveEmbeddingTarget()` 模型解析、知识库→chunk→vec 的 join SQL——混合检索只需在同一事务里加一路 FTS 召回并融合。

## 5. 引用现状

- 入模块：`[i] 来源：《文档名》片段 N\n正文`（`context-formatter.ts:10-12`）。
- 对 UI 的 `Citation`：`{ documentId, documentName, ordinal(在本次结果中的序号), snippet(160 字截断), sourceUrl? }`（`context-formatter.ts:77-87`；类型 `domain.ts:92-99`）。
- **无页码、无段落号、无字符区间透出**：chunk 表里已有的 charStart/charEnd 未进入 Citation；PDF 页码在提取时被 join 掉（§2）。
- 网页剪藏有 sourceUrl 可跳原文（v0.3），本地文档点击只能看到文档名+片段文本。

差距：回答中的事实无法定位到「哪份文档第几页/第几段」。

## 6. 备份/恢复与数据边界（不能破坏的契约）

- 备份**不含向量**：knowledge 轨只导出 KB 元数据、文档元数据与分片文本，注释明确「恢复后走 ingestion pipeline 重新嵌入」（`backup/export.ts:39,80-85`）。
- 结论：**编译产物（摘要/实体/关系）与 FTS 索引、向量同属可重建派生数据**，不进备份、恢复后重编译；v017 必须保证旧档恢复（无编译产物）不影响检索（回落 chunk-only）。

## 7. eval 与任务体系现状（可复用）

- eval 平台（v1.1）：`scripts/eval/lib/` 五件（http/sse-client/assertions/report/mock-seed）+ memory、tool-compact、proactive 三脚本与 golden JSON；报告 `{pass,reason}`，CLI 退出码可做门禁。
- **无 knowledge 域 golden**：现有 critical-path ⑤ 只有 1 条 RAG e2e（mock 资料问答含引用），无「精确字面问题」「语句级引用正确性」「关闭增强即退化」的批量断言。
- 后台任务体系已有 flow run-queue/事件与桌面任务可视化（v0.8/v0.9），知识编译的进度/取消/重试应复用既有任务/事件语义，不新建调度框架。

## 8. 差距汇总（对齐 G1–G8）

| 能力 | v1.2 现状 | v1.3 目标 |
|---|---|---|
| 全文检索 | 无 | FTS5（unicode61+中文 uni-gram）通道，与向量融合 |
| 召回 | 向量 top-4、无阈值 | 双路 RRF 融合、去重、距离阈值、预算自适应条数 |
| 重排 | 无 | 默认规则重排（纯函数）+ 可选本地 LLM 重排 |
| 知识编译 | 无 | 文档摘要 + 实体/关系产物（无模型基线 + 可选 LLM），编译优先检索 |
| 引用坐标 | 文档+片段序号 | PDF 页码/段落序号 + char 区间透出，UI 可定位 |
| 治理 | 仅有哈希/URL 去重底座 | 去重提示、冲突标记、文档替换增量重编译、旧世代退役 |
| 调度 | 摄取同步执行 | 编译后台任务（进度/取消/重试/上限/开关），失败不阻断 chunk 检索 |
| eval | 1 条 RAG e2e | knowledge golden set + 关闭增强的反向验证 |
| 双语 | i18n 框架就位，知识域 P1 硬编码中文 | 知识/编译相关新 UI 直接走 t()，并完成 P1 七域伴随翻译 |

## 9. 约束与不变量（设计必须遵守）

1. **单文件 ≤300 行、TS strict、纯函数核心可密集单测**（版本宪法）。
2. **零新增运行时重型依赖**：FTS5 随 SQLite 内置；better-sqlite3 已在用。
3. **派生索引不进备份、可安全重建**；v017 纯加法迁移，旧库升级后检索行为不回归（新通道默认开启但 chunk-only 仍可用）。
4. **本地优先**：编译默认无模型通道；LLM 增强显式开关、走用户已配置的供应商，不新增任何外发端点。
5. **向后兼容 Citation 契约**：新增坐标字段可选，旧消费端（分享导出/语音）不破坏。
