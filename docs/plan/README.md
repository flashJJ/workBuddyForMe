# Flow Studio —— 可视化工作流编排 · 新增功能方案总览

> 版本：v1（对应 workBuddyForMe v0.7.0 基线）
> 日期：2026-10-05
> 状态：待评审
> 借鉴对象：[langflow](https://github.com/langflow-ai/langflow) v1.12.4

---

## 1. 一句话方案

在 workBuddyForMe 现有的「对话 + 工具 + 知识库 + MCP」能力之上，新增一个**可视化工作流编排模块 Flow Studio**：用户用拖拽画布把「知识检索、模型调用、工具执行、条件分支、人工确认」编排成可复用、可调试、可发布的流程图（DAG），并逐步支持**发布为本地 HTTP API / MCP Server**、**定时自动运行**。

核心思路不是移植 langflow（Python/FastAPI 技术栈完全不同），而是**借鉴其产品形态与架构模式**，在 workBuddyForMe 现有 TypeScript / Next.js / Electron / SQLite 资产上落地。

## 2. 为什么做：现状的三个瓶颈

基于对 v0.7.0 源码的实读（详见 [01-现状与差距分析.md](./01-现状与差距分析.md)）：

1. **执行路径不可控**：对话编排是纯线性的「模型轮 ↔ 工具轮」循环，最多 5 轮（[chat-orchestrator.ts](../../packages/core/src/chat/chat-orchestrator.ts)、`MAX_TOOL_ROUNDS=5`）。调哪些工具、按什么顺序，完全由模型临场决定，结果不可复现。
2. **能力不可复用、不可对外**：工具只能按助手白名单开关，无法组合；MCP 模块**只能作为 client 调用外部服务**，无法把自己的能力暴露出去；也没有定时/事件触发。
3. **技能（skills）表达力弱**：现有技能只是「prompt 模板 + 工具白名单」的声明式文件夹（[skill.ts](../../packages/shared/src/schemas/skill.ts)），没有步骤、分支、数据传递。

这三点恰好是 langflow 的核心价值所在：**显式编排、确定性执行、一键发布**。

## 3. 目标与非目标

### 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 可视化搭建多步骤 AI 流程 | 能用拖拽画布完成「检索 → 判断 → 生成 → 人工审核 → 输出」流程 |
| G2 | 流程确定、可复现、可单步调试 | 相同输入多次运行结果路径一致；可查看每个节点的输入/输出/耗时 |
| G3 | 最大化复用现有能力 | LLM / 13 个内置工具 / MCP 工具 / 知识库检索 / HITL 全部作为节点直接复用，不重写 |
| G4 | 流程可对外提供服务（P1） | 流程可发布为 127.0.0.1 本地 API，并用 `curl` 调通 |
| G5 | 流程可作为 MCP 工具被发现（P1） | workBuddy 作为 MCP client 连接自身暴露的 MCP Server，能看到并调用已发布流程（自举验证） |
| G6 | 离线/定时自动运行（P2） | Electron 桌面端按 cron 定时触发流程并产生运行记录 |

### 非目标（本期明确不做）

- 不移植 langflow 代码、不引入 Python 运行时；
- 不做多人协作、云端同步、流程市场；
- 不做「任意自定义代码节点」（执行用户 JS/Python，桌面端安全风险高）；
- 不做流程版本可视化 diff 编辑器（仅保留版本快照与回滚）；
- 不替代现有聊天与桌面 Agent（task-loop），三者并存、互相调用。

## 4. 方案范围（三期）

| 阶段 | 主题 | 核心交付 |
|---|---|---|
| **P0（MVP）** | 编排 + 执行 + 调试 | 工作流数据模型（迁移 v012）、TypeScript DAG 执行引擎、React Flow 画布、6 类节点、试运行与运行记录 |
| **P1** | 发布为服务 | 本地 HTTP API 发布、MCP Server 暴露、调用密钥、运行态持久化与崩溃恢复 |
| **P2** | 自动化 | Electron 主进程定时调度（cron）、事件触发、运行历史与重试 |

详见 [04-实施路线与风险.md](./04-实施路线与风险.md)。

## 5. 与现有模块的关系（关键设计决策）

- **工作流即工具**：已发布工作流以 `flow:<id>` 限定名注册进现有工具运行时（与 `mcp:<server>:<tool>` 同构，见 [tool-runtime.ts](../../packages/core/src/tools/tool-runtime.ts)）。LLM 在普通对话中即可自主调用流程，**无需修改 assistants 表结构**。
- **节点复用工具内核**：「工具节点」直接调用现有 `Tool.run()`，并**沿用权限门控、熔断器、15s 超时、SSRF 防护**——安全模型不降级。
- **人工节点复用 HITL**：参考现有 pending-confirmations 挂起/恢复与 task-loop 的 pause/resume/SSE 模式。
- **前端技术栈保持一致**：新增 `@xyflow/react`（与 langflow 同为 v12），画布本地状态用 React Flow 自带能力 + `useReducer`，**不引入 zustand**，服务端状态继续用 React Query。
- **数据层沿用裸 SQL + 顺序迁移**：当前为 v011，本期新增 v012（照 [runner.ts](../../packages/database/src/migrations/runner.ts) 的 `PRAGMA user_version` 模式）。

## 7. 成功判据（P0 验收）

1. 在 `/flows` 画布中从零搭出至少 2 个示例流程（随版本内置，类比 langflow starter projects）；
2. 画布「校验」能识别环、孤立节点、参数引用错误并给出定位；
3. 「试运行」可单步/整体执行，底部面板逐节点展示状态、输入、输出、耗时；
4. 含「人工节点」的流程可挂起，提交后从挂起点继续；
5. 已发布流程出现在普通对话的工具列表中（`flow:<id>`），助手可调用并把结果回灌；
6. 全部新接口走统一包络 `{success,data}` / `{success:false,error}`，通过 `pnpm check` 与测试。
