## 二、数据模型（迁移 v013，纯加法）

```sql
CREATE TABLE IF NOT EXISTS workflow_endpoints (
  id TEXT PRIMARY KEY,
  workflow_id TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  -- 密钥：只存 sha256 哈希；prefix 存可展示短头用于 UI 识别
  key_hash TEXT NOT NULL UNIQUE,
  key_prefix TEXT NOT NULL,
  http_enabled INTEGER NOT NULL DEFAULT 0,
  mcp_enabled INTEGER NOT NULL DEFAULT 0,
  sync_timeout_ms INTEGER NOT NULL DEFAULT 60000,
  rate_limit_per_min INTEGER NOT NULL DEFAULT 30,
  -- deny_all | allowlist
  policy_mode TEXT NOT NULL DEFAULT 'deny_all',
  policy_allowed_tools_json TEXT NOT NULL DEFAULT '[]',
  -- 发布版本与策略对齐标记：发布新版本含危险节点时置 1，调用前必须重新确认
  policy_revalidation_required INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'enabled',          -- enabled | disabled
  last_used_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

ALTER TABLE workflow_runs ADD COLUMN endpoint_id TEXT;        -- API/MCP 触发来源端点
ALTER TABLE workflow_runs ADD COLUMN parent_run_id TEXT;      -- 重跑关联
ALTER TABLE workflow_runs ADD COLUMN resumed_from_node TEXT;  -- 重放起点
ALTER TABLE workflow_runs ADD COLUMN interrupt_reason TEXT;   -- process_restart | ...
-- status 新增取值：interrupted（纯文本列，无 CHECK，加法平滑）
CREATE INDEX IF NOT EXISTS idx_workflow_runs_endpoint ON workflow_runs(endpoint_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_workflow_runs_status ON workflow_runs(status);
```

设计要点：

- **一流程一端点**（UNIQUE 不加在 workflow_id 上以保留未来一流程多密钥空间，但 v1 repo 层保证 upsert 单行）；密钥哈希使拖库无法直接冒用；
- 策略与开关存 endpoint 行（可变配置），**策略快照同时写入发布时生成的版本冗余字段**：`workflow_versions` 加一列 `policy_json`（可 NULL；v0.8 版本为 NULL，运行时读 endpoint 当前策略也行，但「随版本不可变」要求执行某版本 run 时用发布那一刻的策略——v1 简化：执行当前已发布版本时快照到 run 行 `run 上下文`，不改 versions 表结构，避免 v013 再加列；policy 快照随 run 落 input 旁道）；
- 状态机扩展：

```text
queued ──claim──► running ──► succeeded / failed / cancelled
                     │
                     └──(进程死亡扫描)──► interrupted ──重跑──► 新 queued run
waiting_human（仅 manual）──(进程死亡扫描)──► interrupted
```

## 三、FlowRunQueue 设计（core/flow/queue/）

### 3.1 接口

```ts
interface FlowRunQueue {
  /** 入队：run 行已是 queued；通知拾取循环 */
  enqueue(runId: string): void;
  /** 执行协程认领（事务原子更新，防多 tick 重复拾取） */
  claimNext(): Promise<ClaimedRun | null>;
  /** 完成/失败/取消时收尾（清理 in-memory 认领标记） */
  settle(runId: string): void;
}

interface EventBus {
  publish(runId: string, event: FlowEventPayload): void;
  subscribe(runId: string, afterSeq: number, listener): () => void;  // 返回取消订阅
}
```

### 3.2 拾取循环与认领

- v1 单进程：容器初始化时启动一个 async 循环（setImmediate 链式自调度，不用固定 interval）：`claimNext → executeRun → settle`，串行；
- claim 用数据库原子语句兜底内存状态：

```sql
UPDATE workflow_runs SET status='running', started_at=@now
WHERE id=@id AND status='queued';
-- changes===1 才算认领到
```

- 队列内存数组只做「有活干」的信号（避免轮询 DB），真实认领以 SQL 事务为准——即使信号重复也不会重复执行；
- manual SSE 路径改为：events 路由先确保 run 被 enqueue（createRun 后统一入队），SSE 立即订阅 EventBus 等 run_started；不再由 SSE 自己驱动 generator，因此断线不取消。

### 3.3 事件流三路消费者统一

```text
executeRun 生成事件
   ├─ run-store 落库（v0.8 既有）
   ├─ EventBus.publish（v0.9 新增：进行中观察者）
   └─ invokeFromChat 的子步骤收集器（v0.8 既有：对话工具卡片）
```

- 画布 SSE：订阅 EventBus 实时事件 + 终态后自动转为 node_executions 回放（v0.8 已有回放逻辑，前置补一段实时订阅）；
- 公开只读 SSE：同上，afterSeq 支持断线补丢（seq 为 EventBus 每 run 单调递增的内存序号；跨进程历史走回放接口）；
- 内存 EventBus 不保留历史（历史在 node_executions），订阅建立时先查 run 状态：终态直接回放、进行中接总线、queued 等待 run_started。

### 3.4 run-service 重构边界

| 保留不动 | 抽出/新增 |
|---|---|
| executeRun 内部全部逻辑（context 回调、引擎迭代、store、active 收尾改为「执行者登记」） | `enqueueRun`（createRun 后入队） |
| createRun 的图校验/落库 | startEvents 退役为「订阅者入口」语义（内部改 subscribeRunEvents） |
| submitHuman/submitToolConfirmation（waiters 仍在单进程有效） | RecoveryScanner（启动收敛） |
| invokeFromChat（对话路径；执行来源由队列改为「队列以 trigger=chat 执行」或保持直接执行——见下） | Unattended policy 注入执行 context |

**chat 路径的处理取舍**：M1 先保持 invokeFromChat 直接执行（它在工具调用协程内，天然串行、无观察者需求），队列只承接 manual/api/mcp。M4 评估是否把 chat 也统一为 enqueue+await（统一触发器模型），若重构影响面大则保留双轨——两者共用 executeRun，安全语义一致，双轨成本可接受。

### 3.5 人工挂起在队列模型下的语义

- manual run 被认领执行、遇 human → waiters.request 注册（进程内）→ EventBus 广播 node_waiting_human → 画布内联提交 resolve → 继续；
- manual run 断线：**不再 abort**（观察连接与执行分离）；waiters 挂起保留，直到提交/取消/进程重启；这是对 v0.8「断线即拒」的语义升级——用户可以关页面后从运行记录里打开同一 waiting run 继续审批（UI M4 补「待审批」入口）；
- api/mcp run：不注册 waiters，interactive=false，策略路径处理。

## 四、HTTP 公开路由（apps/web）

### 4.1 路由与中间件链

```
/api/public/**
  ├─ hostGuard      （127.0.0.1/localhost 白名单）
  ├─ bearerAuth     （查 workflow_endpoints.key_hash；constant-time 比较；disabled→404 混淆）
  ├─ rateLimit      （每 key 令牌桶，内存；Retry-After）
  └─ handler        （definePublicRoute：不注入会话概念，仅 services + endpoint 行）
```

- 不复用 defineRoute（它带托管 token/会话语义）；新增 `definePublicRoute` 姊妹封装，但共用 ApiError→Response、parseBody 等纯函数，错误响应形状一致；
- key 查找：key_hash 建 UNIQUE 索引，O(1)；比较用 `crypto.timingSafeEqual`（等长哈希天然可用）。

### 4.2 同步等待实现

handler 内 await EventBus + run 终态 Promise（带超时）：

```ts
const result = await waitRunTerminal(runId, timeoutMs);
// 内部订阅 bus，终态 resolve；超时返回 null → 202 async 语义
```

同步等待不占用队列线程（队列是自调度串行执行，HTTP 协程只是等待者）。

## 五、MCP Server（core/mcp/server/）

### 5.1 纯处理器（传输无关）

```ts
async function handleMcpMessage(
  msg: JsonRpcMessage,
  ctx: { listFlowTools(): Promise<McpToolDescriptor[]>; callFlow(shortName, args): Promise<McpCallResult>; now(): string },
): Promise<JsonRpcResponse | JsonRpcNotification | null>
```

- 单测可直接喂 JSON-RPC 报文断言输出，不启传输；
- tools/call → callFlow：短码反查 endpoint（mcp_enabled）→ enqueue(trigger=mcp) → 等待终态（90s 上限，超时返回指引 runId 的 text + isError false）；
- 输出 content：`[{ type:'text', text: typeof output==='string'?output:JSON.stringify(output) }]`。

### 5.2 两个 adapter

- **stdio adapter**（`core/mcp/server/stdio-adapter.ts` + `apps/desktop/src/main/mcp-server.ts` 或 packages 下 bin）：stdin 按行 → handleMcpMessage → stdout `encodeMessage`；stderr 只写日志（stdout 是协议通道，污染即死，沿用 v0.6 client 教训）；
  - 打包：electron-builder files 增加 bin；bin 用打包内置 Node 运行（server-manager 已解决 ABI 归集，复用 prepare-server.mjs 产物或独立小型 bundle）；
  - 令牌：env `WBFM_MCP_TOKEN`（推荐，UI 生成命令行时写入）或 initialize params.header（兼容无 env 场景）；
- **http adapter**：`/api/public/mcp` 路由把 JSON body 喂给同一处理器；无状态、bearer 复用。

### 5.3 流程工具描述符

```ts
function toMcpToolDescriptor(wf, graph, shortName): McpToolDescriptor {
  return {
    name: `flow_${shortName}`,
    description: wf.description || `工作流：${wf.name}`,
```

- 审计：tool handler 输出经引擎落 node_executions 时，拒绝原因摘要（`policy_deny:deny_all fetch_webpage danger`）进入 outputs/error 字段，时间线可查；
