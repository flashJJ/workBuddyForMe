# 02 · 功能设计（v0.9）

## 一、用户故事

- **U1 异步触发**：作为调用方程序，我想 POST 一次 `/invoke` 不必保持连接，拿到 runId 后轮询或稍后订阅，流程照样跑完。
- **U2 同步快用**：对于几秒内完成的流程（如网页摘要），我希望一次请求直接拿到结果，像调普通函数一样。
- **U3 崩溃恢复**：作为用户，服务重启后我不想看到永久「运行中」的僵尸记录；中断的运行我能明确知道原因并重跑。
- **U4 多观察者**：我的调用方在等结果的同时，自己也想在浏览器里打开同一 run 看节点进度，两边不打架、不会把对方挤下线。
- **U5 标准协议集成**：我想让任意 MCP 客户端（Claude Desktop、我自己写的脚本）通过 MCP 发现并调用流程，而不用学我的私有 HTTP 格式。
- **U6 受控放权**：无人值守时我清楚哪些危险工具会被调用，默认全拒绝；必要时为特定流程的特定工具开白名单，且这个授权随发布版本固定、可审计。
- **U7 密钥治理**：每个对外流程独立密钥、可随时轮换/吊销，泄露一个不影响其他流程。

## 二、核心概念模型（v0.9 新增部分）

| 概念 | 说明 |
|---|---|
| **Endpoint（端点）** | 一个已发布流程的对外暴露配置，一流程一端点（v1）；含密钥、开关状态、HTTP/MCP 暴露位、限速 |
| **Endpoint Key（端点密钥）** | 生成时产生一次性明文（`wbfm_<40hex>`），库存 `key_hash`（sha256）+ `key_prefix`（前 8 位用于 UI 识别）；明文只在创建/重置时返回一次 |
| **Queue（运行队列）** | queued 运行的进程内待办集合；事务认领、单执行者、顺序拾取（v1 不做优先级） |
| **EventBus（事件总线）** | runId 维度的进程内发布订阅；执行协程发布不可变事件快照，SSE/内部消费者订阅 |
| **Recovery（恢复扫描）** | 进程启动时把无主 queued 重新入队、running 收敛为 interrupted |
| **Unattended Policy（无人值守策略）** | `deny_all`（默认）/ `allowlist`（具体工具名清单，桌面控制类永久禁入）；随发布版本固化 |
| **Replay Run（重放运行）** | 从指定节点重跑：v1 语义为「重放该节点及其全部拓扑上游」，产生关联新 run |

## 三、本地 HTTP API

### 3.1 端点生命周期（编辑器 UI）

在已发布流程的编辑器「发布/对外服务」区：

```text
[ 本地 API ]  开关：关 ○
[ MCP 暴露 ]  开关：关 ○
（开启时展开）
  基址：http://127.0.0.1:34567/api/public
  调用地址：POST /flows/<key>/invoke     ← key 脱敏只在此时完整展示
  密钥：wfk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx  [复制] [重置]
  调用模式：同步优先（超时 60s 自动转异步）  ○ 强制异步
  速率限制：30 次/分（默认）
  ── 无人值守危险操作策略 ──
  ○ 拒绝全部写入/高危操作（推荐）
  ○ 白名单自动允许：[选择具体工具…]（桌面控制类不可选）
  ⚠ 该流程含 2 个写入/高危节点：fetch_webpage(danger)、…
```

- 开启 HTTP/MCP 任一暴露都生成 endpoint 行与密钥；关闭=状态 disabled，密钥保留（再开不用改调用方）；重置密钥=旧 hash 即时失效；
- 未发布流程（draft）不允许开启（按钮禁用并提示先发布）；
- 流程发布新版本后端点仍然有效（端点绑定 workflow_id 而非版本），**策略快照随新版本重新确认**（新版本含新危险节点时，开启状态下要求重新确认策略，否则 API 调用返回 409 `policy_revalidation_required`）。

### 3.2 调用契约

**同步/异步调用**

```http
POST /api/public/flows/:key/invoke?mode=sync|async HTTP/1.1
Host: 127.0.0.1:34567
Authorization: Bearer wfk_xxxxxxxx
Content-Type: application/json

{ "url": "https://example.com/article" }
```

- 入参 body 即 start 节点 input；服务端用 start 入参 zod 校验（必填/类型/默认值同对话链路）；
- `mode=sync`（默认）：执行 ≤ 同步超时（默认 60s，端点可配上限 5–120s）→ 终态响应；超时自动转异步语义（202 + runId），响应头 `X-WBFM-Async: 1`；
- `mode=async`：立即 `202 {runId}`。

**响应（同步终态）**

```json
{ "success": true, "data": { "runId": "r1", "status": "succeeded", "output": "……" } }
```
失败终态 HTTP 200 + `success:true,data.status:'failed'`（调用成功但业务失败，便于调用方读 error；另有专用错误码表见 03 文档），传输层错误（鉴权/限流/校验）才用 401/404/422/429。

**查询与订阅**

```http
GET /api/public/flows/:key/runs/:runId            → 状态/输出/错误/节点摘要
GET /api/public/flows/:key/runs/:runId/events?after=<seq>
```

- events：进行中返回 SSE（接到 EventBus；after=历史事件序号，先补历史快照后接实时）；终态返回一次性回放后关闭连接；
- 只读订阅**永不影响执行**（与 v0.8 的本质区别）：断开/多开都不取消 run。

**错误体**（传输层）

| HTTP | code | 场景 |
|---|---|---|
| 401 | unauthorized | 无/错 bearer |
| 404 | endpoint_not_found | key 不存在或已禁用（不区分以防枚举） |
| 409 | endpoint_disabled / workflow_not_published / policy_revalidation_required | 开关关、流程被停用、新版本危险策略待确认 |
| 422 | validation_failed | 入参不符 start schema（附字段详情） |
| 429 | rate_limited | 超每密钥速率限制（Retry-After） |
| 503 | no_capacity | v1 理论上不出现（串行队列无容量上限，保留位） |

### 3.3 安全交互细节

- 仅绑 127.0.0.1；校验 `Host` 必须是 `127.0.0.1:<port>` 或 `localhost:<port>`，拒绝其他 Host 头（DNS rebinding 防护）；
- 公开路由不读/不写会话 cookie，CORS 默认不发 Access-Control-Allow-Origin（同源 curl/服务端调用不受影响；浏览器跨域默认拒绝即安全姿态，需要时仅允许 `http://localhost:*` 无凭据）；
- 每次调用写审计（run 行 endpoint_id + last_used_at 更新）。

## 四、MCP Server

### 4.1 暴露的工具集

每个「MCP 暴露开启」的流程映射为一个 MCP tool：

```jsonc
// tools/list
{
  "name": "flow_a1b2c3d4",            // 安全标识：flow_ + id 前 8 位十六进制
  "description": "网页摘要器：……",      // workflow.description
  "inputSchema": { /* start 入参 JSON Schema，与对话工具同一份生成器 */ }
}
```

名称不直接用完整 UUID 而用稳定短码（同 id 前缀，列表内去重，碰撞追加位）；MCP 工具描述里附完整流程名便于模型选择。

### 4.2 协议方法（最小集）

| 方法 | 行为 |
|---|---|
| `initialize` | 返回 `{protocolVersion, capabilities:{tools:{}}, serverInfo:{name:'workbuddy-flow',version}}`；校验 MCP 协议版本兼容（参照 client 支持的版本） |
| `notifications/initialized` | 仅消费，返回空通知确认（无响应） |
| `tools/list` | 列开启 MCP 暴露的已发布流程；cursor 分页 v1 忽略（数量少），返回空 nextCursor |
| `tools/call` | 参数 `{name, arguments}` → 映射 workflow → enqueue（trigger=mcp，策略同 API）；v1 行为：等待至终态或 90s 超时；返回 MCP content `[{type:'text', text: output}]`，失败 `isError:true` + 错误文本（结构化错误放 text JSON 附 runId） |
| 其他方法 | method not found（-32601） |

### 4.3 两种承载

- **stdio**：可执行入口（打包后 `workbuddy-mcp-server` bin；开发态 `tsx` 脚本）。spawn 时通过命令行参数/env 接收数据目录与一个「MCP 访问令牌」（用户在 UI 复制的 spawn 命令行自带 `--token`）；进程读库列端点、校验、入队、等待终态。stdio 天然无 HTTP 鉴权层，令牌校验放在 initialize params 或进程 env（env 优先，避免泄露给同机进程列表的方式见 03 文档安全节）；
- **streamable HTTP**：`POST /api/public/mcp`（bearer 同 HTTP API），JSON 请求/响应；v1 不实现 SSE 响应流（长流程经 tools/call 同步等待上限内完成，超时返回 runId 风格的指引文本）。

### 4.4 自举验证流程

设置 → MCP 服务器 → 新增（类型 http，URL `http://127.0.0.1:<port>/api/public/mcp`，bearer 填密钥）→ 启用 → tools/list 出现 `flow_*` → 对话中助手实际调用成功。

## 五、执行恢复与重跑语义

### 5.1 启动恢复扫描（每次容器初始化执行一次）

```text
SELECT * FROM workflow_runs WHERE status IN ('queued','running','waiting_human')
  queued/manual|chat/api|mcp 无 active 认领者
    → 重新入队（waiting_human 的旧挂起一律不复活，标 interrupted: process_restart）
  running / waiting_human
    → status='interrupted', interrupt_reason='process_restart', finished_at=now
```

恢复只做状态收敛与重新排队，不尝试恢复内存中的 waiters（跨进程等待存储是更大的话题，v1 不做；manual SSE 挂起刷新后即失效的行为与 v0.8 一致，但不再有永久僵尸态）。

### 5.2 重跑（v1：重放式）

「从失败节点重跑」的语义明确为：**新建 run，从目标节点沿拓扑反向求其全部祖先闭包，执行闭包子图**（等价于在原图上把闭包外节点标记 skipped/跳过执行），输出路径仍走到可达的 end。

- 为什么不直接复用落库 outputs 跳过上游？跨版本图变化、上游 outputs 体积与引用完整性、人工节点是否重新审批，都需要语义决策；v1 用「重放上游段」保证自洽，成本是多花一次上游执行（本地场景可接受）；
- 新 run 记录 `parent_run_id` 与 `resumed_from_node`；UI 展示「重跑自 ×× 运行的 △△ 节点」；
- 真正的断点续跑（复用历史 outputs、跳过已确认人工节点）登记 v0.10 评估。

### 5.3 运行记录视图

- 入口：`/flows` 顶部「运行记录」或编辑器内「历史」tab；
- 筛选：trigger（手动/对话/API/MCP 带来源徽章）、状态（含 interrupted 独立样式）、时间；
- 行操作：查看节点详情（复用 execution-timeline）、整体重跑、interrupted/failed 行「从失败节点重跑」；
- API 运行不显示人工内联操作（无人值守不挂起），仅展示。

## 六、无人值守策略详细规则

执行 tool 节点时（run-service 门控回调）：

```text
trigger ∈ {manual}     → v0.8 HITL 链路（内联授权）
trigger = chat         → v0.8 现状（非交互，未授权即拒绝）
trigger ∈ {api, mcp}   → 查发布版本策略快照：
    permission=read                         → 放行
    permission∈{write,danger}
      policy.mode='deny_all'                → 拒绝（node 输出 ok:false，审计 policy_deny）
      policy.mode='allowlist'
        toolName ∈ policy.allowed
          且 toolName 不属桌面控制永久禁单   → 放行（审计 policy_allow）
        否则                                → 拒绝（policy_deny）
```

- 永久禁单（任何策略都不可放行）：`screen_snapshot / mouse_* / keyboard_* / window_* / uia_list / app_launch`——无人值守操控 GUI 的风险模型不成立，需桌面操作请走 manual/chat 有人链路；
- 熔断/超时/SSRF 等既有工具安全机制对策略放行的调用同样生效（allowlist 只免 HITL，不免其他防护）；
- 策略确认时点：发布流程时，若图中存在 write/danger 节点，发布弹窗必须列出节点并选择模式；存为版本快照。

## 七、与现有体验的边界（零回归清单）

- 画布「试运行」：仍走 manual + SSE 驱动 + 人工内联，事件机制改为 EventBus 后行为一致（单页面订阅）；
- 对话调用 flow：trigger=chat 不变；M3 的工具子步骤展示不变；
- 取消运行：manual 面板取消语义不变；api/mcp 运行可经 `POST .../control cancel`（带密钥）取消；
- 已发布流程自动注入对话工具表：与端点开关状态**无关**（对外暴露开关不影响对话可见性，两者正交）。
