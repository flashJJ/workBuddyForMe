# 01 · 现状与差距分析（v0.9）

> 基于 v0.8.0（main 1930d30）源码实读。所有结论附代码位置。

## 一、v0.8 执行链路现状（要改造的对象）

### 1.1 run-service 的生命周期绑定

`packages/core/src/flow/run-service.ts` 现状三个关键结构：

```ts
const active = new Map<string, ActiveEntry>();  // runId → { abort }
const waiters = createFlowWaitRegistry();        // 内存挂起 Promise 注册表

createRun(params)   // 仅落库 queued，不执行
startEvents(runId, signal)  // queued 且无活跃 → executeRun 并登记 active；active 已有 → 409；终态 → 409
submitHuman / submitToolConfirmation / cancel   // 操作 waiters/active
```

**差距**：

- 执行协程的唯一驱动者是 SSE 路由对 generator 的迭代（`apps/web/src/app/api/flows/runs/[id]/events/route.ts`）。没有人订阅，没有人迭代，run 就永远 queued；
- `active` Map 没有任何持久化/恢复逻辑。进程死亡后，queued 行无人拾取，running 行永远停在 running；
- 观察者与执行者是同一个连接：单订阅（第二个订阅 409），且观察连接断开会 abort 执行。

**可保留**：`executeRun`（构建执行上下文 + runFlow + run-store 落库 + 终态删 active/清 grant）本身与调度无关，是重构后被队列调用的核心函数；`createRun`（loadCompiledGraph 校验 + 落库）逻辑可直接复用。

### 1.2 三种触发模式的现状

- `trigger=manual`：SSE 驱动，interactive=true，human/tool 挂起走 waiters + 前端内联；
- `trigger=chat`：`invokeFromChat` 直接在工具调用协程内迭代 generator，interactive=false，human 自动拒绝、danger 无确认回调直接拒绝；
- 枚举 `FLOW_TRIGGERS = ['manual','chat','api','mcp','schedule']`（shared 已预留 api/mcp/schedule 字符串），但 api/mcp 路径不存在。

**差距**：api/mcp 触发器需要一条「不依赖调用方连接保持、interactive=false、危险操作走策略而非硬拒绝」的执行路径。chat 路径的「非交互」语义可复用，但它当前直接在 flow 工具内 await 完成，没有排队/恢复。

### 1.3 SSE 事件与落库现状（可复用度高）

- 引擎事件 9 种（run_started/node_*/run_*），run-store 逐节点 upsert node_executions、迁移 run 状态；
- Web SSE 路由已支持**终态回放**（从 node_executions 重建事件流）；
- 前端 `useFlowRunEvents` 有终态主动关流 + 去重（v0.8 修复成果）。

**差距**：进行中运行的事件只存在于执行协程的 generator 里，后来的观察者无法订阅（generator 不能被两次迭代）。需要进程内事件 pub/sub 总线把「执行中的实时事件」与「终态回放」衔接。

## 三、差距矩阵（按模块）

### shared

| 现状 | 差距 | 对策 |
|---|---|---|
| trigger 枚举含 api/mcp 但无类型契约配套 | 无 endpoint/策略/interrupted 类型；无公开 API 请求/响应 schema | 新增 `schemas/flow-serving.ts`、扩 types/flow.ts（run 状态加 interrupted/resuming、Run 加 endpointId/parentRunId/resumedFromNode/interruptReason） |
| ToolSubstep（v0.8 M3） | 无策略判定字段（policy_allow/policy_deny 审计） | node 执行审计结构扩展（存 node_executions 的 outputs/error 旁道，不改 SSE 主协议） |

### database（v013）

| 现状 | 差距 |
|---|---|
| workflow_runs 无触发端点/重跑关联/中断原因列 | 增列 endpoint_id / parent_run_id / resumed_from_node / interrupt_reason（均可 NULL，加法） |
| 无 API 密钥表 | 新增 workflow_endpoints（id/workflow_id/key_hash/key_prefix 展示位/模式同步异步/状态/密钥时间戳/last_used_at） |

### core

| 现状 | 差距 | 对策 |
|---|---|---|
| 执行只能由 SSE generator 迭代驱动 | 无队列、无认领、无 pub/sub、无恢复 | 新增 `flow/queue/`：FlowRunQueue（enqueue/claim/tick）、EventBus（按 runId 订阅不可变事件）、RecoveryScanner |

## 四、两条被否方案与理由

1. **直接把 FlowRunService 改成「startEvents 内部自启动、SSE 只观察」**：能解决「断线不取消」，但 queued 运行仍需要第一个观察者来启动、恢复扫描无处安放、API 同步调用也要伪装成观察者。不如正面引入队列概念，调度职责一次理清。
2. **MCP server 直接引入官方 SDK**：v0.6 client 选型时已评估（官方 SDK 传递 17 个服务端依赖），本版本只用 tools 能力，协议面四个方法，自实现与既有 jsonrpc 资产合计新增量很小；与项目「最小自实现、依赖面克制」的一贯纪律一致。

## 五、结论

v0.9 的改造面集中且边界清晰：**引擎内核不动，动的是「谁在什么时候以什么安全上下文执行 queued 运行」这一层**；对外暴露（HTTP/MCP）是队列之上的两个薄适配；数据层 v013 纯加法。最大的工程风险是 run-service 调度层重构的回归面，以「executeRun 原函数保留 + v0.8 全量测试护栏 + 手动/对话链路逐条回归」控制。
