## 1. 本里程碑做了什么

| 能力 | 行为 |
|---|---|
| 轮换 API | `POST /api/secrets/rotate` 扫描有密文的 Provider，逐条解密 → 重加密 → 写回 |
| Web keyring | `keys/master-keyring.json`：active + fallback；旧 `master.key` 作为 legacy 读入 |
| 轮换顺序 | 先解密全部行 → 生成新 key 并原子写 keyring → 逐行重封装 → `failed===0` 时同步旧 `master.key` |
| 失败处理 | 单条解密失败计 `skipped`，单条加密 / 写回失败计 `failed`；旧密文保留 |
| Desktop | safeStorage 系统密钥不变，只重新封装密文；`keyId` / `legacyKeySynced` 为 null |
| 限额 / 保护 | keyring 最多 3 把；干净轮换后裁剪到 active + previous；失败轮换保留 fallback |
| 审计 | `secrets_rotated` 记录 mode 与 rotated / skipped / failed，不含密文或明文 |
| UI | 设置 → 关于（安全区块）新增「轮换凭证」按钮，二次确认，完成展示计数 |

## 3. 关键口径

1. **先解密后换 key**：若先换 key，旧密文仍可由 fallback 解，但实现顺序遵循 M0；解密阶段失败的行直接归入 `skipped`。
2. **keyring 落盘顺序**：新 key 成为 active 后立即原子写 keyring；旧 active 保留为 fallback。任一步崩溃，旧密文仍可解。
3. **降级兼容**：仅当 `failed===0` 时把新 active key 写入旧 `master.key`；`failed>0` 不覆盖，宁可降级后重新输入失败项，也不掩盖失败。
4. **Desktop 语义**：safeStorage 系统密钥由 OS 管理，代码只重新封装；UI 文案明确「重新加密」，不宣称更换系统密钥。
5. **范围**：仅 Provider API Key；MCP `env/headers` 仍为 P1-3，不纳入本次轮换。
6. **审计**：路由层 `safeAppend` 写 `secrets_rotated`，只含 mode 与计数，不含 Provider 名、密文或明文。

## 4. 契约偏差与说明

| # | 事项 | 说明 |
|---|---|---|
| 1 | Desktop 可用性检测 | 生产 bootstrap 注入 `isAvailable() => true`；safeStorage 真正不可用时表现为逐行 `failed`（500 结果），而非 503。`SECRET_ROTATION_UNAVAILABLE` 由服务层对 `isAvailable=false` 的 cipher 生效 |
| 2 | keyring 最多 3 把 | 轮换时丢弃最旧 fallback，保证 active + 两个 fallback；干净轮换后裁剪到 active + previous |
| 3 | `skipped` 不阻止 legacy 同步 | 跳过项原本就不可解密；`failed===0` 即可同步旧 `master.key`，不因跳过项阻塞降级兼容 |
| 4 | 审计写入位置 | 与 M1 一致，放在路由层，避免 core secrets 服务依赖 AuditService |
