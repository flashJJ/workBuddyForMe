# v1.1 现状与差距分析：elpis 取证 × wbfm 盘点

> 方法：只以两个仓库的源码/配置/既有文档为证据，不凭印象。elpis 侧通读其 code-wiki 七篇与 22 个关键源文件；wbfm 侧跑文件行数/any/深路径引用等全仓扫描并核对核心链路代码。

---

## 1. elpis 是什么

`@fsiaonma/elpis` 1.0.6：**NestJS 12 + LangGraph 0.2 的 AI 应用框架**（上层带 Vite/Vue3 低代码后台，与本次主题无关，不评估前端部分）。AI 运行时按 12 个领域目录组织：agent / contracts / eval / guardrail / mcp / memory / rag / runtime(langchain+langgraph) / skill / store(reference) / tool(builtin) / trace。

它最有辨识度的四个做法：

### 1.1 合同式 SDD 流程（`sdd/part{1,2,3}/{spec,plan,tasks}.md`）

- `spec.md` 写「目标 / **稳定面（合同）** / **禁止** / 验收」，字段名锁死（如 `POST /api/ai/agent/run` 必返回 `{runId,output,steps}`，流式 done 与同步结果同构）；
- `plan.md` 写「**改哪/不改哪**」两列对照 + 争议预裁决（如「全量迁、一次删，不做 Bridge」「失败必须 HTTP 200 + code:442」）+ 目录轮廓（注明「实现可微调，职责不能丢」）；
- `tasks.md` 一任务一条，列「任务 | 完成标准」，完成标准可机械验证（「同 threadId 重启后上下文仍在」），收尾固定一句「走偏了回到 spec/plan，不追加口语 Prompt」。

### 1.2 interface / service / module / internal 四层约定

- 每个领域：`xxx.interface.ts`（只放接口与类型）+ `xxx.service.ts`（无状态实现，构造时经 internal 纯函数一次性加载配置）+ 极薄 module；
- `internal/load-*-config.ts` 是**模块私有**配置读取纯函数，不导出；
- store 域：`store.interface.ts` 定义 TraceStore/MemoryStore/VectorStore 三个端口，`reference/` 放 file/qdrant 参考实现，module 用工厂按配置选实现；
- 消费侧只依赖接口。**但这套靠 NestJS IoC 容器 + Symbol 令牌强制**，在 Next.js 里没有等价挂载点。

### 1.3 compact-tool-result：工具结果中央压缩（253 行纯函数，零 Nest 依赖）

- 唯一调用点在状态图 observe 节点：**只压缩回喂模型的 tool 消息**；
- 四层策略：硬阈值（普通文本 60 字 / observation 总包 2400 / RAG 文本 500 / excerpt 120）→ 黑名单丢长文本键 → 工具结果特化（invoke_agent 只留 `{runId,output}`；retrieve 按 `#L1-L5` 层级去重）→ 通用递归（能 JSON.parse 就按结构压、数组按形状取样、超限降级 `idsOnly`「保 id 不保内容」给下一轮工具调用留引用句柄）；
- **双视图原则**：压缩视图喂模型，完整结果原样进 steps/Trace 供前端回放与审计。

### 1.4 契约集中 + 流式同构 + 零依赖 eval

- `app/ai/contracts/index.ts` 单文件集中 LlmMessage/PlanAction/Step/RunResult，`AgentStreamEvent` 的 done payload 与同步 `RunResult` 同构；
- `eval/assertions.ts` 89 行纯函数断言（stepsContain/outputNotEmpty/guardrailBlocked 双向/outputContainsAny），首个失败短路返回带原因的 `{pass:false,reason}`；框架不挂 eval HTTP，runner 与数据集在业务仓。
- 另有：多 Agent 委托用 `AsyncLocalStorage` 维护 agentStack/depth，显式防环（DELEGATION_CYCLE）防超深；Trace 内存 Map + 异步 store 双写。

## 2. wbfm 现状量化盘点（v1.0 合并后）

### 2.1 基本盘（好的部分，不动）

| 项 | 现状 | 证据 |
|---|---|---|
| 类型严格度 | TS strict + `noUncheckedIndexedAccess`；生产代码仅 6 处 any，全在 backup/restore-ops.ts（不可信备份 JSON，合理场景） | 全仓正则扫描 |
| 包结构 | shared/config/database/ai/core/voice 六包职责清晰，**零跨包 src 深路径引用** | 对 `@wbfm/*/src` 等模式 grep 无命中 |
| API 信封 | `{success,data}` + ApiError + with-api-handler + zod 校验，等价 elpis 的 Filter/Pipe 组合 | lib/server/with-api-handler.ts、validation.ts |
| 配置 | @wbfm/config 集中数据根/环境，单一事实源 | packages/config |
| 契约真源 | SsePayloadMap 集中在 shared，OrchestratorEvent 从它取 payload 类型 | shared/api/sse.ts、core/chat/types.ts |
| RAG/历史预算 | 中央 token 预算（0.9 安全率）、RAG 片段 fitContextBlock、历史递归摘要 | context-budget.ts、prompt.ts、turn-context.ts |
| 评估种子 | eval-memory 已有 golden set + LLM-as-judge + 分级退出码（基础设施错=2/命中率<70%=1） | scripts/eval/eval-memory.mjs |
| 工程纪律 | 300 行门禁、四层测试、turbo 缓存、typecheck 14 任务、lint 0 error | pnpm check |

### 2.2 差距清单（本次要还的债）

**D1｜分层没有强制力，领域逻辑已经越界一次**

- 无 `eslint-plugin-import`、无 `no-restricted-paths`，包依赖方向与目录私有性全靠约定；
- 越界实例：语音**引擎生命周期编排**（settings 驱动的引擎创建/缓存键/sid 解析，226 行 VoiceRuntime + 101 行语音桥 + singleton/model-paths）整体位于 `apps/web/src/lib/server/voice/`。其中「sid 解析顺序：请求覆盖→角色绑定→兜底」「引擎缓存键」是**领域策略**，应与 ASR/TTS 引擎一样属于包；web 应只保留 HMR 单例与 HTTP 接线。

**D2｜工具结果缺中央压缩层（elpis 1.3 的直接对照差距）**

| 回灌模型的内容 | wbfm 有无统一预算 |
|---|---|
| system/RAG 片段 | ✅ 中央 token 预算 + 截断 |
| 历史消息 | ✅ 递归摘要压缩 |
| **工具 output** | ❌ 仅工具各自为政：fetch-webpage 8000 字硬切、clipSummary 120 字；MCP 工具、Flow 工具、桌面控制工具无统一上限 |

`tool-call-loop.ts` 第 248 行把 `result.output` 原样放进 tool message。大结果（如 MCP 返回大表、网页工具绕过自限时）直接进下一轮 prompt，失败形态是上游 400（Ollama 静默截断到 2048 的坑 v1.0 已踩过一次）。

**D3｜热点文件贴线/超限，白名单在膨胀**

- 超 300 行已进白名单 5 个：pet-manager.ts(483)、pet-manager.test.ts(366)、manifest-kokoro-files.ts(384，自动生成合理)、shared/index.ts(360)、core/index.ts(309)（后两个 barrel）；
- ≥260 行的手写热点 12+ 个：task-loop.ts 299、desktop main/index.ts 296、run-service.ts 285(+test 296)、chat-orchestrator.ts 279、mcp/registry.ts 283、backup/export.ts 281、memory-service.ts 281、use-chat-session.ts 291、flow-editor.tsx 296、endpoint-dialog.tsx 290、database mappers.ts 289、workflow-run-repo.ts 296；
- 72 个文件 ≥200 行。门禁没有「预警线」，都是撞 300 才处理。

**D4｜SSE 契约存在手工二次列举**

`OrchestratorEvent` 把 SsePayloadMap 的键手写成 8 项联合；v1.0 新增的 task/flow/voice_audio/voice_state 四个事件没有进入该联合（语音桥/flow SSE 各自在 web 侧定义扩展联合）。目前能跑是因为消费端各管各，但「core 事件集合 = wire 事件集合」这个不变量没有任何机械保障。

**D5｜质量门禁覆盖不均**

- 覆盖率阈值仅 core 包（statements/lines 70%）；web/desktop/ai/voice/database/shared/config 无门槛；
- 根 `tests/e2e` 的 typecheck 是 v1.0 收尾才补进 web 的 typecheck 命令，desktop scripts/spikes 的 lint 同期才补；
- eval 仅 memory 一个域，断言内联在脚本里，无法被其他域复用。

**D6｜开发流程缺「合同」环节**

v0.x/v1.0 的 plan 文档质量高（现状/功能/架构/路线四篇），但没有 elpis 那种「稳定面/禁止」的硬合同段与「可机械验证完成标准」任务板——v1.0 多次出现「代码完成但真机验收项散落在总结文档里」的情况。本方案三件套即试点。

## 3. 借鉴 / 不借鉴 对照裁决

| elpis 做法 | 裁决 | 理由 / wbfm 对应物 |
|---|---|---|
| compact-tool-result 纯函数压缩 + 双视图 | ✅ **M1 移植改造** | D2 直接差距；改为 token 预算驱动（wbfm 已有 token 估算），接入现有 context-budget 账 |
| interface/internal/reference 目录约定 | ✅ **M0/M2 采纳约定** | 不搬 Nest module，只搬「内部文件放 internal/、跨目录只 import 公开面」的纪律，用 ESLint 强制 |
| SDD spec/plan/tasks 三件套 | ✅ **M0 试点** | v1.1 文档即首份试点；后续版本沿用 |
| eval 纯函数断言库 + 数据集外置 | ✅ **M5 采纳** | eval-memory 升级为平台，不重写 |
| 契约集中 + done 同构 | ✅ **M4 加强** | wbfm 真源已在 shared，差「机械派生」和一致性测试 |
| AsyncLocalStorage 委托上下文 | ⏸ 记备案 | wbfm 暂无多 Agent 委派（Flow 是 DAG 不是互调用）；v1.2 若做 invoke-agent 再取 |
| Trace 内存+store 双写 | ➖ 不借 | wbfm tracer/tool trace 落 SQLite，需求形态不同 |
| `@Module`/Symbol 令牌/`@Inject`/useFactory | ❌ 不迁 | Next App Router 无 IoC 容器；工厂函数+ServiceDeps+container 组合根已足够 |
| 全局 Guard/Pipe/Filter/Interceptor | ❌ 不迁 | with-api-handler/zod/ApiError/middleware 是 Next 等价物 |
| glob 扫 dist 注册 skill/agent | ❌ 不迁 | wbfm 技能扫描在运行时扫数据目录（用户文件），框架内置项走显式注册表，扫编译产物与 standalone 打包模型冲突 |
| class-validator DTO + 442 信封 | ❌ 不迁 | 全线 zod，不引入第二套校验 |
| 三层 config 深合并 + createRequire | ❌ 不迁 | @wbfm/config 已是单一事实源，无业务仓/框架仓双配置需求 |
| Qdrant/文件双 VectorStore 端口 | ❌ 不迁 | sqlite-vec 单实现满足本地优先，多存储是伪需求 |
| guardrail 关键词/正则 | 📋 记 v1.2 候选 | 属用户可见功能，不进代码优化版本 |

## 4. 风险预判（详见 03 文档）

1. 边界规则一次性 error 化可能刷出大量历史违例 → 先 warn、分批修、M5 再翻 error；
2. barrel 子路径化会动大量 import → 用 codemod + typecheck 兜底，保留根 barrel 一个版本周期；
3. 语音运行时搬家影响 Next external 与 prepare-server 归集 → 同签名薄壳 + pack:dir e2e 回归；
4. 压缩器「压过头」伤工具链路质量 → 压缩只在入模消息层、保留完整 output 在 trace；eval  golden 用例锁住「下一轮工具仍能拿到 id 引用」。
