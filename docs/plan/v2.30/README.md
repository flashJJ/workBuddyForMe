# v2.30 方案：能力补齐——能力可见、审批可读与内容包/产物收口

> 主题：让用户看得见已经装了什么、审批时知道要装什么、内容包过期能发现、单轮产物不失控。
> 分支：`feat/v2.30-capability-completion`
> 目标：零迁移、零接口破坏、单一主题。

## 1. 背景与目标

v2.17 把能力安装做成了审批闭环，v2.18 把内容包与产物做成了可交付能力。但两条链路的外围仍有四个断点：

- 助手无法列出现有能力，用户问「你装了哪些技能」只能靠模型猜；`capability_list` 只有设计稿；
- 安装审批复用通用工具确认框，只显示 `catalogId` 与理由，看不到目录来源、版本、签名、effect 与将新增哪些工具；
- 内容包固定在上游某个 commit，没有「检查更新」；上游内容变化时，哈希校验会直接拒绝导入，用户不知道是网络问题还是版本过期；
- 单轮产物只有「单文件 2MB」限制，没有数量与总大小上限；一次批量生成可能写十几份产物，把消息区撑满。

本版目标：**能力可见、审批可读、内容包可核对、产物有上限。** 不新增迁移，不引入第三方目录导入。

## 2. 盘点结论

| 来源 | 未交付项 | 本版取舍 |
|---|---|---|
| v2.17 已知边界 | `capability_list` 未实现 | 纳入 P0，只读、零模型成本 |
| v2.17 已知边界 | 安装审批框未展示来源/签名/effect/新增工具 | 纳入 P0，扩展可选 `details` 字段 |
| v2.18 已知边界 | 内容包固定 commit，未做检查更新 | 纳入 P1，只做只读检查，不做自动更新 |
| v2.18 已知边界 | 单轮产物数量限制未运行时计数 | 纳入 P1，数量 + 总大小双上限 |
| 候选 03 B | 第三方本地 ZIP 目录导入 | Non-Goal，供应链风险需要单独版本 |
| 候选 03 C | 内容包自动更新与差异合并 | 降级为「检查 + 手动重新导入」，不做自动替换 |

结论：只补已有链路上的「可见与上限」，不扩大安装入口，不改变签名与权限模型。

## 3. 主题与边界

一句话：**已经装的能力要能被助手说出来，准备装的能力要能被用户看清，外部内容与产物都要有边界。**

- 可见：`capability_list` 只读当前助手可用的能力，不触发安装、不访问网络。
- 可读：审批详情只展示目录中已有的事实，不新增推测字段。
- 可核对：内容包更新检查只比较上游最新 commit 与内置版本，不自动下载、不自动替换。
- 有边界：产物限流在工具执行层生效，超限返回可读错误，不写半份文件。

## 4. 功能清单

### 4.1 能力可见与审批可读（P0）

- 新增只读工具 `capability_list`：
  - 输入可选 `kind` 与 `status`（enabled / disabled / all），默认列出当前助手可用或已安装的能力；
  - 输出 id、名称、种类、状态、版本、权限、effects 与工具名，单次最多 30 条，超出提示用 `capability_search` 缩小范围；
  - 不返回正文、密钥或安装路径；未装配能力服务时返回可读的不可用说明。
- 扩展 `tool_confirmation_required` 事件：新增可选 `details`：
  - `catalogId`、`name`、`kind`、`version`、`source`、`installStrategy`、`signatureStatus`、`permissions`、`effects`、`toolNames`；
  - 仅 `capability_install` 填充；其他工具不出现该字段，旧客户端忽略。
- 审批框默认精简：标题下显示「来源 · 版本 · 将新增 N 个工具」，展开后看完整 effects、权限与签名状态；不改变 allow / deny 决策语义。
- 详情来源只查能力目录，不额外请求网络；目录条目不存在时退回现有 `argsSummary`。

### 4.2 内容包更新检查（P1）

- 新增只读接口 `GET /api/content-packs/:id/update-check`：
  - 读取内置内容包的 `version`（上游 commit 短哈希）与 `sourceUrl`；
  - 请求上游仓库最新 commit（10 秒超时），返回 `currentVersion / latestVersion / updateAvailable / checkedAt / sourceUrl`；
  - 网络失败、限流或仓库不可达时返回 `status: 'unavailable'` 与可读原因，不抛 500。
- 内容包卡片新增「检查更新」按钮，手动触发；不在页面加载时自动请求。
- 三种结果：已是最新、上游有更新（附来源链接）、暂时无法检查。
- 不做自动更新：重新导入仍需先删除旧知识库，避免静默替换用户已编辑的内容包。

### 4.3 单轮产物限流（P1）

- 新增常量：`ARTIFACT_MAX_PER_TURN`（默认 6）与 `ARTIFACT_TURN_MAX_BYTES`（默认 8MB）；单文件 2MB 上限保持不变。
- 在工具运行时的单轮上下文里维护产物计数与累计字节；`artifact_write` 执行前检查：
  - 超数量返回「本轮产物已达上限（6 个），请合并或下一轮再写」；
  - 超总大小返回「本轮产物总大小已达上限（8MB）」；
  - 超限不落盘、不生成附件记录。
- 计数按回合重置，不跨对话累计；失败与跳过不计入。
- 界面沿用现有工具错误展示，不新增组件。

### 4.4 审批决策快照（P2）

- `capability_install` 的 allow / deny 审计事件在 `outcome` 中附带能力条目快照：`catalogId@version`、来源与 effects 摘要。
- 只写字符串摘要，不新增表、不改变审计链哈希字段；审计页可直接看到「批准了哪个版本、来自哪里」。
- 不记录密钥、内联正文或完整清单 JSON。

## 5. Non-Goals

- 不做第三方本地 ZIP 进入能力目录；目录仍只收内置精选包。
- 不做内容包自动更新、差异合并或增量替换。
- 不做能力自动安装、自动启用写工具或绕过审批。
- 不改变签名策略、权限模型与能力包格式。
- 不做产物压缩、打包下载或跨回合产物配额。
- 不做新的存储迁移。

## 6. 阶段拆分

| 阶段 | 内容 | 交付物 |
|---|---|---|
| P0-M1 | `capability_list` + 审批 `details` + 审批框展示 | 工具、事件契约、组件测试 |
| P1-M2 | 内容包更新检查接口与卡片按钮 | 服务方法、路由、三种结果态 |
| P1-M3 | 单轮产物数量/总大小限流 | 常量、运行时计数、工具错误测试 |
| P2-M4 | 审批决策审计快照 | 审计字符串、审计页可见 |
| 收尾 | 发行说明、路线图状态、博客 10 篇 | `docs/roadmap/v2.30-release-notes.md` |

顺序理由：P0 只读、风险最低，先建立「助手能说清装了什么、用户能看清装什么」的闭环；内容包检查涉及外部网络，单独一段并做好不可用降级；产物限流改工具执行层，放在契约稳定之后；审计快照只写字符串，最后补。

## 7. 验收口径

1. `capability_list` 能列出当前已安装/可用能力的 id、状态、版本、权限、effects 与工具名，单次不超过 30 条；无能力服务时返回可读说明。
2. `capability_install` 审批事件带可选 `details`，旧客户端忽略后仍能正常 allow / deny；其他工具不出现该字段。
3. 审批框默认精简、可展开查看来源、版本、签名、effects 与新增工具；目录条目缺失时退回原 `argsSummary`。
4. 内容包检查更新返回最新/有更新/不可用三种结果；网络失败不抛 500，不自动下载或替换。
5. 单轮第 7 个产物或累计超过 8MB 时被拒绝，错误文案可读，磁盘无半份文件。
6. 审批审计能看到 `catalogId@version`、来源与 effects 摘要；不新增迁移。
7. `pnpm check`（typecheck / lint / 300 行 / 目录预算 / 循环 / ASCII）与 `pnpm test` 全绿；i18n 中英键成对。
8. 发行说明、路线图索引、博客 10 篇同版本收尾。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 审批详情信息过载 | 默认精简、展开详情；只展示目录事实，不加推测 |
| `details` 扩展破坏旧客户端 | 字段可选，缺省不出现；旧路径继续用 `argsSummary` |
| 内容包仓库不可达或限流 | 10 秒超时 + `unavailable` 状态；只在手动点击时请求 |
| 产物限流挡住正常批量任务 | 默认 6 个 / 8MB，错误文案说明如何分批；常量集中可调 |
| 能力列表泄露内部信息 | 只返回展示字段，不含路径、密钥与正文；条数上限 30 |
| 审计快照写入失败 | 复用 `safeAppend`，失败只告警，不影响审批结果 |
