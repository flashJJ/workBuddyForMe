# v2.12 M0：能力包签名、升级与健康自检契约冻结

> 状态：📐 待评审（本文为候选口径，评审通过后冻结）
> 范围：清单签名与信任库；同 id 原地升级与回滚；包健康自检与残留清理；启用依赖复核。
> 基线：沿用 v2.10/v2.11 的清单、校验、生命周期与「不做远程市场、不执行任意代码、不共享宿主密钥」。
> 本文是实现唯一口径；偏离需回写本文并同步 [README](README.md)。

## 1. 决策摘要

| # | 决策 | 理由 |
|---|---|---|
| D1 | 签名覆盖「除 `signature` 外的完整清单」（含 `signatureKeyId`） | checksums 已覆盖 payload，清单签名单点即可保证整包完整性；不引入逐文件签名 |
| D2 | canonical 序列化只有一份实现：键递归排序、数组保序、UTF-8、域前缀 `capability-manifest-v1\n` | 签名端与验签端共用，避免「本机签的、本机验不过」 |
| D3 | 信任库放 settings JSON（≤20 把 Ed25519 公钥），不新建表 | 公钥不是秘密；随设置备份；避免为零迁移版本加表 |
| D4 | 策略三档 `off` / `warn` / `require`，默认 `warn` | 既不阻断既有未签名包，也不让验签成为摆设；`off` 是显式逃生门 |
| D5 | `warn`/`require` 下签名无效一律 422；策略只决定「没有签名」与「未知密钥」是否放行 | 策略不能放行「对不上」，否则签名变成降级攻击面 |
| D6 | 升级仅允许同 id、同 kind、版本严格递增；降级列 P1 | 语义最小，避免把升级做成包管理器 |
| D7 | 升级保持旧状态：旧 `enabled` 升级后仍启用，旧 `disabled` 升级后仍禁用 | 用户禁用是意图，升级不应擅自打开 |
| D8 | 升级按 kind 适配，不是统一 `disable → enable` | 工作流/剧本的 enable 会复用旧对象但不刷新内容，必须专门处理 |
| D9 | 升级前预检启用中从属包的精确版本；不满足返回 409 | 依赖当前是精确匹配；静默升级会让从属包「声明对、实际错」 |
| D10 | 健康检查按需实时计算，不建表、不缓存；checksum 只在用户触发时重算 | 零迁移；避免列表加载时扫描 20MB 包 |
| D11 | 孤儿清理只删「执行时仍无数据库行」的目录，进行中升级的 backup 绝不清 | 清理是不可逆操作，必须二次确认归属 |
| D12 | `enable` 增加依赖复核；卸载仍只拦启用中从属包 | 补上「依赖被卸载后，禁用从属包仍可启用」的缺口；禁用从属交给健康报告 |
| D13 | 本版零迁移 | 不新增表/列；回退 v2.11 可直接打开同一数据库 |

## 2. 签名契约

### 2.1 清单字段

```jsonc
{
  "id": "com.example.weekly-review",
  "version": "1.1.0",
  "kind": "event-script",
  // ... 其余既有字段 ...
  "signatureKeyId": "local-dev",
  "signature": "<base64 的 Ed25519 签名>"
}
```

- `signature`：既有字段，最大 4096 字符；base64 编码的 64 字节签名。
- `signatureKeyId`：新增可选字段，3–32 位小写字母/数字/`.`/`_`/`-`；选择信任库中的公钥。
- 两个字段都参与 canonical 序列化（`signature` 自身除外）。

### 2.2 canonical 序列化

```text
canonical(value):
  null      → "null"
  boolean   → "true" | "false"
  number    → JSON 数字格式（本清单只有整数，禁止 NaN/Infinity）
  string    → JSON.stringify(string)
  array     → "[" + items.map(canonical).join(",") + "]"
  object    → "{" + keys.sort().filter(k => value[k] !== undefined)
                    .map(k => JSON.stringify(k) + ":" + canonical(value[k])).join(",") + "}"
```

签名输入：

```text
utf8("capability-manifest-v1\n" + canonical(manifest 去掉 signature 字段))
```

- 域前缀防止同一密钥在其它协议里复用签名。
- 键排序使用 ECMAScript 默认字符串排序（UTF-16 code unit），签名与验签两端必须调用同一函数。
- 黄金向量：键顺序不同但语义相同的清单必须得到同一 canonical 字符串；改任一字段（含 `signatureKeyId`）必须改变 canonical 字符串。

### 2.3 验签结果与策略矩阵

| 结果 | 含义 | `off` | `warn`（默认） | `require` |
|---|---|---|---|---|
| `none` | 无 `signature` 字段 | 放行 | 放行（徽章「未签名」） | **422** |
| `valid` | 信任库中某公钥验签通过 | 放行 | 放行（徽章「已验签」） | 放行 |
| `untrusted` | 签名可解析，但 `signatureKeyId` 不在信任库，或无 keyId 且所有公钥都不匹配 | 放行 | 放行（徽章「未知密钥」） | **422** |
| `invalid` | 密钥存在但验签失败 | 放行（徽章「未校验」） | **422** | **422** |
| `malformed` | base64 解码失败或签名长度不符 | 放行（徽章「未校验」） | **422** | **422** |

- `off` 明确跳过验签：不计算、不阻断，徽章显示「未校验」。只有用户主动关闭时才进入该档。
- 区分 `untrusted` 与 `invalid` 的依据：有 `signatureKeyId` 且该 id 在信任库 → 验签失败即 `invalid`；id 不在库（或无 id 且全部公钥不匹配）→ `untrusted`。无法仅凭字节判断「签名来自未知密钥」还是「被篡改」，因此按 `untrusted` 处理，由策略决定是否放行。
- 验签失败的包**不落盘**：与安装其余校验一样，失败发生在写文件之前。

### 2.4 信任库设置

```ts
interface CapabilityTrustedKey {
  id: string;        // 3–32，[a-z0-9._-]，全局唯一
  label: string;     // 1–40，用户可读备注
  publicKey: string; // PEM SPKI，≤1024 字符，必须能被 crypto.createPublicKey 解析且类型为 ed25519
  createdAt: string; // ISO 时间
}

capabilitySignaturePolicy: 'off' | 'warn' | 'require'; // 默认 'warn'
capabilityTrustedKeys: CapabilityTrustedKey[];                  // ≤20，id 唯一
```

- 存 `AppSettings`，随 `PUT /api/settings` 整组替换；UI 负责保留既有 `createdAt`。
- 服务端校验：id 唯一、数量上限、PEM 可导入、密钥类型必须是 `ed25519`；任一失败 422。
- 删除公钥不回溯已安装包：下次列表/安装/升级时按新信任库重新判定，徽章随之变化。
- 不提供私钥托管；签名工具只接收用户自己的私钥路径。

### 2.5 签名工具

`scripts/sign-capability.mjs`：

```text
node scripts/sign-capability.mjs --manifest <path> --key <private.pem> [--key-id <id>] [--write]
```

- 读清单 → 校验 schema → canonical → Ed25519 签名 → 打印 base64 与 keyId。
- `--write` 才回写清单；默认只打印，避免误改。
- 私钥不进入仓库、不进安装包；仓库内测试密钥全部在用例运行时临时生成。

## 3. 升级契约

### 3.1 前置与预检

`POST /api/capabilities/:id/upgrade`（multipart，字段 `file`）：

1. 已安装该 id；
2. 新清单 `id === 路径 id`；
3. `kind` 与已安装一致；
4. 版本严格大于当前版本（`1` / `1.0` / `1.0.0` 归一化为三段数字比较）；
5. 完整走安装校验链（ZIP 结构、清单 schema、checksums、权限、entry、payload schema、签名策略）；
6. 新清单的依赖：已安装、已启用、版本精确相等（沿用安装口径）；
7. 从属包预检：所有**启用中**、声明依赖当前 id 的包，其 `dependency.version` 必须等于新版本（未声明版本视为兼容）；否则 409 并列出从属包；
8. 同一 id 已有升级在途 → 409。

任何一步失败都不触碰磁盘与数据库。

### 3.2 按 kind 的升级动作

升级不是统一的 `disable → enable`。两类资源的 enable 会复用旧对象但不刷新内容，必须专门适配：

| kind | 旧状态 `enabled` | 旧状态 `disabled` | 回滚动作 |
|---|---|---|---|
| `skill` | disable（删技能目录）→ 换包 → enable（复制新包） | 换包 | 恢复旧包 → enable |
| `mcp` | disable（摘除服务器）→ 换包 → enable（新配置重建） | 换包 | 恢复旧包 → enable |
| `workflow` | 记录旧发布版本号 → disable → 换包 → `addVersion(新图)` → `publishVersion(新版本)` | 换包 → `addVersion(新图)`（保持 disabled） | 恢复旧包 → `publishVersion(旧版本号)`；旧状态 disabled 则无需发布 |
| `pet-action` | disable（删动作资产）→ 换包 → enable（导入新动作，`effectRef` 变为新 motion id） | 换包 | 恢复旧包 → enable（`effectRef` 再次变化） |
| `event-script` | 换包 → `replaceDefinition`（definition_json/name），保持 enabled | 换包 → `replaceDefinition`，保持 disabled | 恢复旧 definition_json/name/enabled |
| `report-widget` | disable（删行）→ 换包 → enable（建新行） | 换包 | 恢复旧包 → enable（恢复旧配置行） |

补充约束：

- `event-script` 升级不允许改剧本 id（`definition.id` 必须等于旧 `effectRef`），否则 422；要换 id 请卸载后重装。
- `pet-action` 升级允许改 `entryKey`，但新 key 与其它动作冲突时 422，且发生在旧动作删除之前（预检阶段）。
- `workflow` 升级产生的旧版本行保留为历史；回滚只重新发布旧版本，不删除新版本行（现有仓储无删版本接口，且历史不应被抹）。
- `report-widget` 的 `effectRef` 恒等于清单 id，不随版本变化。

### 3.3 状态机与原子换目录

升级开始时捕获快照：

```ts
interface UpgradeSnapshot {
  manifest: CapabilityManifest;   // 旧清单
  status: CapabilityStatus;       // 旧状态
  effectRef: string | null;       // 旧句柄
  workflowVersion?: number;       // workflow：旧发布版本号
  scriptDefinition?: string;      // event-script：旧 definition_json + name
  widgetConfig?: string;          // report-widget：旧 config_json
}
```

执行顺序：

1. 预检全部通过后，把新包写入 `rootDir/.staging/<id>-<nonce>/`；
2. 旧 `enabled` → 先执行该 kind 的 disable；失败则中止，磁盘与行不变；
3. 目录换位：`<id>` → `.backup/<id>-<nonce>`，`.staging/...` → `<id>`；换位失败则回滚目录并中止；
4. `replaceManifest(id, 新清单)`：更新 kind/version/name/description/permissions/manifest_json，状态置 `disabled`、`effect_ref = NULL`、`last_error = NULL`；
5. 旧 `enabled` → 执行该 kind 的升级/启用动作，写 `enabled + 新 effectRef`；
6. 成功 → 删除 `.backup` 与空 `.staging`；失败 → 按 §3.4 回滚。

并发保护：进程内 `Set<id>` 记录升级中的包；重复请求 409。单进程假设与 v2.11 一致（桌面壳 fork 一个 standalone 服务）。

### 3.4 回滚

| 失败点 | 处置 |
|---|---|
| disable 失败 | 未换包、未改行；返回 422，旧包保持原状 |
| 目录换位失败 | 尽力恢复旧目录；行未改；返回 500/422 |
| `replaceManifest` 失败 | 恢复目录与行；返回 500 |
| 新 effect 启用失败 | 恢复 `.backup` 目录 → `replaceManifest(旧清单)` → 按 §3.2 回滚动作恢复旧 effect；恢复成功返回 422（附旧版本号），恢复失败落 `disabled + lastError` 并提示重新安装旧包 |
| 回滚后旧 effect 仍失败 | **不假装成功**：状态 `disabled`，`lastError` 写明「升级失败且旧版本恢复失败，请重新安装旧包」；包目录保持在旧版本 |

- 任何路径都不允许出现「目录是新包、清单是旧包」或「状态 enabled、effect 指向旧对象」的中间态。
- `.backup` 只在新版本成功启用后删除；失败回滚后也删除（旧包已回到 live）。

### 3.5 仓储改动

| 仓储 | 新增 | 用途 |
|---|---|---|
| `capability_repo` | `replaceManifest(id, manifest)` | 升级时替换 kind/version/name/description/permissions/manifest_json |
| `event_script_repo` | `replaceDefinition(id, { name, definitionJson, enabled })` | 剧本升级与回滚 |
| `workflow_repo` | 复用既有 `addVersion` / `publishVersion(id, version?)` / `getWorkflow` | 升级发布与回滚发布 |

不新增表、不新增列。

## 4. 健康自检契约

### 4.1 接口

`GET /api/capabilities/health`（按需计算，不缓存）：

```ts
interface CapabilityHealthIssue {
  code: string;                 // 固定枚举，见 4.2
  severity: 'warn' | 'error';
  message: string;              // 人话，含具体文件/依赖 id
  detail?: string;
}

interface CapabilityHealth {
  id: string;
  status: 'ok' | 'warning' | 'broken'; // 有 error→broken；仅有 warn→warning；否则 ok
  issues: CapabilityHealthIssue[];
}

interface HealthReport {
  checkedAt: string;
  packs: CapabilityHealth[];
  orphans: string[];            // 根目录下无数据库行的目录名（排除 .staging/.backup）
}
```

### 4.2 检查项

| code | severity | 判定 |
|---|---|---|
| `pack_dir_missing` | error | 状态行存在，`rootDir/<id>` 不存在 |
| `manifest_invalid` | error | `manifest_json` 无法解析或不过 `capabilityManifestSchema` |
| `checksum_mismatch` | error | payload 文件实际 sha256 与 `checksums` 不符（`detail` 带相对路径） |
| `payload_extra_file` | warn | payload 下存在清单未登记的文件 |
| `dependency_missing` | error | 声明的依赖未安装 |
| `dependency_disabled` | warn | 依赖已安装但未启用 |
| `dependency_version_mismatch` | error | 依赖版本与声明不相等 |
| `effect_missing` | error | 句柄指向的对象不存在（按 kind 探测） |
| `effect_status_mismatch` | error | 包为 enabled，但工作流/剧本实际为 disabled |
| `signature_invalid` | error | 验签 `invalid` / `malformed` |
| `signature_untrusted` | warn | 验签 `untrusted` |

### 4.3 六类 effect 探测

| kind | 探测 |
|---|---|
| `skill` | 技能目录存在且技能服务列表包含该技能名 |
| `mcp` | 注册表存在该 server id |
| `workflow` | 工作流行存在；包 enabled 时状态必须为 enabled |
| `pet-action` | 动作资产行存在，且资产文件存在 |
| `event-script` | 剧本行存在；包 enabled 时 `enabled=1` |
| `report-widget` | 卡片行存在 |

- 探测失败必须转成 issue，不允许让整份报告 500；单个包探测异常记为 `error`，`detail` 带异常消息。
- checksum 重算只在该接口内执行；单包体积上限沿用 20MB，不做全量并发扫描（顺序执行）。

### 4.4 清理

`POST /api/capabilities/health/cleanup`：

- 重新读取数据库行作为唯一真相，只删除「当前无行」的根目录；
- 跳过 `.staging` 与 `.backup`（前者可能有进行中升级，后者是回滚材料）；
- 返回 `{ removed: string[], skipped: string[] }`；删除失败记入 `skipped`，不中断其余项；
- UI 必须二次确认，并展示将删除的目录名。

### 4.5 启用依赖复核

`enable(id)` 在产生副作用前复核：

1. 每个依赖已安装；
2. 依赖状态为 `enabled`；
3. 依赖版本与声明精确相等。

任一不满足 → 422，包保持 `disabled`，写 `lastError`。这样「依赖被卸载后，禁用从属包仍能启用」的漏洞被关闭；卸载仍然只拦启用中从属包，禁用从属包留给健康报告提示。

## 5. 设置、API 与 UI

### 5.1 API

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/capabilities/:id/upgrade` | 原地升级（multipart `file`） |
| GET | `/api/capabilities/health` | 健康报告 + 孤儿目录 |
| POST | `/api/capabilities/health/cleanup` | 清理无主目录 |
| PUT | `/api/settings` | 扩展信任库与签名策略字段（整组替换） |

响应沿用统一包络；升级成功返回 `{ capability, upgrade: { from, to } }`。

### 5.2 管理页

- 列表行新增：签名徽章（已验签/未签名/未知密钥/签名无效/未校验）、健康徽章（正常/警告/损坏）；
- 行内「升级」按钮：选 ZIP → 显示 `旧版本 → 新版本` → 确认 → 结果（成功/已回滚/需重装）；
- 顶部「检查全部」：异步执行，展示每包 issues；损坏项可展开；
- 孤儿目录提示条：列出目录名 → 「清理」二次确认。

### 5.3 设置页

- 信任公钥：列表（label / keyId / 添加时间 / 删除），添加时粘贴 PEM 与 label；
- 签名策略：三档单选；切到 `require` 前调用健康/清单统计，提示「当前 N 个包将不可用/不可升级」；
- 文案说明：签名只证明「清单由某把本地信任的公钥签发」，不证明作者身份。

## 6. 存储与迁移

- **零迁移**：不新增表、不新增列。
- `capability_packs.manifest_json` 直接保存含 `signature` / `signatureKeyId` 的清单；`updated_at` 在升级时刷新。
- 信任库与策略存 `AppSettings` JSON；随设置备份/恢复，无需单独轨。
- 回退 v2.11：旧代码忽略新设置字段与清单签名字段，能力包行结构不变。

## 7. 验收用例

1. 签名黄金向量：键序不同、Unicode、转义字符、可选字段缺省，canonical 稳定；改任一字段 canonical 改变。
2. 策略矩阵逐格：`off` / `warn` / `require` × `none` / `valid` / `untrusted` / `invalid` / `malformed`；阻断项均 422 且不落盘。
3. 信任库：重复 id、超 20 条、非 PEM、非 ed25519 均 422；删除公钥后徽章变「未知密钥」。
4. 升级六类逐类：启用态升级后新内容生效（工作流新图、剧本新台词、卡片新指标、动作新文件、技能新文件、MCP 新配置）；禁用态升级保持禁用。
5. 升级失败路径：坏包 422 不动旧包；从属版本冲突 409；同版本/降级 422；kind 不符 422；启用失败回滚旧包仍可继续用；回滚二次失败落 disabled + lastError。
6. 健康：六类各构造一个 `effect_missing`；checksum 篡改、缺依赖、依赖停用、版本不符、签名无效/未知密钥均被报告；状态分级正确。
7. 孤儿清理：手工放置无主目录 → 列出 → 清理 → 目录消失；有行目录不被删；`.backup` 不被删。
8. 依赖复核：卸载依赖后，禁用从属包 enable 返回 422 且状态仍 disabled。
9. 门禁：`pnpm check`、五包单测、Web 全量生产模式 e2e（新增 ≥3 例）、桌面冒烟均不降级。

## 8. 已知取舍

- **不做逐文件签名**：checksums 已在清单内，清单签名传递覆盖；逐文件签名只增加体积与复杂度。
- **`untrusted` 与 `invalid` 的边界**：没有 keyId 时无法区分「未知密钥」与「篡改」，按 `untrusted` 处理；需要严格判定的用户应要求作者填写 `signatureKeyId` 并在 `require` 下运行。
- **工作流回滚保留新版本行**：现有仓储无删版本接口；保留历史比抹掉更安全，代价是版本列表多一条未发布记录。
- **`pet-action` 的 effectRef 会变**：升级/回滚都重新导入动作，motion id 必然变化；引用方（动画图）按 `entryKey` 而非 id 关联，故可接受。
- **零迁移意味着健康结果不持久化**：没有「上次检查时间/上次健康状态」，每次打开都是实时结果；换来的是可直接回退。
- **升级不并发**：单 id 串行；不同 id 允许并发，服务层不引入全局锁。

## 9. 与方案的偏差（待评审确认）

1. 方案 README 写「无效签名任何策略下都拒绝」，M0 修正为「`off` 跳过验签；`warn`/`require` 下 invalid/malformed 拒绝」。理由：`off` 的语义是显式关闭验签，不能既关闭又阻断。
2. 方案 README 写「启用失败 → 恢复旧包并重新 enable」，M0 细化为按 kind 适配：`workflow` 重新发布旧版本、`event-script` 恢复旧定义、其余重新 enable。
3. 方案 README 将「签名徽章」列为管理页收口，M0 把徽章与策略矩阵提前到 M1，收口页只做展示与策略切换。

## 10. Non-Goals

- 不做远程市场、自动更新、一键升级。
- 不做 CA / 证书链 / 作者身份体系；签名只回答「是否由本地信任的公钥签发」。
- 不做多版本并存与降级 UI（P1）。
- 不做依赖自动安装、版本区间与传递闭包。
- 不做逐文件签名、包加密、包内容差异视图。
- 不做包内任意代码执行；六类仍只登记既有资源类型。
- 不做备份格式变更。
