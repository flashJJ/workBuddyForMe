## 2. 关键实现

1. **报告结构**：`{ checkedAt, packs: [{ id, status, issues }], orphans }`；有 error → `broken`，仅 warn → `warning`，否则 `ok`。
2. **清单二次校验**：仓储 `getManifest` 只做 JSON.parse；健康检查再走 `capabilityManifestSchema.safeParse`，坏结构落 `manifest_invalid`，不会让整份报告 500。
3. **checksum**：逐条校验 `manifest.checksums`（存在性 + sha256），并遍历 `payload/` 报告未登记文件；校验失败带相对路径 detail。
4. **依赖分级**：未安装 error、未启用 warn、版本不符 error；即使包本身 disabled 也照常报告。
5. **六类 effect 探测**：skill 目录 + 服务列表；MCP server id；workflow 状态 `published`；pet-action 行 + 文件可读；event-script 行 + `enabled`；report-widget 行。探测异常统一转 `effect_missing`，detail 带异常消息。
6. **签名始终检查**：健康报告不受安装策略影响；`invalid` / `malformed` → error，`untrusted` → warn，`off` 仅影响安装阻断。
7. **清理**：以数据库行为唯一真相，只删无行根目录；跳过 `.staging` / `.backup`；额外清理超过 24h 的升级残留；删除失败进 `skipped` 不中断。
8. **启用复核**：`enable` 在签名之后、effect 之前检查依赖已安装/已启用/版本精确；失败 422 并保持 disabled。

## 3. 与 M0 的偏差

1. **过期清理时机**：M0 写「服务启动或首次健康检查」；实现放在 `POST /health/cleanup`，保持 `GET /health` 无副作用。副作用是用户需点一次清理才会移除 24h 残留，报告会先列出孤儿。
2. **清理范围**：只处理目录；根目录下的散落文件不进入 `orphans`，也不被清理（避免误删用户文件）。
3. **体积预算**：checksum 读取按文件顺序执行，未额外做 20MB 解压体积门禁；压缩包上传仍受 20MB 限制。若后续出现超大 payload，再补流式哈希。

## 5. 已知边界与后续

- `payload_extra_file` 只扫描 `payload/`；清单文件与根目录散落文件不参与。
- 健康扫描为顺序执行，包数量很大时接口耗时线性增长；M4 管理页做异步「检查全部」。
- 管理页健康徽章、孤儿提示条、清理二次确认在 M4。
- 启用依赖复核与卸载拦截组合后：依赖卸载后，禁用从属包可继续保留，但启用会被 422 拒绝并通过健康报告提示。
