## 2. 关键实现

1. **canonical 输入是规范化清单**：签名工具与运行时都先 `capabilityManifestSchema.parse`，默认值（description/permissions/dependencies/checksums）已补齐；键递归排序、数组保序、`signature` 排除、`signatureKeyId` 参与。
2. **验签职责在 core**：shared 只保留纯 canonicalize；`node:crypto` 不进入客户端 bundle。
3. **策略三入口**：安装、启用都执行 `assertManifestSignature`；`off` 跳过计算；`warn` 拒绝 invalid/malformed；`require` 仅允许 valid。升级入口在 M2 复用同一 helper。
4. **徽章按请求计算**：`list()` 读取当前策略与信任库，逐包验签并写 `signatureStatus`；`off` 显示 `unchecked`，不阻断。
5. **设置钳制**：手改 `settings_kv` 的非法策略回落 `warn`；形状非法、重复 id、超 20 条在读取时丢弃；PEM 不可导入在写入时 422。
6. **签名工具单一实现**：从 `packages/shared/dist/index.mjs` 导入 `capabilitySignaturePayload`；产物缺失或过旧时提示先 build。

## 3. 与 M0 的偏差

- 无契约偏差。两处实现细节：
  1. `capability-wiring` 内部创建 settings 实例（与设置 API 实例共用同一 `settings_kv` 数据源）；因 settings 服务无进程内缓存，读到的策略始终是当前值。
  2. 签名策略测试拆到 `capability-service-signature.test.ts`，原测试文件从 355 行降到 274 行，满足 300 行门禁。

## 5. 已知边界与后续

- 信任公钥管理 UI 在 M4；M1 只提供 settings API 与徽章。
- 手改 settings 写入的不可导入 PEM 不会被读取钳制丢弃，验签按「未知密钥」处理；正常写入路径已 422。
- 健康检查（M3）将始终验签，`off` 只影响安装/启用阻断，不影响报告。
- 升级（M2）复用 `verifyCapabilitySignature` + `assertCapabilitySignatureAllowed`，不新增第二套验签。
