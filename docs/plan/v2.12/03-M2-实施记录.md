## 2. 关键实现

1. **版本严格递增**：`compareCapabilityVersions` 只接受 1–3 段数字；`1.2.3.4` 与 `v2.0` 直接 422，同版本/降级同样拒绝。
2. **预检先于副作用**：id/kind 一致性、依赖已启用且版本精确、启用中从属包版本必须匹配、新资源句柄冲突（排除旧句柄）、剧本 id 不可变；任何一项失败都不 disable、不换目录。
3. **原子换目录**：新包写入 `.staging/<id>-<uuid>` → 旧目录 rename 到 `.backup/<id>-<uuid>` → staging rename 到 live；失败路径先还原目录再恢复旧 effect。
4. **按 kind 适配**：
   - `skill` / `mcp` / `pet-action`：disable → 换包 → enable，句柄可能变化（MCP server id / motion id）；
   - `workflow`：disable → 换包 → `addVersion(新图)` → 发布；禁用态只加版本并显式 `setStatus(disabled)`；
   - `event-script`：换包后 `replaceDefinition`，剧本 id 与启用标记保持不变；
   - `report-widget`：disable（删行）→ 换包 → enable（建新行）。
5. **回滚**：新版本启用失败 → 删除新目录、backup 还原、`replaceManifest(旧清单)`、按 kind 恢复旧 effect；恢复成功返回 422「已回滚」，恢复失败落 `disabled + lastError` 并提示重装旧包。工作流回滚重新发布旧版本，禁用态恢复 current_version；剧本回滚恢复旧定义与启用标记。
6. **禁用从属包提示**：不阻塞升级，但响应列出 `affectedDisabledDependents`，提示其后续启用会因版本不符失败。
7. **签名复用 M1**：升级在写盘前执行当前策略验签；`require` 下未签名升级直接 422。

## 3. 与 M0 的偏差

1. 新增 `workflow_repo.setCurrentVersion`：M0 只要求「禁用态保持禁用」，但 `addVersion` 会改 `current_version`；没有该方法回滚无法真正恢复旧图。
2. 新增 `installed_event_script_repo.getByPackId`：禁用态 `effectRef` 为空，快照需按来源包查剧本行。
3. 管理页「升级」按钮与对话框按 M0 分工留在 M4；本里程碑只交付端点与编排。
4. `.staging` / `.backup` 的 24 小时过期清理按 M0 §3.3 留在 M3。

## 5. 已知边界与后续

- 工作流回滚会在版本列表保留升级时新增的版本行（历史不删）；旧版本重新成为 current/published。
- 回滚二次失败（旧 effect 也起不来）落 `disabled + lastError`，不假装成功。
- 升级中的 `.staging` / `.backup` 目录在成功或回滚后清空；崩溃残留由 M3 健康检查与过期清理负责。
- 升级 UI（选择 ZIP、确认从旧到新、结果提示）在 M4。
