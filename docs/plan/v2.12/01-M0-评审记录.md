# v2.12 M0 评审记录

> 评审对象：[00-M0-契约冻结](00-M0-契约冻结.md)（签名 / 升级 / 健康自检）
> 评审时间：2026-10-30
> 评审方式：逐条对照现有代码、仓储接口、设置服务与门禁，检查「能否落地、失败是否可回滚、安全边界是否闭合、迁移是否为零、验收是否可验证」

## 1. 发现与处置

| # | 级别 | 问题 | 取证 | 处置 |
|---|---|---|---|---|
| R1 | 高 | canonical 序列化若基于「作者手写的原始 JSON」，与验签端「schema 解析后的清单」不一致：schema 会给 `description` / `permissions` / `dependencies` / `checksums` 填默认值，缺省字段的包永远验不过 | `capabilityManifestSchema` 含 `.default()`（`packages/shared/src/schemas/capability.ts:53-70`）；`parseCapabilityZip` 以 `parsed.data` 落盘（`packages/core/src/capabilities/manifest.ts:55-61`） | 已回写 M0 §2.2：签名与验签都先过 schema，canonical 输入是**规范化后的清单**；签名工具同样先 parse 再签名 |
| R2 | 高 | M0 把 `verifyCapabilitySignature` 放 shared，但验签必须用 `node:crypto`；shared 的 schemas barrel 会被 web 客户端打包，引入 Node 内置模块会导致客户端构建失败 | `packages/shared/src/schemas/index.ts` 被 web 组件直接 import；`manifest.ts` 的 `createHash` 只在 core 使用 | 已回写 M0 §4：canonicalize 留在 shared（纯函数），验签与公钥导入放 core `capabilities/signature.ts`（服务端） |

## 2. 已回写 M0 的条款

1. §2.2 canonical 输入改为「schema 解析后的规范化清单」。
2. §2.4 验签职责移到 core，shared 只保留纯 canonicalize。
3. §2.5 签名工具复用 shared 构建产物。
4. §3.1 版本比较严格解析；升级响应带受影响禁用从属包。
5. §3.2 补 skill / mcp / pet-action 的句柄变化与预检排除旧句柄；workflow disabled 升级后显式置回 disabled。
6. §3.3 增加过期 `.staging` / `.backup` 清理时机。
7. §3.5 补 `event_script_repo.replaceDefinition` 与旧行缺失的 404 口径。
8. §4.2 健康检查始终验签。
9. §4.5 `enable` 前按策略复核签名；依赖报错区分未安装/未启用。
10. §5.2 管理页拆分文件，避免 300 行门禁。
11. §7 验收补充「签名工具与验签同一实现」「disabled 工作流升级后状态正确」。

## 4. M1/M2 实施清单（评审补充，不改变契约）

1. `capability.ts` 增 `signatureKeyId`；新增 `capability-signature.ts`（shared，纯 canonicalize）与 core `capabilities/signature.ts`（验签/公钥导入）。
2. `settingsUpdateSchema` + `DEFAULT_SETTINGS` + `AppSettings` 增 `capabilitySignaturePolicy`（默认 `warn`）与 `capabilityTrustedKeys`（默认 `[]`）；服务端钳制 20 条与 PEM 可导入。
3. `CapabilityServiceDeps` 增 `settings`；`capability-wiring.ts` 注入 `createSettingsService`。
4. `install` / `upgrade` 在写盘前执行 `verifyManifestSignature`；`enable` 按策略复核。
5. `capability_repo.replaceManifest`；`installed_event_script_repo.replaceDefinition`。
6. 升级按 kind 适配器拆分：`upgrade/` 目录下六个文件 + 薄分派，避免单文件超限。
7. 健康探测按 kind 拆文件；`health` 接口只做编排与汇总。
8. 管理页拆 `capability-row.tsx` / `capability-upgrade-dialog.tsx` / `capability-health-banner.tsx`；设置页新增独立 `capability-trust-section.tsx`。
9. e2e：签名策略矩阵至少 3 例（warn 允许未签名 / require 拒绝未签名 / invalid 拒绝）、升级成功与回滚 2 例、健康与孤儿清理 1 例。

## 5. 待确认的产品口径

| # | 事项 | 建议 | 备选 |
|---|---|---|---|
| P1 | `require` 下 `enable` 是否阻断未签名包 | 阻断（签名策略必须覆盖启用，否则策略只是安装时的门） | 仅在安装/升级阻断，启用只提示 |
| P2 | 是否允许「同版本修复安装」（版本不变、内容替换） | 不做（P1 留白）；坏包走健康报告 + 卸载重装 | 允许 `force` 参数，风险是绕过版本语义 |
| P3 | 过期 `.staging` / `.backup` 自动清理窗口 | 24 小时；健康报告列出待清理目录，首次检查时清理 | 永不自动清理，只手工清理 |

三项建议默认采纳；确认后 M0 正式冻结，进入 M1。
