# v2.32 方案：数据可带走——恢复预检前置、备份补全、产物打包与空间清理

> 主题：让本地数据不仅能导出，还能安心恢复、批量带走、看清占用。
> 分支：`feat/v2.32-data-portability`（待创建）
> 目标：一次备份 schema 加法升级、零破坏性删除、单一主题。

## 1. 背景与目标

本地优先的前提是「数据在你手里」，但当前数据生命周期只完成了一半：

- **不敢恢复**：恢复预检已经存在（`precheckBackup`），但它在恢复请求内服务端执行，结果随恢复一起返回；用户在点「恢复」之前看不到版本、轨道条数与警告，实际上仍是「先恢复再看结果」。
- **带不走**：备份 schema v7 覆盖对话、知识、设置、附件、技能、任务、情绪与事件，但协作运行（`agent_runs`）与交接（`agent_handoffs`）不随备份迁移；恢复后协作历史为空，`task_runs.agent_run_id` 回落 `NULL`。
- **散着拿**：产物只能单张导出 SVG / PNG，没有跨会话清单，也没有批量打包。
- **看不见**：附件目录没有引用计数，删除消息不清理文件；数据根没有分项占用统计，长期使用只能手动翻目录。

v2.32 补四条链路：预检前置为独立只读步骤；备份 schema v8 加法补协作运行与交接；产物支持多选打包并附 manifest；存储占用可视、孤儿附件先移入回收目录再清理。

## 2. 盘点结论

| 能力 | 现状 | 本版动作 |
|---|---|---|
| 恢复预检 | `packages/core/src/backup/restore-precheck.ts` 已实现版本兼容、轨道计数与三类警告；恢复接口把 `precheck` 与 `result` 一起返回 | 抽成独立只读 API，前端改为「选择归档 → 预检确认 → 执行恢复」两步；恢复接口保留预检结果兼容旧前端 |
| 协作运行 / 交接 | `agent_runs`、`agent_handoffs` 随 v019 迁移存在，但不在备份轨中；`restore-tasks.test.ts` 明确断言恢复后为 0 | 备份 schema v8 增加加法轨，恢复后回填 `task_runs.agent_run_id` |
| 产物导出 | `artifact-export.ts` 只做单个图表产物的 SVG 提取与 PNG 栅格化 | 新增批量打包与 manifest，单张导出保持不变 |
| 附件与存储 | 附件落盘 `attachments/<id>.<ext>`，删除消息不删文件；无占用统计 | 新增只读占用统计与孤儿附件回收，回收只移动、不物理删除 |

## 3. 主题与边界

- 单一主题：数据可带走，不新增对话、记忆或能力功能。
- 备份 schema 从 7 升到 8，只做加法轨；v7 及更早归档继续可读。
- 所有清理动作都是「先扫后移、先移后清」，不提供物理删除入口。
- 不引入新的原生依赖：批量打包复用现有 tar.gz 归档实现。

## 4. 功能清单

### 4.1 恢复预检前置（P0）

- 新增 `POST /api/backup/precheck`：上传归档，只读解析，返回与现有 `BackupPrecheck` 相同的结构（兼容性、源版本、各轨计数、警告）。
- 预检不写数据库、不落盘解压目录；归档大小上限与恢复接口一致。
- 前端恢复流程拆成两步：
  1. 选择归档后先调预检，展示源版本、轨道计数与警告；
  2. 用户勾选轨道并确认后才调用恢复。
- 版本不兼容时前端直接禁用「确认恢复」，不进入恢复请求。
- 恢复接口继续返回 `{ precheck, result }`，旧前端与旧客户端不受影响。

### 4.2 备份补全协作运行（P1，schema v8）

- 在 tasks 轨内增加加法字段：`agentRunCount`、`agentHandoffCount`；负载文件为 `agentRuns.json`、`agentHandoffs.json`。
- v7 及更早归档缺省 0，读取时按空数组处理。
- 恢复顺序：先写 `agent_runs`，再写 `agent_handoffs`，最后按旧 id → 新 id 映射回填 `task_runs.agent_run_id`。
- 重复恢复保持幂等：按主键 upsert，不重复插入交接记录。
- 设置页备份面板的轨道说明补充「协作运行记录」。

### 4.3 产物批量打包（P1）

- 新增 `POST /api/artifacts/export`：接收产物 / 附件 id 列表，返回 tar.gz 流。
- 归档内附 `manifest.json`：条目 id、标题、格式、字节数、来源会话 id 与创建时间。
- 单次最多 100 条、累计不超过 200MB；超限返回可读错误，不生成半份归档。
- 前端在产物卡片支持多选，消息区或产物面板提供「打包下载」。
- 打包复用现有 `packTarGz`，不引入 zip / 原生压缩依赖。

### 4.4 存储占用统计（P2）

- 新增 `GET /api/storage/usage`：返回数据根总分项占用——数据库、`files`、`attachments`、`spills`、`capabilities`、`logs` 与其他。
- 只读遍历目录，限制最大深度与条目数；单次结果短时缓存，避免频繁全盘扫描。
- 设置页「存储」区块展示分项大小与合计，单位自动换算。

### 4.5 孤儿附件清理（P2）

- 判定口径：`attachments/` 下的文件既没有附件表记录、也没有消息或工具产物引用。
- 流程固定为三步：扫描出候选 → 展示数量与字节数（dry-run）→ 用户确认后移动到 `attachments/.trash/<date>/`。
- 回收目录保留 7 天，期间可手动恢复；到期后由同一入口提供「清空回收目录」。
- 不提供「直接删除附件」按钮，避免误操作不可逆。

## 5. Non-Goals

- 云同步、跨设备增量同步、自动定时备份。
- 备份加密与密钥托管。
- zip 格式打包（本版统一 tar.gz）。
- 附件物理删除、消息删除级联删文件。
- 恢复时的轨道合并策略调整（沿用现有覆盖/跳过语义）。

## 6. 阶段拆分

| 阶段 | 内容 | 验证 |
|---|---|---|
| P0-M1 | 预检独立 API + 前端两步恢复 | 预检前后数据库无变化；不兼容归档禁用恢复 |
| P1-M2 | 备份 schema v8 协作轨 + `agent_run_id` 回填 | v7 旧归档可恢复；v8 roundtrip 协作历史完整；重复恢复幂等 |
| P1-M3 | 产物批量打包 + manifest | 条目数 / 字节数与 manifest 一致；超限不落半份归档 |
| P2-M4 | 存储占用统计 + 孤儿附件回收 | 分项之和与总大小一致；dry-run 不移动；回收 7 天可恢复 |

## 7. 验收口径

1. `POST /api/backup/precheck` 不写库：调用前后数据库记录数与文件修改时间不变；版本高于当前时 `compatible = false`。
2. v7 归档可直接恢复；v8 归档恢复后 `agent_runs`、`agent_handoffs` 条数与备份一致，`task_runs.agent_run_id` 指向新 id；重复恢复不产生重复行。
3. 批量打包返回的 tar.gz 内 `manifest.json` 条目数、字节数与实际文件一致；超过 100 条或 200MB 返回可读错误且无残留文件。
4. 占用统计各分项之和不超过合计，且合计与目录实际大小误差在允许范围内；单次请求在 10 万文件规模内可接受。
5. 孤儿清理 dry-run 只返回计数不移动文件；执行后文件位于回收目录，7 天内可通过接口恢复；再次扫描候选为 0。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 备份体积与恢复耗时增加 | 协作轨随 tasks 轨可选导出；恢复按批写入；上线前用真实归档测量一次体积与耗时 |
| 恢复顺序与外键 | 固定「runs → handoffs → 回填 task_runs」顺序，测试覆盖重复恢复与缺省字段 |
| 打包内存占用 | 流式读文件、流式写归档，不把全部产物读入内存 |
| 误删附件 | 先扫后移、回收目录保留 7 天、dry-run 与确认两步；不提供物理删除按钮 |
| 占用扫描拖慢设置页 | 限制遍历深度与条目数，结果短时缓存，失败降级为「无法统计」 |
| 预检重复上传大归档 | 前端只在选择文件后调一次；预检结果不缓存，避免内存驻留 |

## 9. 下一版本衔接

v2.32 完成后，本地数据链路具备「预检 → 恢复 → 打包 → 清理」的闭环。

v2.33 候选待盘点，优先从以下方向评估：备份加密与密钥托管、增量备份、跨设备迁移、附件引用计数内建到写入链路。
