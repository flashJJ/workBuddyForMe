# v2.14 M0：可维护——契约冻结

> 状态：✅ 已冻结（2026-10-31，评审记录见 [02-M0-评审记录](02-M0-评审记录.md)）
> 范围：技能版本化与回退、工作流生产版本、能力包降级 / 修复、运行记录下钻、诊断包（M5）。
> 原则：迁移纯加法；默认行为与 v2.13 一致；回退不删除用户数据；诊断包只白名单组装。
> 关联：[v2.14 方案](README.md) · [现状取证](00-现状取证.md)

## 0. 冻结决策摘要

| # | 决策 | 取舍 |
|---|---|---|
| D1 | 技能版本快照存数据根 `skill-versions/<stateId>/<version>/`，`skill_versions` 表记录元数据 | 用 `skills_state.id` 拼路径，避免技能名进路径导致非法字符 / 注入 |
| D2 | 技能快照在「扫描发现版本或内容变化」时自动创建，同一 (name, version, checksum) 不重复 | 覆盖能力包安装与用户手工放入技能目录两种来源 |
| D3 | 技能快照自动保留最近 5 版，永不删除当前启用版本 | 防止磁盘无上限增长；P1 再提供手动清理 |
| D4 | 技能回退 = 快照目录原子写回 `skills/<name>`，启用态不变 | 不把 `skills/` 改成版本目录映射，避免扫描与用户认知混乱 |
| D5 | 工作流新增 `published_version`，与 `current_version` 分离 | 编辑草稿不再直接影响生产运行 |
| D6 | 运行时取 `published_version`，为空时回退 `current_version` | 兼容从未发布过的历史工作流 |
| D7 | 「设为生产」不改 `current_version`；显式发布仍同步两者 | 区分「编辑位置」与「生产版本」两个概念 |
| D8 | 能力包降级需 `confirmDowngrade=true` + `expectedVersion`；同版本修复需 `repair=true` 且校验和不一致 | 不能只靠前端弹窗；服务端校验 |
| D9 | 降级遇到启用中的反向依赖 → 409 拒绝，不自动禁用依赖方 | 与升级的「自动禁用从属」不同：降级是用户主动回退，禁用副作用应由用户显式处理 |
| D10 | 运行记录下钻只做导航：`runId` 直达任务时间线，不改变审计只读语义 | 审计仍是证据，不是操作入口 |
| D11 | 诊断包白名单组装 + 本地下载，不上传；不含密钥 / 对话 / 记忆 / 绝对路径 | 排障可用，泄密不可接受 |
| D12 | 诊断包 ZIP 采用 `yazl`（纯 JS）新增到 web 依赖 | 仓库无现成 zip 库；避免引入原生依赖 |
| D13 | 迁移 v042 纯加法；审计、审批、任务字段不变 | 旧版本可打开新库，回退不丢数据 |

## 1. 技能版本契约

### 1.1 数据

```sql
CREATE TABLE skill_versions (
  id TEXT PRIMARY KEY,
  skill_state_id TEXT NOT NULL,
  name TEXT NOT NULL,
  version TEXT NOT NULL,
  checksum TEXT NOT NULL,
  manifest_json TEXT NOT NULL,
  dir_path TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE (skill_state_id, version)
);
CREATE INDEX idx_skill_versions_name ON skill_versions(skill_state_id, created_at);
ALTER TABLE skills_state ADD COLUMN active_version TEXT;
```

- `checksum = sha256(canonicalJson({ files: [{ path, size, sha256 }] }))`，`path` 为相对技能目录、`/` 分隔、升序。
- 单技能快照上限 50 MB；超过则不建快照，写健康问题 `SKILL_VERSION_SNAPSHOT_TOO_LARGE`，其余功能不受影响。
- `active_version` 只由「扫描确认」与「回退成功」更新。

### 1.2 快照规则

1. 技能扫描完成、manifest 校验通过后，计算 checksum；
2. 查 `(skill_state_id, version)`：不存在则复制目录到快照路径并插入行；已存在但 checksum 不同则更新该行与快照内容（同版本内容变化只保留最新）；
3. checksum 相同 → 只更新 `active_version`，不复制；
4. 快照后按 `created_at` 保留最近 5 版，删除更早的目录与行，但跳过 `active_version`；
5. 手工删除技能目录时，快照保留，回退可用。

### 1.3 回退

`POST /api/skills/:name/versions/:version/rollback`

- 校验快照存在，否则 409 `SKILL_VERSION_MISSING`；
- 目标目录 `skills/<name>` 写临时目录 → 原目录改名为 `.bak-<timestamp>` → 临时目录换位 → 删除 `.bak`；
- 任一步失败：恢复原目录并返回 500 `SKILL_ROLLBACK_FAILED`；
- 成功后 `active_version = version`、`skills_state.updated_at` 更新；`enabled` 不变；
- 回退后立即重新加载技能；若 manifest 校验失败，仍保留换位结果但写健康问题，由用户修复。

### 1.4 版本列表

`GET /api/skills/:name/versions` → `{ versions: SkillVersionView[] }`

```ts
interface SkillVersionView {
  id: string;
  version: string;
  checksum: string;
  sizeBytes: number;
  createdAt: string;
  active: boolean;
}
```

- 列表按 `createdAt` 倒序；无快照时返回空数组并附 `versioningAvailable: false`（例如快照过大）。

## 2. 工作流生产版本契约

### 2.1 数据与回填

```sql
ALTER TABLE workflows ADD COLUMN published_version INTEGER;
UPDATE workflows SET published_version = (
  SELECT MAX(version) FROM workflow_versions
  WHERE workflow_id = workflows.id AND published_at IS NOT NULL
);
```

### 2.2 语义

| 字段 | 含义 |
|---|---|
| `current_version` | 最近保存的图版本，编辑器打开的内容 |
| `published_version` | 生产运行使用的版本，可为空 |
| `status` | `draft`（有未发布改动）/ `published`（存在生产版本） |

- `addVersion`：只更新 `current_version`，`status` 回 `draft`，`published_version` 不变。
- `publishVersion(id, version)`：发布并设为生产，`current_version` 与 `published_version` 都指向该版本（保持 v2.13 语义）。
- `setProductionVersion(id, version)`：只设 `published_version` 与 `status=published`，不动 `current_version`；版本不存在 → 404。
- 运行解析：`getProductionVersion(id) = published_version ?? current_version`。

### 2.3 运行时改造点

- `flow/run-service.ts` 的两处 `getCurrentVersion` 改为 `getProductionVersion`；
- `mcp/server/mcp-flow-context.ts` 同步改为 `getProductionVersion`；
- 公共端点调用与 MCP 调用因此都固定在生产版本；
- `requirePublished` 校验保留：无生产版本且 `status !== 'published'` → 既有的 `FLOW_NOT_PUBLISHED`。

### 2.4 API 与 UI

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/flows/:id/publish` | 接收可选 `{ version }`；行为不变（发布并设生产） |
| POST | `/api/flows/:id/production` | `{ version }`；只设生产版本 |
| GET | `/api/flows/:id/versions` | 版本列表，含 `production` 标记 |

- 编辑器版本抽屉：版本号、创建时间、`current` / `production` 徽章、「设为生产」按钮；
- 编辑器顶部显示「生产版本 vN；当前草稿 vM」；
- 无生产版本时显示「尚未设置生产版本，运行将使用当前版本」。

## 3. 能力包降级与修复契约

### 3.1 请求字段（multipart）

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 能力包 zip |
| `confirmDowngrade` | 降级时 | 必须为 `'true'` |
| `expectedVersion` | 降级时 | 必须等于包内 manifest.version |
| `repair` | 修复时 | 必须为 `'true'` |

### 3.2 版本判定（`compareCapabilityVersions(next, current)`）

| 结果 | 条件 | 处置 |
|---|---|---|
| `> 0` | 新版本更高 | 正常升级（既有流程） |
| `= 0` | 版本相同 | 仅当 `repair=true` 且包内 checksum 与已安装不同 → 修复安装；否则 422 `CAPABILITY_VERSION_NOT_NEWER` |
| `< 0` | 新版本更低 | 仅当 `confirmDowngrade=true` 且 `expectedVersion` 匹配 → 降级；否则 422 `CAPABILITY_DOWNGRADE_CONFIRM_REQUIRED` |

### 3.3 前置校验（顺序固定）

1. manifest / 签名 / 权限校验（沿用 v2.12）；
2. 目标 manifest 的依赖是否满足已安装版本（不满足 → 422，沿用 `assertDependencies`）；
3. 反向依赖：已启用且依赖本包精确版本 ≠ 目标版本的包 → 409 `CAPABILITY_DEPENDENTS_ACTIVE`，`details.dependents` 列出 id；**不自动禁用**；
4. 暂存解压 → 原子换位 → 失败回滚（沿用既有升级编排）；
5. 成功后健康自检，返回 issue 码列表。

### 3.4 边界

- 降级只保证代码 / 清单 / 生效资源回到旧版，**不承诺数据回滚**；确认文案必须写明。
- 同版本修复只替换文件，不重置已禁用的从属能力。
- 不做依赖自动安装、不做远程版本源。

## 4. 运行记录下钻契约

### 4.1 关联键

- 唯一关联键是 `task_runs.id`（即审计 `run_id`）；
- `runId` 为空的事件不提供入口；关联任务不存在时跳到时间线空态，不返回 404。

### 4.2 入口

| 位置 | 行为 |
|---|---|
| 审计事件行 | 有 `runId` 显示「查看任务」→ `/timeline?scope=task&id=<runId>` |
| 审批项 | `runId` 从纯文本改为链接，同样跳时间线 |
| 审计页 | 支持 `?runId=` 预填过滤；清空过滤同步移除参数 |
| 任务详情 | 治理摘要：模式、工作目录、策略哈希、来源定时任务；最近 10 条关联审计事件（只读，可跳审计页 `?runId=`） |

### 4.3 约束

- 下钻只读，不提供任何写操作；
- 审计页面对不存在的 `runId` 显示「无关联事件」，不报错；
- 任务详情中的工作目录按现有展示规则脱敏（保留盘符与末级目录，中间折叠）。

## 5. 诊断包契约

### 5.1 形态

`GET /api/diagnostics/export` → `application/zip`，文件名 `wbfm-diagnostics-<version>-<YYYYMMDD-HHmmss>.zip`；本地生成，不上传。

### 5.2 内容（白名单）

| 文件 | 内容 |
|---|---|
| `manifest.json` | `formatVersion: 1`、`appVersion`、`schemaVersion`、`platform`、`arch`、`generatedAt`、`entries[]`（路径 / 大小 / sha256） |
| `versions.json` | 应用版本、`LATEST_SCHEMA_VERSION`、实际 schema 版本、Node / Electron 版本（可用时） |
| `audit-verify.json` | `{ ok, checked, firstBrokenSeq?, truncated }` |
| `capabilities.json` | `[{ id, kind, version, status, healthIssues: string[] }]` |
| `runs-summary.json` | 最近 7 天按状态计数；定时来源计数；不含 runId / 任务标题 |
| `settings-summary.json` | 供应商数量、模型数量、策略哈希、默认模式、是否配置工作目录、功能开关 |
| `errors.log` | 最近 200 条 error 级事件摘要（单行，已脱敏） |
| `README.txt` | 一句话说明「不含密钥、对话与记忆内容」 |

### 5.3 脱敏规则

- 禁止出现：API Key / 令牌 / 密码、对话与记忆正文、完整 URL / 域名、文件绝对路径、会话与运行 id；
- 绝对路径统一替换为 `<data-root>` / `<app-dir>` / `<user-dir>`，无法归类则丢弃整行；
- 错误信息中的引号内容、邮箱、URL 一律丢弃；
- 采用白名单组装，不做「先收集再过滤」。

### 5.4 限额

- 生成预算 30 秒；超时返回 503 `DIAGNOSTICS_TIMEOUT`；
- ZIP 上限 10 MB；`errors.log` 单行截断 500 字符；
- 审计校验在全量账本上执行；超过 10 万条时 `truncated=true` 并只校验最近 10 万条。

### 5.5 UI

设置 → 关于 / 诊断：按钮「导出诊断包」，生成期间禁用并显示进度；完成后浏览器下载；失败显示结构化错误码。

## 6. API 汇总

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/skills/:name/versions` | 技能版本列表 |
| POST | `/api/skills/:name/versions/:version/rollback` | 回退技能 |
| GET | `/api/flows/:id/versions` | 工作流版本列表 |
| POST | `/api/flows/:id/production` | 设为生产版本 |
| POST | `/api/capabilities/:id/upgrade` | 新增降级 / 修复字段 |
| GET | `/api/diagnostics/export` | 诊断包下载 |
| GET | `/api/audit/events` | 不变；`runId` 过滤沿用 |

错误码：

| 场景 | 状态 | code |
|---|---|---|
| 技能版本不存在 | 409 | `SKILL_VERSION_MISSING` |
| 技能回退失败 | 500 | `SKILL_ROLLBACK_FAILED` |
| 降级缺少确认 | 422 | `CAPABILITY_DOWNGRADE_CONFIRM_REQUIRED` |
| 降级目标版本不匹配 | 422 | `CAPABILITY_DOWNGRADE_TARGET_MISMATCH` |
| 启用中的反向依赖 | 409 | `CAPABILITY_DEPENDENTS_ACTIVE` |
| 版本未变且非修复 | 422 | `CAPABILITY_VERSION_NOT_NEWER`（沿用） |
| 诊断包生成超时 | 503 | `DIAGNOSTICS_TIMEOUT` |
| 工作流版本不存在 | 404 | `FLOW_VERSION_NOT_FOUND` |

## 7. 数据模型与迁移 v042

- `LATEST_SCHEMA_VERSION` 41 → 42；新增 `v042-maintenance.ts` 与迁移测试；
- 纯加法：`skill_versions`、`skills_state.active_version`、`workflows.published_version`；
- 回填 `published_version` 为历史已发布的最大版本；
- 旧版本打开新库：忽略新表 / 列，技能目录与工作流照旧可用；
- 回退不删除技能快照目录与审计数据。

## 8. 视图与枚举

- `WorkflowView` 新增 `publishedVersion: number | null`；
- 新增 `SkillVersionView`、`DiagnosticManifest`、`DiagnosticEntry` schema（shared）；
- `CapabilityUpgradeResult.upgrade` 增加 `direction: 'upgrade' | 'downgrade' | 'repair'`；
- 任务详情沿用现有字段，不新增列。
