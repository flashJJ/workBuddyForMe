## 1. 本里程碑做了什么

| 能力 | 行为 |
|---|---|
| 版本方向 | `compareCapabilityVersions` 判定 `upgrade` / `downgrade` / `repair`；非法版本仍 422 |
| 降级确认 | 低于当前版本时必须 `confirmDowngrade=true` 且 `expectedVersion` 等于包内版本，否则 422 |
| 同版本修复 | 版本相同且 payload 校验和清单变化时，`repair=true` 允许重装；内容完全一致则拒绝 |
| 反向依赖 | 启用中的能力包仍精确依赖当前版本 → 409 `CAPABILITY_DEPENDENTS_ACTIVE`，`details.dependents` 列出 id，不自动禁用 |
| 编排复用 | 仍走 v2.12 的预检 → 暂存 → 原子换位 → 失败回滚链路；降级不承诺数据回滚 |
| 方向回执 | `CapabilityUpgradeResult.upgrade.direction` 返回方向，UI 据此提示 |
| 对话框 | 首次提交用于探测；降级显示警告 + 勾选确认，同版本差异显示修复安装 |

## 3. 关键口径

1. **顺序**：解析 ZIP → 校验 id/kind → 方向判定（含确认字段）→ 验签 → 依赖满足 → 反向依赖 → 快照与换位。
2. **修复判定**：`canonicalJson(oldManifest.checksums) !== canonicalJson(newManifest.checksums)`；一致时即使 `repair=true` 也返回 422。
3. **反向依赖**：只检查精确版本依赖（`dep.version !== 目标版本`）；未声明版本的依赖不阻塞。409 不自动禁用依赖方。
4. **数据边界**：降级与修复只回退代码、清单与生效资源；确认文案明确不承诺数据回滚。
5. **UI 探测**：首次提交不带确认字段，服务端在改动磁盘前拒绝并返回 `details`；UI 据此展示降级勾选或修复按钮后重试，避免客户端自行解析 ZIP。

## 4. 契约偏差与说明

| # | 事项 | 说明 |
|---|---|---|
| 1 | UI 两次提交 | 浏览器端无 ZIP 解析依赖；采用「探测 → 确认 → 重试」，服务端第一次拒绝时不做任何文件改动 |
| 2 | 依赖冲突细节 | 契约要求 `details.dependents`；同时把错误码提升到 `ERROR_CODES` 以便前端按码提示 |
| 3 | 修复范围 | 修复不重置已禁用的从属能力，与既有升级编排一致；重复修复同内容被拒绝 |
