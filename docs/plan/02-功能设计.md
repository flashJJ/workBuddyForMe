# 02 · 功能设计

## 一、用户故事

- **U1 搭建流程**：作为用户，我想在画布上拖拽节点、连线、配置参数，把"查资料 → 判断 → 写稿 → 等我确认 → 输出"串成一个固定流程，而不是每次靠 AI 自由发挥。
- **U2 调试流程**：我想点"试运行"，逐步看每个节点拿到什么、产出什么、哪里失败，并在人工节点处直接拍板。
- **U3 对话中复用**：我想把调试好的流程发布，之后在普通对话里让助手自动调用它（比如"按我的周报流程整理本周工作"）。
- **U4 外部调用（P1）**：我想用 `curl` 或其他本地程序，通过一个带密钥的 HTTP 接口触发流程；也希望它出现在我的 MCP 工具列表里。
- **U5 自动运行（P2）**：我想让"每日早报"流程每天早上 9 点自动跑一次，结果存进运行记录。

## 二、核心概念模型

| 概念 | 说明 |
|---|---|
| **Flow（工作流）** | 一张有向无环图（DAG），含节点与边；有 draft / published / disabled 状态 |
| **Node（节点）** | 图上的一个处理步骤，有类型、位置、配置（config） |
| **Edge（边）** | 从上游客群节点的输出句柄连向下游节点的输入句柄；条件节点有 true/false 两个源句柄 |
| **Run（运行）** | 一次流程执行，有独立输入、状态、每个节点的执行记录 |
| **输出作用域** | 运行期每个节点产出一个结构化结果，可被下游节点用引用表达式读取 |
| **触发器** | 流程如何被启动：手动 / 对话（flow 工具）/ HTTP API / MCP / 定时（P2） |

## 三、节点目录（P0 共 7 类）

> 设计原则：节点能力全部映射到现有内核，不新造 AI/工具能力。

### 3.1 开始节点 `start`（每个流程唯一）

- 定义流程的**输入参数**：参数名、类型（string/number/boolean）、是否必填、默认值、说明。
- 试运行时在面板填写；被 `flow:<id>` 工具 / API 调用时由调用方传入。
- 输出：`{ params: {...} }`。

### 3.2 模型节点 `llm`

- 配置：模型（复用 providers/models，可空=跟随默认）、system 模板、user 模板、temperature/maxTokens、可选绑定知识库（复用 retrieval，支持开关"始终检索 topK"）。
- 模板支持**引用插值**（见第六节），把上游节点结果塞进提示词。
- 输出：`{ text: string, tokens?: {...} }`。
- 说明：结构化 JSON 输出（json mode）在 P1 提供，P0 条件判断请用 condition 节点。

### 3.3 知识检索节点 `knowledgeSearch`

- 配置：知识库（复用 knowledge_bases）、query 模板、topK（默认 4）。
- 内核：直接调用 `retrieval-service`（query 嵌入→sqlite-vec top-k）。
- 输出：`{ chunks: [{ content, documentName, score }], context: string }`（context 为拼好的可直接入提示词的文本）。

### 3.4 工具节点 `tool`

- 配置：选择工具（内置 13 个 + 已连接的 `mcp:*`）、参数模板（按工具 JSON Schema 渲染表单）。
- 执行：调用现有 `Tool.run()`；**write/danger 工具仍走 HITL 门控与熔断器**；danger 类工具在无人值守（API/定时）触发时默认拒绝（见第七节安全）。
- 输出：对齐 `ToolResult`：`{ ok, output, summary, citations?, images? }`。

### 3.5 条件节点 `condition`（分支）

- 不调用模型（保证确定性）。配置若干条规则，按顺序匹配：
  - 左值：引用表达式；操作符：`==/!=/contains/notContains/startsWith/endsWith/>/</isEmpty`；右值：常量或引用。
  - 多条规则可用 all(且)/any(或) 组合。
- 两个输出句柄 **true / false**：匹配走 true 边，否则走 false 边；未被选中的分支节点标记为 `skipped`。

### 3.6 人工节点 `human`

- 配置：提示文案、需要用户确认/填写的字段（表单 schema）、超时策略（等待 / 自动通过 / 自动拒绝）。
- 执行：运行进入 `waiting_human` 并挂起；P0 挂起态保存在内存 + run 落库（与现有 pending-confirmations 一致，**进程重启后的跨进程恢复放 P1**）。
- 输出：`{ approved: boolean, values: {...} }`。

### 3.7 结束节点 `end`（可多个）

- 配置：输出映射模板，决定整个 Run 的最终输出。
- 运行到任一 end 即成功结束（其余分支不再执行）。

### 节点类型扩展位（P1/P2 预留，不在 P0）

`http`（任意本地 HTTP 调用）、`schedule`（延时/定时分支）、`subflow`（嵌套调用另一个已发布流程）、`transform`（纯模板映射）。

## 四、图的校验规则（保存/运行前）

对应 langflow 的图校验，但收敛为 workBuddy 桌面端所需的最小集：

1. **结构**：恰有 1 个 start、至少 1 个 end；无环（DFS 检测）；无孤立节点；所有节点都有可达 end 的路径。
2. **连线**：边必须连接存在的句柄；condition 的 true/false 句柄至少各使用一次（警告级）；不允许非 condition 节点出现多入边造成的语义歧义（MVP 限制：普通节点单入边，需要汇聚时用 transform/end 节点）。
3. **参数**：所有模板引用的节点/字段必须存在且类型兼容；必填配置不能为空。
4. 校验结果在画布上**定位到具体节点/边**（复用统一错误包络的 `details` 字段携带 nodeId/edgeId）。

## 五、画布交互（P0）

页面：新增 `/flows`（列表）、`/flows/[id]`（编辑器）。

- **布局**：左侧节点面板（拖拽加入）｜中部 React Flow 画布｜右侧配置抽屉；底部可展开"试运行"面板。
- **编辑器工具栏**：保存、校验、撤销/重做（画布态本地）、试运行、发布/取消发布、版本历史。
- **节点视觉**：节点头显示类型图标（lucide）+ 名称；输入/输出句柄；错误态红框、运行态高亮。
- **配置表单**：按节点 config 的 zod schema 自动生成（复用现有表单/Radix 组件风格）；引用字段提供"插入变量"选择器（列出当前可引用的上游节点输出）。
- **试运行面板**：显示每个节点的 状态徽标（等待/运行中/成功/失败/跳过/待人工）、输入、输出、耗时、错误；人工节点在此内联通过/驳回；可重跑（用上一次输入）。
- **示例模板**：内置 2–3 个 starter flow（见第八节），一键复制到"我的流程"。

## 六、数据传递与引用表达式

工具本身是 JSON 参数驱动，因此不照搬 langflow 的句柄强类型，而采用**参数模板 + 运行期输出作用域**：

- 引用语法：`{{$nodes.<节点ID>.outputs.<字段路径>}}`，例如
  - `{{$nodes.search.outputs.context}}`
  - `{{$nodes.start.params.topic}}`
- 节点执行前，引擎用当前作用域做一次模板解析（字符串插值；值为对象时按字段路径取值，缺失即校验失败）。
- 作用域在编译期即可确定可引用集合（拓扑序保证引用只指向祖先节点），供前端"插入变量"使用。
- 非字符串参数（number/boolean/object）支持整字段绑定：参数值写成 `{ "$ref": "nodes.x.outputs.obj" }` 时整体替换而非字符串拼接。

## 七、触发方式与安全矩阵

| 触发器 | 上线 | 上下文 | write/danger 工具节点 | 人工节点 |
|---|---|---|---|---|
| 画布试运行 | P0 | 有用户在场 | 弹 HITL 确认（沿用现状） | 面板内联等待 |
| 对话 `flow:<id>` 工具 | P0 | 有用户在场 | 弹 HITL 确认 | 发 `tool_confirmation_required` 同类事件 |
| HTTP API | P1 | 无人值守 | **默认拒绝**（除非流程显式声明"允许自动执行"且用户在发布时二次确认） | 超时策略生效（挂起等待，回调/超时拒绝） |
| MCP Server | P1 | 无人值守/取决于客户端 | 同 HTTP | 同 HTTP |
| 定时 | P2 | 无人值守 | 同 HTTP | 同 HTTP |

本地服务安全（沿用 desktop `server-manager` 既有做法）：仅绑 `127.0.0.1`、随机 bearer token（safeStorage 加密保存）、发布密钥只展示一次。

## 八、内置示例流程（P0 交付，降低上手成本）

1. **资料研究助手**：start(主题) → knowledgeSearch(网页/笔记库) → condition(是否有足够资料) → llm(成稿/补检索) → human(审核) → end。
2. **周报流水线**：start → llm(按固定模板汇总) → human(确认) → end，演示对话中 `flow:weekly-report` 调用。
3. **网页摘要器**：start(url) → tool:`fetch_webpage`(danger，运行时确认) → llm(摘要) → end，演示工具节点与 danger 门控。

## 九、发布与自动化（P1/P2 功能预览）

### P1：发布为服务

- **本地 HTTP API**：发布后生成 `POST http://127.0.0.1:<port>/api/flow-invoke/<token>`，body 为 start 参数；同步或（长流程）异步返回 runId，经 `GET /runs/:id` 轮询/SSE 订阅。
- **MCP Server**：在现有 MCP 子系统旁新增一个**最小 MCP Server**（复用 `mcp/jsonrpc.ts` 的编解码经验），把每个已发布流程映射为一个 MCP tool（描述取自流程，input schema 取自 start 参数）。workBuddy 自身可作为 client 回连验证（自举）。
- **运行持久化与恢复**：run / node_executions 落库，`waiting_human` 可跨进程恢复；失败节点可在修复配置后"从失败节点重跑"。

### P2：自动化

- Electron 主进程内置轻量 scheduler（常驻端可靠；纯 Web 开发态不保证），流程可配置 cron；
- 事件触发：对话结束等本地事件钩子；
- 运行历史、失败重试与通知（结果写入运行记录，UI 红点提醒）。
