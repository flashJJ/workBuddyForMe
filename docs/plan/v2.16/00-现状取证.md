## 5. 页面请求扇出线索

- `useQuery` 单文件最多 5 个（`use-flows.ts`、`use-knowledge.ts`），页面组件最多 2 个。
- 主要风险不是单个 hook 内查询多，而是页面一次性挂载大量独立面板：设置页一次渲染约 35 个面板，每个面板自取数据。
- 现有 React Query 会对相同 query key 去重，因此「合并接口」不能按拍脑袋的请求数做；必须先测首屏 distinct GET、瀑布层数与 payload 大小。
- 候选试点：设置页（基础区 + 4 分组）。可选手段有两条，需用数据选：可见区懒挂载（减少同时挂载的面板查询）与页面级 facade / 只读聚合端点（减少首屏独立资源数）。

## 6. 已有约束与可复用机制

| 机制 | 现状 | 可复用点 |
|---|---|---|
| 300 行门禁 | `scripts/check-file-lines.mjs`，260 行预警、300 行硬门禁 | 目录预算脚本可并列扩展 |
| 行数白名单 | `scripts/.lines-whitelist.json` 仅 2 条 | barrel 拆分后逐步移除 `schemas/index.ts` 豁免 |

| 域 barrel | core/shared 已有纯 re-export 入口 | web feature 照此建立入口 |
| 测试位置 | 绝大多数与实现同目录 | 移动文件时测试跟随，断言不变 |

## 7. 缺口清单

1. **大目录无二级分区**：24 个目录直接文件 ≥20；最大 84。
2. **feature 无公开入口**：31 个 feature 仅 1 个有 `index.ts`；跨域引用必须知道内部文件名。
3. **跨域耦合未建模**：91 条跨 feature 深引用，哪些是合理能力依赖、哪些是偶然引用，没有矩阵。
4. **没有结构预算门禁**：行数门禁只管单文件，不管目录文件数；目录会继续变胖。
5. **没有循环依赖检查**：barrel 引入后循环风险上升，现有 ESLint 未启用 `no-cycle`。
6. **页面数据获取靠面板各自为战**：设置页 35 个面板同时挂载，首屏请求数未量化。
7. **缺少架构地图**：新功能落点靠口口相传，没有「新增文件放哪里」的决策树。
8. **命名角色不统一**：`service / runner / kernel / panel / section` 等同义后缀并存，靠读代码判断职责。
