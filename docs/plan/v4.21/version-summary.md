> 版本：4.21.0（2026-11-23 发布）

## 1. 本版解决什么

v4.20 把「快」收口后，最大的欠账回到记忆：

1. 召回通道与权重散在多个模块，场景与预算没有单一入口；
2. 同实体多值时按写入顺序取胜，用户无法理解为什么是这条；
3. 只有撤销约束与删除，缺少固定、降权、合并这些中间治理动作；
4. 召回结果不可解释，评测以单测为主，策略变化没有回放对照；
5. 记忆只能看，不能带走。

本版不新增存储模型，把召回、裁决、治理、解释与导出收在现有双时态与审计表之上。

## 2. 里程碑结果

| 阶段 | 结果 |

| M1 统一召回入口 | `chat` / `task` 3 条 × 600 token，`intent-forget` 5 条 × 750 token；置顶不计 token；空查询不写统计 |

## 3. 关键设计

### 3.1 一个入口，场景决定预算

`recall({ query, scene, budget, assistantId, conversationId, signal })` 成为唯一入口，内部仍复用语义、关键词、重要度、新鲜度、置顶与关系邻居通道。场景预设：

| 场景 | 条数 | token | 用途 |
|---|---|---|---|
| `chat` | 3 | 600 | 回合前召回（默认） |
| `task` | 3 | 600 | 任务上下文 |
| `intent-forget` | 5 | 750 | 「忘掉…」定位目标，不注入 |

token 用字符近似（`ceil(chars / 2)`），不引入 tokenizer；置顶条目不计 token，但受条数与置顶上限约束；裁剪按融合分升序丢弃，同分按 id 升序，保证结果可复算。

### 3.2 同主体只注入一条

参与冲突裁决的候选必须同 `subjectKey`、同精确作用域、`active` 且未过期。裁决顺序：

```text
用户固定 > 新鲜度（lastConfirmedAt ?? createdAt，降序）
        > 置信度（confidence，降序）
        > 稳定顺序（version 降序，再 id 降序）
```

每轮每个主体最多注入 1 条，理由枚举 `pinned / fresher / higher-confidence / stable-order`。落选值不删除，仍能在设置页查询——解释的是「这轮为什么选它」，而不是「另一条错了」。

### 3.3 治理动作复用现有字段

固定、升降权、合并与归档都走一次 `PATCH /api/memories/[id]`：

- 固定写 `pin`，取消写 `unpin`；`constraint` 取消固定返回 409；
- 升降权按 0.1 步长调整 `importance`，到边界不再写审计；
- 合并保留目标、归档来源，审计 after 快照只记 `mergedFrom` id；
- 重复操作幂等：目标值不变就不写 `memory_events`。

所有动作 `actor='user'`，统计卡新增 `pinnedActive / downweightedTotal / mergedTotal`。其中后两项由在线事件 + 已轮转聚合共同计数，轮转后仍可复算。

### 3.4 解释不落库，导出只给白名单

最近 5 次召回的轨迹保存在进程内环形缓冲：场景、耗时、候选/入选数量、按分数/预算/冲突的丢弃数、各通道命中数与裁决理由。不写库、不上报、不含 query 原文与记忆正文。

导出是用户主动动作，Markdown / JSON 都只包含 `kind / content / scope / importance / status / pinned / confidence / subjectKey / createdAt / lastConfirmedAt`，排除来源会话与消息 id、向量、审计细则与本机路径。

## 4. 数据与验证

- `pnpm check`：typecheck、lint、行数、目录、循环依赖、MSW、ASCII、资产、surface、E2E 隔离全部通过；
- `pnpm verify:local` 全绿（含单测、集成、评测脚本、性能脚本与 Web 生产构建）；
- 定向 E2E（生产模式）：固定 / 取消固定、降权 0.5→0.3、合并归档、导出下载、召回轨迹面板 1/1 通过；
- 回放对比：16 条 golden 用例 hit@3 `0.875`、零召回率 `0`、关系邻居 4/4，与 v4.20 基线一致；平均召回 `1.46ms`（基线 `0.48ms`，仅机器噪声级别）；
- 行为等价：`chat` / `task` 场景的召回集合与顺序不变，差异只来自显式治理动作。

## 5. 已知限制

- 解释轨迹只在进程内保留 5 次，重启即清空，不做历史归档；
- 合并只归档来源，不做正文去重或摘要融合；
- 冲突裁决依赖已有的 `subjectKey` 标注，未标注的记忆不参与合并；
- 导出包含正文，只适合用户主动备份，不进入任何自动任务；
- token 预算是字符近似，不是模型 tokenizer 的精确计数；
- 回放对比仍以离线 golden 集为主，不覆盖真实模型的长尾语义。

## 6. 下一步

1. 观察治理动作的真实使用率，再决定是否把「合并」扩展为带摘要；
2. 评估把解释轨迹落成本地诊断文件（仍不含正文）的收益；
3. Controller Pipeline / DAG 并行、视觉巡检 L2/L3 继续留待后续版本；
4. 记忆社区聚类与主题簇摘要维持长期挂账，不在本版重开。
