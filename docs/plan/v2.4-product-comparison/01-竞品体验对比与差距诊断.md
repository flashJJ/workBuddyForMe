# 竞品体验对比与差距诊断：Trae / 豆包 vs WorkBuddyForMe

> 目标：回答一个主观感受背后的客观原因——「为什么本产品不如 Trae、豆包好用」，
> 并把差距落到**可按优先级执行的改进清单**。
>
> 取证基准：`main` `e75dbb1`（v2.3 已合入）。外部产品信息采集于 2026-10-19，来源见 [§7](#7-来源)。
> 本文只做诊断与建议，不含最终契约；是否采纳、排期归属以立项评审为准。

## 0. 先说清楚对比口径（避免误伤）

三者不是同一类产品，直接比「好不好用」会失真：

| 产品 | 品类 | 价值主张 | 用户为它付出的前置成本 |
|---|---|---|---|
| **Trae** | AI IDE（字节） | 自然语言驱动写完整工程（SOLO / Builder），多模型可切换、内置 MCP | 装 IDE；模型与算力由产品兜底（免费档含请求额度） |
| **豆包** | 通用个人 AI 助手（C 端） | 对话 / 多模态 / 实时语音 / 内容生产 / Agent「帮你把事做完」 | 装 App 或打开网页；模型与算力由产品兜底 |
| **本产品** | **本地优先私人 AI 工作台** | 数据不出机的对话 · RAG · 工作流 · 桌面 Agent · 有形象与性格的长期陪伴 | **用户自带模型**（OpenAI 兼容供应商 + API Key + 模型） |

因此本文不按「功能多少」打分，而按**价值兑现链条**逐段比：**能不能开始用 → 用起来顺不顺 → 长不长期留得住**。
其中「能不能开始用」这段的差异最大，也最容易被感知为「不好用」。

## 1. 一页结论：差在 6 条根因

按影响面排序（前两条是「致命档」，决定产品能不能被用起来）：

| # | 根因 | 一句话 | 档位 |
|---|---|---|---|
| R1 | **首次价值兑现慢（TTFV）** | 豆包/Trae「装完即用」；本产品必须先配供应商 + API Key + 模型才有第一条回答 | 致命 |
| R2 | **模型能力与延迟由用户决定** | BYO 模型把最影响体感的两个变量（质量、首字延迟）交给了用户的选择与网络 | 致命 |
| R3 | **多模态是硬缺口** | 无图片/视频生成、无实时（全双工）语音对谈；语音还要先下 191–394MB 模型 | 体验 |
| R4 | **Agent 可信度未立口径** | 有桌面 Agent / 多智能体协作 / 可编程工作流，但成功率、失败原因、断点重试对用户不可见 | 体验 |
| R5 | **打磨与一致性欠账** | 观感细节、窄窗排版、空态引导、入口缺失——v2.3 已修一批，仍有剩余（见 §4.2） | 体验 |
| R6 | **生态与平台覆盖** | 豆包有移动端 + 飞书/抖音生态；Trae 有 IDE 生态 + 云端版；本产品仅 Windows 桌面 + 本机 Web | 打磨 |

同时必须承认三条**竞品拿不走的优势**，改进方向不该与它们打架（详见 §5「不要照抄的部分」）：
**本地私有（数据不出机 · 语音链路可离线 · 接本地模型后可完全离线）**、**可编程可扩展（Flow Studio + 本地 API/MCP Server + `.wbfm-pack`）**、**有形象与性格的长期关系（角色卡 / 形象 / 桌宠 / 情绪与关系 / 主动感知）**。

## 3. 为什么「感觉不好用」集中在这几处（机理）

### 3.1 TTFV 断链：第一步就要求用户做「专家决策」

豆包/Trae 的第一次会话在**安装完成的那一刻**就已经可用；本产品的第一次会话要先回答一串专家问题：
选供应商 → 填 baseURL → 填 API Key → 选模型 →（可选）配知识库/工作流 → 再回对话。
任何一环答不上来，用户就停在「配置页」而不是「产品里」。README 里确实留了 `WBFM_MOCK_AI=1` 的兜底，
但那是**开发用环境变量**（[README:46](../../../README.md#L46)），不是面向用户的开箱路径——用户看不到、也不会用。

更麻烦的是：**没有兜底可用模型时，产品等于没有内容**。空对话页 + 空知识库 + 空工作流，
用户会把「没配置好」误读为「这软件没什么用」。

### 3.2 能力长、但入口浅：功能多 ≠ 好用

本产品的功能面（对话 / RAG / 工作流 / 服务发布 / 桌面 Agent / 技能 / MCP / 助手 / 角色卡 / 形象 / 桌宠 / 语音 / 情绪关系 / 主动感知）
明显比绝大多数同类更宽，但**入口与引导薄**：

- 模板只有 3+3+3 且**列表空态不提示「已有现成模板」**（[v2.3 取证 §4.1](../v2.3/01-现状取证.md)）；
- 技能面板**无导入/模板区**（[skills-panel.tsx](../../../apps/web/src/features/settings/skills-panel.tsx) 仅列表 + 启停 + 删除）；
- MCP 预置目录 v2.3 已补（[mcp-panel.tsx](../../../apps/web/src/features/settings/mcp-panel.tsx)），但**助手级技能选择仍缺**（[assistant-form-dialog.tsx](../../../apps/web/src/features/assistants/assistant-form-dialog.tsx) 只有工具级 `enabledTools`），
  而内置技能文案却写「再让助手启用本技能」——口径与实现不一致（[v2.3 取证 §5](../v2.3/01-现状取证.md)）；
- 对话里看不到「这个助手挂了什么」，能力是隐形的。

「功能都在，但我找不到、也不知道它现在在替我做什么」——这正是「不如人家顺手」的典型病灶。

### 3.3 多模态的代差

豆包侧已经是**音视频联合理解 + 全双工实时语音 + 图片/视频生成**的形态；
本产品侧是**文本为主 + 单图理解（需视觉模型）+ 需下载模型的离线语音**。
这不是「少一个小功能」，而是交互模态的代差：用户拿手机对着豆包**边说边打断**、拍一张截图让它改图，
在本产品里都要绕成「打字 → 上传图 → 等下载模型 → 再说话」。

### 3.4 Agent 类能力缺「可信度证据」

本产品在 Agent 侧其实做了不少（桌面观察-决策-执行、工作流节点级可观测、失败节点重放、无人值守策略门控、
多智能体会议舞台），文档里的工程纪律也很严。但**用户视角缺三个东西**：
① 成功率/耗时等量化口径；② 失败时的「为什么失败 + 下一步」；③ 默认安全起步路径（只读观察 → 逐项授权）。
拿不到这三样，用户会把「偶发失败」泛化成「不可信」，进而回避整个功能。

### 3.5 打磨欠账的复利

v2.3 现状取证已经把「不好用」的细节逐条落到文件：原生 `<select>` 与 `type="number"` 的观感、
按固定窗口宽度假设的排版（窄窗必挤压）、固定控件宽、`whitespace-nowrap` 缺失等
（[v2.3 取证 §1–§3](../v2.3/01-现状取证.md)）。这类问题单看不致命，但**叠在一起就是「不专业」的整体印象**，
而且会被用户归因到「不如成熟产品」。

## 4. 差距分层与优先级

### 4.1 三层模型

| 层 | 判定问题 | 对应根因 |
|---|---|---|
| **L1 致命**（决定能否被用起来） | 「我装完能用了吗？第一次有用要多久？」 | R1、R2 |
| **L2 体验**（决定是否顺手） | 「找得到吗？看得见它在干什么吗？做错了我能怎么办？」 | R3、R4、R5 |
| **L3 打磨**（决定是否专业） | 「为什么这里看着像半成品？」 | R5、R6 |

### 4.2 改进清单（P0 / P1 / P2）

> 每项给出：问题 → 做法 → 验收口径 → 主要涉及范围。P0 决定「能不能用起来」，P1 决定「好不好用」，P2 是长线与打磨。

#### P0（建议下一个里程碑内解决）

**P0-1 零配置首启路径（直击 R1）**
- 问题：首次价值必须自备供应商 + Key + 模型；无兜底可用模型时产品形同空壳。
- 做法：首次向导收敛为三步——① 选一个**立即可用**的模型（自动探测本机 Ollama / 一键启动内嵌小模型 / 明确的免费云兜底三选一）；
  ② 连通性 + 首字延迟自检并给出「预计体感」结论；③ 直接落到对话并预置 2–3 个「马上能问出价值」的示例问题。
  把 `WBFM_MOCK_AI` 的兜底思路产品化成**用户可见的一条路径**（而非开发环境变量）。
- 验收：全新安装 → 第一条有效回答 ≤ 60s，且**至少有一条无需 API Key 的可用路径**；无模型时不进入「空对话页」而是进入向导。
- 范围：`apps/web/src/features/settings`（供应商/模型引导）+ 新增首启向导 + 本机 Ollama 探测（Electron 侧）。

**P0-2 模板「看得见、点得动」（直击 R5 的空态）**
- 问题：已有 3 工作流 + 3 技能 + 3 知识库模板，但空态不提示来源，用户不知道有现成货。
- 做法：知识库/工作流/技能/助手/角色卡的**空态改为模板卡片区**，标注「内置模板（可改可删）」+ 一键「以此开始」。
- 验收：五个列表空态均出现模板区；点击后生成可用实例（工作流需含可运行的最小节点图）。
- 范围：`features/knowledge`、`features/flows`、`features/settings/skills-panel.tsx`、`features/assistants`、`features/character-cards`。

**P0-3 语音对话从「可配置」到「可对话」（直击 R3 的语音段）**
- 问题：离线语音已有（PTT + VAD 免手、本地 sherpa-onnx），但要先下 191/394MB 模型、要懂灵敏度/尾静音参数。
- 做法：抽出「一键开启语音对话」入口，模型下载给出体积/耗时/镜像（hf-mirror 已有）与断点体验；
  参数收进「高级」；把「能否连续对话 + 能否打断」做成默认体感而非可调项。
- 验收：开箱开启语音对话无需理解任何参数；打断响应与「说完了」判定给出可量化的默认值。
- 范围：`features/voice`（`voice-input-section.tsx` 等）+ 模型下载 UX + 语音模型的体积/镜像提示。

#### P1（紧随其后）

**P1-1 Agent/任务可信度证据（直击 R4）**
- 做法：任务与协作页给出**每步依据 + 失败原因 + 一键重放失败节点**（工作流重放已存在，需对齐到 Agent/协作）；
  默认以「只读观察 → 逐项授权」起步；对无人值守给出策略摘要。
- 验收：任一任务可从 UI 看到「做了什么、依据是什么、为什么失败」；失败步骤可单点重试。
- 范围：`features/tasks`、`features/agents`/协作、`features/stage`（观察）、运行记录中心。

**P1-2 能力可见性（直击 R5 的入口/口径）**
- 做法：对话页头部或助手卡展示「当前助手：模型 / 知识库 / 技能 / MCP 工具」；助手表单补**助手级技能选择**；
  修正「再让助手启用本技能」的文案口径。
- 验收：对话内可见当前生效能力；助手表单可勾选技能并生效；文案与实现一致。
- 范围：`features/chat`、`features/assistants`、i18n 文案。

**P1-3 一致性收口（v2.3 未完项）**
- 做法：清掉剩余原生 `<select>` / `type="number"` 裸用（v2.3 已迁一批，需最终归零 + 白名单说明）；
  窄窗三尺寸无溢出；长文本/长路径截断策略；补命令面板/快捷键覆盖（已有 command-palette 迹象，需统一）。
- 验收：全仓无裸 `<select>`/`type="number"`（白名单外）；三尺寸无横向溢出。
- 范围：`components/ui`、各 feature 表单、`app-sidebar`、`page-header`。

**P1-4 首字延迟与长回复体感（直击 R2）**
- 做法：Markdown 增量渲染节流、长回复虚拟化/分片、慢模型的「进度 + 取消 + 降级」提示；
  给出首字延迟的可见指标（至少本地自检）。
- 验收：长回复滚动不卡顿；慢模型有明确进度与取消路径。
- 范围：`features/chat` 流式渲染、会话页性能。

#### P2（长线与打磨）

**P2-1 多模态按 ROI 扩**：先把「截图问答」做成 Trae 式顺手入口（拖入截图 → 直接问）；
图片/视频**生成**不自建，走供应商能力或 MCP 接入。
**P2-2 生态桥**：MCP 预置目录继续扩面（如 filesystem/git/sqlite 已可一键）；技能补导入/模板区。
**P2-3 性能与包体**：Electron 冷启动、首屏、内存实测与优化；语音模型下载体验（体积/镜像/断点）。
**P2-4 记忆可解释**：记忆面板 + 「为什么提到这件事」可溯（文档已有软引用 + 可溯纪律，需在 UI 落地）。

## 5. 不要照抄的部分（守住定位红线）

竞品的强项里，有几项**不该学**——照抄会把产品拖进自己必输的战场：

| 竞品强项 | 为什么不该照抄 | 替代策略 |
|---|---|---|
| 通用对话模型质量 | BYO 模式下无法稳定赢；追它就是追一个用户自己选的变量 | 做**模型选择引导 + 本地/免费兜底**，并把「边界与成本」讲清楚 |
| 图片/视频生成 | 自建成本极高且迭代极快，与「本地优先小团队」不匹配 | 走供应商能力 / MCP / 本地网关接入，做成「可选增强」 |
| 移动端原生 App | 与「数据不出机的桌面工作台」定位冲突，且维护成本双倍 | 保持响应式 Web；如需移动，只做**只读查看/提醒** |
| 云账号与团队协作 | 触碰本地私有红线 | 不做云端账号；最多做本地导出/备份（已有）与局域网只读分享 |

## 6. 建议的验收顺序（若采纳）

1. 先做 **P0-1**：它是「用户第一次打开就流失」的唯一闸门，做完才谈得上后面的体验。
2. 再做 **P0-2 / P0-3**：把「已有能力」变成「用户能立刻摸到的能力」。
3. **P1-1 / P1-2** 解决「看不见、不敢用」；**P1-3 / P1-4** 解决「不像成品」。
4. P2 按 ROI 排，不做「为了对齐竞品而做」的功能。
