## 二、图数据模型（前后端共享契约）

新增 `packages/shared/src/schemas/flow.ts`（zod，前后端共用，与现有 `schemas/assistant.ts` 风格一致）：

```ts
// 画布持久化的图（workflow_versions.graph_json）
interface FlowGraph {
  nodes: FlowNode[];
  edges: FlowEdge[];
  viewport?: { x: number; y: number; zoom: number };
}
interface FlowNode {
  id: string;                 // 画布内唯一，作为引用锚点
  type: 'start' | 'llm' | 'knowledgeSearch' | 'tool' | 'condition' | 'human' | 'end';
  position: { x: number; y: number };
  config: Record<string, unknown>;  // 各节点类型的 zod 子 schema 联合判别
}
interface FlowEdge {
  id: string;
  source: string; sourceHandle?: 'true' | 'false';  // 仅 condition 使用
  target: string;
}
```

要点：

- **不存储节点尺寸等纯 UI 运行时信息**（React Flow 自行测量），graph_json 只存语义 + 位置/视口。
- 每个节点类型导出一个 `configSchema: ZodObject`，前端据此渲染配置表单、后端据此校验。
- start 节点额外定义 `inputSchema`（流程入参）；工具节点 config 中的工具名决定参数 schema（从现有工具元数据 `parameters` 取得）。

## 三、DAG 执行引擎（packages/core/src/flow/）

### 3.1 模块划分

| 文件 | 职责 |
|---|---|
| `graph-schema.ts` | 从 shared 引入 zod schema + 节点配置判别 |
| `compiler.ts` | 结构校验（无环/孤立/句柄/可达）、拓扑排序、生成执行计划 `CompiledFlow` |
| `refs.ts` | `{{$nodes.x.outputs.f}}` 与 `{ "$ref": ... }` 解析、作用域类型检查 |
| `engine.ts` | 主执行器：AsyncGenerator，产出运行事件；就绪队列推进；挂起/恢复/取消 |
| `node-handlers/*.ts` | 7 类节点处理器，统一接口（见 3.3） |
| `run-store.ts` | 运行态内存表 + 落库（workflow_runs/node_executions）；P0 挂起内存态，P1 跨进程恢复 |
| `flow-tool.ts` | 把已发布流程包装成现有 `Tool`（`flow:<id>`），接入 tool-runtime |
| `events.ts` | SSE 事件类型（复用 shared/api/sse.ts） |

### 3.2 执行算法（P0 顺序就绪；P1 开放同层并发）

```
compile(graph):
  1) 校验结构（无环 DFS、唯一 start/end、句柄合法、每个节点可达 end）
  2) Kahn 拓扑排序得到 levels
  3) 建立 node -> 上游依赖表、下游邻接表、condition 分支表

run(flowId, version, triggerInput, { signal, mode }):
  scope = Map<nodeId, outputs>           // 输出作用域
  state = Map<nodeId, pending|ready|running|succeeded|failed|skipped|waiting_human>
  queue = [start]
  emit run_started
  while queue 非空:
      node = 取一个就绪节点               // P0：逐个；P1：同 level 无依赖节点可并发
      emit node_started
      // 分支剪枝：condition 未选中分支的后继链标记 skipped（直到合流点）
      if 节点被标记 skipped: emit node_skipped; continue
      if node.type === 'human':
          persist(run=waiting_human); emit node_waiting_human
          humanInput = await 等待 resume(runId, nodeId)   // 复用 pending-confirmations 句柄模式
      resolvedConfig = resolveRefs(node.config, scope)   // 模板/整字段绑定
      outputs = await handler.run(resolvedConfig, ctx)   // 内部已 try/catch 归一
      scope.set(nodeId, outputs); persist(node_execution)
      emit node_succeeded(nodeId, outputsSummary)
      // 推进：condition 仅把命中边的下游置 ready；end 到达即收尾
      enqueueReadySuccessors(node)
  emit run_succeeded(finalOutput) 或 run_failed(error)
```

失败策略（P0）：任一非分支节点失败 → 整个 run 失败并停在失败节点（P1 提供"从失败节点重跑"）。全程支持 `AbortSignal` 取消（对齐现有 chat/task 的中断模型）。

### 3.3 节点处理器统一接口

```ts
interface FlowNodeContext {
  signal: AbortSignal;
  trigger: 'manual' | 'chat' | 'api' | 'mcp' | 'schedule';
  conversationId?: string;            // chat 触发时透传，便于落消息/citations
  emit(event: FlowEvent): void;
  // 复用内核的句柄（由 API 层 container 注入，模式同 chat-orchestrator 的 deps）
  provider: ChatProvider;
  resolveTool(name: string): Promise<Tool | undefined>;
  retrieve(query: string, kbId: string, topK: number): Promise<RetrievalResult>;
  gateToolPermission(tool: Tool, args: unknown): Promise<PermissionDecision>;
  requestHuman(fieldSchema: JsonSchema, meta: HumanMeta): Promise<HumanResult>;
}
interface FlowNodeHandler<C = unknown, O = unknown> {
  type: FlowNodeType;
  run(config: C, ctx: FlowNodeContext): Promise<O>;
}
```

各 handler 到现有内核的映射：

| 节点 | 实现 |
|---|---|
| llm | `provider.chatStream`（拼装 system/user，累积文本；可选先 `ctx.retrieve` 注入 RAG 块，逻辑同 `prompt.ts`/`rag-retriever.ts`） |
| knowledgeSearch | `ctx.retrieve` → `retrieval-service` |
| tool | `resolveTool` → 权限门控 → `Tool.run`（复用 tool-executor 的超时/熔断/归一） |
| condition | 纯本地规则求值，不调模型 |
| human | `ctx.requestHuman`（P0 接 SSE + pending 句柄；无人值守触发器走超时策略） |
| start/end | 读写 scope，无外部调用 |

### 3.4 工作流即工具（`flow:<id>`）

`flow-tool.ts` 对每个已发布流程生成一个 `Tool`：

- `name = flow:<workflowId>`、`description` 取流程描述、`parameters` 由 start 节点 `inputSchema` 生成；
- `run(args)` = 创建一次 run（trigger='chat'）并以事件桥接到当前对话（节点事件映射为现有 tool trace 事件），返回 end 节点输出；
- 在 `tool-runtime.ts` 的 `resolveTool` 增加第三个来源：`builtin → mcp → flow`，与现有限定名机制完全同构，**助手白名单与权限表无需改结构**。

## 四、数据模型（顺序迁移 v012，只做加法）

沿用 better-sqlite3 裸 SQL、snake_case、uuid、`created_at/updated_at` 风格。

```sql
-- v012_flow_studio.sql
CREATE TABLE workflows (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  icon        TEXT NOT NULL DEFAULT 'workflow',
  color       TEXT NOT NULL DEFAULT 'default',
  status      TEXT NOT NULL DEFAULT 'draft'        -- draft | published | disabled
              CHECK (status IN ('draft','published','disabled')),
  current_version INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE workflow_versions (
  id          TEXT PRIMARY KEY,
  workflow_id TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  version     INTEGER NOT NULL,
  graph_json  TEXT NOT NULL,                       -- FlowGraph 序列化
  published_at TEXT,
  created_at  TEXT NOT NULL,
  UNIQUE(workflow_id, version)
);

CREATE TABLE workflow_runs (
  id           TEXT PRIMARY KEY,
  workflow_id  TEXT NOT NULL REFERENCES workflows(id),
  version      INTEGER NOT NULL,
  trigger      TEXT NOT NULL CHECK (trigger IN
               ('manual','chat','api','mcp','schedule')),
  status       TEXT NOT NULL CHECK (status IN
               ('queued','running','waiting_human','succeeded','failed','cancelled')),
  input_json   TEXT,
  output_json  TEXT,
  error_json   TEXT,
  conversation_id TEXT,                             -- chat 触发时关联
  wait_node_id TEXT,                                -- 当前挂起的人工节点（P1 恢复用）
  started_at   TEXT, finished_at TEXT, created_at TEXT NOT NULL
);

CREATE TABLE node_executions (
  id          TEXT PRIMARY KEY,
  run_id      TEXT NOT NULL REFERENCES workflow_runs(id) ON DELETE CASCADE,
  node_id     TEXT NOT NULL,
  status      TEXT NOT NULL CHECK (status IN
              ('running','succeeded','failed','skipped','waiting_human')),
  inputs_json TEXT, outputs_json TEXT, error_json TEXT,
  started_at  TEXT, finished_at TEXT,
  duration_ms INTEGER
);
CREATE INDEX idx_node_executions_run ON node_executions(run_id);
CREATE INDEX idx_workflow_runs_flow ON workflow_runs(workflow_id, created_at);
```

P1 追加（v013）：`workflow_endpoints(workflow_id, token_hash, enabled, created_at)`、`workflow_mcp_config`（并入 settings_kv 亦可）。
P2 追加（v014）：`workflow_triggers(id, workflow_id, kind CHECK(cron|event), config_json, enabled, last_run_at, next_run_at)`。

新增仓储放 `packages/database/src/repositories/`：`workflow-repo.ts`、`workflow-run-repo.ts`（导出挂到现有 `repositories/index.ts`），风格对齐 16 个既有仓储。

## 五、API 设计（App Router，全部走统一包络）

| 方法/路径 | 作用 |
|---|---|
| `GET/POST /api/flows` | 列表 / 新建草稿 |
| `GET/PATCH/DELETE /api/flows/[id]` | 详情（含当前版本图）/ 改名改状态 / 删除 |
| `POST /api/flows/[id]/versions` | 保存图，生成新版本（草稿态自动 +1） |
| `POST /api/flows/[id]/validate` | 只校验不保存，返回带 nodeId/edgeId 的诊断 |
| `POST /api/flows/[id]/publish` | 发布：固定版本、status=published、注册 flow 工具 |
| `POST /api/flows/[id]/runs` | 创建运行（body = start 参数），返回 runId |
| `GET /api/flows/runs/[id]` | 查询运行与各节点执行记录 |
| `GET /api/flows/runs/[id]/events` | **SSE 订阅**运行事件（复用 sse.ts；P0 订阅期内驱动执行，模式同 tasks/events） |
| `POST /api/flows/runs/[id]/control` | `{action: cancel}`（P1 加 resume/retry-from-node） |
| `POST /api/flows/runs/[id]/human` | 人工节点提交 `{nodeId, approved, values}` |
| `GET /api/flows/tool-catalog` | 供工具节点选择：现有工具 + `mcp:*` 元数据（可复用 /api/tools/debug） |

> 订阅驱动执行的生命周期 P0 与 tasks 保持一致（SSE 连接内运行）；**P1 改为落库后由独立执行器接管**，从而支持跨连接/跨进程恢复与无人值守触发。

P1 新增：`POST /api/flows/[id]/endpoints`（创建/吊销调用密钥）、`POST /api/flow-invoke/[token]`（免会话执行端点，独立鉴权）、MCP SSE/HTTP 端点 `/api/mcp-server`。

## 七、关键技术点与对策

1. **环/分支/跳过**：编译期 DFS 保证无环；condition 命中边做可达性标记，未命中分支直到合流点前全部 `skipped`，合流点（多入边）P0 通过"要求所有活跃上游完成"激活。
2. **类型安全的引用**：节点输出类型在 schema 中声明，`refs.ts` 在编译期做可引用集合与类型检查，前端"插入变量"只列合法项，从源头避免运行期 `undefined`。
3. **结构化输出缺口（B5）**：P0 的分支用 condition 节点（声明式规则，确定性）规避"LLM 吐 JSON 不可靠"；P1 再在 `packages/ai` 增加最小结构化能力——优先 OpenAI `response_format=json_schema`，Ollama 等退化为"JSON prompt + 容错解析"（沉淀现有 `llm-planner.ts` 的正则逻辑为公共函数）。
4. **HITL 一致性**：人工节点与 danger 工具统一走权限服务语义；无人值守触发器默认拒绝 danger，发布时显式二次授权（写 tool_permissions 的同构记录或流程级开关）。
5. **长运行/资源**：工具 15s 超时沿用；DAG 运行设整体预算（默认沿用任务步数思路，节点数/时长双上限），防失控。
6. **事务一致性**：一次节点完成 = node_executions upsert + run 状态更新在同一 better-sqlite3 事务内（同步 API，天然简单）。
7. **桌面/网页双态**：所有核心逻辑在 core（平台无关）；P1 的本地端点托管、P2 的 scheduler 放 Electron 主进程，Web 开发态用 Next 路由提供等价但不常驻的能力。
