# 01 · 现状与差距分析

> 所有结论基于 workBuddyForMe v0.7.0 与 langflow v1.12.4 的源码实读，路径相对各自仓库根目录。

## 一、workBuddyForMe 现状事实

### 1.1 技术栈基线

| 层 | 选型 | 证据 |
|---|---|---|
| 应用形态 | Next.js 14.2（App Router）全栈 + Electron 31 桌面壳，pnpm monorepo | 根 `package.json`、`apps/web`、`apps/desktop` |
| 语言/运行 | TypeScript / Node ≥ 22.13 | 根 `package.json` engines |
| 数据 | better-sqlite3 裸 SQL + sqlite-vec 向量库，无 ORM | `packages/database/src/client.ts`、`vector.ts` |
| 迁移 | `PRAGMA user_version` 顺序前向迁移，**当前 v011** | `packages/database/src/migrations/runner.ts` |
| 前端状态 | 仅 @tanstack/react-query v5，无 zustand/redux | `apps/web/package.json` |
| UI | Radix 原语 + 自研 shadcn 式组件 + Tailwind + lucide | `apps/web/src/components/ui` |
| 流式 | fetch + 手写 SSE ReadableStream 解析 | `packages/shared/src/api/sse.ts` |
| 接口约定 | 统一包络 `{success:true,data}` / `{success:false,error}` | `packages/shared/src/api/envelope.ts` |
| 数据目录 | `~/.workbuddy-for-me`（Electron 指向 userData） | `packages/config/src/paths.ts` |

### 1.2 现有「编排」相关能力

| 能力 | 实现形态 | 局限 |
|---|---|---|
| 对话编排 | `streamChat` AsyncGenerator：模型轮 ↔ 工具轮，**线性循环、最多 5 轮** | `packages/core/src/chat/chat-orchestrator.ts`；`MAX_TOOL_ROUNDS=5`（`shared/constants.ts`） |
| 工具执行 | 顺序 for 循环执行一批工具调用，非并行 | `packages/core/src/chat/tool-call-loop.ts` |
| 桌面任务 | task-loop：观察(截图)→LLM 决策(JSON)→执行 的线性环，max_steps=20，**生命周期绑定 SSE 连接，断线即 abort** | `packages/core/src/agent/task-loop.ts`、`api/tasks/[id]/events` |
| 技能 skills | 磁盘 `skill.json`：prompt 模板 + 工具白名单，全局启用 | `packages/core/src/skills/`，**无步骤/分支/数据流** |
| 定时/调度 | **不存在**（core 内无 setInterval/cron/schedule） | — |

### 1.3 可直接复用的资产（本方案的地基）

1. **工具抽象**：`Tool { name, description, parameters(JSON Schema), permission, run(rawArgs, ctx) }`，含 13 个内置工具（时间、知识检索、网页抓取、屏幕/键鼠/窗口等），MCP 工具以 `mcp:<server>:<tool>` 同构接入。
   证据：`packages/core/src/tools/types.ts`、`tool-runtime.ts`、`mcp/mcp-tool.ts`
2. **工具安全运行时**：HITL 权限门控（write/danger 需确认）、熔断器、15s 超时、SSRF 防护。
   证据：`tools/tool-permission-gate.ts`、`tool-executor.ts`、`ssrf-guard.ts`、`api/tools/confirm`
3. **AI 适配层**：统一 `ChatProvider.chatStream / embed`，收敛到 OpenAI wire 形态，支持 function-calling。
   证据：`packages/ai/src/types.ts`、`adapters/openai/adapter.ts`、`adapters/ollama/adapter.ts`
4. **知识库 RAG 内核**：解析→分片→嵌入→sqlite-vec→top-k 检索，可独立调用。
   证据：`core/src/ingestion/`、`core/src/retrieval/retrieval-service.ts`、`database/src/vector.ts`
5. **流式与可观测**：SSE 事件管道、LangSmith tracer。
6. **挂起/恢复范式**：pending-confirmations 与 task-loop 的 control(pause/resume/stop)。
7. **数据层范式**：顺序迁移 + 16 个手写 Repository。
8. **桌面宿主**：Electron 主进程可管理 127.0.0.1 子进程服务（随机端口 + bearer token + safeStorage 加密桥）。
   证据：`apps/desktop/src/main/server-manager.ts`

### 1.4 明确空白（本方案需新建）

| # | 空白 | 影响 |
|---|---|---|
| B1 | 无工作流定义模型（节点/边/端口/DAG 校验） | 无法描述多步流程 |
| B2 | 无 DAG 调度执行器（仅线性循环） | 无法做分支、并行、数据传递 |
| B3 | 前端无任何画布/节点/拖拽依赖（全仓无 reactflow/@xyflow） | 无可视化编排 UI |
| B4 | 无 workflows / runs / node_executions 数据表 | 流程与运行历史无法持久化 |
| B5 | AI 层无结构化输出抽象（现靠正则抽 JSON，见 `agent/llm-planner.ts`） | 条件/结构化节点缺可靠基座 |
| B6 | MCP 仅 client，不能暴露 server | 能力无法对外 |
| B7 | 无定时/事件触发器 | 无法自动化 |

## 二、langflow 能力拆解（借鉴对象）

| 能力 | langflow 实现 | 对 workBuddy 的借鉴方式 |
|---|---|---|
| 可视化画布 | 前端 `@xyflow/react ^12` + zustand 管理画布态 | 引入同款 `@xyflow/react` v12；画布态用 React Flow 原生 + useReducer（不引入 zustand） |
| 组件 = 节点 | Python 类，声明 `inputs/outputs/icon`，输出方法产出数据 | 用 TS「节点处理器注册表 + zod 配置 schema」对应 |
| DAG 执行引擎 | `lfx/src/lfx/graph/`：Vertex/Edge、就绪队列、拓扑推进、事务与追踪 | 用 TS 实现同构的「拓扑就绪队列 + 节点作用域 + 事件流」 |
| 数据在连线上流动 | 上游 output 句柄 → 下游 input 句柄 | 用「节点输出作用域 + 参数模板引用」对应（工具本就是 JSON 参数驱动） |
| 条件路由 | Conditional/Selector 类组件按规则走不同分支 | 「条件节点」输出 true/false 两个分支句柄 |
| 发布为 API | flow → HTTP endpoint，API Key 调用 | P1：Electron/Next 起 127.0.0.1 端点 + 随机密钥 |
| 发布为 MCP Server | `/api/v1/mcp` 把 flow 变成 MCP tool | P1：复用现有手写 JSON-RPC 经验，反向实现最小 MCP Server |
| Playground 调试 | 逐步运行、查看每步结果 | P0：画布底部「试运行」抽屉（逐节点状态/IO/耗时） |
| Starter Projects | 内置模板降低上手成本 | P0：内置 2–3 个示例流程 |
| 可观测 | LangSmith/LangFuse 集成 | 直接复用现有 LangSmith tracer |

## 三、差距矩阵与功能取舍

| 维度 | 现状 | 目标 | 本期策略 |
|---|---|---|---|
| 执行模型 | 线性循环 | 确定性 DAG | P0 新建 TS DAG 引擎（MVP 顺序就绪，P1 同层并发） |
| 编排入口 | 仅自然语言 | 显式画布 + 对话可调用 | P0 画布 + `flow:<id>` 工具双通道 |
| 节点类型 | 工具/技能两类弱抽象 | 6 类显式节点 | P0：start / llm / knowledgeSearch / tool / condition / human / end |
| 流程持久化 | 无 | 定义 + 版本 + 运行记录 | P0 建表；运行态崩溃恢复放 P1 |
| 对外服务 | 无 | 本地 API + MCP | P1 |
| 自动触发 | 无 | cron / 事件 | P2（仅 Electron 常驻端） |
| 自定义代码节点 | 无 | 不做 | 永久非目标（安全） |

## 四、关键可行性结论

1. **技术栈可行**：langflow 已验证 `@xyflow/react` 足以承载此类画布；DAG 引擎是标准算法，TS 实现无外部依赖。
2. **复用率高**：P0 最复杂的三件事——模型调用、工具执行（含安全）、知识检索——workBuddy 都已有生产级实现，新模块主要做「编排与接线」。
3. **侵入性低**：工作流以 `flow:<id>` 工具形态接入对话，不改动 assistants 表与聊天主循环；数据表仅做加法式迁移 v012。
4. **符合产品定位**：本地优先（SQLite、127.0.0.1、随机 token）与「私人 AI 平台」一致，不引入云端依赖。
