# 04 · 实施路线与风险

## 一、里程碑总览

| 里程碑 | 周期（参考） | 目标 | 出口标准 |
|---|---|---|---|
| **M0 地基** | 3–4 天 | 契约 + 数据层 + 空引擎跑通 | 迁移 v012 可升可测；空图/最小图能编译执行 |
| **M1 引擎与节点** | 5–7 天 | 7 类节点 + 分支/挂起 + flow 工具 | 不经 UI 也能用测试跑通全部节点类型 |
| **M2 画布与试运行** | 6–8 天 | React Flow 编辑器 + 调试面板 | 浏览器中搭出并运行 2 个示例流程 |
| **M3 对话集成与发布（P0 收尾）** | 3–4 天 | `flow:<id>` 进对话、内置模板、文档 | README 第七节 6 条验收全过 |
| **M4 服务化（P1）** | 6–8 天 | 本地 API + MCP Server + 运行恢复 | curl 调通；自举 MCP 调通；重启恢复 |
| **M5 自动化（P2）** | 4–6 天 | Electron scheduler + 触发 + 历史 | cron 定时产出运行记录 |

> 周期为单人全职参考值，可按实际人力并行调整；P0（M0–M3）是一个可独立交付的完整闭环。

## 四、验收标准

### P0（功能级，对应 README 成功判据）

1. 可在画布完成 3 个 starter flow 的搭建/复制并保存新版本；
2. 校验能报出：环、孤立节点、非法句柄、错误引用，并在 UI 定位到节点/边；
3. 试运行：全跑与（人工节点处）挂起-继续均正确；每个节点可见 状态/输入/输出/耗时；
4. 发布后 `flow:<id>` 出现在工具目录，普通对话可调用并正确回灌结果；
5. 含 danger 工具节点的流程在对话触发时仍弹 HITL，无人值守默认拒绝（为 P1 预埋策略）；
6. 全程接口符合统一包络，`pnpm check` 与单测通过；v011→v012 迁移在现有库上成功。

### P1

- `curl -H "Authorization: Bearer <token>"` 调用已发布流程获得正确输出；
- 重启应用后 waiting_human 运行可继续；失败节点改配置后可单点重跑；
- 自身 MCP client 可发现并调用本进程发布的流程工具（自举）。

### P2

- 配置 cron 后，到点自动产生一次成功运行记录；桌面端关闭期间错过的任务在启动后按策略补跑/标记。

## 五、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 引擎工作量膨胀（并发/循环/嵌套一次性做太多） | 高 | P0 严格限定：DAG（无循环）、顺序就绪、7 类节点；并发与 subflow 明确推迟 |
| LLM 结构化输出不可靠（B5 现状靠正则） | 中 | P0 分支用声明式 condition，不依赖模型吐 JSON；结构化输出延到 P1 且做协议优先 + 降级 |
| 长运行与 SSE 绑定导致不可无人值守 | 中 | P0 接受与 tasks 相同的连接内生命周期；P1 尽早做"落库 + 独立 runner"解耦，不把 P0 设计成无法演进 |
| React Flow 引入带来学习/样式成本 | 中 | 只用官方基础能力（自定义节点/句柄/Minimap/Controls）；视觉沿用现有 Tailwind/Radix 风格；langflow 已验证可行性 |
| 工作流放大工具权限（danger 被流程绕过） | 高 | 工具节点强制走既有门控/熔断；无人值守默认拒绝 danger，发布时显式授权；执行日志可审计（node_executions） |
| 本地 HTTP/MCP 暴露面安全 | 中 | 仅绑 127.0.0.1、随机 token、密钥哈希存储、只展示一次；MCP 沿用现有 transport 安全约束 |
| Web 端常驻调度不可靠 | 低 | scheduler 只在 Electron 主进程实现，不承诺纯网页后台定时 |
| 与现有 task-loop / chat 概念混淆 | 低 | 文档与命名区分：Flow=确定性 DAG；Task=桌面自主操作环；二者通过"工具节点/flow 工具"单向互操作，不合并 |
| 桌面 nut-js/safeStorage 等环境差异 | 低 | 编排核心全部在 core 平台无关层；桌面特有能力仅在 P1/P2 触碰 |

## 六、与既有路线的衔接建议

- 现有 `task_runs/task_steps`（v011）与本期 `workflow_runs/node_executions`（v012）形态相近但语义不同（自主环 vs 确定性 DAG），**保持两套表**，前端可在"运行记录"层做统一时间线视图，但不做表合并。
- 未来若要让"桌面 Agent 任务"成为流程中的一个节点，可在 P1 之后增加 `agentTask` 节点，内部复用 task-loop 内核——届时是本方案的自然延伸，而非现在提前耦合。
