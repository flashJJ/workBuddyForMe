# WorkBuddy v0.8 版本总结：Flow Studio——把 AI 的临场决策变成确定的流程图

- **版本号**：v0.8.0
- **发布日期**：2026-10
- **主题**：可视化工作流编排 Flow Studio（DAG 编译执行引擎 + 画布试运行 + 发布为对话工具）
- **对应方案**：[v0.8-flow-studio.md](./v0.8-flow-studio.md)
- **分支**：`feature/v0.8-flow-studio`（M0–M3 共 14 个提交）

---

## 1. 主题与价值主张

v0.7 让助手在桌面上「看得见、动得了手」，但普通对话里的工具调用仍有一个根本不确定性：**调什么工具、什么顺序、失败了走哪条路，全靠模型每一轮临场决定**。同一句「帮我整理周报」，今天可能先搜知识库再写，明天可能直接编；多步任务无法预设、无法复现、无法审计。

v0.8 的回答是把确定性的部分从模型手里拿回来：

> 从「每轮靠模型临场决定调什么工具」到「把检索、判断、生成、工具、人工审核画成一张确定的流程图」——流程可调试、可复现，并能作为工具回到普通对话中被助手调用。

| 痛点（v0.7 现状） | v0.8 的回答 |
|---|---|
| 工具调用顺序模型临场决定，相同输入路径不一致 | 确定性 DAG 引擎：Kahn 拓扑定序，分支由声明式规则求值，不调模型 |
| 多步能力只能靠提示词暗示，无法组合复用 | 7 类节点积木 + 节点间数据引用，发布后成为 `flow:<id>` 工具 |
| 复杂流程没有调试手段，错了只能看最终回答 | 试运行面板逐节点看状态/输入/输出/耗时，人工节点挂起内联处理 |
| 前端零画布基础 | 引入 @xyflow/react 12，自定义 7 节点/分支边，不引入状态管理新依赖 |

**关键边界**：v0.8 只做 P0（编排 + 执行 + 调试 + 对话复用）。HTTP API / MCP Server 对外登记 **v0.9**，定时/事件自动化登记 **v0.10**；不做并发、循环、子流程嵌套、自定义代码节点。

## 3. 架构演进

### 3.1 一张图看清分层

```text
浏览器（Next.js）
  /flows 列表 · @xyflow/react 画布 · 配置抽屉 · 试运行面板（EventSource）
  对话页 tool-trace 卡片（tool start/substep/end 三阶段）
        │ REST {success,data} / SSE text/event-stream
Next.js Route Handlers（/api/flows/*）
  校验走 core compileFlow；SSE 生命周期 = 运行生命周期；终态从 node_executions 回放
        │
core/flow
  compiler（环/拓扑/可达诊断）→ engine（就绪队列+分支剪枝+取消）
  refs（模板插值/$ref）→ 7 handlers → run-store（逐节点落库）
  run-service（createRun/startEvents 两段式；manual 交互 / chat 非交互）
  flow-tool（发布流程 → Tool）· starters（3 模板播种）
        │ 复用既有内核
retrieval（sqlite-vec）· ChatProvider · tool-runtime（门控/熔断/15s 超时/SSRF）
        │
SQLite v012：workflows / workflow_versions / workflow_runs / node_executions
```

### 3.2 三个最关键的架构决策

**① 运行生命周期 = SSE 订阅生命周期，登记与执行分离。** `POST /runs` 只写一条 queued 记录并立即返回；`GET /runs/:id/events` 被订阅时才真正启动引擎。这直接复用 v0.7 tasks 已验证的范式：不需要独立 worker 进程，断线即 abort，人工挂起天然随连接存活。代价（跨进程恢复、失败单点重跑）明确登记 v0.9，随服务化一起做。

**② 分支判断绝不调用模型。** condition 节点是声明式规则（`==/contains/>/isEmpty…`，all/any），引擎在执行前完成引用插值后做纯函数比较。这是「相同输入多次运行路径一致」承诺的根基——让模型做分支判断等于把不确定性请回来。结构化输出不可靠的问题因此被整体规避，json_schema 协议随 v0.9 在 ai 层再做。

**③ Flow 与 Task 是两套语义，只通过工具单向互操作。** Flow 是确定性 DAG（你画它跑），Task 是自主操作环（模型决策）；两套表、两个引擎，不合并。未来的 `agentTask` 节点是 Flow 调用 Task 的单向延伸，而不是把 task-loop 塞进流程图。

### 3.3 对话复用：不改编排主循环的第三工具来源

flow 工具没有新开任何对话通道：

- 发布只做一件事——`status=published` + 固定当前版本；`buildTools` 装配工具表时，在助手白名单解析完后追加 `flowToolLister()` 返回的已发布流程，白名单表零改动；
- 对话调用走 trigger=`chat` 非交互路径：不开放 SSE 挂起，human 节点自动按「拒绝」继续（流程可经 condition 走驳回分支），危险工具节点直接拒绝——为 v0.9 无人值守触发器预埋的策略位；
- 节点级进度通过 `ToolContext.onSubstep` 回调上抛，工具循环用「无限容量 + 关闭约定」的异步队列桥接回调与 async generator，前端在**原有 tool 卡片**内多渲染一层子步骤，SSE 事件协议只加了一个 `substep` phase，聊天主循环、消息表结构、HITL 弹窗全部不变。

## 5. 踩坑记录（都已固化为代码或测试）

1. **EventSource 重连风暴**：终态运行服务端回放后关闭流，浏览器默认自动重连→再次回放→32 条重复连接、时间线重复。修复：终态事件后客户端主动 `es.close()` + 按 `type:nodeId` 去重。
2. **dev HMR 单例分裂**：Next 按需编译重置模块级容器，SSE 持有的 flowRunner 与 POST /human 命中的不是同一实例，人工审核 422。修复：容器单例额外存 globalThis（生产无影响）。
3. **空串不触发 nullish 回退**：llm 节点「跟随默认模型」存的是 `modelId: ""`，`?? 默认值` 不生效，所有未显式选模型的节点必报「未配置模型」。改 `||`。
4. **子步骤队列快照延迟求值**：同步连发的多条回调在首次 yield 时数组已被推进到最终态。修复：回调时刻把快照入队而非入队引用。
5. **多 end 拓扑歧义澄清**：MVP 普通节点限单入边（汇聚只能发生在 end），资料研究模板的「空资料/有资料」双路径用两个 end 节点表达，编译器无需放开多入边。

## 6. Non-Goals（本版本明确不做）

- ❌ 流程发布为 HTTP API / MCP Server、跨进程运行恢复、失败节点单点重跑（**v0.9**，随服务化）
- ❌ 节点同层并发、subflow 嵌套、任意 HTTP 节点（**v0.9+**）
- ❌ 定时 / 事件触发自动化（**v0.10**，Electron 常驻端承诺）
- ❌ 节点内执行自定义 JS/Python（安全红线，长期不做）
- ❌ 替换或改造聊天、桌面任务、skills 体系（并存关系）
- ❌ playwright-mcp / UI-TARS 接入（沿用 v0.7 结论）
