## 1. 主题与价值主张

v0.2 给助手装了「手」——工具调用、本地 Ollama 跑起来；但它仍是一只**只读文字**的手：截图里的报错看不懂，docx 会议纪要进不来，好文章贴 URL 只能临时抓一下。

v0.3 的核心命题是：**让 WorkBuddy 能读一切你日常接触的信息源**。我们没有追求大而全的多模态炫技（文生图、语音、视频全部留在 Non-Goals），而是在「读」这一条垂直轴上，把三条最痛的路径打穿：

| 能力 | 解决了什么 | 用户的真实场景 |
|---|---|---|
| 视觉对话（M1） | 聊天能发图，视觉模型流式作答，历史可回看 | 截一张报错弹窗 → 粘贴 → 配一句「这怎么办」 |
| Office 文档解析（M2） | docx/xlsx/pptx 直接拖进知识库 | 会议纪要 docx、报价单 xlsx、方案 pptx → 上传 → 提问能命中 |
| 网页剪藏（M3） | URL 变成文档入库，引用带来源 | 博客 URL → 30 秒后在知识库检索到正文要点，引用角标点得开原文 |

**价值主张**：当 WorkBuddy 能读截图、能读 Office、能读网页，它就从「会聊的命令行工具」变成了真正能融入你知识流的工作台助手。P1 图片型 PDF OCR 留在 v0.4，本期主题闭环清晰，不打肿脸充胖子。

## 3. 架构演进

### 消息模型从单轨到双轨

v0.2 的 `ChatMessage.content` 是 `string | null`，纯文本通道。v0.3 引入 **双轨模型**：

```typescript
// packages/shared
type ContentPart = TextContentPart | ImageContentPart;

interface TextContentPart { type: 'text'; text: string; }
interface ImageContentPart { type: 'image_url'; image_url: { url: string; }; }

// packages/ai
interface ChatMessage {
  role: 'system' | 'user' | 'assistant' | 'tool';
  content: string | ContentPart[];  // 升级点
  // ...
}
```

**设计决策**：
- 不是直接把 `content` 改成 `ContentPart[]`，而是 `string | ContentPart[]`——老消息 `content_parts = '[]'` 时继续走 `content` 字段，完全零回填、零破坏
- `role: tool` 的消息**永远纯文本**，不允许图片内容混入工具上下文
- `content_parts` 列用 `TEXT DEFAULT '[]'`，不做 JOIN 不做拆分，JSON 数组序列化存 SQLite，读的时候 `JSON.parse`

### 附件存储与传输

```
落盘：attachments/<sha256>.<ext>           -- 明文，DB 不存 base64
DB：attachments 表存 (id, filename, mime_type, byte_size, storage_path, content_hash, created_at)
传输：SSE 不传图片字节，前端凭 message.content_parts 里的 id 去 GET /api/attachments/[id] 回流
```

**为什么这样设计**：
- DB 存 base64 会让 SQLite 单消息膨胀 4~6 倍，历史列表拉取变成灾难
- SSE 是纯文本协议，塞图片字节需要额外分片，且所有已连接客户端都会收到（图片只在首轮携带的语义冲突）
- 附件与消息**松耦合**：删除消息不强制删文件，本期不做 GC，P2 登记

### 视觉编排的门控点

```
前端 composer（禁用图片按钮 + 引导文案）
         ↓（绕过也没关系）
服务端 prepareUserTurn
         ↓
assertVisionCapable(message.assistant.model)  ← SSE 打开前
         ↓ 不支持
返回 422 { error: '当前模型不支持图片，请在设置中配置视觉模型' }
         ↓ 支持
组装 OpenAI vision payload（image_url data URL）
         ↓
SSE 开启
```

**门控放在哪里**很重要：放在 SSE 打开前而不是打开后，意味着不浪费已建立的 HTTP 连接，也避免了前端半开状态下的 UI 修复。双保险（前端禁用 + 服务端 422）是因为 Web 层永远不能只信前端。

### 数据层迁移（PRAGMA user_version 2 → 3）

| 改动 | 老数据兼容 |
|---|---|
| 新建 `attachments` 表 | 无老数据影响，全新 |
| `messages ADD COLUMN content_parts TEXT DEFAULT '[]'` | 空数组 = 纯文本，读老消息回落 content 字段 |
| `documents ADD COLUMN source TEXT NOT NULL DEFAULT 'upload'` | 老文档 source 默认 upload |
| `documents ADD COLUMN source_url TEXT` | 老文档 null |

一条原则：**所有迁移都是 ADD COLUMN 带 DEFAULT，从不修改已有列、从不做数据回填**。这让 migration v3 可以安全地在任意 v0.2 数据库上执行，且随时可以向前兼容（老版本读新版本数据时忽略 content_parts 即可）。

## 4. 关键技术决策

### 4.1 多模态契约：为什么不是 Message 本身扩展？

方案文档最初考虑过直接用 OpenAI 的 `ChatCompletionMessage` 结构（content 是数组），但这意味着：
- 所有现有 `msg.content` 的调用点都要改（空数组、数组元素类型判断）
- 工具循环里 tool message 永远纯文本，也被迫套壳
- 老消息读取时 `JSON.parse('[]')` 后再 fallback 到 `content`，逻辑分散

最终选择 `string | ContentPart[]` 的联合类型，配合 `content_parts` JSON 列做持久化——**在语义上与 OpenAI 对齐（数组就是多模态），在实现上保持了纯文本的零成本路径**。

### 4.2 Office 解析的依赖选择

| 格式 | 库 | 决策理由 |
|---|---|---|
| docx | `mammoth` | 纯 JS，零原生依赖；表格按行 `\|` 分隔，天然适合 Markdown 渲染和 RAG 分片 |
| xlsx | SheetJS 官方 0.20.3 | npm 主通道版本陈旧且非官方分发源，固定官方分发并锁 lockfile；多 sheet 遍历，空行过滤 |
| pptx | `fflate` 解 OOXML zip | 不引重型 Office 库（`unzip-stream` + XML 解析足够），`fflate` 纯 JS 且已在 PDF 场景用过 |

**统一入口**：三种格式全部收敛到 `read-document.ts`，按 kind 分发。方案文档里写的「禁止上传链路另起炉灶」是一条铁律——摄入管线必须是单一入口，否则分片、嵌入、向量落库会出现多条分支，后续维护成本翻倍。

### 4.3 网页剪藏的安全边界

剪藏与 `fetch_webpage` 工具共用 `safe-web-fetch.ts`，这是一条 SSRF 护栏链：

```
请求发起
  → URL 规范化（去 utm_*/fragment）
  → 重定向逐跳 SSRF 复检（每一跳都校验目标 IP 段）
  → 3 跳上限
  → 8s 超时
  → 响应头 Content-Type 必须 text/html
  → 200KB 有界读取（ReadableStream + 截断）
  → Readability 抽取正文
  → URL + 正文 hash 双重去重
```

**不引入无头浏览器**——这是一条明确的 Non-Goal。需要 JS 渲染或登录的页面直接置 failed 并提示「无法抽取公开正文」，安全和复杂度之间做出了明确选择。

### 4.4 Ollama 视觉协议的真机验证

v0.3 启动的第一件事不是写代码，而是**跑一遍 Ollama qwen2.5vl:7b 的视觉协议实测**（见提交 `2cf7ab3`）。结论：

> Ollama `/v1/chat/completions` 兼容层原生支持 OpenAI 格式的 `image_url` data URL（`data:image/jpeg;base64,...`），不需要像原生 `/api/chat` 那样转成 `images` 数组字段。

这条实测结论让 AI 层的适配代码变得极其简单——Ollama 适配器不需要任何特殊转换，直接复用 OpenAI 的 payload 组装。**先跑真机再写代码**，避免了花一天写适配器转换逻辑后发现根本不需要的尴尬。

### 4.5 Ollama 工具调用的 fallback 机制

v0.2 里 Ollama 的某些模型（如轻量模型）声明不支持 tools，但代码一律给所有模型带 tools 下发。v0.3 引入 `runProviderTurnWithToolFallback`：

```
首次调用：带 tools 下发
  → 提供商返回 400（模型不支持 tools）
  → 捕获错误，自动去除 tools 参数，重试一次
  → 正常返回（但本轮不做工具调用）
```

**这比在模型配置里加「是否支持 tools」开关好**——因为很多模型的 tool 支持是隐性能力，或者不同版本行为不一致。让运行时自己探测、自动降级，比静态配置更鲁棒。

## 5. 踩坑与取舍

### 坑 1：pdfjs-dist 的 webpack externals

**现象**：Next.js server bundling 时，`pdfjs-dist` 的 `pdf.mjs` 和 `pdf.worker.mjs` 被拆到了不同的 vendor-chunks 里。worker 文件通过 `new URL('./pdf.worker.mjs', import.meta.url)` 定位自己，但因为 chunk 拆分，相对路径指向了一个不存在的位置——PDF 解析直接崩溃。

**根因**：这不是 pdfjs-dist 的 bug，是 Next.js server bundle 拆分策略（`optimizePackageImports` 或者 turbopack 的 chunk 分组）导致的。当一个包的内部文件有相对路径依赖时，webpack/turbopack 把它们拆开就会破坏这个依赖。

**修复**：在 `next.config.mjs` 里把 `pdfjs-dist` 整个包排除出 server bundling（externals），让 Node.js 运行时从 `node_modules` 直接 require。

```javascript
// next.config.mjs
serverExternalPackages: ['pdfjs-dist'],
```

**教训**：凡是有 worker thread / relative path 内部依赖的 npm 包，在 Next server bundling 里都要警惕 chunk 拆分。`sharp`、`@napi-rs/*`、`pdfjs-dist` 都是高危名单。

### 坑 2：PDF 中文逐字换行

**现象**：某些中文 PDF（特别是从 Word 导出的），pdfjs 把单行文字拆成了逐字 span——每个字一个 text item，y 坐标相同、字号相同。RAG 管线按原始顺序取文本后，中文变成了「我 们 认 为 这 个 方 案 ...」，中间夹着 pdfjs 插入的空格或换行。

**根因**：pdfjs 的文本层抽取逻辑对 CJK 字体的换行处理不够鲁棒，Word 导出 PDF 时把每个中文字符单独渲染成一个 `<span>`。

**修复**：在 `mergePdfTextItems` 里按 **y 坐标 + 字号** 两个维度合并。同一行的判断标准是：y 坐标差值 < 字号 × 0.3，且字号完全相同。合并后按 x 坐标排序拼接。

```typescript
// 简化逻辑
function shouldMerge(a, b) {
  return Math.abs(a.y - b.y) < a.fontSize * 0.3
      && a.fontSize === b.fontSize
      && a.x > b.x;  // b 在 a 左边
}
```

**教训**：RAG 的文本抽取不能直接信底层库。PDF、docx、html 都有类似的「结构噪声」问题，需要在 ingestion 层做规范化。

### 坑 3：Radix Dialog 的 z-index 地狱

**现象**：Composer 点图片看大图（lightbox）弹出的 DialogContent 被 DialogOverlay 挡住了。这看起来是不可能的——Overlay 在 Content 下面？

**根因**：Radix UI 的 Dialog 组件里，DialogOverlay 和 DialogContent 都是 `z-50`。当页面上有多个 Dialog（比如知识库弹窗里套一个图片 lightbox），同一个 stacking context 里两个 z-50 元素按 DOM 顺序叠放——后挂载的在上面。但如果 Overlay 的 DOM 节点在 Content 之后（Portal 挂载顺序），Overlay 就盖在 Content 上。

**修复**：把 DialogContent 提到 `z-[51]`，DialogOverlay 保持 `z-50`。**不是用 Tailwind 的 z-50 → z-[51] 这种 hardcode，而是整个 Dialog 体系建立 z-index 层级规范**：Overlay z-50、DialogContent z-[51]、Tooltip/Popover z-[60]。

### 坑 4：本地模型冷加载的连接超时

**现象**：Ollama 本地跑 qwen2.5vl:7b 或其他 7B+ 模型时，首次请求需要 30~60 秒加载模型到 GPU。之前的 `CHAT_CONNECT_TIMEOUT_MS = 10s` 导致客户端收到超时错误，但模型其实还在冷启动。

**决策**：把连接超时从 10s 放宽到 180s。

**但为什么不直接改超时？**——因为需要区分两个阶段：
1. **连接阶段**（TCP 握手 + HTTP 响应头到达）：180s 足够覆盖冷加载
2. **流式阶段**（SSE delta 之间的间隔）：保持较短的心跳检测

超时放宽的同时，前端加了「模型正在加载，首次请求可能较慢」的状态提示，不让用户以为卡死了。

### 取舍：图片只在工具循环首轮携带

视觉模型的 token 成本远高于纯文本。如果每一轮工具调用都把图片重新带上，一个 5 轮的工具循环可能消耗掉 5 倍的视觉 token。

**决策**：图片只出现在用户的首轮消息里，后续的 assistant 消息和 tool result 消息不再携带图片。这在编排器里是硬编码的——`prepareToolLoop` 时过滤掉 content parts 里的 image_url。

这也解释了为什么 `role: tool` 的消息永远纯文本——工具结果不需要图片，也不应该携带图片。

## 6. P1 留白与 Non-Goals

### 为什么 P1 OCR 留到 v0.4

OCR 方案文档里写了两条路线（视觉模型主 + tesseract.js 兜底），都涉及 `@napi-rs/canvas` 这个原生预编译依赖。v0.1 的 Electron ABI 打包坑还历历在目——这类 N-API 包需要在桌面端做 prepare-server 归集和 asarUnpack，且必须先跑一次桌面 pack 冒烟。在 v0.3 的时间窗口里挤 OCR 意味着：

1. 要在 M4 里程碑里塞 3 天工作量，且合入前必须通过桌面端完整打包验证
2. OCR 本身有质量问题（视觉模型慢且烧 token，tesseract 中文一般），两条路都可能踩坑
3. 图片型 PDF 在实际知识库占比不高，优先级低于「什么都能读」的三条主通道

**决策**：整体顺延到 v0.4，不做半成品合入。方案文档 P1 章节完整保留作为 v0.4 的起点。

### 本期明确的 Non-Goals

| 类别 | 不做的事 | 理由 |
|---|---|---|
| 多模态炫技 | 文生图、图片编辑、图片多模态检索 | 偏离「读」的主题，且需要完全不同的基础设施 |
| 音频视频 | 语音输入、TTS、会议转写 | 本期聚焦静态信息源，音视频归入独立大版本 |
| 云端依赖 | 商业 OCR API、无头浏览器剪藏 | 「本机优先」架构原则；无头浏览器太重且安全边界模糊 |
| 格式兼容 | `.doc/.xls/.ppt` 老式二进制、PDF 内嵌图片入库 | Office 只支持 OOXML 新格式是明确声明；PDF 内嵌图片抽取是 OCR 范畴 |
| 复杂剪藏 | 网页快照、订阅式更新 | 非核心路径，依赖无头浏览器或增量抓取 |
| 插件化 | MCP、自定义工具注册 | 维持 v0.2 决策，插件化在独立大版本统一设计 |
