# 候选 03：能力生态与内容包收口

> 来源：[v2.17 已知边界](../v2.17-release-summary.md)、[v2.17-01 来源方案](../scheduled/v2.17-01-builtin-tools-and-capability-broker.md)、[v2.18 已知边界](../v2.18-release-summary.md)。
> 状态：未排期。

## 1. 问题

v2.17 的「能力代理」与 v2.18 的「内容包」都只完成了主链路，外围还留着几处断点：

- 助手无法主动列出现有技能/工具能力，`capability_list` 只有设计稿；
- 安装审批框复用通用工具确认，看不到目录来源、签名、effect 与「将新增哪些工具」；
- 能力目录只收内置精选包，不能导入第三方本地 ZIP；
- 内容包固定上游 commit，没有「检查更新」，上游内容变化时哈希校验直接拒绝导入；
- 单轮产物数量没有运行时计数，批量生成可能撑爆消息区。

## 2. 现状证据

- v2.17 发行说明「已知边界」逐条列出 `capability_list` 未实现、审批框未展示目录元数据。
- v2.18 发行说明「已知边界」写明内容包未做检查更新、产物数量限制未运行时计数。
- 符号链接 realpath 校验从 v2.11 起连续列为后续版本评估。

## 3. 可选方案

| 方案 | 内容 | 成本 | 风险 |
|---|---|---|---|
| A. 能力可见 | 实现 `capability_list` 只读工具 + 安装审批展示来源/签名/effect/新增工具 | 中 | 审批框信息过载 |
| B. 第三方导入 | 允许本地 ZIP 进入「我的目录」，导入前做清单与路径校验 | 中高 | 供应链风险，需签名/白名单策略 |
| C. 内容包更新 | 记录上游来源与版本，支持「检查更新」并在哈希不一致时给出差异提示 | 中 | 上游不可控，可能引入破坏性内容 |
| D. 产物限流 | 单轮产物数量与总大小上限，超限给出可见提示 | 低 | 限制过严会挡正常批量任务 |

## 4. 风险

- 第三方导入与「本地优先、无云服务」不冲突，但会扩大攻击面，必须先定签名与目录白名单。
- 内容包更新需要网络与版本元数据，弱网下要可降级为「手动重新导入」。
- 审批框信息增加会拉长确认路径，需要设计「默认精简、展开详情」。

## 5. 待决策

1. 先做 A + D（低风险、纯本地），还是把 B 一起做。
2. 第三方 ZIP 是否强制签名；未签名包是否只允许「只读工具」。
3. 内容包更新检查的触发方式（手动按钮 / 打开时提示 / 定时）。
4. 单轮产物数量与总大小的默认阈值。
