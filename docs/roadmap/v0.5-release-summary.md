## 1. 主题与价值主张

v0.4 让数据「随身走」，但助手本身仍是金鱼：每开一个新会话都要重新自我介绍，聊过的重要事项转头就忘。瓶颈从「数据出不去」翻到了「经验留不下」。

| 痛点（v0.4 现状） | v0.5 的回答 |
|---|---|
| 长对话按条数硬截断，后文引用不到前文 | M1：全上下文按 token 预算组装，模型级 `contextTokens` 自动探测 |
| 超出预算的旧历史直接蒸发 | M2：递归摘要压缩，旧对话折叠成摘要块注入 system |
| 每次新会话从零开始，个人信息/偏好要反复交代 | M3：长期记忆全链路（提取 → 去重 → 向量存储 → 跨会话召回注入） |
| 记忆一旦做成就成黑盒，像被「监控」 | M4：记忆管理面板 + 助手级开关 + 清空，隐私闭环 |
| 记忆质量拍脑袋，改了 prompt/阈值不知道变好变坏 | P1-2：golden set + LLM-as-judge 回归评估；消息级 👍/👎 反馈 |
| 无用记忆永久堆积 | P1-1：软归档遗忘策略（低重要性 + 长期未召回） |

**价值主张**：从「无状态工具」到「有记忆的助手」。同时把「记住什么、忘记什么、用不用记忆」的控制权全部交给用户——提取内容可见、可删、可一键清空、可按助手关闭。

## 3. 架构演进

### 数据层迁移（PRAGMA user_version 4 → 7）

```sql
-- v005：对话压缩
ALTER TABLE conversations ADD COLUMN summary TEXT;
ALTER TABLE conversations ADD COLUMN summary_turns INTEGER NOT NULL DEFAULT 0;
-- v006：长期记忆（memories_vec 不在迁移内创建，首次写入按嵌入维度动态建表）
CREATE TABLE memories (...kind/status/importance/source_conversation_id/last_accessed_at...);
ALTER TABLE assistants ADD COLUMN memory_enabled INTEGER NOT NULL DEFAULT 0;
-- v007：消息反馈
ALTER TABLE messages ADD COLUMN feedback TEXT;     -- up | down | NULL
ALTER TABLE messages ADD COLUMN feedback_at TEXT;
```

延续四代铁律：只 ADD COLUMN/ADD TABLE 带 NULL/DEFAULT。旧会话 summary NULL 即「未压缩」，旧消息 feedback NULL 即「无反馈」，老助手 `memory_enabled` 默认 0 即「关」。meta 表新增 KV 通道（向量维度、衰减上次运行时间），跨重启的运行期状态不再借道业务表。

### 记忆管线（独立于文档 RAG 向量域）

```text
回合成功（后台，静默）
  └─ extractTurnMemories：prompt 强约束 JSON + zod 校验 + ≤5 条
       └─ rememberCandidates：嵌入 → L2 ≤ 0.35 视为同一记忆（内容更新 + importance 取大）
            └─ memories_vec 虚表（维度独立 meta 记录，与 chunks_vec 互不干扰）

新回合开始
  └─ recall：查询嵌入 → Top-3 → L2 ≤ 1.05 过滤 → touchAccessed
       └─ formatMemoryBlock → system【长期记忆】区块 → memories SSE 事件（前端提示条）

遗忘（回合成功后机会执行，间隔 ≥7 天）
  └─ archiveStale：active + importance <0.4 + 创建 >30 天 + 从未/久未召回 → archived（可恢复）
```

回合后作业收敛到 `post-turn-jobs.ts` 统一入口：递归压缩 → 摘要情景记忆（importance 0.6 event）→ 记忆提取 → 衰减归档，**每一步独立 try/catch 静默**——记忆是增强不是依赖，任何一步失败只 `console.warn('[wbfm] ...')`，绝不影响已完成的回答。

### 上下文预算体系

摘要块（512）与记忆块（512）作为预留席位进入预算：`buildTurnMessages` 按模型 `contextTokens` 扣除 system 人设、工具声明、RAG、图片后组装历史，超预算从最旧开始折叠进摘要。记忆注入不再是「能塞多少塞多少」，而是预算内的一等公民。

## 4. 关键技术决策

### 4.1 召回阈值靠评估实测，不靠拍脑袋（本版本最重要的方法论时刻）

`MEMORY_RECALL_MAX_DISTANCE` 初值 0.78（≈余弦 0.70）沿用「宁少勿多」直觉，golden set 实测**零召回**。用 sqlite-vec 直查 kNN 定位：小型本地嵌入模型（qwen3-embedding:0.6b）下，短中文问句与目标记忆的余弦普遍只有 0.5~0.65（L2 0.80~1.03）——「问法」与「记法」的语义鸿沟比预想大得多。校准为 1.05（≈余弦 0.45）后 11/12 命中。防噪声不靠收紧阈值，靠 Top-3 限量 + system 提示「与当前问题无关时无需提及」。**阈值类参数必须挂一条可重复执行的评估基线，否则调参就是玄学。**

### 4.2 记忆为什么建独立向量管线而不复用 chunks_vec

文档切片与记忆的生命周期、维度、衰减语义完全不同：文档换嵌入模型要全量重建索引，记忆只有千条量级；memories_vec 按 `meta.memory_vector_dimension` 首次写入时动态建表，与 chunks_vec 互不感知。两域各自的重建/清空/迁移互不牵连，代价是一点代码重复（同一套 sqlite-vec 建表模式复制了两份）。

### 4.3 提取为什么强约束 JSON 且失败静默

本地小模型输出格式漂移是常态：提取 prompt 要求纯 JSON 数组 + zod schema 校验 + 单回合上限 5 条，任何解析失败返回空数组。宁可少记不能记错——错误记忆一旦入库会反复被召回，污染后续所有对话；坏记忆的清除成本远高于漏记。

### 4.4 去重为什么是合并而不是新建

用户会反复表达同一件事（「我不吃香菜」/「点餐不要香菜」）。写入前取最近邻，L2 ≤ 0.35 视为同一记忆：内容更新为最新表述、importance 取大、向量更新。这条规则让记忆库随使用收敛而不是膨胀。

### 4.5 反馈为什么随 conversations 备份轨走

👍/👎 是消息不可分割的评价属性，不是独立实体：v007 加在 messages 表上，备份 conversations 轨经 mapMessage 自然携带，恢复端原样写回。没有为此新增端点或独立导出——数据归属决定数据出口。

### 4.6 评估为什么是本地脚本而不是 CI

评估依赖真实 Ollama 模型与嵌入服务，且结果需要人工解读（哪个用例失败、为什么失败）。`pnpm eval:memory` 定位为「发版前手跑的回归基线」：12 用例全量跑一遍约 5 分钟，输出命中率 + judge 均分 + 可选 JSON 结果，配合 `--reset-memories` 显式确认破坏性清空。

## 5. 踩坑与取舍

### 坑 1：阈值「零召回」的三层洋葱（评估方法论的价值实证）

**现象**：golden set 首跑 0/12 全 FAIL，judge 全 0。逐层剥开发现三个独立问题叠加：

1. **评估脚本 bug**：把 SSE `data:` 负载当信封解析（`event`/`data` 是同层两行），delta 永远不累加，所有回答为空；
2. **陈旧服务假象**：本地 3000 端口是两天前启动的 dev server，跑在记忆接线之前的旧代码——召回链路根本不存在；
3. **真实缺陷**：排除上面两层后仍无 `memories` 事件，sqlite-vec 直查发现最优距离 0.91 > 阈值 0.78，纯几何问题。

**教训**：评估工具自身也要先验证有效性；排查时先用探针请求确认链路活着，再谈参数。三层洋葱反过来证明了「每次失败都值得追到底」——如果只修脚本看到全绿就停，零召回会被带进发布。

### 坑 2：陈旧 dev server 的「幽灵行为」

两天前启动的 next dev 持有旧编译产物，API 正常响应但行为是旧的，且新 `pnpm dev:web` 只会 `EADDRINUSE` 失败——错误还被既有服务的健康检查掩盖。**验证功能前先核对服务进程的启动时间与代码版本是否同代**，这已写进评估脚本的使用前提。

### 取舍：单跳召回不做跨记忆综合

「200 元以内送礼物」需要综合手冲咖啡 + 预算两条记忆，向量检索只命中单条。top-4 实测正确记忆排第 6——放宽阈值能救回这一例，但每轮对话都会多注入几条弱相关记忆。**用例分级：单跳召回必须过（11/12 全绿），跨记忆综合登记为已知边界**，等 v0.7+ 知识层演进，不用噪声换分数。

### 取舍：遗忘是软归档不是删除

低重要性记忆归档（archived）而非物理删除：面板可切换查看、可恢复。「忘记」在 UI 语义上是「淡出视线」，删除权永远留给用户——隐私闭环的一致性要求。

## 一句话总结

v0.5 用 21 个提交、三次加法迁移（v005~v007）和一条「提取 → 去重 → 召回 → 注入 → 遗忘」的记忆生命周期，把 WorkBuddy 从「每次对话从零开始」变成了**跨会话记得住、且把记忆控制权交给用户**的助手；一条 golden set 评估基线挖出了「直觉阈值零召回」的真实缺陷（0.78→1.05 实测校准），再次验证：**本地模型的参数没有拍脑袋的空间，可重复执行的评估才是调参的度量衡。**
