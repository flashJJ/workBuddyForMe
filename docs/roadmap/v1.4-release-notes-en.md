## WorkBuddy For Me 1.4.0 — Tasks that divide the work

Release date: **[DATE, 2026-10]** · Platform: **Windows 64-bit** · Installer: `WorkBuddyForMe-Setup-1.4.0.exe`

Complex requests used to land on a single back-and-forth: the model planned, executed, and checked its own work in one answer, with no visible rework loop and no control over how many steps or tokens it spent. v1.4 introduces **Task mode** — a fixed three-role collaboration where a **Planner** breaks the goal into a structured subtask, an **Executor** does the work with the knowledge base and tools, and a **Reviewer** checks every acceptance criterion before delivery. You watch the handoffs live as swimlanes, with a hard budget cap and clear terminal states.

### 🤝 Task mode — Planner / Executor / Reviewer

- Flip the new **Task mode** switch next to the composer (off by default; conversation-scoped and never persisted). Send a goal and the three roles take over, handing off structured cards instead of free-form chat.
- **Planning card**: the subtask title, brief, and a checklist of acceptance criteria.
- **Execution card**: tools actually called (in order), cited evidence documents with page numbers when available, and any honestly reported unfinished items.
- **Review card**: each acceptance criterion marked met / not met, with an **Approve / Rework / Reject** verdict. When the reviewer sends it back, a new round appears in the same card — the work is never restarted silently.

### 📊 Hard three-way budget

Every collaboration is bounded by a **rounds / steps / tokens** budget (defaults: 3 rounds, 20 execution steps, 80k tokens; configurable per task when embedding an agent in a flow). If the cap is hit mid-review, WorkBuddy stops cleanly, delivers the **best-effort result collected so far**, labels what remains unfinished, and marks the run `Budget exceeded` rather than spinning forever.

### 🧾 Collaboration task center

The Tasks page now has a **Collaboration tasks** section: every run with its goal, status badge, live/handoff detail expansion, and a Stop action for active runs. Runs that involve external agents (published flows) are listed alongside conversation-based tasks.

### 🔷 Agent nodes in Flow Studio

- A new **Agent** node is available in the flow palette: configure the goal (supports `{{$nodes.x.outputs.field}}` references, including array indices), linked assistant, knowledge base, tool scopes (knowledge / desktop chips), per-role model overrides, and an optional custom budget.
- During a test run, an agent node expands into a **read-only collaboration swimlane** in the run timeline. Agent nodes can re-run (each run creates a fresh collaboration; old records are never copied).
- **Safety policy**: when a published flow is called unattended (API / MCP endpoint), an agent node that requests desktop control is rejected before the collaboration starts and never executes. Desktop tools run only in an interactive canvas test run, where the authorization dialog clearly states the request was **“Initiated by the Executor of a collaboration task”**. Authorization still goes through the single global approval channel, and “Allow for this task” is scoped to the executor’s internal task run.

### 🔒 Tool authorization with clear attribution

When an Executor inside a collaboration requests a write/danger tool, the authorization dialog shows where the request came from, so a background collaboration can never silently elevate privileges. No confirmation channel means denial — there is no silent allow path.

### 🔁 Knowledge-connected executor

The legacy desktop agent’s knowledge gap is closed: the Executor’s task loop can retrieve from the bound knowledge base in the no-screenshot **tool observation mode**, so evidence in collaboration deliveries comes from the same citation pipeline as regular RAG answers — with the same document names, page/paragraph coordinates, and deduplicated ordinal numbering.

### 🌐 Bilingual throughout

The new agents domain (entry switch, roles/phases/verdict labels, budget bar, terminal banners, task center) and the agent node configuration form ship in **both Simplified Chinese and English**; strict English coverage was extended to the new flow form.

### 🔬 Deterministic evaluation harness

A new mock collaboration protocol makes the whole pipeline testable with zero network calls: 15 golden cases across four categories (knowledge evidence, tool sequences, review interception, budget/cancel) plus three reverse-validation switches (reviewer off / knowledge off / 1-round budget) — all must degrade exactly as specified. Run it yourself against a mock-mode server with `pnpm eval:agent`.

### 🔒 Local-first, as always

Collaboration runs, handoffs, and task runs stay on your computer and are excluded from backups (same policy as workflow run records). No account, no cloud relay: role models are called directly from your machine, Ollama and offline voice models remain supported, and unattended desktop automation remains permanently prohibited.

### ⚠️ Installing this release

The installer is **not yet code-signed** (a signing certificate is planned for a later release). On first run Windows SmartScreen may show a warning:

1. Click **More info**.
2. Click **Run anyway**.

Only download releases from this repository's official Releases page.

### Upgrading

- Use **Settings → About → Check for updates**, or install over the existing version — settings, data, and knowledge bases are preserved. The v0.19/v0.20 database migrations (collaboration run/handoff tables and per-role assistant model columns) apply automatically on first start.
- Role model overrides are optional: assistants without per-role models inherit the normal model fallback chain, so existing assistants work unchanged.
- Note: API keys entered in the development build (`dev:3000`) use a different local key store than installed builds and may need to be re-entered once.
