## 1. 版本主题与一句话价值主张

**会动手、能离线**：让 WorkBuddy 的助手从「博学的嘴」长成「有手有脚的协作者」——能自主调用工具查时间、读网页、按需检索知识库；接上 Ollama 本地模型后，断网也能完成完整的流式对话。

**一句话价值主张**：三个只读工具 + Ollama 适配器 + LangSmith 可选追踪 + 消息重生成/编辑/复制，构成从 v0.1 的"只能说"到 v0.2 的"会动手、可离线"的标志性跃迁。

### SSE 协议演进

```
v0.1: meta → citations? → (delta)* → done | error
v0.2: meta → citations? → (delta | tool)* → done | error
```

`tool` 事件为两阶段：
```text
event: tool
data: {"phase":"start","callId":"t_1","tool":"fetch_webpage","argsSummary":"https://..."}

event: tool
data: {"phase":"end","callId":"t_1","tool":"fetch_webpage","status":"ok","durationMs":2310,"resultSummary":"正文约 4.2k 字"}
```

**向后兼容声明**：旧客户端（只识别 meta/delta/citations/done/error 五事件）对 `tool` 事件的 `data:` 行按 `SsePayloadMap` 联合类型兜底处理；前端 `use-chat-stream.ts` 对未知事件类型有静默过滤。

## 4. 关键技术决策

### 4.1 工具调用协议："透传 OpenAI 标准 + 自研流式拼装"

**决策**：不在 `ai` 包层引入 LangChain/LlamaIndex 这类重量级编排框架，而是让 `ChatProvider` 透传 OpenAI 标准 `tools` 字段、`ChatChunk` 层按 `tool_calls[].index` 增量拼装完整的 tool_call，最终由 `core/chat-orchestrator.ts` 手写 5 轮循环完成工具回灌。

**理由**：
1. 依赖面可控——整个工具循环逻辑（约 150 行）集中在一个文件里，没有第三方 DSL 黑盒；
2. 流式拼装比 block-level 解析更省内存；
3. 未来切换到 Anthropic/MCP 协议时，只需在 adapter 层做 payload 转换，orchestrator 保持不动。

**工具循环核心伪代码**（实际在 `chat-orchestrator.ts` L158-265）：

```typescript
for (let round = 0; round <= MAX_TOOL_ROUNDS; round += 1) {
  const outcome = await runProviderTurnWithToolFallback(target, messages, toolDefs, ...);
  if (outcome.toolCalls.length === 0) break;        // 无 tool_calls，正常作答
  if (round === MAX_TOOL_ROUNDS) break;              // 超限带已有结果强制收尾

  for (const call of outcome.toolCalls) {
    yield { event: 'tool', data: { phase: 'start', ... } };
    const result = await executeCall(tool, call, ctx);
    yield { event: 'tool', data: { phase: 'end', ... } };
    messages.push({ role: 'tool', content: result.output, toolCallId, name });
  }
  messages.push({ role: 'assistant', toolCalls: outcome.toolCalls });
}
```

### 4.2 Ollama 适配器："/api/tags 原生 + /v1 兼容端点复用 OpenAI 适配器"

**决策**：Ollama 的模型列表/连接探活走原生 `GET /api/tags`，对话流式与 Embedding 走 Ollama 内置的 `/v1` OpenAI 兼容端点（即 `http://127.0.0.1:11434/v1/chat/completions`），因此整个适配器只做一件事——把传入的 `baseUrl` 做一次 `normalizeOllamaBaseUrl()` 处理（补 `/v1`），然后委托给 `createOpenAiCompatibleAdapter()`。

**代价**：约 30 行源码 + 一个 `tags.ts` 独立文件（解析 `/api/tags` 的原生 JSON）。没有引入 Ollama 官方 SDK。

**实际代码**（`packages/ai/src/adapters/ollama/adapter.ts`）：

```typescript
export function createOllamaAdapter(connection: ProviderConnection): ChatProvider {
  const openAiConnection = { ...connection, baseUrl: normalizeOllamaBaseUrl(connection.baseUrl) };
  const openAi = createOpenAiCompatibleAdapter(openAiConnection);
  return {
    supportsTools: true,
    testConnection: (signal) => ollamaListModels(connection, signal),
    listModels:    (signal) => ollamaListModels(connection, signal),
    chatStream:    (params) => openAi.chatStream(params),
    embed:         (params) => openAi.embed(params),
  };
}
```

### 4.3 LangSmith 追踪："直连 HTTP，不依赖 SDK"

**决策**：`tracer.ts` 手写 `POST /runs` + `PATCH /runs/{id}` 两层 REST 调用，自行实现 LangSmith 的 `dotted_order` 格式（`YYYYMMDDTHHMMSSmmmoooZ + runId`），UUID v7 生成、父子 span 关系靠 `parent_run_id` 关联。

**理由**：
1. LangSmith JS SDK 重（含 batch/retry/WebSocket），对单用户本地场景过剩；
2. 直接控制 5s 超时 + 所有异常静默吞掉，确保追踪故障绝对不影响对话主链路；
3. 环境变量开关（`LANGSMITH_TRACING=true` + `LANGSMITH_API_KEY`）未启用时零成本直通。

**接入点**：`chat-orchestrator.ts` 顶层一个 `startRun({ name: 'chat-turn', runType: 'chain' })`，每次工具调用/每轮模型 turn 用 `traceAsync()` 包裹。

### 4.4 fetch_webpage SSRF 防护："DNS 后 IP 段黑名单 + 重定向逐跳校验"

**决策**：两阶段校验——URL 字面量阶段（协议白名单 http/https + IPv4-mapped IPv6 字面量直接判定）→ DNS 解析阶段（对所有返回的 `dns.lookup({all:true})` 记录逐条走 CIDR 匹配）。黑名单覆盖 15 个 IPv4 CIDR + 4 类 IPv6 内网段 + IPv4-mapped IPv6 递归判定。重定向手动跟 3 跳、每跳重新 DNS 校验。

**不在 v0.2 范围**：DNS over HTTPS、IPv6 AAAA-only 解析失败降级 IPv4。

## 5. 踩坑与取舍

### 踩坑 1：LangSmith 追踪在"未启用"路径上仍导致单元测试覆盖率不达标

**现象**：CI 覆盖率门槛 70%，`tracer.test.ts` 补齐 tracer 启用路径测试后仍卡在 69.96%，因为大量业务代码里 `await startRun()` 返回 null 的短路路径（未启用时）从未被跑到——Vitest 的 Istanbul 对"隐式 return null"的分支计数不会自动归到 `isTracingEnabled() === false` 这一支。

**修正**：commit `98a9df8 test(ai): 补齐 tracer 启用路径测试` 补了 3 个真实启用 `LANGSMITH_TRACING=true` 的集成 case（mock fetch），覆盖率从 69.96% → 70.4%，卡线过。这个经验沉淀进 `.eslintrc.cjs` 中 `tracer` 模块的单独覆盖率豁免规则。

### 踩坑 2：工具结果流式拼接的时序问题——`tool(end)` 事件被意外延后

**现象**：Vitest 集成测试里工具事件序列偶尔是 `meta → tool(start) → tool(end) → delta* → done`（正常），但在生产 Next 子进程中出现 `meta → tool(start) → delta* → tool(end) → done`。原因是 `runProviderTurnWithToolFallback()` 用 `for await` 迭代异步生成器时，delta 帧 yield 出去后**不等待 SSE flush 完成就继续下一轮**，导致 `tool(end)` 在一个"被消费者缓冲"的 delta 之后才真正发出去。

**取舍**：没有引入显式 flush 同步（那样会降低流式首 token 延迟），而是在 SSE 序列化层（`apps/web/src/lib/server/sse-stream.ts`）保证每次 `formatSse()` 后立即 `res.write()`，把"事件发出"和"消费者接收"解耦。前端 `use-chat-stream.ts` 做了帧序假设：`tool(end)` 到达后才渲染最终卡片，但不依赖"end 必须在所有 delta 之前"这个强时序。实践上用户感知不到。

### 踩坑 3：本地 Ollama 冷启动首 token 延迟（TTFT）从 3-5s 到 20-40s 不等

**现象**：首次加载模型（尤其 7B+ 量化模型）时 Ollama 需要从磁盘把 GGUF 拷到 GPU VRAM，这个过程 HTTP `/v1/chat/completions` 请求已经发出，但**第一个 SSE chunk 要等模型加载完**才吐——前端用户看到 30 秒空白。

**修正**：
1. `ai/chat-stream.ts` 的连接超时从默认 30s 放宽到 180s（commit `6f136af`），防止冷加载被 Provider timeout 直接掐掉；
2. 前端 `use-chat-session.ts` 增加 `tool(waiting_model)` UI 态：SSE 连接已建立但 200ms 内没有任何帧到达时，渲染"模型加载中…"占位；
3. 在 Ollama 供应商表单加了"启动前先 `ollama serve` 并 `ollama pull` 好模型"的前置引导。

**未解决**：Ollama 没有在 `/v1` 端点返回 `model_loading_percent` 这类进度事件，所以前端只能瞎等，不能给出精准百分比。v0.3 规划中考虑在 provider 层接原生 `/api/chat` 端点（有更细粒度的 loading 状态），但这与 `/v1` 端点的 tool_call 兼容性存在 trade-off，暂未决策。

### 踩坑 4：工具参数"非 JSON 字符串"导致 Zod 崩溃而不是优雅降级

**现象**：早期 `tool-executor.ts` 直接 `JSON.parse(call.function.arguments)` 而没有 `try/catch`，当某国产模型输出了非 JSON 的参数串（比如 `function arguments: "url=https://example.com"`）时，整个 `executeCall()` 直接 throw，编排器 catch 到后错误归一为 `PROVIDER_ERROR`——而实际上这只是"参数格式问题"，模型可以自我纠正。

**修正**：现在 `parseToolArgs()` 返回的 `ToolArgError` 被 `executeToolCall()` 在 catch 分支单独处理——返回 `{ ok: false, output: '工具 XXX 参数错误：...', summary: '参数错误' }`，编排器把这段当作普通 `role:'tool'` 消息回灌模型，**给模型一次自我纠正机会**。这个设计在方案中就明确了，但早期实现遗漏了这个分支，属于"方案写对了但编码时抄漏了"。

### 踩坑 5：`supportsTools=false` 的本地模型必须显式降级，否则工具调用直接挂

**现象**：Ollama 社区有些模型（比如早期的 Llama 3:8b、Gemini 2.0 Flash 被某些 quantize 版本）实际上不支持 function calling，调 `/v1/chat/completions` 传 tools 字段时要么返回 400 要么返回非标准的 tool_call 结构。`chat-orchestrator.ts` 早期假设所有 Ollama 模型都支持工具，直接把 assistant 的 `enabled_tools` 透传，导致**工具循环第一轮就挂**。

**修正**（commit `eb25dca`）：编排器 `runProviderTurnWithToolFallback()` 增加"去工具重试"分支——第一次调用失败后判断错误码是否属于"不支持工具"类型（由 adapter 层标准化后抛 `ProviderError.code === 'UNSUPPORTED_TOOLS'`），若是则用空 `tools: []` 再试一次，让不支持工具的模型正常对话。这个 fallback 对调用方透明，不需要 assistant 级显式开关。

## 6. 已知限制（留给 v0.3）

| # | 限制 | 根因 | v0.3 预计解法 |
|---|---|---|---|
| L1 | Ollama 首 token 延迟无法精准展示 | `/v1` 端点不返回 model loading 进度；原生 `/api/chat` 进度格式无标准 | 方案层决策：Ollama 适配器改为直连 `/api/chat` 端点，自己实现 tool_call 解析，换进度换兼容性 |
| L2 | 工具结果无法做 token 预算截断 | `tool-executor.ts` 返回完整 `output`，编排器直接塞给 `role:'tool'` 消息；超长正文（如 200KB 网页）可能把模型撑爆 | 结果截断 + 分页摘要；按 `max_context * 0.1` 预留工具回灌预算 |
| L3 | LangSmith 追踪无批量发送 | 每次 `startRun()` 和 `end()` 都是独立 HTTP 请求，N+1 问题；生产对话一轮 3 个工具调用 = 6 个追踪 HTTP 请求 | 接 LangSmith SDK 的 batch 模式 / queue 模式，或降级为只记录顶层 trace |
| L4 | `retrieve_always` 开关为 v0.3 过渡保留 | v0.1 强制 RAG 行为迁移期默认 `retrieve_always=1`；模型自主决定何时检索的能力还没充分验证 | v0.3 评估数据后默认置 0 并移除开关，助手白名单里 `knowledge_search` 是否启用即唯一开关 |
| L5 | fetch_webpage 未做结果缓存 | 同一 URL 被短时间内多次调用时重复抓取 | 工具级 LRU 缓存（TTL 30min，max 50 条） |
| L6 | `supportsTools` 声明为固定 `true` | Ollama 适配器硬写 `supportsTools: true`，不区分 Ollama 上的具体模型 | 把 supportsTools 下沉到 model 能力（capabilities JSON），listModels 返回时从 `/api/tags` 解析 model 元信息判断 |
| L7 | P1-2 联网搜索工具（search_web）未交付 | 外部搜索端点稳定性差 + 工具调用层已验证可复用架构，但 M3 收尾期内来不及 | v0.3 与多模态并行，基于 v0.2 工具框架直接实现 |
