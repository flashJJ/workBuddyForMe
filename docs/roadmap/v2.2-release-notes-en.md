# WorkBuddy For Me v2.2.0 — Release Notes

## WorkBuddy For Me 2.2.0 — Feel: pet feedback with shape, a configurable animation graph, and event wiring

Release date: **2026-10-18** · Platform: **Windows 64-bit** · Installer: `WorkBuddyForMe-Setup-2.2.0.exe`

v2.1 made the avatar move, but its feedback was *flat*: holding and tapping differed only by one expression, idle motions rotated without any relation to the pet's mood, and a drag was pure displacement that stopped dead on release. v2.2 answers **"what gives an interaction its shape"**:

**Holding is a process (enter → hold → leave) → idle motions follow mood and relationship → a throw keeps its inertia and snaps to edges → every reaction is decided by a configurable animation graph, and awareness/system/relationship events feed the same pipeline.**

One deliberate scope rule throughout: **policy is shared, execution is VRM-first.** Gestures, gating, drag physics, state-group lookup and the whole animation-graph config benefit both renderers. Segment scheduling and mood-tier selection land on 3D VRM only — **users on a Live2D avatar see exactly the same behavior as before this release**, plus the two genuinely cross-renderer wins (more gestures, inertial dragging).

### 🎬 Segmented motion scheduling (VRM only)

- A motion entry is no longer "play one clip" but **a scheduled entry**: `A_Start` plays and hands over to `B_Loop`, which the hold extends, and `C_End` plays on release before returning to idle. Missing segments degrade in order (no A → straight into B; no C → straight back to idle).
- Imported VRMA files are treated as a single whole (`single`) by default. **You are never forced to split your motion** — segment tagging is an optional annotation at import time, and there is no automatic splitting (a bad split is worse than no split).

### 🧠 State-driven idle selection (shared policy / VRM candidate set)

- Candidates come from each backend (VRM: motion entries; Live2D: motion groups), but the **selection policy is one shared set of pure functions**: mood tiers fall back "exact → worse → better → any", relationship level acts as a **hard gate** (not enough, not given), and everything finally falls back to the `Default` group — so no state can ever end up with nothing to play.
- This release also fixed the relationship-level source of truth: the gate had been reading a settings field that never existed, which pinned every user to "Stranger". The display level now arrives over IPC.

### 🖐️ Drag physics and gestures (cross-renderer)

- Velocity sampling and damping run in the main process (the renderer only reports drag events and the final velocity); the window is repositioned per frame at up to 60 Hz.
- Edge snapping uses VPet's **two-threshold** approach — snapping only begins inside the entry threshold and is abandoned once the cursor passes the maintain threshold — so the window never oscillates on the boundary.
- Gestures were completed with double-click (a character action, kept separate from the head-box double-click that focuses the main window) and with **per-gesture cooldowns** (otherwise the second click of a double-click is eaten by the single-click cooldown and the double-click action never fires).

### ⚙️ Interaction animation graph, in three stages

**An entry = trigger key + conditions (relationship level / mood tier / time window) + an action-entry id.** Action chains stay in code; entries only reference an id — which is what makes the whole graph JSON-serializable.

- **Data layer.** `buildInteractionGraph(overrides, disabled)` puts user overrides **before** the built-in graph and drops disabled built-ins; with neither, it reuses the built-in graph object as-is. The "not found → return nothing" semantics are preserved: disabling *every* entry of a trigger key leaves that key unmatched, which is exactly what "disabled" should mean.
- **Persistence.** Overrides and disabled built-in ids live in `settings_kv` and are **clamped server-side entry by entry** (invalid trigger keys, unknown action-entry ids, unknown built-in ids and out-of-range time windows are dropped and de-duplicated), so hand-editing `settings_kv` can never poison the runtime.
- **Visual editing.** A new "Interaction animation graph" panel in Settings: a built-in section (read-only listing with an enable switch, an "Override" button and an "overridden" badge) plus a custom-entry editor (trigger key in 4 groups / relationship level / mood tier / time window / action entry). This one panel deliberately uses **local draft + explicit save** instead of the instant-save used elsewhere — saving whole arrays field-by-field would let in-flight requests overwrite each other.

### 🔗 Event link wiring

`context`, `system` and `relationship` events were a v2.1 leftover: the resolver ignored them entirely, so proactive care and awareness could only stage in the main window and **could not drive the pet**. v2.2 completes the link:

- **One trigger-key scheme for all event kinds**: `touch::<region>::<gesture>`, `context::<trigger>`, `system::<signal>`, `relationship::<up|down>` (a zero delta and chat events build no key).
- **Gating**: quiet hours still **only let `system.voice-end` through**; cooldown moved from per-region to per-trigger-key (touch keeps the region values, everything else defaults to 2s) so one signal cannot fire twice in a row.
- **System signal sources** (new): voice-state edges (`voice-start`/`voice-end`) plus the v2.0 system-awareness bridge (`lock` → `locked`, `unlock`/`resume` → `wake`, and system idle **only on the rising edge** past the work-streak gap — the 30-second polling samples themselves are not forwarded, to avoid flooding). Awareness keeps its explicit user authorization.
- **Transport**: non-touch events are relayed to the pet window over the existing `pet:performance` channel (touch scenes are *not* relayed, to avoid double-playing alongside a real touch), and the pet window feeds them into the very same `resolveAndDispatch`. The main process sanitizes the payload at the IPC boundary and only admits enumerated values.
- **Four default behaviors** were added for the perceptible-and-quiet cases: `context::longNoChat` / `context::workStreak` → `notice` (a face change, no body motion), `system::wake` / `relationship::up` → `cheer` (one-shot motion + joy). Everything else is intentionally left empty, with the reasoning written into code comments and tests: `lateNight` sits inside the default quiet-hours window (it would never fire anyway), `voice-end` triggers after every spoken sentence (it would become noise), `voice-start` would fight the speaking expression, `idle`/`locked` happen when nobody can see the screen, and `relationship::down` gets no default performance per the relationship contract ("no push, no guilt"). The two new action entries contain **no `interaction.start`** — nobody touched the pet, so the three-stage machine must not run.

### 🧹 Hydration gating, cleaned up repo-wide

- `/settings` reported `Did not expect server HTML to contain a <div> in <section>` and fell back to client rendering for a whole Suspense boundary. The mismatch was traced to the tuning panel: its `<section>` rendered a Spinner placeholder on the server and nothing on the client's first frame — the classic query-state structure swap (React #418/#422).
- The fix follows the pattern already used by other panels: **the first frame always equals SSR (static heading only), data-driven content expands after mount**. The same pattern was then swept across 10 more data-driven panels (MCP, permissions, tool breaker/debug, skills, asset list, character cards, memory, voice preferences, and the settings page's provider block).

### Known limits and deferred scope

- **Not yet verified on real hardware**: the three-stage hold feel, throw inertia and edge snap, the body double-click action, and Live2D parity — all need Windows with real multi-monitor setups.
- **System signals in particular need a real-machine pass** (lock / unlock / idle) since the pet runs in an Electron window and the browser dev environment cannot produce those events.
- **Most non-touch keys still ship without a built-in entry**; whether `relationship::down` deserves a "comfort" behavior is a product call.
- **Mood-tier transition animation** (VRM only) is still deferred: it needs `Switch_Up`/`Switch_Down` transition clips for the built-in motions, which is an asset cost.
- **Live2D did not get equivalent capabilities**: per-state motion groups, hold-to-sustain and transition segments all require re-exporting the Cubism assets.
- **Chat events are not wired**: `eventTriggerKey` intentionally returns null for them until we decide whether @-mentions or new messages should drive performance.
