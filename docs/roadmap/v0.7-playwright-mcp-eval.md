# v0.7 浏览器自动化（P1-1）评估结论：playwright-mcp

> 状态：✅ 评估完成（2026-09-30）｜ 决策：v0.7 不真接入 playwright-mcp，登记 v0.8+ 重新评估

## 1. 评估目标

按 [v0.7 方案 P1-1](v0.7-computer-agent.md#p1-1-浏览器自动化playwright-桥)：用户故事「去某网站搜 XX，把前三条结果存进知识库」需要驱动真实浏览器，能处理登录态。原计划「`playwright-mcp` 官方服务器优先评估，不达标再自研」。

本评估文档化结论与依据，便于 v0.8+ 启动浏览器自动化专项时直接复用。

## 2. 评估对象

**microsoft/playwright-mcp**（GitHub 官方仓库）：

- 协议：标准 MCP（stdio / SSE），符合本项目 v0.6 已实现的 MCP 客户端兼容面
- 能力面：tab 创建/切换、navigate、click、fill、select、hover、evaluate、screenshot、pdf 等 ~20 个工具
- 浏览器后端：内置 Playwright bundled 浏览器（chromium-headless-shell）或连接用户已有 Chrome（CDP 端口 9222）

## 3. 评估维度与结论

| 维度 | 评估结果 | 影响本项目 |
|---|---|---|
| **依赖体积** | `@playwright/test` + `playwright-core` ≈ 8MB JS bundle + bundled 浏览器 ≈ 280MB（chromium-headless-shell 仅 Windows 单平台） | 与 v0.4 `@napi-rs/canvas` 归集经验相比，量级是 10×+。打包归集到 asarUnpack 后安装包从当前 ~120MB 涨到 ~400MB |
| **打包影响** | 需在 electron-builder 添加 `asarUnpack: ["node_modules/playwright-core/.local-browsers/**"]`，且 Playwright 装浏览器在 `postinstall` 走外部下载（离线打包需先 `PLAYWRIGHT_BROWSERS_PATH=0` 缓存再归集） | 与 v0.7 M2 `nut-js` 打包 spike 经验一致：原生依赖打包归集链路脆弱；增加打包失败概率 |
| **接入复杂度** | 中等：可走 stdio 子进程（v0.6 已有 stdio MCP 客户端）；但 CDP 连接用户 Chrome 需用户先 `chrome --remote-debugging-port=9222` 启动，UX 阻力大；自动 spawn 浏览器需管理子进程生命周期 | v0.6 MCP 客户端可直连，技术链路 0 改动；但 UX 需在设置页加「Chrome 路径配置 + CDP 端口检测」向导，估 1.5 人日 |
| **与任务模式联动** | playwright-mcp 工具是「DOM 操作」路径，与 P0-2 「屏幕视觉 + 键鼠」路径并存：浏览器任务用 DOM 选择器更准、自绘 UI 用键鼠兜底 | 架构契合：allowedTools 可同时含 `mcp:playwright:click` 与 `mouse_click`；planner 自动选 |
| **离线可用性** | 需首次在线下载 chromium；之后全离线可用 | 违反 v0.7 「云端模型可选加速、本地优先」原则的边缘：浏览器本身是离线的，但下载链路在线 |
| **维护风险** | microsoft/playwright-mcp 在 2025 末才稳定（v1.0），API 仍在演进；与 v0.6 自实现 JSON-RPC 经验对比，外部服务器升级有协议变动风险 | 中：可固定版本号锁 |

## 4. 决策与依据

**v0.7 不真接入 playwright-mcp**，原因：

1. **打包体积失控**：单平台 ~280MB 增量破坏 v0.7 「桌面 Agent」最小可用闭环的轻量定位（M2 nut-js 已增加 ~12MB）；v0.4 Smart App Control + electron-builder 归集链路本就脆弱，再加一层 Playwright 浏览器归集会让打包成功率下降到不可接受
2. **核心场景已被覆盖**：v0.7 P0-3 任务模式 + P0-2 键鼠工具已可完成 demo②「打开浏览器访问指定网页，把正文存入知识库」——通过 `app_launch` 启动 Chrome + `keyboard_type` 输入 URL + `screen_snapshot` 截屏 + `fetch_webpage` 抽正文入库，链路虽不如真 playwright 优雅但闭环可用
3. **登录态复用 ROI 低**：playwright-mcp 真正的优势是「跨会话保留 cookie/profile 的复杂登录态操作」，但本项目当前阶段用户故事尚未触达「需要批量登录网站爬数据」层级；先用本机 Chrome + 用户已登录的 session 由键鼠 + screen_snapshot 操作，未来再视实际使用痛点决定
4. **v0.8+ 重新评估窗口**：当 v0.7 上线后用户反馈集中在「浏览器自动化精度不够」时，再启动 v0.8+ 浏览器自动化专项：那时 playwright-mcp 已更成熟、可重新评估；或考虑自研轻量 DOM 工具组（直接 CDP 协议，避开 Playwright bundle 体积问题）

## 5. 影响与登记

- **v0.7 M4 验收**：demo② 改用「键鼠路径」完成，不依赖 playwright-mcp；验收标准不变
- **M4 范围收窄**：从「playwright-mcp 接入 + demo② + 备份轨 + 发布」收窄为「demo② 键鼠路径 + 备份轨 + 发布」；M4 仍为收尾里程碑，不延期
- **架构留口**：v0.6 MCP 客户端 + v0.7 任务 Agent 循环已为浏览器工具预留接入位（allowedTools 已支持 mcp: 前缀），v0.8+ 评估通过后无需架构改动即可挂载
- **README 路线图**：v0.7 索引行不增加「浏览器自动化」子条目；登记到 v0.8+ 远期展望

## 6. 后续动作

- v0.7 发布后，在 release-summary 中标注「playwright-mcp 评估未接入」结论，引导用户反馈
- v0.8+ 启动时优先复盘 v0.7 浏览器任务实测痛点，再决定接入 playwright-mcp 还是自研轻量 CDP 工具组
