# v2.34.0 发行说明

> 主题：**备份可续——增量归档、链式恢复与基线完整性**
> 发布：已合入 main · tag `v2.34.0`
> 数据库：零迁移，`LATEST_SCHEMA_VERSION = 51`
> 备份格式：schema v8 → v9（新增归档身份与链字段；v8 归档按单段全量兼容）
> 完整方案：[v2.34](../plan/v2.34/README.md)

## 一、核心功能更新

### 1. 全量基线完整性

- 导出会话改为全量读取，取消 10,000 个会话的静默上限；
- 导出消息改为按会话全量读取，取消单会话 500 条的静默上限；
- manifest v9 记录真实 `messageCount`，预检与恢复核对接真实消息数比对；
- 归档仍受 500MB 上限保护：超限直接失败并给出可读错误，不产出半份文件。

### 2. 增量归档

- 导出请求新增 `mode: 'full' | 'incremental'`，默认全量；
- 增量以父段 `startedAt` 为 `since` 下界，只带该时间之后新建的行；
- settings 与 skills 以全量快照写入，其余轨道按 `created_at` 过滤；
- 无全量基线时拒绝增量；链长达到 20 段时要求重新全量；
- 空增量仍产出归档以保持链连续，报告中各轨新增为 0。

### 3. manifest v9 归档链信息

- 新增 `archiveId`、`kind`、`chainId`、`sequence`、`parentArchiveId`、`startedAt`；
- 全量固定 `sequence = 0` 并新建链；增量继承 `chainId` 且父段序号 +1；
- v8 及更早归档缺少这些字段时，统一按「单段全量」补齐；
- v9 客户端可恢复 v8 归档；v8 客户端按 schema 版本拒绝 v9 归档。

### 4. 本地备份登记

- 导出历史写入 `meta backup.history`，保留最近 20 段（归档 id、链 id、序号、类型、时间、轨数、大小、加密标记）；
- 恢复链状态写入 `meta backup.restoreChain`，记录已应用段与缺失序号；
- 两类登记都不进入任何备份轨，不会随设置恢复带回其他机器的状态；
- 最近一次导出摘要由历史首条派生，不再写入 `settings_kv`。

### 5. 链式预检与恢复

- 预检响应新增 `chain`，前端可多选最多 20 个归档；
- 前端按序号排序并校验：恰好一段全量、序号连续、父指针连续、链 id 一致；
- 校验失败返回 `BACKUP_CHAIN_INCOMPLETE` 或 `BACKUP_CHAIN_MISMATCH`（均 422）；
- 恢复仍逐段调用单文件接口，内存峰值不叠加；服务端用 `restoreChain` 校验前置段；
- 增量恢复允许向已有会话追加新消息，会话标题与时间保持本机版本；
- 每段成功后更新链状态；中途失败保留已完成段，可从失败段重试。

### 6. 导出/恢复核对扩展

- 导出的逐轨报告计入消息数，与 manifest 的 `messageCount` 对齐；
- 恢复核对新增链级摘要：已恢复段数、各段声明/写入/跳过合计、缺失序号；
- 核对差异只告警，不阻断恢复。

## 二、重要特性优化

- **设置页备份面板**：新增全量/增量切换、当前链尾展示、增量不可用时的就地提示；
- **备份历史卡片**：展示最近一次导出与更早的 10 段记录，只读；
- **多文件恢复**：选择多个归档后展示链时间线与逐段进度，单段失败不重跑已完成段；
- **核对卡片**：在原有逐轨核对上增加链级段数与缺失序号；
- **恢复进度**：多段恢复按「第 N/M 段」提示，失败提示包含失败段序号与原因；
- **旧归档兼容**：v8 归档不需要重新打包即可作为基线恢复。

## 三、问题修复列表

1. **全量导出静默截断**：会话最多 10,000、单会话消息最多 500，超出部分既不进归档也不告警；改为全量读取并在 manifest 记录真实消息数。
2. **增量消息无法写入已有会话**：原恢复逻辑「会话已存在即整段跳过」，会丢弃增量中的新消息；新增增量追加分支。
3. **导出时间水位竞态**：原 manifest 的 `createdAt` 在打包末尾生成，无法作为下一段安全下界；新增 `startedAt`，以「宁可重复不可遗漏」为原则。
4. **链状态随设置轨迁移**：`backup.lastExport` 原存 `settings_kv`，会被导出到其他机器；迁移到 `meta`，并区分导出历史与恢复链状态。
5. **恢复缺少顺序保护**：增量归档可能被直接恢复；新增服务端前置段校验与链错误码。
6. **核对口径不一致**：声明只算会话、写入包含消息，差异永远存在；manifest 补 `messageCount` 后统一口径，v8 归档回退会话数。
7. **分支负载未随增量过滤**：分支与分支事件原本每次全量写入增量；改为按 `createdAt` 过滤。
8. **运维审计 E2E 的 schema 断言滞后**：断言同步到 v051 的 51，修复 main CI 的 E2E 失败。

## 四、兼容性变更说明

- **数据库**：零迁移，`LATEST_SCHEMA_VERSION` 保持 51；仅使用已有 `meta` 表保存本地备份登记。
- **备份 schema**：由 8 升至 9。v8 归档仍可恢复，按单段全量处理；v8 客户端会拒绝 v9 归档。
- **接口**：
  - `POST /api/backup/export` 新增可选 `mode`；
  - `POST /api/backup/precheck` 响应新增 `chain`；
  - `POST /api/backup/restore` 响应结果新增 `chain`，核对新增可选 `chain` 摘要；
  - `GET /api/backup/last-export` 改为从 `meta` 读取，并额外返回 `history`。
- **错误码**：新增 `BACKUP_CHAIN_INCOMPLETE`、`BACKUP_CHAIN_MISMATCH`，HTTP 状态均为 422。
- **增量语义**：只补 `since` 之后新创建的行，不含既有行的修改、删除、文档重解析与记忆覆盖；全量仍是迁移与克隆的唯一权威。
- **登记位置**：`backup.history` 与 `backup.restoreChain` 存 `meta`，不进入备份；旧 `settings_kv.backup.lastExport` 不再写入。

## 五、升级注意事项

1. **升级前先做一次全量备份**：全量是后续增量的基线，也是迁移的唯一权威。
2. **增量不能替代全量**：删除、重命名、文档重解析、记忆更新不会进入增量；需要精确克隆时请使用全量。
3. **恢复顺序**：先恢复全量基线，再按序号恢复增量；顺序错误会被服务端拒绝。
4. **链状态丢失的处理**：重新恢复一次全量基线即可重置链状态（幂等），再从下一段增量继续。
5. **链长上限**：达到 20 段后需要重新全量开启新链；历史记录保留最近 20 段。
6. **密码**：同一链建议使用同一密码；每个段独立 salt/iv，错密码在预检阶段拒绝。
7. **本地登记不随归档迁移**：把归档拷到另一台机器时，备份历史与恢复链状态不会一起过去；新机器以实际恢复的全量基线重新开始。
8. **旧归档**：v8 归档可直接作为基线；更早归档缺少的字段仍按 0/空数组处理。
