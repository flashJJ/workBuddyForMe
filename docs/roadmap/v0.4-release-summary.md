## 1. 主题与价值主张

v0.3 让助手「什么都能读」——视觉对话、Office 文档、网页剪藏闭环，信息进得来。但真实用了两个月后，瓶颈翻到了另一面：**数据出不去**。

| 痛点（v0.3 现状） | v0.4 的回答 |
|---|---|
| 换机只能手工拷整个 `~/.workbuddy-for-me/`，无校验无选择性，跨版本 schema 随时崩 | M1：四轨道可选 tar.gz 备份 + 合并式恢复 + 向量按需重建 |
| 好对话只能截图，代码/工具过程/引用全丢，还可能把 API Key 发出去 | M2：Markdown / 单文件 HTML 导出，四层脱敏纯函数兜底 |
| 桌面端每次发版手动下载替换，补丁触达不了已安装用户 | M3：electron-updater + GitHub Releases 全自动更新 |
| 扫描版 PDF 文字层为空，文档直接失败，手机拍的合同全部进不来 | M4：视觉模型优先 OCR + tesseract.js 离线兜底 |
| 常用操作要点 3-4 层菜单，重度用户没有键盘流 | M5：Ctrl+K 命令面板（Web 监听 + Electron 全局快捷键） |

**价值主张**：本地优先不等于数据孤岛。v0.4 让数据能打包带走、能体面外发、应用能自我更新，并补齐了摄入侧最后一块「无文字层文档」的短板。P0 三件构成主题闭环，P1 两件（OCR、命令面板）均为方案内承诺项，P2 全部按计划留白，没有一个半成品合入。

## 3. 架构演进

### 数据层迁移（PRAGMA user_version 3 → 4）

```sql
ALTER TABLE documents ADD COLUMN ocr_status TEXT;   -- running | done | failed | skipped | NULL
ALTER TABLE documents ADD COLUMN ocr_engine TEXT;   -- vision | tesseract | NULL
```

延续三代铁律：**只 ADD COLUMN 带 NULL/DEFAULT，不改已有列、不回填数据**。老文档两列均为 NULL，语义即「非 OCR 来源」，所有旧分支行为不变。`partial` 作为新的文档状态进入状态枚举，与 indexed/failed 同级——部分页 OCR 超时不是失败，已识别文本必须可检索。

### 备份归档格式（backup schema v1）

```text
xxx.wbfm-backup（tar.gz）
├── manifest.json        # backupSchemaVersion / appVersion / createdAt / 各轨条目数
├── conversations.json   # 会话 + 消息（content_parts/tool_trace 原样 JSON）
├── knowledge.json       # 知识库 + 文档元数据 + 分片原文（不含向量）
├── settings.json        # 设置（密钥密文不出库）
└── attachments/...      # 可选，按 sha256 文件名存放二进制
```

版本号单调递增、恢复端版本探测 + 未来迁移适配器链，是 v1 格式上线时就写进注释的契约。向量不进备份是刻意的：可再生产物不占体积，也避免跨 embedding 模型的维度冲突。

### OCR 编排结构

```text
read-document（文字层）
  └─ 页密度判定 pageNeedsOcr（<50 字符/页）
       └─ runPdfOcr
            ├─ 视觉可用 → 一次批量渲染（带像素预算）→ 逐页 recognizePageWithVision
            └─ 否则     → tesseract 单 worker 逐页识别
       └─ assembleText：文字层稠密页保留原文 + OCR 页按页序拼接
  └─ extractDocumentText → { text, ocr: { engine, partial } | null }
       └─ 既有分片 → embedding → sqlite-vec（零旁路）
```

超时是分层的：单页 30s 跳过该页继续，全文 5min 封顶，超 50 页只处理前 50 页并标 partial。视觉路线渲染失败是 fatal（整份重试无意义），单页识别失败是 continue；tesseract 渲染失败直接 break。这些区分都来自「哪些错误重试能救回来」的判断，而不是统一 catch。

### 自动更新状态机

```text
idle → checking → available → downloading(0~100%) → downloaded → quitAndInstall
                ↘ not-available
        任意阶段 ↘ error（提示手动下载，不阻塞应用使用）
```

通道（stable/beta）与上次检查时间持久化在独立状态文件，Updater 构造时同步到 `allowPrerelease`。第三方单例 electron-updater 被藏在 `AutoUpdaterLike` 接口后面，单测注入 EventEmitter mock 即可覆盖全状态流转。

## 4. 关键技术决策

### 4.1 恢复为什么是「合并」而不是「覆盖」

覆盖式恢复（清空再导入）实现最简单，但三个问题无法接受：误操作不可撤销、重复导入产生双胞胎、恢复一个只含部分轨道的归档会抹掉其余数据。最终策略：会话按 ID 跳过已存在项，知识库按 content hash 去重，整个写入包在单事务里失败整体回滚，外键依赖按拓扑序写入、不安全的关联直接跳过并计入 warnings。precheck 先报告「将导入 N 会话/M 文档」再执行，破坏性操作必须让用户先看见后果。

### 4.2 脱敏为什么做成纯函数且四场景共用

`sanitizeShareText` 是无依赖纯函数：输入字符串输出字符串，规则只有四类（本地路径、sk- key、Bearer/Basic、key/token/secret/password 赋值串），每条规则独立单测。分享快照对 content/contentParts/tool_trace 全字段递归套用；备份序列化同样复用。**脱敏逻辑只有一份**意味着审计面只有一处——安全相关代码最忌讳每个出口各写各的正则。

### 4.3 OCR 为什么视觉优先而不是 tesseract 优先

v0.3 已有视觉基础设施（vision target 解析默认对话模型、image_url wire、Ollama 真机验证），视觉模型对混排、低清、手写体的识别质量显著优于 tesseract；tesseract 的价值是「零网络、零模型配置也能兜底」，定位为离线降级而非主路线。两条路的输出收敛为同一种纯文本结构，上游永远不感知引擎差异。

### 4.4 命令契约放 shared 而不是 web

`Command`/`fuzzyMatch` 放 shared，web 面板与 desktop 唤起共用同一份类型与匹配算法。fuzzy 匹配选 subsequence 而非 `includes`：输入「xh」能命中「新建对话」，且连续命中权重更高——这是命令面板手感的底线，纯函数单测钉死。

### 4.5 更新逻辑只活在 Electron 主进程

所有 electron-updater 调用在 main 进程，渲染进程只通过 preload 暴露的窄桥订阅状态；`enabled = app.isPackaged` 保证 dev/test 下全部 no-op。无主窗口时 IPC 事件静默丢弃，更新永远不能阻塞应用启动。

## 5. 踩坑与取舍

### 坑 1：pdfjs 吃掉了输入 ArrayBuffer（最隐蔽，静态分析无解）

**现象**：M4 单测全绿，但真机上视觉与 tesseract 两条路线都没有真正产出，多页文档全部失败。

**定位**：插桩 `Worker.prototype.postMessage` 拿到调用栈，发现 pdfjs 在 Node fake-worker 模式的 `LoopbackPort.postMessage` 内执行 `structuredClone(obj, { transfer: [data.buffer] })`——**第一次 `getDocument(data)` 就把输入缓冲 transfer（detach）了**，`data.byteLength` 变 0；原 runner 每页渲染重新打开同一缓冲，第二页起必抛 `DataCloneError: Cannot transfer object of unsupported type`。用独立 node 脚本验证了 transfer 后 byteLength=0、二次 getDocument 必现。

**修复**：text 提取与渲染两处 getDocument 一律传 `data.slice()` 副本；runner 重构为每引擎只打开一次 PDF、`renderPdfPagesToPng` 批量渲染全部目标页（`Map<pageNumber, png>`）再逐页识别。顺带消除了多页 PDF 的重复解析开销。

**教训**：凡是带 worker/transfer 语义的库，输入缓冲的所有权必须当成移交而非出借。这条坑 mock 测不出来——**真机端到端验证是原生/本地模型链路的不可替代环节**。

### 坑 2：视觉图片超本地模型上下文

**现象**：A4@2x（2480×3508，约 870 万像素）视觉 OCR 稳定 400，1.5x/1.25x 也 400，scale1 才通。

**根因**：qwen2.5-vl 按像素桶计 image token（约 784 像素/token），870 万像素 ≈ 4106 token，撞 Ollama 默认 4096 num_ctx；1.25x/1.5x 落同一桶所以一样超。

**修复**：引入像素预算常量（200 万像素 ≈ 2550 image token），渲染前先取 `getViewport({scale:1})` 读基准尺寸，`resolveRenderScale` 按 `sqrt(maxPixels/basePixels)` 等比缩回；A4@2x（200.4 万）仅微缩、识别质量无损，超大画幅自动降档。

### 坑 3：temperature 导致的「随机漏行」

**现象**：修复后端到端走通，但每一页都恰好漏一行；用完全相同的 prompt/图片/流式参数绕开应用直连 Ollama，4 行逐字完整，`finish_reason=stop`——一度怀疑 SSE 增量解析丢 delta。

**结论**：重跑管线一次又完整，证明是采样波动而非解析 bug。OCR 是确定性转录任务，不该有 temperature=0.6 的创作空间。固定 `temperature: 0` 后真机回归逐字稳定。排查过程中的真正收获是那条方法论：**怀疑解析层之前，先用同一请求体绕开应用直连一次**，可以瞬间把问题切成「模型行为」与「应用链路」两半。

### 取舍：partial 不是 failed

单页超时/超页数上限时，旧设计倾向于整篇 failed。但 49/50 页成功时把整份文档判死、让 49 页内容不可检索，是对用户最差的结果。v0.4 引入 `partial`：已识别内容正常分片入库可被 RAG 命中，文档徽标明确提示不完整。检索可用性与诚实标注不矛盾。

### 取舍：不做在线分享、不做备份加密

单用户本地优先的威胁模型下，引入云存储做分享链接的收益远不抵成本；备份加密面对的是「用户能拿到文件就已经物理接触机器」的场景，加密提供的边际安全有限。两者都登记 P2，等真实反馈出现再评估。
