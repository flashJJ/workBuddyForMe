## 2. 技术要点

- **canonical 单一实现**：`canonicalizeCapabilityManifest` 只留在 shared（键递归排序、数组保序、去 `signature`），域前缀 `capability-manifest-v1\n` 防跨协议复用；签名端与验签端都作用于 `capabilityManifestSchema.parse` 后的规范化清单，缺省字段不会造成两端不一致。
- **验签边界**：`node:crypto` 只在 core 的 `capabilities/signature.ts`，shared 保持纯函数，客户端 bundle 不引入服务端加密依赖。
- **策略只决定「没签名/不认识」**：`warn` / `require` 下 `invalid` / `malformed` 无条件 422，避免签名反而成为降级攻击面；`off` 是显式逃生门。策略在安装、升级、启用三个入口都生效。
- **升级状态机**：先 disable 旧 effect → 写 `.staging` → live → `.backup` 原子换位 → 替换清单 → enable 新 effect；任一步失败恢复目录、清单与旧 effect。`skill` / `mcp` / `pet-action` 的句柄可能变化，预检排除旧句柄自身；`event-script` id 不可变，换包走 `replaceDefinition`；`workflow` 新增版本并发布，禁用态升级后显式置回禁用。
- **健康检查以数据库行为真相**：磁盘侧报 `pack_dir_missing` / `checksum_mismatch` / `payload_extra_file` / `orphans`，effect 侧按 kind 探测对象是否存在及状态是否一致；签名始终参与报告，不受安装策略影响。
- **零迁移**：不新增表与列，升级只改 `capability_packs` 既有字段；回退旧版本不破坏数据。

## 6. 已知边界

- 过期清理需要用户点一次「清理残留」，服务启动不自动扫盘。
- `payload_extra_file` 只扫 `payload/`；清单与根目录散落文件不参与。
- 健康扫描同步执行，包很多时耗时线性增长；未做分批/流式。
- 升级不支持降级与同版本修复安装（P1）；工作流回滚保留历史版本行。
- 策略切到 `require` 不实时统计受影响包数；信任库整组保存，多标签页并发覆盖沿用设置页现状。
- 符号链接 realpath 校验、`/capabilities` 运行下钻仍列 P1。
