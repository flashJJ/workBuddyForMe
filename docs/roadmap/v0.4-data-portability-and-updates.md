# v0.4 迭代方案：数据随身

- **版本号**：v0.4.0
- **主题**：数据随身（备份/分享/自动更新 + P1 图片型 PDF OCR 兜底）
- **状态**：方案已定，待评审
- **预估工作量**：约 14-16 人天（一个人全职）

---

## 1. 版本主题与目标

v0.3 让助手「什么都能读」——视觉对话、Office 文档、网页剪藏三板斧已闭环。但数据
**进得来出不去**：

1. 重装系统或换机，所有会话/知识库/设置**没有可移植的备份恢复**——SQLite 文件手工拷贝
   不算备份，缺校验、缺选择性、缺版本对齐。
2. 一次好的对话**无法分享**——截图发朋友圈不体面，对方要的是可阅读的 Markdown/HTML。
3. 桌面端**没有自动更新**——每次发版都要手动下载替换，v0.3 的三个线上 Bug 本可以热修复。
4. 图片型 PDF（扫描件）在 v0.3 是明确 P1 留白，用户上传后**抽出空文本直接失败**，体验断崖。

v0.4 要让数据**可备份、可分享、可更新**，并补上 OCR 兜底：

1. **备份恢复**：分轨导出（会话/知识库/设置可选）、导入校验（schema 对齐 + 版本探测）。
2. **对话分享**：单会话导出为 Markdown/HTML 快照（含工具过程、引用、图片 data URL）。
3. **自动更新**：electron-updater + GitHub Releases，桌面端检查更新、下载、安装、重启。
4. **OCR 兜底（P1）**：图片型 PDF 用视觉模型做 OCR，无视觉模型时 tesseract.js 离线兜底。

**成功指标**：

- 在桌面端触发「备份」→ 选择「会话+知识库」→ 生成一个 `.wbfm-backup` 归档文件 → 在另一台
  机器上「恢复」→ 会话和知识库完整复现，嵌入向量可重建。
- 在任意会话点击「分享」→ 生成一个独立 `.html` 文件，用浏览器打开可阅读完整对话（含代码块、
  图片、工具过程卡片、引用角标），不依赖任何服务。
- 发布 v0.4.1 修复补丁后，已安装 v0.4.0 的桌面端在 24h 内自动检测、下载、安装并重启。
- 上传一份扫描版 PDF（纯图片、无文字层）→ 状态为 indexed → 提问命中 OCR 提取的文本。

## 2. 现状与痛点

| 现状（v0.3） | 痛点 |
|---|---|
| 数据全部在 `~/.workbuddy-for-me/`（SQLite + attachments + files） | 手工拷贝整个目录不算备份：无校验、无选择性、跨版本 schema 不兼容会 crash |
| 无导出 API | 用户无法只导出某个知识库或某段会话 |
| 对话只能看不能分享 | 截图不体面，复制粘贴丢格式 |
| Electron 打包靠 `pnpm build:desktop` 手动生成 + 手动安装 | 无 auto-update；v0.3 的三个线上 Bug 需要手动替换 exe |
| `read-document.ts` 的 PDF 路径仅取 `getTextContent()` 文字层 | 扫描版 PDF 文字层为空 → 分片为空 → indexed 但检索永远 0 命中 |
| `mergePdfTextItems` 只解决文字层跨行合并 | 图片型 PDF 根本没有 text item，合并也白搭 |
| 无全局快捷键 | 常用操作（新会话/搜索/切助手）要点 3-4 层菜单 |
| 无命令面板 | 重度用户效率低，「输入命令名直接执行」是标配 |

## 3. 功能清单

### P0 —— 必做（构成版本主题闭环）

#### P0-1 备份与恢复

- **用户故事**：我要换电脑，把所有知识库和最近一个月的会话导出来，在新机器上恢复。
- **验收标准**：
  1. 设置页新增「备份与恢复」区块：导出按钮触发弹窗，可选「会话」「知识库」「设置」「附件」
     四个轨道（默认全选）；点导出生成一个 `.wbfm-backup` 归档（zip 格式，内含 `manifest.json`
     + 各轨道 JSON + 可选 attachments 二进制）。
  2. `manifest.json` 记录：备份版本号（`backup_schema_version`）、创建时间、源应用版本号、
     各轨道条目数、数据根路径相对映射。
  3. 恢复：选择 `.wbfm-backup` 文件 → 预检查（版本兼容性、轨道完整性）→ 确认弹窗（显示将
     导入 N 个会话 / M 个知识库）→ 执行 → 完成摘要。
  4. 恢复策略：**合并而非覆盖**——同名知识库不重复创建（按 content hash 去重），会话按 ID
     跳过已存在项；嵌入向量按需重建（备份里只存原文+分片文本，不存向量——体积小且可重建）。
  5. 大文件保护：备份归档上限 500MB（超限提示分批），恢复前磁盘空间检查。
- **技术要点**：
  - 导出：`packages/core/src/backup/export.ts`——按轨道从 DB 拉取数据序列化为 JSON，
    附件从 `attachments/` 和 `files/` 读取二进制，用 Node `zlib` + `tar` 打包。
  - 恢复：`packages/core/src/backup/restore.ts`——解析 manifest → 版本探测 → 按轨道
    写入 DB（事务包裹，失败回滚）→ 重建索引（对恢复的知识库文档重新嵌入）。
  - API：`POST /api/backup/export`（SSE 进度流）、`POST /api/backup/restore`（SSE 进度流）。
  - 前端：`apps/web/src/features/settings/backup-panel.tsx`——轨道选择、进度条、恢复确认。
- **工作量**：3 天

#### P0-2 对话分享导出

- **用户故事**：我和助手讨论了一个技术方案，想把这个完整对话发给同事看。
- **验收标准**：
  1. 会话页面右上角「分享」按钮 → 弹窗选择格式（Markdown / HTML）→ 下载文件。
  2. Markdown 格式：按消息顺序渲染，user/assistant 角色标注，代码块保留语法高亮标记，
    工具过程块渲染为 `> 🔧 fetch_webpage (2.3s) → 成功` 引用块，引用角标渲染为脚注链接。
  3. HTML 格式：独立单文件（内联 CSS，图片以 data URL 内嵌），浏览器直接打开可阅读，
    样式与 app 内一致（消息气泡、代码高亮、引用角标可展开）。
  4. 分享文件不含敏感信息：供应商 API Key、本地路径、令牌一律脱敏（替换为 `[REDACTED]`）。
  5. 分享文件尾部附「由 WorkBuddy For Me v0.4.0 生成」水印 + 版本号。
- **技术要点**：
  - `packages/core/src/share/export-conversation.ts`——从 DB 拉取完整会话消息（含
    contentParts、tool_trace、citations），按格式序列化。
  - HTML 模板：`apps/web/src/lib/share/html-template.ts`——内联 CSS（从 tailwind 编译
    提取子集），图片从 `attachments/` 读取转 data URL。
  - Markdown 序列化：`apps/web/src/lib/share/markdown-serializer.ts`。
  - API：`GET /api/conversations/:id/export?format=html|markdown`（返回文件流）。
- **工作量**：2 天

#### P0-3 桌面端自动更新

- **用户故事**：发布了 v0.4.1 修复补丁，已安装用户在下次启动时自动收到更新提示。
- **验收标准**：
  1. `electron-updater` 集成：桌面端启动后异步检查 GitHub Releases（`autoUpdater`），
    检测到新版本→下载→下载完成弹窗提示「重启以完成更新」。
  2. 设置页新增「关于」区块：当前版本号、检查更新按钮、上次检查时间、更新通道
    （`stable` / `beta`，默认 stable）。
  3. 更新失败不阻塞使用：下载失败提示「更新下载失败，可手动下载」并附 release 页链接。
  4. 开发态不触发自动更新（`app.isPackaged` 门控）。
  5. GitHub Releases 的 `latest.yml` 由 `electron-builder` 自动生成，CI 发布时上传。
- **技术要点**：
  - `apps/desktop/src/main/updater.ts`——封装 `electron-updater`：`autoUpdater` 配置
    （`provider: 'github'`、`repo: 'flashJJ/workBuddyForMe'`）、事件转发
    （`checking-for-update` / `update-available` / `download-progress` / `update-downloaded`）。
  - 更新通道：通过 `allowPrerelease` 控制 beta 通道。
  - 前端通知：IPC `updater:status` / `updater:progress` / `updater:downloaded` →
    渲染进程弹窗。
  - 打包配置：`electron-builder.yml` 加 `publish: github`。
- **工作量**：2 天

### P1 —— 争取做

#### P1-1 图片型 PDF OCR

- **用户故事**：我上传一份扫描版合同 PDF，文字层是空的，但模型能 OCR 出内容并回答问题。
- **验收标准**：
  1. `read-document.ts` 的 PDF 路径：先取文字层文本；若提取结果为空或字符数 < 阈值
    （如 50 字符/页），判定为图片型 PDF，触发 OCR 路径。
  2. OCR 策略优先级：①若已配置视觉模型（如 qwen2.5-vl），逐页渲染为图片发视觉模型
    识别；②无视觉模型时用 `tesseract.js`（WASM）离线 OCR，支持中英文（chi_sim+eng）。
  3. OCR 结果与文字层结果格式一致（纯文本），后续分片/嵌入流程不变。
  4. 处理时间较长（10 页 PDF 可能 30s-2min），UI 显示「OCR 识别中…」进度。
  5. OCR 失败时文档状态为 `failed`，error_message 给出可读指引
    （「扫描件 OCR 失败，请尝试配置视觉模型或使用文字版 PDF」）。
- **技术要点**：
  - 视觉模型 OCR：`packages/core/src/ingestion/pdf-vision-ocr.ts`——用 `pdfjs` 的
    `page.render()` 渲染到 canvas → 转 data URL → 调 `ChatProvider.chatCompletion`
    发视觉模型识别。
  - tesseract.js 兜底：`packages/core/src/ingestion/tesseract-ocr.ts`——WASM worker
    初始化，语言包从本地加载（打包进 `resources/` 或首次使用时下载到 cache）。
  - `@napi-rs/canvas` 依赖：需在 `apps/desktop/scripts/prepare-server.mjs` 归集
    win32-x64 二进制 + asarUnpack。
  - 超时保护：单页 OCR 超 30s 跳过，全文超 5min 整体标记 partial。
- **工作量**：3 天

#### P1-2 全局快捷键与命令面板

- **用户故事**：我按 Ctrl+K 直接弹出命令面板，输入「新建会话」「搜索知识库」「切助手」
  快速跳转，不用点菜单。
- **验收标准**：
  1. 全局快捷键：Ctrl+K 打开命令面板（Electron 全局快捷键 + Web 端 keydown 监听）。
  2. 命令面板（Radix Dialog 风格）：模糊搜索命令列表，方向键导航，回车执行。
  3. 内置命令：新建会话、切换助手、搜索会话（标题模糊匹配）、搜索知识库、打开设置、
    检查更新、导出当前会话。
  4. ESC 关闭、Ctrl+K 切换。
- **技术要点**：
  - 命令注册：`packages/shared/src/types/command.ts`——`CommandRegistry` 接口；
    `apps/web/src/features/command-palette/` 组件。
  - Electron 全局快捷键：`globalShortcut.register('CommandOrControl+K', ...)`，
    窗口未聚焦时唤起。
- **工作量**：1.5 天

### P2 —— 留白（登记不承诺）

- 备份加密（当前明文 zip，单用户威胁模型下暂不加密）
- 备份增量（只导出变更部分）
- 对话分享为 PDF 格式
- 自动更新 delta 下载（全量替换，小应用体量可接受）
- OCR 结果的置信度标注与人工校正界面
- 多会话批量分享

## 4. 架构影响

### 改动包与方向（依赖方向保持无环）

```text
packages/core      新增 backup/（export/restore）+ share/（export-conversation）
                    + ingestion/pdf-vision-ocr.ts + tesseract-ocr.ts
packages/shared    新增 backup schema（manifest.json Zod schema）+ command schema
packages/database  migration v4：documents 加 ocr_status / ocr_engine 列
apps/web           备份面板、分享导出 API、命令面板组件
apps/desktop       updater.ts（electron-updater）+ globalShortcut + 打包配置
```

### 数据迁移（PRAGMA user_version 3 → 4）

```sql
ALTER TABLE documents ADD COLUMN ocr_status TEXT;    -- null | 'pending' | 'done' | 'failed' | 'skipped'
ALTER TABLE documents ADD COLUMN ocr_engine TEXT;    -- 'vision' | 'tesseract' | null
```

- 已存在的 documents 行 `ocr_status` 为 null，表示「非 OCR 来源」，不影响原有逻辑。
- 备份/恢复不涉及 schema 迁移——备份格式是独立的 JSON 归档，恢复时按目标库当前
  schema 写入。

### API 新增

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/backup/export` | 触发导出（SSE 进度）→ 返回下载 URL |
| POST | `/api/backup/restore` | 上传归档、预检查、恢复（SSE 进度） |
| GET | `/api/conversations/:id/export` | 导出会话（`?format=html\|markdown`） |
| POST | `/api/documents/:id/ocr` | 手动触发 OCR（管理操作） |

### 打包配置变更

- `electron-builder.yml`：加 `publish: github`；`extraResources` 加 `tesseract/`
  （语言包 + WASM）和 `canvas/`（@napi-rs/canvas 二进制）。
- `scripts/prepare-server.mjs`：归集 @napi-rs/canvas 的 win32-x64 .node 文件 +
  asarUnpack 配置。

## 6. 风险与取舍

### 风险

1. **备份恢复的跨版本兼容**：备份归档的 schema 版本与目标库不一致时如何处理？
   —方案：manifest 里记 `backup_schema_version`，恢复时做版本探测：相同版本直接写入；
   不同版本走迁移适配器链（`backup-migrations/`），不支持则提示「备份版本不兼容」。
   —v0.4 只需支持 v0.3/v0.4 互转，后续版本按需追加适配器。

2. **OCR 性能与体量**：10 页扫描 PDF 用 tesseract.js 可能耗时 1-2 分钟。
   —方案：异步处理 + SSE 进度 + 超时保护（5min 上限）；大文档（>50 页）提示
   「建议拆分后上传」。
   —取舍：不做分布式/并发 OCR，单机单进程足够（本机单用户威胁模型）。

3. **自动更新的签名问题**：v0.4 仍无代码签名证书（留给 v1.0），Windows SmartScreen
   会拦截未签名 exe。
   —方案：沿用 v0.3 的 Smart App Control 降级策略；自动更新本身不受影响
   （electron-updater 下载替换不触发 SmartScreen，仅首次安装时触发）。
   —取舍：beta 通道面向开发者/早期用户，正式推荐安装仍等 v1.0 签名后。

4. **@napi-rs/canvas 原生二进制归集**：与 better-sqlite3 类似，需在打包时正确归集。
   —方案：在 `prepare-server.mjs` 中追加 canvas 的 .node 文件归集逻辑，
   asarUnpack 标记原生模块。
   —验证：打包后冒烟测试 `pdf.render()` 不报错。

### 取舍

- **备份格式选 zip 不选自定义二进制**：zip 有标准库支持、可被任意解压工具检查、
  牺牲一点压缩率换取可调试性。
- **对话分享不做成在线链接**：单用户本地优先，不引入云存储/托管服务；
  导出文件即最终产物，用户自行选择分享渠道。
- **OCR 视觉模型优先而非 tesseract 优先**：视觉模型质量通常更好且已有 v0.3 基础设施；
  tesseract.js 仅作为无视觉模型时的兜底。
- **命令面板不做插件体系**：内置命令够用，不做第三方扩展机制（留给生态成熟后）。

## 7. Non-Goals（本版本明确不做）

1. **云端备份/同步**：不引入任何云存储服务；备份是本地文件，同步由用户自行解决
  （网盘/U盘/Git）。
2. **多用户/团队共享**：不做权限管理、不做协作；单用户本地优先不动摇。
3. **备份加密**：单用户威胁模型下，物理安全即足够；加密留给有明确需求的用户反馈后做。
4. **增量备份**：全量备份简单可靠；增量引入复杂度（差量/版本链/垃圾回收）不值得。
5. **在线对话分享**：不做 `share.workbuddy.com/abc123` 式在线链接；导出文件即终点。
6. **OCR 人工校正界面**：OCR 结果直接入库，不做逐页校正 UI（留给专业文档管理场景）。
7. **多语言 OCR**：仅支持中英文（chi_sim+eng）；其他语言包用户可自行放入 cache 目录。
8. **自动更新的灰度发布**：不做分批灰度；全量推送（小体量应用不值得）。
