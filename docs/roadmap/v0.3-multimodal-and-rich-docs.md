# v0.3 迭代方案：什么都能读

- **版本号**：v0.3.0
- **主题**：什么都能读（多模态视觉对话 + Office 文档 + 网页剪藏）
- **状态**：方案已定，待评审
- **预估工作量**：约 12-14 人天（一个人全职）

---

## 1. 版本主题与目标

v0.2 的助手长出了「手」（工具调用、本地 Ollama），但它仍然**只认字**：

1. 聊天不能发图——截图、报表、手写笔记发了也白带；
2. 知识库只收 txt/md/pdf——日常流转最多的 docx/xlsx/pptx 进不来；
3. 看到好文章只能让助手临时抓一下——URL 不能沉淀进知识库，下次还得重贴。

v0.3 要打通「读」的三条主通道，外加一个兜底：

1. **会看图**：聊天支持粘贴/拖拽/选择图片，视觉模型流式作答，历史可回看。
2. **什么文档都能收**：docx/xlsx/pptx 解析为带结构文本，走现有 RAG 管线入库。
3. **网页可剪藏**：URL → 正文抽取 → 作为文档入知识库，引用带来源链接。
4. **扫描件兜底（P1）**：图片型 PDF 用本地视觉模型 OCR，无视觉模型时 tesseract.js 离线兜底。

**成功指标**：

- 粘贴截图 + 一句话提问，本地视觉模型（如 Ollama qwen2.5-vl）或云端视觉模型完成流式作答；刷新会话后图片与问答完整复现。
- 一份真实 docx（含表格）、xlsx（多 sheet）、pptx 上传后状态为 indexed，提问命中其内容并产生引用角标。
- 贴一个公开文章 URL 剪藏，30 秒内可在知识库检索到正文要点，引用条目可点开原文。
- 未配置视觉模型时选图发送被**友好拦截**（禁用 + 引导文案），不出现未捕获报错。

## 2. 现状与痛点

| 现状（v0.2） | 痛点 |
|---|---|
| `ChatMessage.content` 仅 `string \| null`，[payloads.ts] 直接透传字符串 | 没有 content parts 通道，发不了图；视觉协议是 v0.2 明确的 Non-Goal |
| `MODEL_CAPABILITIES = ['chat','embedding']` | 无法声明/识别视觉模型，UI 无从门控 |
| [read-document.ts] 白名单仅 txt/md/markdown/pdf，pdfjs 只取文本层 | Office 文档 422；扫描版 PDF 抽出空文本直接失败 |
| [fetch-webpage-tool.ts] 正则剥标签 + 8k 字符截断，仅服务于工具上下文 | 无标题/正文结构概念，不能作为文档沉淀；正则抽取对现代页面噪声大 |
| documents 表只有上传文件语义（filename/hash） | 网页剪藏没有 source/URL 立足之地 |
| 消息只有文本、composer 只有 textarea | 截图问答、图表解读类高频场景无解 |
| `files/` 子目录存上传原文 | 聊天附件没有存储位与读取 API |

## 3. 功能清单

### P0 —— 必做（构成版本主题闭环）

#### P0-1 视觉对话全链路（图片输入）

- **用户故事**：我截一张报错弹窗的图直接粘贴到输入框，配一句「这怎么办」，模型看图回答；一周后翻到这条会话，图还在。
- **验收标准**：
  1. 模型能力新增 `vision`；模型管理可勾选，助手使用的模型（绑定模型或默认 chat 模型）无 vision 能力时，图片按钮禁用并提示「当前模型不支持图片，请在设置中配置视觉模型」。
  2. composer 支持**粘贴截图、拖拽图片、点击选择**三种方式；可多图（单条消息 ≤4 张）、可删除待发缩略图；支持 png/jpeg/webp，单张 ≤10MB。
  3. 图片经 `POST /api/attachments`（multipart）落盘到数据根 `attachments/`，返回附件 ID 与预览地址；**附件原文不入库、不进 SSE**，DB 只存元数据。
  4. 发送前在浏览器侧 canvas 压缩（最长边 ≤1600px、JPEG 0.85），控制视觉 token；消息体携带有序附件 ID，允许「纯图片」消息。
  5. 编排器组装标准 OpenAI vision content parts（`text` + `image_url`（data URL））下发；Ollama 协议经实测确认 `/v1` 兼容层行为，不兼容则在 ollama 适配器内做 `image_url → images` 本地转换。
  6. 用户气泡渲染缩略图，点击弹大图（复用 Dialog 做 lightbox）；历史消息从 `content_parts` 还原，纯文本老消息零感知。
  7. 重新生成携带相同图片；停止按钮中断语义不变；工具循环轮次中图片只出现在首轮（控制 token）。
- **技术要点**：
  - `MODEL_CAPABILITIES` 追加 `'vision'`；shared 新增 `ContentPart` 联合类型（text/image）。
  - migration v3：新建 `attachments` 表；messages 加 `content_parts TEXT DEFAULT '[]'`（空数组 = 纯文本，读老消息回落 content）。
  - 能力门控前后端双保险：UI 禁用 + 服务端按解析出的模型 capability 返回 422 友好错误。
- **工作量**：4 天

#### P0-2 Office 文档解析（docx / xlsx / pptx）

- **用户故事**：我把会议纪要 docx、报价单 xlsx、方案 pptx 拖进知识库，处理成功后直接能问「报价单里 A 方案总价多少」。
- **验收标准**：
  1. `detectKind`/上传白名单扩展 `.docx .xlsx .pptx`；解析全部在本机完成，零网络依赖、零原生编译依赖（Electron 打包友好）。
  2. **docx**（mammoth 提取文本）：保留段落与表格文本，表格按行输出；**xlsx**（SheetJS）：每个 sheet 一节（`## Sheet 名`），单元格按行拼接，空行过滤；**pptx**（fflate 解 OOXML zip，抽 `ppt/slides/slide*.xml` 文本节点）：每页一节（`## 第 N 页`）。
  3. 输出为 Markdown 风格纯文本后进入**现有摄入管线**（分片/嵌入/向量落库不变）；解析失败错误可读：加密文档、老式 `.doc/.xls/.ppt` 二进制提示「请另存为新版 .docx/.xlsx/.pptx」。
  4. 单文件沿用 20MB multipart 上限；文档列表显示类型标签；重复内容 hash 去重不变。
- **技术要点**：
  - 新增依赖均为纯 JS：`mammoth`（docx）、`xlsx`（SheetJS，**从官方分发源固定 0.20+ 版本**，npm 主通道版本陈旧）、`fflate`（pptx 解包）。
  - 解析器收敛在 `read-document` 同一入口，按 kind 分发，禁止上传链路另起炉灶。
- **工作量**：2.5 天

#### P0-3 网页剪藏入库

- **用户故事**：我在知识库页贴一个博客 URL，标题和正文自动抽出来入库；之后提问命中它时，引用角标能直接点开原文。
- **验收标准**：
  1. 知识库页新增「从网页导入」：输入 URL → `POST /api/knowledge-bases/[id]/clip`，后台抓取+抽取+摄入，轮询状态复用现有文档 processing→indexed/failed。
  2. 正文抽取使用 `@mozilla/readability` + `linkedom`（轻量 DOM，不引 jsdom），产出标题、正文（Markdown 化纯文本）、来源 URL；抓取安全标准与 `fetch_webpage` 完全同级：SSRF IP 段校验、3 跳重定向逐跳复检、8s 超时、200KB 上限、仅 html/plain。
  3. documents 表新增来源语义：`source ('upload'|'webpage')`、`source_url`；剪藏文档在列表带网页标识，文件名取页面标题（兜底域名+路径），引用角标悬停显示 URL、点击新开原文。
  4. URL 规范化去重（去 `utm_*`/fragment 后与正文双重 hash）；同一 URL 不重复入库。
  5. SSRF 护栏单测全覆盖（与工具共用 `ssrf-guard`，禁止复制一份）。
- **技术要点**：
  - 抽取公共抓取模块 `ingestion/fetch-article.ts`，工具与剪藏共用 SSRF/重定向/有界读取；`fetch_webpage` 是否切换为 Readability 抽取器列为 P1 搭车项（避免本期改变工具行为基线）。
  - 剪藏正文以「标题 + URL + 正文」组成临时 buffer，复用 `ingestion-pipeline`，不新增第二套摄入逻辑。
- **工作量**：2.5 天

### P1 —— 争取做（超期顺延，不留半成品）

#### P1-1 图片型 PDF 的 OCR 兜底

- 触发条件：pdfjs 文本层提取后平均字符密度低于阈值（建议 <20 字符/页）判定为扫描件，避免对文字版 PDF 无谓 OCR。
- **主路线（视觉模型）**：`@napi-rs/canvas`（N-API 预编译，无需 node-gyp）把页面渲染为 120 DPI PNG，逐页喂当前可用的视觉模型，提示词要求逐字转录并保留标题/列表/表格结构；页数上限 20 页，超限报错提示拆分。
- **兜底（tesseract.js）**：未配置视觉模型时走 WASM 本地识别（chi_sim+eng），训练语言包首次使用时下载并在 UI 明示「需一次性下载语言数据」；识别质量差异在结果中标注。
- **打包注意**：`@napi-rs/canvas` 的 win32-x64 二进制需在 [prepare-server.mjs] 归集并 asarUnpack，沿用 v0.1 ABI 教训先做桌面 pack 冒烟。
- **工作量**：3 天；M4 窗口不足则整体顺延 v0.4，不允许只合入一半。

#### P1-2 fetch_webpage 正文质量升级

工具侧切换到 Readability 抽取（与剪藏共用模块），回归现有工具集成测试；**工作量**：0.5 天。

### P2 —— 留白（登记不承诺）

- 知识库里的「以图搜图」/图片多模态嵌入（embedding 仍仅文本，文档内嵌图片不抽取）
- 剪藏页面的完整快照（HTML/截图存档）、订阅与自动更新
- 视觉模型输出图片（文生图）

## 4. 架构影响

### 改动包与方向（依赖方向保持无环）

```text
packages/shared  常量加 'vision' 能力；ContentPart 类型；chat schema 增 attachments；
                 文档 source/sourceUrl schema；ALLOWED_DOC_EXTENSIONS 扩展
packages/ai      ChatMessage.content 升级为 string | ContentPart[]；openai payloads 组装
                 vision wire（image_url data URL）；ollama 视觉兼容性转换（按需）
packages/core    新增 attachments 服务（落盘/读取/校验）、office 解析器、
                 ingestion/fetch-article 公共抓取、clip 剪藏服务；
                 chat-orchestrator 多模态消息组装（vision 能力门控、图片仅首轮）
packages/database migration v3：attachments 表、messages.content_parts、
                 documents.source/source_url；仓储与 mapper 贯通
packages/config  DATA_SUBDIRS 增 attachments: 'attachments'
apps/web         /api/attachments（上传/读取）、/api/knowledge-bases/[id]/clip；
                 composer 图片交互、缩略图/lightbox、消息气泡图片渲染；
                 知识库「网页导入」弹窗与文档类型标识；模型管理 vision 勾选；
                 上传 accept 扩展
apps/desktop     P0 无主进程改动；P1-1 落地时 prepare-server 归集 canvas 二进制
```

### 数据迁移（读兼容、写收敛，PRAGMA user_version 2 → 3）

```sql
CREATE TABLE IF NOT EXISTS attachments (
  id TEXT PRIMARY KEY,
  filename TEXT NOT NULL,
  mime_type TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  storage_path TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  created_at TEXT NOT NULL
);
ALTER TABLE messages  ADD COLUMN content_parts TEXT NOT NULL DEFAULT '[]';
ALTER TABLE documents ADD COLUMN source TEXT NOT NULL DEFAULT 'upload';
ALTER TABLE documents ADD COLUMN source_url TEXT;
```

- 老消息：`content_parts = '[]'` 时完全按 v0.2 纯文本渲染与组装，不做数据回填。
- 老文档：source 默认 upload；附件与消息为松耦合（附件可独立存在，删除消息不强制删文件，本期不做 GC，P2 登记）。
- 附件文件命名 `attachments/<id>.<ext>`，sha256 去重；存储威胁模型与现有 `files/` 一致（明文落盘、本机单用户）。

### 接口与 SSE 变更（追加，不破坏 v0.2）

| 接口 | 变更 |
|---|---|
| `POST /api/attachments` | 新增：multipart 图片上传，返回 `{id, filename, mimeType, url}` |
| `GET /api/attachments/[id]` | 新增：按 id 回流图片（仅监听 127.0.0.1，沿用现有本地服务模型） |
| `POST /api/chat/stream` | body 增 `attachments?: string[]`（有序 ID，≤4）；content 允许为空（有附件时） |
| `POST /api/knowledge-bases/[id]/clip` | 新增：`{url}` → 登记网页文档并后台摄入 |
| SSE | 无新事件；图片不进 delta/done 文本，前端凭 content_parts 渲染 |

## 6. 风险与取舍

| 风险 | 应对 |
|---|---|
| 各家视觉协议差异（Ollama `/v1` 对 image_url 支持随版本变化） | M1 第一件事用本机 qwen2.5-vl 实测；适配器内置 `image_url→images` 转换预案；无 vision 能力模型一律不下发图片 |
| 图片把 token/显存打爆 | 浏览器侧压缩（1600px/JPEG 0.85）、单消息 ≤4 张、10MB 上限、图片仅工具循环首轮携带 |
| 多模态契约动到核心消息模型，波及工具循环/重生成/历史 | content_parts 与 content 双轨：parts 为空即纯文本；编排器集中一处组装 wire；老消息零回填；工具消息（role:tool）永远纯文本 |
| SheetJS 社区版供应链陈旧 | 固定官方分发源 0.20+ 版本并锁 lockfile；pptx 用 fflate 自解 XML，不引入重型 Office 库 |
| 视觉模型 OCR 慢且烧 token，tesseract 中文质量一般 | 双重触发门槛（仅扫描件）+20 页上限；UI 标注 OCR 来源与质量；两条路都失败才置 failed |
| `@napi-rs/canvas` 重蹈 ABI/打包坑 | 仅 P1 引入；prepare-server 显式归集 win32-x64 预编译包 + asarUnpack；合入前先跑桌面 pack 冒烟（v0.1 教训） |
| 剪藏遇到需登录/JS 渲染页面，正文为空 | Readability 抽取为空即置 failed 并提示「无法抽取公开正文」；不引入无头浏览器（Non-Goal） |
| 附件明文落盘的隐私顾虑 | 与 v0.1 上传文档同一威胁模型，文档明示；加密存储列入 v0.4 备份/安全议题 |

**取舍声明**：本期所有新能力依旧**只读、本机、无副作用**；视觉只做「看图」不做「生图」；
Office 只支持 OOXML 新格式，不碰老式二进制格式。

## 7. Non-Goals（本版本明确不做）

- ❌ 文生图 / 图片编辑 / 图片在知识库中的多模态检索
- ❌ 音频与视频（语音输入、TTS、会议转写）
- ❌ 云端商业 OCR API；需登录或 JS 渲染页面的剪藏（无头浏览器）
- ❌ `.doc/.xls/.ppt` 老式二进制 Office 格式、PDF 中的内嵌图片抽取入库
- ❌ 剪藏网页的 HTML/截图完整快照、订阅式自动更新
- ❌ v0.2 顺延的 `search_web` 联网搜索工具（继续顺延，不搭车）
- ❌ MCP / 自定义工具与插件（维持 v0.2 决策，插件化大版本统一设计）
- ❌ 桌面自动更新、安装器签名 → v0.4 / v1.0
