# v0.8 迭代方案：Flow Studio — 看得见、连得出、可复用的可视化工作流

> 状态：✅ v0.8.0 已完成（分支 feature/v0.8-flow-studio；基线 v0.7.0，main commit d7f0efd）
> 详细设计：见 [docs/plan/](../plan/README.md)（现状差距 / 功能设计 / 技术架构 / 实施风险 五篇）

## 1. 版本主题与目标

**一句话价值主张**：从「每轮靠模型临场决定调什么工具」到「把检索、判断、生成、工具、人工审核画成一张确定的流程图」——v0.8 交付可视化工作流编排器 Flow Studio，流程可调试、可复现，并能作为工具回到普通对话中被助手调用。

产品形态借鉴 [Langflow](https://github.com/langflow-ai/langflow)（v1.12.4 源码级对照见 [01-现状与差距分析](../plan/01-现状与差距分析.md)），但**不移植其 Python 代码**，全部在本项目 TypeScript / Next.js / Electron / SQLite 资产上实现，坚持本地优先。

**版本范围声明**：v0.8 只做完整方案的 **P0（编排 + 执行 + 调试 + 对话复用）**。发布为 HTTP API / MCP Server 登记 **v0.9**，定时/事件自动化登记 **v0.10**。

**成功指标**：

- 内置 3 个 starter flow，用户能在画布上从零搭出「资料研究助手」（检索→条件分支→生成→人工审核→输出）并一次跑通
- 相同输入多次运行，执行路径一致（确定性 DAG，分支由声明式规则决定而非模型）
- 每次试运行可逐节点查看 状态 / 输入 / 输出 / 耗时，人工节点可挂起后继续
- 已发布流程以 `flow:<id>` 工具出现在普通对话中，助手可调用并把结果回灌，**不改动 assistants 表与聊天主循环**
- 全部门禁不降级：`pnpm check`（typecheck/lint/行数）+ 新增单测全绿；v011→v012 迁移在现有库升级成功；普通对话 / 知识库 / 桌面任务回归无影响
- 版本号 0.7.0 → 0.8.0，发布 tag v0.8.0

## 2. 现状与痛点

| # | 痛点 | 现状证据 |
|---|------|---------|
| 1 | **执行路径不可控**：对话编排是纯线性的「模型轮 ↔ 工具轮」循环，最多 5 轮；调什么工具、什么顺序全由模型临场决定，不可复现、不可预设 | `packages/core/src/chat/chat-orchestrator.ts`；`MAX_TOOL_ROUNDS=5`（`shared/src/constants.ts`） |
| 2 | **能力不可组合复用**：13 个内置工具 + MCP 工具只能按助手白名单开关，无法串联成固定步骤；MCP 仅 client，能力无法对外 | `core/src/tools/tool-runtime.ts`、`core/src/mcp/`（无 server） |
| 3 | **技能表达力弱**：skills 只是「prompt 模板 + 工具白名单」的声明式文件夹，没有步骤、分支、数据在节点间流动 | `core/src/skills/`、`shared/src/schemas/skill.ts` |
| 4 | **前端零画布基础**：全仓无 reactflow/@xyflow 等节点/拖拽依赖，无 DAG 编辑与可视化调试 UI | `apps/web/package.json` grep 零匹配 |

**关键判断（地基已具备，不必造轮子）**：

- 模型调用（`packages/ai` ChatProvider，支持 function-calling）、工具安全运行时（HITL 门控 / 熔断器 / 15s 超时 / SSRF 防护）、知识库 RAG 内核（解析→分片→嵌入→sqlite-vec→top-k）、SSE 事件管道、LangSmith tracer 全部是生产级现成资产；
- 数据层有成熟的 `PRAGMA user_version` 顺序迁移（当前 v011）与 16 个手写 Repository，新增工作流表照此模式做加法即可；
- v0.7 的 task-loop 已验证「SSE 驱动的长任务 + pause/resume/stop + 逐步落库」模式，人工节点与试运行可直接沿用其挂起/恢复范式。

v0.7 方案中「多智能体编排（仍归 v0.8）」的登记项，由本版本以「确定性 DAG 编排」承接；v0.7 登记的 playwright-mcp 接入、UI-TARS grounding 模型**不属于 v0.8 主线**（浏览器 MCP 未来可作为工具节点被流程直接使用，无需为此延期本版本）。

## 3. 功能清单

> 每个节点/执行能力都映射到现有内核，v0.8 不新造 AI 与工具能力，只做「编排与接线」。

### P0-1 工作流数据模型与版本化

- **用户故事**：我画的流程图能保存、能再次打开编辑、能发布一个固定版本，之后改草稿不影响已发布版本。
- **验收标准**：
  - 新增 4 张表（顺序迁移 **v012**，只做加法）：`workflows` / `workflow_versions` / `workflow_runs` / `node_executions`
  - 图结构（节点/边/位置/视口）序列化为 `graph_json` 存版本表；每次保存生成递增版本；发布固定版本并置 `status=published`
  - 提供两个 Repository（`workflow-repo`、`workflow-run-repo`），一次节点完成的状态更新在同一 better-sqlite3 事务内
- **技术要点**：表结构与字段见 [03-技术架构设计 · 第四节](../plan/03-技术架构设计.md)；图契约用共享 zod schema（`shared/src/schemas/flow.ts`），前后端共用
- **工作量**：S（2 人日）

### P0-2 DAG 编译与执行引擎（core/flow）

- **用户故事**：点运行后，引擎按连线关系自动排序执行；条件不满足的分支自动跳过；某节点失败时整单停在失败点并告诉我原因。
- **验收标准**：
  - 编译器：DFS 环检测、唯一 start/end、孤立节点、非法句柄、节点可达 end 校验；Kahn 拓扑排序生成执行计划；诊断带 nodeId/edgeId 供 UI 定位
  - 执行器：AsyncGenerator 产出 `run_*` / `node_*` SSE 事件；就绪队列推进（v0.8 **顺序执行**）；condition 未命中分支标记 `skipped`；支持 AbortSignal 取消
  - 运行期输出作用域 + 模板引用解析：`{{$nodes.<id>.outputs.<path>}}` 与整字段绑定 `{ "$ref": ... }`；引用合法性在编译期检查
  - 单测覆盖：正常链、条件真假两路、跳过、节点失败、取消、引用解析
- **技术要点**：算法伪代码与模块划分（compiler/refs/engine/run-store）见 [03 · 第三节](../plan/03-技术架构设计.md)
- **工作量**：L（5 人日）

### P0-3 七类节点处理器

- **用户故事**：我能用开始（填参数）、知识检索、大模型、工具、条件判断、人工确认、结束这几种积木拼出真实业务流程。
- **验收标准**：

  | 节点 | 能力 | 复用内核 |
  |---|---|---|
  | `start` | 定义流程入参（名/类型/必填/默认） | 无 |
  | `knowledgeSearch` | 选知识库 + query 模板 + topK，输出 chunks 与拼好的 context | `retrieval-service`（sqlite-vec） |
  | `llm` | 选模型（可跟随默认）+ system/user 模板 + 采样参数，可选绑库做 RAG | `provider.chatStream`、RAG context 拼装 |
  | `tool` | 选内置/MCP 工具 + 参数表单（按工具 JSON Schema 渲染） | `tool-runtime.resolveTool` → 门控/熔断/超时 → `Tool.run` |
  | `condition` | 声明式规则（`==/contains/>/isEmpty…`，all/any 组合），输出 true/false 两分支，**不调用模型** | 纯本地求值 |
  | `human` | 挂起等待审核/填表，输出 `{approved, values}`；v0.8 进程内挂起（SSE 生命周期内） | pending-confirmations 同构句柄 |
  | `end` | 输出映射，决定 Run 最终结果（可多个） | 无 |

- **技术要点**：统一 `FlowNodeHandler` 接口 + 容器注入 provider/retrieve/resolveTool/门控（与 chat-orchestrator 的 deps 模式一致），见 [03 · 3.3](../plan/03-技术架构设计.md)
- **工作量**：M（4 人日）

### P0-4 画布编辑器与校验（/flows）

- **用户故事**：我在 `/flows` 新建流程，从左侧拖节点到画布、连线、在右侧配参数；保存前自动校验并把错误定位到具体节点。
- **验收标准**：
  - 新增依赖 `@xyflow/react@^12`（与 Langflow 同主版本）；**不引入 zustand**，画布态用 React Flow 原生 + useReducer（撤销/重做），服务端态继续用 React Query
  - 页面：`/flows` 列表（状态、最近运行、发布开关）、`/flows/[id]` 编辑器；左侧节点面板 / 中间画布 / 右侧配置抽屉；导航栏在「任务」与「知识库」间加入「流程」
  - 配置表单按节点 config zod schema 生成；引用字段提供「插入变量」选择器（只列拓扑上可引用的祖先节点输出）
  - 校验错误在画布节点/边上红框定位
- **技术要点**：模块结构 `features/flow-editor/`（flow-canvas/nodes/node-panel/config-drawer），视觉沿用现有 Tailwind + Radix 风格
- **工作量**：L（5 人日）

### P0-5 试运行与逐节点调试

- **用户故事**：我点「试运行」填入开始参数，底部面板实时显示每个节点的状态与输入输出；走到人工节点时我直接在面板里通过或驳回，流程继续。
- **验收标准**：
  - 底部运行抽屉：节点状态徽标（等待/运行中/成功/失败/跳过/待人工）、输入、输出、耗时、错误；可重跑（复用上一次输入）
  - 人工节点内联审核表单；提交后从挂起点继续
  - SSE 订阅驱动（`GET /api/flows/runs/[id]/events`），v0.8 执行生命周期与订阅连接一致（同 v0.7 tasks 模式）
  - 工具节点为 danger 级时，试运行中弹出与聊天一致的 HITL 确认
- **工作量**：M（3 人日）

### P0-6 发布并回到对话（flow 工具）

- **用户故事**：流程调好后我点发布，之后在普通对话里说「按我的周报流程整理本周工作」，助手自动调用该流程并把结果答给我。
- **验收标准**：
  - 发布后生成工具 `flow:<workflowId>`：description 取流程描述，parameters 由 start 入参 schema 生成
  - `tool-runtime.resolveTool` 增加第三个来源 `builtin → mcp → flow`；助手白名单、权限表、熔断结构不变
  - 对话中调用时，节点级事件映射为现有 tool trace 子步骤，在 `tool-trace` 卡片中展示
  - **安全约束**：对话/试运行（有人在场）danger 工具节点走 HITL；为 v0.9 无人值守触发器预埋「默认拒绝 danger + 发布时显式授权」策略位
- **工作量**：M（3 人日）

### P0-7 Starter flows 与收尾

- **用户故事**：第一次打开就有可参考的示例，而不是空白画布。
- **验收标准**：
  - 内置 3 个模板（首次启动播种，模式参考 builtin skills）：①资料研究助手（检索+条件+生成+人工）②周报流水线（生成+人工，演示对话调用）③网页摘要器（`fetch_webpage` danger 门控 + 生成）
  - 版本号 0.7.0 → 0.8.0；README/路线图收尾；全量门禁；tag v0.8.0
- **工作量**：S（2 人日）

**v0.8 总工作量参考：约 24 人日**（M0–M3，单人全职口径，含联调与缓冲）。

## 6. 风险与取舍

| 风险 | 应对 |
|---|---|
| 引擎范围膨胀（想一次做并发/循环/嵌套子流程） | v0.8 硬性限定：DAG 无环、顺序就绪、7 类节点；同层并发（v0.9）、subflow/http 节点（v0.9+）明确推迟 |
| LLM 结构化输出不可靠（现状靠正则抽 JSON） | v0.8 分支判断不依赖模型——condition 是声明式规则节点；json_schema 结构化输出随 v0.9 服务化在 ai 层做「协议优先 + 容错降级」 |
| 长运行与 SSE 连接绑定，无法无人值守 | v0.8 接受与 v0.7 tasks 相同的连接内生命周期；但 run/node_executions 先行落库，v0.9 再做「落库 queued + 独立 runner」解耦，保证现在不挡未来 |
| 流程放大工具权限（danger 被绕过 HITL） | 工具节点强制走既有门控/熔断/超时；v0.8 所有触发器均有人在场；node_executions 全程留痕可审计；v0.9 无人值守默认拒绝 danger |
| React Flow 引入成本（新依赖、样式统一） | 只用官方基础能力（自定义节点/句柄/Minimap/Controls）；Langflow 已验证 v12 可行性；视觉沿用 Tailwind/Radix，不引入 zustand |
| 与 v0.7 task-loop 概念混淆 | 命名与文档严格区分：Flow=确定性 DAG（你画它跑），Task=桌面自主环（模型决策）；两套表不合并，未来 `agentTask` 节点作为单向延伸而非现在耦合 |
| 桌面/网页双态差异 | 编排核心全部在平台无关的 core；Electron 特有托管/调度只出现在 v0.9/v0.10 |

## 7. Non-Goals（本版本明确不做）

- ❌ 流程发布为 HTTP API / MCP Server（**v0.9**）
- ❌ 跨进程运行恢复、失败节点单点重跑（**v0.9**，随服务化一起做）
- ❌ 节点同层并发执行、subflow 嵌套、任意 HTTP 节点（**v0.9+**）
- ❌ 定时 / 事件触发的自动化（**v0.10**，仅 Electron 常驻端承诺）
- ❌ 让用户在节点里执行自定义 JS/Python 代码（安全红线，长期不做）
- ❌ 多人协作、云端同步、流程市场
- ❌ playwright-mcp 接入、UI-TARS 等 grounding 模型（沿用 v0.7 登记结论，不进本版本）
- ❌ 替换或改造现有聊天、桌面任务、skills 体系（并存关系）
