# 候选 01：备份可续——增量归档与链式恢复

> 来源：v2.33 §9 下一版本候选、v1.5 备份边界、v2.33 交付复盘。
> 状态：已排期 v2.34，正式方案见 [v2.34 方案](../../plan/v2.34/README.md)。
> 前序：[v2.33 方案](../../plan/v2.33/README.md)。

## 1. 问题

v2.33 让备份「可托付」，但还没做到「可持续」：

- **重复全量**：每次导出都打包全部消息与附件二进制，备份频率越高、数据越大，耗时与体积线性增长。
- **基线静默不全**：导出最多 10,000 个会话、每会话最多 500 条消息；超出部分既不在归档，也不在 manifest 告警，用户无法察觉。
- **无法分段恢复**：只有单文件单次恢复，不能表达「先恢复基线，再按顺序补日常增量」，也无法在迁移前判断链是否完整。

## 2. 现状证据

- `packages/core/src/backup/export.ts`：`conversationsRepo.list(undefined, 10_000)` 与 `messagesRepo.listByConversation(conv.id, 500)` 构成硬上限；manifest 只记录会话数，不记录消息数、归档 id、类型或父链。
- `packages/database/src/repositories/chat/conversation-repo.ts`：`list()` 使用 `LIMIT ?`；`message-repo.ts` 的 `listByConversation()` 同样 `LIMIT ?`，超出即丢弃。
- `packages/core/src/backup/restore-ops.ts`：会话已存在时直接 `continue`，整段跳过——增量归档中「已有会话的新消息」会被丢掉。
- `packages/core/src/backup/restore-archive.ts`：一次只解包一个缓冲区；`apps/web/src/app/api/backup/precheck/route.ts` 与 `restore/route.ts` 的 `readUploadForm` 只读取单个 `file` 字段。
- `packages/core/src/backup/export.ts`：`manifest.createdAt` 在打包末尾生成，无法作为下一段增量的安全水位下界。
- `apps/web/src/app/api/backup/export/route.ts`：`backup.lastExport` 写入 `settings_kv`，会随设置轨被导出。
- `packages/database/src/meta.ts`：已有 `getMeta/setMeta`，可在不迁移的前提下保存本地备份历史与恢复链状态。

## 3. 可选方案

| 方案 | 内容 | 成本 | 风险 |
|---|---|---|---|
| A. 增量补量包 | `created_at > since` 只带新行；settings/skills 小快照；显式声明不含删除/修改 | 中 | 语义需强提示，用户可能误当克隆 |
| B. 变更日志/软删 | 全表增加删除与更新追踪，增量可完整重放 | 高 | 全表迁移与触发器，冲突策略复杂，易半成品 |
| C. 仅链式恢复 | 全量分段打包，按链顺序恢复 | 低 | 不解决重复导出体积 |
| D. 恢复演练 | 隔离临时库演练恢复 | 中 | 不解决备份体积；留作 v2.35 |
| E. 云托管/自动备份 | 服务端保存归档并定时备份 | 高 | 违背本地优先与「文件不托管」边界 |

## 4. 建议取舍

- P0：先修基线完整性（分页全量、真实计数、超限显式失败），否则增量建立在不可信的基线上。
- P1：A 增量补量包 + 链式预检/恢复；多选归档由前端排序，服务端用 `meta` 链状态做顺序保护。
- P2：备份历史、链时间线、迁移清单。
- Non-Goal：B 删除/修改增量（放入 v2.35 评估）、D 恢复演练（v2.35 候选）、E 云托管（永久关闭）。

## 5. 风险与待决策

1. 增量不含删除与修改是否可接受：建议接受，并在 UI 与迁移文档中明示；全量仍是克隆与迁移的唯一权威。
2. 水位取父段 `startedAt` 还是 `createdAt`：建议取 `startedAt`，宁可重复不可遗漏，重复由主键幂等吸收。
3. 链状态的存储位置：建议放 `meta` 而不是 `settings_kv`，避免随设置轨被导出到其他机器。
4. 链长度与体积上限：建议单段 500MB、单链 20 段，超限要求重新全量；不一次上传多段，逐段恢复。
5. v8 归档兼容：作为单段全量基线；v9 新字段保持可选，旧端按 schema 版本拒绝。
6. 已有会话追加消息：只在增量模式启用，全量恢复保持原「已存在即跳过」语义，需双份回归测试。
