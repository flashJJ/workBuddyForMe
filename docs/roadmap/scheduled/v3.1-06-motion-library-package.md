# 动效库包化：从页面内静态注册表到可注入的内容包

> 状态：**已排期 v3.1（只落地方案 A：运行时内容快照）**；方案 B/C 仍待契约与包边界评审。关联：[项目级插件化预研](./v3.1-05-plugin-architecture.md) 的 S2。正式方案见 [v3.1 方案](../../plan/archive/v3/v3.1/README.md)。
> 记录日期：2026-11-15。

## 1. 问题

角色的姿势、动作、行为目前是 web 功能目录里的静态常量：

```ts
new VrmAnimationRuntime({ poses: POSES, motions: MOTIONS, behaviors: BEHAVIORS })
```

带来三个限制：

- 内容包安装后无法注入新动作，必须改代码发版；
- 动效的解析、校验、归一化与渲染绑在同一个 feature 里，无法单独测试或复用；
- 剧本白名单从静态 import 生成，内容变化后校验快照可能不一致。

## 2. 现状证据

| 项 | 现状 |
|---|---|
| 内容定义 | `POSES / MOTIONS / BEHAVIORS` 为静态注册表 |
| 运行时 | `VrmAnimationRuntime` 构造时直接引用静态表 |
| 剧本校验 | `SCRIPT_PRIMITIVES` 由静态 import 生成 |
| 消费方 | 桌宠、主窗形象栏、舞台共用同一运行时 |
| 包边界 | 全部在 web 应用内，没有独立包的公开入口 |

## 3. 可选方案

| 方案 | 做法 | 改造量 | 收益 | 风险 |
|---|---|---|---|---|
| A 最小 | 运行时构造参数接受 `MotionContent` 快照，默认仍用现有内容 | S | 内容可注入、可测试 | 注册表可变后快照一致性 |
| B 推荐 | A + 抽出 `motion` 内部包（types / registry / loader / default content） | M | 边界清晰、可独立测试、可被内容包消费 | 构建顺序与包体积 |
| C 独立仓库 | 动效库单独建仓并发布 npm 包 | L | 理论可独立迭代 | 契约未冻结，双提交/双发布成本高 |

## 4. 推荐

先做 B，但保持单仓多包：

- `motion` 包只暴露纯数据与纯函数：类型、注册表、动作归一化、轨道过滤、内容校验；
- 渲染适配仍留在 web（VRM/Live2D 各自 adapter），包不依赖 three.js / PIXI；
- 默认内容随包发布，内容包通过 `MotionContent` 注入；
- 一次会话固定一个「内容版本号 + 快照」，校验与生成器读同一份快照。

不拆独立仓库，理由与 05 一致：契约仍在演进，安装包/E2E/性能基线都在主仓；拆仓触发条件满足两条再评估。

## 5. 验收口径

1. 默认内容下现有动效 golden 零差异。
2. 注入只含 1 个姿势的测试包，可播放、可被剧本引用。
3. 禁用内容包后注册表恢复，运行时无残留。
4. `motion` 包不依赖渲染库；web 通过公开入口消费。
5. 单文件 ≤300 行、目录预算与循环依赖门禁不新增例外。

## 6. 风险

| 风险 | 对策 |
|---|---|
| 注册表可变导致校验/生成读到不同快照 | 会话级内容快照 + 版本号 |
| 动效包体积增长 | 惰性加载 + 体积上限 + 只加载被引用条目 |
| 包拆分后类型重复 | 类型只放 `motion` 或 `shared`，渲染层不重复定义 |
| 许可 | 动效数据随主项目许可；第三方动作包单独登记来源 |
