## 1. 问题

v2.18 已交付产物、图表、内容包与证据，但知识库的输入端仍是“文本层”：

- PDF 只按行合并文本，标题/章节/表格/图注结构丢失；
- 分块按段落/长度切，表格被切断，章节上下文进不了 embedding；
- 引用只到页码/段落，无法回答“表 3 第 2 行”；
- 复杂 PDF/合同/财报/扫描件解析失败时只有状态，没有结构预览与错误位置；
- RAG 质量没有可重复评测，解析/提示词改动靠人眼回归。

## 2. 现状证据

- `read-document.ts`：PDF 按 TextItem y/fontSize 合并行；仅 txt/md/pdf/docx/xlsx/pptx。
- `text-structure.ts`：只记录页/段落/字符区间；无章节路径与表格。
- `document_chunks`：v001 只有内容/字符区间，v017 补了 page_no/paragraph_no。
- `Citation`：pageNo/paragraphNo/charStart/charEnd/staticKind；无章节/表/行/单元格。
- `knowledge_entities` + mentions：有实体与提及，无实体关系边。
- `scripts/eval/`：有 Agent/工具评测脚本，但没有 Promptfoo 风格的 RAG 回归门禁。

## 3. 可选方案

| 方案 | 内容 | 取舍 |
|---|---|---|
| A（推荐） | TS/Node 原生扩展解析器 + 结构存储 + 结构分块/引用 + Promptfoo | 复用现有栈；一次迁移；风险可控 |
| B | 内嵌 RAGFlow/LightRAG 服务做解析/图检索 | 解析强，但引入 Python/Go 服务、包体与运维成本高 |
| C | 只做图 RAG，不改解析 | 对复杂 PDF/表格帮助有限，引用仍不可追溯 |
| D | 只做会议/屏幕感知 | 偏离知识库主线，与现有语音/知识链路不连续 |

推荐 A：解析、结构、引用、评测四层一起补齐，不引入重型服务。

## 4. 决策

- 主题：「看得懂文档」——深度文档解析与可信 RAG。
- 范围：P0 + P1 + P2 全做。
- 技术：TS/Node 原生扩展；Promptfoo 仅 devDependency。
- 迁移：允许一次 `v043-document-structure`（chunks 结构列 + document_blocks + knowledge_relations）。
- 引用：Citation 增加可选 sectionPath/tableNo/tableRow/tableCell。
- P2 图检索：实体/关系多跳，不做社区检测。
- 旧文档：默认保留原文本检索，提供手动重建。

## 5. 风险

- PDF 表格启发式准确率与多栏/扫描件；
- 迁移与备份恢复；
- 长文档解析耗时；
- 图关系噪声；
- 视觉模型成本与离线可用性；
- Promptfoo CI 用例成本与稳定性。

详细取舍见 [v2.19 方案 §6](../../plan/v2.19/README.md#6-风险与取舍)。
