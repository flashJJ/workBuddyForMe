# 候选 01：记忆图关系边与空闲整理

> 来源：[v2.26 方案](../../plan/v2.26/README.md) §9、[v2.26 发行说明](../v2.26-release-notes.md)「范围说明」。
> 状态：已排期（v2.31），方案见 [v2.31 方案](../../plan/v2.31/README.md)；社区聚类（方案 B）永久关闭。

## 1. 问题

v2.26 把长期记忆做成了「双时态事实 + 混合召回」，但记忆之间仍是孤立行：

- 只能按 `subject_key` 消解同一主体的新旧冲突，无法表达「张三 → 在 → 某公司」「项目 A → 依赖 → 服务 B」这类关系；
- 召回只取与当前问题相似的记忆，无法沿关系走一跳拿到上下文；
- 写入后没有「空闲整理」：重复事实、同义主体、跨会话的弱关联只能等下次抽取碰运气合并。

## 2. 现状证据

- `memories` 表只有 `subject_key / content / kind`，没有边表（`packages/database/src/migrations/v046-memory-lifecycle.ts`）。
- 检索链路 `memory-recall.ts` 只做向量 + FTS 融合，没有邻居扩展。
- v2.26 方案 §9 明确列为未实现，发行说明「范围说明」重复登记。

## 3. 可选方案

| 方案 | 内容 | 成本 | 风险 |
|---|---|---|---|
| A. 只做关系边 + 一跳注入 | 新表 `memory_edges(from_id, to_id, relation, weight)`；抽取阶段补边；召回时对 top 结果扩 1 跳，最多注入 2 条 | 中 | 边质量依赖抽取，容易产生噪声边 |
| B. 边表 + 社区聚类 | 在 A 之上做社区检测与摘要，形成「主题簇」 | 高 | 聚类参数难调，解释成本高 |
| C. 只做空闲整理 | 不改召回，后台任务把同义/重复记忆合并、补 `subject_key` | 低中 | 收益偏隐性，难验收 |

## 4. 风险

- 图边与既有 `subject_key` 冲突消解职责重叠，需先定义「边」与「版本链」的边界。
- 一跳注入会挤占记忆预算（当前 `MEMORY_TOP_K=3`），必须与 v2.26 的置顶/约束配额一起算。
- 不做图数据库，全部落在 SQLite；规模上限与清理策略需要预先约定。

## 5. 待决策

1. 先做 A 还是先做 C；社区聚类（B）是否永久不做。
2. 边的种类白名单（居住/任职/依赖/偏好于…）与抽取方式（规则优先还是 LLM）。
3. 一跳注入的条数、权重与衰减规则。
4. 是否需要独立的「记忆图谱」可视化入口，还是只在召回理由里体现。
