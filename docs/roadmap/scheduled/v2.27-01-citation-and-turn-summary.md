# v2.27-01 来源方案：引用角标、来源定位与回合运行摘要

> 从 [v2.24 方案](../../plan/v2.24/README.md) §3「待交付（P1）」拆出；正式方案见 [v2.27](../../plan/v2.27/README.md)。
> 状态：已排期（v2.26.0 之后的下一个版本，未启动 M0）。
> 已决策：做引用编号契约 + 行内角标 + 来源分组定位 + 回合摘要 + 抓取失败降级；handoff 泳道列 P2；零迁移。

## 1. 问题

v2.18 开始工具结果就带证据字段，v2.19 的引用带章节/表格坐标，v2.24 把工具过程做成了时间线，但用户读答案时仍然无法回答「这句话哪来的」：

- 正文里的 `[1]` 是纯文本，点不动，也无法对应到底部第几条来源；
- 底部来源卡的编号直接取 `citation.ordinal`（文档内片段序号），知识分片从 0 开始、网页结果从 1 开始，同一列表会出现 `[0]` 与重复编号；
- 来源列表平铺，文档与网页混排，看不出「几条来自知识库、几条来自搜索」；
- 一轮结束只有 token 用量，没有「用了几个工具、花了多久、用没用知识库」的整体交代；
- `fetch_webpage` 失败只给「用浏览器打开」，同一 URL 仍可能被反复重试。

## 2. 现状证据

- `Citation` 已有 `documentId / documentName / ordinal / snippet / sourceUrl / pageNo / sectionPath / tableNo / tableRow / tableCell`，但没有展示用编号（`packages/shared/src/types/domain.ts`）。
- 知识分片引用 `ordinal: chunk.ordinal`（文档内序号，从 0 起）；`web_search` 引用 `ordinal: index + 1`（从 1 起）。
- 系统提示词的资料块按 `[1]…[n]` 连续编号（`packages/core/src/retrieval/context-formatter.ts`），提示词也要求「在回答中给出引用」，但前端不解析正文标记。
- 底部来源卡用 `citation.ordinal` 渲染角标（`apps/web/src/features/chat/message/citations-list.tsx`）。
- v2.24 发行说明「范围说明」明确列出行内引用角标、来源卡片定位、handoff 泳道、回合运行摘要、抓取失败降级未交付。

## 3. 可选方案

| 方案 | 内容 | 成本 | 风险 |
|---|---|---|---|
| A. 只修前端编号 | 前端按列表位置重排 1..n，不改后端 | 低 | 与提示词编号仍不对应，角标点了只能滚到列表，无法定位 |
| B. 编号契约 + 角标 + 分组定位 + 回合摘要 | 装配处输出 `citeIndex`；正文解析 `[n]` 渲染可点角标；来源卡分组；补回合摘要与抓取降级 | 中 | 正文解析边界要小心（代码块/链接） |
| C. 后端引用校验 | 回答落库前校验每个 `[n]` 是否存在并自动补标 | 中高 | 模型不配合时体验反而变差，且要改编排链路 |

## 4. 决策

选 B。`citeIndex` 作为展示派生字段，不落库、不加迁移；旧消息由前端按列表位置兜底编号。C 明确不做——角标是增强，不阻断回答。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 正文解析误伤代码/链接 | 跳过 fenced code、inline code、链接与图片语法；只处理独立 `[n]` / `【n】` |
| 模型不输出 `[n]` | 来源卡保持完整；角标缺失不提示错误 |
| 编号在多路引用合并后错位 | 合并时按去重键重新编号，单测锁定 |
| 组件行数超 300 | 解析、分组、摘要各自独立文件，主组件不膨胀 |
